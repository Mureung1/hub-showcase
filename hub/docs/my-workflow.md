# 나만의 워크플로우 — 수직 슬라이스 개발

4주간 작업(계획, 커밋, 회고)을 돌아보면 매주 같은 순서로 작업했다. 이 문서는 그 반복된 순서를 정리한 것이다.

## 반복해서 사용한 작업 순서: 화면 → API → DB

기능 하나를 완성할 때마다 아래 순서를 따랐다.

1. **정적 화면 먼저** — 목업 데이터로 화면/컴포넌트를 만들고 클릭하면 화면만 넘어가는 수준까지 구현
2. **API 연결** — 화면 뒤에 실제 DB/로직을 붙여 목업 데이터를 실제 데이터로 교체
3. **상태 유지·예외 처리** — 새로고침/에러/빈 값 등 예외 상황까지 다듬기

## 입력 / 작업 순서 / 확인 기준 / 결과물

| 항목 | 내용 |
|---|---|
| 입력 | 백로그의 Task 하나(예: T14), 관련 화면 흐름(IA), design skill.css 토큰 |
| 작업 순서 | 1) 정적 UI 구현 → 2) API/DB 연결 → 3) 상태 유지 + 예외 처리 |
| 확인 기준 | 백엔드 단위 테스트 통과, 실제 배포 환경(또는 로컬)에서 시나리오 직접 재현해 확인 |
| 결과물 | 동작하는 화면 + API + 커밋(Conventional Commits), 필요 시 백로그 상태 갱신 |

## 문제가 생겼을 때 다시 확인할 단계

작업기록에서 실제로 썼던 순서 그대로다.

1. **어떤 오류가 있었는지** 먼저 명확히 적는다 (에러 메시지, 재현 화면)
2. **Agent에게 무엇을 요청했는지** 적는다 — "1번부터 하나씩 같이 해보자"처럼 범위를 좁혀서 요청
3. **어떤 답을 검토하고 적용했는지** 적는다 — 원인 파악 → 1차 수정 → 남은 문제 확인 → 2차 수정 순으로, AI가 준 답을 그대로 쓰지 않고 검토 후 적용
4. **무엇으로 성공을 확인했는지** 적는다 — 테스트 통과 또는 실제 배포 환경에서 직접 재현해 확인
