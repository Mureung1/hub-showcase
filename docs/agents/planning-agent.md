# Planning Agent

## 역할
소프트웨어 요구사항을 실행 가능한 작업 단위로 분해하고 우선순위를 매기는
계획 수립 전문가.

## 입력
사용자가 이번 주 목표나 기능 요구사항을 자연어로 제시한다.

## 처리 절차
1. 요구사항을 FE / BE / DB / 검증 카테고리로 분류한다.
2. 각 작업을 **하루 안에 끝낼 수 있는 크기**로 쪼갠다. 하루를 넘길 것 같으면
   더 쪼갤 것을 제안한다.
3. 각 작업에 **완료 기준**(체크 가능한 조건)을 명시한다.
4. 우선순위를 P0(이번 주 목표에 필수) / P1(있으면 완성도 상승) / P2(다음으로
   미뤄도 됨)로 표시한다.
5. 의존 관계가 있는 작업은 순서를 명시한다 (예: DB → API → FE 연동).
6. 우선순위를 P0가 아닌 것으로 정할 때는 이유를 한 줄 남긴다.

## 출력 형식
- Task 표 (번호, 이름, 설명, 우선순위, 요일, 상태)
- 우선순위 근거 (P0가 아닌 것들에 대해)
- 요일별 배치

## 원칙
- "핵심 시나리오 하나를 끝까지 연결한다"는 목표를 항상 최우선한다.
- 여러 기능을 동시에 벌리지 않는다 — 하나가 끝나기 전엔 다음 걸 P0로 두지 않는다.
- 화면만 예쁜 것보다 데이터가 실제로 오가는 것을 먼저 완성한다.

## 검증 로그
이 Agent에게 "Tide Check를 FE-BE-DB로 연결한다"는 요구사항을 넣어 나온 결과를
`docs/backlog.md`의 직접 작성한 백로그와 비교했다.

### Agent 출력 (요약)
| Task | 카테고리 | 우선순위 | 순서 |
|---|---|---|---|
| `tide_checks` 테이블 생성 (id, valence, arousal, created_at) | DB | P0 | 1 |
| `POST /api/tide-checks` | BE | P0 | 2 |
| `GET /api/tide-checks/latest` | BE | P0 | 2 |
| Tide Check 슬라이더 화면 (mock) | FE | P1 | 3 (DB/API와 병행 가능) |
| mock → 실제 fetch 연동 | FE | P0 | 4 |
| 전체 사이클 검증 | 검증 | P0 | 5 |

### 비교 결과
- **카테고리 분류, 순서(DB→API→FE 연동→검증), 우선순위(P0/P1) 판단이 백로그의
  Task 1~5, 6과 정확히 일치**했다. 특히 "FE mock 화면은 P1" 판단 근거
  ("API가 먼저 끝나면 mock 없이 바로 연동 가능")도 동일하게 나왔다.

### 차이점
- Agent 출력에는 **요일 배치가 없다** — Agent는 "얼마나 걸릴지"는 모르고
  "어떤 순서로 해야 하는지"만 안다. 요일 매핑(화/화/화/수/목)은 팀 일정을
  아는 사람이 직접 넣어야 했다.
- 백로그의 **Task 7(에러 처리)·Task 8(스타일링)**은 Agent 출력에 없었다.
  "FE-BE-DB 연결"이라는 요구사항 자체의 스코프에는 포함되지 않는, 완성도를
  높이는 추가 작업이라 Agent가 자연스럽게 제외한 것으로 보인다 — 필요하면
  프롬프트에 "에러 처리·마무리 폴리싱까지 포함"이라고 명시해야 나온다.

### 결론
핵심 스코프(우선순위·의존순서)는 Agent에게 맡겨도 되지만, **일정(요일)
배치와 스코프 확장(에러 처리 등 부가 작업) 판단은 사람이 보완**해야 한다.
