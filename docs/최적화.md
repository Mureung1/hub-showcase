# 위치 쿼리 최적화 — 현황 분석 · 선택지 비교 · 측정 계획

기준 문서: [기획서.md](./기획서.md) §6(백엔드 하이라이트) · [erd.md](./erd.md)(인덱스 계획) · [task.md](./task.md)(T-15)

이 문서는 **측정 → 개선 → 재측정**의 기록이다. 수치는 T-15(k6)로 실측해 채운다.
추정과 실측을 섞지 않는다 — 실측 전 값은 "추정"으로 명시한다.

## 1. 목적

기획서 §6은 위치 조회를 이렇게 규정한다.

> 먼저 PostGIS / Haversine으로 동작 → Redis GeoSpatial 인덱스를 "최적화 단계"로 도입해 개선 전후 비교(스토리텔링)

즉 이 항목의 목적은 **성능 문제 해결이 아니라 "개선 전후를 증명하는 것"** 이다. 목적이 서사이므로,
"무엇을 도입하느냐"보다 **"측정 가능한 개선을 만들 수 있느냐"** 가 선택 기준이 된다.

전제: 측정 없는 최적화를 하지 않는다. 먼저 느린 것을 증명하고, 고치고, 다시 측정한다.

## 2. 현재 구현

위치 계산은 [server/src/repositories/sql.js](../server/src/repositories/sql.js)의 `haversineKm` 하나를 공유하며,
사용처는 성격이 다른 두 곳이다.

### 2.1 딜 조회 (둘러보기 경로)

[dealRepository.js `findNearby`](../server/src/repositories/dealRepository.js)

```sql
SELECT * FROM (
  SELECT d.*, s.name AS store_name,
         6371 * acos(LEAST(1, ...)) AS distance_km
  FROM deals d JOIN stores s ON s.id = d.store_id
  WHERE d.status = 'active' AND d.pickup_deadline_at > now() AND d.remaining_qty > 0
) nearby
WHERE distance_km <= $3
ORDER BY distance_km ASC
```

활성 딜 **전체**에 삼각함수를 계산한 뒤, 계산 결과로 필터한다.

### 2.2 알림 대상 판정 (팬아웃 경로)

[notificationRepository.js `findTargets`](../server/src/repositories/notificationRepository.js)

```sql
FROM users u
CROSS JOIN deal
LEFT JOIN user_interest_categories ic ON ...
LEFT JOIN favorites f ON ...
WHERE u.role = 'consumer' AND (ic.user_id IS NOT NULL OR f.user_id IS NOT NULL) AND (...)
```

`CROSS JOIN`이므로 **딜 등록 1건마다 전체 소비자 유저 수만큼** 거리 계산이 발생한다.

## 3. 발견 — 인덱스가 있는데 안 쓰인다

[001_init.sql](../server/src/db/migrations/001_init.sql)에 이미 다음이 있다.

```sql
CREATE INDEX idx_stores_lat_lng ON stores (lat, lng);
```

그런데 위 두 쿼리 **모두 이 인덱스를 타지 못한다.** 필터 대상이 `lat`/`lng` 컬럼이 아니라
`acos(...)`로 계산된 `distance_km`이기 때문이다. 계산식에는 B-tree 인덱스가 개입할 수 없다.

즉 현재는 **인덱스를 만들어 두고 놀리는 상태**이며, 두 쿼리 다 풀스캔 + 행마다 삼각함수다.

### 어느 쪽이 먼저 터지나

| 경로 | 스케일 요인 | 호출 빈도 |
|---|---|---|
| 딜 조회 | 활성 딜 수 (마감 임박만이라 상한이 낮음) | 사용자 조회 시 |
| **알림 판정** | **전체 소비자 유저 수** | 딜 등록 시마다 |

**팬아웃 경로가 먼저 터진다.** 유저 10만이면 딜 하나 등록에 10만 번 거리 계산이 돈다.
반면 딜 조회는 "마감 임박 + 활성"이라는 조건 자체가 모수를 억제한다.

## 4. 선택지 비교

| | 방식 | 조회 복잡도 | 도입 비용 | 정합성 리스크 |
|---|---|---|---|---|
| **A. bbox 프리필터** | lat/lng 범위로 1차 컷 후 Haversine 정밀 컷 | `O(log N + K)` | SQL 몇 줄, **인프라 0** | 없음 (동일 트랜잭션) |
| **B. PostGIS** | `geography` + GiST, `ST_DWithin` | `O(log N + K)` | 확장 설치 + 마이그레이션 | 없음 |
| **C. Redis Geo** | `GEOADD` / `GEOSEARCH` (geohash sorted set) | `O(log M + K)` | **별도 서버 + 동기화** | **높음 (이중 쓰기)** |
| **D. geohash 컬럼** | 프리픽스 문자열 인덱싱 | `O(log N + K)` | 중간 | 셀 경계 오차 처리 필요 |

### A. bbox 프리필터

```sql
WHERE s.lat BETWEEN $lat - $dLat AND $lat + $dLat
  AND s.lng BETWEEN $lng - $dLng AND $lng + $dLng   -- dLng는 cos(위도)로 보정
  AND 6371 * acos(...) <= $radius                    -- 사각형 → 원 정밀 컷
```

기존 `idx_stores_lat_lng`가 **비로소 살아난다.** 풀스캔이 인덱스 레인지 스캔이 되고,
비싼 삼각함수는 사각형 안에 든 후보에만 적용된다. 인프라 추가 없음, 정합성 리스크 없음.

주의: 경도 1도의 실제 거리는 위도에 따라 변하므로 `dLng = radius / (111 * cos(lat))` 보정이 필요하다.
보정을 빼먹으면 고위도에서 반경 밖 후보를 놓친다.

### B. PostGIS

`ST_DWithin(geography, geography, meters)`는 GiST 인덱스를 직접 사용하고, 극지·날짜변경선까지 정확하다.
Postgres 내부이므로 트랜잭션 정합성이 공짜다. [erd.md](./erd.md)에 이미 전환 로드맵이 적혀 있다.

주의: `geography`는 WGS84 **회전타원체** 기준이라 현재 Haversine(**구체**)과 결과가 최대 0.5% 정도 다르다.
전후 비교 시 거리 숫자 자체가 미세하게 바뀐다.

### C. Redis GeoSpatial

Redis Geo가 이기는 조건은 **후보군이 매우 크고 지리 조건이 가장 선택적인 필터일 때** — 정확히 팬아웃 경로다.
다만 이 프로젝트에 지금 넣기에는 세 가지가 걸린다.

1. **Redis 단독으로는 질의에 답할 수 없다.** 우리 조건에는 `status`, `pickup_deadline_at`,
   `remaining_qty`, 관심 카테고리, 즐겨찾기 조인이 붙는다. Redis는 후보 ID 집합만 반환하고
   결국 Postgres를 다시 조회해야 한다 — **네트워크 왕복이 하나 늘어난다.**
   후보군이 작으면 이 왕복이 이득을 상쇄한다.
2. **이중 쓰기 정합성.** 가게 좌표 수정·삭제, 유저 기준 주소 변경마다 Redis를 함께 갱신해야 하는데
   Postgres 트랜잭션과 원자적이지 않다. 틀어졌을 때의 리컨실 경로까지 필요하다.
3. **현재 데모 규모(가게 3 / 유저 2)에서는 개선 그래프가 나오지 않는다.** 오히려 왕복 비용 때문에
   느려진 그래프가 나올 수 있다.

참고로 Redis Geo는 geohash 52비트(약 0.6m 오차) + 구체 거리라 Haversine과 결과가 사실상 일치한다.
이 점은 장점 — 전후 비교가 동일 기준으로 이뤄진다.

### D. geohash 컬럼

PostGIS 없이 흉내내는 방식. 프리픽스 길이가 반경을 결정하고, 셀 경계에 걸친 후보를 놓치지 않으려면
인접 8셀을 함께 조회해야 한다. A와 비용은 비슷한데 경계 처리가 더 번거로워 우선순위가 낮다.

## 5. 결정

**Redis GeoSpatial은 Backlog에 유지하고, 최적화 서사는 A(bbox)로 만든다.** 근거:

- 남은 Task가 T-15·T-16뿐이다. Redis는 인프라 + 동기화 + 리컨실이 딸린 작업이라 3주차 리스크가 크다.
- **"인덱스를 만들어 두고도 계산 컬럼으로 필터해 못 타고 있었다 → bbox로 살렸다"** 는 서사가
  "Redis를 붙였다"보다 설득력이 크다. 측정으로 원인을 찾아 최소 비용으로 고친 이야기이기 때문이다.
- T-15에서 만들 k6 스크립트와 대용량 시딩을 **그대로 재사용**할 수 있다. 인프라 하나로 그래프 둘.

따라서 [task.md](./task.md)의 해당 Backlog 항목은 의도가 드러나도록 다음으로 바꾼다.

> 위치 쿼리 최적화 전후 비교 (bbox → 필요 시 PostGIS, Redis Geo는 그 다음)

## 6. 측정 계획 (T-15와 공유)

측정 없이 고치지 않는다. 순서는 다음과 같다.

1. **대용량 시딩** — 가게·소비자 유저를 실측 가능한 규모로 부풀린다(현재 시딩은 데모용 소량).
2. **최적화 전 측정** — `EXPLAIN ANALYZE`로 실행 계획과 시간을 기록한다.
   확인할 것: `Seq Scan` 여부, 실제 소요 시간, 처리 행 수.
3. **bbox 적용** — 딜 조회와 알림 판정 양쪽.
4. **최적화 후 재측정** — 동일 조건. `Index Scan` 전환과 시간 변화를 확인한다.

### 7.3 오버셀 증명 (T-15) — 완료

측정일: 2026-07-27 · k6 v2.1.0 · PostgreSQL 16 (Docker) · 로컬 단일 노드

동일한 k6 스크립트([load/oversell.js](../load/oversell.js))로 서버만 바꿔 실행했다.
비교군은 `UNSAFE_STOCK=1`로 띄워 [decrementStockUnsafe](../server/src/repositories/dealRepository.js)
(읽기 → 판단 → 덮어쓰기)를 타게 하고, 실험군은 기본값인 원자적 조건부 UPDATE를 탄다.

| 시나리오 | 경로 | 201 성공 | 409 품절 | 실제 판매 | **오버셀** | 최종 remaining |
|---|---|---|---|---|---|---|
| 재고 3 · 동시 100 | 락 미적용 | 21 | 79 | 21개 | **+18** | 1 |
| 재고 3 · 동시 100 | **원자적 UPDATE** | **3** | 97 | 3개 | **0** | 0 |
| 재고 5 · 동시 50 | 락 미적용 | 36 | 14 | 36개 | **+31** | 2 |
| 재고 5 · 동시 50 | **원자적 UPDATE** | **5** | 45 | 5개 | **0** | 0 |

판정 근거는 k6 카운터가 아니라 DB 상태다([verifyLoad.js](../server/src/db/verifyLoad.js)).
오버셀은 "성공 응답이 정상적으로 반환됐는데 실제로는 재고보다 많이 팔린" 상태이므로,
응답 집계만으로는 검출되지 않는다.

**가장 중요한 발견 — CHECK 제약은 방어선이 아니다.**

락 미적용 경로에서도 `remaining_qty`는 1, 2로 **양수를 유지**했다. 읽은 값을 기준으로 절대값을 쓰기 때문에
(`SET remaining_qty = 2`) 음수로 내려갈 일이 없고, 따라서 `CHECK (remaining_qty >= 0)`이 한 번도 발동하지 않았다.
DB 제약은 통과, HTTP 응답은 201, 로그는 깨끗한데 재고 3개짜리 상품이 21개 팔렸다.
**오버셀이 에러가 아니라 정상 응답의 얼굴로 조용히 새어 나간다** — 이것이 원자적 UPDATE가 필요한 이유다.

불변식 `남은수량 = 총수량 - Σ(활성 예약 수량)`은 미적용에서 `1 = 3 - 21 = -18`로 깨졌고,
적용에서는 네 항목(오버셀·불변식·음수·픽업코드 중복) 전부 통과했다.

**재현 절차**

```bash
npm run seed -w server && npm run seed:load -w server -- --stock=3 --users=100
k6 run -e VUS=100 load/oversell.js
npm run verify:load -w server
```

비교군은 서버를 `UNSAFE_STOCK=1 node src/index.js` 로 띄운 뒤 같은 명령을 실행한다.

**측정 중 발견한 하네스 결함(수정 완료)**

첫 실행에서 500 응답 2건이 나왔다. 원인은 애플리케이션이 아니라 테스트 코드였다 —
k6가 VU 번호를 그대로 `X-User-Id`로 썼는데, `INSERT ... ON CONFLICT DO NOTHING`도 시퀀스를 소모하므로
재시딩할수록 user id에 구멍이 생겨(57~100 없음, max 206) 존재하지 않는 사용자로 요청이 나갔다.
seedLoad가 실제 id를 `load/fixture.json`으로 내보내고 k6가 그것을 읽도록 고쳤다.
위 표의 수치는 모두 수정 후 동일 하네스로 재측정한 값이다.
