# 사이사이 4주 MVP 개발 계획과 Backlog

## 1. 문서 목적

이 문서는 사이사이 MVP의 4주 전체 로드맵과 실제 개발 backlog를 한곳에서 관리하는 단일 기준 문서다. 주차별 목표, 실행 티켓, 완료 게이트와 후속 범위를 함께 기록한다.

세부 기능 계약은 다음 문서를 기준으로 한다.

- 프론트엔드: `docs/frontend-tasks.md`
- 백엔드: `docs/backend-tasks.md`
- DB: `docs/database-tasks.md`
- 디렉터리 규칙: `docs/directory-structure.md`

## 2. 목표와 확정 범위

4주 안에 같은 건물 또는 가까운 생활권 이웃이 정보 공유, 도움 요청, 공동구매를 경험할 수 있는 공개 데모를 출시한다.

- Frontend: React + Vite, Vercel
- Backend: Express + JavaScript ESM, Render
- Auth/Database: Supabase Auth + Postgres
- 사용자 진입: 미리 준비된 이메일/비밀번호 데모 계정
- 최종 시연 흐름: `로그인 → 커뮤니티 선택 → 게시글·댓글 → 도움 요청·댓글·완료 → 공동구매 생성·참여·마감·채팅 → 나의 활동`

### 포함 범위

- 건물형/블록형 추천 커뮤니티 선택
- 자유게시판과 도와주세요의 글·댓글 목록 및 작성
- 도움 요청 작성자 완료 처리
- 공동구매 생성, 참여, 예상 1인 부담금, 목표 인원 차단, 모집자 수동 마감
- 공동구매 참여자 REST 채팅
- 나의 활동과 사용자·커뮤니티·참여자 권한 분리
- 외부에서 접속 가능한 공개 URL

### 제외 범위

- 회원가입, 비밀번호 재설정, 소셜 로그인
- 댓글 수정·삭제, 대댓글과 게시글 수정·삭제
- 결제·송금·정산 상태, 주문, 에스크로
- 파일 업로드, 푸시 알림, Realtime 채팅
- 리뷰·신고, 차단, 관리자 기능

## 3. 1주차 완료와 현재 기준선

상태: **완료**

- 1주차 기획, 디자인, 프로토타입과 task 문서 정리는 완료됐다.
- 문제 정의, 대학생·1인 가구 중심 타깃과 건물형/블록형 커뮤니티 단위를 확정했다.
- 공동구매는 서비스 내 결제 없이 모집·참여·예상 부담금·분배 조율만 제공하기로 했다.
- 프론트, 백엔드, DB의 상태값과 API·데이터 계약을 확정했다.
- 기능 중심 디렉터리 구조와 문서 우선순위를 정리했다.
- React 앱은 소개형 화면만 있고 실제 로그인, 탭, 게시글, 공동구매 기능은 없다.
- `server/`와 `supabase/`는 디렉터리 골격만 있고 실행 코드, migration, API가 없다.

1주차 산출물:

- `docs/product-plan.md`
- `docs/design.md`
- `docs/directory-structure.md`
- `docs/frontend-tasks.md`
- `docs/backend-tasks.md`
- `docs/database-tasks.md`
- `prototype/`

## 4. 운영 규칙

### 상태 표시

- `[ ]`: 시작 전
- `[-]`: 진행 중
- `[x]`: 완료
- `[!]`: 차단됨. 원인과 해제 조건을 항목 아래 기록한다.

### 우선순위

- `P0`: 공개 데모 출시를 위해 반드시 완료
- `P1`: P0 완료 후 반영하는 품질 개선
- `P2`: 4주 이후 backlog

### 공통 완료 조건

- 코드와 문서가 현재 디렉터리 구조 및 API 계약과 일치한다.
- 사용자에게 보이는 화면은 loading, empty, error 상태를 가진다.
- 코드 변경은 `npm run lint`를 통과한다.
- 동작이나 번들에 영향이 있으면 `npm run build`를 통과한다.
- 비밀번호, access token, service role, 사용자 주소를 저장소와 로그에 남기지 않는다.

핵심 의존 순서는 다음과 같다.

```text
프론트 기반·Mock 계약
  → 핵심 화면 전체 구현
  → Supabase schema·RLS·RPC
  → Express API
  → Http repository 통합
  → Vercel·Render·Supabase 배포
  → 공개 URL E2E 검증
```

## 6. 2주차 — 프론트엔드

선행 조건: 없음

## 7. 3주차 — 백엔드·DB 통합

### 주차 목표

Supabase RLS와 원자적 RPC로 데이터 경계를 강제하고 Express API를 통해 프론트를 실제 데이터에 연결한다.

### W3-01. Supabase 프로젝트와 migration 기반 `P0`

선행 조건: 2주차 종료 게이트

- [ ] `supabase init`으로 `supabase/config.toml`을 생성한다.
- [ ] profiles, communities, memberships migration을 작성한다.
- [ ] posts, help_requests, comments migration을 작성한다.
- [ ] group_buys, participants, messages migration을 작성한다.
- [ ] FK, CHECK, unique, partial unique index와 `updated_at` trigger를 추가한다.
- [ ] `supabase db reset`으로 빈 로컬 DB 재현을 확인한다.

완료 기준:

- migration만으로 같은 schema를 반복 생성할 수 있다.
- 댓글은 게시글 또는 도움 요청 중 정확히 하나의 부모만 가진다.
- 사용자당 active membership은 하나만 허용된다.

### W3-02. RLS와 원자적 RPC `P0`

선행 조건: W3-01

- [ ] 모든 핵심 테이블의 RLS를 활성화하고 기본 거부를 적용한다.
- [ ] 같은 커뮤니티 게시글·도움·댓글 조회/작성 정책을 만든다.
- [ ] 참여자 전용 채팅 정책을 만든다.
- [ ] `switch_active_community` 함수를 만든다.
- [ ] `create_group_buy`가 모집과 host 참여를 한 transaction에서 생성하게 한다.
- [ ] `join_group_buy`가 row lock 후 정원·중복·기한·상태를 검사하게 한다.
- [ ] `security definer` 함수의 `search_path`와 execute 권한을 제한한다.

완료 기준:

- 사용자 JWT 기반 테스트에서 다른 커뮤니티 데이터가 차단된다.
- 동시 참여 요청에도 목표 인원을 초과하지 않는다.
- service role 없이 일반 사용자 흐름이 동작한다.

### W3-03. 데모 계정과 seed `P0`

선행 조건: W3-01, W3-02

- [ ] `supabase/seed.sql`에 Auth가 필요 없는 기준 데이터를 작성한다.
- [ ] `scripts/seed-demo.mjs`에 Auth 데모 계정 생성과 샘플 데이터 upsert를 구현한다.
- [ ] 사용자 최소 3명과 건물형·블록형 커뮤니티를 준비한다.
- [ ] 게시글·댓글, open/resolved 도움 요청, 미달·정원 도달·마감 공동구매와 채팅을 준비한다.
- [ ] 비밀번호는 환경 변수로만 받는다.
- [ ] seed 반복 실행 시 중복 데이터가 생기지 않게 한다.

완료 기준:

- 한 명은 host, 한 명은 같은 커뮤니티 member, 한 명은 다른 커뮤니티 사용자 시나리오를 재현한다.
- seed 실행 로그와 저장소에 비밀번호와 service role이 남지 않는다.

### W3-04. Express 기반과 인증·커뮤니티 API `P0`

선행 조건: W3-01

- [ ] Express, Supabase JS, Zod, 보안·로그·테스트 의존성을 추가한다.
- [ ] `app.js`, `server.js`, 환경 변수 검증과 `/health`를 구현한다.
- [ ] Helmet, CORS allowlist, JSON 크기 제한, rate limit, 404, 공통 오류 처리를 만든다.

## 9. 최종 시연 시나리오

1. 사용자 A가 건물형 커뮤니티에 입장해 게시글과 댓글을 작성한다.
2. 사용자 B가 같은 커뮤니티에서 도움 요청에 댓글을 남기고, 작성자만 완료 처리한다.
3. 사용자 A가 공동구매를 만들면 자동으로 host 참여자가 된다.
4. 사용자 B가 참여하면 참여 인원과 예상 부담금이 갱신된다.
5. 목표 인원 도달 후 추가 참여는 차단되지만 host가 마감하기 전까지 상태는 `open`이다.
6. 참여자는 채팅을 이용하고 비참여자와 다른 커뮤니티 사용자는 접근하지 못한다.
7. 각 사용자의 나의 활동에는 본인의 글, 도움 요청과 공동구매 역할만 표시된다.

## 12. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 2주차 UI 범위 과다 | 장식보다 전체 Mock 흐름을 먼저 완성하고 P1을 뒤로 미룬다. |
