## 2. 목표와 성공 조건

### 목표

신규 사용자가 직접 가입하고 주소에 따라 커뮤니티에 자동 배정된 뒤 자유게시판, 도와주세요, 공동구매와 각 채팅을 사용할 수 있는 공개 MVP를 출시한다.

### 필수 기능

1. 이메일/비밀번호 회원가입, 로그인, 로그아웃, 세션 복원
2. 주거 유형 선택, Kakao 주소 검색, 건물 동/H3 기반 커뮤니티 자동 배정
3. 자유게시판 글·댓글 목록과 작성
4. 도와주세요 글·댓글, 작성자 완료, 댓글 작성자와 1:1 채팅
5. 공동구매 생성·참여, 목표 인원 도달 후 모집자 확정, 확정 참여자 그룹 채팅

### 출시 성공 조건

- Vercel 공개 URL에서 신규 사용자 A와 B가 같은 커뮤니티에 가입해 전체 기능을 실행할 수 있다.
- 사용자 C는 다른 커뮤니티 데이터와 A/B의 채팅을 조회하거나 작성할 수 없다.
- 도움 요청은 작성자만 완료하고, 공동구매는 모집자만 확정한다.
- 확정 전 공동구매 채팅방은 존재하지 않고, 확정 시 한 번만 생성된다.
- 주소 원문과 좌표, 비밀번호, access token, service role key가 저장소와 서버 로그에 남지 않는다.
- `npm run lint`, `npm run build`, `npm run test:api`와 RLS/RPC 테스트가 통과한다.

## 3. 확정 계약

### 인증

- Supabase 이메일/비밀번호 Auth를 사용한다.
- 이메일 확인은 비활성화하고 가입 직후 세션을 발급한다.
- 비밀번호는 8~72자, 닉네임은 2~20자로 제한한다.
- 비밀번호 재설정, 소셜 로그인, 별도 logout API는 만들지 않는다.

### 커뮤니티 자동 배정

- 주거 유형은 `apartment_officetel | house_villa` 두 값만 사용한다.
- 인증 사용자가 `GET /api/v1/addresses/search?q=<query>`로 Kakao 주소를 검색한다.
- 아파트·오피스텔은 `정규화 도로명 주소 + 건물명 + 동 번호`의 SHA-256 해시를 커뮤니티 키로 사용한다.
- 주택·빌라는 검색 결과 좌표를 H3 해상도 9 셀로 변환해 커뮤니티 키로 사용한다.
- `POST /api/v1/onboarding/complete`가 프로필 갱신, 커뮤니티 upsert, 기존 active membership 종료, 새 membership 생성을 한 transaction에서 수행한다.
- 추천 후보 선택 화면은 만들지 않는다. 주소 선택 후 서버가 결정한 커뮤니티에 즉시 가입한다.
- 주소 원문과 좌표는 배정 계산 후 저장하지 않는다.

### 도움 요청과 채팅

- 도움 요청 상태는 `open | resolved`다.
- 작성자만 `open → resolved`로 전환할 수 있다.
- 글쓴이는 댓글 작성자 옆 `채팅하기`로 요청별 1:1 방을 만든다.
- 댓글을 작성하지 않은 사용자와는 방을 만들 수 없다.
- 완료된 요청은 글·댓글·채팅 기록만 읽을 수 있고 새 댓글, 새 방, 새 메시지는 작성할 수 없다.

### 공동구매와 채팅

- 공동구매 상태는 `recruiting | confirmed`다.
- 생성자는 host 참여자로 자동 등록된다.
- 목표 인원은 2~50명, 총액은 1~100,000,000원 정수, 마감은 현재부터 10분 이후~30일 이내다.
- 목표 인원 도달과 마감 전이라는 두 조건이 모두 참일 때만 모집자가 확정할 수 있다.
- 확정 transaction에서 상태 변경, 그룹 채팅 생성, 현재 참여자의 채팅 멤버 등록을 함께 수행한다.
- 확정 전 채팅 진입과 확정 후 추가 참여·참여 취소는 허용하지 않는다.
- 예상 부담금은 저장하지 않고 `ceil(totalAmount / participantCount)`로 계산한다.

### 채팅 전송

- 도움 1:1과 공동구매 그룹 채팅은 공통 conversations/messages 모델을 사용한다.
- 채팅 유형은 `help_direct | group_buy`다.
- 메시지는 1~1,000자이며 수정·삭제할 수 없다.
- 활성 채팅 화면은 3초마다 cursor 이후 메시지를 REST polling한다.
- 화면 이탈, 브라우저 탭 숨김, 로그아웃 시 polling을 중단한다.

## 4. 우선순위

- **Must**: 위 다섯 필수 기능, 인증·RLS·데이터 격리, 공개 배포
- **Should**: 없음. 15일 일정에서는 별도 품질 기능을 추가하지 않는다.
- **Could**: 없음. Must 완료 전 신규 제안을 받지 않는다.
- **Won't**: 8절의 제외 범위 전체

## 7. 병렬 작업 규칙

- Frontend 작업자는 `src/`, Backend/DB 작업자는 `server/`와 `supabase/`, QA 작업자는 테스트와 수동 시나리오를 담당한다.
- 루트 `package.json`, 환경 변수 계약과 API 응답 계약은 통합 담당자만 수정한다.
- 같은 파일을 두 작업자가 동시에 수정하지 않는다.
- 매일 통합 후 `npm run lint`와 `npm run build`를 실행한다.
- 7월 30일부터 신규 기능과 시각 장식을 추가하지 않고 테스트 실패와 출시 차단 오류만 수정한다.

- 이미지 업로드와 이미지 URL

- 공동구매 참여 취소, 모집 취소, 완료 상태, 결제·송금·정산
- Realtime/WebSocket, 읽음 표시, 입력 중 표시, 파일 첨부
- 푸시 알림, 리뷰·신고, 차단, 관리자 기능
- React Router와 외부 UI 라이브러리

## 9. 위험과 고정 대응

| 위험 | 고정 대응 |
|---|---|
| Kakao API 실패 | 오류와 재시도 UI를 표시하며 가짜 주소나 임의 커뮤니티를 사용하지 않는다. |
| Render cold start | 첫 요청 실패 화면에서 동일 요청을 재시도할 수 있게 한다. |
| 일정 지연 | 시각 장식은 추가하지 않고 Must 오류를 먼저 해결한다. 필수 기능은 제거하지 않는다. |
| RLS 오류 | service role이 아니라 사용자 JWT A/B/C로 성공·차단 시나리오를 검증한다. |
| 공동구매 동시 참여 | 앱 사전 검사에 의존하지 않고 row lock RPC로 목표 인원을 보장한다. |
| 채팅 중복 polling | 화면 이탈과 탭 숨김 시 요청을 중단하고 메시지 ID로 중복 제거한다. |
