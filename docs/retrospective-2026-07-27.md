# 개인 회고 — 2026.07.27 (과목 완료 체크 기능)

오늘 한 일: 설계만 해두고 미뤄뒀던 과목 완료 체크 기능(슬라이스 1)을 구현하고,
첫 배포 준비 상태를 점검했다. 커밋 1개, PR 1개(#2033).

## 잘한 일

**1. 코드부터 짜지 않고 설계 문서를 먼저 읽었다.**
`docs/feature-completion-history.md`에 "슬라이스 1은 여기까지"라고 적어둔 덕분에 범위를
정할 때 고민할 게 없었다. 구현하다 보니 히스토리 화면도 같이 만들고 싶었는데, 문서에
선을 그어놨으니 참을 수 있었다. 설계할 때 미래의 나를 위해 범위를 적어두는 게 실제로 효과가 있었다.

**2. "고쳤다"에서 멈추지 않고 "동작한다"까지 확인했다.**
완료 버튼을 눌러 목록에서 사라진 걸 보고 끝낼 수도 있었지만, 그건 화면만 바뀐 거지
저장됐다는 증거가 아니다. `PATCH → 200` 확인 → 새로고침 → 재조회 응답에서 빠진 것 확인 →
`?status=done`에 `completedAt` 값이 남아있는 것까지 봤다.
시작할 때 완료 기준을 **"새로고침해도 유지되면 완료"**로 정해둔 게 도움이 됐다.

**3. 성공 경로만 보지 않았다.**
`?status=bogus`처럼 잘못된 값을 넣었을 때 400과 안내 메시지가 나오는지도 확인했다.
잘 되는 경우만 눌러보고 끝내면 놓쳤을 부분이다.

**4. 지난주에 한 번 데인 함정을 미리 처리했다.**
`CREATE TABLE IF NOT EXISTS`는 이미 만들어진 DB 파일에 컬럼을 추가해주지 않는다.
지난주에 겪고 회고에 적어둔 덕분에 이번엔 처음부터 `CREATE TABLE` 쪽과 `ALTER TABLE` 쪽을
양쪽 다 손봤다. 같은 실수를 두 번 하지 않았다.

**5. 되돌리기 어려운 작업은 먼저 확인받고 실행했다.**
push와 PR 등록은 공개되는 작업이라 바로 하지 않고 확인을 받은 뒤에 했다.

## 아쉬운 일

**1. 새로 만든 서버 코드에 테스트가 하나도 없다.**
`completeSubject`, `status` 필터 전부 테스트 0개다. 확인해보니 서버 쪽엔 테스트 파일 자체가
없었다. 통과했다고 적은 22개는 전부 프론트엔드 순수 함수 테스트고, 오늘 새로 짠 코드는
한 줄도 안 덮는다. **3주차에 `write-test` Skill까지 만들어놓고 정작 오늘은 안 썼다.**
브라우저로 눈으로 본 걸로 대체했는데, 눈으로 본 건 다음에 코드가 깨질 때 아무것도 막아주지 못한다.

**2. 만들어둔 검증 에이전트를 안 썼다.**
`feature-verifier`는 지난번에 내가 짠 테스트가 놓친 경계 케이스(`completedAt`이 빈 문자열일 때)를
실제로 찾아줬던 도구다. 오늘은 쓸 생각을 아예 못 했다. 도구를 만드는 것과 습관으로 만드는 건 다른 일이다.

**3. 문서를 갱신하지 않았다.**
`docs/data-model.md`에 `completed_at` 컬럼이 없다. 지난 커밋들을 보면 컬럼을 추가할 때마다
"docs: 데이터 모델에 ~ 반영"을 세트로 했는데 오늘은 빠뜨렸다. 내가 만들어둔 패턴을 내가 안 지켰다.

**4. 경고를 고치지 않고 껐다.**
`App.jsx`에서 `eslint-disable-next-line react-hooks/exhaustive-deps` 주석을 달았다.
`activeSubjects`를 렌더링 중에 계산하다 보니 의존성 배열에 넣을 수 없었던 건데,
**원인을 해결한 게 아니라 경고만 안 보이게 한 것**이다. 지금은 동작하지만 나중에 이 부분을
건드릴 사람(아마 나)이 왜 껐는지 모를 것이다.

**5. 미뤄둔 숙제를 이번에도 미뤘다.**
우선순위 계산 로직이 클라이언트와 서버에 중복돼 있는 문제를 3주차 회고에 "다음에 이어갈 것"으로
적어놓고 이번에도 그냥 넘어갔다. 계산식이 한쪽만 바뀌면 같은 입력에 다른 점수가 나올 수 있는데,
"나중에"라고 적어두는 것만으로는 아무 일도 일어나지 않는다는 걸 확인했다.

## 다음에 다시 한다면

**1. 서버 로직도 테스트부터 짜고 시작한다.**
`completeSubject` 같은 상태 변경 함수는 "없는 id를 주면 null" 같은 경계가 명확해서 오히려
테스트하기 좋다. 프론트에만 적용하던 `write-test` Skill을 서버에도 쓴다.
브라우저 확인은 테스트를 대신하는 게 아니라 테스트 위에 얹는 것이다.

**2. 내가 확인하기 전에 검증 에이전트를 먼저 돌린다.**
내가 짠 코드를 내가 확인하면 잘 되는 경로만 눌러보게 된다. 구현 직후 `feature-verifier`를
돌리는 걸 순서에 고정해서, 쓸지 말지 매번 판단하지 않게 만든다.

**3. 데이터 모델이 바뀌는 작업은 문서 갱신을 같은 커밋에 묶는다.**
컬럼을 추가했으면 `data-model.md`도 그 작업의 일부다. 별도 할 일로 두면 오늘처럼 잊는다.

**4. 경고는 끄기 전에 왜 나는지 한 번 더 본다.**
`exhaustive-deps`는 `useMemo`로 감싸면 주석 없이 정직하게 풀린다.
끄는 게 더 빠르지만, 빠른 게 맞는 건 아니었다.

**5. "다음에 할 것"은 회고에 적지 말고 이슈로 만든다.**
문서에 적어둔 항목은 두 번 연속 그냥 넘어갔다. 이슈로 등록해서 크기와 순서를 정해야
실제로 손에 잡힌다. 중복 계산 로직 정리부터 이렇게 해본다.

`write-test` Skill도 `feature-verifier` 에이전트도 이미 있었는데, 오늘은 둘 다 안 썼다.
