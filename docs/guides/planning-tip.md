# 기획하기 with AI

## 1. 기획이 먼저인 이유

- 기획은 "무엇을 만들지" 결정하는 단계다.
- 기획이 흐려지면 구현 내내 혼란이 생긴다.
- AI는 맥락이 있어야 제대로 결과물을 만든다.
- 기획서는 AI에게 전달할 맥락의 원천이다.
- 기획 없이 바로 구현을 요청하면 AI가 기획까지 임의로 해버릴 수 있다.
- 우리는 전문 기획자까지는 아니어도, "문제 → 기능"의 최소 흐름은 직접 잡아야 한다.

## 2. 기획 과정: 문제에서 기능까지

기획은 넓게 시작해서 좁혀 나가는 방향으로 진행한다.

1. 문제 발견: 어떤 불편이나 니즈가 있는지 관찰에서 출발한다.
2. 문제 정의: 누가, 어떤 상황에서, 무슨 불편을 겪는지 한 문장으로 정리한다.
3. 사용자 시나리오: 사용자가 서비스를 어떻게 쓰는지 흐름으로 적는다.
4. 핵심 기능 도출: 시나리오를 굴리는 데 꼭 필요한 기능만 뽑는다.
5. 우선순위와 MVP: 핵심 기능 2~3개로 좁힌다.

```text
문제 발견
→ 문제 정의
→ 사용자 시나리오
→ 핵심 기능 도출
→ 우선순위/MVP 결정
```

## 3. 문제 정의 잘 쓰기

### 3.1 올바른 문제 정의

문제 정의는 모든 기획의 시작점이다. 여기서 문제가 흔들리면 기획도 흔들린다.

공식:

```text
[누가] [어떤 상황에서] [무슨 불편]을 겪는다
```

나쁜 예:

```text
스터디 관리 앱을 만든다.
```

이 문장은 해결책이지 문제가 아니다.

좋은 예:

```text
스터디원이 출석을 수기로 적다가 자주 빠뜨린다.
```

문제 정의에는 해결책을 넣지 않는다.

### 3.2 문제 정의하기

하려는 서비스의 문제를 직접 정의해본다.

## 4. 사용자 시나리오 쓰기

### 4.1 사용자 시나리오

사용자가 목적을 이루는 과정을 화면과 동작 중심으로 순서대로 적는다.

예시:

1. 모임이 시작된다.
2. 오늘 온 사람을 출석 체크한다.
3. 누가 빠졌는지 한눈에 본다.
4. 지난 기록도 확인한다.

시나리오를 적으면 필요한 화면과 기능이 자연스럽게 보인다.

### 4.2 사용자 시나리오 작성하기

핵심 사용자 시나리오를 작성해본다.

## 5. 기획은 글보다 그림으로 시각화하기

기획을 Markdown 텍스트로만 두지 않는다. 시각화하면 빠진 화면과 단계가 더 잘 드러난다.

### 5.1 왜 시각화하나

- 글만 있으면 흐름이 머릿속에만 남아 빠진 단계를 발견하기 어렵다.
- 사람마다 같은 텍스트를 보고 다른 화면을 상상할 수 있다.
- 화면과 이동을 그리면 "이 화면 다음에는 무엇이 필요한가?"라는 질문이 자연스럽게 생긴다.
- AI에게도 그림이나 흐름을 주면 화면 구현이 더 정확해진다.

### 5.2 무엇을 시각화하나

- 화면 흐름(User Flow): 화면 → 동작 → 다음 화면
- 화면 목록(IA): 어떤 화면들이 필요한지 정리
- 와이어프레임: 화면 안에 어떤 요소가 들어가는지 대략적으로 표현

### 5.3 도구

- 손그림
- Excalidraw
- Figma
- Mermaid

예쁘게 만드는 것이 목표가 아니라, 흐름이 보이게 만드는 것이 목표다.

AI 활용 예시:

```text
이 사용자 흐름을 mermaid 플로우차트로 그려줘.
```

### 5.4 시각화 해보기

주요 흐름을 시각화해서 표현해본다. 손그림으로 시작해도 되고, AI에게 전달해 더 정돈된 형태로 바꿔도 된다.

## 6. AI를 기획 파트너로 활용하기

AI는 기획을 대신 결정하는 도구가 아니라, 기획을 함께 점검하고 확장하는 파트너로 사용한다.

활용 예시:

- 질문받기: "이 기획에서 빠진 관점이나 엣지케이스를 물어봐줘."
- 발산 돕기: "비슷한 서비스는 보통 어떤 기능을 갖는지 10개 나열해줘."
- 압축 돕기: "이 기능들 중 핵심 2개만 고른다면 무엇인지 이유와 함께 알려줘."

단, 정리와 결정은 내가 해야 한다. AI 답변을 그대로 두지 말고 내 말로 다시 정리한다.

산출물:

- 기획서: repository 안의 Markdown 문서
- 시각자료: Mermaid, Excalidraw, Figma 등
- 보조자료: Wiki, Notion 링크
- README에 핵심 내용 표현

## 7. 좁히기: 핵심 기능 2개

기능 욕심은 기본값이다. 의식적으로 줄여야 한다.

기능을 넓게 펼치면 모든 기능이 얕아진다. 핵심 기능은 2개까지로 좁히는 것을 추천한다.

고르는 기준:

- 필수성: 이 기능이 없으면 서비스가 돌아가지 않는가?
- 적합성: 문제 정의를 정확히 해결하는가?

## 8. 기획서에서 작업 분해까지

### 8.1 기획서 구조

위치:

```text
docs/plan.md
```

기본 구조:

```md
## 문제 정의

<누가 / 어떤 상황 / 무슨 불편 — 한 문장>

## 사용자 시나리오

1. ...
2. ...

## 핵심 기능 (2개)

- 기능 A
- 기능 B

## 화면 흐름

- 그림 링크 또는 mermaid
```

PPT, Figma 등 시각화 도구를 함께 사용해도 된다.

### 8.2 작업 분해

위치:

```text
docs/checklist.md
```

확정한 기능을 보고 내가 직접 작업 단위로 쪼갠다. 작업 단위가 작을수록 AI에게 맡기기 쉽고, 내가 검증하기도 쉽다.

예시:

```md
## 1주차

- [ ] 헤더: 로고, 날짜
- [ ] 출석 카드 컴포넌트
- [ ] 출석 목록: 카드 나열
- [ ] 출석 체크 토글
- [ ] 출석 현황 표시
```

덩어리가 크면 AI도 실패하고 나도 검증하기 어렵다. 잘게 쪼갤수록 성공률이 올라간다.

## 9. 미션과 점검

### 9.1 미션

- 문제 정의 한 문장 작성
  - 누가, 어떤 상황, 어떤 불편을 겪는지 쓴다.
  - 해결책을 쓰지 않는다.
- 사용자 시나리오 4~6줄 작성
- 사용자 흐름을 그림으로 표현
  - 손그림, Excalidraw, Mermaid 등 사용 가능
- 핵심 기능 2개 확정

### 9.2 점검: 설명할 수 있나?

- 내 서비스가 푸는 문제를 한 문장으로 설명할 수 있는가?
  - 해결책이 아니라 문제로 설명해야 한다.
- 핵심 기능을 왜 그 2개로 골랐는가?
- 사용자 흐름에서 빠진 화면은 없는가?
  - 그림으로 확인한다.
