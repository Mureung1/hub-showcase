# 답냥이

## 한 줄 소개
매번 맥락을 설명하지 않아도, 대학생이 자주 겪는 꺼내기 어려운 메시지 상황에서 몇 번의 빠른 답변만으로 상황과 관계에 맞는 보낼 말을 받을 수 있는, **관계별 냥이 조력자가 대화로 안내하는** 메시지 작성 도우미 서비스.

## 현재 단계
MVP 구현 단계. 범위는 docs/MVP.md, 주차별 계획은 docs/PLAN.md, 현재 내부 진단은 docs/PRODUCT_REVIEW.md를 따른다. 이 문서의 피드백 루프·예시 DB 누적 등 이후 단계 기능은 여전히 비전 기술이며 이번 단계에서 구현하지 않는다. 변경 이력·근거는 docs/LOG.md 참고.

## 대상 사용자
- 대학생

## 해결하려는 문제 & 가치

### 문제
대학생은 일상에서 반복적으로 꺼내기 어려운 메시지 상황을 마주친다. 받은 메시지에 답할 때뿐 아니라, 먼저 말을 꺼내야 할 때가 오히려 더 어렵다.
- 팀플·조모임에서 무임승차 팀원에게 먼저 꺼낼 말
- 교수님·조교님께 보내는 과제 연장/결석 사유 메일
- 선배·동기 간 존댓말 수위 조절
- 친구·연인에게 꺼내기 어려운 말 (사과·부탁·마음 표현)
매번 무슨 말을 어떻게 써야 할지 고민하느라 시간과 감정 에너지를 쓴다.

### 기존 대안의 한계
ChatGPT 같은 일반 AI 챗봇으로도 보낼 메시지를 받을 수 있지만:
- 매번 상황 맥락(누구와의 대화인지, 어떤 일이 있었는지 등)을 처음부터 설명해야 한다.
- 메모리·커스텀 지시 기능으로 재설명을 일부 줄일 수 있으나, 자유 대화형 입력은 상황을 글로 정리하는 비용이 남는다.
- 일반 챗봇은 답냥이가 정한 대학생 관계 taxonomy, 관계별 톤 기준, 전송 가능성·사실 충실성 검수 절차를 기본 제공하지 않는다.

위 차이는 현재 **제품 가설**이다. AI 글쓰기·추천 UI·관계 영향·한국어 공손성의 간접 근거와 일반화 한계는 [문헌 기반 제품·검수 근거](RESEARCH_REVIEW.md)를 따르며, 범용 AI 대비 실제 선택 우위로 표현하지 않는다.

### 가치
- **검수 기준을 가진 예시 기반**: 팀 작성 예시를 톤 정렬·전송 가능성·사실 충실성 기준으로 검수해 사용한다. 완료 상태는 CHECKLIST T16·T25를 따르며, 실제 효과 피드백 검증은 MVP 이후다.
- **입력 비용 최소화**: 대학생 특유의 반복 시나리오를 카드와 카드별 핵심 질문 1개로 구조화해, 맥락을 글로 설명하지 않고도 3~4번의 선택으로 보낼 말을 받는다.
- **가이드형 대화**: 빈 입력창에서 시작하지 않고 냥이의 짧은 질문과 빠른 답변으로 방식·관계·상황·핵심 의도를 좁힌다. 화면은 대화형이지만 질문과 option은 검수 카탈로그의 결정적 상태 전이이며 자유 대화형 챗봇이 아니다.
- **비교·선택**: 메시지를 대신 써주는 데서 그치지 않고, 사용자가 꺼내기 어려운 말을 톤이 다른 여러 표현으로 제시해 직접 비교하고 선택하게 돕는다.

## 핵심 기능

| 기능 | 설명 |
|---|---|
| 시나리오 선택 | 대학생 특화 관계·상황 4가지를 카드 형태로 제시 |
| 상황 카드 선택 | 시나리오당 6장(공통 5 + 특화 1)을 선택한 뒤 카드별 핵심 질문 1개에 답해 guided AI 세 톤을 생성 — S2 기본 화면 |
| 바로 기본 초안 | 질문 화면에서 `질문 없이 바로 초안 보기`를 선택하면 API 없이 같은 카드의 준비된 정적 초안을 표시. AI 실패 fallback·품질 기준선 역할도 함께 담당 |
| 교수 연락 형식 | 교수·조교 관계에서 메신저/이메일을 먼저 선택. 이메일은 습니다체 고정 전용 6상황과 신원·용건 안내 입력 뒤 제목+본문 정적 3후보 제공 — 실제 발송·AI 이메일 생성은 제외 |
| 목적 선택 | 부탁·사과·거절·질문·제안확인·기타 6종 중 1개 필수 선택 — **"내 상황을 직접 설명하기"**를 눌렀을 때만 등장하는 manual AI 경로 전용 |
| 톤 결과 | 톤을 미리 고르지 않는다. 후보 3개를 톤 3단계(기본 / 더 부드럽게 / 더 분명하게)로 생성해 **가장 무난한 "기본"을 먼저** 보여주고, 사용자가 결과 실물을 보고 고른다 |
| 상황 입력 | **답장/먼저 연락 여부를 화면(S0)에서 먼저 선택**. 상황 카드가 안 맞으면 "직접 설명할게요"를 눌러 모드별 필드 입력 — 답장: "받은 메시지 붙여넣기"(필수) + "상황 설명"(선택), 먼저 연락: "상황 설명"(필수)만 |
| 보낼 말 생성 | **하이브리드**: 카드+핵심 답변 = guided AI, `질문 없이 바로 초안 보기` = 결정적 템플릿, `내 상황을 직접 설명하기` = manual AI. AI는 구조화 출력 1회, 템플릿은 즉시 응답·장애 fallback·평가 기준선이다 (SPEC 2장). T25·T21 합격 전에는 검수 완료로 표현하지 않는다 |
| 결과 복사 | 생성된 보낼 말을 바로 복사해 사용 |
| 관계별 냥이 캐릭터 | 제공 에셋을 Three.js + React Three Fiber 단일 Canvas의 2.5D 캐릭터로 표현하고 단계 상태에 짧게 반응. reduced-motion·WebGL 실패는 정적 이미지로 대체 |
| 피드백 수집 | 보낸 말의 효과 여부를 평가해 예시 데이터베이스 개선에 반영 (이후 단계 — MVP 미구현) |

### 톤 3단계 — 공통 라벨 (확정본은 docs/SPEC.md 1장)

라벨은 전 시나리오 공통 **기본 / 더 부드럽게 / 더 분명하게**이며 기본을 첫 번째로 제시한다. 라벨은 같아도 "부드러움/분명함"의 구현은 관계마다 다르다 — 시나리오별 해석 지침:

세 톤은 입력·카드가 준 사실과 핵심 화행을 바꾸지 않는다. 화행·사실 규칙이 관계별 스타일보다 우선하며, 더 분명한 안도 없는 기한·감정·책임·약속을 추가하거나 상대 선택권을 제거하지 않는다.

| 시나리오 | 더 부드럽게 | 더 분명하게 |
|---|---|---|
| 팀플·조모임 | 상대 사정·협업 여지를 인정하며 완화 | 입력에 있는 요청·확인 대상을 간결하게 명시 |
| 교수님·조교님 | 관계에 맞는 높임과 완곡한 선택권을 유지 | 높임을 유지하며 입력에 있는 용건을 간결하게 명시 |
| 선배·동기 | 지위·거리감을 고려해 조심스럽게 완화 | 하위 관계에 맞는 말투로 입력에 있는 용건을 명시 |
| 친구·연인 | 친밀도를 강요하지 않고 감정 충격을 완화 | 입력에 있는 의도·경계를 분명히 하되 관계·약속을 새로 단정하지 않음 |

## 사용자 흐름

1. 앱 진입
2. 대표 답냥이의 질문에 **답장/먼저 연락 여부를 빠른 답변으로 선택** (내부 S0)
3. 4개 관계 중 하나를 선택하면 해당 관계의 냥이 조력자가 대화를 이어감 (팀플냥 / 교수냥 / 선배냥 / 연인냥)
4. 관계별 냥이가 제시한 **상황 카드** 중 하나를 선택하고 카드별 핵심 질문 정확히 1개에 빠른 답변. 맞는 카드가 없으면 **"내 상황을 직접 설명하기"**로 목적+모드별 텍스트를 입력한다.
5. 생성 — 빠른 답변은 guided AI, 질문 화면의 **"질문 없이 바로 초안 보기"**는 API 없이 정적 템플릿, 직접 설명은 manual AI로 생성한다.
6. 답냥이가 톤 3단계 후보 3개 제시 — 기본 / 더 부드럽게 / 더 분명하게 순. guided AI는 반영한 관계·카드·답변을 표시하고, 실패 fallback은 방금 답한 세부 내용이 반영되지 않았음을 명시한다.
7. 마음에 드는 보낼 말 선택 → 필요하면 후보를 현재 탭에서 직접 수정 → 복사 (**화면상 핵심 과업 완료 지점**). 기본 초안이 마음에 안 들면 S3에서 **"AI로 더 맞추기"**를 펼치고, guided 결과는 **"이 선택으로 새 초안 3개 만들기 / 선택한 답 바꾸기"**를 구분한다. 첫 행동 앞에는 추가 입력 없이 즉시 새 초안이 만들어진다는 안내를 둔다. 성공한 교체의 직전 1세트는 비교·복원할 수 있고 실패 중에는 현재 후보를 유지한다. 더 구체적인 사실은 `내 상황을 직접 설명하기`, 상황 자체가 다르면 `상황 다시 고르기`로 분리한다.
8. (이후 단계 — MVP 미구현) 결과 평가 — "효과 있었어요" 피드백
9. (이후 단계 — MVP 미구현) 좋은 평가를 받은 예시가 데이터베이스에 누적 → 다음 생성에 반영

화면별 상태(로딩/실패/복사 폴백 등)는 docs/SCREENS.md 참고.

## 초기 예시 확보 (콜드스타트 대응)
**확보 방식**: 팀 직접 작성 — 4개 시나리오 × 상황 2개 × 3톤 세트 = 24개. 스키마·작성 기준·검수 방법은 docs/SPEC.md 4장.

이후 단계 보강 후보 (시드에는 출처 태그 `source`로 구분):
- 별도 동의를 받은 대학생의 짧은 과업·자발적 제보로 "실제로 보냈고 효과 있었던 메시지" 후보 수집. 긴 인터뷰는 선택형 (`survey`)
- 대학생 커뮤니티(에브리타임 등) 사례는 원문 수록 금지, 패턴 참고 후 재작성만 (`rewrite` — EDGE_CASES 6-2)

서비스 초기에는 이 시드가 few-shot의 전부이므로 제3자 검수(T16)가 출시 전 필수다. 실제 효과 피드백 기반 개선은 MVP 이후이며, 현재 시드를 효과가 검증된 데이터로 부르지 않는다.

## 화면 구성
docs/SCREENS.md에서 확정한 내부 단계 S0~S3는 유지하되 한 개의 가이드형 대화 셸 안에서 표현한다:

- S2-a 상황 카드 6개(공통5+특화1) → S2-d 카드별 질문 1개 / S2-b 직접 설명(목적+텍스트, 병렬 경로)
- S3 냥이가 건네는 톤 축 후보 3개 묶음(복사, 템플릿은 내 상황에 더 맞추기·상황 다시 고르기, AI는 다시 만들기·입력 내용 수정하기)

## MVP
범위는 docs/MVP.md에서 정의 (In/Out 표가 구현 여부 판단의 단일 기준). 요약:
- In: 답장/먼저 연락 화면 분리, 4개 시나리오, 카드별 질문 1개 guided AI+직접 설명 manual AI+정적 기본 초안, 개인 말투 4종, 교수·조교 메신저/이메일 형식, 톤 3단계 후보, 복사, 상태 처리, 2.5D 냥이, Vercel 백엔드, 원문 없는 PostgreSQL 운영·retrieval 메타데이터, 검수 예시 retrieval의 비프로덕션 합성 평가 기반
- Out: retrieval 운영 활성화·사용자 유래 corpus 자동 편입, 피드백 수집·예시 DB 누적, 로그인, 히스토리, 완전한 3D 리깅·복합 애니메이션, 런타임 멀티에이전트, 시나리오 커스텀, 결제

## 기술 스택 & 아키텍처
- 프론트엔드: React + Vite + TypeScript. 캐릭터는 Three.js + React Three Fiber 단일 Canvas로 렌더링하며 DOM UI와 분리한다
- 백엔드/AI 연동 방식: Vercel Function `/api/generate`가 API 키 보호, 입력 검증, deadline·제한 재시도, 오류 매핑, 레이트리밋과 Gemini API structured output 호출을 담당한다. 최종 모델은 T21 holdout 품질·지연·비용 비교로 결정한다
- AI 실행 방식: guided ID를 서버 정본으로 해석하거나 manual 입력을 검증한 뒤 provider 1회 호출+결정적 검증을 수행한다. 자율 agent loop·런타임 멀티에이전트는 두지 않는다
- 검수 예시 retrieval: Git의 검수 예시 본문을 정본으로 두고 Neon pgvector에는 document embedding·버전·checksum만 저장한다. 현재 작은 corpus에서는 exact top-2를 합성 offline 평가에만 쓰며 운영 selector는 static이다
- 데이터 계층: Neon PostgreSQL + Drizzle ORM. T30 핵심 네 테이블과 독립 `retrieval_examples` metadata table에 원문 없는 버전·생성·평가·embedding 메타데이터만 저장한다
- 배포 환경: Vercel (정적 빌드 + 서버리스 함수 동거, API 키는 환경변수로 서버 보관)

## 데이터 모델

**MVP는 서버 저장 데이터가 있지만 사용자 대화 원문은 저장하지 않는다.** 로그인·히스토리·피드백은 Out이며 받은 메시지·상황 설명·생성 문구·IP·영구 사용자 ID는 서비스 DB에 남기지 않는다. AI 경로의 입력은 provider 처리 과정으로 전송되며 provider 보존 조건은 별도로 고지한다. 데이터는 세 층으로 나뉜다:

- **MVP — 정적 데이터 (docs/SPEC.md에서 확정)**:
  - 시나리오(Scenario): id, 이름, 냥이 조력자 이름, 카드 문구, 톤 축 라벨 3단계 — 프론트 상수
  - 개인 말투(SpeechStyle): id, 사용자 라벨, 예시 — 카드·직접 설명 공통 프론트 상수(T32)
  - 상황 카드(SituationCard): id, 라벨, 범위(공통/시나리오 특화) — 프론트 상수 (SPEC 1장)
  - guided 질문(GuidedContextQuestion): scenarioId×situationId별 질문 1개와 option 3개, stable ID·purpose·사실 경계 — Git 정본(T34)
  - 시드 예시(CuratedExample): scenarioId, situationNote, receivedMessage?, toneLevel, message, source — 프록시 상수('직접 설명' AI few-shot 재료, 24개)
  - 상황 카드 템플릿(CuratedTemplate): scenarioId×situationId×speechStyleId×toneLevel 조회, 시드와 독립 작성 — 프론트 상수(카드 경로 재료, T25 전수 검수 통과 288개, SPEC 4장)
  - 교수 이메일 템플릿(EmailTemplate): emailSituationId×toneLevel의 제목·본문 — 사용자 입력을 로컬에서만 치환하는 18후보 초안(T33)
- **MVP — PostgreSQL 운영 데이터 (SPEC 2장, T30)**:
  - PromptVersion / TemplateVersion: 배포 버전, checksum, 검수 상태·시각
  - GenerationRun: route, scenario/mode/purpose ID, model·버전, latency, token 수, status, 시각. 원문·생성 문구 없음
  - EvaluationRun: 합성/검수 case ID, 모델·버전, 집계 품질 점수·비용·지연. 실제 사용자 원문 없음
  - RetrievalExample: Git example ID·catalog/model version·checksum·관계/목적/모드·document vector. 예시 본문·사용자 query·query vector 없음
- **이후 단계 — 저장 데이터 (스키마 보류)**:
  - 피드백(Feedback): 피드백 2단계 분리 정책(EDGE_CASES 4-1) 기준으로 설계

### 프라이버시 고려
사용자가 입력하는 상황 세부사항과 제3자 대화는 민감 정보다. 서비스 서버·분석·DB에 원문을 남기지 않는 것과 외부 AI provider가 요청을 처리·보존하는 것은 별개다. 실 AI 연결 전에는 전송 대상과 당시 provider 보존 조건을 입력 화면에서 안내한다. 피드백 기반 예시 누적은 개인 식별 정보 제거 기준이 확정되기 전까지 도입하지 않는다.

## 성공 기준

**핵심 과업 정의**: 생성된 후보 3개 중 하나를 **복사**하면 화면상 과업 완료. 복사는 실제 전송·효과가 아니라 상호작용 프록시다. T36은 결과·다듬기·재생성·복사·상황 변경의 5개 allowlist event만 원문·후보·사용자/세션 ID 없이 기록하며 event 수를 실제 사용자 funnel로 표현하지 않는다(SPEC 7장).

**MVP 단계 — 출시 전 검수 합격선 (docs/SPEC.md 5장)**:
- 톤 3단계 블라인드 정렬 일치 90% 이상 (20세트 중 18)
- 후보의 80% 이상이 수정 없이~경미한 수정으로 전송 가능 (60개 중 48)
- 입력에 없는 사실(환각) 0건 + 자리 표시자 하이라이트 100% 동작

**MVP 외부 파일럿 (T22)**:
- 평소 ChatGPT/Gemini와 유효 짝비교를 완료한 대학생 5명을 확보하고, 그중 4명 이상이 C1~C4 카드 과업 4개 중 3개 이상에서 의도 카드를 찾아 도움 없이 최종 문구를 확정. 5명 미만이면 판정 `Pending`
- 5명 중 4명 이상이 배정된 실 AI 직접입력 과업 1개를 도움 없이 확정
- 카드 경로 S0→결과 중앙값 20초 이내, 직접입력 경로 S0→최종 확정 중앙값 60초 이내
- 카드 원문 경계, 탭 임시 보관·외부 provider 전송 차이, 복합 관계 카드 범위를 각각 5명 중 4명 이상이 이해

**범용 AI 대비 경쟁가치 검증**:
- [문헌 기반 제품·검수 근거](RESEARCH_REVIEW.md)로 설계·검수 항목을 정하고, 세부 과업·원시 필드·블라인드 루브릭은 [경쟁가치 검증 절차](COMPETITIVE_VALIDATION.md)를 따른다.
- T20 실 provider 품질 진행 전에는 참여자를 모집하지 않는다. T25 대표 12문구 hard gate 뒤 C1~C4를 ChatGPT·Gemini 통제 기준선과 반복 비교해 원출력 품질·사실 충실성·입력 글자 수만 판정한다.
- 무참여자 `Provisional Go`는 실 provider 품질 진행 허용일 뿐 실제 사용자의 속도·선호·주인의식 증거가 아니다. provider 비종속 프록시·DB 기반 구현을 막지는 않는다.
- T22에서만 긴 인터뷰 없이 사람 대상 과업을 수행한다. 카드 C1~C4는 각 참여자의 평소 ChatGPT 또는 Gemini와 비교하고, 실 AI A1~A4는 답냥이 직접입력 경로 사용성만 확인한다.
- T22 탐색 Go는 사실·사유·약속 추가 0건, 카드 3/4 이상 무도움 완료와 실 AI 1개 완료 각각 4/5, 카드 최종문 합격 80% 이상·비교도구 대비 -10%p 이내, 실 AI 합격 4/5, 카드 원문·저장/provider·복합 관계 이해 각각 4/5를 먼저 통과해야 한다.
- 위 hard gate 뒤 참여자 3/5 이상의 카드 시간 우위와 시간 비율 중앙값 30% 이상 단축을 모두 충족하고, 4/5가 다음 카드 적합 상황에서 답냥이를 먼저 선택해야 `Go`다. 서로 다른 주사용 도구를 묶은 결과는 “이 5명의 평소 사용 도구 대비”로만 표현하며 시장 우월성·지속 사용을 확정하지 않는다.

**지속 사용 가설 (MVP 이후 관찰)**:
- 답냥이는 일상 습관형보다 사건 발생형 도구로 본다.
- 로그인·알림을 추가하지 않고, 동의한 참여자가 1~2주 동안 다른 실제 상황에서 자발적으로 재사용하는지 간단 사용 일지·짧은 체크인으로 확인한다. 긴 인터뷰는 필수가 아니다.

**이후 단계 (정량 지표 — 상세 로깅 도입 후)**:
- 생성된 보낼 말을 수정 없이(또는 소폭 수정만으로) 실제 전송한 비율
- 결과·복사·다듬기 event의 route/scenario별 집계. 식별자가 없어 동일 사용자 funnel·재방문율로 계산하지 않음
- 재방문율 (같은 사용자가 다른 상황에서 다시 사용하는지)
- "효과 있었어요" 피드백 비율
