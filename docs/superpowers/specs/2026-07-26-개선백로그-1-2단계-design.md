### 1-3. 지역 시·군·구 전국 확장

**현재**: `mockData.js:6` `REGIONS`에 시도 2개(서울·경기)·시군구 8개만 하드코딩. BE `validators.js`는 `regionSido`/`regionSigungu`를 길이(각 20)만 검사(화이트리스트 없음). DB 컬럼 `region_sido varchar(20)`, `region_sigungu varchar(20)`, `region_eupmyeondong varchar(20)`(nullable).

**결정**: 시/군/구까지만(읍/면/동 제외, `region_eupmyeondong`은 nullable 유지). 데이터는 **공용 JSON 파일 1개**를 FE·BE가 공유한다.

**설계**:
- 전국 17개 시도 + 약 250개 시군구를 담은 **공용 JSON 1개**를 저장소 공유 위치에 둔다. FE는 지역 셀렉트 렌더에, BE는 화이트리스트 검증에 같은 파일을 import → 단일 소스, 불일치 없음.
  - 구조: `{ "시도명": ["시군구명", ...], ... }` (읍면동 계층 제거).
  - FE는 `mockData.js`의 `REGIONS`를 이 JSON으로 대체. BE는 검증 모듈에서 로드.
- 등록/수정 폼: 지역 입력을 **시도 → 시군구 2단 셀렉트**로. 시도 선택 시 해당 시군구 목록만 노출.
- BE 검증: `regionSido`가 목록에 있고, `regionSigungu`가 그 시도의 하위 목록에 있는지 확인. 불일치 시 400.
- **세종특별자치시 예외**: 세종은 하위 시군구가 없다. `regionSigungu`는 현재 필수(non-empty)이므로 구조를 유지하기 위해 **세종은 `regionSigungu = '세종특별자치시'`**(시도명과 동일)로 둔다. JSON에서 `"세종특별자치시": ["세종특별자치시"]`로 표현하면 검증·셀렉트 로직 변경 없이 처리된다.
  - 참고: 제주는 자치구가 아니라 행정시(제주시·서귀포시)지만 시군구 자리에 그대로 넣으면 되므로 별도 처리 불필요.
- **varchar(20) 한도**: 새 시도명(강원특별자치도·전북특별자치도 등 7자)·시군구명 대부분 20 코드포인트 이내라 문제 없다. 일반구가 있는 시(수원·성남·창원 등)는 **시 레벨까지만**(예: "창원시") 표기해 "시+일반구" 합성으로 20자를 넘기지 않는다.

### 1-4. 신뢰도 표시 개편 (표시만, 알고리즘 아님)

**현재**: `bungae-moim/src/components/TrustBadge.jsx`가 `신뢰도 {score.toFixed(1)}` — 소수점 1자리. 리디자인으로 `TrustBadge`가 헤더에 올라가 전 페이지 상시 노출. 사용처: 헤더(`SiteHeader.jsx`), 상세(`MeetingDetailPage.jsx`), 마이페이지(`MyPage.jsx`).

**결정**: 정수 + 이모지 + 색 밴드. 내부 `trust_score`(numeric)는 불변, 표시 계층만 바꾼다. (신뢰도 알고리즘 본체는 3단계 별도 프로젝트.)

**설계**:
- 밴드 정의: `0–30` 😢 / `31–60` 😐 / `61–90` 🙂 / `91–100` 😍.
- 점수는 정수로 표시: `Math.round(Number(score))`.
  - ⚠️ **pg `numeric`은 JS 문자열로 온다**(CLAUDE.md 함정). `Math.round` 앞에 `Number()` 정규화를 반드시 유지. 밴드 비교도 숫자로.
- 색 밴드: 밴드별 색(빨강 → 회색 → 초록 → 골드)을 배지에 적용.
  - ⚠️ 리디자인 때 `.trust-badge` 대비가 2.1:1로 minor 이슈였고 헤더 상시 노출이라 전 페이지에 걸린다. 색 밴드(특히 빨강·골드)가 헤더 배경(`--ink` 계열) 위에서 대비를 확보하는지 확인.
  - 다크모드 `.trust-badge`의 `--cream-mute` 잔재(components.css:187)도 이때 함께 정리.
- 배지 컴포넌트 한 곳(`TrustBadge.jsx`)만 고치면 세 사용처에 동일 반영된다.

## 2단계 — 항목별 설계 개요 (각자 작업일, 상세 계획서는 착수 시)

### B. 신청 시 한마디 (소모임만)

**목적**: 소모임 승인(F3/F4)에서 모임장이 신청자를 판단할 근거가 지금 닉네임·신뢰도뿐. 모임장이 가입 질문을 설정하고 신청자가 답하게 한다.

**설계**:
- DB: `meetings.apply_question`(nullable text), `meeting_participants.apply_answer`(nullable text). 마이그레이션 2개 컬럼 추가(기존 행은 null).
- 등록/수정 폼: **소모임(small)일 때만** 질문 입력(선택). 번개(flash)는 즉시확정이라 판단 여지가 없어 미지원 — 공용 `MeetingForm`에서 type이 small일 때만 질문 필드 렌더.
- 신청(F1): 질문이 설정된 소모임은 답변 **필수**. 빈 답변이면 400. 질문 없으면 지금과 동일하게 답변 없이 신청.
- 신청자 목록(F3): 응답에 `applyAnswer` 추가, 모임장 화면에 표시.
- E4(수정, full-replace): 대기/승인 신청자(`status IN ('pending','approved','confirmed')`)가 1명이라도 있으면 **질문 수정 잠금**(기존 답변이 엉뚱한 질문에 붙는 것 방지). E4 capacity 잠금과 같은 방식.
- 거절 사유는 범위 밖(나중).

### 2. 마이페이지 모임 내역 (BE 변경 0 — FE 필터만)

**목적**: 취소·종료된 모임이 활성 목록을 어지럽힌다. 완료된 모임은 "모임 내역"으로 따로, 취소된 모임은 숨긴다.

**설계** (검토에서 확인: hosted/joined 응답이 이미 `status`·`start_at`·`end_at`를 담고 있어 **순수 FE 필터로 가능**, 마이그레이션·API 변경 없음):
- `listHostedMeetings`(G1)·`listJoinedMeetings`(G2)는 지금도 취소·종료 포함 전체를 반환한다. FE에서 `status` + `isMeetingEnded`(`utils/status.js`)로 분류.
- 활성 목록(내가 만든 / 참여한): **진행 중·예정만** (`status ≠ cancelled` AND 종료 안 됨).
- 새 **"모임 내역"** 섹션 — 완료된 모임만, **만든/참여 구분**:
  - 내가 만든 완료 = 모임 `status ≠ cancelled` AND 종료됨. (hosted 응답은 `m.status`를 담으므로 직접 검사.)
  - 참여한 완료 = **내 참여상태가 `confirmed`/`approved`** AND 모임 종료됨. (끝.)
    - ⚠️ joined 응답에는 `m.status`(모임 상태)가 없다. 하지만 **E5 취소가 참여자 전원의 `p.status`를 `cancelled`로 바꾸므로**(meetingService.js:494-497), 호스트가 취소한 모임은 내 `p.status`가 이미 `cancelled` → `p.status ∈ {confirmed,approved}` 필터만으로 자동 제외된다. 따라서 "모임 status ≠ cancelled" 조건은 불필요하고, **joined 쿼리에 `m.status`를 추가할 필요가 없어 "BE 변경 0"이 성립한다.**
- **취소된 모임은 어디에도 안 뜸** (활성·내역 양쪽에서 제외).
- 되돌리기/숨김 토글 없음(상태 기반 자동 분리).

### C. 승인·거절 알림 (헤더 뱃지 + 목록)

**목적**: 현재 상세에 "마이페이지에서 확인" 문구만. 신청자가 승인 여부를 직접 들어와 봐야 한다.

**설계**:
- DB: `notifications` 테이블 신설 — `id`, `user_id`(수신자), `type`, `meeting_id`, `is_read`(default false), `created_at`. 인덱스: `(user_id, is_read)` 또는 `(user_id, created_at)`.
- `type` 예: `application_approved`, `application_rejected`, `new_application`, `meeting_cancelled`.
- 생성 지점(알림 INSERT는 행위와 **원자적**으로 — 행위는 커밋됐는데 알림만 유실되는 것 방지):
  - **F1 신청**(`applyToMeeting`) → **소모임 pending 신청일 때만** 모임장에게 1건. `applyToMeeting`은 이미 `withTransaction`을 쓰므로 **기존 트랜잭션 안**에서 INSERT.
  - **E5 취소**(`cancelMeeting`, meetingService.js:492) → 이미 `withTransaction`을 쓰므로 **기존 트랜잭션 안**에서 INSERT. ⚠️ 대상은 **활성 참여자만**(취소 직전 `p.status ∈ {pending,confirmed,approved}`였던 사람). E5는 거절·취소 이력까지 전원을 `cancelled`로 바꾸므로, UPDATE **전에** 활성 참여자 user_id를 먼저 조회해 그들에게만 INSERT(이미 거절당한 신청자에게 "취소됨" 노이즈 방지).
  - **F4 승인/거절**(`respondToApplicant`, meetingService.js:449) → ⚠️ **현재 트랜잭션을 안 쓴다**(상태 확인+갱신을 `UPDATE … WHERE status='pending' RETURNING` 한 문장에 담아 CAS로 처리). 알림을 원자적으로 넣으려면 **F4에 트랜잭션을 새로 감싼다** — `UPDATE`가 `rowCount>0`(실제 승인/거절 성공)일 때만 같은 트랜잭션 안에서 대상 신청자에게 알림 INSERT. 단문 CAS 보장은 그대로 유지된다.
- API: `GET /api/notifications`(목록 + 미읽음 수), `POST /api/notifications/read`(전체 읽음).
- FE: 헤더에 미읽음 뱃지, 알림 목록(드롭다운 또는 페이지). 갱신 = **라우트 이동 시 조회**(폴링 없음). 읽음 = **목록 열면 그 시점 미읽음 전체 읽음 처리**.
- 시작 임박 알림은 스케줄러가 필요해 범위 밖(선택).

### A. 모임 대표 이미지 (Cloudinary)

**목적**: 목록 3열 카드가 텍스트만이라 허전. 대표 썸네일 추가.

**설계**:
- DB: `meetings.image_url`(nullable). 기존 4건은 null.
- 저장소: **Cloudinary**(리사이즈·포맷변환·CDN 자동). 대표 **1장**.
- 업로드: 선택(필수 아님). 이미지 없으면 **카테고리별 기본 이미지**(FE에서 색/아이콘). 형식 jpg/png/webp, ~5MB 제한(클라이언트 + 업로드 프리셋).
- ⚠️ 보안: BE가 받는 `image_url`을 **Cloudinary 도메인 화이트리스트**로 검증(임의 URL 주입 방지).
- 반영: 목록 카드 썸네일 + 상세 헤더.
- ⚠️ **사용자 액션 필요**: Cloudinary 계정 + 업로드 프리셋/키.

### 1-b. 위치 자동설정 (네이버 역지오코딩)

**목적**: 모임 찾기 필터의 지역 기본값을 사용자 위치로 자동 설정("내 주변 모임").

**설계**:
- 흐름: 브라우저 Geolocation으로 좌표 획득 → 좌표를 시도/시군구로 역지오코딩 → 모임 찾기 필터 기본값.
- ⚠️ **BE 프록시 엔드포인트 필수**: 네이버 Reverse Geocoding은 **브라우저 직접 호출 불가**(CORS 미지원 + client secret 노출). FE 좌표 → 우리 BE `GET /api/geocode/reverse?lat&lng` → BE가 네이버 호출 → 시도/시군구 반환.
- **명칭 정규화**: 네이버가 주는 지역명을 공용 REGIONS JSON의 키와 정확히 매칭. 불일치 시 비움.
- 권한 거부/실패 시: 기본값 없이 **비움**(자동설정 없이 수동 선택).
- HTTPS: Geolocation은 secure context 필요(localhost 예외라 개발 가능, 배포 시 HTTPS 필수 — 3주차 배포와 엮임).
- **의존성**: 1-3(지역 확장)의 REGIONS JSON이 있어야 명칭 매칭 가능 → 1(지역) 이후 착수.
- ⚠️ **사용자 액션 필요**: 네이버 클라우드 지도 API 키(client id/secret).

## 사용자 액션 (착수 전 준비물)

- **A 이미지**: Cloudinary 계정 + 업로드 프리셋/키
- **1-b 위치**: 네이버 클라우드 지도 API 키(client id/secret)

## 범위 밖 (이 문서 제외)

- 3단계: 신뢰도 알고리즘 본체 + 출석 체크(F), 정기 모임 시리즈(E) — 별도 프로젝트, 브레인스토밍부터 다시
- 거절 사유, 시작 임박 알림, 읍면동 지역, 카테고리 세분화, 휴대폰 본인인증(보류), 인앱 채팅(보류)
- 기존 백로그: B4+H1 신고, B5 인덱스, 통합 회귀 확장
