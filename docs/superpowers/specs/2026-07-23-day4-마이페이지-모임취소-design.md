# Day4 설계 — 마이페이지(G1/G2) + 모임 취소(E5)

## 1. 목표와 범위

### 이번에 하는 것
- **G1 — 내가 등록한 모임**: `GET /api/users/me/hosted-meetings`. 각 모임에 신청자 수·승인 대기 건수 포함.
- **G2 — 내가 신청/참여한 모임**: `GET /api/users/me/joined-meetings`. 상태(대기/확정/거절/취소 등)와 함께.
- **E5 — 모임 취소**: `DELETE /api/meetings/:id`. 모임장이 자기 모임을 취소, 참여자 전원 `cancelled`로 일괄 갱신.
- **상세 응답에 `isPast` 필드 추가** + FE `isEnded` 정합화(E5와 한 묶음). 종료된 모임에서 취소/신청 버튼이 노출돼 누르면 에러 나던 문제를 해결.
- 위 배선으로 **mock `MEETINGS`가 완전히 사라진다.** FE에 남는 mock 데이터 0.

### 이번에 하지 않는 것
- **E4(모임 수정)** — 금요일 몫. 이번 범위 아님.
- **B4/B5/H1(신고 등)** — 이후.
- **신뢰도 개편** — 별도 설계 문서(`2026-07-22-신뢰도-알고리즘-design.md`), MVP 후.
- **승인 철회(approved→rejected)** — Day3에서 범위 밖으로 확정.
- **F4에 `is_past` 가드 추가** — 종료된 소모임 잔여 pending 승인은 무해로 판단, 그대로 둠(Day4 범위 밖).

## 2. 브레인스토밍에서 확정한 결정

1. **E5 신뢰도 미변경.** 모임장이 판을 엎은 것이므로 확정 참여자에게 −3을 주지 않는다. `meeting_participants`를 `cancelled`로 일괄 UPDATE만. `users.trust_score`는 손대지 않는다.
2. **E5 가드 — "이미 취소만 차단".** 모임장 본인만(403), 없는 모임(404), 이미 `cancelled`면 에러. **종료된(`is_past`) 모임도 취소 허용**(가드 없음, 무해). 참여자 cascade는 명세대로 **전원**.
3. **MyPage 데이터 조달 = 접근 A(기존 패턴 일치).** 다른 실데이터 페이지(Home/List/Detail/Create)처럼 MyPage도 API 모듈에서 **페이지 로컬 state로 직접 fetch**한다. context에 전역 `meetings`를 두지 않는다. E5는 `deleteMeeting(id)` API를 MeetingDetailPage가 직접 호출(F1/F2와 동일).
4. **응답 형태를 하우스 스타일로 통일.** 명세서 원안의 `joined-meetings`는 맨 배열(`{ data: [...] }`)이었으나, 목록·참여자 등 다른 엔드포인트와 같은 `{ data: { items: [...] } }`로 통일한다(소비처 0개, 명세서 예시도 갱신).

## 3. 백엔드

### 3.1 E5 — `DELETE /api/meetings/:id`

**계약**
- 인증 필요. `:id`는 `parseIdParam`으로 안전한 양의 정수 검증(아니면 404).
- 성공: `{ "data": { "status": "cancelled" } }` (200).
- 실패:
  - 없는 모임 → `NOT_FOUND`(404)
  - 모임장 본인 아님 → `FORBIDDEN`(403)
  - 이미 `cancelled` → `VALIDATION_ERROR`(400, "이미 취소된 모임입니다")
  - 비로그인 → `UNAUTHENTICATED`(401)

**구현** — `meetingService.cancelMeeting(meetingId, hostId)`
1. `SELECT host_id, status FROM meetings WHERE id=$1` → 없으면 404.
2. `Number(host_id) !== Number(hostId)` → 403. *(⚠️ pg가 bigint `host_id`를 문자열로 준다 — F3/F4와 같은 함정. 반드시 `Number()` 정규화. listParticipants/respondToApplicant와 동일 패턴.)*
3. `status === 'cancelled'` → `VALIDATION_ERROR`.
4. `withTransaction`으로:
   - `UPDATE meetings SET status='cancelled' WHERE id=$1`
   - `UPDATE meeting_participants SET status='cancelled' WHERE meeting_id=$1`
   - `users.trust_score`는 손대지 않는다.
5. 반환 `{ status: 'cancelled' }`.

동시 요청은 idempotent(재취소는 상태를 다시 cancelled로 쓸 뿐, 신뢰도 변화가 없어 무해)하므로 `FOR UPDATE` 불필요. 3-way 에러 구분(404/403/이미취소)을 위해 SELECT-먼저 방식을 쓴다.

라우트: `routes/meetings.js`에 `router.delete('/:id', requireAuth, ...)` 추가. 기존 `DELETE /:id/apply`와 경로가 다르므로 충돌 없음.

### 3.2 G1 — `GET /api/users/me/hosted-meetings`

**계약** — 인증 필요.
```json
{
  "data": {
    "items": [
      { "id": 4, "title": "...", "type": "small",
        "startAt": "...", "endAt": "...", "status": "recruiting",
        "applicantCount": 3, "pendingCount": 2 }
    ]
  }
}
```
- `applicantCount` = 활성 신청자 수(`status IN ('pending','approved','confirmed')`).
- `pendingCount` = 승인 대기 수(`status = 'pending'`).
- 취소·거절한 신청은 두 집계에서 제외. 정렬 `created_at DESC, id DESC`.
- 취소된(`cancelled`)·종료된 모임도 **포함**(마이페이지에서 내 모임 이력을 다 보여준다).

**구현** — `meetingService.listHostedMeetings(hostId)`. 서브쿼리 집계 1방:
```sql
SELECT m.id, m.title, m.type, m.start_at, m.end_at, m.status,
  (SELECT COUNT(*)::int FROM meeting_participants mp
     WHERE mp.meeting_id = m.id AND mp.status IN ('pending','approved','confirmed')) AS applicant_count,
  (SELECT COUNT(*)::int FROM meeting_participants mp
     WHERE mp.meeting_id = m.id AND mp.status = 'pending') AS pending_count
FROM meetings m
WHERE m.host_id = $1
ORDER BY m.created_at DESC, m.id DESC
```
전용 직렬화(작은 객체). `id`는 `Number()`, count는 `::int`라 그대로 숫자.

### 3.3 G2 — `GET /api/users/me/joined-meetings`

**계약** — 인증 필요.
```json
{
  "data": {
    "items": [
      { "meeting": { "id": 10, "title": "...", "type": "small",
                     "startAt": "...", "endAt": "...",
                     "host": { "nickname": "홍길동" } },
        "status": "pending", "appliedAt": "..." }
    ]
  }
}
```
- 내 모든 참여 이력(`pending`/`confirmed`/`approved`/`rejected`/`cancelled` 전부) 포함 — 거절·취소 이력도 마이페이지에서 확인.
- 정렬 `applied_at DESC`.
- `meeting.host`는 `nickname`만(MyPage가 trustScore를 표시하지 않음 — YAGNI).

**구현** — `meetingService.listJoinedMeetings(userId)`:
```sql
SELECT p.status, p.applied_at,
       m.id, m.title, m.type, m.start_at, m.end_at,
       u.nickname AS host_nickname
FROM meeting_participants p
JOIN meetings m ON m.id = p.meeting_id
JOIN users u ON u.id = m.host_id
WHERE p.user_id = $1
ORDER BY p.applied_at DESC
```
전용 직렬화로 `{ meeting: { id, title, type, startAt, endAt, host: { nickname } }, status, appliedAt }` 매핑.

### 3.4 상세 응답에 `isPast` 추가

`getMeetingDetail`은 이미 `COALESCE(m.end_at, m.start_at) < now() AS is_past`를 SELECT하지만 `evaluateApplicability` **인자로만** 쓰고 응답 `detail`에는 넣지 않는다. `detail` 객체에 `isPast: row.is_past`를 **추가**한다.
- `is_past`는 Postgres boolean → JS boolean 그대로.
- **테스트 안전**: `tests/meetings.detail.routes.test.js`는 응답을 필드 단위(`.id`/`.host`/`.confirmedCount`…)로만 단언하고 전체 객체를 strict `toEqual`하지 않으므로, 필드 추가로 깨지는 기존 테스트는 없다(Day4 TDD로 `isPast` 단언을 새로 추가).

라우트: `routes/users.js`에 두 GET 라우트를 `requireAuth`로 추가하고 `meetingService`의 두 함수를 호출.

## 4. 프론트엔드

### 4.1 API 모듈
- `src/api/users.js`: `fetchHostedMeetings()` → `{ items }`, `fetchJoinedMeetings()` → `{ items }`. (`request`가 `.data`를 언랩.)
- `src/api/meetings.js`: `deleteMeeting(id)` → `DELETE /api/meetings/:id`, `{ status }` 반환.

### 4.2 `MyPage.jsx` 재작성 (접근 A)
- context의 `meetings` 대신 마운트 시 두 API를 로컬 state로 fetch(로딩/에러/재시도 패턴은 기존 실데이터 페이지 그대로).
- **hosted 카드**: 서버 `pendingCount`로 "승인 대기 N건" 배지. `getPendingApplicants(m.participants)` 호출(66줄) **제거** — 이제 서버가 집계를 내려준다. `applicantCount`는 API 계약상 항상 내려오지만(명세서 "신청자 수" 준수), 렌더는 기존 카드가 대기 건수만 보여줬으므로 우선 "승인 대기 N건"만 유지하고 "신청자 N" 표기는 선택으로 둔다(기능 회귀 없음).
- **joined 카드**: `{ meeting, status, appliedAt }`에서 `participation.status` → 최상위 `status`. `meeting.host.nickname`, `formatMeetingSchedule(meeting)` 사용.
- **프로필 카드**: `currentUser`(context, userService가 이미 `trustScore`를 `Number` 정규화) 그대로 사용. `TrustBadge`의 `toFixed` 방어는 유지.
- ⚠️ pg 타입 함정: hosted/joined 응답에 `trustScore`를 새로 노출하지 않으므로 MyPage에는 신규 `toFixed` 리스크 없음. (joined `host`는 nickname만.)

### 4.3 `MeetingDetailPage.jsx` — E5 배선 + `isEnded` 정합화
- **E5 배선**: `cancelMeeting(meeting.id)`(context mock, 동기·무방비) 제거 →
  ```
  onClick={async () => {
    try { await deleteMeeting(id); navigate('/meetings') }
    catch (err) { setActionError(err.message); setConfirmingCancel(false) }
  }}
  ```
  성공 시 목록으로 이동(취소된 모임은 활성 목록에서 사라짐). context에서 `cancelMeeting` import 제거.
- **`isEnded` 정합화 — 두 곳**:
  1. 192줄: `const isEnded = meeting.status === 'finished' || meeting.status === 'cancelled' || meeting.isPast`
  2. **377줄의 "신청 취소하기" 버튼을 `!isEnded`로 감싼다** — 현재 `myParticipation.status ∈ {pending,confirmed,approved}`이기만 하면 무조건 떠서, 종료된 모임의 확정 참여자에게 취소 버튼이 노출되고 누르면 F2의 `is_past` 가드가 에러를 뱉었다. `!isEnded`로 감싸면 종료된 모임에선 상태 pill만 남고 취소 버튼이 사라진다.
  - 호스트 "모임 취소하기"(318줄)는 이미 `!isEnded`로 감싸져 있어 (1)만으로 처리된다. 결과적으로 과거 모임에선 호스트 취소 버튼도 숨는데, 이는 좋은 UX(이미 목록에서 사라진 모임을 취소할 이유 없음)이자 우리 결정("이미 취소만 차단")과 모순 없음(백엔드는 허용하되 UI 진입점만 없음).
  - F4 승인/거절 버튼은 `isEnded` 게이팅하지 않는다 — 백엔드 F4에 `is_past` 가드가 없는 것과 일관(범위 밖).
