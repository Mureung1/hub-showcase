# 꺼내보기 의미 검색 설계

## 목적

꺼내보기는 사용자가 지금 하는 일을 짧게 적으면 보관함에서 다시 쓸 만한 인사이트를 찾아주는 기능이다. 현재 구현은 입력과 제목·메모 등에 같은 단어가 있을 때만 찾을 수 있어 표현이 달라지면 관련 자료를 놓친다.

이 설계는 꺼내보기만 서버 의미 검색으로 전환하는 방법을 정리한다. 보관함 검색은 제목, 메모, 카테고리, 도메인과 URL을 직접 찾는 현재 키워드 검색을 유지한다.

## 결정 요약

- 서버에서 유료 `gemini-embedding-2`를 사용한다.
- 검색 벡터는 768차원으로 만든다.
- 인사이트의 제목과 메모만 의미 검색 단서로 사용한다.
- 카테고리, 도메인과 URL은 의미 검색 벡터에서 제외한다.
- 기존 키워드 검색과 의미 검색을 섞지 않는다.
- 관련도 기준을 넘은 결과를 모두 반환하고 6개 제한을 제거한다.
- 브라우저에서 모델이나 토크나이저를 내려받지 않는다.
- 생성형 LLM으로 검색 결과나 설명을 만들지 않는다.

기존 합성 실험에서 Gemini 의미 검색 단독은 현재 키워드 검색보다 표현이 다른 질문을 잘 찾았다. 키워드 검색과 결합한 결과는 의미 검색 단독보다 정렬 품질이 낮고 관련 없는 결과가 더 많이 섞였다. 합성 결과는 도입 가능성을 확인한 근거일 뿐 실제 사용자 성능을 증명한 결과로 사용하지 않는다.

## 카테고리의 역할

카테고리는 사용자가 자료를 묶어 관리하는 분류다. 자료의 내용을 설명하는 문장으로 취급하지 않는다.

사용자가 `섹스`, `나중에`, `A팀`처럼 개인적인 이름을 붙였을 때 그 이름을 의미 검색에 넣으면, 비슷한 뜻으로 모델이 판단한 상황에서도 관련 없는 인사이트가 나올 수 있다. 따라서 카테고리는 다음 위치에서만 사용한다.

- 보관함 카테고리 필터
- 보관함 키워드 검색의 정확한 이름 단서
- 인사이트 카드의 분류 표시

꺼내보기는 제목과 메모만 사용한다. 실제 사용에서 카테고리 이름을 꺼내보기에 입력하는 행동이 반복되면 의미 확장이 아닌 정확한 이름 일치만 별도로 검토한다.

현재 카테고리 입력과 고정 필터가 연결되지 않는 문제는 [GitHub #71](https://github.com/ppre1ude/hub/issues/71)에서 별도로 다룬다. 카테고리 관리 기능과 의미 검색은 서로 독립적으로 구현할 수 있다.

## 검색 문서

인사이트 하나당 검색 벡터 하나를 만든다.

메모가 있으면 다음 형식을 사용한다.

```text
title: 폼 오류 처리 방법 | text: 회원가입 화면의 오류 안내를 구현할 때
```

메모가 없으면 제목을 본문에도 사용한다.

```text
title: 폼 오류 처리 방법 | text: 폼 오류 처리 방법
```

이 형식은 Gemini가 검색 문서에 권장하는 `title`과 `text` 구조를 따른다. 메모를 본문에 두어 사용자가 남긴 활용 상황을 중심 단서로 사용한다. 별도의 필드 가중치나 같은 문장의 반복 입력은 추가하지 않는다.

검색 입력은 다음 형식을 사용한다.

```text
task: search result | query: 회원가입 오류 메시지를 어떻게 보여줄지 고민 중
```

문서와 입력 형식은 버전으로 관리한다. 형식이나 모델을 바꾸면 기존 벡터를 새 버전으로 다시 만든다.

## 저장 구조

기존 인사이트와 검색 벡터의 수명 주기를 분리하기 위해 별도 테이블을 사용한다.

```text
insight_embeddings
├─ insight_id
├─ user_id
├─ embedding
├─ model_id
├─ projection_version
├─ source_hash
└─ updated_at
```

- `insight_id`는 인사이트와 일대일로 연결하고 삭제 시 함께 제거한다.
- `user_id`와 RLS로 다른 사용자의 벡터를 조회하지 못하게 한다.
- `embedding`은 768차원 벡터다.
- `source_hash`는 제목이나 메모가 달라졌는지 확인한다.
- 검색용 원문을 이 테이블에 다시 저장하지 않는다.

개인 보관함은 사용자별 데이터가 작으므로 처음에는 근사 검색 인덱스를 만들지 않는다. 해당 사용자의 벡터만 정확하게 비교한다. 실제 데이터에서 검색 시간이 문제가 될 때 HNSW 도입을 별도로 판단한다.

## 벡터 생성

인사이트 저장과 검색 준비는 서로 다른 결과로 처리한다.

1. 인사이트를 먼저 저장한다.
2. 데이터베이스에 벡터 생성 작업을 등록한다.
3. 서버 작업자가 제목과 메모를 Gemini에 보내 벡터를 만든다.
4. 벡터와 입력 버전을 저장한다.
5. 실패한 작업만 다시 시도한다.

Gemini 장애 때문에 링크 저장이 실패하거나 지연되지 않아야 한다. 제목이나 메모를 수정하면 새 작업을 등록한다. 카테고리만 바뀐 경우에는 벡터를 다시 만들지 않는다.

기존 보관함의 최초 변환은 Batch API로 실행한다. 이후에는 새로 저장하거나 제목·메모가 바뀐 인사이트만 처리한다.

현재 JavaScript SDK의 임베딩 Batch 인라인 요청은 결과 순서를 보존하지만 요청별 metadata 입력을 지원하지 않는다. 따라서 Batch에는 검색 원문만 보내고, 인사이트 ID·사용자 ID·원문 해시·모델 버전은 Git에서 제외한 로컬 제출 기록에 순서대로 보관한다. 결과 반영은 같은 제출 기록이 있는 환경에서 실행하며, 로컬 기록에는 제목·메모와 API 키를 넣지 않는다.

## 꺼내보기 요청

1. 브라우저가 입력 문장과 로그인 토큰을 서버에 보낸다.
2. 서버가 로그인 사용자를 확인한다.
3. 검색 준비가 끝나지 않은 인사이트가 있으면 최대 8개의 제목과 메모를 Gemini 문서 벡터로 변환한다.
4. 서버가 입력 문장을 Gemini 검색 벡터로 변환한다.
5. Supabase가 같은 사용자의 인사이트 벡터만 비교한다.
6. 관련도 기준을 넘은 인사이트 ID를 가까운 순서대로 반환한다.
7. 브라우저가 이미 불러온 보관함 데이터에서 해당 카드를 찾아 보여준다.

보통의 꺼내보기 요청에는 입력 문장만 Gemini로 보낸다. 다만 새로 저장했거나 제목·메모가 바뀌어 검색 준비가 끝나지 않은 인사이트가 있으면 그중 최대 8개의 제목과 메모도 같은 요청 흐름에서 Gemini로 보낸다. 보관함 전체 내용은 매번 다시 보내지 않으며, 배포 전 기존 데이터 변환을 끝내 정상적인 요청에서 문서 변환이 추가되는 경우를 최소화한다. 검색 점수는 정렬과 운영 검증에만 사용하고 화면에는 표시하지 않는다.

## 관련도 기준과 결과 수

초기 관련도 기준은 합성 실험에서 선택한 코사인 유사도 `0.59`로 시작한다.

- `0.59` 이상인 결과를 가까운 순서대로 반환한다.
- 결과가 같으면 최근 수정된 인사이트를 먼저 반환한다.
- 관련도 기준을 통과한 결과의 개수를 6개로 자르지 않는다.
- `0.59`는 제품의 최적값이 아니라 첫 비공개 테스트를 위한 시작값이다.
- 모델, 검색 문서 형식과 관련도 기준을 하나의 설정 버전으로 기록한다.

사용자별 가중치나 자동 학습은 도입하지 않는다. 비공개 테스트 결과를 모아 전체 사용자에게 적용할 기준을 사람이 검토한 뒤 버전으로 변경한다.

## 실패 처리

- Gemini 요청이나 서버 검색이 실패하면 입력을 유지하고 다시 시도할 수 있는 오류를 보여준다.
- 비용 한도에 도달해도 키워드 검색으로 자동 전환하지 않는다.
- 관련도 기준을 넘는 결과가 없으면 결과 없음 상태를 보여준다.
- 새로 저장한 일부 인사이트의 벡터가 준비되지 않았으면 결과와 함께 짧은 안내를 표시한다.
- 별도의 진행률 화면이나 모델 준비 화면을 만들지 않는다.
- 검색 실패가 보관함 조회와 키워드 검색을 막지 않는다.

## 비용과 개인정보

- Gemini 유료 환경만 실제 사용자 데이터에 사용한다.
- 선불 금액은 10달러로 시작하고 자동 충전을 사용하지 않는다.
- 프로젝트 월 한도는 5달러로 설정한다.
- Google의 한도 반영 지연에 대비해 서비스 내부 사용량 한도도 둔다.
- Gemini API 키는 서버 환경에만 저장한다.
- 입력 문장과 메모 원문을 애플리케이션 로그에 남기지 않는다.
- 검색 준비가 남아 있는 경우 입력 문장뿐 아니라 해당 인사이트의 제목과 메모도 Gemini로 전송될 수 있다.
- 원문 페이지의 본문을 저장하거나 다시 수집하지 않는다.

`gemini-embedding-2`의 유료 텍스트 입력은 100만 토큰당 0.20달러이며 Batch API는 절반 가격이다. 현재 비공개 테스트 규모에서는 생성형 모델보다 비용이 작지만, 실제 사용량은 별도로 기록한다.

## 비공개 테스트에서 확인할 내용

- 표현이 달라도 다시 쓸 만한 인사이트를 찾는지
- 관련 없는 결과가 얼마나 섞이는지
- 결과가 없지만 보관함에는 관련 자료가 있었는지
- 전체 응답 시간과 Gemini 호출 시간
- 사용자 수, 요청 수, 입력 토큰과 실제 비용

클릭은 사용 기록으로만 보고 관련도의 정답으로 간주하지 않는다. 검색 규칙은 사용 기록에 따라 자동으로 바꾸지 않는다. 결과별 피드백 수집 화면은 의미 검색의 첫 구현 범위에 넣지 않고 비공개 테스트 운영 방식에서 별도로 정한다.

## 구현 검증 범위

새 합성 평가 세트나 하이퍼파라미터 비교 실험은 만들지 않는다. 구현 경계와 사용자 격리에 필요한 검증만 수행한다.

- 다른 사용자의 벡터가 검색되지 않는다.
- 제목이나 메모가 바뀌면 벡터 생성 작업이 등록된다.
- 카테고리만 바뀌면 벡터를 다시 만들지 않는다.
- 관련도 기준과 정렬이 적용되고 6개 제한 없이 반환된다.
- Gemini 실패가 저장된 인사이트를 손상시키지 않는다.
- 저장된 인사이트가 준비된 뒤 꺼내보기 결과로 반환되는 대표 흐름이 동작한다.

기존 브라우저 E5 성능 측정과 모델 다운로드 검증은 반복하지 않는다.

## 이번 설계에서 제외한 것

- 카테고리 관리 기능 구현
- 한 인사이트에 여러 카테고리 연결
- 카테고리의 의미 확장 또는 자동 추천
- 키워드 검색과 의미 검색의 RRF 결합
- 생성형 LLM 또는 재정렬 모델
- 브라우저 측 임베딩 모델
- 원문 페이지 수집과 AI 요약
- 사용자별 검색 가중치와 자동 학습
