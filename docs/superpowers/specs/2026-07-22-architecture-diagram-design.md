# 서비스 아키텍처 다이어그램 설계

## 배경

아맞다의 제출 Pull Request 본문에는 저장부터 꺼내보기까지의 실제 데이터 흐름을 한눈에 설명할 자료가 필요하다. 현재 저장소에는 개별 기능과 데이터 계약을 설명하는 문서는 있지만, 웹·Chrome 확장·Android 공유 진입점부터 Vercel API와 Supabase를 거쳐 보관함과 꺼내보기로 이어지는 전체 구조를 한 장으로 보여주는 자료가 없다.

이번 작업은 현재 구현된 구조만 시각화한 독립 HTML과, 그 HTML을 기준으로 생성한 PNG를 제공한다. 제품 런타임이나 데이터베이스 구조는 변경하지 않는다.

## 사용자 결과

- 심사자와 협업자가 한 장의 그림으로 아맞다의 저장·조회 흐름을 이해한다.
- Pull Request 본문에 PNG를 삽입해 별도 도구 없이 구조를 확인한다.
- HTML 원본을 저장소에 남겨 텍스트와 흐름을 이후에도 수정할 수 있다.

## 산출물

- `docs/architecture.html`: 외부 자산 없이 단독으로 열리는 아키텍처 다이어그램
- `docs/assets/amadda-architecture.png`: HTML을 넓은 화면으로 렌더링한 Pull Request용 이미지

HTML은 다이어그램의 단일 원본이다. PNG의 문구·구성·색상은 HTML과 별도로 편집하지 않고, HTML 렌더링 결과를 그대로 캡처한다.

## 시각 방향

확정한 A형 구성을 사용한다. 넓은 흰색 캔버스 위에서 왼쪽의 저장 진입점, 가운데의 애플리케이션과 서버 처리, 오른쪽의 Supabase 저장소가 가로 흐름으로 이어진다. 아래쪽에는 저장된 인사이트를 보관함에서 관리하고 꺼내보기로 찾는 읽기 흐름을 분리해 배치한다.

- `DESIGN.md`의 White Canvas 기준에 맞춰 흰 배경, 검정에 가까운 본문, 옅은 회색 경계선을 사용한다.
- 아맞다 대표 색상은 제목 표식, 주요 경로, 강조선에 제한적으로 사용한다.
- 카드마다 장식용 그림자를 과하게 넣지 않고 경계와 여백으로 계층을 구분한다.
- 화살표는 데이터 이동 방향을 명확히 보여주며, 교차를 최소화한다.
- 화면 폭 약 1600px에서 한 장으로 읽히는 와이드 구성을 기본으로 한다.

## 정보 구조

### 1. 저장 진입점

왼쪽 열에는 사용자가 인사이트를 저장하는 세 가지 현재 진입점을 표시한다.

- 웹: URL 직접 입력
- Chrome 확장: 현재 페이지 저장
- Android: 시스템 공유의 `ACTION_SEND`를 Capacitor가 전달

iOS 공유는 구현되지 않았으므로 포함하지 않는다.

### 2. 애플리케이션과 공통 API

가운데 열은 React/Vite 웹 애플리케이션과 Vercel Express API의 경계를 구분한다. 세 진입점은 다음 두 공통 API로 모인다.

- `POST /api/insights/capture`: 새 인사이트 저장
- `PATCH /api/insights/:insightId/memo`: 저장 직후 또는 보관함에서 메모 갱신

캡처 처리 과정은 현재 서버 코드에 맞춰 다음 순서로 설명한다.

1. 액세스 토큰 검증
2. URL 검증과 정규화
3. 같은 사용자의 동일 URL 중복 확인
4. 인사이트 우선 저장

페이지 제목·설명·대표 이미지 같은 미구현 메타데이터 수집이나 AI 처리는 활성 흐름으로 표시하지 않는다.

### 3. Supabase

오른쪽 열에는 다음 세 요소를 표시한다.

- Supabase Auth: 사용자 인증과 액세스 토큰
- Postgres `public.insights`: URL, 제목, 메모, 카테고리 등 저장
- RLS: 로그인한 사용자 본인의 행만 접근하도록 제한

서버 API를 통한 저장 흐름과 브라우저의 Supabase JS 조회·관리 흐름을 시각적으로 구분한다.

### 4. 보관함과 꺼내보기

아래쪽 읽기 흐름에는 브라우저가 Supabase JS로 본인 인사이트를 조회·수정·삭제하는 보관함과, 현재 구현된 결정적 검색을 표시한다.

- 보관함: 본인 인사이트 목록, 메모 수정, 삭제, 원문 열기
- 꺼내보기: 입력한 상황을 토큰화해 저장된 필드와 비교
- 점수: 메모 4, 제목 3, 카테고리 2, 도메인 1
- 결과: 점수순 상위 6개를 보여주고 원래 URL을 연다.

AI 추천이나 근거 없는 자동 추천으로 오해할 수 있는 표현은 사용하지 않는다. 사용자가 결과 선택 로직을 이해할 수 있도록 `결정적 검색`과 점수 기준을 짧게 명시한다.

## 문구 원칙

- 사용자에게 보이는 제품 용어는 `저장`, `보관함`, `꺼내보기`, `인사이트`를 사용한다.
- 내부 구현을 설명해야 하는 곳에서만 API 경로, `RLS`, `public.insights` 같은 기술 용어를 쓴다.
- `작업팩`, `연결 이유`, `AI 추천`처럼 현재 사용자 경험 또는 구현과 맞지 않는 표현은 포함하지 않는다.
- 문장은 짧게 유지하고, 각 카드가 하나의 책임만 설명하게 한다.

## 반응형과 접근성

- 기본 와이드 캔버스에서는 모든 주요 흐름을 스크롤 없이 한 장에 담는다.
- 좁은 화면에서는 열을 세로로 쌓되, DOM 순서를 저장 진입점 → 애플리케이션/API → Supabase → 보관함/꺼내보기로 유지한다.
- 색상만으로 경로를 구분하지 않고 제목, 선 형태, 화살표 라벨을 함께 사용한다.
- 본문과 보조 문구는 충분한 명도 대비를 확보한다.
- 다이어그램 전체에 설명용 제목을 제공하고, 각 영역은 의미 있는 HTML 섹션과 제목 구조를 사용한다.

## 구현 경계

- HTML, CSS, 필요한 최소 SVG는 `docs/architecture.html` 한 파일 안에 둔다.
- 외부 폰트, CDN, 원격 이미지, JavaScript 런타임 의존성을 사용하지 않는다.
- PNG 생성을 위해 제품 소스나 빌드 설정을 변경하지 않는다.
- 제품 UI, API, 데이터베이스, Android 앱 코드는 수정하지 않는다.
- 제출 전용 `submit` 브랜치는 수정하지 않는다.

## 검증

- HTML을 로컬 브라우저에서 직접 열어 외부 요청 없이 완전히 렌더링되는지 확인한다.
- 약 1600px 너비의 데스크톱 화면에서 문구 잘림, 화살표 교차, 겹침이 없는지 시각 검수한다.
- 좁은 화면에서 카드 순서와 텍스트 가독성을 확인한다.
- HTML에서 생성한 PNG의 실제 크기, 한글 렌더링, 여백과 선명도를 확인한다.
- 현재 소스의 API 경로, 검색 점수, 상위 결과 수, 저장소와 인증 흐름을 다시 대조한다.
- `git diff --check`와 문서 포맷 검사를 실행한다.

전체 테스트 기준선은 Windows의 `core.autocrlf=true` 체크아웃에서 `server/supabase_migration_ci.test.ts`의 LF 전용 정규식 한 건이 실패한다. 해당 워크플로에는 검사 대상인 `persist-credentials: false`가 존재하며, 이번 문서 작업은 이 파일을 변경하지 않는다. 최종 검증에서는 문서 전용 검사와 전체 테스트 결과를 구분해 보고한다.
