## 1. 목표와 범위

소모임(`type = 'small'`)은 모임장이 신청을 승인해야 참여가 확정된다. Day2에서 신청(F1)·취소(F2)까지
뚫었으므로, 지금은 신청이 `pending`으로 쌓이기만 하고 아무도 확정되지 못한다. **이 슬라이스가 빠지면
소모임 타입 자체가 성립하지 않는다**(2주차 계획서 159줄).

### 이번에 하는 것

- BE F3 `GET /api/meetings/:id/participants` — 모임장 전용 신청자 목록
- BE F4 `PATCH /api/meetings/:id/participants/:userId` — 승인/거절
- FE 상세페이지 모임장 카드를 mock에서 실 API로 교체
- **API 명세서 갱신** — 명세서 174줄에는 `GET /participants`가 표에 한 줄만 있고 응답 바디가 없다.
  다른 엔드포인트는 전부 응답 예시를 갖고 있고 Day2에도 명세서를 갱신했으므로(`b56a3ffa`),
  F3 응답 형태와 F4 에러 규칙을 명세서에 반영하는 것까지가 이 슬라이스의 완료 조건이다.

### 이번에 하지 않는 것

- **승인 철회(`approved → rejected`)** — 확장 지점만 코멘트로 남긴다(4.3 참조)
- 신청자 목록 페이징 — 응답 봉투만 열어두고 구현하지 않는다(3.1 참조)
- flash 모임의 참여자 명단 FE 표시 — API는 허용하지만 화면은 소모임만(5.2 참조)
- E3(상세 조회) 수정 — **불필요하다**. 이미 `approved`/`confirmed`에게만 `openChatUrl`을 내려준다
  (`meetingService.js:217-226`). F4로 승인되면 신청자의 다음 상세 조회에서 링크가 자동으로 보인다.
- 새 마이그레이션 — **불필요하다**. `meeting_participants`에 `applied_at`·`responded_at`이 이미 있다.
- **종료된 모임에 대한 승인 가드** — 의식적으로 뺀다. 지난 소모임에도 `pending`이 남아 있을 수 있고
  지금 설계는 그것을 승인할 수 있다(모임장이 뒤늦게 정리하는 것이라 유해하지 않다). Day2에 같은 이유로
  미뤄둔 "F2에 `is_past` 가드 없음"과 짝이 되는 항목이므로, **둘을 함께** 백로그에 남기고 MVP 완성 후
  일괄 처리한다. 취소된 모임은 E5가 참여자 전원을 `cancelled`로 바꾸므로 `pending`이 남지 않아
  자동으로 8번(이미 처리됨)에 걸린다 — 별도 가드가 필요 없다.

## 3. F3 — 신청자 목록 조회

### 3.1 계약

`GET /api/meetings/:id/participants` (로그인 필요)

| 상황 | 응답 |
|---|---|
| 비로그인 | `UNAUTHENTICATED` (401, `requireAuth`) |
| `:id`가 양의 정수가 아님 | `NOT_FOUND` — '모임을 찾을 수 없습니다' |
| 모임 없음 | `NOT_FOUND` — '모임을 찾을 수 없습니다' |
| 모임장 아님 | `FORBIDDEN` — '모임장만 신청자 목록을 볼 수 있습니다' |
| 정상 | `200 { data: { items: [...] } }` |

`items[]` 원소:

```json
{
  "userId": 7,
  "nickname": "홍길동",
  "trustScore": 36,
  "status": "pending",
  "appliedAt": "2026-07-22T01:00:00.000Z",
  "respondedAt": null
}
```

응답을 `{ items: [] }`로 감싸는 이유: 목록 API(`listMeetings`)가 이미 `data: { items, page, totalPages, total }`
형태여서 결이 같고, 나중에 페이징을 붙일 때 응답 형태를 바꾸지 않아도 된다. 신청자가 0명이면 `items: []`.

`applied_at`·`responded_at` 컬럼은 **`timestamp`(타임존 없음)** 인데, 직렬화 결과는 **`Z`가 붙은 UTC
문자열**이다. 실제로 확인한 동작은 이렇다 — DB에 `2026-07-22 10:00:00`을 저장하면 pg 드라이버가 이를
**서버 로컬 시각(KST)으로 해석해 JS `Date`로 파싱**하고, `JSON.stringify`가 그것을 `01:00:00.000Z`로 내보낸다.
위 예시가 `10:00`이 아니라 `01:00Z`인 이유다.

값 자체는 **어긋나 있지 않다**. 브라우저가 `new Date()`로 읽어 KST로 렌더하면 저장한 벽시계 시각(10:00)이
그대로 복원된다. 서버와 클라이언트가 같은 타임존인 지금 구성에서는 정상 동작한다. 위험은 **배포 시점에
Node 프로세스의 TZ가 DB 기록 시점과 달라질 때**이며, 이는 3주차 배포에서 다뤄야 한다(`birthDate`가
`date` 타입에서 같은 이유로 문자열 변환을 택한 선례가 API 명세서에 있다).

이번 슬라이스에서 FE는 이 값을 **화면에 표시하지 않고 서버 정렬 결과만 쓰므로** 어느 쪽이든 무해하다.
마이페이지(G)에서 실제로 시각을 렌더할 때 다시 꺼낸다.

### 3.2 구현

`meetingService.listParticipants(meetingId, viewerId)`:

1. `SELECT host_id FROM meetings WHERE id = $1` → 없으면 `null` 반환(라우터가 `NOT_FOUND`)
2. `Number(row.host_id) !== Number(viewerId)` → `FORBIDDEN` (양쪽 `Number()`가 필수다 — 3.3 참조)
3. 조회:

```sql
SELECT p.user_id, u.nickname, u.trust_score, p.status, p.applied_at, p.responded_at
  FROM meeting_participants p
  JOIN users u ON u.id = p.user_id
 WHERE p.meeting_id = $1
 ORDER BY p.applied_at ASC, p.user_id ASC
```

`user_id` tiebreak를 두는 이유: `applied_at`은 `timestamp`라 동시 신청이 같은 값을 가질 수 있는데,
Postgres는 동률 행의 순서를 보장하지 않는다. tiebreak가 없으면 **같은 데이터에 같은 요청을 해도 순서가
달라질 수 있고**, 나중에 페이징을 붙이면 페이지 경계에서 행이 중복·누락된다.

(테스트에서의 동률 문제는 이것과 별개다 — 6.1의 정렬 테스트는 오히려 `applied_at`을 **서로 다르게**
명시해서 `ORDER BY` 자체를 검증한다. tiebreak는 그 테스트가 다루지 않는 운영상의 동률을 위한 것이다.)

### 3.3 pg 타입 함정 — 이 슬라이스에서 가장 위험한 지점

로컬 DB에 직접 쿼리해 확인한 결과다.

| 컬럼 타입 | JS로 오는 값 | 해당 컬럼 |
|---|---|---|
| `bigint` / `bigserial` | **문자열** `"1"` | `meetings.host_id`, `meeting_participants.user_id` |
| `numeric(4,1)` | **문자열** `"50.0"` | `users.trust_score` |
| `int` | 숫자 `1` | `meetings.capacity` 등 |

pg 드라이버는 `bigint`와 `numeric`을 정밀도 손실을 피하려 문자열로 준다. 결과적으로:

- **모임장 판정에서 `SELECT host_id`를 그대로 비교하면 안 된다.** `req.session.userId`는 숫자다
  (`userService.js:17`이 `id: Number(row.id)`로 정규화하고, `routes/auth.js:35`가 그 값을 세션에 넣는다).
  따라서 `row.host_id !== viewerId`는 `"5" !== 5` → **항상 참**이 되어 **모임장 본인까지 전원 `FORBIDDEN`** 이
  된다. 반드시 양쪽을 `Number()`로 맞춘다. 기존 `getMeetingDetail`이 안전한 것은 `normalizeMeeting`이
  `hostId: Number(row.host_id)`로 바꾼 뒤 `Number(viewerId)`와 비교하기 때문이다(`meetingService.js:219`).
- **응답의 `userId`도 `Number()`로 정규화한다.** 안 하면 JSON에 `"userId": "7"`처럼 문자열로 나가
  다른 엔드포인트(`host.id`, `myParticipation`)와 타입이 어긋난다.
- **`trustScore`는 `Number()`가 없으면 화면이 죽는다.** `TrustBadge`는 `score.toFixed(1)`을 호출하는데
  (`components/TrustBadge.jsx`) 문자열에는 `toFixed`가 없어 **TypeError**가 나고, 모임장 카드가 아니라
  상세 페이지 전체가 크래시한다. "표시가 이상해진다"가 아니라 "터진다"이다.

이 세 가지는 모두 **테스트로 잡힌다** — 6.1의 "모임장이면 200", `userId` 값 비교, 그리고 브라우저 확인
3번에서 드러난다. 다만 원인이 눈에 안 보이는 종류라 여기 미리 적어둔다.

## 4. F4 — 승인 / 거절

### 4.1 계약

`PATCH /api/meetings/:id/participants/:userId` (로그인 필요)

요청 본문: `{ "status": "approved" | "rejected" }`

검사는 아래 순서로 한다.

| # | 상황 | 응답 |
|---|---|---|
| 1 | 비로그인 | `UNAUTHENTICATED` (401, `requireAuth` 미들웨어) |
| 2 | `status`가 `approved`/`rejected`가 아님(누락·`pending`·기타) | `VALIDATION_ERROR` — 'status는 approved 또는 rejected여야 합니다' |
| 3 | `:id`가 양의 정수가 아님 | `NOT_FOUND` — '모임을 찾을 수 없습니다' |
| 3-b | `:userId`가 양의 정수가 아님 | `NOT_FOUND` — '신청을 찾을 수 없습니다' (7번과 같은 메시지) |
| 4 | 모임 없음 | `NOT_FOUND` — '모임을 찾을 수 없습니다' |
| 5 | 모임장 아님 | `FORBIDDEN` — '모임장만 신청을 처리할 수 있습니다' |
| 6 | flash 모임 | `VALIDATION_ERROR` — '소모임에서만 승인/거절할 수 있습니다' |
| 7 | 그 유저의 신청 이력 없음 | `NOT_FOUND` — '신청을 찾을 수 없습니다' |
| 8 | 이미 처리됨(`approved`/`rejected`/`cancelled`) | `VALIDATION_ERROR` — '이미 처리된 신청입니다' |
| 9 | 정상 | `200 { data: { userId, status } }` |

401(1번)은 `requireAuth` 미들웨어라 항상 가장 먼저 걸린다. 그 다음 본문 검증(2번)을 모임장 검사(5번)보다
먼저 하는 이유: 라우터에서 body를 검증하는 기존 관례(`validateCreateMeeting`)와 같고, 잘못된 본문이
`FORBIDDEN`보다 먼저 걸리므로 남의 모임 존재 여부가 오히려 덜 새어나간다.

### 4.2 구현

`meetingService.respondToApplicant(meetingId, hostId, targetUserId, status)`:

1. `SELECT host_id, type FROM meetings WHERE id = $1` → 없으면 `NOT_FOUND`
2. `Number(row.host_id) !== Number(hostId)` → `FORBIDDEN` (3.3 참조)
3. `type !== 'small'` → `VALIDATION_ERROR`
4. 조건부 갱신을 한 문장에:

```sql
UPDATE meeting_participants
   SET status = $3, responded_at = now()
 WHERE meeting_id = $1 AND user_id = $2 AND status = 'pending'
RETURNING status
```

5. `rowCount === 0`이면 추가 `SELECT status`로 두 경우를 구분한다 — 행이 없으면 `NOT_FOUND`(7번),
   있으면 `VALIDATION_ERROR`(8번).
6. 반환 `{ userId: targetUserId, status }`

**트랜잭션을 쓰지 않는다.** `WHERE status = 'pending'`이 상태 확인과 갱신을 한 문장에 담으므로 F1/F2처럼
`FOR UPDATE`로 직렬화할 필요가 없다. 같은 신청을 동시에 두 번 승인해도 두 번째 UPDATE는 0 rows가 되어
8번으로 떨어진다. 5번의 추가 SELECT는 에러 메시지를 고르기 위한 것일 뿐이라, 그 사이에 상태가 또 바뀌어
메시지가 달라져도 실제 데이터는 이미 안전하다.

이 동작은 설계 단계에서 테스트 DB에 직접 실행해 확인했다 — 같은 대상에 조건부 UPDATE를 두 번 날리면
`rowCount`가 `1` → `0`이 되고, `cancelled` 상태를 대상으로 하면 `0`이 나오며, `responded_at`은 `now()`로
채워진다. 승인 후 `confirmed`+`approved` 카운트도 정확히 1이 된다.

### 4.3 승인 철회 확장 지점

4.2의 UPDATE 위에 다음 취지의 코멘트를 남긴다.

> `WHERE status = 'pending'` 때문에 지금은 승인 철회(`approved → rejected`)가 불가능하다. 이걸 열려면
> 확정 참여자를 강제로 내보내는 셈이므로, 먼저 신뢰도 감점 여부(F2는 본인 취소에 −3)와 flash 재오픈
> 대상인지를 정해야 한다. 조건만 넓히면 정책 없이 동작이 생긴다.

## 5. 프론트엔드

### 5.1 API 모듈 (`src/api/meetings.js`)

```js
fetchParticipants(id)                    // GET  /api/meetings/:id/participants
respondToApplicant(id, userId, status)   // PATCH /api/meetings/:id/participants/:userId
```

기존 함수들과 같이 `request()`를 쓰고 `encodeURIComponent`로 경로 파라미터를 감싼다.

`respondToApplicant`는 **JSON 바디를 보내므로 `createMeeting`처럼 `Content-Type: application/json` 헤더를
명시해야 한다.** 바로 옆의 `applyToMeeting`/`cancelParticipation`은 바디가 없어 헤더를 붙이지 않으므로
그것들을 그대로 복사하면 빠뜨리기 쉽다. 빠뜨리면 `express.json()`이 본문을 파싱하지 않아 `req.body`가
`{}`가 되고, 원인을 알기 어려운 `VALIDATION_ERROR`('status는 approved 또는 rejected여야 합니다')로 나타난다.

### 5.2 `MeetingDetailPage.jsx`

카드(`191-236`줄)가 읽는 `meeting.participants`를 별도 state로 교체한다.

```js
const [participants, setParticipants] = useState([])
const [participantsError, setParticipantsError] = useState(null)
const [participantsReloadKey, setParticipantsReloadKey] = useState(0)
const [respondingUserId, setRespondingUserId] = useState(null)  // 중복 클릭 방지
```

`respondingUserId`는 요청 직전에 대상 `userId`로 세팅하고 `finally`에서 `null`로 되돌린다. 그 값과 같은
`userId`의 승인·거절 버튼 **둘 다** `disabled`로 만든다(승인을 누른 뒤 응답을 기다리는 동안 거절도 눌리면
두 번째 요청은 "이미 처리된 신청입니다"로 실패해 사용자에게 혼란스러운 에러가 뜬다).
`PillButton`은 나머지 props를 `<button>`에 그대로 전달하므로 `disabled`가 별도 수정 없이 동작한다.

**Hooks 규칙 주의**: 이 파일은 89·100줄에 조기 return이 있고 `isHost`는 그 아래(126줄)에서 계산된다.
신청자 조회 effect는 조기 return보다 위에 있어야 하므로, 모임장 여부와 `type` 판정을 조기 return 위로
끌어올려 deps에 쓴다(25줄 코멘트가 경고하는 바로 그 지점).

**끌어올릴 때 null 가드가 반드시 필요하다.** 지금의 `meeting.host.id === currentUser.id`는 조기 return
*아래*라서 `meeting`이 항상 존재하지만, 위로 올리면 로딩·에러 중 `meeting`이 `null`이라 `meeting.host.id`가
TypeError를 낸다.

```js
const isHost = meeting ? meeting.host.id === currentUser.id : false
```

`currentUser`는 가드가 필요 없다 — 비로그인이면 `GUEST_USER`(`id: null`)가 들어오도록 이미
`AppStateContext.jsx:16`에서 방어하고 있다.

effect deps는 `meeting` 객체가 아니라 **`meeting?.id`, `meeting?.type`, `isHost`, `participantsReloadKey`**로
둔다. 승인 후 상세를 재조회하면 `meeting` 객체 정체성이 바뀌는데, 객체를 deps에 넣으면 신청자 목록이
불필요하게 두 번 조회된다. 모임장이 아니거나 소모임이 아니면 조회하지 않고 `participants`를 비운다.

승인/거절 핸들러는 F1/F2의 `handleApply` 패턴을 그대로 따른다.

```js
await respondToApplicant(id, userId, status)
setParticipantsReloadKey((k) => k + 1)   // 신청자 목록 갱신
setReloadKey((k) => k + 1)               // 상세도 재조회 — confirmedCount가 approved를 세므로
```

실패 시 기존 `actionError` 배너를 재사용한다. 조회 실패는 `participantsError`로 카드 안에만 표시해서
상세 화면 전체가 에러로 바뀌지 않게 한다.

**카드 상단 카운트(D6)**: 지금 191줄은 `participants.length`를 그대로 "신청자 N명"으로 쓴다. D3으로 목록에
`cancelled`·`rejected`까지 담기므로 그대로 두면 취소자가 신청자로 집계된다. N은 **`pending` + `approved`만**
센다. 193줄의 빈 상태 문구("아직 신청자가 없어요")는 **`participants.length === 0`일 때만** 띄운다 —
신청 이력이 전부 취소·거절이면 카운트는 0이지만 목록에는 행이 있으므로, 카운트 기준으로 빈 상태를
띄우면 "신청자가 없어요"라고 써놓고 그 아래에 사람 목록이 깔리는 모순이 생긴다.

## 7. 리스크

- **pg 타입 함정**(3.3) — `bigint`·`numeric`이 문자열로 온다. `host_id`를 그대로 비교하면 모임장까지
  전원 `FORBIDDEN`이 되고, `trustScore`를 정규화하지 않으면 `TrustBadge`의 `toFixed`가 TypeError를 낸다.
  이 슬라이스에서 **가장 위험한 지점**이다.
- **가짜 정렬 테스트**(6.1) — `applied_at`을 명시하지 않으면 `ORDER BY` 없는 구현도 통과한다.
- **Hooks 규칙 위반 + null 역참조**(5.2) — 조기 return 아래에 effect를 두면 React가 런타임 에러를 던지고,
  `isHost`를 위로 올리면서 null 가드를 빠뜨리면 로딩 중 `meeting.host.id`가 터진다. 1주차에 이 근처
  (StrictMode 경합)에서 실버그를 겪었으므로 주의한다.
- **이중 조회** — effect deps에 `meeting` 객체를 넣으면 승인마다 신청자 목록을 두 번 조회한다.
  deps를 `meeting?.id`/`meeting?.type`으로 두는 이유가 이것이다.
- **정렬 비결정성**(3.2) — `applied_at` 동률에서 tiebreak가 없으면 같은 요청의 순서가 매번 달라질 수 있다.
- **중복 테스트**(6.1) — "거절당한 사람은 재신청 불가"는 이미 커버돼 있다. F4 경로를 거치는 형태로만 가치가 있다.
- 신청자 목록 조회가 실패해도 상세 페이지 전체가 죽지 않아야 한다(5.2).
