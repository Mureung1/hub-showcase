# 신뢰도 시스템 개편 설계 — 모임 후 상호 평가 기반

- 날짜: 2026-07-22
- 상태: **설계 확정, 구현은 MVP 완성(2026-07-24) 이후**
- 범위: `users.trust_score`의 산출 방식을 "취소 시 −3" 단일 규칙에서, 모임 후 상호 평가 이력으로부터 계산하는 비공개 알고리즘으로 교체

## 1. 왜 바꾸는가

기획서 187번은 신뢰도를 "당근마켓 온도와 유사한 개인별 평점"으로 정의하고, 강제 제재 없이 공개해서 모임장의 승인 판단에 참고되게 한다고 정했다. 그런데 현재 구현은 그 정의에 한참 못 미친다.

**지금 점수를 바꾸는 코드는 딱 한 곳이다.**

```js
// F2 참여 취소 — confirmed/approved 상태였을 때만
UPDATE users SET trust_score = GREATEST(trust_score - 3, 0)
```

여기서 나오는 문제가 셋이다.

1. **올라갈 방법이 없다.** 전원 50.0에서 시작해 내려가기만 한다. 성실하게 참여해도 보상이 없다.
2. **규칙이 단순해서 역산된다.** 몇 번만 관찰하면 "확정 후 취소 = −3"을 알아낼 수 있고, `pending` 취소는 무료라는 것도 드러난다.
3. **인센티브가 뒤집혀 있다.** 취소하면 −3, 잠수(노쇼)하면 0점이다. 규칙을 아는 사용자에게 최적 전략은 **"못 가겠으면 취소하지 말고 그냥 안 나가는 것"** 이다. 모임장 입장에선 정반대가 이롭다 — 미리 취소해주면 자리를 채울 수 있다.

3번이 핵심이다. 지금 시스템은 **가장 나쁜 행동에 가장 낮은 벌을 준다.** 노쇼를 감지할 수단이 없기 때문이다.

## 2. 확정한 결정

브레인스토밍에서 정한 것들이다. 각 결정의 근거를 함께 남긴다 — 나중에 "왜 이렇게 했지"를 다시 캐지 않기 위해서다.

| # | 결정 | 근거 |
|---|---|---|
| D1 | 막을 대상은 **감점 회피 + 점수 파밍 둘 다** | 규칙이 투명해서 생기는 문제 전반을 다룬다 |
| D2 | **모임 후 상호 평가**를 점수의 주 입력으로 도입 | 노쇼는 사람만 관찰할 수 있다. 평가 기능 없이는 어떤 공식을 짜도 노쇼 구멍이 남는다 |
| D3 | 구현은 **MVP 이후** | 테이블 신설 + 종료 감지 + 평가 API + UI + 산식 + 표시 변경. 하루에 안 끝난다 |
| D4 | 평가는 **모임장 ↔ 확정 참여자 양방향** | 모임장→참여자로 노쇼를 잡고, 참여자→모임장으로 사기성 모임을 잡는다. 참여자끼리는 서로 모르는 경우가 많고 평가 수가 인원²로 늘어 제외 |
| D5 | **출석 체크는 필수, 태그는 선택** | "왔는가"는 사실, "어땠는가"는 주관이라 분리한다. 태그를 필수로 하면 알림 없는 환경에서 완료율이 떨어진다 |
| D6 | 발견 경로는 **마이페이지 배지 + 신청 시 소프트 게이트** | 이 앱에는 알림이 없다(기획서 6.3). 하드 게이트는 "강제 제재 없음" 방침과 충돌 |
| D7 | **미평가는 중립** (점수 영향 0) | 평가를 안 했다고 감점하면 그 자체가 강제가 된다 |
| D8 | **평가 이력이 원본, 점수는 파생값** | 공식을 나중에 바꿔 전체 재계산할 수 있다. 역산 방지에도 유리하다 — 공식을 조용히 바꾸면 사용자가 알아낸 규칙이 계속 낡는다 |
| D9 | **최근성 가중** — 최근 평가일수록 크게 | 사용자 요청. 과거 한 번의 실수가 영원히 따라다니지 않게 한다 |
| D10 | 취소는 **전부 기록하되 가중치 비대칭** | 노쇼 크게, 임박 취소 작게, 조기 취소 0. "못 가면 일찍 취소해라"가 최적 전략이 되도록 인센티브를 바로잡는다 |
| D11 | 표시는 **정수 + 색 밴드**, 표시 레이어 분리 | 소수점은 −3 같은 작은 변화를 정확히 관측하게 해준다. 나중에 이모지로 교체 가능하게 등급 매핑을 한 곳에 둔다 |
| D12 | 파밍 방지 = **동일 상대 반복 체감 + 상승 포화** | 다양성 가중(대안)은 동네 소모임의 정상 행동을 벌할 위험이 있다 |
| D13 | 평가 자격은 **확정(`approved`/`confirmed`)이었던 사람만** | 거절당한 사람의 보복 평가를 원천 차단한다 |
| D14 | 진술이 **엇갈리면 양쪽 모두 0점** | 노쇼 판정은 일방적이다. 누가 맞는지 모를 때는 벌하지 않는다 |

### 검토 과정에서 스스로 고친 것

설계를 다시 훑으며 발견한 결함들이다. 같은 실수를 반복하지 않도록 남긴다.

- **반복 가중치의 순서가 거꾸로였다.** "같은 사람에게 받는 n번째 평가는 1/n"을 시간순으로 세면, 최근성 감쇠로 이미 6%만 남은 옛 평가가 가중치 1.0 자리를 차지하고 최근 평가가 1/n으로 깎인다. **최신순으로 센다**(가장 최근 평가가 1번).
- **취소된 모임이 평가 대상에서 안 빠져 있었다.** E5로 취소된 모임도 시간이 지나면 "끝난" 상태가 된다.
- **부정 태그에 상한이 없었다.** 긍정만 "최대 3개"로 막아뒀다.
- **평가 수정·철회 규칙이 없었다.**
- **신규 사용자와 상쇄된 사용자가 구분되지 않는다.** 둘 다 50점이다.

## 3. 데이터 모델

### 3.1 `meeting_evaluations` — 평가 이력 (원본)

```
id            bigserial PK
meeting_id    bigint NOT NULL → meetings
rater_id      bigint NOT NULL → users     평가한 사람
ratee_id      bigint NOT NULL → users     평가받은 사람
attended      boolean NOT NULL            평가 대상이 실제로 왔는가
tags          text[] NOT NULL DEFAULT '{}'  선택한 태그 코드
created_at    timestamp NOT NULL DEFAULT now()
updated_at    timestamp NOT NULL DEFAULT now()

UNIQUE (meeting_id, rater_id, ratee_id)
```

`UNIQUE` 제약이 한 모임에서 같은 사람을 두 번 평가하는 것을 막는다.

### 3.2 `participation_cancellations` — 취소 이력 (append-only)

```
id                 bigserial PK
meeting_id         bigint NOT NULL → meetings
user_id            bigint NOT NULL → users
cancelled_at       timestamp NOT NULL DEFAULT now()
was_confirmed      boolean NOT NULL   확정 상태에서 취소했는가
hours_before_start numeric NOT NULL   모임 시작까지 남은 시간(취소 시점 스냅샷)
```

**이 테이블이 왜 필요한가**: `meeting_participants`는 (모임, 사용자)당 한 행뿐이고, `applyToMeeting`이 취소된 행을 되살릴 때 `applied_at`·`responded_at`을 덮어쓴다. 즉 **"몇 번 취소했는지"가 남지 않는다.** D10의 취소 가중치를 계산할 데이터가 아예 없다.

`hours_before_start`를 계산해서 저장하는 이유: 나중에 모임 시작 시각이 수정되면(E4) 재계산 시 값이 달라진다. **취소 당시의 판단이 맞으므로 스냅샷으로 굳힌다.**

### 3.3 `users` 변경

```
trust_score            numeric(4,1)  → 의미 변경: 원본이 아니라 계산 결과 캐시
trust_score_updated_at timestamp     → 신규. 언제 계산된 값인지
evaluation_count       int           → 신규. 점수에 반영된 평가 수 (D11 보완, 4.4 참조)
```

`evaluation_count`는 **점수 계산에 실제로 반영된 평가만** 센다. 6장의 진술 불일치로 무효 처리된 평가는 제외한다 — 화면에 "평가 14건"이라고 띄우는 목적이 "이 점수가 얼마나 많은 근거 위에 있는가"를 보여주는 것이므로, 무효표를 포함하면 그 목적을 배신한다. 점수를 재계산할 때 같이 갱신한다.

### 3.4 태그와 가중치는 코드 상수

DB가 아니라 코드에 둔다. 비공개가 목적인데 DB에 있으면 노출 경로가 하나 더 생기고, 코드에 있으면 git으로 변경 이력이 남고 배포로 조용히 바꿀 수 있다.

## 4. 평가 흐름

### 4.1 언제 열리는가

모임 종료(`COALESCE(end_at, start_at) < now()`) 후 **14일간**. 단, **`meetings.status = 'cancelled'`인 모임은 열리지 않는다.**

14일로 제한하는 이유: 오래된 모임의 기억은 부정확하고, 무한정 열어두면 "언제든 하지" 하고 안 한다.

### 4.2 누가 누구를

```
모임장       →  확정 참여자 전원   (한 화면에서 출석 체크로 일괄 처리)
확정 참여자  →  모임장             (각자)
```

**확정(`approved`/`confirmed`)이었던 사람만** 평가 자격이 있다(D13).

**질문 문구는 모임 타입에 따라 다르다.** `attended`는 `boolean` 하나로 같지만 묻는 말이 달라야 한다. 번개모임은 한 번 만나고 끝이라 "왔는가"가 명확하지만, 소모임은 기간형이다(개발 DB의 `#4`는 7/23~9/20, 두 달). 두 달짜리 모임에 "오셨나요?"는 어느 날을 말하는지 알 수 없다.

| 타입 | 모임장 → 참여자 | 참여자 → 모임장 |
|---|---|---|
| `flash` | "이 분이 오셨나요?" | "모임장이 오셨나요?" |
| `small` | "이 분이 모임에 성실히 참여했나요?" | "모임장이 모임을 성실히 이끌었나요?" |

데이터 구조와 산식은 동일하다. **화면 문구만 분기한다** — 3단계 척도(성실/일부/거의 안 옴)로 늘리면 6장 진술 대조 표의 경우의 수가 9줄에서 급증하는데, 그만한 값어치가 없다고 판단했다.

남는 한계: 소모임은 **종료 후에야 평가창이 열리므로 두 달 뒤에 평가하게 된다.** 기억이 흐릿한 상태의 평가라 정확도가 떨어진다. 기간 중 평가를 허용하는 방안은 "언제 평가창이 열리는가" 규칙이 복잡해져 이번 범위에서 제외했다(9장).

### 4.3 발견 경로 (D6)

- 마이페이지에 "평가할 모임" 섹션 + 하단 네비 아이콘에 **개수 배지**
- 새 모임에 **신청하려 할 때** 미평가가 있으면 한 번 권유 — **건너뛰기 허용**

### 4.4 표시 (D11)

```
지금:   신뢰도 50.0
바꾸면: 🟢 신뢰도 50 · 평가 14건
```

- 내부 계산은 소수점을 유지하고 **표시할 때만** 반올림한다.
- 점수 → 등급 매핑을 **한 곳에** 두고 색·이모지·라벨을 거기서 파생시킨다. 나중에 색 밴드를 이모지로 바꿀 때 그 파일만 고치면 된다.
- **평가 건수를 함께 노출한다.** 평가 0건인 신규 사용자와, 좋은 평가·나쁜 평가가 상쇄되어 50이 된 사용자가 똑같이 보이는 문제를 보완한다.

### 4.5 수정·철회

제출 후 **24시간 내 1회 수정 허용**, 그 뒤 잠금. 잘못 눌렀을 때의 구제책은 필요하지만, 무기한 수정을 허용하면 상대의 평가를 보고 바꾸는 눈치 게임이 생긴다.

## 5. 점수 산식

### 5.1 형태

```
S = Σ (이벤트 점수 × 최근성 가중치 × 반복 상대 가중치)

신뢰도 = 50 + 50 × tanh(S / K)      K = 40 (S > 0) / 25 (S < 0)
```

`tanh`를 쓰는 이유는 **포화가 공식 하나로 해결되기 때문**이다. S가 아무리 커져도 100을 넘지 않고 0 밑으로도 가지 않는다. 곡선이 완만해지는 성질 덕에 50→60은 쉽고 80→90은 훨씬 어렵다 — D12의 상승 포화가 자동으로 나온다. 별도 상한 로직이 필요 없다.

`K`를 부호에 따라 다르게 둔 것이 **비대칭**이다. `K_up(40) > K_down(25)` → **잃기는 쉽고 쌓기는 어렵다.**

### 5.2 이벤트 점수 (초깃값, 전부 코드 상수)

| 이벤트 | 점수 |
|---|---|
| 출석 확인 (`attended = true`) | +1.0 |
| 긍정 태그 (개당, **최대 3개**) | +0.5 |
| 노쇼 (`attended = false`, 확정된 경우만 — 6장 참조) | −5.0 |
| 부정 태그 (개당, **최대 3개**) | −2.0 |
| 확정 상태에서 **24시간 이내** 취소 | −1.5 |
| 그보다 이른 취소 / `pending` 취소 | 0 |

### 5.3 가중치

- **최근성**: `0.5 ^ (경과일 / 90)` — 90일이면 절반, 1년 전 평가는 6%가 남는다.
- **반복 상대**: 같은 사람에게 받은 평가를 **최신순**으로 세어 `n`번째는 `1/n`배. 가장 최근 평가가 1.0, 그다음 0.5, 그다음 0.33.

### 5.4 실제 움직임

| 상황 | S | 점수 |
|---|---|---|
| 신규 가입 | 0 | **50** |
| 서로 다른 모임 5회 성실 참여 | 10 | **62** |
| 서로 다른 모임 20회 | 40 | **88** |
| **친구 3명과만 20회** | 15.5 | **69** |
| 노쇼 1회 | −5 | **40** |
| 노쇼 3회 | −15 | **23** |

같은 20회인데 다양한 사람과면 88, 친구 3명과면 69다. D12가 막으려던 파밍 시나리오가 여기서 꺾인다.

### 5.5 재계산 시점

**평가가 제출·수정되거나 취소가 발생할 때만** 재계산한다. 평가의 경우 **rater와 ratee 두 사람 모두**가 대상이다(6.2 참조) — 진술 대조 때문에 한쪽의 제출이 상대의 판정을 바꾼다.

최근성 감쇠 때문에 아무 일이 없어도 시간이 지나면 이론상 점수가 변하지만, **그것을 실시간으로 반영하지 않는다.** 조회 시점에 재계산하면 모임장 카드에 신청자 10명이 뜰 때 10명분 이력 스캔과 UPDATE가 한 번의 페이지 로드에서 일어난다 — **읽기가 쓰기를 유발한다.** 상세 조회는 이미 쿼리를 4번 돌고 있어 그 위에 얹기 부담스럽다.

결과적으로 활동이 없는 사용자의 점수는 마지막 이벤트 시점의 값으로 남아 있다가, 다음 이벤트 때 한 번에 보정된다. 크론 같은 인프라를 새로 들이지 않는다.

## 6. 진술 대조 규칙 (D14)

노쇼 판정은 일방적이다. 모임장이 "안 왔어요"를 누르면 참여자는 반박할 수단이 없다. 그래서 **양쪽 진술을 대조**한 뒤에 점수를 매긴다.

규칙은 **양방향 대칭**이다. 모임장이라고 특별대우하지 않는다.

| 모임장 → 참여자 A | A → 모임장 | A 점수 | 모임장 점수 |
|---|---|---|---|
| 제출 안 함 | 제출 안 함 | 0 | 0 |
| 제출 안 함 | 왔음 | 0 | 정상 반영 (+) |
| 제출 안 함 | **안 왔음** | 0 | **노쇼 확정 (−5)** |
| 왔음 | 제출 안 함 | 정상 반영 (+) | 0 |
| 왔음 | 왔음 | 정상 반영 (+) | 정상 반영 (+) |
| 왔음 | **안 왔음** | **0 (불일치)** | **0 (불일치)** |
| **안 왔음** | 제출 안 함 | **노쇼 확정 (−5)** | 0 |
| **안 왔음** | 왔음 | **0 (불일치)** | **0 (불일치)** |
| **안 왔음** | **안 왔음** | **0 (상호 지목)** | **0 (상호 지목)** |

**"제출 안 함"이 만드는 결과를 분명히 해둔다**: 모임장이 평가를 안 하면 그 모임에서 **노쇼가 있어도 아무 감점이 없다.** D7(미평가 중립)의 필연적 결과이고, 의도된 동작이다. 모임장에게 평가를 강제하지 않기로 한 이상 이 구멍은 남는다 — 대신 모임장 본인도 그 모임에서 점수를 얻지 못한다.

**상호 지목을 0점으로 두는 이유**: 둘 다 "상대가 안 왔다"고 하면 누가 맞는지 알 수 없다. 실제로 모임장이 안 나타나서 참여자가 지목했는데 모임장이 덮으려고 맞지목하는 상황이 여기 걸리는데, 양쪽 −5로 처리하면 **피해자를 벌하게 된다.** 진술이 엇갈릴 때 벌하지 않는다는 D14의 철학을 그대로 적용한다.

**대가**: 진짜 노쇼도 "모임장 안 왔어요" 한 번이면 빠져나간다. 이것이 D14를 택하며 감수한 비용이고, 악용이 관찰되면 6장만 고쳐 재계산하면 된다(D8의 이점).

**불일치가 무효화하는 범위**: 그 모임에서 두 사람 사이의 평가 **양쪽 모두**(출석 판정과 태그 전부). 다른 참여자들의 평가는 영향받지 않는다.

### 6.1 D7(미평가 중립)과 헷갈리지 말 것

표의 "안 왔음 + 제출 안 함 → −5"는 **미평가를 벌하는 것이 아니다.** A가 평가를 안 했다는 사실 자체에는 아무 점수도 붙지 않는다. 다만 반박이 없으니 **모임장의 평가가 그대로 적용될 뿐**이다. D7은 "평가하지 않은 사람에게 페널티를 주지 않는다"는 뜻이고, "남이 나를 평가한 것을 무효로 만든다"는 뜻이 아니다.

### 6.2 판정은 실시간으로 반영하고, 뒤집힐 수 있다

평가 창(14일)이 열려 있는 동안 상대가 나중에 제출하면 **판정이 바뀐다.** 예를 들어 모임장이 A를 노쇼로 찍은 시점에 A는 −5를 받지만, A가 열흘 뒤 모임장을 "왔음"으로 평가하면 불일치가 되어 **양쪽 0점으로 되돌아간다.**

판정을 창이 닫힌 뒤에 일괄 확정하는 방식도 가능하지만, 그러려면 스케줄러가 필요하다 — 5.5에서 크론을 들이지 않기로 한 결정과 어긋난다. **점수가 14일 동안 흔들릴 수 있음을 감수하고 실시간 반영을 택한다.**

이 때문에 재계산 대상이 한 명이 아니다. 평가가 제출·수정되면 **그 평가에 얽힌 두 사람(rater와 ratee)을 모두** 재계산해야 한다. 한쪽만 갱신하면 상대의 점수가 낡은 판정에 머문다.

## 6.3 선행 조건 — F2에 `is_past` 가드를 넣어야 한다

**이 설계는 F2(참여 취소)에 종료 가드가 없으면 무력화된다.**

평가 자격은 "확정이었던 사람"인데, `meeting_participants`에는 **현재 상태만** 남는다. 그리고 지금 `cancelParticipation`은 이미 끝난 모임도 취소할 수 있다(Day2 리뷰에서 "엣지·무해"로 미뤄둔 항목).

```
A가 모임에 안 감 (노쇼)
  → 모임 종료
  → A가 취소를 누름 → status = 'cancelled'
  → 평가 대상에서 빠짐 → 모임장이 노쇼로 찍을 수 없음 → −5 회피
```

노쇼 −5를 피하려고 취소를 누르는 것이 명백히 이득이 되어, **이 시스템의 존재 이유(노쇼 잡기)가 그대로 무너진다.** Day2에 "무해"로 분류한 판단은 평가 시스템이 없던 시점에서만 맞았다.

**대응**: `cancelParticipation`에 `is_past` 가드를 넣어 **종료된 모임은 취소할 수 없게** 한다. 이 수정은 평가 시스템과 독립적이고 작으므로 **먼저 적용해도 된다** — 지난 모임을 취소한다는 것 자체가 말이 안 되므로 그 자체로 올바른 수정이다.

부수적으로 `participation_cancellations.hours_before_start`는 **항상 양수**가 보장된다. 가드가 없으면 종료 후 취소에서 음수가 나오는데, 그 경우의 가중치가 정의되어 있지 않았다.

## 7. 전환

- 기존 사용자는 전원 50.0이고 감점된 사람이 없다. **그대로 두고** 새 이력이 쌓이는 대로 갱신한다.
- `cancelParticipation`(F2)의 `trust_score - 3` **즉시 감점 코드를 제거**하고, 대신 `participation_cancellations`에 기록만 한다.
- 이력이 없는 과거 감점은 재계산 대상이 아니다. 전환 시점에 감점된 사용자가 있다면 그 값을 유지한 채 새 이력이 덮어쓰게 둔다.

**표시 변경(4.4)은 선행 적용 가능하다.** 평가 시스템 전체를 기다릴 필요 없이, 응답에서 반올림해 내려보내고 `TrustBadge`에 등급 매핑을 붙이면 된다. 나중에 그대로 재사용한다.

## 8. 테스트 관점

구현 시점에 정할 것들이지만, 놓치기 쉬운 지점을 미리 적어둔다.

- **산식은 순수 함수로 분리**해서 이력 배열 → 점수를 단위 테스트한다. 5.4 표의 6가지 시나리오가 그대로 테스트 케이스가 된다.
- **6장의 진술 대조 표 6줄을 각각 테스트**한다. 이 표가 이 설계에서 가장 헷갈리는 부분이다.
- **반복 가중치가 최신순인지** 검증한다 — 시간순으로 세도 통과하는 테스트를 만들지 않도록, 평가 시각을 서로 다르게 배치하고 순서를 바꾸면 결과가 달라지는지 확인한다.
- **취소된 모임에 평가 창이 열리지 않는지**(4.1).
- 평가 자격이 없는 사람(거절·취소·미참여)이 평가를 시도하면 거부되는지(D13).

## 9. 미해결 / 후속

- **태그 목록을 확정하지 않았다.** 긍정·부정 각각 어떤 문구를 둘지는 구현 시점에 정한다. 가중치 구조(긍정 +0.5, 부정 −2.0, 각 최대 3개)만 확정했다.
- **평가 UI의 구체적 화면 설계**는 이 문서 범위 밖이다.
- **점수 하한선 활용**은 도입하지 않는다. 기획서 187번이 "시스템적으로 강제 제재하지 않는다"고 못 박았으므로, 점수가 낮다고 신청을 막지 않는다. 모임장이 보고 판단할 뿐이다.
- **초깃값 튜닝**: 5.2의 숫자들은 근거 있는 추정이지 검증된 값이 아니다. D8(이력 기반)을 택한 이유가 이것이다 — 실제 데이터가 쌓이면 조정하고 전체 재계산한다.
- **소모임 기간 중 평가**는 도입하지 않았다(4.2). 두 달짜리 모임을 종료 후에 평가하는 정확도 문제는 남는다. 필요해지면 "기간형 모임은 시작 후 N일마다 평가창을 연다" 같은 규칙을 별도로 설계해야 한다.
- **모임장이 평가를 안 하면 그 모임의 노쇼는 잡히지 않는다**(6장). 모임장에게 평가를 강제하지 않기로 한 이상 남는 구멍이다. 평가율이 실제로 얼마나 나오는지 보고 다시 판단한다.
