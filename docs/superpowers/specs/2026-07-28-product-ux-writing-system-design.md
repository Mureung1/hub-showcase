# 제품 UX Writing 체계와 전면 문구 전환 설계

## 문서 상태

- 작성일: 2026-07-28
- 관련 이슈: [#87 제품 문체와 상태 문구 체계를 정립한다](https://github.com/ppre1ude/hub/issues/87)
- 상위 외부 기준: [앱인토스 UX 라이팅 가이드](https://developers-apps-in-toss.toss.im/design/ux-writing.html)
- 상태: 설계 방향 승인 완료, 작성 명세 검토 대기

2026-07-28 사용자와 적용 범위를 검토한 결과, 가져오기 화면만 먼저 바꾸지 않고 사용자가 제품 여정에서 만나는 모든 문구를 한 PR에서 함께 개정하기로 했다. 웹 앱, Android 공유, Chrome 확장과 접근성 문구를 같은 기준으로 전환하되 기능 동작과 데이터 계약은 바꾸지 않는다.

## 배경

현재 제품은 전반적으로 친근한 해요체를 사용하지만 화면과 상태에 따라 다음 표현이 섞여 있다.

- `저장됨`, `맥락 저장 완료`, `가져오기를 완료했어요`처럼 명사형과 문장형이 혼재한다.
- `입력해주세요`와 `입력해 주세요`, `~했습니다`와 `~했어요`가 함께 사용된다.
- `계속`, `완료`, `확인`처럼 다음 결과를 예측하기 어려운 행동 문구가 있다.
- 오류마다 발생한 일, 보존된 내용과 다음 행동을 알려주는 정도가 다르다.
- `인사이트`, `링크`, `분류`, `카테고리`처럼 같은 대상을 가리키는 제품 용어가 화면별로 달라진다.
- 화면에 보이는 문구와 접근 가능한 이름의 표현 수준이 다른 경우가 있다.

`src`, `extension`, `server`, `api`의 테스트·픽스처를 제외한 1차 정적 검색에서는 한국어 문구 후보 512줄이 확인됐다. 이 수치에는 사용자 문구가 아닌 내부 예외와 개발자 메시지도 포함되므로, 실제 전환 대상은 인벤토리에서 `개정`, `유지`, `제외`로 분류한다.

가져오기만 먼저 바꾸면 로그인, 저장, 보관함과 꺼내보기에서 기존 문체를 다시 만나 제품 목소리가 끊긴다. 따라서 가이드를 먼저 고정하고 전체 사용자 여정을 같은 변경 안에서 전환한다.

## 목표

- 앱인토스 UX 라이팅 원칙을 아맞다의 도메인과 제품 원칙에 맞게 적용한다.
- 모든 사용자 노출 문구를 화면·상태·역할별로 확인하고 개정 또는 유지 근거를 남긴다.
- 웹, Android 공유와 Chrome 확장에서 하나의 제품 목소리를 제공한다.
- 버튼 문구만 읽어도 다음 행동과 결과를 예측할 수 있게 한다.
- 오류와 상태 문구만 읽어도 현재 상황, 보존된 내용과 가능한 다음 행동을 알 수 있게 한다.
- 화면 문구와 보조기술 문구가 같은 의미를 전달하게 한다.
- 기능 경계를 넘는 불필요한 테스트를 늘리지 않고 실제 회귀 위험에 맞는 최소 검증을 둔다.

## 비목표

- 기능 정책, 상태 전이, API 요청·응답과 데이터 저장 형식 변경
- 레이아웃 재설계, 글꼴, 크기와 행간 같은 시각적 타이포그래피 변경
- 다국어 지원 또는 전역 문구 사전 도입
- 내부 로그, 개발자 전용 예외와 코드 주석의 문체 개정
- 테스트 설명, 픽스처와 사용자가 입력한 콘텐츠 개정
- 외부 서비스가 생성하거나 소유한 문구 개정
- 이용약관, 개인정보처리방침과 보안 안내의 법적·정책적 의미 변경

## 기준의 우선순위

문구 기준이 충돌하면 다음 순서로 판단한다.

1. 기능, 보안, 개인정보와 법적 의미를 정확하게 유지한다.
2. 아맞다의 도메인 언어와 제품 원칙을 유지한다.
3. 앱인토스 UX 라이팅 가이드의 문체 규칙을 적용한다.
4. 화면 공간, 접근성 역할과 사용 맥락에 맞게 길이를 조정한다.

토스의 제품 고유 용어를 복제하지 않는다. 해요체, 능동형, 긍정형, 캐주얼한 경어와 동사 중심 표현을 아맞다의 용어에 적용한다.

### 포함 여부 판단

- 사용자가 볼 수 있거나 보조기술로 들을 수 있으면 인벤토리에 포함한다.
- 같은 문구가 여러 곳에 쓰이면 한 행에 대표 문구를 적고 모든 구현 위치를 연결한다.
- 변경하지 않는 내비게이션, 필드 라벨과 짧은 행동도 `유지`로 기록한다.
- 서버 오류는 화면에 직접 전달되는 경우만 포함한다. 내부에서 안전한 사용자 문구로 교체되는 원본 오류는 제외한다.
- 동적으로 결합되는 문구는 데이터 자리를 표시한 완전한 문장으로 기록한다.

## 기본 보이스

### 해요체

- 설명, 상태, 질문과 오류 문장은 모두 해요체로 쓴다.
- `~했습니다`, `~합니다`, `~하십시오`를 제품 문장에 사용하지 않는다.
- 필드 라벨, 내비게이션 이름, 수량 레이블과 행동 버튼은 문장이 아니므로 짧은 명사형 또는 행동형을 사용할 수 있다.

### 능동형

- 가능한 경우 사용자의 행동이나 제품이 수행한 일을 주어로 둔다.
- `가져오기가 완료됐어요`보다 `인사이트 3개를 보관함에 추가했어요`를 우선한다.
- 주어가 없어도 의미가 명확하면 반복하지 않는다.
- 기간 만료, 사용자 행동의 영향과 안심을 더 정확하게 전달할 때만 수동형을 허용한다.

### 긍정형

- 사용할 수 없는 사실만 강조하지 않고 가능한 다음 행동을 함께 알려준다.
- 실제로 기능을 사용할 수 없거나 결과가 없다는 사실이 중요한 경우에는 부정형을 허용한다.
- 오류를 축소하거나 성공처럼 표현하지 않는다. 정확한 상황과 복구 행동을 함께 쓴다.

### 캐주얼한 경어

- 기본적으로 `~시`, `~시겠어요`, `~께` 같은 과도한 경어를 쓰지 않는다.
- 사용자의 맥락을 조심스럽게 확인하거나 선의가 필요한 질문에만 제한적으로 쓸 수 있다.
- `해주세요`는 `해 주세요`, `되어요`는 `돼요`로 쓴다.

### 동사 중심 표현

- 한자어 명사를 연달아 쓰지 않고 사용자가 이해할 수 있는 동사로 푼다.
- `맥락 저장 완료`보다 `메모와 카테고리를 저장했어요`를 사용한다.
- 기술 상태 이름보다 사용자가 기다리는 일을 설명한다.

## 용어 계약

| 의미                  | 권장 표현  | 피할 표현과 사용 기준                                  |
| --------------------- | ---------- | ------------------------------------------------------ |
| 저장한 대상           | `인사이트` | 저장된 대상을 `링크`라고 부르지 않는다.                |
| 주소를 대화에서 지칭  | `링크`     | `원문 URL`을 사용하지 않는다.                          |
| 입력 형식·검증 대상   | `URL`      | `링크 URL`처럼 같은 뜻을 겹치지 않는다.                |
| 저장 장소             | `보관함`   | 저장 행동 자체를 `보관함`으로 부르지 않는다.           |
| 분류 기준             | `카테고리` | 사용자 UI에서 같은 개념을 `분류`와 섞지 않는다.        |
| 외부 자료 이전        | `가져오기` | 데이터 이관, 마이그레이션 같은 내부 용어를 피한다.     |
| 현재 상황으로 발견    | `꺼내보기` | 검색과 목적을 섞지 않는다.                             |
| 일반 단서 검색        | `검색`     | 꺼내보기와 구분한다.                                   |
| 이전 가져오기 취소    | `되돌리기` | 사용자 UI에서 `Undo`를 사용하지 않는다.                |
| 외부 서비스 권한 연결 | `연결`     | 인증·토큰 같은 내부 구현을 불필요하게 노출하지 않는다. |

`원문 열기`처럼 외부 페이지를 여는 행동은 문맥상 자연스러우면 유지할 수 있다. 주소 자체를 가리키는 명칭에서는 `링크` 또는 `URL`만 사용한다.

## 역할별 작성 규칙

### 제목

- 현재 결과나 사용자가 할 일을 한 문장으로 전달한다.
- 완전한 문장형 제목에는 마침표를 쓰지 않는다.
- 메뉴, 화면 이름과 필드 그룹은 짧은 명사형을 유지할 수 있다.

### 본문과 보조 설명

- 한 문장에는 핵심 정보 하나를 둔다.
- 사용자가 이미 화면에서 알 수 있는 제목과 버튼을 반복하지 않는다.
- 기능 설명보다 지금 필요한 정보와 다음 행동을 우선한다.
- 완전한 문장은 마침표로 끝낸다.

### 버튼

- 누른 뒤 일어날 행동이나 결과를 동사로 표현한다.
- `계속`, `완료`, `확인`처럼 결과를 예측하기 어려운 문구는 구체화한다.
- 일반 다이얼로그의 왼쪽 닫기 행동은 `닫기`를 사용한다.
- 실제 진행 중인 작업을 멈추는 경우에는 `Notion 연결 그만두기`처럼 대상을 명시한다.
- 위험한 행동은 `삭제하기`, `가져오기 되돌리기`처럼 영향을 드러낸다.

### 입력

- 보이는 라벨은 입력 대상의 이름을 간결하게 쓴다.
- placeholder는 라벨을 반복하지 않고 형식이나 예시가 필요할 때만 쓴다.
- 선택 입력은 라벨 뒤에 `(선택)`으로 통일한다.
- 오류는 입력과 연결하고 해결 방법을 알려준다.

## 상태 문구

| 상태         | 기본 구조                             | 예시                                                                                  |
| ------------ | ------------------------------------- | ------------------------------------------------------------------------------------- |
| 진행 중      | 지금 하는 일을 능동형으로 설명        | `가져올 내용을 확인하고 있어요`                                                       |
| 성공         | 실제 결과와 필요한 다음 행동          | `인사이트 3개를 보관함에 추가했어요`                                                  |
| 오류         | 발생한 일 → 보존된 내용 → 다음 행동   | `가져올 내용을 확인하지 못했어요. 입력한 링크는 그대로 두었어요. 다시 시도해 주세요.` |
| 초기 빈 상태 | 시작 행동 → 얻는 결과                 | `첫 인사이트를 저장하면 여기에서 다시 찾을 수 있어요`                                 |
| 결과 없음    | 찾지 못한 범위 → 바꿀 수 있는 입력    | `이 검색어로 찾은 인사이트가 없어요. 검색어를 줄이거나 다른 단서를 입력해 보세요.`    |
| 확인         | 실행할 행동 → 사용자 영향 → 닫기 경로 | `이 가져오기를 되돌릴까요? 이 작업에서 새로 만든 인사이트만 삭제해요.`                |
| 만료         | 만료된 대상과 현재 가능한 행동        | `되돌릴 수 있는 기간이 지났어요`                                                      |

오류 문구는 내부 코드, 스택, 토큰, 원본 서버 응답과 재시도 구현을 노출하지 않는다. 제품이 자동으로 처리하는 내부 재시도는 사용자의 다음 행동에 영향을 줄 때만 설명한다.

## 접근성 문구

- 화면에 보이는 문구와 접근 가능한 이름은 같은 행동과 결과를 뜻해야 한다.
- 공간 때문에 보이는 레이블을 줄여도 `aria-label`은 대상을 구체적으로 설명할 수 있다.
- 진행과 성공은 필요한 경우 `role="status"` 또는 적절한 live region에서 완전한 문장으로 알린다.
- 오류는 `role="alert"`와 입력의 `aria-describedby`를 기존 기능 경계에 맞게 사용한다.
- 같은 상태를 visible text와 live region에서 중복으로 읽지 않게 한다.
- 색이나 아이콘 없이 문구만으로 상태와 다음 행동을 이해할 수 있어야 한다.

## 인벤토리 구조

`docs/ux-writing-inventory.md`는 사용자 여정 순서로 구성한다.

1. 랜딩·로그인
2. 앱 공통 영역과 계정
3. 웹·Android·Chrome 저장
4. 홈과 꺼내보기
5. 보관함·카테고리·카드 관리
6. 가져오기
7. 공통 오류·확인·접근성

각 항목은 다음 열을 가진다.

| 열        | 내용                                         |
| --------- | -------------------------------------------- |
| 화면·상태 | 사용자가 문구를 만나는 위치와 상황           |
| 역할      | 제목, 설명, 버튼, 오류, 로딩, 접근성 문구 등 |
| 현재 문구 | 변경 전 제품 문구                            |
| 개정 문구 | 최종 제품 문구                               |
| 판정      | `개정`, `유지`, `제외`                       |
| 근거      | 적용한 문체·용어 규칙                        |
| 구현 위치 | 컴포넌트, 오류 매핑 또는 확장 파일           |
| 검증      | 가장 가까운 기존 테스트 또는 필요한 검수     |

소스 줄 번호는 변경에 따라 쉽게 낡으므로 기록하지 않는다. 컴포넌트, 상수와 오류 매핑 이름처럼 안정적인 구현 위치를 사용한다.

## 코드 소유권

문구 일관성을 이유로 거대한 공용 문구 사전이나 다국어 계층을 만들지 않는다.

- 화면에서만 쓰는 문구는 해당 컴포넌트에 둔다.
- 오류 코드와 연결된 문구는 기존 모델 또는 오류 매핑 경계에 둔다.
- 여러 화면에서 의미와 변경 주기가 실제로 같은 문구만 기존 공용 컴포넌트에서 공유한다.
- FSD public API와 기능 경계를 문구 작업 때문에 확장하지 않는다.
- 문구 변경에 필요한 타입, 상태와 이벤트 이름은 제품 동작에 영향이 없으면 유지한다.

## 일괄 전환 단위

모든 문구는 한 PR에서 전환하되 검토 가능한 커밋으로 나눈다.

1. UX Writing 가이드, 인벤토리와 활성 제품 문서
2. 랜딩, 로그인과 앱 공통 영역
3. 웹, Android와 Chrome 저장 경험
4. 홈, 꺼내보기, 보관함, 카테고리와 카드 관리
5. 가져오기 전체 흐름
6. 접근성 문구, 직접 노출 오류와 최종 계약 검증

PR 병합 전에는 일부 커밋만 배포하지 않는다. 기능 플래그 없이 한 번에 전체 제품 목소리를 전환한다.

## 테스트 원칙

테스트는 문구가 속한 화면과 기능 경계 안에서 필요한 범위만 적용한다.

- 기존 테스트가 바뀐 문구를 직접 확인하면 기대값만 갱신한다.
- 문구만 바뀐 행동에 같은 흐름의 새 테스트를 중복해서 만들지 않는다.
- 새 테스트는 기존 검증으로 잡을 수 없는 공통 문체 계약이나 중요한 접근성 의미에만 추가한다.
- 홈 테스트로 가져오기 문구를 검증하거나 가져오기 테스트로 보관함 문구를 검증하지 않는다.
- 공통 컴포넌트 테스트는 해당 컴포넌트의 역할만 확인하고 화면별 문구를 소유하지 않는다.
- 모든 화면, 상태와 viewport의 조합을 만들지 않는다. 변경 위험을 대표하는 조합만 선택한다.
- 정확한 문구 자체가 제품 계약인 경우에만 전체 문자열을 고정한다. 일반적인 스타일 규칙은 한 개의 정적 계약으로 검증한다.

### 정적 UX Writing 계약

사용자 노출 파일에만 한정된 계약 검증 하나를 둔다.

- `습니다`, `하십시오`, `해주세요`, `되어요`, `원문 URL`처럼 예외 없이 교정할 수 있는 패턴
- 일반 다이얼로그의 모호한 `취소`
- 제품 용어 계약과 직접 충돌하는 고신뢰 표현

수동형, 부정형과 `없어요`는 허용 예외가 많으므로 전역 금지 패턴으로 검사하지 않는다. 인벤토리와 가장 가까운 기능 테스트에서 맥락을 검토한다. 내부 로그, 개발자 오류와 테스트 데이터는 정적 계약 대상에서 제외한다.

## 시각 검증

시각 검증도 전체 조합이 아닌 대표 위험을 확인한다.

- Desktop 대표 화면에서 제목, 본문과 행동 위계를 확인한다.
- Tablet은 좌우 폭이 좁은 복합 화면 한 곳을 확인한다.
- Mobile `390px`과 작은 Mobile `320px`에서는 가장 긴 오류, 확인 문구와 Footer 행동을 확인한다.
- Chrome 확장 메모 창은 고정된 작은 폭에서 성공과 오류를 확인한다.
- Android 공유는 로딩, 실패 또는 완료 중 문구 길이 영향이 가장 큰 상태를 확인한다.

문구 때문에 줄바꿈이나 넘침이 생기면 해당 컴포넌트의 줄바꿈과 최소 너비만 조정한다. 레이아웃 재설계나 시각적 타이포그래피 결정이 필요하면 #87 범위를 넓히지 않고 별도 판단을 요청한다.

## 전체 검증

PR 직전 다음 검증을 한 번 실행한다.

- 변경 기능과 직접 연결된 테스트
- 정적 UX Writing 계약
- 전체 테스트
- Prettier 검사
- ESLint
- 웹과 Chrome 확장 빌드
- `git diff --check`
- 대표 viewport와 사용자 상태의 시각 검증

실행하지 않은 검증을 통과했다고 기록하지 않는다. 기존 기준선 실패가 생기면 현재 문구 변경과의 관련성을 분리해 보고한다.

## 완료 기준

- 모든 사용자 노출 문구가 인벤토리에서 `개정` 또는 `유지`로 확인된다.
- 앱인토스 UX 라이팅 원칙을 반영한 아맞다 전용 가이드가 있다.
- 웹, Android 공유와 Chrome 확장이 같은 기본 보이스를 사용한다.
- `인사이트`, `링크`, `URL`, `보관함`, `카테고리`, `가져오기`, `꺼내보기`, `되돌리기` 용어가 계약대로 쓰인다.
- 사용자는 버튼만 읽어도 다음 행동을 예측할 수 있다.
- 오류는 발생한 일, 보존된 내용과 가능한 다음 행동을 전달한다.
- 화면 문구와 접근성 문구가 같은 의미를 전달한다.
- 기능 동작, API와 데이터 계약이 바뀌지 않는다.
- 불필요한 교차 화면 테스트와 상태·viewport 조합 테스트가 추가되지 않는다.
- 관련 자동 검사와 대표 시각 검증이 통과한다.

## 후속 관리

- 새 문구는 `docs/ux-writing.md`를 따른다.
- 인벤토리는 전환 기록으로 유지하고 매 문구 변경 때 전체 표를 갱신하지 않는다.
- 기능 의미나 정책이 바뀌는 문구는 해당 기능 이슈에서 먼저 결정한다.
- 다국어 요구가 생기기 전에는 별도 문구 저장 계층을 도입하지 않는다.
- 문서 전체 정본과 이력 통합은 #83에서 계속 다룬다.
