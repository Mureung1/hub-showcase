# 이슈 기반 구현 싸이클 스킬 설계

## 배경

아맞다 저장소의 작업은 다음 흐름을 반복한다.

1. GitHub Issues와 Project에서 다음 작업을 고른다.
2. 원격 기준 브랜치를 동기화하고 작업 브랜치를 만든다.
3. 이슈와 저장소 문서를 기준으로 구현·검증·커밋한다.
4. 브랜치를 푸시하고 한국어 Pull Request를 만든다.
5. 코드 리뷰를 반영한 뒤 사람이 최종 검수하고 병합한다.
6. 병합 후 브랜치와 Issues 및 Project 상태를 정리한다.

현재는 각 단계의 판단과 명령을 매번 다시 구성하므로 누락 가능성과 대화 비용이 크다. 반복 절차는 레포 전용 Codex 스킬로 표준화하고, 제품 판단과 최종 병합처럼 사람 검수가 필요한 경계만 남긴다.

## 목표

- 현재 Git·GitHub 상태를 감지해 작업 순환의 올바른 단계부터 시작하거나 재개한다.
- 브랜치, 커밋, 검증, PR 언어와 Project 상태를 저장소 규칙에 맞게 관리한다.
- 명확하고 되돌릴 수 있는 반복 작업은 중간 확인 없이 진행한다.
- 제품 결정, 모호한 우선순위와 PR 최종 승인·병합은 사람에게 맡긴다.
- 변경 범위에 비해 과도한 검증을 반복하지 않는다.

## 선택한 접근

### 지침 중심의 레포 전용 스킬

`.agents/skills/hub-issue-cycle`에 `SKILL.md`와 UI 메타데이터를 둔다. 스킬은 실행할 때마다 저장소 문서, 로컬 Git과 GitHub 상태를 조회하며 Project 필드 ID나 이슈 번호를 하드코딩하지 않는다.

이 방식은 다음 대안보다 현재 범위에 적합하다.

- 스크립트 중심 자동화는 명령 결과를 결정적으로 만들 수 있지만 Project 구조와 GitHub CLI 출력 변화에 취약하다.
- 플러그인은 여러 저장소나 조직에 배포할 때 유용하지만 단일 저장소의 반복 절차에는 범위가 크다.

반복 실행에서 명령 조합의 오류가 실제로 누적될 때만 작은 보조 스크립트를 추가한다.

## 호출 계약

명시적 호출은 하나의 스킬에 상태 의도를 전달한다.

```text
$hub-issue-cycle 다음 작업
$hub-issue-cycle #39 시작
$hub-issue-cycle 리뷰 반영
$hub-issue-cycle 마무리
```

다음 자연어 요청에도 자동 적용될 수 있도록 설명을 작성한다.

- 백로그와 이슈를 보고 다음 일을 시작해 달라는 요청
- 브랜치 생성부터 구현, 커밋과 PR 생성을 이어 달라는 요청
- 현재 PR의 코드 리뷰를 반영해 달라는 요청
- 병합 후 브랜치와 GitHub 추적 정보를 정리해 달라는 요청

단순한 Git 질문, 이슈 요약만 필요한 요청, 자동 병합 요청에는 이 스킬 전체 순환을 적용하지 않는다.

## 상태 전이

### 1. 방향 설정

- 저장소 루트와 `origin`이 `ppre1ude/hub`인지 확인한다.
- 현재 브랜치, 작업 트리, 연결된 PR과 이슈 상태를 확인한다.
- 사용자 소유 변경이 있으면 보존하고 작업 범위와 겹칠 때만 멈춘다.
- 현재 단계가 분명하면 앞 단계를 반복하지 않고 해당 단계부터 재개한다.

### 2. 다음 작업 선택

- Project #3의 `시작 가능` 항목 가운데 제품 단계가 `현재 MVP` 또는 `후속 후보`이고, 선행 관계와 이슈 완료 기준을 충족한 항목만 후보로 삼는다.
- `보류`와 `제외`는 자동 후보에서 제외하고 제품 단계, 우선순위, 주차와 예상 시간을 함께 비교한다.
- 명확한 최우선 후보가 하나면 자동으로 선택하고 근거와 논의 사항을 알린 뒤 시작한다.
- 후보 간 제품 가치나 범위 판단이 갈리거나 `ready-for-human`, `needs-info`, `blocked` 상태면 사람에게 추천안을 제시하고 멈춘다.
- 사용자가 이슈 번호를 지정하면 해당 이슈가 실행 가능한지만 확인한다.

### 3. 작업 시작

- `main`에서 `git fetch --prune`과 fast-forward 동기화를 수행한다.
- Project 상태를 `진행 중`으로 변경하고 필요하면 시작일을 기록한다.
- `docs/coding-commit-conventions.md`에 따라 `<type>/<이슈번호>-<키워드>` 브랜치를 만든다.
- 이슈 본문과 `AGENTS.md`, `docs/`의 적용 문서를 읽고 완료 기준을 구현 범위로 고정한다.

### 4. 구현과 커밋

- 제품 판단이 새로 필요하지 않은 범위에서 구현을 이어간다.
- UI 변경이면 `DESIGN.md`, 프론트엔드 구조 변경이면 FSD 문서를 추가로 적용한다.
- 사용자 변경과 무관한 파일은 수정하지 않는다.
- 기능 또는 오류 수정은 실패를 재현하는 검증을 먼저 만들거나 확인하고 최소 구현으로 통과시킨다.
- 커밋은 의미 있는 완료 단위마다 `<type>: <한글 명사형 요약>`으로 작성한다.

### 5. 검증과 Pull Request

- 구현 중에는 변경 범위의 테스트와 정적 검사만 실행한다.
- PR 직전 전체 검증은 저장소가 요구하는 명령을 한 번만 실행한다.
- 리뷰 수정 뒤에는 영향받은 검증만 다시 실행하고, 공통 계약이나 빌드 구성이 바뀐 경우에만 전체 검증을 반복한다.
- 브랜치를 푸시하고 제목과 본문이 모두 한국어인 준비된 PR을 만든다.
- PR 본문에는 이슈 연결, 변경 요약, 검증 결과와 사람 검수 항목을 기록한다.
- Project 상태를 `검토 중`으로 변경한다.

### 6. 리뷰 반영

- 미해결 리뷰와 실패한 검사부터 확인한다.
- 리뷰 제안은 코드와 계약을 대조해 기술적으로 타당한 경우에만 반영한다.
- 명확한 수정은 구현, 영향 범위 검증, 커밋과 푸시까지 자동으로 진행한다.
- 제품 동작 변경, 보안 완화, 호환성 손실 또는 모호한 제안은 근거와 선택지를 제시하고 멈춘다.
- 자동 병합은 하지 않는다.

### 7. 병합 후 마무리

- GitHub에서 PR 병합을 확인한 뒤에만 마무리를 시작한다.
- 원격을 fetch·prune하고 안전할 때 로컬 작업 브랜치를 삭제한다.
- 원격 브랜치는 사용자가 삭제하며 스킬은 강제 삭제하지 않는다.
- 이슈를 닫고 Project 상태를 `완료`로 변경한다.
- 상위 이슈 체크리스트, 하위 진행률과 선행 관계에 따라 새로 시작 가능해진 이슈를 갱신한다.
- 수행 결과와 다음 후보를 요약한다.

## 사람 검수 경계

다음 경우에만 자동 진행을 멈춘다.

- 실행 가능한 다음 이슈가 하나로 결정되지 않는 경우
- 이슈 완료 기준과 코드 또는 제품 문서가 충돌하는 경우
- 제품, 디자인, 보안, 데이터 마이그레이션이나 하위 호환성 결정을 새로 내려야 하는 경우
- 사용자 변경과 작업 범위가 겹치는 경우
- 권한, CI 환경 또는 외부 서비스 상태로 안전한 진행이 불가능한 경우
- PR 최종 승인과 병합이 필요한 경우

되돌릴 수 있고 이미 승인된 범위의 GitHub 상태 변경, 브랜치 생성, 커밋, 푸시와 PR 생성에는 중간 승인을 다시 요구하지 않는다.

## 안전 규칙

- 자동 병합, 강제 푸시, 원격 브랜치 삭제와 파괴적 Git 명령을 금지한다.
- `ready-for-human`, `needs-info`, `blocked` 이슈를 자동 구현 대상으로 고르지 않는다.
- 카드 상태만으로 완료를 판단하지 않고 이슈의 완료 기준과 검증 방법을 확인한다.
- GitHub 상태 변경 전후에 대상 이슈와 Project를 다시 조회한다.
- 하드코딩한 Project 필드 ID 대신 필드 이름과 선택지 이름을 실행 시 조회한다.
- GitHub 상태와 로컬 상태가 충돌하면 추측성 수정을 하지 않는다.

초기 버전에는 보조 스크립트와 별도 참고 문서를 추가하지 않는다.

## 검증

- 스킬 생성 도구의 구조 검증을 통과한다.
- `SKILL.md`의 이름, 설명, 호출 예시와 UI 메타데이터가 일치하는지 확인한다.
- 다음 작업, 지정 이슈 시작, 리뷰 반영과 병합 후 마무리 시나리오를 현재 저장소 상태에 대입해 읽기 전용으로 점검한다.
- 애플리케이션 소스를 변경하지 않으므로 제품 전체 테스트와 빌드는 실행하지 않는다.

## 성공 기준

- 사용자가 반복 절차를 단계별로 다시 설명하지 않고 `$hub-issue-cycle`과 의도만 전달해 작업을 재개할 수 있다.
- 자동 진행이 사람 판단을 침범하지 않으며, 사람 검수가 필요하지 않은 중간 절차는 다시 묻지 않는다.
- PR 생성과 병합 후 정리에서 Issues와 Project 갱신이 누락되지 않는다.
- 변경 범위에 비해 과도한 검증을 반복하지 않는다.
