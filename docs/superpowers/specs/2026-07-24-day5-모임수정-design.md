# Day5 — E4 모임 수정 설계 (2026-07-24)

`PATCH /api/meetings/:id`. 모임장이 자신이 등록한 모임의 내용을 수정한다. BE + FE 풀스택.

## 범위

- **포함**: E4 백엔드(엔드포인트·검증·가드·테스트) + E4 프론트(공용 폼 추출·수정 페이지·진입 버튼) + 통합 회귀 테스트에 E4 스텝 추가.
- **제외(이번 세션 밖)**: B4·H1(신고), B5(인덱스). 계획서 Day5의 뒤쪽 항목으로, E4 완료 후 별도로 진행.

## 핵심 설계 결정

1. **전체 교체(full-replace), `type` 불변.** PATCH지만 부분 병합이 아니라 등록 폼 전체를 다시 받아 통째로 UPDATE한다. `validateCreateMeeting`의 holistic·type별 분기 검증을 그대로 재사용하기 위함. `type`(flash↔small)은 참여 모델·정원·기존 참여자를 통째로 뒤엎으므로 변경 불가.
2. **참여자 영향 필드는 "조건부 허용".** 참여자가 있어도 안전 범위 안에서는 수정 가능:
   - `capacity`(flash)는 현재 확정 인원 이상이면 허용(늘리기·유지 OK, 미만 거부).
   - `adultOnly`는 켤 때(false→true) 활성 참여자가 전원 성인일 때만 허용.
3. **상태 가드는 무조건.** 취소된 모임·종료된(지난) 모임은 어떤 필드도 수정 불가.

## 백엔드

**파일**: `src/routes/meetings.js`, `src/services/meetingService.js`, `src/utils/validators.js`

### 엔드포인트
```
PATCH /api/meetings/:id      (requireAuth)
성공: 200 { data: <수정된 모임> }   // createMeeting과 동일한 normalizeMeeting 형태
```
라우트 핸들러는 얇게 유지한다: `parseIdParam` → `updateMeeting(id, req.session.userId, req.body)` → `res.json({ data })`. E4는 type 불변 검사 자체가 기존 type을 알아야 하므로 조회가 반드시 선행된다. 따라서 조회·소유권·검증·가드·UPDATE를 서비스 한 곳에서 처리하고, 순서는 아래 `updateMeeting` 절을 따른다(소유권 → 검증 순 — E5 `cancelMeeting`과 동일하게 NOT_FOUND → FORBIDDEN을 먼저).

### 검증 — `validateUpdateMeeting(body, existingType)` (validators.js 신규)
1. `body.type !== existingType` → `VALIDATION_ERROR "모임 유형은 변경할 수 없습니다"`.
   - **type 검사를 먼저 한다.** 안 그러면 flash→small 시도 시 `validateCreateMeeting`이 small 규칙으로 "endAt이 필요합니다"를 먼저 던져 원인이 흐려진다.
2. 이후 `validateCreateMeeting(body)`에 위임 → 길이(varchar 한도, 코드포인트 계산)·필수·type별 분기(flash=capacity 양의정수, small=endAt)·openChatUrl 패턴을 그대로 재사용. 반환값(정규화된 fields)을 그대로 서비스에 넘긴다.

`validateUpdateMeeting`은 `existingType`을 인자로 받으므로 기존 모임 조회가 검증보다 먼저 일어나야 한다. 따라서 조회·소유권·검증·가드·UPDATE를 모두 서비스 `updateMeeting` 한 곳에서 처리하고, 순서는 (1) 조회→`NOT_FOUND`, (2) 소유권→`FORBIDDEN`, (3) `validateUpdateMeeting(body, row.type)`→`VALIDATION_ERROR`, (4) 상태 가드, (5) 참여자 가드, (6) UPDATE 로 둔다. F4는 남의 모임 존재 누설을 줄이려 본문 검증을 먼저 했지만, E4는 type 불변 검사가 기존 type을 필요로 해 조회가 선행될 수밖에 없다 — 대신 소유권(FORBIDDEN)을 검증보다 앞에 두어, 남의 모임에 대한 상세한 검증 에러가 새어나가지 않게 한다(E5 `cancelMeeting`과 동일한 NOT_FOUND→FORBIDDEN 순).

### 서비스 — `updateMeeting(meetingId, hostId, body)`
E5 `cancelMeeting`의 조회·소유권·상태 가드 패턴을 재사용한다.

1. `SELECT id, host_id, status, type, adult_only, start_at, end_at, capacity FROM meetings WHERE id=$1`
   그리고 상태·시간 판정을 위해 `COALESCE(end_at, start_at) < now() AS is_past`도 같은 쿼리에서 계산(목록 필터와 동일한 DB 시계 기준 — JS Date 재비교 금지).
   → 없으면 `NOT_FOUND "모임을 찾을 수 없습니다"`.
2. `Number(row.host_id) !== Number(hostId)` → `FORBIDDEN "모임장만 모임을 수정할 수 있습니다"`.
   - **pg 타입 함정**: `host_id`는 bigint라 문자열("5")로 온다. `Number()` 정규화 없으면 모임장 본인도 막힌다.
3. `const fields = validateUpdateMeeting(body, row.type)` → `VALIDATION_ERROR`.
4. **상태 가드**:
   - `row.status === 'cancelled'` → `VALIDATION_ERROR "취소된 모임은 수정할 수 없습니다"`.
   - `row.is_past` → `VALIDATION_ERROR "종료된 모임은 수정할 수 없습니다"`.
5. **정원 가드(flash만)**: 활성 확정 인원을 센다 — **기준은 코드베이스 전체와 동일하게** `IN ('confirmed','approved')`
   `SELECT COUNT(*)::int AS n FROM meeting_participants WHERE meeting_id=$1 AND status IN ('confirmed','approved')`.
   `fields.capacity < confirmedCount` → `VALIDATION_ERROR "정원은 현재 확정 인원보다 적을 수 없습니다"`.
   (flash엔 approved가 없어 결과는 confirmed만 셀 때와 같지만, 상세·목록의 `confirmedCount` 정의와 predicate를 통일해 divergence를 없앤다. small은 capacity가 null이라 이 가드를 건너뛴다.)
6. **adultOnly 켜기 가드**: `row.adult_only === false && fields.adultOnly === true`일 때만 검사.
   활성 참여자(`status IN ('pending','confirmed','approved')`)의 `birth_date`를 조회해, 한 명이라도 `isAdult(birth_date) !== true`(미성년 `false` **또는 생년월일 없음 `null`**)이면
   `VALIDATION_ERROR "미성년이거나 생년월일 미입력 참여자가 있어 성인 전용으로 바꿀 수 없습니다"`.
   - 신청(F1)이 adultOnly 모임에서 `false`와 `null`을 모두 막는 것과 일관되게 둘 다 차단한다.
   - 판정은 `src/utils/age.js`의 `isAdult(birthDate, now)`를 재사용.
7. **UPDATE**: 가변 컬럼만 갱신(type·host_id 제외).
   ```sql
   UPDATE meetings SET
     title=$2, category=$3, description=$4,
     region_sido=$5, region_sigungu=$6, region_eupmyeondong=$7,
     start_at=$8, end_at=$9, capacity=$10, adult_only=$11, open_chat_url=$12
   WHERE id=$1 RETURNING *
   ```
   → `normalizeMeeting(rows[0])` 반환.

트랜잭션은 불필요(단일 UPDATE). 정원·adultOnly 가드는 별도 SELECT로 읽으므로 이론상 동시 신청과 경합할 수 있으나(아래 백로그) 모임장 행위라 저위험.

## 프론트엔드

**파일**: `src/api/meetings.js`, `src/App.jsx`, `src/components/MeetingForm.jsx`(신규), `src/pages/MeetingCreatePage.jsx`(리팩터), `src/pages/MeetingEditPage.jsx`(신규), `src/pages/MeetingDetailPage.jsx`(진입 버튼)

### api 클라이언트
```js
export function updateMeeting(id, input) {
  return request(`/api/meetings/${encodeURIComponent(id)}`, {
    method: 'PATCH',
    body: JSON.stringify(input),
  })
}
```
(기존 `respondToApplicant`의 PATCH 패턴과 동일.)

### 공용 폼 추출 — `MeetingForm`
현재 `MeetingCreatePage`의 폼 JSX·상태·검증을 공용 `MeetingForm` 컴포넌트로 추출한다. 두 페이지가 이 컴포넌트를 공유한다.

- **Props**: `initialValues`(수정 시 채움, 등록 시 기본값), `mode`('create'|'edit'), `disabled`(필드별 잠금 집합: `{ type, capacity, adultOnly }`), `onSubmit(payload)`, `submitLabel`, `error`, `submitting`.
- 내부 상태 초기화를 `initialValues` 기반으로 바꾼다(현재는 하드코딩 기본값). 등록 페이지는 기존 기본값을 `initialValues`로 넘겨 **동작 불변**.
- `disabled.type`이면 `PillTabs` 비활성(또는 읽기 전용 표시), `disabled.capacity`/`disabled.adultOnly`면 해당 입력 비활성 + 왜 잠겼는지 힌트 문구.
- payload 조립(`startAt`/`endAt`/`capacity` type 분기)은 폼 안에 유지.

**리스크 관리**: Create는 이미 검증된 흐름이다. 추출 후 등록 동작이 바뀌지 않았는지 `npm run lint`·`npm run build`와 수동 확인으로 검증한다. 추출은 순수 리팩터(동작 동일)를 먼저 커밋하고, 그 위에 Edit를 얹는 순서를 권장.

### `MeetingEditPage`
- 라우트 `/meetings/:id/edit`(App.jsx에 추가, `/meetings/:id`보다 먼저 또는 정적 세그먼트라 순서 무관하나 명시).
- 마운트 시 `fetchMeeting(id)`로 상세를 받아 `initialValues`로 변환.
  - **⚠️ 타임스탬프 프리필(정확성)**: 상세의 `startAt`/`endAt`은 UTC ISO 문자열이다(`timestamp` 컬럼 → 서버가 KST로 해석해 UTC로 직렬화, 예: KST 19:00 → `10:00Z`). date+time 입력으로 분해할 때 `toISOString().slice()` 등 **UTC 기준으로 뽑으면 9시간 밀리고 자정 근처엔 날짜가 하루 어긋난다**(특히 small은 `start_at`이 자정 KST=전날 15:00Z라 UTC 날짜가 하루 전으로 나옴). 반드시 **명시적 KST(Asia/Seoul) 변환**으로 벽시계를 추출한다:
    ```js
    // sv-SE 로케일은 YYYY-MM-DD / HH:mm 포맷을 준다. 브라우저 TZ와 무관하게 KST 벽시계.
    const fmt = new Intl.DateTimeFormat('sv-SE', {
      timeZone: 'Asia/Seoul',
      year: 'numeric', month: '2-digit', day: '2-digit',
      hour: '2-digit', minute: '2-digit', hour12: false,
    })
    // fmt.format(new Date(startAt)) → "2026-07-25 19:00" → date/time로 split
    ```
    저장 시엔 create와 동일하게 `${date}T${time}:00+09:00`로 재조립하므로 왕복이 대칭적이다. 이 변환 유틸은 `MeetingForm`(또는 작은 date 유틸)에 두어 중복을 피한다.
- **가드 반영(FE)**: 모임장이 아니거나(상세의 host.id 비교) 종료·취소 모임이면 폼 대신 안내 + 상세로 돌아가기. `disabled` 집합은 상세 응답으로 계산:
  - `type`은 항상 잠금.
  - `capacity`는 활성 참여자가 있으면(정원 축소 위험) 잠금 — 단순화를 위해 **참여자 존재 여부**로 잠근다(BE는 더 정밀히 "확정 인원 미만"만 막지만, FE는 보수적으로 잠가 혼란을 줄임). 상세 응답의 확정 인원 필드(`confirmedCount`)로 판단.
  - `adultOnly` 켜기는 미성년/무입력 참여자 유무를 FE가 알기 어렵다 → **FE에서는 잠그지 않고**, 켜서 제출했다가 BE가 거부하면 그 에러 메시지를 그대로 표시(서버가 단일 진실). 힌트로 "참여자에 따라 제한될 수 있어요" 안내.
- 제출 성공 시 상세(`/meetings/:id`)로 이동. `submitting` 플래그로 더블 제출 방지(기존 패턴).

### 진입 버튼
상세 host 카드의 "모임 취소하기" 버튼 근처(`isLoggedIn && isHost && !isEnded` 게이트 안)에 "모임 수정하기" 버튼 추가 → `to={/meetings/${id}/edit}`.

## 테스트

### BE (TDD, 기존 스타일 준수)
- 모임장 아님 → `FORBIDDEN`
- 없는 모임 → `NOT_FOUND`
- 취소된 모임 → `VALIDATION_ERROR`
- 종료된(지난) 모임 → `VALIDATION_ERROR`
- `type` 변경 시도 → `VALIDATION_ERROR`
- flash `capacity` < 확정 인원 → `VALIDATION_ERROR`; = 또는 > 확정 인원 → 200
- `adultOnly` 켜기 + 미성년 참여자 → `VALIDATION_ERROR`; + 생년월일 null 참여자 → `VALIDATION_ERROR`; + 전원 성인(또는 참여자 없음) → 200
- happy path: 여러 필드 수정이 응답·DB에 반영
- 길이 검증(title 101자 등)은 `validateCreateMeeting` 재사용으로 커버 — 최소 1건 확인
- **돌연변이 검사**: 각 가드(소유권·상태·정원·adultOnly·type)를 무력화하면 해당 테스트가 실제로 실패하는지 확인(Day3 교훈 — 조건 무력화 시 실패해야 의미 있는 검증).

### 통합 회귀 — `tests/integration.slice.test.js`
기존 전체 흐름(로그인→등록→상세→신청→승인→마이페이지→취소)에 **모임장이 등록 후 수정**하는 E4 스텝을 끼워 넣는다.

### FE
자동화 테스트 없음. `npm run lint`(기존 경고 1건 무시) + `npm run build` 클린 + 수동 확인:
등록 동작 불변(리팩터 회귀), 수정 진입·필드 잠금·제출·상세 반영, 취소/종료 모임 진입 차단.

## 미룸(백로그 → 메모리 `bungae-optimization-backlog`)
- **정원·adultOnly 가드 동시성**: `FOR UPDATE` 없이 count/birth_date를 읽어 수정과 동시 신청이 겹치면 좁은 창(모임장 행위, 저위험). Day3 F2 동시성과 동류.
- FE `capacity` 잠금을 "참여자 존재"로 단순화 → BE보다 보수적(확정 인원 미만만 막으면 되는데 참여자 있으면 전부 잠금). 필요 시 정밀화.
- `applicantCount`/`confirmedCount` FE 렌더는 기존 설계대로 선택 사항.
