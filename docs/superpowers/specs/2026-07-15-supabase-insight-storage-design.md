# Supabase 인사이트 저장 설계

## 목표

로그인한 사용자가 URL을 Supabase에 저장하고 새로고침하거나 다시 방문한 뒤에도 자신의 인사이트만 확인·수정·삭제할 수 있게 한다. 화면은 Supabase SDK를 직접 사용하지 않고 `entities/insight`가 소유한 저장소 포트만 사용한다.

## 범위

- 최소 인사이트 스키마와 SQL migration
- 사용자별 CRUD RLS
- 사용자와 정규화 URL 조합의 중복 방지
- 비동기 CRUD 저장소 포트와 Supabase 어댑터
- 인증된 작업 공간과 원격 저장소 연결
- 로딩·중복·권한·원격 실패 상태 처리
- 저장 후 새로고침 복원 검증

자동 로컬 데이터 이전, 로컬·원격 동시 쓰기, 다중 카테고리, 메타데이터 수집은 포함하지 않는다.

## 데이터 모델

`public.insights`는 다음 값을 저장한다.

- `id`: UUID 기본 키
- `user_id`: `auth.users.id` 외래 키
- `original_url`: 사용자가 입력한 원본 URL
- `normalized_url`: 중복 판별용 정규화 URL
- `domain`: 화면 표시와 검색용 도메인
- `title`: 사용자 제목 또는 대체 제목
- `memo`: 선택 메모
- `category`: 선택 단일 카테고리
- `schema_version`: 현재 값 `1`
- `created_at`, `updated_at`: UTC 시각

`(user_id, normalized_url)`에 고유 제약을 둔다. 수정 시각은 데이터베이스 트리거로 갱신해 클라이언트 시계에 의존하지 않는다.

## 보안

테이블에 RLS를 활성화하고 조회·생성·수정·삭제 각각에 `auth.uid() = user_id` 조건을 적용한다. 생성과 수정에는 `WITH CHECK`도 적용해 다른 사용자 소유권으로 쓸 수 없게 한다. 브라우저에는 publishable key만 사용하며 service role 키는 사용하지 않는다.

## 저장소 경계

기존 동기식 전체 배열 `load/save` 계약을 다음 비동기 CRUD 계약으로 교체한다.

- `list`: 현재 사용자의 전체 인사이트 조회
- `create`: 인사이트 한 건 생성
- `update`: 인사이트 한 건 수정
- `delete`: 인사이트 한 건 삭제

Supabase 행과 도메인 `Insight` 사이의 snake_case/camelCase 변환은 어댑터 내부에서만 수행한다. 화면과 앱 훅은 저장소 결과만 다룬다.

## 상태 흐름

인증 완료 후 사용자 ID로 Supabase 저장소를 생성한다. 작업 공간은 최초 조회가 끝나기 전 로딩 상태를 표시한다. 생성·수정·삭제는 원격 성공 후 화면 상태에 반영하며 실패하면 기존 입력과 인사이트를 보존한다.

중복은 화면의 현재 목록에서 먼저 탐지하고, 동시 요청이나 다른 세션에서 생긴 중복은 PostgreSQL 고유 제약 오류로 최종 판정한다. 권한 오류와 일반 원격 오류는 저장소에서 구분하되 사용자에게 내부 오류 세부 정보나 키를 노출하지 않는다.

## 검증

- migration 구조와 RLS 정책 계약
- Supabase 행 변환
- 정상 조회·생성·수정·삭제
- 정규화 URL 중복
- 권한 오류와 원격 실패
- 비동기 작업 동안 입력과 기존 상태 보존
- 저장 후 다시 마운트했을 때 원격 데이터 복원
- 전체 테스트, lint, build
