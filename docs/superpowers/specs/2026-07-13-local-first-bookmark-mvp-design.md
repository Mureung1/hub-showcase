# 로컬 우선 북마크 MVP 설계

> **역사적 설계 문서 — 2026-07-15 이전 기준**
>
> 이 문서는 계정 없는 Web Storage MVP를 검토할 때의 결정과 구현 순서를 보존한다. 현재 제품 저장소는 Google 로그인, Supabase Postgres와 사용자별 RLS를 사용하며, 다중 기기 캡처를 포함한다. 현재 기준은 [전환 추적 이슈 #21](https://github.com/ppre1ude/hub/issues/21), [다중 기기 캡처 이슈 #36](https://github.com/ppre1ude/hub/issues/36), [캡처 우선 저장 경험 설계](2026-07-15-capture-first-save-experience-design.md)를 따른다.

## 문서 목적

3~4주 안에 아맞다의 핵심 가치인 `저장 → 다시 찾기 → 원문 열기`를 검증한다. 계정, 원격 저장소, 자동 수집, AI 처리처럼 검증 전 운영 비용을 키우는 기능은 이번 MVP의 선행 조건으로 삼지 않는다.

## 제품 가설

사용자는 URL을 거의 마찰 없이 저장할 수 있고, 저장 당시의 개인 맥락을 한 줄만 남겨도 나중에 현재 상황으로 관련 인사이트를 다시 찾아 원문을 열 수 있다.

MVP가 검증해야 하는 것은 기능 수가 아니라 다음 두 질문이다.

1. 저장 과정이 가벼워 실제로 반복해서 저장하는가?
2. 자동 수집이나 AI 없이도 사용자가 남긴 최소 맥락으로 다시 찾을 수 있는가?

## 좁은 사용자 흐름

```mermaid
flowchart LR
  A["URL 입력"] --> B["즉시 저장"]
  B --> C["선택: 제목·한 줄 메모·단일 분류"]
  C --> D["브라우저 로컬 저장"]
  D --> E["보관함 검색 또는 꺼내보기"]
  E --> F["상위 인사이트 확인"]
  F --> G["원문 새 탭 열기"]
```

## MVP 범위

### 포함

- URL 형식 검증과 보수적 정규화
- URL만으로 즉시 저장
- 새로고침 후에도 유지되는 브라우저 로컬 저장
- 제목, 한 줄 메모, 단일 분류의 선택 입력
- 사용자별 URL이 아니라 현재 브라우저 저장소 안의 중복 URL 방지
- 보관함 목록, 수정, 삭제, 원문 열기
- 제목, 메모, 분류, 도메인, URL 기반 검색
- 같은 검색 코어를 사용하는 `꺼내보기`
- 최대 6개 결과와 일치 필드 기반 연결 단서
- 모바일·데스크톱·키보드·빈 상태의 핵심 흐름
- 정적 배포, 실제 사용자 검증, 피드백을 반영한 1회 개선

### 제외

- Google OAuth, Supabase Auth, 원격 사용자 저장소, RLS
- 로그인 후 개인화 온보딩
- 다중 카테고리, 카테고리 CRUD, 색상·정렬 관리
- 서버 메타데이터 수집, 크롤링, 썸네일 처리
- Chrome Extension, Chrome 북마크 파일 가져오기, Notion·Pinterest 어댑터
- AI 요약, 임베딩, AI 추천·자동 분류
- 협업, 알림, 휴지통, 복구, 정렬 옵션

기존에 구현한 로그인 전 소개 화면과 WDS 기반 UI는 제거하지 않는다. 다만 이번 MVP의 선행 작업이나 별도 완성도 작업으로 확장하지 않고 현재 상태를 보존한다.

## 데이터 계약

```ts
type Insight = {
  id: string;
  originalUrl: string;
  normalizedUrl: string;
  domain: string;
  title: string;
  memo: string | null;
  category: string | null;
  createdAt: string;
  updatedAt: string;
};
```

- `originalUrl`은 원문 열기에 사용한다.
- `normalizedUrl`은 로컬 중복 판정에 사용한다.
- 제목을 입력하지 않으면 도메인, 도메인을 얻지 못하면 원본 URL을 사용한다.
- `memo`는 일반 설명보다 사용자의 활용 맥락을 담는 고가치 검색 신호다.
- `category`는 자유 텍스트 하나만 받는다. 앞뒤 공백을 제거하고 연속 공백을 합치며, 빈 값은 `null`로 저장하고 표기 대소문자는 보존한다.
- 로컬 저장 형식에는 `schemaVersion`을 두어 필드 변경 시 마이그레이션할 수 있게 한다.

URL 정규화는 호스트 소문자화, 기본 포트와 fragment 제거, 루트 경로의 trailing slash 제거까지만 수행한다. 추적 파라미터는 `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `fbclid`만 제거한다. 경로 대소문자와 그 밖의 query parameter는 보존한다.

## 검색과 꺼내보기

보관함 검색과 `꺼내보기`는 하나의 결정적 검색 코어를 공유한다. MVP에서는 새 검색 인프라를 도입하지 않고 현재 프로토타입의 토큰 정규화와 필드 가중치 방식을 작은 순수 함수로 분리한다.

권장 가중치:

| 필드          | 가중치 | 이유                                            |
| ------------- | -----: | ----------------------------------------------- |
| `memo`        |    4.0 | 사용자가 저장한 이유와 활용 상황을 직접 담는다. |
| `title`       |    3.0 | 자료의 주제를 가장 직접적으로 보여준다.         |
| `category`    |    2.0 | 사용자가 붙인 단순 분류다.                      |
| `domain`      |    1.0 | 출처를 기억하는 사용자를 돕는다.                |
| `originalUrl` |    0.5 | URL 일부를 기억하는 경우를 보조한다.            |

보관함 검색은 전체 결과 목록을 보여주고, `꺼내보기`는 같은 점수를 사용해 상위 6개만 작업팩으로 표현한다. 연결 단서는 AI 문장이 아니라 `제목`, `메모`, `분류`, `도메인` 중 실제로 일치한 필드에서 만든다.

## 저장 마찰과 검색 품질의 해법

메타데이터를 많이 모으는 대신 검색 가치가 높은 개인 맥락 하나를 선택적으로 요청한다.

> 언제 다시 쓰고 싶은 자료인가요?

- URL 저장은 이 질문에 답하지 않아도 즉시 끝난다.
- 질문은 저장 후에 표시하고 건너뛸 수 있다.
- 답변은 `memo`로 저장하고 검색에서 가장 높은 가중치를 받는다.
- 저장 완료율과 메모 입력률을 함께 측정해 입력 부담을 확인한다.

## 자동화 도입 게이트

### 0단계: MVP

- 네트워크 기반 자동화 비용은 0이다.
- 브라우저에서 URL 정규화와 도메인 추출만 수행한다.
- 크롤러, 작업 큐, 예약 작업, 외부 AI 호출을 만들지 않는다.

### 1단계: 메타데이터 실험

다음 조건을 모두 만족할 때만 별도 실험을 연다.

- 실제 또는 대표 데이터가 20~30개 이상 쌓였다.
- 상황 쿼리 10개 이상으로 기준 검색 품질을 측정했다.
- 기준 검색의 Top-5 적중률이 목표인 70%에 미달한다.
- Top-5 실패 사례의 절반 이상이 원문 정보 부족 때문이다.
- 제목·설명 메타데이터 추가가 Top-5 적중률을 최소 15%p 개선한다.

도입하더라도 저장을 막는 동기 작업이나 주기적 크롤링이 아니라 요청 시 한 번 수집하고 캐시하는 구조부터 검토한다.

### 2단계: AI 실험

일반 메타데이터만으로도 Top-5 목표인 70%를 달성하지 못하고, AI 요약이나 임베딩이 다시 최소 15%p의 개선을 증명할 때만 검토한다. 고정 월 예산, 사용자 동의, 결과 캐시, 실패 시 기존 검색 유지가 필수다.

## 성공 기준

- URL 저장 완료 시간 중앙값이 10초 이하이다.
- URL만 입력해도 저장을 완료할 수 있다.
- 대표 상황 쿼리의 Top-5 적중률이 70% 이상이다.
- 사용자의 80% 이상이 30초 안에 목표 원문을 다시 연다.
- 최소 5명이 배포된 제품으로 핵심 흐름을 사용한다.
- 사용자 피드백을 반영해 최소 한 번 재배포한다.
- 자동 수집과 AI 없이도 기준을 달성하는지 먼저 기록한다.

| MVP-05B     | 검색과 꺼내보기 흐름을 다양한 환경에서 완주한다.                | AFK                   | MVP-03, MVP-04   |

| MVP-08      | 검색 실패 데이터를 근거로 메타데이터 자동 수집 여부를 결정한다. | HITL                  | MVP-IMPROVE      |

`AFK`는 추가 제품 판단 없이 구현·검증할 수 있는 작업이고, `HITL`은 실제 사용자 관찰이나 사람의 제품 결정을 요구하는 작업이다. MVP-01과 MVP-05는 구현을 직접 맡는 단위가 아니라 하위 수직 슬라이스의 완료를 모으는 상위 추적 이슈다.

MVP-07에서 가장 큰 실패 원인 하나를 `MVP-IMPROVE`라는 별도 수직 슬라이스 이슈로 만든다. 이 이슈를 완료하고 재배포한 뒤 MVP-08을 시작한다. 범위를 알 수 없는 개선 구현을 MVP-07 본문에 미리 묶지 않는다. MVP-08은 활성 백로그로 유지하지만 고정 주차는 배정하지 않는다.

## 변경 가능성과 확장 경계

- 로컬 저장소는 교체 가능한 저장 포트 뒤에 둔다. 원격 동기화 필요가 검증되면 Supabase 어댑터를 추가할 수 있다.
- 검색 코어는 UI와 분리한다. MiniSearch나 다른 엔진이 필요해져도 보관함과 `꺼내보기`가 같은 계약을 사용한다.
- 다중 카테고리나 가져오기는 현재 단일 분류와 로컬 저장 경험이 검증된 뒤 별도 수직 슬라이스로 확장한다.
- 기존 상세 구현 계획은 삭제하거나 상태를 바꾸지 않는다. 활성 MVP 범위와 실행 순서는 `docs/backlog.md`와 `docs/checklist.md`를 기준으로 판단한다.
