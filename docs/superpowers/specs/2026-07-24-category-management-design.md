# 사용자 카테고리 관리 설계

## 목적

사용자가 만든 카테고리를 저장·수정 화면과 보관함 필터에서 같은 이름과 색상으로 관리할 수 있게 한다. 한 인사이트에는 카테고리 하나만 연결하며, 카테고리를 선택하지 않아도 저장할 수 있다.

## 현재 문제

현재 카테고리 입력은 인사이트에 저장된 문자열만 바꾸며 보관함의 고정 필터와 동기화되지 않는다. 예를 들어 `안녕`이라는 카테고리를 입력하면 해당 인사이트의 글자만 바뀌고, 보관함에는 새 카테고리 필터가 생기지 않는다.

- GitHub 이슈: [#71 사용자 카테고리를 관리하고 보관함 필터와 동기화한다](https://github.com/ppre1ude/hub/issues/71)
- 관련 제품 결정: [#22 여러 카테고리와 관리 기능의 필요성을 확인한다](https://github.com/ppre1ude/hub/issues/22)

## 사용자에게 달라지는 점

### 저장과 수정

- 저장 후 맥락 입력과 보관함 카드 수정에서 자유 텍스트 입력을 제거한다.
- 사용자는 자신의 카테고리 중 하나를 선택하거나 카테고리 없이 저장한다.
- 목록에 원하는 이름이 없으면 `새 카테고리 만들기`를 선택해 이름과 색상을 정한다.
- 새 카테고리를 만들면 현재 인사이트에 바로 선택되고 보관함 필터에도 나타난다.

### 보관함

- 필터는 `전체 → 사용자 카테고리 → 미분류` 순서로 보여준다.
- 사용자 카테고리는 생성순으로 정렬한다.
- `전체`와 `미분류`는 화면에서만 사용하는 필터이며 카테고리 데이터로 저장하지 않는다.
- 카테고리 이름이나 색상을 바꾸면 필터와 연결된 모든 인사이트 카드에 함께 반영된다.
- 선택 중인 카테고리를 삭제하면 보관함은 `전체` 필터로 돌아간다.

### 카테고리 관리

- 보관함의 `카테고리` 제목 옆에 `관리` 버튼을 둔다.
- 관리 모달에서 카테고리를 만들고 이름과 색상을 바꾸거나 삭제한다.
- 삭제 전에는 연결된 인사이트가 미분류로 이동한다는 사실을 알린다.
- 저장 실패 시 입력을 유지하고 다시 시도할 수 있게 한다.

## 색상 선택

카테고리 색상은 자유 입력이 아니라 24개의 고정 팔레트에서 고른다.

- 색상은 원형 선택 항목을 격자로 배치한다.
- 선택한 항목은 테두리와 체크 표시를 함께 보여준다.
- 색만으로 선택 상태를 전달하지 않는다.
- 각 색상 항목에는 스크린 리더가 읽을 수 있는 이름을 제공한다.
- 데이터베이스에는 HEX 값 대신 `blue-3`, `coral-2` 같은 `color_key`를 저장한다.
- 실제 색상 값은 `src/shared/config/design-system/tokens.ts`에서 관리한다.
- 시즌 팔레트와 자유 색상 선택기는 만들지 않는다.

## 데이터 구조

### 사용자 카테고리

`categories` 테이블은 다음 정보를 가진다.

| 필드         | 역할                                          |
| ------------ | --------------------------------------------- |
| `id`         | 카테고리를 구분하는 UUID                      |
| `user_id`    | 카테고리 소유자                               |
| `name`       | 화면에 표시할 이름                            |
| `color_key`  | 24개 팔레트 중 선택한 색상 키                 |
| `sort_order` | 생성순 표시를 유지하기 위한 숫자              |
| 생성·수정일  | 동일 순서 처리와 운영 확인에 사용하는 시각 값 |

사용자별 카테고리 이름은 앞뒤 공백을 제거하고 연속 공백을 하나로 줄인다. 대소문자만 다른 이름도 중복으로 만들 수 없다. 이름은 1자 이상 50자 이하로 제한한다.

### 인사이트 연결

`insights`에는 비어 있을 수 있는 `category_id`를 추가한다.

- 값이 있으면 같은 사용자의 `categories.id`를 가리킨다.
- 값이 없으면 화면에서 `미분류`로 취급한다.
- 제목·메모 검색은 유지하고 카테고리 이름도 보관함의 정확한 단어 검색에 사용한다.
- 꺼내보기의 Gemini 의미 검색에는 카테고리 이름을 보내지 않는다.

카테고리 ID만 알아낸 사용자가 다른 계정의 카테고리를 자신의 인사이트에 연결하지 못하게 `category_id`와 `user_id`를 함께 확인하는 외래키를 둔다. 애플리케이션 검사에만 의존하지 않는다.

## 기존 데이터 이전

현재 `insights.category`에 저장된 문자열은 다음 순서로 이전한다.

1. `categories` 테이블과 `insights.category_id`를 추가한다.
2. 사용자별로 비어 있지 않은 기존 카테고리 이름을 모은다.
3. 앞뒤·연속 공백과 대소문자 차이만 있는 이름은 같은 카테고리로 합친다.
4. `개발`, `디자인`처럼 현재 고정 색상이 있는 이름은 기존 색상을 이어받는다.
5. 그 밖의 이름은 같은 데이터에서 항상 같은 결과가 나오도록 24개 팔레트에서 순서대로 색상을 배정한다.
6. 모든 기존 인사이트의 `category_id`를 새 카테고리와 연결한다.
7. 백필 전후의 인사이트 `updated_at`이 같은지 검증한다.
8. 비어 있지 않은 기존 카테고리 문자열 중 연결되지 않은 인사이트가 0건인지 검증한다.

기존 `category` 문자열 열은 배포 중 구버전과 새 버전이 겹칠 때를 대비해 이번 배포에서 바로 삭제하지 않는다. 전환 기간에는 데이터베이스 트리거가 구버전의 문자열 변경을 사용자 카테고리와 `category_id`로 바꾸고, 새 버전의 `category_id` 변경·이름 변경·삭제를 문자열에도 반영한다. 새 애플리케이션 코드는 기존 열을 읽거나 쓰지 않고 `category_id`만 사용한다. 실제 데이터 이전과 구버전 트래픽 종료를 확인한 뒤 호환 트리거와 기존 열을 별도 마이그레이션으로 제거한다.

CI는 이전 마이그레이션까지만 적용한 데이터베이스에 legacy fixture를 넣은 뒤 이번 마이그레이션을 적용한다. 이 경로에서 공백 정규화 병합, 식별자 연결, 고정 색상과 정렬 순서, 기존 수정 시각 보존을 검증한다. 복합 외래 키는 `NOT VALID`로 추가하고 후속 마이그레이션에서 검증한다. 고정한 Supabase CLI 2.109.1은 `CREATE INDEX CONCURRENTLY`를 마이그레이션 파이프라인에서 실행하지 못하므로, 조회 인덱스는 별도 마이그레이션으로 격리하고 잠금·실행 시간을 각각 5초로 제한해 운영 중인 `insights` 쓰기를 오래 막지 않는다.

## 사용자 데이터 격리

`categories`에도 `insights`와 같은 사용자별 RLS를 적용한다.

- 로그인한 사용자는 자신의 카테고리만 조회·생성·수정·삭제할 수 있다.
- 카테고리를 만들 때 `user_id`는 현재 로그인 사용자와 같아야 한다.
- 다른 사용자의 카테고리 ID로 인사이트를 업데이트하면 외래키에서 거부한다.
- 브라우저는 Supabase publishable key만 사용하며 service role key를 사용하지 않는다.

RLS는 카테고리 행에 대한 접근을 막고, 사용자 ID를 포함한 외래키는 서로 다른 사용자의 인사이트와 카테고리가 연결되는 것을 막는다. 두 검사를 함께 사용한다.

## 카테고리 삭제와 미분류

애플리케이션의 카테고리 삭제는 데이터베이스 함수 한 번으로 처리하고, 직접 `DELETE`가 실행되어도 같은 연결 해제 규칙이 적용되도록 데이터베이스 트리거로 불변 조건을 보장한다.

1. 로그인 사용자가 해당 카테고리의 소유자인지 확인한다.
2. 카테고리를 삭제하기 직전에 같은 카테고리를 가리키는 사용자의 인사이트만 찾아 `category_id`를 `null`로 바꾼다.
3. 연결이 해제된 카테고리를 삭제한다.
4. 중간 단계가 실패하면 전체 작업을 되돌린다.

이 과정에서 인사이트 행, 제목, 메모와 원문 URL은 삭제하지 않는다. 삭제된 카테고리에 속했던 인사이트는 보관함의 `미분류` 필터에서 확인할 수 있다.

## 프론트엔드 구조

- `entities/category`: 카테고리 타입, 이름 정규화, 저장소 계약과 Supabase 구현을 소유한다.
- `features/category-management`: 관리 모달과 생성·이름/색상 변경·삭제 행동을 소유한다.
- `app`: 인사이트와 카테고리 저장소를 조합하고 두 목록의 상태를 동기화한다.
- `pages/save`: 카테고리 선택과 새 카테고리 생성 진입점을 보여준다.
- `pages/library`: 실제 카테고리 필터와 관리 버튼을 보여준다.
- `entities/insight`: 카테고리 ID와 화면 표시용 카테고리 정보를 사용하며 카테고리 저장소를 직접 호출하지 않는다.

외부 UI 패키지의 모달과 선택 컴포넌트는 `src/shared/ui` 어댑터를 통해 사용한다. 카테고리 화면은 디자인 토큰만 사용하고 모바일에서도 최소 44px 터치 영역을 유지한다.

## 상태 동기화와 실패 처리

- 카테고리 생성이 성공하면 목록에 추가하고 현재 입력의 선택값으로 지정한다.
- 이름이나 색상 변경이 성공하면 카테고리 목록과 인사이트 카드가 같은 객체를 기준으로 다시 렌더링된다.
- 삭제가 성공하면 연결된 인사이트의 카테고리를 화면 상태에서도 `null`로 바꾼다.
- 카테고리 목록을 불러오지 못하면 기존 인사이트는 보여주되 카테고리 변경 기능을 비활성화하고 다시 불러오기 안내를 제공한다.
- 생성·수정·삭제가 실패하면 모달이나 입력을 닫지 않고 사용자의 입력을 유지한다.
- 같은 이름, 빈 이름과 50자를 넘는 이름은 외부 요청 전에 거부하고 데이터베이스에서도 다시 제한한다.

## 최소 검증 범위

테스트 수를 늘리는 대신 데이터 손실과 사용자 흐름에 직접 연결된 경계만 검증한다.

### 데이터베이스

- 기존 카테고리 문자열이 사용자별 카테고리와 `category_id`로 누락 없이 이전된다.
- 다른 사용자의 카테고리는 조회·수정·삭제하거나 인사이트에 연결할 수 없다.
- 카테고리를 삭제하면 인사이트는 남고 `category_id`만 `null`이 된다.

### 프론트엔드

- 새 카테고리를 만들고 인사이트에 선택하면 보관함 필터와 카드에 같은 이름과 색상이 나타난다.
- 카테고리 이름·색상 변경과 삭제가 현재 목록에 반영된다.
- 카테고리 삭제 뒤 연결된 인사이트를 미분류에서 찾을 수 있다.

24개 색상 각각의 렌더링, 모달의 문구·간격, 단순한 버튼 클릭마다 별도 테스트를 만들지 않는다. 기존 테스트는 타입과 사용자 흐름이 바뀌어 필요한 부분만 수정한다.

## 배포와 되돌리기

1. 확장 마이그레이션으로 새 테이블과 연결 열을 추가하고 기존 데이터를 이전한다.
2. 이전 검증이 통과한 뒤 새 프론트엔드를 배포한다.
3. 문제가 생기면 프론트엔드를 이전 버전으로 되돌린다. 기존 `category` 문자열이 남아 있으므로 기존 보관함 동작을 복구할 수 있다.
4. 비공개 테스트에서 새 구조를 확인한 뒤 기존 문자열 열 제거를 별도 진행한다.

카테고리 데이터나 연결을 삭제하는 방식으로 되돌리지 않는다.

## 제외 범위

- 한 인사이트에 여러 카테고리 연결
- 카테고리 직접 정렬
- AI 카테고리 추천과 자동 생성
- 자유 색상 선택기와 시즌 팔레트
- 카테고리를 꺼내보기 의미 검색 단서로 사용
