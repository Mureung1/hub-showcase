## 2. 오늘 새로 확정한 결정 (코드 대조 결과)

### 2-1. E4 full-replace가 새 필드를 지우는 문제 → **서버가 보존**

`updateMeeting`(meetingService.js:568~579)은 컬럼을 명시적으로 전부 덮어쓴다. 여기에 `apply_question`·`image_url`을
그냥 추가하면, 폼이 그 값을 매번 실어 보내지 않는 순간 **조용히 지워진다**. 2026-07-27 최종리뷰가 잡은 읍/면/동
사고와 **정확히 같은 구조**이고, 한마디는 "활성 신청자 있으면 질문 잠금"이라 폼이 값을 안 보낼 여지가 더 크다.

**결정: `applyQuestion`과 `imageUrl` 두 필드만 full-replace의 예외로 둔다.**
- body에 **키가 없으면(`undefined`) 기존 값 유지**, 있으면 교체(`null`이면 명시적 삭제).
- 질문이 잠긴 상태(활성 신청자 존재)에서 **기존 값과 다른 값**을 보내면 `VALIDATION_ERROR`(400). 같은 값이면 통과.
- 다른 필드는 지금처럼 순수 full-replace. 예외는 이 둘로 한정하고 `validators.js`에 주석으로 못 박는다.

근거: FE 버그나 낡은 클라이언트가 값을 날려도 서버가 막는다. 오늘 실제로 당한 실패 모드를 서버 쪽에서 닫는다.

### 2-2. 거절당한 신청(`rejected`) → **어디에도 안 보임**

07-26 설계는 "활성 = `status ≠ cancelled` AND 종료 안 됨 / 내역 = 완료만"인데 `rejected`를 정하지 않아,
규칙대로면 **거절된 신청이 활성 목록에 계속 남는다**.

**결정: `cancelled`와 동일 취급 — 활성·내역 양쪽에서 제외.** 원래 요청이 "취소·완료된 모임이 목록을 어지럽힌다"였고,
거절 사실은 알림(③)이 알려준다.

정리하면 마이페이지 **내가 만든 모임**의 판정은 — 활성: 모임 `status ≠ cancelled` AND 종료 안 됨 / 내역: 모임
`status ≠ cancelled` AND 종료됨 / 안 보임: 모임 `status = cancelled`. (hosted 응답은 `m.status`를 담으므로 직접 검사한다.)

**참여한 모임**의 판정은:
- **활성**: 내 `p.status ∈ {pending, confirmed, approved}` AND 모임 종료 안 됨
- **내역**: 내 `p.status ∈ {confirmed, approved}` AND 모임 종료됨
- **안 보임**: `p.status ∈ {cancelled, rejected}` (모임이 취소되면 E5가 참여자 전원을 `cancelled`로 바꾸므로 자동 포함)
- **안 보임(2026-07-27 추가 결정)**: `p.status = pending`인 채 모임이 **종료된** 경우 — 모임장이 승인도 거절도 하지 않고 모임이 끝난 신청.
  실제로 참여한 것이 아니므로 내역에 넣지 않는다(사용자 결정). 활성에도 남기지 않는다(끝난 모임이 "예정"처럼 보인다).

### 2-3. 이미지 업로드 → **Cloudinary unsigned preset 수용**

프리셋 이름이 FE 번들에 노출돼 제3자가 임의 업로드를 할 수 있다는 걸 인지하고 **감수한다**(서비스 규모가 작다).
완화는 Cloudinary 설정 쪽에서: 업로드 폴더 고정, 최대 5MB, `jpg/png/webp`만.
**배포 후 BE 서명 업로드로 승격**하는 걸 백로그에 남긴다.

BE 검증은 도메인만으로 부족하다 — **`https://res.cloudinary.com/<우리 cloud_name>/image/upload/` 접두사까지 고정**한다
(도메인만 보면 남의 계정 URL이 통과한다).

## 3. 코드 대조로 확인된 전제 (07-26 설계가 맞았음)

- `listJoinedMeetings`(meetingService.js:613)는 **`m.status`를 반환하지 않는다** → 그래도 "BE 변경 0"이 성립한다.
  `cancelMeeting`(:492~498)이 참여자 전원을 `cancelled`로 바꾸므로 `p.status`만 봐도 취소 모임이 걸러진다. ✓
- `applyToMeeting`(:264)과 `cancelMeeting`(:492)은 이미 `withTransaction` 안이다 → 알림 INSERT를 **기존 트랜잭션에** 넣으면 된다. ✓
- `respondToApplicant`(:428)는 **트랜잭션이 없다**(단문 CAS `UPDATE … WHERE status='pending' RETURNING`).
  알림을 원자적으로 넣으려면 **여기에 트랜잭션을 새로 감싼다.** `rowCount > 0`일 때만 INSERT. 단문 CAS 보장은 유지. ✓
- `listParticipants`(:404)의 SELECT에 `p.apply_answer` 한 컬럼만 추가하면 F3가 답변을 실어 준다. ✓

## 4. 구현 함정 (계획서에 그대로 옮길 것)

- **F1 재신청 경로**: `applyToMeeting`은 이전 신청이 `cancelled`면 INSERT가 아니라 **UPDATE**로 되살린다(:304~310).
  이 UPDATE에서 `apply_answer`를 **반드시 새 값으로 덮어써야** 한다 — 안 그러면 예전 답변이 그대로 남는다.
- **E5 알림 대상**: `cancelMeeting`은 거절·취소 이력까지 전원을 `cancelled`로 바꾼다. 알림은 **UPDATE 전에 조회한
  활성 참여자(`pending`/`confirmed`/`approved`)에게만** 보낸다. 이미 거절당한 사람에게 "취소됨"은 노이즈다.
- **pg 타입**: `bigint`(`user_id`, `meeting_id`, `host_id`)와 `numeric`(`trust_score`)은 **JS 문자열**로 온다.
  알림 응답을 만들 때 `Number()` 정규화를 빠뜨리면 FE 비교가 조용히 어긋난다.
- **마이그레이션**: `node-pg-migrate`. `npm run migrate:create <name>` → `migrations/`에 파일 생성 → `npm run migrate`.
  기존 3개 마이그레이션 파일의 스타일을 따른다. 테스트 DB(`bungae_test`)에도 적용돼야 한다.
- **알림 조회 시점**: 라우트 이동 시 조회(폴링 없음). 목록을 열면 그 시점 미읽음 전체를 읽음 처리.

## 5. 배포 전 BE 하드닝 (화요일 마지막 슬롯)

| 항목 | 내용 |
|---|---|
| 세션 저장소 | 기본 `MemoryStore` → **`connect-pg-simple`**(이미 Postgres를 쓰므로 Redis를 새로 붙일 이유가 없다). 재시작마다 전원 로그아웃·메모리 누적·멀티프로세스 불가 해소 |
| 쿠키 | `cookie.secure`(프로덕션만), `sameSite`, `httpOnly` 확인 |
| 세션 고정 | 로그인 시 `req.session.regenerate()` |
| 첫 로그인 경합 | `userService`의 SELECT→INSERT를 `ON CONFLICT (provider, provider_id) DO NOTHING` + 재조회로 |
| build context | FE·BE가 `shared/regions.json`을 **폴더 밖 상대경로**로 import한다. 배포 build context를 저장소 루트로 고정(또는 prebuild 복사) — 안 하면 배포에서 "파일 없음"으로 즉시 실패 |
| 인덱스(B5) | `meeting_participants(user_id)`, `meetings(host_id)`, `notifications(user_id, created_at)`. `meetings`는 PK 말고 인덱스가 하나도 없다 |

## 6. 검증 기준

- **BE**: 기존 스타일대로 TDD(supertest + `bungae_test`). 기준선 **200/200**을 깨지 않고 늘린다.
- **FE**: 자동 테스트 없음 → `npm run lint`(기존 `AppStateContext.jsx` 경고 **1건만** 허용) + `npm run build`.
- **수동 확인**: 구글 로그인이 필요한 흐름은 **사용자 육안 검증으로 모아서** 처리한다(각 태스크에서 서버를 띄우지 않는다).
- 진행 방식은 1단계와 동일: **Subagent-Driven + 태스크별 한글 커밋**(푸시는 요청 시).
