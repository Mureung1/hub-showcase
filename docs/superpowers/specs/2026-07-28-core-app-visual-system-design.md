## 1. 배경

현재 White Canvas 계열 디자인은 콘텐츠를 차분하게 보여 주지만 다음 한계가 있다.

1. 페이지와 카드가 모두 순백색에 가까워 넓은 화면을 오래 볼 때 밝기 부담이 크다.
2. 프로젝트를 소개하는 대표 스크린샷을 갤러리 카드의 썸네일로 축소하면 화면의 인상과 화면별 구분이 약하다.
3. 넓은 화면에서도 하단 내비게이션을 사용해 모바일 레이아웃을 확대한 듯 보인다.
4. 화면별 첫 행동, 보조 탐색, 결과가 한 평면에 놓여 정보 위계가 충분히 드러나지 않는다.

이번 개편은 기존 White Canvas의 절제된 성격을 버리는 전면 재디자인이 아니다. 인증 후 핵심 제품 여정에 한해 따뜻한 Paper, 밝은 Surface, 화면별 대표 색면을 조합해 눈의 부담과 시각적 단조로움을 줄인다. 기능 의미, API, 데이터 계약, 정보 구조는 유지한다.

## 2. 목표

- 순백색이 차지하는 면적을 줄여 오래 보기 편한 기본 화면을 만든다.
- 홈, 보관함, 저장의 첫 행동을 화면별 대표 색면 안에서 명확하게 강조한다.
- 대표 스크린샷을 축소해도 제품과 각 화면의 성격을 식별할 수 있게 한다.
- 데스크톱과 태블릿에는 상단 내비게이션, 모바일에는 하단 내비게이션을 제공한다.
- 기존 디자인 토큰과 FSD 경계를 유지하면서 점진적으로 적용할 수 있는 구조를 만든다.
- 변경 범위에 필요한 검증만 추가한다.

## 3. 범위 밖

다음 항목은 이번 구현에 포함하지 않는다.

- 랜딩 및 로그인 화면 개편
- 가져오기 대화상자, 카테고리 관리, PWA 보조 화면 개편
- Android 공유 화면 개편
- Chrome 확장 프로그램 화면 개편
- 홈 제안 문구 개인화
- 콘텐츠 구조, API, 데이터베이스 스키마 변경
- 새로운 애니메이션 체계나 그래픽 자산 제작
- 구현 전 대표 썸네일 한 장 확정

범위 밖 화면은 후속 이슈로 분리한다. 핵심 앱의 새 체계가 실제 화면에서 안정된 뒤 같은 원칙을 적용하되, 각 채널의 제약에 맞게 별도로 검토한다.

### 4.1 공개 작업 기록의 표현

GitHub 이슈와 PR 본문은 구현 내부 용어보다 사용자가 바로 이해할 수 있는 표현을 사용한다.

| 내부 설계·코드 용어   | 이슈와 PR 본문 표현          |
| --------------------- | ---------------------------- |
| Paper                 | 기본 배경색                  |
| Surface               | 카드·입력 배경색             |
| screen identity color | 화면별 대표 색상             |
| stage                 | 첫 행동을 강조하는 색상 영역 |

내부 용어는 코드 토큰명과 설계 문서에서 역할을 정확히 구분할 때만 사용한다. 공개 작업 기록에는 토큰명, 컴포넌트명, 레이아웃 구현명을 변경 이유처럼 쓰지 않는다.

## 5. 시각 토큰

### 5.1 Paper와 Surface

`Paper`는 페이지의 바탕이고 `Surface`는 콘텐츠를 담는 면이다.

- `Paper`: `#F4F1E9`
  - 인증 후 페이지의 전역 배경
  - 넓은 여백, 결과 영역 사이의 바탕
- `Surface`: `#FFFDF8`
  - 상단바
  - 카드
  - 입력 필드
  - 알림과 보조 패널

기존 `color.canvas`는 랜딩, 로그인과 보조 화면에서도 사용한다. 이번 범위 밖 화면의 색까지 암묵적으로 바꾸지 않도록 값 `#FFFFFF`을 유지한다. `color.surface`와 `color.paper`를 새로 추가하고, 인증 후 워크스페이스 안에서만 기존 공용 컴포넌트가 `color.surface`를 사용하도록 `--color-canvas: var(--color-surface)`를 범위 지정한다.

```ts
color: {
  canvas: "#FFFFFF",
  paper: "#F4F1E9",
  surface: "#FFFDF8",
  retrieveBlue: "#1358D8",
  libraryCoral: "#C94032",
  saveGreen: "#08765B",
}
```

CSS는 기존 원칙대로 토큰에서 생성한 변수만 소비한다. 화면 컴포넌트에 색상 리터럴을 반복해서 작성하지 않는다. 이 범위 지정은 인증 후 핵심 앱만 개편하고 랜딩, 로그인과 보조 화면은 후속 이슈로 남긴다는 범위 계약도 지킨다.

### 5.2 화면 대표 색

대표 색은 화면의 정체성과 첫 행동을 구분하기 위한 도메인 토큰이다.

- `retrieveBlue`: 홈과 꺼내보기
- `libraryCoral`: 보관함
- `saveGreen`: 저장

대표 색은 성공, 경고, 오류 같은 의미를 전달하지 않는다. 기존 의미 색상 토큰과 상태 컴포넌트는 그대로 유지한다. 오류가 발생해도 화면 대표 색을 빨강으로 바꾸지 않으며, 성공 후에도 대표 색을 초록으로 바꾸지 않는다.

### 5.3 대비

기준 텍스트 조합의 WCAG 대비는 다음과 같다.

| 조합                                 |    대비 |
| ------------------------------------ | ------: |
| 잉크 `#151619` / Paper `#F4F1E9`     | 16.03:1 |
| 잉크 `#151619` / Surface `#FFFDF8`   | 17.80:1 |
| Surface `#FFFDF8` / 홈 `#1358D8`     |  6.05:1 |
| Surface `#FFFDF8` / 보관함 `#C94032` |  4.85:1 |
| Surface `#FFFDF8` / 저장 `#08765B`   |  5.50:1 |

대표 색면의 일반 텍스트와 아이콘은 `#FFFDF8`을 사용한다. 반투명 텍스트를 사용할 경우 구현 단계에서 실제 배경과의 4.5:1 이상 대비를 다시 확인한다.

## 6. 레이아웃 구조

### 6.1 공통 셸

인증 후 셸은 다음 순서로 구성한다.

1. 전체 너비 Surface 상단바
2. 전체 너비 화면 대표 색면
3. Paper 위의 화면 본문
4. 모바일에서만 고정되는 Surface 하단 내비게이션

상단바와 대표 색면은 화면 전체 너비를 사용한다. 실제 콘텐츠는 내부 컨테이너로 정렬한다.

- 상단바 내부 최대 너비: `1200px`
- 대표 색면의 행동 영역 최대 너비: `820px`
- 일반 본문 최대 너비: `1200px`

대표 색면은 둥근 카드처럼 안쪽에 띄우지 않는다. 상단바 바로 아래에서 화면 양 끝까지 이어져 페이지의 인상을 만든다. Paper 본문은 이 색면과 분리하되 기존의 얇은 테두리, 작은 반지름, 그림자와 그라디언트를 쓰지 않는 원칙을 유지한다.

### 6.2 내비게이션

내비게이션 정보 구조는 홈, 보관함, 저장으로 유지한다.

- `768px` 이상: 상단바 안에서 로고와 계정 영역 사이에 표시한다.
- `767px` 이하: 화면 하단에 고정한다.
- 모바일에서도 브랜드와 계정 상태를 보여 주는 얇은 상단바는 유지한다.
- 좌측 레일이나 대시보드형 사이드바는 도입하지 않는다.

동일한 링크를 두 벌 렌더링하지 않는다. `AppNavigation` 인스턴스 하나를 상단바 구조 안에 두고, 반응형 스타일로 넓은 화면에서는 일반 흐름의 상단 내비게이션, 모바일에서는 고정 하단 내비게이션으로 배치한다. 이렇게 하면 접근성 이름, 현재 위치, 링크 순서가 화면 크기에 따라 달라지는 일을 막을 수 있다.

## 7. 화면별 구성

### 7.1 홈

홈은 꺼내보기 행동을 파란 대표 색면에서 시작한다.

대표 색면:

- 화면 이름과 한 문장 설명
- 꺼내보기 검색어 입력
- 실행 버튼

Paper 본문:

- 현재의 고정 제안 여섯 개
- 입력 오류가 아닌 로딩, 빈 결과, 검색 결과
- 후속 탐색과 결과 카드

제안 문구는 현재 모든 사용자에게 동일하게 제공된다. 사용자가 선택하면 문구가 검색어 입력에 반영되고 기존 꺼내보기 흐름을 실행한다. 이번 작업에서는 카테고리 필터로 오해하게 만드는 새 기능을 추가하거나 개인화하지 않는다.

### 7.2 보관함

보관함은 찾기를 코럴 대표 색면에서 시작한다.

대표 색면:

- 화면 이름과 한 문장 설명
- 보관함 검색
- 내 저장물 가져오기 행동

Paper 본문:

- 카테고리 선택과 관리 진입점
- 현재 조건에 맞는 인사이트 개수
- 인사이트 카드 그리드
- 로딩, 빈 결과, 오류 복구 안내

인사이트 개수는 화면 전체의 장식적 숫자가 아니라 현재 결과를 설명하는 문맥 정보로 취급한다. 카테고리와 검색 조건 아래, 카드 그리드 바로 위에 배치한다.

- 기본: `인사이트 24개`
- 카테고리 선택: `학습 8개`
- 검색 결과: `검색 결과 3개`

실제 문구는 UX 라이팅 가이드의 수량 표기 원칙을 따르며, 개수 산정 로직은 기존 데이터를 그대로 사용한다.

### 7.3 저장

저장은 링크 입력을 초록 대표 색면에서 시작한다.

대표 색면:

- 화면 이름과 한 문장 설명
- 붙여넣기 행동
- URL 입력
- 저장 시작 버튼

Paper 본문:

- 저장을 위해 추가로 필요한 맥락 입력
- 분석 중, 분석 완료, 저장 완료 상태
- 오류와 다시 시도
- 저장 결과

첫 URL 입력 이후에만 필요한 입력과 상태는 대표 색면에 계속 쌓지 않는다. 대표 색면은 언제나 첫 행동까지만 담고, 진행 상태와 후속 단계는 Paper 본문에서 보여 준다.

## 8. 상태와 문구

상태 표현은 화면 정체성과 분리한다.

- 입력 오류: 문제가 있는 필드 바로 가까이에 Surface 알림으로 표시
- 로딩: Paper 본문에서 현재 처리 중인 대상을 표시
- 빈 상태: Paper 본문에서 다음 행동을 제안
- 성공: Paper 본문에서 결과와 이어서 할 일을 표시

새 문구와 수정 문구는 `docs/ux-writing.md`를 따른다. 다만 이번 작업은 제품 전체 문구를 다시 쓰는 작업이 아니다. 시각 구조 변경 때문에 위치나 문맥이 달라지는 문구만 검토하고, 기능 의미를 바꾸지 않는다.

## 9. 반응형 동작

| 구간             | 상단바                  | 내비게이션 | 대표 색면                 | 본문                             |
| ---------------- | ----------------------- | ---------- | ------------------------- | -------------------------------- |
| `1280px` 이상    | 최대 `1200px` 내부 정렬 | 상단 중앙  | 전체 너비, 내부 `820px`   | 최대 `1200px`                    |
| `768px`~`1279px` | 좌우 여백 축소          | 상단       | 전체 너비, 내부 여백 축소 | 가용 너비 사용                   |
| `767px` 이하     | 브랜드와 계정만 유지    | 하단 고정  | 세로 배치                 | 한 열, 하단 내비게이션 여백 확보 |

모바일에서는 입력과 버튼을 세로로 쌓고 최소 터치 영역을 지킨다. 하단 내비게이션 때문에 마지막 콘텐츠가 가려지지 않도록 안전 영역과 내비게이션 높이를 본문 하단 여백에 반영한다.

## 10. 접근성

- 대표 색에만 의존해 현재 화면이나 상태를 전달하지 않는다.
- 현재 내비게이션은 텍스트, 위치, 접근성 상태로 함께 표시한다.
- `prefers-reduced-motion` 기존 계약을 유지한다.
- 포커스 링은 대표 색면과 Surface 양쪽에서 식별 가능해야 한다.
- 모바일 고정 내비게이션은 확대 및 가상 키보드 사용 중 핵심 입력을 가리지 않아야 한다.
- 대표 색면 안의 입력은 레이블을 유지하며 placeholder만으로 용도를 설명하지 않는다.
- 색상 대비는 토큰뿐 아니라 비활성, hover, focus 상태에서도 확인한다.

## 11. 데이터와 동작 계약

이번 개편은 표현 계층의 변경이다.

- 라우트와 내비게이션 목적지는 유지한다.
- 검색, 꺼내보기, 저장, 가져오기 동작은 유지한다.
- API 요청과 응답 형식은 변경하지 않는다.
- 데이터베이스 스키마와 저장 데이터는 변경하지 않는다.
- 카테고리와 검색 결과 개수는 현재 필터링 결과에서 계산한다.
- 홈 제안 선택 시의 기존 검색 실행 흐름을 유지한다.

시각 구조를 맞추기 위해 도메인 로직을 페이지 컴포넌트로 끌어올리거나 공유 컴포넌트에 화면별 분기를 추가하지 않는다.

## 12. 코드 경계

상세 파일별 작업 순서는 구현 계획에서 확정하되 다음 경계를 지킨다.

- 디자인 토큰: `src/shared/config/design-system`
- 공통 셸과 내비게이션: 기존 인증 후 워크스페이스 및 공용 내비게이션
- 홈 조합: 홈 페이지와 꺼내보기 기능의 공개 인터페이스
- 보관함 조합: 보관함 페이지와 기존 검색·카테고리 기능
- 저장 조합: 저장 페이지와 기존 저장 기능

공통 대표 색면이 세 화면에서 동일한 구조와 접근성 계약을 갖는다면 공용 UI로 추출할 수 있다. 단순히 마크업 몇 줄을 줄이기 위한 선제 추상화는 하지 않는다. 화면별 기능 컴포넌트는 기존 FSD 공개 인터페이스를 통해 조합한다.

## 13. 대표 스크린샷 결정

대표 썸네일은 구현 전에 확정하지 않는다. 현재 후보 A인 홈 단일 장면은 가장 유력하지만, 실제 색과 밀도, 타이포그래피가 적용된 뒤 판단해야 한다.

구현 완료 시 다음 순서로 비교한다.

1. 홈, 보관함, 저장을 각각 데스크톱 기준으로 캡처한다.
2. 프로젝트 갤러리 카드의 실제 16:9 표시 크기로 축소한다.
3. 후보 A인 홈 단일 장면과 대안 구성을 나란히 비교한다.
4. 작은 크기에서 제품 이름, 첫 행동, 색면이 식별되는지 확인한다.
5. 사용자가 확인한 뒤 대표 스크린샷을 별도 산출물로 확정한다.

따라서 대표 이미지 제작은 UI 구현 완료 조건에는 포함하지만, 이번 설계 단계의 확정 항목에는 포함하지 않는다.

## 14. 최소 검증

변경 범위에 직접 필요한 검증만 수행한다.

자동 검증:

- 디자인 토큰 값과 핵심 텍스트 대비
- `768px` 경계에서 내비게이션 위치가 바뀌는 계약
- 홈, 보관함, 저장의 대표 색면과 Paper 본문 구성
- 기존 테스트 중 수정한 동작에 직접 연결된 항목

수동 검증:

- `390px`, `768px`, `1280px`에서 레이아웃 확인
- 모바일 하단 내비게이션이 콘텐츠와 입력을 가리지 않는지 확인
- 대표 색면 안의 focus, error, disabled 상태 확인
- 실제 16:9 갤러리 카드 크기에서 대표 스크린샷 후보 비교

추가하지 않는 검증:

- 변경하지 않은 랜딩, 로그인, 가져오기, 확장 프로그램의 새 시나리오
- 같은 문구나 배치를 여러 경로에서 반복 확인하는 테스트
- 시각 변경과 무관한 전역 사용자 여정
- 구현 세부 DOM 구조를 고정하는 스냅샷 남발

## 15. 구현 의존 순서

구현은 다음 의존 관계를 따른다.

1. Paper, Surface, 화면 대표 색 토큰을 확정한다.
2. 인증 후 공통 셸과 반응형 내비게이션을 변경한다.
3. 공통 대표 색면 계약을 적용한다.
4. 홈, 보관함, 저장을 각각 새 영역에 조합한다.
5. 직접 영향받은 상태와 문구를 확인한다.
6. 최소 자동 검증과 세 해상도 수동 검증을 수행한다.
7. 실제 갤러리 카드 크기로 대표 스크린샷 후보를 비교한다.

화면 구현을 동시에 시작해 공통 셸과 토큰을 중복 수정하지 않는다.
