## 목표

로그인한 사용자가 **남의 모임에 신청**해서, 번개모임은 즉시 확정되고 소모임은 승인 대기에
들어가며, 성인 전용 모임은 미성년/판별불가 계정이 차단되고, 신청을 취소하면 상태가 되돌아가는
전체 흐름을 FE → BE → DB로 실동작시킨다. 승인/거절(F3/F4)은 Day 3, 마이페이지(G)는 Day 4다.

## 범위

- **D5** `PATCH /api/users/me` — 생년월일 최초 입력.
- **F1** `POST /api/meetings/:id/apply` — 참여 신청.
- **F2** `DELETE /api/meetings/:id/apply` — 신청/참여 취소.
- **E3 확장** — 상세 응답에 `canApply` / `blockReason` 추가.
- **목록 확장** — `listMeetings` 응답 항목에 `confirmedCount` 추가.
- **FE** — 생년월일 입력 게이트, 상세 신청/취소 실연동, 목록/상세 정원 표시 일원화.

## 핵심 아키텍처 결정

### 결정 1 — "신청 가능 여부" 판정을 순수 함수 한 곳에 모은다

성인 차단·정원 마감·중복 신청 등의 규칙이 **상세(E3)와 신청(F1) 두 곳에서 각각 구현되면**
어긋난다(Day 1에서 FE/BE 이중 성인 판정이 KST 밖에서 하루 어긋나던 문제와 같은 종류의 함정).
그래서 순수 판정 함수를 하나 만들고 둘이 공유한다.

**`src/utils/participation.js` (신규, 순수 함수):**

```
evaluateApplicability({ meeting, viewer, confirmedCount, existingStatus, isPast, now })
  → { canApply: boolean, blockReason: string | null }
```

- `meeting` — 모임 행(type, capacity, status, adultOnly, hostId). **시각 필드로 직접 판정하지 않음.**
- `viewer` — `{ id, birthDate }` 또는 `null`(비로그인).
- `confirmedCount` — 확정 인원(confirmed + approved).
- `existingStatus` — 이 viewer의 기존 참여 상태(`pending`/`confirmed`/`approved`/`rejected`/`cancelled`) 또는 `null`.
- `isPast` — 모임이 지났는지 여부. **호출부가 DB SQL에서 계산해 주입**한다(아래 B-4). 순수 함수는
  JS 날짜 비교를 하지 않는다.
- `now` — **성인 나이 경계 계산(`isAdult`)에만** 쓰는 시각 주입(테스트 고정용).

**서버가 진실의 원천이다.** 상세는 이 결과를 그대로 응답에 싣고, FE는 버튼 상태를 이걸로만
결정한다(FE의 독립 성인 판정 `isAdultBirthDate`는 **제거**). F1은 같은 함수로 판정한 뒤
`blockReason`을 HTTP 에러로 매핑한다 — FE를 우회한 직접 요청도 여기서 최종 차단된다.

### blockReason 열거값과 우선순위 (위에서부터 먼저 매칭, 첫 매칭이 이긴다)

우선순위 근거: `blockReason`은 "지금 이 사람에게 왜 신청 버튼을 줄 수 없는가"에 답하고,
FE는 그 값으로 보여줄 버튼/문구를 고른다. 그래서 **"이 사람이 이 모임에 대해 누구인가"(정체성)**
를 먼저 알려주고, 그다음 모임 상태, 마지막에 자격(성인) 순으로 둔다.

| 순위 | blockReason | 조건 | FE가 보여줄 것 |
|---|---|---|---|
| 1 | `LOGIN_REQUIRED` | viewer 없음(비로그인) | "로그인하러 가기" |
| 2 | `HOST` | viewer가 모임장 | 모임장 관리 UI(신청 버튼 없음) |
| 3 | `ALREADY_APPLIED` | existingStatus ∈ {pending, confirmed, approved} | 현재 내 상태 + 취소 버튼 |
| 4 | `REJECTED` | existingStatus = rejected | "신청이 거절되었습니다"(재신청 불가) |
| 5 | `CANCELLED_MEETING` | meeting.status = cancelled | "취소된 모임입니다" |
| 6 | `ENDED` | 모임이 지난 시각(`isPast` — **SQL에서 `now()`로 계산해 주입**, 아래 B-4) | "종료된 모임입니다" |
| 7 | `FULL` | **`type === 'flash'`** 이고 `confirmedCount >= capacity` | "정원이 찼습니다" |
| 8 | `BIRTHDATE_REQUIRED` | adultOnly이고 `isAdult(birthDate) === null` | "생년월일 입력이 필요합니다" |
| 9 | `ADULT_ONLY` | adultOnly이고 `isAdult(birthDate) === false` | "성인만 참여할 수 있는 모임입니다" |
| — | `null` | 위 어디에도 안 걸림 | **신청 버튼 활성** |

**정밀화(B-1):** `ALREADY_APPLIED`는 "참여 row가 존재"가 아니라 **위 세 상태일 때만**이다.
`cancelled`는 재신청 허용(순위 3·4 어디에도 안 걸려 아래로 내려가 신청 가능), `rejected`는
순위 4에서 차단(아래 결정 4).

**구현 함정 — FULL의 null 강제변환:** `small`은 `capacity`가 `null`이다. flash 가드 없이
`confirmedCount >= capacity`로 쓰면 JS에서 `5 >= null` → `5 >= 0` → `true`가 되어 **확정 인원이
1명이라도 있는 소모임이 전부 FULL로 오탐**된다. 반드시 `type === 'flash' &&
confirmedCount >= capacity`로 가드하고, 캐시된 `status='closed'`가 아니라 **인원수를 기준**으로
판정한다(스테일 status로 잘못 막는 것 방지). `evaluateApplicability`의 단위 테스트에
"확정자 있는 small은 FULL이 아니다"를 반드시 포함한다.

### 결정 2 — birthDate는 최초 1회만 설정, 이후 잠금

`PATCH /api/users/me`는 `birth_date IS NULL`일 때만 값을 받는다. 이미 값이 있으면
`VALIDATION_ERROR`("생년월일은 수정할 수 없습니다"). 자기신고라 처음 거짓말은 못 막지만,
성인↔미성년을 오가며 성인 전용 모임을 악용하는 건 막는다.

> API 명세서 28번 줄은 "생년월일 등 최초 입력값 등록/수정"으로 돼 있다. 이 슬라이스에서
> 명세서를 "birthDate는 최초 1회만"으로 정정한다.

### 결정 3 — 자기신고 성인 판별의 한계는 "의식적으로 미뤄둔 것"

기획서 196번 줄: 1차 버전 본인확인은 소셜 로그인 수준, **정교한 본인인증은 추후 검토**.
따라서 자기신고 생년월일로 성인을 판별하는 건 스펙에 부합하는 의도된 수준이다. 진짜 강제는
휴대폰 본인확인 등 외부 본인확인기관 연동이 필요하며 이번 주 범위 밖이다. 이 한계를
`participation.js`·D5 핸들러 주석과 본 문서에 명시해, "실수로 뚫린 것"이 아니라 "결정으로
미뤄둔 것"임을 남긴다.

### 결정 4 — 취소(cancelled)는 재신청 허용, 거절(rejected)은 최종

- `cancelled`(내가 취소) → 기존 row를 되살리는 **UPDATE**로 재신청. 새 INSERT는
  `UNIQUE(meeting_id, user_id)` 위반(500)이 되므로 반드시 UPDATE.
- `rejected`(모임장이 거절) → `REJECTED`로 차단. 무한 재신청으로 모임장을 괴롭히는 걸 막는다.
  실수 거절을 되돌릴 수단이 없는 단점은 MVP에서 감안.

### 결정 5 — 정지(suspended) 계정 차단은 이번엔 넣지 않는다

`users.suspended_until`/`SUSPENDED` 코드는 있지만 "정지를 거는 기능"이 이번 주 범위 밖이라
거는 쪽이 없다. F1에 검사만 넣으면 테스트할 수도, 실제 막을 대상도 없어 YAGNI.
정지 기능(H/B 시리즈) 구현 시 `evaluateApplicability`에 `SUSPENDED` 사유를 추가한다.

## 엔드포인트 상세

### D5 `PATCH /api/users/me` (인증 필요)

- 요청: `{ "birthDate": "YYYY-MM-DD" }`.
- 검증: 형식(`^\d{4}-\d{2}-\d{2}$`) + 실제 달력 날짜(월 1–12, 일이 그 달에 유효) + **미래 아님**.
  위반 시 `VALIDATION_ERROR`.
- 이미 `birth_date`가 있으면 `VALIDATION_ERROR`(결정 2).
- 성공: `birth_date` 갱신 후 `normalizeUser` 반환.
- 검증 로직은 `utils/validators.js`에 `validateBirthDate`로 추가(기존 스타일).

### F1 `POST /api/meetings/:id/apply` (인증 필요)

**트랜잭션 안에서 처리한다** — 정원 동시 신청 초과를 막는 게 핵심.

1. `BEGIN`.
2. `SELECT *, COALESCE(end_at, start_at) < now() AS is_past FROM meetings WHERE id = $1 FOR UPDATE`
   — 모임 행 잠금. 같은 모임에 동시 신청한 요청들을 직렬화한다(뒤 요청은 앞 요청 커밋까지 대기 후
   최신 상태로 재판정). `is_past`도 여기서(DB 시계로) 함께 뽑는다(B-4). 없으면 404.
3. 신청자 `birth_date`, 기존 참여 `status`, 확정 인원(confirmed+approved) 조회.
4. `evaluateApplicability({ meeting, viewer, confirmedCount, existingStatus, isPast, now })` 판정.
   - `canApply === false`면 `blockReason`을 에러로 매핑해 throw(아래 매핑표). 트랜잭션 롤백.
5. 통과 시:
   - `flash`: 상태 `confirmed`. 이 신청으로 확정 인원이 정원에 도달하면 `meetings.status='closed'`.
   - `small`: 상태 `pending`.
   - 기존 row가 `cancelled`면 그 row를 새 상태로 **UPDATE**하되 **`applied_at = now()`,
     `responded_at = NULL`도 함께 리셋**(낡은 타임스탬프를 물고 오지 않도록). 없으면 INSERT.
6. `COMMIT`. 응답으로 `{ status }` 반환(FE는 이후 상세를 재조회해 openChatUrl 등 최신값을 받는다).

**blockReason → HTTP 매핑:**

| blockReason | 코드 | HTTP |
|---|---|---|
| `LOGIN_REQUIRED` | (requireAuth가 먼저 처리 — F1에선 도달 불가) | 401 |
| `HOST`, `ALREADY_APPLIED`, `REJECTED`, `CANCELLED_MEETING`, `ENDED` | `VALIDATION_ERROR` | 400 |
| `FULL` | `VALIDATION_ERROR`(message에 정원 마감 명시) | 400 |
| `BIRTHDATE_REQUIRED`, `ADULT_ONLY` | `FORBIDDEN` | 403 |

### F2 `DELETE /api/meetings/:id/apply` (인증 필요)

**트랜잭션 안에서 처리한다.**

1. `BEGIN`, 모임 행 `FOR UPDATE`.
2. 기존 참여 조회. 없거나 이미 `cancelled`면 아무 것도 하지 않는다(이중취소 방지 — 아래 B-3).
   → `NOT_FOUND`("취소할 신청이 없습니다").
3. 상태 전이:
   - `confirmed`/`approved` → `cancelled` + 신뢰도 감점. **감점은 JS 읽기-쓰기가 아니라
     SQL 상대 갱신 `UPDATE users SET trust_score = GREATEST(trust_score - 3, 0)`으로 한다** —
     한 사용자가 서로 다른 두 모임을 동시에 취소하면 모임 행 잠금이 직렬화해주지 못해(감점 대상은
     users 행) JS로 하면 갱신이 유실된다. Postgres 행 잠금이 SQL 상대 갱신은 알아서 직렬화한다.
     flash이고 모임이 `closed`였으면 자리가 비므로 `recruiting`으로 **재오픈**.
   - `pending` → `cancelled`(감점 없음).
   - `rejected` → 취소할 것이 없음(`NOT_FOUND`).
4. `COMMIT`. 응답 `{ status: 'cancelled' }`. FE는 상세 재조회.

**B-3(이중취소 방지):** 신뢰도 감점은 **`confirmed`/`approved` → `cancelled` 전이일 때만**.
이미 `cancelled`인 걸 다시 DELETE해도 두 번 깎이지 않는다.

### 트랜잭션 구현 주의 (필수 — 이 코드베이스 첫 트랜잭션)

이 저장소는 지금까지 트랜잭션을 쓴 적이 없고 `db.js`는 `Pool`만 export한다. **절대 `pool.query`로
`BEGIN`/`FOR UPDATE`/`INSERT`를 나눠 호출하지 말 것** — `pool.query`는 호출마다 풀에서 다른
커넥션을 집어올 수 있어, `FOR UPDATE` 잠금이 INSERT와 다른 커넥션에 걸리면 **잠금이 아무 것도
막지 못하고**(정원 동시 신청 초과 방지가 그대로 뚫림) 원자성도 깨진다.

반드시 **커넥션 하나(`pool.connect()`)를 잡아** 그 `client`로만 트랜잭션을 돌린다:

```
const client = await pool.connect();
try {
  await client.query('BEGIN');
  // ... SELECT ... FOR UPDATE, 판정, INSERT/UPDATE 모두 client로 ...
  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK');
  throw err;            // ApiError(MEETING_FULL 등 '정상 거절')도 여기로 온다
} finally {
  client.release();
}
```

**핵심:** `MEETING_FULL`·`ADULT_ONLY` 같은 "정상적인 거절"도 잠금을 쥔 채 throw되므로, catch에서
`ROLLBACK` 후 release하지 않으면 커넥션이 열린 트랜잭션 상태로 풀에 반납돼 오염된다. 반복 코드가
되면 `withTransaction(fn)` 헬퍼를 하나 만들어 F1/F2가 공유한다(Day4 E5의 일괄 트랜잭션도 재사용).

## E3 상세 응답 확장

기존 `getMeetingDetail`에 다음을 추가한다.

- viewer의 `birth_date`를 조회(기존 myParticipation 조회 쿼리를 확장하거나 별도 조회).
- 모임 조회 SELECT에 `COALESCE(end_at, start_at) < now() AS is_past`를 함께 뽑는다(F1과 같은
  방식 — B-4). `evaluateApplicability`에 `isPast`로 넘긴다.
- `evaluateApplicability(...)`로 `canApply`, `blockReason` 계산해 응답에 포함.
- 기존 `confirmedCount`, `myParticipation`, 조건부 `openChatUrl`은 그대로.

## 목록 응답 확장 — `confirmedCount`

`listMeetings`의 각 항목에 `confirmedCount`를 추가한다(상관 서브쿼리 또는 집계 조인).
안 하면 같은 모임이 홈/목록에선 "0/N명", 상세에선 "K/N명"으로 어긋난다(CLAUDE.md 지적).
FE `MeetingCard`가 `meeting.confirmedCount`를 직접 읽게 하고, 클라이언트 계산
`getConfirmedCount`는 정리한다.

**구현 주의:** `normalizeMeetingListItem`은 `normalizeMeeting`의 **고정 필드 집합만** 매핑한다.
서브쿼리로 뽑은 `confirmed_count`는 `normalizeMeeting`을 타지 않으므로 `normalizeMeetingListItem`
에서 **명시적으로 추가**해야 한다(안 하면 조용히 누락된다). 기존 목록 테스트는 필드 단위 검사
(`toHaveLength`·`map(m=>m.title)`)라 필드 추가로 깨지지 않음(확인함).

> 페이지 크기 20 기준 상관 서브쿼리로 충분. 성능 최적화는 최적화 백로그로 미룬다.

## "지난 모임" 판정 일원화 (B-4)

시간 경과 판정이 지금 **목록 SQL(`COALESCE(end_at, start_at) >= now()`)** 한 곳에 있는데,
F1과 상세 canApply에도 필요해진다.

**JS로 판정하지 않는다.** `start_at`/`end_at`은 `timestamp`(without time zone)라 pg가 돌려주는
JS Date는 Node 프로세스 로컬 타임존으로 파싱된다. 이걸 `new Date()`와 비교하면 목록은 DB `now()`,
신청/상세는 JS 시계로 판정하는 **두 시계 불일치**가 생긴다 — Day1에 4개 타임존에서 잡았던 계열의
버그다. 그래서 **모임을 조회/잠그는 그 SELECT에서 `COALESCE(end_at, start_at) < now() AS is_past`를
함께 뽑아** boolean으로 `evaluateApplicability`에 넘긴다. DB 하나만 시계로 쓰므로 목록과 일관된다.
`evaluateApplicability`는 시각 계산을 하지 않고 주입된 `isPast` boolean만 본다(순수성 유지).
`now`는 성인 나이 경계 계산(`isAdult`)에만 쓴다.

## 프론트 설계

- **`api/users.js` 신규**: `updateMe(birthDate)` → `PATCH /api/users/me`.
- **`api/meetings.js`**: `applyToMeeting(id)`(POST), `cancelParticipation(id)`(DELETE) 추가.
- **생년월일 게이트**: 부트스트랩 후 `isLoggedIn && currentUser.birthDate == null`이면 라우트
  대신 생년월일 입력 화면을 렌더 → `updateMe` 성공 시 user 갱신 후 정상 진입. 기획서 6.1의
  "최초 로그인 시 생년월일 입력" 방침. `birthDateRequired` 대신 `birthDate == null` 기준을
  쓰는 이유: 기존 null 사용자(개발 DB의 유일 계정 포함)도 게이트에 걸려야 하기 때문.
  **1주차 StrictMode 경합 근처를 건드리므로 회귀 주의 — 수동 확인 필수.**
- **상세 신청/취소**: 버튼을 mock 컨텍스트 함수가 아니라 `applyToMeeting`/`cancelParticipation`
  실호출 + **성공 후 상세 재조회**(reloadKey)로 연결. 번개모임은 신청 즉시 confirmed가 되어
  openChatUrl이 새로 내려오므로 재조회 필수. 버튼 활성/문구는 서버 `canApply`/`blockReason` 기준.
  **주의:** 상세의 `myParticipation`은 이제 `cancelled`/`rejected`도 내려온다. FE는 이걸 "참여 중"
  으로 보면 안 되고(취소한 사람은 다시 신청 버튼이 보여야 함), 반드시 `canApply`/`blockReason`으로
  분기한다.
- **컨텍스트 정리**: `AppStateContext`의 mock `applyToMeeting`/`cancelMyParticipation` 제거.
  `respondToApplicant`/`cancelMeeting` mock은 Day 3/4까지 유지.
