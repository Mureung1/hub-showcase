## Slide 1: 제목 (30초)

안녕하세요. 

저는 CalMe 프로젝트의 3주차 개발 결과를 보고하겠습니다.

CalMe는 AI 기반 대학생 일정 관리 서비스입니다.

오늘은 2주차의 Mock 데이터에서 벗어나 **실제 Claude API를 연결**하고, 
AI 분석 결과를 사용자가 **수정하고 저장하는 기능**을 완성한 과정을 말씀드리겠습니다.

---

## Slide 2: CalMe 프로젝트 소개 (1분 30초)

혹시 CalMe를 처음 듣는 분들을 위해 간단히 설명하겠습니다.

**문제점**은 이겁니다. 
대학생들은 학교 공지, 공모전, 팀플 등 여러 곳에서 오는 공지를 매번 다 확인해야 하는데, 
그 과정에서 중요한 마감일을 놓치는 경우가 많습니다.

그래서 이러한 해결책을 생각했습니다
1. 공지를 텍스트나 PDF로 업로드하면
2. AI가 자동으로 분석해서 일정을 추출하고
3. 사용자가 수정할 수 있으며
4. 캘린더에 자동으로 등록됩니다.

**핵심 기능은 3가지**입니다.
첫째, 자동 추출 - AI가 마감일, 제출물 등을 자동으로 찾아냅니다.
둘째, 수정 가능 - AI가 실수할 수도 있으니 사용자가 직접 수정할 수 있습니다.
셋째, 자동 등록 - 수정된 일정은 캘린더에 자동으로 등록됩니다.

## Slide 3: 개발 진행 현황 (30초)

3주 동안의 개발 진행 현황에 대해 말씀드리겠습니다.

**1주차**에는 기획과 설계를 했습니다. 사용자 흐름, 기술 아키텍처, UI 설계 등을 정했습니다.

**2주차**에는 기반을 구축했습니다. 
로그인/회원가입 기능, 텍스트와 PDF 입력 기능을 만들고, 
AI 분석 결과를 표시하는 화면까지 만들었습니다.
다만 이때까지는 아직 Mock 데이터를 활용했었습니다.

**오늘 보고하는 3주차**는 그 Mock을 실제 Claude API로 교체하고,
분석 결과를 수정하고 저장하는 기능을 완성했습니다.

---

## Slide 4: 3주차 목표 및 핵심 변화 (30초)

**3주차 목표**는 "AI 분석부터 일정 저장까지 완전한 흐름을 완성하는 것"입니다.

**2주차 vs 3주차의 핵심 차이**는 이겁니다.

2주차에서는 이미 정해진 Mock 데이터를 반환했습니다.
즉, 실제 공지 내용이 무엇이든 상관없이 고정된 결과를 보여줬습니다.

하지만 **3주차부터는 실제 클로드 API가 공지를 분석**합니다.
"이 공지에는 정말 어떤 정보가 있을까?"를 AI가 판단해서 결과로 줍니다.
그리고 그 결과를 사용자가 수정하고 저장할 수 있습니다.


---

## Slide 5: 기술 아키텍처 - Claude API 통합 (1분)

기술적으로 어떻게 구현했는지 설명하겠습니다.

**전체 흐름**을 보면, 
입력 → 검증 → **클로드 분석** → 수정 → 저장 → 확인 
이렇게 이어집니다.

좀 더 자세히 보면,

**Frontend (React)**는 공지를 입력받고, 분석 결과를 표시하고, 사용자가 수정하도록 합니다.

**Backend (Express)**는 공지 텍스트를 검증하고, 클로드 API를 호출하고, 
응답을 JSON으로 검증한 후 데이터베이스에 저장합니다.

**클로드 모델**
프롬프트와 JSON 스키마로 어떤 형식의 답을 줄지 미리 정합니다.

**Database**는 events 테이블에 저장되는데, 
각 공지(notice)와 사용자(user) 정보와 연결됩니다.

## Slide 6: Claude API 연결 (기술) (1분)

Claude API를 어떻게 활용했는지 더 자세히 설명하겠습니다.

**첫째, 프롬프트 엔지니어링입니다.**
AI에게 "이 공지에서 일정명, 마감일, 제출물을 추출해서 JSON 형식으로 줘"라고 명확하게 지시합니다.
이 프롬프트는 여러 번 시도해서 좋은 버전을 찾았습니다.

**둘째, JSON 스키마입니다.**
AI의 응답 형식을 고정해놓으면, 파싱 오류가 줄어듭니다.
"항상 이 형태로만 답해"라고 미리 정하는 거죠.

**셋째, 오류 처리입니다.**
API가 타임아웃될 수 있고, JSON이 잘못될 수도 있고, 정보가 부족할 수도 있습니다.
이런 경우들을 각각 처리합니다.

**API 호출 흐름**을 보면,
공지 텍스트를 보내고 → Claude API (claude-opus-4-8)를 호출하고 → JSON 응답을 받고 → 검증하고 → 정규화해서 반환합니다.

## Slide 7: 분석 결과 수정 UI (30초)

이제 사용자가 보는 화면입니다.

AI가 분석한 결과로 이런 정보들이 표시됩니다.
일정명, 시작일, 마감일, 시간, 장소, 제출물, 메모, 카테고리 등이요.

사용자는 각 필드를 직접 수정할 수 있습니다.
예를 들어 AI가 날짜를 잘못 읽었다면 수정하고,
필요없는 일정은 삭제하고,
새로운 일정을 추가할 수도 있습니다.

그리고 "이 일정을 등록할 거야/말 거야"를 선택할 수 있습니다.

---

## Slide 8: 일정 저장 기능 (30초)

사용자가 수정을 마치면, 일정을 저장합니다.

**저장 프로세스**는 이렇습니다.
1. 사용자가 수정한 일정을 확인하고
2. 필수 정보(일정명, 날짜)가 있는지 검증하고
3. 여러 일정을 한 번에 저장하고
4. 데이터베이스의 events 테이블에 저장되고
5. 대시보드가 자동으로 업데이트됩니다.

**데이터베이스 관점**에서는,
각 일정이 events 테이블에 저장되는데,
어느 공지(notice)에서 왔는지, 누가(user) 저장했는지 추적할 수 있습니다.

---

## Slide 9: 중복 일정 감지 (30초)

마지막 안전장치가 중복 감지입니다.

**중복의 기준**은 명확합니다.
같은 사용자가 같은 일정명으로 같은 날짜에 일정을 등록하려고 하면,
"어? 이미 같은 일정이 있는데?"라고 경고합니다.

**감지 로직**은,
저장하기 전에 데이터베이스에서 비슷한 일정을 찾고,
있으면 경고 팝업을 띄우고,
사용자가 "강 등록할까요?"라고 선택할 수 있습니다.

이렇게 하면 실수로 중복 등록되는 걸 방지할 수 있죠.

## Slide 10: 시연 (1분)

이제 실제로 동작하는 모습을 보여드리겠습니다.

**시연 순서**는,
1. 로그인해서 대시보드에 접속하고
2. 공지를 텍스트나 PDF로 입력하고
3. "분석하기" 버튼을 누르면 **실제 Claude AI가 분석**하고
4. 분석 결과가 화면에 표시되고
5. 사용자가 수정하고
6. 저장하면 대시보드가 업데이트되는 겁니다.

**중요한 포인트**는 이게 Mock이 아니라 **실제 Claude API**라는 겁니다.
2주차와 달리, 공지 내용에 따라 다른 결과가 나옵니다.

## Slide 11: 어려웠던 점 & 해결 (1분)

개발하면서 만난 어려움들을 말하겠습니다.

**첫째, Claude 프롬프트 최적화입니다.**
처음에는 프롬프트가 좋지 않아서 분석 결과가 정확하지 않았습니다.
여러 번 시도해서 좋은 프롬프트를 찾았어요.
이렇게 하니 정확도가 많이 올랐습니다.

**둘째, JSON 검증입니다.**
API 응답이 항상 올바른 형식은 아니었습니다.
그래서 응답을 받으면 꼼꼼히 검증하는 로직을 추가했습니다.

**셋째, 날짜 형식 통일입니다.**
공지마다 날짜 형식이 다릅니다. "2024-03-15", "3월 15일", "15일" 등등.
AI는 이런 다양한 형식을 이해하지만, 
우리 데이터베이스에는 하나의 형식으로 저장해야 합니다.
그래서 날짜를 정규화하는 함수를 만들었습니다.

**넷째, 중복 감지 기준입니다.**
"중복이 뭔가?"를 명확히 정의하는 데 시간이 걸렸습니다.
결국 "같은 사용자 + 같은 일정명 + 같은 날짜"로 정했는데,
이 과정에서 팀원들과 많은 논의를 했습니다.

**배운 점**은, API를 쓸 때는 완벽한 응답을 기대하지 말고
**견고한 검증 로직**을 만드는 게 중요하다는 겁니다.

---

## Slide 12: 4주차 계획 (1분)

이제 남은 작업을 말씀하겠습니다.

4주차에는 캘린더와 대시보드 개선을 할 예정입니다.
전체적인 테스트를 한 후 완성된 서비스를 최종 배포까지 하는ㄱ게 목표입니다



**4주차에는 4가지를 할 예정입니다.**

첫째, **캘린더 구현**입니다.
월간 캘린더를 보여주고, 등록된 일정을 표시하고, 일정을 클릭하면 상세정보를 봅니다.

둘째, **대시보드 개선**입니다.
마감이 임박한 일정을 "D-1", "D-3" 이런 식으로 표시하고,
지난 일정은 어떻게 처리할지도 정합니다.

셋째, **배포**입니다.
Frontend를 배포하고, Backend를 배포하고, 운영용 데이터베이스를 연결합니다.

넷째, **QA입니다.**
전체 흐름을 테스트해서 버그를 찾고 수정합니다.

**4주차 목표**는 "완성된 서비스를 배포하는 것"입니다.
