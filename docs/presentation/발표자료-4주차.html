01
문제 정의

분명 같은 방향인데, 나만 모른다

대학생은 이동이 필요한 순간 주변에 방향이 겹치는 동행자가 있어도 이를 알 방법이 없어서, 택시 동승으로 아낄 수 있는 돈과 시간을 그냥 놓치고 있습니다.

정문 · 20:30 · 대구역 방향

이 시간, 이 방향으로 가는 학생이 나 말고도 셋이나 더 있었다. 각자 따로 잡느라 나눠 낼 수 있었던 돈도, 같이 갔다면 아꼈을 시간도 모두 놓쳤다.

시간 이점
택시는 가장 빠른 길로 데려다줍니다
금전 이점
인원수만큼 택시비를 나눠 아낍니다
02
솔루션

핵심 기능 2가지

A

매칭 알고리즘

같은 거점 조합 + 희망 시간 ±10분 이내인 사용자를 자동으로 그룹핑해 후보로 보여줍니다.

B

동행 신청 · 수락 플로우

후보 확인 → 신청 → 상대 수락 → 그룹 확정까지 이어지는 절차입니다. 후보를 보여주는 것만으로는 그룹이 만들어지지 않기 때문에, 잠재 수요를 실제 실행으로 전환시킵니다.

03
그 외 기능들

핵심 절차를 받쳐주는 기능들

01

그룹 채팅

만남 장소·시간을 실시간에 가깝게 조율

02

비용 1/N 계산

인원 확정에 따라 예상 택시비를 자동 갱신

03

성별 선호 필터

동성끼리만 매칭을 원하면 선택 가능

04

그룹장 전용 탑승 확인

대표 1인이 확인하면 전원에게 반영

05

평점 · 노쇼 페널티

미평가 시 1시간 후 자동 평가 처리

06

비밀번호 · 게스트 로그인

학교 인증 없이도 바로 체험 가능

04
리스크 대응

만들면서 미리 생각한 것들

안전

모르는 사람과 동승 — 특히 심야·이성 매칭이 불안하다

→

동성끼리만 매칭 선호 필터, 상대방 활동 상태 표시로 신뢰 신호 제공

법적 모호성

택시 합승은 여객자동차운수사업법상 회색지대다

→

앱은 매칭·정보 제공까지만 담당, 실제 탑승 여부는 사용자 자율 판단

정원 분쟁

자리가 부족하면 누굴 먼저 태울지 다툼이 생긴다

→

도착 소요시간이 짧은 사람부터 우선순위로 정렬해 자동 판단

콜드스타트

초기엔 사용자가 적어 매칭 밀도가 낮을 수 있다

→

거점을 정문·북문 등 소수로 좁혀 같은 곳에 등록이 몰리게 설계

05
어떻게 동작하는지

FE - BE - DB

화면(React)이 요청을 보내면 서버(Express)가 매칭·정원·인가 같은 규칙을 판단하고, 그 결과를 Supabase(Postgres)에 저장합니다. 로그인·프로필만 예외적으로 화면이 Supabase에 직접 연결됩니다.

React Vite Express Supabase (Postgres + Auth) Vitest
React (화면) → Express (규칙) → Supabase (저장)
06
문제해결 방식

코드는 AI가, 이해는 제가 채웠습니다

구현 자체는 AI Agent가 담당했지만, 왜 이렇게 동작하는지 모르는 개념이 나올 때마다 멈추고 직접 채워나갔습니다. 결과물을 그대로 받는 게 아니라, 개념의 공백을 스스로 메우면서 흐름을 이해하려 했습니다.

React 상태 · 이펙트 CORS · 배포 브랜치 외래키 제약 RLS 권한 정책 REST API 설계 상태 설계의 함정 TDD 사이클
