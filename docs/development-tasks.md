# 카페 스탬프 MVP 개발 작업 계획

이 문서는 본격적인 개발 전에 각 단계가 무엇을 하는 일인지, 어떤 기술을 쓰는지, 실제로 어떻게 진행할지를 쉽게 확인하기 위한 작업 계획입니다.

손님용 모바일 웹과 사장님용 넓은 화면 웹은 서로 다른 화면이지만 같은 데이터를 사용합니다. 그래서 각 작업은 가능하면 “손님 화면”, “사장님 화면”, “공통 데이터”가 어떻게 이어지는지 함께 확인합니다.

## 전체 개발 흐름

```text
1. 앱 입구 만들기
2. 공통 장부 만들기
3. 로그인과 역할 나누기
4. 손님이 자기 회원번호, QR, 스탬프 보기
5. 사장님이 매장 스캐너 또는 수동 입력으로 손님 찾기
6. 사장님이 조회 결과를 확인하고 스탬프 1개 적립하기
7. 손님 화면에서 바뀐 결과 확인하기
8. 쿠폰과 알림 화면 붙이기
9. 화면을 손님용/사장님용에 맞게 다듬기
10. 배포와 시연 준비하기
```

스탬프 적립의 기본 입력 방식은 손님 QR을 매장 QR·바코드 스캐너로 읽는 것입니다. 스캐너가 없거나 잘 동작하지 않으면 같은 입력칸에 회원번호를 수동으로 입력합니다. 브라우저 카메라 QR 인식은 만들지 않습니다.

쿠폰 사용 기능은 필수 MVP에는 넣지 않습니다. 다만 나중에 시간이 남으면 쿠폰 바코드 번호 입력으로 쿠폰을 사용 처리할 수 있도록, DB에는 바코드 번호와 사용 상태를 미리 담을 수 있게 준비합니다. 고객 QR과 쿠폰 바코드는 서로 다른 목적입니다.

## 1. 앱 입구 만들기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 서비스 안에서 “어느 주소로 가면 어떤 화면이 나오는지” 정하는 단계입니다. 아직 실제 데이터가 없어도 `/login`, `/customer`, `/owner` 같은 주소로 들어갔을 때 알맞은 화면이 나오게 만듭니다. 쉽게 말하면 앱 안에 길 안내판을 세우는 일입니다. |
| 사용하는 기술 | React, Vite, React Router |
| 핵심 결과 | 기본 주소로 들어갔을 때 각각의 화면이 열립니다. |

### 어떻게 할지 자세하게

먼저 앱에서 사용할 기본 주소를 정합니다.

```text
/login
/customer
/customer/coupons
/customer/notifications
/owner
```

각 주소의 역할은 다음과 같습니다.

| 주소 | 역할 |
| --- | --- |
| `/login` | 손님과 사장님이 로그인하는 화면 |
| `/customer` | 손님이 회원번호, QR, 카페별 스탬프를 확인하는 홈 화면 |
| `/customer/coupons` | 손님이 발행된 쿠폰을 확인하는 화면 |
| `/customer/notifications` | 손님이 적립과 쿠폰 발행 알림을 확인하는 화면 |
| `/owner` | 사장님이 스캐너 입력 또는 수동 회원번호 입력으로 고객을 조회하고 스탬프를 적립하는 화면 |

이 단계에서는 아직 Supabase 데이터 연결이나 로그인 권한까지 완성하지 않아도 됩니다. 우선 주소와 화면이 연결되는지만 확인합니다.

처음에는 화면 내용이 단순해도 괜찮습니다.

```text
로그인 화면입니다
손님 홈입니다
쿠폰 화면입니다
알림 화면입니다
사장님 화면입니다
```

이렇게 뼈대를 먼저 만든 뒤, 다음 단계에서 로그인과 데이터 연결을 붙입니다.

### 완료 확인

- [ ] `/login`에 들어가면 로그인 화면이 나온다
- [ ] `/customer`에 들어가면 손님 홈이 나온다
- [ ] `/customer/coupons`에 들어가면 쿠폰 화면이 나온다
- [ ] `/customer/notifications`에 들어가면 알림 화면이 나온다
- [ ] `/owner`에 들어가면 사장님 화면이 나온다
- [ ] 각 주소에서 새로고침해도 화면이 유지된다

## 2. 공통 장부 만들기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 손님 화면과 사장님 화면이 함께 사용할 데이터 저장소를 만드는 단계입니다. 손님은 자기 스탬프와 쿠폰을 보고, 사장님은 회원번호로 손님을 찾아 적립하지만, 둘 다 같은 장부를 바라봐야 합니다. 쉽게 말하면 종이 스탬프 쿠폰북과 매장 장부를 Supabase 안에 만드는 일입니다. |
| 사용하는 기술 | Supabase, PostgreSQL, SQL migration, Supabase Auth와 연결할 `profiles` 구조 |
| 핵심 결과 | 손님, 카페, 스탬프, 쿠폰, 알림, 역할 정보를 저장할 수 있는 기본 DB 구조가 생깁니다. |

### 어떻게 할지 자세하게

이 단계에서는 화면보다 데이터 구조가 중요합니다. 손님과 사장님이 서로 다른 화면을 보더라도, 같은 데이터를 기준으로 움직이게 만들어야 합니다.

만들 장부는 크게 여섯 가지입니다.

| 장부 | 역할 |
| --- | --- |
| `profiles` | 로그인 계정이 손님인지 사장님인지 저장하는 장부 |
| `customers` | 손님 이름과 회원번호를 저장하는 장부 |
| `cafes` | 카페 이름, 목표 스탬프 수, 보상 이름을 저장하는 장부 |
| `stamp_cards` | 손님이 카페별로 스탬프를 몇 개 모았는지 저장하는 장부 |
| `coupons` | 목표 달성 시 발행된 쿠폰을 저장하는 장부 |
| `notifications` | 스탬프 적립과 쿠폰 발행 알림을 저장하는 장부 |

### 손님 장부

손님 장부에는 손님 이름과 회원번호가 들어갑니다.

```text
손님 이름
회원번호
```

회원번호는 사장님이 고객을 찾을 때 쓰기 때문에 중복되면 안 됩니다.

### 카페 장부

카페 장부에는 카페 이름, 목표 스탬프 수, 보상 이름이 들어갑니다.

```text
카페 이름
목표 스탬프 수
보상 이름
```

예를 들면 카페마다 이렇게 다를 수 있습니다.

```text
멜로우 브루: 10개 모으면 아메리카노 1잔
포레스트 커피: 6개 모으면 라떼 1잔
데이라이트 로스터스: 8개 모으면 디저트 할인
```

### 스탬프 장부

스탬프 장부에는 “어떤 손님이 어떤 카페에서 몇 개를 모았는지”가 들어갑니다.

```text
김손님 + 멜로우 브루 = 9개
김손님 + 포레스트 커피 = 3개
```

여기서는 같은 손님과 같은 카페 조합이 두 번 생기면 안 됩니다.

### 쿠폰 장부

쿠폰 장부에는 목표 달성 시 발행된 쿠폰을 저장합니다.

기본으로 필요한 정보는 다음과 같습니다.

```text
어떤 손님에게 발행됐는지
어떤 카페에서 발행됐는지
쿠폰 이름
발행 시간
```

그리고 나중에 쿠폰 사용 기능을 붙일 수 있게 아래 정보도 미리 넣어둡니다.

```text
바코드 번호
쿠폰 상태
사용 시간
```

이번 필수 MVP에서는 쿠폰 사용 기능을 만들지 않습니다. 하지만 DB에는 미리 자리를 만들어둡니다.

쿠폰 예시는 이렇게 볼 수 있습니다.

```text
쿠폰 이름: 아메리카노 1잔
바코드 번호: CP-000001
상태: issued
사용 시간: 비어 있음
```

나중에 시간이 남아서 쿠폰 사용 기능을 붙이면 이렇게 바뀔 수 있습니다.

```text
쿠폰 이름: 아메리카노 1잔
바코드 번호: CP-000001
상태: used
사용 시간: 2026-07-10 15:30
```

### 알림 장부

알림 장부에는 손님에게 보여줄 메시지를 저장합니다.

```text
스탬프 1개가 적립되었습니다
쿠폰이 발행되었습니다
```

일반 적립이면 알림 1개가 생기고, 쿠폰 발행이면 알림 2개가 생깁니다.

### 역할 장부

역할 장부에는 로그인 계정이 손님인지 사장님인지 저장합니다.

```text
손님 계정 -> 특정 손님과 연결
사장님 계정 -> 특정 카페와 연결
```

이 구조가 있어야 로그인 후에 이렇게 판단할 수 있습니다.

```text
이 사람은 손님이니까 손님 화면으로 보낸다
이 사람은 사장님이니까 사장님 화면으로 보낸다
```

### 완료 확인

- [ ] 손님 회원번호가 저장된다
- [ ] 회원번호는 중복될 수 없다
- [ ] 카페마다 목표 스탬프 수와 보상이 저장된다
- [ ] 손님별·카페별 스탬프 수가 저장된다
- [ ] 같은 손님과 같은 카페의 스탬프 카드는 하나만 존재한다
- [ ] 쿠폰에는 바코드 번호와 상태가 들어갈 수 있다
- [ ] 쿠폰 바코드 번호는 중복될 수 없다
- [ ] 처음 발행된 쿠폰은 `issued` 상태가 된다
- [ ] 알림을 저장할 수 있다
- [ ] 로그인 계정을 손님 또는 사장님 역할과 연결할 수 있다

## 3. 로그인과 역할 나누기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 손님과 사장님이 같은 로그인 화면을 쓰더라도, 로그인한 뒤에는 각자 맞는 화면으로 가게 만드는 단계입니다. 쉽게 말하면 입구에서 명찰을 확인하고, 손님은 손님 자리로, 사장님은 사장님 자리로 안내하는 일입니다. |
| 사용하는 기술 | Supabase Auth, React Context, React Router, 보호 라우트 |
| 핵심 결과 | 손님 계정은 손님 화면으로, 사장님 계정은 사장님 화면으로 이동하고 새로고침 후에도 로그인 상태가 유지됩니다. |

### 어떻게 할지 자세하게

로그인은 Supabase Auth의 이메일·비밀번호 로그인을 사용합니다. 이번 MVP에서는 회원가입, 비밀번호 찾기, 소셜 로그인은 만들지 않습니다.

로그인 후에는 Supabase Auth 사용자 ID를 기준으로 `profiles` 장부를 확인합니다.

```text
Auth 사용자 ID 확인
-> profiles에서 role 확인
-> customer면 /customer로 이동
-> owner면 /owner로 이동
```

손님 계정은 특정 손님과 연결되어야 합니다.

```text
손님 로그인 계정
-> profiles.role = customer
-> profiles.customer_id = 해당 손님
```

사장님 계정은 특정 카페와 연결되어야 합니다.

```text
사장님 로그인 계정
-> profiles.role = owner
-> profiles.cafe_id = 담당 카페
```

화면 주소도 보호해야 합니다. 로그인하지 않은 사용자가 `/customer`나 `/owner`에 들어오면 `/login`으로 보내야 합니다.

역할이 맞지 않는 경우도 막아야 합니다.

```text
손님이 /owner에 접근
-> /customer로 이동

사장님이 /customer에 접근
-> /owner로 이동
```

이 단계에서 중요한 것은 화면 이동만이 아닙니다. 실제 데이터 권한은 나중에 Supabase RLS와 RPC에서도 다시 검증해야 합니다. 화면에서 막는 것은 사용자 경험을 위한 1차 안내이고, 진짜 보안은 DB에서 한 번 더 막습니다.

### 완료 확인

- [ ] 손님 계정으로 로그인할 수 있다
- [ ] 사장님 계정으로 로그인할 수 있다
- [ ] 손님 로그인 후 `/customer`로 이동한다
- [ ] 사장님 로그인 후 `/owner`로 이동한다
- [ ] 새로고침 후에도 로그인 상태가 유지된다
- [ ] 로그인하지 않은 사용자는 보호 화면에 접근할 수 없다
- [ ] 손님은 사장님 화면에 접근할 수 없다
- [ ] 사장님은 손님 화면에 접근할 수 없다
- [ ] 로그아웃할 수 있다

## 4. 손님이 자기 회원번호, QR, 스탬프 보기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 손님이 자기 회원번호, 매장 스캐너로 읽을 QR, 여러 카페의 스탬프 현황을 볼 수 있게 만드는 단계입니다. 쉽게 말하면 손님 휴대폰 안에 “내 스탬프 지갑”과 “매장에 보여줄 회원 QR”을 함께 만드는 일입니다. |
| 사용하는 기술 | Supabase JavaScript 클라이언트, RLS, React 상태 관리, 모바일 CSS, QR 표시 라이브러리 |
| 핵심 결과 | 손님이 자기 회원번호, 회원번호 QR, 카페별 현재 스탬프, 목표, 보상을 확인할 수 있습니다. |

### 어떻게 할지 자세하게

손님 화면은 로그인한 손님의 `customer_id`를 기준으로 데이터를 가져옵니다. 손님이 직접 다른 사람 ID를 고르는 방식은 만들지 않습니다.

가져와야 하는 정보는 다음과 같습니다.

```text
손님 이름
회원번호
회원번호 QR
카페별 스탬프 카드
카페 이름
현재 스탬프 수
목표 스탬프 수
보상 이름
```

화면에서는 손님이 사장님에게 보여줄 회원번호가 잘 보여야 합니다.

```text
회원번호: C-1001
```

회원번호 아래에는 매장 스캐너가 읽을 QR을 보여줍니다. QR에 들어가는 문자열은 회원번호 자체가 아니라 서비스 접두어를 붙인 값입니다.

```text
cafe-stamp:C-1001
```

이 접두어를 붙이면 나중에 사장님 화면에서 “우리 서비스의 고객 QR인지” 구분할 수 있습니다. QR 값은 별도 DB 칸에 저장하지 않고, `customers.member_number`를 읽어서 화면에서 만듭니다.

```js
const CUSTOMER_QR_PREFIX = 'cafe-stamp:'

function createCustomerQrValue(memberNumber) {
  return `${CUSTOMER_QR_PREFIX}${memberNumber}`
}
```

QR 표시는 필요할 때 작은 React QR 라이브러리를 추가해 구현합니다. 새 라이브러리는 실제 구현 시점에 선택하고, QR은 이미지 파일로 저장하지 않습니다.

카페별 스탬프는 여러 장의 카드처럼 보여줍니다.

```text
멜로우 브루
9 / 10
보상: 아메리카노 1잔

포레스트 커피
3 / 6
보상: 라떼 1잔
```

이 단계에서는 아직 사장님 적립 기능이 없어도 됩니다. 먼저 손님이 현재 상태를 정확히 볼 수 있어야 합니다.

데이터를 가져오는 중에는 로딩 상태를 보여주고, 실패하면 Supabase 원본 오류를 그대로 보여주지 않고 사용자가 이해할 수 있는 한국어 메시지를 보여줍니다.

```text
스탬프 정보를 불러오지 못했습니다. 잠시 후 다시 시도해 주세요.
```

### 완료 확인

- [ ] 손님 이름이 표시된다
- [ ] 손님 회원번호가 표시된다
- [ ] 손님 회원번호로 만든 `cafe-stamp:<회원번호>` QR이 표시된다
- [ ] QR 값은 DB에 따로 저장하지 않고 회원번호에서 생성된다
- [ ] 여러 카페의 스탬프 카드가 표시된다
- [ ] 카페마다 현재 스탬프와 목표가 표시된다
- [ ] 카페마다 보상 이름이 표시된다
- [ ] 카페별 목표가 서로 다르게 표시될 수 있다
- [ ] 로딩 상태가 표시된다
- [ ] 오류 상태가 한국어로 표시된다
- [ ] 손님은 자기 데이터만 볼 수 있다

## 5. 사장님이 매장 스캐너 또는 수동 입력으로 손님 찾기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 사장님이 매장 QR·바코드 스캐너로 손님 QR을 읽거나, 스캐너가 없을 때 회원번호를 직접 입력해서 손님을 찾는 단계입니다. 쉽게 말하면 카운터에서 스캐너가 회원번호를 자동으로 타이핑해 주고, 안 되면 직접 번호를 입력해 손님 쿠폰북을 찾아보는 일입니다. |
| 사용하는 기술 | Supabase JavaScript 클라이언트, RLS 또는 조회 RPC, React 입력 폼, 넓은 화면 CSS |
| 핵심 결과 | 사장님이 자기 담당 카페를 확인하고, 스캐너 입력 또는 수동 회원번호 입력으로 고객과 해당 카페의 스탬프를 조회할 수 있습니다. |

### 어떻게 할지 자세하게

사장님 화면에는 먼저 담당 카페가 보여야 합니다.

```text
담당 카페: 멜로우 브루
```

그 아래에는 회원번호 입력칸과 조회 버튼을 둡니다. 이 입력칸은 사장님 화면의 가장 중요한 조작 지점이므로 화면 진입 시 자동으로 포커스를 둡니다.

```text
회원번호 또는 고객 QR 입력
[조회]
```

매장 스캐너는 별도 API나 SDK로 연결하지 않습니다. 대부분의 QR·바코드 스캐너는 컴퓨터에서 키보드처럼 동작합니다. 손님 QR을 읽으면 현재 포커스된 입력창에 문자열을 입력하고, 장비 설정에 따라 마지막에 Enter를 보냅니다.

```text
손님 QR 값: cafe-stamp:C-1001
스캐너 동작: 입력창에 cafe-stamp:C-1001 입력
마지막 Enter: 조회 폼 제출
```

스캐너가 없거나 잘 되지 않으면 같은 입력칸에 회원번호만 직접 입력합니다.

```text
수동 입력: C-1001
```

입력값을 그대로 DB 조회에 쓰지 말고, 먼저 작은 파싱 함수로 회원번호를 꺼냅니다.

```js
const CUSTOMER_QR_PREFIX = 'cafe-stamp:'

function parseMemberNumberInput(value) {
  const trimmed = value.trim()

  if (!trimmed) {
    return { ok: false, error: 'empty' }
  }

  if (trimmed.startsWith(CUSTOMER_QR_PREFIX)) {
    const memberNumber = trimmed.slice(CUSTOMER_QR_PREFIX.length).trim()

    if (!memberNumber) {
      return { ok: false, error: 'invalid_qr' }
    }

    return { ok: true, memberNumber }
  }

  if (trimmed.includes(':')) {
    return { ok: false, error: 'invalid_qr' }
  }

  return { ok: true, memberNumber: trimmed }
}
```

사장님이 스캐너로 입력하거나 직접 회원번호를 입력하고 조회하면, 시스템은 다음을 확인합니다.

```text
현재 로그인한 사용자가 사장님인지 확인
사장님의 담당 카페 확인
파싱한 회원번호의 손님 확인
그 손님의 담당 카페 스탬프 카드 확인
```

조회에 성공하면 사장님은 고객 이름과 현재 스탬프를 봅니다.

```text
손님: 김손님
현재 스탬프: 9 / 10
보상: 아메리카노 1잔
```

회원번호가 비어 있거나 존재하지 않으면 명확한 오류를 보여줍니다.

```text
회원번호를 입력해 주세요.
일치하는 고객을 찾을 수 없습니다.
카페 스탬프 고객 QR이 아닙니다.
```

조회 중에는 버튼을 비활성화해서 중복 요청을 줄입니다. 조회가 끝났거나 오류가 나면 다음 손님을 바로 처리할 수 있도록 입력창에 다시 포커스를 둡니다.

중요한 안전 규칙이 있습니다. QR을 스캔하거나 Enter를 눌렀다고 바로 적립하면 안 됩니다. 스캐너와 수동 입력은 고객 조회까지만 자동화하고, 실제 적립은 사장님이 고객 이름과 현재 스탬프를 확인한 뒤 다음 단계의 적립 버튼을 눌러 처리합니다.

### 완료 확인

- [ ] 사장님 담당 카페가 표시된다
- [ ] 회원번호를 입력할 수 있다
- [ ] 화면 진입 시 회원번호 입력창에 포커스가 간다
- [ ] `cafe-stamp:<회원번호>` 입력값에서 회원번호만 추출한다
- [ ] 회원번호만 수동 입력해도 조회된다
- [ ] Enter 키로 조회할 수 있다
- [ ] 빈 회원번호는 조회하지 않고 오류를 보여준다
- [ ] 잘못된 접두어 값은 QR 오류로 안내한다
- [ ] 존재하지 않는 회원번호는 오류를 보여준다
- [ ] 존재하는 회원번호로 고객을 조회할 수 있다
- [ ] 조회 결과에 고객 이름이 표시된다
- [ ] 조회 결과에 담당 카페의 현재 스탬프가 표시된다
- [ ] 조회 중 버튼이 비활성화된다
- [ ] 스캐너 입력이나 Enter 조회만으로는 적립되지 않는다
- [ ] 사장님은 자기 담당 카페 기준으로만 조회할 수 있다

## 6. 사장님이 조회 결과를 확인하고 스탬프 1개 적립하기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 사장님이 조회한 손님 정보를 확인한 뒤 스탬프를 정확히 1개 적립하는 단계입니다. 쉽게 말하면 스캐너로 쿠폰북을 찾은 다음, 사장님이 직접 확인하고 도장을 하나 찍는 일을 DB에서 안전하게 처리하는 것입니다. |
| 사용하는 기술 | PostgreSQL 함수, Supabase RPC, 트랜잭션, React 버튼 상태 |
| 핵심 결과 | 사장님이 버튼을 한 번 누르면 담당 카페의 스탬프가 정확히 1개 증가하거나, 목표 달성 시 쿠폰이 자동 발행됩니다. |

### 어떻게 할지 자세하게

스탬프 적립은 화면에서 직접 계산하지 않습니다. 반드시 Supabase RPC로 처리합니다.

적립 버튼은 고객 조회가 성공한 뒤에만 활성화합니다. QR 스캔, Enter 조회, 수동 입력만으로는 적립 RPC를 호출하지 않습니다.

이유는 적립 과정에서 여러 일이 한 번에 일어나기 때문입니다.

```text
사장님 권한 확인
담당 카페 확인
고객 확인
스탬프 증가
목표 달성 여부 확인
쿠폰 발행
스탬프 0개 초기화
알림 생성
결과 반환
```

이 중 하나라도 실패하면 전체 작업이 취소되어야 합니다. 그래야 쿠폰은 발행됐는데 스탬프가 이상하게 남거나, 알림만 생기는 일이 없습니다.

일반 적립은 이렇게 처리합니다.

```text
적립 전: 3 / 10
적립 후: 4 / 10
알림: 스탬프 1개가 적립되었습니다.
```

목표 직전 상태에서 적립하면 쿠폰을 발행합니다.

```text
적립 전: 9 / 10
적립 후: 0 / 10
쿠폰: 아메리카노 1잔 발행
쿠폰 상태: issued
알림 1: 스탬프 1개가 적립되었습니다.
알림 2: 쿠폰이 발행되었습니다.
```

쿠폰에는 발행 당시의 보상 이름을 복사해 저장합니다. 나중에 카페 보상이 바뀌어도 이미 발행된 쿠폰 이름이 바뀌지 않게 하기 위해서입니다.

쿠폰에는 바코드 번호도 함께 저장합니다.

```text
바코드 번호: CP-000001
상태: issued
```

이번 필수 MVP에서는 이 바코드 번호로 사용 처리까지 하지는 않습니다. 다만 손님 쿠폰 화면에 표시할 수 있게 준비합니다.

여기서 말하는 쿠폰 바코드 번호는 4~5단계의 고객 QR과 다릅니다.

```text
고객 QR: cafe-stamp:C-1001
목적: 고객 조회

쿠폰 바코드 번호: CP-000001
목적: 향후 쿠폰 사용 처리
```

### 완료 확인

- [ ] 적립 버튼을 누르면 스탬프가 정확히 1개 증가한다
- [ ] 고객 조회 전에는 적립 버튼을 누를 수 없다
- [ ] QR 스캔이나 Enter 조회만으로 적립 RPC가 호출되지 않는다
- [ ] 처리 중에는 적립 버튼이 비활성화된다
- [ ] 일반 적립 시 적립 알림이 1개 생성된다
- [ ] 목표 직전 상태에서 적립하면 쿠폰이 1장 발행된다
- [ ] 쿠폰 발행 후 스탬프가 0개가 된다
- [ ] 쿠폰 발행 시 적립 알림과 쿠폰 알림이 생성된다
- [ ] 쿠폰에는 발행 당시 보상 이름이 저장된다
- [ ] 쿠폰에는 고유 바코드 번호가 저장된다
- [ ] 실패하면 중간 상태가 남지 않는다
- [ ] 사장님은 자기 담당 카페에 대해서만 적립할 수 있다

## 7. 손님 화면에서 바뀐 결과 확인하기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 사장님이 적립한 결과가 손님 화면에 그대로 반영되는지 확인하는 단계입니다. 쉽게 말하면 카운터에서 찍은 도장이 손님 휴대폰의 스탬프 지갑에도 똑같이 보이는지 확인하는 일입니다. |
| 사용하는 기술 | Supabase 조회 서비스, React 새로고침/재조회 흐름, RLS |
| 핵심 결과 | 사장님 화면의 처리 결과와 손님 화면의 최신 데이터가 일치합니다. |

### 어떻게 할지 자세하게

이번 MVP에서는 실시간 구독을 만들지 않습니다. 손님 화면은 처음 열 때 또는 새로고침할 때 최신 데이터를 다시 조회합니다.

기본 시연 흐름은 다음과 같습니다.

```text
손님 화면에서 현재 스탬프 확인
-> 사장님 화면에서 스캐너 입력 또는 회원번호 수동 입력
-> 사장님이 고객 조회 결과 확인
-> 사장님이 스탬프 1개 적립
-> 손님 화면 새로고침
-> 변경된 스탬프 확인
```

쿠폰 발행 시나리오는 다음과 같습니다.

```text
손님 화면에서 9 / 10 확인
-> 사장님이 스탬프 1개 적립
-> 쿠폰 발행
-> 손님 화면 새로고침
-> 스탬프 0 / 10 확인
-> 새 쿠폰 확인
-> 새 알림 2개 확인
```

중요한 점은 담당 카페만 바뀌어야 한다는 것입니다.

```text
멜로우 브루 적립
-> 멜로우 브루 스탬프만 변경
-> 포레스트 커피 스탬프는 그대로
```

이 단계는 기능을 많이 새로 만드는 단계라기보다, 손님 화면과 사장님 화면이 같은 데이터를 기준으로 잘 연결됐는지 확인하는 단계입니다.

### 완료 확인

- [ ] 사장님이 일반 적립을 하면 손님 새로고침 후 스탬프가 증가한다
- [ ] 사장님이 쿠폰 발행 적립을 하면 손님 새로고침 후 스탬프가 0개가 된다
- [ ] 쿠폰 발행 후 손님 쿠폰 목록에 새 쿠폰이 나타난다
- [ ] 쿠폰 발행 후 손님 알림 목록에 적립 알림과 쿠폰 알림이 나타난다
- [ ] 적립한 카페 외의 다른 카페 스탬프는 바뀌지 않는다
- [ ] 사장님 화면의 결과와 손님 화면의 결과가 일치한다

## 8. 쿠폰과 알림 화면 붙이기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 손님이 발행된 쿠폰과 알림을 따로 확인할 수 있게 만드는 단계입니다. 쉽게 말하면 스탬프 지갑 안에 “쿠폰함”과 “알림함”을 만드는 일입니다. |
| 사용하는 기술 | Supabase JavaScript 클라이언트, RLS, React 목록 화면, 모바일 CSS |
| 핵심 결과 | 손님이 발행된 쿠폰 목록과 적립·쿠폰 발행 알림을 확인할 수 있습니다. |

### 어떻게 할지 자세하게

쿠폰 화면에서는 손님에게 발행된 쿠폰 목록을 보여줍니다.

보여줄 정보는 다음과 같습니다.

```text
카페 이름
쿠폰 이름
바코드 번호
발행일
```

이번 필수 MVP에서는 사용 처리 기능을 만들지 않으므로, 사용 버튼이나 만료일은 넣지 않습니다.

고객 QR과 쿠폰 바코드는 화면에서 목적을 섞지 않습니다. 고객 QR은 고객 조회용이고, 쿠폰 바코드는 나중에 쿠폰 사용 처리 기능을 붙일 때 사용할 준비 값입니다.

쿠폰 상태는 기본적으로 `issued`인 쿠폰을 사용 가능한 쿠폰으로 봅니다.

```text
상태가 issued인 쿠폰
-> 손님 쿠폰 화면에 표시

상태가 used인 쿠폰
-> 나중에 쿠폰 사용 기능을 만들면 숨기거나 사용 완료로 표시
```

알림 화면에서는 최신 알림을 보여줍니다.

```text
스탬프 1개가 적립되었습니다
쿠폰이 발행되었습니다
```

알림은 최신순으로 보여주는 것이 좋습니다. 이번 MVP에서는 읽음 처리나 외부 푸시 알림은 만들지 않습니다.

### 완료 확인

- [ ] 손님 쿠폰 목록이 표시된다
- [ ] 쿠폰에 카페 이름이 표시된다
- [ ] 쿠폰에 발행 당시 보상 이름이 표시된다
- [ ] 쿠폰에 바코드 번호가 표시된다
- [ ] 쿠폰에 발행일이 표시된다
- [ ] 사용 버튼, 만료일, 사용 완료 처리 등 제외 기능이 들어가지 않는다
- [ ] 손님 알림 목록이 표시된다
- [ ] 적립 알림이 표시된다
- [ ] 쿠폰 발행 알림이 표시된다
- [ ] 알림은 최신순으로 표시된다

## 9. 화면을 손님용/사장님용에 맞게 다듬기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 손님은 휴대폰에서 편하게 보고, 사장님은 매장 컴퓨터나 태블릿의 넓은 화면에서 빠르게 처리할 수 있게 화면을 다듬는 단계입니다. 쉽게 말하면 같은 서비스라도 손님에게는 지갑처럼, 사장님에게는 카운터 업무 화면처럼 보이게 만드는 일입니다. |
| 사용하는 기술 | CSS, 반응형 레이아웃, 접근성 기본 규칙, 기존 디자인 토큰 |
| 핵심 결과 | 손님 화면은 320~480px 모바일에서, 사장님 화면은 1024px 이상 넓은 화면에서 핵심 흐름을 편하게 사용할 수 있습니다. |

### 어떻게 할지 자세하게

손님 화면은 모바일 기준으로 다듬습니다.

확인할 화면 폭은 다음과 같습니다.

```text
320px
393px
480px
```

손님 화면에서는 카드가 잘리지 않고, 버튼을 누르기 쉬워야 합니다.

```text
회원번호가 잘 보인다
스탬프 카드가 가로로 넘치지 않는다
쿠폰과 알림 목록을 읽기 쉽다
주요 버튼 터치 영역이 충분하다
```

사장님 화면은 넓은 화면 기준으로 다듬습니다.

확인할 화면 폭은 다음과 같습니다.

```text
1024px
1280px
1440px
```

사장님 화면에서는 입력과 결과 확인이 한눈에 들어와야 합니다.

```text
담당 카페가 보인다
스캐너 또는 수동 입력 영역이 명확하다
입력창 포커스가 잘 보인다
고객 조회 결과가 바로 보인다
현재 스탬프와 보상이 잘 보인다
적립 버튼이 찾기 쉽다
처리 결과 메시지가 눈에 잘 들어온다
```

오류와 로딩 상태도 함께 다듬습니다.

```text
로그인 중
데이터 불러오는 중
조회 중
적립 처리 중
오류 발생
빈 목록
```

시각 효과보다 중요한 것은 시연 흐름이 끊기지 않는 것입니다. 시간이 부족하면 장식보다 로그인, 조회, 적립, 쿠폰, 알림, 새로고침 반영을 우선합니다.

### 완료 확인

- [ ] 손님 화면은 320px에서 가로 스크롤이 없다
- [ ] 손님 화면은 393px에서 핵심 흐름을 사용할 수 있다
- [ ] 손님 화면은 480px에서 자연스럽게 보인다
- [ ] 사장님 화면은 1024px에서 핵심 정보가 한눈에 보인다
- [ ] 사장님 화면은 1280px에서 입력과 결과 영역이 안정적이다
- [ ] 사장님 화면은 1440px에서 지나치게 흩어져 보이지 않는다
- [ ] 주요 버튼은 누르기 쉽다
- [ ] 입력창에는 라벨과 오류 메시지가 연결된다
- [ ] 키보드 포커스가 보인다
- [ ] 로딩, 오류, 빈 상태가 어색하지 않다

## 10. 배포와 시연 준비하기

| 구분 | 내용 |
| --- | --- |
| 해야 할 일 쉽게 설명 | 만든 MVP를 실제 인터넷 주소에서 열고, 같은 시연을 여러 번 반복할 수 있게 준비하는 단계입니다. 쉽게 말하면 가게 문을 실제로 열고, 데모 전에 장부를 항상 같은 상태로 되돌릴 수 있게 하는 일입니다. |
| 사용하는 기술 | Vercel, Supabase 프로젝트 설정, 환경변수, 프로덕션 빌드, 시연 데이터 초기화 SQL |
| 핵심 결과 | 배포 주소에서 손님과 사장님이 로그인하고, 일반 적립과 쿠폰 발행 시나리오를 반복 시연할 수 있습니다. |

### 어떻게 할지 자세하게

배포는 Vercel을 우선 사용합니다. 프런트엔드에는 공개 가능한 Supabase URL과 anon key만 넣습니다.

```text
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY
```

절대 넣으면 안 되는 값도 있습니다.

```text
Supabase service_role key
실제 비밀번호
개인 로컬 설정
```

배포 후에는 Supabase Auth 설정에서 배포 URL이 허용되어 있는지 확인합니다.

시연 데이터도 준비해야 합니다.

```text
손님 파일럿 계정
사장님 파일럿 계정
확인하기 쉬운 회원번호
손님 QR 값: cafe-stamp:<회원번호>
목표가 다른 카페 여러 개
사장님 담당 카페
일반 적립 상태
쿠폰 발행 직전 상태
```

데모는 최소 두 가지를 반복할 수 있어야 합니다.

일반 적립 시나리오:

```text
손님 화면에서 현재 스탬프 확인
-> 사장님이 스캐너 입력 또는 수동 입력으로 회원번호 조회
-> 사장님이 조회 결과 확인
-> 스탬프 1개 적립
-> 손님 화면 새로고침
-> 스탬프 증가 확인
```

쿠폰 발행 시나리오:

```text
손님 화면에서 목표 직전 스탬프 확인
-> 사장님이 스캐너 입력 또는 수동 입력으로 회원번호 조회
-> 사장님이 조회 결과 확인
-> 스탬프 1개 적립
-> 쿠폰 자동 발행
-> 손님 화면 새로고침
-> 스탬프 0개, 새 쿠폰, 새 알림 확인
```

스캐너가 있는 경우에는 손님 휴대폰의 QR을 실제로 읽어 봅니다. 스캐너가 없거나 준비되지 않았을 때는 `cafe-stamp:C-1001` 같은 값을 입력창에 붙여넣고 Enter를 눌러 같은 흐름을 검증합니다. 수동 fallback도 반드시 확인합니다.

시연 전후로 데이터를 되돌리는 방법도 필요합니다. 그래야 같은 데모를 여러 번 안정적으로 보여줄 수 있습니다.

### 완료 확인

- [ ] 프로덕션 빌드가 성공한다
- [ ] Vercel 배포가 성공한다
- [ ] 배포 주소에서 로그인할 수 있다
- [ ] Supabase Auth 배포 URL 설정이 되어 있다
- [ ] 손님 파일럿 계정이 준비되어 있다
- [ ] 사장님 파일럿 계정이 준비되어 있다
- [ ] 시연용 회원번호가 준비되어 있다
- [ ] 손님 QR 값 `cafe-stamp:<회원번호>`로 조회할 수 있다
- [ ] 스캐너가 없을 때 붙여넣기+Enter로 같은 조회 흐름을 검증할 수 있다
- [ ] 회원번호 수동 입력 fallback을 검증할 수 있다
- [ ] 일반 적립 시나리오를 배포 주소에서 성공한다
- [ ] 쿠폰 발행 시나리오를 배포 주소에서 성공한다
- [ ] 시연 데이터를 목표 직전 상태로 복구할 수 있다
- [ ] 손님 휴대폰과 사장님 컴퓨터 웹 화면으로 리허설할 수 있다
