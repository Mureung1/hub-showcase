# SPEC-AUTH-001. 회원가입·로그인 UI (Email Auth UI)

- 상태: **Ready (Step 1~3 확정, 구현 대기)**
- 기준 문서: `CLAUDE.md` 2·6·7장, `docs/architecture.md`, `docs/dev-setup.md`, `docs/DESIGN.md`
- 작성 방식:
  - 0장 "고정 사항"은 확정된 정책에서 온 것이며, 이 Spec에서 임의로 바꾸지 않는다.
  - 1장 "결정 사항"은 사용자가 직접 결정했다. Agent는 질문과 선택지를 제시하고 결정을 받아 적었다.

## 0. 고정 사항 (정책 확정)

### 0.1 한 줄 목표

사용자가 이메일·비밀번호로 회원가입하고 이메일 인증을 완료한 뒤 로그인·로그아웃할 수 있다. 인증 UI는 실제 Supabase Auth와 연결되며, 서비스 데이터(Chat·Question 등)는 이 Spec에서 여전히 Mock으로 동작한다.

### 0.2 기존 문서에서 오는 고정 규칙

- 인증 방식: 이메일 + 비밀번호. **이메일 인증 완료가 서비스 이용의 필수 조건**이다 (CLAUDE.md 2장).
- React는 Supabase Auth 기능(회원가입·로그인·로그아웃·세션 확인)에 한해 Supabase Client를 직접 사용할 수 있다. 서비스 데이터 조회·저장에는 사용하지 않는다.
- 프론트 환경변수는 Supabase URL과 Publishable Key만 둘 수 있다. `VITE_` 값은 공개로 간주한다. 실제 `.env`는 커밋하지 않는다.
- 사용자 식별자는 `auth.users.id`. 비회원 데이터의 회원 이전, 게스트 병합은 MVP 제외.
- 닉네임·표시명 입력은 범위에서 제외한다 (`profiles` 테이블 미도입).
- 비밀번호 재설정은 SPEC-AUTH-004로 보류 (Should).
- 세션 복원·토큰 갱신·Protected Route 고도화는 SPEC-AUTH-002, Express JWT 검증은 SPEC-AUTH-003. 이 Spec은 **인증 화면 UI와 가입·로그인·로그아웃 동작까지만** 다룬다.
- 로그인 후 Auth 표시 위치는 좌측 패널 하단 (기존 결정).
- 컴포넌트는 Astryx 우선, 색·간격은 토큰 (DESIGN.md).

### 0.3 제외 범위

- 새로고침 세션 복원·자동 로그인 유지·라우트 가드 고도화 (→ SPEC-AUTH-002)
- Express Auth Middleware·API 연동 (→ SPEC-AUTH-003)
- 비밀번호 재설정 (→ SPEC-AUTH-004)
- 소셜 로그인, 프로필 편집, 계정 삭제
- 서비스 데이터의 사용자별 저장 — 로그인해도 Chat·Question은 기존 Mock 흐름 그대로 (→ SPEC-DB-001에서 연결)

## 2. 화면 구조와 라우팅

- **React Router를 도입한다** (결정 1-1). 이 Spec이 패키지 추가(`react-router`)의 승인 근거다.
- 라우트 구성:

| 경로 | 화면 |
|---|---|
| `/login` | 로그인 페이지 |
| `/signup` | 회원가입 페이지 |
| `/verify-email` | "인증 메일을 보냈습니다" 안내 페이지 (재발송 버튼 포함) |
| `/` | 기존 3단 워크스페이스 |

- 비로그인 상태로 `/`에 진입하면 `/login`으로 보낸다 (결정 1-3). 이 Spec에서는 **초기 진입 시 1회 세션 확인** 수준의 단순 처리만 하고, 새로고침 복원·가드 고도화는 SPEC-AUTH-002에서 완성한다.
- 로그인 성공 시 `/`로 이동한다. 로그아웃 시 `/login`으로 이동한다.
- 인증 페이지 레이아웃: 화면 중앙 카드형 (Astryx 기본 요소 조합). 페이지 하단에 전환 링크 — `/login`에는 "계정이 없으신가요? 회원가입", `/signup`에는 "이미 계정이 있으신가요? 로그인" (결정 1-2).

---

## 3. 회원가입 흐름

- 입력 필드: **이메일, 비밀번호, 비밀번호 확인** (결정 2-1).
- 클라이언트 검증 (제출 전, 필드별 inline 에러 표시):
  - 이메일 형식
  - 비밀번호 최소 8자 (결정 2-2)
  - 비밀번호 확인 일치
- Supabase 프로젝트 설정도 최소 8자로 일치시킨다 (대시보드 Auth 설정 — `docs/dev-setup.md`에 기록).
- 가입 호출: `supabase.auth.signUp` + `emailRedirectTo`를 앱의 `/login`으로 지정 (결정 2-3).
- 가입 성공 → `/verify-email` 안내 페이지로 이동:
  - 문구: 가입한 이메일 주소를 포함해 "인증 메일을 보냈습니다" 안내
  - [인증 메일 재발송] 버튼 (`supabase.auth.resend`) — 성공 시 재발송 완료 안내
  - "로그인으로 돌아가기" 링크
- 사용자가 메일의 인증 링크를 클릭하면 `/login`에 도착해 직접 로그인한다. **자동 로그인은 하지 않는다** (결정 2-3, 세션 처리는 002 범위).
- 제출 중에는 버튼을 비활성화하고 로딩 표시(중복 제출 방지).

---

## 4. 로그인·로그아웃

### 4.1 로그인

- 입력 필드: 이메일, 비밀번호. 호출: `supabase.auth.signInWithPassword`.
- 성공 시 `/` 워크스페이스로 이동.
- 제출 중 버튼 비활성 + 로딩 표시.

### 4.2 로그인 실패 표시 (결정 3-1)

- **미인증 계정** (Supabase의 email not confirmed 계열 에러): 전용 안내 "이메일 인증을 완료해주세요" + [인증 메일 재발송] 버튼을 폼 아래에 표시한다.
- **그 외 모든 실패**: Supabase 에러 메시지 원문을 폼 아래에 그대로 표시한다 (MVP 디버깅 편의). 콘솔에도 남긴다.
- 에러 표시에 비밀값·토큰 등 비밀 정보를 포함하지 않는다.
- 후속 개선 후보: 실사용자 대상 배포 전에 주요 에러의 한국어 매핑 도입 (이 Spec 개정 또는 후속 Spec).

### 4.3 Auth 영역과 로그아웃 (결정 3-2·3-3)

- 좌측 패널 하단에 **로그인 이메일 + [로그아웃] 버튼을 항상 표시**한다.
- [로그아웃] 클릭 → 확인 팝업 "로그아웃할까요?" (Astryx Dialog) → 확인 시 `supabase.auth.signOut` 후 `/login` 이동, 취소 시 닫기.

## 5. 패키지·환경변수·Supabase 설정

- 추가 패키지 (이 Spec이 승인 근거): `react-router`, `@supabase/supabase-js` — 둘 다 `apps/web`에 설치. 루트 lock 단일 유지.
- Supabase Client는 별도 모듈(예: `apps/web/src/lib/supabase.ts`)에서 1회 생성한다. 컴포넌트에서 SDK를 직접 호출하지 않고 auth feature의 Service/Hook을 거친다 (CLAUDE.md 7장).
- 환경변수 (`apps/web/.env.local`, 커밋 금지 — `.env.example`만 갱신):

```text
VITE_SUPABASE_URL
VITE_SUPABASE_PUBLISHABLE_KEY
```

- Supabase 대시보드 수동 설정 체크리스트 (`docs/dev-setup.md`에 추가):
  - Email 인증 활성화, **Confirm email 필수(ON)**
  - 비밀번호 최소 길이 8
  - Site URL·Redirect URL에 로컬 개발 주소(`http://localhost:5173` 등)와 `/login` 경로 등록
- 인증 기능 코드는 `apps/web/src/features/auth/`에 둔다 (페이지·Hook·Service·타입).

## 6. 상태·오류 처리 규칙

- 각 폼은 `idle / loading / error` 상태를 구분한다. 성공은 라우트 이동으로 표현한다.
- 재발송 버튼은 연타 방지를 위해 발송 직후 잠시 비활성화한다 (구현 재량, 예: 30초).
- Supabase Auth 응답의 사용자 정보는 auth feature 내부 타입으로 다루고, 서비스 도메인 계약(`@decision-log/shared`)에 넣지 않는다 (userId 계약 포함 여부는 SPEC-AUTH-002~003에서 재검토 — SPEC-SCHEMA-001 3장).

## 7. Acceptance Criteria

- [ ] AC1. `/login`, `/signup`, `/verify-email`, `/` 라우트가 동작하고, 비로그인 상태로 `/` 진입 시 `/login`이 표시된다.
- [ ] AC2. 회원가입 폼이 클라이언트 검증(이메일 형식·8자·확인 일치)을 inline 에러로 표시하고, 검증 통과 전 제출되지 않는다.
- [ ] AC3. 실제 Supabase 프로젝트에서 가입 → 인증 메일 수신 → `/verify-email` 안내·재발송 동작 → 메일 링크 클릭 → `/login` 도착까지 이어진다.
- [ ] AC4. 미인증 상태 로그인 시 "이메일 인증을 완료해주세요" + 재발송 버튼이 표시되고, 인증 완료 후 로그인하면 `/` 워크스페이스가 열린다.
- [ ] AC5. 잘못된 자격증명 로그인 시 Supabase 에러 원문이 폼 아래에 표시된다.
- [ ] AC6. 좌측 패널 하단에 로그인 이메일과 [로그아웃]이 표시되고, 로그아웃 확인 팝업 → 확인 시 `/login`으로 이동한다.
- [ ] AC7. 프론트 코드·환경변수에 Supabase URL·Publishable Key 외 비밀값이 없고, 실제 `.env`가 커밋되지 않으며, `.env.example`과 `docs/dev-setup.md`(대시보드 체크리스트)가 갱신된다.
- [ ] AC8. `npm run typecheck / lint / build` 통과. 로그인 후 기존 Mock 워크스페이스(happy-path)가 회귀 없이 동작한다.

Supabase 프로젝트가 준비되지 않아 실측할 수 없는 AC(3·4·5)는 구현 후 "미확인 + 사유"로 보고하고, 프로젝트 연결 후 확인한다.
