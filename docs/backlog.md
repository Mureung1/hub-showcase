# Development Task List (Draft)

Priority: `P0` foundational/blocking (prerequisite for other work) · `P1` MVP core · `P2` MVP enhancement · `P3` lower priority / stretch

## P0 — Foundation

- [x] **Backend server skeleton** — write `src/server.ts`/`app.ts`, wire up cors/morgan/express.json middleware, shared `errorHandler`, health-check route (`backend/` currently has only dependencies + tsconfig, no entry point)

- [ ] **DB schema design (Prisma)** — define models for items / disposal rules / regional rules, `prisma init` + write `schema.prisma`; DB is hosted on Supabase (free tier Postgres) — Prisma stays as the ORM, Supabase just supplies the `DATABASE_URL`

- [x] **공공데이터포털 (Korea Public Data Portal) integration** — API key obtained for `기후에너지환경부_분리배출 정보조회 서비스` (15156866) and `행정안전부_생활쓰레기배출정보 조회서비스` (15155080); client for the former built in `backend/src/services/govDisposalApiClient.ts` (+ mock fallback). See `docs/TASK.md` Day 3 for details.

- [x] **Object Normalizer → catalog-wide matching (with whitespace normalization)** — replaced the static ~12-entry English-label dictionary (`objectNormalizer.ts`, deleted) with direct matching: Gemini Vision now guesses the object's name in Korean (styled like official 품목명), and `itemService.findBestMatchingItem` matches that guess against the full 731-item synced catalog. Two real gaps found via manual testing and fixed: (1) a banana peel photo failed even though "바나나껍질" existed in the catalog and was findable via search — dictionary just didn't cover it; (2) hairspray failed because the catalog has "헤어 스프레이" (with a space) while a natural guess is "헤어스프레이" (no space) — plain SQL `contains`/`ILIKE` doesn't match across spacing differences. Fixed by loading all 731 items (small enough to hold in memory) and comparing with whitespace stripped from both sides, exact match preferred over substring. Verified against both real cases plus their alternate spacings. **Tried and rejected**: constraining Gemini's response via `responseSchema.enum` with all 731 item names, to guarantee the output is always a literal catalog name — Gemini API itself rejects this with `400 INVALID_ARGUMENT: "too much branching for serving"`. This is a hard API-side limit on enum size, not something to retry as-is; would need item categories to narrow the candidate set to ~20-30 before an enum constraint becomes viable (not implemented — no category field exists on `Item` yet).

- [x] **Gov catalog bulk sync** — `backend/scripts/syncGovCatalog.ts` upserts the full ~730-item `getItem` catalog (confirmed live: omitting `itemNm` returns the entire catalog, paginated) into `Item`/`DisposalRule` in one pass, replacing per-item lazy caching. Run manually via `npm run sync:catalog -w backend` — kept separate from `prisma db seed` since the team shares one Supabase instance; re-run periodically (e.g. monthly) to catch catalog updates.

## P1 — MVP core features

- [x] **AI photo recognition flow** — photo upload (multer) → Vision AI call → Object Normalizer → Public Data API lookup → LLM explanation generation → return result (end-to-end). Vision AI + LLM explanation both run on **Gemini** (`gemini-2.5-flash`, falls back to `gemini-2.5-flash-lite` on daily quota limit) — switched from OpenAI since it has no standing free tier. Verified with real API calls, not just mocks.
- [x] **Result screen (ResultPage)** — render disposal steps / part-by-part separation / common mistakes / rationale, matching `prototype/result.html` structure. `ConfirmPage` (previously an unbuilt stub) also implemented: receives the photo, calls recognize, shows the single top-prediction result, falls back to Search on no-match. Deliberately does **not** replicate `prototype/confirm.html`'s multi-candidate confidence-percentage UI, since the backend only returns one prediction with no confidence score — fabricating fake percentages was rejected in favor of an honest single-result UI.
- [x] **Item search (SearchPage)** — search-by-name API + UI, reusing the same result component as photo recognition
- [x] **Regional disposal rules — backend + region selection UI** — `행정안전부_생활쓰레기배출정보 조회서비스` (15155080, `household_waste_info/info`) integrated: `RegionDistrict` (one-time synced coverage list, `npm run sync:districts`) + `RegionRule` (cached per-address resolution, merging 생활쓰레기/음식물쓰레기/재활용품/대형폐기물 independently since their zone boundaries can differ within one 구/군). `GET /api/regions/{provinces,districts,zones,rules}` + a working 시/도→구/군→(세부 구역) cascading picker wired into HomePage's location pill (`features/region/`), replacing the never-implemented prototype region sheet. Coverage is real but uneven (222/226 시/군/구 exist in the dataset at all, but depth varies hugely — 부산 32 rows vs 강원 2252 nationwide); uncovered 구/군 shows real alternatives rather than fabricating data. Zone-label parsing went through 3 rounds of real-data surprises: 동 range notation ("산격1동~4동"), 읍/면 for 군-level areas (동-only assumption filtered these out entirely), and non-geographic method-based zoning (강릉시: "문전수거 지역"/"거점수거 지역", not a dong at all) — settled on a permissive length-based filter (reject only the one confirmed garbage case, an instruction paragraph leaked into the region-name field) rather than continuing to whitelist administrative-unit suffixes.
- [x] **RulesPage itself** — renders the resolved `RegionRule` (steps/schedule per category) for the region saved via the HomePage sheet (was already done as of the regional-rules work, this line was just stale)
- [x] **Today's disposal schedule (HomePage)** — shows which items can be disposed of today based on the user's set region (was already done as of the regional-rules work, this line was just stale)
- [x] **Multilingual support (Korean/English first)** — Expanded from a single-page toggle to app-wide: `frontend/src/i18n/{ko,en}.ts` is a hand-typed dictionary (not react-i18next — 2 languages, ~50 fixed strings, `en.ts`'s `satisfies Record<keyof typeof ko, string>` catches missing translations at compile time) driving a `LanguageContext` (persisted to `localStorage`, so the toggle survives navigation — the old `ResultPage`-local `useState` reset on every route change). `PageHeader` now renders the 🌐 toggle itself, so every page that uses it (Home/Search/Result/Confirm/Rules) gets it for free; `RegionSelectSheet` translated too. `DisposalRule`'s ko/en explanation-text pattern from before is unchanged. **Known gap, not addressed this round**: `RegionRule.categories[category].method` (government free text like "종량제 봉투에 담아 배출") has no English translation yet — still Korean-only in English mode on RulesPage/HomePage. Also out of scope: `BulkyPage`/`PointsPage` (still empty stubs — nothing to translate).
- [x] **Region picker English names (시/도, 구/군, 동/읍/면)** — evaluated and rejected a rule-based romanization library (`@romanize/korean`) after testing it against real place names: it got "강릉시" wrong ("Gangreung" instead of the correct "Gangneung", missing the ㄹ→ㄴ nasalization rule after a nasal batchim) — a real, visible defect on a well-known place, not a hypothetical edge case. Reused Gemini instead (same infra as `Item.nameEn`/`DisposalRule` bilingual explanations), which correctly produces "Gangneung-si" by drawing on real documented usage rather than deriving romanization from first principles. Two-tier caching to match how the data is actually sourced: `RegionDistrict.ctpvNmEn`/`sggNmEn` batch-synced once (`npm run sync:region-names-en -w backend`, 16 시/도 + 226 구/군, resumable — a mid-run Gemini 503 left it half-done and re-running correctly skipped already-translated rows) since that table is already fully synced locally; `RegionZoneName` (new model) lazily caches 동/읍/면 names the first time each is seen, keyed by the raw Korean string alone since romanization doesn't depend on which district it's in. Needed a follow-up prompt fix after the first sync: 시/도-level 특별시/광역시/특별자치시 suffixes were being romanized literally ("Seoul-teukbyeolsi") instead of using the universally recognized dropped-suffix form ("Seoul") — re-ran after tightening the prompt with explicit examples for both cases (drop suffix for metro cities, keep "-do"/"-si"/"-gun"/"-gu" for regular divisions). Verified live against real government zone data (Daegu 북구's 33 동, including parenthetical variants like "관문동(매천제외)" → "Gwanmun-dong (excluding Maecheon)").
- [x] **English search support (`nameEn`)** — Done as originally scoped: `Item.nameEn` column + one-time batch script `backend/scripts/syncItemNamesEn.ts` (`npm run sync:item-names-en -w backend`, chunks of 50, `DisposalRule.method` passed as disambiguation context per the original plan, ~4s delay between batches for Gemini free-tier RPM). Ran against the full 731-item catalog — verified live (e.g. "battery" → 건전지/AA 건전지/CR 건전지/..., "Plastic" → 비닐/랩/PCR 플라스틱/...). `searchItems` now matches `name OR nameEn`. **Deliberately not built this round**: the zero-result LLM-fallback (guessing Korean terms when a plain English substring match returns nothing) — precomputed `nameEn` covers the direct-match case, which is the majority of the value; the fallback is a separate, unverified-cost addition to pick up later.

## P2 — MVP enhancements

- [x] **Bulky waste reporting guide (BulkyPage)** — item → region → fee lookup → link to official reporting site flow. Initially planned as hand-seeded data (no known nationwide API), but found a real one during scoping: 환경부_전국대형폐기물수거수수료정보표준데이터 (`tn_pubr_public_lar_was_fee_api`, data.go.kr 15114146) covers 143 지자체 — synced all ~22,831 rows into `BulkyWasteFee` via `syncBulkyWasteFees.ts` (full wipe-and-reinsert, no natural per-row key to upsert against; annual update cycle makes this safe). Item options are populated per-region from real data, not a fixed list (naming isn't standardized across districts — e.g. Daegu Buk-gu literally uses "쇼파" not "소파"). **Correction after initial ship**: first assumed `larWasSpcfct`(규격) and `mngInstNm`(관리기관명) were always empty based on testing only 2 districts — a broader nationwide check (prompted by the user pushing back on "we're only showing category+price, is that really all the data has?") found the initial sample was misleading: **52% of rows (11,882/22,831) do have a real `larWasSpcfct`, and 49% (11,127) have a real `mngInstNm`.** Added both as columns, re-ran the sync, and now show `spec` under the category/fee line when present (still show the full list, unlabeled, for the districts that genuinely don't report it), and fall back to displaying `mngInstNm` as a contact when no official report-site URL is seeded. Official report-site URLs themselves still have no API coverage, so `BulkyWasteReportSite` stays a small hand-verified seed (2 real districts checked by hand: Haeundae-gu, Daegu Buk-gu). **Scope note**: the issue also mentioned connecting a "pre-report confirmation step" via `ConfirmPage`, but `ConfirmPage` already serves the photo-recognition confirm flow (see Day 5) and the actual `prototype/bulky.html` flow doesn't have a separate confirm screen anyway (fee card → report button directly) — skipped as a stale requirement, same as the earlier Day 9 ConfirmPage note.

- [ ] **Multilingual expansion (Chinese/Japanese/Vietnamese)** — add sequentially after Korean/English (P1); not mentioned in current README feature text but still listed under 기술 스택/AI, needs confirmation before scheduling
