# 나만의 워크플로우 & Agent 협업 과정

4주간의 계획(`plan-agent`), PR/커밋 이력, 회고, 그리고 `.claude/agents`·`.claude/skills`에 정착된 Agent/Skill을 모아 반복적으로 쓴 작업 순서를 정리한다.

---

## 1. 나만의 워크플로우

### 패턴 A — 기능 개발 워크플로우

지역별 규정, 주변 수거 장소, 대형폐기물 신고, 다국어 지원 등 대부분의 기능이 이 순서로 만들어졌다.

- **입력**: GitHub Issue로 등록된 기능 요구사항 (또는 README/TASK.md에 명시된 미구현 항목)
- **작업 순서**
  1. GitHub Issue로 기능 명세 등록
  2. 기능 단위 브랜치 생성 (`기능/설명` 또는 개인 브랜치)
  3. `plan-agent`에게 태스크 분해 요청 — [제약 조건 1] BE 선해결, [제약 조건 2] CLAUDE.md 원칙(LLM은 공식 데이터를 가공·번역만), [제약 조건 3] Zod 검증·Object Normalizer, [제약 조건 4] 다국어 토글 구조, [제약 조건 5] DoD(에러 핸들링 + 수동 e2e 테스트) — 5가지를 만족하는 Day 단위 태스크로 쪼갬
  4. 백엔드 API·서비스 레이어 우선 구현 (routes → controllers → services 계층 분리)
  5. 프론트엔드 실데이터 연동 (`@tanstack/react-query`, mock 제거)
  6. 수동 e2e 테스트 (화면 → 요청 → DB/공공데이터 API → 응답 → 화면 갱신 한 사이클 직접 확인)
  7. `점검` 에이전트로 CLAUDE.md 원칙·계층 분리·컨벤션·디자인 시스템·TASK.md 정합성 감사
  8. PR 생성 → merge → TASK.md/backlog.md/README 갱신 (`docs:` 커밋)
- **확인 기준**
  - `점검` 에이전트 보고에 ❌ 위반 항목 없음 (⚠️ 경미는 허용, 사유 남김)
  - 수동 e2e 테스트에서 골든 패스 + 최소 1개 엣지케이스(빈 값/데이터 없음 등) 확인
  - `npm run lint`, `tsc -b`/`tsc --noEmit` 통과
- **결과물**: merge된 PR, 갱신된 TASK.md 체크박스, 실제로 동작하는 화면
- **문제가 생겼을 때 다시 확인할 단계**
  1. `CLAUDE.md` 핵심 원칙 — AI가 규정을 가공·번역이 아니라 새로 만들어내고 있지 않은지
  2. `docs/CONTRIBUTING.md` 계층 분리 — 컨트롤러에 비즈니스 로직/에러 응답이 직접 섞여 있지 않은지
  3. `.claude/skills/confisort-design-system/SKILL.md` — 임의의 색상/그림자/radius를 쓰지 않았는지
  4. 다국어 토글 — 재요청 없이 즉시 전환되는 구조를 깨지 않았는지
  5. `docs/TASK.md` "리스크 & 메모" — 과거에 이미 한 번 겪은 실수 패턴(StrictMode 이중 호출, 공백 미정규화 매칭 실패 등)과 같은 유형인지부터 대조

### 패턴 B — 버그 수정 워크플로우

StrictMode 무한 로딩 버그, Object Normalizer 매칭 실패(헤어스프레이/바나나껍질), 지역 선택 시 공공 API 중복 호출 등 실제로 겪은 버그들이 이 순서로 해결됐다.

- **입력**: 실제 사용(수동 클릭 테스트) 중 발견된 재현 가능한 오작동
- **작업 순서**
  1. 실제 데이터/화면으로 재현 조건 확정 (어떤 입력에서 어떤 증상이 나오는지)
  2. 원인 분석 — 코드를 직접 읽고 왜 이렇게 짜였는지 이해 (AI가 짠 코드도 예외 아님)
  3. 최소 범위로 수정 (원인이 된 로직만, 관련 없는 리팩터링 배제)
  4. 같은 조건 + 인접 케이스로 재검증
  5. `fix:` 커밋 + `docs/TASK.md` "리스크 & 메모"에 원인과 해결 방식 기록
- **확인 기준**: 최초 재현 조건에서 증상이 사라지고, 원인과 무관한 다른 화면/기능에 회귀가 없는지 수동 확인
- **결과물**: `fix:` 커밋, TASK.md에 남긴 원인/해결 기록 (다음에 비슷한 문제가 났을 때 바로 찾아볼 수 있도록)
- **문제가 생겼을 때 다시 확인할 단계**
  1. 같은 원인 패턴이 다른 곳에도 있는지 grep으로 전수 확인 (예: 공백 미정규화 매칭은 여러 곳에서 재발 가능)
  2. `useEffect` 안에서 `useMutation`을 직접 호출하는 패턴이 남아있지 않은지 (StrictMode 이중 호출 이력)
  3. TASK.md 체크박스와 실제 코드 상태가 다시 어긋나지 않았는지

## 2. Agent 협업 과정 시각화

| 단계 | 사용 도구 | 사람이 결정한 것 | AI(Agent)가 수행한 것 |
|---|---|---|---|
| **기획** | `plan-agent` | 요구사항, 기능 우선순위, CLAUDE.md 핵심 원칙 확정 | Day 단위 vertical slice 태스크 분해, 5개 아키텍처 제약 조건 검증, DoD 체크리스트 생성 |
| **설계** | `confisort-design-system` Skill | 컬러 토큰·타이포그래피·spacing 등 디자인 기준 확정 (`skill.md` 작성) | 새 화면에 토큰 적용, 기존 프로토타입(`prototype/*.html`)과의 시각적 일치 여부 반영 |
| **구현** | Claude Code (범용) | 백엔드 계층 분리(`routes`/`controllers`/`services`) 등 아키텍처 규칙 결정 | 규칙에 따른 실제 코드 작성 (라우트, 컨트롤러, 서비스, 컴포넌트) |
| **검증** | `점검` 에이전트 + 수동 테스트 | 실제 브라우저 클릭 테스트, 최종 merge 여부 판단 | CLAUDE.md 원칙·계층 분리·컨벤션·디자인 토큰·TASK.md 정합성을 파일:라인 근거로 감사·보고 (수정은 하지 않음) |
| **배포** | 없음 (Agent 미사용) | GitHub main 브랜치로 merge, Vercel 배포 확인 — 전 과정 직접 수행 | 없음 |

**참고**
- `점검` 에이전트는 매 PR마다 항상 돌린 것은 아니고, 컨벤션 이탈이 의심되거나 TASK.md 정합성을 다시 맞추고 싶을 때 필요 시 사용했다.
- 배포는 Vercel의 GitHub 연동 자동 배포를 그대로 쓴 것으로, Agent가 관여한 지점이 없다.
