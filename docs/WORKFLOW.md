# 하루 체크아웃 개발 Workflow

## 1. 이 문서를 작성한 이유

이 Workflow를 처음부터 완성해 놓고 4주 동안 그대로 사용한 것은 아니다. 프로젝트를 진행하면서 계획 없이 바로 코드를 수정하거나, Agent가 작업한 결과를 충분히 이해하지 못한 채 다음 단계로 넘어가는 일이 있었다. 마지막 주에 실제로 반복했던 작업 순서와 검증 방법을 다시 확인해 문서로 정리했다.

이 프로젝트에서 사람과 Agent의 역할은 다음과 같았다.

- **사람이 결정한 것**: 어떤 문제를 해결할지, 기능 범위, 개인정보 처리 방식, 데모에 포함할 기능과 최종 완료 여부
- **Agent에게 맡긴 것**: 기존 코드 조사, 작업 계획과 코드 초안, 테스트 실행, 배포 설정, 브라우저 조작과 로그 확인
- **사람이 다시 확인한 것**: Agent가 제시한 결과를 사용할지, 기능을 수정할지, 배포하고 PR에 포함할지

코드와 문서 초안의 많은 부분을 Agent에게 맡겼기 때문에, “누가 파일을 작성했는가”보다 “무엇을 요청했고 어떤 결과를 근거로 적용했는가”를 중심으로 기록한다.

## 2. 서비스가 동작하는 구조

| 구성 요소 | 하는 일 | 사용한 서비스 |
|---|---|---|
| 프런트엔드 | 사용자가 감정과 사진을 입력하고 기록을 확인하는 화면 | React, Vercel |
| 백엔드 | AI 정리 요청을 받고 Gemini와 통신 | Express, Render |
| 게스트 저장 | 로그인하지 않은 기록과 사진을 현재 브라우저에 저장 | IndexedDB |
| 로그인 저장 | 로그인한 사용자의 기록과 사진을 계정별로 저장 | Supabase DB·Storage |
| AI 정리 | 입력한 내용을 감정, 원인, 내일의 작은 행동으로 정리 | Gemini |

게스트 사용자는 기록을 외부 서버로 자동 전송하지 않고 자신의 브라우저에 저장한다. AI 정리에 동의하면 프런트엔드가 Render의 Express 서버에 요청하고, 서버가 Gemini를 호출한다. 로그인 사용자는 Supabase 계정으로 기록과 사진을 저장한다.

## 3. Workflow의 입력과 결과물

### 작업을 시작할 때 확인한 것

- 수업 미션과 제출 기준
- 사용자·튜터 피드백
- 현재 코드와 Git 커밋
- 이전 계획·진행 문서
- 오류 화면, 테스트 결과, API 응답과 배포 로그

### 작업이 끝났을 때 남긴 것

- 기능 코드와 코드로 작성된 테스트
- Vercel 프런트엔드와 Render 백엔드 배포
- 실제 화면·API·데이터 저장 검증 기록
- Git 커밋과 PR
- showcase와 데모 영상

## 4. 실제로 반복한 작업 순서

| 순서 | 무엇을 했는가 | 사람이 한 일 | Agent가 한 일 | 확인 기준 |
|---|---|---|---|---|
| 1 | 요구사항과 현재 상태 확인 | 수업 자료와 원하는 결과 전달 | 코드, 문서와 Git 기록 조사 | 이미 된 것과 남은 일 구분 |
| 2 | 작업 범위 결정 | 만들 기능과 제외할 기능 결정 | 작업을 작은 단위로 나누고 계획 초안 작성 | 한 번에 확인 가능한 완료 기준 |
| 3 | 설계와 테스트 필요 여부 결정 | 개인정보·저장 방식과 화면 흐름 승인 | 기존 구현과 가능한 방법 비교 | 단순 수정인지 중요한 로직인지 구분 |
| 4 | 구현 | Agent가 제시한 방향을 확인 | 기존 구조를 이용해 최소 코드 작성 | 정한 기능 범위만 동작 |
| 5 | 코드 검사 | 결과와 실패 항목 확인 | 기존 테스트와 프로덕션 빌드 실행 | `npm run verify` 통과 |
| 6 | 실제 배포 화면 검사 | 사용할 계정과 데이터, 최종 완료 여부 결정 | Codex 전용 브라우저로 화면 조작, API·로그 확인 | 핵심 사용자 흐름 동작 |
| 7 | 오류 수정 | 수정 범위 승인 | 첫 오류의 원인을 찾고 한 곳만 수정 | 실패했던 검사를 다시 통과 |
| 8 | 배포와 기록 | Push·PR 포함 여부 결정 | Git 작업, 배포 상태와 증거 정리 지원 | 실제 주소와 검증 기록이 남음 |

문구나 스타일처럼 영향이 작은 수정은 별도 설계 문서나 TDD 없이 수정 후 검증했다. 저장, 인증, AI, 날짜 계산처럼 실패했을 때 영향이 큰 기능은 먼저 흐름과 테스트 사례를 정했다. 모든 작업에 형식적으로 TDD를 적용한 것은 아니다.

## 5. Agent와 Skill 파일은 무엇인가

`.claude/agents`와 `.claude/skills` 안의 파일은 그 자체로 기능을 실행하는 프로그램이 아니다. Claude Code나 작업 Agent에게 “이 역할에서는 무엇을 하고 무엇을 하지 말아야 하는지” 알려 주는 자연어 지침 파일이다.

### 저장소의 Agent

| Agent | 지침 내용 | 실제 연결 근거 |
|---|---|---|
| `task-planner` | 코드를 수정하지 않고 현재 상태, 작업 순서와 완료 기준을 작성 | [PR #1254](https://github.com/connect-AIAgentChallenge-26-1/hub/pull/1254) |
| `feature-verifier` | 구현하지 않고 코드·API·자동 검사 결과를 근거로 통과·실패·미확인을 구분 | [PR #1254](https://github.com/connect-AIAgentChallenge-26-1/hub/pull/1254), `npm run verify` |

### 저장소의 Skill

| Skill | 지침 내용 | 실제 연결 근거 |
|---|---|---|
| `feature-development` | 현재 코드 확인 → 화면·데이터·API 흐름 설계 → 사용자 승인 → 구현 | [PR #1575](https://github.com/connect-AIAgentChallenge-26-1/hub/pull/1575) |
| `write-test` | 테스트 사례 확인 → 실패하는 테스트 확인 → 최소 구현 → 통과 확인 | [PR #1851](https://github.com/connect-AIAgentChallenge-26-1/hub/pull/1851) |

회고·PR·체크아웃 문안을 편하게 작성하려고 만든 개인용 `retro` 파일은 개발 절차와 연결되지 않으므로 프로젝트 Skill과 Git 커밋에서 제외했다.

### Codex 작업 Agent

Codex 작업 Agent는 위 저장소 파일과 별개로 이 채팅에서 실제 작업을 수행한 도구다. 로컬 파일과 Git을 확인하고, 코드를 수정하거나 명령을 실행할 수 있다. Codex 데스크톱 앱의 전용 브라우저를 사용하면 사용자가 열어 둔 Vercel, Render와 Supabase 화면에서 클릭·입력·새로고침 같은 작업도 수행할 수 있다.

## 6. “검증해보셈” 요청을 Agent가 처리한 방법

사용자가 실제로 한 요청은 다음과 같이 짧았다.

> 검증해보셈 그리고나서 showcase 작성 해보셈

사용자가 테스트 파일, 테스트 개수나 실행 명령을 지정한 것은 아니다. Codex가 다음 자료를 읽고 검증 범위를 정했다.

1. `client/package.json`과 `server/package.json`에 등록된 테스트 명령
2. 저장소에 이미 존재하던 테스트 파일
3. 수업 미션에 적힌 핵심 기능, 빈 입력, 서버 오류와 새로고침 유지 기준
4. 이 프로젝트의 핵심 기능인 Gemini, IndexedDB와 Supabase 저장 흐름

따라서 클라이언트 21개와 서버 12개 테스트를 이번 검증에서 새로 만든 것은 아니다. 이전 기능 개발 과정에서 Agent가 기능 코드와 함께 작성해 둔 테스트를 Codex가 발견해 모두 실행했다. 테스트 파일별 내용과 처음 추가된 커밋은 `docs/verification-2026-07-29.md`에 기록했다.

## 7. 코드로 작성된 자동 검사

### `npm run verify`

저장소 루트에서 이 명령을 실행하면 다음 세 작업이 차례로 실행된다.

1. 클라이언트 Vitest 테스트 24개
2. 서버 Node 테스트 13개
3. React 프로덕션 빌드

7월 29일에는 세 명령을 각각 실행했다. `npm run verify`는 같은 검사를 다음에도 빠뜨리지 않고 한 번에 실행하기 위해 7월 30일 Workflow 정리 과정에서 추가했다.

### 테스트가 확인하는 것

- **클라이언트 24개**: 달력 계산, 주간 필터, 게스트·로그인 진입, IndexedDB 저장·복원·삭제, Supabase 계정별 기록·사진 저장, PWA 설정, 감정 리포트 집계와 별도 동의 후 AI 분석 요청
- **서버 13개**: 하루 AI 정리와 리포트 AI 분석의 응답 형식, 잘못된 AI 응답 재시도, AI 장애 처리, 기록 삭제, Supabase 연결 설정과 데모 모드
- **프로덕션 빌드**: React 코드를 Vercel에 올릴 수 있는 배포용 파일로 만드는 과정에서 문법·import·번들 오류가 없는지 확인

테스트 이름은 자연어로 작성돼 있지만 실제 판정은 `expect(...)` 같은 코드가 수행한다. 대부분 실제 Gemini나 Supabase를 호출하지 않고 가짜 응답과 메모리 저장소를 사용한다. 따라서 자동 검사 통과만으로 실제 배포 서비스 전체가 정상이라고 판단하지 않았다.

## 8. Codex 전용 브라우저를 이용한 수동 검증

자동 검사 다음에는 Codex 데스크톱 앱의 전용 브라우저를 사용했다. 이것은 테스트 파일을 실행한 것이 아니라, Codex가 배포된 서비스를 실제 사용자처럼 한 번 직접 조작한 검증이다.

### Codex가 실제로 수행한 작업

1. Vercel에 배포된 하루 체크아웃 첫 화면을 열었다.
2. 게스트 모드로 들어가 빈 입력에서 저장 버튼과 AI 버튼 상태를 확인했다.
3. 감정 문장과 검증용 사진을 입력했다.
4. AI 전송 동의 전후의 버튼 상태를 비교했다.
5. Gemini 정리를 실행해 감정, 원인과 내일의 작은 행동이 표시되는지 확인했다.
6. 게스트 기록을 IndexedDB에 저장하고 새로고침한 뒤에도 기록이 남는지 확인했다.
7. 기존 테스트 계정의 로그인 세션이 복원되는지 확인했다.
8. 로그인 상태에서 검증용 기록과 사진을 저장했다.
9. 캘린더와 상세 화면에서 Supabase에 저장된 기록과 사진이 보이는지 확인했다.
10. 검증용 기록을 삭제하고 목록에서 사라지는지 확인했다.
11. Render의 `/api/health`를 열어 `{"status":"ok","storage":"supabase"}` 응답을 확인했다.
12. Render 로그에서 서버 실행과 Supabase 저장 모드를 확인했다.
13. 브라우저 오류·경고가 남았는지 확인했다.

검증에 사용한 임시 로그인 기록은 확인 후 삭제했다. 환경변수는 등록된 이름만 확인하고 API 키와 실제 값은 문서에 기록하지 않았다.

### 이 방식의 의미와 한계

- 실제 배포 주소와 로그인 세션을 사용하므로 코드 테스트가 놓치는 화면·서버·DB 연결 문제를 찾을 수 있다.
- Codex가 클릭과 입력을 수행하지만, 사람이 브라우저를 사용해 한 번 확인하는 것과 같은 수동 검증이다.
- 매 Push마다 자동으로 반복되지 않으며, 사람이 Codex에게 다시 검증을 요청해야 한다.
- 확인하지 못한 기능은 통과가 아니라 `미확인`으로 기록한다.

실행 결과는 `docs/verification-2026-07-29.md`에 남겼다. 로컬 `feature-verifier`는 코드·API·자동 검사에 집중하고, 로그인과 화면 조작은 브라우저를 사용할 수 있는 Codex 작업 Agent가 담당했다.

## 9. 다음 작업에서 사용할 검증 요청문

```text
현재 코드와 배포된 서비스를 검증해줘. 코드는 먼저 수정하지 마.

1. 기존 테스트가 무엇인지 먼저 설명하고 npm run verify를 실행해.
2. Codex 전용 브라우저로 Vercel 화면의 게스트 저장, AI 정리와 새로고침 후 기록 유지를 확인해.
3. 로그인 상태에서 기록과 사진 저장, 조회와 삭제를 확인해.
4. Render health 응답과 서버 로그를 확인해.
5. 각 항목을 통과·실패·미확인으로 나누고 실제 근거를 적어줘.
6. 문제가 있으면 첫 오류와 원인만 보고하고, 수정은 내 확인 후 진행해.
```

## 10. 문제가 생겼을 때 처리한 순서

1. 테스트, 빌드, 브라우저 요청 또는 서버 로그에서 첫 오류를 찾는다.
2. 화면 → 프런트엔드 → 서버 → 외부 서비스 중 실패 구간을 좁힌다.
3. 관련 코드와 기존 테스트를 확인한다.
4. 원인 한 곳만 수정한다.
5. 실패했던 검사와 `npm run verify`를 다시 실행한다.
6. 로컬에서 통과하면 Codex 전용 브라우저로 배포 환경의 같은 흐름을 확인한다.
7. 확인하지 못한 항목은 통과가 아니라 `미확인`으로 기록한다.

여러 설정을 한꺼번에 바꾸지 않고 첫 오류 하나씩 확인하는 방식으로 Render 배포, CORS, Supabase 환경변수와 사진 업로드 문제를 해결했다.

## 11. 사람과 Agent가 맡은 일

| 사람이 결정한 내용 | Agent에게 맡긴 실행 |
|---|---|
| 상담을 기다리는 동안 감정을 정리하도록 돕는 서비스 목적 | 수업 자료와 기존 코드 정리 |
| 게스트 기록은 브라우저에 저장 | IndexedDB 구현과 테스트 초안 |
| AI 전송은 사용자 동의 후 실행 | 동의 상태와 Express·Gemini 연결 |
| 로그인 사용자는 Supabase에 동기화 | Auth·DB·Storage 연결 |
| 데모에 보여 줄 기능과 제외할 기능 | 기능 구현, 테스트와 배포 화면 확인 |
| 개인정보 원칙과 최종 완료 판단 | 로그·API·브라우저 결과 수집 |
| PR·회고·체크아웃을 본인의 말로 작성 | 실행 결과와 참고 근거 정리 |

Agent에게 파일 작성을 많이 맡겼더라도 제품의 문제, 기능 범위, 개인정보 원칙과 최종 적용 여부는 사람이 결정했다. 반대로 테스트 코드의 세부 내용과 배포 설정처럼 설명하기 어려운 부분은 완전히 이해했다고 과장하지 않고 문서에 한계로 남긴다.

## 12. 자동화된 것과 수동인 것

- Git Hook이나 GitHub Actions CI를 만든 것은 아니다.
- `npm run verify`는 사람이 실행하거나 Agent에게 요청해야 동작한다.
- Codex 브라우저 검증도 사람이 요청해야 시작한다.
- GitHub에 Push하면 Vercel과 Render가 새 버전을 자동으로 배포한다.
- 검증을 건너뛰어도 Push를 막는 장치는 없다.

따라서 “CI나 Hook을 구축했다”가 아니라 “Agent에게 코드 검사와 실제 브라우저 검증을 요청하는 절차를 파일로 정리했다”고 설명한다.

## 16. 2026-07-31 감정 리포트 추가 검증

- 기존 IndexedDB·Supabase 기록을 그대로 사용해 전체 기록 수, 기분 분포, 최근 감정·원인과 작은 행동을 모아보는 리포트 탭을 추가했다.
- 리포트를 만들기 위해 새로운 AI 요청이나 데이터 저장 구조를 추가하지 않았다.
- 리포트 집계 테스트 2개를 추가한 뒤 클라이언트 테스트 23개, 서버 테스트 12개와 프로덕션 빌드를 통과했다.

- 로컬 환경에는 배포용 API 주소가 없어 AI 요청은 실패 안내까지만 확인했고, 실제 배포 Gemini 흐름은 Push 후 다시 확인한다.

## 17. 2026-08-01 리포트 AI 전체 분석

- 기본 리포트는 계속 새로운 AI 요청 없이 브라우저 또는 Supabase의 기존 기록을 집계한다.
- 사용자가 리포트 화면에서 별도로 동의하고 버튼을 누른 경우에만 현재 화면의 제한된 요약 텍스트를 Gemini로 보낸다. 사진과 전체 원문은 보내지 않는다.
- AI 결과는 `전체 흐름`, `반복해서 보이는 장면`, `다음 기록에서 살펴볼 점`으로 제한했다. 상담, 진단, 치료와 입력에 없는 사실 추정을 금지하는 리포트 전용 지시문을 사용한다.
- AI 요청이 실패하면 가짜 분석을 대신 표시하지 않고 다시 시도하라는 안내를 보여준다.
- 클라이언트 테스트 24개, 서버 테스트 13개와 프로덕션 빌드를 통과했다.
