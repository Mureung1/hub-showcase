## 2. 정직성 규칙 준수도

규칙: (a)근거 없이 강점/기본 남발 금지 (b)AI 작성 코드에 aiBar 정직 표기 (c)구현% 보수적.

| 모델 | (a)절제 | (b)aiBar | (c)구현 보수 | 종합 |
|---|---|---|---|---|

| haiku | C (ok 남발) | C (aiBar 오용) | C (impl 45~55) | **C** |

**haiku의 핵심 결함**: aiBar를 "AI가 이 코드 썼다"는 정직 플래그가 아니라 일반 숙련도바로 오용 — Git 협업에 self 80, 미보유(gap) 항목에도 self:0/assist:0 aiBar를 억지로 채워 신호 희석. 반대로 opus는 AI 코드가 아닌 항목(Git·네트워크·글쓰기)엔 aiBar를 **생략**해 플래그 의미를 지킴.

## 3. 근거 깊이

- **opus·sonnet 최상** — 핵심 repo 전부 + "누가 무엇을 했나(귀속) 분리". opus는 비공개·소형 repo(URL-shorter·exex·keyword-alarm)까지 소환, OS/네트워크를 쪼개 평가.
- **haiku 유일하게 뭉뚱그림** — 개별 근거 대신 "16개 repo 운영"을 통째로 근거화, Computer-Networking을 자료구조로 오분류, action이 "~심화 학습" 일반론.

## 4. 결론

- **추천: opus** — 보수 규율 지키면서 "AI 안 쓴 진짜 강점(Git·자기작성 위키)"만 정확히 크레딧. 강점 무차별 삭제 안 함. 갭 분석 목적(뭘 실제로 메우나)에 가장 실용적.
- 차선: **sonnet** (최대 엄격·서열 교정력, 과냉 감수 시).
- 회피: **haiku** (준비도 낙관 부풀림 → "정직한 갭 분석" 취지 훼손).
- opus의 유일한 약점: 네이버를 홀로 🟡로 둔 관대함(분산·대용량 게이트 미충족 감안 시 🔴이 더 정직).

## 5. 메타 발견 — "작은 모델 = 낙관"은 균일하지 않다

- **haiku = 낙관 편향** (fit·impl·self% 전방위 부풀림 + 스키마 억지 채움).
- **fable = 반대로 과냉** (네이버 강점0·기본0). 단 근거 구체성·aiBar 배치는 상위권 유지.
- → 작은 모델의 실패 방향이 제각각. **haiku는 낙관, fable은 과냉.**

## 6. 하네스에 주는 시사점 (다음 단계)

이 baseline이 **하네스가 왜 필요한지**를 실증한다:
- 같은 입력·같은 스키마인데 **모델마다 fit이 26~70으로 벌어짐** = 스키마 강제만으론 부족.
- **haiku의 실패(aiBar 오용, ok 남발, gap에 aiBar 억지)** 는 하네스 **검증기(validator)** 로 잡아야 할 정확한 대상:
  1. `status`가 strong/ok인데 `tags`에 repo/wiki 근거가 없으면 → 반려 (근거 없는 충족 금지).
  2. `aiBar`는 코드 근거(repo tag) 있는 항목에만 허용, gap 항목엔 금지.
  3. `impl`이 `concept`보다 크게 높으면 경고(이 지원자 전제 위반).
- → **하네스 v1의 검증 규칙 = haiku가 틀린 지점들.** 이걸 통과 못 하면 재생성. 그러면 작은 모델도 opus에 가깝게 수렴하는지가 이번 주 검증 목표.
