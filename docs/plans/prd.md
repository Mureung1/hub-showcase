# PtoP 제품 요구사항 문서(PRD)

> 문서 기준일: 2026-07-27
>
> PtoP(Project to Portfolio)의 현재 구현 상태와 다음 개발 기준을 정리한 최신 PRD다. 초기 아이디어와 변경 이력은 [초기 기획서](./plan.md)에서 관리한다.

## 1. 제품 개요

PtoP는 GitHub Repository의 작업 근거와 사용자의 짧은 회고를 결합해, 프로젝트 경험을 포트폴리오에 활용할 수 있는 기술적 도전과 문제 해결 단서를 정리해주는 서비스다.

사용자는 긴 회고록을 처음부터 작성하지 않는다. 2D 작업실에서 분석을 시작하고, Repository 분석이 진행되는 동안 Poppy의 짧은 질문에 답한다. 서비스는 GitHub에서 확인한 사실과 사용자가 직접 말한 경험을 구분한 뒤, 함께 검토할 수 있는 결과로 보여준다.

## 2. 해결하려는 문제

프로젝트를 완성한 뒤에도 다음 내용을 다시 정리하기 어렵다.

- 팀 프로젝트에서 내가 실제로 담당한 작업이 무엇이었는지
- 구현 중 어떤 문제를 해결했는지
- 어떤 대안을 검토하고 현재의 결정을 내렸는지
- GitHub 기록을 포트폴리오 문장으로 어떻게 바꿀지

기존 방식처럼 빈 문서에 회고를 길게 작성하면 시작 부담이 크다. 반대로 Repository만 분석하면 작업 의도와 개인의 판단을 알 수 없다. PtoP는 두 입력을 최소한의 사용자 개입으로 연결한다.

## 3. 제품 목표

### 3.1 핵심 목표

- 사용자가 GitHub Repository 분석을 쉽게 시작하도록 한다.
- 팀 전체의 기록을 사용자의 개인 경험으로 오해하지 않도록 한다.
- 분석 중 짧은 회고를 입력할 수 있게 해 대기 시간을 의미 있는 시간으로 바꾼다.
- Repository 근거와 사용자 경험을 함께 확인할 수 있는 결과를 제공한다.
- 포트폴리오 작성을 시작하는 심리적 부담을 2D 작업실과 Poppy로 낮춘다.

### 3.2 제품 원칙

- **근거 우선**: GitHub API, 파일 구조, commit, PR 등 확인 가능한 자료를 우선한다.
- **개인 기여 분리**: 로그인한 사용자 또는 선택한 GitHub ID를 기준으로 개인 작업을 구분한다.
- **최소 입력**: 사용자가 긴 회고문을 작성하지 않아도 핵심 결과를 얻을 수 있게 한다.
- **불확실성 표시**: 근거가 부족하거나 회고와 후보가 일치하지 않으면 확정하지 않고 상태를 알려준다.
- **사람의 검토 유지**: AI 결과를 완성된 사실이 아니라 검토 가능한 후보와 초안으로 제공한다.
- **게임은 경험 계층**: 2D 작업실은 진입 장벽을 낮추지만 분석 정확성과 접근성을 방해하지 않는다.

## 4. 대상 사용자

- 프로젝트 경험을 포트폴리오로 정리하려는 대학생 개발자
- 팀 프로젝트에서 자신의 기여와 기술적 도전을 복기하려는 개발자
- 프로젝트를 끝낸 뒤 무엇을 어필해야 할지 정리하기 어려운 초기 개발자

## 5. 핵심 사용자 흐름

### 5.1 첫 방문부터 분석 시작까지

1. 사용자는 랜딩페이지에서 PtoP의 목적과 작업실 분위기를 확인한다.
2. 사용자는 GitHub 로그인 버튼을 선택한다.
3. 인증이 완료되면 작업실에 입장한다.
4. 사용자는 방향키 또는 WASD로 캐릭터를 이동한다.
5. 새 Repository 분석 PC에 접근해 `E` 키 또는 대체 버튼으로 분석 화면을 연다.
6. Repository URL과 분석 대상 GitHub ID를 확인한다.
7. 사용자가 분석을 시작하면 분석 화면으로 전환된다.

### 5.2 분석 중 회고 작성

1. 왼쪽에는 Repository 분석 시스템 로그를 보여준다.
2. 오른쪽에는 Poppy와 회고 입력 UI를 보여준다.
3. Poppy는 한 번에 하나의 짧은 질문을 제시한다.
4. 사용자는 선택지 또는 짧은 답변으로 응답한다.
5. 답변은 Repository별 임시 초안으로 저장한다.
6. 분석이 먼저 끝나도 화면을 자동으로 결과 페이지로 전환하지 않는다.
7. 사용자가 `결과 확인하기`를 선택하면 저장된 회고와 분석 결과를 함께 전송한다.

### 5.3 결과 확인과 보완

1. 결과 화면은 프로젝트 요약, 개인 작업, 기술적 도전 후보를 우선 보여준다.
2. 각 후보에는 GitHub 근거와 사용자 회고의 연결 상태를 표시한다.
3. 회고와 후보가 일치하지 않으면 `일부 일치`, `확인 필요`, `근거 없음` 등으로 알린다.
4. 사용자는 AI가 찾지 못한 경험을 직접 추가할 수 있다.
5. 사용자는 결과를 확인한 뒤 작업실로 돌아갈 수 있다.

## 6. 화면 요구사항

| 화면 | 목적 | 필수 요소 | 상태 |
| --- | --- | --- | --- |
| 랜딩페이지 | 서비스 이해와 시작 유도 | 작업실 영상, 서비스 소개, GitHub 로그인, 작업실/분석 이동 | 구현 |
| GitHub 인증 | 사용자 식별과 분석 기준 확보 | Supabase GitHub OAuth, 성공·실패·취소 처리 | 구현 |
| 2D 작업실 | 분석 기록 탐색과 새 분석 진입 | 맵, 캐릭터, PC, Poppy, 키보드 안내, 대체 버튼 | 구현 |
| Repository 입력 화면 | 분석 대상 지정 | URL, GitHub ID, 검증 메시지, 분석 시작 | 구현 |
| 분석 중 화면 | 분석 상태와 회고 입력 병렬 제공 | 시스템 로그, Poppy 질문, 입력창, 선택지, 전송 버튼 | 구현 |
| 분석 결과 | 근거 기반 결과 전달 | 요약, 활동, 기술적 도전, 근거, 회고 정렬 상태 | 구현 |
| 포트폴리오 초안 | 결과를 포트폴리오 구조로 변환 | Background, Problem, Solution, Technical Challenge, Result | 예정 |

## 7. Repository 분석 요구사항

### 7.1 입력

- GitHub Repository URL
- 분석 대상 GitHub ID
- GitHub OAuth 로그인 사용자 정보

GitHub ID는 로그인 사용자의 ID를 기본값으로 채우되, 사용자가 직접 수정할 수 있다. 팀 프로젝트에서는 분석 대상 ID를 명시해야 하며, ID가 없는 활동은 개인 기술적 도전 후보의 근거로 사용하지 않는다.

### 7.2 분석 대상

- Repository 기본 정보와 기술 스택
- 프로젝트 디렉터리와 주요 파일
- commit, PR, Issue 및 변경 파일
- 사용자의 활동과 변경 영역
- 기술적 도전 후보를 뒷받침하는 근거

### 7.3 출력

- 프로젝트 한 줄 요약
- 사용자의 주요 작업 영역
- 기술적 도전 후보
- 후보별 근거와 신뢰 상태
- 분석에 사용된 데이터 범위와 제한 사항

### 7.4 분석 원칙

- commit 수는 활동 참고 지표일 뿐 기여도나 실력의 절대값이 아니다.
- 팀 전체의 구현을 사용자의 경험으로 단정하지 않는다.
- GitHub API 요청 한도 초과, 권한 부족, 데이터 부재를 구분해 안내한다.
- AI 응답이 실패했을 때 임의의 하드코딩 결과를 제공하지 않는다.
- 분석 결과는 확정된 포트폴리오 문장이 아니라 사용자가 검토할 후보로 표시한다.

## 8. 회고 및 분석 연결 요구사항

### 8.1 회고 입력 원칙

- 한 화면에 많은 질문을 동시에 노출하지 않는다.
- 한 번에 하나의 질문만 제시한다.
- 한 문장 또는 짧은 선택지 답변으로도 진행할 수 있다.
- 질문을 건너뛸 수 있다.
- 분석 완료가 입력 중인 내용을 중단하지 않는다.
- 같은 분석 결과에서 저장 버튼을 반복해서 눌러도 중복 요청이 발생하지 않는다.

### 8.2 회고 질문

- 프로젝트를 시작한 배경과 목표는 무엇이었나요?
- 내가 맡은 역할은 무엇이었나요?
- 가장 해결하기 어려웠던 문제는 무엇이었나요?
- 해결을 위해 어떤 선택을 했나요?
- 다시 진행한다면 무엇을 바꾸고 싶나요?

### 8.3 정렬 결과 상태

Repository 분석 후보와 회고는 다음 상태로 비교한다.

| 상태 | 의미 | 사용자 안내 |
| --- | --- | --- |
| `matched` | GitHub 근거와 회고가 같은 도전을 가리킴 | 결과에 함께 반영 |
| `partial` | 일부 키워드 또는 맥락만 연결됨 | 추가 확인 권장 |
| `mismatched` | 회고와 AI 후보가 다른 문제를 설명함 | 후보를 확정하지 않음 |
| `no_evidence` | 회고 내용과 연결되는 GitHub 근거가 없음 | 개인 경험으로 별도 표시 |

회고 분석 결과는 AI가 만든 단정이 아니라, 사용자가 검토할 수 있는 연결 정보로 제공한다.

## 9. 결과 화면 정보 구조

결과 화면은 정보량을 줄이고 다음 우선순위로 보여준다.

1. **프로젝트 요약**: 어떤 프로젝트인지 한눈에 이해한다.
2. **나의 작업**: 분석 대상 GitHub ID와 연결된 작업을 보여준다.
3. **기술적 도전 후보**: 여러 후보를 보여주되 최종 선택은 1개로 제한한다.
4. **근거와 연결 상태**: 파일, commit, PR, 회고가 어떻게 연결되는지 확인한다.
5. **내 경험 추가**: AI가 찾지 못한 경험을 제목과 짧은 메모로 보완한다.
6. **포트폴리오 초안으로 이어가기**: 최종 문장 생성은 사용자의 확인 이후 시작한다.

## 10. 데이터 저장 및 API

### 10.1 저장 데이터

- Repository 분석 결과
- 분석 대상 GitHub ID
- 사용자 회고 초안
- 기술적 도전 후보와 근거
- 회고와 후보의 정렬 결과

회고와 분석 결과는 분석 결과 ID를 기준으로 연결한다. 동일 분석 결과에 다시 저장하면 새 행을 만들지 않고 기존 초안을 갱신한다.

### 10.2 현재 API

```text
POST /api/v1/repository-analyses/:analysisId/reflection
GET  /api/v1/repository-analyses/:analysisId/reflection
```

저장 API는 회고 초안과 선택한 기술적 도전 후보를 함께 받아 정렬 결과를 생성한다. Supabase migration이 적용되지 않은 환경에서는 저장 필드 부재를 감지해 기존 스키마로 재시도할 수 있지만, 운영 환경에서는 migration을 먼저 적용해야 한다.

### 10.3 보안 및 소유권

- API 키와 Supabase service role key는 서버 환경변수로만 관리한다.
- GitHub OAuth redirect URL은 로컬·배포 환경별로 분리한다.
- 현재는 서버 저장 경계까지 구현되어 있으며, 사용자별 분석 결과 소유권 검증과 RLS 강화는 후속 작업이다.
- Repository 분석 데이터와 회고는 필요한 범위만 저장한다.

## 11. 게임형 작업실 요구사항

### 11.1 구현 범위

- 단일 2D 작업실 맵
- 기본 캐릭터와 방향별 스프라이트
- 방향키/WASD 이동
- 장애물 충돌
- 새 분석 PC와 이전 분석 PC
- `E` 키 상호작용
- 키보드 조작을 사용할 수 없는 사용자를 위한 버튼 기반 진입 경로

### 11.2 접근성 및 안전장치

- 핵심 기능은 게임 조작 없이도 접근할 수 있어야 한다.
- 모바일 또는 작은 화면에서는 목록·버튼 기반 대체 흐름을 제공한다.
- 분석 모달 바깥 클릭으로 작업이 사라지지 않도록 명시적인 닫기 동작을 사용한다.
- 분석 중 새로고침이나 네트워크 오류가 발생해도 작성 중인 회고를 가능한 범위에서 보존한다.

## 12. 인증과 배포

- 인증: Supabase Auth의 GitHub OAuth
- 웹: Vercel 배포
- API: Render 배포
- 데이터: Supabase
- 로컬 웹 기본 주소: `http://localhost:5173`
- 로컬 API 기본 주소: `http://localhost:3000`
- 배포 웹 주소: `https://www.ptop.site`

환경별로 다음 값을 분리한다.

- `VITE_API_BASE_URL`
- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY`
- `WEB_ORIGIN`
- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

## 14. 성공 지표

- 로그인 후 분석 시작까지 사용자가 막히지 않는다.
- 분석 중 회고 입력이 자동 화면 전환으로 유실되지 않는다.
- 사용자의 GitHub ID와 무관한 팀원의 작업이 개인 기술적 도전으로 과도하게 노출되지 않는다.
- 사용자가 분석 결과에서 근거와 AI 해석을 구분한다.
- 사용자가 결과 확인 후 작업실과 기존 분석 결과로 다시 이동할 수 있다.
- 최소한의 회고 입력만으로도 결과에 개인의 맥락이 반영된다.

## 15. 제외 범위

- 멀티플레이와 실시간 캐릭터 동기화
- 캐릭터 생성·커스터마이징
- 사용자가 직접 맵을 편집하는 기능
- Repository 전체 소스 코드를 무제한으로 AI에 전송하는 분석
- 사용자의 검토 없이 완성된 포트폴리오라고 확정하는 자동 생성
- Notion 등 외부 서비스로의 자동 내보내기
