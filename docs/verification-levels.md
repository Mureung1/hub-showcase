# verification-levels.md — 다층 검증 방법

> 왜 있는 문서인가: **단위 테스트만으로는 배포된 서비스가 동작한다고 말할 수 없다.** 2026-07-28에
> 단위 테스트 22개가 전부 통과하는 상태에서 (1) 상태 확인 API 한 번에 서버 프로세스가 죽는 경로와
> (2) 외부 LLM이 조용히 규칙 폴백으로 떨어지는 경로가 둘 다 살아 있었다. 둘 다 단위 테스트로는
> 잡히지 않고, 각각 다른 레벨의 검증에서 잡혔다.
>
> 변경을 배포하기 전에 **아래 5레벨 중 해당되는 것을 모두 돌리고, 결과를 남긴다.**

---

## 레벨 정의

| 레벨 | 무엇을 보는가 | 무엇을 못 보는가 | 도구 |
|---|---|---|---|
| **L1 단위** | 순수 함수의 입출력 (점수·매칭·스케줄) | 네트워크, 상태코드, 렌더링, 외부 API | `npm --prefix frontend test` (vitest) |
| **L2 계약** | HTTP 상태코드·헤더·입력 검증·저장 라운드트립·CORS | 화면, 사용자 흐름, 외부 LLM 실제 응답 | `curl` 스크립트 |
| **L3 외부 연동 실호출** | **실제 외부 API를 진짜로 부른다** — 응답 시간, 스키마 준수, 하드룰 위반 여부, 키 없음/실패 시 폴백 | 화면에서의 표현 | `curl` + 직접 SDK 호출 |
| **L4 브라우저 흐름** | 실제 사용자 경로, **UI 상태 변화**(pending·disabled·메시지), 콘솔 에러, 네트워크 요청/응답 본문 | 장애 상황 | Browser 도구(`read_page`/`javascript_tool`/`read_network_requests`) |
| **L5 장애 주입** | 의존성이 죽었을 때의 동작 — 프로세스 생존, 타임아웃, 폴백, 사용자에게 보이는 메시지 | — | 잘못된 환경변수·지연 목 서버·프로세스 강제 종료 |

**핵심 원칙**

- L1이 다 통과해도 L2~L5를 건너뛰지 않는다. 레벨마다 보는 게 다르다.
- **L3은 "붙어 있다"가 아니라 "실제로 응답한다"를 본다.** 모킹하면 이 레벨의 의미가 없다.
- L5는 "실패했을 때 사용자가 무엇을 보는가"까지 확인한다. 로그만 보면 부족하다.
- 결과는 이 문서 형식으로 남긴다 — 다음 사람이 "이건 확인된 건가?"를 되묻지 않게.

## 레벨별 실행 방법

### L1 — 단위

```bash
npm --prefix frontend test
```

### L2 — API 계약

```bash
npm run verify:api                                    # 로컬(http://localhost:3001)
BASE=https://hub-backend-kymx.onrender.com npm run verify:api   # 배포 대상
```

정상 경로만 보지 말고 **거부되어야 하는 입력이 실제로 거부되는지**를 같이 본다.

확인 항목(2026-07-28 기준 14건): health 200 · 없는 경로 404 JSON · 동의 없이 저장 거부 400 · anonId 없이 저장/조회/삭제 거부 400 · 저장 201 · **화이트리스트(허용 안 된 필드가 저장되지 않는지)** · 조회 · 삭제 · 삭제 후 0건 · CORS 허용 origin 통과 · **CORS 미허용 origin 차단**.

> 화이트리스트와 CORS 차단은 "되는 것"이 아니라 **"안 되는 것"을 확인하는 항목**이다. 이런 건 정상 경로 테스트에서 절대 안 걸린다.

### L3 — 외부 연동 실호출

```bash
# 실제 LLM 왕복 (프론트가 보내는 형식과 동일하게: {role, text})
curl -m 90 -X POST http://localhost:3001/api/mbti-chat -H "Content-Type: application/json" \
  -d '{"consent":true,"messages":[{"role":"user","text":"혼자 조용한 곳에서 집중이 잘 됩니다."}]}'
```

같이 확인할 것:

- **응답 시간**을 잰다. 코드의 타임아웃 상한과 비교해 마진이 얼마인지 본다
- 키가 없을 때 `available:false`로 떨어지는지 (LLM 키 환경변수를 **빈 값으로 두고** 백엔드를 기동해 확인)
- 동의 없이 호출하면 400인지
- 출력에 **하드룰 금칙 표현**(진단·성적 예측·우열·정확도 수치)이 없는지
- 보충 모드(`knownMbti`)에서 확정 유형이 유지되는지 — 대화 내용을 **일부러 반대로** 넣어 확인한다

> 페이로드 필드명을 프론트와 다르게 쓰면 서버가 조용히 폴백으로 떨어진다. 검증 실패로 오인하기 쉬우니
> 항상 프론트 코드(`components/steps/StepMbtiChat.jsx`)에서 실제 형식을 확인하고 맞춘다.

### L4 — 브라우저 사용자 흐름

전 구간을 실제로 클릭해서 통과하고, **UI 상태 변화를 캡처**한다.

- 각 스텝의 버튼 라벨(대부분 JSX로 동적 생성돼 grep으로 안 나온다)
- 비동기 작업 중 `pending` 표시·버튼 비활성 여부 → 이건 스크린샷으로 남긴다
- `read_network_requests`로 **요청·응답 본문**을 확인 (상태코드만 보면 부족하다)
- `read_console_messages`로 에러 0건 확인
- 동의 게이트: 체크 전에는 입력 UI 자체가 없는지

### L5 — 장애 주입

| 주입 | 방법 | 기대 동작 |
|---|---|---|
| DB 다운 | 잘못된 `SUPABASE_URL`로 기동 | health가 **503 degraded**, **프로세스 생존**. 크래시하면 실패 |
| 네트워크 지연 | 지연 목 서버(스크래치패드) | 화면에 대기 표시, 상한 시간 후 타임아웃 메시지, 버튼 복구 |
| 백엔드 정지 | `lsof -ti:3001 \| xargs kill -9` | 앱이 **끝까지 진행**되고 "서버 연결 실패 — 앱은 계속 사용할 수 있습니다" 표시 |
| LLM 타임아웃 | `CALL_TIMEOUT_MS`를 낮춘 사본 | 다음 모델로 폴백. 폴백도 실패하면 규칙 설문 경로 |

## 2026-07-28 실행 기록

대상: `/api/health` 예외 처리 수정, 서버 IO pending·타임아웃 추가, LLM 타임아웃 폴백 수정.

### L1 — 단위: **22개 통과**

`npm run build`·`npm run lint`도 통과. 번들 86.41 → 86.71 kB(gzip).

### L2 — API 계약: **14건 PASS / 0 FAIL**

로컬 백엔드 + **실제 Supabase** 연결로 실행. 저장 → 조회 → 삭제 라운드트립 후 `storedCount`가 4로 복귀(테스트 데이터 잔존 없음).

특기: 비허용 필드(`name`, `freeText`)를 함께 보냈으나 응답·저장에 포함되지 않음(ALLOWED_FIELDS 화이트리스트 동작). 미허용 origin(`https://evil.example.com`)에 CORS 허용 헤더가 붙지 않음.

### L3 — 외부 LLM 실호출: **문제 1건 발견 → 수정**

| 확인 | 결과 |
|---|---|
| 실제 Gemini 왕복(서버 경유) | 성공 · **6.3s / 7.1s / 8.1s** (3회) |
| 원시 SDK 직접 호출 | `gemini-flash-latest` **7.5s** · `gemini-flash-lite-latest` **1.5s** |
| 키 없음 | `{"available":false,"mbti":null}` — 프론트 규칙 폴백 유도 |
| 동의 없음 | `400 consent_required` |
| 빈 메시지 | `400 messages_required` |
| 보충 모드(`knownMbti:"ENFP"`) | 대화를 일부러 INTJ 성향으로 넣었는데도 **ENFP 유지** |
| 하드룰 금칙어 | 없음. 전부 "…일 수 있습니다" 가능성 표현 |

**발견한 결함**: 첫 시도(입력이 긴 2메시지)가 **12,025ms**로 `CALL_TIMEOUT_MS = 12000`을 넘겨 실패했다.
문제는 실패했다는 것 자체가 아니라, **타임아웃 오류에는 `status`가 없어서 `isRetriable()`이 false**였다는 점이다.
그래서 실측 **1.5초**로 훨씬 빠른 `gemini-flash-lite-latest`를 **시도조차 하지 않고** 규칙 폴백으로 떨어졌다.
`flash-latest`의 구조화 출력이 6~8초가 기본이므로 12초 상한은 마진이 얇고, 입력이 조금만 길면 재현된다.

**수정**: `isRetriable()`이 `llm_timeout`도 재시도 대상으로 보게 했다(`backend/src/lib/llm.js`).
`MODEL_CHAIN` 길이만큼만 도니 무한루프는 없다. 실패 경로에 `console.warn` 로그도 추가했다 —
전에는 LLM이 조용히 죽어도 Render 로그에 아무것도 남지 않았다.

**수정 검증**: `CALL_TIMEOUT_MS`를 3초로 낮춘 사본으로 강제 재현 →
`[llm] gemini-flash-latest 실패(재시도 가능): llm_timeout` 로그 후 **두 번째 모델로 폴백해 4.6초에 INTJ 정상 응답**.

### L4 — 브라우저 흐름: 전 구간 완주 · 콘솔 에러 0건

- 랜딩 → MBTI 입력(INTJ) → AI 보충 → 공부 설문 5문항 → 스트레스 설문 4문항 → 결과 1/2·2/2 → 오늘 계획 → 실천 카드 → 루틴 실행 → 회고 리포트 전 구간 통과
- **AI 채팅 경로도 브라우저에서 실호출**: 동의 체크 전에는 입력창이 렌더링되지 않음(ADR-008 동의 게이트 동작). 동의 후 2문항 대화 → `POST /api/mbti-chat` **200** → 응답 본문에 `mbti:"INTJ"`, `confidence:"mid"`, `observedSignals` 3개가 `focusEnergy`·`planningStability`·`inputStyle`로 정확히 연결됨
- **UI 상태 변화 확인**: 저장/삭제 진행 중 라벨이 `저장 중…`/`삭제 중…`으로 바뀌고 **3버튼 모두 비활성**, "서버가 잠들어 있으면 첫 응답까지 최대 1분" 안내 표시. 완료 후 라벨·활성 복귀, 성공 메시지와 건수 갱신
- 스트레스 설문은 4문항을 **모두** 답해야 `결과 보기`가 활성화됨

### L5 — 장애 주입: 4건 모두 기대대로

| 주입 | 수정 전 | 수정 후 |
|---|---|---|
| 잘못된 `SUPABASE_URL` + health 호출 | **프로세스 즉사** (`Error: supabase count: TypeError: fetch failed` → 종료, HTTP `000`) | **503 degraded** 응답 + 프로세스 생존(2회 연속 호출 정상) |
| 30초 지연 서버 | 무한 대기 | **20초에 중단**, 버튼 복구, "서버 연결 실패" 표시 |
| 백엔드 강제 종료 | — | 앱이 결과 화면까지 **완주**, "앱은 계속 사용할 수 있습니다(로컬 저장은 유지)" 표시 |
| LLM 타임아웃 | 즉시 규칙 폴백 | 다음 모델로 폴백 → 4.6초 정상 응답 |

### 별도 발견 — 배포 환경 조치 필요 (코드로 못 고침)

**배포된 백엔드는 `/api/mbti-chat`에 `{"available":false,"mbti":null}`을 반환한다.**
`isLlmAvailable`이 false라는 뜻이고, **Render 환경변수에 `GEMINI_API_KEY`가 없다**는 의미다.

- 영향: 배포 환경에서 AI 근거 보충 기능이 **꺼져 있다**. `showcase.json`의 techStack에는 "Gemini API"가 들어 있다
- 다만 폴백 계약은 정상 동작하므로 **사용자 흐름은 끊기지 않는다**(규칙 설문으로 진행)
- 조치: Render 대시보드 → `hub-backend` → Environment에 `GEMINI_API_KEY` 추가(사용자가 직접). 키 값은 채팅·문서·커밋에 남기지 않는다(`docs/security-secrets.md`)
