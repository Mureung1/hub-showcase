## S1 · 타이틀 (20초)

안녕하세요, WeatherPilot 만들고 있는 양서형입니다.

**WeatherPilot은 날씨 데이터로 소상공인 매출을 지키는 자율 마케팅 에이전트입니다.** 비 오는 날, 폭염인 날 매출이 빠지는 걸 에이전트가 미리 감지해서 마케팅 문자를 준비해 두고, 사장님은 검토하고 승인만 하는 서비스예요.

오늘은 프로젝트를 짧게 소개하고, 이번 3주차에 한 작업을 말씀드린 다음, 마지막에 질문 두 가지를 드리고 싶습니다.

## S2 · 문제 정의 (30초)

먼저 왜 이걸 만들었는지부터요.

실제 상권 데이터를 보면 **비 오는 날 매출이 평균 18%, 폭염 낮 시간대엔 20%까지 빠집니다.** 날씨는 예보로 미리 알 수 있는데도 매출은 그냥 빠져요.

왜냐하면 사장님 입장에선 **대응이 전부 수작업이기 때문입니다.** 오늘 날씨 확인하고, 문구 고민하고, 발송까지 — 장사하면서 이걸 매일 하기는 어렵죠. 이 간극을 에이전트가 메우자는 게 출발점입니다.

## S3 · 솔루션 (40초)

동작은 다섯 단계입니다. **날씨와 매출을 분석하고 → 문구·쿠폰 초안을 만들고 → 사장님이 검토·승인하면 → 발송하고 → 쿠폰 사용을 추적합니다.**

여기서 핵심은 세 번째, **사람이 게이트라는 거예요.** 에이전트가 다 준비하지만 발송 버튼은 사장님이 누릅니다.

설계 원칙은 세 가지를 지켰습니다. **API 키는 전부 서버에만** 있고, **광고 문자 관련 법적 필터는 서버가 강제**해서 UI를 우회해도 법은 못 우회하고, **에이전트 파이프라인은 순수 함수**라 크론이 돌리든 API가 부르든 테스트가 부르든 같은 코드가 돕니다.

## S4 · 스코프 (30초)

스코프는 정직하게 표기했습니다.

**날씨는 기상청과 OpenWeatherMap 실연동, LLM 제안은 Groq, 문자는 Solapi로 제 번호에 실제 발송, DB와 스케줄러도 실구축입니다.** 반면 POS 연동은 수동 입력과 CSV 업로드로 대체했고, 카카오 알림톡이나 080 수신거부 실회선은 모의로 뒀습니다. Instagram 게시는 우선순위를 따져서 이월했고요.

"뭐가 진짜냐"를 항상 이 표로 먼저 말씀드리고 시작합니다.

## S5 · 3주차 개요 (50초)

이번 주 이야기입니다. 한 줄로 요약하면 — **배포를 앞당기고, 남은 시간을 전부 마감 품질에 썼습니다.**

원래 계획엔 배포가 수·목이었는데, **마감 전 최대 리스크가 배포라고 판단해서 월요일에 먼저 끝냈어요.** FE는 Vercel, BE는 Render로요.

그렇게 확보한 버퍼로 — 화요일엔 배포된 앱을 직접 리뷰해서 나온 개선 5건, 저희는 퀵윈 팩이라고 불렀는데 이걸 구현하고 테스트·법적 체크리스트 검증까지 했고, 수요일엔 데이터 흐름 아키텍처를 문서화했고, 오늘 목요일엔 진단 표시 버그 수정하고 프론트 테스트를 도입하고, 기동 잡이라는 안정화 작업을 했습니다. 하나씩 조금 더 자세히 말씀드릴게요.

## S6 · 배포 (40초)

구조는 이렇습니다. **Vercel의 프론트가 Render의 Express 서버를 부르고, 서버가 Supabase를 씁니다.** 매일 아침 6시 반 크론도 이 서버에서 돌아요.

배포하면서 지킨 것 세 가지인데요. **CORS는 배포된 프론트 도메인만 화이트리스트**하고 와일드카드는 금지했고, **로컬 .env 키 목록과 배포 환경변수를 1:1로 대조**해서 누락을 없앴고, 마지막으로 **배포 URL에서 제안 조회부터 승인, 발송, 쿠폰 사용, 추적까지 전 플로우를 실제로 재현**해서 확인했습니다.

무료 플랜이라 서버가 슬립되는 문제가 있는데, 이건 뒤에 안정화에서 말씀드릴게요.

## S7 · 퀵윈 팩 (50초)

배포하고 나서 **제가 사용자 입장으로 배포된 앱을 처음부터 다시 써봤는데, 어색한 게 5개 나왔습니다.** 그걸 묶어서 하루에 처리한 게 퀵윈 팩이에요.

몇 개만 짚으면 — **QW-1은 흐린 날인데 화면엔 "맑은 날 매출 +12%"라고 뜨는 모순**이었어요. mock 데이터 잔재였고, 진단 결과를 API에 실어서 실데이터로 바꿨습니다.

**QW-3은 문자 이모지 문제**인데, 한국 LMS는 EUC-KR이라 이모지가 실리지 않고 통신사에서 떼어냅니다. 그래서 문자 경로에서만 이모지를 제거하고 SNS용은 유지하게 분리했어요.

**QW-4는 사장님이 할인율을 직접 고치는 기능**인데, 편집을 열어주는 대신 발송 직전에 서버가 가드레일로 20% 초과를 다시 검사합니다. UI를 고쳐도 서버는 못 속여요.

## S8 · 검증 (40초)

기능이 코드를 바꿨으니 검증을 뒤에 붙였습니다.

**서버 테스트 100개가 통과하고, 비어 있던 라우트 상태 전이와 쿠폰 redeem 경계를 보강했습니다.** 프론트에도 이번에 vitest를 처음 도입해서 API 어댑터에 21케이스를 넣었고요.

법적 요건은 — **(광고) 표기, 수신동의 필터, 야간 발송 차단, 무료수신거부 문구, 이 네 가지가 전부 서버에서 강제되는지 코드와 테스트로 대조**를 마쳤습니다.

마지막으로 오늘 한 기동 잡인데요. **무료 플랜은 서버가 슬립돼서 6시 반 크론을 놓칠 수 있어요. 그래서 서버가 깨어날 때 오늘 제안이 없으면 만들고, 날씨가 바뀌었으면 초안을 다시 만들게 했습니다.** 승인되거나 발송된 건 건드리지 않고요.

## S9 · 설계 포인트 → Q1 빌드업 (40초)

질문으로 넘어가기 전에, 이번 주에 제일 배운 게 많았던 설계 하나만 공유드릴게요.

프론트와 백엔드가 각자 굴러가면 두 가지가 어긋나기 시작하더라고요. API 응답 모양, 그리고 문자 미리보기와 실제 발송 문구요.

그래서 **모노레포의 packages/shared에 API 응답 타입과 문자 본문을 조립하는 함수를 두고, 양쪽이 그걸 import하게 했습니다.** 그랬더니 **API가 어긋나면 런타임이 아니라 컴파일 에러로 잡히고**, 미리보기와 발송이 같은 함수를 쓰니까 **"미리보기랑 실제 문자가 다른" 종류의 버그는 구조적으로 불가능**해졌어요.

이게 맞는 방향인지가 궁금해서, 첫 번째 질문으로 이어집니다.

## S10 · Q&A (질문 낭독 후 경청)

두 가지 여쭙고 싶습니다.

**Q1.** 방금 보신 것처럼 저희는 shared 패키지로 타입과 로직을 공유해서 드리프트를 컴파일 에러로 잡았는데요. **현업에서는 API 계약을 어떻게 관리하시나요?** OpenAPI 코드젠이나 tRPC 같은 도구 이야기를 들었는데 언제 뭘 쓰는지 궁금하고요. 특히 **FE와 BE가 다른 언어, 다른 저장소로 분리되면 이런 공유 방식은 어떻게 바뀌는지** 궁금합니다.

**Q2.** 이번 프로젝트에서 AI 코딩 도구를 적극적으로 써서 속도는 냈는데, 솔직히 **"동작은 하는데 확신이 없는" 순간들이 있었습니다.** 도구가 제안한 코드를 어디까지 이해하고 넘어가야 하는지 기준을 못 잡겠더라고요. **멘토님은 AI가 생성한 코드를 리뷰하실 때 무엇을 보시는지** 여쭙고 싶습니다.

감사합니다.

## 예상 반문 대비

- **"왜 tRPC를 바로 안 썼나?"** → 챌린지 스코프에선 shared import가 가장 단순했고, 타입+로직(문자 조립)을 같이 공유해야 해서 스키마만 공유하는 방식보다 맞았다. 도구 도입 기준이 궁금한 것.
- **"테스트 100개면 커버리지는?"** → 개수보다 위치로 답: 법적 필터·가드레일·상태 전이·redeem 경계 등 돈/법이 걸린 경로 위주로 보강했다.
- **"기동 잡이 크론과 중복 실행되면?"** → 오늘 제안이 이미 있으면 스킵, 날씨 바뀐 draft만 재생성, 승인·발송분은 보존 — 멱등하게 설계했다.
