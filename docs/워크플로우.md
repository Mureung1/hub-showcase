# 나만의 AI 협업 워크플로우

> 3주간 "마감할인" 프로젝트를 AI와 함께 만들며 정착시킨 일하는 방식. 발표·회고용 정리.

## 0. 이 프로젝트 한 줄 소개

**마감할인** — 카페·베이커리가 마감 임박 재고를 등록하면, 조건에 맞는 근처 소비자에게 알림을 보내 선착순 예약·픽업으로 잇는 로컬 매칭 플랫폼. 버려질 재고와 그걸 싸게 살 근처 사람이 서로를 못 찾는 문제를 푼다.

스택: React + Vite / Express / PostgreSQL(raw SQL) / Docker / FCM / Vitest.

---

## 1. 한 문장으로 요약한 나의 방식

> **결정은 내가, 실행은 AI가, 검증은 반드시 눈으로.**

- **결정(내가)**: 무엇을 만들지, 어떤 기술로, 어떤 트레이드오프를 감수할지.
- **실행(AI가)**: Task 분해, 이슈 등록, 코드 작성, 1차 검증.
- **검증(항상)**: curl·브라우저·DB·동시성 스크립트로 실제 동작을 확인한 뒤에만 "완료".

AI의 결과를 그대로 받지 않는 것이 핵심이다. Service에 SQL이 섞인 구조를 Repository로 분리하라고 요구했고, "관심 설정이 목록까지 걸러야 하나?" 같은 설계 판단은 근거를 들어 함께 검토했다.

---

## 2. Task 하나가 흐르는 순서 (핵심 루프)

모든 기능은 이 8단계를 그대로 탄다. 예외 없이 반복해서 리듬을 만들었다.

```
① task.md에서 Task·완료 기준(DoD) 확인
② GitHub Issue로 작업 세분화 등록
③ Repository → Service → Route 순으로 구현 (서버)
④ curl로 정상·실패 경로 검증 (2xx / 4xx)
⑤ 브라우저로 화면 흐름 확인
⑥ DB 쿼리로 데이터 반영 확인
⑦ Task ID를 남겨 커밋·푸시  (예: "feat(server): ... (T-08)")
⑧ 검증 결과를 이슈에 기록하고 종료
```

**왜 이 순서인가**
- ②에서 큰 Task를 잘게 쪼개 이슈로 남기면, 나중에 "무엇을 왜 이렇게 했는지"가 그대로 근거로 남는다.
- ③의 레이어 방향(`routes → services → repositories → db`)을 한 방향으로 고정해, SQL은 Repository에만·검증은 Service에만 있게 했다.
- ④~⑥ 세 겹 검증: API·화면·데이터를 각각 다른 도구로 확인해 "된 줄 알았는데 안 되는" 상황을 막는다.

## 3. 3주간 실제로 만든 것 (Task 지도)

| 주차 | Task | 핵심 |
|---|---|---|
| 1주 | T-01~T-05 | DB 스키마·마이그레이션, 시딩, 역할 선택, 가게·딜 등록 |
| 2주 | T-06~T-11 | 딜 목록(위치 기반)·상세, **선착순 예약(오버셀 0)**, 픽업 확인, 알림 대상 판정 |
| 3주 | T-12~T-17 | 관심 설정, FCM 푸시·인앱 알림, 만료 처리, 예약 알림 |

부수적으로: Repository 레이어 분리 리팩터, Vitest+RTL 테스트 도입, showcase 제출물.

총 **16개 GitHub 이슈**, 모든 커밋에 Task ID. 이슈마다 검증 결과 코멘트를 남겨 닫았다.

## 4. 역할별로 나눠 쓴 Agent와 Skill

AI를 하나의 만능 도구로 쓰지 않고 **역할별로 나눠** 활용했다. (`~/.claude/agents/`)

### 서브에이전트

| 에이전트 | 언제 | 무엇을 |
|---|---|---|
| **planner** | 새 기능·"어떻게 나눌까" | 작업 분해 + 우선순위(P0-P3)·의존성·리스크 |
| **architect** | 기술 선택(A vs B)·스키마 설계 | 트레이드오프와 함께 결정 |
| **reviewer** | 코드 작성 직후 | 정확성·동시성·컨벤션 검토 |
| **test-writer** | 기능 완료 후 | 깨질 지점을 겨냥한 테스트 |

역할 분리의 요점: **planner(무엇을 어떤 순서로) vs architect(기술적으로 어떻게)** 를 나눴고, 읽기 전용 에이전트는 실수로도 코드를 못 바꾸게 도구 권한을 제한했다.

### 스킬

- **code-tutor** — 생성된 코드를 개념 단위로 설명받아 **직접 이해**하고 학습 상태를 기록. AI가 짠 코드를 남의 코드로 두지 않기 위한 장치. (커넥션 풀, 트랜잭션, 콜백, React state 등을 이 방식으로 내재화)

## 5. 나를 지키는 두 가지 검증 습관

AI 협업에서 가장 위험한 건 "되는 것처럼 보이는 것"이다. 두 습관으로 막았다.

### (1) 동시성은 말이 아니라 숫자로 증명한다
이 프로젝트의 기술 셀링포인트인 선착순 재고 차감을 **실측**으로 검증했다.

```
재고 5개에 동시 요청 50건 → 성공 정확히 5건, 품절 45건
남은 수량 0, 불변식(총수량 − 활성예약 = 남은수량) 판정 OK
발급된 픽업코드 5개 전부 중복 없음  → 오버셀 0건
```

핵심은 "확인 후 차감"이 아니라 **조건부 UPDATE 한 문장**(`... WHERE remaining_qty >= qty`)이라는 점. 행 락 안에서 조건 검사와 차감이 원자적으로 일어나 동시 요청에도 초과 성공이 불가능하다.

### (2) 통과하는 테스트는 일부러 깨뜨려 본다
Vitest로 `RequireRole` 가드 테스트 3개를 작성한 뒤, **조건을 반전시켜 3개 모두 실패**하는 것을 확인하고 원복했다. 통과하는 테스트는 그것만으로 아무것도 증명하지 못하기 때문. 테스트가 실제 동작을 붙잡고 있다는 유일한 증거다.

이 습관 덕에 실제 버그도 잡았다 — FCM을 실제 서비스 계정 키로 검증하다 firebase-admin ESM 초기화 오류와 무효 토큰 오판정(전체 토큰 삭제 위험) 2건을 발견해 고쳤다.

## 6. 시연 시나리오 (처음 보는 사람용)

핵심 루프 하나를 끝까지 보여주는 것이 가장 강력하다.

1. **소비자** — 내 주변 마감 할인 목록(거리순) → 딜 상세 → **예약** → 픽업코드 발급
2. **사장님** — 대시보드에 예약 수 자동 반영 → **픽업 확인**(코드 입력) → 완료
3. **알림** — 사장님이 딜 등록 → 조건 맞는 소비자에게 **FCM 푸시** / 소비자가 예약 → 사장님에게 푸시
4. **(하이라이트)** 동시성 스크립트 실행 → "재고 5, 동시 50요청 → 정확히 5건" 로그를 라이브로

준비: `npm run migrate && npm run seed && npm run dev`. 데모는 Chrome 프로필 2개(소비자·사장님)로 푸시까지.

## 7. 세 문장 회고

- **리듬이 품질을 만든다.** 매 Task를 같은 8단계로 태우니, 검증을 건너뛰고 싶은 유혹이 줄었다.
- **AI에게 판단을 위임하지 않았다.** 코드는 맡겨도 "왜 이렇게"는 내가 답할 수 있어야 한다는 기준을 지켰다(code-tutor).
- **눈으로 본 것만 완료다.** curl·브라우저·DB·동시성 4중 검증이 "될 줄 알았는데"를 없앴다.
