# GOTCHAS

## 반드시 피할 것

### MVP에 자동화를 몰래 넣지 않는다

MVP는 수동 입력과 답글 복사 게시가 기준이다. 자동 리뷰 수집, 자동 답글 게시, 자동 신고는 Phase 2 이후이며 별도 리스크 검토가 필요하다.

### 악성 의심 리뷰에 답글 초안을 바로 만들지 않는다

악성 의심 리뷰는 먼저 위험도 판단과 대응 센터로 연결해야 한다. 오탐으로 판단되어 위험도 ①·②로 조정된 뒤에만 일반 답글 흐름으로 복귀한다.

### 법률 자문처럼 보이는 문구를 쓰지 않는다

가능한 문구:

- “일반적인 절차 정보입니다.”
- “필요하면 법률 전문가 상담을 검토할 수 있습니다.”

금지 문구:

- “고소하면 이깁니다.”
- “명예훼손이 성립합니다.”
- “이렇게 하면 법적으로 해결됩니다.”

법적 안내 영역에는 항상 “일반적인 정보 안내이며 법률 자문이 아닙니다”를 노출한다.

### 보상·환불 약속을 자동으로 쓰지 않는다

답글 초안은 보상, 환불, 서비스 제공을 약속하지 않는다. 보상은 사장님이 직접 판단하고 직접 수정할 때만 들어갈 수 있다.

### 확인되지 않은 사실을 단정하지 않는다

배달 지연 원인, 조리 상태, 배달 기사 책임, 고객 행동은 확인 전 단정하지 않는다.

좋은 표현:

- “전달해 주신 내용은 확인해 보겠습니다.”
- “포장과 전달 과정을 점검하겠습니다.”

나쁜 표현:

- “배달 기사님 문제였습니다.”
- “조리 과정에는 문제가 없었습니다.”

### 매장 프로필에 없는 정보를 답하지 않는다

문의 답변은 매장 프로필의 운영 정보에 등록된 항목만 사용한다. 없으면 “확인 후 안내드리겠습니다”로 처리한다.

### 이벤트 기간이 끝난 내용을 답글에 넣지 않는다

이벤트는 기간을 함께 관리해야 하며, 만료 후 답글에서 제외한다.

### 고객 개인정보를 과하게 저장하지 않는다

닉네임, 주문 정보, 증거 파일은 목적에 필요한 최소 범위로만 저장한다. 반복 악성 고객 추적도 개인정보 리스크를 동반하므로 보관 기간과 접근 권한이 필요하다.

## 자주 헷갈리는 판단

| 상황 | 올바른 처리 |
|---|---|
| 칭찬과 불만이 함께 있음 | 불만으로 분류하고 복합 플래그를 둔다 |
| 별점은 낮지만 본문은 칭찬 | 본문 우선, 확인 필요 표시 |
| 리뷰가 감정적이지만 경험 기반 | 단순 불만 또는 정당한 클레임 가능성을 먼저 본다 |
| 고객이 환불을 요구함 | 곧바로 악성으로 보지 말고 구체적 피해 사실과 요구 수준을 함께 본다 |
| 사장님이 악성이라고 판단함 | 시스템 판단보다 사장님 최종 판단을 허용하되, 자동 실행은 하지 않는다 |

## 구현 시 주의할 점

- LLM 결과를 그대로 저장하거나 게시하지 않는다. 후처리 검사를 둔다.
- 분류 결과에는 항상 근거를 함께 보여준다.
- “확인 필요” 상태를 제품 흐름의 예외가 아니라 정상 상태로 설계한다.
- 플랫폼 자동화가 들어오면 계정 제재, 약관, 자격증명 보관 리스크를 별도 ADR로 다룬다.
