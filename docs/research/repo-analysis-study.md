# Git Repository 분석 학습 노트

## 학습 목표

PtoP가 프로젝트 경험을 정리하기 위해 Git Repository에서 어떤 정보를 읽고, 그 정보를 어떻게 포트폴리오 초안으로 연결할 수 있는지 정리한다.

## Repository에서 분석할 수 있는 정보

| 분석 대상 | 얻을 수 있는 정보 | PtoP에서 활용하는 방식 |
| --- | --- | --- |
| README | 프로젝트 목적, 주요 기능, 실행 방법, 기술 스택 | 프로젝트 요약과 포트폴리오 소개 문장 생성 |
| 폴더 구조 | 프론트엔드/백엔드 구분, 도메인 구조, 주요 기능 영역 | 프로젝트 구조 요약과 핵심 기능 후보 추출 |
| package.json | 사용 라이브러리, 프레임워크, 스크립트 | 기술 스택 자동 정리 |
| 주요 코드 파일 | 실제 구현된 기능, 상태 관리, API 연결, 컴포넌트 구조 | 핵심 구현 내용과 기술적 어필 포인트 추출 |
| commit log | 작업 순서, 자주 수정한 파일, 기능 개발 흐름 | 내가 한 일과 기여 흐름 추론 |
| PR/Issue | 문제 상황, 논의 내용, 리뷰, 의사결정 | 문제 해결 과정과 협업 경험 정리 |

## GitHub Repository에서 수집 가능한 데이터

GitHub Repository URL을 입력받는 경우에는 README와 코드 파일뿐 아니라 GitHub REST API를 통해 공개된 활동 기록을 함께 확인할 수 있다. PtoP는 모든 데이터를 같은 의미로 해석하지 않고, **확인 가능한 사실**과 **AI가 제안하는 해석**을 구분해야 한다.

| 범주 | 수집 가능한 데이터 | PtoP 활용 방식 | 해석 시 주의점 |
| --- | --- | --- | --- |
| 기본 정보 | 이름, 설명, 토픽, 라이선스, 생성일, 최근 수정일, 기본 브랜치, 홈페이지, stars, forks | 프로젝트 개요와 한 줄 소개의 근거 | stars나 forks는 개인의 프로젝트 기여를 뜻하지 않는다. |
| 문서와 기술 스택 | README, Wiki, 언어별 코드 바이트, `package.json`, lock 파일, 설정 파일 | 문제 정의, 주요 기능, 사용 기술, 실행 환경 정리 | README와 실제 코드가 최신 상태로 일치하지 않을 수 있다. 언어 비율은 코드 바이트 기준이다. |
| 코드 구조 | 파일 트리, 폴더 구조, 확장자, 진입점, 컴포넌트/API/DB/테스트/CI 관련 파일 | 프로젝트 구조와 기능 영역을 요약하고 주요 구현 후보를 찾는다. | 파일이 존재한다는 사실만으로 작성자나 난이도를 판단하지 않는다. |
| 커밋 이력 | 작성자, 날짜, 메시지, SHA, 변경 파일, 추가/삭제 라인, 서명 검증 정보 | 개인 작업의 시기, 반복 작업 주제, 기능 개발 흐름을 확인한다. | 커밋 수나 변경 라인은 작업량의 참고 지표일 뿐 품질과 실제 기여도를 의미하지 않는다. |
| 참여자 | contributor 목록, 계정, 커밋 수 | 팀 구성과 `커밋 기준 활동 비중`을 표시한다. | contributor API 응답은 캐시될 수 있고, squash merge나 pair programming 등 실제 협업 방식을 반영하지 못할 수 있다. |
| Pull Request | 작성자, 제목, 본문, 상태, 머지 시점, 리뷰어, 리뷰 댓글, 변경 파일 | 기능 제안, 구현 근거, 코드 리뷰와 협업 경험을 연결한다. | PR이 없는 프로젝트에서는 이 근거를 사용할 수 없다. |
| Issue | 작성자, 담당자, 라벨, 상태, 마일스톤, 댓글, 관련 PR | 해결하려던 문제와 논의 과정을 확인한다. | 담당자 지정만으로 실제 작업자를 단정하지 않는다. |
| 품질과 배포 | 테스트 파일, GitHub Actions workflow, check 결과, 태그, Release, 배포 링크 | 테스트, 자동화, 릴리스, 배포 경험을 설명하는 단서로 사용한다. | workflow 파일이 있어도 실제로 항상 성공했거나 운영 품질이 보장되는 것은 아니다. |

### GitHub API 참고 자료

- [Repository API](https://docs.github.com/en/rest/repos/repos): 기본 정보, contributor, 언어, 태그, 토픽 등
- [Commits API](https://docs.github.com/en/rest/commits/commits): 커밋 목록, 작성자, 메시지, 변경 이력 등
- [Pull Requests API](https://docs.github.com/en/rest/pulls/pulls): PR 목록, 리뷰, 변경 파일 등
- [Issues API](https://docs.github.com/en/rest/issues/issues): Issue, 라벨, 담당자, 댓글 등

공개 Repository는 일부 API를 인증 없이 조회할 수 있지만, private Repository와 조직 권한 정보는 사용자의 GitHub 인증 및 적절한 권한이 필요하다. PtoP MVP에서는 공개 Repository 분석을 우선 지원하고, 인증 기반 private Repository 분석은 별도 기능으로 분리한다.

## PtoP 분석 데이터 우선순위

모든 데이터를 즉시 깊게 분석하면 처리 시간이 길어지고 결과의 근거도 흐려질 수 있다. PtoP는 다음 순서로 확장한다.

1. **1차 필수: 프로젝트와 개인 활동의 기본 근거**
   - README, 기술 스택, 참여자, 사용자가 지정한 GitHub ID의 커밋, 최근 작업 흐름
2. **2차 핵심: 역할과 협업을 설명하는 근거**
   - 사용자가 작성한 PR, 연결된 Issue, PR 변경 파일, 리뷰와 논의 내용
3. **3차 확장: 포트폴리오 품질을 높이는 근거**
   - 코드 구조, 테스트와 CI, Release와 배포, AI 질문 기반 회고 기록

초기 결과에서는 Repository owner를 곧바로 사용자로 가정하지 않는다. Repository URL과 함께 사용자의 GitHub ID를 입력받거나, 분석 후 참여자 목록에서 본인 계정을 선택하게 해야 한다.

## 분석 결과의 신뢰도 표현 원칙

PtoP 결과는 데이터의 성격에 따라 표현 방식을 다르게 한다.

| 결과 종류 | 예시 | 화면 표현 원칙 |
| --- | --- | --- |
| 확인 가능한 사실 | 커밋 수, PR 제목, Issue 상태, 변경 파일, 언어 비율 | 수치·원문·GitHub 링크를 함께 제공한다. |
| 계산 결과 | 커밋 기준 활동 비중, 기간별 활동량 | 계산 기준과 분석 시점을 명시한다. `기여도`라는 단정적 표현은 사용하지 않는다. |
| AI 해석 또는 제안 | 반복 작업 주제, 역할 후보, 포트폴리오 문장 초안 | `AI 제안`, `사용자 확인 필요` 라벨을 붙이고 수정·제외할 수 있게 한다. |

권장 결과 흐름:

```text
GitHub의 확인 가능한 흔적
→ 반복되는 작업 주제와 근거 링크
→ AI의 역할/문제 해결 제안
→ 사용자의 수정과 회고 답변
→ 포트폴리오에 활용할 수 있는 정리 초안
```

이 방식은 AI가 사용자의 역할을 과장하거나 단정하는 위험을 줄이고, 사용자가 결과를 검증하면서 자신의 실제 경험을 보완하도록 돕는다.

## README 분석 관점

- 프로젝트가 무엇을 해결하려는지 확인한다.
- 주요 기능 목록이 있는지 확인한다.
- 사용 기술과 실행 방법이 정리되어 있는지 확인한다.
- 배포 링크, 시연 이미지, 데모 설명이 있는지 확인한다.
- README가 부족하면 코드와 폴더 구조를 더 많이 참고해야 한다.

## 폴더 구조 분석 관점

폴더 구조는 프로젝트의 기능 단위와 관심사 분리를 파악하는 데 도움이 된다.

예시:

```text
src/
  components/
  pages/
  hooks/
  api/
  utils/
```

위 구조에서는 다음과 같이 추론할 수 있다.

- `components`: 재사용 UI 컴포넌트가 있음
- `pages`: 화면 단위 라우팅이 있음
- `hooks`: 공통 상태나 로직을 분리했을 가능성이 있음
- `api`: 서버 통신 로직이 있음
- `utils`: 공통 유틸 함수가 있음

## package.json 분석 관점

`package.json`에서는 기술 스택과 실행 방식을 확인할 수 있다.

- `dependencies`: 실제 서비스 코드에서 사용하는 라이브러리
- `devDependencies`: 개발, 빌드, 테스트 도구
- `scripts`: 실행, 빌드, 테스트 명령어

예시:

```json
{
  "dependencies": {
    "react": "...",
    "vite": "..."
  },
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  }
}
```

이 경우 PtoP는 `React`, `Vite` 기반 프론트엔드 프로젝트로 정리할 수 있다.

## 주요 코드 파일 선별 기준

모든 파일을 같은 비중으로 분석하면 핵심을 놓칠 수 있다. 우선순위를 정해 분석한다.

1. README와 설정 파일을 먼저 본다.
2. 진입점 파일을 확인한다.
   - 예: `main.jsx`, `App.jsx`, `server.js`, `app.ts`
3. 화면 또는 라우팅 파일을 확인한다.
4. API 호출 파일을 확인한다.
5. 상태 관리, 비즈니스 로직, 유틸 파일을 확인한다.
6. 테스트 파일이 있다면 기능 의도를 함께 확인한다.

## commit log 분석 관점

commit log는 사용자가 어떤 순서로 작업했는지 보여준다.

확인할 수 있는 정보:

- 어떤 기능이 먼저 만들어졌는가?
- 어떤 파일을 자주 수정했는가?
- 버그 수정이나 리팩토링이 있었는가?
- 문서 작업과 기능 작업이 어떻게 나뉘었는가?

예시 commit:

```text
feat: 로그인 기능 구현
fix: 토큰 만료 처리 오류 수정
refactor: API 호출 로직 분리
docs: README 실행 방법 추가
```

이 흐름에서는 로그인 기능 구현, 인증 예외 처리, API 로직 구조 개선, 문서화 경험을 추출할 수 있다.

## 분석 결과 분류 방식

PtoP는 분석 결과를 다음 항목으로 나눠 보여준다.

- 프로젝트 목적
- 핵심 기능
- 기술 스택
- 주요 구현 내용
- 역할 후보
- 문제 해결 과정 후보
- 포트폴리오 문장 후보

## 분석 시 주의할 점

- 코드만 보고 사용자의 실제 역할을 단정하지 않는다.
- commit author가 여러 명이면 개인 기여도 추론에 주의한다.
- README가 최신 상태가 아닐 수 있다.
- 자동 분석 결과는 사용자가 수정할 수 있어야 한다.
- 분석 결과는 "정답"이 아니라 "초안"으로 제공해야 한다.
