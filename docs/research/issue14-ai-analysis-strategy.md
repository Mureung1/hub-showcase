# Issue #14 AI 분석 전략

## 문서 목적

Issue #14에서는 GitHub Repository를 단순히 commit 수로 요약하는 것이 아니라, 포트폴리오에 활용할 수 있는 기술적 도전 후보를 근거와 함께 제안한다. 이 문서는 AI에 어떤 데이터를 전달하고, 결과를 어디까지 신뢰하며, RAG를 언제 도입할지에 대한 현재 결정이다.

## 분석 결과의 위치

PtoP는 다음 정보를 하나의 후보로 묶는다.

- Background: 프로젝트 맥락에 대한 분석 초안
- Problem: Repository에서 확인할 수 있는 문제 상황 후보
- Solution: 구현 흔적을 기반으로 한 해결 방식 후보
- Technical challenge: 기술적으로 확인할 수 있는 도전 지점
- Why it matters: 포트폴리오에서 설명할 가치가 있는 이유
- Confidence: 근거의 충분한 정도
- Requires user confirmation: 실제 역할·의도·문제 해결 여부를 사용자가 확인해야 하는지
- Evidence: 파일, commit, PR, Issue 등 원본으로 이동할 수 있는 근거

이 결과는 포트폴리오 완성본이나 사용자의 역할에 대한 판정이 아니다. Repository에서 확인한 사실을 기반으로 사용자가 자신의 경험을 회고할 수 있도록 돕는 후보 목록이다.

## 입력 컨텍스트 구성

전체 Repository를 AI에 전달하지 않고, 다음 우선순위로 텍스트 파일을 선택한다.

1. README, package.json, tsconfig, vite.config, nest-cli 등 프로젝트 설명과 실행 설정
2. main, index, app, server, client, bootstrap 등 진입점
3. api, controller, service, route, repository, feature 경로
4. test, tests, __tests__, test/spec 파일
5. CI와 배포 설정

현재 제한은 다음과 같다.

| 제한 | 값 | 이유 |
| --- | ---: | --- |
| 최대 파일 수 | 20개 | API 호출과 prompt 크기 제한 |
| 파일당 최대 문자 수 | 6,000자 | 하나의 큰 파일이 전체 맥락을 독점하지 않게 함 |
| 전체 최대 문자 수 | 40,000자 | 모델 비용과 응답 지연을 제한 |
| 토큰 예상 | 문자 4개당 1토큰 | 정확한 tokenizer가 없는 단계의 보수적인 추정 |

lock 파일, node_modules, 빌드 결과, 이미지·폰트·압축 파일은 제외한다. 파일을 잘라낸 경우 context에 truncated 상태를 남겨 AI가 전체 파일을 읽었다고 오해하지 않게 한다.

## 검색 방식 비교

| 방식 | 장점 | 단점 | 현재 판단 |
| --- | --- | --- | --- |
| 전체 Repository를 prompt에 포함 | 구현이 단순함 | 토큰·비용 증가, 민감정보와 불필요한 코드 전달 | 사용하지 않음 |
| 우선순위 기반 파일 검색 | 구현·테스트가 단순하고 근거 연결이 쉬움 | 복잡한 Repository의 일부 맥락을 놓칠 수 있음 | 초기 선택 |
| 임베딩 기반 RAG | 대규모 Repository와 반복 질문에 유리 | 임베딩 저장·검색·갱신·운영 복잡도 증가 | 후속 검토 |

## 초기에는 RAG를 도입하지 않는 이유

현재 PtoP의 한 번의 분석은 하나의 Repository를 대상으로 제한된 결과를 만드는 흐름이다. 이미 tree, README, package manifest, 주요 파일, commit·PR·Issue를 우선순위로 추릴 수 있으므로, 지금 바로 벡터 DB를 추가하는 것보다 다음을 먼저 검증하는 것이 적절하다.

- 어떤 파일이 실제 기술적 도전 후보를 만드는 데 유용한지
- 후보마다 어떤 근거가 연결되어야 신뢰성을 설명할 수 있는지
- 40,000자 범위에서도 Background/Problem/Solution 후보가 유의미한지
- 사용자가 AI 후보를 얼마나 수정하고 확인하는지

RAG를 먼저 도입하면 검색 정확도보다 임베딩 모델, chunk 크기, similarity threshold, 저장소 갱신 정책을 먼저 운영해야 한다. 현재는 검색 품질의 기준 데이터와 사용자 피드백이 부족하므로, 우선순위 기반 검색을 baseline으로 삼는다.

## RAG를 다시 검토할 조건

다음 조건이 확인되면 임베딩 기반 RAG를 별도 이슈로 검토한다.

- 큰 Repository에서 40,000자 제한만으로 핵심 파일을 자주 놓치는 경우
- 동일 Repository에 대해 회고 질문과 포트폴리오 질문을 반복해서 처리하는 경우
- 사용자가 특정 기능이나 기간을 질문하고 관련 코드만 다시 찾아야 하는 경우
- 사용자 피드백에서 현재 검색 누락이 반복적으로 확인되는 경우

그때도 전체 코드를 무조건 임베딩하지 않고, 파일 경로·commit·PR·Issue와 연결된 chunk만 색인한다. 검색 결과에는 원본 URL과 filePath를 함께 보존해 AI 응답의 근거를 추적할 수 있어야 한다.

## Prompt 규칙

AI에는 다음 규칙을 고정해서 전달한다.

- 제공된 Repository와 evidence에 없는 사실을 만들지 않는다.
- commit 수와 변경 줄 수만으로 실제 기여도나 난이도를 판단하지 않는다.
- 사용자의 역할·의도·문제 해결 여부를 단정하지 않는다.
- 각 후보에는 하나 이상의 evidence를 연결한다.
- 근거가 부족하면 requiresUserConfirmation을 true로 설정한다.
- 응답은 정해진 JSON 구조로만 반환한다.

응답이 malformed JSON이거나 evidence가 없는 후보만 포함하면 후보를 저장하지 않는다. AI 설정이 없는 환경에서는 기존 Repository 구조화 분석은 유지하고, technicalChallenges는 빈 배열과 warning으로 반환한다.

## 결과 해석 원칙

신뢰도는 AI의 확신을 그대로 믿는 점수가 아니라, 입력된 근거가 후보를 얼마나 직접 설명하는지 나타내는 보조 상태다.

- high: 코드 구조와 변경 기록 등 여러 근거가 같은 도전을 설명함
- medium: 관련 근거는 있으나 사용자 경험 확인이 필요함
- low: 일부 흔적만 있어 후보로 제시할 수 있으나 확인이 반드시 필요함

모든 후보는 화면에서 근거 링크와 사용자 확인 필요 상태를 함께 보여준다. PtoP가 해야 할 일은 사용자를 대신해 경험을 확정하는 것이 아니라, 사용자가 자신의 경험을 빠르게 기억하고 설명하도록 돕는 것이다.

## 검증 계획

- 우선순위 파일이 예상 순서로 선택되는지 테스트한다.
- 파일별·전체 문자와 예상 토큰 제한을 테스트한다.
- malformed JSON과 evidence 누락 후보를 거부하는지 테스트한다.
- AI 설정이 없을 때 기존 분석 결과가 유지되는지 테스트한다.
- 후보가 Supabase snapshot과 React 화면에서 같은 evidence를 사용하는지 통합 확인한다.
