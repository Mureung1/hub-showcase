# 알바노트 3주 개발 백로그

## 1. 개발 목표

2026년 7월 10일 기준으로, 앞으로 3주 동안 알바노트의 발표 가능한 MVP를 개발한다.

목표는 완성형 상용 서비스가 아니라, 실제 Supabase와 연결된 상태에서 사장님과 알바생의 핵심 흐름이 동작하는 1차 버전이다.

## 2. 개발 기준

- 개발 인원: 1명
- 개발 기간: 3주
- 목표 결과물: React SPA 기반 발표 가능한 MVP 데모
- 데이터/인증: 실제 Supabase Auth, Supabase Postgres 연결
- 사용자 범위: 사장님과 알바생 모두 포함
- 개발 비중: 핵심 기능 동작 70%, 디자인 정리 30%
- 디자인 기준: `docs/Design.md`
- 아키텍처 기준: `docs/Architecture.md`
- 기능 범위 기준: `docs/mainplan.md`

## 3. 우선순위 기준

| 우선순위 | 의미 |
| --- | --- |
| `P0` | 없으면 MVP 핵심 흐름이 동작하지 않는 필수 작업 |
| `P1` | MVP 완성도와 사용성을 위해 필요한 작업 |
| `P2` | 있으면 좋지만 3주 안에 밀릴 수 있는 작업 |

## 5. 1주차 개발 계획: 기반 구축

1주차 목표는 실제 개발을 시작할 수 있는 기반을 만들고, 로그인 후 매장과 기본 화면까지 도달하는 것이다.

### 주요 목표

- Supabase 연결
- DB 테이블 생성
- 인증 흐름 구현
- React SPA 라우팅 구현
- 공통 레이아웃 구현
- 매장 선택 흐름 구현

## 6. 2주차 개발 계획: 근무표와 매장 운영 기능

2주차 목표는 사장님이 매장을 운영하기 위한 근무표와 알바생 관리 기능을 구현하는 것이다. 대타 요청은 근무표 데이터가 있어야 자연스럽게 연결되므로, 근무표 기능을 먼저 안정화한다.

- 월간 근무표 조회
- 일간 근무표 상세 조회
- 근무 일정 등록, 수정, 삭제
- 반복 근무 등록 기초
- 기본 급여 계산

| T-24 | P1 | 알바생 주요 화면 디자인 정리 |

### 2주차 완료 기준

- 사장님이 알바생의 매장별 정보를 등록할 수 있다.
- 월간 달력에서 근무 일정을 확인할 수 있다.
- 날짜를 클릭하면 일간 상세 화면으로 이동한다.
- 사장님이 근무 일정을 등록, 수정, 삭제할 수 있다.
- 알바생은 본인의 근무와 매장 근무 흐름을 확인할 수 있다.
- 기본 예상 급여가 화면에 표시된다.

## 7. 3주차 개발 계획: 공개 대타 요청 완성 및 QA

3주차 목표는 알바노트의 핵심 차별점인 공개 대타 요청 흐름을 완성하고, 발표 가능한 데모 상태로 다듬는 것이다.

- 공개 요청 목록 조회
- 대타 신청
- 먼저 신청한 알바생 후보 선정
- 사장님 승인/거절
- 승인 시 근무표 자동 변경
- 웹 내부 알림
- 핵심 QA와 데모 준비

### 3주차 완료 기준

- 같은 매장 알바생이 공개 요청에 신청할 수 있다.
- 가장 먼저 신청한 알바생만 후보로 선정된다.
- 사장님이 대타 요청을 승인하거나 거절할 수 있다.
- 승인된 대타 요청이 근무표에 반영된다.
- 핵심 알림이 생성되고 조회된다.
- 발표 시연용 계정과 시나리오가 준비된다.

3. 알바생 초대 및 시급 등록
4. 근무표 등록
5. 알바생 로그인
6. 월간 근무표 확인
7. 일간 근무표 상세 확인
8. 알바생이 공개 대타 요청 등록

10. 사장님이 대타 요청 승인

## 9. 리스크와 대응

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 혼자 개발하기에 기능 범위가 넓음 | 일정 지연 가능 | P0 작업을 먼저 끝내고 P1/P2는 유동적으로 조정한다. |
| Supabase Auth와 권한 구현이 예상보다 복잡함 | 로그인 이후 흐름 지연 | 1주차에 인증과 권한을 먼저 처리한다. |
| 대타 신청 동시성 처리가 까다로움 | 핵심 기능 신뢰도 저하 | Service Layer에서 상태 전이를 제한하고 DB 제약/트랜잭션을 우선 검토한다. |
| 디자인 정리에 시간이 많이 소요됨 | 기능 개발 시간 부족 | `Design.md`의 기존 규칙을 재사용하고 새 디자인 실험을 줄인다. |
| 반복 근무 구현 범위가 커질 수 있음 | 2주차 지연 가능 | MVP에서는 단순 주간 반복만 우선 구현한다. |

## 10. 우선순위 운영 원칙

- 1주차 말까지 인증과 매장 선택이 되지 않으면 2주차 기능을 줄인다.
- 2주차 말까지 근무표 등록/조회가 안정화되지 않으면 반복 근무를 축소한다.
- 3주차에는 새로운 기능 추가보다 대타 요청 흐름 완성과 QA를 우선한다.
- P2 작업은 P0와 P1이 안정적으로 끝난 경우에만 진행한다.
- 발표 데모에 직접 보이지 않는 기능은 과감히 후순위로 둔다.
