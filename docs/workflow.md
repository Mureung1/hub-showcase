# 나만의 워크플로우 정리

> 3주차 금요일 "워크플로우 정리와 발표" 미션 산출물. 3주 동안 AI(Claude Code)와 어떤 순서로 일했고, 어떤 Skill·Agent를 썼는지 정리한다.

## 기본 사이클

새 작업을 시작할 때마다 대체로 이 순서를 따랐다.

1. **데일리 미션 확인** — 그날의 공식 미션 PDF를 `docs/checklist.md`의 기존 계획과 대조해서, 이미 하기로 한 태스크 중 오늘 미션에 맞는 게 있는지 먼저 확인한다.
2. **이슈 먼저, 구현은 나중** — 새 기능이나 확장 작업은 구현 전에 GitHub 이슈로 먼저 등록한다(무엇을/왜 하는지, DoD, 목표일). Project 보드("3주차 - 자소서 초안 생성 슬라이스")에도 반영한다. 이렇게 하면 나중에 "이번 주에 뭘 했지"를 코드가 아니라 이슈 목록만 보고도 파악할 수 있다.
3. **설계 결정은 옵션을 좁혀서 나에게 확인** — 여러 방법이 있는 지점(예: 자소서 초안 API에 프로필을 어떻게 전달할지, 초안 저장 범위를 어디까지로 할지, vitest를 어떻게 도입할지)은 AI가 임의로 정하지 않고, 트레이드오프를 정리해서 나한테 확인받은 뒤 진행했다.
4. **작업 단위 쪼개기** — 체크리스트에 새 태스크를 넣거나 범위가 큰 기능을 시작할 때는 `planning-agent`로 요일별 작업 단위로 먼저 쪼갰다.
5. **구현** — 화면/스타일 작업은 `design-review` 스킬 기준(디자인 시스템 토큰)을 따르고, 테스트는 `test-writer` 스킬 컨벤션을 따랐다.
6. **검증은 대상에 따라 다르게** — 아래 "검증 방식" 참고.
7. **문서는 그때그때 갱신** — 기능이 끝나면 `docs/checklist.md`와 `README.md`를 미루지 않고 바로 그 자리에서 실제 상태에 맞게 고쳤다. 나중에 몰아서 하면 뭘 언제 했는지 기억이 안 나서 부정확해지기 때문이다.
8. **커밋·푸시는 명시적으로 요청받았을 때만** — AI가 알아서 커밋하지 않고, 매번 "커밋 푸시 해줘"라고 말했을 때만 진행하도록 규칙을 정했다.

## 쓴 Skill

- **design-review** — 새 화면이나 CSS를 만들 때 임의로 색상·간격·폰트 크기를 새로 정하지 않고, `docs/variables.css`에 이미 있는 디자인 토큰만 쓰도록 강제한다.
- **test-writer** — 백엔드 vitest 단위테스트(AAA 구조), 프론트 React 컴포넌트 테스트(Testing Library), 여러 화면을 가로지르는 Playwright E2E, 이 세 가지 중 어떤 상황에 어떤 방식을 쓸지 매번 새로 정하지 않고 하나의 컨벤션으로 통일했다.

## 쓴 Agent

- **planning-agent** — 체크리스트에 새 태스크(T-번호)를 시작하거나 새 기능/확장을 시작하기 전에, 요구사항을 요일별 작업 단위로 쪼개는 데 썼다. 예: 3주차 시작할 때 T9~T14 순서와 우선순위를 이걸로 먼저 정했다.
- **verification-agent** — 기능 구현이 끝난 직후, 커밋하기 전에 실제 앱을 브라우저(Playwright)나 curl로 직접 구동해서 진짜 Definition of Done을 충족하는지 확인하는 데 썼다. 코드를 읽고 "이러면 될 것 같다"고 판단하는 대신, 실제로 로그인하고 화면을 넘기면서 검증하게 했다.

## 검증 방식은 대상에 따라 다르게 가져갔다

- **순수 함수** (`essayAnalysis.js`의 문항 분석 로직처럼 입력→출력이 결정적인 코드)는 vitest 단위테스트로 TDD(RED→GREEN→REFACTOR)했다.
- **LLM 호출이나 Supabase처럼 외부 의존이 있는 코드**(`draftGeneration.js`, 자소서 초안 API 등)는 억지로 모킹해서 단위테스트를 만들지 않고, curl로 실제 요청을 보내 응답을 확인하는 방식으로 검증했다. 모킹된 테스트가 통과해도 실제 Claude API·Supabase 연동이 깨져 있으면 의미가 없다고 판단했기 때문이다.
- **여러 화면을 가로지르는 흐름**(로그인→입력→추천→상세→초안 생성)은 Playwright로 실제 브라우저를 띄워 전체 시나리오를 검증했다.

## 과정에서 교정한 것

- 목요일 "TDD로 기능 만들기" 미션에서, 원래 배운 절차는 "스펙과 시나리오 정하기 → RED → GREEN → REFACTOR" 네 단계인데, 처음엔 시나리오 표를 따로 정리하는 단계를 건너뛰고 바로 테스트 코드부터 썼다. 이후 수업자료를 다시 보고 "이 절차대로 하자"고 스스로 교정해서, 그다음부터는 테스트 코드를 쓰기 전에 입력→기대 결과→이유를 표로 먼저 정리하고 확인받는 단계를 넣었다.
- 배포처럼 AI가 통제할 수 없는 외부 요인(Vercel 계정 인증 오류로 배포가 막힌 상황)이 생겼을 때는, 그 문제가 풀릴 때까지 기다리기만 하지 않고 같은 시간에 다른 트랙(챌린지 공식 대시보드용 `showcase.json` 작성, 이슈 정리)을 병행해서 진행했다.

## 발표용 요약 (5분 내외)

1. **문제/핵심 기능** — 대학생 맞춤 공고 추천 + 자소서 초안 생성 Agent 서비스 (README 참고)
2. **3주간 한 일** — 1주차 기반 구축 → 2주차 추천 기능 → 3주차 자소서 초안 생성 + 확장(Supabase 영속화, 로그인 게이트, 배포)까지 계획보다 빠르게 끝내고 스코프를 넓혀감
3. **워크플로우 핵심 3가지**
   - 이슈 먼저, 구현은 나중 — 모든 작업이 GitHub 이슈+Project 보드로 추적됨
   - planning-agent로 쪼개고, verification-agent로 실제 동작을 검증 — 코드가 그럴듯해 보이는 것과 실제로 동작하는 것은 다르다
   - 문서(`checklist.md`/`README.md`)는 몰아서 하지 않고 그 자리에서 갱신
4. **어려웠던 점** — TDD 절차 중 시나리오 정리 단계를 건너뛴 것을 교정한 경험, 통제 불가능한 외부 요인(배포 계정 오류) 대응
5. **다음 주 계획** — 실제 채용 공고 크롤링(이슈 #23)으로 목업 데이터 대체, 데모데이 준비
