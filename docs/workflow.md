# 나만의 워크플로우 정리

> 3주차 금요일 "워크플로우 정리와 발표" 미션에서 처음 작성했고, 4주차(마지막 주) "서비스 배포와 Agent 협업 과정 발표" 미션(이슈 #28)에서 캠프 4주 전체를 다루도록 확장했다. AI(Claude Code)와 어떤 순서로 일했고, 어떤 Skill·Agent를 언제부터 왜 썼는지 정리한다. 다이어그램은 [README.md의 "Agent 협업 워크플로우"](../README.md#agent-협업-워크플로우) 참고.

## 4주 타임라인

- **1주차 — 기반 구축**: 기술스택(Vite+React, Express, Supabase, Claude API) 결정, 정보 입력 화면·목업 공고 데이터 작성. 아직 Skill/Agent 없이 일반적인 대화형 요청으로 진행.
- **2주차 — 공고 추천 기능**: 목표(추천 목록 화면)보다 앞서 공고 상세까지 완료. 이 주에 처음으로 `planning-agent`(계획 수립)·`verification-agent`(기능 검증) 서브에이전트를 직접 만들어 활용하기 시작 — curl+브라우저 E2E+서브에이전트 3중 검증 체계가 이때부터 자리잡았다.
- **3주차 — 자소서 초안 생성**: 본작업(T9~T16)을 계획보다 빠르게 끝내고 스코프를 넓힘(Supabase 영속 저장, 로그인 게이트, 배포, `profile` 재조회 구조 개선). `design-review`·`test-writer` 스킬을 이 주에 만들어 화면/테스트 컨벤션을 통일했고, 금요일에 처음으로 워크플로우 자체를 정리해봤다(이 문서의 시작).
- **4주차 — 최종 마무리(이번 주)**: 배포는 이미 끝난 상태에서, 실제 채용 공고 크롤링(이슈 #23, 화~수 완료)·데모 영상 제작(이슈 #27, 수요일 완료)·이 워크플로우 정리 확장(이슈 #28, 목요일)에 집중. 크롤링은 처음 계획했던 캐치(catch.co.kr) 대신 최종적으로 링커리어를 대상으로 확정했고(아래 "이번 주 의사결정" 참고), `verification-agent`로 실제 크롤링 데이터를 검증하는 과정에서 진짜 버그 여러 개(추천 매칭 로직이 실제 데이터 키워드 형식과 안 맞던 문제, 새로고침 시 초안 수정 내용이 되돌아가던 문제 등)를 찾아 그 자리에서 고쳤다. 데모 영상은 목소리 대신 자막만으로 만들었고, 그 과정도 아래 별도 섹션으로 정리했다.

## 배포 과정과 확인 기준

3주차 목~금요일에 실제로 겪은 배포 흐름이다. 이번 주(4주차) 공식 미션이 요구하는 "배포 과정과 확인 기준 정리"는 이미 지난주에 실전으로 겪은 내용이라 여기 그대로 옮긴다.

**배포 설정**
- **백엔드(Render)**: Web Service로 GitHub 연동, Root Directory `backend`, Build Command `npm install`, Start Command `npm start`, Region Singapore(한국 사용자 기준 지연 고려), Instance Type Free. 환경변수 5개(`SUPABASE_URL`/`SUPABASE_SERVICE_KEY`/`ANTHROPIC_API_KEY`/`APP_LOGIN_ID`/`APP_LOGIN_PASSWORD`) 등록.
- **프론트엔드(Vercel)**: Vite 프리셋 자동 인식, 환경변수 `VITE_API_BASE_URL`에 Render 주소 등록. Production Branch를 기본값 `main`에서 `work`로 수정 — `main`은 부트캠프 템플릿만 있는 stale 브랜치라 실제 코드(`package.json` 등)가 없어서, 처음엔 이 사실을 모르고 `main` 기준으로 배포를 시도했다가 빌드가 실패했다.

**확인 기준** (이번 주 미션의 "검증" 요구사항과 매칭)
1. FE 주소가 외부에서 열리는가 — 배포된 Vercel URL에 curl/브라우저로 직접 접속해 200 확인.
2. BE 상태 확인 API가 응답하는가 — 인증 없이 호출하면 401, 올바른 인증이면 200이 오는지 curl로 확인(로그인 게이트가 실제로 걸려 있는지까지 같이 검증).
3. 화면에서 보낸 요청이 DB 저장·조회까지 이어지는가 — 코드만 읽고 판단하지 않고 `verification-agent`로 프로덕션 URL 기준 로그인→정보입력→추천→상세→초안 생성 전체 흐름을 실제로 구동해 재검증.
4. 실패한 배포는 로그를 읽고 원인을 기록 — Render 로그에 뜨는 "No open ports detected, continuing to scan..."은 서버가 아직 부팅 중이라 뜨는 일시적 메시지이지 실패가 아니었다. 이후 "Your service is live"가 뜨는지까지 보고 진짜 성공/실패를 구분했다.

## 기본 사이클

새 작업을 시작할 때마다 대체로 이 순서를 따랐다.

1. **데일리 미션 확인** — 그날의 공식 미션 PDF를 `docs/checklist.md`의 기존 계획과 대조해서, 이미 하기로 한 태스크 중 오늘 미션에 맞는 게 있는지 먼저 확인한다.
2. **기능은 항상 수직 슬라이스(Vertical Slice) 단위로 정의** — "화면 UI를 만든다" 처럼 화면만 그럴듯한 수평적 정의 대신, "화면에서 요청 → 서버 처리 → DB 저장 → 응답 → 화면 반영"까지 한 바퀴가 실제로 도는 단위로 작업을 잡는다. 2주차는 정보입력→추천목록→상세, 3주차는 상세→자소서 초안 생성→저장까지가 각각 하나의 슬라이스였다. 이렇게 하면 "다 됐는지"를 눈으로 확인할 기준이 생긴다.
3. **이슈 먼저, 구현은 나중** — 새 기능이나 확장 작업은 구현 전에 GitHub 이슈로 먼저 등록한다(무엇을/왜 하는지, DoD, 목표일). Project 보드("3주차 - 자소서 초안 생성 슬라이스")에도 반영한다. 이렇게 하면 나중에 "이번 주에 뭘 했지"를 코드가 아니라 이슈 목록만 보고도 파악할 수 있다.
4. **작업 단위 쪼개기** — 체크리스트에 새 태스크를 넣거나 범위가 큰 기능을 시작할 때는 `planning-agent`로 요일별 작업 단위로 먼저 쪼갰다. 하나의 작업은 "명확한 한 문장 + 눈으로 확인 가능한 완료 기준"이 되도록 잡는다.
5. **구현 전 전략부터 검토, 코드는 그다음** — 이슈 하나를 집었을 때 바로 구현을 시키지 않고, 먼저 "어떻게 구현할지"를 확인한다 — 여러 방법이 있는 지점(예: 자소서 초안 API에 프로필을 어떻게 전달할지, 초안 저장 범위를 어디까지로 할지, vitest를 어떻게 도입할지, profile을 재전송할지 서버가 재조회할지)은 AI가 임의로 정하지 않고 트레이드오프를 정리해서 확인받은 뒤 진행했다. 판단 기준은 역할이 제자리에 있는지(화면 일은 화면에, DB 처리는 서버에), 기존 프로젝트 구조를 따르는지, 변경 범위가 필요한 만큼만인지였다.
6. **구현** — 화면/스타일 작업은 `design-review` 스킬 기준(디자인 시스템 토큰)을 따르고, 테스트는 `test-writer` 스킬 컨벤션을 따랐다.
7. **검증은 대상에 따라 다르게** — 아래 "검증 방식" 참고.
8. **문서는 그때그때 갱신** — 기능이 끝나면 `docs/checklist.md`와 `README.md`를 미루지 않고 바로 그 자리에서 실제 상태에 맞게 고쳤다. 나중에 몰아서 하면 뭘 언제 했는지 기억이 안 나서 부정확해지기 때문이다.
9. **커밋·푸시는 명시적으로 요청받았을 때만** — AI가 알아서 커밋하지 않고, 매번 "커밋 푸시 해줘"라고 말했을 때만 진행하도록 규칙을 정했다. 작은 단위로 자주 커밋해서, 문제가 생겨도 돌아갈 지점을 남긴다.

## 반복되는 작업 패턴 (입력 → 단계 → 검증 기준 → 산출물)

"기본 사이클"이 매번 따른 순서라면, 아래는 4주 동안 여러 번 반복된 작업 유형별로 실제 입력·단계·검증 기준·산출물을 정리한 것이다.

| 작업 유형 | 입력 | 단계 | 검증 기준 | 산출물 |
|---|---|---|---|---|
| **새 기능 슬라이스 개발** (예: 추천 목록, 자소서 초안 생성) | 이슈에 적힌 요구사항(무엇을/왜, DoD) | 이슈 등록 → planning-agent로 요일별 분해 → 구현 전 전략 확인 → 구현(design-review/test-writer) → 검증 → 문서화 | 화면 요청→서버 처리→DB 저장·조회→응답→화면 반영까지 한 바퀴가 실제로 도는가(수직 슬라이스 완료 기준) | 동작하는 화면/API + 테스트 코드 + 갱신된 `checklist.md`/README |
| **배포·재배포 확인** | 배포된 FE/BE 주소, 환경변수 목록 | 로그 확인("live" 여부) → curl로 인증·핵심 API 재현 → verification-agent로 브라우저 전체 흐름 재검증 | 배포 성공(빌드 통과)이 아니라 기능 성공(실제 요청→응답→DB 반영)까지 되는가 | curl/브라우저로 확인된 정상 응답, 실패 시 로그 기반 원인 기록 |
| **실제 크롤링 데이터 검증** | 크롤링 스크립트가 만든 실제 데이터 파일(`postings.json`) | 실제 데이터 샘플 직접 열람 → 기존 로직(매칭/초안 생성)에 그대로 통과시켜보기 → verification-agent로 브라우저 재현 | 목업 데이터가 아니라 실제 데이터 형식·분량 기준으로 동작하는가(키워드 형식, 문항 개수/글자수 등) | 발견한 실제 버그 목록 + 수정 커밋 + 재검증 로그 |
| **미디어(데모 영상) 제작** | 대본 초안, 실제 앱 녹화본 | 자동화 구간(Playwright 녹화) / 사람 판단 구간(슬라이드+자막 문구)을 분리 제작 → 사용자 확인 → ffmpeg로 조립 | 목표 시간(5분 미만)과 보안(로그인 정보 비노출)을 실측 기준으로 만족하는가 | 완성된 mp4 + `showcase.json`의 `demoVideoUrl` |

## 쓴 Skill

- **design-review** — 새 화면이나 CSS를 만들 때 임의로 색상·간격·폰트 크기를 새로 정하지 않고, `docs/variables.css`에 이미 있는 디자인 토큰만 쓰도록 강제한다.
- **test-writer** — 백엔드 vitest 단위테스트(AAA 구조), 프론트 React 컴포넌트 테스트(Testing Library), 여러 화면을 가로지르는 Playwright E2E, 이 세 가지 중 어떤 상황에 어떤 방식을 쓸지 매번 새로 정하지 않고 하나의 컨벤션으로 통일했다.

## 쓴 Agent

- **planning-agent** — 체크리스트에 새 태스크(T-번호)를 시작하거나 새 기능/확장을 시작하기 전에, 요구사항을 요일별 작업 단위로 쪼개는 데 썼다. 예: 3주차 시작할 때 T9~T14 순서와 우선순위를 이걸로 먼저 정했다.
- **verification-agent** — 기능 구현이 끝난 직후, 커밋하기 전에 실제 앱을 브라우저(Playwright)나 curl로 직접 구동해서 진짜 Definition of Done을 충족하는지 확인하는 데 썼다. 코드를 읽고 "이러면 될 것 같다"고 판단하는 대신, 실제로 로그인하고 화면을 넘기면서 검증하게 했다.

## 검증 방식은 대상(단위/통합/E2E)에 따라 다르게 가져갔다

- **단위 테스트** — 순수 함수(`essayAnalysis.js`의 문항 분석 로직처럼 입력→출력이 결정적인 코드)는 vitest로 TDD(스펙과 시나리오 정하기 → RED → GREEN → REFACTOR) 했다. `validate.js` 예시처럼 함수가 아직 없어 import 자체가 깨질 땐 스텁(빈 껍데기 함수)부터 만들어 RED를 정상적으로 보는 것부터 시작했다.
- **통합 테스트/curl** — LLM 호출이나 Supabase처럼 외부 의존이 있는 코드(`draftGeneration.js`, 자소서 초안 API 등)는 억지로 모킹해서 단위테스트를 만들지 않고, curl로 실제 요청을 보내 응답을 확인했다. 모킹된 테스트가 통과해도 실제 Claude API·Supabase 연동이 깨져 있으면 의미가 없다고 판단했기 때문이다.
- **E2E** — 여러 화면을 가로지르는 흐름(로그인→입력→추천→상세→초안 생성)은 Playwright로 실제 브라우저를 띄워 전체 시나리오를 검증했다. 기능을 고친 뒤에는 관련 화면을 다시 통과시켜 회귀(기존 기능이 깨지지 않았는지)까지 같이 확인했다.
- 전부 TDD로 만들지는 않았다 — 검증·계산처럼 규칙이 분명한 로직은 TDD로, 화면/디자인처럼 눈으로 확인하는 게 더 빠른 영역은 TDD 대상에서 제외하고 Playwright/verification-agent로 확인했다.

## 과정에서 교정한 것

- 목요일 "TDD로 기능 만들기" 미션에서, 원래 배운 절차는 "스펙과 시나리오 정하기 → RED → GREEN → REFACTOR" 네 단계인데, 처음엔 시나리오 표를 따로 정리하는 단계를 건너뛰고 바로 테스트 코드부터 썼다. 이후 수업자료를 다시 보고 "이 절차대로 하자"고 스스로 교정해서, 그다음부터는 테스트 코드를 쓰기 전에 입력→기대 결과→이유를 표로 먼저 정리하고 확인받는 단계를 넣었다.
- 배포처럼 AI가 통제할 수 없는 외부 요인(Vercel 계정 인증 오류로 배포가 막힌 상황)이 생겼을 때는, 그 문제가 풀릴 때까지 기다리기만 하지 않고 같은 시간에 다른 트랙(챌린지 공식 대시보드용 `showcase.json` 작성, 이슈 정리)을 병행해서 진행했다.

## 문제가 생겼을 때 다시 확인하는 단계

같은 종류의 문제가 반복될 때마다 매번 처음부터 원인을 찾지 않도록, 지금까지 겪은 문제 유형별로 먼저 확인하는 순서를 정리했다.

1. **배포된 화면/API가 이상하게 동작할 때**
   - Render 로그부터 확인 — "No open ports detected, continuing to scan..."은 부팅 중 정상 메시지이므로, "Your service is live"가 떴는지까지 봐야 진짜 실패인지 알 수 있다.
   - 환경변수(`SUPABASE_URL`/`SUPABASE_SERVICE_KEY`/`ANTHROPIC_API_KEY`/`APP_LOGIN_ID`/`APP_LOGIN_PASSWORD`, 프론트의 `VITE_API_BASE_URL`)가 실제 배포 환경에 등록돼 있는지 먼저 확인 — 로컬에서는 되는데 배포에서만 안 되면 대부분 이쪽 문제였다.
   - Vercel의 Production Branch가 실제 코드가 있는 브랜치(`work`)로 잡혀 있는지 확인 — `main`은 코드가 없는 stale 브랜치라 여기 배포하면 빌드부터 실패한다.
   - 코드를 읽고 "이러면 될 것 같다"로 끝내지 않고, `verification-agent`로 실제 배포 주소에 curl/브라우저로 다시 접속해 확인한다.
2. **크롤링한 실제 데이터로 기능이 이상하게 동작할 때**
   - 목업 데이터를 가정하고 짠 로직(매칭 키워드 형식, 자소서 문항 개수/글자수 가정)이 실제 데이터 형식과 다른 경우가 많으므로, 실제 데이터 샘플 1~2건을 직접 열어 필드 형식을 눈으로 다시 확인한다.
   - 재크롤링 이후 문제라면 공고 id가 안정적으로 유지됐는지(크롤링 순서가 아니라 원본 사이트의 고유 id를 쓰고 있는지) 먼저 의심한다.
3. **영상/미디어 파일 작업(ffmpeg 등)에서 특정 구간만 이상할 때**
   - 전체를 다시 만들기 전에, 문제되는 구간만 최소 단위로 떼어내 재현되는지 먼저 확인한다(같은 스타일의 다른 구간은 정상인지 대조).
   - 내용(텍스트) 문제인지 방식(필터/인코딩) 문제인지 구분하기 위해 내용을 단순한 값으로 바꿔서 같은 문제가 재현되는지 본다.
   - 원인을 못 찾은 채 다른 방법으로 우회하지 않고, 재현 조건을 좁힌 뒤 방식을 바꾼다.
4. **문서(`checklist.md`/`workflow.md`/README)가 실제 상태와 달라 보일 때**
   - 최종적으로 무엇을 했는지는 코드/커밋 로그가 기준이고, 문서는 그걸 옮겨 적은 결과물이라는 걸 기억한다 — 계획 당시 문서(예: 크롤링 대상 후보 검토)와 실제 구현 결과가 달라졌다면, 계획 문서를 지우지 말고 "왜 바뀌었는지"까지 남기고 최종 상태를 반영한 문단을 새로 추가한다.

## 이번 주(4주차) 의사결정 — 크롤링 대상/범위

- **대상 사이트 선정 과정에서 계획이 실제로 바뀐 사례**: 처음엔 robots.txt를 실제로 확인해서 캐치(catch.co.kr)를 후보로 잡았다(잡코리아는 Claude 계열 봇을 명시 차단, 사람인은 접근 자체가 봇 차단 페이지로 리다이렉트되어 둘 다 배제). 하지만 실제 구현 단계에서 링커리어(linkareer.com)의 공고 상세 페이지를 열어보니, 화면에 렌더링되는 HTML을 파싱할 필요 없이 페이지에 이미 `__NEXT_DATA__`라는 `<script>` 태그로 그 페이지의 전체 데이터가 JSON으로 그대로 박혀 있는 걸 발견했다 — 여기엔 로그인 없이도 실제 자소서 문항 전문과 글자수 제한까지 포함돼 있었다. 그래서 최종 크롤링 대상은 캐치가 아니라 링커리어로 바뀌었다. 계획 문서(`docs/crawling-plan.md`)에 이 판단 과정을 남기고, 실제 스크립트(`backend/scripts/crawlPostings.mjs`, `backend/scripts/lib/linkareer.js`)는 그 문서 그대로 구현했다.
- **로그인 게이트 우회는 여전히 하지 않음**: 링커리어로 대상이 바뀐 뒤에도 "로그인 게이트가 있는 페이지는 자동화로 우회하지 않는다"는 원칙 자체는 그대로 유지했다 — 다만 링커리어는 채용/인턴 카테고리의 자소서 문항을 애초에 로그인 없이 공개하고 있어서, 이번엔 이 원칙 때문에 못 가져온 필드가 없었다. 원칙은 사이트가 바뀌어도 그대로 지키되, 실제로 막히는지는 매번 다시 확인해야 한다는 걸 확인한 사례다.
- **데이터 품질 필터를 추가로 판단**: 실제로 100건을 긁어보니 링커리어 자체의 내부 테스트용 공고("테스트입니다" 류)가 섞여 있었고, 일부 공고는 자소서 문항이 6개를 넘거나 전체 글자수가 지나치게 많아 초안 생성 시 토큰 예산을 넘길 위험이 있었다. 둘 다 크롤링 스크립트 단계에서 `isTestPosting`/`hasReasonableEssayLoad` 필터로 걸러내기로 했다 — 사용자가 실제로 마주칠 데이터라서, 화면이나 백엔드 로직이 아니라 데이터 소스 단계에서 막는 게 맞다고 판단했다.
- **공고 id를 크롤링 순서가 아니라 링커리어의 실제 `activity.id`로 고정**: 처음엔 크롤링한 순서대로 1부터 번호를 매겼는데, 재크롤링하면 같은 공고라도 순서가 바뀌면서 번호가 달라져 Supabase에 이미 저장된 자소서 초안(`drafts` 테이블, `posting_id`로 연결)이 엉뚱한 공고를 가리키게 되는 문제를 뒤늦게 발견했다. 링커리어가 각 공고에 부여한 고유하고 영구적인 `activity.id`를 그대로 스키마의 `id`로 쓰도록 바꿔서, 재크롤링해도 기존 저장된 초안이 깨지지 않게 했다.
- **그래도 공고가 없어지는 경우(폐지된 공고)는 자동 삭제하지 않기로 결정**: 재크롤링 후 특정 공고가 더 이상 존재하지 않아 그 공고에 연결된 초안이 "고아"가 될 수 있는데, 이 초안들을 자동으로 지우는 건 사용자가 공들여 쓴 데이터를 되돌릴 수 없이 없애는 파괴적인 조치라고 판단해 보류했다. 대신 그 공고를 열려고 할 때 뜨는 404 메시지를 "이 공고는 더 이상 제공되지 않아요. 목록으로 돌아가서 다른 공고를 확인해주세요."처럼 사용자가 이해할 수 있게 바꾸는 선에서 마무리했다.

## 이번 주 데모 영상 제작 과정(이슈 #27)

목소리 녹음 대신 자막만으로 5분 미만 데모 영상을 만들었다. 이 작업은 다른 태스크와 달리 "코드가 맞다/틀리다"가 아니라 결과물(영상)의 내용·톤·타이밍을 사용자가 직접 눈으로 보고 계속 다듬어야 하는 작업이라, 협업 방식 자체가 달랐다.

- **자동화로 만든 것과 사람이 검토한 것을 분리**: 실제 앱 화면 시연 구간은 Playwright로 로그인부터 정보입력→추천목록→상세→초안 생성·저장까지 실제 조작을 자동 재생하며 녹화했고(`record_video_dir`), 서비스 소개/기술적 특징/Agent 활용 방식 구간은 python-pptx로 만든 슬라이드에 문장 단위 자막을 입혀 별도 영상으로 만든 뒤 하나로 이어붙였다. 자동화가 잘하는 부분(반복 조작, 정확한 타이밍 계산)과 사람이 판단해야 하는 부분(어떤 내용을 말할지, 톤이 자연스러운지)을 나눠서 진행했다.
- **영상 녹화처럼 되돌리기 어려운 작업은 시작 전에 반드시 확인받기로 함**: 녹화·영상 조립처럼 한번 만들면 다시 찍거나 처음부터 다시 이어붙여야 하는 작업은, 사용자가 "영상 녹화 시작은 나에게 물어보고 해", "영상 만들기 전에 내가 다시 확인할게"라고 명시적으로 요청한 뒤로는 매번 시작 전에 확인받았다. 코드 커밋과 마찬가지로, 비용이 크고 되돌리기 어려운 작업은 자동으로 진행하지 않는다는 원칙이 영상 작업에도 그대로 적용된 사례다.
- **보안 문제를 사용자가 먼저 발견하고 고침**: 첫 녹화본에 로그인 화면이 그대로 담겨 실제 로그인 아이디가 화면에 노출된 걸 사용자가 확인 과정에서 발견했다. 녹화 파일에서 정보입력 화면이 시작되는 시점을 정확히 찾아 그 이전 구간을 잘라내고, 잘린 만큼 모든 자막 타이밍도 같이 앞으로 당겨서 다시 동기화했다.
- **디버깅은 추측하지 않고 원인을 좁혀가며 확인**: 특정 자막 한 줄만 화면에 렌더링되지 않는 문제가 있었는데, 내용을 바꿔보고(평범한 영문 텍스트로 교체) 별도 파일로 최소 재현을 만들어보는 식으로 하나씩 원인을 제거해가며 확인했다. 결국 특정 자막 렌더링 방식(`subtitles`/`.ass` 자막 필터) 자체의 문제로 좁혀져서, 더 안정적으로 동작하는 다른 방식(`drawtext` 필터)으로 전체를 바꿔 해결했다 — 원인을 특정하지 못한 채로 "이 방법이 왜 안 되는지 몰라도 다른 방법으로 우회"하지 않고, 재현 가능한 최소 단위까지 좁힌 뒤에 방식을 바꿨다.
- **목표 시간(5분 미만)에 맞추는 것도 눈대중이 아니라 실측 기준으로**: 자막 표시 속도를 조절할 때, 초기엔 대본 분량으로 대략 추정한 시간을 썼다가 실제 렌더링된 영상 파일들의 길이를 ffmpeg로 직접 측정해 이 값과 어긋나는 걸 사용자가 지적했다. 이후로는 항상 실제 파일 길이를 기준으로 목표 시간(4분 30초)에 맞춰 자막 속도(글자당 시간)를 역산했다.

## Supabase는 서버 전용 키로, 계층은 프로젝트 규모에 맞게

- **키 관리** — 브라우저에서 직접 Supabase를 부르지 않고 항상 Express(`backend/`)를 거친다. `SUPABASE_SERVICE_KEY`(`service_role` 키)는 서버 환경변수(`backend/.env`, gitignored)로만 관리하고 프론트에는 절대 넣지 않는다. 접근 통제를 서버가 하므로 RLS(Row Level Security)를 깊게 다루지 않아도 조회·저장이 된다 — 수업자료에서 설명한 "서버 경유 연결" 구조 그대로다.
- **계층 분리, 단 프로젝트 규모에 맞게** — 수업자료의 예시는 Router/Controller/Service 3계층으로 나누지만, 이 프로젝트는 `routes/*.js`가 라우팅+요청 검증(Router+Controller 역할)을 같이 하고 `services/*.js`(`matching.js`, `claude.js`, `essayAnalysis.js`, `draftGeneration.js`)가 실제 DB/LLM 호출을 맡는 2계층으로 단순화했다. "기존 구조를 따르는지" 기준으로 봤을 때, 지금 규모(라우트 3개)에서 Controller를 따로 떼는 건 오히려 파일만 늘리는 과한 분리라고 판단했기 때문이다.
- **Supabase client** — `backend/src/lib/supabaseClient.js` 하나에서 `createClient(SUPABASE_URL, SUPABASE_SERVICE_KEY)`로 연결 객체를 만들고, 각 서비스/라우트가 이걸 `import`해서 `.from(테이블명).select()/.insert()/.upsert()`로 쓴다 — ORM 없이 쿼리 빌더 방식 그대로.

## 이번 주 다룬 것과 연결되는 개발 개념

3주차 수업자료("설계하고 작업나누기", "테스트코드이해")가 정리해준 대로, 이번 주 실제로 한 일들을 기존 개발 개념 이름과 연결하면:

| 이번 주 한 일 | 연결되는 개념 |
|---|---|
| 화면→서버→DB→화면 한 바퀴 단위로 기능 정의 | 수직 슬라이스(Vertical Slice), 사용자 스토리 |
| 이슈에 DoD(완료 기준)를 먼저 적고 시작 | 인수 기준(Acceptance Criteria), Definition of Done |
| 구현 전에 전략·트레이드오프를 먼저 확인 | 설계 리뷰 |
| 라우트(`routes/`)·서비스(`services/`)·DB 클라이언트(`lib/supabaseClient.js`)를 역할별로 분리 | 관심사의 분리(Separation of Concerns) |
| 작업 하나 끝날 때마다 커밋 | 버전 관리, 점진적 개발 |
| vitest(단위) · curl(통합) · Playwright(E2E)를 대상에 맞게 구분 | 테스트 피라미드 |
| 기능 유지한 채 `postJson` 헬퍼로 중복 제거 등 | 리팩토링(Refactoring) |

## 4주차 학습자료와 연결되는 개념

4주차 학습자료("배포와 발표")가 정리한 개념과 이번 주 실제로 한 일을 연결하면:

## 발표용 요약

1. **문제/핵심 기능** — 대학생 맞춤 공고 추천 + 자소서 초안 생성 Agent 서비스 (README 참고)
2. **4주간 한 일** — 1주차 기반 구축 → 2주차 추천 기능(planning-agent·verification-agent 도입) → 3주차 자소서 초안 생성(T9~T16) + 확장(Supabase 영속화, 로그인 게이트, 배포) → 4주차 실제 링커리어 크롤링(이슈 #23)·자막 기반 데모 영상 제작(이슈 #27)·워크플로우 정리(이슈 #28)까지 완료
3. **워크플로우 핵심 4가지**
   - 기능은 항상 수직 슬라이스 단위로 정의 — 화면 UI만이 아니라 화면→서버→DB→화면까지 한 바퀴가 실제로 도는 것을 완료 기준으로 삼음
   - 이슈 먼저, 구현은 나중 — 모든 작업이 GitHub 이슈+Project 보드로 추적됨
   - 구현 전에 전략·트레이드오프를 먼저 확인하고, planning-agent로 쪼개고, verification-agent로 실제 동작을 검증 — 코드가 그럴듯해 보이는 것과 실제로 동작하는 것은 다르다
   - 문서(`checklist.md`/`README.md`)는 몰아서 하지 않고 그 자리에서 갱신
4. **어려웠던 점** — TDD 절차 중 시나리오 정리 단계를 건너뛴 것을 교정한 경험, 통제 불가능한 외부 요인(배포 계정 오류) 대응, 크롤링 중 로그인 우회 여부를 판단해야 했던 경험, 크롤링 대상 사이트를 계획(캐치) 대비 실제 구현 단계에서 링커리어로 바꾼 경험, 데모 영상에서 특정 자막만 렌더링되지 않던 문제를 최소 재현으로 좁혀 원인을 찾은 경험
5. **남은 일** — 4주 과정에서 계획했던 핵심 기능·크롤링·데모 영상 제출은 모두 완료된 상태. 마지막 날(4주차 목요일)은 새 기능을 추가하지 않고, 이미 정한 데모 흐름을 실제 배포 주소에서 안정적으로 재현하는 것과 이 워크플로우 문서·Agent 협업 다이어그램을 최종 상태에 맞게 정리하는 것만 남았다.
