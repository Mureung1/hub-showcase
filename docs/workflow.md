# 나만의 워크플로우

4주간 기획서(`plan.md`) → 체크리스트(`checklist.md`) → 주간 계획(`weekly-plan.md`) → PR(`.github/pull_request_template.md`)로 이어진 작업과, 실제 커밋 히스토리를 되짚어 보니 반복해서 쓴 작업 순서는 크게 두 갈래였다. 하나는 **새 기능을 처음부터 만들 때**(2~3주차, 매칭 알고리즘·동행 신청 플로우), 다른 하나는 **이미 동작하는 화면에서 신고된 문제를 고칠 때**(4주차 대부분)다. 둘을 하나로 뭉뚱그리면 실제와 안 맞아서 따로 적는다.

## 워크플로우 A — 새 기능 개발 (계획 → TDD → 배선 → 검증)

핵심 기능 2개(매칭 알고리즘, 동행 신청/수락 플로우)와 탑승 확인·평점 시스템처럼 로직이 복잡한 기능에 쓴 순서.

| 단계 | 내용 |
|---|---|
| 1. 입력 | 기능 요구사항 한 줄 (예: "같은 거점 조합 + 희망 시간 ±15분 이내 후보를 보여준다") |
| 2. 작업 순서 | ① `feature-slice` 스킬로 하루 단위 작업 + 완료 기준으로 쪼갬 → ② 순수 함수로 로직 분리(`server/matching.js`, `describeCost.js`) → ③ Vitest로 Red(실패 테스트) 먼저 작성 → Green(구현) → ④ Express 라우트/React 컴포넌트에 배선 → ⑤ `vertical-slice-verifier` 에이전트로 실서버·실DB 검증 |
| 3. 확인 기준 | `npm test`(server) 통과 + 에이전트가 curl로 실제 요청/응답을 찍어 PASS/FAIL 보고 |
| 4. 결과물 | 통과하는 테스트 파일(`*.test.js`) + 동작하는 API/화면 + 커밋 |

**문제가 생겼을 때 재확인 순서**
1. 테스트가 실패하면 — 순수 함수(`matching.js` 등)만 먼저 의심. 라우트/DB보다 로직이 원인일 확률이 높음.
2. 테스트는 통과하는데 화면에서 안 되면 — 배선 문제(라우트 순서, camelCase/snake_case 필드명 불일치)를 의심. `vertical-slice-verifier`의 5번째 절차(silent data problem 체크)가 이 케이스용.
3. 그래도 안 풀리면 — `docs/plan.md`의 시나리오로 돌아가 "이 기능이 실제로 해결하려는 문제가 뭐였는지"부터 다시 확인.

## 워크플로우 B — 버그 수정 (재현 → 근본 원인 → 수정 → 라이브 검증)

4주차에 가장 많이 반복한 순서. 사용자가 스크린샷/증상으로 문제를 알려주면 시작됨.

| 단계 | 내용 |
|---|---|
| 1. 입력 | 증상 설명 또는 스크린샷 (예: "방 만들고 뒤로가기 하면 인원이 0/4로 보여") |
| 2. 작업 순서 | ① 관련 코드를 직접 읽고 가설 세움 → ② Node 스크립트(서비스 롤 키 + `signInAnonymously()`로 테스트 계정 생성)나 실제 브라우저 조작으로 **직접 재현** → ③ 가설이 맞는지 재현 결과로 확인 → ④ 코드 수정 → ⑤ 같은 방식으로 다시 재현해 고쳐졌는지 확인 → ⑥ 테스트 계정/데이터 정리 |
| 3. 확인 기준 | 수정 전 재현 결과와 수정 후 재현 결과를 나란히 비교해서 "이전엔 X가 나왔는데 지금은 Y가 나온다"를 눈으로 확인 |
| 4. 결과물 | 커밋(원인 한 줄 요약 포함) + 정리된 테스트 데이터 (남겨두면 다음 조회에 고아 데이터로 다시 나타남) |

**문제가 생겼을 때 재확인 순서**
1. 가설대로 고쳤는데 재현이 안 풀리면 — 가설 자체가 틀렸을 가능성. 관련된 다른 라우트(`join`/`create-room`/`leave`처럼 같은 상태를 건드리는 다른 엔드포인트)를 마저 읽고 상태가 어디서 바뀌는지 전체 흐름을 다시 그림.
2. 서버 스크립트가 `ECONNREFUSED`로 실패하면 — 백엔드(포트 4000)가 안 떠 있는 것. 프론트/백 두 서버를 각각 켜야 하는 모노레포 구조라 이 실수가 반복됨.
3. 브라우저 조작(`computer` 클릭)이 반응 없으면 — 좌표 클릭 대신 `javascript_tool`로 버튼을 텍스트로 찾아 `.click()` 실행. 새로 렌더링된 화면에서 좌표 클릭이 자주 씹히는 문제가 이 프로젝트에서 반복 확인됨.
4. 테스트 계정을 지우는 걸 잊으면 — 다음 후보 목록 조회 때 "고아 데이터"로 다시 나타남(과거에 실제로 이 문제로 35개가 쌓였었음). 수정 검증이 끝나면 반드시 `matching_requests`/`users`/`auth.users` 세 곳 모두 정리.

## 두 워크플로우의 공통점
- 코드를 고치기 전에 항상 **실제로 재현하거나 테스트를 먼저 실패시켜서**, "고쳤다고 주장하는 것"과 "실제로 고쳐진 것"을 구분함.
- 수정 후에도 같은 방법으로 다시 확인해서, 눈으로 비교 가능한 before/after를 남김.
- PR에는 `.github/pull_request_template.md`의 "내가 설명할 수 있는 부분 / 아직 이해 못 한 부분 / 새로 알게 된 것"을 채워 회고를 남김 — 매주 반복.
