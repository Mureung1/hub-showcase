# AI Agent와의 협업 워크플로우 (잔소리봇, 3주차 기준)

## 핵심 메시지

AI에게 계획과 구현을 맡기되, 실제 코드·테스트·데이터 흐름을 다시 확인하고
다른 도구로 교차 검증한 뒤에만 다음 단계로 넘어갔다.

## 1. 전체 작업 흐름

1. **feature-slice**(계획) — 요구사항을 GitHub Issue 단위(하루 안에 끝낼 크기)로 분해, 우선순위·완료기준 제안
2. **TDD 여부 판단**(simple-tdd) — `lib/**` 순수 함수면 Red(스텁+실패)에서 멈춰 확인받고 Green으로
3. **구현**
4. **검증** — Playwright(UI 흐름), curl·supertest(API), 실제 실행 결과로 확인
5. **code-review** — 컨벤션·패턴·에러처리·테스트 유무를 정적으로 점검하고 수정 제안만 제공
6. **이슈 close**
7. **커밋** — Conventional Commits 축약형 + 한글 설명

## 2. Skill/Agent 목록과 역할

| 이름               | 역할                                                                                                 | 코드 수정        |
| ------------------ | ---------------------------------------------------------------------------------------------------- | ---------------- |
| feature-slice      | 요구사항 → 이슈 단위 작업 분해                                                                       | 안 함            |
| feature-verify     | 이슈 번호 기준 요구사항 대비 실동작 검증(Playwright)                                                 | 안 함            |
| code-review        | 컨벤션·패턴·에러처리·테스트 정적 점검                                                                | 안 함            |
| test-writer        | `lib/**`=Vitest 단위, `routes/**`=supertest 통합 테스트 규칙 + DB 가드(prefix/teardown/DATABASE_URL) | 테스트 코드만    |
| simple-tdd         | 순수 함수 신규 작성 시 스펙표→Red→Green→Refactor, 단계별 확인                                        | 테스트·구현 수행 |
| nagging-bot-design | 확정된 디자인 톤(색/레이아웃/타이포) 적용                                                            | 스타일만         |

이 목록 자체가 목적이 아니라, 각 Skill/Agent는 "AI 제안을 검증 없이 통과시키지 않기 위한" 체크포인트로 기능한다.

## 3. AI 제안을 그대로 받지 않고 검증한 사례

**사례 1 — DB 직접 조작 제안 거절**
완료 상태만 직접 수정하면 대응 TaskEvent가 없어 History가 어긋날 수 있다는 점을 확인했다. 이후 개발 DB도 반드시 실제 API 경로로만 조작한다는 원칙을 세웠다.

**사례 2 — #29 중복 이슈 판단**
`lib/nudge.ts`를 새로 만드는 이슈(#29)가 계획서에 있었지만, 확인해보니 #23~#28에서 `nudgeMessages.js`/`buildNudgeMessage()`로 이미 통합 구현돼 있었다. 새 파일을 만들자는 제안 대신 기존 구현을 먼저 확인하고 중복 close 처리했다.

**사례 3 — 알림 간격 설계 기준 재검토**
최초 검토안은 "할일 유형별 기본 간격"(시험공부/리포트마다 다른 고정값)이었는데, 이 기준이 근거 없는 임의 가정이라는 걸 확인하고 "마감 긴급도(D-day) × 현재 레벨" 조합으로 바꿔 `src/lib/nudgeInterval.ts`로 확정했다(#44).

## 4. Claude Code와 Codex를 함께 쓴 방식

고정 역할 분담보다 교차 검증을 중심으로 활용했다. 한 도구가 만든 코드와 완료 보고서를 다른 도구에 넘겨 실제 파일·테스트·데이터 흐름을 다시 확인했다.

예를 들어 STEP3 이후 Gemini 연동, 완료 기록 컨텍스트 구조, Focus 전달 경로는 Codex가 진행하고 인수인계 문서를 작성했다. 이 문서를 그대로 신뢰하지 않고 Claude Code로 넘겨 세션 마이그레이션, 중복 완료 멱등성 등 핵심 불변식 10개가 실제 코드와 일치하는지 파일·라인 단위로 확인한 뒤 다음 단계로 진행했다.

## 5. 이번 주 시행착오 (Trial & Error)

**사례 A — 통합 테스트 DB 가드가 실제로는 뚫려 있던 문제**

- **상황**: `routes/**` 통합 테스트는 `server/.env.test`가 없으면 실행을 skip하도록 설계돼 있었다(안전 기본값).
- **발견**: 테스트 설정이 개발용 `.env`를 읽을 수 있어, 테스트 DB가 없는데도 개발 DB가 연결된 것처럼 판단할 가능성이 있었다.
- **수정**: 테스트 전용 환경파일만 직접 읽고, 없으면 DB 주소를 빈 값으로 강제해 개발 DB 접근을 차단했다.

**사례 B — 데이터가 사라진 것처럼 보인 미스터리**

- **상황**: 특정 task가 STEP 검증 중 반복적으로 화면에서 사라진 것처럼 보임.
- **발견**: 삭제된 적이 없고, DB를 직접 편집(`status: done`)하면서 대응 `TaskEvent`가 누락돼 event-log 기반 뷰에서 안 보인 것.
- **수정**: "DB는 항상 정상 API 경로로만 조작" 원칙 수립(3번 사례 1과 동일 사건).

## 6. 이번 주에 정리한 원칙

- AI의 완료 보고서는 증거가 아니라 검증 대상이다.
- DB는 실제 API 경로로만 변경한다.
- 근거 없는 기준보다 사용자 문제와 데이터 흐름을 기준으로 설계한다.
- 큰 작업은 하루 안에 끝낼 수 있는 수직 슬라이스로 나눈다.
