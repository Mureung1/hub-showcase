# 나의 AI 워크플로우 (2~3주차 기준)

3주 동안 AI(Claude Code)와 어떤 순서로 일했는지, 어떤 Skill/Agent를 언제 썼는지 정리한다.

## 1. 전체 흐름

### ① 주간 계획 수립 (월요일 오전)
- 이번 주 공식 목표를 확인한다.
- [계획 수립 Agent](agents/planning-agent.md)에게 요구사항을 주고 작업 단위로 쪼갠 결과를 받는다.
- Agent 결과를 그대로 쓰지 않는다 — 직접 짠 백로그와 비교해서 빠진 것·과한 것을 조정한다.
  (예: 3주차엔 Agent의 FE/BE/DB 고정 카테고리가 테스트/문서/Agent 산출물 같은
  이질적인 작업엔 안 맞는다는 걸 발견해서, Agent 문서의 처리 절차 자체를 고쳤다.)
- 우선순위(P0/P1/P2)를 매기고 요일에 배치한 뒤 GitHub 이슈로 등록한다.

### ② 기능 하나씩 진행 (화~목)
- 코드부터 쓰지 않는다. **화면 → 데이터 → 흐름** 순서로 먼저 설계하고, 이슈에 기록한다.
- 완료 기준(체크 가능한 조건)을 미리 정해둔다 — "됐다"를 판단할 기준이 없으면 끝을 알 수 없기 때문.
- 조건 분기나 계산이 있는 순수 함수는 [테스트코드 생성 Skill](../.claude/skills/tidenote-test-writer/SKILL.md)로
  시나리오 표부터 정리하고, red(실패 확인) → green(통과) 순서로 만든다.
  화면(UI)이나 디자인은 TDD 대상에서 뺀다 — 눈으로 보는 게 더 빠르다.

### ③ 검증 (기능 완료할 때마다)
두 가지 검증을 구분해서 쓴다.

| | [기능 검증 Agent](agents/verification-agent.md) | [코드 검증 Agent](agents/code-verification-agent.md) |
|---|---|---|
| 질문 | 요구사항대로 동작하는가? | 코드가 유지보수 가능한 상태인가? |
| 방법 | curl, 브라우저 직접 조작 | 코드 읽기, 테스트 실행 |

두 Agent 모두 "코드가 맞아 보인다"는 이유로 pass를 주지 않는다 — 반드시 실행해서 확인한다.
(예: 에러 처리 기능은 실제로 서버를 꺼서 네트워크 에러를 재현하고, 다시 켜서 재시도가
성공하는 것까지 확인한 뒤에야 완료로 표시했다.)

### ④ 커밋 / PR
- 하루 작업 단위로 브랜치를 나눈다.
- PR 본문에 주요 작업 리스트와 함께, "내가 설명할 수 있는 부분 / 아직 이해 못 한 부분 /
  새로 알게 된 것" 세 가지를 남긴다 — AI가 짠 코드를 내 말로 설명할 수 있는지 스스로 점검하는 장치.

| 이름 | 만든 시점 | 역할 |
|---|---|---|
| 계획 수립 Agent | 2주차 | 요구사항을 작업 단위로 나누고 우선순위·순서를 정함 |
| 기능 검증 Agent | 2주차 | 완료 기준을 실제 실행해서 pass/fail 판정 |

| 코드 검증 Agent | 3주차 | 최근 변경분의 테스트 존재 여부·버그·스타일 점검 |

## 3. 이번 3주에서 배운 것

- **Agent 결과를 그대로 밀어붙이지 않는 습관이 실제로 도움이 됐다.** 계획 수립 Agent가
  놓친 요일 배치, 스코프 확장(에러 처리 등)은 매번 사람이 채워야 했다.
- **공식 미션과 내 백로그가 어긋날 때, 임의로 판단하지 않고 매번 확인받고 진행했다.**
  어느 쪽을 우선할지는 코스 진행 상황을 아는 사람이 정해야 하는 문제였다.
- **"실행해서 확인"이 진짜로 버그를 잡는다.** GET 요청이 404를 줬을 때 이걸 그냥
  에러로 처리했다면, 첫 사용자가 처음 앱을 열자마자 에러 문구를 보게 됐을 것이다.
  실제로 서버를 꺼보고 나서야 이 케이스를 발견했다.
- **디자인 스펙은 한 번에 안 맞는다.** Figma 슬라이더 하나를 실제 스펙에 맞게
  구현하는 데 여러 차례 피드백을 주고받았다 — union+blur, progressive blur처럼
  텍스트로 설명하기 어려운 디테일은 스크린샷과 실제 export 코드를 같이 받아야
  정확하게 구현할 수 있었다.
