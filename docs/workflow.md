# 나만의 워크플로우 (하소AI, 4주 회고)

4주간의 계획서·백로그·커밋 로그·Claude Code 사용 기록을 되짚어, 반복해서 썼던 작업 순서 두 가지를 정리했다. 새 기능을 추가할 때는 워크플로우 A를, 배포 후 문제가 생겼을 때는 워크플로우 B를 그대로 따라가면 된다.

---

## 워크플로우 A — API/기능 연동

**언제 쓰나**: 새 외부 API(날씨, 공휴일, GPT, GPT Image)를 붙이거나 프론트-백엔드를 새로 연결할 때.
**근거**: `backend : Fast API 설정` → `날씨, 기 api 연결` → `holiday weather api 수정` → `프론트-백엔드 API 연결` → `GPT Image 실제 연동, 헤더 정리, GPT-5로 모델 교체` 순으로 반복된 커밋 패턴.

| 항목 | 내용 |
|---|---|
| **입력** | 연동할 API 문서/키, 백로그의 해당 주차 P0 항목, 기존 라우터/서비스 코드 구조(`backend/app/routers`, `backend/app/services`) |
| **작업 순서** | 1) `services/`에 API 클라이언트 함수 작성 → 2) `routers/`에 엔드포인트로 노출 → 3) 로컬에서 FastAPI 서버 띄워 단독 호출 테스트 → 4) 프론트(`src`)에서 fetch 연결 → 5) 실제 UI에서 값이 화면에 반영되는지 확인 |
| **확인 기준** | 로컬에서 curl/브라우저로 200 응답 + 기대한 필드가 채워짐, 프론트 화면에 에러 없이 표시됨, 실패 시(키 미발급 등) 대체 흐름이 있는지 |
| **결과물** | 동작하는 라우터/서비스 코드 + 커밋 1개(기능 단위로 작게) |
| **문제 생기면 다시 볼 곳** | `.env` / `.env.example` 키 이름 일치 여부 → API 응답 원문(status code, body) → 백로그에 적어둔 "막힐 경우 대체 방안" |

## 워크플로우 B — 배포 후 버그 진단 (Claude Code와 함께)

**언제 쓰나**: 배포된 환경에서만 재현되는 문제(응답이 비어 있음, CORS 에러, 모델 교체 후 토큰 부족 등)를 고칠 때.
**근거**: `showcase.json`의 `agent.workflows[0]`에 이미 정리돼 있고, `.claude/settings.local.json`의 허용된 curl/python 명령 목록이 실제로 이 순서를 그대로 보여준다 — `/health` 확인 → `/generate` 재현 호출 → `/weather` 확인 → 임시 python 스크립트로 원인 검증 → 수정 → git add/commit/push.

| 항목 | 내용 |
|---|---|
| **입력** | 증상 설명(예: "GPT-5 응답이 빈 결과로 옴"), 배포 주소(FE: hub-five-delta.vercel.app, BE: haso-ai-backend.onrender.com) |
| **작업 순서** | 1) 증상을 그대로 전달 → 2) 관련 코드(`services/openai_client.py` 등)와 배포 환경 변수 탐색 요청 → 3) 배포 주소에 curl로 실제 재현 (`/health`, `/generate`, `/weather`) → 4) 원인 확인되면 임시 python 스크립트(`test_*.py`)로 수정안 검증 → 5) 원인 확정 후 코드 수정 → 6) `git add` → `git commit` → `git push` (push 시 Vercel/Render가 자동 재배포) |
| **확인 기준** | 재현 curl이 실패를 재현함 → 수정 후 같은 curl이 성공함 → 재배포 후 같은 curl을 배포 주소에 다시 날려 확인 |
| **결과물** | 원인이 명확한 커밋 메시지(예: "GPT-5 응답 토큰 부족으로 빈 결과 나오는 문제 수정") + 재배포된 서비스 |
| **문제 생기면 다시 볼 곳** | 배포 환경변수(Vercel/Render 대시보드)가 로컬 `.env`와 같은 키를 갖고 있는지 → CORS 허용 origin에 최신 프론트 배포 주소가 들어있는지 → 모델/API 버전이 바뀐 경우 응답 스키마가 달라지지 않았는지 |

---

## 두 워크플로우의 공통점

- **작게 커밋한다**: 커밋 메시지 하나가 "무엇을 왜 고쳤는지"를 그대로 설명한다 (예: `GPT-5 응답 토큰 부족으로 빈 결과 나오는 문제 수정`).
- **먼저 재현, 그다음 수정**: 원인 없이 코드를 먼저 고치지 않는다. curl/테스트 스크립트로 증상을 재현한 뒤에만 수정한다.
- **로컬 확인 → 배포 확인**: 로컬에서 되는 걸 확인해도, 배포 주소에 대해 같은 확인을 한 번 더 한다 (환경변수/CORS가 다르기 때문).
