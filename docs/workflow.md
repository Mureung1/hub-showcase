# SpecFit 개발 워크플로우

> 3주간 SpecFit을 만들면서 실제로 반복한 작업 방식을 정리한 문서. 프로젝트 자체의 기획/기능은 `plan.md`, 작업 이력은 `checklist.md`를 참고하고, 여기서는 "어떻게 작업했는지"만 다룬다.

## 요약

기획과 이슈 우선순위 결정은 직접 하고, 실제 코드 작성·테스트·디버깅은 로컬 VS Code의 **Claude Code CLI**가 맡았다. 별도로 클라우드 세션의 Claude도 함께 열어두고 설계 검토, 이슈 문서 초안, 코드 리뷰 2차 의견을 받는 식으로 두 개를 병행했다. 3주 내내 **이슈 기반 개발**과 **TDD** 두 루틴을 반복하며 진행했다.

---

## 1. 역할 분담

| | 담당 |
|---|---|
| **나** | 요구사항·화면 흐름·이슈별 완료 기준 등 기획 문서 작성. 이슈 단위로 우선순위와 스코프 결정. 매 기능이 끝날 때마다 브라우저에서 직접 동작 확인 → 필요하면 스코프 정정·피드백. |
| **AI (Claude Code)** | 이슈마다 실제 호출부·기존 코드를 먼저 확인한 뒤 구현 계획 수립. 계획을 승인받은 뒤 코드 작성. 일부 기능은 테스트부터 작성하는 방식(Red → Green → Refactor)으로 진행. |

## 2. 로컬 CLI + 클라우드 세션 병행

개발은 Claude Code를 중심으로 진행했다. 실제 코드 작성·테스트·디버깅은 로컬 VS Code에서 Claude Code CLI가 맡았고, 별도로 클라우드 세션의 Claude도 함께 열어두고 설계 검토나 이슈 문서 초안, 코드 리뷰에 대한 2차 의견을 받는 식으로 두 개를 병행했다. 로컬 CLI는 실제 저장소 파일을 직접 읽고 고치며 테스트를 돌리는 "실행" 역할, 클라우드 세션은 코드베이스 접근 없이 "검토·아이디어" 역할로 나뉜다.

## 3. 두 가지 개발 루틴

실제 개발은 이슈 기반 개발과 TDD, 두 가지 루틴을 반복하는 식으로 진행했다.

### ① 이슈 기반 개발 Workflow

```
1. 완료 기준이 담긴 이슈 문서 작성
        ↓
2. 이슈별로 AI에게 구현 요청
        ↓
3. AI가 관련 코드·호출부 확인 후 계획 제시
        ↓
4. 코드 작성 + 로컬 테스트 (Vitest / Playwright)
        ↓
5. 브라우저에서 동작 확인 후 커밋
```

완료 기준이 담긴 이슈 문서를 먼저 쓰고 AI에게 구현을 요청하면, 관련 코드를 먼저 확인한 뒤 계획을 세우고, 그 계획을 승인한 다음에 코드를 작성하는 순서로 진행했다. 여러 파일에 걸친 기능(로그인/북마크 등)은 코드 작성 전에 **Plan 모드**로 먼저 파일 단위 계획을 세우고 승인받은 뒤 진행했고, 완성된 전체 사용자 플로우는 **Playwright E2E 테스트**로 검증했다.

### ② TDD Workflow (예: 컴퓨터활용능력 참고 정보 표시 기능)

```
1. 입력/출력·테스트 시나리오 말로 합의
        ↓
2. 실패하는 테스트 작성 (Red)
        ↓
3. 테스트를 통과시키는 최소 구현 (Green)
        ↓
4. 필요할 때만 리팩토링
        ↓
5. 실제 화면에 연결하고 재검증
```

일부 기능은 실패하는 테스트부터 작성하는 TDD 방식으로 진행했다. 스펙(입출력·테스트 시나리오)을 말로 먼저 합의하고, 실패하는 테스트를 작성해 실제로 실패하는 걸 확인한 뒤, 테스트를 통과시키는 최소한의 구현만 추가하고, 정리할 게 있을 때만 리팩토링하는 순서. 코드만 보고 넘어가지 않고 매 단계 직접 확인하면서 진행했다.

## 4. 함께 활용한 Skill / Agent

| | 역할 |
|---|---|
| **simple-tdd** (프로젝트 전용 Skill) | 스펙 합의 → 실패하는 테스트(Red) → 최소 구현(Green) → 리팩토링 순서로, 단계마다 확인받으며 진행하도록 강제하는 프로젝트 로컬 Skill. |
| **Plan 모드** (Agent) | 여러 파일에 걸친 기능(로그인/북마크 등) 구현 전, 파일 단위 계획을 먼저 세우고 승인받은 뒤 코드를 작성하도록 하는 모드. |
| **Playwright E2E 테스트** | 전체 사용자 플로우와 "홈" vs "초기화" 같은 상태 보존/리셋 분기 시나리오를 브라우저 자동화로 검증. |
| **specfit-design** (프로젝트 전용 Skill) | 이 문서를 HTML로 옮기면서 함께 정리한 Skill. `src/styles/tokens.css`/`src/App.css`의 실제 SpecFit 디자인 토큰(크림/더스티로즈 라이트 + "핑크-네이비 반전" 다크모드, pill 버튼, 톤이 있는 그림자, 스테퍼 컴포넌트)을 그대로 문서화해뒀다가, 발표 자료·데모 페이지 등 SpecFit 관련 산출물을 만들 때 재사용한다. |

## 5. 실제 사례로 본 워크플로우 — 배포에서 부딪힌 것들

이슈 기반 개발 루틴이 실제로 어떻게 작동했는지 보여주는 예시로, 배포(Vercel + Render) 과정에서 실제로 부딪히고 해결한 것들:

- 환경변수로 CORS 허용 origin과 API 주소를 분리 (로컬/배포 환경 자동 전환)
- 서버 재시작 시 DB가 비어있으면 자동으로 862건을 시드하는 로직을 배포 전에 미리 반영
- `PORT` 환경변수를 수동 지정한 게 플랫폼 자동 할당과 충돌 — 제거로 해결
- 배포 플랫폼의 브랜치/런타임 자동 감지 오류 — `work` 브랜치로 직접 재지정

이런 문제들도 "이슈 문서 작성 → AI가 원인 확인 후 계획 제시 → 수정 → 실제 배포 환경에서 재검증" 루틴 안에서 처리했다.

## 6. 프로젝트 배경 (요약)

SpecFit은 재학 중인 대학생이 자신의 스펙(학력·경력·자격증·전공·외국어)을 실제 채용공고 862건과 대조해, 지금 지원 가능한 공고 비율과 무엇을 보완하면 더 많은 공고에 지원할 수 있는지를 보여주는 갭 분석 서비스다. 기존 취업 플랫폼이 "지금 당장 지원 가능한 공고 추천"에 집중하는 것과 달리, 아직 시간 여유가 있는 재학생에게 "재학 중 준비 로드맵"을 제공하는 게 목표다. 판정은 5개 항목(학력·경력·자격증·전공·외국어) AND 대조이고, 컴퓨터활용능력은 판정에 포함하지 않는 참고 정보로만 표시한다. 자세한 기획/기능/화면 흐름은 `docs/plan.md`, API는 `docs/api.md`, 작업 이력은 `docs/checklist.md`를 참고.
