## Agent 2개

### `feature-slice` (2026-07-13 도입)
- **역할**: 요구사항/기능 아이디어를 하루 단위 Task로 쪼개고 최우선/P0/P1로
  우선순위를 매긴다. `docs/plan.md`·`docs/api-spec.md`를 먼저 읽고 기존
  스펙과 어긋나지 않게 분해하며, 스코프 크리프를 경계하도록 설계돼 있다.
- **도구**: Read, Grep, Glob — 쓰기 권한 없음(읽기 전용). 계획 단계에서
  코드를 건드리면 검증되지 않은 변경이 섞일 위험이 있다는 게 이유.
- **언제 쓰나**: 새 기능을 시작하기 전, 또는 주간 계획을 세울 때.
- **실제 효과**: `docs/backlog.md` 07-15 갱신 — feature-slice 감사 결과
  "완료(✅)"로 표시됐던 항목 상당수가 실제로는 구 기획(용어 팝업)이 코드에
  그대로 남아 있었음을 발견. 07-20 갱신 — 3주차 작업을 재검토해
  `analyzeArticle`이 5개 필드를 한 번의 호출로 반환하는 통합 함수임을
  코드로 확인하고, 분리돼 있던 두 Task(문단 요약 생성 / 종목 영향 해설
  생성)를 하나로 병합했다.

### `feature-verify` (2026-07-17 도입)
- **역할**: 구현이 문서화된 요구사항(API 스펙/기획서/데이터 모델)을 실제로
  만족하는지 코드와 실행 중인 서버를 근거로 검증한다. 우선순위는
  `api-spec.md` > `plan.md` > `data-model.md`/마이그레이션 >
  CLAUDE.md "구현 유의사항" 순. `backlog.md`의 체크박스
  상태는 신뢰하지 않고, 항상 파일경로:줄번호로 근거를 남긴다. `npm run dev`는
  직접 실행하지 않는다(에이전트가 멈춰버림) — 대신 curl로 이미 떠 있는
  로컬 서버(`localhost:4000`/`5173`)를 찔러 확인하는 패턴을
  `.claude/settings.local.json`의 허용 목록에서도 확인할 수 있다.
- **도구**: Read, Grep, Glob, Bash — 코드 수정은 명시적으로 금지.
- **언제 쓰나**: 기능 구현이나 마이그레이션 직후, 커밋 전후.
- **실제 효과**: `docs/backlog.md` 07-20 갱신 — feature-verify로 수직
  슬라이스 완성도를 점검한 결과 MVP 최우선 기능인 `analyzeArticle`이
  여전히 고정 응답만 반환한다는 걸 재확인, 이를 근거로 `#13`(프롬프트
  설계)→`#14`(실연결)→`#12`(DB 전환) 순서로 착수 우선순위를 재조정했다.

## Skill 2개

### `design` (2026-07-09 도입)
색상/타이포그래피/컴포넌트 스타일/인터랙션 규칙의 단일 소스. 새 화면·
컴포넌트를 만들거나 기존 화면을 수정할 때 참조한다. 가장 중요한 규칙은
"인터랙션에 자바스크립트를 쓰지 않는다 — `:focus`/`:checked`/네이티브
`<details>`만 사용"으로, 과거 라디오 숨김 CSS 셀렉터 회귀를 겪은 뒤
규칙으로 못박은 것이다. 07-13 피벗 때 프로토타입 3화면과 함께 전면
교체됐다.

### `testing` (2026-07-23 도입)
Vitest 기반 단위 테스트 작성 컨벤션. 서버 순수 함수나 클라이언트
컴포넌트에 새 테스트 파일을 추가할 때 참조한다. 파일은 코드와 같은
위치에 `*.test.js`/`*.test.jsx`로 두고, `describe`/`it` 구조(정상 케이스/
빈 값/경계값/실패하는 경우/순수성 카테고리)와 한글 문장형 제목, 표 형태
케이스는 `it.each`, mock은 `vi.spyOn`+`afterEach(vi.restoreAllMocks)`를
컨벤션으로 정했다. 기능이 안정된 3주차 막바지에야 도입된 건 앞서
"반복된 작업 순서" 절의 테스트/CI 후순위 배치 패턴과 일치한다.

## 원칙 요약

사람이 정하는 것: 문제 정의, 핵심 기능 우선순위, 화면별 정책(블라인드
처리·저장 시점 등). AI에게 위임하는 것: 요구사항을 Task로 분해, 구현 코드
작성, 구현이 스펙과 실제로 일치하는지 검증. 계획 단계(`feature-slice`)
에이전트를 읽기 전용으로 만든 것도 같은 맥락 — 아직 확정되지 않은 계획이
코드에 직접 손대는 걸 막기 위해서다. Skill 2개는 필요해진 시점에 하나씩
추가됐다(디자인 일관성 → 계획 자동화 → 신뢰성 검증 → 회귀 방지 순), 처음부터
전부 갖추고 시작하지 않았다.
