# Pinned Codex production conversation 소유권 지도

- 분류: 기술 참고
- 성숙도: 채택
- 대상 pin: `@openai/codex@0.144.0`, upstream commit `767822446c7a594caa19609ca435281a9ec67e0d`
- 범위: `codex-core`, App Server의 per-thread listener, production TUI·exec의 thread/task/turn/item identity, conversation ownership, input routing, terminal·history·cleanup

이 문서는 [Core·TUI·exec conversation ownership pattern을 지도화한다](../tickets/006-map-first-party-conversation-ownership.md)의 source evidence asset이다. [Pinned method lifecycle 근거표](004-method-lifecycle-fact-table.md)와 [Connection·App Server ingress architecture 지도](005-first-party-connection-ingress-architecture.md)의 결론을 복사하지 않고 pinned production source와 tests에서 conversation ownership을 다시 추적했다. 최종 AY-PLE module seam, public identity API, concurrency·delivery·recovery policy는 [첫 tracer와 module seam을 선택한다](../tickets/008-choose-first-tracer-and-module-seams.md)부터 [Connection loss와 unknown outcome 정책을 결정한다](../tickets/012-decide-connection-and-unknown-outcome-policy.md)까지의 decision ticket이 결정한다.

## 결론

1. First-party production 구조에는 TUI와 exec가 공유하는 별도 범용 conversation kernel이 없다. `codex-core`의 `ThreadManager`·`CodexThread`·`Session`이 engine conversation의 deep module이고, App Server가 이를 protocol로 노출하며, TUI와 exec는 각 use case에 맞는 state projection을 직접 소유한다.
2. 이 사실은 AY-PLE이 monolithic `HeadlessCodexClientHost`를 유지해야 한다는 뜻도, 반드시 별도 generic kernel을 만들어야 한다는 뜻도 아니다. Source가 반복해서 보여 주는 ownership locality는 **single connection ingress, native identity 기반 scope routing, surface별 conversation state**다. 이를 하나 또는 여러 Module로 표현할지는 [첫 tracer와 module seam을 선택한다](../tickets/008-choose-first-tracer-and-module-seams.md)가 product tracer에 맞춰 결정해야 한다.
3. Successful same-thread resume는 native `ThreadId`를 유지하지만, ID stability와 process restart 뒤 recoverability는 다르다. Ephemeral thread와 아직 materialize되지 않은 fresh thread는 ID를 알아도 durable resume source가 남지 않을 수 있다. Idle thread에서 시작한 user turn은 core submission ID를 running turn ID로 사용하지만, 이미 turn이 active인 상태의 두 번째 `turn/start`는 새 response ID를 반환하면서 input을 기존 active turn으로 steer할 수 있다. Item ID도 source-owned이지만 string 형식과 생성 주체는 균일하지 않다. Process generation마다 이를 새 UUID로 remap하거나 모두 UUIDv7로 가정할 근거는 없다.
4. Command·active task·pending input·event drain은 thread-local이다. Bootstrap 예외를 제외한 TUI steady state도 한 ingress에서 native `ThreadId`로 per-thread store에 route하고, 현재 화면에 보이지 않는 thread의 진행을 막지 않는다. Generation-wide journal이나 current-view global lock은 first-party conversation invariant가 아니다.
5. Start/resume response snapshot, live notification, **지원되는 persistence 상태에서만 가능한** `thread/read(includeTurns: true)` snapshot, exact turn terminal, late/background observation drain은 서로 다른 authority다. Core의 background process watcher는 terminal 뒤에도 원래 `Session`·`TurnContext` ownership을 유지할 수 있다. Exec의 조건부 terminal-time one-shot backfill과 TUI의 replay buffer는 각 surface의 recovery 편의이며 generic delivery contract가 아니다.
6. 채택 대상은 ownership과 scope pattern이다. Core/TUI의 unbounded queues, magic capacities, detached overflow task, string error parsing, weak persistence outcome, widget reconstruction과 exec의 single-turn 즉시 종료 정책은 복사하지 않는다.

## 생성·resume·fork와 history 소유권

### Start와 준비 완료 조건

- `ThreadManager`의 start/resume wrapper는 `spawn_thread_with_source`로 수렴한다. ([start](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager.rs#L647-L720), [resume](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager.rs#L760-L817))
- Core는 first event가 `INITIAL_SUBMIT_ID`의 `SessionConfigured`인지 확인한 뒤에만 `CodexThread`를 manager map에 publish한다. Duplicate insertion의 losing runtime은 shutdown한다. ([readiness barrier](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager.rs#L1636-L1676))
- 이는 “fully initialized before in-process publication” pattern의 근거다. Stdio의 response/notification ordering 보장은 아니며 [Pinned method lifecycle 근거표](004-method-lifecycle-fact-table.md)를 덮어쓰지 않는다.

### Resume·fork

- Resume가 동일 ID·동일 rollout path의 live thread를 만나면 같은 `Arc<CodexThread>`를 반환한다. 다른 path면 거부하고, stopped entry면 map에서 제거한 뒤 같은 native ID로 새 runtime을 만든다. ([live resume](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager.rs#L1541-L1562), [same-Arc test](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager_tests.rs#L945-L1003))
- Fork는 source의 committed history snapshot을 읽고 새 `ThreadId`와 `forked_from` lineage를 만든다. Live subagent fork는 read 전에 rollout을 materialize하고 flush한다. ([fork snapshot](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager.rs#L949-L1070), [live flush barrier](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager.rs#L723-L757))
- Resume identity equality와 fork identity inequality는 ThreadStore 기반 test로 고정된다. ([identity test](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager_tests.rs#L1200-L1306))

### Live state·snapshot 권위

- Non-ephemeral `Session`은 native `ThreadId`로 `LiveThread`를 create/resume하고 ephemeral thread는 persistence를 생략한다. ([persistence construction](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/session.rs#L579-L647))
- App Server `thread/read`의 authority는 상태별로 다르다. `includeTurns: false`는 persisted `ThreadStore` metadata를 우선하고 persisted row가 없는 loaded thread—fresh unmaterialized와 ephemeral을 포함한다—는 live snapshot으로 fallback한다. `includeTurns: true`는 materialized inline-history persistent thread에서만 turn history를 만들 수 있다. Loaded ephemeral thread는 명시적으로 거절되고, fresh unmaterialized persistent thread는 `load_history()`에서 실패하며, exact pin의 paginated history도 unsupported다. Loaded non-ephemeral thread는 persisted metadata와 live handle의 store history를 결합하고 unloaded thread는 persisted metadata/history를 함께 읽지만, 이 branch matrix를 “loaded live history는 항상 된다”로 일반화할 수 없다. Metadata mutation의 live/cold routing은 또 별도다. ([read selection](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/thread_processor.rs#L2255-L2297), [ephemeral guard와 live history](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/thread_processor.rs#L2366-L2412), [unmaterialized rejection test](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/tests/suite/v2/thread_read.rs#L1195-L1247), [paginated rejection test](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/tests/suite/v2/thread_read.rs#L208-L324), [metadata mutation](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager.rs#L572-L608))
- TUI는 start/resume response의 thread/session/initial turns를 bootstrap authority로 사용한다. `thread/read(includeTurns)` fallback은 live listener attach가 아니라 `ReplayOnly` snapshot으로 표시한다. ([response mapping](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app_server_session.rs#L1522-L1565), [live-vs-replay](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/session_lifecycle.rs#L256-L319))

채택 가능한 제약은 “resume/fork/history를 TS client가 재구현한다”가 아니다. Core/App Server가 소유한 native history authority를 사용하되, live attachment와 point-in-time snapshot을 혼동하지 않고 unsupported persistence 상태에는 별도 recovery policy가 필요하다는 사실을 Interface에 보존하는 것이다.

## Thread-local command와 turn 소유권

### Core command 경로

- `Codex`는 high-level queue pair다. 각 thread는 bounded submission channel(capacity 512), unbounded event channel, 한 submission loop와 shared termination future를 가진다. ([queue pair](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/mod.rs#L386-L399), [channels](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/mod.rs#L468-L469), [session-loop spawn](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/mod.rs#L726-L739))
- 한 FIFO submission loop가 `Op`를 순서대로 dispatch하고, `Session`은 동시에 최대 한 running task와 thread-local input queue를 소유한다. ([loop](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/handlers.rs#L714-L872), [session invariant](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/session.rs#L25-L48))
- Task start는 turn lifecycle을 기록하고 background task를 spawn한 뒤 single active turn에 설치한다. Completion은 current task slot을 take하고 terminal을 emit한 뒤 same-`turn_state` pointer guard로 active turn을 clear한다. ([start](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/tasks/mod.rs#L313-L451), [finish](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/tasks/mod.rs#L563-L804))

`512`와 unbounded event queue는 pinned implementation fact이지 AY-PLE delivery contract가 아니다. Mailbox `VecDeque`와 active-turn pending `Vec`도 scope-local이지만 unbounded다. [Event delivery와 transcript recovery model을 결정한다](../tickets/011-decide-delivery-and-recovery-model.md)가 external client bound와 overflow semantics를 정한다.

### Start·steer·interrupt

- Core의 user input handler는 regular turn이 active면 같은 turn의 pending steer input으로 넣고 idle이면 새 `RegularTask`를 시작한다. ([routing](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/handlers.rs#L194-L285))
- `steer_input`은 active task, optional expected native turn ID, steerability와 nonempty input을 atomically 검증하고 turn-local queue에 append한다. ([steer](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/mod.rs#L3867-L3947), [mismatch test](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/tests.rs#L9993-L10036))
- App Server의 `turn/start`는 `Op::UserInput`을 submit하고 새 submission ID를 response turn ID로 사용한다. Idle thread에서는 이 ID로 regular turn이 시작된다. 이미 `T1`이 active이면 core는 새 `T2` context를 만든 뒤 input을 `T1`에 steer하고 `steer_input`이 반환한 `T1`을 버리므로 response `T2`는 running turn identity가 아니다. ([mapping](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/turn_processor.rs#L521-L568), [user-input handler](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/handlers.rs#L194-L285), [active ID return](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/mod.rs#L3882-L3947))
- Active `T1` 중 이 T2 context를 만들기 전에 supplied turn settings를 thread state에 적용할 수 있다. Settings validation 또는 steer가 실패하면 core `Error` event가 `T2` correlation ID를 사용하고 App Server가 T2-scoped public `error` notification으로 번역할 수 있지만, T2 `turn/started`나 terminal은 생기지 않는다. 따라서 “response T2는 inert alias”로도 취급할 수 없다. ([settings와 error emission](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/handlers.rs#L194-L285), [validation error](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/turn_context.rs#L586-L652), [public error translation](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/bespoke_event_handling.rs#L879-L919), [notification mapping](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/bespoke_event_handling.rs#L1551-L1566))
- TUI는 notification-derived cached active turn이 있으면 `turn/steer(expectedTurnId)`, 없으면 `turn/start`를 사용한다. Missing active turn이면 cache를 clear하고 start로 전환하며, mismatch면 server-reported actual ID로 한 번 재시도한다. Non-steerable turn의 queueing은 `ChatWidget` policy다. ([TUI routing](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_routing.rs#L517-L678), [typed methods](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app_server_session.rs#L771-L868))
- TUI는 user turn submit 직후 `user_turn_pending_start`를 세워 후속 **user input**을 queue하고 `TurnStarted`를 처리할 때 해제한다. `turn/start` response 자체는 `ThreadEventStore.active_turn_id`를 설정하지 않는다. 이는 response와 notification 사이의 local input race를 막는 TUI surface barrier이지 interrupt target authority는 아니다. ([set pending](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/chatwidget/input_submission.rs#L354-L359), [queue while pending](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/chatwidget/input_flow.rs#L96-L165), [clear on start](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/chatwidget/turn_runtime.rs#L59-L62), [response path](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_routing.rs#L652-L675))
- 실제 `AppCommand::Interrupt`가 route될 때 interrupt path는 cache 유무로 둘로 갈린다. `ThreadEventStore.active_turn_id`가 있으면 TUI가 exact ID를 보내고 mismatch actual ID로 한 번 재시도한다. Cache가 없으면 `startup_interrupt()`가 empty `turnId`를 보낸다. Exact-pin App Server는 이를 native turn에 결속되지 않은 startup-cancellation sentinel로 해석해 core `Op::Interrupt` submit 직후 응답한다. No-active 상태면 MCP startup만 취소해 terminal이 없고, operation이 처리될 때 이미 active task가 생겼다면 그 native turn의 별도 terminal이 나올 수 있다. `user_turn_pending_start` 자체는 user-input queue predicate일 뿐 interrupt command를 emit하지 않으므로, pure pre-`TurnStarted` user pending이 이 branch를 반드시 탄다고 일반화하지 않는다. Empty sentinel의 checked-in race test도 없다. Normal interrupt의 same-thread terminal barrier와 같은 operation으로 취급하면 안 된다. ([TUI route](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_routing.rs#L517-L560), [empty sentinel](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app_server_session.rs#L822-L845), [server branches](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/turn_processor.rs#L1346-L1408), [core race](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/mod.rs#L3960-L3966), [cancellable predicate](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/chatwidget/interaction.rs#L401-L425))
- Steer와 normal interrupt mismatch 추출은 structured field가 아니라 서로 다른 message parser이므로 채택 가능한 contract가 아니다. ([steer parser](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app.rs#L650-L678), [interrupt parser](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app.rs#L706-L721))

Source는 per-thread single-active-task라는 engine constraint와 TUI의 queue/retry/startup-cancel UX를 구분한다. AY-PLE이 active input을 steer, queue, reject 또는 새 `ModelingRun`으로 처리할지와 empty sentinel을 어느 boundary에서 감출지는 [Thread·turn concurrency 정책을 결정한다](../tickets/010-decide-concurrency-policy.md)의 product policy다.

## Event 전달 경로와 multi-thread 진행

### 단일 drain owner

- Core의 `CodexThread.next_event()`는 한 receiver를 소비하는 API이며 별도 status `watch`만 제공한다. Event는 rollout persistence를 시도하고 status projection을 갱신한 뒤 queue로 전달된다. ([delivery](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/mod.rs#L1946-L1983))
- App Server가 thread당 한 listener로 이 stream을 drain하고 subscribed connection에 fanout한다. Core queue 자체는 broadcast가 아니다. ([listener](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L277-L343))
- TUI main loop는 한 branch에서 `app_server.next_event()`를 계속 drain하고, 별 branch가 현재 active thread receiver를 렌더링한다. ([main loop](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app.rs#L1180-L1231))

따라서 external client도 connection event stream의 drain authority를 하나로 두고 그 위에 per-thread projection과 product subscribers를 둬야 한다. 여러 consumer가 transport `next_event`를 경쟁적으로 호출하게 하면 안 된다.

### TUI multi-thread projection

- TUI는 typed notification의 native `thread_id`를 추출해 thread, invalid, app-scoped, global로 분류한다. Server request는 먼저 surface 지원 정책을 적용하고 recognized thread-scoped variant만 route하며 unsupported request는 reject하고 threadless request는 ignore한다. ([notification target classification](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/app_server_event_targets.rs#L37-L192), [notification dispatch](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/app_server_events.rs#L61-L177), [request routing policy](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/app_server_events.rs#L179-L222))
- Primary가 아닌 **tracked·supported** inactive thread의 notification과 server request도 해당 store에 반영된다. Unknown non-primary state update는 drop될 수 있다. Active 화면은 rendering focus일 뿐 known inactive runtime progression의 global lock이 아니다. Checked-in tests는 개별 inactive-thread routing을 고정하지만 distinct A/B/A ingress interleaving은 고정하지 않는다. ([notification enqueue와 unknown drop](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_routing.rs#L877-L935), [request enqueue](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_routing.rs#L1016-L1063), [inactive approval test](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/tests.rs#L2184-L2265))
- `ThreadEventStore.active_turn_id`는 `turn/started`에서 설정하고, 다른 turn의 completion에는 지우지 않는다. Exact matching `turn/completed`와 `thread/closed`에서 clear하고 snapshot의 latest `InProgress` turn으로 recompute하며, missing-active steer response도 cache를 명시적으로 clear한다. ([active turn projection](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_events.rs#L89-L123), [missing-active reset](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_routing.rs#L595-L604))
- Thread switch는 이전 receiver/composer state를 store로 돌리고 대상 snapshot을 replay한 뒤 `ChatWidget`을 다시 만든다. ([activation](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_routing.rs#L44-L106), [selection](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/session_lifecycle.rs#L348-L443))
- Bootstrap 중 `primary_thread_id`가 아직 없으면 TUI는 thread-scoped notification/request에서 추출한 routing key를 별도로 보존하지 않고 unbounded `pending_primary_events`에 typed payload만 보관한다. Payload 안 native ID는 남지만 start response로 primary를 안 뒤에는 모든 pending event를 그 eventual primary key 아래 강제로 replay한다. 이 staging에는 cross-thread scope correctness, bound, byte size나 overflow oracle이 없다. Checked-in tests는 eventual primary와 동일한 approval 하나의 replay와 동일 thread event 둘의 nonblocking delivery만 고정한다. 이는 single-primary startup convenience이며 general native-scope routing invariant로 복사할 수 없다. ([notification routing](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/app_server_events.rs#L143-L152), [request routing](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/app_server_events.rs#L179-L222), [forced replay](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_routing.rs#L1109-L1159), [pending storage](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/thread_routing.rs#L1166-L1189), [single approval test](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/tests.rs#L198-L249), [nonblocking test](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/tui/src/app/tests.rs#L460-L497))

Bootstrap 예외를 제외한 native scope routing과 tracked inactive-thread progression은 후속 design의 검증 기준이다. `primary_thread_id`, side/subagent navigation, composer save, widget reconstruction과 terminal badges는 TUI product policy다. Distinct A/B/A ingress oracle은 [Source conformance verification matrix를 결정한다](../tickets/013-decide-source-conformance-verification.md)가 소유한다.

## Terminal·backfill·정리 소유권

### Terminal은 drain이 아니다

- Core task finish는 supplied `TurnContext.sub_id`의 `TurnComplete` 또는 `TurnAborted`를 emit한다. Active state cleanup은 explicit turn-ID guard가 아니라 current task slot을 take하고 terminal 뒤 같은 `turn_state` pointer가 여전히 current slot인지 확인해 clear하는 방식이다. 그 뒤 terminal rollout flush를 시도한다. ([terminal path](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/tasks/mod.rs#L563-L804))
- Exec는 start/resume response를 bootstrap authority로 사용하고 target turn response ID를 primary output filter key로 보존한다. ([bootstrap](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/lib.rs#L802-L954))
- Ingress loop는 facade에서 전달받은 server request를 notification output filter와 무관하게 처리하고, notification filtering 전에 terminal backfill을 시도한다. Config/deprecation warning과 일부 unscoped warning도 primary target 밖에서 output projection에 들어온다. Exec가 받은 request의 policy는 MCP elicitation auto-cancel과 나머지 unsupported request reject의 조합이지만, lower queue/facade overload와 auth-refresh pre-reject 때문에 exhaustive handler는 아니다. ([ingress order](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/lib.rs#L993-L1045), [filter](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/lib.rs#L1287-L1345), [Exec request policy](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/lib.rs#L1655-L1735), [lower queue pre-reject](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/in_process.rs#L638-L668), [facade pre-reject](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server-client/src/lib.rs#L540-L580))
- Primary Exec session/config가 non-ephemeral이면, origin thread와 target 여부에 관계없이 빈 `turn.items`를 가진 `turn/completed`마다 output filter 전에 `thread/read(includeTurns)`를 한 번 호출한다. Primary config가 ephemeral이면 이 backfill branch 전체를 건너뛴다. Completion payload의 origin thread가 ephemeral인지는 별도로 검사하지 않으므로 non-ephemeral primary session에서는 unrelated empty completion도 read를 유발한 뒤 output filter에서 버려질 수 있다. 성공한 read에서 matching turn을 찾으면 그 items를 terminal payload에 채운다. 그 뒤 JSONL processor만 이미 start됐지만 completion이 누락된 item을 reconcile하고, human processor는 마지막 AgentMessage—없으면 마지막 Plan—를 final output 후보로 복구한다. Read failure만 warning을 남기고 matching turn 누락은 조용히 원 payload를 유지한다. 어느 경우든 **matching primary terminal**이면 processor가 shutdown을 시작하지만 unrelated terminal은 filter에서 버린다. ([ingress와 primary config flag](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/lib.rs#L993-L1045), [ephemeral guard와 backfill](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/lib.rs#L1347-L1412), [JSONL reconciliation](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/event_processor_with_jsonl_output.rs#L357-L371), [JSONL terminal](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/event_processor_with_jsonl_output.rs#L500-L552), [human terminal](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/event_processor_with_human_output.rs#L300-L333), [human fallback](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/event_processor_with_human_output.rs#L485-L499))

이 backfill은 CLI final output 복구 정책이지 모든 thread 상태에서 사용할 수 있는 transcript API도, `turn/completed` 뒤 late child notification까지 모두 drain됐다는 증거도 아니다. [Pinned method lifecycle 근거표](004-method-lifecycle-fact-table.md)가 고정한 terminal과 late/background observation 구분을 유지하고, [Event delivery와 transcript recovery model을 결정한다](../tickets/011-decide-delivery-and-recovery-model.md)에서 delivery retention과 authoritative recovery source를 정한다.

Legacy history reducer는 terminal event의 exact ID를 먼저 찾지만 unknown/no-ID abort나 unmatched completion을 current replay turn에 적용하는 fallback도 가진다. 이는 imperfect rollout을 reconstruct하는 history convenience이지 live terminal correlation invariant가 아니다. External client의 live state machine에 복사하지 않는다. ([abort fallback](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server-protocol/src/protocol/thread_history.rs#L1197-L1226), [completion fallback](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server-protocol/src/protocol/thread_history.rs#L1240-L1282))

### Background process 소유권

- `UnifiedExecProcessManager`는 initial yield 전에 live process를 manager store에 넣어 turn interruption이 마지막 process `Arc`를 떨어뜨리지 못하게 한다. Stored process의 exit watcher에는 원래 `Arc<Session>`과 `Arc<TurnContext>`를 전달한다. ([retain before yield](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/unified_exec/process_manager.rs#L450-L470), [store and watcher](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/unified_exec/process_manager.rs#L858-L907))
- Output task와 exit watcher는 그 original context를 보존해 delta와 end event를 emit한다. Late observation은 새 generation/global journal이 아니라 process가 시작된 original turn context에 귀속된다. ([output watcher](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/unified_exec/async_watcher.rs#L37-L101), [exit watcher](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/unified_exec/async_watcher.rs#L104-L157), [end emission](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/unified_exec/async_watcher.rs#L191-L237))
- Production tests는 `TurnComplete` 뒤에도 process가 alive일 수 있고 background end event가 별도로 도착함을 고정한다. 따라서 turn terminal, process lifetime과 observation drain은 독립 경계다. ([survives turn complete](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/tests/suite/unified_exec.rs#L2390-L2474), [background end event](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/tests/suite/unified_exec.rs#L722-L815))

### Subscription·thread·process lifetime

- `thread/unsubscribe`는 한 connection을 thread subscriber set에서 제거할 뿐 즉시 thread를 shutdown하지 않는다. Loaded·subscribed면 `Unsubscribed`, loaded·already absent면 `NotSubscribed`, not-loaded면 pending request/thread/watch teardown을 정리하고 `NotLoaded`를 반환한다. Exec는 typed response의 status를 구분하지 않는다. ([unsubscribe](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/thread_processor.rs#L822-L860), [repeat test](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/tests/suite/v2/thread_unsubscribe.rs#L368-L423), [Exec request](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/lib.rs#L1596-L1610))
- App Server listener는 subscriber가 0이어도 core event drain을 계속하며, no-subscriber와 inactive/non-running 상태가 각각 30분 유지된 뒤 unload를 시도한다. Running thread라면 unload를 미룬다. Teardown은 pending server request를 취소하고 App Server thread state를 먼저 제거한 뒤 10초 bounded shutdown을 별도 task에서 실행한다. Shutdown이 complete이고 이 teardown이 manager entry를 실제 제거한 경우에만 watch state를 제거하고 initialized connection 전체에 opt-out 규칙을 적용한 `thread/closed`를 broadcast한다. Entry가 이미 없거나 submit failure/timeout이면 `thread/closed` 없이 끝나며, failure/timeout은 warning과 함께 core thread를 loaded 상태로 남긴다. ([30분 constant와 predicate](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L1-L80), [listener와 unload branch](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L277-L375), [teardown outcome](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L389-L446), [broadcast sender](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/outgoing_message.rs#L589-L615), [connection filter](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/transport.rs#L198-L234))
- Unload ID가 `pending_thread_unloads`에 있는 동안 new listener attach는 “closing; retry after closed”로 거절된다. Shutdown failure/timeout이면 marker만 제거되고 loaded thread가 남아 이후 attach 후보가 되지만 이 recovery branch의 독립 test는 없다. 이 transient closing/reattach policy는 [Connection loss와 unknown outcome 정책을 결정한다](../tickets/012-decide-connection-and-unknown-outcome-policy.md)와 [Source conformance verification matrix를 결정한다](../tickets/013-decide-source-conformance-verification.md)가 소유한다. ([attach gate](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L138-L171), [marker와 outcome](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L355-L445))
- Core shutdown은 explicit `Op::Shutdown`과 session-loop join이다. Manager-wide bounded shutdown은 thread들을 concurrent하게 종료하고 complete만 map에서 제거하며 submit-failed/timed-out thread는 추적 상태로 남긴다. ([per-thread shutdown](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/session/mod.rs#L807-L825), [manager report](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager.rs#L891-L947))
- `ThreadManager.remove_thread`는 registry ownership만 제거하며 다른 `Arc<CodexThread>`가 남을 수 있다. ([remove semantics](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/core/src/thread_manager.rs#L891-L896))
- Exec는 matching terminal 뒤 `thread/unsubscribe`를 시도하고 client를 shutdown한다. Unsubscribe failure는 warning만 남기고 loop를 끝내며 client shutdown failure도 warning이다. Event stream EOF면 unsubscribe branch를 거치지 않고 client shutdown으로 간다. 이는 best-effort one-shot process cleanup이지 thread terminal이나 durable detach의 정의가 아니다. ([exec loop와 cleanup](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/lib.rs#L986-L1063), [unsubscribe request](https://github.com/openai/codex/blob/767822446c7a594caa19609ca435281a9ec67e0d/codex-rs/exec/src/lib.rs#L1596-L1610))

Browser disconnect, connection unsubscribe, engine thread idle/unload, active turn terminal과 child-process termination은 다른 state machine이다. 이를 하나의 generation state로 collapse하지 않는다. Exact unknown-outcome와 reconnect UX는 [Connection loss와 unknown outcome 정책을 결정한다](../tickets/012-decide-connection-and-unknown-outcome-policy.md)가 결정한다.

## AY-PLE 경계 비교

[Codex App Server를 우선 지원 실행 엔진으로 사용한다](../../../adr/0005-use-codex-app-server-as-first-class-mvp-runtime.md), [제품 작업을 native Codex 조합으로 실행한다](../../../adr/0007-use-native-codex-composition-for-product-actions.md)와 [Codex-native 제품 작업 조합](../../../architecture/codex-native-product-composition.md)의 product intent는 Codex-native capability 위에 앱 기능을 올리고, `ModelingInvocation → ModelingRun`을 제품 receipt로 유지하며 raw protocol shape를 제품 계약으로 승격하지 않는 것이다. 이 source audit은 그 방향을 다음처럼 구체화한다.

| 관심사 | First-party 근거 | AY-PLE 후보이며 아직 최종 결정이 아닌 것 |
| --- | --- | --- |
| 내부 conversation identity | TUI와 exec는 live thread/turn correlation에 native ID를 사용하지만 TUI는 `SessionId`를 drop하고 history path는 turn/item ID를 합성할 수 있다. | 후보는 native correlation과 관찰 경로를 함께 보존해야 한다. Exact TS branding, alias와 browser exposure는 [Identity authority와 product reference 정책을 결정한다](../tickets/009-decide-identity-and-authority.md)가 정한다. |
| Conversation collection | Core manager와 TUI projection은 native `ThreadId` keyed collection을 사용한다. | Connection과 per-thread projection ownership을 Interface에서 식별 가능하게 한다. 하나 또는 여러 Module인지는 [첫 tracer와 module seam을 선택한다](../tickets/008-choose-first-tracer-and-module-seams.md)가 정한다. |
| Product execution | Exec는 한 target turn을 exact match하고 TUI는 tracked thread를 독립 route한다. | `ModelingRun`은 한 native attempt의 receipt지만 thread cardinality나 UI conversation과 동일하지 않다. |
| 현재 view | TUI active thread는 rendering focus이고 tracked inactive thread도 진행한다. | Browser focus·SSE subscriber가 engine execution의 global lock이 되지 않게 한다. |
| History·recovery | Core/App Server가 native history를 소유하지만 exact-pin `thread/read(includeTurns)` availability와 replay identity는 persistence/history path에 따라 달라진다. | TS layer가 raw rollout reconstruction을 소유하지 않는다. 지원 상태를 구분한 snapshot/reconciliation method와 unavailable-history policy만 사용한다. |
| Surface 정책 | TUI와 exec의 queue, retry, backfill, failover가 서로 다르다. | 첫 AY-PLE tracer가 필요한 정책만 product adapter에 둔다. Hypothetical generic feature를 먼저 추출하지 않는다. |

현재 source evidence만으로 “범용 `CodexChatKernel`을 독립 package로 반드시 만든다”거나 “기존 `HeadlessCodexClientHost`를 얇게 고친다”는 결론은 둘 다 성립하지 않는다. 확정 가능한 것은 [첫 tracer와 module seam을 선택한다](../tickets/008-choose-first-tracer-and-module-seams.md)와 [Identity authority와 product reference 정책을 결정한다](../tickets/009-decide-identity-and-authority.md)가 다음 Interface pressure를 만족하는지 검증해야 한다는 점이다. 모두 하나의 deep Module 내부 seam으로 표현할 가능성을 열어 둔다.

- Connection ingress와 request completion ownership을 conversation projection과 구분할 수 있어야 한다.
- Native scope correlation과 per-thread lifecycle projection은 product DTO로 변환되기 전에 보존되어야 하지만 독립 public package일 필요는 없다.
- [제품 실행 root를 분리한다](../../../adr/0006-separate-package-app-data-and-semester-workspace-roots.md)의 workspace 경계, `ModelingRun`, browser-safe DTO, SSE와 user-facing retry/queue 같은 product concern이 native lifecycle authority를 덮어쓰지 않는 경계를 보여야 한다.
- Shared conversation abstraction의 깊이와 추출 시점은 첫 tracer와 실제 consumer 수로 검증한다.
