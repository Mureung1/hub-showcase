## Question

Workspace-local `AGENTS.override.md`, `.codex/`와 descriptor 밖 Skill entry가 bundle-valid 판정과 별개로 effective-native-context gate를 닫고 bytes를 보존하는 negative smoke는 무엇인가? Conflicting `AGENTS.md`, `.codex/`와 `.agents/skills/`가 있는 parent Git fixture 안에 workspace를 만들어 fixed project boundary가 ancestor project entry를 배제하고 actual pinned Codex의 workspace·repository scope에는 package-declared workspace instructions·Skills만 발견되며 ancestor·user 항목은 배제됨을 어떻게 검증할 것인가? `Semester Ready` 전 `thread/start`·`turn/start`·Skill input이 한 번도 없고 bundle 설치가 App mutation만으로 끝났음을 어떤 trace로 증명할 것인가? Ticket 011 single envelope의 `approved`, `prepared`, `discard_requested`, `active_ready` commit 직전·직후, Browser response 유실, duplicate tab/approve, Browser close와 primary `SIGKILL`을 fault-inject해 old-or-new complete state만 관찰되고 same transaction·same discard intent로 수렴함을 어떤 crash trace로 증명할 것인가? Discard의 markerless empty·target absent·nonempty replay와 transition 중 concurrent login·cancel·logout race가 각각 bounded cleanup과 shared account/Runtime lease로 수렴함을 어떻게 증명할 것인가? Bundle-valid pending 기록 뒤 auth-only Runtime close, workspace Runtime start, fresh account read와 active Ready pointer commit 사이 각 interruption에서 재실행이 Ready를 합성하거나 discard를 제안하지 않고 같은 transaction에 join해 retry·reauth로 수렴함을 어떤 crash trace로 증명할 것인가? Actual GitHub에서 관찰한 redirect와 강제 중단 뒤 resume 또는 safe full restart, network 차단 verified-cache reuse와 retained archive offline repair, corrupt archive reacquisition, unavailable asset의 no-auto-downgrade와 downloaded Mach-O의 quarantine·Gatekeeper·native execution을 어떤 black-box evidence로 남길 것인가? `200/206/416` 전체 matrix와 synthetic prior descriptor의 exact-pair rollback contract는 scripted resolver integration이 소유한다. 첫 public release의 public smoke는 rollback command가 노출되지 않고 current descriptor와 executed Runtime identity가 일치함을 검증하며, unavailable current + seeded older의 no-auto-downgrade와 실제 이전 public pair가 생긴 뒤의 still-supported rollback command를 별도 소유한다. 정상 종료 뒤 같은 command가 exact Runtime cache·격리 OAuth session·active workspace를 재사용하고 `WorkspaceManifest`·workspace instruction/Skill bundle·effective-context validation 뒤 setup wizard 없이 Ticket 012의 compact semester status center를 여는 `ready-relaunch`와 complete process-tree cleanup을 어떤 자동·수동 trace로 검증할 것인가? Unsupported prerequisite, network interruption, hash mismatch·corrupt cache, auth cancel·expiry, setup conflict와 recovery·rollback을 어떤 isolated profile과 expected observable outcome으로 검증해야 product release smoke가 green인가? 자료 import·학업 action·confirmed academic state는 이 release smoke에 포함하지 않는다.

## Answer

Clean-machine gate는 한 거대한 E2E가 아니라 같은 `candidateDigest`를 참조하는 다섯 evidence class의 합성으로 고정한다.

| Class | 책임 |
| --- | --- |
| `resolver_scripted` | Fake transport의 `200/206/416`, malformed range, retry, corrupt cache/archive, unavailable asset와 synthetic prior exact pair |
| `setup_deterministic(I0)` | Production setup Module의 모든 durable commit boundary, response loss, duplicate approve, discard와 account/Runtime lease race |
| `packed_black_box(I1)` | G1 exact `.tgz`를 test hook 없이 실행한 signed-out preflight, package resource failure, host·signal cleanup |
| `prepublication_live(I2)` | 같은 candidate bytes의 real managed OAuth, actual pinned Codex, hostile native context, quarantine와 representative `SIGKILL` |
| `exact_public(S7)` | 실제 public npm exact version과 immutable GitHub Runtime asset의 clean first-run·Ready·relaunch·cleanup |

S7만 actual public smoke다. [Ticket 015](015-publication-release-gates.md)의 `S5 npm green ∧ 모든 injected GAT retired` 뒤에만 열며, public source·npm·Runtime identity와 workspace bundle digest가 I0–I2의 retained evidence와 같아야 한다. 새 macOS user 또는 초기화된 Apple Silicon VM, default Gatekeeper, supported Node `>=22.12 <23`·npm 10·Chrome, repository/npm project 밖 cwd에서 AY-PLE package/cache/auth/workspace가 없는 baseline을 먼저 증명한다. OS에 Python executable이 존재하는지 자체를 oracle로 삼지 않고 process tree의 executable path로 repository/system Python을 전혀 쓰지 않았음을 확인한다.

S7은 먼저 G1/S2 public README·release card의 사용자 표시 command `npx ay-ple@<exact-version>`을 그대로 실행해 npm prompt를 사람이 승인하고, 정상 종료 뒤 `npx --yes ay-ple@<exact-version>`으로 automated `ready-relaunch`를 수행한다. 두 command는 같은 exact package spec이다. Pages Landing은 S7 뒤에 열리고 실제 body equality는 Ticket 015의 S9가 판정한다. Direct S7 phase는 `candidate_bound → clean_baseline → preflight_passed → runtime_verified → local_ui_available → account_connected → workspace_approved_prepared → workspace_runtime_context_verified → semester_ready → ready_relaunch → clean_shutdown` 순서이며, retained I2 instruction-source conformance가 같은 candidate digest인지 별도 blocking assertion으로 확인한다. Dynamic loopback Origin, host/listener/Runtime/writer 최대 1개, exact Runtime만의 download·verification·launch, app-owned OAuth와 scaffold, fresh account·manifest·bundle·context validation, orphan/port/lease 0이 blocking oracle이다.

Ready 전에는 `thread/start`·`thread/resume`·`turn/start`·Skill input이 모두 0이고 bundle 설치는 app mutation만으로 끝난다. `prepared`의 app-side manifest·bundle·conflict scan 뒤 auth-only Runtime을 완전히 닫고 exact workspace Runtime을 시작하며, internal non-Browser production port의 `config/read(cwd=<workspace>, includeLayers=true)`·`skills/list(cwds=[<workspace>], forceReload=true)`와 fresh ChatGPT read를 통과해야 Ready를 commit한다.

Instruction-source probe는 S7의 숨은 test hook이 아니라 retained I2 conformance다. I2 product가 Ready 뒤 secret-free exact launch attestation을 남기고 정상 종료하면, public tarball에서 제외된 repository-only harness가 같은 executable·argv/config·canonical cwd·controlled `HOME`·`CODEX_HOME`으로 Runtime 하나를 재현한다. `thread/start(cwd=<workspace>, ephemeral=true)` response의 cwd, `thread.ephemeral == true`, `thread.path == null`, Turn 0과 `instructionSources`만 확인하고 `thread/unsubscribe`·Runtime close 뒤 rollout/process/session 0을 확인한다. Archive/delete·Turn·별도 Browser/API route는 없다. Repository-scope source·Skill은 package declaration과 exact match하고 hostile ancestor·ambient-user canary는 0이어야 한다. SYSTEM/ADMIN scope는 기록한다. 이 I2 failure는 candidate를 막지만 Ready 전 production guard를 소급 대체하지 않는다.

Workspace와 recovery는 [Ticket 011](011-bootstrap-and-setup-recovery.md)의 single envelope를 그대로 검증한다. `approved → prepared → active_ready`의 file write·sync·rename·directory sync·readback 직전·직후와 response loss·duplicate request는 I0 deterministic failpoint가 모두 닫는다. Actual `SIGKILL`은 exhaustive timing을 가장하지 않고 외부에서 식별되는 대표 checkpoint만 I2/S7에서 실행한다. Matching `owned_incomplete`는 root identity와 `discard_requested`를 먼저 durable하게 남기고 receipt-known exact app-created entry만 no-follow로 지운 뒤 same-identity empty root와 envelope를 정리한다. 각 unlink·`rmdir`·state clear의 직전·직후도 fault-inject한다. Durable intent가 없는 markerless empty, unknown·modified nonempty, symlink·identity drift, admitted/prepared/Ready target은 삭제하지 않는다. Missing declared file만 explicit absent-only recovery를 허용하고 modified·extra·context conflict는 bytes를 보존한 `manual_recovery_required`로 닫는다.

S7 actual GitHub lane은 redirect 한 번과 partial sync 뒤 재실행을 관찰해 valid `206` resume 또는 `200/416` safe restart를 통과하고 final digest를 다시 확인한다. I2는 retained local candidate 또는 non-public controlled transport만 사용하며 public GitHub readback을 주장하지 않는다. 전체 `200/206/416` matrix와 unavailable current + seeded older의 no-auto-downgrade·synthetic prior rollback은 scripted resolver가 소유한다. Public Runtime-cache와 retained-archive repair는 S7의 별도 profile에서 GitHub delivery만 선택적으로 차단해 npm/provider dependency와 섞지 않는다. 첫 public release S7은 rollback command가 노출되지 않고 current descriptor와 executed Runtime identity가 일치함만 실제로 검증한다.

Default Gatekeeper를 바꾸거나 quarantine xattr를 삭제하지 않는다. Exact digest, 각 Mach-O의 `codesign --verify --strict`, untouched actual native execution이 green이어야 한다. `spctl`과 xattr 존재는 top-level `.app`이 아닌 CLI archive에서 단독 blocking oracle이 아니며, actual launch가 막히면 signing/packaging 결정을 다시 열어야 한다.

Browser tab close는 setup/host cancellation이 아니다. 모든 tab을 닫아도 foreground operation이 계속되고 exact Origin reopen·duplicate invocation은 같은 transaction을 observe/join해야 한다. Host lifecycle은 별도 profile의 `SIGHUP`·`SIGINT`·`SIGTERM`과 representative primary `SIGKILL`로 검증하며 bounded child/port/lease cleanup이 product 자체로 끝나야 한다.

각 destructive/network/auth case는 fresh OS user 또는 reverted VM을 기본으로 하며 npm cache, Browser profile, app data, `CODEX_HOME`·auth, Runtime cache, workspace/hostile parent와 process namespace를 격리한다. 실제 public root selector가 없는데 `HOME` override만으로 clean을 합성하지 않는다. 증거는 candidate, environment, ordered phase/assertion, fault boundary, process graph, artifact digest와 terminal result를 가진 append-only run으로 남긴다. Native RPC raw response·config·Skill content·absolute path는 저장하지 않고 method/count, root-aliased layer/source·relative Skill path/scope/digest와 ephemeral assertions만 allowlist한다. OAuth verification URL·user code·login ID·token/JWT·auth file hash·email·signed redirect query·raw provider error는 owner-only bundle에도 저장하지 않는다. Public receipt에는 root alias·coarse outcome·candidate/evidence digest만 싣는다. `unknown`, inferred source, manual security override, broad/harness cleanup으로만 사라진 process가 있으면 green이 아니다.

현재 repository에는 public package/host/Landing, RuntimeResolver, pre-workspace managed OAuth, v3 workspace/setup envelope, production `SetupJourney`·Compact Ready UI·Browser-safe projection, two-stage native context port/probe, RC/publication ledger와 smoke recorder가 없어 이 smoke를 아직 실행할 수 없다. Ticket 012 UI는 immutable prototype evidence일 뿐 production 구현이 아니다. 이 ticket의 `resolved`는 release protocol을 결정했다는 뜻이지 현재 candidate가 green이라는 뜻이 아니다. 공식 근거, isolated profile matrix, exact trace와 current gap은 [Clean-machine public `npx` smoke protocol 연구](../assets/clean-machine-smoke-protocol-research.md)에 기록했다.
