# 기획서 — 로컬 마감 할인 매칭 플랫폼 (가제: "떨이" / "마감임박")

## Context (배경 · 왜 만드는가)

로컬 카페·베이커리·음식점은 **당일 소진해야 하는 재고**(빵, 디저트, 신선식품, 반찬 등)를 매일 떠안는다. 마감 시간에 남은 재고는 대부분 폐기되어 **직접적인 금전 손실 + 음식물 쓰레기**로 이어진다. 사장님 입장에서는 "반값이라도 팔면 이득"이지만, 이를 **제때 알릴 채널이 없다**(인스타에 올리기엔 늦고, 단골 문자는 번거로움).

반대로 소비자(특히 지역 주민·대학생)는 **가성비 있게 좋은 가게의 상품**을 사고 싶지만, 어느 가게가 언제 마감 할인을 하는지 알 방법이 없다.

이 프로젝트는 **마감 임박 재고를 실시간으로 등록하고, 관심 있는 근처 사용자에게 알림을 보내 픽업으로 연결**하는 양면 매칭 플랫폼을 만든다. 기존 검증된 모델(Too Good To Go, 라스트오더)이 존재하므로 **수요는 검증됨** — 차별화는 초기 공략 지역의 밀도와 등록/알림 UX에 둔다.

**이번 단계의 산출물은 코드가 아니라 "기획 문서"다.** (문제 정의 · 사용자 시나리오 · 핵심 기능 · 데이터 모델 초안 · MVP 범위 확정)

---

## 확정된 기획 결정사항

| 항목 | 결정 |
|---|---|
| 거래 방식 | **MVP = 예약 + 현장결제.** 앱은 예약/재고차감/픽업코드만 담당. 결제 다각화(PG 연동)는 차후 |
| 타겟 사용자 | **제품은 범용**(지역 주민 누구나). 단 **초기 공략점은 대학가 1곳**으로 밀도 확보 (콜드 스타트 대응 + 데모·검증 용이) |
| 알림 범위 | **관심 카테고리 매칭 + 관심 가게(즐겨찾기)** 위주. 여기에 **위치 조건**을 사용자가 선택: ⓐ "N km 반경 안에 있을 때만 받기" / ⓑ "항상 받기" |

## 1. 문제 정의

**공급자(자영업자) 측**
- 당일 소진 재고가 마감 시점에 남으면 폐기 → 순손실
- 남은 재고를 즉시 알릴 저비용 채널이 없음
- 재고 처리를 위한 별도 인력·시간이 없음 (등록이 30초 안에 끝나야 함)

**수요자(사용자) 측**
- 근처 어느 가게가 지금 마감 할인 중인지 알 수 없음
- 좋은 가게의 상품을 저렴하게 사고 싶은 니즈 (특히 가성비 민감층)
- 알림이 너무 많으면 피로 → 관심 카테고리·가게·거리로 걸러야 함

**핵심 문제 한 줄:** "버려질 재고"와 "그걸 싸게 살 근처 사람"이 서로를 실시간으로 찾지 못한다.

---

## 2. 사용자 시나리오

### 시나리오 A — 사장님(공급자)
1. 마감 2시간 전, 팔다 남은 크루아상 5개가 보인다.
2. 앱에서 **상품 등록**: 사진 1장 + 카테고리(베이커리) + 수량(5) + 원가/할인가 + 픽업 가능 시간대.
3. 등록 즉시, 조건에 맞는 근처 사용자에게 알림이 나간다.
4. 예약이 들어오면 실시간으로 남은 수량이 줄어드는 걸 확인.
5. 손님이 오면 **픽업코드/바코드를 확인**하고 상품을 건네준 뒤 완료 처리.

### 시나리오 B — 사용자(수요자)
1. "베이커리" 카테고리 관심 등록 + 자주 가는 가게 즐겨찾기 + 위치 조건("2km 안에 있을 때만 알림").
2. 마감 할인 알림 수신: "○○베이커리 크루아상 5개, 4,000→2,000원, 21시까지 픽업".
3. 앱에서 목록/지도로 확인 후 **예약**(수량 선택) → 재고가 즉시 차감되고 **픽업코드 발급**.
4. 픽업 시간 내에 매장 방문 → 코드 제시 → **현장에서 결제**하고 수령.

### 시나리오 C — 선착순 경합 (백엔드 하이라이트)
1. 인기 매장이 디저트 3개를 등록.
2. 동시에 여러 사용자가 예약 시도 → **동시성 제어로 정확히 3명만 성공**, 나머지는 "품절" 처리.

## 3. 핵심 기능

### 3.1 상품 등록 (공급자)
- 필드: 사진, 상품명, **카테고리**(베이커리/디저트/신선식품/반찬/음료 등), 수량, 원가, 할인가, 픽업 가능 시간대, (자동) 매장 위치
- 요구: 등록이 매우 빠를 것(사진+수량 중심). 마감 임박이라 **유효시간(픽업 마감)** 지나면 자동 비활성화

### 3.2 알림 (수요자 타게팅) — 이번 기획의 핵심 로직
알림 발송 대상 판정 규칙:
- **카테고리 매칭**: 등록 상품의 카테고리가 사용자의 관심 카테고리에 포함 → 후보
- **즐겨찾기 매장**: 등록 매장이 사용자의 즐겨찾기에 포함 → 후보
- **위치 조건 (사용자별 설정)**:
  - ⓐ *반경 조건형*: 사용자의 현재/기준 위치가 매장 반경 **N km 이내일 때만** 알림
  - ⓑ *항상형*: 거리와 무관하게 관심 조건이면 알림
- 최종 발송 = (카테고리 매칭 OR 즐겨찾기) AND (위치 조건 통과)
- MVP 알림 채널: **인앱 알림/폴링 먼저**, 여유 시 푸시(FCM 등)

### 3.3 예약 & 실시간 재고 차감 (선착순)
- 예약 시 원자적으로 재고 차감(오버셀 방지). 재고 0이면 예약 불가
- 예약 성공 시 **픽업코드/바코드 발급**
- (정책) 노쇼 대비: 픽업 마감 시간 지나면 예약 자동 만료 → 재고 복원(정책 결정 필요, 아래 리스크 참고)

### 3.4 픽업 확인 (공급자)
- 사장님이 코드 입력/바코드 스캔으로 예약 검증 → 완료 처리
- 완료 시 통계(판매 수량) 반영

## 4. 데이터 모델 초안 (엔티티 수준)

- **User**: id, 이름, 위치(기준 좌표), 관심 카테고리[], 위치조건(반경형 N km / 항상형)
- **Store**: id, 이름, 위치(lat/lng), 카테고리, 사장님 계정
- **Favorite**: user_id, store_id (즐겨찾기)
- **Deal(마감상품)**: id, store_id, 상품명, 카테고리, 사진, 원가, 할인가, **총수량 / 남은수량**, 픽업 시작~마감 시각, 상태(활성/품절/만료)
- **Reservation**: id, deal_id, user_id, 수량, 픽업코드, 상태(예약/픽업완료/만료), 생성시각

핵심 불변식: `Deal.남은수량 = 총수량 - Σ(활성 Reservation.수량)`, 항상 ≥ 0.

---

## 5. MVP 범위

**포함 (4주 내 "작동+시연" 목표)**
1. 사장님 상품 등록 / 픽업 확인
2. 사용자 관심 설정(카테고리·즐겨찾기·위치조건) + 알림(인앱)
3. 목록/지도 조회
4. 예약 + 선착순 재고 차감 + 픽업코드 발급
5. (백엔드 하이라이트) 동시성 제어 + 위치 기반 조회

**제외 (Out of Scope, 차후)**
- 앱 내 사전 결제 / PG 정산 / 환불
- FCM 실시간 푸시 (여유 시)
- 리뷰·평점, 사장님 정산 리포트, 실제 대규모 사용자 확보

---

## 6. 백엔드 하이라이트 (프로젝트 셀링 포인트)

이 두 가지가 프로젝트의 기술적 매력 포인트이며, 여기에 집중 투자한다.

- **선착순 재고 동시성**: 단일 DB 기준 원자적 `UPDATE 남은수량 = 남은수량 - :qty WHERE deal_id = :id AND 남은수량 >= :qty` 또는 비관적 락(`SELECT ... FOR UPDATE`)부터 시작. **부하 테스트(k6/Locust)로 "락 미적용 시 오버셀 발생 → 적용 후 정확히 소진"을 그래프로 증명**하면 강력한 데모.
- **위치 기반 조회**: 먼저 PostGIS / Haversine으로 동작 → Redis GeoSpatial 인덱스를 "최적화 단계"로 도입해 개선 전후 비교(스토리텔링). 알림 대상 판정에도 이 쿼리 재사용.

## 7. 리스크 & 미결 정책

- **콜드 스타트**: 초기 공략점을 대학가 1곳으로 좁혀 밀도 확보. 데모는 사장님 계정 시딩으로 시연.
- **경쟁 서비스 존재**: 차별점 한 줄 필요(대학가 밀도 / 30초 등록 UX / 세밀한 알림 조건). 심사 대비 준비.
- **노쇼 정책 (미결)**: 예약 후 안 오면? → 픽업 마감 후 자동 만료·재고 복원 정책 확정 필요. MVP에선 단순 만료로 시작 권장.
- **위치 기준점 (미결)**: 사용자의 "위치"를 실시간 GPS로 볼지, 등록한 기준 주소로 볼지 결정 필요. MVP는 기준 주소 권장(단순).

---

## 8. 기획 검증 방법 (이 문서의 다음 단계)

1. **사장님 인터뷰 2~3곳**: 실제로 마감 재고가 얼마나 남는지, "30초 등록"이면 쓸지 확인
2. **사용자 인터뷰 5명 내외**: 알림 조건(카테고리/거리)이 실제 니즈와 맞는지, 현장결제·픽업이 허들이 아닌지
3. **경쟁 서비스 비교표**: 라스트오더/Too Good To Go 대비 우리 차별점 1줄 도출
4. 인터뷰 결과로 노쇼·위치기준 정책 확정 → 이후 화면 설계(와이어프레임)·API 설계 단계로 진행
