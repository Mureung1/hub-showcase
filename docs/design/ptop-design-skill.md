# PtoP Design Skill

## 목적

이 Skill은 PtoP 화면을 새로 만들거나 수정할 때 사용하는 디자인 작업 절차다.  
단순히 예쁘게 꾸미는 것이 아니라, 사용자가 Repository를 입력하고 분석 결과를 확인하는 핵심 흐름이 가장 먼저 보이도록 만드는 것이 목표다.

디자인 기준은 `Mascoat.png`의 포피(Popy) 마스코트와 `docs/design-system.md`를 따른다.

## 사용 시점

다음 작업을 할 때 이 Skill을 적용한다.

- PtoP 메인 화면을 수정할 때
- HTML/CSS 프로토타입을 수정할 때
- Repository 입력, 로딩, 결과, 오류 화면을 만들 때
- 마스코트나 로고를 화면에 배치할 때
- 디자인이 너무 딱딱하거나 AI가 만든 듯해 보인다는 피드백을 반영할 때

## 디자인 원칙

### 1. 핵심 행동을 첫 화면에 둔다

PtoP의 첫 화면은 서비스 설명보다 Repository URL 입력이 먼저 보여야 한다.

반드시 포함할 요소:

- PtoP 로고
- GitHub Repository URL 입력창
- `분석 시작` 버튼
- “분석하고 싶은 프로젝트의 Git Repository 주소를 입력해보세요.” 수준의 짧은 안내 문구

피해야 할 요소:

- 첫 화면에 긴 서비스 소개 문단 배치
- `Project to Portfolio` 같은 중복 설명을 크게 반복
- 입력창보다 마스코트나 장식 이미지를 크게 배치

### 2. 입력 → 로딩 → 결과 흐름을 실제 동작처럼 보여준다

프로토타입이라도 단순 소개 페이지처럼 보이면 안 된다.  
사용자가 URL을 입력하고 분석을 시작하면 상태 변화가 보여야 한다.

필수 상태:

- 기본 상태: URL 입력 가능
- 로딩 상태: 분석이 진행 중임을 보여주는 spinner
- 성공 상태: 참여자, 기여도, 주요 작업 결과
- 오류 상태: 잘못된 URL 또는 API 실패 안내

### 3. 성공 결과는 실제 근거 기반으로 보여준다

분석 결과는 하드코딩된 가짜 성공 데이터처럼 보이지 않아야 한다.

허용하는 결과:

- GitHub API에서 가져온 참여자
- commit 수 기준 기여도
- 최근 commit message 기반 주요 작업
- Repository 원문 링크

피해야 할 결과:

- 실제 요청과 관계없는 임의 프로젝트명
- 사용자의 역할을 확정적으로 단정하는 문장
- 근거 없는 “프론트엔드 80% 담당” 같은 표현
- 실패했는데도 성공한 것처럼 보이는 mock 결과

### 4. 포피 마스코트는 보조 역할로만 사용한다

포피는 PtoP의 친근한 인상을 만드는 자산이지만, 핵심 기능을 가리면 안 된다.

사용하기 좋은 위치:

- 서비스 소개 섹션
- 빈 상태 안내
- 분석 완료 안내
- 문서나 PR 첨부 이미지

피해야 할 위치:

- Repository 입력창 바로 옆에서 입력 흐름을 방해하는 위치
- 분석 결과 수치 위
- 모든 섹션의 반복 장식
- 로딩 spinner 자체

### 5. 검정 border에 의존하지 않는다

PtoP는 검정색, 흰색, 민트를 사용하지만 검정 테두리로 화면을 나누면 딱딱해 보인다.

구분 방식 우선순위:

1. 충분한 여백
2. 밝은 민트 또는 흰색 배경 면
3. 약한 회색/민트 border
4. 부드러운 shadow

피해야 할 스타일:

- 두꺼운 검정 border
- 섹션마다 강한 외곽선
- 카드 안에 카드가 중첩되는 구조
- 불필요한 선이 많은 대시보드 느낌

## 화면별 작업 절차

### 메인 입력 화면

1. 로고를 상단 중앙에 둔다.
2. 로고 바로 아래에 Repository 입력창을 둔다.
3. 입력창과 버튼은 하나의 pill 형태로 묶는다.
4. 입력창 아래에 짧은 안내 문구를 둔다.
5. 첫 화면에서 아래 소개 섹션이 살짝 이어지도록 세로 여백을 조정한다.

검토 질문:

- 사용자가 처음 봤을 때 어디에 URL을 넣어야 하는지 바로 아는가?
- 로고가 입력창보다 과하게 크지 않은가?
- 설명 문구가 입력 행동을 방해하지 않는가?

### 분석 로딩 화면

1. URL 제출 후 버튼을 비활성화한다.
2. 민트 컬러 기반 spinner를 보여준다.
3. “Repository를 분석하고 있어요”처럼 현재 동작을 설명한다.
4. 로딩 중 레이아웃이 갑자기 흔들리지 않도록 결과 영역의 폭을 유지한다.

검토 질문:

- 사용자가 분석이 진행 중이라고 느낄 수 있는가?
- spinner가 로고나 마스코트보다 기능 상태처럼 보이는가?
- 로딩 문구가 짧고 명확한가?

### 분석 결과 화면

1. Repository 이름과 원문 링크를 먼저 보여준다.
2. 참여자 목록과 commit 수 기준 기여도를 보여준다.
3. 주요 작업은 최근 commit message 기반으로 보여준다.
4. commit 수는 참고 지표라는 뉘앙스를 유지한다.

검토 질문:

- 참여자와 기여도가 한눈에 보이는가?
- 주요 작업의 근거가 commit message라는 점이 드러나는가?
- 결과가 사용자의 역할을 과장하지 않는가?

### 오류 화면

1. 실패 원인을 짧게 안내한다.
2. 입력창은 유지해서 사용자가 바로 수정할 수 있게 한다.
3. 가짜 성공 데이터를 대신 보여주지 않는다.
4. 공개 Repository인지, URL 형식이 맞는지 확인하도록 안내한다.

검토 질문:

- 사용자가 다음 행동을 알 수 있는가?
- 오류가 너무 공격적인 빨간색으로 보이지 않는가?
- 실패 상황을 숨기지 않았는가?

### 소개/랜딩 섹션

1. 첫 화면 아래로 스크롤했을 때 서비스 소개가 이어지게 한다.
2. 대상, 문제, 해결, 형태를 짧은 카드로 보여준다.
3. 핵심 기능은 2~3개 카드로 정리한다.
4. 마스코트는 필요할 때만 작게 사용한다.

검토 질문:

- 소개 섹션이 첫 화면의 입력 흐름보다 앞서지 않는가?
- 긴 문단보다 구조화된 카드로 읽히는가?
- 마스코트가 정보보다 더 눈에 띄지 않는가?

## 컬러와 컴포넌트 규칙

기본 색상은 `docs/design-system.md`의 CSS 변수를 따른다.

```css
--color-ink: #151817;
--color-muted: #565656;
--color-paper: #ffffff;
--color-soft-paper: #fbfffd;
--color-mint: #62d6a5;
--color-mint-dark: #26a875;
--color-mint-soft: #e6fbf2;
--color-mint-line: #a8d9c3;
--color-line: #dce8e2;
```

컴포넌트 기본값:

- 버튼: 민트 배경, pill 형태, 굵은 텍스트
- 입력창: 흰 배경, pill 형태, 충분한 좌우 여백
- 카드: 흰색 또는 아주 밝은 민트 배경, 약한 border, 부드러운 shadow
- spinner: 로고 이미지가 아닌 CSS 기반 민트 spinner
- 링크: 민트 다크 컬러와 굵은 텍스트

## 작업 전 체크리스트

- [ ] 이번 작업이 입력, 로딩, 결과, 오류 중 어느 화면에 영향을 주는지 확인했다.
- [ ] `docs/design-system.md`의 컬러와 컴포넌트 규칙을 확인했다.
- [ ] 마스코트가 필요한 작업인지, 단순 장식인지 판단했다.
- [ ] 실제 데이터 흐름과 무관한 하드코딩 결과를 추가하지 않기로 했다.

## 작업 후 체크리스트

- [ ] 첫 화면에서 Repository 입력창이 가장 먼저 보인다.
- [ ] URL 입력 후 로딩 상태가 명확히 보인다.
- [ ] 결과 화면은 참여자, 기여도, 주요 작업 순서로 읽힌다.
- [ ] 오류 상황에서 임의 성공 데이터를 보여주지 않는다.
- [ ] 검정 border가 과하게 쓰이지 않았다.
- [ ] 마스코트가 핵심 정보를 가리지 않는다.
- [ ] 데스크톱과 모바일에서 텍스트와 버튼이 잘리지 않는다.

## 피드백 반영 규칙

사용자가 다음과 같은 피드백을 주면 이 Skill을 수정한다.

- “AI가 만든 것 같다”
- “너무 딱딱하다”
- “핵심 기능이 잘 안 보인다”
- “마스코트가 너무 튄다”
- “검정 경계선이 부담스럽다”
- “첫 화면에서 바로 입력하고 싶다”

피드백을 받으면 단순히 한 화면만 고치지 말고, 같은 문제가 다시 생기지 않도록 이 Skill의 원칙이나 체크리스트도 함께 보강한다.
