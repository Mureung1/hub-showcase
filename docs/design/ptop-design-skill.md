# PtoP Design Skill

## 목적

이 문서는 PtoP 화면을 만들거나 수정할 때 반복해서 사용하는 디자인 절차다. 게임형 작업실의 몰입감과 Repository 분석 결과의 신뢰성을 함께 유지하는 것이 목표다.

항상 다음 문서를 먼저 확인한다.

- 공통 디자인 규칙: `docs/design/design-system.md`
- 작업실 설계와 와이어프레임: `docs/design/game-workspace-design.md`
- 에셋 라이선스: `docs/research/game-asset-license.md`
- 사용자 흐름: `docs/plans/plan.md`

## 적용 범위

- 랜딩 페이지와 GitHub 로그인
- 2D 작업실과 컴퓨터 상호작용
- Repository 입력 모달
- 분석 진행과 Poppy 회고 대화
- 분석 결과와 작업실 복귀
- 모바일 대체 UI

## 작업 절차

### 1. 사용자 행동을 한 문장으로 정의한다

화면이 무엇을 보여주는지보다 사용자가 무엇을 끝내야 하는지 먼저 적는다.

좋은 예:

```text
사용자가 새 분석 컴퓨터 앞에서 Repository URL을 입력하고 분석을 시작한다.
```

피해야 할 예:

```text
예쁜 컴퓨터 모달을 만든다.
```

한 화면에서 주요 행동이 두 개 이상이면 화면 또는 단계를 분리한다.

### 2. 게임과 웹 UI의 책임을 나눈다

다음 기준을 사용한다.

| 질문 | 담당 |
| --- | --- |
| 캐릭터가 어디에 있는가? | Phaser |
| 컴퓨터와 상호작용 가능한 거리인가? | Phaser |
| 어떤 Repository를 분석할 것인가? | React |
| API가 성공했는가? | React |
| 모달과 대화창을 어떻게 보여줄 것인가? | React |

Phaser Scene에서 API를 호출하거나 React DOM을 직접 조작하지 않는다.

### 3. 상태를 먼저 그린다

구현 전에 해당 화면의 상태를 나열한다.

- 기본
- 접근 또는 focus
- 입력
- 진행
- 성공
- 빈 상태
- 오류
- 비활성

게임 상호작용은 다음 상태를 추가한다.

- 상호작용 대상 없음
- 대상 접근
- 상호작용 가능
- 모달 또는 대화 중
- 작업 완료

### 4. 작은 와이어프레임으로 검증한다

와이어프레임에는 다음 정보만 표시한다.

- 캐릭터 위치
- 상호작용 대상
- 주요 행동
- 상태 안내
- 닫기 또는 돌아가기

장식, 그림자, 세부 애니메이션은 흐름이 확정된 뒤 결정한다.

### 5. 에셋 출처를 확인한다

에셋을 코드에 추가하기 전에 `docs/research/game-asset-license.md`에 기록한다.

- 공식 원문 URL
- 제작자
- 라이선스
- 상업적 사용과 수정 가능 여부
- 크레딧 요구사항
- 공개 Repository 포함 가능 범위
- PtoP에서 실제로 사용할 파일

공식 원문을 확인할 수 없으면 후보에서 제외한다.

### 6. 책임 단위로 파일을 나눈다

다음 책임은 같은 파일에 넣지 않는다.

- Phaser 인스턴스 생성과 React UI
- 캐릭터 입력과 상호작용 판정
- 에셋 경로와 Scene 상태
- 분석 API와 게임 이벤트
- 대화 UI와 회고 저장 API

새 파일을 만들기 전에 다음을 확인한다.

- 파일의 역할을 한 문장으로 설명할 수 있는가?
- 외부에서 사용하는 인터페이스가 명확한가?
- 단독 테스트가 가능한가?
- 이름만 다른 중복 추상화가 아닌가?

### 7. 기능과 시각 표현을 함께 검증한다

UI 작업을 완료하기 전에 다음 순서로 확인한다.

1. 테스트와 타입 검사
2. 데스크톱 브라우저
3. 작은 모바일 viewport
4. 키보드만 사용한 흐름
5. `prefers-reduced-motion`
6. 네트워크 오류와 빈 상태
7. Canvas가 비어 있지 않은지 pixel 확인

## 화면별 기준

### 랜딩 페이지

- 작업실 경험을 보여주는 영상 또는 poster를 첫 화면에 사용한다.
- GitHub 로그인 행동이 첫 viewport에서 보여야 한다.
- 로그인하지 않아도 서비스 목적을 이해할 수 있어야 한다.
- 로그인 후에는 다시 가입을 유도하지 않고 작업실 진입을 제공한다.

### 작업실

- 기본 캐릭터로 바로 이동할 수 있어야 한다.
- 새 분석 컴퓨터와 이전 분석 컴퓨터가 구분되어야 한다.
- 상호작용 가능할 때만 keycap 안내를 표시한다.
- 맵을 둘러보지 않아도 모바일 목록 UI에서 같은 기능에 접근할 수 있어야 한다.

### Repository 입력

- URL 입력을 가장 먼저 focus한다.
- GitHub ID는 로그인 정보로 자동 입력하고 수정 가능한 보조 입력으로 제공한다.
- 형식 오류, 비공개 Repository, rate limit, 서버 오류를 구분한다.
- 제출 중 중복 요청을 차단한다.

### Poppy 대화

- 질문은 한 번에 하나만 보여준다.
- 한 문장 답변, 건너뛰기, 이전 답변 수정이 가능해야 한다.
- 분석 완료가 대화를 끊지 않아야 한다.
- Poppy는 질문과 상태를 안내하지만 분석 근거를 대신하지 않는다.

### 분석 결과

- Repository 근거, 사용자 회고, AI 해석을 구분한다.
- 수치보다 기술적 도전과 근거의 연결을 우선한다.
- 사용자가 AI 후보를 선택하거나 직접 경험을 추가할 수 있어야 한다.
- 작업실 복귀 후 완료된 Repository 컴퓨터가 추가되어야 한다.

## 컴포넌트 검토 질문

- 이 컴포넌트가 API, 게임 상태, 표현을 동시에 관리하고 있지 않은가?
- props가 너무 많다면 화면 책임이 섞인 것은 아닌가?
- 조건문이 많다면 상태 모델을 별도 순수 함수로 분리할 수 있는가?
- CSS가 전역 `style.css`에 계속 누적되고 있지 않은가?
- 게임 기능을 제거해도 분석 기능이 동작하는가?

## 작업 전 체크리스트

- [ ] 사용자 행동과 완료 조건을 한 문장으로 적었다.
- [ ] 변경 대상 화면의 모든 상태를 나열했다.
- [ ] React와 Phaser 책임을 구분했다.
- [ ] 사용할 에셋의 공식 라이선스를 확인했다.
- [ ] 기존 컴포넌트와 스타일 중 재사용할 부분을 확인했다.

## 작업 후 체크리스트

- [ ] 주요 행동이 하나로 보인다.
- [ ] 모달과 대화 중 게임 입력이 멈춘다.
- [ ] 오류가 발생해도 다음 행동을 알 수 있다.
- [ ] 분석 완료가 작성 중인 회고를 중단하지 않는다.
- [ ] 키보드와 모바일 대체 흐름이 동작한다.
- [ ] 파일별 책임을 한 문장으로 설명할 수 있다.
- [ ] 테스트, 타입 검사, 빌드와 브라우저 검증을 완료했다.

## 피드백 반영 규칙

동일한 UI 문제가 반복되면 한 화면의 CSS만 수정하지 않는다.

1. 문제가 발생한 디자인 규칙을 찾는다.
2. 이 문서 또는 디자인 시스템의 기준을 먼저 수정한다.
3. 영향받는 화면을 함께 확인한다.
4. 재발을 막을 수 있는 체크리스트나 테스트를 추가한다.
