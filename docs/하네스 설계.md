# 하네스 설계 (이번 주 계획)

> 작성 2026-07-21 · 커리어 코파일럿의 **AI 갭 분석 하네스** 설계 기록.

## 목표
공고(JD) + 내 프로필(위키·GitHub 근거) → **구조화된 갭 분석 JSON**을,
**여러 모델(Claude·로컬)에서 스키마를 지키며 일관되게** 뽑는 하네스를 설계한다.
```
입력: 공고 JD + 내 프로필
  → [하네스: SCPC 형식]
출력: 갭 분석 JSON (요구역량 등급 · 개념/구현% · 갭 액션 = JobCard 모양)
```

## 가치 명제 (이번 주에 검증할 가설)
> **좋은 하네스면 작은/무료 로컬 모델로도 구조화 출력이 나온다** → 오픈소스로 풀면 사람들이 자기 구독/로컬로 쓴다.
- 원래 목표 = 오픈소스. 지금은 Claude 구독으로 baseline.
- 로컬 모델을 보는 이유: 더 작고·로컬에서 무료. "엔진을 작게·공짜로 바꿔도 틀(하네스)이 버티나"를 본다.

## SCPC 형식 적용 (위키 [[SCPC AI챌린지 (하네스 설계)]])
재사용 4단계:
1. **정답 역추적** — 정답 있는 dev 케이스에서 "이 신호→이 판단" 규칙을 **데이터로** 발굴(감 X).
2. **병렬 분해** — 차원별 서브에이전트가 규칙 도출 + 감사관이 하드코딩 검사.
3. **일반화 검증** — train/holdout 분리, **안 본** holdout으로 채점.
4. **실전 분포 점검** — 실제 공고 분포에서 규칙 발동 확인.

핵심 교훈 3개:
- **곱셈 게이팅** — 뿌리(요구역량 추출=focal)부터 맞춰야 뒷 칸(등급·갭)이 열림 → 공략 순서 강제.
- **문자매칭 ≠ 의미분류** — "Java 3년"과 "자바 경력자"를 같은 요구로. 표현 암기는 과적합.
- **구조화 출력 스키마** — 출력을 JSON 스키마로 강제.

## 역할 분담 (human-in-the-loop — 이게 최우선)
"AI랑 대화만 하면 내 역량이 안 드러난다"는 문제의식. 하네스가 **판단이 사는 층**(L5 명세 + L7 검증)이라, 여기서 사람 역량이 드러난다.

| 승현이 한다 (판단·설계 — 못 넘김) | Claude가 한다 (실행·보조) |
|---|---|
| 출력 스키마 설계 | 스키마 코드 구현 |
| 정답 루브릭/dev셋 정의 ("좋은 갭 분석이란?") | dev 케이스 수집·정리 |
| 실패 분류 (틀리면 *왜*) | 모델 호출·출력 수집, 실패 표 |
| 하네스 수정 결정 (규칙 추가? 출력 제약?) | 결정대로 프롬프트·검증기 수정 |
| Claude vs 로컬 차이 해석 → 처방 | 같은 입력 여러 모델에 돌려 diff |

> Claude는 **적대적 비평가**도 겸함 — 설계를 그냥 받지 않고 "과적합 아냐?" "이 스키마 여기서 깨져" 하고 찌른다. 결정은 승현.
> 핵심 로직(하네스 프롬프트·검증·스키마)은 **승현이 직접 타이핑**. 뼈대·반복은 Claude.

## 진행 방식: 애자일 (워터폴 아님)
설계 다 하고 나중에 붙이는 게 아니라 — **매일 = 설계 한 조각 → `/api/analyze`에 붙여 실제 JD로 돌림 → 관찰 → 수정.**

## 주간 계획 (7/21~)
| 요일 | 사이클 |
|---|---|
| 월/화 | 출력 스키마 v1 + dev셋/루브릭(승현) → 붙일 뼈대(Claude) |
| 화/수 | 하네스 v1(요구역량 추출부터) → Claude로 실제 JD → 승현이 실패 분류 |
| 수/목 | 스키마 강제·검증 + 일관성(같은 입력 N번) → 승현이 "어디가 흔들리나" 판단 |
| 목 | 엔진 스왑 + Claude vs 로컬 비교 → 승현이 차이 해석·처방 |
| 금 | holdout(안 본 공고) 검증 + 튜닝 + **결정 로그 문서화**(판단 궤적 = 역량 증거) |

## 결정 로그
- **(7/21) 스택 = Node + Express + SQLite (Spring 아님).** 원칙: *각 프로젝트는 목적에 맞게 설계한다.* 이 프로젝트 목적 = **오픈소스 배포** → clone 받아 바로 실행·가벼움이 최우선이라 Node/Express/SQLite. 나는 Java/Spring 지망이지만, Spring 실력 증명은 목적이 다른 다른 프로젝트(캡스톤·병원 스케줄링)의 몫. "강점이니 어디든 Spring"이 아니라 **목적이 스택을 정한다.**
- **(7/21) 엔진 = baseline 먼저, 어댑터 나중.** `claude -p` 하나로 baseline을 만들고, 로컬 모델 붙일 때 그 diff를 보고 어댑터 인터페이스를 추출한다. 이유: 엔진이 하나뿐인데 어댑터부터 만들면 over-engineering — "진짜 필요한 모양"은 두 번째 엔진이 알려준다.
- **(7/21) 저장소 = 로컬-퍼스트.** 오픈소스·로컬-퍼스트 철학상 클라우드(Supabase)보다 임베디드가 맞음. Node 스택이라 H2가 아니라 **SQLite**. 갭 분석 캐싱(공고·스펙 안 바뀌면 재분석 X)이 유일한 실수요. `store.js` 계층 분리 덕에 교체 비용 = 파일 하나.
- **엔진 슬롯 = 하네스의 엔진 자리.** 오픈소스 배포 시 사용자가 상황에 맞춰 고름: 구독→`claude -p` / API키→Anthropic API / 무료·로컬→Ollama. (BYO — 메인테이너는 호스팅·키 제공 안 함.)
