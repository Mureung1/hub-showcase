# 데모데이 리허설 스크립트 (초안)

> 인쇄용 아님 — 포스터 두 장을 실제로 짚어가며 말로 설명하는 연습용 초안이다. 포스터에 적힌 단어를 그대로 읽는 게 아니라 문장으로 풀어서 썼다. 그대로 외우기보다, 소리 내어 읽어보고 막히는 부분·어색한 부분을 자기 말로 바꿔가는 용도로 쓰면 된다.

## 포스터① — 프로젝트 기획 소개

**헤더**
"안녕하세요, 제 프로젝트는 REFIT이라는 AI 운동 코치입니다. 손목이나 발목같은 관절 통증이나 시간 부족으로 계획한 운동을 못 하게 됐을 때, 오늘 뭘 해야 할지 판단 없이 루틴을 대신 재편성해주는 서비스입니다."

**문제 정의**
"이 프로젝트를 시작한 문제는 저의 경험으로부터 시작했습니다. 저는 통증이나 시간 부족으로 계획한 운동을 못 할 때, 오늘 뭘 해야 할지 판단하는 데 시간을 쓰거나, 판단을 미루고 그냥 그날 운동을 안하는 날이 많았습니다. 이 두 가지 패턴 (판단에 시간 쓰는 것과 그냥 스킵하는 것) 을 각각 해결하는 게 이 프로젝트의 핵심 기능 두 개입니다."

**핵심 기능 1 — 통증 예외 재편성**
"첫 번째는 통증 예외 재편성입니다. 사용자가 통증 부위를 목록에서 선택하면, 그 부위와 관련된 관절을 쓰는 운동은 하드 필터로 제외하고, 같은 타겟 부위의 대체 운동 후보들 중에서 LLM이 하나를 고릅니다. 여기서 중요한 건, LLM이 아무 운동이나 자유롭게 추천하는 게 아니라 후보 id만 고르도록 구조적으로 강제해서(enum), 목록 밖의 운동을 지어내는 AI 환각을 차단했습니다. 그리고 마지막엔 항상 전문가 상담을 권장하는 문구를 붙입니다. 저는 의도적으로 '이 대체운동이 안전하다'는 의료적 판단은 하지 않고, 구조적으로 그 관절을 안 쓰는 운동을 고르는 것까지만 하도록 범위를 좁혔습니다."

**핵심 기능 2 — 스킵/시간부족 예외 재편성**
"두 번째는 스킵이나 시간 부족으로 세션을 건너뛸 때의 재편성입니다. 세션을 스킵하면, 이번 주 안에 비어있는 휴식일이 있는지, 그리고 같은 부위는 48시간 간격을 둬야 한다는 제약을 어기지 않는지 확인해서 재배치하거나, 안 되면 그냥 스킵으로 기록만 합니다. 이건 사용자가 거부할 수 없는 결과로 구현해놓았습니다 — 그 주의 스케줄 상태로 자동 계산되는 거니까요."

**아키텍처**
"구조는 단순한 3단입니다. 화면은 React와 Vite, 서버는 Express, DB는 Supabase PostgreSQL이고 Prisma로 ORM 연결했습니다. 화면과 서버는 JSON으로, 서버와 DB는 Prisma로 통신합니다."

**기술 스택**
"기술 스택 전체는, 화면 쪽엔 React·Vite·React Router·Tailwind CSS, 서버 쪽엔 Express·Prisma, DB는 PostgreSQL, 그리고 품질·배포 쪽엔 Vitest·Playwright·GitHub Actions·Vercel·Render를 썼습니다."

## 포스터② — AI Agent Workflow

**헤더**
"이제 두 번째 포스터는, 이 프로젝트를 AI Agent랑 어떻게 만들었는지에 대해 이야기 하겠습니다. 3주 동안 기능을 만들 때마다 반복된 협업 방식입니다."

**01 일하는 순서 (5단계 + 루프)**
"일하는 순서는 이렇습니다. 첫째, 문제 정의는 항상 제가 먼저 합니다 — 기획과 범위는 AI한테 맡기지 않고요. 둘째, 코드부터 짜지 않고 설계서를 먼저 받아서 완료 기준이랑 이 설계에 대한 장단점, 한계점 그리고 다른 다양한 방법을 출력하고 이를 검토합니다. 셋째, 여러 선택지가 있는 판단 — 예를 들면 라이브러리 선택 같은 건 AI가 정하는 게 아니라, 근거만 받고 제가 직접 고릅니다. 넷째, 구현이 끝나면 화면 캡처나 API 호출로 직접 확인하고 문제가 있다면 설계단계로 다시 돌아가 어떻게 설계가 되었는지 다시 확인하고 에러를 고치거나 논리적인 문제가 있다면 처음부터 다시 설계를 했습니다. 다섯째, 커밋은 항상 제가 직접 터미널에서 실행합니다. 그리고 다음 기능으로 넘어갈 때마다 2번 설계서부터 다시 도는 구조예요 — 문제 정의(1번)는 항상 지키는 원칙이고, 2번부터 5번까지가 기능마다 반복되는 절차입니다."

**갈리는 판단 사례**
"이 '갈리는 판단'이 두루뭉실한 얘기가 아니라는 걸 보여주려고 실제 사례를 적어놨어요. 예를 들면 대체 운동 이미지를 어디서 가져올지 — wger.de라는 사이트를 제가 직접 선택했고, E2E 테스트 도구도 Playwright랑 Cypress 중에 검토해서 Playwright를 골랐고요, 프론트-백엔드 연결 방식도 CORS 대신 프록시 방식을 채택했습니다."

**직접 확인한 방법**
"확인 방법도 구체적으로 — curl로 API를 직접 호출해보고, Prisma 스크립트로 DB를 직접 조회하고, Playwright나 브라우저로 화면을 직접 스크린샷 찍어서 확인하고, lint랑 테스트를 돌려서 회귀도 확인했어요. 그리고 배포하고 나서만 생기는 문제들도 실제로 겪었습니다 — SPA를 새로고침하면 404가 뜨는 문제, 라우터 연결 코드가 빠져있던 문제, Prisma 7 버전에 대응하면서 CommonJS에서 ESM으로 전환해야 했던 문제 같은 것들요."

**02 규칙을 CLAUDE.md에 박아둔다**
"이 원칙들을 그냥 마음가짐으로 두지 않고, CLAUDE.md라는 파일에 규칙으로 박아뒀어요. 코드 짜기 전에 설계서부터 쓰라는 design-first, 선택지가 여럿인 판단은 먼저 물어보라는 ask-before-deciding, 이 두 개를 스킬로 만들어서 매번 지키게 했고요, 서브에이전트는 프로젝트 규모상 필요가 적어서 거의 안 썼습니다."

**evidence — 커밋 · TDD**
"커밋은 제가 직접 실행한다는 것도 사실이에요 — AI가 git add나 commit을 대신 실행한 적이 한 번도 없고, 메시지 초안만 받아서 제가 직접 터미널에서 커밋했습니다. 그리고 핵심 로직 몇 개는 TDD로 개발했어요 — 스킵 문구 생성 함수, 인접 요일 검증 로직, 공통 fetch 유틸 같은 것들을 Red → Green → Refactor 순서로 만들었습니다."

**클로징**
"그래서 이 프로젝트는 느리지만, 설명할 수 있는 결과물이에요. 판단을 매번 저한테 되묻게 하니까 속도는 느리지만, 'AI가 알아서 결정한 것'이 아니라 '제가 결정하고 AI가 구현한 것'이 남아서, 이 프로젝트의 모든 선택을 제 말로 설명할 수 있습니다."
