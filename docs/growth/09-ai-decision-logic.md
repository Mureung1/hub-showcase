# 9. AI 판단 로직 — 3사 답변을 어떻게 쟁점으로 나누고 비교할까

3사 답변을 실제로 받아오는 것까지는 됐다(SPEC-AI-001, 실제 호출·SSE·배포까지). 근데 그 답들을 **"비교"해서 쟁점으로 정리하는 Manager**가 진짜 어려운 부분이라는 걸 이제 알았다. 텍스트를 해석하고 분류하는 건 코드로 딱 떨어지는 게 아니라, "무엇을 같은 주제로 볼지", "어디까지 합의로 볼지" 같은 **기준을 사람이 먼저 정해야** 했다. 그래서 이 분야를 레벨 10으로 파고들며 자료조사를 했고, 이 문서에 그 여정을 다 담는다. **아직 최종 결론은 못 냈지만**, 조사가 여러 논점을 거의 확정 수준으로 좁혀줬다.

## ① 지금까지 정한 것 (구조)

- **Manager의 역할** — 성공한 3사 답변(각각 주제별 섹션으로 쪼개진 구조)을 받아 ⓐ 쟁점(Agenda)으로 **분류**하고 ⓑ 각 쟁점을 **합의(consensus)/충돌(conflict)로 판정**한다. 회의 사회자가 세 사람의 답을 안건으로 정리하는 것과 같다.
- **서버로 옮긴다** — 지금은 브라우저가 고정 템플릿으로 가짜 Agenda를 만든다. 실제 Manager는 서버가 돌리고, 결과 Agenda를 **DB에 저장**한다(새로고침해도 복원 — 지금 한계 해소).
- **기존 흐름에 이어붙인다** — 3사 답변이 끝나는 SSE 스트림에 곧장 이어서 Agenda까지 실시간으로 흘린다.
- **모델은 Qwen(최저가) via OpenRouter** — Manager는 화면에 모델명이 안 나오는 내부 엔진이라 최저가로 시작하되, OpenRouter로 붙여 DeepSeek·Kimi와 갈아끼우며 비교할 수 있게.
- **쟁점 개수는 Manager 재량 + 상한**(예: 최대 5~6개).

여기까지는 "구조"고, 정작 핵심인 "판단 기준"을 정하려고 조사를 했다.

## ③ 자료 조사 (레벨 10)

### 3-0. "파이프라인 쪼개기"와 "분류"는 별개다

거의 별개가 맞다. 정확히 구분하면:
- **분류(classification)** = "쟁점이란 무엇인가"를 정하는 **정의의 문제**.
- **파이프라인 쪼개기** = "그 일을 AI에게 몇 번 나눠 시킬 것인가"의 **구현의 문제**.

식당 비유: "이 요리는 무엇인가(분류)"와 "주방에서 몇 단계로 만드는가(파이프라인)"는 다른 질문. 같은 파스타를 한 번에 볶을 수도, 소스·면을 따로 만들어 합칠 수도 있다.

다만 한 군데에서 딱 붙어 있다 — **쟁점을 먼저 확정하고 각 AI 답을 나중에 배정하면 "이 쟁점에 몇 개 AI가 참여했나"가 자동으로 세어진다.** 한 번에 시키면 AI가 스스로 "이건 2대 1이야"라고 말해야 하고, 그건 검증할 방법이 없다. 그래서 순서는 **분류 방법을 먼저 정하고 → 그 방법이 요구하는 파이프라인 모양이 따라 나온다.**

### 3-1. 기초 개념 4개 (고등학생 눈높이)

뒤 이야기가 전부 이 4개 위에 선다.

**(1) 임베딩(embedding) — 문장을 좌표로 바꾸기.** 컴퓨터는 글자를 못 다루고 숫자만 다룬다. 문장을 숫자 목록으로 바꾸는 게 임베딩. 지도 위치가 (위도, 경도) 두 숫자이듯, 임베딩은 문장을 (0.23, -0.81, 0.44, …) 수백~수천 개 숫자로 표현한다. 핵심 성질: **의미가 비슷한 문장은 좌표도 가까워진다.** ("강아지가 뛴다"와 "개가 달린다"는 가깝고, "환율이 상승했다"는 멀다.)

**(2) 코사인 유사도(cosine similarity) — 두 좌표가 얼마나 가까운가.** 0~1 숫자로 잼(1에 가까울수록 비슷). 실측 감각: 같은 뜻 다른 표현(패러프레이즈)은 대체로 0.9 이상, 무관한 글 두 편은 평균 0.28 정도. 실무에선 "몇 점 이상이면 같은 얘기"로 볼지 **기준선(threshold)**을 실험으로 정한다(한 연구는 0.5~0.9를 훑어 0.8이 최적임을 찾고 그 주변을 좁혀 들어갔다).

**(3) 클러스터링(clustering) — 가까운 것끼리 묶기.** 좌표가 가까운 문장끼리 자동으로 그룹을 만든다. 교실에서 가까이 선 사람끼리 동그라미 치는 것. 사람이 "이건 A조"라고 안 알려줘도 되어 **비지도 학습(unsupervised)**이라 부른다.

**(4) NLI / 함의(entailment) — "같은 편인가"를 판정.** 두 문장의 관계를 셋 중 하나로:

| 관계 | 의미 | 예 |
|---|---|---|
| 함의(entailment) | A가 참이면 B도 참 | "비가 온다" → "땅이 젖는다" |
| 모순(contradiction) | 동시에 참 불가 | "A안 채택해야" ↔ "A안 피해야" |
| 중립(neutral) | 서로 무관 | "비가 온다" ↔ "고양이가 귀엽다" |

### 3-2. 가장 중요한 통찰 — "비슷함"과 "같은 편"은 완전히 다르다

이걸 놓치면 설계 전체가 틀어진다.

> 문장 1: "이 상황에서는 A안을 채택해야 합니다."
> 문장 2: "이 상황에서는 A안을 절대 채택하면 안 됩니다."

이 둘의 **코사인 유사도는 매우 높다**(단어가 거의 같고 주제가 동일). 임베딩 입장에선 "둘 다 A안 채택 여부를 논하는 문장"이라 가깝다. 그런데 이건 **정반대 주장 = 우리 시스템에서 가장 중요한 "충돌"**이다. (임베딩 모델이 이걸 놓치는 이유: Sentence Transformer는 어떤 데이터로 훈련됐냐에 따라 "유사함"의 정의가 달라진다 — NLI로 훈련되면 모순/함의 구분에 강하지만 미세 패러프레이즈엔 약할 수 있고, 반대도 마찬가지.)

**결론: 시스템은 반드시 2단 구조여야 한다.**

| 단계 | 묻는 질문 | 도구 |
|---|---|---|
| 1단계: 묶기 | "이 두 문장이 같은 주제인가?" | 임베딩 유사도 or LLM |
| 2단계: 판정 | "이 두 문장이 같은 결론인가?" | NLI / LLM 추론 |

그리고 이건 우연히도 우리가 **ADR-005에서 이미 정해둔 `AgendaClassifier`(묶기)와 `ConflictComparator`(판정) 두 포트와 정확히 같은 구조**다. 아키텍처는 이미 옳았다.

### 3-3. 분류 방법 4가지

**방법 A — 한 번에 시키기.** 3사 답을 통째로 프롬프트에 넣고 "쟁점으로 정리해줘" → JSON. *장점*: 가장 단순·저렴·빠름(1콜). *단점*: 묶기+판정+이름+근거가 동시에 일어나 어디서 틀렸는지 모름(냄비에 다 넣고 끓인 뒤 맛 이상하면 원인 못 찾음). LLM 주제분석은 초기 단계에서 과분할·과잉범주화가 생겨 별도 리뷰·통합 단계가 필요한데, 1콜엔 그 단계가 없다.

**방법 B — 기준 답 하나를 뼈대로 (Pivot).** 다중 문서 요약의 고전 기법. 3개를 대등하게 씨름하지 말고 하나를 "기준"으로 삼아 나머지를 거기 붙인다. (논문: 가장 중요한 문서 하나를 식별한 뒤 다른 문서 문장을 그 문서 문장에 정렬 — 단순하지만 효과적.) *비유*: 3명 여행계획서 중 한 명 걸 목차("1.숙소 2.교통 3.식당")로 삼아 나머지를 그 칸에 담기. *장점*: 각 판단이 "이 섹션이 쟁점 3번인가?" 단순 예/아니오로 쪼개져 LLM이 잘함, 근거 추적 자연스러움. *단점(중요)*: 기준 답이 놓친 쟁점은 통째로 사라짐(Claude 기준이면 Gemini만 말한 주제가 갈 곳 없음 → **논점 2 정면 충돌, "놓친 쟁점 모으기" 단계 필수**), 어느 답을 기준으로 삼을지 규칙 필요 + 그 선택이 결과를 편향.

**방법 C — 쪼개고, 묶고, 이름 붙이기 (LLooM, Stanford HCI).** 세 연산: **Distill**(LLM이 긴 답을 "주장 하나=한 줄" atomic claim으로 잘게) → **Cluster**(그 줄들을 임베딩으로 바꿔 코드가 묶음 — 싸고 빠르고 재현 가능) → **Synthesize**(각 묶음을 LLM에 보여 "관통 개념이 뭐야?"로 제목 받기). *결정적 강점*: 주제를 먼저 뽑은 뒤 문서-주제마다 "이 문서가 이 주제에 속하나?"를 물어 **한 문서가 여러 클러스터에 속할 수 있음(다중 배정)**. AI 한 섹션이 여러 쟁점을 건드리는 건 흔하다("예산 늘리되 일정 유지"는 예산·일정 양쪽). Amazon도 "문서마다 여러 핵심 구절 추출이 단일 주제 규정보다 결정적 이점"이라 관찰. *단점*: 호출 여러 번(비용·지연↑), 임베딩 모델 별도, threshold 실험 필요.

**방법 D — 목록 먼저, 배정 나중 (TnT-LLM, Microsoft).** 1단계에서 LLM이 라벨 분류체계를 반복 생성·정제, 2단계에서 배정. 우리 규모에선 2단계의 "분류기 학습"은 불필요하고 **1단계 아이디어만**: 쟁점 목록을 먼저 확정하고 배정은 따로. (유사 계열 CHIME: 주장·개체 추출 → 최상위 범주 생성 → 계층 배정.)

**C vs D 차이:**

| | 묶는 주체 | 특징 |
|---|---|---|
| 방법 C | 코드(임베딩 유사도)가 묶고 LLM은 이름만 | 재현 가능·저렴, 하지만 "비슷함≠같은 편" 함정 |
| 방법 D | LLM이 쟁점 목록을 상상해 만들고 배정 | 의미 이해한 묶음, 하지만 매번 결과 흔들림 |

### 3-4. 실증 비교 (SC-Taxo, 2026) — 결합형이 최고

같은 벤치마크로 비교한 최신 논문. **순도(Purity)** = 같은 묶음에 정말 같은 종류만 들어갔는지(높을수록 좋음):

| 방식 | 계열 | 순도 |
|---|---|---|
| CHIME | 순수 LLM | 41.8 |
| TnT-LLM | 순수 LLM | 57.6 |
| GoalEx | 순수 LLM | 47.6 |
| Knowledge Navigator | 임베딩 클러스터링 | 42.4 |
| SCYCHIC | 임베딩 클러스터링 | 50.6 |
| CAM-Taxo | LLM+클러스터링 결합 | 62.2 |
| SC-Taxo | LLM+클러스터링 결합 | 64.8 |

읽는 법: **순수 임베딩(42.4)만으론 부족**("비슷함≠같은 편" 때문), **순수 LLM(TnT-LLM 57.6)이 임베딩보다 낫고**, **둘을 결합(62~65)이 최고.** 즉 C·D 중 택일이 아니라 **섞는 게 현재 문헌의 결론.**

### 3-5. 숨은 함정 — 입력 순서가 결과를 바꾼다

여러 문서를 LLM에 넣을 때 **어느 걸 먼저 넣었냐가 결과를 바꾼다.** 최근 실험에서 요약은 순서상 첫 번째 문서와 ROUGE-L·BERTScore가 더 높게 나왔고, 찬성·중립·반대 모든 입장에서 입력 위치에 따른 유의한 차이가 관찰됨. 쉽게: **프롬프트에 Claude를 항상 첫 번째로 넣으면 쟁점 목록이 Claude 시각으로 치우친다** → "3사 공평 비교"라는 제품 약속이 조용히 깨진다.

LLM 판사의 **위치 편향**도 같은 계열(첫/마지막 위치를 10~15%p까지 선호). 완화책: 각 쌍을 양쪽 순서로 평가해 일관된 것만 채택, "순서에 영향받지 말라" 명시, 여러 판사 앙상블, 판정 전 근거 먼저 쓰게.

→ **해야 할 것: provider 순서를 질문마다 무작위/회전하고 그 순서를 레코드에 스탬프.** 나중에 "Claude 편향 아니냐" 의심을 검증할 유일한 방법.

### 3-6. MoA 최신 반전 — 우리는 "이기는 쪽"에 서 있다

원 논문(Wang et al. 2024): 여러 layer의 proposer가 답을 내고 aggregator가 정제·통합. MoA가 "답 하나 고르는 LLM-ranker"보다 우수하다 주장.

**그런데 "When Agents Disagree"(2026.3)가 이걸 뒤집는다.** 42태스크×7카테고리(N=210):

| 방식 | 단일 모델 대비 승률 |
|---|---|
| 다양한 팀 + judge 선택 | 0.810 |
| 동질 팀 + judge | 0.512 |
| 다양한 팀 + 다수결 | 0.496 |
| 다양한 팀 + **MoA 합성** | **0.179** |

**합성(synthesis)은 42태스크 전부에서 judge 선택에 졌고, 단일 모델에게도 82% 패배.** 해석: "합성은 평균을 내고, 선택은 고른다" — 다양한 팀의 가치는 후보 분산에 있는데 합성은 그걸 하나의 타협안으로 뭉개 파괴한다.

**Decision Log 함의(큼):** 우리 아키텍처는 이미 **"합성이 아니라 선택"** — Manager가 답을 블렌딩하지 않고 쟁점별로 갈라 **사용자(인간)가 고르게** 한다. 즉 실패하는 쪽(synthesis)이 아니라 **이기는 쪽(selection)**에 있고, selector가 LLM이 아니라 인간이다. → 포지셔닝: "MoA를 의사결정 도구로 구현" 보다 **"MoA의 합성 병목을 인간 selector로 대체했다"**가 더 정확·방어 가능. (덤: 약한 모델[Haiku]을 강한 팀에 섞은 조합이 승률 0.929로 최고이면서 최저가 — 3사 최소 티어 선택을 사후 정당화.)

### 3-7. 합의·충돌 판정 — 가장 위험한 발견

논점 4의 실증. Amazon RAG 모순 탐지(1,867샘플, LLM을 context validator로):
- **모든 모델이 높은 정밀도·낮은 재현율.** 모순을 지적하면 믿을 만하지만 실제 모순 상당수를 놓친다. Claude-3 Haiku+기본 프롬프트 **재현율 0.036**, CoT 붙여야 0.344.
- **CoT 효과는 모델 계열별 정반대** — Claude는 개선(Sonnet +31%, Haiku +46%), Llama-70B는 26% 악화.
- **문서 간 pair 모순이 가장 쉽고, 문서 내부 self-모순이 가장 어렵다.** (우리는 3사 답변 간 비교 = pair형 = LLM이 가장 잘하는 유형. self-contradiction은 신경 안 써도 됨.)
- 전문가 2명 일치율도 74%, 조건부 모순은 40개 중 17개만.

**결론 3가지:**
1. **Manager는 충돌을 과소 탐지할 것** — 재현율 낮음 = conflict가 consensus로 잘못 자동 통과. 우리 정책상 이건 `passed(auto_consensus)`로 DB에 박히는 오류이고 사용자 판단 기회가 사라진다. → **판정 임계를 "충돌 쪽으로 편향"이 안전한 기본값.** 잘못 충돌로 보내면 사용자가 보고 "같은 얘기네" 채택하면 되지만, 잘못 합의로 보내면 복구 경로가 없다.
2. 우리 과제는 pair형이라 다행(LLM 강점 영역).
3. **CoT는 모델별 A/B 필수** — Qwen에서 CoT가 도움될지는 실측 전엔 모름. 논점 5 A/B 항목에 명시.

### 3-8. 구조화 출력의 세금 — "JSON 시키면 멍청해진다"

Tam et al.(EMNLP 2024): JSON·XML 강제하면 추론 능력이 유의하게 하락, 제약이 엄격할수록 심함. 소형 모델은 더: 하드 스키마 디코딩이 스키마 유효율 61.5%→100%로 올렸지만 정답률 19.7%→11.0%로 떨어뜨렸고 "구조는 맞지만 내용 틀림"이 49.5%→88.9%로 급증. 처방: **"자유롭게 추론하고 늦게 제약하라(reason free, constrain late)."**

**Manager = Qwen 최저가 + strict JSON은 이 함정 한가운데.** 완화책:
1. **스키마 필드 순서 = 사고 순서.** LLM은 필드를 순차 생성하므로 답을 추론보다 앞에 두면 생각 전에 결론을 확정한다. → **각 Agenda 객체에 `comparisonNote` 같은 임시 추론 필드를 `kind`보다 앞에 두고 저장 전 버린다.** 추가 호출 없이 CoT 효과.
2. **필드 description에 판정 기준을 넣는다.** 설명 최적화만으로 추출 정확도 60%↑ 사례. → `kind` enum에 `consensus`="표현은 달라도 실질 주장이 같음", `conflict`="양립 불가능한 권고"처럼 정의를 스키마에 박는 게 프롬프트 본문보다 효과적.
3. **컨텍스트는 최소로.** 최소한의 컨텍스트 증가가 가장 큰 향상을 주고 이후는 한계효용, 늘리면 오히려 정확도 하락 사례도.

**OpenRouter 실무 제약:** `response_format`에 `type:"json_schema"` + `strict:true`, provider 설정에 `require_parameters:true`로 구조화 출력 지원 프로바이더로만 라우팅. 스트리밍도 유효 부분 JSON이 흘러 3사 SSE 이어붙이기와 호환. 비스트리밍엔 Response Healing 플러그인. **⚠️ Qwen 계열은 구조화 출력 시 `max_tokens`를 설정하지 말 것** — JSON이 중간에 잘려 파싱 실패. 5~6 Agenda × stance 3개면 출력이 길어 실제 걸릴 함정.

### 3-9. 근거 grounding — sourceRefs 환각 방지

"근거 없는 비교 결과 저장 금지" 정책의 정석 = **앵커 제약(anchor constraint)**: 먼저 텍스트의 유효 span을 모두 식별한 뒤, 추출은 그 안에서만 선택·조합하도록 강제 → 모든 요소가 원문 토큰으로 역추적, 날조 차단.

우리는 이미 유리 — **`sectionId`가 안정 식별자**라 프롬프트에 유효 `sectionId` 목록을 주고 enum으로 제약하면 앵커 제약이 거의 공짜. 2단 검증을 얹는다: 추출 시 근거로 **원문 그대로의 텍스트 span(quote)**을 받고, 규칙기반 정확·퍼지 문자열 매칭으로 위치 확인, 의미 검증으로 실제 뒷받침하는지 확인. 실패한 필드는 폐기(공백 정규화·소문자화는 허용, 단어 추가·삭제는 거부).

→ **구체 처방: stance마다 `quote`(해당 섹션 원문 부분 문자열) 필수 → 서버에서 정규화 후 substring 검사 → 실패 stance 폐기, stance 0개 된 Agenda도 폐기.** 이러면 "근거 없는 비교 저장 금지"가 선언이 아니라 **코드로 강제**된다.

### 3-10. 사용자에게 불일치 보여주기 (HCI 실증) + 경쟁 지형

조사 중 최고의 수확 — **FAccT '24, KAIST(N=252)가 우리 제품 가설을 직접 검증:**
- 다수 LLM 출력 간 **불일치는 인식된 AI 역량을 낮췄지만 정보 이해도를 높였다.** 이 긍정 효과는 **2개** 읽은 참가자에게서 가장 두드러짐.
- 일관된 답을 본 참가자 중 자기 답이 AI와 달랐던 사람은 **3명 빼고 전원 AI를 따라감(과의존)**. 불일치를 본 참가자는 더 높은 비율로 자기 답 고수.
- **3개는 역효과** — 모든 정확도 수준에서 이해도 저해. 다수결 휴리스틱에 의존해 소수 정답을 무시, 인지 부하로 대충 훑음.
- 발견한 **5가지 불일치 유형**: Main Answer(핵심 답 다름), Detail Volume(근거 양), Detail Content(근거 내용), Detail Expansion(한쪽이 더 확장), Paraphrasing(표현만). → **Paraphrasing·Detail Expansion = 충돌 아님, Main Answer = 진짜 충돌, Detail Content = 회색지대.** 이 5분류는 논점 1(grain)·4(판정)에 그대로 쓸 기성 taxonomy.

함의: **3개를 그냥 던지면 인지 부하로 실패한다는 실증 = Manager의 존재 이유 그 자체.** 3열 원문을 나란히 던지는 게 아니라 쟁점 단위로 압축해 충돌만 골라주는 우리 설계가 정확히 이 연구의 처방(저자도 유사도로 차이를 자동 하이라이트하고 유형 라벨을 붙여 제시하라 권고).

**경쟁 지형:** Perplexity가 2026.2 Model Council 출시(한 질의를 Claude Opus 4.6·GPT-5.2·Gemini 3.0에 동시 전송, 서로 답 안 보고 독립 생성). Karpathy의 오픈소스 LLM Council. MultipleChat은 "실질적 불일치일 때만 드러내고 아니면 조용히 하나 고르기". → **우리 차별점은 "여러 AI에 물어본다"가 아니라 결정의 기록(DecisionNote) + 다음 질문으로의 Context 승계.** 챌린지 제출 시 이 축으로 포지셔닝.

### 3-11. Qwen을 Manager로 — 냉정한 평가 + 보완 기법

- 독립 판사 패널 검증에서 GPT-4o-mini는 1,260회 쌍대 비교 중 **99.6%를 무승부**로 반환하며 사실상 기능 못함. 판사별 무승부율 편차도 큼(Gemini Flash 76.7%, GLM-5 50.3%). Haiku 재현율 0.036도 같은 방향 → **약한 모델은 신뢰할 쌍대 평가 변별력이 부족할 수 있다.**
- **저가 모델로 버티는 기법 2가지:** ⓐ 태스크별 판정 기준을 프롬프트에 주입(비용 0) + 앙상블 스코어링 → 최대 85.8%(+13.5pp), 특히 소형 모델이 앙상블에서 큰 이득. ⓑ **Cascaded Selective Evaluation** — 저렴한 모델을 1차 판사로, 필요할 때만 강한 모델로 에스컬레이션 → 저비용으로 80%+ 인간 일치율.
- → **Qwen이 `kind` 판정에 낮은 신뢰도를 표시하거나 stance가 애매한 Agenda만 상위 모델로 에스컬레이션**하는 설계를 config 레벨에 두면 ADR-005의 "설정으로 모델 교체"와 맞물린다.

## ④ 조사가 8개 논점에 준 답 (매핑)

| # | 논점 | 조사가 주는 답 |
|---|---|---|
| 1 | 분류의 결 | **claim에 가깝게 잘게.** 문헌은 LLM 과분할을 경고하나 theme 단위는 `kind` enum 단일값 스키마와 충돌. FAccT 5유형(Main Answer / Detail×3 / Paraphrasing)을 grain 정의에 차용 |
| 2 | 단일 소스 | **판단이 아니라 카운트.** 2-pass로 쪼개면 provider 수가 결정론적으로 나옴. `resolution_reason` 신규 값 추가만 남은 결정 |
| 3 | 2:1 부분 합의 | **자동 다수결 금지.** FAccT에서 사용자가 다수결 휴리스틱으로 소수 정답 무시가 관찰됨 → 충돌로 넘겨야 |
| 4 | 합의/충돌 기준 | Paraphrasing·Detail Expansion=합의, Main Answer=충돌, Detail Content=회색. **판정은 충돌 쪽으로 편향**(재현율<정밀도) |
| 5 | 의미 정렬 품질 | **CoT on/off를 A/B 항목에 명시**(모델 계열별 효과 정반대) |
| 6 | 계약 모양 | **stance에 `quote` 필수 → substring 검증으로 정책 강제. `reasoning` 필드를 `kind` 앞에** |
| 7 | 프롬프트 설계 | **스키마 = 프롬프트.** enum description에 판정 기준 인코딩, 필드 순서=사고 순서, 컨텍스트 최소 |
| 8 | 실패 정책 | strict + require_parameters + Response Healing. **Qwen은 max_tokens 미설정.** 검증 실패 stance 폐기, stance 0개면 Agenda 폐기 |

**가장 먼저 손댈 지점은 논점 1이 아니라 "파이프라인을 2-pass로 쪼갤지"로 보인다.** 그 결정이 논점 2·3을 판단 문제에서 카운팅 문제로 강등시키고 6번 계약도 따라 확정되기 때문. 배정 단계의 provider 카운트를 **결정론적 코드**로 세면:

| provider 수 | 입장 분포 | 처리 |
|---|---|---|
| 3 | 일치 | consensus → 자동 통과 |
| 3 | 2:1 | 충돌 (다수결 자동처리 금지) |
| 2 | 일치 | consensus로 처리하되 미언급 provider 표시 |
| 2 | 불일치 | 충돌 |
| 1 | — | 단일 소스 안건 |

Manager는 "몇 대 몇"을 판단하지 않고 배정·stance만 내놓고, **판정 규칙은 서버 코드가 소유**(재현성·감사가능성↑).

## ⑤ 현재 기운 방향 (아직 확정 아님)

**거의 확정적인 것:**
- 순수 임베딩 클러스터링 단독 **탈락**("비슷함≠같은 편").
- 방법 A(한 번에)도 실질 **탈락**(디버깅 불가 + 과분할 방지 없음 + provider 카운트 검증 불가).
- **한 섹션이 여러 쟁점에 속할 수 있게(다중 배정) 허용.**
- **provider 입력 순서 무작위화 + 기록.**
- 판정은 **충돌 쪽으로 편향**, stance에 **quote 필수+substring 검증**, **reasoning 필드를 kind 앞에**, **Qwen max_tokens 미설정.**

**아직 못 정한 것 — 방법 B vs C+D 혼합:**

| | 방법 B (Pivot) | 방법 C+D 혼합 |
|---|---|---|
| 구현 난이도 | 낮음 | 중간 |
| LLM 호출 수 | 2~3회 | 3~4회 + 임베딩 |
| 재현성 | 중간 | 높음 |
| 논점 2(단일 소스) | 별도 처리 필요 | 자동 관찰 |
| 챌린지 일정 적합성 | 좋음 | 빠듯할 수 있음 |
| 문헌상 품질 | 검증 사례 적음 | 최고 점수 |

**현재 기운 쪽: 방법 B** — 챌린지 마감 있고, Qwen 최저가, 임베딩 인프라 아직 없음. 단 B로 가도 **"기준 답이 놓친 쟁점 모으기" 단계는 필수**이고 그게 논점 2의 답이 된다.

**다음에 팔 것(택1):** ⓐ 방법 B에서 기준 답 선택 규칙(가장 긴 답? 섹션 최다? 무작위?)과 "놓친 쟁점 모으기" 구현을 더 조사, 또는 ⓑ 지금 선에서 방법 B를 실제 프롬프트 구조 + Zod 스키마로 그려보기.
