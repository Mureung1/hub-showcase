# ADR-0002 — 생산 스택

상태: 채택됨
날짜: 2026-07-22

## 맥락

기능 단위 Phase(00~06) 실행을 시작하려면 생산용 프론트엔드, 백엔드, DB, LLM 실행 위치를 확정해야 한다. 사용자가 2026-07-22에 스택을 직접 결정했다.

## 결정

- 프론트엔드: **React + TypeScript + Vite** (`frontend/`)
- 백엔드: **Supabase** — Postgres(DB), Auth(이메일 로그인), Storage(증거 파일), Edge Functions(서버 로직·LLM 호출)
- 실행 환경: **로컬 Supabase** (supabase CLI + Docker, `supabase start`). 클라우드 프로젝트는 쓰지 않는다.
- LLM 호출: **Supabase Edge Functions**(Deno/TypeScript)에서만 수행한다. LLM API 키는 Edge Functions 환경변수로만 주입하고 브라우저 번들에 절대 넣지 않는다.
- 인증: MVP에 Supabase Auth 이메일 로그인을 포함하고, 모든 테이블과 Storage 버킷에 RLS(Row Level Security)로 매장 소유권을 강제한다.
- 스키마 변경은 `supabase/migrations`의 SQL 마이그레이션으로만 한다.
- 테스트: Vitest(단위·컴포넌트·통합). 결정적 규칙(분류 엣지 케이스, 금칙 정책, 인사이트 감지)은 순수 TS 모듈로 분리해 LLM·DB 없이 단위 테스트 가능해야 한다.

## 결과

좋아지는 점:

- 프론트, 서버 로직, 테스트가 TypeScript 하나로 통일된다.
- DB·인증·스토리지·서버리스 함수를 Supabase 하나로 받아 별도 백엔드 서버 구현·운영이 없다.
- 로컬 CLI 실행으로 "코드는 로컬 전용, 외부 부작용 없음" 하네스 원칙이 유지된다.

감수할 점:

- Docker Desktop과 supabase CLI가 로컬에 필요하다.
- Edge Functions는 Deno 런타임이라 Node 라이브러리 호환성에 제약이 있다.
- 도메인 로직이 프론트·Edge Functions·SQL(RLS)로 분산될 수 있으므로 순수 TS 모듈 분리 규칙을 지켜야 한다.

후속 작업:

- `HARNESS/phases/PHASE_PLAN.md`와 각 Phase prompt를 이 스택 기준으로 유지한다.
- 배포 방식은 제품 Phase 2 이후 별도 ADR로 결정한다.

## 대안

### FastAPI + PostgreSQL 별도 백엔드

기각. 언어가 Python·TS 둘로 나뉘고 서버 구현, 마이그레이션, 인증을 직접 만들어야 해서 MVP 범위 대비 무겁다.

### 프론트에서 LLM 직접 호출

기각. LLM API 키가 브라우저 번들에 노출된다. Edge Functions 경유로 키를 서버 측에만 둔다.

### Supabase 클라우드 프로젝트

보류. MVP는 로컬 CLI로 충분하고, 외부 서비스 의존과 자격증명 관리가 늘어난다. 배포 단계(제품 Phase 2 이후)에서 재검토한다.
