# Build the runtime harness before the AY-PLE product layer

AY-PLE will first build a Runtime Harness with a Runtime Inspector, AgentRuntimeKernel, FakeRuntimeAdapter, and CodexRuntimeAdapter before implementing product-specific SourceSelection, StatePatch, Review, or TrustedState flows. FakeRuntimeAdapter may be used to develop the interface and UI quickly, but CodexRuntimeAdapter parity is a product-layer gate: by the end of week 1, before work on `codex/w1d7` on Sunday, July 12, 2026, the same Runtime Inspector must be able to run and cancel a prompt through both adapters and show compatible normalized run lifecycle events and run logs.

This deliberately avoids building AY-PLE features directly on raw Codex app-server events, while also preventing the project from drifting into a fake-only harness that discovers Codex integration constraints too late.

Runtime Inspector capabilities are engine-inspection affordances, not student-facing product commitments. Common chat capabilities such as prompt input, transcript, streaming output, cancellation, errors, run history, profile slots, attachments, approvals, settings, and thread/session slots should be considered while shaping the Runtime Harness and AgentRuntimeKernel, but AY-PLE will decide separately whether, where, and how those capabilities appear in a user-friendly product surface.

The repository will use an early package-first topology for these boundaries instead of growing the runtime inside the existing server/client apps and extracting it later. Week 1 implementation should focus on real runtime packages and harness apps: `packages/runtime-core`, `packages/runtime-fake`, `packages/runtime-codex`, `apps/server`, and `apps/inspector`. AY-PLE product packages such as `packages/ay-ple-domain`, `packages/ay-ple-modeling`, and `packages/ay-ple-review` may be created as boundary placeholders, but product-specific behavior waits until the CodexRuntimeAdapter parity gate is met.

The Runtime Harness should be reference-first rather than scratch-built. The Codex app-server protocol, lifecycle, and schema should be taken from official OpenAI documentation, the generated schema for the pinned Codex version, and the open-source `openai/codex` app-server materials before inventing local protocol shapes. Public third-party implementations may inform transport, logging, and inspector ergonomics, but copied code requires explicit license review and should not define AY-PLE's product-facing interface.

Within `packages/runtime-codex`, protocol coverage should be broad and shallow while product semantics stay narrow and stable. A small `CodexRawClient` may expose generated-schema-backed app-server methods for Runtime Inspector experiments, and `CodexRuntimeAdapter` should implement the `runtime-core` adapter interface by translating raw Codex events into normalized run events. This split is a role separation inside one package, not a mandate for heavy abstraction layers, factories, or product code depending on raw Codex protocol types.
