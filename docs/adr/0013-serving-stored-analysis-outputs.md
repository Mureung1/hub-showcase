# ADR 0013. 화면 조회를 저장된 분석 산출물 조회로 둔다

## 맥락

Express가 요청마다 공고 표를 집계하면 같은 질문에 같은 계산을 다시 수행한다. 집계 결과는 분석 버전이 바뀔 때만 달라지므로 요청 횟수만큼 반복할 이유가 없다.

집계를 서버가 수행하면 직무마다 다른 라벨을 서버 코드가 알아야 한다. 요구 차원과 그 표시 문구는 [통계 모델](../statistics-model.md)의 승격 절차가 직무별로 정하는 값이고, 직무를 넓힐 때마다 조회 계층이 따라 바뀐다. 조회 계층은 스키마를 정의하지 않는다([ADR 0006](0006-migration-ownership.md)).

## 결정

화면 조회는 저장된 분석 산출물을 그대로 반환한다.

- Express는 `active_analysis_versions`에서 직무의 활성 분석 버전을 찾는다.
- `analysis_outputs`를 `(analysis_version, scope_level, scope_id, output_type)`으로 조회하고 `payload`를 그대로 반환한다.
- `analysis_outputs` 한 행이 화면 한 벌이다. 서버는 payload를 만들지 않는다.
- 직무별 라벨은 payload 안에 담긴다. 조회 계층은 라벨을 알지 않는다.
- 화면 조회는 에이전트를 호출하지 않는다([아키텍처](../architecture.md) 9장).

계약은 [데모 시드 계약](../../agent/data/demo_seed/CONTRACT.md) 4장이 고정하고, 구현은 `server/src/outputs.js`다. 개발 단위는 [백로그](../backlog.md) Phase 22다.

## 고려한 선택지

| 선택지 | 결과 |
| --- | --- |
| 요청마다 공고 표를 집계 | 같은 질문에 같은 계산을 반복하고 직무 라벨이 서버 코드로 들어온다 |
| 집계 결과를 서버 메모리에 캐시 | 계산 위치는 그대로여서 라벨이 여전히 서버에 남고 활성 버전 전환과 캐시 수명이 어긋난다 |
| 저장된 산출물을 그대로 반환 | 계산은 분석 실행에서 한 번 일어나고 조회 계층은 버전 선택만 맡는다 |

## 선택 이유

집계는 분석 버전을 만드는 시점의 작업이고, 조회는 어느 버전을 볼지 고르는 작업이다. 두 작업을 분리하면 조회 응답이 활성 버전에만 의존하므로 같은 버전에 같은 응답이 나온다.

payload가 라벨을 담으면 직무를 넓히는 일이 데이터 추가로 끝난다. 조회 계층은 `output_type`과 범위만 알면 되고 직무 수에 따라 커지지 않는다.

## 결과와 제약

- 활성 분석 버전에 요청한 산출물이 없으면 조회는 빈 값을 내지 않고 `NO_ACTIVE_ANALYSIS` 오류를 낸다. 화면은 그 직무의 분석이 준비되지 않았음을 안내로 표시한다.
- 공고 범위의 `strategy`·`roadmap` 요청에 행이 없으면 그 공고가 속한 기업군, 다시 직무 전체 순으로 한 칸씩 넓힌다. 떨어뜨렸을 때는 payload의 `scope`를 실제로 사용한 범위로 바꿔 화면이 무엇을 보고 있는지 밝힌다. 요청한 범위의 결과인 것처럼 다른 범위의 결과를 보이지 않는다.
- payload 스키마가 바뀌면 화면과 산출물 생성 경로가 함께 바뀐다. 조회 계층은 중간에서 형태를 고치지 않는다.
- 체크 상태 반영과 로드맵 재조합은 이 경로 밖에 있다. 저장된 산출물을 재료로 삼아 조합기가 수행한다([아키텍처](../architecture.md) 9.1).
