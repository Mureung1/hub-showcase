01 — 문제 인식 및 배경

진짜 비용은 읽는 게 아니라,
무엇을 읽을지 고르는 것

LLM 분야 논문의 생산 속도가 개인이 따라잡을 한계를 넘었다. arXiv에는 하루에도 수십 편이 올라온다.

기존 요약 서비스 · 한계 ①
전부 요약해서 쏟아낸다
목록만 길어질 뿐, "무엇을 읽을지 고르는" 문제를 그대로 사용자에게 되돌려준다.
기존 요약 서비스 · 한계 ②
선별하지만 근거가 없다
왜 골랐는지 말해주지 않으면 연구자는 믿지 않는다 — 놓친 게 없다는 걸 확인할 방법이 없기 때문이다.

선별을 하더라도, 왜 골랐고 무엇을 버렸는지를 보여주지 못하면 연구자는 결국 arXiv를 직접 다시 뒤진다.

02 — 아이디어 개요

고른 이유와 버린 이유를 함께 보여주는 에이전트

차별점은 요약 품질이 아니다 — 요약은 어느 LLM이든 어느 정도 한다. 차별점은 에이전트의 판단 과정 전체가 사용자에게 열려 있다는 것이다.

12편 중 4편을 골랐고, 8편은 이 이유로 뺐다 이 논문은 초록으로 충분, 저 논문은 본문까지 한 번에 안 나와 스스로 다시 썼다
03 — 시스템 아키텍처

요청한 그 순간 실행되는 백엔드

  • 프론트(바닐라 HTML/JS) → FastAPI → 에이전트 루프 5단계 ↔ 도구
  • SSE로 과정을 실시간 스트리밍. 다 끝나고 한 번에 주는 방식이 아니다.
  • 도구는 LLM(Gemini Flash)·arXiv·본문 수집·저장 — 독립된 Python 함수.
  • 정적 사이트 + cron 배치가 아니라 요청 순간 실행. 그래서 상시 서버가 필요하다.
04 — agent 사용 방법 · 서비스

사용자가 부려 쓰는 서비스 속 에이전트

주제를 입력하면 에이전트가 그 순간 실행되고, 판단 과정이 단일 세로 타임라인에 SSE로 실시간으로 흐른다.

  • 판단(judge) — 12편 중 4편을 선별하고, "제외된 8편 보기"로 버린 이유까지 연다.
  • 카드 배지 — "본문까지 읽음 / 초록으로 충분". 도구 선택이 눈에 보이는 유일한 곳.
  • 재시도 로그 — 스스로 검증해 요약을 보완한 기록을 감추지 않는다.
  • 위계는 레이아웃이 아니라 스타일로 — 과정은 작고 흐리게, 결과는 크고 선명하게.
05 — 구현 과정 · 직접 만든 개발 도구
