# 3주차-설계하고 작업나누기 (With AI)

## AI와 설계하고 작업나누기

## 1. 왜 설계부터 하나

"기능 만들어줘" 한 문장으로 시키면 무슨 일이 생기나.

#### 1.1 한 방에 시키면 생기는 일

- 덩어리가 크면 AI도 자주 실패하고, 나도 어디서 잘못됐는지 찾기 어려움
- 결과가 나와도 판단할 기준이 없음. 내가 그린 그림이 없기 때문
- 며칠을 써도 "다 됐는지"를 말할 수 없음. 끝의 기준이 없기 때문

#### 1.2 설계는 무엇을 하는 일인가

- 설계: 만들기 전에 무엇을 어떻게 만들지 정하는 일
- 코드는 AI가 쓴다. 나는 무엇을 만들지 정의하고, 나온 결과를 판단한다
- 설계가 있어야 AI의 산출물을 검토할 기준이 생김

---

## 4. 계획 점검

계획은 검증 가능해야 함.

따라서 아래와 같은 통과 기준으로 검증해봐야함.

| 질문 | 통과 기준 |
| --- | --- |
| 크기 | 작업 하나가 적당한 기간안에 끝날까? (반나절 등) |
| 완료 기준 | 끝났을 때 확인할 방법이 있는가 |
| 순서 | 핵심 동작이 먼저인가 (UI 다듬기와 예외처리는 뒤로) |
| 빠진 것 | 빈 값, 실패, 데이터 없음 같은 경우를 다뤘는가 |

위 조건을 검증하는 Agent를 만드는 것도 방법.

좋은 게획의 간단 예시)

```
1. comments 테이블 생성 (Table Editor에서 확인)
2. GET /api/comments가 목록 응답 (브라우저로 확인)
3. 화면에 목록 표시 (목록이 보임)
4. 입력하면 저장 (새로고침해도 남음)"
```

## 5. 작업을 작게 나누는 기준

#### 작게 나눌때의 장점

- AI에게 시키는 단위가 명확해져 실패가 줄어듦
- 작업 하나가 끝날 때마다 검증하고 커밋할 수 있음
- 막혔을 때 어디서 막혔는지 바로 보임

![task-breakdown](https://lucas-image.codesquad.kr/1784524369823_task-breakdown.png)

- 작업 하나 = 명확한 한 문장 + 확인가능한 완료 기준
- 정해진 일정 크기보다 크면 더 나눈다

---

## 6. 이슈로 등록하고 시작한다

- 나눈 작업을 이슈로 등록한다. 제목은 할 일, 본문에는 완료 기준
- 우선순위를 표시하고, 하나씩 집어서 개발한다
- 작업 하나가 끝나면 완료 기준으로 확인하고 커밋한다. 그다음 작업으로 넘어간다

---

## 7. 개별 구현 전 검토사항 - 구현 전에 전략부터 받는다

작업 하나를 집었을 때, 바로 코드를 시키지 않는다.

어떻게 구현할지 전략을 먼저 받고, 구조를 검토한 뒤에 구현시킨다.

좋은 구조는 내가 그리는 것이 아니라, AI의 전략을 검토해서 유도하는 것이다.

#### 7.1 무엇을 받아야 할까?

```
이 작업을 구현하기 전에, 구현 전략부터 보여줘. 코드는 아직 쓰지 마.
1) 만들거나 고칠 파일과 각 파일의 역할
2) 데이터가 어디에 있고 어떻게 흐르는지 (state 위치, 요청과 응답)
3) 이렇게 구현하는 이유. 다른 방법이 있다면 장단점도
```

#### 7.2 좋은 구조인지 검토하는 기준

| 질문 | 좋은 신호 | 나쁜 신호 |
| --- | --- | --- |
| 역할이 제자리인가 | 화면 일은 화면에, 데이터 처리는 서버에 | 화면(FE)이 DB를 직접 부름 |
| 하나가 한 가지 일만 하나 | 파일과 컴포넌트가 역할별로 나뉨 | 한 파일이 화면과 요청과 검증을 다 함 |
| 기존 구조를 따르나 | 지금 프로젝트의 폴더와 방식 그대로 | 갑자기 새 패턴이나 라이브러리를 끌고 옴 |
| 변경 범위가 적절한가 | 필요한 파일 몇 개만 고침 | 작은 기능인데 프로젝트 절반을 고침 |

- 수정이 필요하면 요청한다.
    - > "기존 routes 구조를 따라줘", "이 컴포넌트는 나눠줘", "새 라이브러리 없이 해줘"

#### 7.3 기준이 아직 안 보여도 검토할 수 있다

위 표의 판단이 어렵다면, 판단 대신 이렇게 한다.

- 비교를 시킨다
    - 전략 하나만 보면 좋은지 알 수 없음.
        - 나란히 놓인 차이는 읽을 수 있음.
        - 판단이 아니라 선택으로.
        - > 이 방법 말고 다른 방법 2가지를 보여주고,  
        > 셋의 장단점을 표로 비교해줘. 어떤 걸 추천하는지와 이유도.
- 질문을 고정
    - 몇 가지만 물어도 AI가 스스로 약점을 말한다. 답을 듣고 이해되면 통과, 안 되면 더 묻는다
        - > "왜 이렇게 하는데", "다른 방법은 없어", "이 방식의 단점은 뭐야".
- 구조적 변화 관찰
    - 변경하는 파일이 몇 개인가 (작은 기능에 10개면 의심),
        - 새 라이브러리를 설치하는가 (package.json이 바뀌면 멈추고 묻기),
        - 기존 폴더 밖에 새 구조를 만드는가

#### 7.4 이해하지 못한 전략은 통과시키지 않는다

- 전략을 읽고 내 말로 설명할 수 없으면 승인하지 않는다
- "왜 이렇게 하는지", "다른 방법은 없는지"를 물어서 이해한 뒤에 구현을 진행시킨다
- 검토의 목표는 정확한 판단이 아니라, 그대로 통과시키지 않는 습관이다
- 좋은 아키텍처는 한 번의 큰 결정이 아니라, 작업마다 이 검토를 반복한 결과다

---

중요한 것은 내 작업에서 아래 질문을 반복하는 것.

- 이 기능은 작게 나뉘었나?
- 사용자가 확인할 수 있는 흐름인가?
- 끝났다고 판단할 기준이 있나?
- 코드가 역할별로 나뉘었나?
- 내가 이 구조를 설명할 수 있나?
