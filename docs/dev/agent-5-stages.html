hub · run_agent() · 5-stage judgment loop

다섯 단계로, 논문을 스스로 판단한다

에이전트가 "주제 하나"를 받아 "결과"를 만들어내기까지 거치는 다섯 개의 판단 단계. 각 단계는 LLM에게 무언가를 묻고, 그 응답을 코드가 검증해 다음 단계로 넘긴다.

이 페이지는 역할 · 필요성 · 방식 · 기준 · 처리 단계 · 데이터 형식 · 완료 기준(확인 위치 포함) · 도구 비교까지 다룬다. 판단 기준(무엇이 "중요한 논문"인가)은 코드가 아니라 prompts/*.md의 문장에 전적으로 달려 있다 — 문장을 바꾸면 결과도 바뀐다.

1
판단
judge
전체 후보 · 1회
역할 검색된 논문 후보들 중 지금 주제와 정말 관련 있는 것을 추리고, 뺀 논문에도 왜 뺐는지 이유를 남긴다.
왜 필요한가 이 서비스의 정체성이 걸린 단계다. 그냥 다 요약해 쏟아내면 리스트만 길어질 뿐이고, 왜 이걸 골랐는지 말해주지 않으면 연구자는 결과를 믿지 않는다. 제외 사유는 부산물이 아니라 이 서비스가 파는 결과물 자체다.
어떤 방식 논문 제목·초록 일부와 사용자가 입력한 주제를 LLM에게 건네고, 고른 논문과 뺀 논문을 이유와 함께 나눠 받는다. 코드가 "빠짐없이 판단했는지"를 다시 세어 확인하고, 누락된 논문이 있으면 자동으로 제외 목록에 채워 넣는다.
어떤 기준 3~5편 정도를 고르되 억지로 채우지 않는다. 고른 논문·뺀 논문 모두 한 문장 이유가 필수다. 판단 자체가 완전히 실패하면(응답을 하나도 못 받으면) 여기서 진행을 멈춘다.
처리 단계
  1. 후보 논문에 순번(index)을 매기고, 제목 + 초록 앞 500자만 추려 후보 목록을 만든다 (본문 전체를 보내면 비용이 커짐)
  2. 주제(topic)와 후보 목록을 프롬프트에 채워 LLM에게 보낸다
  3. 응답을 JSON으로 파싱한다 — 실패하면 picked·excluded 모두 빈 배열로 간주해 "판단 실패"로 처리
  4. picked + excluded가 후보 전체를 덮는지 개수를 검증하고, 빠진 index는 "판단 누락" 사유로 excluded에 채운다
  5. 정리된 결과를 다음 단계(도구 선택)로 넘긴다
데이터 형식
입력
[
  {"index": 0, "title": "Tree-of-Agents: Hierarchical Planning...",
   "abstract": "We present a hierarchical..."},
  {"index": 1, "title": "A Survey of Prompt Engineering",
   "abstract": "This survey covers..."}
]
출력
{
  "picked": [
    {"index": 0, "score": 4,
     "reason": "planning에 계층 구조를 도입한 새 방법론. 핵심 주제와 직결."}
  ],
  "excluded": [
    {"index": 1, "reason": "planning과 직접 관련 없는 일반 서베이."}
  ]
}
완료 기준
터미널 코드(오프라인 테스트) 웹(완성 후)
터미널 — python -m app.agent --topic "..." --limit 3 실행 시 출력되는 judge 이벤트에서, picked·excluded의 index를 합치면 후보 전체 개수와 정확히 같은지 눈으로 확인.
코드 — mock으로 LLM 응답을 대신해 _judge_papers()를 직접 호출, 누락 index가 자동으로 excluded에 채워지는지 확인(이미 검증됨).
웹(완성 후) — judge 이벤트가 화면에 강조 블록으로 뜨고 "제외된 N편 보기"가 펼쳐지는지 브라우저에서 확인. (SSE·화면은 아직 미구현, Week 2~3)
2
도구 선택
select_tool
논문마다
역할 논문 한 편 한 편마다, 초록만 읽고 요약해도 되는지 아니면 PDF 본문까지 받아 읽어야 하는지를 정한다.
왜 필요한가 에이전트가 실제로 "도구를 고르는" 유일한 순간이다. 매번 본문을 받으면 정확하지만 느리고 비용이 크다. 매번 초록만 보면 빠르지만 부실해진다. 논문마다 다르게 판단해야 진짜 에이전트답다.
어떤 방식 논문 제목과 초록을 LLM에게 보여주고 "본문이 필요한가"를 물어 판단을 받는다. 필요하다고 하면 PDF를 내려받아 텍스트를 뽑고, 그마저 실패하면 초록으로 자동 되돌아간다.
어떤 기준 새 방법론을 제안하는데 구조·수식 설명이 초록에 없으면 본문이 필요하다고 본다. 서베이거나 초록에 이미 수치까지 다 있으면 초록으로 충분하다고 본다. 판단이 애매하면 "초록으로 충분" 쪽을 택한다 — 비용이 덜 드는 선택이다.
처리 단계
  1. 판단(judge) 단계에서 선택된 논문을 하나씩 순서대로 꺼낸다
  2. 논문 제목 + 초록을 프롬프트에 채워 LLM에게 "본문이 필요한가"를 묻는다
  3. 응답을 JSON으로 파싱 — 실패하면 need_fulltext: false로 간주(비용이 적은 쪽 fallback)
  4. need_fulltext가 true면 PDF를 내려받아 텍스트를 추출한다
  5. 추출이 실패하면(파일이 없거나 파싱 오류) 본문 대신 초록을 그대로 쓰도록 되돌린다
데이터 형식
입력
{
  "title": "Tree-of-Agents: Hierarchical Planning...",
  "abstract": "We present a hierarchical..."
}
출력
{
  "need_fulltext": true,
  "reason": "새 알고리즘을 제안하나 초록에 세부 설정이 없음"
}
완료 기준
터미널 코드(오프라인 테스트) 웹(완성 후)
터미널 — python -m app.agent 출력의 read 이벤트에서 used_fulltext 값이 논문마다 다르게(true/false) 찍히는지 확인.
코드 — 존재하지 않는 PDF 주소로 fetch_fulltext()를 직접 호출해 예외 없이 None이 반환되고, 이후 초록으로 자동 대체되는지 확인(Week 1 검증 완료).
웹(완성 후) — 카드에 "본문까지 읽음" / "초록으로 충분" 배지가 논문마다 다르게 붙는지 확인. (Week 3)
3
요약
summarize
논문마다 · 검증과 왕복
역할 논문 하나를 "기여 · 방법 · 결과" 세 자리로 고정된 형식에 맞춰 정리한다.
왜 필요한가 자유 문단으로 요약하면 논문마다 정보가 다른 자리에 있어 훑어보기 어렵다. 세 항목이 항상 같은 자리에 있어야 여러 카드를 눈으로 훑으며 비교할 수 있다.
어떤 방식 논문 제목과 (초록 또는 본문) 내용을 LLM에게 주고 세 항목을 받는다. 형식이 깨져서 못 읽으면 같은 요청을 다시 보내 최대 세 번까지 시도한다.
어떤 기준 전문 용어는 풀어쓰지 않고 그대로 둔다 — 연구자에게는 그게 더 정확한 정보다. 원문에 없는 내용은 지어내지 않고, 모르면 모른다고 쓴다. 세 번을 시도해도 형식이 안 나오면 이 논문은 실패 처리하고 다음으로 넘어간다.
처리 단계
  1. 도구 선택 단계에서 정해진 원문(초록 또는 본문 텍스트)을 가져온다
  2. 제목 + 원문(재시도라면 이전 피드백도 함께)을 프롬프트에 채워 LLM에게 보낸다
  3. 응답을 JSON으로 파싱 — 실패하면 같은 요청을 최대 3번까지 재시도
  4. 3번 다 실패하면 요약은 None → 이 논문은 처리 중단(부분 실패로)
  5. 성공하면 자기 검증(4단계)으로 넘긴다
데이터 형식
입력
{
  "title": "Tree-of-Agents: Hierarchical Planning...",
  "source_text": "(초록 또는 PDF 본문 텍스트)",
  "feedback_block": "(재시도 시에만 채워짐)"
}
출력
{
  "contribution": "긴 작업을 상위 계획과 하위 실행으로 분리하는
                    계층적 에이전트 구조를 제안.",
  "method": "상위 플래너가 목표를 하위 작업으로 분해하고,
             실패 시 상위로 되돌려 재계획.",
  "result": "WebArena에서 단일 에이전트 대비 성공률 18%p 상승.
             다만 비용은 2.3배."
}
완료 기준
터미널 코드(오프라인 테스트) 웹(완성 후)
터미널 — python -m app.agent 출력의 paper_done 이벤트에 contribution·method·result 세 키가 모두 채워져 찍히는지 확인.
코드 — 일부러 깨진 JSON을 3번 연속 반환하도록 mock해, 이 논문만 paper_failed로 빠지고 나머지 파이프라인은 멈추지 않는지 확인(이미 검증됨).
웹(완성 후) — 카드에 기여·방법·결과 세 줄이 항상 같은 자리에 보이는지 확인. (Week 3)
4
자기 검증
verify · Reflexion
논문마다 · 최대 2회 되돌림
역할 방금 만든 요약이 실제로 쓸 만한지 스스로 다시 읽고 평가한다. 부실하면 요약 단계로 되돌려 다시 쓰게 한다.
왜 필요한가 "스스로 점검했다"는 사실 자체가 이 서비스가 파는 신뢰의 일부다. 검증 없이 한 번에 나온 요약을 그대로 내보내면, 부실한 요약이 걸러지지 않은 채 그대로 사용자에게 간다.
어떤 방식 원문과 방금 만든 요약을 함께 LLM에게 보여주고 "이 요약이 괜찮은가"를 판정받는다. 괜찮지 않다면 무엇이 부족한지 피드백을 받아, 그걸 다음 요약 시도에 그대로 붙여준다.
어떤 기준 지어낸 내용이 없는지가 가장 중요하다. 그 외 이 논문만의 기여가 맞는지, 결과에 근거(수치·실험)가 있는지를 본다. 최대 두 번까지 되돌리며, 두 번을 넘기면 마지막 요약을 그대로 쓴다 — 이미 만든 것을 버리지 않는다.
처리 단계
  1. 방금 만든 요약과 원문을 함께 프롬프트에 채워 LLM에게 "이 요약이 괜찮은가"를 묻는다
  2. 응답을 JSON으로 파싱 — 실패하면 is_good: true로 간주(통과, 비용이 적은 쪽 fallback)
  3. is_good이 true면 이 요약을 그대로 채택하고 트렌드 추론(5단계)으로 넘어간다
  4. false면 feedback을 저장하고, 요약(3단계)으로 되돌아가 feedback을 프롬프트에 포함해 다시 시도한다
  5. 이 왕복을 최대 2회까지 반복하고, 그 이후엔 마지막 요약을 그대로 채택한다
데이터 형식
입력
{
  "title": "...",
  "source_text": "...",
  "summary_json": {"contribution": "...", "method": "...", "result": "..."}
}
출력
{
  "is_good": false,
  "feedback": "실험 설정 설명이 누락됨"
}
완료 기준
터미널 코드(오프라인 테스트) 웹(완성 후)
터미널 — python -m app.agent 출력에 retry 이벤트가 최소 한 번은 실제로 찍히는지 확인. 한 번도 안 나오면 verify 프롬프트가 너무 관대하다는 신호.
코드 — is_good: false를 mock으로 반환시켜, 다음 요약 시도의 프롬프트에 feedback이 실제로 포함되고 최대 2회를 넘겨 되돌지 않는지 확인(이미 검증됨, attempt: 1로 정확히 한 번 발동).
웹(완성 후) — 앰버 톤 재시도 로그가 화면에서 감춰지지 않고 남아 있는지 확인. (Week 3)
5
트렌드 추론
trend
전체 요약 종합 · 1회
역할 개별 논문 요약들을 다시 훑어보고, 여러 논문을 관통하는 흐름이나 연결점을 찾는다.
왜 필요한가 요약 목록만 쭉 나열되면 "그래서 요즘 무슨 흐름인지"는 사용자가 직접 머릿속에서 조합해야 한다. 이 단계가 그 일을 대신해줘야 단순 요약 사이트와 달라진다.
어떤 방식 지금까지 만든 모든 요약을 한꺼번에 LLM에게 보여주고, 공통된 흐름과 그 흐름을 뒷받침하는 논문들을 함께 받는다. 흐름마다 반드시 근거가 된 논문을 표시하게 한다.
어떤 기준 흐름 하나에 최소 두 편 이상의 논문이 근거로 있어야 한다 — 한 편만 해당하면 그건 흐름이 아니라 그 논문만의 특징이다. "여러 논문이 이 주제를 다룬다" 같은 당연한 말은 흐름으로 치지 않는다. 근거를 댈 수 없는 흐름은 애초에 만들지 않는다. 요약된 논문이 하나도 없으면 이 단계는 건너뛴다.
처리 단계
  1. 성공한 모든 논문의 요약을 index + title + 3키 요약 형태로 모은다
  2. 성공한 논문이 하나도 없으면 LLM 호출 없이 곧장 빈 결과로 건너뛴다
  3. 주제와 모은 요약 목록을 프롬프트에 채워 LLM에게 보낸다
  4. 응답을 JSON으로 파싱 — 실패하면 흐름 없이 트렌드 없는 상태로 간주
  5. 결과를 최종 완료 이벤트에 담아 전체 파이프라인을 마무리한다
데이터 형식
입력
{
  "topic": "LLM agent planning", "n": 3,
  "summaries_json": [
    {"index": 1, "title": "...", "contribution": "...",
