# 사내 LLM 사용 보안 게이트웨이

## 1. 문제 정의

### 1.1 문제 상황

조직 구성원이 업무에 ChatGPT·Claude·Gemini 같은 외부 LLM API를 사용하는 것이 일상화되면서, 프롬프트 안에 개인정보(이름, 전화번호, 주민번호, 이메일 등)나 사내 기밀(영업 정보, 미공개 코드, 고객 데이터)을 그대로 입력한 채 외부로 전송하는 사고가 발생할 수 있다.

문제는 이를 막을 지점이 없다는 것이다. 각 임직원이 어떤 LLM을, 어떤 프롬프트로 호출하는지 조직 차원에서 파악하거나 통제하기 어렵고, 사후에 로그를 확인하는 방식으로는 이미 정보가 외부로 나간 뒤다.

### 1.2 왜 사내 LLM(자체 구축)이 아니라 외부 API + 게이트웨이인가

이 문제를 풀 때 "애초에 외부로 나가는 것 자체가 문제라면, 사내에 Llama 같은 오픈소스 LLM을 직접 띄워서 폐쇄망 안에서만 쓰면 되지 않느냐"는 반론이 나올 수 있다.

하지만 이 서비스가 타깃으로 하는 조직은 정확히 반대 상황에 있다. Claude·GPT 같은 상용 API가 제공하는 최신 모델 성능(코드 생성, 복잡한 추론, 최신 지식 반영)이 업무에 필요해서 이미 쓰고 있거나 써야 하지만, 그 과정에서 요청에 개인정보·기밀이 새어나가는 것은 막고 싶은 조직이다. 사내 LLM 자체 구축은 이런 조직에게 대안이 되지 못한다.

| 사내 LLM 자체 구축 | 게이트웨이 + 외부 API |
|---|---|
| Llama·Qwen 등 오픈소스 모델은 최신 상용 모델(Claude, GPT) 대비 성능 격차가 존재 | 항상 최신 상용 모델의 성능을 그대로 활용 |
| GPU 인프라 구축·운영 비용, 모델이 나올 때마다 재배포 필요 | 인프라 부담 없이 API 사용료만 지불 |
| 파인튜닝·서빙 전담 인력 필요 | 게이트웨이 도입만으로 기존 워크플로우 유지 |

즉 이 서비스는 "사내 LLM으로 대체"가 아니라, **이미 쓰고 있고 앞으로도 써야 하는 외부 상용 API의 요청 경로에 보안 통제를 끼워 넣는 것**을 목표로 한다. 로컬 LLM(Ollama 등)은 이 구조에서도 쓰이지만, 그 역할은 사용자의 실제 업무 요청을 대신 처리하는 것이 아니라 요청 내용의 위험도를 판단하는 보조 검사기(3.4)로 한정된다.

### 1.3 왜 "생성 결과 검증"이 아니라 "요청 가로채기"인가

LLM이 만든 응답을 사후에 검수하는 방식(RAG 기반 문서 검색·사후 감사 등)도 고려할 수 있지만, 이 서비스가 막으려는 사고는 애초에 **요청에 담겨 나가는 입력값**이다. 응답을 아무리 잘 검증해도 프롬프트 자체에 포함된 개인정보·기밀은 이미 LLM 제공자 서버로 전송된 뒤이므로 사후 대응으로는 늦다.

그래서 이 서비스는 문서를 검색해 응답을 보강하는 RAG 구조가 아니라, 임직원의 요청이 실제 LLM API로 나가기 전 **중간에서 요청을 가로채 검사하는 프록시(게이트웨이)** 구조를 택한다. 이 구조에서는 검사 대상이 "요청 텍스트"로 고정되기 때문에 문서 검색·임베딩 같은 RAG 요소가 필요 없다.

### 1.4 문제 정의 요약

> 클로드·GPT 등 최신 상용 LLM API를 업무에 써야 하지만 보안 통제가 필요한 조직을 대상으로, 외부로 나가는 요청에 개인정보·기업 기밀이 포함되어 있는지 실시간으로 탐지하고 정책에 따라 마스킹·차단·통과를 결정하는 프록시형 게이트웨이로 해결한다. 사내 LLM을 직접 구축하는 대신, 이미 쓰고 있는 외부 API의 요청 경로에 보안 계층만 추가하는 접근이다. 정규식 탐지, NER 개체명 인식, 로컬 LLM 기반 위험도 판단을 조합하되, 연구형 정확도가 아니라 **동작하는 파이프라인**을 목표로 한다.

## 2. 사용자 시나리오

커넥트웍스(3.4.1의 가상 조직) 소속 개발자 B는 자신의 사번 계정으로 사내 업무용 LLM 챗봇(사내 게이트웨이를 거쳐 실제로는 OpenAI API를 호출하는 내부 도구)에 로그인한다. 기존 채팅 세션 목록에서 새 세션을 열고, 고객 문의 로그를 붙여넣은 뒤 "이 문의 내용을 요약해줘"라고 요청한다. 로그에는 고객의 전화번호와 이메일이 그대로 포함되어 있다.

**1) 요청 전송**
B가 요청을 보내면, 실제 OpenAI로 가기 전에 게이트웨이가 요청 본문을 가로챈다.

**2) 탐지**
게이트웨이는 정규식으로 전화번호·이메일 패턴을 찾아내고, NER 모델로 로그에 섞여 있던 고객 이름을 추가로 탐지한다. 동시에 로컬 LLM이 텍스트 전체를 훑어 "고객 개인정보로 의심되는 내용이 포함되어 있다"는 위험도 점수를 매긴다.

**3) 정책 적용**
DLP 정책 엔진은 탐지된 전화번호·이메일·이름을 마스킹(`010-****-5678`, `홍*동` 등)으로 치환한 뒤, 마스킹된 텍스트를 실제 OpenAI API로 전달한다. 만약 위험도가 특정 임계치를 넘는 경우(예: 사내 기밀 유출 의심)에는 마스킹이 아니라 요청 자체를 차단하고 B에게 사유를 안내한다.

**4) 응답 반환 및 로그 적재**
B는 마스킹된 입력 기준으로 요약된 응답을 받는다. 게이트웨이는 이번 요청에서 무엇이 탐지되어 어떤 조치를 취했는지 로그로 남긴다.

## 3. 핵심 기능

### 3.1 멀티 LLM 게이트웨이 (프록시 + 어댑터 패턴)
`LLMProvider` 인터페이스를 두고 OpenAI·Claude·Gemini 등 제공자별 어댑터를 구현한다. 클라이언트는 게이트웨이의 통일된 엔드포인트(`/v1/chat`)만 호출하고, 게이트웨이가 내부적으로 실제 제공자 API로 라우팅한다.

### 3.2 정규식 기반 PII·인프라 값 탐지 + 마스킹
전화번호, 주민등록번호, 이메일, 카드번호, API 키 등 패턴이 정형화된 개인정보를 정규식으로 탐지하고, 탐지된 값을 마스킹 처리(`010-1234-5678` → `010-****-5678`)해 원문 대신 전달한다.

#### 3.2.1 코드 붙여넣기에 대한 정책

개발자가 사내 코드를 붙여넣고 질문하는 것은 이 서비스에서 가장 빈번한 사용 패턴이므로 별도 원칙을 둔다. **코드 안에 박힌 "값"과 코드의 "로직"을 나눈다.**

| 대상 | 예 | 조치 | 근거 |
|---|---|---|---|
| 코드 속 자격증명·인프라 값 | 내부 IP, 사내 도메인, DB 접속 문자열, API 키, private key | 마스킹 | LLM이 실제 값을 알 필요가 없어 가려도 답변 품질이 떨어지지 않는다 |
| 코드 로직·구조 자체 | 비즈니스 알고리즘, 클래스 설계 | 통과 + 로깅 | 가리면 질문이 성립하지 않고, 기밀 여부 판별도 불가능하다 |

원칙은 **마스킹해도 손해가 없는 것만 마스킹한다**는 것이다. nginx 설정을 고쳐달라고 할 때 서버 IP가 `10.0.3.14`든 `<INTERNAL_IP_1>`이든 LLM의 답은 같지만, 함수명과 로직을 가리면 답이 나올 수 없다. 로직 영역은 차단하는 대신 탐지 로그(3.6)에만 남겨 사후 추적 대상으로 넘긴다.

#### 3.2.2 탐지 패턴 목록

| 구분 | 패턴 |
|---|---|
| 개인정보 | 전화번호, 주민등록번호, 이메일, 카드번호 |
| 자격증명 | API 키·토큰, `-----BEGIN ... PRIVATE KEY-----` 블록, `.env` 형태의 `KEY=VALUE` |
| 인프라 값 | 사설 IP(`10.x.x.x`, `172.16~31.x.x`, `192.168.x.x`), 내부 호스트·도메인(`*.internal`, `*.local`, 사내 도메인), DB 접속 문자열(`postgres://user:pw@host:5432/db`) |

인프라 값 3종은 3.2.1의 "마스킹해도 손해 없는 값"에 정확히 해당하는 실질적 방어선이다.

#### 3.2.3 응답 역치환 (P2)

마스킹 시 `10.0.3.14` → `<INTERNAL_IP_1>` 치환 맵을 요청 단위로 보관했다가, LLM 응답이 돌아올 때 역치환하면 사용자는 실제 값이 박힌 완성된 결과를 받는다. 외부로는 나가지 않았는데 사용자 경험은 무손실이다. 보안 목표가 "외부 전송 차단"이지 "직원에게 숨기기"가 아니고, 어차피 사용자 본인이 입력한 값이므로 논리적으로도 어긋나지 않는다. 구현은 치환 맵 하나면 되지만 우선순위는 P2로 둔다.

### 3.3 NER 기반 개체명 탐지
정규식만으로는 잡히지 않는 사람 이름·주소·회사명 등 비정형 개인정보를 이미 학습된 한국어 NER 모델(HuggingFace 공개 모델)로 태깅한다. 직접 파인튜닝하지 않고 추론(inference)만 수행한다.

### 3.4 로컬 LLM 기반 위험도 분석
Ollama 등으로 로컬에 띄운 소형 LLM(Llama3 8B, Qwen2.5 7B 등)에 "이 텍스트에 기업 기밀·영업정보로 의심되는 내용이 있는지 판단해 위험도 점수(0~100)와 이유를 JSON으로 반환하라"는 분류 프롬프트를 던져, 정규식·NER로 잡히지 않는 맥락적 위험(영업 비밀, 미공개 계획 등)을 보완적으로 탐지한다. 파인튜닝은 하지 않는다.

정규식은 정형 PII, NER은 인명·지명·기관명 태깅까지만 담당하므로 **"이 내용이 대외비인가"를 실제로 판정하는 것은 이 로컬 LLM 하나뿐이다.** 따라서 아래 카테고리 정의가 곧 이 분류 프롬프트의 명세이며, DLP 정책 규칙(3.5)과 QA 시나리오의 정답 기준도 여기서 파생된다.

#### 3.4.1 데모 기준 가상 조직

대외비의 범위는 조직마다 다르므로, 판정 기준을 세우려면 소속 조직이 먼저 고정되어야 한다("우리 회사 3분기 매출"은 대외비지만 "네이버 작년 매출 알려줘"는 통과여야 한다). 데모에서는 아래 가상 조직을 기준으로 삼는다.

> **커넥트웍스(ConnectWorks)** — 사내 협업 SaaS를 만드는 직원 200명 규모의 중견 IT 기업. 세이프게이트를 도입해 임직원의 외부 LLM 사용을 통제한다.

| 구분 | 값 |
|---|---|
| 프로젝트 코드명 | 오로라(차세대 에디터), 세이렌(결제 리뉴얼), 하버(데이터 파이프라인) |
| 내부 시스템명 | 클로버허브(사내 포털), 아톰(배포 시스템), 렛저(정산 시스템) |
| 주요 거래처(가상) | 대한물산, 미래테크, 한빛금융 |

이 고유명사들은 정규식으로도 NER로도 걸러지지 않는다(NER은 `프로젝트 오로라`를 기관명으로 태깅할 수는 있어도 그것이 대외비인지는 모른다). 그래서 조직별 기밀 용어를 코드에 하드코딩하지 않고 `server/src/services/detectors/confidential-terms.json` 사전 파일로 분리해, 로컬 LLM 분류 프롬프트에 컨텍스트로 주입한다. 조직이 바뀌면 이 파일만 교체하면 된다.

#### 3.4.2 기밀 카테고리

| 카테고리 | 예시 | 기본 조치 |
|---|---|---|
| 미공개 재무·실적 | "3분기 영업이익률이 12%로 나왔는데 이걸로 보고서 써줘" | 차단 |
| 계약·거래조건 | "대한물산 단가를 15% 할인해주는 조건인데 검토해줘" | 차단 |
| 미공개 제품·로드맵 | "프로젝트 오로라 11월 출시 일정 정리해줘" | 차단 |
| 내부 시스템 구성 | "아톰 배포 서버가 10.0.3.14인데 이 설정 파일 고쳐줘" | 값만 마스킹 (3.2.1) |
| 인사 정보 | "김OO 인사평가 C등급인데 피드백 문구 작성해줘" | 차단 |
| 법무·분쟁 | "한빛금융과 진행 중인 소송 대응 논리 정리해줘" | 차단 |

API 키·토큰 등 자격증명은 패턴이 정형화되어 있어 정규식(3.2)이 담당하므로 이 표에서 제외한다.

#### 3.4.3 용어 사전은 차단 목록이 아니라 카테고리 태깅용이다

사전에 등재된 용어가 나왔다고 해서 곧바로 차단하면 정당한 업무 질문이 막힌다. 예를 들어 "아톰 배포가 실패하는데 이 설정 좀 봐줘"는 시스템 이름 하나가 언급됐을 뿐 유출 피해가 없는 요청인데, 단순 키워드 매칭 방식에서는 차단된다. 반대로 같은 요청에 들어 있던 DB 비밀번호와 내부 IP는 정규식 목록에 없어 그대로 통과한다 — **막아야 할 것은 놓치고 막지 말아야 할 것은 막는** 최악의 조합이다.

따라서 `confidential-terms.json`의 각 항목은 소속 카테고리와 조치(`차단` / `마스킹` / `로깅만`)를 함께 갖는다. 사전은 "무엇을 막을지"의 목록이 아니라 "무엇이 어느 카테고리인지"의 사전이고, 최종 판단은 DLP 정책 엔진(3.5)이 한다. 내부 시스템명은 `로깅만`, 재무·실적 용어는 `차단`으로 등재하는 식이다.

#### 3.4.4 위험도 임계치

| 점수 | 조치 |
|---|---|
| 0~59 | 그대로 통과 |
| 60~79 | 마스킹 후 통과 |
| 80~100 | 차단 |

초기값이며, 2주차에 실제 Ollama 점수 분포를 확인한 뒤 조정한다.

### 3.5 DLP 정책 엔진
탐지 결과(정규식 + NER + 위험도 점수)를 종합해 "차단 / 마스킹 후 전달 / 그대로 통과" 중 하나로 분기하는 규칙 기반 엔진이다. 초기 버전은 if-else 조합의 단순 규칙 3~5개로 시작한다.

### 3.6 탐지 로그
어떤 요청에서 무엇이 탐지되어 어떤 조치가 취해졌는지 저장한다. 대시보드 UI는 향후 확장으로 미루고, 초기에는 콘솔 로그 또는 간단한 테이블 조회로 대체한다. 모든 로그는 어떤 사용자가 보냈는지(3.7) 식별자로 연결되어, 사용자별 탐지 이력 조회가 가능하다.

### 3.7 사용자 인증 및 채팅 세션
사원은 회원가입으로 계정(사번/이름/비밀번호)을 직접 생성하고, 로그인해야 chat-demo·log-viewer에 접근할 수 있다. 로그인 후에는 실제 사내 챗봇처럼 사용자별로 채팅 세션이 분리되어, 이전 대화 목록을 이어서 조회할 수 있다. 탐지 로그(3.6)도 "누가" 보냈는지 사용자 단위로 귀속되어, 반복적으로 민감정보를 입력하는 사용자·부서를 log-viewer에서 식별할 수 있게 한다.

### 3.8 요청 속도 제한 (Rate Limiting)
`/v1/chat`은 요청마다 외부 LLM API를 호출하므로, 특정 계정이 짧은 시간에 요청을 반복하면 비용·남용 위험이 있다. 이를 막기 위해 **계정(로그인 사용자) 단위로 요청 한도**를 둔다. 데모 범위에서는 보수적으로 **분당 3회, 시간당 10회**를 기본값으로 하고, 한도를 넘으면 LLM을 호출하지 않고 `429`(요청 한도 초과)로 응답하며 재시도까지 남은 시간을 안내한다. 한도값은 환경변수로 조정 가능하다. IP가 아니라 계정 기준이므로, 로그인해야 접근 가능한(3.7) 구조와 함께 "누가 얼마나 요청했는지"를 사용자 단위로 통제한다.

## 4. 개발 범위 — 3주 MVP 기준

3주 안에 4개 기능(정규식 탐지, NER, 로컬 LLM 위험분석, DLP 정책)을 포함한 멀티 LLM 게이트웨이를 "완전한 프로덕션 수준"으로 만드는 것은 불가능하다고 판단, **기존 오픈소스·API를 조합하는 엔지니어링**으로 접근 범위를 좁힌다 — NER 모델은 직접 학습하지 않고 공개 모델을 가져다 쓰고, 로컬 LLM 위험분석도 파인튜닝 없이 프롬프트 분류로 대체한다.

| 우선순위 | 기능 | 시간 부족 시 대안 |
|---|---|---|
| 필수 | 정규식 탐지 + 마스킹 | 그대로 구현 |
| 필수 | 게이트웨이 프록시 구조 | 그대로 구현 |
| 필수 | 사용자 인증(회원가입/로그인) + 채팅 세션(3.7) | 그대로 구현 |
| 중요 | NER 개체명 인식 | 공개 데모/API 활용, 직접 서빙 최소화 |
| 중요 | 로컬 LLM 위험분석 | 프롬프트 기반으로 심플하게 (파인튜닝 금지) |
| 있으면 좋음 | DLP 정책 엔진 | 규칙 3~5개짜리 단순 버전 |
| 있으면 좋음 | 대시보드/로깅 UI | 콘솔 로그 + 간단 테이블로 대체 |

### 주차별 계획

**1주차 — 학습 + 뼈대 구축**
- LLM API 사용법(메시지 구조, 스트리밍 여부), 분류 프롬프트 작성법, PII 정규식 패턴, Ollama 사용법, 프록시/미들웨어 패턴 학습
- `/v1/chat` 엔드포인트로 요청을 그대로 실제 LLM API에 통과시키는 최소 프록시 구현
- `LLMProvider` 어댑터 인터페이스 설계 (OpenAI/Claude/Gemini 구현체)
- PII 정규식 패턴 목록 정리(문서화)

**2주차 — 핵심 탐지 기능**
- HuggingFace `transformers` 추론 사용법, 한국어 NER 모델 후보 조사(klue/bert-base 계열, Bareun, KoNLPy+개체명사전 등) 학습
- 정규식 탐지 + 마스킹 로직 구현
- NER 파이프라인 연동(사람이름/주소/회사명 태깅)
- 정규식 + NER 결과 통합 함수
- Ollama 로컬 LLM에 위험도 분석 프롬프트 연동
- (권장) 1주차가 끝나는 시점에 NER 후보 모델 2~3개를 미리 로컬에서 돌려본다 — 이 주가 가장 시간이 많이 들 것으로 예상되는 구간

**3주차 — 통합 + 데모**
- DLP 정책 설계, 간단한 로깅 구조 학습
- 탐지 결과에 따른 차단/마스킹/통과 정책 분기 로직
- 전체 파이프라인 연결(요청 → 탐지 → 마스킹/차단 → LLM 호출 → 응답)
- 민감정보 포함 시나리오 테스트 케이스 작성
- 데모용 프론트/스웨거 문서, 발표자료 준비

## 5. 기술 스택 및 프로젝트 구조

### 5.1 프론트엔드 — 데모 화면 구성

데모 목적의 화면으로, 로그인 세션(전역으로 유지해야 하는 상태) 하나만 화면 간에 공유되고 나머지는 화면별 로컬 상태로 충분하다. 로그인 여부만 가벼운 컨텍스트로 두고, zustand 같은 전역 상태 라이브러리는 도입하지 않는다.

- **auth**: 회원가입(사번/이름/비밀번호)·로그인 화면
- **chat-demo**: 로그인한 사용자의 채팅 세션 목록 + 세션별 대화, 프롬프트 입력 → 전송 → 결과 카드(그대로 통과 / 마스킹 후 통과 / 차단) 표시, 탐지된 항목과 사유 하이라이트
- **log-viewer**: 탐지 로그(3.6)를 시간·사용자·탐지항목·조치결과 컬럼의 테이블로 조회, 최신순. 사용자별 필터링 가능

```
src/
├── components/              # 공통 UI (Button, Badge, Table 등)
├── features/
│   ├── auth/                # 회원가입/로그인
│   ├── chat-demo/           # 채팅 세션 목록 + 프롬프트 입력 → 결과(마스킹/차단) 표시
│   └── log-viewer/          # 탐지 로그 테이블 조회 (사용자별 필터)
├── api/                     # axios client, /v1/auth, /v1/chat, /v1/logs 호출 함수
└── main.jsx
```

### 5.2 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 프론트 | React + Vite | 화면 2개뿐이라 zustand 제외, axios만 사용 |
| 백엔드 | Express (Node 단일) | 게이트웨이가 I/O 바운드(외부 LLM API·Ollama 호출 대기)라 Node 비동기 모델과 맞음 |
| NER | 우선 HuggingFace Inference API 호출 | 4번 표의 "공개 데모/API 활용" 대안과 동일 노선. 안 되면 2주차에 Python(FastAPI+transformers) 서비스로 전환 — [backlog.md](backlog.md) P1 "로컬 테스트"는 이 판단을 위한 모델 선정용 스크립트로 우선 취급 |
| 로컬 LLM 위험도 | Ollama REST API를 Node axios로 직접 호출 | 언어 무관하게 REST라 별도 서비스 불필요 |
| 사용자 인증 | 세션 기반 로그인(`express-session`) + 비밀번호 해시(`bcrypt`) | 별도 SSO 연동 없이 자체 계정 시스템으로 시작 |
| 탐지 로그·계정·세션 저장 | better-sqlite3 | 로그·계정 규모가 작아 파일 DB로 충분 |

### 5.3 프로젝트 디렉토리 구조

```
hub/
├── src/                     # 프론트 (5.1 구조)
├── server/
│   ├── src/
│   │   ├── routes/          # /v1/auth, /v1/chat, /v1/logs
│   │   ├── providers/       # LLMProvider 어댑터 (openai/claude/gemini)
│   │   ├── services/
│   │   │   ├── detectors/   # regex 탐지, NER 클라이언트, Ollama 위험도 클라이언트
│   │   │   │                 #  + confidential-terms.json (조직별 기밀 용어 사전, 3.4.1)
│   │   │   ├── policy/      # DLP 정책 엔진 (차단/마스킹/통과 분기)
│   │   │   └── auth/        # 회원가입/로그인, 세션 검증
│   │   ├── data/            # sqlite DB (사용자/세션/채팅/로그)
```

## 6. (참고) 향후 고려

정규식·NER의 탐지 정확도 고도화, 로컬 LLM 파인튜닝, 탐지 로그 기반 대시보드 UI, 정책 엔진의 규칙 확장 등은 3주 MVP 이후 확장 과제로 검토한다. 데모 단계에서는 "전화번호를 넣으면 마스킹되고, 기업 기밀 문장을 넣으면 차단되는" 시나리오 3~4개가 안정적으로 동작하는 것을 목표로 한다.
