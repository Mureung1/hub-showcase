01 / Data lineage

원본을 바로 화면에 쓰지 않습니다.

서로 다른 기관의 데이터를 정제·검증하고, 반복 가능한 기준본을 거쳐 서비스 DB로 올립니다. 이 과정이 숫자의 신뢰성과 재현성을 만듭니다.

01 INPUT서울시 · KOSIS
공공 원천 데이터점포, 상권, 매출, 유동인구, 인구
02 PREPARE수집 · 정제
형식 통일컬럼, 기간, 좌표계, 결측값을 맞춤

data_sources가 하는 일

원천 제공처, 수집시점, 기준 기간, 행 수, 원본 URL, SHA-256 hash를 남깁니다. 분석 숫자가 어디서 왔는지 나중에도 추적할 수 있습니다.

SQLite를 먼저 쓰는 이유

운영 DB에서 import를 반복하지 않고, 로컬 기준본에서 중복·누락·공간 연결을 먼저 검증합니다. SQLite는 임시 DB가 아니라 재현 가능한 기준 시료입니다.

“이 숫자가 어디에서, 언제 왔는가?”를 data_sources로 답할 수 있게 설계했습니다.

02 / Database map

점포, 상권, 통계는 서로 다른 단위입니다.

03 / Analysis journey

분석은 예측이 아니라, 근거 있는 비교입니다.

사용자가 고른 상권·업종·분기를 기준으로 공식 지표를 조회하고, 수요·경쟁·매출·안정성을 나누어 보여줍니다.

월 추정매출, 결제 건수, 평일·주말과 시간대별 매출을 봅니다.

LocalTwin은 “여기서 창업하면 성공한다”를 단정하지 않습니다. 수요·경쟁·매출·안정성의 근거를 한 화면에 모아 사용자가 판단하도록 돕습니다.

06 / Quality & operations

기준본에서 검증하고, 운영 환경으로 승격합니다.

로컬 SQLite 검증은 화면이 뜨는지 보는 과정이 아닙니다. 공공 원천 데이터를 서비스 DB로 옮겨도 숫자·관계·좌표·기간·출처가 깨지지 않는지 확인하는 품질 단계입니다.

SQLite 기준 시료

중복·누락, 키 관계, 좌표 범위, 분기, 시간대 값, 원천 hash를 검증합니다.

반드시 구분해 표시할 숫자

현재 점포 위치 기반 수, 분기별 공식 통계, 반경 조건의 주변 점포 수는 계산 기준이 다릅니다. 값뿐 아니라 기준시점·공간 범위·출처를 함께 보여야 합니다.

3D Gaussian Splatting의 위치

사진·영상 기반 3DGS는 현장 탐색 가능성을 검증하는 실험 기능입니다. 핵심 분석 기능과 분리하며, 저장소·GPU·개인정보 처리 조건을 별도 운영합니다.

The four lines to remember

LocalTwin을 설명하는 네 문장

  1. 공공데이터를 정제하고 출처까지 기록합니다.
  2. Supabase에는 서비스가 조회할 검증된 데이터를 넣습니다.
  3. FastAPI가 분석 규칙과 DB 조회를 맡고, React는 결과를 이해하기 쉬운 화면으로 바꿉니다.
  4. 지도는 전체를 빠르게 보여주고, 선택 점포만 3D로 자세히 탐색합니다.
