## 작업 내용

`docs/rules/subTasks.md`의 화면10(투표 마감 확인 모달)·화면11(최종 결과 화면)을 개선하고, 화면12(전체 공통 마무리 워크스루)로 이번 UI/UX 고도화 4개 묶음 전체를 점검한다. 검증 과정에서 추가로 발견된 마감 요청 중복 처리 방지, 그리고 지금까지 앱 어디서도 실제로 쓰이지 않던 `Toast` 컴포넌트를 일정 응답 제출 완료 알림에 실제로 도입하는 작업도 이 묶음에 포함한다.

## 확정된 설계 결정

- 결과 화면의 페이지네이션 훅은 `ResultHeatmap.tsx`가 소유한다 — `ResultPage.tsx`엔 로딩/에러/리다이렉트 조건부 `return`이 여러 개 있어서 그 뒤에서 새 훅(`usePagedDateRange`)을 부르면 Hooks 규칙 위반이 된다. `ResultHeatmap.tsx`는 그 조건부 return들을 다 통과한 뒤에만 마운트되므로(`SchedulePage.tsx`의 로딩 게이트를 통과한 뒤에만 마운트되는 `ScheduleEditor.tsx`와 동일한 구조) 그 안에서 훅을 부르면 안전하다.
- 마감 확인 모달은 `isClosing` 상태를 추가해 마감 버튼 중복 클릭, 요청 중 취소 버튼 클릭, 요청 중 배경(overlay) 클릭으로 모달이 닫히는 것을 막는다 — `ScheduleEditor.tsx`의 확정 모달이 이미 `isSubmitting`으로 이 패턴을 쓰고 있으므로 그대로 재사용한다.
- 마감 확인 모달의 참여 현황은 `ProgressBar`만 넣지 않는다. `ProgressBar` 자체는 막대만 그리고 수치는 표시하지 않으므로, 관리자 대시보드 본문과 동일하게 "N명 중 M명 완료" 텍스트 + 퍼센트를 함께 보여준다.
- `Toast`(`useToast`)는 현재 앱 어디서도 호출되지 않는 죽은 코드 상태임을 확인함(`CopyLinkBox`는 로컬 `copied` state를 씀, Toast와 무관). 이번 기회에 **일정 응답 제출 완료 시**(`ScheduleEditor.tsx`의 `handleConfirm` 성공 이후) "응답이 저장됐어요" 토스트를 실제로 띄우는 데 처음 도입한다. `ScheduleEditor.tsx`는 subTask3 소관 파일이라, 이 항목은 subTask3 작업과 맞물려 진행한다.

## 우선순위

- 1·2번(마감모달, 결과화면)이 핵심, 3번(Toast 도입)도 이번에 실제로 진행, 4번(마무리 워크스루)까지가 이번 UI/UX 고도화의 필수 범위
- 후순위 항목은 필수 범위 밖 — 1~4번을 다 끝낸 뒤에 사용자와 상의해서 진행

## 작업 순서

아래 순서대로 진행한다. 각 묶음이 끝날 때마다 수동으로 확인한 뒤 다음 묶음으로 넘어간다.

### 1. 투표 마감 확인 모달
1. 상단에 경고 아이콘(빨간/주황 원형 배지, 느낌표) 추가
2. "투표를 마감할까요?" 제목 + 참여 현황을 "N명 중 M명 완료" 텍스트 + 퍼센트 + `ProgressBar`(2주차 UIUX-2에서 만든 컴포넌트)로 함께 표시 — 관리자 대시보드 본문의 `dashboard-section`/`dashboard-status-row` 패턴 재사용
3. "마감 후에는 참여자가 더 이상 응답을 수정할 수 없습니다" 안내 문구
4. "마감할게요"(빨간 버튼, 기존 `.button--danger` 클래스 재사용)/"취소" 버튼 스타일 정리
5. `isClosing` 상태 추가 — 요청 중 "마감할게요" 버튼 중복 클릭 방지, "취소" 버튼 비활성화, 배경(overlay) 클릭으로 모달이 닫히지 않도록 `Modal`의 `onClose`에서 `isClosing`이면 무시(`ScheduleEditor.tsx`의 `isSubmitting` 패턴 재사용)

이 묶음이 끝나면: 마감 확인 모달에서 실제 참여 현황(수치+퍼센트+막대바)이 정확히 표시되고, 마감 버튼 클릭이 실제 마감 처리까지 이어지는지, 요청 중에는 중복 클릭·취소·배경 클릭이 모두 무시되는지 확인한다.

### 2. 최종 결과 화면
6. `ResultHeatmap.tsx` 내부에서 `usePagedDateRange(slots)` 훅을 호출해 페이지네이션 적용 — 화살표로 7일씩 이동. `ResultPage.tsx`는 조건부 return이 있어 그 뒤에서 훅을 부르면 안 되므로 건드리지 않는다.
7. 페이지 이동 시 색상 등급(순위 기반)이 페이지와 무관하게 전체 데이터 기준으로 정확히 유지되는지 확인 — `levelMap`은 `useScheduleResult.ts`에서 전체 슬롯 기준으로 이미 한 번만 계산되므로, 렌더링만 페이지 단위로 필터링하면 등급 계산 로직은 안 건드려도 자동으로 보장된다(별도 구현 불필요, 확인만).

이 묶음이 끝나면: 결과 화면에서 날짜를 넘겨도 히트맵 색상이 일관되게 보이는지 확인한다.

### 3. 일정 응답 제출 완료 토스트
8. `ScheduleEditor.tsx`의 `handleConfirm` 성공 후 `useToast()`로 "응답이 저장됐어요" 토스트 표시 — `Toast`가 이번에 처음으로 실제 사용되는 지점

이 묶음이 끝나면: 일정을 제출한 뒤 대시보드로 이동하면서 토스트가 뜨고 자동으로 사라지는지 확인한다.

### 4. 전체 공통 마무리
9. subTask1~4의 완료 기준 전체(화면1~12)를 순서대로 워크스루하며 하나씩 재확인 — `ScreenHint` 안내문구·전환 트랜지션 적용 여부 포함
10. 빠진 부분 보완

이 묶음이 끝나면: 홈부터 결과 화면까지 전체 플로우를 한 번에 수동으로 훑어 subTask1~4의 완료 기준이 모두 반영됐는지 확인한다.
