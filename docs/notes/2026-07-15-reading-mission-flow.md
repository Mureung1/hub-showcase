# 읽기·미션 흐름 결정 (2026-07-15)

API 설계 검증 중 읽기 화면 방향을 두고 논의한 결과를 기록한다. 나중에 "왜 하이라이트를 안 하나"가 반드시 나올 내용이다.

## 결론

**하이라이트 없이, 글 전체를 대상으로 미션을 낸다.**

```
오늘의 글 → 원문 읽기(외부 저자 원글) → 미션(글 전체 대상) → 한 줄 기록
```

- `anchorType = whole_content`, `selectedQuote = null`
- 앱 내 하이라이트 없음, 문장 직접 입력 없음, 읽기 참여 측정 없음

## 검토한 대안과 탈락 이유

1. **원문 전문을 앱에 저장해 앱 내에서 하이라이트**
   - 저작권: RSS 전문을 저장·재노출하는 것은 법적 리스크. `content_strategy.md`가 이미 "본문 전문 저장 금지"로 정함.
   - 실서비스화 시 문제가 되므로 탈락.

2. **인앱 브라우저로 원문 열고 그 위에서 하이라이트**
   - 남의 페이지에 우리 UI를 얹어야 함 → 페이지마다 깨지고 회색지대.
   - 게다가 현재 스택은 React 웹. 인앱 브라우저는 네이티브 개념이고, 웹에서 iframe은 대부분 CSP로 차단됨.
   - 탈락.

3. **원문 읽고 돌아와 기억나는 문장을 직접 입력** (`user_quote`)
   - 저작권·기술 문제는 없음.
   - 타이핑/복붙 마찰이 크고 "할 일이 하나 더 생기는" 느낌. 사용자가 원치 않음.
   - 탈락.

4. **원문 읽고 → official_excerpt(공식 소개문)에서 하이라이트**
   - 소개문은 이미 합법 저장. 하지만 원문을 다 읽고 나서 소개문에 하이라이트하는 것은 의미가 약함.
   - 탈락.

5. **하이라이트 자체를 없애고 글 전체 대상 미션** ← 채택
   - 하이라이트의 원래 역할은 "미션의 대상(앵커)을 정하는 것"이었다. 앵커를 글 전체로 두면 하이라이트가 불필요해진다.
   - 미션 4종(질문/반박/연결/표현)은 원래 글 전체를 물어도 자연스럽다.
   - 흐름이 "읽기 → 미션"으로 단순해지고, 저작권·기술 제약이 모두 사라진다.

## 잃는 것

"인상 깊은 문장을 스스로 고르는" 작은 능동성. 다만 미션에 답하는 것 자체가 더 큰 능동적 사고이므로 손실은 작다고 판단.

## 영향

- 프론트 `Read.tsx`의 문장 하이라이트를 걷어낸다. "원문 읽기 안내 + 미션으로" 화면으로 축소.
- `Mission.tsx`에서 "칠한 문장" 인용을 제거. 나머지는 유지.
- 오늘 작업 대부분은 살아남는다.
