# QA 체크리스트 설계 검토

이 문서는 Sprint 1 핵심 QA 체크리스트를 구현 전에 검증하기 위한 논의 자료다. 아직 확정되지 않은 항목을 정리한 것이며, 결정 전에는 `docs/quality/` 문서를 수정하지 않는다.

## 검토 대상

- `docs/quality/README.md`
- `docs/quality/core-flow.md`
- `docs/quality/api-smoke.md`
- `docs/quality/rss-dry-run.md`
- `docs/quality/seed-data.md`

## 반드시 결정할 항목

### 1. 익명 테스트 사용자 정리 범위

**현재 문제**

`delete from auth.users where is_anonymous`는 테스트 사용자가 아닌 실제 익명 사용자까지 모두 삭제할 수 있다.

**Codex 권장안**

- 테스트 시작 시 생성한 사용자 UUID를 기록한다.
- `user_interests`와 `auth.users`는 기록한 UUID만 대상으로 삭제한다.
- 정리 후 시작 전 행 수로 돌아왔는지 확인한다.

**Claude 검증 질문**

- 테스트 사용자만 안전하게 특정할 수 있는 더 단순한 방법이 있는가?
- 원격 Supabase 프로젝트에서도 실수 없이 실행할 수 있는가?

### 2. 사용자 A/B 세션 분리 방법

**현재 문제**

같은 브라우저의 시크릿 창 두 개는 세션을 공유할 수 있어 서로 다른 익명 사용자 A/B를 보장하지 못한다.

**Codex 권장안**

- 일반 창과 시크릿 창, 서로 다른 브라우저 또는 서로 다른 브라우저 프로필을 사용한다.
- 테스트 전에 A와 B의 UUID가 실제로 다른지 확인한다.

**Claude 검증 질문**

- 수동 QA에서 가장 재현하기 쉬운 분리 방법은 무엇인가?
- 추후 Playwright로 자동화할 경우 별도 browser context로 충분한가?

### 3. 요청 본문의 `userId` 처리

**현재 문제**

`core-flow.md`는 다른 사용자의 `userId`가 있으면 요청을 거부하도록 하고, `api-smoke.md`는 해당 값을 무시하도록 한다.

**선택지**

1. 요청 스키마에 없는 `userId`를 `422`로 거부한다.
2. `userId`를 무시하고 access token에서 추출한 사용자 ID로 저장한다.

두 방식 모두 요청 본문의 `userId`로 저장해서는 안 된다.

**Codex 권장안**

요청 스키마에 없는 필드를 허용하지 않고 `422`로 거부한다. 잘못된 클라이언트 요청을 빠르게 발견할 수 있고 API 계약이 명확하다.

**Claude 검증 질문**

- MVP에서 `422` 거부가 불필요한 복잡도를 만들지는 않는가?
- Pydantic 요청 스키마에서 일관되게 적용할 수 있는가?

### 4. 관심사 노출 필터 담당

**현재 문제**

화면에서는 `launchStatus`가 `hidden` 또는 `preparing`인 관심사를 제외해야 하지만 현재 `GET /api/interests`는 21건 전체를 반환한다.

**선택지**

1. 백엔드가 선택 가능한 관심사만 반환한다.
2. 백엔드는 전체를 반환하고 프론트엔드가 필터링한다.

**Codex 권장안**

백엔드에서 `hidden`, `preparing`을 제외한다. 여러 클라이언트가 생겨도 노출 규칙을 반복 구현하지 않으며 프론트엔드는 받은 목록을 표시하는 데 집중할 수 있다.

**Claude 검증 질문**

- `preparing` 관심사를 비활성 상태로 보여줄 요구가 있는가?
- 현재 API의 21건 반환 완료 기준을 변경해도 되는가?

### 5. 사용자 관심사 재저장 방식

**현재 문제**

첫 저장만 정의되어 있고 사용자가 다시 선택했을 때 기존 행을 유지할지 교체할지 정해지지 않았다.

**선택지**

1. 요청받은 목록으로 기존 관심사를 전체 교체한다.
2. 기존 관심사에 새 항목을 추가한다.

**Codex 권장안**

온보딩 화면의 현재 선택 상태가 최종 상태가 되도록 전체 교체한다. 같은 요청을 반복해도 결과가 같아야 한다.

**Claude 검증 질문**

- 전체 교체 과정에서 일부 삭제 후 저장 실패가 발생하면 어떻게 처리할 것인가?
- Sprint 1에서는 트랜잭션 처리가 필요한가, 더 단순한 방법이 있는가?

### 6. RSS dry-run 반복 실행 기대 결과

**현재 문제**

dry-run은 DB에 저장하지 않으므로 같은 feed를 두 번 실행해도 두 번째 신규 저장 예정이 0건이 되지 않는다.

**Codex 권장안**

- DB 상태가 같을 때 같은 dry-run을 두 번 실행하면 결과 건수와 canonical URL 목록이 동일해야 한다.
- 실제 저장 후 같은 feed를 dry-run했을 때 기존 URL의 신규 저장 예정이 0건이어야 한다.

**Claude 검증 질문**

- 실제 저장 없이 중복 제거를 검증할 수 있는 별도 방법이 필요한가?
- dry-run 출력에서 URL 정규화 전후 값을 함께 보여줘야 하는가?

### 7. seed 데이터 최소 범위

**현재 문제**

모든 관심사에 글 3건을 만들면 21개 관심사 기준 최소 63건이 필요해 Sprint 1 기준으로 과하다.

**Codex 권장안**

- 테스트 관심사 3개 이상
- article 전체 6개 이상
- 각 테스트 관심사에 추천 가능한 글 2개 이상
- 모든 article은 관심사 태그를 1개 이상 가짐
- 유료 콘텐츠 전문과 원문 전체를 저장하지 않고 제목, URL, 공식 발췌문 등 최소 메타데이터만 사용

**Claude 검증 질문**

- 오늘의 글 1~3개 추천을 확인하기에 6건이 충분한가?
- `curated_only` 빈 상태까지 같은 seed에서 검증할 수 있는가?

### 8. API smoke test 판정 방식

**현재 문제**

현재 `curl` 명령은 응답 일부만 출력하므로 HTTP 상태 코드, 정확한 응답 개수와 전체 정렬을 판정하지 못한다. `/docs` 항목도 실제로는 `/openapi.json`만 확인한다.

**Codex 권장안**

- HTTP 상태 코드를 별도로 확인한다.
- 관심사 배열 길이, 필드명과 전체 정렬을 실제로 판정한다.
- `/docs`의 200 응답과 `/openapi.json`의 라우트 목록을 분리한다.
- `verify_supabase.py` 실행 명령은 백엔드 uv 환경을 사용하도록 경로를 확정한다.

**Claude 검증 질문**

- Sprint 1에서는 수동 `curl`로 충분한가, 짧은 자동 검증 스크립트가 필요한가?
- 실패 시 어떤 값이 달랐는지 바로 보이도록 만들 수 있는가?

## 추가 검토할 QA 항목

### 관심사 선택 화면

- 새로고침 후에도 동일한 익명 세션 UUID가 유지되는가?
- 저장 요청에 `Authorization: Bearer <access_token>`이 포함되는가?
- access token과 secret 키가 애플리케이션 로그에 출력되지 않는가?
- 목록 조회 중 로딩 상태가 표시되는가?
- 목록 조회 실패 시 에러 상태와 재시도 방법이 있는가?
- 저장 실패 시 완료 화면으로 이동하지 않는가?
- 저장 버튼 연속 클릭 시 중복 요청이 발생하지 않는가?
- 320px 또는 375px 화면에서 텍스트와 주요 버튼이 잘리지 않는가?
- DB 확인 쿼리는 최근 5행이 아니라 테스트 사용자 UUID로 범위를 제한하는가?

### RSS dry-run

- 빈 feed를 성공 0건과 수집 실패 중 어느 쪽으로 처리하는가?
- 원문 링크가 없는 item을 제외하고 사유를 출력하는가?
- 깨진 링크, 유료 콘텐츠, 접근성 unknown을 어떻게 분류하고 제외하는가?
- `reading_time_minutes`와 `quality_score` 계산 결과를 확인할 수 있는가?
- 제외된 item마다 제외 사유를 확인할 수 있는가?

### seed 정리

- `content_interest_tags`, `articles`, `source_interests`, `sources` 순서로 안전하게 정리할 수 있는가?
- seed 데이터와 실제 수집 데이터를 명확하게 구분할 수 있는가?
- seed 적용 전후 행 수와 정리 후 원복 여부를 확인하는가?
