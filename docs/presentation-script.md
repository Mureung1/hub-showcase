## 2. Articles 프로젝트 한눈에 (40초)

Articles는 한 줄로 말하면, **번역기 없이 영문 경제 뉴스를 완독하고, 스스로
투자 판단을 내린 뒤 AI의 해석과 비교하며 배우는 모의투자 학습 서비스**
입니다.

타겟은 아주 명확해요. 해외 주식도, 영문 뉴스도 둘 다 처음인 완전
초보자입니다. 이분들이 왜 어려움을 겪냐면, 번역기를 돌려도 낯선 금융
영어 문장 구조는 여전히 이해가 안 되고, 또 하루에도 쏟아지는 외신 중에
뭐가 진짜 주가에 영향을 주는 뉴스인지 선별할 기준이 없어서 쉽게 지치고
포기하게 됩니다.

참고로 증권사 API 연동해서 실제 매매하는 기능은 스코프 밖입니다. 어디까지나
**판단력을 훈련하는 도구**예요.

## 3. 핵심 기능 4가지 (45초)

핵심 기능은 네 가지입니다.

첫째, **원문 리더뷰**입니다. 문장이 어렵다고 팝업이 뜨는 게 아니라, 문장을
탭하면 바로 아래 아코디언으로 번역이 펼쳐져요. 읽는 흐름을 안 끊으려고
이렇게 설계했습니다.

둘째, AI가 문단을 3줄로 요약해주고 종목에 미치는 영향까지 해설해주는데,
이건 **판단을 내리기 전까지는 화면에 숨겨둡니다.** 사용자가 AI 답을 먼저
보고 따라가지 않게 하려는 의도예요.

셋째, Bullish·Neutral·Bearish 셋 중 하나로 직접 판단하면, 바텀시트에서
내 선택과 AI의 해석을 나란히 비교해줍니다.

넷째, 이 과정에서 나온 핵심 용어들이 자동으로 단어장에 쌓입니다.

## 4. 화면 스크린샷 (30초)

실제 화면 흐름 그대로 보여드리면, 대시보드에서 오늘의 기사를 고르고 →
리더뷰에서 읽으면서 문장 번역을 보고 → 판단을 내리면 바텀시트가 뜨고 →
그 과정에서 단어장이 자동으로 채워집니다.

이 흐름은 잠시 뒤에 라이브로도 직접 보여드릴게요.

## 5. 기술 스택 (35초)

기술 스택은 프론트가 React 19에 Vite, 백엔드는 Express 5, DB랑 인증은
Supabase, 그리고 LLM은 Claude API를 쓰는데 모델은 `claude-haiku-4-5`로
고정해뒀습니다. 요약·번역·용어 선별·심리 판별 전부 짧고 정형화된 반복
작업이라, 굳이 무거운 모델 안 쓰고 저지연·저비용 모델이 더 적합하다고
판단했어요.

기술적으로 신경 쓴 부분 하나만 짚으면, Claude를 **호출 한 번**으로 문장
번역, 용어 선별, 문단 요약, 인사이트, 시장심리까지 다섯 개 필드를 동시에
받아옵니다. 호출을 나누지 않아서 응답 지연이랑 비용을 같이 줄인 거죠.

## 7. 3주차에 진행한 작업 내용 (45초)

3주차에 뭘 했는지 조금 더 구체적으로 보여드릴게요. 크게 네 갈래였습니다.

가장 큰 건 **실제 Claude 연결**이었어요. 그동안 목업 응답으로 개발하다가

## 8. AI와 일하는 순서 (워크플로) (50초)

이제 본론입니다. **제가 AI와 어떻게 역할을 나눠서 일했는지**요.

간단히 말하면, **저는 문제를 정의하고 우선순위를 정하고, 블라인드 처리
같은 화면별 정책을 결정**했습니다. **AI는 그 요구사항을 실행 가능한
Task로 쪼개고, 실제 코드를 작성하고, 그 구현이 제가 정한 스펙과
실제로 일치하는지 검증**했어요.

작업 순서는 이렇습니다. 먼저 기획서를 확인하고, `feature-slice`라는
에이전트로 요구사항을 하루 단위 Task와 우선순위로 쪼갭니다. 그걸 GitHub
이슈로 등록하고, 구현한 다음, `feature-verify`라는 에이전트로 스펙 대비
검증을 받고, 마지막으로 백로그 문서에 진행 상황을 기록합니다.

## 9. 전담 Agent 2개 + Skill 2개 (55초)

이 워크플로를 돌리려고 만든 도구가 Agent 두 개, Skill 두 개입니다.

`feature-slice`는 요구사항을 받아서 우선순위가 매겨진 Task로 쪼개는
역할인데, **읽기 전용**이에요. 계획 단계에서 코드를 건드리면 검증 안 된
변경이 섞일 수 있어서 일부러 권한을 안 줬습니다.

`feature-verify`는 "구현했다"와 "검증됐다"를 구분하려고 만들었어요.
체크리스트 문서의 체크박스는 신뢰하지 않고, 실제 코드랑 돌아가고 있는
서버를 근거로 PASS·FAIL을 판정합니다.

`design` Skill은 색상이나 타이포그래피 같은 디자인 규칙을 한 곳에 모아둔
문서고, `testing` Skill은 테스트 작성 컨벤션을 정리한 겁니다.

재밌는 건, 이 네 개가 한 번에 만들어진 게 아니라 **프로젝트를 진행하면서
필요해진 순서대로 하나씩 늘어났다**는 점이에요. 디자인 일관성이 먼저
필요했고, 그다음 계획 자동화, 그다음 신뢰성 검증, 마지막으로 회귀 방지
순서였습니다.

## 11. 마무리 (30초 + Q&A)

정리하면, 이번 3주 동안 배운 건 한 가지로 요약됩니다. **사람은 의사결정과
우선순위를, AI는 분해와 구현과 검증을 맡으면 속도와 신뢰를 동시에 가져갈

여기까지입니다. 질문 받겠습니다.

### Q&A 예상 질문 메모

- **"Agent는 왜 읽기 전용으로 만들었나요?"**
  → 계획 단계에서 코드를 건드리면 검증되지 않은 변경이 섞일 위험이
  있어서, `feature-slice`는 의도적으로 Read/Grep/Glob만 갖게 했습니다.
- **"AI가 짠 코드를 얼마나 믿고 쓰나요?"**
  → 안 믿습니다. `feature-verify`로 스펙 대비 검증을 거치고, 7/22
  실 LLM 연결 직후 나온 파싱 버그·stale 제목 버그처럼 mock에서는 안
  보이던 문제가 실제 연결 후에 드러난 사례도 있었어요.
- **"왜 모델을 haiku로 고정했나요?"**
  → 요약·번역·용어선별·심리판별이 짧고 정형화된 반복 작업이라 저지연·
  저비용 모델이 더 적합하다고 판단했습니다.
- **"가장 힘들었던 순간은?"**
  → 실 LLM을 붙인 직후(7/22)였어요. mock으로 개발할 때는 안 보이던
  엣지케이스(파싱 fallback, stale 제목)가 한꺼번에 드러나서 바로
  대응해야 했습니다.
