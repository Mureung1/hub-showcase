## 2. 최근 창작 서브에이전트 규칙 변경 분석

### 질의

최근 커밋에서 바뀐 창작 관련 서브에이전트 규칙의 핵심은 무엇인가.

### 분석 결과

최근 커밋은 창작을 메인 Codex가 즉흥적으로 처리하지 않고 다음 역할로
분리하는 구조를 도입했다.

- `design_creative_planner`: 비시나리오 기획 GAP 분류와 허가된 대안 생성
- `design_creative_reviewer`: 비시나리오 창작 결과의 독립 검수
- `scenario_designer`: 일반 시나리오 Draft와 분리 개선안 작성
- `scenario_writer`: 플레이어 노출 인게임 스크립트 집필
- `scenario_reviewer`: 일반 시나리오와 대본의 독립 검수
- 메인 Codex: 프로젝트·근거·권한 확정, Task Packet 작성, 결과 대조,
  Approval Queue와 적용 책임

공용 agent type은 안정적인 역할과 출력 계약을 소유한다. 프로젝트별 창작
방향은 공용 agent 설정에 누적하지 않고 프로젝트 내부 PCA로 분리하는 것이
핵심이었다.

## 3. 공용 에이전트 하나로 여러 프로젝트를 담당할 수 있는가

### 질의

같은 `scenario_designer`라도 프로젝트마다 장르, 시나리오 구조와 필요한
문서가 다른데 하나의 공용 에이전트가 창작을 총괄하면 문제가 생기지 않는가.

### 결론

역할이 같고 프로젝트 적응 정보만 다르다면 공용 에이전트와 프로젝트별 PCA
조합이 적합하다.

- 공용 에이전트는 일반 시나리오의 책임, 입력 검사, Draft와 개선안 분리,
  반환 형식과 승인 경계를 소유한다.
- PCA는 해당 프로젝트의 창작 목표, 플레이 경험, 대상 경로, 필수 근거,
  우선순위, 금지사항, `TBD`, provenance와 reviewer를 소유한다.
- canonical 문서는 게임에서 사실로 확정된 세계관, 시나리오, 시스템과
  콘텐츠를 소유한다.
- Task Packet은 이번 한 번의 요청 범위, 사용자 사실·선택·금지사항과 권한을
  전달한다.

프로젝트의 분위기나 장르가 다르다는 이유만으로 공용 에이전트를 복제하면
공통 안전 규칙과 검수 계약이 서로 달라질 위험이 더 크다.

## 4. 프로젝트별 개별 에이전트가 더 유리한 경우

### 질의

공용 에이전트와 프로젝트별 규칙보다 프로젝트마다 개별 에이전트를 만드는
편이 나은 경우는 언제인가. 수행 절차를 PCA에 넣으면 해결되지 않는가.

### 결론

다음과 같은 프로젝트 차이는 PCA로 처리할 수 있다.

- 프로젝트별 문체와 분위기
- 참조할 세계관·콘티·시나리오 문서 위치
- 사건 구성 순서와 작업 체크리스트
- 프로젝트별 금지 요소와 품질 기준
- 출력 형식의 세부 차이

새 공용 agent type을 검토할 조건은 프로젝트 차이가 아니라 역할 자체의
차이다.

- 입력과 산출물의 종류가 기존 역할과 근본적으로 다르다.
- 별도 provenance 체계가 필요하다.
- 독립 검수 계약과 품질 판정이 기존 역할과 충돌한다.
- 기존 역할에 합치면 권한이나 책임 경계가 모순된다.

`scenario_designer`와 `scenario_writer`의 분리가 실제 예다. 전자는 상위 사건
구조·Scene·분기를 설계하고 개선안을 Draft와 분리한다. 후자는 플레이어 노출
대사·지문·선택지와 Scene 구현 명세를 작성하고 `CW-*`·`NR-*`를 사용한다.

## 5. PCA가 canonical fact를 소유하지 않는다는 의미

### 질의

시나리오를 만들려면 세계관과 콘티 같은 자료를 참고해야 하는데, PCA가 확정
사실을 소유하지 않는다면 해당 자료는 어떻게 전달하는가.

### 결론

PCA에는 사실 자체를 복제하지 않고 정확한 canonical 문서 경로와 출처
우선순위, 읽을 조건을 기록한다.

예:

```text
PCA
  - 필수 근거 파일: project_brief.md, world_setting.md, main_scenario.md
  - 출처 우선순위: 현재 사용자 지시 → 대상 시나리오 → 세계관 → 시스템
  - 규칙이 소유하지 않는 사실: 세계관 정사, 기존 사건, 시스템 판정
```

실제 세계관 사실은 `design/world/`, 시나리오 사실은 `design/narrative/`,
시스템 규칙은 `design/systems/`가 계속 소유한다. PCA는 전문 에이전트가
어디를 어떤 우선순위로 읽고, 충돌이나 누락에서 어떻게 행동할지를 정한다.

`scenario_writer`의 별도 PCA가 필요한 제외 범위로 유지했다.

## 7. Task Packet의 ID·버전·SHA-256 고정 의미

### 질의

“규칙 ID·버전·SHA-256을 Task Packet에 고정한다”는 것은 무엇인가.

### 설명

전문 에이전트가 어떤 PCA의 정확히 어느 파일 내용을 기준으로 작업했는지
재현하기 위한 규칙 참조다.

- ID: 어떤 프로젝트·분야의 규칙인가
- 경로: active 파일인지 archive snapshot인지
- 버전: 규칙의 논리적 개정 번호
- SHA-256: 전달한 파일 바이트가 실제 파일과 같은지 확인하는 지문
- 규칙 기준: `active_current | archived_snapshot`

이 값은 세계관이나 시나리오를 확정하는 승인이 아니다. 호출 기준을 식별하고
나중에 결과의 출처와 검수 조건을 확인하기 위한 실행 계약이다.

## 8. PCA 부재 시 자동 설정 설계

### 요청

기존 공용 에이전트 방식을 유지하되, 사용자가 창작을 요청했는데 해당 분야
PCA가 없으면 planning-only 절차를 자동으로 수행해 빈틈없는 PCA 계획을
자연스럽게 만들도록 한다.

### 구현 원칙

1. PCA가 없으면 창작 실행만 `blocked_missing_creative_rule`로 중단한다.
2. 같은 대화에서 Automatic Setup Design을 즉시 시작한다.
3. 메인 Codex가 프로젝트, 문서 역할과 최소 canonical owner를 먼저 확인한다.
4. 현재 요청과 확정 문서에서 알 수 있는 항목을 미리 채운다.
5. 결과를 실질적으로 바꾸는 선택만 권장 기본값과 함께 질문한다.
6. 사용자가 답하지 않은 값은 공개한 보수적 기본값 또는 `TBD` 원칙으로
   완성한다.
7. 모든 필드가 채워진 설정 계획과 에이전트가 보충한 값·근거를 보여준다.
8. 계획 단계에서는 파일을 저장하지 않는다.
9. 사용자가 `그대로 구현해`처럼 명시적으로 요청하면 PCA와 색인을 저장한다.
10. PCA 구현은 확정 기획 문서 변경이나 창작안 승인을 허가하지 않는다.

실제 UI Plan mode 전환 자체를 필수 조건으로 두지 않고, 현재 대화에서
planning-only 행동을 강제하는 방식으로 구현했다.

### 추가한 template

- `docs/templates/project_creative_agent_setup_plan.md`

template에는 routing, 항목별 용도·결정·근거, 완성 규칙 명세, 에이전트가
보충한 기본값, 저장 경로와 원래 작업 재개 조건을 포함했다.

## 9. 재검토에서 발견한 문제

### 9.1 Task Packet이 신규 reviewer를 허용하지 않음

`AGENTS.md`는 `design_creative_reviewer` 호출에도 Task Packet을 요구했지만
Task Packet template의 대상 agent 목록에는 reviewer가 없었다.

해결:

- `docs/templates/specialist_task_packet.md` 대상 목록에
  `design_creative_reviewer`를 추가했다.
- 검증기의 `SPECIALIST_AGENT_TYPES`에 다섯 agent type을 한곳에 정의했다.
- Task Packet과 handoff workflow가 모든 agent 이름을 포함하는지 회귀
  테스트로 고정했다.

### 9.2 기존 프로젝트의 창작 기능이 일괄 차단될 가능성

JIT 게이트를 도입하면 PCA가 없는 기존 프로젝트는 첫 창작 요청에서 바로
Draft를 만들 수 없다. 이는 의도한 안전 장치지만, 모든 분야 규칙을 한꺼번에
만드는 migration도 바람직하지 않았다.

해결:

- 기존 프로젝트에도 요청하지 않은 PCA를 일괄 생성하지 않는 JIT 정책을
  유지했다.
- PCA가 없는 분야는 첫 실제 창작 요청에서 설정 계획을 만들고 사용자 구현
  요청 뒤 원래 작업을 재개한다.
- 검색·요약·검토, GAP `classify`, 비창작 구조화, 임시 아이디어와 기계적
  적용은 PCA 없이 계속 가능하다고 명시했다.
- 십이인연록에는 현재 필요한 메인 시나리오 PCA만 두고 인게임 스크립트 등
  다른 분야 PCA는 미리 만들지 않았다.

### 9.3 색인의 메타데이터 동기화가 검증되지 않음

기존 검증은 색인 링크 존재 여부만 확인해 분야, role, agent, 검수 정책과
버전이 실제 PCA와 달라도 통과할 수 있었다.

해결:

- 색인에 다음 routing·실행 메타데이터를 모두 기록하도록 schema를 확장했다.
  - PCA ID
  - 분야
  - canonical role
  - 경로 선택자
  - 대상 경로
  - 허용 작업
  - 기본 agent type
  - 검수 정책
  - 버전
  - 상태
- 검증기가 각 색인 값을 실제 PCA와 전부 대조하도록 구현했다.

### 9.4 적용 범위가 겹치는 active 규칙을 선택할 수 없음

Minimal Source Rule 때문에 모든 PCA 파일을 열어 비교할 수 없으므로,
색인만으로 active 규칙 하나를 결정할 수 있어야 했다.

해결:

- routing key를 `canonical role + exact/subtree 대상 경로 + 허용 작업`으로
  정의했다.
- 같은 role에서 경로가 포함·중복되고 허용 작업도 겹치는 active PCA를
  검증 오류로 처리했다.
- `exact/exact`, `exact/subtree`, `subtree/subtree` 조합을 모두 테스트했다.
- 같은 경로라도 작업이 다르거나 canonical role이 다르면 공존할 수 있게
  했다.
- archive snapshot과 retired 규칙은 새 active routing 후보에서 제외했다.

### 9.5 SHA-256 고정의 운용 비용

PCA의 공백이나 표현만 바뀌어도 SHA-256이 달라진다. active 규칙 변경만으로
과거 결과 전체를 재검수하면 안전성보다 운용 중단 비용이 지나치게 커진다.

해결:

- PCA 개정 전 현재 파일의 정확한 바이트를
  `agents/rules/archive/<rule_slug>/v<version>.md`에 보존한다.
- archive snapshot의 SHA-256을 프로젝트 PCA 색인에 기록한다.
- 과거 결과는 당시 PCA ID·버전·SHA-256과 검수 상태를 유지한다.
- active PCA가 바뀌어도 과거 결과를 자동 무효화·수정·재검수하지 않는다.
- 과거 결과는 기존 상태로 선택·승인·기계적 적용을 계속할 수 있다.
- 새 생성·수정·재구성·선택 반영은 현재 active PCA를 사용한다.
- 현재 규칙 재검수는 사용자가 명시적으로 요청했을 때만 read-only로
  수행한다.
- Task Packet이 정확히 지목한 active 파일이나 archive snapshot의
  경로·버전·SHA-256이 실제 파일과 다를 때만
  `blocked_creative_rule_integrity`로 중단한다.

## 오늘 확정한 운영 원칙

1. 공용 agent type은 역할을, PCA는 프로젝트별 창작 행동을 소유한다.
2. PCA는 canonical fact를 소유하지 않고 정확한 근거 문서 경로를 참조한다.
3. PCA는 요청된 분야에만 JIT로 만든다.
4. PCA가 없으면 창작 결과를 만들기 전에 완성된 설정 계획을 제시한다.
5. 설정 계획은 사용자 구현 요청 전에는 저장하지 않는다.
6. 같은 프로젝트라도 일반 시나리오와 인게임 스크립트 PCA는 분리한다.
7. 색인은 role·경로·작업으로 active PCA 하나를 결정할 수 있어야 한다.
8. active PCA 개정 전 이전 버전을 불변 snapshot으로 보존한다.
9. active PCA 변경만으로 과거 결과를 무효화·재검수하지 않는다.
10. 새 창작과 수정은 현재 active PCA를 사용한다.
11. 현재 규칙 재검수는 사용자가 명시적으로 요청할 때만 read-only로 한다.
12. PCA 구현은 확정 기획 문서 변경이나 창작안 승인을 뜻하지 않는다.

## 현재 상태

- 모든 변경은 아직 미커밋 상태다.
- 십이인연록에는 메인 시나리오 PCA만 존재한다.
- 인게임 스크립트나 다른 기획 분야 PCA는 실제 요청 전까지 생성하지 않는다.
- PCA 구현 과정에서 `design/`의 확정 기획 문서는 변경하지 않았다.
