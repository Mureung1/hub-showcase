# 2026-07-21 개발 일지

## 주제

시나리오 작성 전용 서브 에이전트 `scenario_writer` 추가와 인게임 스크립트
승인 workflow 구축

## 오늘의 목표

확정된 시나리오를 실제 플레이 화면에 사용할 지문·대사·선택지와 구현용 씬
명세로 구체화하는 반복 작업을 전용 서브 에이전트에 맡길 수 있도록 한다.

핵심 방향:

- 시나리오 원본과 관련 확정 문서를 근거로 챕터 단위 인게임 스크립트를 작성한다.
- 플레이어 노출 대본과 씬·분기·Outcome·상태·제작 정보를 한 문서에서 관리한다.
- 원본에 직접 없는 창작 내용은 모두 각주로 공개하고 확정 사실처럼 다루지 않는다.
- 저장 요청이 있어도 명시적 승인 전에는 확정 문서를 수정하지 않고 Approval
  Queue의 `pending` 초안으로 남긴다.
- 승인 적용 시 신규 스크립트와 상위 문서 링크를 하나의 `restructure` 항목으로
  재확인하고 원자적으로 반영한다.

## 작업 배경

기존 메인 시나리오는 사건 순서와 선택 결과를 소유했지만, 플레이어가 실제로
읽는 문장과 Unity가 연결할 씬·선택·Outcome ID, 상태 표현, 제작·QA 메모까지
구체화하는 전용 역할과 절차는 없었다.

범용 문서 작성 흐름만으로 이 작업을 처리하면 다음 경계가 불명확했다.

- 어디까지 원본에 근거한 내용이고 어디부터 창작 보완인지 구분하는 방법
- 플레이어가 선택하기 전에 행동이나 결과를 대본이 대신 확정하지 않도록 하는 기준
- 시나리오, 시스템, UI와 기술 문서 사이의 필드 및 입력 모드 검증 기준
- 챕터 대본의 canonical 경로와 상위 문서 링크 갱신 범위
- 승인 전 초안 저장 위치와 승인 후 적용 절차

따라서 시나리오 저작을 범용 기획 문서 작성의 예외 처리로 두지 않고,
`scenario_writer`와 전용 workflow·skill·template의 조합으로 분리했다.

    하기 위한 Asset Promotion 규칙도 보강했다.

## 주요 결정

### 전용 서브 에이전트의 책임 범위

결정:

- `scenario_writer`는 확정 시나리오를 챕터별 인게임 스크립트 승인 초안으로
  변환하는 범위가 명확한 저작 작업만 담당한다.
- 대상 프로젝트는 한 개로 확정하고, 관련 세계관·시스템·콘텐츠·UI·기술
  확정 문서를 필요한 범위에서 조회한다.
- 다른 서브 에이전트를 추가로 생성하지 않는다.
- 결과 전달 시 프로젝트, 근거 파일, 승인 항목, 작성 범위, 창작 각주 수,
  미해결 `TBD`와 충돌 여부를 요약한다.

이유:

- 시나리오 대본 작성에는 일반 문서 정리와 다른 창작 공개 및 플레이어 주도권
  검토가 필요하다.
- 에이전트 책임을 좁혀야 확정 설정과 창작 제안이 섞이는 위험을 줄일 수 있다.

### 플레이어 노출 대본과 구현 명세의 결합

결정:

- 하나의 인게임 스크립트 문서에 지문·대사·선택지와 씬 ID, 진입·종료 조건,
  입력 모드, 분기, Outcome, 상태 변화, 공개 정보, RAG·메모리 참조, 제작 및
  QA 메모를 함께 둔다.
- 한 씬은 하나의 입력 대기 지점 또는 하나의 확정 결과 전달 단위로 나눈다.
- `choice_only`와 `choice_and_text`에는 선택지가 있어야 하고,
  `narrative_only`에는 `continue_outcome_id`가 필요하다.

이유:

- 대본과 구현 정보가 분리되면 문장, 선택지와 실제 분기 연결이 서로 어긋날 수 있다.
- 기획 검토와 구현 전달이 같은 씬 단위를 기준으로 이루어져야 추적이 쉽다.

### 플레이어 주도권 보존

결정:

- 플레이어가 아직 선택하지 않은 행동이나 대사를 대본이 대신 확정하지 않는다.
- 확정 시나리오가 지정한 고정 독백만 예외로 사용한다.
- 선택지 표시 뒤에는 입력을 기다리며 자동 선택이나 자동 결과 확정을 추가하지 않는다.
- 분기 결과와 상태 변경은 확정 Outcome 또는 창작이라고 명시한 제안에만 연결한다.

### 창작 내용의 전수 공개

결정:

- 원본 사건을 새 문장으로 풀어 쓴 지문과 대사도 창작으로 본다.
- 원본에 없는 line·scene·choice·outcome ID, 상태 플래그, 연결, 연출과 제작
  지시도 모두 창작으로 본다.
- 각 창작 항목에 `CW-<chapter>-<number>` 형식의 Markdown 각주를 직접 연결한다.
- 각주는 대상 ID나 필드, 원본에 없던 부분, 작성 이유와 설정·시스템·후속 장면
  영향을 설명한다.
- 안전하게 제안할 수 없는 구현값과 에셋 ID는 `TBD`로 둔다.

이유:

- 자연스럽게 보이는 대사나 내부 ID도 원본에 없으면 새 정사나 구현 계약으로
  오인될 수 있다.
- 창작 범위를 문서 안에서 바로 추적할 수 있어야 사용자가 승인 영향을 판단할
  수 있다.

### 인게임 스크립트의 문서 역할과 경로

결정:

- 인게임 스크립트는 `scenario` 역할의 상세 문서로 분류한다.
- 표준 경로는
  `design/narrative/scripts/<chapter_slug>_ingame_script.md`로 정한다.
- 상위 시나리오는 사건과 분기 구조를 소유하고, 인게임 스크립트는 승인된 범위의
  플레이어 표현과 씬 연결을 구체화한다.
- 새 스크립트를 승인 적용할 때 `design/README.md`, 게임 개요와 상위 시나리오의
  링크 갱신을 같은 `restructure` 승인 범위에 포함한다.

### 승인 경계

결정:

- 서브 에이전트가 저장할 수 있는 결과는 대상 프로젝트 Approval Queue의
  `pending` 항목까지다.
- 승인 전에는 `design/narrative/scripts/`, Decision Log와 Version History를
  수정하지 않는다.
- 기준 Git 커밋, 대상별 비교 범위, SHA-256, 원본 요약과 승인 후 링크 갱신을
  승인 항목에 기록한다.
- 사용자 명시 승인 후에도 적용 직전에 모든 대상을 다시 확인하며 하나라도
  달라졌으면 일부만 반영하지 않고 `needs_reconfirmation`으로 이동한다.

## 함께 보강한 승인 에셋 규칙

동일 변경 범위에는 승인용 이미지의 위치와 적용 완료 조건을 명확히 하는 규칙도
포함되었다.

- `approvals/assets/`는 승인 전 검토용 임시 저장소로 사용한다.
- `design/assets/`는 승인 적용이 끝난 canonical 저장소로 사용한다.
- 적용 전에 검토본 SHA-256과 승인 후 경로의 파일 상태를 확인한다.
- canonical 경로 반영과 승인·결정·버전 문서의 참조 갱신을 확인한 뒤 해당
  검토본만 삭제한다.
- 검토본 삭제까지 끝난 뒤에만 승인 항목을 `applied`로 처리한다.
- 해시 불일치, 경로 충돌 또는 참조 미갱신이 있으면 검토본을 유지하고
  `needs_reconfirmation`으로 이동한다.

이 규칙은 `scenario_writer`의 핵심 저작 기능과는 별도이지만, 승인 산출물의
임시 위치와 canonical 위치를 명확히 하는 운영 안전장치로 함께 반영했다.

- 승인 항목에 기준 커밋, 대상별 SHA-256, 원본 요약, 재확인 결과와 연결된
  결정·버전 ID가 남아 있는지 확인했다.

## 남은 작업 후보

1. 프롤로그 Phase 2~4와 혼돈 전투를 별도 승인 항목으로 작성한다.
2. Unity의 실제 `scene_type` 열거형을 확정한다.
3. 주인공·흑의인·장소·RAG 참조 ID가 실제 레지스트리에 등록되었는지 확인한다.
4. 신당 내부 제단의 실제 `illustration_id`와 BGM·효과음·VFX 리소스 ID를 정한다.
5. 한 화면 글자 수와 line 자동·수동 진행 규칙을 UI·기술 문서에 확정한다.
6. 다른 챕터에서도 창작 각주 누락, 플레이어 주도권과 씬 데이터 조합을 같은
   기준으로 검증한다.

## 작업 중 주의 사항

- `scenario_writer`는 창작물을 확정 사실처럼 작성할 권한이 없다.
- 사용자가 창작 보완을 허용하지 않으면 원본만으로 작성하고 부족한 부분은
  `TBD` 또는 질문으로 남긴다.
- 승인 큐에 초안이 생성되었다는 사실만으로 확정 문서에 반영하지 않는다.
- 승인 적용 전 원본이나 영향 범위가 달라졌으면 기존 승인을 재사용하지 않는다.
- 이 개발 일지는 과거 작업 기록이며 현재 행동 규칙의 근거로 사용하지 않는다.
  현재 규칙은 `AGENTS.md`, `README.md`, `docs/plan.md`, `docs/architecture.md`,
  `docs/workflows/`와 `docs/skills/`를 우선한다.
