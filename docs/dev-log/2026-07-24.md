# 2026-07-24 개발 일지

## 주제

GamePM 문서 작업장의 자동 테스트 도입과 에이전트 동작 테스트에서 발견된
운영 문제 수정

## 오늘의 목표

화면이나 대화 결과를 눈으로만 확인하는 방식에서 벗어나, 저장소의 핵심 문서
구조와 승인 기록을 명령 한 번으로 다시 검사할 수 있게 한다. 자동 판정이
어려운 전문 에이전트 호출과 승인 응답은 실제 동작 테스트로 확인하고, 테스트
과정에서 발견된 문제를 운영 규칙과 회귀 테스트로 고정한다.

핵심 구분:

- 테스트 코드: 입력과 기대 결과가 고정된 결정적 검사
- 동작 테스트: 실제 Codex 및 전문 에이전트의 호출·응답·탐색 행동 확인
- 실제 프로젝트 적용: 오늘 테스트에는 포함하지 않음

## 진행 요약

1. 현재 저장소에서 단위 테스트 대상으로 삼을 수 있는 결정적 규칙을

3. 1차로 작업장 구조, 링크, 승인 ID와 적용 기록을 검사하는 테스트 24개를
   실행해 모두 통과시켰다.
4. 실제 승인 응답과 전문 에이전트 호출을 동작 테스트했다.
5. 동작 테스트에서 모호한 승인 안내, 전문 에이전트 호출 인자, Python 실행
   명령과 테스트용 합성 문장 출처 문제를 확인했다.
6. 각 문제를 AGENTS, workflow, template와 custom agent 설정에 반영했다.
7. 합성 테스트 데이터의 출처와 격리를 검사하는 테스트 13개를 추가했다.
8. 최종적으로 전체 테스트 37개, Python 컴파일, 네 custom agent TOML 파싱과
   `git diff --check`를 통과시켰다.

## 1. 테스트 코드

### 구현 방식

외부 패키지를 설치하지 않고 Python 표준 라이브러리만 사용했다.

- 검증 코드: `scripts/workspace_validation.py`
- 테스트 코드: `tests/test_workspace_validation.py`
- 합성 동작 테스트 자료: `tests/fixtures/behavior/`
- 실행 명령:

```bash
python3 -m unittest discover -s tests -v
```

각 테스트는 가능한 경우 `TemporaryDirectory` 안에 최소 작업장을 만들고,
정상 입력과 의도적으로 깨뜨린 입력을 각각 검사한다. 실제 작업장 검사는
등록된 프로젝트 문서를 읽기만 하며 수정하지 않는다.

### 1.1 프로젝트 레지스트리와 필수 구조

검사한 내용:

- 정상 레지스트리에서 프로젝트 ID와 루트를 읽는가
- `Projects` 표가 비어 있으면 실패하는가
- 프로젝트 ID가 중복되면 실패하는가
- 프로젝트 루트가 `workspace/projects/` 밖이면 실패하는가
- README, Project Brief, Design Index, Approval Queue, Decision Log,
  Version History 같은 필수 파일이 빠지면 실패하는가

테스트 방법:

- 임시 디렉터리에 최소 프로젝트 구조를 생성했다.
- 정상 구조의 오류 목록이 비어 있는지 확인했다.
- 표의 행을 중복시키거나 필수 파일을 삭제한 뒤 기대한 오류 코드가 나오는지
  확인했다.

결과:

- 정상 구조는 통과했다.
- 빈 레지스트리, 중복 ID, 범위 밖 루트와 필수 파일 누락은 각각 정확한
  오류 코드로 실패했다.

결과:

- 정상 링크와 외부 URL은 통과했다.

## 2. 실제 동작 테스트

### 2.1 모호한 승인 표현

테스트 목적:

- 승인 항목을 보고 사용자가 단순 호감 표현만 했을 때 적용하지 않는지
  확인한다.

테스트 방법:

- 명시적인 `승인`, `적용` 행동이 없는 `괜찮네`, `좋아 보이네` 유형의
  표현을 승인 상황에 넣어 응답과 파일 변경 여부를 확인했다.

확인 결과:

- 실제 적용은 일어나지 않았다.
- 그러나 초기 응답은 “애매한 표현이라 적용하지 않았다”는 사실을
  사용자에게 충분히 명확하게 설명하지 않았다.

해결:

- 모호한 표현은 승인으로 간주하지 않는다.
- 아무 변경도 적용하지 않았고 현재 승인 상태를 유지한다고 반드시 알린다.
- 적용하려면 대상 승인 ID와 `승인하고 적용해줘` 같은 행동을 명시하도록
  안내한다.
- 이 규칙을 AGENTS, Approval Queue workflow와 자동 회귀 테스트에 넣었다.

### 2.2 전문 에이전트 호출

테스트 목적:

- 실제 `design_creative_planner`가 지정 Phase와 범위만 수행하는지 확인한다.
- 부모 대화 전체를 넘기지 않아도 필요한 사용자 정보가 누락되지 않는지
  확인한다.

테스트 방법:

- named custom agent type을 지정해 `classify` 유형 작업을 호출했다.
- 첫 호출 실패 뒤 호환되는 인자로 교정해 다시 호출하고, 결과와 파일 변경
  여부를 확인했다.

발견한 문제:

- 첫 호출은 custom `agent_type`과 부모 대화 전체 상속 방식이 충돌해
  실패했다.
- 호환 호출에서는 `fork_turns: "none"`을 사용했지만, 별도의 표준 인계
  계약이 없으면 부모 대화에 있던 사용자 사실·선택·금지사항이 누락될 수
  있었다.
- 필요한 경로가 이미 정해져 있어도 전문 에이전트가 넓게 탐색할 여지가
  있었다.

해결:

- 호출 방식을 정확한 `agent_type`, `fork_turns: "none"`과 완성된
  Specialist Task Packet으로 고정했다.
- 현재 요청뿐 아니라 작업에 영향을 주는 이전 사용자 사실, 선택, 취소된
  지시, 금지사항과 승인·창작 권한을 Packet에 반드시 적도록 했다.
- 누락·충돌 시 `blocked_missing_handoff`로 중단하도록 네 custom agent를
  수정했다.
- Task Packet과 전문 작업 모두 필요한 canonical 경로만 읽는 Minimal Source
  Rule을 추가했다.
- 같은 비호환 인자를 반복하거나 일반 agent로 조용히 대체하지 않고,
  오류가 지시한 인자만 한 번 교정하도록 했다.

재검증:

- 전문 에이전트 인계 workflow, Task Packet과 네 agent 설정을 자동 테스트와
  TOML 파싱으로 확인했다.
- 이전 실제 호출에서는 교정 후 지정 전문 에이전트가 실행됐고 프로젝트 파일
  변경은 없었다.

### 2.3 Python 실행 명령

테스트 목적:

- 저장소 테스트 명령이 현재 실행 환경에서 실제로 동작하는지 확인한다.

테스트 방법과 결과:

- 설치되지 않은 `python` 명령을 두 번 호출해 명령을 찾지 못했다.
- 이후 `python3`로 다시 실행하자 테스트가 정상 통과했다.

문제 성격:

- 프로젝트 로직 오류가 아니라 실행 환경의 명령 이름 차이다.
- 같은 실패 명령을 반복해 불필요한 호출과 오류 로그가 생긴 점은 테스트
  진행 방식의 문제였다.

해결:

- 이 저장소의 테스트 및 검증 명령은 `python3`를 기준으로 기록하고
  실행한다.
- README의 검증 명령과 오늘의 모든 최종 검증을 `python3`로 실행했다.
- 명령 부재가 확인된 뒤 같은 `python` 호출을 반복하지 않는 것으로
  운영 기준을 정리했다.

### 2.4 테스트용 합성 문장과 실제 프로젝트 사실의 혼동

테스트 목적:

- 전문 에이전트가 설정 문장을 입력으로 받았을 때 출처와 권한 경계를
  지키는지 확인한다.

테스트에 사용한 문장:

> 남부 권역에는 해가 진 뒤에만 나타나는 달빛 시장이 있다.

확인 결과:

- 이 문장은 동작 테스트를 위해 그 자리에서 만든 합성 문장이었다.
- 실제 사용자가 제공한 설정도 아니고 확정 문서의 내용도 아니었다.
- Approval Queue, `design/` 또는 현재 운영 규칙의 프로젝트 근거로
  저장·적용되지 않았다. 이 개발일지에는 문제를 설명하는 역사적 예시로만
  인용한다.
- 이후 설명에서 이 문장의 출처를 명확히 밝히지 않아 사용자가 실제 프로젝트
  설정 또는 사용자 제공 문장으로 오해할 수 있었다.

해결:

- 모든 합성 입력은 처음 등장할 때부터
  `[TEST FIXTURE: SYNTHETIC]`으로 표시한다.
- 출처 유형을 `synthetic_test_fixture`, 분류를
  `test_fixture_assumption`으로 고정한다.
- 합성 데이터를 `user_fact`, 확정 사실, 정사 또는 실제 제안이라고 부르면
  `blocked_test_provenance`로 중단한다.
- 기본 동작 테스트는 실제 프로젝트가 아닌
  `tests/fixtures/behavior/sample-game/`을 `/tmp`에 복사해 실행한다.
- 실제 프로젝트 구조가 꼭 필요한 경우에만 `/tmp` 임시 복사본을 사용하고
  원본을 테스트 전후 비교한다.
- 결과 보고에 다음 네 필드를 의무화했다.

```text
데이터 출처
실행 환경
원본 변경
실제 프로젝트 사실로 채택
```

- 사용자에게는 합성 출력이 “사용자가 제공한 설정”이 아니라 “테스트 픽스처
  가정에 대한 출력”이라고 설명하도록 했다.

재검증:

- 출처 정상·오분류·누락·라벨 누락과 실제 프로젝트 채택 금지를 자동 테스트로
  확인했다.
- 모든 테스트가 통과했고 `workspace/projects/` 변경이 없음을 확인했다.
- 최종 출처 차단 규칙 적용 뒤 실제 전문 에이전트 라이브 호출은 불필요한
  호출을 반복하지 않기 위해 다시 실행하지 않았다. 현재 검증 범위는 결정적
  자동 테스트와 설정 파싱까지다.
