# 2026-07-10 개발 일지

## 주제

문서 요청 처리 workflow 재정의와 `document_change` 상위 라우터 추가

## 오늘의 목표

게임 기획 콘텐츠를 바로 작성하기 전에, 만들어둔 기능들을 운영하기 위한
규칙과 스킬의 우선순위를 점검하고 문서 요청 처리 구조를 정리한다.

핵심 방향:

- 신규 문서 작성과 기존 문서 수정을 성급하게 나누지 않는다.
- 문서 관련 요청은 먼저 검색한 뒤 생성, 수정, 자료 취합, 기획서화, 질문으로 분기한다.
- `approval_queue`는 모든 기능 자체가 아니라 변경 결과물을 검토하고 승인하는 후속 허브로 둔다.
- 승인 전에는 `workspace/design/` 확정 문서를 수정하지 않는다.

## 진행 요약

1. 현재 저장소의 `README.md`, `docs/plan.md`, `docs/checklist.md`를 확인했다.
2. `workspace/project_brief.md`, `workspace/design/`, 승인 큐, 결정 로그, 버전 기록 상태를 확인했다.
3. 처음에는 프로젝트 브리프 작성이 우선이라고 판단했지만, 사용자가 게임 기획 콘텐츠보다 규칙과 스킬 정비가 우선이라고 정정했다.
4. 현재 기능별 workflow와 skill의 완성도를 점검했다.
5. `approval_queue`가 전체 기능이 아니라 문서 변경 흐름의 후속 승인 허브임을 정리했다.
6. 신규 문서 작성이 항상 기획서 작성은 아니라는 문제를 확인했다.
7. 신규 생성과 기존 문서 수정 여부를 알기 전에는 `create_document` 같은 상위 workflow가 부족하다고 판단했다.
8. 문서 관련 요청의 최상위 workflow를 `document_change`로 재정의했다.
9. `document_change`를 새로 추가하고, 기존 `write_design_doc`와 `propose_change`를 하위 workflow로 정리했다.
10. README와 architecture 문서의 설명과 예시를 새 구조에 맞게 수정했다.

## 주요 결정

### 첫 작업 우선순위

처음에는 비어 있는 `workspace/project_brief.md`를 보고 게임 프로젝트 브리프를 먼저 작성하는 계획을 제안했다.

사용자 정정:

- 당장 게임 기획을 시작하려는 것이 아니다.
- 먼저 만들어둔 기능들을 위한 규칙과 스킬을 정비해야 한다.

결정:

- 현재 단계의 우선순위는 게임 콘텐츠 작성이 아니라 Codex 운영 규칙과 workflow 정비다.

### 기능 범위 이해

사용자는 현재 만들어진 규칙과 스킬이 전부 `approval_queue` 기능에 대한 것인지 질문했다.

정리:

- `approval_queue`는 전체 기능이 아니라 승인 대기, 승인, 적용 상태를 관리하는 후속 허브다.
- `intake`, `project_search`, `write_design_doc`, `propose_change`, `decision_log`, `version_history`는 각각 별도 역할을 가진다.
- 다만 문서 생성과 변경 흐름의 결과물이 승인 큐를 거치므로 `approval_queue`가 중심축처럼 보인다.

결정:

- 기능 설명에서 `approval_queue`를 전체 기능으로 취급하지 않는다.
- 승인 큐는 산출물 검토와 적용 전 안전장치로 표현한다.

### 신규 문서 작성 기능의 한계

사용자는 신규 문서를 만드는 것이 항상 기획서는 아니라고 지적했다.

예:

- 설정집에 항목을 추가할 수 있다.
- 기존 자료만으로 기획서를 만들어달라고 할 수도 있다.
- 요청 당시에는 신규 문서인지 기존 문서 수정인지 알 수 없을 수 있다.

초기 후보:

- `create_document`: 신규 문서 생성 상위 workflow
- 기능 분리: 설정 추가, 자료 정리, 기획서 작성 등을 각각 별도 workflow로 분리

문제:

- `create_document`는 기존 문서 수정 가능성을 처리하기에 너무 좁다.
- 요청 내용을 검색해보기 전에는 신규 생성인지 기존 문서 수정인지 판단할 수 없다.

결정:

- 상위 workflow 이름과 역할은 `document_change`로 둔다.
- 문서 관련 요청은 생성과 수정을 먼저 확정하지 않고, 검색 후 분기한다.

### `document_change` 분기 구조

문서 관련 요청의 분기는 다음 다섯 가지로 정했다.

- `create_new_document`: 관련 확정 문서가 없고 독립 문서로 분리하는 것이 자연스러운 경우
- `update_existing_document`: 관련 확정 문서가 있고 기존 문서 갱신이 자연스러운 경우
- `compile_from_sources`: 자료 정리, 요약, 출처 묶음이 목적일 경우
- `draft_design_from_materials`: 기존 자료를 기획서 형식으로 구조화할 경우
- `ask_for_clarification`: 분기나 대상 문서 판단 근거가 부족한 경우

결정:

- `document_change`는 문서 생성 규칙이 아니라 문서 요청 라우터다.
- 실제 기획서 초안 작성은 `write_design_doc` 하위 workflow가 맡는다.
- 실제 기존 문서 변경안 작성은 `propose_change` 하위 workflow가 맡는다.

## 사용자 질문과 답변

### Q1. 이제 어떤 작업부터 시작해야 하는가?

초기 답변:

- 비어 있는 `workspace/project_brief.md`를 보고 프로젝트 브리프 작성이 우선이라고 판단했다.

수정:

- 사용자는 게임 기획 콘텐츠 작성이 아니라 기능 규칙과 스킬 정비가 목표라고 정정했다.

결정:

- 운영 규칙과 workflow 정비부터 진행한다.

### Q2. 지금 어느 기능에 대해 어느 정도까지 규칙과 스킬을 만들었는가?

답변:

- 입력 분류, 신규 기획서 작성, 기존 문서 변경안 생성, 승인 큐, 결정 로그, 버전 기록, 프로젝트 검색의 기본 workflow가 있다.
- `conflict_review`, `document_completion`, `planning_assistant`, `korean_game_design_style` 스킬이 있다.
- 다만 승인 문구 판정, 상태 전환 규칙, 문서 타입별 세부 작성 규칙, 검색 답변 포맷 등은 아직 얕다.

결정:

- 현재 상태는 기능 뼈대가 있고 세부 판단 규칙을 보강해야 하는 단계로 본다.

### Q3. 전부 `approval_queue` 기능에 대한 것인가?

답변:

- 아니다.
- `approval_queue`는 중심 허브지만 전체 기능은 아니다.
- 다른 workflow는 요청 분류, 검색, 초안 작성, 변경안 작성, 결정 기록, 버전 기록을 담당한다.

결정:

- 기능 구조를 승인 큐 하나로 축소해서 설명하지 않는다.

### Q4. 신규 문서가 항상 기획서는 아닌데 어떻게 처리해야 하는가?

답변:

- 기존 `write_design_doc`라는 이름과 흐름은 너무 좁다.
- 처음에는 범용 `create_document`를 제안했지만, 사용자가 신규 문서인지 기존 문서 수정인지 모를 수 있다고 지적했다.

결정:

- 상위 단위를 `create_document`가 아니라 `document_change`로 올린다.

### Q5. 기존 문서 수정도 하나로 묶어야 하는 것 아닌가?

답변:

- 맞다.
- 생성과 수정을 별도 최상위 workflow로 두면 요청 초기에 라우팅이 흔들린다.
- 먼저 관련 문서를 검색하고, 그 결과에 따라 생성, 수정, 자료 취합, 기획서화, 질문으로 분기해야 한다.

결정:

- `document_change`가 문서 관련 요청의 최상위 workflow가 된다.

### Q6. `docs/workflows/document_change.md`에는 무엇이 들어가는가?

답변:

- 목적, 사용 조건, 검색 후 분기 단계, branch rule, output, safety rule이 들어간다.
- 핵심은 문서 생성 규칙이 아니라 문서 요청 라우터라는 점이다.

결정:

- 해당 내용을 실제 파일로 추가한다.
