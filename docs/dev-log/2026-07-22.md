## 기록 성격

## 오늘의 목표

기획서의 비어 있는 부분을 AI가 임의로 확정하지 않으면서도 사용자가 허용한
범위에서는 실질적인 창작 대안을 만들 수 있게 한다. 일반 시나리오 작성,
인게임 스크립트 작성과 검수를 역할별 서브 에이전트로 분리한다.

동시에 각 게임 프로젝트를 처음 열었을 때 현재 목표와 확정 문서 구성을 바로
파악할 수 있도록 프로젝트 루트에 README 랜딩 페이지를 둔다.

핵심 방향:

- 창작 가능한 공백과 사용자만 결정할 수 있는 사실을 구분한다.
- 사용자가 허가한 공백에만 복수 대안을 만든다.
- 창작자와 검수자를 분리한다.
- 서브 에이전트는 초안과 검수 결과만 반환하고 프로젝트 상태를 직접 바꾸지
  않는다.
- 프로젝트 README는 탐색용 색인이며 상세 설정의 원본이 아니다.
- 확정 문서와 README 링크 변경은 같은 승인 범위에서 동기화한다.

## 작업 배경

기존 구조에는 인게임 스크립트 작성용 `scenario_writer`가 있었지만 다음 작업은
메인 Codex가 직접 수행했다.

- 일반 시나리오 Draft 작성과 구조 개선 검토
- 작성된 시나리오·스크립트의 최종 검수
- 일반 기획 문서의 GAP 분류와 창작 대안 생성

이 구조에서는 작성자와 검수자의 관점이 분리되지 않고, 기획 창작도 절차는
있지만 전담 역할의 프로젝트 적응형 판단이 부족했다. 또한 프로젝트의 확정
문서가 늘어날수록 `project_brief.md`, `design/README.md`, Approval Queue와
세부 문서를 각각 열어야 현재 상태를 파악할 수 있었다.

## 기획 창작 보완 구조

### GAP 분류

기획 Draft의 누락을 다음 세 유형으로 구분한다.

| 유형 | 의미 | 처리 |
|---|---|---|
| `creative_fillable` | 프로젝트 근거 안에서 설계 대안을 만들 수 있는 공백 | 사용자 허가 후에만 대안 생성 |
| `user_fact` | 실제 프로젝트 결정이나 외부 사실이 필요한 공백 | 창작하지 않고 `TBD`와 질문 유지 |
| `dependency` | 다른 canonical owner나 선행 승인이 필요한 공백 | 의존성을 기록하고 해소 전까지 `TBD` |

실제 플랫폼, 엔진, 예산, 일정, 인력, 등록 에셋·데이터 ID, 외부 계약과 법적
조건은 `user_fact`로 두며 AI가 추측하지 않는다.

### 전담 창작 에이전트

`design_creative_planner`는 대상 문서가 게임 개요, 세계관, 시스템, 콘텐츠,
UI 또는 기술 중 어떤 역할인지 확인하고 그 역할에 맞는 Creative Design Brief를
구성한다.

동작 Phase:

```text
Main
  → design_creative_planner(classify)
  → 사용자에게 전체 GAP 공개
  → 사용자 허가
  → design_creative_planner(generate_options)
  → 사용자 선택·원본 재확인
  → design_creative_planner(incorporate_selection)
  → Main 검토
  → pending 승인안
```

`classify`에서는 대안을 만들지 않는다. `generate_options`는 메인 Codex가
전달한 정확한 GAP ID만 다룬다. `incorporate_selection`에서는 사용자가 선택한
안만 Draft에 넣고 선택하지 않은 대안은 Creative Proposal Log에 보존한다.

### 창작 출처 구분

- 일반 기획 창작: `CP-*`
- 일반 시나리오 구조 개선: `Scenario Improvement Review`
- 인게임 스크립트의 구체 문장·ID·연출: `CW-*`
- 인게임 스크립트가 상위 시나리오와 달라진 구조: `NR-*`

같은 내용에 여러 출처 표식을 중복 적용하지 않는다. 밸런스 수치는 확정값이
아니라 검증 지표와 재조정 조건을 가진 `provisional` 가설로 관리한다.

## 시나리오 작성·검수 서브 에이전트 구조

### 역할 분리

| 에이전트 | 책임 |
|---|---|
| `scenario_designer` | 일반 시나리오의 원안 기반 Draft와 분리된 구조 개선안 작성 |
| `scenario_writer` | 프로젝트별 Writer's Brief, 인게임 대본과 구현용 씬 명세 작성 |
| `scenario_reviewer` | 두 산출물의 원본 충실도, 서사 품질, 플레이 가능성, 출처 표식과 승인 경계 독립 검수 |

작성 흐름:

```text
일반 시나리오
Main → scenario_designer → scenario_reviewer → Main → pending

인게임 스크립트
Main → scenario_writer → scenario_reviewer → Main → pending

검토 전용
Main → scenario_reviewer → Main → Scenario Review Report
```

검수 결과는 `blocking`, `required_revision`, `authorial_reconsideration`, `note`로
구분한다. `blocking`이나 `required_revision`이 남으면 원 작성 에이전트에
되돌려 수정하고 다시 검수한다. 선택적 개선 의견은 Draft에 자동 반영하지
않는다.

모든 작성·창작·검수 에이전트는 read-only handoff만 반환한다. Approval Queue
저장, 승인 판단, 원본 재확인, 확정 문서 적용, Decision Log와 Version History
갱신은 메인 Codex가 담당한다.

## 프로젝트 README 랜딩 페이지

### 목적

각 프로젝트 루트의 `README.md`에서 다음 정보를 한 번에 확인할 수 있게 했다.

- 프로젝트의 짧은 설명
- 프로젝트 ID, 상태, 장르, 플랫폼·엔진과 현재 초점
- 현재 존재하는 확정 기획 문서와 각 문서의 한 문장 책임
- Project Brief, Design Index, Temporary Ideas, Approval Queue, Decision Log와
  Version History 링크
- 처음 프로젝트를 읽는 순서

### 원본 소유 경계

프로젝트 README는 탐색용 요약·색인이다. 세계관, 시나리오, 시스템, 콘텐츠,
UI와 기술 상세의 canonical owner가 아니다.

- 소개는 `project_brief.md`와 확정 `game_overview`만 요약한다.
- 실제로 존재하고 상태가 `confirmed`인 문서만 링크한다.
- 승인 전 문서나 예정 경로는 확정 문서 목록에 넣지 않는다.
- 세부 사실을 복제하지 않고 역할, 링크와 한 문장 책임만 기록한다.
- 확정 문서 생성·삭제·이동·역할 변경 시 README, `design/README.md`와 영향을
  받는 game overview 링크를 같은 승인 범위에서 갱신한다.

### 실제 적용

`docs/templates/project_readme.md`를 추가하고
`workspace/projects/chronicles-of-the-twelve-bonds/README.md`에 십이인연록의
Project Snapshot, 현재 초점, 확정 문서 지도와 작업 문서 링크를 구성했다.

프로젝트 목록 안내인 `workspace/projects/README.md`에도 프로젝트 진입 시 루트
README를 먼저 확인하고, 상세 설정은 연결된 `design/` 문서를 원본으로 사용한다는
규칙을 추가했다.

## 주요 결정

### 작성자와 검수자를 분리한다

결정:

- 일반 시나리오와 인게임 스크립트는 작성 에이전트와 검수 에이전트를 분리한다.
- 검수자는 작성자의 Sources 요약에 의존하지 않고 프로젝트 원본을 직접 읽는다.
- 검수자가 Draft를 직접 고치지 않고 메인 Codex가 결과를 원 작성자에게
  되돌린다.

이유:

- 같은 역할의 자체 검수만으로는 출처 누락이나 구조적 약점을 놓칠 수 있다.
- 검수자가 직접 수정하면 원안, 제안과 검수 결과의 경계가 흐려질 수 있다.

### 서브 에이전트는 프로젝트 상태를 직접 저장하지 않는다

결정:

- 네 custom agent의 sandbox를 `read-only`로 둔다.
- Approval Queue를 포함한 프로젝트 파일 저장은 메인 Codex만 수행한다.

이유:

- 창작 권한과 승인·적용 권한을 분리한다.
- 병렬 또는 반복 검수 과정에서 프로젝트 기록이 중간 결과로 덮이는 것을
  방지한다.

### 프로젝트 README는 상세 문서를 대신하지 않는다

결정:

- README는 프로젝트 설명, 현재 초점과 확정 문서 지도만 소유한다.
- 상세 설정은 역할별 canonical 문서에 유지한다.

이유:

- 프로젝트 진입성은 높이면서 같은 사실이 README와 상세 문서에서 서로 다르게
  유지되는 문제를 막기 위해서다.
