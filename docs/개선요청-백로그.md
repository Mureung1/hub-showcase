사용자가 요청한 개선 항목 5개 + 경쟁 서비스 비교에서 도출한 제안.
**아직 착수하지 않았다.** 각 항목의 "확인 필요"를 먼저 정리한 뒤 그날 계획을 세워 진행한다.

접수 시점 기준선: 브랜치 `N126_이상진`, 최신 커밋 `315ef961`(리디자인 완료·푸시됨), BE 테스트 187/187.

## 1. 지역 데이터 전국 확장 + 위치 자동 설정

### 요구사항
- 대한민국 전체 시/도 · 시/군/구를 전부 추가
- 사용자 컴퓨터 위치를 자동으로 감지해 지역이 기본 설정되게

### 현재 상태
- `bungae-moim/src/data/mockData.js`의 `REGIONS` 상수에 **하드코딩**: 시/도 2개(서울특별시, 경기도), 시/군/구 8개, 읍/면/동 19개뿐
- DB: `meetings.region_sido varchar(20)`, `region_sigungu varchar(20)`, `region_eupmyeondong varchar(20)`
- 백엔드 검증(`validators.js`)은 **길이만 검사하고 화이트리스트가 없다** — 임의 문자열도 통과한다
- 파일 주석에 "실제 서비스에서는 이 파일 전체가 API 응답으로 대체됩니다"라고 적혀 있으나 아직 상수 그대로

### 작업 범위(예상)
- 전국 행정구역 데이터 확보 → FE 상수 또는 별도 JSON, 혹은 BE 테이블 + 조회 API
- 시/도 17개, 시/군/구 약 250개, 읍/면/동까지 가면 약 3,500개
- BE에 지역 화이트리스트 검증 추가(현재 없음)

### 결정 (2026-07-24)
**시/군/구까지.** 읍/면/동은 제외한다(약 3,500개라 셀렉트 박스로 못 쓰고 검색형 입력을 새로 만들어야 함).
기존 `region_eupmyeondong` 컬럼은 nullable이라 그대로 두면 된다.

### 확인 필요
- **(a) 데이터를 어디에 둘까?** FE 상수 JSON(간단, 번들 커짐) / BE 테이블 + API(정석, 마이그레이션 필요) 둘 중 하나.
  시/군/구까지면 약 250건이라 FE 상수로도 부담이 크지 않다.
- **(c) 위치 자동 설정의 정확도 문제** — 브라우저 Geolocation API는 **위도·경도만** 준다. "서울특별시 강남구"로 바꾸려면 좌표→행정구역 **역지오코딩**이 필요하고, 이건 카카오/네이버 지도 API 키가 있어야 한다(무료 쿼터 있음). 또한 HTTPS에서만 동작한다(`localhost`는 예외라 개발은 가능하지만 배포 시 HTTPS 필수 — 3주차 배포 과제와 엮인다).
- **(d) 자동 설정을 어디에 적용?** 모임 등록 폼의 기본값 / 모임 찾기 필터의 기본값 / 둘 다.
- **(e) 사용자가 위치 권한을 거부하면?** 기본값 없이 두거나, 마지막 선택 지역을 기억하거나.

## 2. 마이페이지에서 취소·완료된 모임 삭제

### 요구사항
- 마이페이지에서 취소된(하거나) 완료된 모임을 삭제할 수 있게

### 현재 상태
- 마이페이지는 G1(내가 등록한 모임) / G2(참여한 모임) 두 목록을 보여주기만 한다
- E5(`DELETE /api/meetings/:id`)는 **모임 취소**이지 삭제가 아니다 — `status`를 `cancelled`로 바꾸고 참여자를 전원 cascade 취소한다. 행은 남는다
- 종료 판정은 `utils/status.js`의 `isMeetingEnded(meeting)`

### 결정 (2026-07-24)
**내 목록에서 숨기기(소프트 삭제).** DB에서 지우지 않는다.

이유: 하드 삭제는 그 모임에 참여했던 **다른 사람의 이력까지 지우고**, 신뢰도 감점 근거도 사라진다.
특히 3번 결정으로 신뢰도 알고리즘을 도입하기로 했는데, 그 설계는 **"이력이 원본이라 공식을 바꿔 전체
재계산할 수 있다"**를 핵심 장점으로 삼는다. 하드 삭제는 그 전제를 무너뜨린다.

구현 방향: `meeting_participants`에 `hidden_at` 컬럼을 두거나, "사용자 × 모임" 숨김 기록을 별도 테이블로.
모임장이 만든 모임(G1)과 참여한 모임(G2) 양쪽에 적용해야 하므로 후자가 더 깔끔할 수 있다.

### 확인 필요
- **(a) 대상 범위** — "취소된 모임"과 "종료된 모임" 둘 다인가? 모집 중인 모임은 제외가 맞겠지.
- **(b) 되돌리기(숨김 해제)가 필요한가?** 필요하면 "숨긴 모임 보기" 토글이 있어야 한다.
- **(c) 모임장이 자기 모임을 숨기면 참여자 화면에는 그대로 보이는 게 맞나?** (숨기기는 각자 화면에만 적용)

## 3. 신뢰도 점수 옆 이모지

### 요구사항
| 점수 | 이모지 |
|---|---|
| 0~30 | 우는 이모지 |
| 31~60 | 무표정 이모지 |
| 61~90 | 웃는 이모지 |
| 91~100 | 하트뿅뿅 이모지 |

### 현재 상태
- `components/TrustBadge.jsx`가 `신뢰도 {score.toFixed(1)}` 형태로 **소수점 1자리**까지 표시
- 리디자인으로 `TrustBadge`가 **헤더에 올라가 전 페이지에 상시 노출**된다
- 사용처: 헤더, 상세(모임장·신청자), 마이페이지 프로필

### ⚠️ 먼저 알아야 할 것 — 지금 신뢰도는 올라갈 방법이 없다
- 현재 신뢰도 로직은 **"확정 후 취소 −3" 하나뿐**이다. 가입 시 50에서 시작해 **내려가기만 한다.**
- 즉 이모지를 붙이면 실질적으로 **무표정(31~60)에서 시작해 우는 얼굴로만 이동**하고, 웃는 얼굴이나 하트는 **아무도 도달할 수 없다.**
- 이미 `docs/superpowers/specs/2026-07-22-신뢰도-알고리즘-design.md`에 개편 설계가 있다(모임 후 상호 평가 + 출석 체크 → 이력에서 점수 산출). 그 문서에 **"표시 변경(정수 + 색 밴드 + 평가 건수)은 선행 적용 가능"**이라고 이미 적혀 있다.

### 결정 (2026-07-24)
**이모지 + 표시 개편 + 신뢰도 알고리즘 본체까지 전부 적용한다.** 즉 이 항목은 단순 이모지 추가가 아니라
`2026-07-22-신뢰도-알고리즘-design.md`의 구현 전체를 포함한다. 그 설계의 핵심은:

- 모임 종료 후 **모임장 ↔ 확정 참여자 상호 평가**(출석 체크 필수 + 태그 선택)
- 그 **이력에서 점수를 계산**한다 — 이력이 원본이라 공식을 바꿔 전체 재계산이 가능
- `tanh` 포화(높을수록 오르기 어려움), 같은 상대 반복 평가 `1/n` 체감(친구끼리 파밍 차단),
  최근성 감쇠(반감기 90일), 노쇼는 **양쪽 진술이 엇갈리면 아무도 벌하지 않음**

**범위가 크다.** 5개 요청 항목 중 단연 가장 큰 작업이고, 사실상 별도 프로젝트에 가깝다:
DB 테이블 신설(평가 이력), 모임 종료 감지, 평가 UI, 점수 산출 배치 또는 온디맨드 계산, 기존 `trust_score` 마이그레이션.

### 확인 필요
- **(a) 이 항목을 하나의 작업일로 볼까, 여러 날로 쪼갤까?** 다른 4개 항목과 규모가 다르다.
  제안: **표시 개편(이모지+정수+색 밴드)을 먼저 하루**에 끝내고, **알고리즘 본체는 별도로** 브레인스토밍부터 다시 시작.
- **(b) 이모지 4종을 구체적으로 무엇으로?** 예: 😢 / 😐 / 🙂 / 😍. 확정 필요.
- **(c) 점수를 정수로 바꾸는 게 맞나?** 지금은 `50.0`처럼 소수점. 경계값(30/31, 60/61, 90/91)을 다루려면 정수가 깔끔하다.
- **(d) 기존 사용자의 `trust_score`(현재 전원 50 근처)는 새 공식으로 재계산하나, 아니면 시작점으로 두나?**
- **(e) 평가 이력이 없는 신규 사용자는 어느 밴드에 놓나?** 50이면 무표정에서 시작한다.

### 현재 상태

- 그 안에서는 이미 브랜드·nav가 왼쪽, 인증 영역이 `margin-left: auto`로 오른쪽에 붙어 있다

### 확인 필요
- **(a) "끝"이 화면 끝인가, 지금 컨테이너 끝인가?**

- **(b) 헤더가 전체 폭이 되면 본문(1200px)과 좌우가 어긋난다.** 로고가 본문 왼쪽 끝보다 더 왼쪽에 있게 되는데, 괜찮은지.

CSS 한두 줄. 5개 항목 중 가장 작다.

## 5. 생년월일 인증 → 휴대폰 본인인증

### 요구사항
- 생년월일 직접 입력 대신 **휴대폰 번호로 본인 인증**을 받아 성인 여부 판정
- 성인이 아니어도 휴대폰 인증을 했으면 **"본인 인증 완료" 표시**를 줘서 믿을 만한 사람임을 보여주기

### 현재 상태
- D5: 최초 로그인 시 생년월일을 직접 입력(`BirthDateGate`), `users.birth_date`에 저장
- 성인 판정은 서버가 `canApply` / `blockReason`으로 내려준다
- 자기 신고식이라 **아무 날짜나 넣을 수 있다** — 요청의 문제의식은 정확하다

### ⚠️ 이 항목에는 기술적·행정적 벽이 있다. 조사 결과를 먼저 공유한다

**"휴대폰 번호로 성인 인증"은 두 가지 서로 다른 기술이 섞여 있다.**

| | SMS 인증(OTP) | 본인확인 서비스(PASS·NICE 등) |
|---|---|---|
| 확인되는 것 | 그 번호를 **지금 소유**하고 있다 | **실명·생년월일·성별·내외국인** |
| 성인 여부 판정 | **불가능** — 번호만으로는 나이를 알 수 없다 | 가능 |
| 필요 조건 | 문자 발송 API(네이버 SENS, CoolSMS 등) 결제 수단 | **사업자등록증 + 본인확인기관과 계약** |
| 개인·학생 프로젝트 | 가능 | **사실상 불가** |

NICE평가정보의 휴대폰 본인확인 서비스는 신청 시 **사업자등록증 사본**과 서비스 신청서를 제출해 계약을 체결해야 shop ID가 발급된다. 개인 개발자가 사업자등록 없이 붙이기는 어렵다.

**즉 요청을 그대로 구현하려면 사업자등록이 필요하다.** 그렇지 않다면 아래 대안 중 하나를 골라야 한다.

### 대안
1. **SMS OTP + 생년월일 병행** — 문자로 번호 소유는 검증하고, 생년월일은 지금처럼 직접 입력받는다. "휴대폰 인증 완료" 배지는 진짜로 줄 수 있다(요청의 후반부는 충족). 다만 **성인 인증은 여전히 자기 신고**다. 문자 발송 비용이 건당 발생한다(수십 원 수준).
2. **본인확인 흐름을 UI만 흉내내고 실제 연동은 하지 않음** — 포트폴리오용으로 화면과 상태 전이만 만든다. 정직하게 "데모"라고 명시해야 하고, 실제 인증 효과는 없다.
3. **현행 유지 + 배지만 추가** — 생년월일은 그대로 두고, 별도의 검증 수단이 생길 때까지 인증 배지를 보류.
4. **사업자등록 후 실제 연동** — 범위를 크게 벗어난다.

### 추가 조사 — "사업자등록증 없이 생년월일 검증이 정말 불가능한가?" (2026-07-24 확인)

**법적 의미의 검증은 불가능하다.** 다만 지금(완전 자기 신고)과 법적 검증 사이에 **중간 단계가 있다.**

| 단계 | 방법 | 사업자등록 | 신뢰 수준 |
|---|---|---|---|
| 현재 | 우리 폼에 생년월일 직접 입력 | 불필요 | 아무 값이나 가능 |
| **중간** | **소셜 계정(카카오·구글)이 보관 중인 생일·출생연도를 받아옴** | **불필요** | 조작하려면 계정 설정을 미리 바꿔야 함 |
| 법적 | 본인확인기관(NICE·KCB·PASS) | **필요** | 실명·생년월일 법적 확인 |

**중간 단계가 가능한 근거:**
- 카카오 로그인에 `birthday`(생일) · `birthyear`(출생연도) · `age_range`(연령대) 동의항목이 있다
- 이 항목들은 **비즈 앱** 상태가 필요한데, **사업자등록번호 없이도 "개인 개발자 비즈 앱" 전환이 가능하다.** 조건은 ① 앱 소유자 카카오계정 **본인인증 완료** ② 앱 아이콘 등록 ③ 카카오비즈니스 약관 동의. 이 세 가지뿐이다
- 다만 항목별로 **검수**가 필요하고, 개인 개발자 비즈 앱은 **카카오싱크(비즈니스 채널 연결) 불가** 제한이 있다

**⚠️ 그러나 카카오 공식 문서가 직접 못박아둔 문장이 있다:**
> "카카오는 본인인증기관이 아니므로 카카오계정의 연계정보로 서비스의 본인 인증을 대신할 수 없음"

즉 카카오에서 받은 생년월일은 **카카오계정에 사용자가 입력해둔 값**이지 법적으로 확인된 값이 아니다. 구글도 마찬가지다(프로필의 자기 기재 값).

**결론:**
- "만 19세 이상임을 법적으로 보증"하려면 → **사업자등록 + 본인확인기관 계약 외에 길이 없다**
- "지금보다 조작하기 번거롭게 만들고, 사용자가 생년월일을 타이핑하는 단계를 없앤다" → **카카오 생일·출생연도로 가능하다.** 우리 폼에 즉석에서 아무 날짜나 치는 것과 달리, 카카오 계정 설정을 미리 바꿔야 하므로 마찰이 생긴다
- 참고로 **카카오 로그인은 이미 심사 대기 중**이다. 이 경로는 절반쯤 진행돼 있다

### 확인 필요
- **(a) 위 "중간 단계"(카카오 생일·출생연도로 `BirthDateGate` 대체)로 만족하는가?** 법적 효력은 없지만 사업자등록 없이 갈 수 있는 최선이다.
- **(b) 구글로만 로그인한 사용자는 어떻게 하나?** 카카오에서만 생년월일을 받는다면 구글 사용자는 여전히 직접 입력이 필요하다 — 두 경로가 갈린다.
- **(c) "본인 인증 완료" 배지의 의미를 무엇으로 정의할까?** 카카오 생년월일 제공 동의 완료 / SMS OTP 통과 / 둘 다.
- **(d) SMS OTP를 별도로 넣을까?** 번호 소유만 확인되고 나이는 알 수 없지만, 배지 근거로는 쓸 수 있다. 문자 발송 비용이 건당 발생한다.
- **(e) 기존 `users.birth_date` 데이터와 `BirthDateGate`는?** 유지·병행·폐기.
- **(f) 휴대폰 번호를 저장하면 개인정보다.** 암호화·마스킹 정책이 필요하다(현재 이메일만 저장 중).

# 경쟁 서비스 비교에서 도출한 추가 제안

당근 모임, 문토, 소모임을 조사해 우리 프로젝트에 없는 것 중 **효과 대비 작업량이 좋은 것**을 골랐다.

### A. 모임 대표 이미지 — **채택, 외부 스토리지**
당근 모임·문토 모두 모임 카드에 **썸네일 이미지**가 있다. 우리는 텍스트만이라 목록이 밋밋하고, 리디자인으로 만든 3열 카드 그리드가 특히 허전하다.

**결정: 외부 스토리지(S3·Cloudinary 등)에 저장.** 로컬 디스크는 3주차 배포 때 무료 호스팅이 재시작하면 파일이 날아간다.

**결정 (2026-07-24): Cloudinary.** 이미지 전용 서비스라 업로드만 하면 리사이즈·포맷 변환·CDN을 자동 처리한다.
설정이 가장 빨라 기능 자체에 집중할 수 있다. (S3는 IAM·버킷 정책·CORS + 리사이즈 직접 구현이 붙는다)

**확인 필요**
- **(a) 이미지 없이 등록할 수 있나?** 필수면 등록 마찰이 커지고, 선택이면 기본 이미지가 필요하다(카테고리별 기본 색·아이콘 등).
- **(c) 몇 장?** 1장(대표)만인지 여러 장인지.
- **(d) 용량·형식 제한과 리사이즈** — 원본을 그대로 두면 목록에서 수 MB 이미지를 여러 장 받게 된다.
- **(e) 기존 모임 4건은 이미지가 없다.** 마이그레이션 시 nullable로 두면 된다.

### B. 신청 시 한마디 — **채택**
당근은 모임 가입 시 **가입 질문을 설정하고 답변을 필수로 받을 수 있다.** 우리 소모임 승인 흐름(F3/F4)에서 모임장이 승인 여부를 판단할 근거는 지금 **닉네임과 신뢰도뿐**이다.

**결정 (2026-07-24): 모임장이 질문을 설정하고, 질문이 없으면 답변 없이 그냥 신청된다.**
즉 질문은 **모임 단위의 선택 항목**이다. 설정돼 있으면 신청 화면에 답변 입력이 뜨고, 없으면 지금과 똑같이 동작한다.

구현 방향: `meetings.apply_question`(nullable) + `meeting_participants.apply_answer`(nullable)
+ 신청 화면 조건부 입력 + 신청자 목록에 답변 표시.

**확인 필요**
- **(a) 답변이 필수인가?** 질문이 설정된 모임에서 답변을 비우고 신청할 수 있나. (당근은 필수 설정이 가능)
- **(b) 번개모임에도 질문을 달 수 있나?** 번개는 신청 즉시 확정이라 모임장이 읽고 판단할 여지가 없다. **소모임만**이 자연스러워 보인다.
- **(c) E4(모임 수정)와의 관계** — 수정은 full-replace다. 이미 답변을 받은 뒤 질문을 바꾸면 기존 답변이 엉뚱한 질문에 붙는다. 참여자가 있으면 질문 수정을 잠글지 정해야 한다.
- **(d) 거절 사유도 남길까?** 지금 거절은 이유 없이 처리된다.

### C. 승인·거절 알림 — **채택, 헤더 뱃지 + 알림 목록**
현재 상세 화면에 **"별도 알림은 없으니 마이페이지에서 확인해주세요"**라는 문구가 그대로 있다. 신청자가 승인됐는지 알려면 직접 들어와 봐야 한다.

**결정: 알림 테이블 + 헤더 읽지 않음 뱃지 + 알림 목록.** 실시간 푸시·이메일은 제외(브라우저 권한·서비스워커·HTTPS·발송 서비스가 따라붙어 범위가 급증).

**확인 필요**
- **(a) 어떤 이벤트를 알림으로?** 후보: 내 신청이 승인/거절됨 · 내 모임에 새 신청이 옴 · 참여한 모임이 취소됨 · 모임 시작이 임박함.
  마지막 항목은 **스케줄러가 필요**해서 성격이 다르다(다른 셋은 사용자 행동 시점에 만들면 된다).
- **(b) 갱신 방식** — 페이지 이동/새로고침 때만 조회할지, 주기적 폴링을 넣을지.
- **(c) 읽음 처리** — 목록을 열면 전체 읽음인지, 항목별인지.

### D. 카테고리 확장 — 미채택 (작업량이 작아 끼워 넣기 좋음)
우리는 4개(운동/스터디/취미/식사). 당근은 스터디·가족육아·반려동물·봉사활동·음식·투자금융·문화예술·인문학책·게임·음악·공예 등으로 세분화돼 있다.
상수 배열이라 작업량이 매우 작다. **BE에 카테고리 화이트리스트가 없다**는 기존 백로그 항목과 함께 처리하면 좋다.

### E. 정기 모임 반복 생성 — **채택, 시리즈로 묶기** ⚠️
당근은 매주·격주·매월 반복 일정을 **최대 6개까지 한 번에** 생성하되, 만들어진 뒤에는 각각 별개 모임이다.

**결정: 시리즈로 묶는다** — 한 번 신청하면 전체 회차에 참여되고, 시리즈 단위로 수정·취소한다.

**⚠️ 이 선택은 파급이 크다.** 당근 방식(독립)은 기존 로직을 거의 안 건드리지만, 시리즈 방식은 핵심 도메인을 다시 설계해야 한다:
- **참여 모델**: `meeting_participants`가 지금은 "사용자 × 모임"이다. 시리즈면 "사용자 × 시리즈"가 되거나, 회차마다 행을 만들되 시리즈로 묶어야 한다
- **정원**: 회차별 정원인가 시리즈 전체 정원인가
- **취소**: 한 회차만 못 가는 경우와 시리즈 전체를 그만두는 경우가 다르다 — F2(참여 취소)가 두 갈래가 된다
- **신뢰도**: "확정 후 취소 −3"이 회차마다 적용되면 한 번 빠질 때마다 감점이다. 출석·평가도 회차 단위인지 시리즈 단위인지 정해야 한다
- **E4(수정)/E5(취소)**: full-replace 수정이 시리즈 전체에 적용되는지, 한 회차만인지
- **목록·상세**: 시리즈를 한 카드로 보여줄지 회차별로 보여줄지

#### "신뢰도를 알고리즘으로 바꾸면 시리즈 문제가 해결되지 않나?" (2026-07-24 질문)

**부분적으로 맞다. 하지만 알고리즘이 새 문제를 하나 만든다.**

- **해결된다**: "회차마다 −3 감점"은 사라진다. 취소 자체가 감점 이벤트가 아니게 되므로.
- **해결되지 않는다**: 위 6개 파급 중 신뢰도는 하나뿐이다. 참여 모델·정원·취소 두 갈래·E4 범위·목록 표시는 신뢰도와 무관하게 그대로 남는다.
- **⚠️ 새로 생긴다**: 7/22 설계의 **"같은 상대 반복 평가 `1/n` 체감"**은 친구끼리 점수를 올려주는 파밍을 막는 장치인데,
  **정기 모임에서는 정상적인 반복 참여자가 그 감쇠에 그대로 걸린다.** 10주 스터디를 성실히 나온 사람이 매주 같은
  사람들에게 평가받으면 2회차부터 기여도가 반토막씩 난다. **정기 모임 참여자일수록 점수가 안 오르는 역차별**이
  생기고, 이건 설계 의도와 정반대다.

딸린 문제들:
- **출석 체크는 반드시 회차별**인데 참여 행이 시리즈 단위면 출석을 어디에 기록하나 → 별도 회차 테이블이 필요
- **평가를 회차마다 하나, 시리즈당 한 번 하나?** 후자면 10주 중 5주만 나온 사람을 어떻게 평가하나
- **부분 노쇼** 개념이 필요 — "3주차만 안 나옴"을 "양쪽 진술 대조" 규칙에 어떻게 넣을지

**순서 문제**: 알고리즘은 아직 존재하지 않는다(3단계). 시리즈와 알고리즘을 동시에 설계하면 서로 얽혀
각각보다 훨씬 어려워진다.

**추천**: 알고리즘을 먼저 완성해 실제로 굴려본 뒤 시리즈를 얹는다. 그때는 `1/n` 감쇠를 "정기 모임은 예외"처럼
조정할 근거가 데이터로 생긴다. 지금 둘을 같이 설계하면 전부 추측으로 정해야 한다.

#### 결정 (2026-07-24): 데이터는 독립, 표시만 시리즈

**"묶는 것은 표시의 문제이고 도메인은 건드리지 않는다."**

- `meetings`에 **`series_id`(nullable)** 컬럼만 추가한다. 반복 생성으로 한 번에 만든 회차들이 같은 값을 갖는다
- **참여·정원·취소·신뢰도·E4·E5는 전부 지금 그대로 회차별로 동작한다.** 위에 나열한 6개 파급이 거의 사라진다
- 화면에서만 `series_id`로 묶어 "한 소모임의 여러 일정"처럼 보여준다
- `1/n` 감쇠 역차별 문제도 **회피된다** — 각 회차가 독립 모임이므로 평가 구조가 지금과 동일하다.
  (다만 같은 사람들이 반복해서 만나는 정기 모임 특성상 감쇠가 걸리는 것 자체는 남는다. 알고리즘 구현 때 재검토할 것)

**⚠️ 이 선택의 대가 — 신청이 회차별이다.** 데이터가 독립이므로 6주 시리즈면 원칙적으로 **6번 신청**해야 한다.
화면에서 하나처럼 보이는데 신청은 따로 해야 하면 어긋난 느낌을 준다. 아래 (b) 참고.

**추가 결정 (2026-07-24)**
- **목록 표시: 시리즈당 카드 1장으로 접는다.** "매주 화 19:00 · 7/28~9/1 · 정기 6회"를 보여주고,
  클릭하면 회차 목록으로 간다. 목록 조회에 `series_id` 그룹핑이 들어가고 회차 목록 화면이 하나 필요하다.
- **신청은 회차별로 따로.** "여러 회차 한 번에 선택"은 만들지 않는다. 참여하고 싶은 회차에 각각 신청한다.

**확인 필요**
- **(a) 상세 페이지에서 다른 회차를 보여줄까?** "이 모임의 다른 일정" 목록 같은 형태. 신청이 회차별이므로 이게 있으면 이동이 편하다.
- **(b) 마이페이지에서도 묶을까?** 6회차를 다 신청하면 지금 구조에선 6개가 나열된다.
- **(c) 반복 규칙과 최대 회차** — 매주/격주/매월, 최대 몇 개까지(당근은 6개).
- **(d) 시리즈 카드의 "참여 인원"은 무엇을 보여주나?** 회차마다 인원이 다르다. 가장 가까운 회차 기준 / 합계 / 표시 안 함.
- **(e) 회차가 하나씩 지나가면 시리즈 카드는?** 지난 회차를 뺀 나머지로 접어서 계속 보여주고, 전부 지나가면 목록에서 사라진다.
- **(f) 회차 중 하나를 취소하면?** 독립이므로 그 회차만 취소된다. 시리즈 카드의 "정기 6회" 표기를 어떻게 조정할지.

### F. 출석 체크 — **채택, 신뢰도 알고리즘과 묶음**
당근은 모임장이 **QR 코드**를 만들고 참가자가 현장에서 찍어 출석을 인증한다.
우리 `2026-07-22-신뢰도-알고리즘-design.md`가 이미 **"출석 체크 필수 + 상호 평가"**를 신뢰도 산출의 핵심 입력으로 설계해뒀다. 즉 새 아이디어가 아니라 **이미 설계된 것의 구현**이고, 3번(이모지)이 의미를 가지려면 이게 있어야 한다.

**결정: 3-b(신뢰도 알고리즘 본체)와 한 프로젝트로 묶는다.**

**확인 필요**
- **(a) QR 방식인가, 모임장이 명단에서 수동 체크하는 방식인가?** QR은 현장 인증이라 신뢰도가 높지만 카메라·HTTPS가 필요하다. 수동 체크는 훨씬 간단하지만 모임장이 마음대로 찍을 수 있다.
- **(b) 참여자도 "나 갔다"를 표시하나?** 설계문서의 "양쪽 진술 대조 후 엇갈리면 아무도 벌하지 않음"이 이걸 전제한다.

### G. 찜 / 관심 모임 — 미채택
목록에서 바로 저장해두고 나중에 보는 기능. 현재 없음. 작업량 작음.

### H. 인앱 채팅 — **보류** (2026-07-24 검토 후 결정)

주변부 비용이 커서 당분간 오픈채팅 링크 방식을 유지한다. 아래는 재검토할 때를 위한 조사 기록.

**어느 수준을 원하느냐에 따라 하루짜리부터 별도 프로젝트까지 갈린다.**

현재는 **카카오 오픈채팅 링크를 승인된 참여자에게만 공개**하는 방식으로 외부에 위임하고 있다.

| 수준 | 방식 | 작업량 | 한계 |
|---|---|---|---|
| **1. 폴링** | `messages` 테이블 + POST/GET(`?since=`) + FE가 3~5초마다 조회 | **하루 정도** | 실시간 아님, 폴링 부하, 읽음 표시 없음 |
| **2. SSE** | 서버→클라 단방향 스트림(Express에서 비교적 간단), 전송은 POST | 중간 | 연결 유지 필요, 서버 인스턴스가 여러 개면 브로드캐스트에 Redis pub/sub 필요 |
| **3. WebSocket** | socket.io 등 양방향 실시간 | **큼** | 세션을 WS에 태우는 인증, 재연결, 스케일아웃, 배포 환경의 WS 지원 |

**⚠️ 진짜 무거운 건 채팅 자체가 아니라 주변부다.** 메시지를 주고받는 것만은 어렵지 않다. 부담은 여기서 온다:

- **읽지 않은 메시지 수** — C(알림)와 같은 문제를 다시 푼다
- **메시지 알림** — 역시 C와 겹침
- **신고·차단** — B4·H1(신고)과 겹침. 채팅이 생기면 신고 대상이 메시지로 늘어난다
- **이미지 전송** — A(Cloudinary)와 겹침
- **페이지네이션** — 메시지가 쌓이면 무한 스크롤이 필요
- **접근 권한 회수** — 참여 취소·거절·모임 취소 시 채팅을 어떻게 할지
- 메시지 수정·삭제, 접속 중 표시, 타이핑 중 표시

**참고**: 지금의 오픈채팅 링크 방식은 사실 합리적인 선택이다. 위 주변부를 전부 카카오톡이 대신 해주고 있고,
사용자도 이미 익숙한 앱에서 대화한다. 인앱 채팅으로 바꾸면 **"카톡을 안 써도 된다"**는 이점과
**"카톡보다 불편한 채팅을 직접 유지해야 한다"**는 비용을 맞바꾸는 것이다.

**추천**: 하려면 **수준 1(폴링)로 시작**하고, **C(알림)와 같이 설계**한다. 둘 다 "읽지 않음" 개념이 필요해서
따로 만들면 같은 문제를 두 번 푼다. 수준 3을 목표로 한다면 별도 프로젝트로 본다.

**재검토 시 정할 것**
- 수준 1/2/3 중 어디까지 / 오픈채팅 링크를 대체할지 병행할지 / 모임별 단체 채팅만인지 1:1도 필요한지
