# 3주차 개인 개발 Workflow

이 문서는 3주차 작업을 진행할 때 사용할 개인 개발 흐름을 정리한 문서입니다. 작은 단위로 계획하고, 테스트로 확인한 뒤, 검토와 문서화를 거쳐 PR까지 이어지는 순서를 기준으로 합니다.

## 1. 문제와 요구사항 확인

### 무엇을 하는 단계인지
사용자가 원하는 기능, 제외할 범위, 완료 조건을 먼저 정리한다.

### 왜 필요한지
요구사항을 잘못 이해하면 필요 없는 기능을 만들거나 중요한 조건을 놓칠 수 있다.

### 내가 확인할 질문
- 이번 작업에서 꼭 해야 하는 것은 무엇인가?
- 이번 작업에서 제외해야 하는 것은 무엇인가?
- 성공했다고 판단할 기준은 무엇인가?

### 완료 조건
- 구현 범위와 제외 범위를 문장으로 설명할 수 있다.
- 테스트하거나 확인할 핵심 동작을 하나 이상 정했다.

## 2. GitHub Issue 작성

### 무엇을 하는 단계인지
작업 목표, 체크리스트, 예상 변경 파일, 완료 조건을 Issue로 기록한다.

### 왜 필요한지
작업 이유와 범위를 나중에도 추적할 수 있고, PR에서 무엇을 해결했는지 연결하기 쉽다.

### 내가 확인할 질문
- Issue 제목이 작업 내용을 바로 알 수 있게 쓰였는가?
- 체크리스트가 너무 크지 않은가?
- 테스트와 문서 작업도 포함했는가?

### 완료 조건
- Issue에 목표, 작업 목록, 완료 조건이 적혀 있다.
- 작업 브랜치나 PR에서 연결할 Issue 번호를 확인했다.

## 3. Plan Mode로 구현 계획 수립

### 무엇을 하는 단계인지
바로 코드를 고치기 전에 작업 순서와 테스트 대상을 정리한다.

### 왜 필요한지
작업을 작게 나누면 중간에 잘못된 방향으로 크게 진행하는 일을 줄일 수 있다.

### 내가 확인할 질문
- 어떤 파일을 먼저 읽어야 하는가?
- 가장 작은 테스트 대상은 무엇인가?
- 구현 전에 결정해야 할 위험한 선택이 있는가?

### 완료 조건
- 작업 순서가 정리되어 있다.
- 첫 번째 테스트 대상이 정해져 있다.

## 4. 작은 기능 단위로 구현

### 무엇을 하는 단계인지
한 번에 큰 기능을 만들지 않고, 확인 가능한 작은 기능부터 구현한다.

### 왜 필요한지
문제가 생겼을 때 원인을 찾기 쉽고, 테스트와 리뷰도 쉬워진다.

### 내가 확인할 질문
- 이 변경이 하나의 목적만 가지고 있는가?
- 요청하지 않은 기능을 같이 넣고 있지 않은가?
- 기존 구조와 이름 규칙을 따르고 있는가?

### 완료 조건
- 변경 범위가 작고 설명 가능하다.
- 관련 없는 파일을 수정하지 않았다.

## 5. TDD 적용

### 무엇을 하는 단계인지
기능 구현 전에 실패하는 테스트를 먼저 작성하고, 그 테스트를 통과시키는 방식으로 구현한다.

### 왜 필요한지
테스트가 실제로 새 요구사항을 잡아내는지 확인할 수 있다.

### 내가 확인할 질문
- 이 테스트는 구현 전 실패하는가?
- 테스트가 사용자 입장에서 보이는 결과를 확인하는가?
- API 요청은 필요한 만큼만 mock 처리했는가?

### 완료 조건
- 실패 테스트를 먼저 실행했다.
- 최소 구현 후 같은 테스트가 통과한다.

## 6. 테스트 실행

### 무엇을 하는 단계인지
작성한 테스트와 관련 테스트를 실행해 기능이 의도대로 동작하는지 확인한다.

### 왜 필요한지
코드가 눈으로 보기에는 맞아 보여도 실제 동작이 다를 수 있다.

### 내가 확인할 질문
- 집중 테스트가 통과하는가?
- 실패 흐름 테스트도 있는가?
- 테스트 결과를 기록할 수 있는가?

### 완료 조건
- 관련 테스트가 통과했다.
- 실패한 테스트가 있다면 원인과 다음 조치가 정리되어 있다.

## 7. 빌드 확인

### 무엇을 하는 단계인지
프로덕션 빌드가 가능한지 확인한다.

### 왜 필요한지
테스트는 통과해도 빌드 설정, import, 문법 문제로 실제 배포 빌드가 실패할 수 있다.

### 내가 확인할 질문
- `npm.cmd run build`가 성공하는가?
- 경고나 오류가 이번 변경과 관련 있는가?
- 빌드 실패가 환경 문제인지 코드 문제인지 구분했는가?

### 완료 조건
- 빌드가 성공했다.
- 실패했다면 실패 원인과 재현 명령을 기록했다.

## 8. code-validation-agent로 검토

### 무엇을 하는 단계인지
변경된 파일, diff, 테스트 결과, 예외 처리, 문서 반영 여부를 종합 점검한다.

### 왜 필요한지
구현자가 놓친 문제를 검토 단계에서 발견할 수 있다.

### 내가 확인할 질문
- `git diff`를 기준으로 실제 변경을 확인했는가?
- `vertical-slice-validator` 기준으로 수직 슬라이스가 검증되었는가?
- 문제를 중요도 순으로 정리했는가?

### 완료 조건
- 검토 결과가 작성되어 있다.
- 수정이 필요한 항목과 수정 방향이 분리되어 있다.

## 9. README 및 문서 업데이트

### 무엇을 하는 단계인지
구현한 기능, 구조, 데이터 흐름, 실행 방법을 문서에 반영한다.

### 왜 필요한지
나중에 프로젝트를 다시 볼 때 기능이 어떻게 동작하는지 빠르게 이해할 수 있다.

### 내가 확인할 질문
- README가 현재 기능을 정확히 설명하는가?
- Mermaid 다이어그램이 실제 구조와 맞는가?
- 기존 문서를 불필요하게 지우지 않았는가?

### 완료 조건
- 필요한 문서가 업데이트되었다.
- 문서 내용이 코드와 어긋나지 않는다.

## 10. git diff 확인

### 무엇을 하는 단계인지
커밋 전에 전체 변경 내용을 마지막으로 확인한다.

### 왜 필요한지
실수로 수정한 파일, 디버깅 코드, 불필요한 변경을 커밋하지 않기 위해 필요하다.

### 내가 확인할 질문
- 수정한 파일 목록이 예상과 일치하는가?
- 민감한 정보가 포함되어 있지 않은가?
- 코드와 문서 변경이 하나의 작업으로 묶이는가?

### 완료 조건
- `git status --short`와 `git diff`를 확인했다.
- 커밋에 포함할 변경만 남아 있다.

## 11. commit

### 무엇을 하는 단계인지
완료한 작업을 하나의 의미 있는 단위로 저장한다.

### 왜 필요한지
작업 이력을 남기고, 문제가 생겼을 때 변경 단위를 추적할 수 있다.

### 내가 확인할 질문
- 커밋 메시지가 `feat`, `fix`, `style`, `refactor`, `docs`, `chore` 중 하나로 시작하는가?
- 한 커밋에 너무 많은 주제가 섞이지 않았는가?
- 테스트 결과를 커밋 전에 확인했는가?

### 완료 조건
- 커밋이 생성되었다.
- 커밋 메시지가 작업 내용을 설명한다.

## 12. push

### 무엇을 하는 단계인지
로컬 커밋을 원격 저장소에 올린다.

### 왜 필요한지
PR을 만들고 다른 사람이 변경 내용을 확인할 수 있게 한다.

### 내가 확인할 질문
- 올릴 브랜치가 맞는가?
- 원격에 올라가면 안 되는 파일이 포함되지 않았는가?
- push 전에 마지막 테스트 결과를 알고 있는가?

### 완료 조건
- 원격 브랜치에 커밋이 올라갔다.
- GitHub에서 브랜치를 확인할 수 있다.

## 13. PR 작성

### 무엇을 하는 단계인지
변경 내용을 설명하고 리뷰를 요청하는 Pull Request를 만든다.

### 왜 필요한지
작업 의도, 테스트 결과, 확인해야 할 점을 한곳에 모아 리뷰할 수 있다.

### 내가 확인할 질문
- PR 설명에 무엇을 바꿨는지 적었는가?
- 테스트 실행 결과를 적었는가?
- 수동 확인 방법과 남은 위험을 적었는가?

### 완료 조건
- PR이 생성되었다.
- 관련 Issue가 연결되어 있다.
- 리뷰어가 변경 내용과 확인 방법을 이해할 수 있다.
