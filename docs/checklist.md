# 1주차 React 프로토타입 작업 체크리스트

## 1. 목적

이 문서는 `docs/plan.md`의 1주차 React 프로토타입 범위를 실제 구현 가능한 작업 단위로 분해한 체크리스트입니다.

1주차 프로토타입은 완성된 서비스가 아니라, 사용자가 관심 직무를 입력했을 때 샘플 채용공고 데이터를 기반으로 요구역량 요약과 학습/프로젝트 추천을 확인할 수 있는 화면 흐름을 검증하는 것을 목표로 합니다.

MVP는 사용자가 핵심 가치를 경험할 수 있는 최소 제품이고, 프로토타입은 그 MVP를 만들기 전에 화면과 흐름을 빠르게 검증하는 실험물입니다. 따라서 1주차에는 React 내부 mock data와 rule 기반 로직으로 핵심 흐름만 구현합니다.

## 2. 1주차 구현 범위

### 포함

- [ ] React 기반 직무 입력 UI를 구현한다.
- [ ] 샘플 직무 선택 버튼을 구현한다.
- [ ] 직무별 mock job data를 준비한다.
- [ ] 직무별 샘플 공고 조회 흐름을 구현한다.
- [ ] 분석 근거 카드를 표시한다.
- [ ] 요구역량 요약 카드를 표시한다.
- [ ] 추천 학습 키워드 카드를 표시한다.
- [ ] 추천 프로젝트 카드를 표시한다.
- [ ] Verifier 검토 문구를 표시한다.
- [ ] 초기, 입력 중, 분석 중, 분석 완료, 지원하지 않는 직무, 에러 상태를 처리한다.

### 제외

- [ ] Express 서버는 구현하지 않는다.
- [ ] 실제 LLM API는 호출하지 않는다.
- [ ] 실시간 채용공고 크롤링은 구현하지 않는다.
- [ ] DB 저장은 구현하지 않는다.
- [ ] 로그인은 구현하지 않는다.
- [ ] 사용자 현재 역량 기반 Gap 분석은 구현하지 않는다.

## 3. 구현 규칙

### 3.1 Mock Job Data 구조

직무 단위로 조회 가능한 구조를 사용합니다.

```js
{
  id: 'frontend',
  label: '프론트엔드 개발자',
  aliases: ['frontend', '프론트엔드', '프론트엔드 개발자'],
  jobs: [
    {
      company: '샘플 기업',
      title: '프론트엔드 개발자',
      techStacks: ['React', 'TypeScript', 'REST API'],
      requirements: ['컴포넌트 설계', 'API 연동 경험'],
      preferred: ['협업 경험', '테스트 코드 경험'],
      tasks: ['웹 화면 개발', '사용자 인터페이스 개선'],
      projectHints: ['채용공고 검색 결과를 카드로 보여주는 React 대시보드']
    }
  ]
}
```

### 3.2 직무별 Mock Data 조회 방식

- 사용자 입력값은 소문자 변환과 공백 제거를 기준으로 정규화한다.
- 정규화된 입력값이 `label` 또는 `aliases`와 일치하면 해당 직무 데이터를 반환한다.
- 일치하는 직무가 없으면 “지원하지 않는 직무” 상태를 반환한다.

### 3.3 기술 및 키워드 빈도 집계 방식

- `techStacks`, `requirements`, `preferred`, `tasks` 배열을 순회한다.
- 같은 문자열은 1개 키워드로 보고 등장 횟수를 센다.
- 기술 스택은 빈도순으로 정렬한다.
- 동일 빈도일 경우 mock data에 먼저 등장한 순서를 유지한다.
- 화면에는 상위 5개 키워드와 분석한 공고 수를 표시한다.

### 3.4 학습 우선순위 생성 규칙

- 기술 스택 빈도가 높은 항목을 우선한다.
- `requirements`에 포함된 항목은 `preferred`에만 포함된 항목보다 우선한다.
- 1주차 프로토타입에서는 상위 3개 학습 키워드를 생성한다.

### 3.5 프로젝트 추천 생성 방식

- mock data의 `projectHints`가 있으면 우선 사용한다.
- `projectHints`가 부족하면 상위 기술 스택 2개 이상과 주요 업무 키워드 1개 이상을 조합한다.
- 추천 프로젝트는 2개만 표시한다.
- 추천 결과가 없으면 대체 문구를 표시한다.

### 3.6 Verifier 검증 조건

- 입력 직무와 선택된 mock data 직무가 일치하는지 확인한다.
- 분석한 공고 수가 1개 이상인지 확인한다.
- 추천 학습 키워드가 실제 집계된 기술 또는 요구사항에서 나온 것인지 확인한다.
- 추천 프로젝트가 최소 1개 이상의 집계 키워드와 연결되는지 확인한다.
- 조건을 만족하면 “샘플 공고 기반으로 생성된 결과입니다” 문구를 표시한다.

## 4. Feature별 작업 체크리스트

### Feature 1. 문서 기준 확정

- [ ] `plan.md`의 1주차 프로토타입 범위를 확인한다.
- [ ] 1주차 제외 범위를 checklist 상단에 명시한다.
- [ ] MVP와 프로토타입의 차이를 checklist 요약에 반영한다.

### Feature 2. Mock Data

- [ ] 직무별 mock data 구조를 정의한다.
- [ ] 프론트엔드 개발자 샘플 공고 데이터를 3~5개 작성한다.
- [ ] 각 공고에 기술 스택, 자격요건, 우대사항, 업무 키워드, 프로젝트 힌트를 포함한다.
- [ ] 지원하지 않는 직무 입력 시 사용할 empty state 데이터를 정의한다.

### Feature 3. 직무 입력 UI

- [ ] 직무명 입력창을 만든다.
- [ ] 예시 직무 버튼을 만든다.
- [ ] 분석 시작 버튼을 만든다.
- [ ] 입력값이 비어 있을 때 분석을 막는다.

### Feature 4. 직무별 데이터 조회

- [ ] 사용자 입력값을 정규화하는 규칙을 구현한다.
- [ ] `label`과 `aliases` 기준으로 mock data를 찾는다.
- [ ] 일치하는 직무가 없을 때 empty state를 반환한다.

### Feature 5. 요구역량 분석 로직

- [ ] 분석한 샘플 공고 수를 계산한다.
- [ ] 기술 스택 빈도를 집계한다.
- [ ] 자격요건 키워드를 집계한다.
- [ ] 우대사항 키워드를 집계한다.
- [ ] 주요 업무 키워드를 집계한다.
- [ ] 빈도순 상위 키워드를 결과 데이터로 만든다.

### Feature 6. 추천 로직

- [ ] 상위 기술 스택을 기준으로 학습 키워드 3개를 생성한다.
- [ ] 자격요건 키워드를 우대사항 키워드보다 우선한다.
- [ ] 프로젝트 힌트 또는 상위 키워드 조합으로 추천 프로젝트 2개를 생성한다.
- [ ] 추천 결과가 없을 때 대체 문구를 만든다.

### Feature 7. Verifier

- [ ] 입력 직무와 조회된 직무 데이터의 일치 여부를 확인한다.
- [ ] 분석한 공고 수가 1개 이상인지 확인한다.
- [ ] 학습 키워드가 집계 결과에 포함되는지 확인한다.
- [ ] 추천 프로젝트가 집계 키워드와 연결되는지 확인한다.
- [ ] 검증 통과/실패에 따른 안내 문구를 만든다.

### Feature 8. 결과 UI

- [ ] 분석 근거 카드를 만든다.
- [ ] 요구역량 요약 카드를 만든다.
- [ ] 학습 방향 카드를 만든다.
- [ ] 프로젝트 추천 카드를 만든다.
- [ ] Verifier 검토 문구를 표시한다.

### Feature 9. 상태 처리

- [ ] 초기 상태를 정의한다.
- [ ] 입력 중 상태를 정의한다.
- [ ] 분석 중 로딩 상태를 정의한다.
- [ ] 분석 완료 상태를 정의한다.
- [ ] 지원하지 않는 직무 상태를 정의한다.
- [ ] 예상하지 못한 에러 상태를 정의한다.

### Feature 10. 테스트 및 검증

- [ ] “프론트엔드 개발자” 입력 시 결과 카드가 표시되는지 확인한다.
- [ ] 예시 직무 버튼 클릭 시 입력값과 결과가 갱신되는지 확인한다.
- [ ] 지원하지 않는 직무 입력 시 empty state가 표시되는지 확인한다.
- [ ] 분석한 공고 수와 기술 빈도가 mock data와 일치하는지 확인한다.
- [ ] 추천 학습 키워드와 프로젝트가 집계 키워드 기반인지 확인한다.

### Feature 11. 후속 작업 분리

- [ ] Express API 연동을 후속 작업으로 분리한다.
- [ ] LLM API 연동을 후속 작업으로 분리한다.
- [ ] 실시간 채용공고 수집을 후속 작업으로 분리한다.
- [ ] 사용자 역량 입력과 Gap 분석을 2차 MVP 작업으로 분리한다.

## 5. 검증 시나리오

### 시나리오 1. 지원하는 직무 입력

- [ ] 사용자가 “프론트엔드 개발자”를 입력한다.
- [ ] 분석 시작 버튼을 누른다.
- [ ] 분석한 샘플 공고 수가 표시된다.
- [ ] 기술 스택 빈도 상위 5개가 표시된다.
- [ ] 학습 키워드 3개가 표시된다.
- [ ] 프로젝트 추천 2개가 표시된다.
- [ ] Verifier 검토 문구가 표시된다.

### 시나리오 2. 예시 직무 버튼 클릭

- [ ] 사용자가 예시 직무 버튼을 클릭한다.
- [ ] 입력창에 예시 직무명이 반영된다.
- [ ] 분석 시작 후 결과 카드가 표시된다.
- [ ] 이전 결과가 있다면 새 결과로 갱신된다.

### 시나리오 3. 지원하지 않는 직무 입력

- [ ] 사용자가 mock data에 없는 직무를 입력한다.
- [ ] 분석 시작 버튼을 누른다.
- [ ] 지원하지 않는 직무 안내 문구가 표시된다.
- [ ] 결과 카드 대신 empty state가 표시된다.

### 시나리오 4. 빈 입력값

- [ ] 사용자가 직무명을 입력하지 않는다.
- [ ] 분석 시작 버튼을 누른다.
- [ ] 분석 요청이 실행되지 않는다.
- [ ] 직무명을 입력하라는 안내 문구가 표시된다.

### 시나리오 5. 결과 근거 확인

- [ ] 분석한 공고 수가 mock data의 공고 개수와 일치한다.
- [ ] 기술 빈도가 mock data의 `techStacks` 등장 횟수와 일치한다.
- [ ] 학습 키워드가 실제 집계된 기술 또는 요구사항에서 나온다.
- [ ] 추천 프로젝트가 최소 1개 이상의 집계 키워드와 연결된다.

- [ ] 실시간 채용공고 크롤링

- [ ] 여러 직무 동시 비교
- [ ] 사용자 현재 역량 입력

- [ ] 장기 학습 로드맵 자동 생성
