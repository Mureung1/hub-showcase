# CareerSignal 릴리스 검증 체크리스트

이 문서는 분석 버전의 활성화, 배포, 최종 결과물 공개 가능 여부를 판단하는 수용 기준이다. 개발 작업과 담당·일정은 GitHub Issues와 GitHub Projects에서 관리하고, 범위와 순서는 [개발 백로그](backlog.md)에서 관리한다.

## 1. 기반 수직 슬라이스

- [x] 직무 선택에서 준비 로드맵까지 다섯 화면이 연결된다.
- [x] React, Express, Supabase, FastAPI의 독립 실행 경계가 구성된다.
- [x] 샘플 공고가 저장소에 적재되고 Express가 조회한다.
- [x] 네 화면의 데이터 계약이 fixture로 검증된다.
- [x] 합격 전략과 준비 로드맵이 범위와 체크 상태를 공유한다.

## 2. 설계와 계약

- [ ] 데이터 계층, 저장 구조, 그래프, Wiki의 정의가 기준 문서에 있다.
- [ ] 분류체계 발견·승격 절차와 지표 정의가 기준 문서에 있다.
- [ ] 공통 실행 계약이 Pydantic 스키마로 구현된다.
- [ ] 순수 도메인 로직이 저장소와 모델에 의존하지 않는다.
- [ ] 온톨로지 버전에 두 그래프 층의 노드·엣지 유형과 허용 연결이 등록된다.
- [ ] 지표 정책 버전에 최소 표본, 억제 정책, 불확실성 방법이 등록된다.

## 3. 실행 환경

- [ ] 생성 모델의 식별자가 실제 응답으로 확인되고 코드와 문서에 반영된다.
- [ ] 구조화 출력이 스키마를 준수한다.
- [ ] 임베딩 차원이 확인되고 벡터 컬럼 정의에 반영된다.
- [ ] 교차 모델 응답이 확인된다.
- [ ] 저장소 연결과 벡터 확장이 확인된다.
- [ ] 실행별 토큰과 비용 한도의 초기값이 설정된다.
- [ ] 생성 모델 키를 Express가 보유하지 않는다.

## 4. 데이터 준비

- [ ] 기업 공식 채용공고 원문이 직무·기업군·출처 메타데이터와 함께 저장된다.
- [ ] 대상 회사의 공식 채용·기술 자료가 저장된다.
- [ ] 공공·직무 표준의 기준과 용어가 구조화된다.
- [ ] 외부 전문가 자료가 작성자·게시일·허용 용도와 함께 저장된다.
- [ ] 원본 스냅샷의 내용 변경이 데이터베이스에서 차단된다.
- [ ] 접근할 수 없게 된 자료의 스냅샷과 관찰 기록이 보존된다.
- [ ] 평가 세트의 정답과 루브릭을 사람이 확정한다.
- [ ] 청크, 임베딩, 키워드 인덱스가 같은 데이터 버전으로 연결된다.

## 5. 분류체계와 지표

- [ ] 요구 표현이 분류체계와 무관하게 추출되고 근거 위치가 원문과 일치한다.
- [ ] 기지 추출과 잔여 추출이 분리 실행된다.
- [ ] 후보와 기존 차원의 관계가 동의어·상하위·관련·신규로 판정된다.
- [ ] 승격되지 않은 후보가 통계에 포함되지 않는다.
- [ ] 승격 결정이 독립 공고 수, 독립 회사 수, 평가 세트 대조 결과와 함께 기록된다.
- [ ] 분류체계 버전 발행 시 해당 데이터셋의 할당이 전량 재계산된다.
- [ ] 지표 적용 가능성이 정의되고 적용 불가 조합이 계산되지 않는다.
- [ ] 모든 지표 행이 표본 수, 기간, 범위, 불확실성을 함께 저장한다.
- [ ] 표본 상태가 정책 버전의 임계값과 일치한다.
- [ ] 서로 다른 지표 정책 버전의 수치를 비교하지 않는다.

## 6. 에이전트

- [ ] 데이터 수집 에이전트가 자료를 발견·수집·평가해 원본과 출처 평가를 저장한다.
- [ ] 지식 구축 에이전트가 사전 의미 층을 구축한다.
- [ ] 계보 기록 파이프라인이 계보 층과 사후 의미 층을 기록한다.
- [ ] 등록되지 않은 노드·엣지 유형과 허용되지 않은 연결이 폐기된다.
- [ ] Wiki가 생성 조건을 충족한 역량에 대해서만 생성된다.
- [ ] Wiki의 모든 필드가 허용된 계층의 근거를 가진다.
- [ ] 통계 분석 에이전트가 차원을 발견하고 할당한다.
- [ ] 집계 파이프라인이 지표를 결정적으로 계산하고 저장한다.
- [ ] 채용공고 해석 에이전트가 명시 요구, 추론 요구, 회사 맥락 신호를 구분한다.
- [ ] 합격 전략 에이전트가 체크리스트 개념과 버전 인스턴스를 분리해 저장한다.
- [ ] 준비 로드맵 에이전트가 깊이 프로파일을 반영한 학습 전략을 생성한다.
- [ ] 각 에이전트가 입력·출력 스키마를 통과한다.
- [ ] 근거가 부족한 에이전트가 조사 요청을 발행하고 오케스트레이터가 수집을 스케줄링한다.
- [ ] 에이전트가 다른 도메인 에이전트를 직접 호출하지 않는다.
- [ ] 각 실행이 종료 사유를 기록한다.

## 7. 검증

- [ ] 여덟 검사가 모두 구현되고 검사별로 판정이 기록된다.
- [ ] 판정이 일곱 유형 중 하나로 저장된다.
- [ ] 자료 계층과 허용 용도 위반이 자동으로 차단된다.
- [ ] 근거 위치가 원문과 일치하지 않는 주장이 폐기된다.
- [ ] 통계의 분모, 표본, 중복 제거, 재계산이 일치한다.
- [ ] 근거 함의 검사가 모든 공개 후보 주장에 적용된다.
- [ ] 교차 모델 감사가 위험 기반 표본에 적용된다.
- [ ] 편차 없음 주장이 범위 전수 확인을 근거로 가진다.
- [ ] 범위 전수 확인이 없으면 판단 근거 부족을 출력한다.
- [ ] 신뢰도가 주장 유형별 정책과 구성값으로 판정된다.
- [ ] 생성 모델의 자기 보고를 신뢰도로 사용하지 않는다.
- [ ] 수리 반복이 한도 안에서 종료된다.

## 8. 오케스트레이션과 버전

- [ ] 공고 추가·수정·삭제가 해당 직무와 영향 범위의 분석을 재실행한다.
- [ ] 분류체계 버전 발행이 해당 직무의 할당과 통계를 재실행한다.
- [ ] 자료 유형별 변경이 정의된 후속 단계만 재실행한다.
- [ ] 영향받지 않은 분석 결과가 재사용된다.
- [ ] 실행이 데이터·분류체계·모델·프롬프트·검색 정책·지표 정책 버전을 기록한다.
- [ ] 일부 단계가 실패하면 기존 활성 버전을 유지한다.

## 9. 수용 평가와 릴리스 게이트

- [ ] 평가 세트 채점이 활성화 이전에 실행된다.
- [ ] 요구 표현 추출의 정밀도와 재현율이 기준을 충족한다.
- [ ] 차원 할당 정확도가 기준을 충족한다.
- [ ] 근거 정확도와 미지원 주장 비율이 기준을 충족한다.
- [ ] 해석에서 로드맵까지의 식별자 연결이 끊기지 않는다.
- [ ] 수용 기준을 충족하지 않은 버전이 활성화되지 않는다.
- [ ] 전체 검증을 통과한 직무 분석 버전만 원자적으로 활성화된다.
- [ ] 실행 한도에 도달해 조사를 마치지 못한 결과가 공개되지 않는다.

## 10. 저장 결과 조회와 체크 상태

- [ ] 화면 조회가 에이전트를 호출하지 않고 활성 분석 결과를 반환한다.
- [ ] 범위 선택이 네 분석 화면에 같은 범위로 적용된다.
- [ ] 체크 변경이 준비 현황 카드에 즉시 반영된다.
- [ ] 체크 변경이 포트폴리오·자소서·면접 전략을 변경하지 않는다.
- [ ] 체크 적용이 프로젝트 로드맵과 학습 전략만 재조합한다.
- [ ] 체크 상태가 체크리스트 개념 식별자에 연결되어 버전 변경 후에도 유지된다.
- [ ] 로딩, 빈 결과, 미지원 직무, 서버 오류 상태가 일관된 화면과 응답을 제공한다.

## 11. 계측

- [ ] 검색 후보가 전략별 점수와 함께 기록된다.
- [ ] 검색 결과의 사용 목적이 일곱 유형으로 기록된다.
- [ ] 근거가 연결된 주장의 비율이 보고된다.
- [ ] 인용한 근거가 주장을 지지하는 비율이 보고된다.
- [ ] 검색 전략별 기여도가 비교 가능한 형태로 보고된다.
- [ ] 표본 수렴 관찰이 기록된다.

## 12. 보안과 비용

- [ ] API 키가 환경변수와 배포 환경 비밀값으로 관리된다.
- [ ] API 키와 수집 원문이 클라이언트 번들, 로그, Git 이력에 노출되지 않는다.
- [ ] 검색, 재시도, 토큰 사용량에 실행별 한도가 적용된다.
- [ ] 영상 분석 모델에 공개 자료만 입력된다.
- [ ] 수집 대상의 이용 조건과 robots 정책이 기록된다.
- [ ] 구성요소가 허용 범위 밖의 테이블에 쓰지 못한다.

## 13. 배포와 클로즈드 베타

- [ ] React, Express, FastAPI, Supabase가 배포 환경에서 연결된다.
- [ ] API 주소가 환경별 설정으로 분리된다.
- [ ] 배포 환경에서 다섯 화면 흐름과 범위 변경이 검증된다.
- [ ] 배포 환경에서 체크 상태와 재조합이 검증된다.
- [ ] 장애 시 활성 분석 버전이 유지되고 안전한 오류가 표시된다.
- [ ] 베타 피드백 Issue 템플릿과 분류 기준이 준비된다.
- [ ] 배포 URL과 데모 시나리오가 문서에 연결된다.

## 14. 확장과 최종 결과물

- [ ] 베타에서 재현된 P0 문제와 발표를 막는 P1 문제가 수정·회귀 검증된다.
- [ ] 허용된 출처의 공고 변경이 데이터 버전과 재실행 범위에 반영된다.
- [ ] 추가 직무가 파이프라인과 화면 계약을 재사용하고 분류체계를 데이터로 추가해 분석된다.
- [ ] 사용자 공고 입력이 입력 검증, 동일 분석 캐시, 통계 분리 원칙을 지킨다.
- [ ] 관측 화면이 수작업 데이터 없이 운영 테이블에서 파생된다.
- [ ] 데모가 저장 결과 조회, 범위 변경, 체크 상태 조합, 근거 경로 추적을 재현한다.
- [ ] 발표 자료가 문제, 자료 정책, 여섯 에이전트, 분류체계 발견, 검증, 계측 결과를 설명한다.
- [ ] GitHub Projects의 최종 범위 Issue가 완료 조건과 검증 근거를 가진다.
