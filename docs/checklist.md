# CareerSignal 릴리스 검증 체크리스트

이 문서는 3주차 MVP를 클로즈드 베타로 전환하고 4주차 최종 결과물을 공개할 수 있는지 판단하는 수용 기준이다. 개발 작업과 담당·일정은 GitHub Issues와 GitHub Projects에서 관리하고, 프로젝트 범위와 우선순위는 [개발 백로그](backlog.md)에서 관리한다.

## 1. 기반 수직 슬라이스

- [x] 직무 선택→통계 분석→채용공고 해설→합격 전략→준비 로드맵의 5화면이 연결된다.
- [x] React·Express·Supabase·FastAPI의 독립 실행 경계가 구성된다.
- [x] 샘플 공고가 Supabase에 적재되고 Express가 조회한다.
- [x] 통계 분석·채용공고 해설·합격 전략·준비 로드맵의 화면 데이터 계약이 fixture로 검증된다.
- [x] 합격 전략과 준비 로드맵이 범위와 체크 상태를 공유한다.

## 2. 데이터 준비

- [ ] 기업 공식 채용공고 원문 18~30건이 직무·기업군·출처 메타데이터와 함께 저장된다.
- [ ] 대상 회사 5~8곳의 공식 채용·기술 자료가 저장된다.
- [ ] NCS·직무사전의 직무 기준과 용어가 구조화된다.
- [ ] 외부 블로그·YouTube 전략 자료가 작성자·게시일·신뢰도·허용 용도와 함께 저장된다.
- [ ] 실제 공고별 기대 추출 결과와 해설 루브릭을 사람이 확정한다.
- [ ] Raw 원문, Wiki, 청크, 임베딩, 그래프가 같은 데이터 버전과 근거 식별자로 연결된다.

## 3. 에이전트

- [ ] 데이터·지식 에이전트가 자료를 발견·수집·평가하고 Wiki·벡터·그래프를 구축한다.
- [ ] 통계 분석 에이전트가 직무별 요구사항과 전체·기업군·기간 통계를 생성한다.
- [ ] 채용공고 해설 에이전트가 직무 기준선과 기업군·개별 공고 편차를 근거와 함께 생성한다.
- [ ] 합격 전략 에이전트가 체크리스트와 포트폴리오·자소서·면접 전략을 생성한다.
- [ ] 준비 로드맵 에이전트가 기본 프로젝트 로드맵·학습 전략·선수 관계를 생성한다.
- [ ] 각 에이전트가 입력·출력 Pydantic 스키마를 통과한다.
- [ ] 근거가 부족한 에이전트가 제한된 횟수 안에서 데이터·지식 에이전트에 조사를 요청한다.
- [ ] 단계별 Verifier가 수치·근거·범위·식별자 연결을 검사한다.

## 4. 오케스트레이션과 버전

- [ ] 공고 추가·수정·삭제가 해당 직무와 영향 기업군·공고의 분석을 재실행한다.
- [ ] 공식 자료·표준 자료·외부 전략 자료 변경이 정의된 후속 단계만 재실행한다.
- [ ] 다른 직무의 영향받지 않은 분석 결과는 재사용된다.
- [ ] 에이전트 실행이 데이터·모델·프롬프트·검색 정책 버전을 기록한다.
- [ ] 일부 단계가 실패하면 기존 활성 분석 버전을 유지한다.
- [ ] 전체 검증을 통과한 직무 분석 버전만 원자적으로 활성화된다.

## 5. 저장 결과 조회와 체크 상태

- [ ] 일반 화면 조회가 FastAPI 에이전트를 호출하지 않고 활성 분석 결과를 반환한다.
- [ ] 직무·기업군·개별 공고 선택이 네 분석 화면에 같은 범위로 적용된다.
- [ ] 통계 결과가 채용공고 해설·합격 전략·준비 로드맵 에이전트의 공유 근거로 사용된다.
- [ ] 체크 변경이 합격 전략 페이지의 준비 현황 카드에 즉시 반영된다.
- [ ] 체크 변경이 포트폴리오·자소서·면접 전략을 변경하지 않는다.
- [ ] 체크 적용이 프로젝트 로드맵과 학습 전략만 규칙으로 재조합한다.
- [ ] 체크 상태가 직무·기업군·개별 공고 범위별로 구분된다.
- [ ] 로딩·빈 결과·미지원 직무·서버 오류 상태가 일관된 화면과 응답을 제공한다.

## 6. 품질과 평가

- [ ] 추출 결과가 평가 세트의 요구사항·필수/우대·근거 문장 기준을 충족한다.
- [ ] 통계의 분모·표본 수·비율·기간 비교가 원문 집계와 일치한다.
- [ ] 공고 해설의 주장마다 통계·원문·공식 자료 근거가 연결된다.
- [ ] 외부 블로그·영상이 기업의 직접 요구사항이나 통계 근거로 사용되지 않는다.
- [ ] 공고 해설→체크리스트→합격 전략→준비 로드맵의 항목 식별자가 끊기지 않는다.
- [ ] Hybrid RAG와 GraphRAG 비교 평가에서 그래프 사용 구간의 효과와 오류가 기록된다.
- [ ] 모델·프롬프트 변경 뒤 평가 세트 회귀 테스트가 통과한다.
- [ ] 사람 표본 검토에서 치명적인 미지원 주장과 출처 오인이 없다.

## 7. 보안과 비용

- [ ] OpenAI·Gemini·Supabase 키가 환경변수와 배포 환경 비밀값으로 관리된다.
- [ ] API 키와 수집 원문이 클라이언트 번들·로그·Git 이력에 노출되지 않는다.
- [ ] 웹 검색·재시도·토큰 사용량에 실행별 한도가 적용된다.
- [ ] Gemini 무료 등급에는 공개 YouTube 자료만 입력된다.
- [ ] 수집 대상의 이용 조건·robots 정책·출처 표기가 기록된다.

## 8. 배포와 클로즈드 베타

- [ ] React·Express·FastAPI·Supabase가 배포 환경에서 연결된다.
- [ ] 프론트의 API 주소와 서버의 FastAPI 주소가 환경별 설정으로 분리된다.
- [ ] 배포 환경에서 5화면 핵심 흐름과 범위 변경을 검증한다.
- [ ] 배포 환경에서 체크 상태와 프로젝트·학습 로드맵 재조합을 검증한다.
- [ ] 장애·실패 시 활성 분석 버전이 유지되고 사용자에게 안전한 오류가 표시된다.
- [ ] 베타 피드백을 GitHub Issue로 등록할 템플릿과 분류 기준이 준비된다.
- [ ] 배포 URL과 데모 시나리오가 팀 문서에 연결된다.

## 9. 4주차 최종 결과물

- [ ] 베타에서 재현된 P0 문제와 발표를 막는 P1 문제가 수정·회귀 검증된다.
- [ ] 허용된 기업 공식 출처의 공고 추가·수정·삭제가 데이터 버전과 재실행 범위에 반영된다.
- [ ] 백엔드 외 추가 직무가 같은 데이터·에이전트·화면 계약으로 분석되고 다섯 화면에서 선택된다.
- [ ] 비로그인 사용자 공고 입력이 입력 검증·동일 분석 캐시·서비스 통계 분리 원칙을 지킨다.
- [ ] 데모가 저장 결과 조회, 범위 변경, 체크 상태 조합, 사용자 공고 입력의 핵심 흐름을 재현한다.
- [ ] 발표 자료가 문제, 자료 신뢰도, 다섯 에이전트, 분석 오케스트레이터, GraphRAG, 평가 결과와 확장성을 설명한다.
- [ ] GitHub Projects의 최종 범위 Issue가 완료 조건과 검증 근거를 가진다.
