# 개발 체크리스트

## 0. 프로젝트 기반 정리

- [ ] MVP에서 우선 지원할 첫 번째 게임 프로젝트를 1개 정한다.
- [ ] 프로젝트 식별자 규칙을 정하고 모든 요청에 사용할 `Project_ID` 형식을 정의한다.
- [ ] 프로젝트 메타데이터 항목을 정의한다: 프로젝트명, 장르, 사용 협업 도구, 사용 엔진, 우선 룰셋.
- [ ] 문서 타입을 정의한다: 회의록, 설정집, 시나리오, 밸런스 테이블, 태스크, 버그 리포트.
- [ ] 팀장 승인 상태를 정의한다: 대기, 승인, 보류, 수정 요청.
- [ ] 자동 실행 가능한 작업과 승인 후 실행해야 하는 작업을 구분한다.
- [ ] README와 plan 문서 기준으로 1단계, 2단계, 3단계 범위를 다시 확인한다.

## 1. 1단계: 노코드 프로토타입

- [ ] Notion에 회의록 DB 구조를 만든다.
- [ ] Notion에 분석 리포트 DB 구조를 만든다.
- [ ] Notion에 태스크 후보 DB 구조를 만든다.
- [ ] Make 또는 Zapier에서 Notion 회의록 생성 이벤트를 트리거로 연결한다.
- [ ] 회의록 본문을 LLM으로 전달하는 자동화 흐름을 만든다.
- [ ] LLM 응답 형식을 요약, 설정 충돌 후보, 하위 태스크 후보로 나눈다.
- [ ] 분석 결과를 Notion 분석 리포트 DB에 저장한다.
- [ ] 하위 태스크 후보를 Notion 태스크 후보 DB에 저장한다.
- [ ] 팀장이 승인 또는 보류할 수 있는 필드를 Notion에 추가한다.
- [ ] 샘플 회의록 1개로 전체 자동화 흐름을 검증한다.

## 2. 2단계: 커스텀 서버 및 멀티 테넌시

- [ ] Python FastAPI 기반 서버 프로젝트 구조를 만든다.
- [ ] 환경 변수 관리 방식을 정의한다: LLM API 키, Notion 토큰, GitHub 토큰, Slack/Discord Webhook.
- [ ] `Project_ID`를 필수로 받는 공통 요청 모델을 정의한다.
- [ ] 문서 업로드 API를 설계한다.
- [ ] 분석 요청 API를 설계한다.
- [ ] 승인, 보류, 수정 요청 API를 설계한다.
- [ ] 프로젝트 메타데이터 등록 API를 설계한다.
- [ ] Vector DB로 Chroma 또는 Pinecone 중 하나를 선택해 연결한다.
- [ ] 프로젝트별 Namespace 또는 Collection 생성 로직을 만든다.
- [ ] 문서 임베딩 저장 시 `Project_ID`, 문서 타입, 작성일, 버전, 출처 메타데이터를 함께 저장한다.
- [ ] 검색 요청에서 항상 현재 `Project_ID`에 속한 문서만 조회되도록 제한한다.
- [ ] 서로 다른 두 프로젝트의 샘플 문서를 넣고 검색 결과가 섞이지 않는지 테스트한다.

## 3. 핵심 에이전트 구현

### 3.1 기획 검증 에이전트

- [ ] 설정집 문서를 검색해 신규 회의록 또는 아이디어와 비교하는 흐름을 만든다.
- [ ] 캐릭터 설정 충돌을 탐지하는 프롬프트를 작성한다.
- [ ] 세계관 규칙 충돌을 탐지하는 프롬프트를 작성한다.
- [ ] 지역, 사건, 아이템, 퀘스트 설정 충돌을 탐지하는 프롬프트를 작성한다.
- [ ] 충돌 결과에 기존 설정, 신규 설정, 충돌 이유, 권장 대응을 포함한다.
- [ ] 충돌 결과를 팀장 승인 화면 또는 리포트로 전달할 수 있는 구조로 정리한다.
- [ ] 승인된 설정 변경을 Notion 문서 갱신 요청으로 변환한다.

### 3.2 시나리오 기반 리소스 파서

- [ ] 시나리오 텍스트를 장면, 대사, 액션 단위로 나누는 파싱 흐름을 만든다.
- [ ] 필요한 NPC 목록을 추출한다.
- [ ] 필요한 대사 파일 목록을 추출한다.
- [ ] 필요한 이펙트와 사운드 목록을 추출한다.
- [ ] 필요한 UI와 컷신 리소스 목록을 추출한다.
- [ ] 추출된 리소스를 태스크 후보로 변환한다.
- [ ] 태스크 후보에 리소스 종류, 등장 위치, 우선순위, 담당 파트 후보를 포함한다.
- [ ] 팀장 승인 후 Notion 태스크 DB에 등록할 요청 형태로 변환한다.

### 3.3 리스크 및 병목 예측 에이전트

- [ ] Notion 칸반 상태 이동 데이터를 수집하는 흐름을 만든다.
- [ ] GitHub 커밋 빈도 데이터를 수집하는 흐름을 만든다.
- [ ] GitHub PR 대기 시간을 수집하는 흐름을 만든다.
- [ ] GitHub Issue 상태를 수집하는 흐름을 만든다.
- [ ] 마감 임박 태스크를 탐지한다.
- [ ] 착수 지연 태스크를 탐지한다.
- [ ] 후속 작업을 막는 태스크를 탐지한다.
- [ ] 리스크 리포트에 원인, 영향받는 작업, 권장 대응을 포함한다.

### 3.4 페르소나 기반 자동 리마인더

- [ ] 리마인더 대상 조건을 정의한다: 마감 임박, 미착수, 장기 대기, 블로커 발생.
- [ ] 담당자, 마감일, 현재 상태, 관련 후속 작업을 가져오는 흐름을 만든다.
- [ ] AI 부팀장 비서 페르소나의 메시지 톤 가이드를 작성한다.
- [ ] Slack 메시지 템플릿을 작성한다.
- [ ] Discord 메시지 템플릿을 작성한다.
- [ ] 자동 발송 전 팀장 승인 단계를 연결한다.
- [ ] 승인된 리마인더만 실제 발송되도록 제한한다.

## 4. 커넥터 구현

### 4.1 NotionConnector

- [ ] Notion 페이지 조회 기능을 만든다.
- [ ] Notion DB 조회 기능을 만든다.
- [ ] Notion 분석 리포트 생성 기능을 만든다.
- [ ] Notion 태스크 생성 기능을 만든다.
- [ ] Notion 태스크 상태 갱신 기능을 만든다.
- [ ] Notion 문서 갱신 요청을 생성하는 기능을 만든다.

### 4.2 GitHubConnector

- [ ] GitHub Issue 생성 기능을 만든다.
- [ ] GitHub Issue 상태 조회 기능을 만든다.
- [ ] GitHub PR 목록과 대기 시간 조회 기능을 만든다.
- [ ] GitHub 커밋 활동 조회 기능을 만든다.
- [ ] Unity 데이터 변경안을 커밋 대상으로 정리하는 기능을 만든다.
- [ ] 자동 커밋과 푸시는 승인된 항목에만 허용되도록 제한한다.

### 4.3 SlackConnector 또는 DiscordConnector

- [ ] Slack Webhook 메시지 발송 기능을 만든다.
- [ ] Discord Webhook 메시지 발송 기능을 만든다.
- [ ] 승인 요청 메시지 형식을 만든다.
- [ ] 리마인더 메시지 형식을 만든다.
- [ ] 발송 실패 시 재시도 또는 실패 리포트 생성 방식을 정한다.

### 4.4 UnityConnector

- [ ] Unity에서 서버로 버그 리포트를 보낼 API 형식을 정의한다.
- [ ] Unity 데이터 동기화 대상 파일 형식을 정의한다: JSON, CSV, ScriptableObject.
- [ ] Unity 데이터 변경안을 생성하는 기능을 만든다.
- [ ] 변경 전후 diff를 생성하는 기능을 만든다.
- [ ] Unity 인에디터 버그 리포트를 수신하는 기능을 만든다.

## 5. 3단계: Unity 연동

- [ ] Notion 밸런스 테이블과 Unity 데이터 파일의 필드 매핑 규칙을 정의한다.
- [ ] Notion 값 변경을 감지하는 흐름을 만든다.
- [ ] 변경된 Notion 값을 Unity 데이터 변경안으로 변환한다.
- [ ] JSON 데이터 파일 동기화 프로토타입을 만든다.
- [ ] CSV 데이터 파일 동기화 프로토타입을 만든다.
- [ ] ScriptableObject 동기화 방식은 Unity 쪽 구현 계획으로 분리한다.
- [ ] Unity 에디터에 AI 제보 버튼을 추가한다.
- [ ] 버튼 클릭 시 콘솔 에러 로그를 수집한다.
- [ ] 버튼 클릭 시 선택된 오브젝트의 인스펙터 값을 수집한다.
- [ ] 버튼 클릭 시 화면 스크린샷을 수집한다.
- [ ] 수집 데이터를 서버로 전송한다.
- [ ] 서버에서 Notion 버그 DB 등록 요청을 만든다.
- [ ] 서버에서 GitHub Issue 생성 요청을 만든다.
- [ ] 기존 이슈와 중복 가능성을 비교하는 흐름을 만든다.

## 6. 팀장 컨트롤 타워

- [ ] 설정 충돌 결과를 확인하는 화면 또는 리포트 구조를 만든다.
- [ ] 리소스 태스크 후보를 확인하는 화면 또는 리포트 구조를 만든다.
- [ ] 일정 리스크 리포트를 확인하는 화면 또는 리포트 구조를 만든다.
- [ ] 외부 도구 반영 전 변경안을 확인하는 화면 또는 리포트 구조를 만든다.
- [ ] 승인, 보류, 수정 요청 액션을 정의한다.
- [ ] 승인된 항목만 커넥터 실행 큐로 전달한다.
- [ ] 보류된 항목은 외부 도구에 반영하지 않는다.
- [ ] 수정 요청 항목은 재분석 또는 수동 수정 대상으로 되돌린다.
- [ ] 승인 이력을 저장한다: 승인자, 승인 시각, 대상 작업, 실행 결과.

## 7. 검증 및 완료 기준

- [ ] README의 6개 핵심 기능이 모두 작업 항목으로 포함되어 있는지 확인한다.
- [ ] `Project_ID`가 없는 분석 요청은 처리되지 않도록 테스트한다.
- [ ] 서로 다른 프로젝트의 설정집이 검색 결과에 섞이지 않는지 테스트한다.
- [ ] 회의록 1개를 입력하면 요약, 충돌 후보, 태스크 후보가 생성되는지 테스트한다.
- [ ] 시나리오 텍스트에서 NPC, 대사, 이펙트, 사운드 리소스가 추출되는지 테스트한다.
- [ ] Notion 태스크 지연 데이터를 기반으로 리스크 후보가 생성되는지 테스트한다.
- [ ] GitHub PR 대기 시간이 리스크 리포트에 반영되는지 테스트한다.
- [ ] 리마인더 메시지가 팀장 승인 전에는 발송되지 않는지 테스트한다.
- [ ] 승인된 Notion 태스크 생성 요청만 실행되는지 테스트한다.
- [ ] Unity 버그 리포트가 Notion 버그 DB와 GitHub Issue 요청으로 변환되는지 테스트한다.
- [ ] JSON/YAML 룰셋을 변경했을 때 프로젝트별 검증 기준이 바뀌는지 테스트한다.
- [ ] 1단계 노코드 프로토타입 완료 기준을 충족하는지 확인한다.
- [ ] 2단계 커스텀 서버 완료 기준을 충족하는지 확인한다.
- [ ] 3단계 Unity 연동 완료 기준을 충족하는지 확인한다.
