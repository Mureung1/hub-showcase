TeamFlow 작업 기록

TeamFlow를 만들 때
이 순서로 작업했습니다.

AI에게 계획부터 검증까지 한꺼번에 맡기지 않았습니다. 무엇을 만들지는 사람이 먼저 정하고, AI는 구조 파악과 구현을 도왔으며, 결과는 다른 역할로 다시 확인했습니다.

8단계 전체 흐름

사람이 계획을 확인하기 전에는 코드를 수정하지 않습니다. 중간에 막히면 무조건 코드부터 고치지 않고 원인이 있는 단계로 돌아갑니다.

  • 사람 결정
  • AI 수행
  • 도구·Skill
  1. 01

    요구사항·제외 범위·완료 기준 확정

    문제, 사용자, 포함·제외 범위와 직접 확인할 완료 기준을 정합니다.

    사람 결정
  2. 02

    저장소·기존 변경·구조 파악

    Git 상태, 지침, 관련 화면·API·DB와 기존 테스트를 먼저 읽습니다.

    도구·Skill
  3. 03

    화면·데이터·사용자 흐름 설계와 작업 분해

    사용자 동작부터 결과가 화면에 돌아올 때까지 작업을 나눕니다.

    AI 수행
  4. 04

    사람의 계획 승인

    사람이 기능 동작, 우선순위와 어디까지 수정할지 정합니다.

    사람 결정
  5. 05

    작은 수직 슬라이스 구현

    가장 작은 사용자 흐름을 화면·서버·데이터까지 끝까지 연결합니다.

    AI 수행
  6. 06

    테스트 작성과 선택적 TDD

    규칙은 TDD, 일반 기능은 구현 후 테스트로 요구사항과 회귀를 확인합니다.

    테스트 Skill
  7. 07

    읽기 전용 독립 검증

    코드를 고치지 않고 요구사항별로 무엇이 되고 안 되는지 확인합니다.

    검증 Agent
  8. 08

    배포 확인·실사용·사람의 최종 판단

    외부 환경에서 핵심 흐름을 다시 실행한 뒤 사람이 완료를 결정합니다.

    사람 결정
실패하면 이전 단계로 구조 불일치 → 구조 파악 · assertion 실패 → 구현 · 검증 실패 → 설계/구현 · 배포 오류 → 상태/Network/로그/CORS/환경변수 · 실사용 불편 → 요구사항

작업하면서 지킨 것

코드를 많이 만드는 것보다 기존 작업을 건드리지 않고, 작은 기능부터 끝내고, 실제로 확인한 내용과 못 한 내용을 같이 남겼습니다.

먼저 읽고 나서 수정

저장소 루트, 지침, Git 상태, 관련 코드와 인접 테스트를 먼저 확인합니다.

작은 기능 하나를 끝까지

화면이나 API 한쪽이 아니라 사용자가 확인할 한 흐름을 끝까지 연결합니다.

계획을 확인한 뒤 구현

AI가 계획을 제안해도 무엇을 만들지와 구현 시작 여부는 사람이 정합니다.

만든 쪽과 확인하는 쪽 분리

검증 Agent는 문제를 발견해도 코드나 테스트를 직접 수정하지 않습니다.

선택적 TDD

권한·검증·계산·API 계약처럼 기대 결과가 명확한 규칙에 적용합니다.

한 일과 못 한 일 같이 기록

실행한 명령과 결과뿐 아니라 Mock 범위와 확인하지 못한 부분도 남깁니다.

역할은 이렇게 나눴습니다

계획, 구현, 테스트 작성과 최종 확인을 한 역할에 전부 맡기지 않았습니다. 각자 맡은 일과 남길 결과를 따로 정했습니다.

사람

무엇을 만들지 결정

범위와 우선순위, 마지막 반영 여부를 직접 정합니다.

  • 목표·범위·우선순위 결정
  • 계획 승인과 선택지 확정
  • 검증 결과의 최종 반영 판단
상위 계획 대화

주간 목표와 남은 일 정리

현재 진행 상황을 목표와 비교해 무엇부터 할지 정리합니다.

  • 주간·일간 목표 연결
  • P0·P1·P2와 선후관계 정리
  • 완료·미완료·다음 범위 갱신
구조 파악 도구

현재 코드부터 확인

새 구조를 제안하기 전에 Understand와 저장소 탐색으로 현재 연결을 봅니다.

  • 관련 파일과 의존 관계
  • 화면–API–DB 데이터 흐름
  • 기존 패턴과 변경 위험
코딩 Agent

확인받은 범위만 구현

계획에서 정한 파일과 기능 범위 안에서 작은 기능 하나를 끝까지 연결합니다.

  • 기존 구조와 관례 재사용
  • 무관한 변경과 범위 확장 금지
  • 변경 파일·실행 결과·한계 인계
teamflow-test-authoring

테스트 작성과 TDD

어디까지 테스트할지 정하고 필요한 경우 TDD 순서로 진행합니다.

  • 정상·빈 값·경계·실패 사례
  • Red–Green–Refactor 기록
  • 관련 테스트에서 전체 회귀까지
verification_agent

구현과 별도로 다시 확인

테스트나 구현을 고치지 않고 요구사항별 결과와 확인 방법만 보고합니다.

  • 요구사항별 증거 연결
  • 테스트 품질과 TDD 증거 확인
  • 통과·실패·확인 불가·범위 제외
배포 도구

배포된 화면에서 확인

설정 파일만 보지 않고 외부 주소에서 기능을 직접 실행합니다.

  • 외부 주소와 상태 확인 API
  • Network·로그·CORS·환경변수
  • DB 저장·조회와 새로고침 유지

단계별로 확인할 것

각 단계마다 들어오는 정보, AI가 할 일, 사람이 정할 일, 확인 방법과 남길 내용을 같은 순서로 적었습니다.

단계 입력 AI 수행 사람 결정 확인 기준 결과물 실패 시
1. 요구사항·제외 범위·완료 기준 확정 문제, 사용자, 제약 포함·제외·완료 기준 정리 제품 동작과 우선순위 직접 확인 가능한 표현 기능 목표와 완료 기준 질문 후 같은 단계
2. 저장소·기존 변경·구조 파악 요구사항, 저장소, Git 상태 지침·코드·테스트 탐색 참고 자료의 신뢰 범위 관련 계층과 흐름 설명 관련 파일과 주의할 점 더 좁게 재탐색
3. 화면·데이터·사용자 흐름 설계와 작업 분해 완료 기준과 기존 패턴 화면·데이터·흐름 설계 권한·소유권·순서 작고 직접 확인할 수 있는 작업 작업 계획과 변경 지점 1단계 또는 2단계
4. 사람의 계획 승인 설계안과 위험 크기·누락·검증성 점검 승인·수정·보류 추가 결정 없이 구현 가능 승인된 구현 계획 1~3단계 수정
5. 작은 수직 슬라이스 구현 승인 계획과 기존 코드 작은 수직 슬라이스 연결 새 기능 결정과 범위 확장 행동부터 결과까지 실행 코드와 구현 보고 설계 또는 구현 수정
6. 테스트 작성과 선택적 TDD 요구사항과 회귀 위험 테스트 방식·사례·실행 TDD와 테스트 비용 assertion으로 완료 기준 확인 테스트와 실행 근거 구현 또는 환경 복구
7. 읽기 전용 독립 검증 원 요구사항과 구현 결과 수정 없이 실행 결과 확인 통과·수정·보류 요구사항별 확인 방법 표시 검증 보고서 설계·구현·테스트 인계
8. 배포 확인·실사용·사람의 최종 판단 검증 결과와 운영 설정 외부 핵심 흐름 재실행 유지·수정·완료 결정 화면–API–DB 연결 확인 배포 증거와 한계 원인을 찾은 단계로 돌아감

막혔을 때 돌아갈 곳

문제가 생겼다고 바로 코드를 고치지는 않습니다. 요구사항, 환경, 구현, 배포 중 어디에서 막혔는지 먼저 확인합니다.

요구사항 불명확

사람이 기능 동작과 범위를 정한 뒤 1단계부터 다시 시작합니다.

구조 불일치

저장소와 데이터 흐름을 다시 읽고 2~3단계를 수정합니다.

assertion 실패

정해 둔 완료 기준과 assertion을 만족하도록 5단계 구현으로 돌아갑니다.

import·권한·환경 오류

Red로 세지 않고 실행 환경을 복구한 다음 assertion 단계까지 다시 실행합니다.

검증에서 문제 발견

설계가 빠졌는지 구현이 잘못됐는지 나눠 3단계 또는 5단계로 돌아갑니다.

배포 실패

/health → Network → 로그 → CORS → 환경변수 순서로 확인합니다.

실사용 불편

테스트 통과와 별개로 새 요구사항과 완료 기준을 정의합니다.

확인할 수 없음

성공으로 추측하지 않고 원인과 다음 확인 방법을 기록합니다.

테스트가 통과해도 기능을 직접 확인해야 합니다. 최종 파일만으로는 TDD 순서를 알 수 없고, 배포 설정 파일이 있어도 실제 배포가 됐다는 뜻은 아닙니다.

TeamFlow에서 실제로 해본 것

결과만 적지 않고, 처음 생각과 달라진 부분이나 실제로 다시 확인한 과정도 함께 적었습니다. 테스트 숫자는 지금의 고정값이 아니라 당시 기록입니다.

  1. 1

    Figma 생성물을 설계 입력으로 해석

    생성 코드를 그대로 붙이지 않고 필요한 화면, 상태와 사용자 동작만 정리해 기존 React·Express·Shared 구조에 맞게 다시 나눴습니다.

    Figma는 화면과 동작을 정리할 때 참고

  2. 2

    React–Express–Supabase 수직 슬라이스

    입력 → React → Express → Repository → Supabase/RLS → 응답 → 화면 갱신과 새로고침 재조회까지 한 흐름씩 연결했습니다.

    입력부터 새로고침 후 재조회까지 한 번에 확인

  3. 3

    자료실 파일 크기 검증 TDD

    경계값 테스트를 먼저 만들고 assertion Red, 최소 구현, Green, 모달 정리, 관련 테스트와 전체 회귀 확인 순서로 진행했습니다.

    환경 오류는 Red로 계산하지 않음

  4. 4

    AI 할 일 잠금 규칙 재설계

    처음 규칙은 실패하거나 거절된 할 일까지 잠가서 너무 강했습니다. 현재 상태를 기준으로 다시 정하고 Web·API·DB에 같은 규칙을 적용했습니다.

    같은 잠금 규칙을 UI·API·DB에 적용

  5. 5

    배포 플랫폼보다 데모 핵심 흐름 우선

    플랫폼을 바꾸는 데 시간을 더 쓰기보다, 실제 Render 데모에서 AI 팀원 생성, 할 일 배정, 실행, 사람 검토와 공유 노트 반영을 먼저 확인했습니다.

    플랫폼 변경보다 실제 데모 동작을 먼저 확인

최종 완료 기준

파일을 만들거나 커밋한 것만으로 끝났다고 보지 않았습니다. 아래 내용을 직접 확인하고 사람이 마지막으로 승인해야 완료입니다.

  • 승인된 요구사항과 제외 범위가 유지되었다.
  • 화면·API·데이터 흐름을 직접 실행했다.
  • 관련 테스트와 적절한 회귀 범위를 실행했다.
  • TDD를 주장하면 Red·Green 순서의 근거가 있다.
  • 검증 Agent의 실패와 확인 불가를 처리했다.
  • 배포가 필요하면 외부 환경에서 핵심 흐름을 확인했다.
  • 비밀값과 사용자 작업, 무관 파일을 보호했다.
  • 남은 한계와 다음 확인 방법을 기록했다.
  • AI가 한 일과 사람이 결정한 일을 설명할 수 있다.
  • 사람이 최종 결과의 반영을 승인했다.

중요한 건 내가 설명하고 다시 확인할 수 있는 상태입니다.

사람이 방향을 정하고 AI가 작업을 돕습니다. 만든 결과는 따로 확인하고, 문제가 생기면 원인이 있는 단계로 돌아갑니다.
