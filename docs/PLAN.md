> 목표: 3주차 말에 docs/MVP.md의 완료 기준(DoD) 충족.

목표: 목 응답으로 "선택 → 입력 → 생성 → 복사" 전체 흐름이 모바일에서 끝까지 동작.

- [ ] S3 결과 화면: 톤 라벨 배지가 붙은 후보 3개 (톤 축 순서 배치)
- [ ] 복사 기능: 버튼 "복사됨" 상태 전환 + 클립보드 실패 시 텍스트 자동 선택 폴백. 추가 토스트는 T23 플랫폼별 시스템 피드백 확인 뒤 결정 (카톡 인앱 브라우저 대응)
- [ ] 플레이스홀더 감지: `[...]`·`OO` 패턴 하이라이트 + "빈칸을 채워주세요" 배지
- [ ] 생성 상태 UI: 로딩(20초 타임아웃) / 실패(다시 시도) / 429(문구 구분) — 목의 강제 케이스로 검증
- [ ] 결과 후 동선: 템플릿은 "내 상황에 더 맞추기"→S2-b, AI는 "다시 만들기"→같은 입력 리롤. "상황 수정"은 source별 직전 S2로 복귀 — 리롤 중 버튼 비활성+로딩, **리롤 실패 시 기존 후보 3개 유지** + 오류 문구 (SCREENS S3 상태(리롤))
- [ ] 시나리오 변경("다시 선택") 처리: 입력값 유지, 기존 결과 폐기 (SCREENS S2 헤더 규칙)
- [ ] 입력 검증 UI(S2-b): 목적·텍스트 미충족 시 버튼 비활성 + 안내 문구 / 결과에서 "상황을 더 적으면 더 맞는 보낼 말" 문구 (EDGE_CASES 1-1)

## 리스크 · 유동 항목

- 3주차 프록시 리스크는 Vercel+`/api/generate` 구조보다 provider 보존 고지, 서버 취소·API 타입검사, holdout 모델 선택과 실 품질 검수 시간이다. 3주차 초에 프록시를 붙여 검수 기간을 확보한다.
- 시드 예시 24개의 톤 구분 품질이 서비스 품질의 상한 — 2주차 검수에서 미달이면 3주차 품질 검수 시간을 늘린다.
- 하이브리드 도입으로 정형 상황은 템플릿 경로가 담당 — 프롬프트 품질 루프(3주차)와 독립적으로 완성되므로 3주차 리스크를 줄이는 방향.
- **콘텐츠량이 2주차의 가장 큰 리스크.** 상황 카드 템플릿이 72개(시드 24개와 독립 작성)로 신규 작성 총량이 크다. 2주차 안에 72개 전량 작성+검수가 빠듯하면, 시나리오별 특화 카드(4개) 검수를 3주차 초로 미루고 공통 5카드(20개)를 먼저 완성하는 것으로 축소 우선순위를 둔다.
- 대표 12문구 또는 무참여자 모델 벤치마크가 Iterate/No-go면 백엔드 기능으로 보완하지 않는다. taxonomy·템플릿·카드 기대 문구를 수정해 같은 프로토콜로 다시 검증한다. T22의 실제 사용자 No-go도 같은 원칙을 적용한다.
- 피드백 수집(효과 있었어요)은 MVP Out — 3주 내 구현하지 않는다 (S3에 레이아웃 자리만 고려).
