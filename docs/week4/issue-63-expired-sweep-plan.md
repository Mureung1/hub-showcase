# 마감 지난 지원금 정리(sweep) 추가 (이슈 #63)

> 작성일: 2026-07-25 (토) · 대상 이슈: [#63 마감 지난 지원금이 계속 노출됨](https://github.com/syd348/hub/issues/63)

## 목표 (한 줄)

**크롤러가 실행될 때마다 이미 저장된 공고 중 마감이 지난 것을 재검증해서 삭제한다 — 재수집 여부와 무관하게.**

## 현재 상태 (전환 전, 조사 완료)

- `dday`는 크롤링 시점에 `parseDeadline()`(`crawler/src/mapper.ts`)이 `deadline` 원문 텍스트를
  파싱해 계산한 정적 정수로 저장됨 — 이후 재계산되지 않음
- 마감 지난 공고 제외는 `crawler/src/pipeline.ts`의 `processAnnouncements()`에서
  `dday < 0`인 항목을 upsert 전에 걸러내는데, 이건 **그날 API 응답에 새로 포함된 공고에만** 적용됨
- 서버(`server/src/db/subsidies-repo.ts`, `routes/subsidies.ts`)는 마감일 기준 재검증 로직이 없음
- 결과: 이미 DB에 있는 공고가 API에서 더 이상 안 내려오면(재수집 안 되면) 마감이 지나도 영구히 방치됨

## 범위

### 포함 (이번 이슈)
- 크롤러 파이프라인에 "정리(sweep)" 단계 추가: 매 실행마다 DB에 이미 저장된 전체 row의
  `deadline` 텍스트를 다시 파싱해 오늘 날짜 기준 `dday`를 재계산, 음수면 삭제
- 기존 `parseDeadline` 로직 재사용 (새 파싱 규칙 불필요)
- 스키마 변경 없음 ("상시 접수"/"예산 소진시까지" 같은 비-날짜 텍스트는 원래도 `dday=9999`로 처리돼
  sweep 대상에서 자연히 제외됨)

### 제외 (다음으로)
- 삭제 대신 소프트 삭제(비활성 플래그)로 바꾸는 것 — 지금은 이력 보관 요구사항이 없어 하드 삭제로 충분
- server 쪳 실시간 재검증(요청마다 날짜 비교) — 크롤러가 매일 도니 최대 하루 지연은 허용 범위로 판단

## 실행 순서

### 묶음 1 — sweep 함수 구현 (완료, 2026-07-25)
- [x] `crawler/src/sweep.ts` — Supabase에서 전체 row(`id`, `deadline`) 조회 → 오늘 날짜 기준
      재계산 → `dday < 0`인 id 목록 삭제
  - **`parseDeadline` 그대로 재사용은 불가능했음** — 저장된 `deadline`은 원본 API 텍스트
    ("2026-07-20 ~ 2026-08-14")가 아니라 이미 변환된 포맷("2026. 9. 30")이라 `parseDeadline`의
    정규식(하이픈 구분자)이 매칭 안 됨. 저장 포맷을 다시 파싱하는 `recomputeDday()`를 새로 작성
- [x] `crawler/src/index.ts` 파이프라인에 upsert 이후 sweep 단계 추가
- [x] 단위 테스트(`sweep.test.ts`) — 마감 지난 deadline은 삭제 대상, "상시 접수"/파싱 불가 원문은

|------|------|-----------|
| 삭제 vs 소프트 삭제 | 삭제하면 이력이 안 남음 | **하드 삭제로 결정** — 이력 보관 요구사항 없음, 필요해지면 별도 이슈로 소프트 삭제 전환 |

| 전체 row 재조회 비용 | 매일 전체 조회는 데이터가 늘수록 비용 증가 | 현재 규모(1500여 건)에선 무시할 수준, 규모가 커지면 `deadline` 텍스트 파싱 실패율 등과 함께 재검토 |
