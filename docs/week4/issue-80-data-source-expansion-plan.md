# 데이터 소스 확장 + 첨부파일 파싱 전략 (이슈 #80)

> 작성일: 2026-07-27 (월) · 대상 이슈: [#80 K-Startup·소상공인24 크롤링 소스 추가](https://github.com/syd348/hub/issues/80)
> `docs/week4_plan.md`의 "소상공인 매칭 정확도 개선" 논의 중 파생된 하위 주제를 별도 문서로 분리.

## 배경

사용자가 배포된 서비스를 직접 써보며 소상공인 매칭 정확도가 낮다고 판단, 실제 데이터로 원인을
조사했다(2026-07-27).

**1. 소상공인 vs 중소기업 대상 불일치** — bizinfo 실제 600건 표본에서 `trgetNm`(지원대상)에
"소상공인"이 명시된 건 7.5%뿐이고, 77.7%는 "중소기업"이라고만 되어 있음. 이 77.7%를 들여다보면
R&D 기획지원·해외진출·투자포럼·금융지원 프로그램처럼 성장·수출 지향 기업 대상 공고가 많아,
동네 카페·음식점 같은 소상공인 사용자에게는 현실적으로 안 맞는 경우가 많다.

**2. 업종 카테고리 매칭률도 낮음** — 온보딩 6개 업종(음식점/카페·베이커리/소매·유통/서비스업/
제조업/기타) 정규식 매칭이 실측 6.2%만 성공(이슈 #52 당시 6.6%와 유사). 원인은 정규식 튜닝
문제가 아니라 구조적 — bizinfo 대분류(기술/경영/수출/내수/창업/인력/금융)가애초에 "업종별"이
아니라 "지원 기능별" 분류라, 대다수 공고가 업종 자체를 언급하지 않는다.

**사용자 결정(2026-07-27)**: 위 두 문제는 업종 매칭을 억지로 끌어올리기보다, ①"중소기업"
카테고리를 하나 만들어 폭넓게 보여주고 ②소상공인 전용 공고가 많은 다른 사이트를 크롤링 소스에
추가하는 방향으로 보완한다. 이 문서는 ②(데이터 소스 확장)의 세부 계획.

### K-Startup 상세 조사 (실제 API 호출 결과)

인증키 없이 `nidview.k-startup.go.kr`의 프리뷰 엔드포인트로 실제 데이터를 받아 필드를 확인했다
(단, 이게 정식 프로덕션 엔드포인트인지 데모용인지는 미확인 — 실사용 전 data.go.kr 정식 키 발급
검토 필요).

**주요 필드** (`pbanc_sn`=공고일련번호부터 실제 값까지 확인):
- `biz_enyy`(사업업력): 실제 값 예 `"7년미만,10년미만"` — **bizinfo엔 없던 필드가 K-Startup엔
  처음부터 구조화되어 있음**. 이슈 #67에서 AI로 어렵게 추출하던 businessYears를 K-Startup은
  API 필드로 바로 얻을 수 있다는 뜻
- `aply_excl_trgt_ctnt`(신청제외대상내용): 실제 값 예 `"국세 혹은 지방세를 체납중인 개인, 기업"`
  — 사용자가 우려한 "체납/분납" 조건이 별도 구조화 필드로 이미 분리되어 있음
- `biz_trgt_age`(사업대상연령): 실제 값 예 `"만 20세 미만,만 20세 이상 ~ 만 39세 이하,만 40세 이상"`
- `aply_trgt`(신청대상 카테고리): 실제 값 예 `"일반기업"` — bizinfo의 `trgetNm`처럼 뭉뚱그려져
  있어 업종 구분엔 큰 도움 안 됨
- **아쉬운 점**: 지원금액(amount) 전용 필드 없음(`pbanc_ctnt` 자유텍스트에서 정규식 필요,
  bizinfo와 동일한 상황) / 첨부파일 다운로드 링크 필드 없음(`detl_pg_url` 상세페이지만 있음 —
  다만 신청대상·제외대상·업력·연령이 이미 API로 나오니 애초에 첨부파일 의존도가 bizinfo보다
  낮을 수 있음)

## 사용자가 실제로 관찰한 문제: 본문에 지원대상/지원금 정보가 없는 공고

사용자가 sbiz24.kr을 간단히 확인한 결과, 공고 본문에 지원대상·지원금 정보가 아예 없고 첨부파일에만
있는 경우가 있음 — 그런데 **첨부파일 양식이 일관되지 않음**(bizinfo와 마찬가지로 기관마다
PDF/HWP/HWPX 등 제각각). 이슈 #67에서 bizinfo 첨부파일 하나를 놓고 이미 이 문제를 실증적으로
풀어본 경험이 있어, 그 결론을 그대로 적용할 수 있다.

### 옵션 비교: AI 구조화 추출 vs 정규식 정규화 파싱

**옵션 A — 정규식 정규화 파싱**
- 방법: PDF/HWP 텍스트를 추출한 뒤, "지원대상:", "지원금액:" 같은 패턴을 정규식으로 매칭
- 장점: 무료, 빠름, 외부 API 의존 없음
- 단점(이슈 #67에서 실증): **문서 포맷이 일관되지 않으면 정규식 하나로 커버가 안 됨** —
  bizinfo `bsnsSumryCn`(사업개요 요약문) 하나만 해도 정규식 신호가 낮았다(업력 11.7%, 직원수
  7.7%, 매출 2~6%). 여러 기관이 각자 다른 양식으로 만든 첨부파일까지 대상이면, 사이트가
  늘어날수록 포맷 다양성이 커져서 정규식의 한계가 더 뚜렷해질 것

**옵션 B — AI 구조화 추출("요약"이 아니라 스키마 강제 추출)**
- 방법: 이슈 #67처럼 JSON 스키마로 필드 타입을 강제해서 모델이 직접 구조화된 JSON을 반환하게 함
  (자유 텍스트 "요약" 후 재파싱하는 방식이 아님 — 이 차이가 중요, 아래 참고)
- 장점(이슈 #67에서 실증): 문서 포맷이 PDF든 HWPX든, 표현이 "50인 미만"이든 "직원 50명 이하"든
  같은 프롬프트/스키마로 처리 가능 — **포맷 다양성에 훨씬 잘 일반화됨**. qualifications/
  documents 필드는 100%/80%로 기존 정규식 대비 대폭 개선된 바 있음
- 단점(이슈 #67에서 실증): 무료 티어 요청 한도가 병목 — `gemini-2.5-flash` 하루 20건/모델.
  사이트를 추가하면 처리해야 할 문서 수가 늘어나서 **이 병목이 더 심해진다** — 아래 리스크 표 참고

**"AI 요약" vs "AI 구조화 추출"은 다른 것 — 용어 정리**: 사용자가 "AI를 사용해서 요약하는
방식"이라고 표현했는데, 순수 자유 텍스트 요약(예: "이 문서는 소상공인 대상 지원사업입니다"
같은 문장)은 그 자체로 매칭 로직이 쓸 수 있는 구조화된 값이 아니라서 결국 그 요약문을 또
파싱해야 하는 문제가 그대로 남는다. 이슈 #67에서 채택한 방식은 요약이 아니라 **JSON 스키마로
필드 타입(text/integer/array)을 강제해 모델이 직접 최종 구조를 반환**하게 하는 것 — 재파싱
단계 자체가 없어진다. 이번에도 이 방식(구조화 추출)을 그대로 채택하는 게 맞다고 판단한다.

**결론(제안)**: 옵션 B(AI 구조화 추출)를 이슈 #67과 동일한 파이프라인(`gemini-extract.ts`,
`document-cache.ts`)으로 재사용해서 확장한다. 정규식은 완전히 버리지 않고 "본문에 정보가 있는
경우"의 1차 시도로는 계속 쓰되(무료·빠름), 첨부파일까지 가야 하는 경우엔 AI가 유일하게 현실적인
방법이라고 본다.

### 추가로 고려한 대안 (더 나은 방법이 없을지)

- **하이브리드 텍스트 우선 추출**: 첨부파일에서 텍스트 레이어만 먼저 뽑아(PDF는 텍스트 추출,
  HWPX는 이슈 #67에서 만든 `<hp:t>` 정규식 추출 재사용) 그 텍스트에 정규식을 먼저 돌려보고,
  실패하면(신뢰도 낮으면) 그때만 AI를 호출하는 방식. **무료 티어 절약 효과가 있어 실제로
  가치 있는 제안** — 사이트가 늘어나 처리량이 늘어날수록 이 절약이 더 중요해진다. 다만 "본문
  자체에 지원대상/지원금이 아예 없는" 케이스는 애초에 정규식이 적용될 대상 텍스트가 문서
  전체 어디에 있는지 몰라서 정규식 우선순위가 크게 의미 없을 수 있음 — 실제 데이터로 검증 필요
- **스캔 이미지 PDF(텍스트 레이어 없음)**: 소상공인24 같은 기관이 스캔본을 올리는 경우 텍스트
  추출 자체가 안 됨 — 이 경우 Gemini의 네이티브 PDF 비전 처리(OCR 불필요, 이슈 #67에서 이미
  검증됨)가 사실상 유일한 방법. 사이트별로 스캔 이미지 PDF 비율을 실측해 봐야 함
- **정규식만으로 충분한 사이트가 있을 수도 있음**: 사이트마다 공고 양식 표준화 정도가 다를 수
  있어(예: 특정 사이트는 관행적으로 "지원대상" 필드를 항상 본문에 명시), 사이트별로 정규식
  성공률을 먼저 실측한 뒤 AI 필요 여부를 사이트 단위로 판단하는 것도 방법 — 모든 사이트를
  일괄로 AI 우선 처리하지 않아도 됨

### K-Startup 실제 엔드포인트 확보 + 표본 확대 조사(160건)

`nidview.k-startup.go.kr` 프리뷰 페이지의 JS(`view/js/app/api.js`)에서 폼 action을 역추적해
실제 호출 URL을 확보:

```
GET https://nidview.k-startup.go.kr/view/public/call/kisedKstartupService/announcementInformation?page=N&perPage=N&rcrt_prgs_yn=Y
```

인증키 불필요, 전체 29,568건 보유. 단 `rcrt_prgs_yn` 쿼리는 **서버가 실제로 필터링하지 않음**
(응답에 Y/N 섞여 나옴 — k-skill 프로젝트 문서가 `supt_regin`에 대해 언급한 것과 동일한 유형의
상위호환 이슈). 클라이언트 사이드로 재필터링 필요.

진행중(`rcrt_prgs_yn === 'Y'`, 클라이언트 필터) 160건 실측:

- **`biz_enyy`(업력) 결측 0%, 그러나 160건 전부 예외 없이 "10년미만"이 상한**(예비창업자/1년/
  2년/3년/5년/7년/10년미만 7개 토큰만 등장, "10년 이상"급 값 전무). 리스크 표의 "K-Startup
  커버리지가 창업기업에 치우칠 가능성"은 **가능성이 아니라 구조적 확정**으로 재평가함 —
  창업진흥원이 운영하는 사이트라 창업 초기기업만 대상으로 함
- `supt_biz_clsfc`(사업분류): 창업교육/멘토링·컨설팅/시설·공간·보육/행사·네트워크가 90%+,
  실질적 자금 지원(`정책자금`)은 1.9%뿐
- `aply_excl_trgt_ctnt`(신청제외대상) 실질값 있는 비율 46.9%(과반 미달, 나머지는 "공고문
  참조" fallback) — 최초 조사의 사례 1건보다 낮은 신뢰도
- `pbanc_ctnt` 자유텍스트에 금액 패턴 있는 비율 1.2%

**사용자 결정(2026-07-28)**: 위 제약(업력 10년 이내 전용)을 명시하고도 K-Startup을 소상공인24와
병행 추가하기로 확정 — 업력 짧은 카페·음식점 등에는 여전히 유용하다고 판단. 구현 이슈:
[#94](https://github.com/syd348/hub/issues/94)

### 소상공인24 구조 확인 재시도 (실패)

curl로 페이지 HTML + 메인 JS 번들(`index.1cd822e3.js`, 2.6MB)을 받아 정적 분석 시도. `/biz/mdle/pbanc`
같은 API 경로 문자열은 번들에서 발견됐지만(`ce("/biz/mdle/pbanc").detail(pbancSn)` 형태), 실제
REST 규칙(base URL, list/search 전체 경로)은 코드에서 동적으로 조립돼 정적 분석으로 못 찾음 —
추측성 요청(`/api/biz/mdle/pbanc/list` 등)은 전부 404. K-Startup(단순 jQuery 페이지)과 달리
소상공인24는 OCR WASM 모듈까지 포함된 무거운 SPA라 이 방식이 안 맞음.

**사용자 결정(2026-07-28)**: 지금은 보류 — 브라우저(Chrome 확장 연결 또는 사용자 DevTools
