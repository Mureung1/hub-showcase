# 차후 공부 방안 (커리어 코파일럿)

> 지금은 밑바닥(생 SQL·수동 테스트)으로 개념을 손에 익히고, 아래는 **나중에** 얹을 것들. 순서는 "개념 먼저 → 추상화 나중".

## 1. ORM (Object-Relational Mapping) — 우선순위 높음
- **무엇**: DB 방언·드라이버 차이를 숨겨주는 계층. 코드 한 번 짜고 설정만 바꿔 MySQL/Postgres/SQLite 교체.
- **후보**: JS = Prisma·Drizzle / **Spring(내 주력) = JPA·Hibernate**.
- **왜 지금 안 하나**: ORM부터 배우면 "돌아가는데 왜 느린지 모르는" 사람이 됨. **생 SQL로 개념(JOIN·인덱스·트랜잭션·N+1) 먼저.**
- **함정**: "ORM = SQL 몰라도 됨"은 거짓. 개념 없이 쓰면 **N+1 쿼리 지옥**. (우리 목업 당근 카드의 "JPA N+1 → fetch join"이 그 예.)
- **공부 시점**: 생 SQL로 CRUD·조인·인덱스가 익으면 → JPA로 같은 걸 다시 구현해 비교.

## 2. 자동화 테스트 (Vitest + Supertest) — 이번 주 목요일 계획
- 지금은 **수동 curl 스모크 테스트**. 나중에 **테스트 코드**로 `npm test` 자동 검증.
- Vitest(유닛) + Supertest(Express API 통합). TDD 1건: 스키마 검증 또는 CRUD 라우트를 테스트 먼저.

## 3. RETURNING (모던 SQLite) — 리팩터 후보
- `addInterest`의 두 스텝(INSERT + 재조회 SELECT)을 **한 문장**으로:
  `INSERT ... RETURNING *` + `.get()`. prepare 1번·재조회 없음.
- 로컬 SQLite라 속도 이득은 미미하지만, **원격 DB면 왕복 1번 절약**(Supabase가 이 방식). 코드도 짧아짐.

## 4. 배포 마감 (오픈소스용)
- **빌드+통합 서빙**: `vite build`로 프론트를 정적 파일로 굽고, Express가 그 정적 파일 + `/api`를 함께 서빙 → 사용자는 `npm start` 하나 + localhost.
- **데스크톱 래핑**: Tauri·Electron으로 감싸면 더블클릭 앱(터미널 없이). 서버가 앱 안에 숨음.

## 5. 대규모 마이그레이션 패턴 (참고 — 우리 규모엔 아직 불필요)
- **Strangler Fig**: 새 것으로 트래픽을 조금씩 옮기다 옛것 완전 대체.
- **Dual-write → Cutover**: 옛/새 DB 병행 쓰다 검증되면 전환.
- MSA(마이크로서비스)는 "앱을 여러 서비스로 쪼개기"지 DB 교체 전략이 아님. 로컬-퍼스트 도구엔 오버킬.
