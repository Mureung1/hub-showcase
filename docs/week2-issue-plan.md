### 완료된 P0 신뢰성 수정 (미커밋, 작업트리 상태)

- **점수 계산 결정론화:** `applyScores`가 패치마다 clamp하던 순서 의존성을 제거(전 패치 합산 후 1회 clamp). 전수 감사에서 순서에 따른 점수·TOP3 변동 **0/19,683** 확인(이전 rules-v2는 729/53). 알고리즘 버전 **rules-v3**로 승격.
- **결과 ID·스냅샷 수명:** 입력 지문(fingerprint)당 immutable `(resultId, createdAt)` 하나. 답을 바꾸면 새 결과로 새 ID·생성시각 발급, 입력 불변 시 재저장 없이 createdAt 안정. `updatedAt`·`schemaVersion`·`inputFingerprint` 분리 저장. reset/전체삭제가 완료·집중·피로 상태도 초기화.
- **정직한 표기:** UI의 `task/state-only` → `행동·상태 기반 기준(baseline)`(실제 과제 입력이 없으므로). `confidence` → `signalStrength`. 루틴 표시시간 = 단계 합계로 단일화. 미사용 dead code 2파일 제거.
- **회귀 자산:** `scripts/audit-scoring-order.mjs`(순서 독립성 전수 감사) 저장. 정식 테스트 러너는 의존성 승인 후 별도.
- 검증: `npm run lint`·`npm run build` 통과, 공식결과 있음/없음 두 경로 브라우저 완주.

### 논문 관점에서의 P0 재검토 결과

P0는 계산·데이터 무결성(결정론·수명) 문제로 **교육학적 내용과 직교**하며, 논문 근거와 상충하지 않는다. 오히려 인출 중심 루틴(정답 노출 전 회상, [A3]), 모든 사용자 공통 evidence-based baseline 유지([A5])와 **일치**한다. 따라서 P0 자체를 바꿀 필요는 없고, 논문은 **다음 기능(메타인지 보정 루프)** 을 강하게 지지한다(§신규 이슈 #11).

## 1. 이번 주 목표

### 주간 목표

현재 MVP의 핵심 수직 슬라이스를 **입력 → 규칙 기반 추천 → 오늘의 공부·회복 루틴 → localStorage 저장 → 새로고침 복구 → 피드백 기록**까지 검증 가능한 상태로 완성한다.

첨부 학습자료의 FE·BE·DB 연결 목표는 이 프로젝트의 현재 기술 경계에 맞게 다음처럼 적용한다.

```text
React 화면(FE)
→ scoring/recommendations 도메인 로직
→ localStorage 저장소
→ 저장 결과 복구 및 화면 갱신
```

현재 MVP에는 Express, Supabase, 회원가입, 외부 AI API를 추가하지 않는다. 서버 저장은 개인정보·동의·삭제·보존·보안 설계가 끝난 뒤의 별도 단계다.

### 이번 주 완료 기준

- 공식 MBTI 결과 입력 경로와 공식 결과 없음 경로를 각각 끝까지 수동 테스트한다.
- task/state-only baseline과 MBTI 힌트 추가 결과의 차이를 정확도·효과 향상으로 오해하지 않도록 확인한다.
- 결과, 실천 기록, 추천 평가가 저장·복구·삭제되는지 확인한다.
- 모바일과 데스크톱에서 핵심 흐름을 확인한다.
- 최소 1~2명의 사용성 검증을 진행하고 개인 응답 원문은 GitHub Issue에 올리지 않는다.
- `npm run build`와 `npm run lint`가 통과한다.
- 발표용 핵심 시나리오와 QA 결과를 문서화한다.

## 4. GitHub에 등록하는 방법

### 방법 A — GitHub 웹에서 등록

1. [`bricepark94/hub` Issues](https://github.com/bricepark94/hub/issues)로 이동한다.
2. `New issue`를 누른다.
3. 이 문서의 Issue 제목을 Title에 복사한다.
4. `목적`, `작업`, `완료 기준`을 본문에 복사한다.
5. Labels를 선택한다. 저장소에 label이 없다면 먼저 생성하거나 기존 label에 맞춘다.
6. 담당자가 정해졌다면 Assignees를 지정한다.
7. 이번 주 milestone 또는 GitHub Project가 있다면 연결한다.
8. `Submit new issue`를 누른다.
9. 실제 Issue 번호와 URL을 이 문서의 우선순위 표에 반영한다.

### 방법 B — GitHub CLI로 한 건 등록

저장소 루트에서 로그인 상태를 확인한 뒤 실행한다.

```bash
cd /Users/bricepark/Documents/hub
gh auth status
gh issue create \
  --repo bricepark94/hub \
  --title "[QA] 공식 MBTI 결과 입력 흐름 E2E 수동 검증" \
  --body-file /tmp/hub-issue-1.md
```

`/tmp/hub-issue-1.md`에는 Issue 1의 `목적`, `작업`, `완료 기준`을 넣는다. label이 실제 저장소에 존재하는지 확인한 뒤 다음 옵션을 추가할 수 있다.

```bash
--label "type: qa" --label "priority: p0" --label "area: ui"
```

### 등록 전 확인

- [ ] 같은 목적의 열린 Issue가 없는지 검색했다.
- [ ] 한 Issue가 한 사람·하루 안에 완료 가능한 크기다.
- [ ] 작업 목록과 검증 가능한 완료 기준이 있다.
- [ ] 선행 Issue와 우선순위가 표시되어 있다.
- [ ] 사용자 개인정보, 설문 응답, 자유의견 원문이 없다.
- [ ] 서버·AI·회원가입 등 현재 MVP 제외 기능이 섞이지 않았다.

## 5. 계획 수립 Agent에 줄 수 있는 프롬프트

```text
docs/context.md, docs/plan.md, docs/checklist.md와 현재 git diff를 읽어라.
현재 MVP 기술 경계(Vite, React, JavaScript, localStorage)를 유지하고,
회원가입·서버 저장·AI API·커뮤니티 기능은 제안하지 마라.

이번 주 목표를 입력 → 추천 → 루틴 → 저장 → 복구 → 피드백의
수직 슬라이스 완성과 검증으로 두고, 남은 작업을 한 사람 기준
0.5~1일 크기의 GitHub Issue로 분해하라.

각 Issue에 목적, 작업 체크리스트, 완료 기준, 우선순위, 선행 작업,
권장 label을 포함하라. MBTI는 약한 탐색 힌트로만 다루고,
스트레스는 진단·치료가 아니라 피로 신호·회복 루틴으로 표현하라.
사용자 응답 원문이나 개인정보를 GitHub Issue에 넣지 마라.
```

Agent의 결과는 그대로 등록하지 않고, 현재 코드와 중복 Issue를 사람이 확인한 뒤 등록한다.
