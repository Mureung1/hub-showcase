# PtoP 프로젝트 기록

## 문제 정의

프로젝트 경험을 쌓는 대학생 개발자는 프로젝트가 끝난 뒤 시간이 지나면 자신이 맡은 역할, 기여도, 핵심 구현 내용, 문제 해결 과정을 정확히 기억하고 정리하기 어렵다.

## 서비스 방향

PtoP는 GitHub Repository를 입력하면 프로젝트 참여 정보와 작업 흔적을 빠르게 확인하고, 나중에 포트폴리오와 회고로 확장할 수 있는 정리 초안을 만드는 서비스다.

현재는 모든 코드를 깊게 분석하기보다, 공개 GitHub API로 확인할 수 있는 객관적인 작업 흔적을 먼저 다룬다.

## 현재 MVP 범위

- GitHub Repository URL 입력
- Repository 기본 정보 확인
- contributors API 기반 참여자 확인
- commit 수 기반 기여도 퍼센트 표시
- 최근 commit message 기반 주요 작업 단서 표시
- 오류 발생 시 임의 결과를 만들지 않고 안내

## MVP에서 제외한 것

- private repository 분석
- README 전체 내용 분석
- 코드 파일 내부 분석
- PR/Issue 분석
- AI가 사용자의 역할을 자동 확정하는 기능
- Notion 또는 GitHub Pages 자동 내보내기

## 주요 결정 기록

### Repository URL 입력을 첫 흐름으로 둔 이유

사용자가 프로젝트를 정리할 때 가장 먼저 가지고 있는 자료는 GitHub Repository다.  
따라서 파일 업로드나 복잡한 설정 없이 Repository URL 하나로 시작할 수 있게 하는 것이 MVP에 가장 적합하다고 판단했다.

### commit 수 기반 기여도를 참고 지표로만 표현하는 이유

commit 수는 작업량의 일부 단서가 될 수 있지만, 실제 기여도나 실력을 절대적으로 설명하지는 못한다.  
따라서 PtoP에서는 commit 수를 객관적인 참고 지표로만 보여주고, 사용자가 직접 보완해야 할 정보와 구분한다.

### 회고 초안 생성을 3주차 이후로 미룬 이유

회고 초안은 분석 결과가 어느 정도 신뢰 가능해야 의미가 있다.  
먼저 Repository 분석 결과 구조를 안정화한 뒤, 그 결과를 기반으로 회고 초안을 만드는 방향이 더 안전하다고 판단했다.

### 기술적 도전 후보 분석을 근거 기반으로 제한한 이유

AI가 Repository만 보고 사용자의 역할이나 문제 해결 경험을 확정하면 포트폴리오 내용이 실제 경험과 달라질 수 있다. 따라서 PtoP는 파일, commit, PR, Issue 같은 확인 가능한 근거를 후보와 함께 보여주고, 사용자가 확인해야 하는 내용은 별도로 표시한다.

초기에는 벡터 DB를 추가하지 않고 우선순위 기반 파일 검색과 토큰 제한을 먼저 검증한다. 실제 누락 패턴과 사용자 질문이 쌓인 뒤 RAG 도입 여부를 다시 판단한다.
