# 알고리즘

사진→영양 수치, 오늘 데이터→광고 추천/리더보드 점수. 화면/저장 구조·코드 위치는 `CLAUDE.md`의
"Core domain flow" / "Ads" / "Leaderboard" 절, 시스템 전체 다이어그램은 루트 `README.md` 참고.
이 문서는 **로직 자체**(공식·임계값·우선순위)만 다룬다.

## 영양 분석 알고리즘

### 1. 하이브리드 매칭 — AI는 "무엇·얼마나"만, 수치는 공공 DB가 우선

AI(Gemini)는 음식 식별과 섭취량(g) 추정만 담당하고, 실제 영양 수치는 식약처 공공 DB를 우선
사용한다. AI 추정치(`estimatedNutrients`)는 DB 매칭이 전부 실패했을 때만 쓰는 최종 폴백이다.

#### 파이프라인 전체 (v2)

```
사진 → [0] 전처리(1024px·q0.85, 이미 적용)
     → [P] 프라이어 프리페치 — 급식이면 그날 NEIS 메뉴 목록 (Gemini 호출과 병렬, 캐시)
     → [1] Gemini 1회 — 장면·이름후보·역할·조리법·상대량 (시나리오 불문 호출 1회)
     → [2] 이름 해석 — 역색인으로 넓게 회수 → 게이트가 최선 선택
     → [3] 중량 — servSize > 표준×(portionRatio ⊕ trayFillRatio) > 절대 추정
     → [4] 수치 — 환산 → Atwater → 음식별 현실범위 → **판 단위 검증**
     → 항목별 영양 + 출처/신뢰도 배지 + 판 경고
```

설계 원칙은 하나로 압축된다: **AI 호출은 1회로 고정하고, 정확도는 그 앞뒤의 결정론적 파이프라인에서
번다.** AI에게는 "무엇·역할·상대량"만 묻고 숫자는 DB가 낸다.

#### 탐색 순서 (`server/nutrition/resolveFood.js`의 `resolveFoodItems`)

① 로컬(음식DB 스냅샷 + 레시피DB) 즉시 조회 → ② **역색인 retrieval + 게이트** → ③ 놓친 것만 원격
식약처 **병렬 1라운드** → ④ 보류 후보 재검증 → 그래도 없으면 AI 추정치.

#### 단일 실패점 제거 — 검색어를 여러 개 받는다

예전엔 정확도가 `dbSearchName` **하나**에 걸려 있었다. AI가 이름을 하나 잘못 지어내면 뒤의 매칭·
중량·보정이 아무리 정확해도 전부 다른 음식의 수치가 된다. 이제 AI가 `nameCandidates`(2~3개)를 내고,
서버는 후보 **전부**를 역색인에 던진 뒤 게이트 점수가 가장 높은 하나를 고른다. 후보 하나가 틀려도
나머지가 살린다.

#### retrieval-then-gate (`server/nutrition/nameIndex.js`)

**순서를 뒤집은 것이 v2의 핵심이다.** 예전 매처(`nameMatcher.js`)는 답을 하나만 주고, 게이트는 그것을
통과/탈락시킬 수만 있었다 — 더 나은 후보로 **바꿔줄 수는 없어서**, 게이트를 엄격하게 할수록 매칭
실패가 늘어나는 구조였다. 지금은 자모 bi-gram 역색인으로 후보를 넓게 회수(recall)하고 게이트가 그중
최선을 고른다(precision). 이제 게이트를 엄격하게 유지해도 매칭률이 떨어지지 않는다.

- **자모 bi-gram**을 쓰는 이유는 recall이다. 음절 bi-gram은 `꽁치김치조림`↔`꽁치조림`에서 겹치는 게
  `꽁치` 하나뿐이지만, 자모로 풀면 조리법 꼬리(`ㅈㅗㄹㅣㅁ`)까지 잘게 겹쳐 후보로 끌어온다.
- 정렬은 **(게이트 점수 → 역할 일치 → 음식DB 우선)** 사전식. 역할 일치를 점수에 섞지 않고
  tie-break로만 쓰는 이유는, 역할이 맞다는 것만으로 이름이 덜 닮은 후보가 이기면 안 되기 때문이다.
- 최고점과 **0.05 안**인 후보들은 우열을 가릴 수 없다고 보고 100g당 수치를 **평균**한다. 하나를
  임의로 고르면 `파스타`가 `냉파스타`가 되는 편향이 생긴다(DB엔 일반명 레코드가 거의 없고 전부 특정
  변형이라, 일반적인 검색어일수록 심하다). ⚠️ 다만 **전부 평균하면 오히려 나빠진다** — 실측:
  `감자채볶음`이 단독 67kcal/100g인데 통과 후보 전부(5건) 평균은 102로 벌어졌다. 밴드를 넓히지 말 것.
- 게이트 점수가 **0.85 이상이면 원격 조회를 건너뛴다**("확실하지 않은 항목에만 비싼 일을 시킨다").

실측 매칭률(`npm run check:matchrate`, 학식·급식 실제 메뉴 667종): **46.8% → 63.3%**(+110종).
칼로리 비중이 큰 역할일수록 높다 — 면 88%, 김치 87%, 밥 85%, 국 82% / 반찬 56%, 음료 30%.

#### 출처 선택 — 같은 음식도 식당과 급식은 다른 음식이다

식약처 DB는 같은 이름을 **출처별로 따로** 갖고 있고 수치가 크게 다르다:

| 음식 | 급식 출처 | 외식/프랜차이즈 출처 |
|---|---|---|
| 돼지갈비구이 | 132 kcal/100g | **294~295** |
| 김치찌개 | **19 kcal/100g** | (식당 기준 50~60) |
| 돈가스 | 148 kcal/100g | (식당 기준 250~270) |

`server/nutrition/foodLookup.js`의 `ORIGIN_PREFERENCE`가 **맥락에 따라** 고른다:

| `servingContext` | 출처 우선순위 | 쓰이는 곳 |
|---|---|---|
| `restaurant`(기본) | 프랜차이즈 공식 → 외식 분석 → 가정식 분석 → 외식 산출 → 급식 | 사진·텍스트 분석, 지도 탭 식당 메뉴 |
| `packaged` | **프랜차이즈 공식** → 가정식 분석 → 외식 → 급식 | 포장지·용기·바코드가 보이는 가공식품, 편의점 도시락, 전국 체인 |
| `home` | **가정식 분석** → 외식 → 프랜차이즈 → 급식 | 집에서 차린 상차림 |
| `cafeteria` | **급식** → 외식 → 가정식 → 프랜차이즈 | 학식·급식 화면, 식판 사진 |

⚠️ **맥락은 화면이 아니라 항목마다 정해진다.** AI가 사진을 보고 항목별로 `servingContext`를 판정해
돌려주고, 그 값이 요청 단위 기본값을 이긴다. 예전처럼 화면이 하드코딩하면 한 사진 안의 급식 식판과
포장 음료를 동시에 맞출 수 없고, 실제로 **식판 사진도 편의점 도시락도 전부 식당 수치로** 계산됐다.
화면은 여전히 합리적인 기본값을 준다(`precisionEngine`은 `cafeteria` 고정, 지도 탭은 AI가
`isFranchise`로 표시한 체인만 `packaged`).

원격 조회에서 음식DB와 가공식품DB 중 무엇을 쓸지도 **도착 순서가 아니라 맥락**이 정한다
(`REMOTE_SOURCE_PREFERENCE`). 예전엔 먼저 응답한 쪽을 채택해서, 같은 이름이 양쪽에 다 있으면 그날의
네트워크 사정에 따라 답이 달라졌다.

⚠️ 이 선택이 가능하려면 빌드가 출처를 버리지 않아야 한다. `scripts/buildFoodDB.js`는 예전에
이름당 레코드 1건만 남기고 나머지를 폐기했는데(그때 우선순위가 급식이라 외식 수치가 통째로
사라졌다), 지금은 `item.variants[]`에 전부 보존한다.

#### 양 환산 (`server/nutrition/servingWeight.js`)

- DB 값은 100g당 → `scaleNutrients(dbNutrients, baseValue, grams)`로 실제 소비량에 맞춰 환산.
- **1인분 중량 결정 순서** — 후보는 셋이고 맥락에 따라 순서가 다르다:
  - 식당 단품·집밥: `referenceGrams`(검증한 식당 1인분) → DB `servingGram` → 역할 표준 → 중립값 200g
  - 급식 트레이: **역할 표준** → `referenceGrams` → DB `servingGram` → 기본값(반찬 50g)
  - 포장·프랜차이즈: **DB `servingGram`**(제조사가 표시한 값) → `referenceGrams` → 역할 표준.
    한식 역할 표준도 역할 범위 검사도 걸지 않는다 — 제품 제공량은 제조사가 표시한 **사실**이지
    추정이 아니라서 "반찬치고 크다"는 식으로 이상치 판정할 근거가 없다(초코바 20g도 도시락 700g도
    정상이다). 단위 오기만 5~2000g으로 거른다.

  트레이가 역할 표준을 먼저 보는 이유: 급식은 배식 정책상 역할별로 양이 고정돼 있고 그걸 재현
  가능하게 만드는 게 `mealPortions.js`의 존재 이유다. 다른 두 후보는 트레이 기준이 아니다 —
  `referenceGrams`는 명시적으로 "식당 1인분"이고(잡채 200g은 급식 부찬의 두 배 넘는다), 식약처
  `foodSize`는 같은 밥인데도 레코드마다 제각각이다(실측: 쌀밥 450g·차조밥 290g·강낭콩밥 300g).
  실측 검증: NEIS 20개 트레이에서 **같은 58% 매칭 항목**이 역할 우선이면 공식 열량의 52%를,
  `referenceGrams` 우선이면 66%를 차지했다 — 나머지 42% 항목이 더 얹힐 걸 감안하면 후자는 과대다.

  DB `servingGram`은 세 겹으로 거른다: ⓐ 정확히 `100`이면 무시(1회 제공량이 아니라 **영양성분
  기준량**이 새어 들어온 값, 10,349건 중 871건) ⓑ **역할을 아는 경우에만** 역할별 절대 범위(밥
  100~500g, 국·탕 200~900g, 주찬 80~400g, 반찬 20~150g) 밖이면 버린다 ⓒ **근거 있는 기준값**(정량
  사전 또는 실제로 알아낸 역할 표준)이 있으면 그 대비 0.4~2.0배 밖도 버린다.

  ⚠️ **이 파일에서 반복해서 틀린 건 언제나 같은 모양이다 — 근거 없는 기본값으로 근거 있는 값을
  기각하는 순환.** 세 번 다른 얼굴로 나왔다:

  | # | 어디서 | 증상 | 규모 |
  |---|---|---|---|
  | ① | 비율 가드의 **분모** | 돼지갈비가 어떤 패턴에도 안 걸려 기준이 50g → DB의 정확한 220g이 4.4배 이상치로 기각 | "돼지갈비 73kcal" |
  | ② | 절대 범위의 **역할** | 역할을 못 알아보면 기본값 `side`가 되고 그 범위 20~150g이 그대로 검사에 쓰임 → 도시락 500g·음료 350ml가 전부 기각 | 프랜차이즈 8,259건 중 **57.5%** |
  | ③ | **역할 분류 자체** | 이름 패턴이 11,347종 중 3,606종(31.8%)에서 실패 | ①②의 뿌리 |

  ①은 분모를 근거 있는 값으로 좁혀서, ②는 **역할을 실제로 알아본 경우에만** 역할 범위를 쓰도록 해서
  고쳤다(모르면 범용 10~1200g). ③은 이 파일 혼자 풀 수 없어서 **AI가 판정한 역할(`roleHint`)**을
  받는다 — 이름 패턴이 걸리면 그쪽이 항상 우선한다(재현 가능성).

  `resolveServingWeight`는 고른 값과 함께 **왜 골랐는지**(`source` / `founded`)를 돌려준다.
  `founded === false`는 "이 숫자엔 아무 근거가 없는 중립값"이라는 뜻이고, 아래 배식비율 경로가
  그 플래그로 열리고 닫힌다.

- **실제 섭취량**(`resolveConsumedGrams`)은 근거가 강한 순으로 고른다:
  1. `match.servSize` — 포장에 인쇄된 1회 제공량. 추정이 아니라 사실이라 항상 이긴다.
  2. **표준 1인분 × 배식비율(`portionRatio`)** — AI에게 "몇 g이냐"가 아니라 "보통 1인분에 비해 얼마나
     담겼냐"를 물은 값. 사람도 사진만 보고 200g인지 400g인지는 잘 못 맞히지만 "보통보다 조금 많다"는
     잘 맞힌다. **표준값이 `founded`일 때만** 이 경로를 쓴다 — 근거 없는 중립값 200g에 비율을 곱하면
     모르는 값끼리 곱하는 셈이라 오히려 나빠진다.
  3. AI의 절대 그램 추정(`estimatedGrams`) — 위 둘이 없을 때. 음식별 1인분 범위로 보정해 쓴다.

  사진 프롬프트는 절대 크기 추정을 돕기 위해 **실제 식기 치수를 자로 준다**(밥공기 지름 10.5cm ≈
  가득 210g, 국그릇 13cm ≈ 300ml, 종이컵 7cm ≈ 180ml, 접시 23cm, 급식 식판 38cm, 숟가락 20cm).

  로컬 DB의 1인분은 `servSize`가 아니라 `referenceServingGram`으로 따로 나간다 — `servSize`에 실으면
  1번 규칙에 걸려 곱빼기·소식이 전부 표준 1인분으로 뭉개진다. `servSize`는 포장 단위처럼 **진짜
  근거가 있는** 1회량(가공식품·레시피DB)만 담는다.
- DB 레코드에 없는 개별 항목(예: 식이섬유)만 `fillMissingNutrients`로 AI 값을 보완.

> **왜 이 규칙이 이렇게 생겼나** — 6주차에 "외식 출처는 연포탕 1인분이 1000g"이라는 제공량
> 이상치를 고치려고 빌드 우선순위를 급식으로 뒤집었는데, 그게 제공량뿐 아니라 **영양밀도까지**
> 급식으로 바꿔버린 부작용이 있었다. 지금은 둘을 분리한다 — 제공량은 위 범위로 거르고,
> 영양밀도는 맥락에 맞는 출처를 고른다. 손잡이 하나로 두 문제를 동시에 조절하려던 게 실패의 원인이었다.

#### 급식 closed-set 프라이어 (`src/lib/menuPrior.js`)

한국 학교급식은 영양(교)사가 **표준레시피 × 1인 배식량**으로 영양을 산출해 NEIS에 공개한다. 즉 급식
사진에는 그날의 공식 메뉴명 목록이 **이미 존재**하는데, 사진 분석은 그걸 안 쓰고 AI에게 맨땅에서
이름을 지어내게 하고 있었다.

프로필에 학교가 있으면 그날 메뉴 목록을 **Gemini 호출과 병렬로** 가져와 프롬프트에 넣는다. 그러면
식별이 **open-set → closed-set**으로 바뀐다 — AI는 목록에서 고르기만 하면 되고, 고른 이름이 곧 DB
조회에 쓸 표준명이 된다. 함께 지시하는 것 둘: 목록에 없는 것(개인 간식·우유)은 자유 식별,
**목록에 있어도 사진에 안 보이면 제외**(안 담은 반찬을 합산하지 않는다).

- `(학교코드, 날짜)`로 캐시 — 같은 학교 학생들이 같은 날 찍으면 두 번째부터 네트워크 0.
- 실패하거나 학교가 없으면 조용히 null → 기존 open-set 경로 그대로. 프라이어는 부가 정보다.
- 목록을 받은 경우 그 사진은 학교 급식이 확실하므로 `servingContext`를 `cafeteria`로 고정한다
  (우리가 아는 사실이 AI 추측보다 강한 근거다).
- NEIS 원문의 알레르기 번호·각주 기호(`미역국 (5.6)`, `백김치*`, `H참외`)는 `cleanMenuName`이 벗긴다.

#### 이름 유사도 게이트 (`src/lib/foodMatch.js`)

비정확 매칭은 `foodNameSimilarity ≥ 0.7`을 통과해야 채택된다. 한국어 음식명은 핵심 명사가 뒤에
오므로 endsWith(접두 수식어 변형, "돌솥비빔밥"→"비빔밥")는 통과, startsWith("라면"→"라면땅")는
탈락이 기본 규칙이다. 여기에 예외 둘:

- **DB 변형명** `기본명_수식어`(`김치찌개_돼지고기`, `갈비구이_소고기_양념`) — 식약처 DB 레코드
  대부분이 이 형태라, 막아두면 DB에 도달할 수 없다. endsWith와 같은 등급으로 취급.
- **조리법 접미사**(`돼지갈비`→`돼지갈비찜`) — 엄밀히는 다른 음식이지만 AI 추정치로 폴백하는
  것보다 훨씬 낫다. 0.72로 통과선을 살짝 넘긴다.
- **앞머리·꼬리 공유도**(`꽁치김치조림`↔`꽁치조림`, `감자채볶음`↔`감자볶음`) — 한국어 급식·식당
  메뉴명은 재료가 이름 **가운데** 끼어드는 형태가 지배적인데, 이건 위 세 관계 어디에도 해당하지
  않아 전부 0점이었다. 실측: NEIS 급식 288항목 중 DB가 찾은 198건의 **29%(57건)가 이렇게 버려지고
  있었다**. 공유 비율 0.6에서 통과선을 넘도록 매핑한다.

**꼬리(음식 종류)가 다르면 앞머리가 같아도 무조건 차단한다** — 한국어 음식명은 꼬리가 곧 종류라
`계란국`(국)과 `계란빵`(빵)은 다른 음식이다. 이 veto가 없으면 앞머리 공유도만으로 0.75가 나와,
급식 계란국 한 그릇이 158kcal/100g짜리 빵으로 계산된다(실측 474kcal). `국수`가 `국`으로,
`케이크`가 `크`로 읽히지 않도록 긴 꼬리를 먼저 본다.

v2에서 더한 규칙 셋(전부 위 veto를 **뒤집지 못한다** — veto는 즉시 0을 반환하고 끝난다):

- **`_` 변형명의 정체는 앞부분이다.** 식약처 `기본명_수식어`에서 음식은 `_` 앞이라, 전체 문자열에
  endsWith를 걸면 `햄버거_치킨`이 "치킨의 접두 수식어 변형"으로 읽혀 0.80을 받는다(실제로는 햄버거).
  그래서 순서 규칙은 **기본명끼리만** 태운다.
- **순서 무시 비교** — `_` 변형명은 마디 순서가 우리말 어순과 반대인 경우가 많다
  (`샌드위치_바삭몬테크리스토` ↔ `몬테크리스토샌드위치`). `_`가 있는 쪽에 한해 글자 구성 Dice로 본다.
- **자모 유사도**(≥0.85)로 순수 오탈자 구제 — `닭갈비`↔`닥갈비`는 음절로 33% 손실이지만 자모로는 12%다.

그리고 완화의 대가로 하나를 **좁혔다**: 앞머리·꼬리 공유도에서 **꼬리만 공유할 때는 기준을 0.7로
올린다.** 이 규칙의 취지는 "재료가 가운데 끼어든 같은 음식"인데, 앞머리가 아예 다르면 그건 재료가
다른 음식이다 — 실측 오매칭 `콩자반`↔`김자반`(2/3=0.667로 통과, 180 vs 500kcal/100g)이 여기서 걸린다.
`팬케이크`↔`핫케이크`(3/4=0.75)는 그대로 남는다.

⚠️ **앞뒤 관계가 하나라도 있었으면 그 판정이 최종이다.** 앞머리·꼬리 공유도는 관계가 전혀 없을 때만
쓰는 최후 규칙 — 이걸 어기면 `라면`→`라면땅`이 앞머리를 100% 공유한다는 이유로 0.75를 받아
되살아난다(구현 중 실제로 겪었다).

`치킨`→`제육(돼지고기 수육)`, `파스타`→`토스트(식빵)`, `콩자반`→`간자장`, `우유`→`우동`,
`치킨`→`햄버거_치킨`, `콩자반`→`김자반` 같은 오매칭은 **전부 0점 또는 기준 미달로 차단**된다
(`fooddb.test.js`가 고정).

#### 확정 동의어는 판정이 아니라 정규화로 (`server/nutrition/textNormalize.js`)

`달걀`↔`계란`은 자모로도 전혀 안 닮아서(ㄷㅏㄹㄱㅑㄹ vs ㄱㅖㄹㅏㄴ) 어떤 임계값으로도 못 잡는다.
확정 동의어는 형태소 치환 테이블(`MORPHEME_SYNONYMS`)로 처리한다 — 검색어와 DB 이름 **양쪽에 똑같이**
걸리므로 `계란국`이 `달걀국`에 exact로 붙는다. `foodData.js`의 keywords 별칭은 음식 하나당 한 줄이라
달걀말이·달걀국·달걀찜을 전부 등록해야 하는데, 형태소 치환은 한 줄로 그 전부를 덮는다.

#### 이름이 닮아도 영양이 어긋나면 뺀다

retrieval을 넓히면서 새로 생긴 위험이다. 실측: `치킨`이 레시피DB `삼계치킨`(120kcal/100g)에 0.85로
붙는데, 우리가 검증한 치킨은 180~326이다. 이름만 보면 "치킨의 한 종류"가 맞지만 대표값으로는 틀렸다.
그래서 `foodData`가 **검증 범위를 가진 음식에 한해** 그 범위를 벗어나는 후보를 랭킹에서 뺀다
(여기서는 `clampToPlausibleNutrients`의 0.5/1.5 여유를 쓰지 않는다 — 저쪽은 "이미 채택한 값을 고칠지"
판단이라 오탐이 비싸지만, 여기는 후보 선택이라 하나 버려도 다음 후보나 AI 추정이 받아준다).

이 게이트는 **두 엔진 모두**에 걸린다. 예전엔 `resolveFood`에만 있고 `precisionEngine`(한 판 통합
분석)에는 없어서, 트레이 경로에서만 유사도 0짜리 오매칭이 무검증으로 합산됐다.

#### 역할 충돌 veto — 꼬리 규칙이 못 미치는 곳

꼬리 veto는 **양쪽 다 알아볼 수 있는 꼬리를 가졌을 때만** 동작한다. `푸팟퐁커리`·`몬테크리스토
샌드위치` 같은 창작·외래 메뉴명엔 안 걸린다. 그래서 AI가 준 상차림 역할(`role`)과 후보 이름의 역할이
**범주적으로** 다르면 유사도 계산 전에 잘라낸다(국 ↔ 후식).

인접한 역할끼리는 막지 않는다 — `main`↔`side`(제육볶음은 주찬이기도 부찬이기도 하다),
`rice`↔`noodle`, `side`↔`kimchi`, `dessert`↔`drink`. 여기서 자르면 정상 매칭이 대량으로 죽는다.
후보 이름에서 역할을 아예 못 읽으면 판단 근거가 없으므로 **막지 않는다**(모르면 통과).

#### 사용자 보정 — 조리법 1탭 (`src/lib/foodNameCorrection.js`)

이 앱의 정확도는 결국 `dbSearchName` 하나에 걸려 있다. 그게 틀리면 뒤의 매칭·중량·보정이 아무리
정확해도 전부 엉뚱한 음식의 수치가 된다. 그리고 **가장 자주 틀리는 축이 조리법**이다 — 같은 재료라도
구이/찜/조림/튀김이 DB에 서로 다른 레코드로 있고, 사진으로는 양념 색과 국물 유무로만 구분해야 한다.
재료(돼지/소/닭)는 AI가 거의 틀리지 않아서 보정 축을 조리법 하나로 좁혔다.

결과 카드에서 조리법 칩을 누르면 **검색어의 조리법만 갈아끼워 DB를 다시 조회**한다(Gemini는 다시
부르지 않는다 — 맥락·역할·비율·AI 추정 폴백은 원래 식별 결과를 그대로 재사용). "직접 수정"이 결과
수치를 손으로 덮어쓰는 것과 다른 지점이다: 사용자가 확실히 아는 건 영양수치가 아니라 자기가 먹은
음식이므로, 이쪽이 물어보기 쉬운 질문이고 답이 곧바로 정확도로 이어진다.

**매칭이 확실한 결과(`confidence === 'high'`)에는 띄우지 않는다** — 잘 맞은 값 밑에 "고쳐보세요"가
붙으면 맞는 값을 의심하게 만든다. 음식이 하나일 때만 다루는 것은 "직접 수정"과 같은 이유다.

#### 현실성 보정 (`clampToPlausibleNutrients`, `src/lib/nutrition.js`)

먼저 `applyAtwaterEnsemble`(탄4·단4·지9로 역산한 칼로리가 20% 넘게 어긋나면 탄단지를 calories에
맞춰 비례 보정)을 거친 뒤, `foodData.js`의 음식별 현실 범위로 상·하한을 건다(하한의 50% 미만 /
상한의 150% 초과일 때만). DB 매칭이 없어 AI 추정치를 쓸 때도, **한 판 통합 분석·단일 메뉴 분석에서도**
동일하게 거친다(예전엔 트레이 경로만 이 보정을 통째로 건너뛰어 경로마다 수치가 달랐다).
새 예외 케이스는 `foodData.js` 테이블에 추가하는 방식으로 확장(코드 분기를 늘리지 않는다).

⚠️ 이 두 보정은 **계통적 오류를 못 잡는다**. Atwater는 DB 레코드가 이미 자기 정합이라(전수 측정
결과 출처별 이탈률 0~5%) 사실상 무동작이고, 범위 클램프의 0.5~1.5배 밴드는 오탐을 피하려 일부러
넓다(돈가스 급식 296kcal은 하한 430의 절반인 215보다 커서 안 걸린다). 즉 "수치가 통째로 2배 틀린"
문제는 여기가 아니라 **출처 선택과 중량 결정에서** 고쳐야 한다.

#### NEIS 공식 수치는 확정값 (`src/lib/anchoredNutrients.js`)

NEIS 급식 식단정보는 영양(교)사가 표준레시피로 산출해 공시한 값이라 우리 추정보다 정확하다. 그래서
**공식으로 받은 항목은 손대지 않고**, 안 받은 항목만 남은 열량에서 역산한다.

학교마다 공개 항목이 다르다 — 열량은 항상 있고, 탄수·단백·지방은 있을 때도 없을 때도 있고,
**식이섬유와 나트륨은 NEIS에 아예 없다.**

```
공식 { 열량 800, 단백질 15 }
  → 단백질 15g = 60kcal 확정
  → 남은 740kcal을 탄수·지방에 배분 (우리 추정치의 에너지 구성 비율대로,
     추정치가 근거를 못 주면 KDRI 에너지적정비율 탄수 60%·지방 25%로)
  → 탄수 111.7g, 지방 32.6g  (Atwater 역산 = 800kcal ✓)
  → 식이섬유·나트륨은 열량 조정 비율(0.8배)만큼 함께 조정
```

예전엔 공식 값이 있는 항목만 비율로 스케일하고 나머지는 원래 추정값을 그대로 뒀다. 그래서 열량은
0.8배로 줄었는데 나트륨은 1.0배로 남는, 앞뒤가 안 맞는 합계가 나왔다.

⚠️ **공식 값끼리 Atwater가 안 맞아도 고치지 않는다.** NEIS 수치가 자기들끼리 정확히 정합하지 않는
경우가 실제로 있는데(열량 800인데 탄단지 역산은 725), "확정된 것은 바꾸지 않는다"가 이 모듈의
계약이다. 우리가 더 정확하다고 볼 근거가 없다.

#### 단백질·지방 현실성 보정 (`src/lib/macroPlausibility.js`)

기존 보정 둘은 이 오류를 못 잡는다: `applyAtwaterEnsemble`은 탄단지의 **합**만 보므로 단백질 40g·
탄수 0g·지방 0g도 열량 160이면 완벽히 정합이고, `clampToPlausibleNutrients`는 foodData에 등록된
60여 종에만 걸린다. 그 사이로 "한 끼 단백질 42g"이 그대로 빠져나간다.

기준은 **KDRI 에너지적정비율(AMDR)** — 탄수 55~65%, 단백질 7~20%, 지방 15~30%. 상한(단백질 20%,
지방 30%)을 보정 시작점으로 쓴다. 절대 그램이 아니라 **그 끼니의 열량에 비례**하는 게 요점이다:
800kcal 급식 한 끼의 단백질 상한은 40g으로 현실 한계와 정확히 맞고, 1500kcal 고기 정식이라면 같은
규칙이 75g을 허용한다. 절대값 40g으로 자르면 후자를 틀리게 만든다.

여기에 **한 끼 절대량 상한**(단백질 40g / 지방 35g에서 시작)을 함께 건다. 에너지비만으로는 판 전체가
과대추정된 경우를 못 잡기 때문이다 — 실측 사고가 정확히 그랬다(1021kcal / 단백질 60g은 에너지비로
23%라 정상 범위다). 둘 중 **더 엄격한 쪽**을 쓴다.

딱 자르지 않고 **점근 곡선으로 눌러 담는다**. 60g과 80g을 둘 다 40g으로 만들면 "더 많이 먹은 쪽"이라는
정보가 사라지기 때문이다 — 이 곡선은 시작점에서 연속이고, 단조증가하며, 상한에 점근한다.

⚠️ **DB 실측값에는 걸지 않는다.** 식약처 DB 11,255건을 전수 조사하니 단백질 에너지비 35% 초과가
**5.5%**, 지방 50% 초과가 **5.0%**였고 전부 진짜 음식이었다 — 가자미찜 단백질 60%, 갈비구이_돼지고기
지방 65%, 갈비탕 67%. 여기에 캡을 걸면 §1.5에서 힘들게 도달한 그 레코드를 스스로 망가뜨린다. 그래서:

| 적용 지점 | 대상 | 제외 |
|---|---|---|
| 항목 단위(`capEstimatedMacros`) | **AI 추정치만** | DB 실측값, foodData가 검증한 영양소 |
| 한 끼 단위(`correctMealMacros`) | 합계 전체 | foodData가 검증한 음식의 몫 |

한 끼 보정은 **근거가 약한 항목부터**(AI 추정 → 레시피DB → 식약처DB) 깎고, 한 항목을 40% 넘게 깎지
않는다(한 끼가 초과한 책임을 항목 하나에 다 지우면 그 항목이 통째로 틀린 값이 된다). 덜어낸 만큼
열량도 함께 줄인다 — 같은 출처에서 나온 값이라 단백질이 과대였다면 열량도 과대였다고 보는 게 일관적이다.

**급식에 NEIS 공식 수치가 있으면 이 보정을 아예 걸지 않는다** — 공식 값이 정답지인데 일반 규칙으로
덮으면 안 된다.

#### 판 단위 검증 (`src/lib/mealStandards.js`)

항목 단위 보정이 못 잡는 게 하나 더 있다: 항목마다 조금씩 어긋나 **어느 것도 개별 범위를 벗어나지
않으면서 합계만 크게 틀린** 경우. 그건 합계에서만 보인다.

기준값은 우리가 지어낸 게 아니라 **학교급식법 시행규칙 별표3(학교급식 영양관리기준)**이다 — 초등
534/634, 중학 800, 고등 900kcal. 영양(교)사가 실제로 이 기준에 맞춰 식단을 짜므로 진짜 앵커다.
저장소의 NEIS 실제 샘플로 검증했다: 중학교 4끼 평균 **804**(기준 800), 고등 5끼 803(기준 900),
초등 3끼 674(기준 534~634). 밴드는 ±35% — 실제 샘플 12끼를 전부 포함하는 최소 폭이다.

⚠️ **이 기준으로 값을 자동 보정하지 않는다.** 벗어나면 경고 문구만 띄운다. 외부 정답지 없이 밴드로
값을 깎으면 그게 바로 이 저장소가 반복해서 틀린 패턴 — 근거 없는 기준으로 근거 있는 값을 기각하는 것 —
이 된다. 자동 보정은 NEIS 공식 수치처럼 **외부 정답지가 있을 때만** 한다(`precisionEngine`의
`applyProportionalCalibration`).

#### 출처 배지 (신뢰도 투명화)

| 배지 | 의미 |
|---|---|
| 식약처DB | 음식 표준DB 매칭 |
| 식약처DB(가공) | 가공식품 표준DB 매칭 |
| 공식 영양표 | 프랜차이즈로 식별된 경우(AI가 공식 수치 기준으로 응답) |
| 추정 | DB 매칭 전부 실패, AI 추정치 사용 |

### 2. 권장 영양소 계산 (`src/lib/nutrition.js`의 `calcRecommendedNutrients`)

신체정보(나이·키·몸무게·성별·활동량)가 있는 사용자에게만 적용. 게스트/신체정보 미입력 사용자는 이
계산을 건너뛰고 분석 자체는 그대로 진행(권장량 대비 비교만 비활성). 순수함수로 구현되어 입력이
같으면 항상 같은 결과(부작용 없음).

- **BMR (Mifflin-St Jeor)**
  - 남: `10×kg + 6.25×cm − 5×age + 5`
  - 여: `10×kg + 6.25×cm − 5×age − 161`
- **TDEE** = BMR × 활동계수 (low 1.375 / moderate 1.55 / high 1.725)
- **탄단지 기본 비율**: 탄수 50% · 단백 20% · 지방 30% (kcal→g 환산: 탄4·단4·지9 kcal/g)
- **식이섬유**: 여 25g / 남 30g 기본값
- **나트륨**: 2000mg 상한 기준(초과형이라 "부족" 판정 대상이 아님)

`calories`/`protein`/`carbs`/`fat`/`fiber`/`sodium` 6개 지표가 `NUTRIENT_LABELS`로 앱 전체의 공통
스키마. 하루 상태(달성/보통/위험) 3단계 판정, 부족 영양소 상위 N개 추출도 같은 파일의 분류 함수가
담당.

### 3. 정확도 벤치마크 — 두 개가 **동시에** 통과해야 한다

```bash
npm run check:nutrition            # scripts/nutritionAccuracy.js — 무과금, 중량 결정 정확도
npm run check:matchrate            # scripts/matchRate.js — 무과금, DB 매칭률(= LLM에 맡기는 비율)
npm run check:nutrition:cafeteria  # scripts/precisionEngineAccuracy.js — 유료(OpenRouter), 가끔
```

벤치마크가 급식 하나뿐이던 시절에 급식 쪽으로만 튜닝이 흘러 "돼지갈비 73kcal"이 나왔다.
**한쪽만 보고 고치지 말 것.**

#### `check:nutrition` — DB가 가진 실측 제공량을 정답지로

식약처 DB에는 레코드마다 그 음식의 **실제 1회 제공량**이 들어 있다(프랜차이즈 8,259건, 외식·가정식
1,278건, 급식 648건 — placeholder 100g 제외). 이걸 정답지로 쓰면 과금 없이 8천 건 규모로 잴 수 있다.

| 항목 | 무엇을 재나 |
|---|---|
| **[1] 1인분 hold-out** | 레코드의 진짜 제공량을 **가리고** 정량 사전+역할 표준만으로 예측 → 오차. 실제 앱이 겪는 상황이다(제공량이 없는 998건, placeholder 871건, 범위 밖 값) |
| **[2] 근거 폐기율** | 반대 방향의 실패 — 진짜 제공량이 **있는데도** 규칙이 이상치라며 버리는 비율. 버릴수록 [1]의 폴백 품질에 의존하게 된다 |
| **[3] 출처 선택 불변식** | 식당 맥락은 외식 출처를, 급식 맥락은 급식 출처를 고르는가 (PASS/FAIL — 종료 코드에 반영되는 유일한 항목) |
| **[4] 출처 간 격차** | 같은 음식의 식당↔급식 수치 차이(평균 27%) — [3]이 지키는 것의 크기 |
| **[5] 영양밀도 hold-out** | 프랜차이즈 공식 수치 대비 밀도 오차. **13종뿐이라 신호가 약하다** — 이것만 보고 튜닝하지 말 것 |

**[1]과 [2]는 중량만 잰다.** 밀도의 정확성은 [5]가 약하게, end-to-end 정확도는 유료 벤치마크가
맡는다. 이 경계를 흐리지 말 것.

#### `check:matchrate` — DB 커버리지 = LLM에 맡기는 열량의 비율

학식·급식 실제 메뉴 667종에서 통합 해석 엔진이 몇 %를 식약처 DB에 연결하는지 잰다(원격 조회 없이
로컬만, 무과금). **매칭 실패는 곧 "Gemini 추정이 채울 열량"이고 그게 급식 공식 열량의 약 48%**라,
매칭률 1%p는 LLM에 맡기는 열량이 그만큼 준다는 뜻이다. 유료 벤치마크의 통과 개수보다 훨씬 안정적인
개선 신호다.

단일 매처 방식과 나란히 찍어 retrieval의 기여도를 분리해 보여주고, 역할별 매칭률과 미매칭 목록도
함께 낸다. 현재 **63.3%**(목표선 60%) — 면 88% / 김치 87% / 밥 85% / 국 82%로 칼로리 비중이 큰 역할은
충분히 덮고, 남은 미달분은 대부분 원재료성 식품(과일·우유)과 창작 조합 메뉴명이라 매칭 규칙으로는
메울 수 없다. **유사도 허용치를 풀어 이 숫자를 올리지 말 것**(오매칭 위험).

#### `check:nutrition:cafeteria` — 유료, 드물게

NEIS 실제 급식 20건 대비 총 kcal 오차 ≤20%. **통과 개수를 목표로 삼지 말 것** — 급식 메뉴 항목의
42%가 DB에 아예 없어 공식 열량의 약 48%를 Gemini가 채우므로, 20샘플의 통과/탈락은 규칙 변경보다
LLM 출력에 좌우된다. 평균 오차만 읽고, 호출이 과금되므로 자주 돌리지 않는다(§1.6 참고).

### 4. 검증 예시 (수치가 말이 되는지 감으로 확인할 때)

- 떡볶이: 음식DB 100g 기준 144kcal → 250g 환산 → 360kcal
- 초코파이: 가공식품DB `servSize` 70g 기준 347.9kcal, DB에 없는 식이섬유만 AI 값으로 보완
- 돼지갈비(식당): `갈비구이_돼지고기` 294kcal/100g × 200g → **약 590kcal**
  (개편 전에는 급식 레코드 + 중량 50g으로 **70~110kcal**이 나왔다 — 이 값이 보이면 회귀다)

개발 중 `import.meta.env.DEV`일 때 각 항목 처리 결과가 `[분석 진단]` 로그로 브라우저 콘솔에
찍힌다(매칭된 검색어/그램/최종 영양소) — 정확도 이슈 조사 시 여기서부터 본다.

## 광고추천·리더보드 알고리즘

두 기능 모두 "오늘의 영양 데이터를 하나의 숫자/추천으로 압축"한다는 점에서 계열이 비슷하다. 배경(왜
쿠팡인지, 왜 로그인 계정끼리만 비교하는지)은 `CLAUDE.md`의 "Ads" / "Leaderboard" 절 참고.

### 1. 영양소 기반 광고 추천 (`src/utils/adRecommendation.js`의 `recommendAdProducts`)

순수 함수. 입력은 오늘 실측 영양 데이터, 출력은 노출할 상품 배열(항상 1개 이상).

#### 우선순위

1. **실측 부족 영양소 상위 1~3개**가 있으면, 그 영양소와 매칭되는 상품을 우선 노출. 매칭 대상은
   앱이 실제로 추적하는 5개 지표 — `protein`/`fiber`/`calories`/`carbs`/`fat`(`AD_NUTRIENTS`의
   `tracked: true`). `sodium`은 상한형(초과를 막는 지표)이라 "부족" 개념이 없어 광고 매칭에서
   의도적으로 제외.
2. 오늘 기록이 없거나 부족 영양소를 계산할 수 없으면(신체정보 없는 게스트 등) **폴백 미량영양소
   목록을 순환**해서 표시(`vitaminD`/`calcium`/… 등 앱이 추적하지 않는, 광고 전용 지표).
3. **절대 빈 배열을 반환하지 않는다** — 폴백 목록 자체가 순환하며 항상 최소 1개를 채운다. 배너가
   비어 보이는 상태는 설계상 존재하지 않는다.

#### 지켜야 하는 제약

- `id`/`nutrient`는 추천 로직이 참조하는 키이므로, 상품 데이터(`src/data/coupangProducts.js`)를
  갱신할 때도 이 두 필드는 건드리지 않는다.
- 법정 고지 문구(`COUPANG_DISCLOSURE`)와 AD 배지는 상품이 몇 개든, 어떤 폴백 상태든 항상
  렌더링(렌더링을 생략하는 조건분기를 추가하지 않는다).
- 회귀 검증: `npm run check:ads`(`scripts/check-ad-recommendation.mjs`).

#### (예정) 상품 데이터 자동 수집

지금은 손입력. 쿠팡파트너스 검색 API로 자동화하는 설계(오프라인 배치 + 정적 JSON, 시간당 10회 API
한도라 실시간 호출 불가)는 [03-개발스펙.md](03-개발스펙.md) §6에 정리 — 파트너스 API 키 발급 조건
(누적 판매 15만원) 미충족으로 **보류 중**.

### 2. 리더보드 점수 공식 (`src/lib/nutritionScore.js`의 `calcScore`/`getScoreBreakdown`)

로그인 계정끼리만 "오늘의 순위"를 비교(게스트는 기기에 묶인 임시 식별자뿐이라 비교할 고정 신원이
없음). 5주차 §4부터 배점표 기반으로 개편 — 앱이 실제로 추적하는 5개 영양소만 채점 대상(식이섬유·
미량영양소는 배점에서 제외, 표시되는 점수가 전부 실측 데이터에 근거하게 하기 위함), 항목별로 점수를
반올림한 뒤 합산(합산 후 한 번에 반올림하지 않음):

| 항목 | 배점 | 채점 방식 |
|---|---|---|
| 칼로리 적정성 | 40 | 목표의 90~110%면 만점, 그 밖은 50%/150% 지점에서 0점까지 선형 감점(과다·과소 모두 감점) |
| 단백질·탄수화물·지방 | 각 10(합 30) | 목표 달성률, 100%에서 만점(그 이상은 자름) |
| 나트륨 | 30 | 상한 지표 — 한도 이내면 만점, 넘으면 초과 비율만큼 감점 |

- **JS 버전(`nutritionScore.js`)과 SQL 버전(`supabase/schema.sql`의 `get_daily_leaderboard()`)이
  반드시 동일해야 한다** — 한쪽만 고치면 클라이언트 표시 점수와 서버 순위가 어긋난다. 공식을 바꿀
  때는 항상 두 곳을 함께 수정.
- `get_daily_leaderboard()`는 `SECURITY DEFINER`로 실행되고 `rank`/`score`/`is_me`만 반환 — 다른
  사용자의 실제 섭취 데이터는 어떤 경로로도 노출되지 않는다.
- SQL 함수 자체는 `schema.sql`을 Supabase 프로젝트에 다시 실행해야 반영(또는 증분 마이그레이션
  `supabase/migrations/2026-07-28_score-v2-leaderboard.sql`). 배포 후 잊기 쉬운 지점.
