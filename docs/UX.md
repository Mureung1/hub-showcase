# UX 설계 가설과 검증 기준

> **상태: 2026-07-12 근거 검토 완료, 효과 검증 대기.** 동료심사 연구·공식 플랫폼 지침과 업계 사례를 구분해 기존 설계에 대조했다. 업계 블로그는 패턴 후보일 뿐 효과 근거가 아니며, 아래 선택의 실제 효과는 T22·T23 전까지 제품 가설이다. 구현 반영 시점은 CHECKLIST.md 해당 항목(T8, T10, T14, T20, T22, T23).

## 1. 이 서비스의 UX 문제 정의

답냥이의 성공 루프는 경로별로 다르다. 외부 파일럿의 잠정 목표는 **카드 경로 S0→결과 20초**, **직접입력 경로 S0→복사 60초**다:

```
카톡에서 보낼 말이 막힘 → 진입 → 방식·관계 선택 → [상황 카드 → 즉시 결과] 또는 [다른 상황 → 목적·입력 → 생성 대기] → 3개 비교 → 복사 → 카톡 복귀
```

UX가 승부를 보는 지점은 4곳이고, 이 문서는 각 지점의 근거 수준과 검증할 설계 가설을 기록한다:

1. **입력 전** — "내 상황이네"라고 3초 안에 느끼게 (시나리오 카드)
2. **대기** — 5~20초를 불안 없이 기다리게 (생성 로딩)
3. **선택** — 후보 3개를 노력 없이 비교하게 (결과 화면)
4. **복사-복귀** — 마지막 행동이 반드시 성공하게 (클립보드)

## 2. 대기 UX — 완전한 세 후보가 올 때까지 스켈레톤 표시

**근거 수준**: 토큰 스트리밍, 스켈레톤, 시간 경과 문구는 생성형 AI 제품에서 관찰되는 업계 패턴이다([TheFrontKit](https://thefrontkit.com/blogs/what-is-streaming-ui-in-ai-applications), [mindrind](https://mindrind.net/ux-ui-design-generative-ai-apps/), [UX Tigers](https://www.uxtigers.com/post/think-time-ux)). 이 자료들은 동료심사 효과 연구가 아니므로 특정 첫 토큰 시간이나 문구 주기가 체감 대기·이탈을 줄인다고 주장하지 않는다.

**답냥이 결정과 미검증 가설**:
- 구조화 응답도 기술적으로 스트리밍할 수 있다. 답냥이가 부분 후보를 노출하지 않는 이유는 schema 전체를 검증하기 전의 불완전 문구를 보여주지 않고 세 안을 동시에 비교하게 하려는 제품 trade-off다.
- 결과 카드와 같은 모양의 스켈레톤 3장을 표시한다. 시간 경과 문구는 실제 provider 진행 단계를 아는 것처럼 “읽는 중·거의 완료”라고 말하지 않고, “보낼 말을 준비 중이에요”, 10초 뒤 “평소보다 조금 더 걸리고 있어요”처럼 경과 상태만 알린다.
- 4~5초 전환·10초 안내는 구현 주기일 뿐 효과가 검증된 수치가 아니다. T22에서 이탈·체감 노력, T20에서 실제 provider 상태와 문구 정합을 확인한다.
- 생성 중단 버튼은 20초 timeout이 있는 MVP 범위에서 제외한다. 효과가 좋아서가 아니라 범위 결정이다.

## 3. 다중 후보 선택 UX — 세로 스택 3카드 + 원클릭 리롤 (효율·agency 함께 검증)

**조사 결과**: [Fu et al., CHI 2023](https://doi.org/10.1145/3544548.3581351)에서는 메시지 단위 추천이 문장 단위 추천보다 빠르고 만족도가 높았지만 agency는 낮았다. [Buschek et al., CHI 2021](https://doi.org/10.1145/3411764.3445372)에서는 선택지가 늘수록 탐색이 늘고 6개 조건이 느려졌으며, 3개 조건을 적절하다고 본 참여자가 가장 많았다. 그러나 두 연구 모두 영어 업무 이메일·추천 문구 맥락이므로 **한국어 완성문 세 개가 최적이라는 증거는 아니다**. [Li et al., CHI 2024](https://doi.org/10.1145/3613904.3642625)에서는 자기선택한 AI-primary 작성 방식이 낮은 ownership·책임감·다양성과 연관됐고, [Draxler et al., TOCHI 2024](https://doi.org/10.1145/3637875)는 AI 제공 조건의 낮은 ownership과 사용자 통제·주도성의 중요성을 관찰했다. 자세한 인과·일반화 경계는 [문헌 기반 제품·검수 근거](RESEARCH_REVIEW.md)를 따른다.

**답냥이 적용 — 기존 결정이 패턴과 일치, 세부 지침 추가**:
- 세로 스택 3카드와 톤 배지는 별도 탭 전환 없이 비교하게 하려는 현재 설계 가설이다(SCREENS 핵심 결정 1). 실제 비교 노력·선택 시간은 T22에서 검증한다.
- AI 결과의 "다시 만들기" 원클릭 리롤 ✓. 템플릿 결과는 동작이 다른 "내 상황에 더 맞추기"로 분리 (SCREENS 핵심 결정 3)
- **추가 지침**: 카드 간 시각적 차이는 톤 배지로만 준다 — 카드 크기·색을 다르게 해 특정 후보를 추천하는 연출 금지(선택은 사용자 몫이라는 서비스 전제). 후보 전문을 접지 않고 모두 노출(카톡 메시지 길이면 접기가 불필요하고, 접으면 비교가 깨짐).
- 세 안 중 하나를 자동 선택하거나 자동 전송하지 않는다. 복사 뒤 실제 전송 전 사용자가 문구와 사실을 다시 확인할 수 있어야 한다.
- 세 후보 개수는 유지하되 확정된 최적값으로 표현하지 않는다. T22에서 선택 시간·후수정량과 5점 척도 “내가 실제로 할 말 같다”를 함께 기록한다.

## 4. 복사 UX — 버튼 상태 전환을 공통 피드백으로 사용

**공식 지침**: Android 13+는 클립보드 쓰기 때 시스템 확인 UI를 표시하며, [Android Developers](https://developer.android.com/develop/ui/views/touch-and-input/copy-paste)는 중복 알림을 피하도록 앱 토스트·스낵바 제거를 권고한다. 모바일 웹·iOS·카톡 인앱 브라우저의 피드백은 같다고 가정할 수 없으므로 T23 실기기 확인이 필요하다.

**답냥이 적용**:
- 모든 환경에서 **버튼 자체가 “복사됨 ✓” 상태로 1.5초 전환**되게 해 앱 내부의 공통 피드백으로 사용한다. 1.5초는 구현값이며 효과 수치가 아니다.
- 앱 토스트를 모든 환경에서 강제하지 않는다. 시스템 확인 UI가 없는 환경에서 추가 피드백이 필요한지는 T23에서 확인하고 platform-aware 적용을 결정한다. 토스트를 쓰게 되면 하단 브라우저 바와 겹치지 않는 위치를 실기기로 정한다.
- 실패 폴백(텍스트 자동 선택)은 기존 결정 유지 ✓ — 카톡 인앱 브라우저에서 실기기 검증 필수 (CHECKLIST T23).

## 5. 일반 모바일 지침 (통용 원칙 — 별도 출처 없음)

- **주 CTA는 화면 하단**: S2 생성 버튼은 입력 필드 아래 고정 노출(스크롤에 묻히지 않게), 엄지 도달 범위.
- **터치 타깃 최소 44px**, 카드·버튼 간 간격은 DESIGN.md spacing 토큰(md 16px) 이상.
- **키보드 열림 대응**: S2에서 키보드가 열려도 생성 버튼 접근 가능해야 함(입력 후 키보드 닫기 강요 금지).
- 시나리오 카드 문구는 SPEC 1장 확정본 — 기능 설명이 아니라 **상황 공감 문구**("할 말은 해야 할 때")로 유지한다. 카드가 곧 서비스의 첫 신뢰 지점.
- **뷰포트**: 375×667에서 S0 선택 2개가 초기 화면에 보이고, 320×568에서 가로 넘침이 없어야 한다. 모바일 히어로는 핵심 선택을 밀어내지 않게 축소한다.
- **카드 밀도**: 상황 카드 6개는 2열 유지, "다른 상황이냥?"만 전체 폭. 탈출구가 화면 아래로 과도하게 밀리지 않게 한다.
- **초점·스크롤**: 단계 전환 시 새 제목으로 초점을 옮기고 상단으로 스크롤한다. 내부 S0~S3 이름은 사용자에게 노출하지 않는다.
- **선택·상태 접근성**: 목적 칩은 보이는 legend와 `aria-pressed`, 생성 영역은 `aria-busy`, 모든 버튼은 일관된 `:focus-visible`을 사용한다. 글자 수는 매 입력마다 전체를 읽지 않도록 과도한 `aria-live`를 피한다.
- **시각·모션**: 본문과 버튼은 WCAG 2.2 AA 대비를 충족하고, `prefers-reduced-motion`이면 스켈레톤 애니메이션을 중지한다. 긴 결과는 `overflow-wrap: anywhere`로 보호한다.
- **안전 영역**: sticky CTA는 `safe-area-inset-bottom`을 반영한다.

## 6. 현재 설계 가설 요약

| 지점 | 현재 설계 가설 | 상태 |
|---|---|---|
| 대기 | 결과 카드 모양 스켈레톤 3장 + 실제 진행을 가장하지 않는 경과 문구. 부분 스트리밍 미노출은 제품 trade-off | 지침 → T8·T20·T22 |
| 선택 | 세로 스택 3카드 + 톤 배지, 후보 간 동등한 시각 무게, 전문 노출. 세 개의 최적성·ownership은 T22 탐색 | 기존 결정 + 지침 → T9·T22 |
| 복사 | 버튼 “복사됨” 상태 전환 + 자동 선택 폴백. 추가 토스트는 실기기 결과로 결정 | 기존 결정 재검토 → T10·T23 |
| 전반 | 375×667·320×568, CTA·safe area, 44px, 초점·대비·키보드·reduced motion | 보강 지침 → T14·T22 |

## 7. MVP 밖 (이후 단계 후보)

토큰 스트리밍 표시, 생성 중단 버튼, 후보 부분 수정(문장 단위 편집), 햅틱 피드백, 다크 모드.
