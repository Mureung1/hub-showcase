# ADR — 아키텍처 결정 기록

**이 문서의 역할**: 왜 그렇게 정했는가 — 되돌리기 어려운 결정과 기각한 대안의 기록. 그 결정이 만들어 낸 현재 구조는 `ARCHITECTURE.md`에 있다. 여기서 구조를 다시 설명하지 않는다.

ADR(Architecture Decision Record)은 되돌리기 어렵거나 이후 작업에 영향을 주는 기술·제품 결정을 기록한다.

결정 1건은 이 문서의 `## ADR-NNNN` 섹션 1개다. 이미 쓴 섹션은 지우지 않고 상태만 바꾼다 — 어떤 결정이 왜 뒤집혔는지가 결정 자체만큼 중요하기 때문이다.

## 목록

| ADR | 상태 | 내용 |
|---|---|---|
| [ADR-0001](#adr-0001--기술-선택) | 대체됨 | 스택 결정 전까지 정적 프로토타입만 유지 — ADR-0002로 대체 |
| [ADR-0002](#adr-0002--생산-스택) | 채택됨 | React+TypeScript+Vite / Supabase(로컬 CLI+Docker), LLM은 Edge Functions에서만, 이메일 로그인+RLS 포함 |

## 작성 기준

ADR은 다음 경우에 작성한다.

- 생산용 기술 스택을 정할 때
- DB, 배포, 인증, LLM 공급자처럼 교체 비용이 큰 결정을 할 때
- 제품 범위를 바꾸는 결정을 할 때 (핵심 기능 추가, PRD 7장 제외 기능의 해제)
- 플랫폼 자동 수집·자동 게시처럼 리스크가 큰 기능을 도입할 때

## 형식

새 결정은 이 문서 맨 아래에 다음 형식으로 덧붙이고, 위 목록 표에 한 줄을 추가한다.

## ADR-0001 — 기술 선택

상태: 대체됨 — 생산 스택은 [ADR-0002](#adr-0002--생산-스택)에서 확정
날짜: 2026-07-10

### 맥락

현재 저장소는 리뷰지기 PRD와 HTML·CSS 프로토타입을 보유하고 있다. 사용자는 하네스 엔지니어링을 시작하기 위해 문서와 작업 규칙을 먼저 정리하려고 한다.

아직 생산용 앱의 프론트엔드, 백엔드, DB, 배포 방식, LLM 연동 방식은 확정되지 않았다. 따라서 지금 `src/`, `app/`, `server/` 같은 구현 폴더를 만들면 이후 스택 결정과 충돌할 가능성이 높다.

### 결정

- 현재 단계의 기술 산출물은 정적 HTML·CSS 프로토타입으로 유지한다.
- 제품 기준은 `docs/PRD.md`로 둔다.
- 실제 앱 소스 구조는 생산용 스택을 결정한 뒤 생성한다.
- 그 전까지는 문서, 테스트 계획, 하네스 작업 루프를 먼저 정리한다.
- MVP 구현 시에도 자동 리뷰 수집과 자동 게시 기능은 만들지 않는다.

### 결과

좋아지는 점:

- 불필요한 구현 폴더와 빈 파일을 만들지 않아 구조가 덜 오염된다.
- PRD와 프로토타입을 기준으로 기능 경계를 먼저 합의할 수 있다.
- 이후 어떤 스택을 선택하더라도 도메인 경계를 유지할 수 있다.

감수할 점:

- 당장 실행 가능한 앱 서버나 빌드 파이프라인은 없다.
- 실제 데이터 저장, AI 호출, 플랫폼 연동은 다음 ADR 이후에 구현해야 한다.

### 대안

#### 지금 React 또는 Next.js 앱을 바로 생성

보류했다. 화면은 이미 정적 프로토타입으로 검증 가능하고, 생산용 요구사항이 더 정리되기 전에는 스택 잠금이 빠르다.

#### 지금 백엔드 API부터 생성

보류했다. 데이터 모델과 LLM 입출력 계약이 먼저 필요하다.

#### 현재 HTML·CSS 프로토타입을 최종 제품으로 확장

보류했다. 프로토타입은 시연과 검토에는 충분하지만, 실제 입력 저장, 분석, AI 연동, 계정 관리에는 별도 앱 구조가 필요하다.

## ADR-0002 — 생산 스택

상태: 채택됨
날짜: 2026-07-22

### 맥락

기능 단위 Phase(00~06) 실행을 시작하려면 생산용 프론트엔드, 백엔드, DB, LLM 실행 위치를 확정해야 한다. 사용자가 2026-07-22에 스택을 직접 결정했다.

### 결정

- 프론트엔드: **React + TypeScript + Vite** (`frontend/`)
- 백엔드: **Supabase** — Postgres(DB), Auth(이메일 로그인), Storage(증거 파일), Edge Functions(서버 로직·LLM 호출)
- 실행 환경: **로컬 Supabase** (supabase CLI + Docker, `supabase start`). 클라우드 프로젝트는 쓰지 않는다.
- LLM 호출: **Supabase Edge Functions**(Deno/TypeScript)에서만 수행한다. LLM API 키는 Edge Functions 환경변수로만 주입하고 브라우저 번들에 절대 넣지 않는다.
- 인증: MVP에 Supabase Auth 이메일 로그인을 포함하고, 모든 테이블과 Storage 버킷에 RLS(Row Level Security)로 매장 소유권을 강제한다.
- 스키마 변경은 `supabase/migrations`의 SQL 마이그레이션으로만 한다.
- 테스트: Vitest(단위·컴포넌트·통합). 결정적 규칙(분류 엣지 케이스, 금칙 정책, 인사이트 감지)은 순수 TS 모듈로 분리해 LLM·DB 없이 단위 테스트 가능해야 한다.

### 결과

좋아지는 점:

- 프론트, 서버 로직, 테스트가 TypeScript 하나로 통일된다.
- DB·인증·스토리지·서버리스 함수를 Supabase 하나로 받아 별도 백엔드 서버 구현·운영이 없다.
- 로컬 CLI 실행으로 "코드는 로컬 전용, 외부 부작용 없음" 하네스 원칙이 유지된다.

감수할 점:

- Docker Desktop과 supabase CLI가 로컬에 필요하다.
- Edge Functions는 Deno 런타임이라 Node 라이브러리 호환성에 제약이 있다.
- 도메인 로직이 프론트·Edge Functions·SQL(RLS)로 분산될 수 있으므로 순수 TS 모듈 분리 규칙을 지켜야 한다.

후속 작업:

- `HARNESS/phases/PHASE_PLAN.md`와 각 Phase prompt를 이 스택 기준으로 유지한다.
- 배포 방식은 제품 Phase 2 이후 별도 ADR로 결정한다.

### 대안

#### FastAPI + PostgreSQL 별도 백엔드

기각. 언어가 Python·TS 둘로 나뉘고 서버 구현, 마이그레이션, 인증을 직접 만들어야 해서 MVP 범위 대비 무겁다.

#### 프론트에서 LLM 직접 호출

기각. LLM API 키가 브라우저 번들에 노출된다. Edge Functions 경유로 키를 서버 측에만 둔다.

#### Supabase 클라우드 프로젝트

보류. MVP는 로컬 CLI로 충분하고, 외부 서비스 의존과 자격증명 관리가 늘어난다. 배포 단계(제품 Phase 2 이후)에서 재검토한다.
