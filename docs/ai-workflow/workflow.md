# CareerSignal AI 개발 워크플로

## 1. 목적

이 워크플로는 Claude와 Codex가 같은 프로젝트 규칙을 따르며 계획, 구현, 테스트, 기능 검증, 코드 리뷰, 배포 확인을 역할별로 수행하는 절차를 정의한다. AI의 출력은 초안과 검증 근거이며 사용자가 범위, 우선순위, 반영 여부를 결정한다.

서비스 내부의 수집·통계·지식·해석·전략·로드맵 에이전트와 개발 협업 Agent는 서로 다른 계층이다. 이 문서는 CareerSignal을 개발하는 AI 협업만 다룬다.

## 2. 구성요소

| 구분 | 구성요소 | 책임 |
| --- | --- | --- |
| 규칙 | `AGENTS.md`, `CLAUDE.md` | 프로젝트 구조, Git, 문서, 검증 규칙 |
| Agent | `planner` | 작업 분해, 순서, 수용 기준 |
| Agent | `feature-verifier` | 요구사항과 실제 동작 대조 |
| Agent | `code-reviewer` | 코드 품질, 회귀, 보안, 테스트 누락 검토 |
| Skill | `design-workflow` | 화면 시안, 승인, 구현, 시각 검증 절차 |
| Skill | `generate-tests` | 테스트 사례, TDD, 실행과 결과 기록 절차 |
| 주 작업 Agent | Claude 또는 Codex | 승인된 범위의 실제 구현 |
| 결정 | 사용자 | 계획, 시안, 범위 변경, 최종 결과 승인 |

## 3. 실행 순서

### 3.1 계획

1. `planner`가 저장소와 관련 기준 문서를 읽는다.
2. 요구사항을 작업 단위, 의존 관계, 우선순위, 수용 기준으로 정리한다.
3. 사용자가 작업 크기, 순서, 제외 범위를 검토하고 계획을 승인한다.

### 3.2 디자인과 구현

1. 화면 구성 변경에는 주 작업 Agent가 `design-workflow`을 사용한다.
2. 저장소 밖의 HTML 시안을 사용자에게 제시한다.
3. 사용자가 시안을 승인하면 주 작업 Agent가 승인된 실행 환경만 수정한다.
4. 화면 작업이 아니면 승인된 계획에서 바로 구현한다.

### 3.3 테스트

1. 주 작업 Agent가 `generate-tests`를 사용해 수용 기준을 테스트 사례로 변환한다.
2. 한 기능은 가능한 경우 실패 테스트를 먼저 확인한다.
3. 대상 테스트와 관련 회귀 테스트를 실행한다.
4. 실행하지 못한 통합 검사는 이유와 조건을 기록한다.

### 3.4 독립 검증

1. `feature-verifier`가 수용 기준별 동작을 `PASS`, `FAIL`, `NOT_VERIFIED`로 판정한다.
2. `code-reviewer`가 승인 범위의 diff를 검토한다.
3. 실패와 차단 발견 사항은 사용자에게 돌아간다.
4. 사용자가 수정 범위를 정하면 주 작업 Agent가 수정하고 검증을 반복한다.

### 3.5 배포 확인

1. 프론트엔드 production build와 백엔드·에이전트 테스트 결과를 확인한다.
2. Vercel 프론트엔드 주소와 Render Health API 응답을 확인한다.
3. 배포 환경의 주소와 비밀값이 환경변수로 분리되어 있는지 확인한다.
4. 화면 요청이 Express와 Supabase 또는 FastAPI까지 이어지는지 확인한다.
5. 데모의 핵심 사용자 흐름과 오류 상태를 직접 실행한다.
6. 실패하면 배포 로그에서 원인을 확인하고 수정·재검증한다.

## 4. 승인 지점

| 지점 | 사용자 결정 |
| --- | --- |
| 계획 | 포함 범위, 제외 범위, 작업 순서, 수용 기준 |
| 시안 | 정보 구조, 화면 상태, 시각 방향 |
| 범위 변경 | 새 기능, 새 라이브러리, 예상 밖의 파일 변경 |
| 검증 | 실패 수정 여부와 재검증 범위 |
| 배포 | 공개 가능 여부와 데모 범위 |

## 5. 호출 방법

### 5.1 Claude

- 계획: `planner` Agent에게 요구사항과 관련 경로를 전달한다.
- 기능 검증: `feature-verifier` Agent에게 승인된 수용 기준과 검증 대상을 전달한다.
- 코드 리뷰: `code-reviewer` Agent에게 검토할 diff 범위를 전달한다.
- 디자인: `design-workflow` Skill에 화면 요구사항과 대상 실행 환경을 전달한다.
- 테스트: `generate-tests` Skill에 수용 기준과 테스트 대상을 전달한다.

Claude용 정의는 `.claude/`에 있고, 각 파일은 `.agents/`의 공통 정의를 기준으로 삼는다.

### 5.2 Codex

- Agent 역할은 `.agents/agents/<이름>.md`를 읽도록 지정하고 분석 전용 하위 Agent에 맡긴다.
- Skill은 `.agents/skills/<이름>/SKILL.md`를 읽도록 지정해 주 작업 Agent가 절차를 수행한다.
- 호출할 때 요구사항, 대상 경로, 허용 작업, 기대 출력 형식을 함께 전달한다.

`.agents/`는 두 도구가 공유하는 기준 정의다. 도구별 자동 탐색 여부와 무관하게 명시적 경로로 호출할 수 있다.

## 6. 안전한 점검

1. 작은 완료 기능 하나와 해당 수용 기준을 선택한다.
2. `planner`에는 파일 변경 없이 계획만 요청한다.
3. `feature-verifier`에는 읽기와 기존 테스트 실행만 허용한다.
4. `code-reviewer`에는 지정한 diff의 검토만 요청한다.
5. Skill은 결과 초안까지만 만들고 사용자의 승인 전에는 제품 코드를 수정하지 않는다.
6. 각 출력이 정해진 형식, 근거, 미확인 항목을 포함하는지 확인한다.

이 점검은 기존 구현을 변경하지 않으며 Agent와 Skill의 지시문이 프로젝트 규칙에 맞는지만 확인한다.

## 7. 공통 출력 원칙

- 확인한 사실, 추론, 미확인 상태를 구분한다.
- 테스트를 실행하지 못한 항목을 통과로 표현하지 않는다.
- 파일 경로, 테스트 명령, 화면 또는 응답을 검증 근거로 남긴다.
- Agent 결과를 자동으로 다음 단계에 반영하지 않는다.
- Git 브랜치 생성, 커밋, 병합, push는 사용자가 수행한다.
