# AI Agent Workflow

이 문서는 프로젝트 결과물과 함께 개발 과정을 소개할 때, AI 도구가 맡은 일과 사람이 확인한 일을 분명하게 보여주기 위한 기록입니다. 아맞다는 사람이 제품을 결정하고, AI 도구가 조사·정리·구현·검증을 돕는 방식으로 개발했습니다.

해결할 문제, 기능 우선순위, 화면 선택, 허용할 범위, 변경 내용을 검토하고 병합하도록 요청하는 Pull Request의 최종 병합은 사람이 결정했습니다. AI 도구는 정한 방향을 작업으로 나누고, 놓치기 쉬운 확인을 돕는 역할을 맡았습니다.

## 반복한 개발 흐름

### 1. 이슈로 목표를 분명히 합니다

먼저 GitHub Issue(작업의 목표와 완료 조건을 기록하는 항목)에 사용자가 얻을 결과, 변경 범위, 제외할 일, 완료 조건을 적습니다. 이 단계에서 만들 일과 제외할 일을 함께 정해 작업이 불필요하게 커지는 일을 막았습니다.

GitHub Project는 이슈의 우선순위와 진행 상태를 보여주는 작업판으로 사용했습니다. 다음 일을 고를 때는 아직 결정이 필요한 일, 사람이 직접 확인해야 하는 일, 선행 작업이 끝나지 않은 일을 구분했습니다.

### 2. 구현 전에 선택지를 비교합니다

화면이나 기능의 방향이 여러 갈래일 때는 선택지를 먼저 비교했습니다. `Office Hours`와 `grill-me`는 사용자 문제, 성공 기준, 숨은 가정을 질문으로 점검하는 데 사용했습니다. `brainstorming`은 가능한 접근을 둘 또는 셋으로 나누어 장단점을 비교하고, 사람이 선택할 수 있게 만드는 데 사용했습니다.

선택한 방향은 문장과 화면 예시로 확인한 뒤 명세로 남겼습니다. 명세에는 사용자에게 보이는 변화, 유지할 동작, 반응형 화면과 접근성처럼 반드시 지킬 조건을 적었습니다.

### 3. 구현 계획을 검토 가능한 단위로 바꿉니다

`writing-plans`는 승인된 명세를 파일별 작업 순서와 확인 방법으로 바꾸는 데 사용했습니다. 계획에는 어떤 파일을 왜 바꾸는지와 어떤 결과를 확인할지를 적습니다.

같은 계획을 제품, 디자인, 구현 관점에서 차례로 검토했습니다. `plan-ceo-review`는 제품 가치와 사용자에게 주는 의미를, `plan-design-review`는 화면의 정보 순서와 일관성을, `plan-eng-review`는 구현 범위와 유지보수 위험을 살폈습니다. 세 검토는 이미 선택한 방향의 빈틈을 찾는 데 집중했습니다.

### 4. 작업반장이 반복 절차를 정리합니다

`작업반장`은 아맞다 저장소를 위해 만든 Skill입니다. 여기서 Skill은 특정 상황에서 따라야 할 작업 방법을 정리한 안내서입니다.

작업반장은 GitHub Issue와 Project, 현재 작업 브랜치와 Pull Request 상태를 읽어 다음 단계를 판단합니다. 작업 브랜치는 기본 코드와 분리해 한 작업의 변경을 쌓는 공간입니다. 실행할 수 있는 이슈를 찾고, 최신 기본 브랜치인 `main`에서 작업 브랜치를 만들며, 리뷰 반영과 병합 뒤 정리까지 이어집니다.

도입 이유는 변경 이력을 관리하는 Git과 GitHub의 반복 절차를 매번 다시 설명하면서 생기는 누락을 줄이기 위해서였습니다. 제품 선택, 디자인 판단, 사람의 실제 기기 확인, 최종 병합은 사람이 맡고, 작업반장은 그 결정에 필요한 작업 상태와 절차를 정리합니다.

### 5. Codex와 서브에이전트가 승인된 범위를 구현합니다

`Codex`는 저장소의 코드와 문서, 이슈와 Pull Request를 함께 살펴보고 승인된 범위를 구현하는 주 작업 에이전트입니다. 변경 내용을 설명하고, 필요한 파일만 고치며, 커밋과 Pull Request에 무엇이 바뀌었는지 남깁니다.

`subagent-driven-development`는 독립적으로 나눌 수 있는 조사·구현·검토 작업에 사용했습니다. 서브에이전트는 하나의 좁은 일을 맡고 결과를 보고하며, 주 작업 에이전트와 사람이 결과를 확인합니다. 작은 문구 수정이나 단순한 화면 조정은 주 작업 에이전트가 직접 처리했습니다.

### 6. 변경 위험에 맞춰 확인합니다

`test-driven-development`는 새로운 동작이나 오류 수정처럼 기대 결과가 분명한 경우에 사용했습니다. 먼저 실패하는 확인을 만들거나 기존 확인이 실패하는지 보고, 필요한 만큼만 코드를 고쳐 통과시키는 방식입니다.

작업 성격에 따라 확인 방법을 정했습니다. 문구, 순수한 시각 조정, 문서는 관련 형식 검사·빌드·직접 화면 확인으로 확인합니다. 저장 방식, 인증, 오류 복구처럼 사용자 데이터나 핵심 흐름에 영향을 주는 변경은 그 행동을 확인하는 테스트가 필요합니다.

`gstack QA·Review`는 실제 브라우저에서 화면 크기, 키보드 조작, 접근성, 주요 사용자 흐름을 확인하는 데 사용했습니다. 자동 확인과 함께 화면이 의도대로 보이는지 확인하고, 실제 기기·로그인·외부 서비스처럼 사람이 직접 확인해야 하는 조건은 별도로 남겼습니다.

### 7. 리뷰와 병합은 사람이 마무리합니다

`CodeRabbit`은 Pull Request의 변경을 자동으로 검토합니다. 제안은 코드와 이슈에 적은 약속에 맞는지 확인한 뒤, 타당한 것만 반영했습니다.

리뷰 반영 뒤에는 바뀐 부분과 직접 관련된 확인만 다시 실행합니다. 최종 화면 확인과 Pull Request 병합은 사람이 맡습니다. 병합이 확인된 뒤 작업반장이 이슈와 Project 상태를 정리하고, 다음에 시작할 수 있는 일을 다시 확인합니다.

## 다음 작업을 시작할 때 쓰는 템플릿

반복 작업은 아래 질문에 답하면서 시작했습니다.

1. 사용자가 달라졌다고 느껴야 하는 결과는 무엇인가요?
2. 이번 작업에서 바꾸는 것과 바꾸지 않는 것은 무엇인가요?
3. 제품·디자인·보안처럼 사람이 먼저 결정해야 하는 선택은 있나요?
4. 이슈의 완료 조건을 확인하려면 어떤 증거가 필요한가요?
5. 동작을 바꾼다면 어떤 테스트가 필요한가요? 동작을 바꾸지 않는다면 왜 테스트가 필요 없는가요?
6. 실제 기기, 로그인, 외부 서비스처럼 자동으로 확인할 수 없는 조건은 무엇인가요?
7. Pull Request에서 사람이 가장 먼저 볼 항목은 무엇인가요?

이 질문의 답이 분명하면 이슈를 만들고, 최신 기본 브랜치인 `main`에서 작업 브랜치를 만듭니다. 구현 뒤에는 실제로 실행한 확인과 남은 조건을 구분해 기록합니다.

이 문서에 적은 흐름은 각 도구의 역할과 사람이 책임져야 할 판단을 구분해 둔 기록입니다. 이후에도 새 작업은 이 흐름을 참고해 필요한 절차만 골라 진행합니다.
