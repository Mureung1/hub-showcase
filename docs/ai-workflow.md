# 나만의 AI 협업 워크플로우 (3주 회고)

> Beacon을 만들며 Claude Code와 어떻게 일해 왔는지 정리한 문서. 3주차 마무리 발표의 근거 자료.

## 한 줄 요약

**계획 → 구현 → 검증 → 기록**의 주간 사이클을 매번 같은 순서로 돌리되, 각 단계마다 **전용 스킬**을 붙이고 무거운 작업은 **서브에이전트에 위임**한다. 문서(`docs/`)를 단일 원천으로 삼아 대화가 길어져도 맥락이 흔들리지 않게 한다.

## 원칙 3가지

1. **문서가 진실의 원천.** 코드보다 먼저 `plan.md`(기획)·`prd.md`(스펙)·`design.md`(디자인)·`roadmap.md`(실행)를 본다. AI에게 "무엇을/왜"를 매번 설명하지 않고 문서를 가리킨다.
2. **작업마다 전용 스킬.** 계획·구현·검증·PR 작성을 각각 스킬로 고정해, 매번 즉흥으로 지시하지 않고 **같은 규율**을 재현한다.
3. **위임과 압축으로 컨텍스트를 아낀다.** 탐색·구현은 서브에이전트에 맡기고, 결과만 메인 맥락에 남긴다.

---

## 주간 사이클 — 4단계와 스킬 매핑

```
[월] 계획          [화~목] 구현              [수시] 검증              [매일 끝] 기록
weekly-plan  →  tdd-feature-loop  →  verify-feature-requirements  →  daily-pr
                + beacon-design(UI)
```

### 1단계 · 계획 — `weekly-plan`
- **언제**: 새로운 "N주차"를 시작하는 월요일.
- **무엇을**: 루트·`docs/`의 모든 md를 읽어 그 주 목표·우선순위·수용 기준을 뽑고, 평일 5일 크기의 task로 쪼갠다. 의존성/마이그레이션이 있는 작업을 앞쪽에 배치하고 Day 5는 통합·버퍼로 둔다.
- **게이트**: Day 1~5 표를 보여주고 **명시적 승인**을 받은 뒤에만 Notion 보드(`Naver AI Agent Challenge` → `N주차` 페이지 → 일별 태스크 DB)로 배선한다. 승인 전에는 쓰지 않는다.

### 2단계 · 구현 — `tdd-feature-loop` (+ UI는 `beacon-design`)
- **`tdd-feature-loop`**: 기능 하나를 Given/When/Then 수용 기준으로 좁힌 뒤 **실패하는 테스트 먼저(Red)** → **최소 구현(Green)** → 리팩터. 새 테스트 + 전체 테스트 → `lint` → `build`를 한 번에 돌려 함께 보고한다. 범위 밖은 명시하고 통과를 위한 임의 스키마 변경·모킹을 넣지 않는다.
- **`beacon-design`**: UI를 만들거나 스타일링할 때 항상 `docs/design.md`를 단일 원천으로 삼는다. 색·라운드·그림자는 **CSS 토큰 변수로만**(하드코딩 금지), 공용 클래스(`.card`·`.badge`·`.pill`·`.btn.accent` 등)를 재사용. 인디고 accent는 브랜드/CTA/에이전트 전용, 국내 관례색(상승·매수=빨강 / 하락·매도=파랑 / 관망=앰버) 유지.

### 3단계 · 검증 — `verify-feature-requirements`
- **독립 읽기 전용 에이전트.** 코드를 절대 수정하지 않고, 수용 기준을 원자 단위로 쪼갠 뒤 `git diff`·관련 코드·테스트·lint·build를 근거로 각 항목을 **PASS / FAIL / NOT VERIFIED**로 판정한다.
- **정직성 규율**: 추정으로 PASS를 주지 않는다. 외부 서비스(Discord·KIS) 라이브 경로를 실제로 돌리지 않았으면 **"NOT VERIFIED"로 명시**한다. → `roadmap.md`에 "⚠️ 멀티유저 라이브 E2E 미실시"처럼 남는 이유.

### 4단계 · 기록 — `daily-pr`
- **언제**: 하루 작업 끝.
- **무엇을**: 그날 커밋을 모아 부트캠프 PR 템플릿 4개 섹션(**주요 작업 / 내가 설명할 수 있는 부분 / 아직 이해 못 한 부분 / 새로 알게 된 것**)을 겸손한 1인칭 회고체로 채운 **붙여넣기용** 초안을 만든다. 파일 경로·함수명은 본문에 넣지 않고, PR을 직접 생성하지도 않는다(사람이 붙여넣음).
- **CI 연동**: `.github/workflows/auto-merge.yml`가 매일 자동 머지하되, `main` 대상이거나 `review` 라벨이 붙은 PR은 건너뛴다 → 리뷰가 필요하면 라벨로 옵트아웃.

## 위임 전략 — 모델·서브에이전트

- **모델 위임**: 오케스트레이션(계획·분배·판단)은 빠른 상위 모델이 잡고, 실제 구현은 Sonnet/Opus **서브에이전트**에 맡긴다. 메인 스레드는 "무엇을 시킬지"에 집중.
- **병렬 탐색**: 코드베이스를 파악할 때 `Explore` 에이전트를 **여러 개 병렬**로 띄워(예: "이번 주 태스크 상태" + "AI 협업 워크플로우") 각자 다른 영역을 훑게 하고, 결론만 회수한다.
- **컨텍스트 압축(`caveman`/`cavecrew`)**: 서브에이전트 결과를 압축해 메인 맥락에 남겨 긴 세션에서도 컨텍스트가 오래 간다.

## 컨텍스트 관리

- `CLAUDE.md`에 컨벤션·핵심 결정을 못 박아 매 세션 시작 시 자동 로드.
- `docs/`를 역할별 단일 원천으로 분리(plan/prd/design/roadmap/discord-linking) → 중복 설명 제거.
- 지속 메모리에 "이 프로젝트에서 결정한 방식"(모델 위임·디자인 토큰 스왑·주차 계획)을 저장해 세션이 바뀌어도 이어간다.

## 핵심 설계 결정이 워크플로우에 준 영향

- **에이전트 배치**: 복기(review)는 1-shot LLM 호출이 아니라, 도구 3종(`search_past_trades`·`get_price_context`·`get_past_reviews`)을 **스스로 다단계 호출**해 근거를 모으는 코칭 에이전트. 감시는 스케줄러(Cron)가 하고 **알림 문구만** 에이전트가 만든다. → "어디에 에이전트를 두는가"를 먼저 정하니 구현 범위가 명확해졌다.
- **디자인 = `design.md` 단일 원천 + 토큰**: 디자인 레퍼런스가 바뀌어도 **토큰 값만 스왑**하고 변수명·컴포넌트는 그대로 → 컴포넌트를 다시 안 건드림.
- **DB = RLS 전제**: 1인용 MVP도 처음부터 RLS로 설계해 2단계 다중 사용자 전환 비용을 낮췄다.
- **자본시장법 경계 = 거울 프레임**: AI가 추천·가치평가·미래지시를 하지 않고 사용자 자신의 과거 행동만 비추도록 프롬프트 가드레일을 넣었다.

## 배운 점 / 다음 주 개선

- **테스트 우선이 검증을 쉽게 한다**: Red→Green 기록이 남으니 `verify` 단계에서 근거를 찾기 쉬웠다.
- **정직한 NOT VERIFIED가 부채를 가시화한다**: 단위 테스트 통과 ≠ 라이브 E2E. 이 구분을 문서에 남긴 덕에 WP-H(멀티유저 라이브 E2E)가 명확한 다음 작업으로 남았다.
- **다음 주**: 외부 의존(Discord 2계정·KIS) 라이브 E2E를 사이클 안에 정례화하고, 알림 "메모리 한 줄"의 에이전트화를 재검토한다.
