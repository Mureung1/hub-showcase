### GitHub API 클라이언트: @octokit/rest + @octokit/graphql (용도별 분담)
- 날짜: 2026-07-09
- 배경/문제: 프로필 분석·레포/이슈 조회에 GitHub API를 호출해야 함. 비인증 60회/시간 제한, 페이지네이션, rate limit 헤더 처리가 필요. GitHub는 REST와 GraphQL을 모두 제공하며, 작업 성격에 따라 유불리가 다름.
- 선택한 방안: 공식 클라이언트 계열을 용도별로 나눠 사용.
  - **프로필 분석 → GraphQL (`@octokit/graphql`)**: 레포 목록 + 언어 비율 + 커밋/PR 이력을 한 쿼리로 조회해 REST의 N+1 호출을 회피.
  - **이슈 검색 → REST (`@octokit/rest`의 `/search/issues`)**: 라벨·언어 필터 검색이 단순하고 직관적.
  - 우리 서버가 프론트에 노출하는 API는 REST로만 제공하고, GitHub의 GraphQL 호출은 백엔드 내부 구현으로 감춘다(우리 쪽 GraphQL 서버는 만들지 않음).
- 고려했던 대안: `axios`로 직접 호출 (KNU_Capstone_Backend에서 사용해 익숙) / REST만으로 프로필 분석까지 처리.
- 이유: 인증·페이지네이션·rate limit 처리가 내장돼 보일러플레이트가 줄고, GitHub 전용이라 유지보수가 편함. 프로필 분석은 중첩·집계 데이터라 GraphQL이 호출 수·전송량 모두 유리하고, 검색은 REST가 간단해 각각의 강점을 취함.

### DB(MongoDB) 저장 범위: 분석·추천까지 저장
- 날짜: 2026-07-09
- 배경/문제: GitHub API rate limit 대응과 재조회/필터링 지원을 위해 어디까지 영속화할지 결정 필요. 단, 공개 GitHub 정보만 사용하고 별도 개인정보는 수집하지 않음(plan §6).
- 선택한 방안: 프로필 분석 결과와 추천 결과까지 저장. 컬렉션 설계는 아래 참조.
- 고려했던 대안: (a) 캐시 최소(레포/이슈 캐시 + API 사용량만, 분석·추천은 stateless로 매번 계산) (b) 북마크·기여 이력까지 포함한 풀 스키마.
- 이유: (a)는 재조회가 느리고 API를 더 소모, (b)는 MVP 범위를 넘음. 분석·추천 저장이 plan의 MVP 기능(재조회/필터링)과 정확히 일치하며 rate limit 방어에도 유리. 북마크·이력은 향후 확장으로 미룸.

#### DB 컬렉션 설계 (초안)
> 상세 스키마·인덱스는 백엔드 착수 시 [architecture.md](architecture.md)에 확정. 여기서는 저장 범위 결정에 따른 컬렉션 윤곽만 기록.

- **Analysis** — 프로필 분석 결과 캐시
  - `githubId`(unique index), `languages[]`, `skillLevel`, `activitySummary`(커밋/PR 수, 기여 레포 등), `analyzedAt`
- **RepoCache** — 레포 메타 캐시(rate limit 대응)
  - `fullName`(owner/repo, unique index), `description`, `primaryLanguage`, `languages[]`, `stars`, `topics[]`, `goodFirstIssueCount`, `fetchedAt`
- **IssueCache** — 이슈 메타 캐시
  - `repoFullName` + `number`(복합 index), `title`, `labels[]`, `difficulty`, `url`, `state`, `fetchedAt`
- **Recommendation** — 추천 결과(재조회/필터링용)
  - `githubId`, 선호조건 스냅샷(`languages[]`, `difficulty`, `topics[]`), `items[]`(`repoFullName`, `issueNumber`, `matchScore`, `reason`), `createdAt`
- **ApiUsage** — GitHub 토큰 rate limit 추적 (KNU 패턴 재사용)
  - 토큰/날짜 키, `count`

공통: 캐시 컬렉션은 `fetchedAt` 기준 만료 처리(TTL 또는 조회 시 갱신), 스키마에 `timestamps: true`.

### DB 전환: MongoDB → Supabase(PostgreSQL) + Prisma
- 날짜: 2026-07-13
- 배경/문제: 백엔드 착수 직전, MongoDB 결정(2026-07-09)을 재검토. 저장 데이터가 캐시·스냅샷 성격이라 문서 DB 우위로 판단했으나, 그 근거가 결정적인지 다시 확인 필요.
- 선택한 방안: Supabase 무료 티어(PostgreSQL) + Prisma ORM. 기존 컬렉션 윤곽은 테이블로 매핑(`analyses`, `repo_cache`, `issue_cache`, `recommendations` + `recommendation_items` FK 분리, `api_usage`). 배열은 `text[]`, 요약·스냅샷은 `JSONB`.
- 고려했던 대안: (a) MongoDB Atlas 유지(기존 결정) (b) 기존에 사용 중인 Atlas 클러스터에 DB만 분리해 공용 사용.
- 이유:
  - Mongo의 우위였던 "배열·중첩 데이터"는 Postgres의 네이티브 배열·JSONB로 충분히 커버 — 결정타가 아니었음.
  - 향후 확장(북마크, 기여 이력, 활동 기반 스코어링)은 관계·집계 중심이라 SQL이 유리. "관계 복잡해지면 전환" 예정이었다면 코드 착수 전인 지금이 전환 비용 0인 시점.
  - `Recommendation.items[]` 임베딩을 FK 분리로 바꾸면 추천-레포/이슈 관계가 스키마로 명시됨.
  - 국내 백엔드 취업 시장이 RDB 중심이라 포트폴리오 통용 범위가 넓음.
- 주의: Supabase 무료 티어는 1주 비활성 시 프로젝트 일시정지 → 데모 시연 전 상태 확인 또는 주기적 ping 필요. 캐시 만료는 TTL 인덱스 대신 조회 시 `fetched_at` 검사로 처리.

### 이슈 분석 기능: 경량 LLM API 도입 — 지연 생성 + 캐싱
- 날짜: 2026-07-14
- 배경/문제: 추천 상세 화면의 "기여 시작 가이드"가 이슈와 무관한 고정 문구뿐. 이슈 본문·코멘트를 분석해 요약/필요 기술/시작 가이드를 제공해 "초보자가 이슈를 보고 겁먹지 않게" 하는 핵심 가치를 채우고 싶음.
- 선택한 방안: 경량(저비용) LLM API로 이슈 분석. **제공자/모델은 구현 착수 시(W3) 확정** — 각 제공자의 경량 티어 기준 이슈 1건당 $0.01 미만이라 어느 쪽이든 비용은 무시 가능. JSON 스키마 보장 기능(structured outputs/JSON 모드)이 있는 제공자를 우선한다: 응답 `{issueSummary, requiredSkills, guide[]}` 파싱 안정성 확보.
  - **지연 생성(lazy)**: 추천 목록 생성 시가 아니라 사용자가 상세 화면에 진입한 이슈만 그 시점에 분석 — 안 열어본 이슈엔 비용 0, 추천 API 응답 속도 유지.
  - **캐싱**: 분석 결과를 `issue_cache`에 저장해 같은 이슈는 재분석하지 않음.
- 고려했던 대안: 규칙 기반 분석(본문 길이·코드블록·라벨 등 휴리스틱) — 비용 0이지만 요약 품질이 얕음.
- 이유: 경량 모델 기준 비용이 무시 가능한 수준이고 lazy+캐싱으로 실비용은 0에 수렴. 구현도 `services/`에 llmService 추가 정도로 가벼움. 포트폴리오 관점에서 LLM 연동 경험 어필 포인트.
- 주의: API 키는 `.env`로 관리(커밋 금지). LLM 호출 실패/rate limit 시 분석 필드 없이 상세 화면이 정상 동작하도록 폴백(필드는 명세상 옵셔널). 제공자 교체가 쉽도록 호출부는 `llmService` 한 곳에 격리.

### 프로필 분석: 언어 비율은 최근 12개월 커밋 가중 + skillLevel 판정 규칙
- 날짜: 2026-07-15
- 배경/문제: 초기 구현(본인 소유 레포의 언어별 바이트 합산)이 실사용자 검증에서 체감과 어긋남 — 파일 용량 큰 옛 Swift 레포가 1위로 나오고, 조직 레포(캡스톤·인턴십)의 Java 작업은 OWNER 필터에 걸려 통째로 누락.
- 선택한 방안: `contributionsCollection.commitContributionsByRepository`(최근 12개월, 조직 레포 포함)로 레포별 커밋 수를 얻고, 각 레포의 언어 구성 비율을 **커밋 수로 가중 평균**. 반올림 후 1% 미만 언어는 표시 제외. skillLevel 규칙: advanced = 커밋 300+ 그리고 (PR 20+ 또는 기여 레포 3+) / intermediate = 커밋 50+ 또는 PR 5+ 또는 타인 레포 기여 1+ / 나머지 beginner.
- 고려했던 대안: (a) 바이트 기준 유지 + 최근 푸시 순 정렬(부분 보완) (b) 레포별 커밋 히스토리 전수 조회(정확하지만 N+1).
- 이유: "레포에 쌓인 코드 용량"이 아니라 "최근에 실제로 작성한 언어"가 첫 기여 추천의 입력으로 옳음. 쿼리 1개 유지(N+1 회피). 검증 결과 본인 계정이 Swift 43% → Java 47%로 체감과 일치. advanced 조건을 AND에서 완화한 것은 자기 레포 위주 활동자(예: torvalds)는 contributedRepos가 0이라 영원히 도달 불가한 결함 때문.
- 주의: 커밋 수는 최근 12개월 한정(GraphQL 제약). 언어 구성은 여전히 레포 내부 바이트 비율 기반이므로 레포 간 비중만 커밋이 정함.

### 프로필 레포 표시: 최근 활동(1년·소속 포함)과 기여 이력(평생·외부만) 분리
- 날짜: 2026-07-15
- 배경/문제: "어디에 기여했는가"를 프로필에 보여주고 싶은데, GitHub의 소유 개념과 사용자 체감이 어긋남 — 소속 조직(캡스톤·인턴십) 레포는 GitHub상 '타인 소유'라 기여 이력에 섞이고, 정작 진짜 오픈소스 기여(kakao/actionbase, 1커밋)는 언어 비율에 묻힘.
- 선택한 방안: 두 목록으로 분리. `recentRepos` = 최근 12개월 커밋한 모든 레포(본인+소속 조직, 커밋 수 표시), `contributionHistory` = 진짜 외부 레포 기여만(평생, 스타 수 표시). 외부 판별 = 본인/소속 조직(`organizations`, read:org 스코프) 소유가 아니고 스타 10개 이상.
- 고려했던 대안: (a) 소유 기준만으로 분리(조직 레포가 기여 이력에 섞임) (b) 조직 필터만 사용(비공개 멤버십이면 누수) (c) 스타 컷만 사용(유명 조직 소속원의 사내 레포 오분류).
- 이유: 조직 필터+스타 컷 병행이 서로의 구멍을 메움 — 멤버십이 비공개라도 팀프로젝트류는 스타가 없어 걸러짐. 기여 이력은 기간 제한이 없어 오래된 오픈소스 기여도 유지(첫 기여자 대상 서비스에서 강한 동기부여 신호). 레포별 평생 커밋 수는 N+1이라 제공하지 않음.
- 주의: GitHub GraphQL `repositoriesContributedTo`의 `orderBy: STARGAZERS`가 실제 정렬을 보장하지 않아 코드에서 직접 정렬(상위 N 자르기 전에 정렬 필수). 서버 토큰에 read:org 스코프 필요(.env.example 기록).

### 분석 캐시 TTL: POST 24시간 재사용 + GET 7일 경과 시 재분석 (조회 시점 검사)
- 날짜: 2026-07-16
- 배경/문제: 캐시(analyses) 구현 시 두 가지 수명 정책이 필요 — POST 재분석 요청은 얼마나 캐시를 재사용할지, GET 조회는 얼마나 오래된 기록까지 그대로 돌려줄지. 오래된 기록의 정리 방식(배치 삭제 vs 조회 시점 검사)도 결정 필요.
- 선택한 방안: POST는 24시간 이내 캐시 재사용(기존 명세 유지). GET은 7일 이내면 저장본 반환, 7일 초과면 낡은 프로필로 보고 재분석해 갱신본 반환. 만료 행은 삭제하지 않고 조회 시점에 analyzedAt 검사로 처리(스키마 주석의 기존 원칙과 일치).
- 고려했던 대안: (a) GET은 신선도 무관 마지막 기록 반환(영원히 낡은 프로필 노출 가능) (b) 주기 배치로 만료 행 삭제(크론 인프라 추가 필요, 삭제 직후 GET이 404가 되어 UX 후퇴).
- 이유: GitHub 활동은 주 단위로 유의미하게 변하므로 7일이 "새로고침인데 낡은 데이터" 체감을 막는 적정선. 배치 없이 조회 시점 검사만으로 동작해 인프라가 늘지 않고, 재분석이 자연스럽게 캐시를 덧씌워 삭제가 불필요.
- 주의: GET이 7일 경과 기록을 만나면 GitHub 호출이 발생하므로 "GET은 호출 없음" 가정은 7일 이내에만 성립(openapi.yaml 갱신됨).

### 추천 후보 수집: 이슈 우선 검색 → 레포 우선 검색으로 전환
- 날짜: 2026-07-20
- 배경/문제: 초기 구현(REST `/search/issues`로 good first issue 검색)의 스모크 테스트에서 스타 0개·갓 생성된 유령 레포가 상위에 노출. 이슈 검색 qualifier에는 레포 품질 조건(stars, pushed)이 없어 사후 필터로 거르면 후보가 텅 비는 문제.
- 선택한 방안: 레포 검색(`/search/repositories`)을 먼저 수행 — `stars:>=100 pushed:>=3개월 good-first-issues:>=2 archived:false`로 "건강한 레포"를 검색 단계에서 보장하고, 그 레포들의 담당자 없는 오픈 이슈를 GraphQL 쿼리 1개로 일괄 조회(#5의 N+1 회피 패턴 재사용). 언어당 결과가 5개 미만이면 스타 기준을 20으로 낮춰 재검색(니치 언어 폴백).
- 고려했던 대안: (a) 이슈 우선 검색 유지 + 사후 필터(후보 고갈 위험) (b) per_page 확대(유령 레포 비율은 그대로).
- 이유: 첫 기여자에게 중요한 것은 이슈의 신선도보다 리뷰해줄 메인테이너의 생존. 레포 품질 신호(stars/pushed/gfi 문화)는 전부 레포 속성이므로 레포에서 출발하는 것이 자연스럽고, 호출 수는 동일(검색 1 + GraphQL 1). 2026-07-09 결정의 "이슈 검색 → REST"는 이 구조로 대체(기존 `searchIssues`는 보조 수집용으로만 유지).

### 추천 기준: 문턱(레포 건강) → 규칙 점수(능력 정합) → LLM 재순위(흥미·이슈 명확성) 3단 구조
- 날짜: 2026-07-20
- 배경/문제: 언어·난이도만으로 추천하면 같은 조건의 사용자가 모두 같은 목록을 받음(개인화 부재). 또한 목적함수("첫 PR이 머지될 확률 최대화")를 어떤 기준으로 분해할지 정리 필요.
- 선택한 방안: 3단 구조로 역할 분리 — ① **문턱**: 레포 수용성(메인테이너 생존·입문 문화·선점 여부)은 점수가 아니라 하드 필터(검색 qualifier)로 미달 시 제외 ② **규칙 점수**: 정량 신호(언어 일치·난이도 라벨·스타·활동성) + skillLevel↔난이도 정합(화요일 추가 예정) ③ **LLM 재순위**: 프로필 컨텍스트(recentRepos·contributionHistory) 기반 흥미 매칭과 이슈 본문 명확성 판단 — 규칙으로 불가능한 정성 영역만 담당(#6에서 구현, 실패 시 규칙 점수로 폴백).
- 고려했던 대안: (a) 규칙 점수에 기준을 계속 추가(점수가 평평해져 변별력 붕괴) (b) LLM에 추천 전체 위임(존재하지 않는 레포 환각·건강성 검증 불가) (c) 의존성 마이닝(사용자 레포의 매니페스트에서 실사용 라이브러리 추출) — 효과 최대지만 W3 일정상 4순위로 보류, W4/향후 확장 카드.
- 이유: 사실 검증이 필요한 영역(레포 건강)은 결정적 규칙이, 취향·문맥 영역은 LLM이 각자 잘하는 것만 맡는 분담. LLM 실패가 서비스 실패로 번지지 않는 폴백이 공짜로 확보됨. 규칙 동점 뭉침(85점 도배)·analysis 미활용 문제도 이 구조가 해소.

### hard 난이도 = 기능 구현급(enhancement) 이슈
- 날짜: 2026-07-20
- 배경/문제: 초기 구현은 "gfi도 help wanted도 아닌 라벨 = hard"로 판정하고 hard 검색은 라벨 무관이었음. 코드리뷰에서 모순 발견 — hard 선택 시 question/discussion 잡탕 이슈가 섞이고, gfi 라벨 이슈가 easy로 표시되어 난이도 가점도 어긋남. "라벨 없음"은 어려움이 아니라 미분류일 뿐.
- 선택한 방안: hard를 "기능 구현급 이슈"로 정의 — 검색 라벨 필터를 `enhancement`로 지정, 추천 이유 문구도 "기능 구현급 이슈라 도전할 만해요"로 정합. 난이도 판정 우선순위는 gfi(easy) > help wanted(medium) > 나머지(hard) 유지 — enhancement+gfi 복합 라벨은 입문자용 기능 이슈이므로 easy가 맞음.
- 고려했던 대안: (a) 미분류로 인정하고 문구만 정직하게(정보 가치 낮음) (b) hard 옵션 제거(명세·FE 변경 범위가 가장 큼).
- 이유: 첫 기여 서비스에서 hard의 실용적 의미는 "버그 리포트 너머의 기능 구현에 도전"이며, enhancement 라벨이 그 의도를 가장 잘 포착. 검색 잡탕 문제도 라벨 필터로 함께 해소.
- 주의: GraphQL `filterBy.labels`는 AND 매칭이라 enhancement/feature를 OR로 묶을 수 없어 가장 보편적인 `enhancement` 하나로 시작 — 결과 부족하면 feature 라벨 2차 검색을 추후 검토.

### 이슈 분석(#6) LLM 실패 시 폴백: 캐시는 성공 결과만 저장, TTL 없음
- 날짜: 2026-07-21
- 배경/문제: #6 착수 전 설계 논의. LLM 호출은 실패할 수 있는데(rate limit·타임아웃·스키마 위반), 이때 캐시된 값이 있는 경우/없는 경우를 각각 어떻게 응답할지, 그리고 실패 결과 자체를 캐시에 남길지 미정이었음.
- 선택한 방안: (1) `issue_cache`엔 **LLM 호출이 성공했을 때만** `issueSummary`/`requiredSkills`/`guide`를 쓴다 — 실패 결과(null)는 절대 저장하지 않는다. (2) 캐시된 값이 있으면 최신 여부와 무관하게 그대로 반환한다(TTL 없이 "한 번 성공하면 영구 캐시" — `Analysis`의 7일 TTL과는 다른 정책). (3) 캐시가 없는데 LLM이 실패하면 `issueSummary` 등 필드를 null로 둔 채 200을 정상 응답한다 — 에러 페이지로 내리지 않는다(상세 화면의 핵심 정보는 LLM 없이도 이미 완전함).
- 고려했던 대안: (a) 실패도 캐시에 기록해 재시도 폭주를 막는 방식 — 기각. null을 캐시하면 다음 조회가 "캐시 히트"로 처리돼 영원히 재시도가 안 됨 (b) 이슈 분석에도 `Analysis`처럼 N일 TTL을 둬서 주기적 재생성 — 기각. 이슈 본문·코멘트는 프로필과 달리 정적이라 낡아도 신뢰도 저하가 크지 않고, TTL은 LLM 비용만 늘림(이슈 #6의 "실비용 0에 수렴" 목표와 배치).
- 이유: "캐시에 성공만 남긴다"는 규칙 하나로 재시도 로직을 별도로 안 만들어도 **다음 조회가 곧 재시도**가 되는 복원력이 공짜로 생김. 에러 페이지를 안 쓰는 것도 같은 맥락 — LLM 파트 실패가 핵심 기능(추천 목록·이슈 링크) 접근을 막으면 안 됨.
- 참고: `docs/openapi.yaml`의 `issueSummary`/`requiredSkills`/`guide`는 이미 옵셔널로 명세돼 있어 이 정책과 스키마 변경 없이 바로 맞음.

### 이슈 분석·재순위(#6) LLM 제공자: Google Gemini (Flash / Flash-Lite) 무료 티어
- 날짜: 2026-07-21
- 배경/문제: #6 착수 전 설계 논의. "경량 티어 기준 비용·JSON 스키마 보장 기능 비교 후 선택"이 이슈에 명시된 조건. 배포용 개인 인스턴스가 없어 무료 티어 전제([decisions.md](decisions.md) 2026-07-13 Node.js 유지 결정과 같은 제약)라, LLM도 완전 무료로 쓸 수 있는 제공자가 필요했음. Claude API는 claude.ai Pro 구독과 별개로 종량 과금되어 제외.
- 선택한 방안: **Google Gemini API 무료 티어**(Flash / Flash-Lite 모델, `response_mime_type: application/json` + `response_schema`로 JSON 강제). 카드 등록 없이 무료, `issueSummary`/`requiredSkills`/`guide` 스키마를 안정적으로 강제할 수 있음.
- 고려했던 대안: (a) Groq 무료 티어 — 오픈웨이트 모델(Llama 등) 기준 요청 한도는 더 넉넉하고(`llama-3.1-8b-instant` 기준 일 14,400회) 속도도 빠르지만, JSON 강제 기능의 검증된 안정성이 Gemini만큼 확실치 않고 소형 오픈웨이트 모델이라 요약 품질이 상대적으로 낮을 것으로 판단 (b) Claude API — 코드 품질·structured outputs는 검증됐지만 Pro 구독과 무관하게 과금돼 "완전 무료" 조건에 안 맞음.
- 이유: 사용자가 Gemini·Groq 둘 다 실제 써본 경험상 Gemini가 낫다고 판단(2026-07-21). 이슈 #6의 핵심 요구사항(JSON 스키마 보장)에서 Gemini의 `response_schema`가 가장 안정적. 무료 티어 한도(분당 15~30요청 수준, 계정별 상이)는 이슈 상세 지연생성+캐시, 추천 1건당 1회 재순위 정도의 트래픽엔 충분.
- 주의: Google이 예고 없이 무료 한도를 조정한 전례가 있음(2025-12 대폭 축소 사례) — 다만 앞선 결정("LLM 실패 시 폴백")이 rate limit 초과도 동일하게 흡수하므로 별도 대응 불필요.
- 참고: 2026-07-13 결정(무료 티어 호스팅 전제로 Node.js 유지)과 같은 제약 축.

- 날짜: 2026-07-21

### 이슈 상세 분석(#6) API: 새 엔드포인트 대신 GET /api/recommendations/{id}에 선택적 쿼리 파라미터 추가
- 날짜: 2026-07-23
- 배경/문제: #6 구현 착수. "상세 화면에 진입한 이슈 1건만 그 시점에 분석"(2026-07-14 결정)을 실제로 동작시키려면 FE가 상세 진입 시 재요청을 보내야 하는데, 이때 새 전용 엔드포인트를 만들지 기존 조회 엔드포인트를 확장할지 결정이 필요했음. `docs/openapi.yaml`의 `GET /api/recommendations/{id}` 설명은 이미 2026-07-14 시점부터 "상세 화면 진입 시 해당 이슈의 LLM 분석이 지연 생성된다"고 이 엔드포인트를 지목해 서술하고 있었음.
- 선택한 방안: `GET /api/recommendations/{id}`에 선택적 쿼리 파라미터 `repoFullName`/`issueNumber`를 추가. 없으면 캐시된 분석값만 병합(LLM 미호출, 비용 0), 있고 해당 이슈가 아직 미분석이면 그 1건만 LLM 분석 후 `IssueCache`에 영구 저장.
- 고려했던 대안: 이슈 단건 분석 전용 새 엔드포인트(`GET /api/recommendations/{id}/items/{position}/analysis` 등) — 기각. 이미 커밋된 API 문서·계약과 어긋나고, FE가 파라미터를 안 보내는 기존 호출과의 하위 호환을 별도로 신경 써야 함.
- 이유: 파라미터를 안 보내는 기존 호출은 동작이 전혀 바뀌지 않아 하위 호환이 자동으로 보장되고, 이미 문서화된 엔드포인트 설명과 일치해 계약 일관성이 유지됨.

### LLM 재순위(#6 3단 구조 ③) 대상 범위·트리거·보정 방식
- 날짜: 2026-07-23
- 배경/문제: 2026-07-20 결정("문턱 → 규칙 점수 → LLM 재순위" 3단 구조)에서 3단계 자체는 미구현 상태였음. 재순위를 언제(트리거), 무엇에(대상 범위), 어떻게(점수 반영 방식) 적용할지 미정이었음.
- 선택한 방안: (1) **대상**: 목록에 노출되는 최종 `MAX_ITEMS`(10)건만 — 트리밍 전 후보군(최대 24개)은 제외. (2) **트리거**: 추천 생성(`POST /api/recommendations`) 시점, 트리밍 직후 저장 직전. (3) **보정**: 규칙 점수(`scoreItem`)를 뼈대로 LLM이 `matchScore`에 -15~+15 가감(`isValidRerankResult`로 범위 강제), `reason`은 성공 시 LLM이 흥미·문맥 반영해 다시 씀·실패 시 규칙 reason 유지. (4) **입력**: 이슈 본문(명확성 판단)+프로필의 `recentRepos`/`contributionHistory`(흥미 매칭) — CONTRIBUTING.md는 상세 전용이라 재순위엔 안 씀. (5) **실패 처리**: `Promise.allSettled`로 병렬 호출, 개별 이슈 실패 시 그 항목만 규칙 점수/이유 유지, 전체 추천 생성은 안 죽음. (6) **캐시**: 재순위 결과는 `IssueCache`에 저장 안 함(프로필마다 값이 달라지는 사용자별 계산이라 이슈 단위 영구 캐시 대상이 아님) — `RecommendationItem`에 최종값으로만 저장.
- 고려했던 대안: (a) 트리밍 전 후보군 전체를 재순위 — 기각. 후보군이 최대 24개까지 갈 수 있어 "지연 생성으로 실비용 0에 수렴"(2026-07-14 결정) 원칙과 충돌하고 `POST` 응답 지연도 더 커짐. (b) 상세 열람이 쌓일 때마다 그때그때 재정렬 — 기각. 목록이 사용자가 보는 도중 순서가 바뀌는 UX 문제, "몇 건 쌓이면 재정렬하나"라는 트리거 조건을 추가로 정해야 하는 문제, "일부만 분석된 상태의 정렬" 정의가 애매한 문제가 겹침.
- 이유: 목록은 생성 시점에 이미 전부 노출되는 정보라 그 10건에 대한 비용은 "안 열어본 이슈엔 비용 0" 원칙의 적용 대상이 아니라고 재해석함(그 원칙은 상세 정보인 `issueSummary`/`guide`에 적용). 병렬+부분실패 허용은 오전에 구현한 이슈 분석의 폴백 철학을 그대로 재사용.

### LLM 재순위: 건별 병렬 호출(10회) → 배치 호출 1회로 재설계
- 날짜: 2026-07-23
- 배경/문제: 바로 위 결정대로 `Promise.allSettled`로 10건을 병렬 호출하게 구현하고, `GEMINI_API_KEY`를 실제로 발급받아 실서버로 테스트했더니 **10건 전부 `429`(Gemini 분당 요청 한도 초과)로 실패**하는 걸 실측 확인함(로그: `Gemini API 호출 실패 {"status":429, ...}` × 10, 그런데도 추천 생성 자체는 200으로 정상 응답 — 폴백은 의도대로 작동). 무료 티어 RPM 한도가 순간 동시 요청 10개를 못 버티는 게 원인.
- 선택한 방안: 이슈 10건을 개별 요청 10번이 아니라 **프롬프트 하나에 `[0]`~`[9]`로 번호 매겨 나열하고, 요청 1번으로 배열 응답**(`[{ index, adjustment, reason }, ...]`)을 받는 구조로 변경(`llmService.rerankItems`). 검증 함수도 `isValidRerankResult`(단건) → `isValidBatchRerankResult(parsed, itemCount)`(배열, 일부 index만 응답해도 허용)로 교체. GitHub 이슈 본문 조회(`fetchIssueBody`)는 Gemini와 무관한 REST 호출이라 그대로 10건 병렬 유지.
- 고려했던 대안: (a) 병렬 호출 수를 2~3개로 제한하고 나머지는 순차 처리 — 기각. 여전히 요청 횟수가 10회라 분당 한도 자체를 줄이지 못하고, 순차 대기 때문에 `POST` 응답 지연이 오히려 늘어남. (b) 재시도 로직 추가(429 시 잠시 대기 후 재시도) — 기각. 사용자 요청(POST) 하나가 여러 초씩 재시도를 기다리게 되는 건 더 나쁜 UX고, 애초에 요청 수 자체를 줄이는 게 근본 해결.
- 이유: 실측으로 드러난 문제라 이론적 설계보다 우선함. 요청 수를 10 → 1로 줄이면 같은 분당 한도 안에서 여러 사용자의 동시 추천 생성 요청도 훨씬 여유 있게 처리 가능. 배열 응답의 일부 누락을 허용하는 `isValidBatchRerankResult` 설계는 기존 "부분 실패 허용" 철학을 배치 단위로 그대로 계승.

### 모델을 `gemini-2.0-flash-lite` → `gemini-flash-lite-latest`로 교체 (근본 원인 정정)
- 날짜: 2026-07-23
- 배경/문제: 배치 호출 1번으로 줄인 뒤에도 여전히 429가 나서 Gemini 응답 본문을 직접 까봤더니, 원인이 "분당 요청 한도 초과"가 아니라 **`gemini-2.0-flash-lite` 모델 자체의 무료 티어 할당량이 이 키에서 `limit: 0`**이었음이 드러남(`GenerateRequestsPerMinutePerProjectPerModel-FreeTier`/`GenerateRequestsPerDayPerProjectPerModel-FreeTier` 둘 다 0). 즉 바로 위 결정에서 "동시 요청 10개가 RPM을 못 버텼다"고 적은 원인 추정은 부정확했음 — 요청을 1개로 줄여도 어차피 0/분이라 항상 실패했을 것. `models` API로 조회하니 모델 자체는 이 키에 등록돼 있어(`models/gemini-2.0-flash-lite` 목록에 존재) 존재 여부 문제도 아니었음.
- 선택한 방안: `gemini-2.0-flash-lite`, `gemini-2.0-flash` 대신 **`gemini-flash-lite-latest`**로 교체. `gemini-flash-latest`/`gemini-flash-lite-latest` 둘 다 이 키에서 실제 200을 확인했고(직접 `generateContent` 호출로 검증), 그중 경량 티어인 `-lite-latest`를 선택(2026-07-21 결정의 "경량 모델" 원칙 유지).
- 고려했던 대안: `gemini-2.5-flash-lite` — 404("no longer available to new users")로 애초에 신규 발급 키에서 못 씀.
- 이유: 버전 고정 모델(`gemini-2.0-*`)은 이 계정에서 무료 할당량이 아예 열려 있지 않고, `-latest` 별칭 모델만 무료 할당이 됨을 실측으로 확인함. 2026-07-21 결정에 이미 적어둔 "Google이 예고 없이 무료 한도를 조정한 전례가 있다"는 우려가 실제로 재현된 사례 — 향후 이 모델도 막히면 `models` API로 그 시점에 무료 할당이 열려 있는 모델을 다시 조회해 교체해야 함.
