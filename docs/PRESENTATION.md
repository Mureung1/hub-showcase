## 실제 동작 워크스루 — 클릭 → 서버 → DB 한 바퀴

> 슬라이드 4의 데모를 **실제 데이터·요청 흐름**과 함께 한 단계씩 풀어쓴 것.
> 발표 중 화면을 조작하며 이 순서대로 읽으면 "화면만이 아니라 **서버와 DB가 실제로 돈다**"를 보여줄 수 있다.
> **개발자도구 → Network 탭**을 열어두고, 각 단계에서 실제 요청이 뜨는 걸 함께 가리키면 설득력이 커진다.
> (현재 라이브 데이터 기준: 발행 65편 · 저자 22명 · ch-1 리더보드 6편.)

### 0. 사전 — 두 서버가 떠 있다
- `cd backend && npm run dev` → `http://localhost:4000` (Express)
- `cd frontend && npm run dev` → `http://localhost:5173` (Vite)
- 확인용: `curl http://localhost:4000/api/health` → `{ status: "ok", db: "ok" }` (서버 + DB 연결까지 살아있다는 증거)

### 1. 둘러보기 — "목록이 DB에서 온다"
- **화면**: 상단 "둘러보기" 클릭 → 문서 카드 65편, 저자 22명, 좋아요 수가 제각각.
- **내부**: `storage.loadPublished()` → `GET /api/documents?status=published` → `optionalAuth`(비로그인 통과) → supabase-js가 `service_role`로 `documents`에서 **발행분만** 조회 → `toApiDoc()`이 snake→camel 변환 → 카드 렌더.
- **말할 것**: "이 목록은 화면에 박아둔 게 아니라 매번 Supabase에서 옵니다. `status='draft'`나 남의 초안은 애초에 응답에 안 실립니다."
- **증거**: Network 탭의 `documents?status=published` 응답 JSON, 또는 `curl "http://localhost:4000/api/documents?status=published"`.

### 2. 정렬·필터 — "같은 데이터를 다르게 본다"
- **화면**: **인기순** 클릭 → `좋아요 41`짜리가 위로. **장르=로그라이크** + **분류=성장·강화** 칩 → 하데스·슬더스 계열만 남음. 검색창에 `가챠` → 가챠 역기획들만.
- **내부**: 목록은 이미 받아둔 배열을 **클라이언트에서** 정렬/필터한다(`ArchivePage.jsx`). 장르는 `genreOfGame(gameTag)`로 계산, 분류는 `category` 컬럼, 검색은 제목·게임·시스템·분류·저자 대상.
- **말할 것**: "필터 칩이 문서 수만큼 늘지 않도록, 장르(게임에서 계산)와 분류(고정 어휘 컬럼) 두 축으로만 겁니다."

### 3. 문서 상세 — "발행분은 누구나, 코멘트도 DB에"
- **화면**: 아무 문서나 클릭 → 섹션 본문 + 아래에 사람 코멘트(예: 젤다 사당 예시엔 "섹션을 구역으로 나눈 게 깔끔해요…").
- **내부**: `GET /api/documents/:id` → 발행 문서라 공개 → `sections`(jsonb) 렌더, `comments`(jsonb) 중 `is_ai=false`는 섹션 아래, `__overall__`은 "AI 총평" 패널, `__score__`는 "AI 채점" 패널로 분기.
- **말할 것**: "코멘트는 화면 상태가 아니라 문서 행의 jsonb에 저장돼 있어, 새로고침해도 그대로입니다."

### 4. 로그인 — "프론트가 Supabase를 직접 부르는 유일한 지점"
- **화면**: 로그인 → 우상단에 내 이름.
- **내부**: 프론트가 **Supabase Auth를 직접**(anon 키) 호출 → `access_token` 수령 → `AuthContext`가 `setAuthToken()`으로 `api.js`에 주입 → **이후 모든 요청에 `Authorization: Bearer`** 자동 부착.
- **말할 것**: "데이터는 전부 백엔드를 거치지만, 로그인만 예외로 프론트가 Supabase를 직접 씁니다. 대신 서버는 그 토큰을 **그대로 믿지 않고** 매 요청마다 `getUser()`로 다시 검증합니다."
- **증거**: Network 탭에서 이후 요청 헤더에 `Authorization: Bearer …`가 붙는 것.

### 5. 작성 → 발행 — "새 행이 아니라 status를 뒤집는다"
- **화면**: 작성하기 → 순기획 **원페이지 피치**(짧은 필드) 작성 → **임시저장** → 태그 채우고 **발행** → 상세로 이동.
- **내부**:
  - 임시저장 → `POST /api/documents`(신규) → 서버가 `author_id`를 **주입**(클라가 보낸 값은 매퍼가 버림) → `status='draft'` 행 생성, 서버가 uuid 발급.
  - 발행 → `PATCH /api/documents/:id` → 같은 행의 `status`를 `published`로 **flip**(코멘트·`created_at` 보존) → `publish_requires_tags` 제약이 태그 없으면 DB에서 막음.
- **말할 것**: "발행은 초안을 지우고 새로 만드는 게 아니라 한 행의 상태만 바꿔서, 작성 중 달린 코멘트가 살아남습니다."
- **증거**: 태그 없이 발행 시도 → `400`(부록 B curl). Supabase 대시보드에서 같은 행의 `status`가 바뀌는 것.

### 6. AI 피드백/채점 — "서버 안에서만 Gemini를 부른다"
- **화면**: (회원, 챌린지 제출 시) 발행 직후 "AI가 검토 중…" → 상세에 **AI 채점**(총점+항목별) + **AI 총평**.
- **내부**: `POST /api/documents/:id/ai-feedback` → `requireAuth` + **소유자 확인**(아니면 403) + **일일 한도** 조회 → `aiFeedback.js`가 `responseSchema`로 구조를 강제해 Gemini 호출 → 결과를 `comments`에 append, 점수는 `ai_score` 컬럼에 저장, `ai_feedback_logs`에 1건 기록.
- **말할 것**: "`GEMINI_API_KEY`는 서버 `.env`에만 있고 프론트 번들엔 없습니다. 채점은 별도 호출이 아니라 이 피드백 호출에 합쳐져 추가 비용이 0입니다."
- **증거(라이브 1콜)**: 실제 제출 → 점수가 뜨고, `curl "http://localhost:4000/api/documents/<id>"`에 `aiScore`가 실려 있음.

### 7. 챌린지 리더보드·좋아요 — "점수와 반응이 남는다"
- **화면**: 챌린지 → **종료된 가챠 챌린지**에 점수순 리더보드(스타레일 91 → … ). 진행 챌린지엔 "참가 N명". 상세에서 **좋아요** 클릭 → 숫자 +1, 새로고침해도 유지.
- **내부**: 리더보드는 `ai_score` 내림차순(`ChallengesPage.jsx`). 좋아요 → `POST /api/documents/:id/reactions`(`requireAuth`) → `reactions` 테이블 토글(유저당 1회) → `syncReactionCounts()`가 `documents.likes`를 다시 세어 반영.
- **말할 것**: "좋아요는 유저당 1회로 `reactions` 테이블에 남고, 표시용 카운트는 서버가 다시 계산해 맞춥니다."

> **한 줄 요약(이 워크스루의 결론)**: 모든 읽기·쓰기는 `storage.js → api.js → Express → Supabase`라는 **하나의 길**을 지나고, 민감한 값(작성자·AI 여부·점수)은 전부 **서버가 정한다**. 화면은 그 결과를 그릴 뿐이다.

## 부록 A — 백엔드 설명 근거 (Q&A·심화용)

발표 중 백엔드 질문이 오면 아래를 근거로 답한다. (파일 경로는 실제 코드)

- **데이터 창구 단일화** — 모든 화면 → `frontend/src/lib/storage.js` → `frontend/src/lib/api.js`의 `request()`. 프론트가 Supabase 데이터를 직접 부르는 곳은 **없다**(인증만 예외).
- **인증 흐름** — 로그인만 프론트가 Supabase Auth를 직접 호출(anon 키). 발급된 access token은 `AuthContext`가 `setAuthToken()`으로 `api.js`에 넘기고, 서버는 매 요청마다 `auth.getUser(token)`으로 **JWT를 다시 검증**한다(`backend/src/middleware/requireAuth.js`).
- **수정 권한** — 회원 문서는 `author_id` 일치, 비회원 문서는 **scrypt 해시된 수정용 비밀번호**(`backend/src/lib/password.js`). 해시는 API로 절대 안 나가고 `hasEditPassword` 불리언만 나간다.
- **발행 = status flip** — 초안 행의 `status`를 `published`로. 코멘트·`created_at` 보존.
- **AI 코멘트는 서버가 append** — `toDbRow()`가 클라의 `comments`·`likes`·`bookmarks`·`ai_score`를 아예 안 받는다(재발행 시 데이터 손실·점수 위조 차단).
- **RLS** — `documents`·`profiles`·`ai_feedback_logs`·`reactions` 전부 ON, 정책 없음. service_role만 우회.

## 부록 B — DB에서 실제로 온다는 증거 (curl)

## 부록 C — 예상 질문과 답변

- **왜 sections/comments를 JSONB로?** — 문서 구조가 유연하고 한 번의 조회로 통째로 가져오기 위해. 대신 코멘트 동시 쓰기 유실 가능성이 있어, 사람+AI 코멘트가 늘어난 지금 **별도 테이블로 정규화**를 다음 단계로 잡아뒀다.
- **AI 비용은?** — 무료 티어(Gemini) + **유저당 일일 호출 한도**(미리보기 합산). 채점은 별도 호출이 아니라 피드백 호출에 통합해 추가 비용 0.
- **왜 RLS 정책을 안 만들었나?** — anon 키가 프론트에 공개되므로 "정책 없이 ON"으로 직접 접근을 전부 막고, 접근은 service_role을 쥔 백엔드 한 문으로만. 정책을 세밀히 짜는 대신 **문을 하나로 좁히는** 선택.
- **역기획 vs 순기획 차이?** — 역기획은 기존 게임 분석(평가 기준: 관찰→추론·구체성·구조 완결성), 순기획은 오리지널 제안(피치 명확성·차별성·실현가능성·재미 가설). AI 프롬프트가 `kind`로 갈린다.
- **AI 점수를 믿을 수 있나?** — "절대 평가가 아닌 참고 점수"로 명시하고, **배점을 공개**해 근거를 투명하게. 사람 코멘트와 병행한다.
- **확장성?** — 저장소 교체 지점이 `storage.js` 하나라 백엔드/DB를 바꿔도 화면은 그대로. 코멘트 정규화가 다음 큰 조각.
