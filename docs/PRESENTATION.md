## 1. 오프닝 + 코어 루프 개념 (2분)

> "게임 기획자를 꿈꾸는 대학생이 가장 먼저 막히는 지점이 뭘까요? 아이디어가 없어서가 아닙니다. 아이디어는 다들 있어요. 문제는 그 아이디어를 '플레이어가 반복하게 될 행동'으로 구체화하는 부분입니다."

- 게임 개발에서 가장 기본이 되는 개념이 **코어 루프**라는 걸 짧게 정의한다: 플레이어가 반복하게 되는 핵심 행동의 흐름. 예: `전투 → 보상 → 성장 → 도전 → 반복`.
- 이걸 직접 겪은 문제로 가져온다: 장르는 떠오르는데 반복 행동을 정의하기 어렵고, 참고 게임은 있는데 그 재미 구조를 내 기획으로 옮기기 어렵다는 점.

- **게임 비유로 한 번 더 풀어주기 (~40초)**:

  > "코어 루프를 게임에 빗대면 이렇습니다. Slay the Spire를 예로 들면, 카드 한 장을 내고 효과를 보는 건 몇 초짜리 아주 작은 루프입니다. 전투 하나에 들어가서 적을 처치하고 보상을 고르는 건 몇 분짜리 조금 더 큰 루프고요. 그 전투를 여러 번 거쳐 보스까지 가고, 지더라도 성장 자원이 남아 다음 판에 다시 도전하게 만드는 건 훨씬 더 큰 루프입니다. 즉 게임 안에는 이런 루프가 하나만 있는 게 아니라, 작은 것부터 큰 것까지 여러 겹으로 쌓여 있습니다. 오늘 저희가 다루는 Core Loop Builder는 이 중에서 '전투 하나' 정도 크기의 중간 루프 하나를 설계하는 데 집중하고 있고, 여러 크기의 루프를 함께 다루는 건 앞으로의 개선 방향입니다."

- "이 문제를 AI Agent가 같이 풀어주는 서비스를 4주간 만들고 있습니다"로 다음 섹션 연결.

## 2. 서비스 소개 (1.5분)

> "Core Loop Builder는 장르와 참고 게임을 입력하면, AI가 코어 루프 후보를 같이 브레인스토밍하고, 그걸 시각화하고, 포트폴리오용 기획 초안까지 만들어주는 서비스입니다."

- 한 줄 소개 그대로 말하기 (`project-plan.md` 1번 참고).
- 서비스가 "기획서를 대신 써주는 도구"가 아니라 "기획자의 사고 과정을 단계별로 도와주는 파트너"라는 점을 강조 — 이 프로젝트에서 제일 중요하게 지킨 방향.
- 뒤에 있는 구조를 한 문장으로: Input → Genre Loop → Reference Analysis → Brainstorming → Loop Visualizer → Portfolio Writer → Critic, 이렇게 **7단계 Agent 파이프라인**으로 나눠서 작동한다.

## 3. 작업 과정 설명 (2.25분)

> "이 서비스를 만드는 과정 자체도 AI Agent(Claude Code)와 함께 진행했습니다."

- **1주차**: 기획서 확정 → 서비스 소개 랜딩 페이지 구현 → 핵심 흐름을 검증하기 위한 정적 프로토타입 제작(지금 시연할 것).
- **디자인 시스템**: glassmorphism + game감이라는 방향을 잡고, 실제로 색상을 세 번 바꿔가며(다크 네온 → 파스텔 → 블루-바이올렛-시안 쿨톤) 다듬은 과정을 짧게 언급 — "인스타그램 그라디언트처럼 보인다"는 피드백을 받고 톤을 바꾼 것처럼, 시행착오를 거쳐 디자인 시스템 문서와 재사용 가능한 skill로 남겼다는 점.
- **개발 환경**: client(React)/server(Express)로 구조를 나누고, LLM 키는 server에서만 다루는 규칙, 커밋 컨벤션까지 미리 정해뒀다는 점.
- **기술 스택을 비유로 설명 (~25초, 청중이 개발자가 아닐 수 있어서)**:

  > "React는 화면을 레고 블록처럼 조립하는 도구인데, 여러분이 매일 쓰는 유튜브나 인스타그램 웹 버전도 비슷한 방식으로 만들어져 있습니다. Express는 그 화면이 보낸 요청을 받아 처리하는 창구 역할이고, 배달앱이나 당근마켓 같은 서비스 뒤편에도 비슷한 구조가 있습니다. Claude API는 코어 루프를 실제로 생성해줄 AI 두뇌 역할이고요 — 사실 이 발표 자료와 지금까지 보여드린 코드 자체도 Claude Code라는 AI 개발 도구와 함께 만들었습니다."

- **백로그**: 2~4주차 할 일을 우선순위(P0/P1/P2)로 미리 정리해서, 개발 중 판단이 흔들리지 않게 준비했다는 점.
- 한 문장 요약: "기획 → 디자인 → 개발 환경 → 백로그, 이 순서로 준비하고 이제 실제 AI 연동 개발에 들어갑니다."

## 4. 프로토타입 시연 (2.5분)

`prototype/index.html`을 브라우저로 연다. 6개 탭(입력 → 분석 → 후보 → 루프 → 초안 → 피드백)을 순서대로 클릭하며 설명한다.

1. **입력** (~15초) — "장르, 참고 게임, 원하는 플레이 경험을 입력받습니다. 지금은 샘플 값이 채워져 있어요: 로그라이크 덱빌딩 RPG, Slay the Spire와 Hades." 하단의 "정리된 의도" 박스를 가리키며 AI가 입력을 어떻게 요약하는지 보여준다.
2. **분석** (~15초) — 장르 기본 루프와 참고 게임 분석 포인트를 보여준다. "이 게임이 왜 재밌는지를 반복 구조로 뜯어보는 단계입니다."
3. **후보** (~30초) — 후보 3개 카드를 보여주며 추천도 점수를 짚는다. "하나의 정답이 아니라 여러 방향을 비교할 수 있게 합니다." 선택된 카드(후보 B)를 클릭해 넘어간다.
4. **루프 시각화** (~40초) — 원형 다이어그램을 보여주며 행동→보상→성장→도전→반복 흐름을 손으로 따라가며 설명한다. "이게 이 서비스의 핵심 산출물입니다 — 막연했던 아이디어가 눈에 보이는 순환 구조가 됐습니다." (아까 오프닝에서 말한 '전투 하나' 크기의 중간 루프가 바로 이겁니다, 라고 1절에서 한 비유와 연결해준다)
5. **기획 초안** (~30초) — 게임 콘셉트, 기획 의도, 주요 시스템이 자동 생성된 걸 보여준다. "포트폴리오에 바로 붙일 수 있는 형태로 나옵니다."
6. **피드백** (~20초) — 강점/주의점/개선 제안을 보여주며 마무리. "AI가 결과만 주고 끝나는 게 아니라, 다시 검토할 거리를 던져줍니다."

시연 중 반드시 짚을 말: "지금 보시는 건 흐름을 검증하기 위한 정적 프로토타입이고, 지금부터 2~4주차에 이 흐름을 실제 Claude API로 동작하게 만드는 게 남은 개발입니다."

## 5. 마무리 (1.25분)

> "코어 루프는 게임 기획에서 가장 작지만 가장 중요한 질문에 답합니다 — 플레이어는 무엇을 반복하고, 왜 다시 하게 되는가. Core Loop Builder는 이 질문에 대한 답을 AI와 함께 찾아가는 도구입니다."

- **남은 일정, 실제 발표에서 말할 압축 버전 (~25초)**:

  > "2주차는 입력부터 후보 생성까지를 실제 Claude API로 동작하게 만드는 주입니다. 서버에만 API 키를 두고, 장르 분석과 참고 게임 분석을 각각 맡는 함수 두 개를 만들어 후보 생성 API 하나로 합칩니다. 이때 그냥 챗봇에 물어보는 것과 다르게, 프롬프트에 좋은 예시를 미리 넣고 정해진 형식으로만 답하게 강제해서 — 결과가 뭉뚱그린 조언이 아니라 사용자 조건에 실제로 묶인 구체적인 답이 되게 만듭니다. 3주차는 시각화와 기획 초안, 4주차는 사용자 테스트와 배포로 마무리합니다."

- **위 압축 버전의 배경 (Q&A에서 더 물어보면 이걸로 답변, 발표 본문에서는 말하지 않음)**:

  > "2주차는 지금 보신 흐름 중 입력부터 후보 생성까지를 실제로 동작하게 만드는 주입니다. 서버에 Claude API를 붙이는데, API 키는 서버에만 두고 클라이언트에는 절대 노출하지 않습니다. 방금 시연에서 본 '분석' 단계와 '후보' 단계를 각각 담당하는 함수를 서버에 두 개 만들고 — 하나는 장르별 기본 루프를 뽑는 Genre Loop Agent, 하나는 참고 게임의 반복 구조를 분석하는 Reference Analysis Agent입니다 — 이 둘의 결과를 받아서 코어 루프 후보 3개를 만들어주는 API 하나로 합칩니다. 이 API는 `POST /api/loops/candidates`라는 이름으로 이미 설계해뒀고, 후보 각각에 제목과 설명, 단계별 흐름, 추천 점수를 담아 응답하도록 스키마까지 정해둔 상태입니다. 2주차가 끝날 때 기준은 '후보 3개가 하드코딩이 아니라 매번 입력에 따라 실제로 달라지는가'입니다.
  >
  > 여기서 신경 쓰는 부분이 하나 더 있습니다. 그냥 챗지피티 창에 '로그라이크 게임 코어 루프 알려줘'라고 물어보는 것과 다르려면, 프롬프트 자체를 다르게 짜야 합니다. 세 가지를 챙기려고 합니다. 첫째, 좋은 코어 루프 예시 몇 개를 프롬프트에 미리 넣어둬서 — '위험 지역 선택 → 카드와 유물 획득' 같은 구체적인 동사구 흐름으로 답하도록 유도합니다. 둘째, 자유 텍스트가 아니라 제목·단계·태그가 채워진 정해진 형식으로만 답하게 강제합니다. 셋째, 사용자가 입력한 '원하는 플레이 경험'을 각 후보가 어떻게 만족하는지 한 문장씩 반드시 설명하게 만들어서, 일반적인 장르 조언이 아니라 이 사용자의 조건에 실제로 묶인 답을 받습니다. 넷째(발표에서는 생략 가능), Critic Agent에도 '반복 동기·보상-도전 연결·장르 기대 부합' 같은 고정 루브릭을 줘서, "잘했어요" 식이 아니라 기준별로 짚는 피드백을 받습니다.
  >
  > 3주차는 사용자가 고른 루프를 원형 다이어그램으로 시각화하고, 그걸 바탕으로 포트폴리오용 기획 초안과 AI 피드백까지 만드는 주입니다. 4주차는 실제 사용자 3명 이상에게 테스트를 받고, 피드백을 반영한 뒤 배포와 최종 발표 준비로 마무리합니다."

- Q&A로 전환.

## 예상 질문 대비 메모

- **"게임에 코어 루프가 하나만 있나요?"** — 아니다. Slay the Spire 기준으로 보면 카드 한 장 내는 몇 초짜리 micro loop, 전투 하나를 치르는 몇 분짜리 meso loop, 여러 전투를 거쳐 보스까지 가고 실패해도 자원이 남아 재도전하게 만드는 훨씬 큰 macro loop까지 여러 크기의 루프가 겹쳐 있다. Core Loop Builder는 지금 이 중 meso loop(전투 하나 수준) 하나만 설계 대상으로 삼고 있고, 이는 4주 MVP 범위를 좁히기 위한 의도적 단순화다. micro/macro 루프까지 함께 설계하거나 루프 간 관계(작은 루프가 큰 루프를 어떻게 지탱하는지)를 보여주는 건 `docs/BACKLOG.md`의 P2(범위 밖) 항목으로 남겨둔 향후 개선 방향이다.
- **"그냥 챗지피티에 물어보는 거랑 뭐가 다른가요?"** — 세 가지가 다르다. (1) 한 번의 질문-답이 아니라 장르 분석 → 참고 게임 분석 → 후보 브레인스토밍 → 시각화 → 초안 → 피드백으로 이어지는 단계별 파이프라인이라 각 단계 결과를 검증하고 다시 쓸 수 있다. (2) 프롬프트에 좋은 코어 루프 예시를 미리 넣고, 자유 텍스트가 아니라 제목·단계·태그가 채워진 정해진 형식으로만 답하게 강제해서 "재미있게 만드세요" 같은 뭉뚱그린 답 대신 구체적인 동사구 흐름을 받는다. (3) 사용자가 입력한 원하는 플레이 경험을 각 후보가 어떻게 만족하는지 명시하게 만들어서, 일반적인 장르 조언이 아니라 이 사용자 조건에 실제로 묶인 답을 받는다. Critic Agent도 "반복 동기·보상-도전 연결·장르 기대 부합" 같은 고정 루브릭으로 짚어서, 챗봇의 "좋아요, 잘했어요"보다 구체적인 피드백을 준다.
- **"왜 하필 코어 루프인가?"** — 게임 기획 지망생이 포트폴리오를 준비할 때 가장 많이 막히는 지점이자, 다른 기획 요소(세계관, 캐릭터)보다 먼저 정해야 설득력 있는 설명이 가능한 개념이기 때문.
- **"MVP 범위를 왜 이렇게 잡았나?"** — 4주 안에 "코어 루프 설계 사고 과정을 AI가 얼마나 잘 도와주는가"를 보여주는 게 핵심이라, 로그인/결제/데이터 수집처럼 핵심과 무관한 기능은 전부 제외했다는 점(`project-plan.md` 10번 참고).
- **"AI Agent 구조를 왜 7단계로 나눴나?"** — 하나의 거대 프롬프트로 모든 걸 처리하면 결과를 검증하거나 특정 단계만 다시 실행하기 어렵다. 단계별로 나누면 각 Agent의 책임이 분명해지고, 나중에 특정 단계(예: 참고 게임 분석)만 따로 개선할 수 있다.
- **"참고 게임 분석이 부정확하면 어떻게 하나?"** — 사용자가 게임 설명을 직접 보완할 수 있고, 결과를 그대로 확정하는 게 아니라 수정 가능한 초안으로 제공한다(`project-plan.md` 17번 리스크 대응).
- **"디자인은 왜 glassmorphism + 게임감인가?"** — 사용자가 게임 기획자를 꿈꾸는 사람이라, 서비스 자체도 "게임을 설계하는 도구"라는 느낌을 주고 싶었다. 다만 장식적 게임 클리셰 대신 진행바·배지 같은 "성취" 모티프로만 절제해서 표현했다.
