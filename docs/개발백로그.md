# 개발 백로그

- 문서 상태: 2주차 개발 착수 전 초안
- 최종 수정일: 2026-07-10
- 참고: [서비스 기획서](../서비스%20기획서.md) §9 기능 도입 순서

## 백로그란

앞으로 해야 할 작업을 우선순위 순으로 정리해 둔 목록이다. 스프린트를 시작하기 전에 "무엇을, 언제, 왜" 할지 미리 정해두면 개발 중간에 범위가 흔들리지 않는다. 진행하면서 계속 갱신하는 살아있는 문서이며, 완료된 항목은 상태를 바꾸고 새로 발견된 작업은 우선순위를 매겨 추가한다.

## 우선순위 기준

| 등급 | 의미 |
|---|---|
| P0 | 기반 작업. 이게 없으면 다른 작업도 진행할 수 없음(백엔드, DB, 인증 등) |
| P1 | 이번 4주 스프린트 안에 반드시 끝내야 하는 핵심 기능 |
| P2 | 여유가 있으면 진행, 없으면 다음 스프린트로 미룸 |

## Task 목록

### P0 — 기반 작업

| # | Task | 설명 | 현재 상태 |
|---|---|---|---|
| 1 | 백엔드 구현 (API) | React 프론트와 통신할 REST API 서버 기본 구조 (Express) | 완료 — Express 서버 기동 확인, 일정 CRUD API 동작 확인 |
| 2 | DB화 | 일정/카테고리/친구/게시물/반응 스키마 설계 및 실제 DB 연결 | 완료 — Neon Postgres 연결, 전체 기능 범위 스키마 설계 및 마이그레이션 적용 |
| 3 | 회원가입·로그인 (인증) | 실제 사용자 계정 개념 도입, 세션/토큰 인증 | 구현 완료, 검증 중 — 커스텀 JWT(access 15분+refresh 30일), `/api/schedules`도 인증 유저 기준으로 전환 |
| 4 | 인증 영상 업로드·저장 | 프론트에서 찍은 영상을 서버/스토리지에 실제 저장 | 미착수 — 지금은 브라우저 메모리 blob URL이라 새로고침하면 사라짐 |
| 5 | 인증 영상 코멘트 기능 | 인증 피드에 댓글 작성·조회 | 미착수 — 눈빛 반응만 있고 댓글은 없음 |

> **DB 선택 메모 (Task 2)**: Postgres는 Neon으로 선택. Supabase는 Auth/Storage까지 포함된 BaaS라 이 프로젝트엔 과함 — 인증은 커스텀 JWT, 영상은 Cloudflare R2로 쓰기로 이미 정해서 Supabase의 부가 기능을 쓸 일이 없음. Neon은 Postgres 기능만 있어 가볍고, DB 브랜칭(스키마 실험 시 편함)도 지원. 무료 티어 동작 방식도 Neon은 미사용 시 컴퓨트만 슬립했다가 요청 오면 짧게 깨어나는 반면, Supabase는 7일 미사용 시 프로젝트 자체가 일시정지돼서 대시보드에서 수동 재개가 필요함 — 개발 중 자주 끊길 수 있어 Neon이 더 적합하다고 판단.

> **인증 방식 선택 메모 (Task 3)**: 세션 기반 로그인(서버가 세션을 메모리/DB에 들고 쿠키로 세션 id만 전달) 대신 커스텀 JWT를 선택. 이유: (1) DB는 이미 Neon Postgres인데 Supabase Auth 같은 외부 인증 서비스를 쓰면 유저 데이터가 두 군데(Neon의 User 테이블 + Supabase Auth)로 쪼개져서 조인·마이그레이션이 번거로워짐 — 인증도 우리 DB 안에서 자체 해결. (2) access token(JWT, 15분)은 서버가 매 요청마다 DB를 조회하지 않고 서명만 검증하면 되어 가벼움 — Render/Railway 같은 무료 티어 백엔드에서 요청마다 DB 왕복이 줄어드는 게 이득. (3) 다만 JWT는 발급하면 만료 전엔 강제로 무효화할 수 없다는 단점이 있어서, 수명이 긴 refresh token(30일)만 해시로 DB(`RefreshToken` 테이블)에 저장해 로그아웃·탈취 시 즉시 폐기 가능하게 함 — access token은 가볍게, refresh token은 통제 가능하게 두 방식을 절충. (4) refresh token은 httpOnly 쿠키로만 주고받아 프론트 JS가 직접 접근 못 하게 해서 XSS로 인한 탈취 위험을 줄임.
