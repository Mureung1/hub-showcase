# AI와 함께 개발한 과정

## 1. 프로젝트와 개발 목표

`있는대로`는 자취생이 냉장고에 보유한 재료와 소비기한을 관리하고, 지금 사용할 수 있는 재료를 중심으로 1인분 레시피를 추천받는 서비스다.

이 프로젝트의 개발 목표는 기능을 많이 만드는 것만이 아니었다. 개발 경험이 많지 않은 상태에서 AI Agent와 함께 요구사항을 구체화하고, 프런트엔드·백엔드·데이터베이스·외부 AI API가 연결되는 과정을 직접 이해하는 것도 중요한 목표였다.

따라서 AI에게 프로젝트 전체를 한 번에 만들어 달라고 요청하지 않았다. 내가 해결하려는 사용자 문제와 원하는 화면을 설명하고, Codex와 대화하면서 필요한 개발 개념을 확인한 뒤 작은 기능부터 구현하고 검증하는 페어 프로그래밍 방식으로 진행했다.

## 2. 3주간의 개발 과정

### 1주 차: 아이디어를 화면으로 표현하기

첫 주에는 자취생이 냉장고 속 재료를 잊거나 소비기한을 놓치고, 남은 재료로 무엇을 만들지 결정하기 어렵다는 문제를 정의했다.

처음부터 복잡한 서버 기능을 구현하기보다 HTML·CSS·JavaScript로 기본 화면을 만들었다. 냉장고 재료, 식단 추천, 레시피 상세, 구매 추천을 하나의 사용자 흐름으로 구성하고, 화면을 직접 보면서 정보 구조와 사용 순서를 반복해서 수정했다.

이 과정에서 `DESIGN.md`와 `DESIGN_SKILL.md`를 작성했다. 색상, 글자 크기, 카드, 버튼, 소비기한 경고, 모바일 화면 등 UI의 공통 기준을 문서로 남겨 이후 Agent가 화면을 수정할 때도 같은 디자인 방향을 유지하도록 했다.

### 2주 차: 정적인 화면을 실제 기능으로 바꾸기

둘째 주에는 프로젝트를 React와 Vite 기반 프런트엔드, Express 기반 API 서버 구조로 전환했다.

큰 기능을 한 번에 구현하지 않고 GitHub Issue와 Project를 이용해 작업을 나눴다. 냉장고 재료 등록, 보유 재료 기반 메뉴 추천, 레시피 상세, 부족 재료와 구매 정보 안내를 4개의 상위 TASK와 세부 Issue로 구분하고, 각 작업에 완료 기준을 작성했다.

먼저 mock 데이터로 사용자 흐름을 검증했다. 재료를 등록했을 때 화면에 반영되는지, 추천 결과가 없거나 오류가 발생했을 때 어떤 상태를 보여줄지, 추천 카드에서 레시피 상세로 이동할 수 있는지, 부족한 재료를 구매 검색으로 연결할 수 있는지를 차례로 확인했다.

이 단계에서 React 컴포넌트와 상태, 프런트엔드와 API의 역할, 사용자 입력과 화면 갱신의 관계를 실제 기능을 만들면서 배웠다.

### 3주 차: 실제 데이터와 생성형 AI 연결하기

셋째 주에는 mock 중심의 기능을 실제 서비스 구조로 교체했다.

먼저 Supabase에 재료 데이터를 저장하고 조회·등록·수정·삭제 API를 각각 구현했다. 한 기능을 구현할 때마다 API와 화면을 따로 확인한 뒤 다음 기능으로 이동했다. 소비기한 자동 계산, 같은 재료의 수량 병합, 기본 양념 처리와 추천용 태그 같은 서비스 정책도 이 과정에서 추가했다.

레시피 추천은 Gemini API를 이용해 구현했다. 서버가 Supabase에서 보유 재료를 조회하고, 소비기한과 태그를 기준으로 우선순위를 계산한 뒤 허용된 정보만 Gemini에 전달하도록 구성했다.

Gemini가 생성한 결과는 그대로 사용하지 않았다. Zod 스키마와 서버 정책을 이용해 응답 형식, 부족 재료 개수, 소비기한이 지난 재료, 중복 레시피와 조리 조건을 다시 검증했다. 같은 재료와 조건에서 불필요한 호출이 반복되지 않도록 캐시와 레시피 fingerprint도 적용했다.

마지막으로 실제 추천 결과가 추천 카드, 레시피 상세, 부족 재료 구매 검색까지 이어지는 전체 흐름을 검증했다.

## 3. AI와 함께 일한 방식

Codex는 코드를 대신 작성하는 도구로만 사용하지 않았다. 요구사항을 개발 작업으로 바꾸고, 코드 구조와 오류 원인을 설명하며, 구현 결과를 테스트하는 페어 프로그래밍 파트너로 활용했다.

기능이나 UX 방향이 여러 갈래로 나뉠 때는 바로 구현하지 않고 선택지와 장단점을 비교했다. 이번 작업에 포함할 범위와 제외할 범위, 정상 동작과 실패 상태의 완료 기준을 먼저 정한 다음 구현했다.

한 기능을 구현한 뒤에는 실제 화면이나 API 응답을 확인했다. 기대한 결과와 다르면 오류 메시지와 현재 상태를 근거로 다시 질문하고, 수정 이유를 이해한 뒤 같은 문제가 반복되지 않도록 테스트나 문서에 남겼다.

Gemini는 개발을 돕는 Agent가 아니라 서비스 안에서 레시피를 생성하는 AI로 사용했다. Codex와 함께 Gemini의 입력 범위, 출력 형식, 보안, 오류 처리와 검증 정책을 설계하면서 생성형 AI를 서비스에 안전하게 연결하는 방법을 배웠다.

## 4. 반복해서 사용한 Workflows

### 작은 단위로 연결하는 개발

1. 해결하려는 사용자 문제를 설명한다.
2. 기능을 GitHub Issue와 완료 기준으로 정리한다.
3. 프런트엔드·백엔드·DB 작업을 구분한다.
4. 한 번에 하나의 기능만 구현한다.
5. 화면과 API에서 결과를 확인한 뒤 다음 기능으로 이동한다.

### Mock에서 실제 데이터로 확장

1. mock 데이터로 사용자 흐름을 먼저 확인한다.
2. Supabase 조회를 단독으로 연결한다.
3. 재료 등록·수정·삭제 API를 각각 구현하고 검증한다.
4. 실제 데이터가 화면에 반영되는지 확인한다.
5. Gemini를 별도로 연결한 뒤 전체 추천 흐름을 통합 검증한다.

### AI 응답 검증

1. 실제 보유 재료와 사용자가 선택한 조리 조건을 정리한다.
2. 허용된 재료 필드만 Gemini에 전달한다.
3. 구조화된 JSON 응답을 받는다.
4. Zod와 서버 정책으로 형식과 추천 조건을 검증한다.
5. 인증 실패, 사용량 제한, 타임아웃과 잘못된 JSON을 테스트로 재현한다.

### 사용자 흐름 중심 UI 검증

1. 재료를 등록하고 목록에 반영되는지 확인한다.
2. 추천 조건을 선택하고 결과를 조회한다.
3. 추천 카드에서 레시피 상세로 이동한다.
4. 부족한 재료와 구매 검색 연결을 확인한다.
5. 빈 데이터·로딩·오류·재시도 상태와 표시되는 화면을 확인한다.

### 문서와 코드 동기화

1. `AGENTS.md`에 Agent의 개발 절차와 완료 조건을 기록한다.
2. `DESIGN_SKILL.md`와 `DESIGN.md`에 UI 기준을 기록한다.
3. API 명세에 입력·출력·추천 정책·오류 코드를 기록한다.
4. QA 보고서에 실제 검증 결과와 후속 작업을 기록한다.
5. 테스트·lint·build를 통과한 뒤 변경을 커밋한다.

## 5. 품질과 보안을 위해 적용한 기준

- Gemini API 키와 Supabase Secret Key는 서버 환경변수에서만 사용한다.
- 프런트엔드와 로그에 비밀키, 전체 재료 데이터와 전체 AI 응답을 노출하지 않는다.
- Gemini에는 업무에 필요한 재료 필드만 전달한다.
- 소비기한이 지난 재료는 추천 대상에서 제외한다.
- Gemini의 응답은 Zod 형식 검증과 서버 정책 검증을 모두 통과해야 한다.
- 인증 실패·사용량 제한·타임아웃·잘못된 JSON·DB 조회 실패를 표준 오류로 처리한다.
- 마지막 성공 결과가 있으면 유지하고, 사용자가 다시 시도할 수 있는 상태를 제공한다.
- 관련 테스트와 전체 테스트, lint와 프로덕션 build를 품질 게이트로 사용한다.

## 6. 개발 과정에서 배운 점

처음에는 원하는 화면과 기능을 설명하는 데 집중했다. 프로젝트가 진행되면서 하나의 기능을 프런트엔드·백엔드·DB 작업으로 구분하고, 오류가 어느 단계에서 발생했는지 확인하며, 완료 조건과 테스트를 먼저 생각할 수 있게 됐다.

또한 생성형 AI의 응답을 그대로 신뢰해서는 안 된다는 점을 배웠다. 입력 데이터의 범위를 제한하고, 출력 형식과 서비스 정책을 검증하며, 실패 상황을 사용자 경험과 테스트에 반영해야 실제 서비스에서 사용할 수 있다.

3주 동안 배운 것은 AI에게 개발을 맡기는 방법이 아니라, Agent에게 질문하고 결과를 직접 확인하면서 개발을 학습하는 방법이었다. AI는 나를 대신한 개발자가 아니라, 다음 단계를 이해하고 시도할 수 있도록 도와준 개발 파트너였다.
