# 개발 스펙

이전에 폴더 하나에 16개 문서(아키텍처·빌드·테스트·인터랙션 가이드 + PRD 9종 + 구현프롬프트 4종)로
나뉘어 있던 것을 한 파일로 합쳤다(원본 폴더는 삭제됨). **`CLAUDE.md`가 이 저장소의 살아있는 1차 아키텍처 레퍼런스**이므로, 거기
이미 상세히 있는 내용(프록시 구조·배포 분기·env var·핵심 도메인 흐름·게스트 우선 저장·인증·라우팅/
디자인 시스템 컨벤션)은 여기서 반복하지 않고 "CLAUDE.md 참고"로만 표시한다. 이 문서는 CLAUDE.md가
**다루지 않는 것**만 담는다: (1) 다이어그램에 딸린 세부 사실·미해결 이슈 기록, (2) 지금도 유효한
how-to 레퍼런스(인터랙션 튜닝값·APK 빌드 절차·CSV 테스트 절차·학식 데이터 갱신법), (3) 보류 중인
설계 문서, (4) 이미 구현이 끝난 PRD들의 "코드에서 바로 안 보이는" 결정 사항만 압축한 상태 기록.

## 1. 아키텍처 — CLAUDE.md에 없는 것만

전체 시스템 구조·게스트 우선 저장 분기·사진→영양 수치 핵심 흐름·인증(합성 이메일)·배포 토폴로지의
Mermaid 다이어그램은 루트 `README.md`에 있다(원래 이 문서의 옛 원본 `architecture.md`에도 같은
다이어그램이 있었지만, 텍스트 설명이 전부 CLAUDE.md와 겹쳐 통합 과정에서 그 부분은 버렸다 —
CLAUDE.md가 1차 출처). CSV·광고 흐름도 CLAUDE.md의 "CSV backup"/"Ads" 절이 이미 더 상세하다.

옛 `architecture.md`에만 있고 CLAUDE.md에는 없던 것 — 4~6주차에 걸쳐 쌓인 기능별 "왜 이렇게
결정했는가" 기록과, 그림을 그리며 발견한 미해결 이슈 목록이다. 아래 그대로 보존한다.

### 1.1 4주차 — 학식·급식 / 직업 추천 / AI 식습관 분석

- 급식·학식 카드는 하나(`MealCard.jsx`)를 공유 — 메뉴마다 알레르기 칩을 반복하지 않고 메뉴명 옆
  번호 위첨자(`src/lib/allergyDisplay.js`) + 카드 하단 범례 1줄로 축약. NEIS 공식 번호와 학식
  키워드 추정 둘 다 `allergyRules.js`의 M1~M19로 통일하고 `estimated` 플래그로 배지만 다르게 그린다.
- 대학 학식은 5개 식당(제2·3·4학생회관·생활과학대학 + 제1학생회관은 크롤링 데이터 자체가 없어 외부
  안내 페이지 링크로 대체) × 주간 단위로 한 번에 받아온다. 하이브리드 판정은
  `src/lib/cnuWeekFallback.js`의 순수 함수(`resolveCnuWeekResult`) 하나로 분리돼 파서/크롤러를
  몰라도 테스트 가능. 화면은 주 전체를 한 번만 받아 날짜·식당·학생/직원 트랙 전환을 전부 클라이언트
  에서 처리한다(탭 클릭마다 서버 재호출 없음).
- 직업 기반 추천(`src/lib/occupationKeywords.js`)은 부족 영양소 추천과 **병렬로** 도는 완전히
  별개의 검색 — 실패해도 서로 영향 없음. **6주차에 화면 노출(별도 섹션·범례·다른 색 핀)이
  제거되고 결과만 영양소 추천 목록에 조용히 병합**됐다(§1.3 참고) — 4주차 PRD의 "다른 색 핀 +
  범례" UI는 더 이상 유효하지 않다.
- AI 식습관 분석은 원본 끼니 기록을 절대 Gemini에 보내지 않는다 — `src/lib/dietSummary.js`의 집계
  요약(일평균 칼로리·영양소별 달성률·자주 먹은 음식·과다/부족 항목)만 전달. 같은 기간(7/30일)
  분석은 하루 1회만 호출(`dietAnalysisCache.js`, localStorage) — 그래서 "다시 분석" 버튼이 없다.

### 1.2 5주차 — 한 판 통합 분석 / 점수 100점 개편 / 식비 지도 / 학교 검색 안정화

- 한 판 통합 분석은 새 파이프라인이 아니라 기존 사진/텍스트 분석과 같은 결과 카드·저장 상태
  머신에 입력만 다르게 얹는 방식 — `AnalysisResultCard`에 `titleOverride`/`sourceNote` prop 2개만
  추가. meal record 스키마는 바꾸지 않아 식단 탭 표시 이름 규칙("첫 음식명 외 N개")도 그대로.
- 영양 점수는 리더보드/오늘의 점수 전용 공식(`nutritionScore.js`)을 배점표 기반으로 다시 짬 —
  앱이 추적하는 5개 영양소(칼로리·단백질·탄수화물·지방·나트륨)만 채점, 달력의 하루 상태 판정
  (`calcDayStatus`)은 기존 6개 기준 그대로 유지(둘은 원래 다른 목적). SQL도 같은 공식으로 다시
  짰으므로 배포된 Supabase는 `supabase/migrations/2026-07-28_score-v2-leaderboard.sql` 재적용
  필요(자세한 배점표는 [01-알고리즘.md](01-알고리즘.md) 참고).
- 식비 위치 지도는 네이버 지도 초기화를 `useNaverMap.js` 공용 훅으로 뽑아 공유(SDK 로딩 자체는
  이미 `useNaverMapLoader.js`가 모듈 전역으로 한 번만 함). 건물 좌표(5곳)는 실측 하드코딩 —
  2·4학생회관은 그 이름의 POI가 지도 서비스에 아예 없어(실측 확인) 건물 내 매장/동일 건물의 다른
  이름("2학생회관커피점", "상록회관")으로 대신 찾았다.
- NEIS 학교 검색은 `SchoolSearchField.jsx`로 분리해 입력 300ms 디바운스 + AbortController 자동
  검색으로 전환. `fetchWithTimeout`이 호출부가 넘긴 외부 `signal`도 받아 내부 타임아웃과 "이전
  검색어 요청 취소"를 구분 처리(취소는 조용히 무시, 진짜 타임아웃만 에러 표시).

### 1.3 6주차 — 정밀 영양 산출 엔진 / 인분 조절 / 나트륨 상한형 / 급식 카드 / 직업 배경화

- 정밀 영양 산출 엔진(`server/nutrition/precisionEngine.js`의 `analyzeTray()`)이 5주차의 순수
  Gemini 추정을 대체 — 식약처 DB에 실제 매칭되는 항목은 실측값, 매칭 실패분만 Gemini로 채운다.
  `server/data/foodDB.json`(11,347종)은 CSV 수동 다운로드 대신 `scripts/buildFoodDB.js`가 API로
  직접 수집했고, 학교·기관 급식 출처를 최우선해 1인분 그램이 학생 트레이 기준에 가깝게 나온다
  (외식/가정식 출처는 "탕"류 등에서 식당용 큰 그릇 단위가 섞여 있었음 — 실측으로 발견해 우선순위
  변경). **매칭률·정확도 둘 다 가이드 목표(80%, 16/20) 미달** — 구조적 한계(원재료 DB 미보유)가
  원인이라 있는 그대로 기록.
  > ⚠️ **정정(§1.5)** — "원재료 DB 미보유가 원인"은 **틀린 진단이었다.** 실제 원인은 ① 중량 기본값
  > 50g ② 기준량 placeholder 100g을 제공량으로 오인 ③ 정량 사전 커버리지 41개 ④ 빌드 dedup이
  > 외식 레코드를 폐기 ⑤ 유사도 게이트가 식약처 변형명 체계를 차단, 다섯 가지였다. 그리고 위
  > "급식 출처 최우선" 변경 자체가 제공량 문제를 고치려다 **영양밀도까지** 급식으로 바꿔버린
  > 부작용을 낳았다(§1.5에서 해소).
- 인분 수 조절은 `baseNutrients`(1인분 원본)를 절대 덮어쓰지 않고 표시·저장 시점에만 배율을
  곱하는 구조 — 이 원칙을 어기면 인분을 여러 번 오갈 때 부동소수점 오차가 쌓인다. 저장 기록에
  `servings`가 추가되지만 기존 레코드는 이 필드가 없어도 1인분으로 해석되어 마이그레이션 불필요.
- 나트륨 상한형: 조사 결과 "6개 중 4개 충족" 같은 이분법은 애초에 이 앱에 없었음을 확인 — 기존
  3단계 카운트 판정(`calcDayStatus`)은 그대로 두고 "영양소별 방향(target/limit)" 규칙만
  `nutrientCriteria.js` 하나로 모았다. 이 과정에서 `dietSummary.js`가 나트륨 방향을 반전하지 않아
  "적게 먹어 잘하고 있는 날"을 "부족"으로 잘못 판정하던 실제 버그를 발견해 고쳤다.
- 급식 카드는 `MealCard.jsx`에 `layout='numbered'|'stacked'` prop 하나만 추가 — 급식만 세로·가운데
  정렬, 학식 카드는 `layout` 미지정(기본값 `'numbered'`)으로 코드 변경 없이 그대로 동작.
- 직업 추천은 화면 노출(별도 섹션·범례·다른 색 핀)만 제거하고 검색 결과는 조용히 영양소 추천
  목록에 병합 — 직업 매칭 장소는 예상 섭취량 계산을 거치지 않아 "추천 이유" 자체가 안 뜨므로,
  텍스트로 직업을 언급할 자리가 없다.

### 1.4 그림을 그리며 발견한 것 — 기록 시점 기준 미해결 이슈

architecture.md 작성 당시 실제로 어긋나 있던 연결들. 코드는 고치지 않고 기록만 남겼던 것들이라,
이 문서 작성 시점까지도 별도로 고쳤다는 근거가 없으면 아직 유효하다고 보고 다룰 것.

1. **기간별 CSV의 `recommended_*`/`compliant`는 항상 빈칸** — `csv.js`의 내보내기가
   `dailyRecord.getRecord()`로 "그날의 권장량 스냅샷"을 읽는데, 그 스냅샷을 쓰는 유일한 함수
   `dailyRecord.upsertMeal()`을 아무도 호출하지 않는다. 끼니 저장은 전부 `dataStore →
   mealStore/Supabase`로 가는데 이 스냅샷 경로만 옛 구조에 남음 → 신규 기록에서 해당 컬럼이 항상
   빈 값(파일 형식은 유효해 가져오기는 정상). 선택지: 컬럼을 내보내기에서 빼거나, 저장 시점의
   `effectiveRecommended`를 실제로 스냅샷하거나.
2. **Kakao는 "롤백용"인데 키는 현역** — `/api/places`·`/api/geocode`·`kakao.js`의 `searchPlaces`·
   `PlaceMap.jsx`·`useKakaoLoader.js`는 어떤 화면도 안 쓰지만, `/api/reverse-geocode`(좌표→지역명)는
   지금도 쓰여서 `KAKAO_REST_API_KEY`가 여전히 필수. 롤백 코드와 현역 기능이 같은 키·같은 파일을
   공유해 롤백 코드를 지우려 해도 깔끔히 안 떨어짐. 선택지: 역지오코딩을 네이버로 옮기거나, 롤백
   경로를 정식 폐기 선언.
3. ~~텍스트 분석은 식약처 DB를 안 탄다~~ — **해소됨**. 텍스트 경로를 사진 경로와 같은 구조
   (AI 식별 → `resolveFoodItem` 공유 → 식약처 DB 캐스케이드)로 재구성.
4. **로그인해도 기기에 남는 설정** — `dayStatus`(달력 수동 상태)·`cardSettings`(표시 영양소)·
   `adData`(광고 집계)는 `effectiveUserId`로 키를 잡지만 저장 위치는 항상 localStorage. 같은
   계정으로 다른 기기에 로그인하면 이 설정들은 따라오지 않는다(식단·프로필만 동기화).
5. **업데이트 채널이 둘** — APK가 원격 URL을 로드하므로 웹 배포 = 앱 업데이트지만, Capacitor
   플러그인은 APK 재설치가 필요. 웹 코드가 새 플러그인을 쓰기 시작하면 배포는 됐는데 구버전
   APK에서만 깨지는 상태가 생길 수 있음(3주차 CSV 저장이 정확히 이 형태였음). 선택지: 네이티브
   기능 호출부에 "플러그인 없음" 폴백(`fileExport`는 이미 있음), 또는 앱 안에 최소 버전 안내.
6. **게스트 데이터는 기기 하나에 묶임** — `GUEST_ID = 'guest'` 고정 버킷 하나뿐이라 한 브라우저 =
   한 게스트. 기기 이동 수단은 CSV 백업뿐이고 캐시를 지우면 복구 경로가 없음(의도된 설계지만
   사용자에게는 MY 탭 안쪽에만 그 사실이 있음).

### 1.5 식당 음식 정확도 오버홀 — "돼지갈비 73kcal" 추적기

사용자 신고: 지도 탭 식당 대표메뉴 "돼지갈비"가 **73kcal**, 한 판 통합 분석에서도 **110kcal**.
재현 결과 원인이 네 겹이었고, 각각이 독립적으로 2~5배씩 값을 깎고 있었다.

| # | 원인 | 증거 | 조치 |
|---|---|---|---|
| A | 중량이 50g으로 떨어짐 | `classifyMenuRole('돼지갈비')`이 어떤 패턴에도 안 걸려 `DEFAULT_ROLE='side'`(50g) | `mealPortions.js`에 갈비·족발·강정·생선조림 계열 패턴 추가 + `matched` 플래그 반환 |
| A' | 가드가 **거꾸로** 걸림 | `ratio = dbItem.servingGram / referenceWeight` = 220/50 = 4.4 → 정확한 220g을 "이상치"라며 기각하고 틀린 50g 채택 | 비율 가드 폐기 → `servingWeight.js`의 **역할별 절대 범위** |
| A'' | 기준량 placeholder | foodSize가 정확히 `100`인 레코드 871건은 1회 제공량이 아니라 영양성분 기준량이 새어 들어온 값 | `isUsableServingGram`이 100을 거부 |
| B | 정량 사전 41개뿐 | 갈비·수육·보쌈·족발·닭갈비·초밥·회·햄버거·피자·죽 등이 전부 미등록 → 중량 기준도 현실범위 보정도 **둘 다** 미적용 | `foodData.js`에 20여 항목 추가(수치는 외식 출처 레코드 평균에서 역산) |
| C | 빌드가 외식 레코드 폐기 | `buildFoodDB.js`의 dedup이 이름당 1건만 남김 + 우선순위가 급식 → 김치찌개 19kcal/100g, 돼지갈비구이 132(외식 294) | `variants[]`로 출처 전부 보존 + 조회 시 맥락(`restaurant`/`cafeteria`)으로 선택 |
| D | 유사도 게이트 충돌 | 식약처는 `기본명_수식어` 체계인데 게이트는 endsWith만 통과 → `김치찌개→김치찌개_돼지고기` 0.14로 탈락, 갈비류는 `resolveFood` 경로에서 **매칭 자체가 실패** | `_` 변형명·조리법 접미사만 예외 처리(오매칭 차단은 유지) |

**기존 보정 레이어가 왜 하나도 못 잡았나** — 둘 다 원리상 이 오류에 무력하다.
`applyAtwaterEnsemble`은 탄단지를 `calories`에 맞출 뿐 `calories`를 고치지 않는데, foodDB 11,347건
전수 측정 결과 레코드는 이미 자기 정합이라(출처별 이탈률 0~5%) 사실상 무동작이었다.
`clampToPlausibleNutrients`는 하한의 50% 미만만 잡는데 돈가스 급식 296kcal은 바닥 215보다 커서
안 걸렸고, 돼지갈비는 애초에 표에 없었다. 밴드를 좁히는 건 오탐 때문에 못 한다(의도된 설계) —
**계통적 오류는 보정이 아니라 데이터 선택과 중량 결정에서 고쳐야 한다.**

**구조 변경 두 가지**
- `server/nutrition/servingWeight.js` 신설 — 중량 결정을 `resolveFood`와 `precisionEngine`이
  서로 다르게 하던 것을 한 곳으로 모았다(두 엔진이 같은 입력에 다른 답을 내던 게 A의 배경).
- `servSize` / `referenceServingGram` 분리 — 로컬 음식DB의 1인분을 `servSize`에 실으면
  `resolveConsumedGrams`가 **사진에서 추정한 실제 섭취량을 덮어써서** 곱빼기·소식이 전부 표준
  1인분으로 뭉개진다. `servSize`는 포장 단위처럼 진짜 근거가 있는 값만 담는다.

**왜 여기까지 왔나 (재발 방지)** — 유일한 정확도 스크립트가 NEIS 급식 20건만 채점했다. 벤치마크가
급식뿐이라 §1.3의 "급식 출처 최우선" 같은 결정이 계속 급식 쪽으로 흘렀고, 앱 사용의 대부분인 식당
음식은 한 번도 측정되지 않았다. 무과금 오프라인 벤치마크를 추가해 **두 벤치마크가 동시에 통과해야**
회귀가 아니게 했다(§1.7에서 `scripts/nutritionAccuracy.js`로 확장·대체).

### 1.6 급식 트레이 과다 계산 — 이름 유사도의 구조적 공백

§1.5 직후 "급식 한 판 단백질 42g·지방 41g"이 보고됐다. 원인이 §1.5와 또 달랐다.

- **`precisionEngine`에 유사도 게이트가 아예 없었다.** `resolveFood`는 예전부터 0.7 미만을
  걸렀는데 트레이 엔진에만 없어서, **유사도 0.0짜리 오매칭이 무검증 합산**되고 있었다
  (실측: `콩자반`→`간자장`, `양념갈비`→`양념두부`). 같은 게이트를 이 엔진에도 붙였다.
- **그런데 게이트를 그대로 붙이면 좋은 매칭의 29%가 함께 죽었다.** `foodNameSimilarity`가
  접두/접미/포함 관계만 모델링해서, 한국어 급식 메뉴의 지배적 형태인 **가운데 재료 삽입**
  (`꽁치김치조림`↔`꽁치조림`, `참치야채죽`↔`참치죽`, `감자채볶음`↔`감자볶음`)이 전부 0점이었다.
  NEIS 288항목 기준 DB가 찾은 198건 중 **57건**이 이렇게 버려졌다 → 앞머리·꼬리 공유도 규칙 추가
  (탈락 57 → 26건, 남은 26건은 대부분 진짜 오매칭).
- **그 완화의 안전장치로 "꼬리(음식 종류)가 다르면 차단"을 넣었다.** 없으면 `계란국`이
  `계란빵`에 0.75로 붙어 국 한 그릇이 158kcal/100g짜리 빵으로 계산된다(실측 474kcal).
- **트레이 중량을 역할 표준 우선으로.** §1.5에서 식당용으로 만든 `referenceGrams`가 트레이에도
  1순위로 적용돼 부찬이 두 배로 잡혔다(잡채 200g). 근거는 §1.5 표가 아니라 실측 —
  같은 58% 매칭 항목이 역할 우선 52% vs 사전 우선 66%(공식 열량 대비).
- **트레이 프롬프트에 식당용 문구를 잘못 넣었었다.** §1.5에서 "조리 기름·양념을 반영하라(재료만
  계산하면 낮아진다)"를 세 프롬프트에 일괄 적용했는데, 급식은 반대로 기름·양념이 적다 —
  트레이 프롬프트만 "급식 식판이다, 외식 수치를 가져오면 과대추정" + 총량 가이드로 되돌렸다.

실측 결과(실제 CNU 7첩): **1021 → 733kcal, 단백질 41.9 → 34.9g, 지방 21.4 → 16.1g,
식이섬유 16.5 → 8.9g.** 새우볶음밥 트레이: 1156 → 752kcal, 단백질 47.7 → 34.9g.

⚠️ **NEIS 벤치마크로는 이 개선이 안 보인다** — 통과 11/20 → 9/20, 평균오차 22.8% → 22.7%.
이유를 측정했다: 급식 메뉴 항목의 **42%가 DB에 아예 없고**(몬테크리스토샌드위치·푸팟퐁커리·
감바스알리오올리오·십원빵 같은 현대/퓨전/브랜드 메뉴), **공식 열량의 48%를 Gemini가 채운다.**
20개 표본에서 통과/탈락은 그 LLM 출력에 좌우돼 규칙 변경 신호를 덮는다. 평균오차가 더 안정적인
지표이고 그건 평평하다. **여기서 통과 개수를 좇아 튜닝하지 말 것** — 진짜 병목은 DB 커버리지다.

## 2. 인터랙션 구현 — 튜닝 레퍼런스

PRD v2 §4의 구현 결과. 코드는 5개 파일이 전부: `src/components/Pressable.jsx`(공통 프레스
컴포넌트 — 버튼/탭/카드 전부 경유), `src/lib/tabs.js`(탭 순서 단일 소스), `src/lib/useTabTransition.js`

### 2.1 framer-motion을 안 쓰는 이유(번들 실측)

| | raw | gzip |
|---|---|---|
| 도입 전 | 579.64 kB | 170.01 kB |
| framer-motion 도입 후 | 705.49 kB | 211.08 kB (+41.07 kB, +24%) |
| 채택한 CSS 방식 | 581.82 kB | 170.93 kB (+0.92 kB) |

임계치(gzip 40KB) 초과로 기각. APK가 번들을 내장하지 않고 원격 URL을 그대로 로드하므로 증가분을
콜드 스타트마다 모바일 네트워크로 받는다는 점도 근거 — 요구되는 모션이 전부 `transform`/`opacity`뿐
이라 CSS로 동일하게 구현 가능해 라이브러리 이득이 없다.

### 2.2 화면 전환이 두 갈래인 이유

- **View Transitions API 지원(Chrome/Android WebView 111+, 기본 경로)**: 브라우저가 나가는/
  들어오는 화면을 스냅샷으로 합성 — 이전 라우트를 직접 들고 있다가 재렌더할 필요가 없어
  `useEffect` 재실행(지도 검색·AI 추천 API 중복 호출) 문제가 없다.
  ```js
  document.startViewTransition(() => flushSync(() => navigate(toPath)))
  ```
  `flushSync`가 없으면 React 18+ 비동기 렌더링 때문에 콜백 종료 시점에 새 화면이 DOM에 없어
  전환이 빈 화면으로 잡힌다.
- **미지원 브라우저**: 들어오는 화면만 방향대로 슬라이드-인(`.tds-screen`), 나가는 화면 연출만 빠짐.
- `data-nav-direction`은 탭바를 거치지 않는 이동(화면 안 `Link`, 뒤로가기)에서도 갱신돼야 한다.
  `AppShell`이 경로 변경마다 다시 계산해 `none`으로 되돌린다 — 없으면 직전 탭 전환 방향값이 남아
  같은-탭 이동에도 엉뚱한 슬라이드가 붙는다.
- **상단바/하단 탭바는 전환에서 제외**: `::view-transition-old/new(root)` 스냅샷은 화면 전체라
  `position:fixed`인 탭바도 포함됨 — 조치 없이 root에 `translateX`를 걸면 탭 전환마다 탭바가
  깜빡인다. 해결: 두 바에 각자 `view-transition-name`을 줘 root에서 분리(`.tds-appbar`=Header,
  `.tds-tabbar`=BottomTabBar), 크로스페이드를 꺼서(`old`는 `display:none`, `new`는 `animation:none`)
  전환 내내 제자리 유지 + 탭 아이콘 바운스가 라이브로 계속 재생되게 함(`new`가 정지 이미지가 아닌
  실제 라이브 표현이라 가능). `::view-transition-group`의 기본 위치/크기 보간은 일부러 남김(헤더는
  스크롤 복원 위치가 화면마다 달라질 수 있어 튀지 않게). 이 규칙들은 `prefers-reduced-motion`
  미디어쿼리 **밖**에 둔다. 구조적으로도 `AppShell`/`LoadGate`가 레이아웃 라우트라 탭바가 항상
  마운트 상태를 유지(`src/__tests__/appShell.tabbar.test.jsx`가 DOM 노드 동일성으로 고정).

### 2.3 FR-4.3 검증 — 애니메이션 속성 전수 확인

```bash
grep -rn "transition:" src/ --include=*.jsx --include=*.js --include=*.css | grep -viE "transform|opacity"
```

## 3. APK 빌드 절차

원격 URL 방식(현재)/로컬 번들 방식의 트레이드오프, 외부 링크·카메라/위치 권한·뒤로가기·로그인·CSV의
동작 방식은 **CLAUDE.md의 "Android app wrapper" 절이 이미 다룬다** — 여기는 실제 빌드 단계만.

### 3.1 최초 1회 확인

`capacitor.config.json`의 `server.url`이 실제 배포 고정 주소인지 먼저 확인(틀리면 흰 화면 — 가장
흔한 실패 원인). Vercel 프로젝트 Settings → Domains에서 확인, 다르면 `url`/`allowNavigation` 첫
항목을 갱신하고 `npm run app:sync:config` 실행. **주소를 바꿨다면 네이버 클라우드 Maps 콘솔의 Web
서비스 URL과 Supabase Auth의 Redirect URL에도 그 주소를 등록**해야 지도·로그인이 정상 동작한다.

### 3.2 사전 준비

- Android Studio(SDK 포함) + JDK 17. Android Studio 내장 JBR로 충분하고, 터미널에서 `gradlew`를
  직접 돌릴 때는 `$env:JAVA_HOME = "C:\Program Files\Android\Android Studio\jbr"`로 잡아준다.
- `targetSdkVersion`은 34다. **직접 배포(APK 파일 전달·사내 배포)에는 문제없지만, Google Play에
  올릴 거라면 플레이 정책상 더 높은 targetSdk가 요구될 수 있다** — 그때는 `variables.gradle`을
  올리고 권한·백그라운드 제약 변경사항을 다시 검증해야 하므로 별도 작업으로 잡을 것.
- `npm install` 1회(Capacitor 패키지는 이미 `package.json`에 있음). `android/`는 이미
  `npx cap add android` 완료 상태, 권한(인터넷·네트워크 상태·카메라·위치)도
  `AndroidManifest.xml`에 이미 반영·`usesCleartextTraffic="false"`도 켜져 있음.

### 3.3 아이콘·스플래시

`scripts/make-android-icons.ps1`이 `branding/symbol image.png`에서 런처 아이콘 15개(적응형 전경 +
레거시 사각·원형 × 5밀도)와 스플래시 11개(세로·가로 × 5밀도 + 기본)를 만든다. 결과 PNG는 커밋돼
있으므로 **로고를 바꿀 때만** 다시 돌리면 된다.

```powershell
powershell -ExecutionPolicy Bypass -File scripts\make-android-icons.ps1
```

`@capacitor/assets`를 쓰지 않은 이유와 크롭 좌표를 픽셀로 찾는 이유는 스크립트 헤더 주석에 있다
(요약: 원본이 캡션 박힌 시안 이미지라 그대로 쓰면 아이콘에 "FAVICON (512x512 PNG)" 글자가 들어간다).
적응형 아이콘 배경색(`values/ic_launcher_background.xml`)은 스크립트의 `$BG`와 같은 값이어야 한다.

### 3.4 설정 반영 — **릴리스 빌드 전 반드시 실행**

```bash
npm run app:sync          # = vite build → cap sync android
```

`cap sync`가 하는 일이 두 가지고 **둘 다 빼먹으면 조용히 틀린 APK가 나온다**:

1. `dist/` → `android/app/src/main/assets/public` 복사 + `capacitor.config.json` 생성
2. **설치된 Capacitor 플러그인을 네이티브 프로젝트에 등록**(`capacitor.build.gradle` /
   `capacitor.settings.gradle`)

②를 놓치면 웹 코드는 플러그인을 부르는데 APK에는 그 플러그인이 없는 상태가 된다 — 빌드는 성공하고
화면도 멀쩡한데 그 기능만 런타임에 죽는다. 실제로 출시 직전까지 `@capacitor/filesystem`과
`@capacitor/share`가 등록돼 있지 않았고(= APK에서 CSV 내보내기가 동작하지 않는 상태), §1 목록의
"업데이트 채널이 둘" 항목이 예고한 사고가 그대로 일어나 있었다. **`npm install`로 Capacitor
플러그인을 추가/삭제했다면 `app:sync` 후 두 gradle 파일의 diff를 반드시 커밋할 것.**

`assets/public`은 `.gitignore` 대상이라 `cap sync`가 덮어쓰기만 하고 **지워진 파일은 남긴다.**
`public/`에서 뺀 파일이 계속 APK에 실릴 수 있다 — 실제로 branding 목업 3개(14MB)가 남아 있어
APK가 18MB였고, 폴더를 지우고 다시 sync하니 4MB가 됐다. 이상하게 크면 다음을 먼저 의심할 것:

```bash
rm -rf android/app/src/main/assets/public && npm run app:sync
```

로컬 번들 방식으로 되돌린 경우만 배포 백엔드 주소를 넣어 빌드:

```bash
# Windows PowerShell
$env:VITE_API_BASE_URL="https://<배포주소>"; npm run app:sync
```

### 3.6 서명된 릴리스 APK

서명 설정은 `android/app/build.gradle`의 `signingConfigs.release`에 들어 있고, 값은
`android/keystore.properties`에서 읽는다(커밋 금지 — 템플릿은 `keystore.properties.example`).
그래서 **Android Studio에서 빌드 변형을 release로 두고 Build > Build APK(s)만 눌러도 서명된 APK가
나온다** — 마법사에서 매번 keystore를 고를 필요가 없다.

**최초 1회 — 키스토어 만들기**

Android Studio → Build → Generate Signed Bundle / APK → APK → **Create new...** 로 만들거나,
터미널에서:

```powershell
& "C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe" -genkeypair -v `
  -keystore android\mealyze-release.jks -alias mealyze -keyalg RSA -keysize 2048 -validity 10000
```

그 뒤 `android/keystore.properties.example`을 `android/keystore.properties`로 복사해 채운다.

⚠️ **`storeFile`에 윈도우 절대경로를 쓸 때 `\` 대신 `/`를 쓰거나 `\\`로 이스케이프할 필요는 없다** —
build.gradle이 `Properties.load()`를 쓰지 않고 `key=value`를 그대로 읽는다. 규격대로
`Properties.load()`를 쓰면 `C:\Users\...`의 `\U`가 사라지고 `\t`가 탭이 되어
"Keystore file not found"가 나는데, 키스토어는 저장소 밖에 두는 게 맞으니 절대경로가 정상
사용 형태다(구현 중 실제로 밟았다).

**빌드**

```powershell
$env:JAVA_HOME = "C:\Program Files\Android\Android Studio\jbr"
cd android; .\gradlew.bat :app:assembleRelease
```

또는 Android Studio → Build Variants를 `release`로 → Build → Build APK(s).
산출물은 `android/app/build/outputs/apk/release/app-release.apk`(현재 약 4MB).

`keystore.properties`가 없으면 **빌드가 즉시 실패한다.** Gradle 기본 동작은 실패가 아니라
`app-release-unsigned.apk`를 뱉는 것인데, 그건 기기에 설치되지 않으면서 빌드는 초록색이라
"빌드는 됐는데 왜 설치가 안 되지"로 만나게 된다. `build.gradle`의 `gradle.taskGraph.whenReady`
가드가 그 경우를 끊는다(Generate Signed 마법사는 keystore를 직접 주입하므로 막지 않는다).

**서명 확인**

```powershell
& "$env:LOCALAPPDATA\Android\Sdk\build-tools\34.0.0\apksigner.bat" verify --verbose --print-certs `
  android\app\build\outputs\apk\release\app-release.apk
```

`Verified using v2 scheme: true`와 인증서 DN이 우리 것인지 본다. `META-INF/... not protected by
signature` WARNING 수십 줄은 v1(JAR) 서명 스킴의 정상 잡음이고 exit code도 그 때문에 0이 아니다 —
문제 아님.

⚠️ **키스토어와 비밀번호를 잃으면 같은 앱으로 영원히 업데이트할 수 없다.** applicationId가 같아도
서명이 다르면 기기가 설치를 거부하고, 사용자는 기존 앱을 지우고 새로 깔아야 한다(게스트 모드
로컬 데이터도 함께 사라진다). 저장소 바깥에 따로 백업할 것.

⚠️ **재배포할 때마다 `versionCode`를 올린다**(`android/app/build.gradle`). 다만 서버 URL 방식이라
**웹 변경만으로는 APK 재배포가 필요 없다** — 네이티브 설정·권한·아이콘·플러그인이 바뀔 때만이다.

## 5. 대학 학식 폴백 JSON 갱신 (`server/data/univ-meals.json`)

크롤링(`server/univMealAdapters/cnu.js`)이 실패했을 때만 대신 쓰인다. **평소엔 자동 갱신** —
크롤링이 성공하면 서버가 그 결과를 이 파일에 그대로 저장해 다음 실패 때의 최신 폴백이 된다. 아래는
크롤링이 오래 실패했을 때만 필요한 수동 절차다.

1. 제2·3·4학생회관·생활과학대학(4개 건물 — 제1학생회관은 이 시스템에 데이터가 없어 항상
   `external`, 갱신 대상 아님)의 실제 운영 메뉴를
   https://mobileadmin.cnu.ac.kr/food/index.jsp 에서 확인.
2. `cnu.days`의 해당 날짜(`YYYYMMDD`) →
   `cafeterias.<cnu2|cnu3|cnu4|cnuLife>.meals.<breakfast|lunch|dinner>.<student|staff>`에 채움:
   ```json
   { "status": "open", "price": 6000, "note": null, "menus": [{ "name": "메뉴명", "allergyCodes": ["M6"], "estimated": true }] }
   ```
   운영 안 하는 끼니는 `{ "status": "closed", "price": null, "note": null, "menus": [] }`.
3. `cnu.updatedAt`을 오늘 날짜(`YYYY-MM-DD`)로 갱신 — 화면 "○월 ○일 기준" 안내에 그대로 쓰임.
4. 저장 후 커밋·배포.

스키마: `cnu = { week: 'YYYYMMDD'(그 주 월요일), updatedAt, days: [{ date, cafeterias: { cnu1(항상
status:'external'), cnu2, cnu3, cnu4, cnuLife } }] }` (보통 월~토 6일). `meals.<끼니> = { student:
MealSlot, staff: MealSlot }`, `MealSlot = { status: 'open'|'closed'|'suspended'|'external', price,
note, menus: [{name, allergyCodes, estimated:true}] }`.

## 6. 예정/보류 중 — 쿠팡 파트너스 상품 자동 수집

**보류 중** — 파트너스 API 키 발급 조건(누적 판매금액 약 15만원) 미충족. 아래는 조사·설계가 끝난
상태의 사양이다.

### 6.1 원래 구상("사용자 요청마다 실시간 검색")이 불가능한 이유

- 검색 API 호출 한도가 **시간당 10회**(전체 계정 기준, 공식 문서의 "분당 50회"는 실제와 다름).
  초과 시 `rCode: 403`, **403이 3번 누적되면 파트너스 계정 API가 영구 제한될 수 있음**.
- API 키 발급에 누적 판매금액 약 15만원 조건 — 파트너스 가입만으로는 안 나옴.
- 검색 결과 최대 10개, `minPrice`/`maxPrice` 파라미터 미지원(넣어도 무시되고 가격 뒤섞임).

### 6.2 대안 설계 — 사전 수집 + 정적 서빙

사용자별로 달라지는 건 "어떤 영양소가 부족한가"뿐이고(이미 `adRecommendation.js`가 판정), 영양소는
11개(`AD_NUTRIENTS`)로 고정 — 즉 자동화할 부분은 "영양소별 상품 목록을 최신으로 유지하는 것" 하나뿐.

```
[주기적 배치] scripts/fetch-coupang-products.mjs — 영양소 11개 × 검색 1회(시간당 10회 한도 →
  6분 간격 강제, 또는 주 1회) → src/data/coupangProducts.generated.json(커밋)
[런타임] API 호출 0회 — adRecommendation.js/DeficientNutrientAds.jsx는 이 파일을 읽기만 함(변경 없음)
```

장점: 한도 안전(런타임 호출 0), 서버 라우트 불필요(Render/Vercel 이중 배포 문제 없음), 키 노출
위험 0(로컬/CI Secret에만), 배치 실패 시 직전 커밋 JSON이 폴백. 잃는 것: "같은 영양소 사용자끼리
다른 상품" 개인화는 포기(하지만 개인화 자체는 이미 영양소 판정 단계에서 일어남).

### 6.3 키가 없는 동안 지금 할 수 있는 것(권장)

현재 등록된 제휴 링크 9개의 **상품명·가격·이미지만 손으로** `src/data/coupangProducts.js`에 채우면
지금 구조에서 카드가 완성된다(각 항목의 `// sourceUrl:` 주석에 실제 상품 페이지 주소 있음). 상품명을
채우면 같은 영양소의 2·3번 상품도 자동으로 노출 대상이 된다(지금은 중복 방지로 1번만 씀).

### 6.4 기술 사양 (키 확보 후 Step 2에서 그대로 사용)

**HMAC 인증**:
```
message   = datetime + method + path + query   (이 순서로 단순 연결, query는 ? 없이 별도)
datetime  = UTC "yyMMddTHHmmssZ" (예: 260722T143022Z)
signature = HMAC-SHA256(message, SECRET_KEY)   (hex)
header    = Authorization: CEA algorithm=HmacSHA256, access-key=<ACCESS>, signed-date=<datetime>, signature=<sig>
```

**검색 응답**: `{ rCode, rMessage, data: { productData: [{ productId, productName, productPrice,
productImage, productUrl, isRocket, categoryName }] } }` — `rCode==="0"`이면 성공, `productUrl`에
제휴 추적이 이미 붙어 있어 별도 deeplink 변환 불필요.

**스키마 매핑**: `productId→id(cp-<nutrient>-<productId>)`, `productName→productName`,
`productPrice→price`, `productImage→imageUrl`, `productUrl→partnersUrl`, 검색 키워드로 `nutrient` 역산.

### 6.5 구현 시 반드시 지킬 제약

| 항목 | 이유 |
|---|---|
| 호출 간 최소 6분 간격 강제 + 403 시 즉시 중단 | 시간당 10회 한도, 403 3회 = 계정 영구 정지 가능성 |
| 런타임 호출 금지 | 배치 전용, 사용자 요청 경로에서 절대 호출 안 함 |
| `COUPANG_ACCESS_KEY`/`COUPANG_SECRET_KEY`는 `VITE_` 접두사 금지 | 이 설계에서는 배포물에 아예 안 들어감(로컬/CI Secret만) |
| 배너는 항상 표시(빈 배열 금지) | `generated.json`이 비거나 깨져도 손입력 목록으로 폴백해야 함 |

- **FR-19 커스텀 조합 빌더**: 이름 매칭 없이 DB 항목을 직접 선택(Gemini 호출 없음) —
  `buildComboAnalysis`는 기존 `scaleNutrients`/`sumNutrients`만 조합하는 순수 함수. 완료 시 기존
  `AnalysisResultCard`/저장 흐름에 그대로 합류.
- **FR-20 동적 수분 목표**: `getWaterTargetMl(weightKg, activity) = weightKg×30 × (1+보너스)`,
  보너스 `{low:0, moderate:0.08, high:0.15}`(TDEE 계수를 그대로 곱하면 비현실적으로 커져 완만하게
  재정규화). 신체정보 없으면 기존 8잔 상당(1600ml) 폴백. 저장 모양이 `{glasses}`→`{mlConsumed}`로
  바뀌었지만 레거시 `{glasses}` 레코드는 읽을 때만 `glasses×200`으로 환산(소급 변환 없음).
- **FR-21 비밀번호 찾기(보안 질문)**: 가입 시 보안 질문 5개 중 택1 + 답 등록(`crypto.scrypt` 해시,
  `security_questions` 테이블 — RLS는 켜되 정책 없음, `SUPABASE_SERVICE_ROLE_KEY`로 서버만 접근).
  `/forgot-password`에서 아이디 → 질문 확인 → 답+새 비밀번호로 재설정. 계정(login_id) 단위 5회 실패
  → 15분 잠금(로그인 실패 잠금의 "5회→1분"과는 별개 상수). 오답과 "계정 없음"은 같은 문구로 응답해
  계정 존재 여부 비노출. **`supabase/migrations/2026-07-29_security-questions.sql` 실행 +
  `SUPABASE_SERVICE_ROLE_KEY` 환경변수(서버 전용, `VITE_` 접두사 절대 금지 — 없으면 이 기능 전체가
  500 에러) 설정 필요.** 서버(`server/proxy.js`)가 여기서 처음으로 Supabase를 직접 호출한다
  (`server/supabaseAdmin.js`) — 그 외 기존 라우트는 여전히 클라이언트가 anon key+RLS로 직접 접근.

**아직 실행 안 됐을 수 있는 Supabase 마이그레이션 3종**(순서대로): `2026-07-29_gamification.sql` →
`2026-07-29_xp-leaderboard.sql` → `2026-07-29_security-questions.sql`. 배포된 Supabase 프로젝트에서
리더보드/보안 질문/레벨 관련 에러가 나면 가장 먼저 이걸 의심할 것(`schema.sql` 자체가 이 마이그레이션들
전부를 반영한 최신본이므로, 신규 프로젝트라면 `schema.sql` 한 번 실행으로 충분).

### 1.7 경로 분리 — 단일 메뉴 / 복합 메뉴 / 배식 정량

§1.5·§1.6이 각각 하나의 증상을 고쳤다면, 이번엔 **"어디서 나온 음식이냐"를 화면이 아니라 항목마다
판정**하도록 구조를 바꿨다. 외부 기획안(제미나이)을 현재 스택과 대조해 채택·조정한 결과다.

#### 왜 필요했나 — 화면 단위 하드코딩의 한계

맥락(`context`)은 §1.5에서 도입됐지만 **화면이 고정값을 보냈다**: 사진·텍스트 분석은 무조건
`restaurant`, 학식 패널은 무조건 `cafeteria`. 그래서

- 사용자가 **급식 식판을 사진으로 찍으면** 외식 수치(김치찌개 61kcal/100g)로 계산됐고,
- **편의점 도시락·프랜차이즈 포장**도 마찬가지였다 — 업체가 식약처에 제출한 공식 수치가 DB에
  9,346건이나 있는데 그걸 우선 볼 방법이 없었다.

이제 AI가 항목마다 `servingContext`(`restaurant`/`packaged`/`cafeteria`/`home`)를 판정해 돌려주고,
**항목 값이 요청 단위 기본값을 이긴다**. 한 사진 안에 급식 식판과 포장 음료가 같이 있을 수 있어,
요청 하나에 맥락 하나로는 원리상 둘 다 맞출 수 없다.

#### 측정 — 무과금 벤치마크로 드러난 진짜 병목

`scripts/nutritionAccuracy.js`(§1.5의 `restaurantAccuracy.js`를 확장·대체)를 만들어 식약처 DB가
가진 **실측 1회 제공량**을 정답지로 8천 건 규모를 쟀다. 여기서 지배적인 원인 하나가 나왔다:

> **프랜차이즈 레코드 8,259건 중 57.5%가 "역할 절대범위 밖"이라며 진짜 제공량을 기각당하고 있었다.**

원인은 §1.5에서 고친 것과 **글자 그대로 같은 순환**이었다. `classifyMenuRole`이 11,347종 중
3,606종(31.8%)에서 실패하고 그때 기본값 `side`가 되는데, 그 역할의 범위 20~150g이 검사에 그대로
쓰였다. §1.5에서는 그 순환을 비율 가드의 **분모**에서만 걷어냈고, **범위 검사 쪽에는 남아 있었다.**

| 지표 | 전 | 후 |
|---|---|---|
| 외식·가정식 근거 폐기율 | 56.1% | **46.0%** |
| └ 최종 평균오차 | 44.2% | **31.0%** |
| 프랜차이즈 근거 폐기율 | 72.9% | **0.0%** |
| 급식 근거 폐기율 | 82.3% | 78.4% |

(프랜차이즈가 0%인 건 `packaged` 맥락이 표시 제공량을 최우선으로 쓰기 때문이다 — 제조사가 표시한
1회 제공량은 추정이 아니라 사실이라 한식 역할 표준으로 이상치 판정할 근거가 없다.)

#### 기획안 대조 — 채택하지 않은 것과 그 이유

| 기획안 항목 | 판정 |
|---|---|
| 참조물(수저·종이컵·접시) 스케일 프롬프트 | **채택** — 실제 식기 치수를 자로 준다 |
| 조리법 보정 칩 | **채택**, 단 `confidence === 'high'`가 아닐 때만 노출 |
| `isPackagedFood`/`isFranchiseBrand` 플래그 | **채택**(`servingContext: 'packaged'`로 통합). 그전까지 브랜드는 배지에만 쓰이고 DB 조회엔 아무 영향이 없었다 |
| 배식비율(Portion Ratio) | **채택** — LLM은 절대 그램보다 상대 비율을 훨씬 잘 맞힌다 |
| 주재료 범주 사전 veto | **경량판 채택** — 새 분류체계 대신 기존 role 충돌로(인접 역할은 예외) |
| **`trayPosition` 위치 기반 역할** | **미채택.** 급식 경로엔 **사진이 아예 없다**(NEIS/학식 메뉴 텍스트). 식판 사진 경로에서도 5구 식판 배치는 학교마다 달라 이름보다 약한 신호고, 이미 `role`을 직접 묻고 있어 중복이다 |

#### 부수 수정 — 원격 소스 경쟁 조건

음식DB와 가공식품DB를 병렬 조회한 뒤 **먼저 도착한 쪽**을 채택하고 있었다(`if (state.resolved)
continue`). 같은 이름이 양쪽에 다 있으면 그날의 네트워크 사정에 따라 같은 입력에 다른 답이 나온다.
맥락별 우선순위(`REMOTE_SOURCE_PREFERENCE`)로 결정론화했다.

#### 급식 경로 회귀 확인

이번 변경 중 급식에 닿는 건 둘이다: 역할 범위 완화(위)와 `precisionEngine`이 매칭된 DB 레코드의
`category`를 역할 힌트로 넘기게 한 것(예전엔 그 값을 Gemini 프롬프트용으로만 쓰고 **중량은 원래
메뉴명으로 다시 분류**해서 같은 항목의 역할이 두 곳에서 갈릴 수 있었다).

오프라인으로 실제 트레이 중량을 비교하니 사실상 그대로였다(CNU 7첩 850g 변화 없음, 단무지만
30g→50g — 역할 표준을 따라간 것으로 의도한 동작). NEIS 유료 벤치마크도 **통과 9/20 → 10/20,
평균오차 22.7% → 22.7%**로 회귀 없음.

⚠️ **이 개선도 §1.6과 같은 이유로 NEIS 벤치마크에는 거의 안 잡힌다.** 급식 항목의 42%가 DB에 없어
LLM이 채우는 구조가 그대로이기 때문이다(위 "최악 3개"가 전부 `[gemini]` 항목이 열량의 절반 이상을
차지하는 케이스다). `npm run check:nutrition`(무과금)의 [1]/[2]를 1차 게이트로 쓰고, 유료 벤치마크는
평균오차만 확인하는 용도로 드물게 돌린다.

### 1.8 사진 분석 알고리즘 v2 — 3시나리오(단일·다중·급식판) 통합

§1.5~§1.7이 개별 사고를 고쳤다면, 이번엔 **파이프라인 구조 자체**를 바꿨다. 축은 하나다:
**AI 호출은 시나리오 불문 1회로 고정하고, 정확도는 그 앞뒤의 결정론적 단계에서 번다.**

#### 가장 큰 구조 변경 — retrieval-then-gate

예전 이름 해석은 매처가 답을 **하나만** 주고 게이트가 통과/탈락만 시켰다. 게이트는 그 하나를 더 나은
후보로 **바꿔줄 수 없어서**, 게이트를 엄격하게 할수록 매칭 실패가 늘어나는 구조였다 — §1.6에서
"게이트를 붙였더니 좋은 매칭의 29%가 같이 죽었다"가 정확히 이 구조의 증상이었다.

순서를 뒤집었다. 자모 bi-gram 역색인(`server/nutrition/nameIndex.js`)으로 후보를 넓게 회수하고,
게이트가 그중 최선을 고른다. 이제 게이트를 엄격하게 유지해도 매칭률이 떨어지지 않는다.

| 지표(학식·급식 실제 메뉴 667종) | 전 | 후 |
|---|---|---|
| DB 매칭률 | 46.8% | **63.3%** (+110종) |
| 로컬 해석 속도 | — | 2.4ms/건 (667건 1.6초) |

매칭률이 중요한 이유: **미매칭 항목의 열량은 전부 Gemini가 채우고, 그게 급식 공식 열량의 약 48%다**
(§1.6에서 측정). 매칭률 1%p는 LLM에 맡기는 열량이 그만큼 준다는 뜻이라, 유료 NEIS 벤치마크의 통과
개수보다 훨씬 안정적인 개선 신호다. `npm run check:matchrate`로 상시 측정한다.

#### 단일 실패점 제거

정확도가 `dbSearchName` **하나**에 걸려 있었다 — AI가 이름을 하나 잘못 지어내면 뒤가 아무리 정확해도
전부 다른 음식의 수치가 된다. 이제 AI가 `nameCandidates`(2~3개)를 내고 서버가 후보 전부를 역색인에
던진다. 급식은 여기서 한 걸음 더 나가 아예 **closed-set**으로 바꿨다(아래).

#### 급식 closed-set 프라이어 — 안 쓰고 있던 정답지

한국 학교급식은 영양(교)사가 표준레시피 × 1인 배식량으로 영양을 산출해 NEIS에 공개한다. 즉 급식
사진에는 **그날의 공식 메뉴명 목록이 이미 존재**하는데, 사진 분석은 그걸 안 쓰고 AI에게 맨땅에서
이름을 지어내게 하고 있었다. 프로필에 학교가 있으면 Gemini 호출과 **병렬로** 목록을 가져와 프롬프트에
넣는다(`src/lib/menuPrior.js`, `(학교코드,날짜)` 캐시라 두 번째 사용자부터 네트워크 0).

#### 판 단위 검증 — 기준을 지어내지 않았다

항목 단위 보정은 "항목마다 조금씩 어긋나 합계만 크게 틀린" 계통 오차를 못 잡는다. 그래서 한 끼
총열량 밴드를 뒀는데, 기준값은 **학교급식법 시행규칙 별표3(학교급식 영양관리기준)**을 그대로 쓴다 —
초등 534/634, 중학 800, 고등 900kcal. 저장소의 NEIS 실제 샘플로 검증했다: **중학교 4끼 평균 804kcal
(기준 800)**, 고등 803(기준 900), 초등 674(기준 534~634).

⚠️ **벗어나도 자동 보정하지 않고 경고만 띄운다.** 외부 정답지 없이 밴드로 값을 깎으면 그게 바로 이
저장소가 §1.5~§1.7에서 반복해서 틀린 패턴(근거 없는 기준으로 근거 있는 값을 기각)이 된다.

#### 구현 중 실제로 겪은 실패 셋 (같은 실수 반복 방지)

1. **early-return을 fall-through로 바꿨다가 `라면`→`라면땅`이 되살아났다.** 앞뒤 관계(startsWith)로
   "다른 음식"이라 판정한 것을, 뒤의 앞머리·꼬리 공유도 규칙이 0.75로 뒤집었다. → 관계가 하나라도
   있었으면 그 판정이 최종이도록 되돌렸다.
2. **retrieval을 넓혔더니 이름만 닮은 후보가 채택됐다.** `치킨`→`삼계치킨`(120kcal/100g, 검증 범위는
   180~326), `파스타`→`냉파스타`(64). → foodData 검증 범위를 랭킹 veto로 추가.
3. **"통과 후보 전부 평균"이 오히려 나빴다.** `감자채볶음`이 단독 67kcal/100g인데 전체 평균은 102로
   벌어졌다. → 최고점 ±0.05 밴드만 평균한다. 측정 없이 "평균이 더 대표적일 것"이라고 넘겼으면
   그대로 악화됐을 지점이다.

#### 채택하지 않은 것

- **`trayPosition`(칸 위치로 역할 추정)** — 급식 텍스트 경로엔 사진이 아예 없고, 식판 사진에서도 5구
  배치는 학교마다 달라 이름보다 약한 신호다. 이미 `role`을 직접 묻고 있어 중복이라 넣지 않았다.
  대신 칸을 **얼마나 채웠나**(`trayFillRatio`)만 받는다 — 칸 크기는 고정이라 이건 실제로 유용하다.
- **저신뢰 항목 크롭 재질의(2차 Gemini 호출)** — 항목당 ~2초가 붙고, 지금은 조리법 1탭 보정(§1.7)이
  같은 역할을 비용 0으로 한다. 매칭률이 더 오른 뒤에도 남는 꼬리를 보고 판단할 일이다.

### 1.9 급식 공식 수치 확정 + 단백질·지방 현실성 보정

#### ① NEIS 공식 수치를 "확정값"으로 (`src/lib/anchoredNutrients.js`)

급식 영양은 영양(교)사가 표준레시피로 산출해 NEIS에 공시한 값이 있는데, 우리는 그걸 **비율 스케일의
목표치로만** 쓰고 있었다. 문제는 NEIS가 학교마다 다른 항목을 준다는 것이다 — 열량은 항상, 탄수·단백·
지방은 있을 때도 없을 때도, **식이섬유·나트륨은 아예 없다**. 예전 `applyProportionalCalibration`은
공식 값이 있는 키만 스케일을 계산했으므로, 열량이 0.8배로 줄어도 나트륨은 1.0배로 남았다.

이제 순서를 명확히 한다:

1. 공식으로 받은 항목은 **그대로 확정**(바꾸지 않는다)
2. 공식 열량에서 확정된 다량영양소 열량을 빼고, **남은 열량을 미확정 다량영양소에 배분**
3. 열량과 무관한 항목(식이섬유·나트륨)은 열량 조정 비율만큼 함께 조정

배분 비율은 우리 추정치의 에너지 구성을 따르고, 추정치가 근거를 못 주면 KDRI 에너지적정비율
(탄수 60%·단백 15%·지방 25%)로 폴백한다.

```
공식 { 열량 800, 단백질 15 } + 추정 { 1000kcal, 탄수120, 지방35, 섬유6, 나트륨1400 }
  → 열량 800(확정) · 단백질 15(확정)
  → 탄수 111.7 · 지방 32.6 (남은 740kcal 배분, Atwater 역산 800 ✓)
  → 섬유 4.8 · 나트륨 1120 (0.8배)
```

⚠️ **공식 값끼리 Atwater가 안 맞아도 고치지 않는다.** 실제로 그런 레코드가 있다(열량 800인데 공시된
탄단지 역산은 725). "확정된 것은 바꾸지 않는다"가 계약이고, 우리가 더 정확하다고 볼 근거가 없다.

#### ② 단백질·지방 현실성 보정 (`src/lib/macroPlausibility.js`)

**측정이 설계를 바꾼 사례다.** 처음엔 "단백질 40g 넘으면 깎는다"는 단순 캡을 만들려 했는데, 식약처 DB
11,255건을 전수 조사하니 그러면 안 되는 게 드러났다:

| | 비율 | 실제 사례 |
|---|---|---|
| 단백질 에너지비 >35% | **5.5%** | 가자미찜 60%, 가자미조림 54%, 가자미 매운탕 56% |
| 지방 에너지비 >50% | **5.0%** | 갈비탕 67%, 갈비구이_돼지고기 65%, 갈매기살구이 65% |

**전부 진짜 값이다.** 일괄 캡을 걸면 §1.5에서 힘들게 도달한 `갈비구이_돼지고기` 레코드를 스스로
망가뜨린다. 그래서 근거의 세기에 따라 적용 범위를 나눴다:

| 지점 | 대상 | 제외 |
|---|---|---|
| 항목(`capEstimatedMacros`) | **AI 추정치만** | DB 실측값 · foodData 검증 영양소 |
| 한 끼(`correctMealMacros`) | 합계 | foodData 검증 음식의 몫 · NEIS 공식 수치가 있는 급식 |

기준값은 **KDRI 에너지적정비율**(단백질 7~20%, 지방 15~30%)의 상한을 시작점으로 쓴다. 절대 그램이
아니라 열량 비례라, 800kcal 급식의 단백질 상한이 정확히 40g이 되고 1500kcal 고기 정식은 75g까지
허용된다. 여기에 **한 끼 절대량 상한**(단백질 40g·지방 35g 시작)을 함께 걸어 더 엄격한 쪽을 쓴다 —
에너지비만으로는 판 전체가 과대추정된 경우를 못 잡기 때문이다(1021kcal/60g은 에너지비 23%로 정상).

딱 자르지 않고 점근 곡선으로 눌러 담는다(60g과 80g을 둘 다 40g으로 만들면 "더 먹은 쪽"이라는 정보가
사라진다). 한 끼 보정은 근거가 약한 항목부터 깎고 한 항목당 40%를 넘기지 않으며, 덜어낸 만큼 열량도
함께 줄인다(같은 출처에서 나온 값이라 단백질이 과대였으면 열량도 과대였다).

**실측 동작 확인**

| 입력 | 결과 |
|---|---|
| AI 추정 200kcal / 단백질 40g / 지방 20g | **단백질 17.4g · 지방 10.9g** (탄수가 흡수, 열량 유지) |
| 이상 트레이 1021kcal / P60 / F47 (추정 항목 다수) | P **53.8** · F **43.1**, 식약처DB 항목은 그대로 |
| 정상 CNU 7첩 733kcal / P34.9 / F16.1 | **보정 없음**(원본 배열 그대로 반환) |
| 치킨 한 마리 900kcal / P70 / F52 (검증된 음식) | **보정 없음** |

### 1.10 UI 정리 — 영양 카드 통일 · 지도 초기 화면

#### 식단 탭과 달력 탭의 영양 카드를 **같은 컴포넌트**로

같은 정보(영양소별 섭취 현황)를 두 탭이 서로 다른 모양으로 그리고 있었다 — 식단 탭은 굵은 막대 +
`16 / 131 g` + "115g 더 필요해요", 달력 탭은 얇은 막대 + "65% 부족".

**통일 방향은 식단 탭 쪽 모양이다.** 퍼센트만 보여주는 쪽보다 "얼마나 더 먹어야 하는지"가 숫자로
바로 나오는 편이 다음 행동으로 이어진다. 다만 구현은 식단 탭의 로컬 `IntakeBar`를 되살리는 게 아니라
**`NutritionStatusPanel` 한 곳을 이 모양으로 다시 쓰고** 두 탭이 그걸 공유하는 형태다 — 스타일을
베껴 맞추면 한쪽만 고칠 때 또 갈라진다.

같이 정리한 것 셋:

- **표시 순서는 `NUTRIENT_LABELS` 순서 고정.** 예전 패널은 충족 → 부족 → 초과로 재정렬했는데,
  그러면 날마다 줄 순서가 바뀌어 같은 영양소를 눈으로 찾기 어렵다.
- **나트륨 "상한" 배지 제거.** 방향이 반대라는 걸 배지 대신 문구가 직접 말한다
  ("한도까지 82mg 남았어요" / "400mg 줄여야 해요"). 배지는 퍼센트만 보여주던 시절
  "70%니까 아직 부족하네"로 읽힐 여지 때문에 붙였던 것이라, 문장이 생긴 지금은 역할이 겹친다.
- **`excludeKeys` prop.** 식단 탭은 칼로리를 상단 `TodayScoreSummary`가 이미 보여주므로
  `excludeKeys={['calories']}`로 뺀다. 달력 탭은 6개를 다 그린다(그쪽 요약 카드는 달성률 링이라
  칼로리 절대량을 따로 보여주는 곳이 없다). 카드 표시 설정(`useVisibleNutrients`)은 그대로 위에서
  한 번 더 걸린다.

`src/__tests__/nutrientCard.shared.test.jsx`가 ① 두 페이지의 컴포넌트 공유와 ② 목표형/한도형 문구
형식을 둘 다 잠근다 — 나트륨에 "더 필요해요"가 붙으면 소금을 더 먹으라는 말이 된다.

#### 지도 시작 위치는 "지금 보고 있는 화면"이 정한다

| 화면 | 지도 |
|---|---|
| 주변 식당 | 내 현재 위치 중심(검색하면 결과에 맞춰 `fitBounds`) |
| 학식·급식 → **대학 학식** | 그 대학 학식당 **전부**가 한눈에 들어오게 |
| 학식·급식 → **급식** | 프로필의 초·중·고 학교 위치로 이동 + 그 지점에 핀 |

탭에 들어오는 순간 프로필에 따라 알아서 움직인다 — 사용자가 토글을 건드릴 때까지 기다리지 않는다.

**"전국 지도로 시작"의 원인**은 초기 줌 상수가 아니었다(이미 15였다). 학식·급식 뷰가 학교 설정과
무관하게 **항상 충남대 5곳**을 핀으로 띄워서, 내 위치가 서울이면 `fitBounds`가 서울과 대전을 둘 다
담으려고 남한 전체로 줌아웃한 것이다. 세 겹으로 막는다:

1. **관계있는 핀만 띄운다** — 대학 학식이면 대학 학식당, 급식이면 내 학교.
2. **`fitPlacesOnly`** — 대학 학식 화면은 내 위치를 bounds 계산에서 뺀다(`skipBounds`). 타지에
   있어도 학식당들만 딱 맞게 잡힌다. ⚠️ 이때 bounds 씨앗을 `centerLatLng`(= 내 위치)로 깔면
   마커를 빼도 중심이 bounds에 남으므로, 씨앗도 첫 번째 대상 마커로 잡아야 한다.
3. **최저 줌 12** — 그래도 멀면 줌과 중심을 되돌린다. 멀리 있는 핀이 화면 밖으로 나가더라도 중심
   주변이 읽히는 쪽이 낫다.

지도(MapPage)와 바텀시트(CafeteriaPanel)가 "지금 대학 학식인가 급식인가"를 공유해야 해서, 그 선택을
`src/lib/mealKind.js` 한 곳으로 뽑고 CafeteriaPanel이 마운트 직후와 전환 때마다 부모에 알린다.

#### 내 학교 핀 (`src/lib/schoolLocation.js`)

NEIS 학교기본정보에는 **위경도가 없다**(`{name, officeCode, schoolCode, kind}`뿐). 그래서 학교 이름을
`/api/geocode`로 좌표로 바꾼다. 같은 이름의 학교가 여러 지역에 있는 경우가 흔해(중앙초등학교 등)
교육청 이름을 앞에 붙여 지역을 좁힌다.

학교 위치는 안 바뀌므로 **학교 코드로 기기에 영구 캐시**하고, 실패도 캐시한다(지오코딩이 안 되는
학교를 탭에 들어올 때마다 다시 시도할 이유가 없다). 좌표를 못 얻으면 조용히 핀 없이 동작한다.

⚠️ 구현 중 자초한 버그 하나 — `focus`(지도 중심 고정)에 `myPosition`을 폴백으로 넣었더니 focus가
**항상** 채워져서 주변 식당 검색 결과에 `fitBounds`가 안 걸렸다(검색해도 화면이 안 움직인다).
focus는 "정말로 중심을 고정하고 싶을 때만" 채워야 한다.

### 1.11 APK 빌드 전 최종 점검 — 5개 분야 병렬 리뷰에서 발견한 14건

출시 직전, 이 세션에서 커밋되지 않은 전체 변경분(§1.7~1.10, 영양 해석 엔진 재설계 + 지도 위치 로직
+ UI 통일)을 프론트엔드·백엔드·AI·QA·코드리뷰 5개 관점에서 각각 독립적으로 점검했다. 총 14건을
찾았고(critical 2 · high 7 · medium 4 · low 1) 전부 실제 코드로 재현·검증한 뒤 고쳤다. 두드러진 것만
남긴다 — 각 항목의 상세 근거는 해당 파일의 주석에 있다(중복 서술하지 않는다).

**critical 2건 — 둘 다 "근거 없는 기본값이 근거 있는 값을 조용히 덮어쓴다"는 이 저장소의 반복
실패 패턴(§1.5~1.6)의 새 변종이었다.**

- `scripts/buildFoodDB.js`가 `classifyMenuRole`의 매칭 성공 여부(`matched`)를 버리고 `category`
  문자열만 저장해서, 이름 패턴에 못 걸린 음식(11,347종 중 3,606종=31.8%)도 "역할을 안다"고
  오판됐다. `server/nutrition/precisionEngine.js`가 이걸 급식 중량 계산의 `roleHint`로 그대로
  믿는 바람에 `foodData.js`가 정확히 아는 1인분(예: 돈가스 200g)이 반찬 기본값(50g)으로 4배
  축소됐다. `categoryMatched` 필드를 추가해 실제 매칭 여부일 때만 힌트로 넘기도록 고쳤다
  (기존 `server/data/foodDB.json`은 외부 API 재호출 없이 로컬 재계산으로 패치).
- `src/pages/Analyze.jsx`가 `fetchMenuPrior` 성공(= 이 시간대 학교 급식이 존재함)만으로 사진 속
  **모든** 항목의 `servingContext`를 `'cafeteria'`로 일괄 고정했다 — 급식 시간대에 학교 밖 식사를
  찍어도 급식 밀도(외식 대비 2~4배 낮음)가 적용됐다. 이제 급식 식판(sceneType)이거나 그 항목
  이름이 실제 오늘 공식 메뉴 목록과 일치할 때만 고정한다. 같은 곳에서 `schoolKind`가
  `profile?.school?.kind`로 무조건 폴백해 급식 아닌 사진에도 학교급식 칼로리 밴드(§1.9
  `mealStandards.js`)가 적용되던 문제도 그 폴백을 없애 함께 해결됐다.

**NEIS 공식 수치가 사진 분석 경로에서 버려지던 비대칭** — QA와 코드리뷰 두 관점이 서로 다른
방식으로 같은 결함을 발견했다(교차검증). `fetchMenuPrior`가 병렬로 받아오는 `officialTotals`를
`server/nutrition/precisionEngine.js`(메뉴명 기반 "한 판 통합 분석" 버튼)만 `applyOfficialAnchors`로
반영하고, 정작 가장 흔한 사용 경로인 사진 촬영 분석은 전혀 쓰지 않았다. `applyProportionalCalibration`
(항목별 수치를 합계와 같은 비율로 맞추는 함수)을 `precisionEngine.js`에서 `src/lib/anchoredNutrients.js`
로 옮겨 단일 소스로 만들고, `Analyze.jsx`도 이제 같은 함수로 앵커링한다(단, 사진에 급식 외 개인
간식이 섞여 있으면 적용하지 않는다 — officialTotals는 "그 급식만의" 합계라 섞어 쓰면 안 된다).

**나머지 high 4건**: ① 조리법 1탭 보정이 `dbSearchName`만 바꾸고 `displayName`은 안 바꿔서, 저장되는
기록의 이름과 실제 반영된 수치가 다른 음식을 가리켰다. ② "국·탕" 보정 칩이 `국`과 `탕`을 한 칩으로
묶어서 '탕' 요리는 칩이 활성 표시조차 안 되고, 눌러도 존재하지 않는 이름("삼계국")으로 재조회됐다 —
두 선택지로 분리했다. ③ `NutritionStatusPanel`(§1.10에서 재설계한 카드)이 한때 자체 이분법
(`actual>=recommended`)으로 색·문구를 정해서, 같은 화면의 `TodayScoreSummary`/`DaySummaryCard`(3단계
`classifyNutrientStatus`)와 판정 기준이 갈렸다 — 이제 `row.status`를 그대로 따른다. ④ `판 단위 검증`
경고 문구가 분석 시점(인분 1배)에 고정돼, 인분 조절·조리법 보정 후에도 안 바뀌었다 — 근거(context)만
저장하고 문구는 렌더 시점마다 현재 표시 총량으로 다시 계산한다.

**medium 2건**: 급식 학교 지오코딩 실패 시 지도에 안내 없이 핀만 사라지던 무음 실패에 안내 문구를
추가했다(`getSchoolLocation`은 그대로 두고 `MapPage`가 "조회 중"과 "확정 실패"를 구분하는 상태를
따로 든다). `nameCandidates`(AI가 내는 검색어 후보) 개수에 서버 상한이 없어 조작되거나 예상보다 큰
응답 하나가 식약처 API에 과도한 동시 호출을 낼 수 있던 것도 항목당 6개로 잘랐다.

**검증**: 5개 분야 리뷰 자체는 다중 에이전트 워크플로로 병렬 수행했고, 고치는 작업은 파일 충돌·테스트
검증 리스크 때문에 직접 순차로 진행했다. `recipeToPer100`(레시피DB 1인분 가정 중량)에 같은 패턴의
`matched` 미확인이 하나 더 있었지만, 고쳐보니 기존 회귀 테스트(가지겉절이 오매칭 방지)가 깨졌다 —
이 함수는 cafeteria·restaurant 양쪽에서 공유되고 레시피DB 자체가 반찬류 창작 레시피가 다수라 "역할
불명 = side 50g"이 검증된 기본 추정이었다. 되돌리고 이유를 주석으로 남겼다 — **하나의 버그 패턴이
모든 호출부에서 같은 수정을 요구하지는 않는다.**

### 1.12 2차 점검 — 1차 수정이 만든 회귀 3건과 배포 리스크

같은 5개 분야 병렬 리뷰를 한 번 더 돌렸다. 목적은 "1차가 놓친 것"과 **"1차 수정이 새로 만든 것"**이고,
후자가 실제로 3건 나왔다. 총 33건(중복 제거 19) 중 아래를 고쳤다.

#### 1차 수정이 만든 회귀 3건 — 전부 "고친 방향이 반대편을 깨뜨린" 형태

**① 급식 중량 붕괴 (`servingWeight.js`).** §1.11에서 `roleHint`를 `categoryMatched`로 거르게 했더니,
역할을 못 알아본 음식(31.8%)의 cafeteria 1순위가 비어 **2·3순위인 `reference`(=식당 1인분)와
`db`(=대개 외식 레코드의 포장량)로 흘러내렸다.** 게다가 그때 비율 가드의 분모(`trustedReference`)도
null이 되고 범위 검사도 `FALLBACK_BOUNDS[10,1200]`으로 넓어져 아무것도 못 막는다.

NEIS 실제 115끼로 재서 네 전략을 비교했다:

| 전략 | DB매칭분/공식 | 공식 초과 끼니 | 최악 |
|---|---|---|---|
| 회귀 상태(reference/db 폴백) | 61.4% | **13** | 871 → 1495 |
| 반찬 범위로만 가드 | 55.0% | 7 | |
| 트레이 범위(20~350)로 가드 | 57.8% | 9 | 871 → 1495 |
| **역할 표준만 (채택)** | **53.9%** | **5** | 913 → 1156 |

급식 출처 레코드의 실제 배식량만 골라 쓰는 변형도 재봤지만 115끼 중 11회만 발동하고 결과가 동일해
(초과 5끼) 복잡도만 늘어 채택하지 않았다. 채택안은 `mealPortions.js`가 이미 적어둔 원칙과 같다 —
*"한 판에는 주찬보다 부찬이 많아서 모르면 반찬이 통계적으로 맞다."*

⚠️ **이 지표를 `check:nutrition`의 `[6]`으로 넣었다**(초과 8끼 초과 시 FAIL). 이 회귀는 기존
`[1][2][3]` 어디에도 안 잡혔다 — 레코드 단위 hold-out은 "한 판이 통째로 부푸는" 사고를 못 본다.
`[2]`의 급식 폐기율이 78%→90%로 오르는데 이건 **의도된 결과**다(급식 배식량은 재현 가능해야 하므로
레코드별 편차보다 역할 표준을 우선한다 — CLAUDE.md가 명시한 설계).

**② 조리법 1탭 보정이 정반대로 깨졌다 (`foodNameCorrection.js`).** §1.11에서 `displayName`을 함께
갱신하도록 고쳤는데, 정작 `nameCandidates`는 그대로 뒀다. 서버는 검색어를
`[...nameCandidates, dbSearchName, fallbackSearchName]` 순으로 보고 앞쪽이 exact로 걸리면 즉시
확정하는데 AI는 항상 `nameCandidates[0] === dbSearchName`으로 낸다. 결과: **수정 전에는 "수치는
조림인데 이름은 구이"(무해한 no-op), 수정 후에는 "이름은 조림인데 수치는 구이"** — 사용자가 명시적으로
고친 값이 저장 기록에서 다른 음식을 가리키게 됐다. 실측으로 고등어구이 142 → (보정) 142(무변화) →
(수정 후) 고등어조림 108을 확인했다.

이름 필드가 **네 개**(`nameCandidates`/`dbSearchName`/`fallbackSearchName`/`displayName`)인데 전부
함께 움직여야 하는 게 원인이라, 조립을 `buildCorrectedIdItem()` 순수 함수 하나로 모으고 네 필드가
같이 바뀌는지를 테스트로 잠갔다. 같은 종류의 드리프트가 두 번 연달아 났으므로 화면에서 손으로
조립하지 말 것.

**③ 검색어 상한이 안전망을 먼저 버렸다 (`resolveFood.js`).** §1.11에서 넣은 `MAX_TERMS_PER_ITEM(6)`을
**합친 뒤** 잘라서, 배열 맨 뒤의 `fallbackSearchName`이 가장 먼저 날아갔다. 그건 "항상 dbSearchName보다
더 일반적인 상위 카테고리명"인 마지막 안전망이라, 후보가 많을수록 안전망이 사라지는 정반대 결과였다
(창작 메뉴명 6개 + fallback '돈가스' → 매칭 실패, 5개로 줄이면 정상). 이제 `nameCandidates`에만 상한을
걸고 두 안전망은 항상 붙인다.

#### APK에서만 드러나는 것 — 웹 테스트로는 절대 안 잡히는 종류

- **뒤로가기가 모달을 무시하고 앱을 종료했다.** 홈(`/analyze`)에서 새 사진 출처 시트를 열고 하드웨어
  뒤로가기를 누르면 시트가 닫히는 게 아니라 앱이 꺼졌다(입력한 메뉴명까지 소실). 웹뷰에서는 하드웨어
  back이 keydown을 만들지 않아 `useFocusTrap`의 Escape 처리가 영영 발동하지 않는다. 그래서
  `useAndroidBackButton`이 **열린 `[role=dialog][aria-modal]`에 Escape를 대신 쏜다** — 오버레이마다
  콜백을 등록받는 대신 이미 있는 통로를 재사용해서, 기존 모달을 하나도 안 고치고 전부 커버되고
  앞으로 추가되는 것도 자동으로 포함된다.
- **갤러리 PNG가 압축되지 않았다.** `toDataURL`의 quality 인자는 손실 포맷에만 적용되는데 PNG 입력을
  PNG로 유지하고 있었다. 안드로이드 스크린샷이 전부 PNG라 '갤러리에서 선택'이 생기면서 실사용 경로가
  됐고, 1024px로 줄여도 base64 2MB를 넘겨 느린 회선에서 업로드만으로 28초 타임아웃을 넘긴다.
  항상 JPEG로 내보낸다(투명 픽셀이 검게 나오지 않도록 흰 배경을 먼저 깐다).
- **카메라 권한을 거부하면 막다른 길이었다.** 웹뷰가 파일 선택창을 아예 안 띄우고 `change`도 안 줘서
  눌러도 아무 일이 없다. "응답이 없으면 경고" 식 타이머 감지는 사용자가 카메라를 그냥 취소한 정상
  상황과 구분할 수 없어(오탐) 쓰지 않고, 시트에 빠져나갈 길을 상시 안내하는 쪽을 택했다.

#### 나머지 수정

- **NEIS 실패가 영구였다** (`menuPrior.js`) — 실패를 성공과 같은 캐시에 `[]`로 담아, 한 번만 흔들려도
  그날 그 학교의 closed-set 프라이어·공식 앵커링·판정 밴드가 세션 내내 꺼졌다. 실패는 60초 TTL로 분리.
  같은 형태가 `schoolLocation.js`에도 있었는데 그쪽은 **localStorage에 영구 저장**이라 더 나빴다(기기에서
  학교 핀이 다시는 안 뜬다). 성공만 영구 캐시하고 실패는 메모리 5분으로 바꿨고, 예전 버전이 남긴
  `{failed:true}` 기록도 무시하고 재시도한다.
- **프라이어 조회가 "병렬"이 아니었다** — 주석은 "Gemini 호출과 병렬로(왕복이 늘지 않는다)"라고 적혀
  있었지만 완전한 직렬이다(메뉴 목록이 프롬프트 본문에 들어가야 해서 구조적으로 병렬화 불가).
  타임아웃이 28초라 NEIS가 느린 날 스피너를 그만큼 보게 된다. 자체 데드라인 2.5초를 걸고 주석을
  사실에 맞게 고쳤다.
- **앵커링 가드가 구조적으로 무력이었다** (`Analyze.jsx`) — §1.11에서 넣은
  `items.every(it => it.servingContext === 'cafeteria')`는 바로 위에서 식판 사진의 모든 항목을
  'cafeteria'로 덮어쓰기 때문에 **항상 true**였다. 정작 가드가 필요한 유일한 상황(식판 + 개인 간식이
  한 프레임)에서만 무력해진다. 판정을 "공식 메뉴 목록 소속 여부"로 바꿨다.
- **인분 조절이 오경고를 냈다** — §1.11에서 plateWarning을 렌더 시점 재계산으로 바꾸면서 servings 배율까지
  곱해, 사용자가 "2인분"이라고 입력하면 "사진에 안 담긴 반찬이 있거나 일부 항목이 잘못 인식됐을 수
  있어요"가 떴다. 방금 사용자가 알려준 사실을 시스템이 오류라고 되돌려 말하는 셈이다. 인분은 추정이
  아니라 명시된 의도이므로 판정에서 뺐다(보정·직접 수정에는 계속 반응한다).
- `/api/precision-analyze`의 `menus` 상한 30(무제한이면 이벤트 루프 정지 + 유료 프롬프트 폭증),
  OpenRouter 스키마 폴백을 400/422로 한정(429/401/402까지 이미지 포함 본문을 한 번 더 태우고 있었다),
  `useNaverMap` cleanup에 `map.destroy()`(같은 DOM에 지도가 겹겹이 쌓였다),
  `BottomSheet`의 `suppressClick` 누수(콘텐츠를 끌면 다음 손잡이 탭 한 번이 통째로 무시됐다).

#### 배포 — 코드가 아니라 환경변수가 문제였다

`SUPABASE_SERVICE_ROLE_KEY`와 `NEIS_API_KEY`가 README 표·`.env.example`·`render.yaml`·Vercel
체크리스트 **어디에도** 없었다. 둘 다 **빠뜨려도 배포가 성공하고 대부분의 화면이 정상으로 보이는**
종류라 눈에 안 띈다. 넷 다 채우고 배포 후 확인용 curl/절차를 README에 넣었다.

> **정정(§1.13 실측):** 이 절은 처음에 "`SUPABASE_SERVICE_ROLE_KEY`가 프로덕션에 없어
> `/api/auth/*`가 이미 500"이라고 적었는데, 그건 문서에 없다는 사실로부터 추론한 것이었다.
> 배포 전 점검에서 실제로 찔러 보니 `/api/auth/security-question`이 1.2초 걸려
> `{"found":false}`를 돌려준다 — DB까지 다녀왔다는 뜻이고 키는 설정돼 있다. **문서에 없는 것과
> 배포에 없는 것은 다른 문제였다.**

걱정거리로 지목됐지만 실측 결과 문제없던 것들도 기록해 둔다 — `server/data/foodDB.json` 10MB는
GitHub·Vercel 한도상 안전하고(로드 265ms, 프로덕션 `/api/food-serving` 200으로 번들 포함 확인)
**LFS로 옮기면 오히려 Vercel 배포가 깨진다.** Supabase는 이번 변경에 필요한 마이그레이션이 없고
(RPC·RLS 정상), 카메라/갤러리는 네이티브 재빌드 없이 동작한다(서버 URL 모드 유지).

⚠️ 원격이 3개(`origin`=Mealaze / `hub` / `upstream`=조직 repo)다. `git push`는 `origin`에만 가므로,
**Vercel이 보고 있는 저장소가 origin이 맞는지 확인하고 푸시할 것** — 아니면 웹은 그대로인데 APK만
구버전에 머문다(서버 URL 모드라 APK는 배포된 웹을 그대로 로드한다).

> **정정(§1.13):** 원격은 3개가 아니라 2개다. `origin`(Mealaze)이 이미 `12nick-kr/hub`로 이름이
> 바뀌어 있어서 `hub` 원격과 같은 저장소를 가리킨다 — 푸시할 때 GitHub가 `This repository moved`
> 리다이렉트를 내보내며 정상 반영된다. 실질 후보는 `12nick-kr/hub`와 조직 `upstream` 둘뿐이다.

### 1.13 APK 배포 전 보안·안정성 점검

첫 릴리스 APK를 뽑기 직전 점검. 앞의 §1.11/§1.12가 **웹 로직**을 봤다면 여기는 **배포물 자체**
(APK 매니페스트 · 번들 · 프로덕션 엔드포인트 · 의존성)를 본다. 실제로 요청을 보내 확인한 것만 적는다.

#### 고친 것

**① `android:allowBackup="true"` — 인증 토큰이 사용자 모르게 구글 드라이브로 복제된다**

화면이 WebView라 로그인 세션(Supabase JWT + refresh token)과 게스트 식단이 전부 WebView
localStorage, 즉 앱 내부 저장소에 있다. Capacitor 템플릿 기본값 `allowBackup="true"`는 그걸 통째로
자동 백업에 포함시킨다. **refresh token의 사본이 클라우드에 남고**, 백업을 복원하면 다른 기기에서
로그인 상태가 되살아날 수 있는데 사용자는 그런 사본이 생긴 줄도 모른다.

`allowBackup="false"`로 끄고, targetSdk 31+에서는 그것만으로 기기 간 직접 전송(D2D)이 안 막히므로
`res/xml/data_extraction_rules.xml`로 cloud-backup과 device-transfer를 둘 다 제외했다.
**잃는 기능은 없다** — 기기 이전용 백업/복원은 MY 탭 CSV가 담당하고, 그쪽은 무엇이 옮겨가는지
사용자에게 보여준다.

⚠️ 이 변경은 **APK를 다시 빌드해야** 반영된다. 서버 URL 방식이라 웹 배포로 자동 갱신되는 항목이
아니다(네이티브 매니페스트). 확인법: `aapt dump xmltree <apk> AndroidManifest.xml`에서
`android:allowBackup=(type 0x12)0x0`이면 적용된 것, `0xffffffff`면 옛 APK다.

**② 보안 응답 헤더가 하나도 없었다(Vercel이 자동으로 붙이는 HSTS 제외)**

`X-Frame-Options`·CSP `frame-ancestors`·`X-Content-Type-Options`·`Referrer-Policy` 전무 →
로그인 화면을 iframe에 얹는 클릭재킹과 MIME 스니핑이 열려 있었다.

배포 경로가 둘이라 헤더도 두 군데에 있어야 한다. **Vercel에서는 화면(정적 파일)을 CDN이 직접
내보내므로 `server/proxy.js`를 거치지 않는다** — Express 미들웨어만 넣으면 Render에서만 적용되고
정작 실사용 배포는 무방비로 남는다. 그래서 값을 `server/securityHeaders.js` 한 곳에 두고
`vercel.json`에도 같은 값을 적은 뒤, `securityHeaders.test.js`가 **두 파일을 대조해 어긋나면
실패**하게 했다(사람이 기억할 일이 아니다).

⚠️ 전체 CSP(`script-src`/`style-src`…)는 **일부러 넣지 않았다.** 네이버 지도 SDK를 외부에서 로드하고
스타일이 전부 인라인 객체라, 잘못 좁히면 배포되는 순간 전 사용자가 흰 화면을 보고 서버 URL 방식이라
**이미 설치된 APK까지 같이 죽는다.** 지시자가 `frame-ancestors` 하나뿐인 CSP는 다른 리소스를 전혀
제한하지 않으므로 깨질 여지 없이 클릭재킹만 막는다. 넓히려면 실기기 확인이 선행돼야 한다.
`Permissions-Policy`도 뺐다 — 카메라·위치를 실제로 쓰는 앱이라 잘못 적으면 그 기능이 통째로 막히는데,
헤더가 없을 때의 기본값이 이미 "동일 출처만 허용"이라 얻는 것보다 잃을 게 크다.

#### 수용한 위험 — 왜 지금 고치지 않는가

| 취약점 | 판단 |
|---|---|
| `react-router` 오픈 리다이렉트 (moderate, CVE-2025-68470 우회) | **노출면 없음.** 저장소 전체의 `navigate()` 호출이 전부 하드코딩 내부 경로거나 `location.pathname`이고, `useSearchParams`를 아예 안 쓴다 — 외부가 리다이렉트 대상을 정할 통로가 없다. 고치려면 react-router v7 메이저 업그레이드(6→7)뿐이라 출시 직전 위험 대비 이득이 없다. |
| `react-router` deserializeErrors 생성자 주입 (moderate) | **해당 없음.** SSR 하이드레이션 경로의 취약점인데 이 앱은 순수 SPA다. |
| `postcss` 경로 순회 (high) | **빌드 타임 전용.** `vite → postcss`이고 소스맵 자동 로딩 경로라 런타임 노출이 없다. `vite`가 `devDependencies`가 아니라 `dependencies`에 있는 건 실수가 아니다 — `render.yaml`이 `NODE_ENV=production`을 설정해서 devDeps가 설치되지 않기 때문이고, 옮기면 Render 빌드가 깨진다. |
| `tar`/`brace-expansion` 등 (critical 포함) | `@capacitor/cli`(devDependency) 경유. 런타임 번들·APK 어디에도 안 들어간다. |

#### 확인만 하고 손대지 않은 것 (문제 없었음)

- **비밀값 유출 없음** — 서버 전용 키 8개(OpenRouter/식약처×3/NEIS/네이버/카카오/Supabase
  service_role)의 **실제 값**으로 `dist/`와 APK `assets/`를 전수 검색해 0건. `.env`는 추적 안 됨.
- **릴리스 APK의 WebView 디버깅 비활성** — Capacitor `CapConfig`가
  `webContentsDebuggingEnabled`의 기본값을 `FLAG_DEBUGGABLE`로 잡으므로 릴리스에서는 자동으로
  꺼진다(`chrome://inspect`로 남의 앱 WebView를 열 수 없다). 설정 추가 불필요.
- **SECURITY DEFINER 함수 3개 모두 `set search_path = public`** — `get_daily_leaderboard`,
  `increment_total_xp`, `get_xp_leaderboard`. search_path 하이재킹 방어가 이미 돼 있다.
- **프로덕션 console.log 없음** — `src/`의 `console.log` 4곳이 전부 `import.meta.env.DEV` 가드 안.
- **`/api/fooddb` 에러 응답에 키가 안 섞인다** — `throw` 지점을 전부 훑었고 메시지가 모두 우리가 쓴
  한국어 상수다. URL이나 `apiKey`가 문자열에 들어가는 경로가 없다.
- **CORS 미설정 = 동일 출처만** — 브라우저가 교차 출처 호출을 차단한다. APK도 같은 오리진이라 무관.
- **레이트리밋 5단계** — 전역 60/분, gemini 30/10분, chat 15/시간, auth 쓰기 10/시간·읽기 20/시간·
  재설정 10/15분. 비밀번호 재설정은 IP가 아니라 계정 단위 DB 잠금이 주 방어선.
- **ErrorBoundary가 `main.jsx`에서 앱 전체를 감싼다.**
