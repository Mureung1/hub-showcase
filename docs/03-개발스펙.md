# 개발 스펙

이전에 폴더 하나에 16개 문서(아키텍처·빌드·테스트·인터랙션 가이드 + PRD 9종 + 구현프롬프트 4종)로
나뉘어 있던 것을 한 파일로 합쳤다(원본 폴더는 삭제됨). **`CLAUDE.md`가 이 저장소의 살아있는 1차 아키텍처 레퍼런스**이므로, 거기
이미 상세히 있는 내용(프록시 구조·배포 분기·env var·핵심 도메인 흐름·게스트 우선 저장·인증·라우팅/
디자인 시스템 컨벤션)은 여기서 반복하지 않고 "CLAUDE.md 참고"로만 표시한다. 이 문서는 CLAUDE.md가
**다루지 않는 것**만 담는다: (1) 다이어그램에 딸린 세부 사실·미해결 이슈 기록, (2) 지금도 유효한
how-to 레퍼런스(인터랙션 튜닝값·APK 빌드 절차·CSV 테스트 절차·학식 데이터 갱신법), (3) 보류 중인
설계 문서, (4) 이미 구현이 끝난 PRD들의 "코드에서 바로 안 보이는" 결정 사항만 압축한 상태 기록.

## 1. 아키텍처 — CLAUDE.md에 없는 것만

전체 시스템 구조·게스트 우선 저장 분기·사진→영양 수치 핵심 흐름·인증(합성 이메일)·배포 토폴로지의
Mermaid 다이어그램은 루트 `README.md`에 있다(원래 이 문서의 옛 원본 `architecture.md`에도 같은
다이어그램이 있었지만, 텍스트 설명이 전부 CLAUDE.md와 겹쳐 통합 과정에서 그 부분은 버렸다 —
CLAUDE.md가 1차 출처). CSV·광고 흐름도 CLAUDE.md의 "CSV backup"/"Ads" 절이 이미 더 상세하다.

옛 `architecture.md`에만 있고 CLAUDE.md에는 없던 것 — 4~6주차에 걸쳐 쌓인 기능별 "왜 이렇게
결정했는가" 기록과, 그림을 그리며 발견한 미해결 이슈 목록이다. 아래 그대로 보존한다.

### 1.1 4주차 — 학식·급식 / 직업 추천 / AI 식습관 분석

- 급식·학식 카드는 하나(`MealCard.jsx`)를 공유 — 메뉴마다 알레르기 칩을 반복하지 않고 메뉴명 옆
  번호 위첨자(`src/lib/allergyDisplay.js`) + 카드 하단 범례 1줄로 축약. NEIS 공식 번호와 학식
  키워드 추정 둘 다 `allergyRules.js`의 M1~M19로 통일하고 `estimated` 플래그로 배지만 다르게 그린다.
- 대학 학식은 5개 식당(제2·3·4학생회관·생활과학대학 + 제1학생회관은 크롤링 데이터 자체가 없어 외부
  안내 페이지 링크로 대체) × 주간 단위로 한 번에 받아온다. 하이브리드 판정은
  `src/lib/cnuWeekFallback.js`의 순수 함수(`resolveCnuWeekResult`) 하나로 분리돼 파서/크롤러를
  몰라도 테스트 가능. 화면은 주 전체를 한 번만 받아 날짜·식당·학생/직원 트랙 전환을 전부 클라이언트
  에서 처리한다(탭 클릭마다 서버 재호출 없음).
- 직업 기반 추천(`src/lib/occupationKeywords.js`)은 부족 영양소 추천과 **병렬로** 도는 완전히
  별개의 검색 — 실패해도 서로 영향 없음. **6주차에 화면 노출(별도 섹션·범례·다른 색 핀)이
  제거되고 결과만 영양소 추천 목록에 조용히 병합**됐다(§1.3 참고) — 4주차 PRD의 "다른 색 핀 +
  범례" UI는 더 이상 유효하지 않다.
- AI 식습관 분석은 원본 끼니 기록을 절대 Gemini에 보내지 않는다 — `src/lib/dietSummary.js`의 집계
  요약(일평균 칼로리·영양소별 달성률·자주 먹은 음식·과다/부족 항목)만 전달. 같은 기간(7/30일)
  분석은 하루 1회만 호출(`dietAnalysisCache.js`, localStorage) — 그래서 "다시 분석" 버튼이 없다.

### 1.2 5주차 — 한 판 통합 분석 / 점수 100점 개편 / 식비 지도 / 학교 검색 안정화

- 한 판 통합 분석은 새 파이프라인이 아니라 기존 사진/텍스트 분석과 같은 결과 카드·저장 상태
  머신에 입력만 다르게 얹는 방식 — `AnalysisResultCard`에 `titleOverride`/`sourceNote` prop 2개만
  추가. meal record 스키마는 바꾸지 않아 식단 탭 표시 이름 규칙("첫 음식명 외 N개")도 그대로.
- 영양 점수는 리더보드/오늘의 점수 전용 공식(`nutritionScore.js`)을 배점표 기반으로 다시 짬 —
  앱이 추적하는 5개 영양소(칼로리·단백질·탄수화물·지방·나트륨)만 채점, 달력의 하루 상태 판정
  (`calcDayStatus`)은 기존 6개 기준 그대로 유지(둘은 원래 다른 목적). SQL도 같은 공식으로 다시
  짰으므로 배포된 Supabase는 `supabase/migrations/2026-07-28_score-v2-leaderboard.sql` 재적용
  필요(자세한 배점표는 [01-알고리즘.md](01-알고리즘.md) 참고).
- 식비 위치 지도는 네이버 지도 초기화를 `useNaverMap.js` 공용 훅으로 뽑아 공유(SDK 로딩 자체는
  이미 `useNaverMapLoader.js`가 모듈 전역으로 한 번만 함). 건물 좌표(5곳)는 실측 하드코딩 —
  2·4학생회관은 그 이름의 POI가 지도 서비스에 아예 없어(실측 확인) 건물 내 매장/동일 건물의 다른
  이름("2학생회관커피점", "상록회관")으로 대신 찾았다.
- NEIS 학교 검색은 `SchoolSearchField.jsx`로 분리해 입력 300ms 디바운스 + AbortController 자동
  검색으로 전환. `fetchWithTimeout`이 호출부가 넘긴 외부 `signal`도 받아 내부 타임아웃과 "이전
  검색어 요청 취소"를 구분 처리(취소는 조용히 무시, 진짜 타임아웃만 에러 표시).

### 1.3 6주차 — 정밀 영양 산출 엔진 / 인분 조절 / 나트륨 상한형 / 급식 카드 / 직업 배경화

- 정밀 영양 산출 엔진(`server/nutrition/precisionEngine.js`의 `analyzeTray()`)이 5주차의 순수
  Gemini 추정을 대체 — 식약처 DB에 실제 매칭되는 항목은 실측값, 매칭 실패분만 Gemini로 채운다.
  `server/data/foodDB.json`(11,347종)은 CSV 수동 다운로드 대신 `scripts/buildFoodDB.js`가 API로
  직접 수집했고, 학교·기관 급식 출처를 최우선해 1인분 그램이 학생 트레이 기준에 가깝게 나온다
  (외식/가정식 출처는 "탕"류 등에서 식당용 큰 그릇 단위가 섞여 있었음 — 실측으로 발견해 우선순위
  변경). **매칭률·정확도 둘 다 가이드 목표(80%, 16/20) 미달** — 구조적 한계(원재료 DB 미보유)가
  원인이라 있는 그대로 기록.
- 인분 수 조절은 `baseNutrients`(1인분 원본)를 절대 덮어쓰지 않고 표시·저장 시점에만 배율을
  곱하는 구조 — 이 원칙을 어기면 인분을 여러 번 오갈 때 부동소수점 오차가 쌓인다. 저장 기록에
  `servings`가 추가되지만 기존 레코드는 이 필드가 없어도 1인분으로 해석되어 마이그레이션 불필요.
- 나트륨 상한형: 조사 결과 "6개 중 4개 충족" 같은 이분법은 애초에 이 앱에 없었음을 확인 — 기존
  3단계 카운트 판정(`calcDayStatus`)은 그대로 두고 "영양소별 방향(target/limit)" 규칙만
  `nutrientCriteria.js` 하나로 모았다. 이 과정에서 `dietSummary.js`가 나트륨 방향을 반전하지 않아
  "적게 먹어 잘하고 있는 날"을 "부족"으로 잘못 판정하던 실제 버그를 발견해 고쳤다.
- 급식 카드는 `MealCard.jsx`에 `layout='numbered'|'stacked'` prop 하나만 추가 — 급식만 세로·가운데
  정렬, 학식 카드는 `layout` 미지정(기본값 `'numbered'`)으로 코드 변경 없이 그대로 동작.
- 직업 추천은 화면 노출(별도 섹션·범례·다른 색 핀)만 제거하고 검색 결과는 조용히 영양소 추천
  목록에 병합 — 직업 매칭 장소는 예상 섭취량 계산을 거치지 않아 "추천 이유" 자체가 안 뜨므로,
  텍스트로 직업을 언급할 자리가 없다.

### 1.4 그림을 그리며 발견한 것 — 기록 시점 기준 미해결 이슈

architecture.md 작성 당시 실제로 어긋나 있던 연결들. 코드는 고치지 않고 기록만 남겼던 것들이라,
이 문서 작성 시점까지도 별도로 고쳤다는 근거가 없으면 아직 유효하다고 보고 다룰 것.

1. **기간별 CSV의 `recommended_*`/`compliant`는 항상 빈칸** — `csv.js`의 내보내기가
   `dailyRecord.getRecord()`로 "그날의 권장량 스냅샷"을 읽는데, 그 스냅샷을 쓰는 유일한 함수
   `dailyRecord.upsertMeal()`을 아무도 호출하지 않는다. 끼니 저장은 전부 `dataStore →
   mealStore/Supabase`로 가는데 이 스냅샷 경로만 옛 구조에 남음 → 신규 기록에서 해당 컬럼이 항상
   빈 값(파일 형식은 유효해 가져오기는 정상). 선택지: 컬럼을 내보내기에서 빼거나, 저장 시점의
   `effectiveRecommended`를 실제로 스냅샷하거나.
2. **Kakao는 "롤백용"인데 키는 현역** — `/api/places`·`/api/geocode`·`kakao.js`의 `searchPlaces`·
   `PlaceMap.jsx`·`useKakaoLoader.js`는 어떤 화면도 안 쓰지만, `/api/reverse-geocode`(좌표→지역명)는
   지금도 쓰여서 `KAKAO_REST_API_KEY`가 여전히 필수. 롤백 코드와 현역 기능이 같은 키·같은 파일을
   공유해 롤백 코드를 지우려 해도 깔끔히 안 떨어짐. 선택지: 역지오코딩을 네이버로 옮기거나, 롤백
   경로를 정식 폐기 선언.
3. ~~텍스트 분석은 식약처 DB를 안 탄다~~ — **해소됨**. 텍스트 경로를 사진 경로와 같은 구조
   (AI 식별 → `resolveFoodItem` 공유 → 식약처 DB 캐스케이드)로 재구성.
4. **로그인해도 기기에 남는 설정** — `dayStatus`(달력 수동 상태)·`cardSettings`(표시 영양소)·
   `adData`(광고 집계)는 `effectiveUserId`로 키를 잡지만 저장 위치는 항상 localStorage. 같은
   계정으로 다른 기기에 로그인하면 이 설정들은 따라오지 않는다(식단·프로필만 동기화).
5. **업데이트 채널이 둘** — APK가 원격 URL을 로드하므로 웹 배포 = 앱 업데이트지만, Capacitor
   플러그인은 APK 재설치가 필요. 웹 코드가 새 플러그인을 쓰기 시작하면 배포는 됐는데 구버전
   APK에서만 깨지는 상태가 생길 수 있음(3주차 CSV 저장이 정확히 이 형태였음). 선택지: 네이티브
   기능 호출부에 "플러그인 없음" 폴백(`fileExport`는 이미 있음), 또는 앱 안에 최소 버전 안내.
6. **게스트 데이터는 기기 하나에 묶임** — `GUEST_ID = 'guest'` 고정 버킷 하나뿐이라 한 브라우저 =
   한 게스트. 기기 이동 수단은 CSV 백업뿐이고 캐시를 지우면 복구 경로가 없음(의도된 설계지만
   사용자에게는 MY 탭 안쪽에만 그 사실이 있음).

## 2. 인터랙션 구현 — 튜닝 레퍼런스

PRD v2 §4의 구현 결과. 코드는 5개 파일이 전부: `src/components/Pressable.jsx`(공통 프레스
컴포넌트 — 버튼/탭/카드 전부 경유), `src/lib/tabs.js`(탭 순서 단일 소스), `src/lib/useTabTransition.js`
(방향 결정 → `<html data-nav-direction>` → View Transitions 실행 + 중복 클릭 가드), `src/index.css`
(모든 keyframe), `src/components/ProgressBarFill.jsx`(`transform:scaleX`로 채움).

### 2.1 framer-motion을 안 쓰는 이유(번들 실측)

| | raw | gzip |
|---|---|---|
| 도입 전 | 579.64 kB | 170.01 kB |
| framer-motion 도입 후 | 705.49 kB | 211.08 kB (+41.07 kB, +24%) |
| 채택한 CSS 방식 | 581.82 kB | 170.93 kB (+0.92 kB) |

임계치(gzip 40KB) 초과로 기각. APK가 번들을 내장하지 않고 원격 URL을 그대로 로드하므로 증가분을
콜드 스타트마다 모바일 네트워크로 받는다는 점도 근거 — 요구되는 모션이 전부 `transform`/`opacity`뿐
이라 CSS로 동일하게 구현 가능해 라이브러리 이득이 없다.

### 2.2 화면 전환이 두 갈래인 이유

- **View Transitions API 지원(Chrome/Android WebView 111+, 기본 경로)**: 브라우저가 나가는/
  들어오는 화면을 스냅샷으로 합성 — 이전 라우트를 직접 들고 있다가 재렌더할 필요가 없어
  `useEffect` 재실행(지도 검색·AI 추천 API 중복 호출) 문제가 없다.
  ```js
  document.startViewTransition(() => flushSync(() => navigate(toPath)))
  ```
  `flushSync`가 없으면 React 18+ 비동기 렌더링 때문에 콜백 종료 시점에 새 화면이 DOM에 없어
  전환이 빈 화면으로 잡힌다.
- **미지원 브라우저**: 들어오는 화면만 방향대로 슬라이드-인(`.tds-screen`), 나가는 화면 연출만 빠짐.
- `data-nav-direction`은 탭바를 거치지 않는 이동(화면 안 `Link`, 뒤로가기)에서도 갱신돼야 한다.
  `AppShell`이 경로 변경마다 다시 계산해 `none`으로 되돌린다 — 없으면 직전 탭 전환 방향값이 남아
  같은-탭 이동에도 엉뚱한 슬라이드가 붙는다.
- **상단바/하단 탭바는 전환에서 제외**: `::view-transition-old/new(root)` 스냅샷은 화면 전체라
  `position:fixed`인 탭바도 포함됨 — 조치 없이 root에 `translateX`를 걸면 탭 전환마다 탭바가
  깜빡인다. 해결: 두 바에 각자 `view-transition-name`을 줘 root에서 분리(`.tds-appbar`=Header,
  `.tds-tabbar`=BottomTabBar), 크로스페이드를 꺼서(`old`는 `display:none`, `new`는 `animation:none`)
  전환 내내 제자리 유지 + 탭 아이콘 바운스가 라이브로 계속 재생되게 함(`new`가 정지 이미지가 아닌
  실제 라이브 표현이라 가능). `::view-transition-group`의 기본 위치/크기 보간은 일부러 남김(헤더는
  스크롤 복원 위치가 화면마다 달라질 수 있어 튀지 않게). 이 규칙들은 `prefers-reduced-motion`
  미디어쿼리 **밖**에 둔다. 구조적으로도 `AppShell`/`LoadGate`가 레이아웃 라우트라 탭바가 항상
  마운트 상태를 유지(`src/__tests__/appShell.tabbar.test.jsx`가 DOM 노드 동일성으로 고정).

### 2.3 FR-4.3 검증 — 애니메이션 속성 전수 확인

```bash
grep -rn "transition:" src/ --include=*.jsx --include=*.js --include=*.css | grep -viE "transform|opacity"
```

현재 걸리는 건 `stroke-dashoffset` 2건(`Result.jsx` 달성률 링, `NutritionStatusPanel.jsx` 도넛)뿐
— SVG 페인트 전용 속성이라 리플로우 비용이 없어 의도적으로 남김. 3주차에 실제로 고친 건 영양소
진행 막대 4곳(`transition: width` → `ProgressBarFill`의 `transform: scaleX()`로 교체, 6개 막대가
동시에 움직여도 레이아웃→페인트→합성을 프레임마다 다시 타지 않게).

### 2.4 크롬 DevTools CPU 4x 스로틀 프레임 확인

1. `F12` → `⋮` → More tools → Rendering → **Frame Rendering Stats**(FPS 오버레이) +
   **Paint flashing**(초록 번쩍 = 매 프레임 재도색, 전체 화면이 번쩍이면 안 됨).
2. Performance 패널 → 톱니바퀴 → **CPU: 4× slowdown**(`Ctrl+Shift+M`으로 기기 툴바까지 켜면 더 정확).
3. Record → 탭 5개 왕복 + 버튼/카드 프레스 → 정지.
4. 확인: Frames 트랙에 빨간(long frame) 막대 없어야 함, Main 트랙에 Layout/Recalculate Style이
   전환 구간에서 반복되면 안 됨(transform/opacity만 쓰면 Compositor만 바쁨).
5. **reduce-motion 확인**: 같은 패널의 Emulate CSS media feature prefers-reduced-motion → reduce
   설정 시 슬라이드가 사라지고 150ms 페이드로 대체, 버튼 프레스도 scale 없이 투명도만 변해야 함.

## 5. 대학 학식 폴백 JSON 갱신 (`server/data/univ-meals.json`)

크롤링(`server/univMealAdapters/cnu.js`)이 실패했을 때만 대신 쓰인다. **평소엔 자동 갱신** —
크롤링이 성공하면 서버가 그 결과를 이 파일에 그대로 저장해 다음 실패 때의 최신 폴백이 된다. 아래는
크롤링이 오래 실패했을 때만 필요한 수동 절차다.

1. 제2·3·4학생회관·생활과학대학(4개 건물 — 제1학생회관은 이 시스템에 데이터가 없어 항상
   `external`, 갱신 대상 아님)의 실제 운영 메뉴를
   https://mobileadmin.cnu.ac.kr/food/index.jsp 에서 확인.
2. `cnu.days`의 해당 날짜(`YYYYMMDD`) →
   `cafeterias.<cnu2|cnu3|cnu4|cnuLife>.meals.<breakfast|lunch|dinner>.<student|staff>`에 채움:
   ```json
   { "status": "open", "price": 6000, "note": null, "menus": [{ "name": "메뉴명", "allergyCodes": ["M6"], "estimated": true }] }
   ```
   운영 안 하는 끼니는 `{ "status": "closed", "price": null, "note": null, "menus": [] }`.
3. `cnu.updatedAt`을 오늘 날짜(`YYYY-MM-DD`)로 갱신 — 화면 "○월 ○일 기준" 안내에 그대로 쓰임.
4. 저장 후 커밋·배포.

스키마: `cnu = { week: 'YYYYMMDD'(그 주 월요일), updatedAt, days: [{ date, cafeterias: { cnu1(항상
status:'external'), cnu2, cnu3, cnu4, cnuLife } }] }` (보통 월~토 6일). `meals.<끼니> = { student:
MealSlot, staff: MealSlot }`, `MealSlot = { status: 'open'|'closed'|'suspended'|'external', price,
note, menus: [{name, allergyCodes, estimated:true}] }`.

## 6. 예정/보류 중 — 쿠팡 파트너스 상품 자동 수집

**보류 중** — 파트너스 API 키 발급 조건(누적 판매금액 약 15만원) 미충족. 아래는 조사·설계가 끝난
상태의 사양이다.

### 6.1 원래 구상("사용자 요청마다 실시간 검색")이 불가능한 이유

- 검색 API 호출 한도가 **시간당 10회**(전체 계정 기준, 공식 문서의 "분당 50회"는 실제와 다름).
  초과 시 `rCode: 403`, **403이 3번 누적되면 파트너스 계정 API가 영구 제한될 수 있음**.
- API 키 발급에 누적 판매금액 약 15만원 조건 — 파트너스 가입만으로는 안 나옴.
- 검색 결과 최대 10개, `minPrice`/`maxPrice` 파라미터 미지원(넣어도 무시되고 가격 뒤섞임).

### 6.2 대안 설계 — 사전 수집 + 정적 서빙

사용자별로 달라지는 건 "어떤 영양소가 부족한가"뿐이고(이미 `adRecommendation.js`가 판정), 영양소는
11개(`AD_NUTRIENTS`)로 고정 — 즉 자동화할 부분은 "영양소별 상품 목록을 최신으로 유지하는 것" 하나뿐.

```
[주기적 배치] scripts/fetch-coupang-products.mjs — 영양소 11개 × 검색 1회(시간당 10회 한도 →
  6분 간격 강제, 또는 주 1회) → src/data/coupangProducts.generated.json(커밋)
[런타임] API 호출 0회 — adRecommendation.js/DeficientNutrientAds.jsx는 이 파일을 읽기만 함(변경 없음)
```

장점: 한도 안전(런타임 호출 0), 서버 라우트 불필요(Render/Vercel 이중 배포 문제 없음), 키 노출
위험 0(로컬/CI Secret에만), 배치 실패 시 직전 커밋 JSON이 폴백. 잃는 것: "같은 영양소 사용자끼리
다른 상품" 개인화는 포기(하지만 개인화 자체는 이미 영양소 판정 단계에서 일어남).

### 6.3 키가 없는 동안 지금 할 수 있는 것(권장)

현재 등록된 제휴 링크 9개의 **상품명·가격·이미지만 손으로** `src/data/coupangProducts.js`에 채우면
지금 구조에서 카드가 완성된다(각 항목의 `// sourceUrl:` 주석에 실제 상품 페이지 주소 있음). 상품명을
채우면 같은 영양소의 2·3번 상품도 자동으로 노출 대상이 된다(지금은 중복 방지로 1번만 씀).

### 6.4 기술 사양 (키 확보 후 Step 2에서 그대로 사용)

**HMAC 인증**:
```
message   = datetime + method + path + query   (이 순서로 단순 연결, query는 ? 없이 별도)
datetime  = UTC "yyMMddTHHmmssZ" (예: 260722T143022Z)
signature = HMAC-SHA256(message, SECRET_KEY)   (hex)
header    = Authorization: CEA algorithm=HmacSHA256, access-key=<ACCESS>, signed-date=<datetime>, signature=<sig>
```

**검색 응답**: `{ rCode, rMessage, data: { productData: [{ productId, productName, productPrice,
productImage, productUrl, isRocket, categoryName }] } }` — `rCode==="0"`이면 성공, `productUrl`에
제휴 추적이 이미 붙어 있어 별도 deeplink 변환 불필요.

**스키마 매핑**: `productId→id(cp-<nutrient>-<productId>)`, `productName→productName`,
`productPrice→price`, `productImage→imageUrl`, `productUrl→partnersUrl`, 검색 키워드로 `nutrient` 역산.

### 6.5 구현 시 반드시 지킬 제약

| 항목 | 이유 |
|---|---|
| 호출 간 최소 6분 간격 강제 + 403 시 즉시 중단 | 시간당 10회 한도, 403 3회 = 계정 영구 정지 가능성 |
| 런타임 호출 금지 | 배치 전용, 사용자 요청 경로에서 절대 호출 안 함 |
| `COUPANG_ACCESS_KEY`/`COUPANG_SECRET_KEY`는 `VITE_` 접두사 금지 | 이 설계에서는 배포물에 아예 안 들어감(로컬/CI Secret만) |
| 배너는 항상 표시(빈 배열 금지) | `generated.json`이 비거나 깨져도 손입력 목록으로 폴백해야 함 |
| 의약품 오인 표현("치료"/"예방"/"개선 보장") 걸러내기 | 쿠팡에서 받아온 상품명에 섞여 올 수 있음 — 수집 단계에서 제외 |

착수 시 순서: Step 0(파트너스 대시보드에서 15만원/승인 확인) → Step 2(`fetch-coupang-products.mjs`
구현, `--dry-run`/`--nutrient=` 옵션) → Step 3(GitHub Actions cron 등 갱신 자동화, 선택).
