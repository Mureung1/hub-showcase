# 나의 AI 워크플로우 (3주차 정리)

3주 동안 Claude Code와 함께 "We should do.."를 만들면서 자연스럽게 자리잡은 작업 순서와, 그 과정에서 쓰고 있는 Skill·Agent를 정리한다.

## 일하는 순서

1. **계획 (스코프가 애매할 때만) — `plan` 에이전트**
   새 기능을 시작할 때 범위가 애매하면 `plan` 에이전트를 먼저 돌린다. 이 에이전트는 코드나 문서를 직접 건드리지 않고, `docs/개발백로그.md`의 P0/P1/P2 표 형식 그대로 우선순위·실행 순서만 뽑아준다. 요청이 명확한 작업(이번 주 간식 주기 기능 등)은 이 단계를 건너뛰고 바로 구현으로 간다.

2. **구현 — `dev-planning`·`design` Skill**
   `.claude/skills/dev-planning/SKILL.md`(기획 원칙, 코드 규칙, 인프라 규칙)와 `.claude/skills/design/SKILL.md`(컬러·폰트·픽셀 그래픽 규칙)를 기준으로 코드를 짠다. 두 문서 다 "하지 말 것" 섹션이 있어서, 새 기능을 짤 때마다 여기부터 대조한다. 예를 들어 아이콘을 새로 그릴 땐 `border-radius` 대신 `clip-path` 계단 노치를 쓰는 규칙, 색은 항상 기존 `--scheduler-*` 팔레트를 쓰는 규칙을 먼저 확인한다.

3. **검증 — `verify` 에이전트**
   기능을 실제로 구현한 뒤에는 `verify` 에이전트로 넘긴다. 이 에이전트는 정상 경로보다 엣지케이스(권한, 동시성, 입력 검증 등)에 집중하고, 실제 연결된 Supabase에 `verify-` 접두사 계정을 만들어서 검증한 뒤 반드시 정리하고 끝낸다. 화면까지 관련된 기능은 가능하면 Playwright로 실제 클릭까지 재현한다.

4. **문서화 — 백로그·이슈**
   기능이 끝나면 `docs/개발백로그.md`의 해당 Task 행을 갱신하고, 필요하면 GitHub Issue를 새로 만들거나 체크리스트를 갱신한다. 문서 상태가 실제 코드 상태보다 뒤처지지 않게 하는 게 목표다.

5. **PR**
   `.github/pull_request_template.md` 형식(주요 작업 리스트 / 내가 설명할 수 있는 부분 / 아직 이해 못 한 부분 / 새로 알게 된 것)을 채워서 PR을 올린다. 뒤 세 항목을 채우는 과정에서 내가 실제로 뭘 짰는지, 뭘 아직 모르는지 한 번 더 정리하게 된다.

## 이번 주 실제 사례

간식 주기 기능은 스코프가 명확해서 `plan` 단계는 건너뛰고 바로 구현 → Playwright로 직접 화면까지 확인(별도 `verify` 에이전트 대신 직접 검증) → 백로그·이슈 갱신 → PR(#28) 순서로 진행했다.

## 아직 잘 안 되는 부분

- `plan`/`verify` 에이전트를 매번 쓰지는 않는다 — 스코프가 작으면 건너뛰는데, 이 판단 기준을 아직 명확한 규칙으로 정리하지 못했다.
- 디자인 규칙(색·폰트·그래픽 기법)은 문서화가 잘 되어 있는데, 실제로 아이콘 하나를 그릴 때마다 스크린샷을 찍어보면서 값을 반복 조정하는 시간이 길다 — 더 빠르게 확인하는 방법을 찾고 싶다.
