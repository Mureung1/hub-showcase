# 나의 첫 Skill — 디자인가이드 스킬

## 왜 만들었나

오늘 미션은 Core Loop Builder의 핵심 화면 3개(입력 → 후보 선택 → 루프 시각화)를 glassmorphism과 game감이 있는 스타일로 디자인하는 것이었다. 그런데 디자인은 한 번에 끝나지 않았다. 처음엔 어두운 네온 게임 콘솔 느낌으로 만들었다가, Pinterest에서 본 밝은 파스텔 글래스 스타일 레퍼런스를 보고 완전히 다시 스킨을 입혔고, 그다음엔 "너무 인스타그램 같다"는 피드백을 받아 색상을 다시 쿨톤(블루-바이올렛-시안)으로 바꿨다. 세 번 갈아엎으면서 깨달은 건, 매번 "이게 우리 스타일에 맞나?"를 판단하는 기준이 내 머릿속에만 있었다는 점이다. 다음에 화면을 하나 더 만들 때, 혹은 몇 주 뒤에 오늘 정한 규칙을 잊어버렸을 때, 이 판단 기준을 다시 처음부터 떠올려야 한다면 비효율적이라고 생각했다. 그래서 이 판단 기준 자체를 skill로 만들기로 했다.

## 무엇을 담았나

skill은 `core-loop-builder/.claude/skills/design-guide/SKILL.md`에 만들었고, 세 가지 층으로 구성했다.

1. **참조 파일 링크** — `design/design-tokens.css`(실제 CSS 값)와 `design/DESIGN_SYSTEM.md`(색상 역할·컴포넌트 패턴·모티프 규칙 설명)를 먼저 보게 했다. skill 자체에 모든 규칙을 다 적기보다, "무엇을 확인해야 하는가"는 skill에 두고 "구체적으로 무엇이 맞는 값인가"는 별도 문서에 두는 게 낫다고 판단했다. 색상 하나가 바뀔 때마다 skill 파일까지 통째로 고치고 싶지 않았다.
2. **한 줄 요약** — 스타일 방향을 한 문단으로 압축했다. 체크리스트를 보기 전에 "대충 이런 느낌이어야 한다"는 감을 먼저 잡게 하기 위해서다.
3. **자체 점검 체크리스트** — 배경, 글래스 4요소(반투명+블러+테두리+inset 하이라이트), 강조색 사용 규칙, 텍스트 색, game-feel 모티프의 종류 제한, 모션 규칙, 접근성, 반응형까지 8개 항목으로 정리했다. 이 중 "글래스 4요소"와 "game-feel은 성취 언어로만"은 오늘 작업하면서 직접 실수하거나 고민했던 지점을 그대로 규칙으로 옮긴 것이다. 예를 들어 처음 어두운 버전을 만들 때는 배경만 반투명하게 하고 inset 하이라이트를 빼먹어서 "그냥 어두운 카드"처럼 보였던 시행착오가 있었는데, 그 경험을 "4가지가 다 있어야 유리로 보인다"는 명시적 규칙으로 박아뒀다.

## 의도와 결과를 어떻게 검증했나

skill을 다 쓰고 나서, 실제로 Skill 도구를 통해 `design-guide`를 호출해보려고 했다. 그런데 "Unknown skill: design-guide"라는 에러가 났다. 방금 만든 프로젝트 스코프 skill은 지금 세션에 이미 로드된 목록에는 없고, 그 프로젝트 폴더에서 새로 세션을 시작해야 인식된다는 걸 이번에 알게 됐다. 이건 처음 skill을 만들어보면서 겪은 가장 실질적인 배움 중 하나였다 — skill은 "파일을 저장하는 순간" 작동하는 게 아니라, 로드되는 시점이 따로 있다는 것.

그래서 대신 체크리스트를 직접 손으로 짚어가며 오늘 만든 3화면 목업과 대조해봤다. 대부분 항목은 통과했지만, "접근성" 항목을 짚다가 실제로 허점을 하나 발견했다 — 목업의 입력 필드가 전부 `readonly` 데모용이라 실사용 시 필요한 포커스·대비 검증을 스킵하고 넘어갔다는 점이다. 체크리스트가 없었다면 "루프 다이어그램에 `aria-label`을 넣었으니 접근성은 챙겼다"고 넘어갔을 가능성이 크다. 8개 항목을 순서대로 강제로 짚는 것만으로도, 내가 신경 쓰고 있다고 착각했던 부분과 실제로 챙긴 부분 사이의 간극이 드러났다.

## 피드백을 어떻게 반영했나

색상을 두 번 바꾸는 과정 자체가 이미 하나의 피드백 반영 사이클이었다. 처음 파스텔 버전(하늘색-바이올렛-코랄)이 "인스타그램 같다"는 지적을 받았을 때, 단순히 그 화면의 색상 코드만 바꾸고 끝내지 않았다. `design-tokens.css`, `DESIGN_SYSTEM.md`, 그리고 `SKILL.md`의 체크리스트 문구까지 세 곳을 모두 코랄 언급을 지우고 쿨톤 규칙으로 고쳤다. 이렇게 한 이유는 skill 안에 직접 써둔 원칙 때문이다 — "규칙이 실제 취향과 어긋난 채로 남아있으면 다음번 검토가 틀린 기준으로 통과된다." 만약 화면만 고치고 문서를 그대로 뒀다면, 다음에 이 skill을 호출한 미래의 나(또는 다른 개발 세션)는 "코랄을 써도 된다"는 낡은 규칙을 기준으로 검토하게 됐을 것이다.

## 배운 점

- **skill은 정적인 문서가 아니라, 판단이 바뀔 때마다 같이 갱신해야 하는 살아있는 규칙집이다.** 코드에 테스트가 있듯, 디자인에는 이런 체크리스트가 회귀 테스트 역할을 한다.
- **skill과 원본 데이터(토큰/문서)를 분리해두면 갱신 비용이 줄어든다.** 색이 바뀌어도 skill의 구조 자체는 그대로고, 참조하는 값만 바뀌면 된다.
- **skill이 로드되는 시점과 만들어지는 시점은 다르다.** 오늘처럼 "만들자마자 써보기"가 항상 되는 건 아니라는 걸 실제로 겪고 나서야 알았다. 다음에는 skill을 만든 후 검증이 필요하면, 새 세션에서 확인하는 절차를 미리 계획에 넣어야겠다.
- **체크리스트는 "내가 잘하고 있다고 믿는 것"과 "실제로 챙긴 것" 사이의 차이를 드러낸다.** 접근성 항목에서 그걸 직접 경험했다.

다음에 이 skill을 다시 열어볼 때는, 실제 프로덕션 화면(목업이 아니라 React 컴포넌트)에 대고 검증해보면서 체크리스트 항목이 여전히 유효한지, 빠진 항목은 없는지 다시 점검해볼 계획이다.
