## 3. HTML/CSS/JS, TypeScript, React(JSX), Vite, Node.js의 관계

### 3-1. 브라우저가 유일하게 아는 언어: HTML/CSS/JS

- HTML = 뼈대, CSS = 옷(디자인), JS = 움직임(동작)
- 브라우저는 **이 세 가지만** 실행할 수 있다.

### 3-2. TypeScript = JS + "타입 검사" 문법 가족

- 타입 표시(`: string`), `interface`, `enum`, 제네릭 등 — 전부 "실행 전에 실수를 미리 잡자"는 같은 목적의 문법 모음.
- **실행 시점엔 다 사라짐** (번역될 때 타입 표시는 지워지고 순수 JS만 남음).

### 3-3. JSX = JS + "코드 안에 HTML 태그 쓰기" 문법 (React가 만듦)

```jsx
// JSX (브라우저가 못 읽음)
function Hello() { return <h1>안녕</h1>; }

// 번역 후 순수 JS (브라우저가 읽을 수 있음)
function Hello() { return React.createElement('h1', null, '안녕'); }
```

- 딱 이 한 가지 문법만 추가된, 비교적 단순한 확장.
- TS와는 독립적인 확장이라 **둘 다 쓰면 파일 확장자가 `.tsx`가 됨**.

| 확장자 | 타입 표시(TS) | HTML 태그(JSX) |
|---|---|---|
| `.js`  | ❌ | ❌ |
| `.ts`  | ✅ | ❌ |
| `.jsx` | ❌ | ✅ |
| `.tsx` | ✅ | ✅ |

### 3-4. React = JSX 문법 + 진짜 동작하는 라이브러리(전부 순수 JS로 구현됨)

JSX는 선택사항일 뿐, React의 진짜 핵심은:

- **컴포넌트**: 화면 조각을 함수로 만들어 재사용
- **훅(hooks)**: `useState`(값 기억), `useEffect`(반응하기) 등 상태 관리
- **가상 DOM**: 데이터가 바뀌면 바뀐 부분만 찾아서 효율적으로 화면 갱신

→ 이 전부 **이미 순수 JS로 구현되어 있어서 번역이 필요 없음.** 번역이 필요한 건 우리가 쓰는 JSX/TS 문법뿐.

**이름의 유래**: 데이터가 바뀌면 화면이 개발자의 수동 조작 없이 자동으로 "반응(react)"해서 갱신된다는 의미.

### 3-5. Vite = 번역 + 개발 서버 + 빌드 도구

- Vite 자신도 대부분 JS/TypeScript로 만들어진 프로그램 (내부에 속도용 esbuild(Go 언어)도 일부 사용).
- **개발 중**: `localhost:5173` 서버를 열고, 브라우저가 파일을 요청할 때마다 `.tsx`를 그 자리에서(on-demand) 순수 JS로 번역해 전달. 코드가 바뀌면 웹소켓으로 알려서 새로고침 없이 즉시 반영(HMR).
- **빌드 시(`npm run build`)**: 전체를 한꺼번에 번역·압축해서 배포용 정적 파일 생성.

### 3-6. gcc(C 빌드도구)와 비교

| | gcc | Vite |
|---|---|---|
| 번역 대상 | C 코드 → **기계어(0/1)** | `.tsx` → **순수 JS** |
| 결과물 | CPU가 직접 실행하는 `.exe` | 여전히 JS (브라우저·Node가 실행해야 함) |
| 번역 시점 | 한 번에 전부(컴파일) | 개발 중엔 요청할 때마다 즉석 번역 |
| 비유 | 미리 다 조리해 포장한 도시락 | 주문할 때마다 즉석 조리하는 포장마차 |

### 3-7. Node.js — 브라우저 밖에서 JS를 실행시켜주는 도구
- C언어의 gcc로 빌드하면 결과물이 기계어 즉 exe, 그러나 Vite로 빌드하면 여전히 JS라서 실행을 위한 엔진 필요 = Node.js
- JS는 원래 브라우저 안에서만 실행 가능했음. **Node.js가 그 실행 엔진을 브라우저 밖으로 꺼내 컴퓨터에서도 쓸 수 있게 만든 것.**
- Node.js 자체는 **C++로 제작**됨:
  - **V8 엔진**(C++, 구글이 크롬용으로 만든 JS 실행 두뇌, Node가 그대로 가져다 씀)
  - **libuv**(C, 파일/네트워크 등 시스템 자원을 다루는 손발 역할)
- Vite, npm, TypeScript 컴파일러 같은 도구들은 **전부 JS로 짜여진 프로그램**이고, 이걸 실행시켜주는 게 Node.js.

## 4. 전체 관계 한눈에 보기

```
                     ┌─────────────────────────────┐
                     │   C++ / C  (진짜 밑바닥)      │
                     │   V8 엔진 + libuv             │
                     └───────────────┬─────────────┘
                                     │ 감싸서 포장
                                     ▼
                     ┌─────────────────────────────┐
                     │        Node.js                │
                     │  (브라우저 밖에서 JS 실행)      │
                     └───────────────┬─────────────┘
                                     │ 이 위에서 실행됨
                                     ▼
        ┌───────────────────────────────────────────────┐
        │   Vite, npm, TypeScript 컴파일러 등 (전부 JS 도구) │
        └───────────────────┬───────────────────────────┘
                             │ 번역 대상으로 받는 우리 코드
                             ▼
     ┌───────────────┐            ┌───────────────┐
     │  TypeScript    │            │  JSX (React)   │
     │  JS + 타입검사  │            │  JS + HTML태그  │
     └───────┬───────┘            └───────┬───────┘
             │        둘 다 쓰면 .tsx       │
             └───────────────┬─────────────┘
                             ▼
                    Vite가 실시간 번역
                  (타입 지우기 + JSX 변환)
                             │
                             ▼
                     ┌───────────────┐
                     │   순수 JS      │  ← 브라우저가 진짜 이해하는 것
                     └───────┬───────┘
                             │
              이 안에서 React 라이브러리
           (컴포넌트/훅/가상DOM, 이미 순수 JS로 구현됨)
                        함수들이 호출되며 동작
                             │
                             ▼
                  ┌─────────────────────┐
                  │  HTML + CSS + JS 결과 │  ← 브라우저 화면에 그려짐
                  └─────────────────────┘
```

**한 줄 요약**: C++로 만든 Node.js 위에서 Vite(JS 도구)가 돌아가고, Vite는 우리가 편하게 쓰려고 만든 TypeScript(타입)와 JSX(React 문법)를 실시간으로 순수 JS로 번역해서 브라우저에 전달한다. 그 순수 JS 안에서 React 라이브러리(컴포넌트·훅·가상DOM)가 동작하며 최종적으로 브라우저가 이해하는 HTML/CSS/JS 화면이 그려진다.

## 9. React란 정확히 무엇인가 (개념 정의)

React는 **"컴포넌트 단위로 화면을 조립하고, 데이터가 바뀌면 화면이 자동으로 반응(재렌더링)하게 해주는 UI 라이브러리"**다.

핵심 구성요소 세 가지 — 전부 순수 JS로 이미 구현되어 있는 실제 동작 코드:

- **컴포넌트**: 화면 조각을 함수로 만들어 재사용
- **훅(hooks)**: `useState`(값 기억), `useEffect`(반응하기) 등으로 상태를 관리
- **가상 DOM**: 데이터가 바뀌면 바뀐 부분만 찾아서 효율적으로 화면 갱신

**이름의 유래**: 원래는 데이터가 바뀌면 개발자가 "이 부분 화면 다시 그려라"라고 일일이 명령해야 했다. React는 "데이터가 이렇게 생겼으면 화면은 이런 모양"이라고만 정해두면, 데이터가 바뀔 때마다 화면이 자동으로 "반응(react)"해서 갱신된다 — 그 특징을 그대로 이름으로 가져온 것.

*(참고로 코드 안에 HTML 태그를 쓰는 문법인 JSX도 React가 처음 만들었지만, JSX 자체는 Vue·Solid 같은 다른 라이브러리도 가져다 쓸 수 있는 별도 이름의 문법이다.)*

## 10. client 폴더 파일 하나씩 뜯어보기

| 폴더/파일 | 역할 |
|---|---|
| `dist` | `npm run build`의 완성품 창고 (배포용 최종 파일) |
| `node_modules` | 설치된 라이브러리 창고 |
| `src` | 실제로 짜는 코드 (11번에서 자세히) |
| `package.json` | client 전용 재료 목록 |
| `vite.config.ts` | Vite한테 주는 설명서 (`/api` 프록시 설정 등) |

### 10-1. tsconfig가 3개로 나뉜 이유

- **`tsconfig.json`**: 설정이 거의 없고, "아래 두 설명서를 참고해!"라고 안내만 하는 목차.
- **`tsconfig.app.json`**: **`src` 폴더(브라우저에서 도는 코드)**를 검사할 때 쓰는 규칙 (JSX 허용 등).
- **`tsconfig.node.json`**: **`vite.config.ts` 자기 자신(Node.js에서 도는 코드)**을 검사할 때 쓰는 규칙.

실행되는 "장소"(브라우저 vs Node.js)가 다르면 검사 규칙도 따로 정해줘야 해서 나뉜 것 — 실내화 규칙과 실외화 규칙이 다른 것과 같다. (`*.tsbuildinfo`는 TypeScript가 지난 검사를 기억해두는 캐시 메모장일 뿐, 신경 안 써도 됨.)

### 10-2. `.env.example` — 실제 내용

```
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=
VITE_API_BASE_URL=http://localhost:4000
```

"이 프로젝트를 켜려면 이런 비밀 정보 3가지가 필요해요"라고 미리 알려주는 빈 서식지. 빈칸(`=` 뒤에 아무것도 없음)이라 깃허브에 올려도 안전하고, 진짜 값은 각자 이 파일을 복사해 `.env`(커밋 안 함)를 만들어 채운다.

`VITE_`로 시작하는 이유: Vite는 보안상 **`VITE_`로 시작하는 값만** 브라우저 코드에서 쓸 수 있게 허락한다. (다른 이름의 비밀값은 실수로도 브라우저에 노출 안 되게 막아둔 것.)

### 10-3. `index.html` — 웹사이트가 시작되는 첫 관문

```html
<body>
    <div id="root"></div>
    <script type="module" src="/src/main.tsx"></script>
</body>
```

내용이 거의 텅 비어있다. 딱 두 가지: `<div id="root">`(화면을 채울 빈 상자)와, 그 상자를 채워줄 `main.tsx`를 가리키는 스크립트 태그. 실제 화면 내용은 여기 없고, **`main.tsx`가 React를 이용해 이 빈 상자 안에 화면을 통째로 그려 넣는다** — React 앱은 보통 "빈 종이 한 장 + 자바스크립트가 나머지를 다 채운다"는 구조다.

### 10-4. package.json은 자주 보고, tsconfig.json은 거의 안 본다

- **`package.json`**: 새 라이브러리 설치(`npm install ___`)할 때마다 자동으로 업데이트되고, PR 리뷰할 때도 diff로 자주 마주친다. **자주 결과를 보게 되는 파일.**
- **`tsconfig.json`**: 한 번 세팅되면 그 뒤로 거의 안 건드리고, 이상한 타입 에러 원인을 찾을 때나 특수한 상황에서만 연다. **거의 손 안 대는 파일.**

비유: `package.json`은 자주 여닫는 냉장고 문, `tsconfig.json`은 집 지을 때 한 번 정한 배관 설계도.

## 11. src 폴더 안 구성요소 하나씩 뜯어보기

실행 순서를 따라가면 이해가 쉽다.

### 11-1. 실행 흐름 4단계 (여기가 핵심)

1. **`main.tsx`** — 이 앱의 첫 번째 심장박동. `index.html`의 빈 상자(`#root`)에 `App`을 그려 넣으라는 시작 신호를 보냄. 릴레이 달리기의 첫 주자가 바통을 드는 순간.
   ```tsx
   ReactDOM.createRoot(document.getElementById('root')!).render(
     <React.StrictMode><App /></React.StrictMode>,
   )
   ```
2. **`App.tsx`** — 화면의 맨 꼭대기 컴포넌트. 지금은 `ProjectIntro` 하나만 보여주지만, 앱이 커지면 "어떤 페이지들을 배치할지" 안내하는 지붕 역할을 하게 됨.
3. **`ProjectIntro.tsx`** — 지금 화면에 실제로 보이는 내용. 앞으로 만들 컴포넌트들도 이런 식으로 하나씩 만들어져 `App.tsx`에서 조립된다.
4. **`App.css` / `index.css`** — 각각 `App`, 전체 공통 스타일을 입히는 옷.

### 11-2. `lib/supabase.ts` — DB로 가는 열쇠 발급소

```ts
const supabase = createClient(supabaseUrl, supabaseAnonKey)
```

**정정할 점**: 이 파일 자체가 "DB 라이브러리"는 아니다. 진짜 라이브러리는 `@supabase/supabase-js`(npm으로 설치한 남의 코드)이고, `supabase.ts`는 **"그 라이브러리를 우리 프로젝트에 맞게 미리 설정해둔 우리 코드"**다. `lib/` 폴더는 "외부 라이브러리를 가져와 프로젝트용으로 미리 설정/연결해두는 코드"를 모아두는 곳.

`.env` 값이 없으면 `throw new Error(...)`로 일부러 앱을 바로 멈추게 해둔 것도 특징 — "몰래 조용히 고장나는 것"보다 "바로 티나게 알려주는 것"이 낫기 때문.

### 11-3. 몰라도 되는 것 (있다는 것만 알면 충분)

- **`App.test.tsx`**: "화면에 제목이 잘 보이는지" 자동 확인하는 테스트. `npm run test`로 실행됨.
- **`test/setup.ts`**: 테스트 돌리기 전 준비물을 챙겨주는 설정. 한 번 세팅하고 거의 안 건드림.
- **`vite-env.d.ts`**: `.env` 값을 코드에서 쓸 때 TypeScript가 타입을 알 수 있게 미리 귀띔해주는 파일.

### 11-4. 아직 비어있는 폴더들 — 미리 만들어둔 빈 방

| 폴더 | 나중에 뭐가 들어올지 (이 프로젝트 예시) |
|---|---|
| `components/` | 재사용하는 화면 조각 (예: `Button`, `TimeSlotPicker`) |
| `pages/` | 페이지 단위 화면 (예: `CreateEventPage`, `VoteResultPage`) |
| `hooks/` | 재사용하는 로직 (예: `useAuth`, `useEventList`) |
| `types/` | 여기저기 같이 쓰는 타입 정의 (예: `Event`, `User`) |

**구분법**: "생김새를 재사용" → components, "화면 통째로" → pages, "동작을 재사용" → hooks, "데이터 모양을 재사용" → types.

## 12. types 폴더 ↔ C 헤더파일 비유, 어디까지 맞나

**꽤 정확한 비유이지만, 헤더파일의 "일부 역할"에만 해당한다.**

C의 헤더파일(`.h`)은 두 가지 일을 한다:
1. **구조체/함수 시그니처 선언** (`struct Point { int x; int y; };`) — 이게 TS의 `types/` 폴더 역할과 똑같다.
2. **매크로, 인라인 함수처럼 진짜 동작하는 코드도 포함 가능** — 이건 TS의 `types/` 폴더엔 **절대 없다.** 진짜 로직(함수 구현)은 안 넣고, "이 데이터는 이런 모양이다"라는 선언만 있다.

결정적 차이: C 헤더는 `#include`로 **텍스트가 그대로 복사**되지만, TS는 `import`로 **모듈 단위 참조**를 한다. 또 TS 타입은 컴파일하면 완전히 사라져서 실행 파일에 흔적이 남지 않는다.

**한 줄 정리**: "헤더파일 중에서, 구조체/시그니처만 선언해두는 부분"이라고 생각하면 거의 정확하다.
