# AI 설계 노트 — 답냥이

> 목적: 답냥이는 단순히 문장을 생성하는 서비스가 아니라, **정형 상황은 전수 검수 가능한 결정적 템플릿으로 빠르게 해결하고 복합 맥락에서만 생성형 AI를 쓰는 메시지 작성 도우미**다. 이 문서는 현재 구현, 다음 구현 단계, 선택 근거를 분리해 기록한다.

## 1. 문제 정의와 AI 사용 경계

대학생이 어려워하는 것은 문장 생성 자체보다 관계·목적·감정의 맥락을 매번 설명해야 하는 부담이다. 이를 모두 자유 입력 AI로 풀면 응답이 느리고, 비용이 늘며, 정형 상황에서도 사실을 지어낼 위험이 생긴다.

| 사용자 상황 | 처리 방식 | 이유 |
|---|---|---|
| 일정 조율, 감사·확인, 부탁, 사과, 거절, 관계별 특화 카드 | 로컬 템플릿 | 선택만으로 의도가 충분히 정해진다. 즉시 응답하고 API 비용·대기·환각 위험이 없다. |
| 카드에 없는 상황, 받은 메시지의 세부 내용에 답해야 하는 경우, 감정 완급이 중요한 경우 | 생성형 AI | 받은 메시지·상황 설명·목적을 함께 반영해야 하므로 규칙 문구만으로 품질을 보장하기 어렵다. |

라우팅은 추정이 아니라 사용자의 명시적 선택으로 결정한다.

```text
상황 카드 선택(situationId 있음) ──→ 템플릿 3개 즉시 반환, API 호출 0회
“다른 상황이냥?”(situationId 없음) ─→ 목적 + 맥락 입력 → AI 1회 호출 → 후보 3개
```

이 결정은 다음을 설명할 수 있게 한다.

- 모든 요청을 AI로 보내지 않아 비용과 지연을 줄였다.
- 정형 문구에는 결정적 결과와 전수 검수 가능성을, 개인 맥락에는 생성의 유연성을 사용했다.
- 카드 경로의 실패 가능성과 AI 품질 편차를 핵심 과업(복사)에서 분리했다.

## 2. 현재 구현 상태와 목표 구조

현재 프론트엔드는 72개 카드 문구 **초안**을 컴포넌트 내부에서 조회해 UI 흐름을 시연한다. T25 전수 검수와 T26 독립 템플릿 엔진·라우터는 미완료다. 직접입력 경로도 **개발용 고정 예시**만 반환하며 아직 외부 AI API를 호출하지 않는다. 포트폴리오와 사용자 문구에서 초안을 검수 완료 자산으로, 목을 실제 AI 생성으로 과장하지 않는다.

현재 추가한 공용 경계는 다음과 같다.

```text
src/domain/message.ts
  └─ 관계·목적·상황 카드·톤의 단일 카탈로그

src/services/generation/contracts.ts
  └─ 요청 검증, 구조화된 AI 응답 검증, UI 응답 정규화

src/services/generation/mockGenerator.ts
  └─ 개발용 normal / delay / error500 / error429 강제 케이스
```

실 API 단계(T18~T20)에서는 같은 계약을 유지하며 아래 경계만 추가한다.

```text
클라이언트 생성 서비스
  ├─ 템플릿 라우터 → 로컬 템플릿 응답
  └─ AI 라우터 → POST /api/generate
                         └─ Vercel 서버리스 함수
                              ├─ 프롬프트 빌더
                              ├─ AI provider structured output
                              └─ 런타임 검증·응답 정규화
```

API 키는 서버 환경변수에만 둔다. 브라우저에서 AI provider를 직접 호출하지 않는다.

## 3. 구조화된 응답과 방어적 검증

모델에는 UI 라벨을 맡기지 않는다. 모델의 내부 출력은 다음처럼 최소화한다.

```ts
type GeneratedReply = {
  candidates: {
    toneLevel: 1 | 2 | 3;
    text: string;
  }[];
  situationSummary?: string;
  warning?: string;
};
```

서비스가 `toneLevel`에서 고정 라벨(기본 / 더 부드럽게 / 더 분명하게)을 다시 부여해 UI 계약을 만든다.

```ts
type GenerationResponse = {
  source: 'template' | 'ai';
  candidates: {
    toneLevel: 1 | 2 | 3;
    toneLabel: string;
    text: string;
  }[];
  situationSummary?: string;
  warning?: string;
};
```

`src/services/generation/contracts.ts`는 다음을 런타임에서 검사한다.

- 후보가 정확히 3개인지, 1·2·3 톤이 각각 하나씩 있는지
- 빈 문장·중복 문장·600자 초과 문장을 거절하는지
- 모델이 보낸 임의의 톤 라벨을 신뢰하지 않는지
- 선택적으로 전달되는 요약·경고가 비어 있거나 너무 길지 않은지
- 제한된 협박 키워드 휴리스틱으로 명백한 일부 표현을 1차 분류하는지
- 카드 요청과 AI 요청의 필수 필드·입력 길이가 맞는지

이 검증은 완전한 콘텐츠 안전 판별기가 아니다. 키워드 정규식은 오탐·미탐이 가능한 최소 휴리스틱이다. 프롬프트 안전 규칙, holdout 평가, 사용자 최종 검토를 함께 쓰며 검증 실패 시 후보를 보여 주지 않고 `generation_failed` 처리로 연결한다.

## 4. 프롬프트 아키텍처 (실 API 단계 설계)

프롬프트는 React 컴포넌트에 두지 않는다. Vercel 함수가 추가되는 시점에 서버 전용으로 다음 구조를 사용한다.

```text
api/_lib/prompt/
├── systemPrompt.ts         # 서비스 역할, 안전·사실 충실성 원칙
├── relationshipRules.ts    # 팀플/교수님/선배/친구별 존댓말·톤 해석
├── situationRules.ts       # 목적·상황 카드의 의도 규칙
├── outputSchema.ts         # GeneratedReply JSON Schema
├── examples.ts             # T16을 통과한 few-shot 시드 주입 인터페이스
└── buildPrompt.ts          # 위 조각과 사용자 데이터를 조합
```

`buildPrompt`의 조합 순서는 다음으로 고정한다.

1. 시스템 역할: 한국 대학생의 메시지 작성 조력자
2. 공통 원칙: 입력에 없는 이름·날짜·수치·사유를 만들지 않음, 불확실하면 `[과목명]`처럼 표시
3. 관계 규칙: 존댓말 하한선과 부드러움/분명함의 관계별 해석
4. 목적 규칙: 부탁·사과·거절·질문·제안·기타의 전달 목표
5. T16을 통과한 동일 관계 few-shot 예시
6. 사용자 데이터를 `<received_message>`, `<situation>` 데이터 블록으로 격리
7. JSON Schema 기반 출력 형식

사용자 입력은 지시가 아니라 데이터로 취급하도록 데이터 블록과 structured output을 함께 사용한다. 이는 “이전 지시를 무시하라” 같은 상충 입력의 성공률을 낮추는 완화책이지 완전한 보안 경계가 아니다. 프롬프트 주입 holdout과 `stop_reason`·런타임 응답 검증으로 이탈을 확인한다.

## 5. 실패·불확실성 처리

| 상황 | 사용자 경험 | 데이터 보존 |
|---|---|---|
| 요청 중 | 생성 버튼 잠금, 중복 요청 차단, 대기 안내 | 입력 유지 |
| 20초 초과 | 타임아웃 안내와 재시도 | 입력·기존 정상 후보 유지 |
| 429 | 잠시 후 재시도 안내 | 입력 유지 |
| 5xx·빈 응답·잘못된 JSON | 안전한 일반 오류와 재시도 | 입력·기존 정상 후보 유지 |
| 안전 검증 실패 | 공격적 결과를 표시하지 않고 다시 작성 안내 | 입력 유지 |
| 입력이 너무 짧음 | 더 구체적인 상황을 적도록 안내 | 생성 전 차단 |

카드 템플릿은 복합 맥락의 안전한 대체재가 아닐 수 있으므로, AI 실패 시 무관한 템플릿을 강제로 제시하지 않는다. 사용자는 보존된 입력을 고쳐 재시도할 수 있다.

클라이언트 타임아웃만으로 provider 호출이 취소되지는 않는다. T18은 클라이언트보다 짧은 서버 deadline, `AbortController`, 출력 토큰 상한, 제한된 재시도와 provider 오류 매핑을 함께 구현한다.

## 6. 비용·성능 정책

- 카드 경로는 API 호출이 없어 비용 0, 즉시 응답이다.
- AI 경로는 후보 3개를 **한 요청**으로 받아 왕복과 토큰 오버헤드를 줄인다.
- 입력은 받은 메시지 500자, 상황 설명 300자로 제한한다.
- 클라이언트는 생성 중 중복 클릭을 막고, 서버는 IP당 분당 10회 제한을 둔다.
- 개발 환경은 실제 provider 대신 목 생성기의 강제 오류 케이스로 상태 UI를 검증한다.
- 운영 비용은 `AI 호출 수 × (입력 토큰 단가 + 출력 토큰 단가)`로 산정한다. Haiku 4.5부터 동일 holdout을 평가하고, SPEC 5장 합격선을 통과하는 가장 빠르고 저렴한 모델을 선택한다. 실제 연결 직전에 provider의 모델·가격을 재검증한다.

동일 요청의 해시 캐시·분산 레이트리밋은 트래픽 관측 후 도입한다. 민감한 원문을 키로 한 영구 캐시는 만들지 않는다.

## 7. 개인정보·재방문 정책

- 서버는 받은 메시지·상황 설명·생성 문구를 로그·분석 이벤트·DB에 저장하지 않는다.
- 분석 이벤트에는 관계·상황 카드·목적·톤·출처 같은 식별자만 허용한다.
- 카톡 전환 후 복귀를 위해 현재 탭의 `sessionStorage`에만 임시 보관한다. 마지막 선택 후 30분이 지나면 저장본을 삭제하고, 사용자는 “이 탭의 작성 내용 지우기”로 즉시 삭제할 수 있다.
- 실 AI 경로에서는 원문이 외부 provider로 전송된다. 서비스의 비저장과 provider의 처리·보존을 구분해 안내하며, 당시 정책과 ZDR 실제 적용 여부를 T20 전에 확인한다. 표준 Anthropic API 보존은 별도 합의가 없으면 입력·출력을 최대 30일 내 삭제하는 조건이므로 “이 탭에만 존재”한다고 표현하지 않는다. [Anthropic API 보존 정책](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data)
- 로그인·히스토리·원문 기반 재방문 기능은 MVP Out이다.

재방문은 원문 보관보다 **선택값만** 기억하는 방식이 안전하다. 이후 단계에서 사용자가 명시적으로 허용한 경우에만 최근 관계·상황·선호 톤을 `localStorage`에 저장하고, 초기 화면의 “지난 선택으로 시작”과 전체 삭제를 제공한다. 이 기능은 별도 기획 승인이 필요하다.

## 8. 사용자 통제 UX

답냥이는 최종 답을 대신 결정하지 않는다.

- 세 톤 후보를 같은 비중으로 제시하고 사용자가 직접 고른다.
- 자리 표시자가 있으면 복사 전 채우도록 표시한다.
- 복사 실패 시 텍스트를 선택해 수동 복사를 가능하게 한다.
- AI 실패 시 사용자의 입력을 유지한다.

후보 직접 편집, “더 짧게/더 부드럽게/더 분명하게” 부분 재생성, 즐겨찾기는 유용하지만 현재 MVP 범위 밖의 UX 결정이다. 실제 생성 품질·첫 복사 상호작용률을 측정한 뒤 별도 승인으로 도입한다.

## 9. 품질 평가

대표 평가 골격은 `src/evaluation/generationCases.ts`에 있다. 현재 4개는 groupwork가 없고 일부가 시드와 유사하며, 테스트도 데이터 모양만 확인하므로 품질 검수 완료 근거가 아니다. T21에서 시드와 겹치지 않는 holdout을 최소 시나리오당 2개로 보강하고 실제 생성 결과를 기록한다.

1. 관계에 맞는 존댓말·거리감인가
2. 입력의 의도와 받은 메시지 맥락을 보존했는가
3. 사실·사유·약속을 임의로 추가하지 않았는가
4. 과도하게 비굴하거나 공격적이지 않은가
5. 메신저에 바로 붙여넣을 길이인가
6. 세 톤 후보가 내용은 유지하면서 태도만 충분히 구분되는가

실 API 연결 후에는 각 케이스를 반복 생성해 모델 ID·프롬프트 버전·반복 횟수·톤 정렬·전송 가능성·사실 충실성·지연·실제 토큰 비용을 보고서로 기록한다. 기존 SPEC의 합격선(톤 정렬 90%, 전송 가능성 80%, 환각 0건)을 사용하고, 통과 모델 중 지연·비용이 가장 낮은 모델을 선택한다.

## 10. 대안과 선택 근거

| 검토한 대안 | 선택 | 이유 |
|---|---|---|
| 모든 요청을 AI로 생성 | 하이브리드 | 카드 경로의 즉시성·안정성·비용 우위를 유지한다. |
| 브라우저에서 provider 직접 호출 | Vercel 프록시 | API 키 노출과 클라이언트 신뢰 경계를 막는다. |
| 자유 텍스트 응답 | structured output + 런타임 검증 | UI가 후보 수·톤·길이를 안전하게 다룬다. |
| Zod 등 외부 스키마 라이브러리 | 현재는 수동 타입 가드 | 작은 고정 스키마라 의존성과 번들 증가 없이 검증 가능하다. 복잡해지면 서버 전용 도입을 재검토한다. |
| 원문 히스토리·로그인 | 임시 보관과 선택값 기반 후속 제안 | 민감한 제3자 대화 보관을 피하고 MVP 범위를 지킨다. |

## 11. 포트폴리오 서술 기준

### 현재 구현

- S0~S3 흐름, 카드 문구 초안 조회, 직접입력 목 응답, 실패·타임아웃, 입력 복원·삭제, 복사 폴백을 구현했다.
- AI 출력을 3개 톤 후보 계약으로 제한하고 후보 수·톤 중복·빈 값·길이와 제한적 안전 휴리스틱을 런타임 검증했다.
- 관계별 평가 케이스의 코드 골격과 반복 가능한 테스트 기반을 만들었다.

### 설계 완료·구현 대기

- 관계·목적·안전·few-shot·출력 스키마를 조합하는 서버 전용 프롬프트 빌더, provider 오류·보존 경계를 설계했다.
