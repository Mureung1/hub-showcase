# llm-agent-plan.md — 제품 내 LLM 에이전트 설계 (설계 전용, 구현은 게이트 후)

> **상태: 설계 문서.** 실제 외부 LLM 호출은 아직 하지 않는다. 이 문서는 "언젠가 붙일 때 바로 시작"할 수 있도록 모델·역할·프롬프트·JSON 스키마·PII·동의·구현 절차를 미리 정해 둔 것이다. 원칙은 [evidence-catalog.md](./evidence-catalog.md) **P-D**, 결정 이력은 [decisions.md](./decisions.md) ADR-004.

## 0. 왜 지금은 설계만인가 (게이트)

제품 내 LLM은 사용자 데이터를 외부 API(OpenAI/Gemini)로 보내야 하므로, 도입 전 다음(게이트 G6, evidence-data-roadmap §10)을 충족해야 한다.

- **PII 최소화**: 원문 응답·자유의견·이름을 프롬프트에 넣지 않는다. **비식별 파생값만** 보낸다.
- **동의**: 외부 처리에 대한 별도 동의 후에만 호출.
- **비용·지연·실패**: 호출당 비용·지연을 감당하고, 실패 시 규칙 기반 결과로 **폴백**.
- **환각·정확도**: 검증되지 않은 효과·진단·성적예측으로 오해되지 않게. 출력에 출처·불확실성 표시.

→ 이 조건이 서면 아래 설계대로 구현한다.

## 1. 역할 분리 — 두(세) 에이전트, 모델을 역할로 나눔

한 호출에 합치지 않는다. 시스템 프롬프트·요구 품질이 다르다.

| 에이전트 | 하는 일 | 모델 성격 | 환각 위험 |
|---|---|---|---|
| **설명 에이전트** | 규칙 기반 매칭 결과(TOP 방법·이유)를 사용자 눈높이 자연어로 **설명** | 저비용·빠름(자주 호출) | 낮음 — 이미 정해진 결과를 풀어 말할 뿐 |
| **분석 에이전트** | 수집된 비식별 집계(`/api/analysis`)를 한국어 **요약·해석** | 구조화 강한 모델, **JSON 강제** | 중간 — 수치 왜곡 방지 필요 |
| (이후) **MBTI 페르소나** | 유형 톤으로 대화 보조 | 저비용 | 유형 고정판단처럼 보이지 않게(P-B) |

> 제공자는 OpenAI / Google Gemini 등 자유. **정확한 모델 ID는 구현 시점에 각 제공자 공식 문서로 확정**한다(여기서 특정 버전명을 못박지 않음). 선택 기준: 설명=저비용·저지연, 분석=구조화 출력(JSON schema) 지원.

## 2. 닫힌 기준 = 할루시네이션 방어막 (P-D)

- LLM에게 "이 사람에게 뭐가 맞아?"(열린 창작)를 묻지 않는다.
- 대신 **규칙 엔진이 이미 낸 결과 + `matching-criteria.md`의 닫힌 기준**을 주고 **"이 결과를 설명/요약만 하라"(확인)** 로 좁힌다.
- 판단 근거는 우리 출처 식별자([E*]/[F*])로 인용하게 한다.
- **AI는 생성, 사용자는 승인**: 새 문항·새 매칭 규칙 초안은 AI가 만들어도 **사용자 승인 전 반영하지 않는다.**

## 3. 입력·출력 계약 (PII 안전)

**프롬프트에 넣는 것(비식별만):**
```
temperament(예: NT), matchedMethods[], baselineMethods[],
행동지표 요약(라벨 수준), calibrationError, fitScore, 관련 근거 id[]
```
**절대 넣지 않는 것:** 이름, 자유응답 원문, 원 설문 응답 전체, 식별 가능한 조합.

**출력은 JSON 강제** (Gemini `responseSchema`/`responseMimeType`, OpenAI structured outputs 등). 예:
```json
{
  "summary": "문자열(2~3문장, 가능성 표현)",
  "citations": ["E3", "F1"],
  "uncertainty": "문자열(한계·주의)",
  "disallowed_check": true
}
```
- `citations`는 우리 reference id에서만. 없는 근거를 만들면 무효 처리.
- 진단·성적예측·유형 우열 표현이 있으면 폴백(규칙 기반 문구).

## 4. 아키텍처 — 프론트에서 직접 부르지 않는다

```
프론트 → (동의됨) → 우리 backend 프록시 → 외부 LLM API
```
- **API 키는 backend `.env`에만**(`OPENAI_API_KEY`, `GEMINI_API_KEY`). 프론트 번들·`VITE_`에 절대 노출 금지.
- backend에 `POST /api/explain`, `POST /api/analysis-summary` 라우트를 두고, **입력을 비식별 필드로 서버에서 재검증**한 뒤 호출.
- 실패·타임아웃 시 규칙 기반 결과를 그대로 반환(앱 흐름 유지).

## 5. 구현 시 체크리스트 (게이트 통과 후 그대로 실행)

1. backend에 SDK 추가: `openai` 또는 `@google/genai`(승인 후 의존성). 키는 `.env`(커밋 금지, `.env.example`만).
2. `backend/src/lib/llm.js` — 제공자 클라이언트 + JSON 스키마 강제 + 실패 폴백을 한 곳에.
3. 라우트에서 **allowlist로 입력 재검증**(§3) 후 호출. 출력 JSON 검증(citations·disallowed_check).
4. 프론트: 동의 토글 + "AI 설명 보기"(선택). 미동의/실패 시 규칙 문구.
5. eval 셋: 매칭 결과 → 기대 설명의 쌍 몇 개로 회귀 확인(수치 왜곡·환각 검출).
6. 문구 점검: 가능성 표현, 진단·효과 단정 없음, 출처 표시.
7. 비용·지연 로깅, 호출량 상한.

## 6. 하지 않을 것

- 프론트에서 외부 API 직접 호출(키 노출).
- 원문 응답·자유의견 외부 전송.
- LLM에게 최종 판정·진단·성적예측 위임.
- 검증 전 "AI가 정확히 매칭한다"는 표현.
