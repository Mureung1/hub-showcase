# 후속 작업 우선순위

## 목적

이 문서는 현재 1차 프론트엔드 MVP 이후의 작업 우선순위를 정리한다.

현재 프로토타입은 홈, 타임테이블, 부스, 부스 상세, 공지 목록, 공지 상세 흐름을 정적 데이터로 검증하는 단계다. 다음 작업은 기능을 무작정 늘리는 것이 아니라, 실제 축제 운영 데이터와 사용자 검증에 견딜 수 있는 MVP로 수렴시키는 데 초점을 둔다.

## 현재 상태

완료된 항목:

- 모바일 우선 홈 화면
- 타임테이블 날짜/카테고리 필터
- 부스 날짜/카테고리/검색 필터
- 부스 상세
- 공지 목록/상세
- 디자인 시스템 초안
- Product Design UI/UX 감사
- 하단 내비게이션 `공지` 명확화
- 홈의 운영 부스 수 신호 추가
- 부스 배치도 placeholder 개선
- mock 데이터임을 나타내는 `임시 데이터` 표시

남은 핵심 문제:

- 실제 축제 데이터 구조가 확정되지 않았다.
- 부스 배치도는 아직 실제 이미지가 아니다.
- 현재 시간, 날짜, 운영 상태는 실제 데이터와 연결되어 있지 않다.
- 키보드/스크린리더 접근성은 아직 별도 검증하지 않았다.
- 테스트 자동화가 없다.

## P0. 실제 데이터 구조 확정

가장 먼저 해야 한다. 데이터 구조가 흔들리면 UI, 필터, 상세 화면, 이후 API 연결이 모두 다시 흔들린다.

### 해야 할 일

- 축제 날짜 형식 확정
- 타임테이블 데이터 필드 확정
- 타임테이블 카테고리 확정
- 부스 데이터 필드 확정
- 부스 카테고리 확정
- 부스 메뉴/가격 구조 확정
- 공지 데이터 필드 확정
- 중요 공지 표시 규칙 확정
- 운영 시간과 운영 상태 계산 방식 확정

### 완료 기준

- `src/data/festivalData.ts`의 mock 데이터가 실제 운영 데이터 스키마와 같은 형태를 가진다.
- 타입은 `src/types/festival.ts`에 반영되어 있다.
- 날짜, 카테고리, 위치, 운영 시간, 메뉴, 가격, 공지 본문이 화면별로 일관되게 사용된다.

## P1. 부스 배치도 실제 자산 반영

부스 위치 확인은 기획서의 핵심 과업이다. 현재는 지도형 placeholder이므로 실제 배치도 이미지로 교체해야 한다.

### 해야 할 일

- 날짜별 배치도 이미지 수급 방식 결정
- 이미지 비율과 권장 해상도 결정
- 모바일에서 배치도 확대 보기 필요 여부 결정
- 부스 위치 값과 배치도 표기 방식 일치
- 배치도 이미지가 없을 때의 대체 상태 설계

### 완료 기준

- 부스 화면에서 날짜별 배치도 이미지 또는 실제에 가까운 자산을 볼 수 있다.
- 이미지가 없는 날짜에는 명확한 빈 상태가 표시된다.
- 부스 목록의 위치 표기가 배치도 영역과 충돌하지 않는다.

## P1. 운영 상태와 시간 정보 실제화

현재 홈의 시간, 날짜, 운영 상태는 MVP 시연용 값이다. 사용자는 이런 정보를 live 정보처럼 받아들일 수 있다.

### 해야 할 일

- 현재 시간을 실제 브라우저 시간으로 표시할지 결정
- 축제 날짜 기준 시간을 별도로 둘지 결정
- `부스 운영 중`을 현재 시간 기준으로 계산할지 결정
- 일정의 `다음 일정` 계산 로직 추가
- 운영 종료/운영 전 상태 표시 설계

### 완료 기준

- 홈의 현재 시간과 다음 일정이 정적 상수가 아니다.
- 운영 상태가 부스 운영 시간과 모순되지 않는다.
- mock 상태가 남아 있다면 화면에서 명확히 구분된다.

## P1. 빈 상태와 예외 상태 추가

정적 데이터가 충분할 때는 문제가 보이지 않지만, 실제 데이터가 들어오면 빈 상태가 반드시 필요하다.

### 해야 할 일

- 선택한 날짜에 일정이 없을 때
- 선택한 날짜에 부스가 없을 때
- 검색 결과가 없을 때
- 공지가 없을 때
- 배치도 이미지가 없을 때
- 데이터 로딩 실패 상태

### 완료 기준

- 사용자가 빈 화면을 보지 않는다.
- 각 빈 상태는 다음 행동을 제안한다.
- 필터 초기화 또는 다른 날짜 선택 같은 회복 경로가 있다.

## P2. 접근성 검증

스크린샷 감사로는 접근성을 완전히 검증할 수 없다.

### 해야 할 일

- 키보드 탭 순서 확인
- 하단 내비게이션 포커스 확인
- 상세 화면의 뒤로가기 포커스 확인
- 스크린리더에서 주요 버튼 이름 확인
- 320px, 390px, 430px 모바일 폭 확인
- 긴 텍스트와 큰 글자 설정에서 레이아웃 확인

### 완료 기준

- 주요 흐름을 키보드만으로 이동할 수 있다.
- 아이콘 버튼과 주요 액션은 의미 있는 accessible name을 가진다.
- 작은 화면에서도 주요 CTA와 하단 내비게이션이 겹치지 않는다.

## P2. 테스트 자동화 도입

현재 회귀 검증은 `pnpm lint`와 `pnpm build` 중심이다. 필터와 화면 흐름이 늘어나기 전에 최소 테스트를 추가해야 한다.

### 해야 할 일

- Vitest 도입 여부 결정
- `filterSchedules` 단위 테스트
- `filterBooths` 단위 테스트
- 검색 결과 없음 테스트
- 날짜/카테고리 필터 조합 테스트
- 가능하면 React Testing Library로 화면 전환 smoke test 추가

### 완료 기준

- 필터 로직의 정상/빈 결과가 자동 검증된다.
- 주요 화면 전환이 깨졌을 때 테스트가 실패한다.
- `pnpm test` 또는 동등한 검증 명령이 문서화된다.

## P2. 문서 최신화

구현이 디자인 시스템과 감사 리포트보다 앞서간 부분이 있다.

### 해야 할 일

- `docs/design/DESIGN.md`에 다음 컴포넌트 반영
  - MVP badge
  - data status
  - booth signal
  - map placeholder
  - bottom nav `공지`
- `README.md`에 실행 방법 추가
- 현재 MVP 범위와 out-of-scope 명시
- 감사 리포트의 개선 반영 여부 표시

### 완료 기준

- 새 작업자가 문서만 보고 현재 구조와 MVP 범위를 이해할 수 있다.
- 디자인 문서와 구현이 서로 모순되지 않는다.

## P3. 사용자 검증 준비

실제 방문객 관점의 검증은 아직 하지 않았다.

### 해야 할 일

- 3-5개 핵심 과업 정의
- 모바일 테스트 시나리오 작성
- 과업 성공 기준 작성
- 사용자 피드백 기록 양식 작성

### 추천 과업

- 지금 다음 공연이 무엇인지 찾기
- 특정 날짜의 공연 일정 찾기
- 떡볶이를 파는 부스 찾기
- 부스 위치와 가격 확인하기
- 중요 공지 확인하기

### 완료 기준

- 사용자 테스트에서 과업별 성공/실패를 기록할 수 있다.
- 실패한 과업은 UI 개선 항목으로 연결된다.

## 권장 작업 순서

1. 실제 데이터 구조 확정
2. 부스 배치도 실제 자산 반영
3. 운영 상태와 시간 정보 실제화
4. 빈 상태와 예외 상태 추가
5. 접근성 검증
6. 테스트 자동화 도입
7. 문서 최신화
8. 사용자 검증 준비

## 다음 작업으로 가장 적합한 항목

다음 작업은 `P0. 실제 데이터 구조 확정`이 가장 적합하다.

이유:

- 이후 API 연결 여부와 관계없이 반드시 필요하다.
- 현재 mock 데이터, 타입, 필터 로직의 기준이 된다.
- 부스 배치도, 운영 상태 계산, 빈 상태 설계도 데이터 구조에 의존한다.
