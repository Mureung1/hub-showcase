# 화면 · 상태 설계

> 화면 구조와 상태는 이 문서가 담당하고, 시각 스타일은 DESIGN.md 토큰을 따른다. 변경 이력·근거는 docs/LOG.md 참고.

## 핵심 결정 5가지

1. **톤 사전 선택 제거 — 후보 3개 = 톤 3단계.** 사용자는 결과를 보기 전엔 톤 단계의 의미를 알 수 없으므로, 톤 축은 입력 UI가 아니라 **결과 화면의 구조**로 옮긴다. 후보 3개를 톤 3단계(기본/더 부드럽게/더 분명하게 공통 라벨)로 생성한다 (API 1회).
2. **S2 기본은 상황 카드 선택, 목적+텍스트 입력은 이탈 경로.** 시나리오당 상황 카드 6개(공통 5 + 특화 1)를 고르면 텍스트 입력 없이 즉시 결과(템플릿). 맞는 카드가 없으면 "다른 상황이냥?"으로 기존 목적 6칩 + 모드별 텍스트 입력이 열려 AI로 생성한다 (SPEC 1·2장).
3. **결과 후 1차 동선은 source에 맞춘다.** 템플릿은 "내 상황에 더 맞추기"로 S2-b 입력에 연결하고, AI만 "다시 만들기"로 3개 전부 재생성한다. "상황 수정"은 source별 직전 S2 화면으로 돌아가는 보조 동선이다.
4. **답장/먼저 연락 여부는 S0 화면에서 명시적으로 선택한다.** 받은 메시지 유무로 자동 판별하는 방식은 쓰지 않는다 — 토글(같은 화면에서 필드만 전환)과 화면 분리 두 버전을 비교한 결과, 화면 분리가 "지금 어떤 상황을 입력 중인지"를 사용자에게 더 명확히 전달했다. S0은 앱의 진입점이 된다.
5. **상황 카드는 답장·먼저 연락 두 모드에 동일하게 제시한다.** "답장은 받은 내용에 의존해 템플릿이 어렵다"는 전제는 감사·확인처럼 내용을 몰라도 성립하는 답장에는 과도한 제약이다 — 카드 문구를 모드 공용으로 쓰면 답장에서도 제로 타이핑 경로가 성립한다(SPEC 4장). '다른 상황이냥?'을 눌렀을 때만 모드별 텍스트 필드(결정 4)가 나타난다.

## 화면 흐름

실제 흐름은 앱 밖에서 시작하고 끝난다:

```
(카톡/메일에서 메시지 수신 또는 보낼 일 발생)
   → 앱 진입
      [S0 답장/먼저 연락 선택] → [S1 시나리오 선택] → [S2 상황 카드/직접 입력] → [S3 결과 (톤 축 후보 3개)]
              ▲                      ▲ 방식 다시 고르기    ▲    │ 상황 수정         │ AI: 다시 만들기
              │                      └──────────────────────┘  └────┘◄─────────────────┘
              │                                                   └ 템플릿: 내 상황에 더 맞추기 → S2-b
              └──────────────────────────────── 처음으로 ◄───────────────────────────────┘
   → 복사 → 카톡/메일로 복귀 → 붙여넣기 → 전송
```

- 라우터 없이 단일 페이지 내 단계(step) 전환으로 충분 (MVP 기준). 별도 라우팅 라이브러리 도입은 구조 변경이므로 사전 승인 필요.
- 모바일 퍼스트: 기준 뷰포트 375px, 데스크톱은 중앙 정렬 max-width 컨테이너.
- **상태 유지**: 카톡에서 메시지를 복사해 돌아오는 흐름상 브라우저가 백그라운드에 다녀온다. 입력값·결과는 현재 탭의 sessionStorage에만 보존하고, 마지막 활동 뒤 30분 후 삭제한다. 사용자는 "이 탭의 작성 내용 지우기"로 즉시 삭제할 수 있다.
- **사용자용 단계 표현**: S0~S3는 내부 문서 식별자다. 실제 화면에는 `S0` 같은 개발 용어를 노출하지 않고 자연어 제목 또는 `1/4` 형식만 사용한다.
- **단계 전환**: 화면이 바뀌면 새 `h2`로 초점을 옮기고 상단으로 스크롤한다. 입력값이 남아 있는 동안에는 모든 단계에서 "이 탭의 작성 내용 지우기"를 찾을 수 있어야 한다.

## S0. 답장 · 먼저 연락 선택

| 요소 | 내용 |
|---|---|
| 구성 | **대표 답냥이 인사 문구**(서비스 한 줄 소개, 텍스트·이모지 수준) + 큰 선택지 2개 (세로 스택) — 앱의 진입점 |
| 선택지 | "답장할래요"(자주 쓰는 답장은 카드로 바로 고르고, 받은 내용에 딱 맞추려면 메시지를 붙여넣음) / "먼저 연락할래요"(카드로 바로 고르거나 상황을 직접 설명) |
| 상호작용 | 선택 → S1로 전환. 선택한 모드는 S2까지 유지되며 필드 구성을 결정한다 |
| 상태 | 기본 상태만 존재 (데이터 로딩 없음), 뒤로가기 없음(진입점) |

## S1. 시나리오 선택

| 요소 | 내용 |
|---|---|
| 구성 | 시나리오 카드 4개 (세로 스택, 모바일 기준) |
| 헤더 | "← 방식 다시 고르기" 링크 (S0 복귀) |
| 카드 | **냥이 조력자 이름** + 시나리오명 + 대표 상황 한 줄 + 오른쪽 원형 고양이 조력자 미디어 슬롯 (예: "교수냥 — 교수님·조교님 · 결석·기한 연장·질문, 정중하게"). 에셋 전에는 브랜드 배지로 보이고, 준비 후 동일 영역에 관계별 일러스트를 넣는다. 냥이 네이밍은 SPEC 1장 |
| 상호작용 | 카드 탭 → S2로 전환. 선택 상태 시각화는 `--color-primary` 사용 |
| 상태 | 기본 상태만 존재 (데이터 로딩 없음) |

## S2. 상황 선택

기본 화면은 **상황 카드 그리드**다. 목적 선택·텍스트 입력은 "다른 상황이냥?"을 눌러야 나오는 이탈 경로다.

### S2-a. 상황 카드 (기본)

| 요소 | 내용 |
|---|---|
| 헤더 | 선택한 시나리오명 + "← 다른 관계 고르기" 링크 (S1 복귀) |
| 카드 | 시나리오당 **6장**(공통 5 + 특화 1, SPEC 1장) — 일정 조율 / 감사·확인 / 부탁 / 답장이 늦었을 때 사과 / 거절 + 관계별 특화 1장(예: 교수님·조교님 → 결석·과제 문의). **답장·먼저 연락 두 모드에 동일하게 제시** (핵심 결정 5) |
| 답장 안내 | "카드는 받은 내용을 읽지 않는 자주 쓰는 답장이에요. 내용에 딱 맞추려면 ‘다른 상황이냥?’을 골라주세요."를 짧게 노출 |
| 이탈 카드 | **"다른 상황이냥?"** — 7번째 자리, 톤이 다른(냥이 말투) 버튼으로 시각적으로 구분. 탭 시 S2-b로 전환 |
| 상호작용 | 카드 탭 → 해당 `scenarioId`×`situationId` 템플릿을 즉시 조회 → **로딩 없이 바로 S3 전환** (SPEC 2장 라우팅) |
| 상태 | 기본 상태만 존재 (템플릿 조회는 동기적 — API 호출 없음) |

### S2-b. 다른 상황이냥 (이탈 — 수동 입력)

| 요소 | 내용 |
|---|---|
| 헤더 | 제목 "상황을 조금 더 알려주세요" + "← 상황 카드로 돌아가기" 링크 (S2-a 복귀) |
| 목적 선택 | 보이는 `fieldset/legend` "어떤 말을 전하고 싶나요? (필수)" + 칩 6개 단일 선택. 선택 상태는 `aria-pressed`로 전달 |
| 받은 메시지 (답장 모드만) | textarea, 최대 500자 + 남은 글자 수. 라벨: "받은 메시지 붙여넣기". **주 필드(필수)**. placeholder는 시나리오별 예시. **먼저 연락 모드에서는 이 필드 자체가 화면에 없다** |
| 상황 설명 | textarea, 최대 300자 + 남은 글자 수. **답장 모드에서는 보조(선택)**, **먼저 연락 모드에서는 주 필드(필수)**. placeholder로 입력 예시 제시 (예: "벌써 3번째 이런 상황") |
| 입력 조건 | 답장 모드: 받은 메시지 필수 / 먼저 연락 모드: 상황 설명 필수 (EDGE_CASES 1-1) |
| 안내 문구 | 목적 선택 아래에 "실명·연락처·학번은 빼고 적어주세요"를 노출. 실 AI 연결 후에는 "입력은 보낼 말 생성을 위해 [provider]로 전송되며, 서비스 서버·분석에는 원문을 저장하지 않아요. provider 보존 조건: [검증한 요약/링크]"를 함께 안내 (EDGE_CASES 1-3, 1-5) |
| 생성 버튼 | 라벨 **"보낼 말 3가지 만들기"**. 활성 조건: 목적 선택됨 && 모드별 필수 필드 입력됨. 비활성 안내를 제공하고, 키보드가 열린 상태에서도 접근 가능한 sticky CTA + `safe-area-inset-bottom` 대응 |
| 상태 | 기본 / **생성 중**(버튼 비활성 + 로딩 표시, 20초 타임아웃) / **실패**(오류 문구 + 다시 시도 버튼, 429는 문구 구분). 이 경로는 항상 AI 호출이라 항상 로딩 상태를 거친다 (SPEC 2장 라우팅) |

**모드 변경 시 입력 초기화**: S0로 돌아가 모드를 바꾸면 받은 메시지·상황 설명 입력값은 초기화한다(필드의 의미 자체가 달라지므로 유지가 오히려 혼란). 단 이미 고른 관계(시나리오)는 유지한다.

톤 조절 UI는 이 화면에 없다 — 톤은 S3의 결과 축으로 표현된다 (핵심 결정 1).

## S3. 결과 — 톤 축 후보 3개

| 요소 | 내용 |
|---|---|
| 후보 카드 | 3개 고정, **toneLevel 오름차순 = "기본"(가장 무난한 안)이 맨 위** (선택 부담 최소화). 각 카드에 톤 라벨 배지 + 전체 텍스트 + 복사 버튼 |
| 톤 라벨 | SPEC 1장 확정 공통 라벨: **기본 / 더 부드럽게 / 더 분명하게** (전 시나리오 동일) |
| 복사 | 성공 시 버튼을 1.5초간 "복사됨 ✓"로 전환 / 실패 시 해당 텍스트 자동 선택 폴백 (EDGE_CASES 3-1). 앱 토스트는 기본 요구하지 않고 T23에서 시스템 피드백이 없는 환경에 필요한지 판단. 첫 복사 성공 = 화면상 핵심 과업 완료. `copy` 이벤트는 지원 플랜에서 결과 세트당 첫 성공만 조건부 계측 (SPEC 7장, T24) |
| 자리 표시자 안내 | `[...]`·`OO` 패턴 포함 시 해당 부분 하이라이트 + "빈칸을 채워주세요" 배지 (EDGE_CASES 2-3 — 자리 표시자는 환각 방지를 위한 의도된 출력, 감지 UI는 전송 사고 방지 보조 장치) |
| 재시도 1차 | `source: "template"`은 **"내 상황에 더 맞추기"**로 표시하고 S2-b 입력으로 이동한다. `source: "ai"`만 **"다시 만들기"**로 표시해 같은 입력으로 즉시 리롤한다. 같은 라벨에 다른 동작을 숨기지 않는다 |
| 재시도 2차 | "상황 수정" — 템플릿이면 S2-a, AI면 기존 목적·입력이 남은 S2-b로 복귀. 시나리오·모드는 유지 |
| 상태 (리롤) | **리롤 중**: 다시 만들기·복사 버튼 비활성 + 로딩 표시 (20초 타임아웃, S2-b와 동일 기준). **리롤 실패**: 기존 후보 3개를 그대로 유지한 채 오류 문구 + "다시 시도" 노출 (429는 문구 구분) — 사용자가 가진 유일한 결과를 실패로 날리지 않는다 |
| 안내 | 입력이 매우 짧았던 경우 "상황을 조금 더 적으면 더 맞는 보낼 말이 나와요" (S2-b 경로에서만 해당) |
| 이동 | "처음으로" → S0 (전체 초기화) |
| 출처 재노출 안 함 | 결과 화면에는 `template`/`ai` 배지를 다시 표시하지 않는다. 선택·입력 시점에 경로와 provider 전송을 충분히 설명하고 각 경로가 T25·T21을 통과한 경우에만 적용한다. `source`는 계측·복귀·리롤 규칙에 사용 (SPEC 2장) |
| MVP 제외 | 피드백 버튼("효과 있었어요")은 이 화면에 들어올 예정이나 MVP에서는 미구현 — 레이아웃만 자리 고려 |

## 컴포넌트 후보 (구현 시 기준, 확정 아님)

```
App
└─ MessageFlow (step 상태 관리: mode | scenario | input | result, sessionStorage 동기화 — input 내부에 S2-a/S2-b 서브스텝)
   ├─ ModeSelect            (답장/먼저 연락 큰 선택지 2개, S0)
   ├─ ScenarioCardList / ScenarioCard
   ├─ SituationCardList / SituationCard  (상황 카드 6개 + "다른 상황이냥?", S2-a)
   ├─ PurposeSelect         (목적 칩 6개, 단일 선택 필수 — S2-b 전용)
   ├─ ReceivedMessageInput  (붙여넣기 textarea — S2-b·답장 모드에서만 렌더)
   ├─ SituationInput        (상황 설명 textarea + 글자수 + 안내 — S2-b)
   ├─ GenerateButton        (기본/로딩/실패 상태 — S2-b)
   └─ ResultList / ResultCard (톤 라벨 배지 + 복사 + 플레이스홀더 하이라이트)
```

## UX 세부 지침

생성 대기(스켈레톤+진행을 가장하지 않는 경과 문구), 복사 피드백(버튼 상태 전환+실기기별 추가 피드백 판단), CTA 하단 고정 등 상호작용 세부는 **docs/UX.md 6장 요약표**를 따른다.

공개 전 접근성·모바일 합격선:

- 375×667에서 S0 두 선택지가 첫 화면에 보이고, 320×568에서도 가로 넘침이 없다.
- 상황 카드 6개는 모바일에서도 2열을 유지하고 "다른 상황이냥?"만 전체 폭으로 둔다.
- 모든 동작 요소는 최소 44×44px, 모든 버튼은 일관된 `:focus-visible`을 가진다.
- 단계 전환 초점, 키보드만으로 전 흐름, 스크린리더 상태 안내, `prefers-reduced-motion`, 긴 결과 줄바꿈을 검증한다.
- 결과 카드 3장은 같은 표면색·크기를 사용하고 톤 배지만 달리한다.

## DESIGN.md 토큰 적용 지침

- 상호작용 요소(선택된 카드/칩, 생성 버튼, 복사 버튼)만 `--color-primary`를 사용한다. 실패·경고 상태는 `--color-danger`로 분리한다.
- 본문·제목·버튼 모두 `--font-sans`를 사용한다. 한국어 가독성을 우선해 장식 폰트는 MVP UI에 쓰지 않는다.
- 카드 radius는 `--radius-lg`, 버튼·칩은 `--radius-pill`, 입력 요소는 `--radius-sm`를 따른다.
