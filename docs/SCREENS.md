# 화면 · 상태 설계

> 화면 구조와 상태는 이 문서가 담당하고, 시각 스타일은 DESIGN.md 토큰을 따른다. 변경 이력·근거는 docs/LOG.md 참고.

## 핵심 결정 6가지

1. **톤은 결과 축, 카드 말투는 관계 안전 기본값으로 시작한다.** 톤은 결과 후보 3개(기본/더 부드럽게/더 분명하게)로 유지한다. 카드 guided AI는 저장된 말투 또는 관계 안전 기본값을 쓰며 카드 전에 별도 선택을 요구하지 않는다. 직접 설명은 요청 전에 S2-b에서 말투를 고른다.
2. **S2는 카드→질문 1개와 직접 설명의 병렬 경로다.** 상황 카드 6개는 구조화 맥락의 시작점이고, 카드별 빠른 질문 정확히 1개 뒤 AI 세 톤을 만든다. `질문 없이 바로 초안 보기`는 정적 템플릿, `내 상황을 직접 설명하기`는 받은 내용·세부 맥락을 반영하는 동등한 보조 경로다 (SPEC 1·2장).
3. **결과 후 동선은 생성 route와 복귀 위치에 맞춘다.** guided/manual AI만 명시적 재생성을 제공한다. 기본 초안은 같은 카드 질문이나 직접 설명으로 돌아간다. guided 실패 fallback에는 방금 고른 세부 답이 반영되지 않았음을 숨기지 않는다.
4. **답장/먼저 연락 여부는 S0 화면에서 명시적으로 선택한다.** 받은 메시지 유무로 자동 판별하는 방식은 쓰지 않는다 — 토글(같은 화면에서 필드만 전환)과 화면 분리 두 버전을 비교한 결과, 화면 분리가 "지금 어떤 상황을 입력 중인지"를 사용자에게 더 명확히 전달했다. S0은 앱의 진입점이 된다.
5. **상황 카드는 답장·먼저 연락 두 모드에 동일하게 제시한다.** guided 답장도 받은 원문을 읽지 않으므로 이를 카드와 질문 화면에서 안내한다. 받은 내용에 맞춰야 하면 `내 상황을 직접 설명하기`로 이동한다.
6. **내부 단계는 유지하고 표현만 가이드형 대화로 바꾼다.** S2 안에 context 하위 단계를 추가하되 사용자 진행 표시는 기존 4단계를 유지한다. UI transcript는 AI로 보내지 않고 확정된 ID 또는 직접 입력만 보낸다.

## 화면 흐름

실제 흐름은 앱 밖에서 시작하고 끝난다:

```
(카톡/메일에서 메시지 수신 또는 보낼 일 발생)
   → 앱 진입 → (SP 스플래시 — 세션당 1회, 잠깐 표시 후 자동 소멸)
      [S0 답냥이 질문·빠른 답변] → [S1 관계별 냥이 선택] → [S2 카드→질문 1개 / 직접 설명] → [S3 냥이가 건네는 톤 후보 3개]
              ▲                      ▲ 방식 다시 고르기    ▲    │ 선택·입력 수정 │ AI: 다시 만들기
              │                      └──────────────────────┘  └────┘◄─────────────────┘
              │                                                   └ 템플릿: 내 상황에 더 맞추기 → S2-b
              └──────────────────────────────── 처음으로 ◄───────────────────────────────┘
   → 복사 → 카톡/메일로 복귀 → 붙여넣기 → 전송
```

- 라우터 없이 단일 페이지 내 단계(step) 전환으로 충분 (MVP 기준). 별도 라우팅 라이브러리 도입은 구조 변경이므로 사전 승인 필요.
- **가이드형 대화 셸**: 앱 헤더·현재 냥이 상태·발자국형 진행 표시·대화 영역은 단계 사이에 유지한다. 이전에 확정한 방식·관계는 오른쪽 사용자 말풍선으로 요약하고, 현재 냥이 질문과 선택지만 활성 턴으로 보여준다. 전체 자유 대화 기록을 흉내 내기 위해 불필요한 메시지를 쌓지 않는다.
- **캐릭터 스테이지**: 제공 에셋은 유지되는 셸의 Three.js + React Three Fiber 단일 Canvas에서 2.5D로 렌더링한다. 관계 선택 전에는 대표 답냥이, 선택 후에는 해당 관계 냥이 전신, AI 생성 중에는 생각하는 답냥이로 텍스처를 바꾼다. 상태는 `idle | selected | generating | result` 네 종류만 두고, 관계 카드의 네 냥이와 대화 헤더 아바타는 정적 이미지를 사용해 Canvas를 늘리지 않는다. WebGL 실패·reduced-motion에서는 현재 상태와 같은 정적 이미지/`냥` 배지로 폴백하며 DOM 선택 흐름은 동일하다 (T29).
- 모바일 퍼스트: 기준 뷰포트 375px, 데스크톱은 중앙 정렬 max-width 컨테이너.
- **상태 유지**: 카톡에서 메시지를 복사해 돌아오는 흐름상 브라우저가 백그라운드에 다녀온다. 입력값·결과는 현재 탭의 sessionStorage에만 보존하고, 마지막 활동 뒤 30분 후 삭제한다. 사용자는 "이 탭의 작성 내용 지우기"로 즉시 삭제할 수 있다.
- **사용자용 단계 표현**: S0~S3는 내부 문서 식별자다. 실제 화면에는 `S0` 같은 개발 용어를 노출하지 않고 자연어 제목 또는 `1/4` 형식만 사용한다.
- **단계 전환**: 화면이 바뀌면 새 `h2`로 초점을 옮기고 상단으로 스크롤한다. 입력값이 남아 있는 동안에는 모든 단계에서 "이 탭의 작성 내용 지우기"를 찾을 수 있어야 한다.

## SP. 스플래시 (진입 브랜딩)

| 요소 | 내용 |
|---|---|
| 구성 | 전체 화면 오버레이 — 서비스 배지("대학생 메시지 작성 도우미") + 브랜드명 "답냥이" + 한 줄 소개("꺼내기 어려운 말을 관계와 목적에 맞춰 3가지 톤으로 바로 써줘요.") |
| 동작 | 1.5초 표시 후 0.3초 페이드아웃. 화면 탭 또는 아무 키 입력 시 즉시 스킵 |
| 노출 조건 | 세션당 1회(sessionStorage `dabnyangi:splash-seen`). 카톡을 다녀오는 같은 세션 재방문에는 다시 뜨지 않는다 |
| 접근성 | `prefers-reduced-motion: reduce`이면 페이드 없이 1초 표시 후 즉시 제거. 장식 레이어(`aria-hidden`)로 초점·스크린리더 흐름을 차단하지 않으며 S0가 항상 아래에 렌더된 상태다 |
| 상태 | `visible → leaving(페이드) → gone` 3단계. 데이터 로딩 없음 |

## S0. 답장 · 먼저 연락 선택

| 요소 | 내용 |
|---|---|
| 구성 | 대표 답냥이 아바타·이름·상태가 있는 헤더 + 왼쪽 냥이 말풍선 "지금 필요한 건 어떤 말이냥?" + 빠른 답변 2개 — 앱의 진입점 |
| 선택지 | "답장할래요"(자주 쓰는 답장은 카드로 바로 고르고, 받은 내용에 딱 맞추려면 메시지를 붙여넣음) / "먼저 연락할래요"(카드로 바로 고르거나 상황을 직접 설명) |
| 상호작용 | 선택 → S1로 전환. 선택한 모드는 S2까지 유지되며 필드 구성을 결정한다 |
| 상태 | 기본 상태만 존재 (데이터 로딩 없음), 뒤로가기 없음(진입점) |

## S1. 시나리오 선택

| 요소 | 내용 |
|---|---|
| 구성 | 이전 방식 선택을 오른쪽 사용자 말풍선으로 요약 + 대표 답냥이의 관계 질문 + 관계 카드 4개. 선택 뒤부터 해당 관계 냥이가 대화를 이어간다 |
| 헤더 | "← 방식 다시 고르기" 링크 (S0 복귀) |
| 카드 | **냥이 조력자 이름** + 시나리오명 + 대표 상황 한 줄 + 오른쪽 원형 관계별 냥이 아바타 (예: "교수냥 — 교수님·조교님 · 결석·기한 연장·질문, 정중하게"). 이미지 로드에 실패하면 같은 영역의 `냥` 텍스트 배지로 폴백한다. 냥이 네이밍은 SPEC 1장 |
| 상호작용 | 카드 탭 → S2로 전환. 선택 상태 시각화는 `--color-primary` 사용 |
| 상태 | 기본 상태만 존재 (데이터 로딩 없음) |

## S2. 상황 선택

기본 활성 턴은 관계별 냥이의 질문과 두 경로다. **자주 쓰는 상황에서 빠르게 고르기**는 6개 카드 그리드, **내 상황을 직접 설명하기**는 목적·개인 말투·텍스트 입력으로 이어지는 맞춤 경로다. 둘은 속도와 맥락 반영의 차이를 짧게 설명하고 같은 위계의 표면으로 제시한다.

### S2-a. 상황 카드 (기본)

| 요소 | 내용 |
|---|---|
| 연락 형식 선택 | `교수님·조교님` 관계에만 상황 카드보다 먼저 **"어디로 연락할까요?"**를 묻고 `메신저 / 이메일` 네이티브 라디오를 제공한다. 다른 관계는 이 단계를 표시하지 않고 메신저로 동작한다. 선택은 현재 탭 30분 상태에만 보존한다 |
| 빠른 경로 안내 | 카드 묶음 제목은 **"자주 쓰는 상황에서 빠르게"**, 설명은 **"카드를 고르고 한 가지만 답하면 세 가지 톤으로 써드려요"**로 둔다. 카드 선택 전에 개인 말투를 묻지 않는다 |
| 헤더 | 대화 헤더의 아바타·이름을 선택한 관계별 냥이로 전환 + "← 관계 바꾸기" 링크 (S1 복귀). 이전 방식·관계는 사용자 말풍선으로 요약 |
| 카드 | 시나리오당 **6장**(공통 5 + 특화 1, SPEC 1장) — 일정 조율 / 감사·확인 / 부탁 / 답장이 늦었을 때 사과 / 거절 + 관계별 특화 1장(예: 교수님·조교님 → 결석·과제 문의). **답장·먼저 연락 두 모드에 동일하게 제시** (핵심 결정 5) |
| 답장 안내 | "빠른 카드는 받은 내용을 읽지 않아요. 내용에 딱 맞추려면 ‘내 상황을 직접 설명하기’를 골라주세요."를 짧게 노출 |
| 맞춤 경로 | 카드 묶음과 같은 위계의 큰 버튼 **"내 상황을 직접 설명하기"** + **"받은 내용이나 세부 상황을 반영해요"** 설명. 탭 시 S2-b로 전환 |
| 상호작용 | 카드 탭 → 저장된 개인 말투가 있으면 재사용하고, 없으면 관계 기본값(`groupwork/senior/friend=haeyo`, `professor=seumnida`)을 정한 뒤 S2-d 질문으로 이동 |
| 상태 | 기본 상태만 존재. 카드 탭 자체는 API를 호출하지 않는다 |

교수·조교가 `메신저`를 고르면 위의 6카드·직접 설명 병렬 흐름을 사용한다. `이메일`을 고르면 메신저 경로를 숨기고 **"이메일은 예의를 위해 습니다체로 작성해요"**를 안내한 뒤 `면담 요청 / 수업·과제 질문 / 결석 문의 / 기한 조정 요청 / 추천·자문 요청 / 감사·후속 연락` 6카드를 표시한다. 이메일 카드 선택은 S2-c 입력으로 이동하며 AI를 호출하지 않는다.

### S2-d. 카드 핵심 질문 1개 (guided AI)

| 요소 | 내용 |
|---|---|
| 질문 | 선택한 관계×카드의 Git 정본 질문 정확히 1개. **"한 가지만 더 골라주면, 고른 내용만 반영해서 세 가지 톤으로 써볼게. 이유·날짜·상대 마음은 짐작하지 않아요."**를 함께 노출 |
| 빠른 답변 | 질문당 세 개의 전체 폭 동작 버튼. 탭이 곧 `guided_ai` 생성 요청이며 접근 가능한 이름에 `선택하고 초안 만들기` 의미를 포함 |
| 답장 안내 | **"빠른 답변은 받은 메시지 내용을 읽지 않아요. 내용까지 반영하려면 직접 설명해 주세요."** |
| 기본 초안 | 보조 버튼 **"질문 없이 바로 초안 보기"**. API를 호출하지 않고 동일 카드 정적 템플릿을 표시하며 **"세부 상황을 반영하지 않은 준비된 기본 초안이에요."**라고 안내. T25 전에는 `검수된` 표현 금지 |
| 직접 설명 | **"내 상황을 직접 설명하기"** + **"받은 내용이나 구체적인 사정을 직접 반영해요."**. S2-b로 이동 |
| 로딩·초점 | option 탭 뒤 중복 호출을 막고 새 결과/로딩 heading으로 초점을 이동한다. live region에 **"고른 내용으로 세 가지 톤을 만들고 있어요"**를 알림 |
| 실패 fallback | timeout·429·provider 미설정·최종 실패 시 같은 카드 기본 초안을 표시하고 **"맞춤 초안을 만들지 못해 기본 초안을 보여드려요. 방금 고른 세부 답은 반영되지 않았어요."**를 status/alert로 알림. 재시도와 직접 설명 이동 제공 |
| 모바일 | 320/375px에서 option은 2열 chip이 아니라 한 열 전체 폭 버튼. textarea나 두 번째 질문은 두지 않는다 |

### S2-c. 교수 이메일 정보 입력

| 요소 | 내용 |
|---|---|
| 공통 필수 | 받는 분 성함과 호칭(예: `김민서 교수님` 또는 `박지훈 조교님`), 학과, 학번, 이름, 전달할 구체 내용. 브라우저 현재 탭 sessionStorage에만 최대 30분 보존하고 provider·서버·분석으로 보내지 않음을 안내한다 |
| 면담 요청 추가 | 가능한 시간대 2~3개를 필수로 받고, 대면·온라인 가능 여부는 선택으로 받는다 |
| 생성 버튼 | **"이메일 3가지 만들기"**. 필수 입력을 모두 채워야 활성화되며 누락 항목을 문장으로 안내한다 |
| 이동 | `← 이메일 상황 다시 고르기`로 S2-a의 이메일 카드 목록에 복귀하며 입력은 유지한다. 연락 형식을 메신저로 바꾸면 이메일 결과는 폐기하되 입력은 같은 30분 세션 동안 보존한다 |
| 경계 | 로컬 정적 템플릿만 사용하므로 로딩·재시도·provider 전송 안내가 없다. 이메일에 맞는 카드가 없는 자유 설명 AI는 T33 범위 밖이다 |

### S2-b. 직접 설명 (맞춤 — 수동 입력)

| 요소 | 내용 |
|---|---|
| 헤더 | 관계별 냥이 말풍선과 헤더 보조 문구 **"직접 설명으로 맞춤 작성 중"** + "← 자주 쓰는 상황에서 고르기" 링크 (S2-a 복귀). 답장 모드는 **"어떤 말을 받았는지 알려주라냥"**과 "받은 내용을 적지 않아도 괜찮아요. 메시지를 붙여넣거나, 답장에 필요한 상황만 간단히 알려주세요."로 받은 내용 생략 가능성을 안내한다 |
| 받은 내용 (답장 모드만) | 폼의 첫 필드. textarea, 최대 500자 + 남은 글자 수. 라벨: **"받은 내용 (선택)"**. 관계별 핵심 요약 예시 placeholder를 제공한다. **먼저 연락 모드에서는 이 필드 자체가 화면에 없다** |
| 상황 설명 | textarea, 최대 300자 + 남은 글자 수. **답장 모드에서는 보조(선택)**, **먼저 연락 모드에서는 주 필드(필수)**. placeholder로 입력 예시 제시 (예: "벌써 3번째 이런 상황") |
| 목적 선택 | 텍스트 입력 다음에 보이는 `fieldset/legend` **"어떤 말을 전하고 싶나요? (필수)"** + 칩 6개 단일 선택. 선택 상태는 `aria-pressed`로 전달 |
| 개인 말투 선택 | 목적 아래 보이는 `fieldset/legend` **"평소 어떤 말투를 쓰나요? (필수)"**를 둔다. 네 관계 모두 `습니다체 / 요체 / 이다체 / 용용체`를 노출하고 각 옵션은 이름과 짧은 예시를 함께 보여준다. 앞선 템플릿 결과에서 바꾼 선택이 있으면 유지하며 최소 44px·키보드 단일 선택·색 외 선택 표시를 제공한다 |
| 입력 조건 | 답장 모드: 받은 내용 또는 상황 설명 중 하나 필수 / 먼저 연락 모드: 상황 설명 필수 (EDGE_CASES 1-1) |
| 안내 문구 | 목적 선택 아래에 "실명·연락처·학번은 빼고 적어주세요"를 노출. 실 AI 연결 후에는 "입력은 보낼 말 생성을 위해 [provider]로 전송되며, 서비스 서버·분석에는 원문을 저장하지 않아요. provider 보존 조건: [검증한 요약/링크]"를 함께 안내 (EDGE_CASES 1-3, 1-5) |
| 생성 버튼 | 라벨 **"보낼 말 3가지 만들기"**. 활성 조건: 목적 선택됨 && 개인 말투 선택됨 && (답장: 받은 내용 또는 상황 설명 중 하나 입력 / 먼저 연락: 상황 설명 입력). 비활성 안내를 제공하고, 키보드가 열린 상태에서도 접근 가능한 sticky CTA + `safe-area-inset-bottom` 대응 |
| 상태 | 기본 / **생성 중**(버튼 비활성 + 로딩 표시, 20초 타임아웃) / **실패**(오류 문구 + 다시 시도 버튼, 429는 문구 구분). 이 경로는 항상 AI 호출이라 항상 로딩 상태를 거친다 (SPEC 2장 라우팅) |

**모드 변경 시 입력 초기화**: S0로 돌아가 모드를 바꾸면 받은 메시지·상황 설명 입력값은 초기화한다(필드의 의미 자체가 달라지므로 유지가 오히려 혼란). 단 이미 고른 관계(시나리오)는 유지한다.

전달 강도를 고르는 톤 조절 UI는 이 화면에 없다 — 톤은 S3의 결과 축으로 표현된다. 개인 말끝인 `speechStyleId`만 S2-b에서 고른다.

## S3. 결과 — 톤 축 후보 3개

| 요소 | 내용 |
|---|---|
| 냥이 질문 | **"어느 톤으로 보낼까냥?"** — `기본 / 더 부드럽게 / 더 분명하게` 세 결과 중 고르라는 안내다. 카드·AI 결과 설명 모두 현재 말투명도 함께 확인시킨다 |
| 카드 결과 말투 | `source: "template"`일 때 후보 묶음 위에 **"말투 바꾸기"** 네이티브 라디오를 표시한다. 선택하면 같은 상황의 다른 정적 말투 세트를 로컬에서 즉시 조회하고 복사 성공·폴백 상태를 초기화한다. AI 호출·로딩·런타임 어미 변환은 없다 |
| AI 결과 말투 | `source: "ai"`는 숨은 추가 provider 호출을 만들지 않는다. 말투를 바꾸려면 **"입력 내용 수정하기"**로 S2-b에 돌아가 선택을 바꾸고 사용자가 다시 생성을 요청한다 |
| 후보 카드 | 위 질문 아래 3개 고정, **toneLevel 오름차순 = "기본"(가장 무난한 안)이 맨 위** (선택 부담 최소화). 각 카드에 톤 라벨 배지 + 전체 텍스트 + 복사 버튼. 세 카드는 한 묶음이라는 외곽 컨테이너 안에서 같은 표면·크기를 유지 |
| guided 선택 요약 | AI 성공은 UI 카탈로그 label로 **"선택한 내용: 관계 · 카드 · 빠른 답변"**을 구성한다. provider가 보낸 요약으로 대체하거나 의미 반영 완료를 단정하지 않는다. 필요한 경우 **"추측하지 않은 내용: 날짜 · 이유 · 상대 사정"**을 함께 표시 |
| fallback 안내 | 기본 초안과 guided 실패 fallback은 세부 답 반영 여부를 명시하고 AI 맞춤 결과처럼 보이게 하지 않는다 |
| 톤 라벨 | SPEC 1장 확정 공통 라벨: **기본 / 더 부드럽게 / 더 분명하게** (전 시나리오 동일) |
| 복사 | 성공 시 버튼을 1.5초간 "복사됨 ✓"로 전환 / 실패 시 해당 텍스트 자동 선택 폴백 (EDGE_CASES 3-1). 앱 토스트는 기본 요구하지 않고 T23에서 시스템 피드백이 없는 환경에 필요한지 판단. 첫 복사 성공 = 화면상 핵심 과업 완료. 성공 때 콘텐츠 없이 `copy_succeeded`를 best-effort 기록한다 (SPEC 7장, T36) |
| 자리 표시자 안내 | `[...]`·`OO` 패턴 포함 시 해당 부분 하이라이트 + "빈칸을 채워주세요" 배지 (EDGE_CASES 2-3 — 자리 표시자는 환각 방지를 위한 의도된 출력, 감지 UI는 전송 사고 방지 보조 장치) |
| 기본 초안→AI | 사용자가 질문 없이 본 기본 초안에는 **"AI로 더 맞추기"**를 제공한다. S2-d로 화면을 되돌리지 않고 S3 후보 아래에 같은 카드 질문 1개·option 3개를 펼치며 관계·카드·말투와 기존 후보를 보존한다. option 탭이 guided 요청이다 |
| 실패 fallback→AI | guided 실패로 본 기본 초안에는 primary **"같은 선택으로 AI 다시 만들기"**를 제공해 저장된 question/option ID로 재시도한다. 기존 후보는 요청 성공 전까지 유지하고 secondary manual 경로를 제공 |
| guided 다듬기 | guided 성공은 **"이 선택으로 새 초안 3개 만들기"**와 **"선택한 답 바꾸기"**를 구분한다. 행동 앞에 “지금 고른 답은 그대로 유지되며 버튼을 누르면 추가 입력 없이 새 초안 3개가 바로 만들어진다”는 안내를 보인다. 답 바꾸기는 같은 카드 질문을 S3에 펼치며 상황 카드를 다시 고르게 하지 않는다 |
| manual 재시도 | `manual_ai`는 **"같은 입력으로 다른 표현 만들기"**로 같은 입력을 재사용하고 **"입력 고쳐 다시 쓰기"**로 S2-b에 돌아간다. **"상황 다시 고르기"**도 결과에서 1탭으로 제공한다 |
| 상황 변경 | 모든 메신저 결과에서 **"상황 다시 고르기"**로 S2-a에 돌아갈 수 있다. AI 전환 CTA와 의미를 섞지 않는다 |
| 상태 (리롤) | **리롤 중**: 다시 만들기·복사 버튼 비활성 + 로딩 표시 (20초 타임아웃, S2-b와 동일 기준). **성공**: “새 초안 3개가 준비됐어요”와 수정·복사·이전 초안 비교 안내를 화면에 표시. **리롤 실패**: 기존 후보 3개를 그대로 유지한 채 오류 문구 + "다시 시도" 노출 (429는 문구 구분) — 사용자가 가진 유일한 결과를 실패로 날리지 않는다 |
| 직전 결과 | 후보 교체가 성공했을 때만 직전 1세트를 현재 탭 메모리에 둔다. **"현재 초안 / 이전 초안"**으로 비교하고 이전 초안을 복원하면 두 세트를 swap해 한 단계 undo/redo를 제공한다. 여러 세대 history·DB 저장은 하지 않는다 |
| 직접 수정 | 각 후보의 **"직접 수정"**은 최대 600자 로컬 textarea와 현재 글자 수를 열고 복사는 수정문을 사용한다. `[...]`·`OO`가 남은 후보는 행동명을 **"빈칸 채우기"**로 바꾸고 편집창을 열 때 첫 자리 표시자를 자동 선택한다. **"원래 문장으로"**로 해당 후보를 되돌리며 수정문은 AI·event API·DB에 전송하지 않는다 |
| 안내 | 입력이 매우 짧았던 경우 "상황을 조금 더 적으면 더 맞는 보낼 말이 나와요" (S2-b 경로에서만 해당) |
| 이동 | "처음으로" → S0 (전체 초기화) |

### S3-e. 교수 이메일 결과

- 질문은 **"어떤 이메일로 보낼까냥?"**, 후보 라벨은 `정석 / 더 정중하게 / 더 간결하게`다.
- 각 후보는 제목과 본문을 시각적으로 분리하고 `제목 복사 / 본문 복사 / 전체 메일 복사`를 제공한다. 전체 복사는 `제목: ...` 뒤 빈 줄과 본문을 결합한다.
- 제목·본문의 `[...]` 자리 표시자를 모두 감지해 빈칸 확인 안내를 유지한다.
- `이메일 정보 수정하기`는 S2-c, `이메일 상황 다시 고르기`는 S2-a 이메일 카드 목록으로 돌아간다. AI 리롤과 `내 상황에 더 맞추기`는 표시하지 않는다.
| 출처 재노출 안 함 | 결과 화면에는 `template`/`ai` 배지를 다시 표시하지 않는다. 선택·입력 시점에 경로와 provider 전송을 충분히 설명하고 각 경로가 T25·T21을 통과한 경우에만 적용한다. `source`는 계측·복귀·리롤 규칙에 사용 (SPEC 2장) |
| MVP 제외 | 피드백 버튼("효과 있었어요")은 이 화면에 들어올 예정이나 MVP에서는 미구현 — 레이아웃만 자리 고려 |

## UX 세부 지침

생성 대기(스켈레톤+진행을 가장하지 않는 경과 문구), 복사 피드백(버튼 상태 전환+실기기별 추가 피드백 판단), CTA 하단 고정 등 상호작용 세부는 **docs/UX.md 7~8장**을 따른다.

공개 전 접근성·모바일 합격선:

- 375×667에서 S0 두 선택지가 첫 화면에 보이고, 320×568에서도 가로 넘침이 없다.
- 가이드형 대화 셸의 헤더·현재 질문·첫 선택지는 375×667 첫 화면에서 함께 보인다. 대화 말풍선은 화자 위치뿐 아니라 이름·모양·텍스트로 구분한다.
- 상황 카드 6개는 모바일에서도 2열을 유지하고 "내 상황을 직접 설명하기" 경로는 설명을 포함한 전체 폭 버튼으로 둔다. S2-d 빠른 답변 3개는 320/375px에서 한 열 전체 폭으로 둔다.
- 모든 동작 요소는 최소 44×44px, 모든 버튼은 일관된 `:focus-visible`을 가진다.
- 단계 전환 초점, 키보드만으로 전 흐름, 스크린리더 상태 안내, `prefers-reduced-motion`, 긴 결과 줄바꿈을 검증한다.
- 결과 카드 3장은 같은 표면색·크기를 사용하고 톤 배지만 달리한다.

## DESIGN.md 토큰 적용 지침

- 상호작용 요소(선택된 카드/칩, 생성 버튼, 복사 버튼)만 `--color-primary`를 사용한다. 실패·경고 상태는 `--color-danger`로 분리한다.
- 본문·제목·버튼 모두 `--font-sans`를 사용한다. 한국어 가독성을 우선해 장식 폰트는 MVP UI에 쓰지 않는다.
- 카드 radius는 `--radius-lg`, 버튼·칩은 `--radius-pill`, 입력 요소는 `--radius-sm`를 따른다.
