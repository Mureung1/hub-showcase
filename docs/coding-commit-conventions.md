# 코딩/커밋 컨벤션

이 프로젝트의 코드 작성과 커밋 메시지는 Notion의 [코딩/커밋 컨벤션](https://app.notion.com/p/396f551ebf2380deaaaacff5c78a000e)을 따른다. 브랜치 이름과 PR 작업 단위는 Notion의 [브랜치 전략](https://app.notion.com/p/396f551ebf2380aca2e4d6d9eff0d616)을 따른다.

## 브랜치 전략

- 협업 작업은 기능, 수정, 문서 등 작업 단위별 브랜치를 만들어 진행한다.
- 브랜치 이름은 `<type>/<이슈번호>-<간단-키워드>` 형식으로 작성한다.
- 키워드는 영어 소문자와 하이픈을 사용해 짧게 작성한다.
- 브랜치 type은 커밋 메시지 type과 비슷하지만 완전히 같은 목록은 아니다.

| type       | 의미             | 예시                       |
| ---------- | ---------------- | -------------------------- |
| `feat`     | 새로운 기능 추가 | `feat/12-login`            |
| `fix`      | 버그 수정        | `fix/34-token-error`       |
| `refactor` | 코드 리팩토링    | `refactor/56-user-service` |
| `docs`     | 문서 수정        | `docs/78-readme-update`    |
| `style`    | 코드 포맷/스타일 | `style/79-format`          |
| `test`     | 테스트 코드      | `test/80-signup`           |
| `deploy`   | 배포 관련        | `deploy/81-v1.2.0`         |
| `hotfix`   | 긴급 패치        | `hotfix/82-critical-bug`   |

PR은 작업 브랜치 단위로 생성하고, 리뷰와 필요한 검증을 거친 뒤 기준 브랜치에 병합한다.

### 제출 브랜치

- `main`을 유일한 개발 기준 브랜치로 유지하고 항상 최신 상태에서 작업 브랜치를 만든다.
- `submit`은 사용자가 명시적으로 요청한 경우에만 평일 한국 시간 18시 30분 이후, 하루 작업을 마치고 외부 제출 Pull Request를 만들기 직전에 생성한다.
- `submit`을 평소에 생성·동기화·관리하거나 기능, 수정, 문서 커밋을 직접 쌓지 않는다.
- 생성 시점의 최신 `main`에서 `submit`을 만들고 `.github/workflows/` 디렉터리 전체만 제외한다.
- `.github/workflows/`를 제외한 모든 추적 파일의 경로와 내용은 생성 시점의 `main`과 동일해야 한다.
- 제출 이후에는 `submit`을 개발 기준으로 사용하지 않으며, 다음 명시적 요청이 오면 기존 브랜치에 변경을 누적하지 않고 최신 `main`에서 다시 만든다.

## 커밋 메시지

- 형식은 `<type>: <한글 요약>`으로 작성한다.
- 요약은 `<변경 대상> + <수행한 작업>` 구조의 한국어 명사형으로 작성한다.
- 수행한 작업에는 `작성`, `추가`, `삭제`, `구현`, `연결`, `분리`, `복원`, `보완`, `교정`처럼 실제 변경 결과를 나타내는 단어를 사용한다.
- 변경 대상이나 추상적인 상태만 적은 `인사이트 카드 선택 모드`, `저장 화면 시각 체계`, `일괄 삭제 저장소 구현 정합성` 같은 요약은 사용하지 않는다.
- 요약에 `연결한다`, `수정했다`, `추가합니다`처럼 문장을 끝내는 동사형 표현을 사용하지 않는다.
- 커밋명을 짧게 만들기 위해 변경 대상이나 수행한 작업을 생략하지 않는다.
- 장문형 본문은 사용하지 않는다. 커밋명만으로 해당 커밋 단위에서 수행한 작업 내용을 한눈에 파악할 수 있게 작성한다.
- 커밋 전에는 커밋명만 읽고 “무엇을 어떻게 바꾼 커밋인가?”에 답할 수 있는지 확인한다.

| 잘못된 예                           | 올바른 예                                             |
| ----------------------------------- | ----------------------------------------------------- |
| `feat: 인사이트 카드 선택 모드`     | `feat: 인사이트 카드 다중 선택 기능 추가`             |
| `fix: 일괄 삭제 저장소 구현 정합성` | `fix: 앱 작업공간에 인사이트 일괄 삭제 기능 연결`     |
| `fix: 선택 종료와 삭제 범위 안내`   | `fix: 선택 종료 초점 복원과 전체 삭제 범위 안내 보완` |
| `feat: Google 로그인과 세션 흐름`   | `feat: Google 로그인과 세션 흐름 연결`                |
| `fix: 인사이트 시각 기본값 시간대`  | `fix: 인사이트 시각 기본값 시간대 교정`               |

- 사용 가능한 type은 다음 기준을 따른다.

| type       | 의미                                 |
| ---------- | ------------------------------------ |
| `feat`     | 새로운 기능 추가                     |
| `fix`      | 버그 수정                            |
| `docs`     | 문서 수정                            |
| `style`    | 코드 포맷, 세미콜론 등 비기능적 변경 |
| `refactor` | 기능 변화 없는 리팩토링              |
| `test`     | 테스트 코드 추가 또는 수정           |
| `chore`    | 빌드, 패키지, 설정 등 기타 작업      |
| `perf`     | 성능 개선                            |
| `ci`       | CI/CD 관련 설정 변경                 |
| `revert`   | 이전 커밋 되돌리기                   |

## 코드 스타일

- Front-end 코드는 ESLint, Prettier, Google Style Guides를 기준으로 작성한다.
- Back-end 코드는 Notion 컨벤션의 Back-end 규칙과 Google Style Guide 계열 규칙을 따른다.
- 함수나 메서드 파라미터는 2개까지 inline으로 작성한다.
- 파라미터가 3개 이상이면 각 파라미터를 한 줄씩 개행한다.
- 파라미터가 2개 이하라도 줄이 지나치게 길어지면 한 줄씩 분리한다.
- 팀원이 이해하기 어려운 특이한 코드에는 주석을 작성한다.
- 주석은 기본적으로 설명 대상 코드 위에 작성한다.
