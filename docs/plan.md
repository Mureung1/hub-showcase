## 1. 문제 정의

대학생 팀 프로젝트는 **시작 단계에서 실패한다.**

서로 잘 모르는 팀원들이 위계도 경험도 없이 첫 회의에서 계획과 역할을 정해야 하는데, 이 과정이 어색함과 눈치보기 속에 흐지부지되면서 **계획 없는 프로젝트**와 **불공정한 분담**이 굳어진다.

### 세부 문제

| # | 문제 | 원인 |
|---|------|------|
| 1 | 역할 분담 실패 | 조장·발표 등 기피 역할을 아무도 먼저 말하지 못함. 위계가 없어 "너 이거 해"라고 말할 사람이 없음 |
| 2 | 일정 수립 실패 | 마감일만 알고 마일스톤·세부 태스크로 쪼개는 경험이 없음. 시험 기간 등 학사 일정 고려 실패 |
| 3 | 진행 파악 불가 | 각자 역할에 매몰되어 전체 진행률과 병목을 아무도 모름 |

### 핵심 인사이트

- 기업용 PM 툴과의 차별점: 대학생 팀에는 **PM(위계)이 없다.** AI가 "관리자"가 아니라 **아무도 하기 싫은 말을 대신 해주는 중립적 중재자** 역할을 맡는다.
- 대학생 팀플은 기간이 짧고(3~8주), 사용 빈도가 낮으며, 툴 설치 자체가 진입장벽이다. → **일회성 고밀도 사용(킥오프)** 에 집중하고, 지속 관찰 기능(모니터링 에이전트)은 향후 확장으로 분리한다.

## 3. 서비스 범위

| 기능 | 설명 | AI 활용 |
|------|------|---------|
| ① AI 플래닝 | 주제(≤200자)·과제 유형(힌트)·마감일·인원·사진/PDF 첨부·**기피 날짜**(개별 토글) 입력 → **역할 정의 + 마일스톤·태스크** 제안 → 생성자 수정·승인 | Claude API가 역할 정의까지 생성. '조장' 역할 강제 포함, 역할별 min 합 ≤ 인원 ≤ max 합 서버 검증, 기피 날짜 회피. 재생성은 프로젝트당 3회, 확정 후 잠금 |
| ② AI 역할 배정 | 비공개 설문 → 점수 매트릭스 배정(서버 실행) → AI가 이유 설명 | 배정은 결정적 로직, **설명·타협안 제안은 Claude API** (팀 단위 서술) |
| ③ 계정·초대 | 회원가입(이름·아이디+[중복확인]·이메일(선택)·비밀번호 8자 이상 영문/숫자 조합), 로그인("로그인 상태 유지" 지원), 초대 링크로 팀원 각자의 기기에서 참여 | 없음 |
| ④ 진행 공간 (사이드바 3탭) | **대시보드**(팀 진행률·전주 대비 증감·D-day·마일스톤별 진행률·최근 활동·팀원 목록) / **프로젝트 진행**(내 태스크·파일/링크 업로드+코멘트·참여 잔디 캘린더) / **프로젝트 관리**(내 프로젝트 리스트·[메인] 지정·순서 변경·완료 처리·삭제) | 없음 (수동 CRUD). 활동 로그·스냅샷이 향후 모니터링 에이전트의 데이터 소스가 됨 |
| ⑤ 알림 | 팀 이벤트 발생 시 인앱 알림 — 팀원 합류, 설문 마감, 배정 결과 공개, 역할 교환, 파일/링크 업로드 | 없음 (이벤트 기반 규칙) |

### 진행률 이력 (스냅샷)

- 프로젝트별 전체 진행률을 **주 1회(서버 KST 기준) 스냅샷**으로 저장 → 대시보드의 "지난주 대비 n% 상승" 표시에 사용
- 첫 주(이전 스냅샷 없음)에는 증감 문구를 표시하지 않음

## 4. 사용자 시나리오

1. 홈 화면(서비스 소개) 접속 → 팀원 중 한 명(=생성자)이 **회원가입(아이디+비밀번호)** — 가입 즉시 **자동 로그인되어 대시보드에 착지**, 빈 상태의 "새 프로젝트 시작하기"로 위저드 진입
2. 위저드 입력(3스텝): 프로젝트 제목, 주제(최대 200자), 과제 유형(힌트 카드), 이미지/PDF 첨부(선택) → 마감일 + 캘린더에서 **기피 날짜** 개별 토글(마감일 빨간 표시·기피 회색 블럭, D-day와 "진행 가능 기간" 실시간 표시) → 인원 수(3~8)
3. 플래닝 에이전트가 입력을 받아 **역할 정의 + 마일스톤 + 태스크** 생성(기피 날짜를 제외한 일정으로 계획). 생성자가 태스크·역할을 인라인 수정하거나 "다시 제안받기"(최대 3회)
4. 생성자가 **"이대로 확정"** → 초대 링크 발급 (확정 후에는 재생성 잠금)
5. 나머지 팀원들이 링크 접속 → 해당 페이지에서 즉시 회원가입 + 본인 닉네임 입력(정원·닉네임 중복 검사) → 설문 응답
6. **설문 제출 수가 정원과 같아지면 자동으로 배정 진행**. 제출 수가 정원에 미달하면 마감되지 않으며, 생성자가 수동 마감을 시도하면 **"현재 n명 중 m명이 설문에 참여하였습니다. 전체 참여 인원을 m명으로 수정할까요?"** 확인 UI 표시 — 수락 시 정원을 제출 인원으로 하향하고 배정 진행(역할 min/max는 새 인원 기준으로 재검증·자동 조정, 가입했지만 미제출인 팀원은 배정에서 제외). 대기 화면에 "m/n명 제출" 현황 표시
7. 점수 로직이 역할을 배정하고, 플래닝 에이전트가 **팀 단위 서술**로 이유를 설명. 생성자가 결과 확인 후 **"프로젝트 생성 완료"** = 팀 전체에 결과 공개
8. 공개 후 **10분 내 1회**, 생성자가 두 팀원의 역할을 맞교환할 수 있음 (교환 사실은 팀원 화면에 표시)
9. 프로젝트 진행: 각 팀원이 태스크 상태(할 일/진행 중/완료)를 변경하고, 파일 또는 링크를 업로드하며 코멘트(100자)를 남김. 활동은 참여 잔디 캘린더에 기록되고, 대시보드에서 팀 전체 현황을 확인. 팀 이벤트는 알림으로 전달
10. 프로젝트가 끝나면 생성자가 **"프로젝트 완료"** 버튼으로 완료 처리 → 프로젝트 관리의 "완료된 프로젝트" 섹션으로 이동

## 5. 역할 배정 설계 (핵심 차별 기능)

### 설문 문항 (2분 완료)

| 문항 | 형식 | 비고 |
|------|------|------|
| 선호 역할 | 역할 카드 드래그로 1~3순위 | 선호 ≠ 능력 분리 |
| 기피 역할 | 최대 1개 선택 | 절대 배제 조건 |
| 역할별 경험 | 해봤다/안 해봤다 체크 | 자신감 5점 척도 대신 사용 — 조작 유인이 적음 |
| 리더 의향 | 예/아니오/상관없음 | 조장 역할 배정에만 반영 |

### 배정 로직: "결정적 로직 + LLM 설명" 2단 구조

**1단 — 점수 매트릭스 (서버에서 실행, LLM 미사용)**

```
점수 = 선호 1순위 +3 / 2순위 +2 / 3순위 +1
     + 경험 있음 +1
     + 기피 역할 -10
     + (조장 한정) 리더 의향 예 +2 / 아니오 -10
→ 팀원×역할 매트릭스에서 역할별 min/max 인원 규칙을 지키는 그리디 배정
```

- 같은 입력 → 같은 결과 (재현성·공정성 보장, "왜?"에 답할 수 있음)
- 인원 ≠ 역할 수: 역할별 최소/최대 인원 규칙으로 1인 다역·다인 1역 처리
- **서버에서만 실행** — 개인 설문 응답이 클라이언트로 내려가지 않아 비공개가 실제로 보장됨

**2단 — LLM의 역할 (Claude API)**

- 배정 결과의 **이유를 자연어로 설명** (개인 응답 노출 금지 → "팀 전체 선호를 종합했을 때 이 조합의 만족도가 가장 높음" 식의 팀 단위 서술. 입력도 개인 응답이 아닌 집계 통계만 사용)
- **전원 기피 역할(예: 발표) 타협안 제안**: 로테이션, 해당 역할 담당자의 다른 태스크 경감 등

### 공정성 절차

- 설문은 비공개, 설명은 팀 단위 서술 (비공개 약속과 투명성의 충돌 해소)
- 배정 공개 후 **10분 내 1회**, 생성자가 두 팀원의 역할을 맞교환 가능 (서버 시각 기준, 교환 사실은 팀원 화면에 명시) — 무한 재배정 루프 방지
- 사람은 결과보다 **절차**가 공정할 때 납득한다

## 7. 기술 구성

- **프론트엔드**: React (Vite) + react-router, 모바일 우선 반응형, Soft Mint 디자인 토큰
- **백엔드**: Express — **유일한 API 게이트웨이** (모든 요청이 Express를 경유, Supabase 키는 서버에만 존재)
- **DB·파일**: Supabase — Postgres(데이터) + Storage(비공개 버킷, 다운로드는 서명 URL 1시간)
- **인증**: 아이디+비밀번호 자체 인증 — bcrypt 해시 + JWT(httpOnly 쿠키, "로그인 상태 유지" 시 만료 연장) + 초대 링크 토큰. 가입 시 이름 필수, 이메일은 선택 저장
- **AI**: Claude API 서버사이드 호출 2종 (`@anthropic-ai/sdk`, 모델은 env로 설정)
  - 플래너: 과제 정보(주제·유형 힌트·마감일·인원·기피 날짜 목록, 첨부는 이미지/문서 블록) → structured outputs로 역할/마일스톤/태스크 JSON 강제 → 서버 2차 검증 → 실패 시 재시도 1회 → 유형별 기본 템플릿 폴백
  - 배정 설명: 배정 결과 + 팀 단위 집계 통계 → 자연어 설명·타협안 생성
- **화면 동기화**: 폴링(수 초 간격) — 설문 마감·결과 공개 등 프로젝트 단계 전환과 알림을 팀원 화면에 반영

## 8. 엣지케이스 대응

| 케이스 | 대응 |
|--------|------|
| 배정 불복 | 공개 후 10분 내 1회, 생성자가 역할 맞교환 (서버 시각 기준, 교환 사실 표시), 이후 확정 |
| 전원 기피 역할 | LLM이 로테이션/보상 타협안 제안, 최종은 팀 투표 |
| 설문 제출 수 < 정원 | 마감 불가. 생성자가 수동 마감 시 "현재 n명 중 m명이 설문에 참여하였습니다. 전체 참여 인원을 m명으로 수정할까요?" 확인 → 수락 시 정원을 제출 인원으로 하향 후 배정 진행 (역할 min/max 재검증·자동 조정, 가입했지만 미제출인 팀원은 배정 제외) |
| 진행 가능 기간 부족 | 위저드에서 (오늘~마감일 일수 − 기피 날짜 수)가 7일 미만이면 경고 표시(진행은 허용). 마감일 변경 시 범위 밖 기피 날짜는 자동 해제 |
| 인원 ≠ 역할 수 | 역할별 최소/최대 인원 규칙으로 1인 다역·다인 1역 |
| 설문 응답 역추론 | 배정 설명을 팀 단위 서술로 제한, 개인 응답 인용 금지. 배정·통계 계산은 서버에서만 수행 |
| LLM 출력 오류 | structured outputs 스키마 강제 + 서버 검증(조장 포함, min/max 합, 날짜 범위, roleId 정합) → 재시도 1회 → 유형별 기본 템플릿 폴백 |
| 재생성 남용(비용) | "다시 제안받기" 프로젝트당 3회, 확정 후 잠금 — 서버에서 강제 |
| 아이디 중복 | 실시간 검사 API + DB unique 제약 이중화(가입 시점 레이스 대비), 동일 문구("사용중인 아이디입니다") 처리 |
| 초대 정원 초과·동시 가입 | 정원·닉네임 중복 검사를 트랜잭션으로 묶어 레이스 방지, 링크 유출 시 정원 제한이 방어선 |
| 파일 남용 | 형식 화이트리스트(png/jpg/pdf/docx/pptx/xlsx/zip), 파일당 10MB, 태스크당 5개(재업로드는 교체), 비공개 버킷+서명 URL |
| 잔디·스냅샷 날짜 어긋남 | 활동 날짜와 주간 진행률 스냅샷은 서버에서 KST 기준으로 확정 (배포 서버 UTC 문제 방지). 첫 주는 "지난주 대비" 미표시 |
| 알림 누락·중복 | 알림은 서버 이벤트 발생 시점에 1회 생성, 읽음 상태를 사용자별로 저장 |
| Supabase 무료 티어 | 7일 미사용 시 일시정지 — 시연 전 접속으로 깨우기 체크리스트화 |

## 9. 향후 확장 가능성

- **모니터링 에이전트**: 대시보드 '진행상황 모니터링' 버튼 — 버튼 클릭 시(온디맨드) 제출된 진행 상황을 판단해 현재 진행도·마일스톤 달성률 평가, 필요 시 재계획 제안, 참여도가 부족한 팀원에게 1:1 리마인드. 현재의 활동 로그·업로드·진행률 스냅샷이 그대로 데이터 소스가 된다
- **과제 요건 변경 시 재계획**: 진행률·역할을 보존한 태스크 재생성 ("확정 후 재생성 잠금"과의 충돌을 푸는 별도 설계 필요)
- **최종 기여도 요약**: 자기 신고 데이터의 신뢰성 문제, 성적 분쟁 악용 리스크 검토 후 도입
- **주간 체크인 봇**: 30초 상태 업데이트 + 막힌 점 수집
- **외부 채널 알림**: 이메일·카카오 (현재는 인앱 알림만)
- **아이디/비밀번호 찾기**: 이메일 등록 계정 대상 (로그인 화면의 링크는 자리만 유지)
- **학교 학사일정 API 연동**, 과제 유형 템플릿 확장
- **파일 용량·정책 확장** (유료 티어 전환 시)

## 개발 로그 (결정·검증)

> 작업(슬라이스/커밋 단위)마다 **왜 그렇게 구현했는지 + 어떻게 검증했는지**를 짧게 남긴다. 최신이 위로.

### 2026-07-27 · 배정 결과 10분 내 1회 역할 맞교환
- **왜**: 배정 불복 대비 공정 절차 — 공개 후 10분 내 생성자가 두 팀원 역할을 1회 맞교환(무한 재배정 방지). "사람은 결과보다 절차가 공정할 때 납득".
- **방식**: `POST /api/projects/:id/swap`(생성자·`status=assigned`·`!swap_used`·`now−revealed_at≤10분` 가드) → 두 팀원의 **실무 역할만 교차 저장**(조장 표식 유지, `unique(project,member,role)` 무충돌) → `swap_used=true` + 활동로그 `swap`. `GET /result`에 뷰어 `isCreator`·`swapUsed`·member `id` 추가. `AssignmentResult.jsx`는 지난 배정 슬라이스에서 뺐던 맞교환 UI(카운트다운·2명 선택)를 서버 연동으로 복원. `revealed_at`·`swap_used` 컬럼 기존 재사용(마이그레이션 없음).
- **검증**: curl — 맞교환 전/후 두 팀원 실무 역할 **뒤바뀜**(조장 유지)·`swapUsed` false→true → 2회차 409 · 비생성자 403 · 만료(revealed_at 11분 전 조정) 409 · 진행 탭 역할 반영. `oxlint`·`build` 통과. 테스트 데이터 정리.
- **참고(단순화)**: 맞교환 후 `assignment_stats`/AI 설명은 재계산하지 않음(원래 알고리즘 배정 설명 유지, 카드의 실제 역할만 갱신).
