# SpendMate — 프로젝트 기획 및 요구사항 정의서

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | SpendMate |
| 한 줄 소개 | 기록하는 가계부가 아니라, 소비 습관을 바꿔주는 AI 코치 — 영수증을 찍으면 자취생 특화 카테고리로 분석하고, 현재 소비 속도로 생활비가 언제 바닥나는지 예측해 알려준다 |
| 핵심 철학 | AI는 소비를 줄이라고만 하지 않는다. 줄일 수 없는 소비라면, 같은 상품과 서비스를 더 현명하게 이용할 수 있는 방법까지 함께 제안한다 |
| 대주제 | 대학생(본인)이 겪는 문제 해결 |
| 개발 기간 | 4주 |
| 타겟 유저 | 자취/기숙사 생활 중인 대학생, 용돈·생활비를 스스로 관리해야 하는 학생 |

## 2. 문제 정의 (Problem Statement)

* 대학생·자취생은 정해진 예산 안에서 식비·생활비를 관리해야 하지만, 지출을 매번 손으로 기록하는 건 귀찮아서 며칠 지나면 흐지부지된다.
* 기존 가계부 앱은 "기록"과 "월별 리포트"까지만 도와줄 뿐, "이대로 쓰면 이번 달 생활비가 언제 바닥나는지" "지금 뭘 줄여야 하는지"는 알려주지 않는다.
* 넷플릭스·유튜브뮤직 등 구독 서비스는 매달 똑같이 빠져나가는데, 안 쓰는 구독을 깜빡하고 계속 결제하거나 해지 방법을 몰라서 방치하는 경우가 많다.
* 은행/카드 API 연동은 국내에서 오픈뱅킹 인증·사업자 등록이 필요해 개인 프로젝트로는 사실상 불가능 → 영수증 사진 기반 입력으로 대체.

### 2-1. 계좌 자동연동(마이데이터) 대신 이미지 업로드를 택한 이유

* 마이데이터(본인신용정보관리업)는 오픈뱅킹보다 더 엄격한 금융위원회 정식 허가가 필요한 라이선스라, 4주짜리 학생 프로젝트로는 실제 데이터 연동이 원천적으로 불가능하다.
* 카드 결제 문자(SMS) 자동 기록 방식(Spendy 등)도 검토했으나, 안드로이드 네이티브 전용이라 iOS 지원이 불가능하다.
* → 영수증/온라인 주문내역 캡처 이미지 업로드 방식이 (1) 별도 인허가가 필요 없고 (2) iOS·안드로이드 구분 없이 동일하게 동작한다는 점에서 가장 현실적인 선택.

### 2-2. 경쟁 서비스 분석

| 서비스 | 제공 기능 | 한계 |
|---|---|---|
| 토스 | 소비 내역 조회, 예산 관리, 월별 소비 분석 | 과거 기록 중심, 미래 예측/개입 없음 |
| 뱅크샐러드 | 자산 통합 관리, 소비 분석, 예산 관리 | 범용 자산관리 앱이라 학생 특화 아님 |
| Instant Tally | 영수증/결제 스크린샷 AI 자동 가계부 작성 | 입력 자동화까지만, 분석·코칭 없음 |
| ScanToSheet | 영수증 OCR로 항목 추출 + 지출 통계 | 통계 제공까지만, 행동 제안 없음 |
| Spendy 등 | 카드 결제 문자(SMS) 자동 읽어서 지출 자동 기록 | 안드로이드 네이티브 전용(iOS 불가), 예측·코칭 없음 |

→ 차별화는 "OCR" "분석" 같은 기능이 아니라, **"예측 + 종합 판단에 따른 선택적 개입"**이라는 가치에서 만든다.

### 2-3. 핵심 사용자 시나리오

**등장인물**: 자취 3개월 차 대학생 사용자. 매달 생활비 40만원으로 식비·생필품을 해결해야 한다.
 
1. **가입 & 온보딩**: 사용자는 앱에 가입하고 이번 달 생활비 예산(40만원)과 넷플릭스·유튜브뮤직 구독을 등록한다.
2. **일상적 사용**: 편의점에서 도시락을 사고 영수증을 찍어 업로드한다. OCR이 항목·금액·날짜를 인식하고 "편의점" 카테고리로 자동 분류한다. 오분류가 있으면 사용자가 직접 수정한다.
3. **케이스 A — 평소와 다르지 않을 때**: 사용자가 평소처럼 학식과 장보기 위주로 소비한 주에는, 업로드 직후 "이번 달 소비 패턴은 안정적이에요"라는 짧은 안내만 뜨고 별다른 개입은 없다.
4. **케이스 B — 신호는 같지만 상황이 다를 때**: 시험 기간이라 배달 음식이 늘었다. 아직 예산 사용률이 낮은 시점이라면 앱은 "배달비가 늘었지만 예산 상황은 여유로우니 개입하지 않는다"고 판단한다. 반면 월 중순이 지나 예산 사용률이 이미 높은 상태에서 배달비가 늘면, 앱은 이를 예산 유지 목표에 대한 위험 신호로 판단해 실제 지출 데이터를 조회(`get_expense_summary` Tool)한 뒤, "최근 배달비 비중이 늘어 이번 달 예산 유지가 어려워질 것 같아요"라고 근거 숫자와 함께 먼저 말을 건다.
5. **챗봇 질의응답 케이스**: 사용자가 "이번 달 나 돈 많이 썼어?", "구독 뭐 있었지?" 처럼 물어보면, Agent가 필요하다고 판단할 때만 내부 데이터 조회 Tool을 호출해 실제 숫자를 근거로 답한다. 외부 API 없이 우리 서비스가 이미 가진 데이터(지출 요약, 구독 목록)만으로 응답한다.
6. **월말 생존 모드**: 예산 소진이 임박하면 화면이 자동으로 "남은 돈 / 남은 기간 / 오늘 쓸 수 있는 금액"을 보여주는 전용 모드로 전환되어, 사용자가 월말까지 버틸 수 있도록 돕는다.
7. **주기적 확인**: 사용자는 대시보드에서 카테고리별 소비 현황과 예산 소진 예상일을 언제든 확인하고, 구독 결제일이 다가오면 알림과 해지 방법 안내를 받는다.

## 3. 핵심 가치 제안 (Value Proposition)

* **기록이 아니라 예측**: "20만원 남았습니다"가 아니라 "현재 소비 속도라면 8월 26일에 생활비가 소진됩니다"
* **분석이 아니라 개입**: 영수증 업로드 직후, 상황을 종합 판단해 필요한 경우에만 즉시 개입
* **일방적 조언이 아니라 근거 있는 대화**: "배달 줄이세요"라고 막연히 말하지 않고, 실제 지출 데이터를 조회해 구체적인 숫자(비중, 증가율)를 근거로 코칭한다
* **대학생 페르소나 특화**: 식비/카페/배달/편의점/밀키트/마트/학식 등 자취생 카테고리 체계
* **월말 생존 모드**: 예산 소진 임박 시 "남은 돈 / 남은 기간 / 오늘 쓸 수 있는 금액"을 보여주는 전용 화면
* **고정비까지 반영한 정밀 예측**: 구독료는 평균 추정이 아니라 확정값으로 예측에 반영

### 3-1. 이 서비스를 이용함으로써 사용자가 얻는 이득

* **기록 부담 해소**: 영수증만 찍으면 항목·금액·카테고리가 자동 정리되어, 손으로 가계부를 적는 습관이 오래가지 못해 겪던 좌절을 없앤다.
* **돈 떨어지기 전에 미리 안다**: "이대로 쓰면 언제 바닥나는지"를 미리 알려줘서, 월말에 갑자기 잔액이 없어 당황하는 상황을 예방한다.
* **실제로 아낀다**: 막연히 "줄이세요"가 아니라 실제 지출 데이터를 근거로 "무엇이 얼마나 늘었는지" 구체적으로 짚어줘서, 스스로 행동을 바꿀 수 있게 돕는다.
* **새는 돈을 막는다**: 안 쓰는 구독을 인지하고 해지까지 안내받아, 매달 자동으로 빠져나가던 불필요한 고정비를 줄인다.
* **선택 스트레스 감소**: 예산이 빠듯한 시기에도 "오늘 쓸 수 있는 돈"이 명확해져, 매번 지출을 결정할 때마다 느끼던 불안을 줄인다.
* **자취생 현실에 맞는 조언**: 범용 카테고리가 아니라 배달/편의점/밀키트 등 실제 자취 소비 패턴에 맞춘 코칭을 받는다.

## 4. 차별점 (기존 가계부 앱 대비)

| 구분 | 기존 가계부 앱 (토스/뱅크샐러드) | AI 소비 코치 |
|---|---|---|
| 시점 | 과거 기록 조회 | 현재 데이터로 미래 소진 시점 예측 |
| 개입 방식 | 없음 (또는 단순 알림) | 여러 신호를 종합 판단해 필요할 때만 선택적으로 개입 |
| 결과물 | 월별 리포트/그래프 | 예측 멘트 + 근거 기반 코칭 + 월말 생존 모드 UI |
| 카테고리 | 식비/교통비/문화 등 범용 | 배달/편의점/카페/밀키트/마트/학식 등 자취생 특화 |
| 타겟팅 | 전 연령 범용 | 대학생·자취생 전용 |

## 5. 핵심 기능 아키텍처

전체 흐름을 한 문장으로 요약하면: **규칙 기반 분석으로 소비 신호를 생성하고, AI 소비 코치 Agent가 그 신호를 목표에 비추어 종합 해석하여, 필요할 때만 적절한 Tool을 선택·실행하는 구조.**

```
영수증 업로드
    │
    ▼
OCR → 카테고리 분류 → 예산 계산 → 소비 패턴 분석   (결정론적 로직)
    │
    ▼
Context (소비 신호)
[단기 - 이번 달]
- 배달비 증가율
- 예산 잔액 / 소진 위험도
[장기 - 가입일~오늘, 최대 90일]
- 카테고리별 소비 추세
- 구독 상태
    │
    ▼
🤖 AI 소비 코치 Agent (챗봇 + 지출 추가 시 1회 판단)
    Goal: "사용자가 예산 안에서 지속 가능하게,
           그리고 더 경제적으로 소비하도록 돕는다"
    (Context를 Goal에 비추어 해석)
    │
    ├─ 개입/응답 불필요 → Tool 호출 없이 짧은 안내만 제공
    └─ 내부 데이터 조회 Tool 실행 (get_expense_summary, get_subscriptions 등 —
       외부 API 없이 우리 서비스가 이미 계산한 데이터만 조회)
    │
    ▼
Tool 실행 결과 (실제 지출 요약/구독 목록 등 숫자 데이터)
    │
    ▼
Agent가 결과를 근거(Context 인용)로 삼아
사용자 친화적 메시지로 정리
    │
    ▼
사용자 화면 출력 (챗봇 답변, 또는 지출 추가 직후의 짧은 코칭 멘트)
```

### 5-1. 결정론적 분석 (F1~F8, F12, F13) 및 선택 기능

| # | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F1 | 영수증/주문내역 업로드 | 영수증 사진 또는 온라인 쇼핑 주문내역 캡처 업로드 | 필수 |
| F2 | OCR 텍스트 추출 | OCR API로 항목/금액/날짜 텍스트 추출 | 필수 |
| F3 | 지출 파싱 및 저장 | 항목·금액·날짜 구조로 파싱해 DB 저장 | 필수 |
| F4 | 자취생 특화 카테고리 분류 | 배달/편의점/카페/밀키트/마트/학식/쇼핑 등 자동 분류 | 필수 |
| F5 | 소비 요약 대시보드 | 카테고리별 지출 합계, 그래프 시각화 | 필수 |
| F6 | 생활비 소진 예측 | 변동비(이번 달 누적 일평균)+고정비 결합, 예산 소진 예상일 계산. 일평균은 월초부터 오늘까지 누적 데이터로 계산해 날짜가 지날수록 자연스럽게 안정화됨. **고정비(구독 합계)는 예산에서 매번 별도로 빼는 방식이라, 구독 결제를 지출(F12)로 중복 입력하면 이중 계산됨 — 그래서 F13 화면에 "구독은 지출로 따로 안 넣어도 된다"는 안내 문구를 넣어 애초에 중복 입력을 막는 쪽으로 처리(정교한 자동 중복 감지는 하지 않음, 텍스트 매칭 기반 추론이 이 프로젝트에서 계속 불안정했던 전례 때문)** | 필수 |
| F13 | 구독(고정비) 등록·관리 | 정기결제 서비스 등록, F6 계산에 확정값으로 반영 | 필수 |
| F7 | 월말 생존 모드 | 남은 돈 / 남은 기간 / 오늘 쓸 수 있는 금액 화면 | 필수 |
| F8 | 소비 Context 계산 | Agent에 전달되는 하나의 Context 객체를 생성한다. **단기 신호**(이번 달 기준): 배달비 증가율, 예산 대비 지출률. **장기 신호**(가입일부터 오늘까지, 최대 90일): 카테고리 구성/추세. 데이터량에 따라 구성 비율만(5~13일) 또는 구성 비율+추세(14일 이상)를 포함하며, 90일 초과분은 자동 제외 | 필수 |
| F12 | 수동 지출 입력 | 영수증/캡처가 없는 지출(현금, 계좌이체, 더치페이 등)을 사용자가 직접 금액·카테고리·날짜로 입력. 자취생 지출 중 상당수가 영수증 없는 계좌이체·현금·더치페이라 이게 빠지면 예측·Context 정확도가 크게 떨어지므로 필수로 승격. F6 소진 예측과 F8 Context 계산 모두에 반영 | 필수 |
| F9 | 예산 목표 설정 | 카테고리별/전체 월 예산 설정, 목표 대비 소비율 표시 | 선택 (시간 남으면) |
| F14 | 결제 예정 알림 + 해지 가이드 | 구독 결제일 임박(예: 3일 전) 시 알림 발송 + 서비스별 해지 방법 안내 문구 제공 (실제 자동 해지는 미지원) | 선택 (시간 남으면) |
| F10 | 주간 리포트 알림 | 주 단위로 소비 요약 + 예측/코칭 멘트를 정리해 알림으로 발송 | 선택 (시간 남으면) |

이 신호들은 전부 정해진 계산식으로 산출되며, LLM의 판단이 개입되지 않는다.

### 5-2. SpendMate Agent (F16)

* **Goal**: "사용자가 예산 안에서 지속 가능하게, 그리고 더 경제적으로 소비하도록 돕는다."
* **작동 방식**: 두 가지 진입점을 가진 하이브리드 챗봇으로 동작한다.
  1. **사용자 질의응답** — 사용자가 채팅창에 질문("이번 달 돈 많이 썼어?", "구독 뭐 있지?", "예산 얼마로 잡았지?")을 하면, Agent가 답변에 실제 데이터가 필요한지 스스로 판단해 필요할 때만 Tool을 호출한다.
  2. **지출 추가 시 1회 판단** — 영수증 저장/수동 입력으로 새 지출이 생길 때마다, 그 시점의 Context(이번 달 예산 사용률, 최근 배달비 비중 등)를 보고 먼저 말을 걸지 말지 스스로 판단한다.
* **Context (Agent 입력값)**: 이번 달 기준 단기 신호(배달비 증가율, 예산 잔액/소진 위험도)를 기본으로 하며, 데이터가 쌓이면 장기 신호(카테고리 소비 구성/추세, 구독 상태)도 함께 참고한다.
* **Tool**: 외부 API가 아니라 **우리 서비스가 이미 계산해둔 내부 데이터를 조회하는 함수**를 Tool로 사용한다 (예: `get_expense_summary` — F5 집계 API 재사용, `get_subscriptions` — F13 API 재사용, `get_budget` — F6 전제조건으로 만든 예산 API 재사용, "예산 얼마야?" 같은 질문에 답하기 위해 3주차 중 추가). 예산이 아직 설정 안 된 경우(`amount: null`)는 "아직 예산을 설정하지 않으셨어요" 식으로 안내한다. Agent는 다음 중 하나를 수행한다:
  1. **개입/응답 불필요** → Tool을 호출하지 않고 간단한 안내만 제공
  2. **Tool 호출** → 실제 데이터를 조회해 그 숫자를 근거로 답변
* Agent는 하나의 신호만으로 판단하지 않는다. 일부 신호가 같더라도 전체 Context가 다르면 판단이 달라질 수 있다. (예: 배달비 증가율이 같더라도, 예산 사용률이 낮으면 조용히 있고 예산 사용률이 높으면 먼저 말을 걸 수 있다.)
* Tool 호출 시, 판단 근거가 된 소비 신호와 목표를 함께 반환하며, 이는 사용자에게 노출되는 선택 이유 문구(Reasoning Summary) 생성에 사용된다.
  * 예(Tool 호출): "최근 배달비 비중이 증가해 이번 달 예산 유지 목표에 영향을 줄 것으로 판단해 지출 데이터를 확인했습니다."
  * 예(개입 안 함): "이번 달 예산 사용률이 안정적이므로 추가 안내는 하지 않았습니다."
* **Tool 결과 정리**: Agent는 Tool 호출로 끝나지 않는다. Tool이 반환한 원본 데이터(JSON)를 그대로 노출하지 않고, 근거 숫자와 함께 사용자가 이해하기 쉬운 하나의 메시지로 정리해 전달하는 역할까지 담당한다.

### 5-3. F11·F15를 스코프에서 제외한 이유

> 2주차 진행 중 멘토링 피드백을 계기로 방향을 바꿨다. 원래 F11(Recipe Tool, 공공데이터포털 레시피 API)과 F15(Smart Purchase Tool, 네이버 쇼핑 검색 API 기반 최저가 비교)는 둘 다 검증 안 된 외부 API에 의존하고 매칭 로직도 복잡해서, 4주 개인 프로젝트로는 리스크가 컸다. 내부 데이터만으로 반복구매를 감지해 최저가 없이 코칭만 하는 축소판도 검토했으나, 신선식품처럼 반복 구매가 애초에 정상적인 소비 패턴인 품목까지 "반복구매 감지"에 걸려 의미 없는 코칭이 되는 문제가 있어 **F11·F15 둘 다 스코프에서 완전히 제외**했다.
>
> 이 결정에 따라 **영수증을 품목 단위로 쪼개서 파싱할 필요도 함께 사라졌다** — 품목명이 필요했던 이유는 레시피 추천(재료 파악)과 반복구매 감지뿐이었는데 둘 다 빠졌기 때문이다. 그래서 마트/편의점/쇼핑/밀키트 영수증도 배달·카페와 동일하게 **"상호명 + 총액 + 카테고리" 한 줄로만 저장**한다. 좌표 기반 품목 파싱이 매장마다 깨지다가 Claude API로 해결했던 그 과정 자체는 유의미한 문제 해결 경험이었지만, 실제 코드는 걷어냈다 — 필요해지면 그때 다시 붙일 수 있다는 전제.
>
> F16 Agent가 그래도 Tool을 쓰긴 하는데(5-2 참고), 이건 "F15"라는 이름의 별도 기능이 아니라 그냥 **F16 자체가 우리 서비스 내부 API(F5, F13)를 조회하는 방식**일 뿐이다. 외부 의존성 없이도 "Agent가 스스로 판단해서 Tool을 부른다"는 핵심 경험은 그대로 살릴 수 있기 때문에, Tool 자체를 없애지는 않고 이 형태로만 남겼다.

**스트레치 (4주차 여유 시, 시간이 정말 많이 남으면)**
* 네이버 쇼핑 API 기반 실제 최저가 비교 (F15 부활)
* 영수증 품목 단위 파싱 재도입 (Claude 기반)
* 쿠폰/할인 정보 추천
* 정기배송 vs 일반구매 비교

### 5-4. 왜 이것이 "AI 에이전트"인가

F1~F8, F12, F13은 계산과 규칙으로 끝나는 결정론적 파이프라인이라 에이전트가 필요 없다. 반면 F16(Agent)은 여러 신호를 목표에 비추어 종합 해석해 **개입 여부와 Tool 선택**을 스스로 판단해야 하므로 진짜 tool-calling 에이전트 구조가 필요하다.

Agent는 하나의 규칙으로 Tool을 선택하지 않고, 여러 소비 신호와 목표를 종합적으로 고려해 개입 여부와 Tool을 결정한다. "개입하지 않음" 역시 가능한 선택지 중 하나일 뿐이다.

**데모로 증명하는 방법**: 일부 신호(예: 배달비 증가)는 같지만 전체 Context(예산 사용률 등)가 다른 두 케이스를 보여준다.
- Case A: 배달비 증가 + 예산 사용률 낮음 → 개입 안 함
- Case B: 배달비 증가 + 예산 사용률 높음 → 지출 데이터 조회 Tool 호출 후 근거 숫자와 함께 먼저 말을 건다

"신호가 다르면 결과가 다르다"는 규칙 기반으로도 가능하지만, "일부 신호가 같아도 전체 Context가 다르면 판단이 달라진다"는 것은 여러 신호를 종합 해석한다는 것의 가장 직접적인 증거가 된다.

## 6. 요구사항 정의 (Requirements)

### 6.1 기능 요구사항 (Functional Requirements)

* 사용자는 회원가입/로그인 후 본인 계정으로 영수증을 업로드할 수 있어야 한다.
* 시스템은 OCR을 통해 상호명, 항목, 금액, 결제일시를 추출해야 한다.
* 시스템은 추출된 항목을 자취생 특화 카테고리로 자동 분류해야 하며, 사용자는 오분류를 수동으로 수정할 수 있어야 한다.
* 시스템은 월별/카테고리별 소비 합계를 대시보드로 시각화해야 한다.
* 사용자는 정기결제(구독) 서비스를 등록·수정·삭제할 수 있어야 한다.
* 시스템은 월 예산, 일평균 변동비 소비 속도, 구독(고정비) 합계를 함께 계산해 예산 소진 예상일을 산출해야 한다.
* 시스템은 남은 예산이 임계치 이하로 떨어지면 "월말 생존 모드" 화면을 자동으로 노출해야 한다.
* 시스템은 영수증 업로드 직후, 소비 패턴 신호(배달비 증가율, 예산 소진 위험도, 구독 미사용 여부 등)를 계산해 AI 소비 코치 Agent에 전달해야 한다.
* **AI Agent는 소비 분석 결과를 바탕으로 개입이 필요하다고 판단한 경우에만 적절한 Tool을 호출하며, 개입이 불필요한 경우에는 Tool을 호출하지 않고 분석 결과만 사용자에게 제공한다.**
* 개입이 불필요하다고 판단한 경우에도, 시스템은 "현재 소비 패턴은 안정적이에요" 같은 짧은 안내 메시지를 함께 제공해야 한다 (침묵 처리하지 않는다).
* Agent는 하나의 소비 신호만으로 Tool을 결정하지 않으며, 여러 소비 신호와 현재 상황을 종합적으로 고려하여 개입 여부와 Tool을 선택해야 한다.
* 시스템은 Tool 선택 시 판단 근거가 된 소비 신호를 함께 반환하고, 이를 바탕으로 사용자에게 선택 이유를 자연어로 설명해야 한다.
* 사용자는 영수증/캡처가 없는 지출(현금, 계좌이체, 더치페이 등)을 금액·카테고리·날짜로 직접 입력할 수 있어야 하며, 이 데이터는 F6 예측과 F8 Context 계산에 동일하게 반영되어야 한다.
* (선택) 사용자는 카테고리별/전체 예산 목표를 설정할 수 있다.
* (선택) 구독 결제 예정일 임박 시 알림 + 해지 방법 안내를 제공한다 (실제 자동 해지는 미지원).
* (선택) 시스템은 주 단위로 소비 요약과 예측/코칭 멘트를 정리해 알림으로 발송할 수 있다.

### 6.2 비기능 요구사항 (Non-functional Requirements)

* **정확도**: 국내 영수증(감열지 포함) OCR 인식 정확도를 1주차에 사전 테스트하고, 오인식 시 수동 보정 UI를 제공한다.
* **예측 신뢰성**: 소진일 예측은 "일평균 소비 × 남은 일수" 기반 선형 추정으로 시작한다. 일평균 소비는 고정된 기간(예: 최근 7일)이 아니라, **이번 달 시작일부터 오늘까지 누적된 전체 데이터**로 계산한다. 이렇게 하면 월 초에는 자연스럽게 며칠치 평균으로 시작하고, 날짜가 지날수록 별도 로직 없이 더 많은 데이터를 반영하며 안정화된다. 확률·정밀도를 과장하는 표현(예: "소진 확률 82%", "추천 신뢰도 95%")은 사용하지 않는다.
* **데이터 품질 안내**: "신뢰도" 같은 LLM 자기평가 지표 대신, 객관적 조건(데이터량, API 결과 유무)에 따른 규칙 기반 안내 문구를 표시한다.
  * 이번 달 소비 데이터가 임계치(예: 5일) 미만인 경우: "아직 데이터가 적어 예측·추천 정확도가 낮을 수 있어요. 데이터가 쌓일수록 예측이 더 정확해져요."
  * 가입 후 5일 미만인 경우: 장기 소비 패턴(카테고리 구성, 추세, 구독 이용 패턴)은 노출하지 않고 "아직 장기 소비 데이터가 부족해 습관 분석은 제한적이에요."로 안내한다.
  * 가입 후 5~13일: 아직 추세(증가/감소) 판단은 하지 않고, 카테고리별 소비 구성 비율(예: 배달 58% / 편의점 18% / 카페 11%)만 보여준다.
  * 가입 후 14~89일: 카테고리별 구성 비율에 더해 증가/감소 추세도 함께 보여준다.
  * 가입 후 90일 이상: 최근 90일 데이터만 사용하고 그 이전 데이터는 자동으로 제외한다.
  * 가격비교 API가 결과를 찾지 못한 경우: "가격 정보를 찾지 못해 이번엔 비교 결과를 제공하지 않습니다."
* **응답 속도**: 결정론적 분석 결과는 5초 이내 노출을 목표로 한다. Agent가 Tool을 호출하는 경로는 외부 API 왕복이 추가되므로 별도 목표치(예: 10~15초)를 두고, 비동기 로딩 UI로 체감 지연을 완화한다.
* **설명 가능성(Explainability)**: Tool 선택 이유는 실제 계산된 신호값에 근거해야 하며, LLM이 근거 없이 이유를 지어내지 않도록 신호 값을 프롬프트/함수 반환값으로 명시적으로 전달한다.
* **외부 의존성 검증 원칙**: 확신 없는 외부 데이터(API, 크롤링)에 의존하는 기능은 1주차에 PoC(사전 검증)를 진행하고, 안정적으로 동작하지 않으면 과감히 스트레치로 내린다.
* **보안/개인정보**: 영수증 업로드 이미지 및 파싱 데이터는 본인 계정에만 접근 가능하도록 인증 처리한다.
* **비용 관리**: OCR/LLM/외부 검색 API는 호출량 기반 과금이므로, 4주 개발/데모 기간 내 무료 티어 한도 내에서 운용 가능한지 사전 확인한다.

## 7. 4주 로드맵

**진행 우선순위**: ① OCR PoC → ② Agent 프롬프트·내부 Tool 설계 → ③ 구현. 이 시점부터는 기획을 늘리기보다, 각 기능이 실제로 동작하는지 검증하는 데 집중한다.

| 주차 | 목표 | 주요 작업 |
|---|---|---|
| 1주차 | 입력 파이프라인 구축 + PoC | 영수증 업로드 UI, OCR 연동, 파싱, DB 스키마 설계 |
| 2주차 | 분류 및 시각화 | 카테고리 분류 로직, 소비 요약 대시보드, 구독 등록·관리 화면 |
| 3주차 | 예측 + Agent + Tool 연동 | 소진일 예측, 생존 모드 UI, 소비 패턴 신호 계산, AI 소비 코치 Agent(챗봇 + 지출 추가 시 1회 판단) 구현, 내부 데이터 조회 Tool 연동, Reasoning Summary 생성 |
| 4주차 | 마무리 | 예산 목표 설정(선택), 알림(선택), 스트레치 기능(시간 남을 때만), 버그 수정, **데모 계정용 3개월치 시드 데이터 준비**(장기 Context가 Agent 판단에 실제로 반영되는 모습을 보여주기 위함), 데모 시나리오(아래 10번 참고) 준비 |

세부 작업 체크리스트는 별도 문서(`개발_체크리스트.md`)를 참고한다.

## 8. 기술 스택 

* **백엔드**: Spring Boot (Java)
* **AI Agent / Tool Use**: Claude API (tool use) — 소비 Context를 받아 개입 여부·Tool 호출을 판단. Tool은 외부 API가 아니라 우리 서비스 내부 API(지출 요약, 구독 목록 조회)를 재사용
* **OCR**: 네이버 클로바 OCR — 상호명·총액·날짜만 추출 (품목 단위 파싱은 하지 않음, 아래 5-3 참고)
* **DB**: PostgreSQL + JPA/Hibernate — 영수증 원본 메타데이터 + 파싱된 지출 내역 테이블 분리
* **프론트엔드**: React — 대시보드 차트 라이브러리 활용

> 네이버 쇼핑 검색 API·공공데이터포털 레시피 API는 1주차 PoC까지는 진행했으나, 외부 의존성·매칭 로직 복잡도를 고려해 최종 스코프에서 제외했다 (5-3 참고).

## 9. 리스크 및 고려사항

* 국내 영수증(감열지, 손글씨) OCR 인식률이 낮을 수 있음 → 1주차 실제 샘플 테스트 필수
* 소진일 예측은 초기 데이터 부족 시 부정확할 수 있음 → 신뢰구간 안내
* Agent의 Tool 호출 경로는 결정론적 파이프라인보다 디버깅 난이도가 높음 → 필수 파이프라인(F1~F8)을 먼저 안정화한 후 Agent/Tool 연동. 필수 기능 일정에 영향을 주지 않도록 Agent/Tool 관련 코드는 별도 브랜치·모듈로 개발할 것을 권장
* 레시피 추천(F11)·최저가 비교(F15)는 스코프에서 완전히 제외됨 — Agent의 Tool은 우리 서비스 내부 데이터 조회로 한정됨
* Agent 응답 경로는 외부 API 왕복이 추가되어 5초 목표 달성이 어려울 수 있음 → 별도 목표치 설정 및 비동기 UI로 완화
* 신규 서비스 특성상 실제 사용자는 장기(90일) 데이터를 가질 수 없음 → 데모 계정에 3개월치 시드 데이터(가짜 영수증)를 미리 준비해 장기 Context가 Agent 판단에 반영되는 모습을 시연. 실제 신규 사용자에게는 가입 후 14일 미만 시 장기 패턴 분석을 노출하지 않고 안내 문구로 대체
* 구독 해지(F14)는 실제 자동 해지가 불가능함 → "해지 방법 안내 + 알림"까지로 스코프를 명확히 제한

## 10. 데모 시나리오

발표에서 Agent의 판단 과정을 증명하기 위해, 다음 순서로 4개 케이스를 보여준다.

| 순서 | Context | 결과 |
|---|---|---|
| 1 | 정상 소비 (특이 신호 없음) | 개입 안 함 |
| 2 | 배달비 증가 + 예산 사용률 낮음 | 개입 안 함 |
| 3 | 배달비 증가 + 예산 사용률 높음 (2와 일부 신호는 같지만 전체 Context가 다름) | 지출 데이터 조회 Tool 호출 → 근거 숫자와 함께 먼저 말을 건다 |
| 4 | 사용자가 챗봇에 "이번 달 얼마 썼어?"라고 질문 | 지출 데이터 조회 Tool 호출 → 실제 숫자로 답변 |

2번과 3번을 나란히 보여주는 것이 핵심이다 — 일부 신호(배달비 증가)는 같아도 전체 Context(예산 사용률)가 다르면 Agent의 판단이 달라진다는 것을 직접 증명한다. 이는 "결국 if-else 아니냐"는 질문에 대한 가장 직접적인 반증이 된다.

**사용자 화면 노출 순서**: 판단 이유 → Tool 조회 결과(실제 숫자) → 코칭 메시지. 순서대로 보여줘야 "왜 → 무엇을 근거로 → 뭐라고 말해주는지"의 스토리가 자연스럽게 이어진다.

**검증 절차**: 데모 전 동일 Context를 5~10회 반복 실행해 결과가 일관되게 나오는지 확인한다(LLM temperature를 0 또는 낮게 설정 권장).
