# GamePM Codex Workspace 기획서

## 1. 문제 정의

혼자 게임을 기획할 때도 아이디어, 설정, 변경 요청, 결정 근거, 버전 기록이 쉽게 흩어진다. AI가 바로 확정 문서를 수정하면 편하지만, 나중에 어떤 변경이 왜 들어갔는지 추적하기 어려워진다.

이 저장소는 별도 API 제품을 만들지 않고, Codex가 이 폴더의 규칙 문서를 읽고 게임 기획 보조 에이전트처럼 작업하는 구조를 목표로 한다.

## 2. 목표 사용자

### 개인 게임 기획자

- 게임 설정, 시스템, NPC, 퀘스트, 아이템, UI 문서를 Markdown으로 관리한다.
- 아이디어와 확정 설정을 분리한다.
- 변경안을 승인 큐에서 검토한 뒤 확정 문서에 반영한다.

### Codex 작업 에이전트

- 저장소의 규칙, 워크플로우, 템플릿, 스킬을 읽는다.
- 작업 전에 대상 프로젝트를 식별하고 프로젝트별 기록을 분리한다.
- 사용자 요청을 아이디어, 검색, 기획서 작성, 변경안, 승인 처리로 구분한다.
- 일반 시나리오는 `scenario_designer`, 인게임 스크립트는 `scenario_writer`,
  두 산출물의 독립 검수는 `scenario_reviewer`, 일반 기획 창작 보완은
  `design_creative_planner`에 위임한다.
- 창작 역할은 프로젝트 생성 시 미리 만들지 않는다. 사용자가 실제 창작을
  요청했을 때 분야별 프로젝트 창작 규칙의 planning-only 설정 설계를 현재
  대화에서 자동 수행한다. 에이전트가 확인 가능한 값과 보수적 기본값으로
  완성안을 제시하고, 구현 요청으로 활성화한 뒤 기존 전문 agent가 그 규칙을
  읽어 동작한다.
- 비시나리오 프로젝트 창작 규칙은 검수 정책을 반드시 정하며, 독립 검수가
  필요한 결과는 `design_creative_reviewer`가 같은 규칙과 원본을 직접 확인한다.
- 전문 에이전트 호출 전 현재 요청과 이전 사용자 결정·금지사항을
  Specialist Task Packet으로 명시하고, 전체 대화 상속 없이 정확한 전문 역할에
  전달한다.
- 서브에이전트 handoff를 검토한 뒤 Approval Queue 저장과 승인 경계를 직접
  통제한다.
- 승인 전에는 확정 문서를 수정하지 않는다.
- 승인 후에는 확정 문서, Decision Log, Version History를 함께 갱신한다.

## 3. 핵심 흐름

### 공통: 전문 에이전트 인계

1. Codex는 대상 프로젝트, canonical role, 작업 Phase와 필수 근거를 확정한다.
2. 현재 요청과 작업에 영향을 주는 이전 대화에서 사용자 사실, 선택,
   금지사항, 승인·창작 권한과 제외 범위를 빠짐없이 Task Packet에 옮긴다.
3. 필수 필드가 빠졌으면 호출하지 않고 저장소에서 확인하거나 사용자에게 묻는다.
4. 전문 `agent_type`과 `fork_turns: "none"`으로 호출하고 전체 부모 대화는
   상속하지 않는다.
5. 전문 에이전트는 Task Packet 누락 시 `blocked_missing_handoff`를 반환하며,
   메인 Codex는 반환 결과를 Packet과 대조한 뒤에만 다음 단계로 진행한다.
6. 창작 작업이면 프로젝트 창작 에이전트 ID, 규칙 기준, 경로·버전·SHA-256,
   적용 범위와 검수 정책을 Packet에 포함한다. 규칙 없음·범위 불일치·규칙
   참조 무결성 오류 상태에서는 창작 결과를 만들지 않는다.

### 공통: 프로젝트 창작 에이전트 규칙

1. 새 프로젝트와 기존 프로젝트에 규칙을 자동 생성하지 않는다.
2. 첫 창작 요청에서 정확한 분야 규칙이 없으면 대안·Draft를 만들지 않고
   planning-only 설정 설계에서 적용 범위, 실행 agent, 작성 절차, 창작 원칙,
   금지사항, 근거, 출력과 검수 정책의 완성 권장안을 제시한다.
3. 사용자의 구현 요청으로 `agents/README.md`와 독립 분야 규칙을 active
   상태로 저장한다. 규칙은 행동 설정이며 Approval Queue나 canonical design
   문서를 소유하지 않는다.
4. 기존 규칙은 사용자가 개정을 요청할 때만 planning-only 설정 설계로 바꾼다.
5. 색인의 canonical role, 경로 선택자, 대상 경로와 허용 작업으로 active
   규칙 하나를 선택하고 범위가 겹치는 규칙은 검증에서 차단한다.
6. 기존 규칙 개정 전 원문은 SHA-256이 고정된 archive snapshot으로 보존한다.
   과거 결과는 당시 규칙과 검수 상태를 유지하며 현재 규칙 재검수는 사용자가
   명시적으로 요청할 때만 수행한다.
7. 일반 시나리오와 대본은 항상 독립 검수한다. 비시나리오는 규칙마다
   `self_and_main | independent_high_risk | independent_always`를 결정한다.

### 공통: 동작 테스트 출처와 격리

1. Codex는 동작 테스트 전에 Behavior Test Manifest를 작성한다.
2. 합성 입력은 `[TEST FIXTURE: SYNTHETIC]`과
   `synthetic_test_fixture`로 표시하며 사용자 사실이나 확정 사실과 분리한다.
3. 기본 테스트는 전용 `sample-game` 픽스처를 `/tmp`에 복사해 실행한다.
4. 실제 프로젝트 구조가 필요한 경우에만 `/tmp` 임시 복사본을 만들고 원본을
   테스트 전후 비교한다.
5. 출처 누락이나 오분류는 `blocked_test_provenance`로 중단한다.
6. 결과에는 데이터 출처, 실행 환경, 원본 변경과 실제 프로젝트 채택 여부를
   명시한다.

### 3.0 프로젝트 선택과 생성

1. Codex는 `workspace/project_registry.md`에서 요청 대상 프로젝트를 확인한다.
2. 기존 프로젝트 작업은 해당 `workspace/projects/<project_slug>/` 안에서만 수행한다.
3. 새 프로젝트 요청이면 고유 슬러그와 독립된 프로젝트 README, Brief,
   Design, Ideas, Approvals, Decisions, Versions 구조를 생성한다.
4. 프로젝트가 여러 개이고 대상이 불명확하면 파일을 수정하기 전에 사용자에게 확인한다.

### 3.1 아이디어 저장

1. 사용자가 확정 반영 없이 아이디어를 말한다.
2. Codex는 `docs/workflows/temporary_idea.md`에 따라
   `workspace/projects/<project_slug>/ideas/temporary_ideas.md`에 아이디어를 기록한다.
3. 확정 문서는 수정하지 않는다.
4. 사용자가 문서화 또는 변경 제안 전환을 요청하면 관련 자료를 다시 검색해
   Approval Queue 항목으로 전환하고 원래 아이디어를 연결한다.

### 3.2 신규 기획서 작성

1. 사용자가 신규 문서 작성을 요청한다.
2. Codex는 관련 문서를 검색하고 `docs/workflows/document_structure.md`에
   따라 게임 개요, 세계관, 시나리오, 시스템, 콘텐츠, UI 또는 기술 문서로
   역할을 분류한다.
3. 역할별 템플릿을 우선 사용해 canonical owner 문서의 초안을 작성한다.
4. 일반 기획 Draft의 누락은 `design_creative_planner`의 `classify` Phase에
   위임한다. 메인 Codex가 결과를 검토해 창작 가능한 GAP을 한 번에 보여준 뒤
   창작 보완 여부를 묻는다.
5. 사용자가 허가한 정확한 GAP ID와 active 프로젝트 창작 규칙만
   `generate_options` Phase에 전달해 위험도별 2~3개 대안과 추천안을 만든다.
   규칙이 독립 검수를 요구하면 `design_creative_reviewer` 검수를 거친다.
   선택 후 원본과 규칙 버전을 재확인하고
   `incorporate_selection` Phase에서 선택안만 `CP-*`로 공개한다. 사실 정보는
   `TBD`, 수치 가설은 `provisional`로 둔다.
6. 시나리오 문서이면 active 일반 시나리오 창작 규칙을
   `scenario_designer`에 전달한다. 에이전트가 관련 자료를 읽고 원안 기반 Draft와
   별도 개선 권고를 작성한다. `scenario_reviewer`가 인과, 동기, 긴장, 정보
   공개, 선택과 분기를 독립 검수하며 필수 수정은 작성자에게 되돌린다.
7. 프로젝트 README, `design/README.md`와 개요서에는 상세 내용을 복제하지
   않고 역할, 한 문장 요약과 상대경로 링크만 제안한다.
8. 창작안 선택 후에도 확정 문서가 아닌 `pending` Approval Queue 항목으로
   다시 검토받는다.

### 3.3 기존 문서 변경

1. 사용자가 설정 변경을 요청한다.
2. Codex는 관련 확정 문서를 확인한다.
3. 충돌 가능성, 영향 범위, 누락 정보를 정리한다.
4. `design_creative_planner`가 누락을 GAP으로 분류하고, 사용자가 허가한
   `creative_fillable`과 active 프로젝트 창작 규칙에만 복수 창작 대안을
   만든다. 선택된 안은 `CP-*`와 함께
   변경 Draft에 넣되 일반 시나리오 구조와 인게임 스크립트에는 각 전용 규칙을
   우선한다.
5. 시나리오 변경이면 `scenario_designer`가 요청 Draft와 추가 구조 개선 권고를
   분리하고 `scenario_reviewer`가 검수한다. 사용자가 권고를 선택하면 원본을
   재확인해 작성자 갱신과 재검수를 거친 뒤 다시 승인받는다.
6. 변경안은 `workspace/projects/<project_slug>/approvals/approval_queue.md`에 올릴 형식으로 작성한다.
7. 요청이 여러 문서 역할에 걸치거나 기존 문서를 분리해야 하면 경로별 작업
   목록이 있는 `restructure` 승인안으로 묶고 일부만 적용하지 않는다.
8. 문서 목록·경로·역할이나 담당 범위가 바뀌면 프로젝트 README,
   `design/README.md`와 개요서 링크 갱신을 같은 승인 범위에 포함한다.

### 3.4 승인 처리

1. 사용자가 특정 승인 큐 항목을 명시적으로 승인한다.
2. Codex는 적용 직전 대상 문서의 현재 내용을 다시 확인한다.
3. 변경안을 `workspace/projects/<project_slug>/design/`에 반영한다.
4. `workspace/projects/<project_slug>/decisions/decision_log.md`와 `workspace/projects/<project_slug>/versions/version_history.md`를 갱신한다.

### 3.5 검색과 질의응답

1. 사용자가 기존 설정을 질문한다.
2. Codex는 대상 프로젝트를 결정하고 해당 프로젝트 루트의 관련 문서만 검색한다.
3. 답변에는 가능한 한 파일 경로와 근거를 포함한다.
4. 검색만 요청한 경우 문서를 수정하지 않는다.

### 3.6 인게임 스크립트 작성

1. 사용자가 시나리오를 실제 플레이용 대본으로 작성해 달라고 요청한다.
2. Codex는 active 인게임 스크립트 창작 규칙을 확인한 뒤
   `scenario_writer`에 대상 챕터의 초안 작성을 위임한다.
3. 에이전트는 프로젝트 Brief, 게임 개요, 세계관, 상위 시나리오와 기존 승인
   대본에서 프로젝트별 작가 정체성과 Writer's Brief를 구성한다.
4. 원본보다 나은 사건 순서, 공개 시점, 분기, Outcome 또는 인물 동기가 있으면
   하나의 최적안에 직접 반영해 플레이어 대본과 씬 명세를 작성한다.
5. 구체 창작은 `CW-*`, 원본 구조 변경은 `NR-*`로 이유와 영향을 공개한다.
6. Codex는 결과를 `scenario_reviewer`에 위임해 원본 충실도, 서사 품질, 씬
   데이터와 창작 공개를 독립 검수하고 필수 수정은 작가에게 되돌린다.
7. 검수 통과 후 상위 시나리오 변경, 스크립트와 링크 갱신은 하나의 `restructure` 승인
   항목으로 저장하고 승인 전에는 `design/narrative/`를 수정하지 않는다.
8. 세계관 정사나 시스템 규칙 변경은 별도 고위험 승인 항목으로 분리하고,
   의존 대본은 선행 적용과 재확인 전까지 `TBD`로 둔다.

## 4. 핵심 원칙

- 승인 전에는 확정 문서를 수정하지 않는다.
- 프로젝트별 기획과 승인·결정·버전 기록을 섞지 않는다.
- 아이디어, 변경안, 결정, 버전 기록을 분리한다.
- 게임 개요, 세계관, 시나리오, 시스템, 콘텐츠, UI와 기술 문서의 역할을
  분리하고 상세 사실의 원본 문서를 하나만 유지한다.
- 게임 개요는 전체 방향과 상위 루프, 상세 문서 링크를 제공하고 장면·설정·
  수치·데이터 상세를 누적하지 않는다.
- 출처 없는 설정은 확정 사실처럼 쓰지 않는다.
- 창작 가능한 누락은 먼저 사용자에게 허가받고 복수 대안으로 제시한다.
  선택된 기획 창작은 `CP-*`로 공개하며 선택 자체를 승인으로 보지 않는다.
- 사용자만 알 수 있는 사실은 창작하지 않고, 검증 전 수치는 `provisional`과
  검증 조건을 유지한다.
- 일반 시나리오의 개선 권고는 원안 기반 Draft와 분리하고, 사용자가 선택한
  뒤에도 갱신된 승인안을 다시 검토받는다.
- 누락된 정보는 `TBD`로 남기고 필요한 질문을 만든다.
- 전문 에이전트에는 전체 대화 대신 완성된 Task Packet을 전달하고, 누락되거나
  범위를 벗어난 handoff는 승인 초안이나 확정 변경에 사용하지 않는다.
- 테스트용 합성 문장은 사용자 제공 사실이나 프로젝트 정사로 표현하지 않고,
  전용 픽스처와 `/tmp` 실행 복사본 밖으로 승격하지 않는다.
- Codex 입력창이 실행 환경이고, 이 저장소가 규칙과 상태 저장소다.

- 독립 실행 CLI 제품
- 백엔드 서버
- 웹 UI
- 외부 도구 자동 동기화
