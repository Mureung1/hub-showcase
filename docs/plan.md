## 1. 한 문장

최신 AI 논문을 **스스로 판단해서** 골라 읽고 요약하는 에이전트를, 연구자가 웹에서 직접 부려 쓰는 서비스.

## 2. 문제

LLM 분야 논문의 생산 속도가 개인이 따라잡을 한계를 넘었다. arXiv에 하루에도 수십 편이 올라온다.
**진짜 비용은 읽는 게 아니라 "무엇을 읽을지 고르는 것"이다.**

기존 요약 서비스들은 이 문제를 풀지 못한다. 전부 요약해서 쏟아내면 목록만 길어질 뿐이다.
선별을 하더라도 **왜 골랐는지 말해주지 않으면 연구자는 그 결과를 믿지 않는다.** 놓친 게 없다는 걸 확인할 방법이 없기 때문이다.

## 3. 해법 — 그리고 왜 이게 다른가

에이전트가 논문을 고르고, **고른 이유와 버린 이유를 함께 보여준다.**

이 서비스의 차별점은 요약 품질이 아니다. 요약은 어느 LLM이든 어느 정도 한다.
차별점은 **에이전트의 판단 과정 전체가 사용자에게 열려 있다는 것**이다.

- 12편 중 4편을 골랐고, 8편은 이런 이유로 뺐다
- 이 논문은 초록으로 충분했고, 저 논문은 본문까지 읽었다
- 이 요약은 한 번에 안 나와서 스스로 다시 썼다 — 이런 점이 부족해서

**과정은 로딩 화면이 아니라 감사 기록(audit trail)이다.** 이 관점이 이 프로젝트의 전부다.
연구자가 타겟이기 때문이다. 연구자는 근거 없는 주장을 읽지 않는다.

## 4. 타겟

**AI 연구자·개발자.**

이 선택이 강제하는 것들:
- 전문 용어를 풀어쓰지 않는다 (풀어쓰면 오히려 정보가 준다)
- 원문 초록을 항상 병기한다 (요약을 검증할 수 있어야 한다)
- 기술 용어를 화면에 노출한다 (`rate_limit_exceeded`가 "일시적 오류"보다 친절하다)
- 판단 근거·제외 사유를 숨기지 않는다

**타겟이 아닌 사람:** AI를 처음 접하는 일반인. 이들을 위한 서비스라면 완전히 다르게 만들어야 한다.

## 5. 성공 기준

| 기준 | 판단 방법 |
|---|---|
| **놓치지 않는다** | 사용자가 "제외된 N편"을 열어보고 납득하는가 |
| **흐름이 보인다** | 트렌드 종합이 개별 요약의 나열이 아니라 논문 간 연결을 말하는가 |
| **믿을 수 있다** | 트렌드의 주장 → 논문 카드 → 원문까지 끊기지 않고 이어지는가 |

**실패의 정의:** 사용자가 요약만 읽고 "이거 맞나?" 하며 결국 arXiv를 직접 뒤진다면 실패다.

## 6. 범위

**만든다**

- 주제 입력 → 에이전트 실행 → 실시간 과정 표시 → 결과
- 5단계 single-agent 루프: 판단 → 도구 선택 → 요약 → 자기 검증 → 트렌드 추론
- 선별 근거 · 제외 사유 · 재시도 기록 노출
- 원문 초록 병기 + arXiv 링크
- **multi-agent 확장** — single-agent 루프가 완주된 뒤, 판단·요약·검증을 독립된 에이전트로 분리해 협업시킨다 (§10 7번)

**안 만든다** (챌린지 4주 기준)

| 제외 | 이유 |
|---|---|
| 로그인 · 북마크 · 개인화 | DB·인증이 붙는 순간 4주로 불가능 |
| arXiv 외 소스 (뉴스·HN·Papers with Code) | arXiv만으로 핵심 가치 증명 가능 |
| 검색 · 필터 · 카테고리 분류 | 에이전트가 판단하는 게 이 서비스의 요지. 필터는 그 반대 |
| 매일 자동 배치 | §8 참조. 이제 사용자가 요청할 때 돈다 |

## 7. 핵심 결정과 이유

| 결정 | 대안 | 왜 이걸 골랐나 |
|---|---|---|
| **실시간 실행** | 미리 돌려놓고 결과만 보여주기 | 챌린지 목표가 "에이전트를 활용한 웹 서비스". 미리 돌리면 사용자와 에이전트가 만나지 않는다 |
| **SSE 스트리밍** | 다 끝나고 한 번에 응답 | 3분간 빈 화면은 이탈. 그리고 과정 자체가 이 서비스의 가치다 |
| **단일 타임라인** | 좌우 분할 / 챗봇 | 초반 30초간 결과가 없어 반쪽이 빈다. 그리고 실제로 일어나는 일이 하나의 시간 흐름이다 |
| **plain HTML/JS** | React | 4주. 배울 것을 줄이는 게 전략 |
| **single-agent를 먼저 완주** | 처음부터 multi-agent | multi-agent는 single-agent 여러 개가 협업하는 것. single-agent가 안 되면 multi-agent도 안 된다. 목표에 포함하되 순서는 지킨다 (§10) |
| **과정 로그 유지** | 완료 시 정리 | 되짚을 수 없으면 신뢰할 수 없다 |

## 8. 왜 "매일 자동 배치" 방식이 아닌가

처음 구상은 정적 사이트 + 자동화 스케줄러로 매일 논문을 수집·요약해 정적 페이지에 쌓는 방식이었다.
서버 비용 0원이라는 장점이 있어 다시 떠오르기 쉬운 방향이라, 버린 이유를 남겨둔다.

**그 방식은 에이전트가 아니다.** LLM이 "요약 함수" 하나로만 쓰인다. 정해진 순서대로
수집 → 요약 → 렌더링하는 단방향 파이프라인이다. 스스로 판단하지도, 도구를 고르지도, 결과를 검증하지도 않는다.

**그 방식은 웹 서비스가 아니다.** 사용자는 미리 만들어진 결과를 구경만 한다. 에이전트와 상호작용하지 않는다.

이 프로젝트의 목표는 "매일 뉴스레터를 자동 발송하는 것"이 아니라
"사용자가 요청한 순간 스스로 판단하며 일하는 에이전트를 웹에서 부려 쓰는 것"이다.
비용이 들더라도, 사용자의 요청을 받아 그 자리에서 실행되는 구조를 택한다.

## 9. 위험

| 위험 | 실제 발생 확률 | 대응 |
|---|---|---|
| **LLM 무료 티어 한도 초과** | **높음.** 논문 4편에 LLM 호출 20회+. 개발 중 하루 한도가 금방 참 | 개발 중엔 논문 2~3편으로 제한. 한도 걸리면 유료 전환(월 수천 원) |
| **판단 품질이 나쁨** | 중. 프롬프트가 전부를 좌우 | `prompts.md`에 버전 기록. 반복 개선 |
| **트렌드가 뻔한 소리** | 중. "여러 논문이 LLM을 다룬다" 같은 무의미한 종합 | 논문 칩으로 근거를 강제. 근거를 못 대면 그 흐름은 버린다 |

## 10. 4주 안에 반드시 되어야 하는 것

우선순위 순. 위에서부터 끊어서 낸다.

1. 에이전트가 터미널에서 5단계를 완주한다
2. 웹에서 주제를 넣으면 결과가 나온다 (동기 방식이어도 됨)
3. SSE로 과정이 실시간으로 흐른다
4. 판단 근거 · 제외 사유가 화면에 보인다
5. 부분 실패 · 결과 없음 · 전체 실패가 각각 다르게 처리된다
6. 트렌드 종합이 논문 칩으로 근거와 연결된다
7. **multi-agent 확장** — 1~6번이 안정된 뒤 시도. 판단·요약·검증을 독립된 에이전트로 분리해
   메시지를 주고받게 한다. 순서를 건너뛰지 않는다: 1~6번 없이 7번은 만들 수 없다.

**1~3번까지가 최소 데모.** 4~6번이 이 프로젝트를 다른 요약 서비스와 구분한다.
**7번은 이 프로젝트의 정식 목표다** — 다만 1~6번이라는 토대 위에서만 의미가 있다.
