# 기획서 v3 - 미리캣 (이동 경로 상시 감시 에이전트)

미어캣 무리는 보초를 세운다. 한 마리가 망을 보는 동안 나머지는 각자 일을 하고, 위험이 보일 때만 경보를 낸다. 미리캣은 내 출근길의 보초다.

## 문제

축제, 공사, 사고, 행사로 버스가 우회하거나 도로가 통제되면 지자체나 버스조합 게시판에 공지가 올라온다. 근데 공지는 한 번 올라오고 끝이다. 다시 노출되지 않는다. 공지가 올라오는 시점과 그 정보가 필요한 시점(이동 직전)이 어긋나 있고, 소스도 여러 게시판에 흩어져 있어서 사람이 매번 챙겨보는 건 비현실적이다. 그래서 공지가 분명히 있었는데도 예고 없이 지연을 당하게 된다.

문제를 쪼개면 두 개다.

- 수집: 서울 밖에는 이런 정보를 모아주는 시스템 자체가 없다. 기관별 게시판에 흩어져 있음
- 전달: 모아놔도(서울 TOPIS) 결국 사용자가 들어가서 봐야 하고, 통제 목록 수십 건 중에 내 경로에 걸리는 걸 골라내는 것도 사용자 몫이다. 통제 목록은 내 경로/시간대랑 결합돼야 의미 있는 정보가 된다

실제 사례 (직접 확인함, 2026년):

- 갑천도시고속도로 원촌육교 긴급 통제 (3.30~4.3): 지반침하로 전면 통제, B1 우회 + 오정농수산시장 정류장 미정차. 대전시 공지로만 안내됨. 이 길로 출근하던 사람은 알 방법이 사실상 없었음
- 대덕구 문평동 화재로 시내버스 우회 (3.21, 버스조합 공지)
- 시간표 변경 공지는 버스조합/세종교통공사에 거의 매달 올라옴
- 0시축제 때는 29개 노선 365대가 우회했음 (2023~2025. 올해부터 폐지됐지만 빵축제 확대 등 이런 유형의 공지는 계속 나옴. 특정 축제가 아니라 공지 패턴 자체를 다루는 거라 상관없음)
- 야구 홈경기(볼파크, 대전역 옆) 연 70회+, 콘서트 등. 통제 공지는 없지만 일정 자체는 공개된 사실이고 주변 경로에 반복적으로 영향을 줌. 공식 공지가 드물지만 임팩트 큰 쪽이면 이쪽은 자주 있고 중간 임팩트라 서로 보완됨

## 뭘 만드나

고정 경로를 등록해두면 에이전트가 매일 대신 확인하고 결과를 보내주는 서비스.

- 이상 없는 날: "오늘 출근 경로 이상 없음 · 확인: 대전시 공지, 버스조합, KBO (06:30)" 같은 한 줄 보고
- 영향이 있는 날: 경보. 뭐가, 언제까지, 출처 어디인지 + 리포트 링크

사용자가 검색하러 오는 서비스가 아니다(Pull → Push). 확인하는 주체가 사용자에서 에이전트로 넘어간다. 이런 공지에 걸리는 날은 드물어서 사용자가 확인하러 오는 구조는 무조건 실패한다. 확인 비용이 0이어야 드물게 오는 경보 한 번이 가치가 된다.

이상 없는 날에도 한 줄을 보내는 이유: 몇 주간 아무 소식이 없으면 "이거 돌아가고는 있나?"가 되고, "못 찾은 건지 진짜 없는 건지"도 구분이 안 된다. 확인한 소스랑 시각을 같이 보내면 "이상 없음"이 그냥 주장이 아니라 검증 가능한 보고가 된다. 보초가 서 있다는 증거이기도 하고. 알림 수준은 나중에 선택 가능하게(매일/주간 요약/영향 시만), MVP에서는 매일 고정.

지도 앱이랑 경쟁하는 게 아니다. 지도는 "어떻게 가지?"에 답하고 이건 "내 경로에 무슨 일 생겼나?"에 답한다.

## 경쟁 서비스

| 서비스 | 하는 것 | 안 되는 것 |
|--------|---------|----------|
| 서울 TOPIS | 통제/우회 공지 통합 게시, 지도에 통제구간 표시 | 서울만 있음. Pull이라 들어가서 봐야 함(존재 자체를 모르는 사람이 대부분). 개인 경로 개념 없음. → 경쟁자가 아니라 서울 확장하면 수집 소스가 됨 |
| 카카오맵 | 이벤트 레이어 (축제/공연 위치) | 레이어 직접 켜서 보는 능동 조회. 교통 영향이랑 연결 안 됨 |
| 네이버지도 | 실시간 교통정보, 승하차 알림 | 하루짜리 임시 우회/통제 공지를 길찾기에 반영하는 기능 확인 안 됨 |

공지 수집(TOPIS, 서울만)이랑 지도/교통정보(카카오, 네이버)는 각각 있는데, 흩어진 공지를 모아서 개인 경로에 매칭해 먼저 알려주는 건 없다.

## 여기까지 온 과정

| | 형태 | 왜 바꿨나 |
|--|------|----------|
| v0 | 경로 등록 → 혼잡도 예측 알림 | 예측은 정확도를 보장할 수 없고 틀리면 신뢰가 무너짐 |
| v1 | 길찾기 검색 → 공지 기반 경로 재정렬 (지도 앱 형태) | 지도 앱 기능 확장으로 보임. 검색형은 대부분 "별 일 없음"이라 사용자가 떠남. 그리고 배치 크롤링은 에이전트가 아님 |
| v2 | 고정 경로 상시 감시 + Push | 확인 주체를 에이전트로 이전. v0의 예측 문제는 사실 기반 브리핑으로, 수동 등록 문제는 최초 1회 등록으로 해결 |
| v3 | v2 + 스택 교체 (LangGraph/Langfuse/평가셋) | 제품은 유지하고 구현을 프로덕션 에이전트 스택으로. 아래 "왜 이 스택" 참고 |

원칙: 예측하지 않는다. 이미 공지된 사실을 사람 대신 찾아서 경로 맥락과 결합해 전달한다.

## 왜 이 스택인가

이 프로젝트에서 가져가려는 건 기능 목록이 아니라 "에이전트를 운영 시스템으로 만들어본 경험"이다. BUA(파인튜닝, 벤치마크, 논문)가 연구 쪽이었으니 이번엔 반대쪽 — 매일 돌고, 실패를 처리하고, 품질을 계속 측정하는 시스템. 그래서 세 가지를 스택에 박는다.

- LangGraph: Planner → Scout → Analyst → Reporter를 손으로 짠 함수 호출이 아니라 그래프로 구성. 상태 관리, 조건 분기, 자기검증 실패 시 재시도 루프를 그래프 엣지로 표현
- Langfuse (셀프호스트): 모든 LLM 호출과 에이전트 단계를 트레이싱. 리포트의 trace 뷰어도 이 데이터를 쓰면 됨. 에이전트 관측성은 안 해본 분야고 지금 실무에서 필수로 굳어지는 중
- 평가 하네스: 검증2에서 모은 공지 10건을 일회성 테스트로 버리지 않고 ground truth 라벨을 붙인 평가셋으로 저장. 프롬프트나 모델을 바꿀 때마다 추출 정확도 회귀 테스트가 자동으로 돎. "정답 데이터 없이 품질을 어떻게 관리하나"에 대한 우리 답이기도 함

## 사용 흐름

1. 경로 등록 (1회): 출발지/도착지/시간대 입력 → 경로 API로 후보 조회해서 지도에 띄움 → 평소 다니는 경로 선택. 이때 두 점이 아니라 경로 객체(경유 도로, 이용 노선, 경유 정류장, 좌표열)를 저장. 안 고른 후보도 저장해둠 (나중에 대안 제시용)
2. 에이전트가 매일 조사: 경로 구성요소 보고 관할 기관 파악 → 게시판이랑 주변 대형시설 일정 탐색
3. 이상 없으면 아침에 디스코드로 확인 보고 한 줄
4. 영향 발견하면 경보 메시지: "출근 경로의 갑천도시고속도로 구간이 긴급보수로 전면 통제됩니다 (3/30~4/3, 출처: 대전시 공지)"
5. 링크 열면 리포트: 원문 링크, 영향 구간 지도, 대안 경로, 조사 과정(trace)

## 핵심 기능

### A. 조사 에이전트 (LangGraph)

경로가 주어지면 조사 계획을 스스로 세운다. 노드 구성:

- Planner: 경로 구성요소 보고 어떤 소스를 볼지 결정
- Scout: 게시판 탐색 + 공지 수집 (BUA 브라우저 에이전트 패턴 재사용) + LLM 구조화 추출 (이벤트명/위치/기간/영향범위)
- Verifier: 추출 결과를 원문과 대조. 뽑은 노선 번호가 원문에 진짜 있는지, 기간이 맞는지. 실패하면 Scout로 되돌아가 재추출, 재실패 시 신뢰도 낮음 표시 (그래프의 조건 분기 엣지)
- Analyst: 4단계 매칭 + 알림 판단
- Reporter: 보고/경보/리포트 생성

전 과정이 Langfuse에 트레이스로 남고, 리포트의 조사 과정 화면이 이걸 보여준다.

수집 대상은 두 층:

- Tier 1 - 공식 통제/우회 공지 (영향 확정): 시 공지, 버스조합, 행사 주최측 게시판. 비정형이라 LLM 추출
- Tier 2 - 인파 이벤트 일정 (영향 가능성): KBO 등 스포츠 일정(정형 데이터라 쉬움), 콘서트. "혼잡할 것"이라고 안 하고 "일정이 있고 시공간이 겹친다"까지만 말함. 무예측 원칙 유지

소스 확인 기록: 조사할 때마다 확인한 소스 목록 + 시각을 기록. 확인 보고랑 리포트에 노출. 시스템이 약속하는 건 "모든 정보"가 아니라 "이 소스들을 확인했다"는 사실.

### B. 매칭 + 알림 판단

추출된 정보를 경로 객체랑 4단계로 매칭:

1. 노선: 공지의 "B1 우회" ↔ 내 이용 노선 목록. 문자열 대조라 확실함
2. 정류장: 미정차/이설 정류장 ↔ 내 경유 정류장
3. 도로명: "갑천도시고속도로 통제" ↔ 내 경유 도로. 자차용
4. 반경 (폴백): 노선/도로 명시 안 된 정보("OO공원 일대 행사", 이벤트 일정)는 지오코딩해서 경로 좌표열과 거리 + 기간 겹침으로 스코어링

교통 공지 대부분은 노선이나 도로명을 명시해서 1~3에서 결정론적으로 판정되고, 반경 계산은 애매한 것들 안전망.

알림 정책 (알림 남발 방지가 목표):

- 경보: Tier 1은 매칭되면 바로. Tier 2는 규모+근접도+시간 겹침 다 만족할 때만. 반복 이벤트(홈경기)는 유형 음소거 옵션 — 볼파크 옆 통근자한테 매 경기 알림 가면 재난문자 꼴 남
- 확인 보고: 영향 없는 날 한 줄. 수준 선택은 매일(기본)/주간/영향 시만

### C. 브리핑 리포트

결과물은 알림 메시지가 아니라 리포트다. 메시지는 트리거.

- 사실: 수집된 공지/일정 그대로 + 출처 링크
- 판단: 규칙 기반 매칭 결과 (결정론적, 예측 아님)
- 대안: 등록 때 저장해둔 미선택 후보 경로에 같은 매칭을 다시 돌려서 "후보 B는 영향권 밖 (B1 안 탐, 통제구간 안 지남)" 식으로만 제시. 매칭 결과의 부정형이라 이것도 예측이 아님. v1의 경로 재정렬이 여기로 이동해서 부활한 셈
- 문장: LLM은 위 내용 조립만. 사실에 없는 말(혼잡 예측 등) 생성 금지를 프롬프트로 강제

리포트 화면: 요약 한 줄 + 기간 + 출처 / 지도(내 경로 + 통제구간 강조 + 이벤트 반경 + 대안 점선) / 대안 섹션 / 조사 trace (Langfuse 데이터 기반, 접이식) / 원문 링크. 경보 메시지는 디스코드 embed 카드로 (문제/기간/출처/대안 유무/리포트 버튼), 확인 보고는 평문 한 줄로 — 색이랑 형태로 무게 차이가 보이게.

## 아키텍처

```
[등록 시 1회] 출발지/도착지 입력 → 경로 API → 후보 선택
             → 경로 객체 저장 {경유 도로, 이용 노선, 경유 정류장, 좌표열, 시간대}

┌─────────────────────────────────────────────┐
│ 서버                                          │
│  스케줄러 → LangGraph 그래프                   │
│   Planner → Scout ⇄ Verifier → Analyst        │
│   → Reporter                                  │
│  전 단계 Langfuse 트레이싱                      │
│  평가 하네스: 공지 평가셋으로 추출 회귀 테스트     │
└──────────────┬──────────────────────────────┘
               │ 경보 or 매일 확인 보고
      ┌────────┴────────┐
      ▼                 ▼
┌──────────┐   ┌────────────────────────┐
│ 디스코드   │   │ 웹                      │
│ 경보 embed │──▶│ 경로 등록 (후보 선택)     │
│ + 확인보고 │링크│ 리포트 (요약+지도+대안     │
│ 한 줄     │   │ +trace+원문)            │
└──────────┘   └────────────────────────┘
```

- Frontend: React + Vite
- Backend: FastAPI + APScheduler
- 에이전트: LangGraph (Planner/Scout/Verifier/Analyst/Reporter 노드)
- 관측성: Langfuse 셀프호스트 (docker). trace 뷰어 데이터 소스 겸용
- 평가: 공지 평가셋 (ground truth 라벨) + 추출 정확도 회귀 스크립트
- 경로/지오코딩: 네이버지도 API (자차 Directions은 도로명 포함, 지도는 등록 화면이랑 리포트 안에서만 씀)
- 대중교통 경로: ODsay (노선번호/정류장 목록. 검증3에서 확인함)
- 알림: 디스코드 웹훅 (MVP. 몇 줄이면 됨). 메일/텔레그램은 확장
- 수집정보 스키마: 원문 URL / 이벤트명 / Tier / 위치 / 기간 / 영향 노선·구간·정류장 / 규모 / 출처
- 경로 객체 스키마: 좌표열 / 경유 도로 / 이용 노선 / 경유 정류장 / 시간대

웹의 역할: 알림 받는 곳이 아니라 등록 + 근거 열람실. 알림은 한 줄이고 "왜?"에 대한 답(리포트, trace, 원문)이 웹에 있다. 자주 안 들어가는 게 정상이다. 들어갈 필요가 없게 만드는 게 목표니까.

## 데모 시나리오

1. 메인 (Tier 1): 갑천도시고속도로 경유 출근 경로 등록 → 첫날 "이상 없음" 확인 보고를 먼저 보여줌 → 원촌육교 통제 공지(실제 3월 공지 원문)를 주입 → LangGraph 조사 과정이 웹에 실시간으로 흐름 (Verifier 통과 포함) → 디스코드에 경보 embed 도착 → 리포트 (지도에 통제구간 + "후보 B 영향권 밖" + trace). 확인 보고랑 경보의 무게 차이가 대비되고, 클라이맥스는 리포트 화면
2. 보조 (Tier 2): 대전역 인근 경로 등록 → 당일 한화 홈경기 감지 → "이동 시간대에 경로 인근에서 경기 시작 (18:30, 출처: KBO)" 알림. 실데이터라 주입 없이 라이브로 돔. 시즌 중이라 데모 당일 실제로 동작하는 게 포인트

## 스코프

MVP:
1. 경로 등록 (입력 → 후보 선택 → 경로 객체)
2. LangGraph 조사 그래프 (Planner/Scout/Verifier/Analyst/Reporter) + Langfuse 트레이싱
3. 공지 평가셋 + 추출 회귀 스크립트
4. KBO 일정 연동 (Tier 2, 정형 데이터라 쉬움)
5. 4단계 매칭 + 알림 판단
6. 디스코드: 경보 embed + 매일 확인 보고
7. 리포트 (요약 + 지도 + 대안 + trace + 원문)

확장 (여유 되면, 3주차 이후):
- 알림 수준 설정 UI (MVP는 매일 고정)
- 콘서트/공연 일정 (예매처 크롤링. 팝업스토어는 소스가 SNS라 이번엔 제외)
- 구글 캘린더 연동 (위치 있는 일정만. "회식"처럼 위치 추론 안 되는 건 개입 안 함. 되물으면 확인 비용을 사용자한테 떠넘기는 거라)
- 출발 1시간 전 재조사 1회
- 메일/텔레그램 채널

## 확장 가능성

고정 경로 감시 모델은 이동이 곧 비용인 쪽(물류 배송 권역, 통근 셔틀, 학원차)에 그대로 이식됨. 그리고 에이전트가 쌓는 구조화 공지 데이터는 지금 어디에도 없는 DB라 그 자체로 가치가 생김. 서울 확장하면 TOPIS가 수집 소스로 들어옴.
