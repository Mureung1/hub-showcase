# [기획서] 대학생 맞춤형 올인원 정보 큐레이션 및 스케줄링 대시보드

**부제: 개인화된 프로필 검증 및 유휴 시간 분석 기반 정보 추천 플랫폼**

## 1. 배경 및 문제 정의 (Problem Statement)

- **정보의 극심한 파편화:** 교내 공지사항, 대외활동 정보, 정부/지자체 청년 정책 지원금, 각종 공모전 정보가 수십 개의 독립된 채널로 흩어져 있어 학생들이 기회를 탐색하는 데 소모하는 인지적 비용과 탐색 비용이 지나치게 큼.
- **복잡한 자격 요건 파악의 한계:** 대부분의 공고는 학년, 전공, 거주지, 소득 분위 등 복잡한 제한 요건을 포함하고 있음. 학생들이 본인이 실제 수혜 대상인지 텍스트를 일일이 분석하다가 지쳐 중도에 포기하는 사례가 빈번함.
- **물리적 스케줄링의 부재:** 유익한 공모전이나 대외활동을 발견하더라도, 본인의 학업 일정(시험 기간, 과제 마감) 및 개인 일정(아르바이트 등)과 겹치는지 직관적으로 매칭하기 어려워 지원을 망설이거나 팀 빌딩 후 중도 하차하는 문제가 발생함.
- **행동 유도 실패 (정보 포기):** 이러한 탐색 피로감이 누적되면서 대다수 대학생이 유용한 혜택과 스펙 업 기회가 존재함에도 불구하고 "찾아볼 생각조차 안 하는" 정보 무기력 상태에 빠지게 됨.



## 2. 솔루션 개요 (Solution Overview)

> **"프로필 설정 한 번으로 내 일정과 요건에 딱 맞는 기회만 정밀 필터링하여 제공하는 TypeScript 기반 맞춤형 스마트 대시보드"**

사용자가 최초 1회 본인의 세부 프로필(전공, 학년, 거주지, 소득 분위, 관심사 등)을 입력하면 시스템이 수집된 공고의 자격 요건을 분석하여 지원 가능한 공고만 초개인화하여 필터링합니다. 동시에 유저의 캘린더 일정을 실시간으로 분석하여 학업 스케줄 상 실제로 수행 가능한 여유 기간(유휴 시간)이 확보된 활동을 우선순위로 제안하고 일정을 관리해 주는 대시보드 기반 올인원 웹 서비스입니다.

## 3. 핵심 기능 (Key Features)



### ① 유저 프로필 기반 초개인화 필터링 (Personalized Filtering)

- **입력 데이터 세분화:** 학과/전공, 학년, 현재 거주지 및 연고지(예: 경남 진주시), 관심 분야 태그, 소득 분위 정보 수집.
- **자동 조건 매칭 메커니즘:** 크롤링된 공고 텍스트 내 자격 제한 조건(예: "이공계열 한정", "경상남도 거주 대학생 대상")을 파싱하여, 유저의 프로필과 부합하여 즉시 '지원 가능한' 공고만 1차 선별하여 대시보드에 노출.



### ② 일정 연동형 스마트 추천 시스템 (Calendar-Aware Recommendation)

- **개인 맞춤형 캘린더 기능:** 유저가 대시보드 내 내장 캘린더에 학기 일정, 중간·기말고사 기간, 자격증 시험, 고정 아르바이트 시간 등 필수 개인 일정을 등록.
- **데드라인 및 유휴 시간 분석:** 공모전/대외활동의 실제 수행 기간 및 접수 마감일이 유저가 등록한 고부하 일정(예: 시험 기간)과 중첩되는지 타임라인 상에서 매칭 분석.
- **컨텍스트 기반 핏(Fit) 제안:** *"이 공모전은 시험 기간 일주일 전에 마감되므로 도전하기 이상적입니다!"* 또는 *"해당 활동 기간 중 아르바이트 시간을 제외하고 주당 약 12시간의 여유 스케줄이 확인되어 추천합니다"* 등 구체적인 스케줄 데이터 근거를 기반으로 행동을 유도.



### ③ 올인원 카테고리 대시보드 (Unified Dashboard UI)

- **4대 영역 통합 뷰:** 대외활동 / 공모전 / 정책 및 지원금 / 교내 행사 등 파편화된 영역을 단일 대시보드 내 탭 및 그리드 카드뷰 형태로 시각화.
- **관심 활동 스크랩 및 일정 자동 동기화:** 유저가 관심 공고를 스크랩하면 해당 공고의 접수 시작일, 마감일, 대외활동 수행 기간이 내부 캘린더 타임라인에 자동으로 등록되며 커스텀 D-Day 푸시 알림 제공.



## 4. 전체 기술 스택

**Frontend**

```
React 18 + TypeScript
Vite (빌드 도구)
Tailwind CSS + shadcn/ui (UI 컴포넌트)
Zustand (전역 상태관리 — 유저 프로필, 캘린더 상태)
React Hook Form + Zod (폼 + 밸리데이션)
React Query (TanStack Query) — 서버 상태 캐싱/동기화
FullCalendar.js — 캘린더 UI
React Router — 라우팅
```

**Backend**

```
Node.js + Express + TypeScript
Prisma (ORM) — PostgreSQL 스키마 관리 및 타입 안전성
Zod — 백엔드 요청 밸리데이션 (프론트와 스키마 공유 가능)
JWT — 인증
node-cron — 크롤링 스케줄링
```

**Database**

```
PostgreSQL (Supabase 또는 Railway 등에서 호스팅)
```

**Data Collection**

```
Python + BeautifulSoup / Playwright (동적 페이지 대응)
스크래핑 결과는 API를 통해 Node 백엔드로 전달, 또는 DB 직접 적재
```

**배포/인프라**

```
Frontend: Vercel
Backend: Railway
DB: Supabase (PostgreSQL)
```



## 5. 구현 순서 (Implementation Sequence)

> **핵심 원칙:** 카테고리 하나(공모전/대외활동)로 크롤링 → DB → 필터링 → 화면 → 캘린더까지 **세로로 완전히 뚫은 뒤**, 그 다음 정책/지원금 등으로 **가로로 확장**한다. 이렇게 하면 일정이 부족해도 발표에서 보여줄 "완결된 스토리" 하나는 확실히 확보된다.



### 1단계 — 크롤링 대상 사전 조사 (선행 필수)

가장 먼저 해야 할 일은 **어떤 사이트가 실제로 크롤링 가능한지 확인**하는 것이다.

- robots.txt·이용약관에서 크롤링 허용 여부를 확인하지 않으면 이후 IP 차단이나 법적 문제로 파이프라인 자체가 무너질 수 있음
- 정적 HTML인지 JS 렌더링(SPA)인지에 따라 BeautifulSoup만으로 충분할지, Playwright가 필요할지 개발 공수가 크게 달라짐
- 실제 공고 페이지 몇 개를 미리 뜯어봐야 "자격 요건이 어떤 문장 패턴으로 표현되는지" 파악할 수 있고, 이는 이후 파싱 로직 설계의 기반이 됨

> ⚠️ 이 단계를 건너뛰고 스키마부터 설계하면, 이후 "로그인 후에만 보이는 정보였다" 혹은 "사이트 구조가 매번 바뀐다" 같은 문제를 뒤늦게 발견해 스키마를 갈아엎어야 하는 상황이 발생할 수 있음.



### 2단계 — 데이터 모델 설계 (크롤링 조사 결과 반영)

1단계에서 확인한 실제 데이터 구조를 바탕으로 Prisma 스키마를 설계한다.

- 조사 없이 스키마부터 짜면 "이 필드가 빠졌네" 하는 뒤늦은 리팩토링이 발생
- 공모전/대외활동 카테고리부터 우선 스키마화하고, 정책·지원금 관련 필드는 나중에 확장 가능하도록 여지만 남겨둠



### 3단계 — 크롤러 구현 + 시드 데이터 확보

공모전/대외활동 카테고리 크롤러를 완성해 실제 데이터를 DB에 채운다.

- 프론트엔드는 실제 데이터가 있어야 UI 완성도를 제대로 검증할 수 있음 (더미 데이터로 만들면 실데이터 연동 시 레이아웃이 깨지는 경우가 흔함)
- 자격 요건 파싱(정규식/규칙 기반) 로직도 이 단계에서 함께 검증



### 4단계 — 유저 프로필 + 인증

- 프로필 데이터가 있어야 "필터링"이라는 핵심 로직을 테스트할 수 있으므로, 크롤링 데이터 확보 직후 배치
- Supabase Auth로 빠르게 처리해 개발 시간 절약



### 5단계 — 프로필 기반 필터링 로직 + 대시보드 카드뷰

- 실데이터와 실프로필이 준비된 상태에서 "조건에 맞는 공고만 노출" 로직을 구현
- 이 시점에 **하나의 카테고리로 크롤링 → DB → 필터링 → 화면**까지 파이프라인이 처음부터 끝까지 살아있게 됨
- 여기서 구조적 결함이 있다면 카테고리를 확장하기 전에 미리 발견하고 바로잡을 수 있음



### 6단계 — 캘린더 연동(FullCalendar) + 개인 일정 등록

- 이미 검증된 공고 데이터가 있으므로 "마감일 자동 등록" 같은 연동 기능을 바로 테스트 가능



### 7단계 — 스마트 매칭 로직 (유휴 시간 분석)

- 핵심 차별화 기능이지만, 전제 조건(공고 데이터 + 유저 캘린더)이 모두 갖춰진 뒤에 붙여야 로직 검증이 정확함
- 처음엔 규칙 기반으로 단순하게 시작 (예: "마감일이 시험 기간과 겹치지 않으면 우선순위 +1") — 초기부터 복잡한 알고리즘을 시도하면 디버깅 시간이 초과될 위험이 큼



### 8단계 — 스크랩 + D-Day 알림

- 지금까지 구현한 기능들의 "완성"을 보여주는 마무리 기능이라 뒤로 배치



### 9단계 — 정책/지원금 카테고리 확장 (시간 여유 시)

- 이 시점엔 이미 파이프라인 구조(크롤러 → 파싱 → 필터링 → UI)가 검증되어 있어, 새 카테고리 추가는 "복붙 + 파싱 규칙 변경" 수준의 작업이라 상대적으로 빠름
- 시간이 부족하면 이 단계는 생략하고, "구조상 확장 가능하도록 설계했다"는 점을 발표에서 강조하면 됨 (실제 구현 없이도 설계 사고력 어필 가능)

## 6. 개인정보 및 법적 고려사항 (Privacy & Legal Considerations)



### 민감정보 처리 방침

- 수집 항목 중 소득 분위, 거주지는 민감도가 높은 정보로 분류하고 별도 표시.
- 최초 프로필 입력 화면에 개인정보 수집·이용 동의 체크박스 배치 (수집 목적: 자격 요건 매칭, 보유 기간: 회원 탈퇴 시 삭제 등 최소한의 고지 문구 포함).
- 포트폴리오/데모 목적 서비스이므로 실제 운영 수준의 개인정보처리방침 전문까지는 작성하지 않되, "왜 이 정보를 수집하는지, 어떻게 삭제할 수 있는지"는 UI 상에 명시 — 실서비스였다면 법적 검토가 필요한 영역임을 인지하고 있다는 점을 발표에서 언급.
- 소득 분위 등 민감정보는 DB 저장 시 필터링 연산에만 쓰이는 파생값(예: 등급 코드)으로 최소화하여 저장하고, 원본 증빙 자료(소득 증명서 등)는 애초에 수집하지 않는다.



### 크롤링 데이터의 저작권 문제

- 공고 원문 전체를 그대로 복제하여 게시하지 않는다. 제목, 핵심 자격 요건, 마감일 등 사실 정보(저작권 보호 대상이 아닌 정보)만 파싱하여 표출하고, 상세 내용은 원문 링크로 연결한다.
- 이는 법적 리스크 최소화뿐 아니라, "우리는 정보 큐레이션 서비스이지 콘텐츠 복제 서비스가 아니다"라는 서비스 정체성과도 부합.
