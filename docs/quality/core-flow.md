# 핵심 플로우 QA — 관심사 선택

온보딩의 관심사 선택 플로우를 **같은 순서로 반복 확인**한다. 순서를 바꾸면 재현이 안 된다.

## 사전 조건

- 백엔드 실행 중 (`cd backend && uv run fastapi dev app/main.py`)
- 프론트 실행 중 (`cd frontend && npm run dev`)
- `interests` 21건 존재 (`active` 19 + `curated_only` 2)

### 익명 세션 A / B 준비

RLS 경계를 확인하려면 **서로 다른 익명 사용자 두 명**이 필요하다. 혼자서는 격리를 증명할 수 없다. 자기 데이터가 보이는 것은 RLS가 꺼져 있어도 통과한다.

**세션은 브라우저 저장소(`localStorage`)에 저장된다.** 저장소가 같으면 같은 사용자다.

| 방법 | 결과 |
| --- | --- |
| **일반 창 + 시크릿 창** | 저장소가 분리된다. **이 방법을 쓴다** |
| 시크릿 창 두 개 | **저장소를 공유한다. 같은 사용자가 된다** |

**두 창의 UUID가 실제로 다른지 반드시 먼저 확인한다.** 이 확인을 건너뛰면, 사실은 같은 사용자인데 "차단됐다"는 잘못된 결론이 나온다.

각 창의 콘솔에서:

```js
(await supabase.auth.getSession()).data.session.user.id
```

**두 UUID를 기록해둔다.** 6번 정리에서 이것만 삭제한다.

```
A = ________________________________
B = ________________________________
```

## 1. 관심사 목록 표시

**실행** — 온보딩 화면 진입

**기대 결과**

- **처음에는 `displayOrder` 1~10, 10개만 표시된다** (`db-schema.md`의 `display_order` 설계 의도)
- 순서가 `displayOrder` 오름차순이다 (AI → IT·개발 → 커리어·취업 → …)
- `hidden`, `preparing` 관심사는 **응답에 아예 오지 않는다.** 백엔드가 거른다
- 아무것도 선택되지 않은 상태로 시작한다
- 다음 버튼이 비활성 상태다

**실행** — "더보기" 클릭

**기대 결과** — 나머지 11개가 이어서 표시되어 총 21개가 된다. 더보기 버튼은 사라진다.

**실패 신호**

| 증상 | 원인 |
| --- | --- |
| 목록이 비어 있음 | 백엔드 미실행, 또는 Vite 프록시 미적용 (`/api` 호출이 5173으로 감) |
| 처음부터 21개가 다 보임 | 초기 노출 개수 제한 누락 |
| 순서가 뒤죽박죽 | `.order("display_order")` 누락 |
| `hidden`/`preparing` 항목이 응답에 있음 | 백엔드 필터 누락. **프론트에서 숨겨도 네트워크 탭에 그대로 보인다** |
| 콘솔에 `display_order is undefined` | camelCase 변환 확인 (`displayOrder`여야 함) |

## 2. 선택과 해제 (최대 3개)

**실행** — 관심사 3개를 선택 → 그중 1개를 다시 눌러 해제 → 다른 1개 선택

**기대 결과**

- 선택된 항목에 선택 표시(체크 아이콘 + 반전 배경)가 남는다
- 다시 누르면 해제된다
- 선택 개수가 화면에 반영된다 (`2 / 3 선택`)
- 선택 개수가 0이면 다음 버튼이 비활성

**실행 (한도 도달)** — 3개를 고른 뒤 **선택하지 않은 태그**를 누른다

**기대 결과**

- **미선택 태그가 비활성 상태로 보인다.** 눌러도 선택되지 않는다
- **왜 못 고르는지 안내가 보인다** (`3 / 3 선택 · 더 고르려면 하나를 해제하세요`)
- **선택된 태그는 여전히 눌러서 해제할 수 있다.** 3개를 채운 뒤 아무것도 못 바꾸면 안 된다

**실패 신호**

| 증상 | 원인 |
| --- | --- |
| 해제가 안 됨 | 토글이 아니라 추가만 하고 있음 |
| 4개째가 선택됨 | 한도 검사 누락 |
| 3개 채운 뒤 해제도 안 됨 | 선택된 태그까지 비활성시켰다 |
| 눌러도 아무 반응이 없는데 이유를 모르겠음 | 로직으로만 막고 UI에 표시하지 않았다 |
| 같은 항목이 두 번 들어감 | 중복 제거 안 됨. **`user_interests`의 PK가 `(user_id, interest_id)`라 저장 시 에러가 난다** |

> **화면의 제한은 방어가 아니다.** 개발자 도구로 요청을 조작하면 4개도 보낼 수 있다. 백엔드도 같은 규칙을 검사해야 한다 (`api-smoke.md` 참조).

## 3. 저장 (구현됨 — `POST /api/user-interests` + `replace_user_interests` RPC)

**동작 정의 — 전체 교체.** 요청받은 목록이 사용자의 최종 관심사가 된다. 사용자 JWT가 적용된 client로 `replace_user_interests(uuid[])` RPC를 호출하며, RPC 내부에서 검증·기존 행 삭제·새 행 삽입이 **한 트랜잭션**으로 실행된다. REST delete/insert 두 번이 아니다. 같은 요청을 반복해도 결과가 같다.

**실행** — A 세션에서 관심사 3개 선택 후 "깸 시작하기"

**기대 결과**

- `user_interests`에 **정확히 3행**, 전부 **A의 `user_id`**로 저장된다
- 다음 화면(오늘의 깸)으로 이동한다

```sql
select interest_id from user_interests where user_id = 'A의 UUID';
```

**실행 (재저장)** — 다시 온보딩으로 돌아가 2개만 선택 후 저장

**기대 결과** — **3행이 아니라 2행이 된다.** 해제한 관심사가 사라져야 한다.

**실패 신호**

| 증상 | 원인 |
| --- | --- |
| 0행 저장 | RLS 차단. 사용자 JWT가 전달되지 않았다 → 백엔드가 `create_user_client()`를 쓰는지 확인 |
| 재저장 후 5행 (3+2) | 전체 교체가 아니라 추가하고 있다 |
| 재저장 후 0행 | RPC 검증 실패인데 프론트가 에러를 무시했다. **에러를 띄우고 완료 화면으로 넘기지 않아야 한다** |
| **RLS 없이도 저장됨** | 백엔드가 `create_admin_client()`를 쓰고 있다. **secret 키는 RLS를 우회한다.** 즉시 고쳐야 한다 |
| 중복 키 에러 | 같은 관심사를 두 번 보내고 있다 (RPC가 `INTEREST_IDS_DUPLICATED`로 422 반환해야 한다) |
| **429** | **익명 가입 rate limit(IP당 시간당 30건)에 걸렸다.** Auth 장애가 아니다. 한 시간 기다리거나 대시보드에서 조정한다 |

**동시 재설정 원자성** — 같은 사용자가 동시에 두 번 재요청하면(예: 1개짜리와 2개짜리) 최종 행 수는 항상 **한 요청의 완전한 집합**(1 또는 2)이어야 한다. 0(빈 집합), 3(합집합), 중복 행이면 실패다. `replace_user_interests`는 `pg_advisory_xact_lock`으로 사용자별 동시 호출을 직렬화한다(`supabase/migrations/20260716081125_add_replace_user_interests_advisory_lock.sql`). 검증은 local Supabase에서 같은 사용자 토큰으로 두 psql 세션을 동시에 실행해 확인한다.

## 4. 오늘의 깸 카드 조회 (구현됨 — `GET /api/articles/today`)

**실행** — 관심사 저장 후 오늘의 깸 화면 진입

**기대 결과**

- 로딩 중에는 로딩 상태가 보인다
- 성공하면 저장한 관심사에 맞는 카드 1~3개가 API가 반환한 순서 그대로 보인다(첫 카드는 대표 카드, 나머지는 목록)
- 카드에 원문 본문·문장 배열·AI 요약이 없다. "읽고 미션 받기" 링크가 `originalUrl`로 새 탭을 연다
- 저장한 관심사에 태그된 후보가 없으면 **`500`이 아니라** 빈 목록과 관심사별 안내 문구(`emptyStateMessage`)가 보인다
- API 호출이 실패하면 에러 상태와 재시도 버튼이 보이고, 재시도를 누르면 다시 호출한다

**실패 신호**

| 증상 | 원인 |
| --- | --- |
| 관심사가 있는데도 빈 목록 | 후보 article이 실제로 없거나(`access_type`/`trust_level`/`default_exposure`/`quality_score` 조건 미달), 태그가 안 붙어 있다 |
| 후보 없음인데 `500` | 백엔드가 빈 RPC 결과를 예외로 처리하고 있다 |
| 카드 순서가 RPC 결과와 다름 | batch 조회 후 원래 순서로 재정렬하지 않았다 |
| 카드에 원문 전문·요약이 보임 | 응답 스키마가 `official_excerpt`가 아닌 다른 필드를 새어 보내고 있다 |

## 5. 경계 확인 (실패해야 정상)

**이 항목이 없으면 위의 확인은 전부 무의미하다.** "저장이 된다"는 확인은 시스템이 뚫려 있어도 통과한다.

### 5-1. 인증 없이 저장 요청

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST http://localhost:8000/api/user-interests \
  -H "Content-Type: application/json" \
  -d '{"interestIds": ["<아무 uuid>"]}'
```

**기대 결과** — `401`. 저장되지 않는다.

### 5-2. 요청 본문에 `userId`를 넣어 전송

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST http://localhost:8000/api/user-interests \
  -H "Authorization: Bearer <A의 access_token>" \
  -H "Content-Type: application/json" \
  -d '{"interestIds": ["<uuid>"], "userId": "<B의 UUID>"}'
```

**기대 결과** — **`422`.** 요청 스키마에 없는 필드는 거부한다 (`extra="forbid"`).

**왜 무시가 아니라 거부인가** — 조용히 무시하면 프론트 개발자가 그 필드가 의미 있다고 믿게 된다. 즉시 드러나야 한다.

### 5-3. B가 A의 데이터를 조회

B 세션(시크릿 창)에서 관심사 화면을 다시 열거나, B의 토큰으로 조회한다.

**기대 결과** — **A가 저장한 관심사가 보이지 않는다.**

**실패 신호** — **A의 데이터가 보이면 RLS가 뚫린 것이다.** 백엔드가 `create_admin_client()`를 쓰고 있거나, `user_id`를 요청에서 받고 있다. `user_id`는 **토큰에서만** 뽑아야 한다.

> RLS 경계는 `uv run scripts/verify_supabase.py`가 자동으로도 검증한다. 화면 경유 확인이 목적일 때만 수동으로 한다.

## 6. 정리

**사전 조건에서 기록한 A, B의 UUID만 삭제한다.**

> **위험** — `delete from auth.users where is_anonymous`를 실행하지 않는다. 깸의 사용자는 **전원이 익명 사용자**다. 이 쿼리는 "모든 사용자 삭제"와 같다.
>
> 실행 전 **프로젝트 ref가 개발용인지 확인한다.**

```sql
delete from user_interests
where user_id in ('<A의 UUID>', '<B의 UUID>');

delete from auth.users
where id in ('<A의 UUID>', '<B의 UUID>');
```

**확인** — 삭제 후 두 UUID가 남아 있지 않은지 본다.

```sql
select count(*) from auth.users where id in ('<A의 UUID>', '<B의 UUID>');
-- 기대: 0
```

## 화면 상태 확인

기능이 동작하는 것과 쓸 만한 것은 다르다.

- [ ] 목록 조회 중 로딩 상태가 표시된다
- [ ] 목록 조회 실패 시 에러 상태와 재시도 수단이 있다
- [ ] 저장 실패 시 **완료 화면으로 이동하지 않는다**
- [ ] 저장 버튼 연속 클릭 시 중복 요청이 나가지 않는다 (`disabled` 처리)
- [ ] 새로고침 후에도 같은 익명 세션 UUID가 유지된다
- [ ] access token과 secret 키가 콘솔·로그에 출력되지 않는다
- [ ] 320px, 375px 화면에서 텍스트와 버튼이 잘리지 않는다
- [ ] 오늘의 깸 목록 조회 중 로딩 상태가 표시된다
- [ ] 오늘의 깸 조회 실패 시 에러 상태와 재시도 버튼이 있다
- [ ] 후보가 없는 관심사는 빈 상태 안내 문구를 보여주고 `500`이 아니다
- [ ] 카드 1~3개가 API 순서 그대로 보이고 원문 링크가 새 탭으로 열린다
