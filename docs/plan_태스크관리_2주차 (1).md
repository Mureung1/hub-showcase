# @plan 태스크 관리 기능 — 2주차 작업 계획

**기능: 태스크 관리 (서비스의 뼈대)**

설계 결정사항 반영: 담당자 1명, 담당자 없음 허용, 상태 3단계(대기·진행·완료), soft delete, 활동 로그 기록, 진행도 2종(팀/개인).

**⚠️ 이번 갱신 사항**: 로그인 방식은 아이디/비밀번호가 아니라 **이름 선택 방식**으로 확정됐다(JWT 없음). 본격적인 "초대코드 진입 → 이름 선택" 흐름은 3주차 작업이지만, 태스크 담당자 권한 체크(완료는 담당자만)와 "내 진행도" 계산에는 "지금 나는 누구인가"라는 식별자가 필요하다. 그래서 이번 주에 **간이 이름 선택 UI**(멤버 목록에서 내 이름 고르기 → localStorage 저장)를 먼저 만든다. 로그인이 없으므로 별도 인증 붙이는 작업 없이 이번 주에 권한 체크까지 바로 구현한다. 3주차에는 이 로직을 그대로 재사용하고 진입 경로(초대코드)만 앞에 붙이면 된다.

## 작업 목록

| 순서 | 작업 | 구분 | 우선순위 | 완료 기준 |
|------|------|------|----------|-----------|
| 1 | teams / members(이름만, 인증정보 없음) / tasks / activity_logs 테이블 설계 + 생성 | BE | 🔴 | SQLite에 4개 테이블 생성, 더미 멤버 2~3명 + 태스크 1건 INSERT 성공 |
| 2 | 태스크 CRUD API — 목록 조회(GET) + 추가(POST, 담당자=member_id FK, nullable) | BE | 🔴 | 브라우저/Postman으로 추가한 태스크가 목록에 보임. 담당자 미지정 추가도 성공 |
| 3 | 간이 이름 선택 UI — 멤버 목록에서 "나" 선택 → localStorage 저장 | FE | 🔴 | 새로고침해도 선택한 이름이 유지됨. (본격 초대코드 진입 흐름은 3주차, 이번 주는 currentUser 식별만) |
| 4 | 태스크 상태 변경 API (PATCH, 대기↔진행↔완료 자유 전환, 요청에 memberId 포함) | BE | 🔴 | 상태 변경 후 재조회 시 반영 확인 |
| 5 | 완료 처리 권한 체크 — PATCH 요청의 memberId ≠ 담당자면 완료 처리 거부 | BE | 🔴 | 담당자 아닌 이름으로 완료 시도 → 실패 응답. 담당자 없음 태스크는 아무나 완료 가능(임시 규칙, 필요 시 조정) |
| 6 | 활동 로그 자동 기록 (모든 상태 변경, 완료↔미완료 되돌리기 포함) | BE | 🔴 | logs 테이블에 변경 전/후 상태 + memberId + 시각이 남음 |
| 7 | 태스크 목록 화면 (카드 리스트 + 상태 뱃지, 완료=초록 `--color-success`) | FE | 🔴 | API 데이터가 화면에 렌더링됨 |
| 8 | 태스크 추가 폼 (제목 · 담당자 드롭다운(멤버 목록) · 마감일) | FE | 🔴 | 폼 제출 → 새로고침 없이 목록에 추가됨. 담당자 미지정 허용 |
| 9 | 상태 변경 UI + 권한 반영 (담당자 본인 아니면 완료 버튼 비활성/에러 토스트) | FE | 🔴 | 담당자로 로그인 상태일 때만 완료 처리 성공, 아니면 UI에서 막힘 |
| 10 | 진행도 바 2종 — 팀 전체(보라 그라데이션) + 내 진행도(currentUser 기준, 파랑 그라데이션) | FE | 🟡 | 완료/전체 비율이 바 길이로 표시됨. 내 진행도는 3에서 저장한 이름 기준으로 필터링 |
| 11 | 태스크 soft delete (archived 플래그) + 목록에서 숨김 | BE+FE | 🟡 | 삭제 버튼 → DB엔 남고 화면에선 사라짐 |
| 12 | 활동 로그 화면 (누가 언제 뭘 바꿨는지 리스트) | FE | 🟡 | 로그 API 데이터가 시간순으로 표시됨 |
| 13 | 마감임박 표시 (D-1 이하만 빨강 — 유일하게 허용되는 빨강 사용처) | FE | 🟢 | 마감 하루 전 태스크에만 빨간 표시, 그 외엔 절대 빨강 없음 |

## 의존성

- **BE 축**: 1 → 2 → 4 → 5, 4 → 6
- **이름 선택(식별자) 축**: 1 → 3 (멤버가 있어야 고를 이름이 있음), 3 → 5 · 9 · 10
- **FE 축**: 2 → 7 → 8 → 9, 4 → 9, 3 → 10, 6 → 12, 2 → 11

```
1 ─┬→ 2 ─┬→ 4 ─┬→ 5 ─┐
   │     │     └→ 6 ─→ 12
   │     └→ 7 → 8 → 9 ─→ 10
   └→ 3 ───────────────┴→ (5, 9, 10에 currentUser 공급)
```

## 추천 진행 순서 (하루 단위)

- **1일차**: 1 + 2 (DB, 멤버·태스크 기본 API) → 커밋 2회
- **2일차**: 3 + 7 + 8 (이름 선택 간이 UI + 목록 + 추가 폼) → 눈에 보이는 결과물 확보
- **3일차**: 4 + 5 + 9 (상태 변경 API + 권한 체크 + FE 세트) ← 담당자만 완료 규칙이 이번 주에 완성되는 지점
- **4일차**: 6 + 10 (활동 로그 + 진행도 바 2종) ← 여기까지가 "발표 가능한 상태" 최소선
- **5일차**: 11, 12, 13 + 버그 정리, PR 작성

## 주의점

- 각 순서마다 커밋 1개 이상 (몰아서 커밋 금지)
- 진행도 바에 빨강 절대 금지 — 팀=보라, 개인=파랑. 빨강은 13번 마감임박 표시에만
- 로그인이 없으므로 memberId는 매 요청마다 body/param으로 넘긴다 (JWT/세션 없음). 서버는 이걸 그대로 신뢰하는 수준으로 충분함 — 대학생 팀플용 프로토타입이라 과한 보안 설계는 불필요
- 3주차에 "초대코드 진입 → 이름 선택" 화면이 생기면, 3번 작업의 localStorage 저장 로직을 그대로 재사용하고 진입 경로만 앞단에 붙이면 된다 (재작업 없음)
