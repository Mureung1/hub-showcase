## S1 · 타이틀 (20초)

안녕하세요, WeatherPilot 만들고 있는 양서형입니다.

**WeatherPilot은 날씨 데이터로 소상공인의 매출을 지키는 자율 마케팅 에이전트입니다.** 비 오는 날, 폭염인 날 매출이 빠지는 걸 에이전트가 미리 감지해서 마케팅 문자를 준비해 두고, 사장님은 검토·승인만 하는 서비스예요.

오늘은 이 프로젝트를 **처음 보시는 분도 이해하실 수 있게 소개**하고, 3주간 어떻게 만들었는지 설명한 다음, **배포된 앱으로 직접 시연**하겠습니다.

## S2 · 문제 (40초)

먼저 왜 만들었는지부터요.

실제 상권 데이터를 보면 **비 오는 날 매출이 평균 18%, 폭염 낮 시간대엔 20%까지 빠집니다.** 날씨는 예보로 미리 알 수 있는데도 매출은 그냥 빠져요.

왜냐하면 사장님 입장에선 **대응이 전부 수작업이기 때문입니다.** 날씨 확인하고, 문구 고민하고, 발송까지 — 장사하면서 매일 하기는 어렵죠.

그래서 사장님이 진짜 원하는 건 더 좋은 마케팅 툴이 아니라 **"마케팅을 안 해도 되는 상태"** 예요. 저는 이걸 의사결정 대행이라고 봤습니다.

## S3 · 솔루션 (40초)

동작은 다섯 단계입니다. **날씨와 매출을 분석하고 → 문구·쿠폰 초안을 만들고 → 사장님이 검토·승인하면 → 발송하고 → 쿠폰 사용을 추적합니다.**

여기서 핵심은 세 번째, **사람이 게이트라는 거예요.** 에이전트가 다 준비하지만, 발송 버튼은 사장님이 누릅니다. 자동으로 문자를 쏘는 게 아니라, 사람이 승인한 것만 나갑니다.

## S4 · 스코프 (30초)

스코프는 정직하게 표기했습니다.

**날씨는 기상청과 OpenWeatherMap 실연동, LLM 제안은 Groq, 문자는 Solapi로 제 번호에 실제 발송, DB·스케줄러도 실구축, 인스타그램은 본인 계정 게시까지 붙였습니다.** POS 연동은 수동 입력과 CSV로 대체했고, 카카오 알림톡·080 실회선·타인 계정 SNS 게시는 모의로 뒀습니다.

**"뭐가 진짜냐"를 항상 이 표로 먼저 말씀드리고 시작합니다.** 데모의 쿠폰 추적도 실시간처럼 보이지만 실제로는 쿠폰 코드 기반 누적 집계라고 정직하게 밝힙니다.

## S5 · 3주 여정 (50초)

어떻게 만들었는지 3주로 요약하면 —

**1주차엔 날씨 앙상블과 DB를 세웠습니다.** 기상청과 OpenWeatherMap 두 소스를 가중 병합하고 한쪽이 죽으면 폴백하게 했고, 매출 30일치로 이 가게의 날씨별 진단을 계산했습니다.

**2주차엔 에이전트 코어예요.** LLM이 제안을 만들고, 스키마 검증과 가드레일로 안전하게 거른 뒤, 매일 아침 6시 반 크론이 자동 생성합니다.

**3주차엔 프론트를 실연동하고, (광고) 문자를 실제로 보내고, 쿠폰 추적을 붙이고, Vercel과 Render로 배포**했습니다.

## S6 · 설계 원칙 3 (40초)

이번에 제일 신경 쓴 설계 원칙 세 가지입니다.

**첫째, API 키는 전부 서버에만 있습니다.** 프론트엔 시크릿이 하나도 없어요.

**둘째, 광고 문자 관련 법적 필터는 서버가 강제합니다.** (광고) 표기·수신동의·야간 차단을 서버에서 보장해서, UI를 우회해도 법은 못 우회합니다.

**셋째, 에이전트 파이프라인은 순수 함수예요.** 크론이 돌리든 API가 부르든 테스트가 부르든 같은 코드가 같은 결과를 냅니다.

## S7 · 핵심 기술 (40초)

핵심 기술은 다섯 개입니다.

**날씨 앙상블**은 두 소스를 가중 병합하고 장애 시 폴백합니다. **실매출 진단**은 이 가게 데이터로 비 오는 날 몇 퍼센트 빠지는지 실제로 계산해요. **LLM은 Groq가 생성하되, 할인율 상한·금칙어·창작 상호를 서버 가드레일이 다시 검사**합니다. **쿠폰 실측**은 쿠폰 코드로, 날씨가 회복된 게 아니라 이 캠페인이 만든 매출을 직접 추적합니다.

## S8 · 라이브 데모 (3분)

> 사전 준비: `?uat` 없이 배포 URL 열어두기 · 탭 B에 네이버 "부산 서면 날씨" · 오늘 제안 미리 1회 생성.
> **야간(21~08시) 발표면**: 발송이 예약으로 전환되니, 문자를 미리 받아두고 "미리 온 문자"로 보여준다.

이제 배포된 앱으로 시연하겠습니다.

- **① 날씨 일치 확인 (~30초)** — 우리 앱과 네이버 날씨를 나란히 놓고, "기상청·OpenWeather N개 소스 평균" 배지를 짚으며 **여러 실제 API를 합친 값**임을 보여줍니다.
- **② 오늘의 제안 (~40초)** — 대시보드에 뜬 제안을 읽어줍니다. **"이건 저장된 mock이 아니라, 방금 날씨와 매출 진단을 보고 Groq가 생성한 문구"** 라는 점을 강조.
- **③ 검토 → 발송 (~60초)** — "제안 검토하기" → "이대로 발송하기". **서버가 동의자만 걸러 (광고) 표기·수신거부 문구를 자동 삽입** — 제 폰에 실제 문자가 옵니다. 화면에 쿠폰 코드도 뜹니다.
- **④ 쿠폰 사용 → 추적 (~30초)** — 쿠폰을 사용 처리하면 **추적 카드에 사용 인원·귀속 매출이 반영**됩니다. "실시간처럼 보이지만 쿠폰 코드 기반 누적 집계"라고 정직하게 덧붙입니다.

## S9 · 결과 (30초)

3주 뒤 결과입니다. **프론트는 Vercel, 백엔드는 Render에 배포했고, 서버 테스트 126개가 통과합니다.** 날씨·LLM·문자 세 가지 실연동을 배포 환경에서 검증했고요.

**제안 조회부터 승인, (광고) 문자 발송, 쿠폰 사용, 추적까지 전 플로우가 배포 URL에서 실제로 돌고**, 매일 아침 크론도 상시 실행됩니다.

## S10 · 비전공자의 3주 (40초)

마지막으로 하나만요. 솔직히 **코드 대부분은 AI가 썼습니다.** 그래서 이 3주는 정신력 이야기가 아니라 관찰 보고예요.

**AI는 문법·프레임워크·API·배포 같은 "코드를 쓰는 능력"의 격차는 체감되지 않을 만큼 좁혀 줬습니다.** 제 숙련도가 병목이 된 적은 거의 없었어요.

반면 **무엇을 안 만들지 정하고, 완료 기준을 먼저 쓰고, 결과를 의심해서 검증을 시스템으로 만드는 일은 사람 몫**이었습니다. AI가 빨라질수록 병목은 검증하는 사람이더라고요.

## S11 · Q&A / 감사 (질문 경청)

## 예상 질문 대비

- **"왜 Claude가 아니라 Groq?"** → 원안은 Claude API. 챌린지 기간 무료·OpenAI 호환이라 Groq로 갔고, provider 교체 지점(caller)만 바꾸면 되도록 분리해 뒀다.
- **"쿠폰 추적이 실시간인가?"** → 아니다. 쿠폰 코드 기반 누적 집계다. 데모에선 실시간처럼 보이게 연출하지만 그렇게 정직하게 표기한다.
- **"테스트 126개면 커버리지는?"** → 개수보다 위치. 법적 필터·가드레일·상태 전이·redeem 경계 등 돈·법이 걸린 경로 위주로 봤다.
- **"타인 계정에도 인스타 자동 게시가 되나?"** → 본인 계정만. 타인 계정은 Meta App Review(2~4주)가 필요해 모의로 뒀고, Solapi 문자도 같은 원칙(본인 번호만 실발송)이다.
