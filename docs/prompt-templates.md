# 프롬프트 템플릿 — 설계 먼저, 작게 나누기

> 출처: AI Agent Challenge 강의 "AI와 설계하고 작업나누기". `[기능 이름]`/`[작업 이름]` 자리만 바꿔서 매번 재사용한다.

## 언제 어느 템플릿을 쓰나

- **템플릿 A** — 새 기능을 처음 시작할 때 (예: "통증 재편성", "스킵 로직"). 한 번만 쓴다.
- **템플릿 B** — 템플릿 A로 나눈 작업(이슈) 중 하나를 실제로 구현하기 직전. 작업마다 매번 쓴다.

두 단계가 겹쳐 있는 구조다 — 기능 전체를 한 번 설계 → 그 안에서 나뉜 작업마다 구현 전략을 다시 받는다.

## 템플릿 A — 기능 전체 설계 요청

```
[기능 이름] 기능을 만들기 전에 설계서부터 작성해줘. 아직 코드는 짜지 마.

먼저 이 기능을 수평적("[기능] UI를 만든다")이 아니라 수직적으로 정의해줘.
예: "[기능]을 하면 실제로 [핵심 동작]이 일어나고, 새로고침해도 그 결과가 남는다."

아래 순서로 설계서를 써줘:
1. 완료 기준(Definition of Done)
2. 작업 크기 검토 (반나절/하루 안에 끝날 크기인지, 크면 뭘 나중으로 미룰지)
3. 빠진 것 확인 (기획서·요구사항 대비 빠뜨린 게 없는지)
4. 장점과 단점
5. 한계점 (이 방식이 구조적으로 못 하는 것, 어디서 깨지는지 — 4번과 분리해서 명시. 내가 대안을 생각해볼 수 있게 숨기지 말고 보여줘)
6. 다른 방법 검토 (대안과 왜 이 방법을 택하는지)
7. 화면 변경 사항 (뭐가 생기고 뭐가 바뀌는지)
8. 필요한 테이블/컬럼
9. 필요한 API (엔드포인트, request/response)

다 쓰면 내가 검토하고, 승인하면 이슈로 등록해서 세부 작업을 나눠줘.
```

## 템플릿 B — 작업 하나의 구현 전략 요청

```
[작업 이름]을 구현하기 전에 구현 전략부터 보여줘. 코드는 아직 쓰지 마.
1) 만들거나 고칠 파일과 각 파일의 역할
2) 데이터가 어디에 있고 어떻게 흐르는지 (state 위치, 요청과 응답)
3) 이렇게 구현하는 이유, 다른 방법이 있다면 장단점도
4) 이 구현의 한계점 (다루지 않는 엣지 케이스, 나중에 깨질 수 있는 지점 — 3번과 분리해서)

기존 프로젝트 구조(라우터·컴포넌트 패턴)를 그대로 따르고, 새 라이브러리는 쓰지 마.
```

## 전략을 받은 뒤 검토할 때 (이해 안 되거나 의심스러우면)

- "이 방법 말고 다른 방법 2가지를 보여주고, 셋의 장단점을 표로 비교해줘. 어떤 걸 추천하는지와 이유도."
- "왜 이렇게 하는데?"
- "다른 방법은 없어?"
- "이 방식의 단점은 뭐야?"

**원칙**: 전략을 읽고 내 말로 설명할 수 없으면 승인하지 않는다. 판단이 어려우면 비교표를 시키거나 위 질문을 고정으로 던져서, 정확한 판단 대신 "그대로 통과시키지 않는 습관"으로 검토한다.

## 좋은 구조인지 보는 기준

| 질문 | 좋은 신호 | 나쁜 신호 |
|---|---|---|
| 역할이 제자리인가 | 화면 일은 화면에, 데이터 처리는 서버에 | 화면(FE)이 DB를 직접 부름 |
| 하나가 한 가지 일만 하나 | 파일과 컴포넌트가 역할별로 나뉨 | 한 파일이 화면·요청·검증을 다 함 |
| 기존 구조를 따르나 | 지금 프로젝트의 폴더와 방식 그대로 | 갑자기 새 패턴이나 라이브러리를 끌고 옴 |
| 변경 범위가 적절한가 | 필요한 파일 몇 개만 고침 | 작은 기능인데 프로젝트 절반을 고침 |
