## 2. 발견된 결함 14건 — 전체 목록

### 2.1 렌더 조건 계열

**① T-007 — completed 전환 후 답변 카드 소실**
렌더 조건이 `review_required`만 보고 `completed`를 놓쳤다. → `review_required || completed`.

**② T-015 — StrictMode 이중 마운트 하이드레이트**
ref 가드를 제거하고 per-run `cancelled` 방식으로 전환.

### 2.2 인프라 계열

**③ T-015 — GRANT 마이그레이션 누락**
> "RLS만으론 부족 — 마이그레이션 생성 테이블에 `authenticated`·`service_role` 테이블 DML GRANT가 없어 `permission denied`"

`grants.sql`로 GRANT + default privileges 부여. **RLS를 켰다고 접근이 되는 게 아니다.**

**④ T-018 — 테스트 계정 상수 대입 시 빌드 깨짐**
> "상수를 실제 값으로 바꾸면 `TS2367`(리터럴 타입끼리 교집합 없는 비교)로 빌드가 깨지는 결함이 있었다. **자리표시자 상태에서만 검증한 탓에 놓쳤다**"

두 상수에 `: string` 주석을 붙여 양쪽에서 통과하게 수정.
**교훈: 자리표시자로 검증한 것은 검증한 게 아니다.**

### 2.3 "갇힘" 계열 — 같은 실수를 3번 반복했다

이게 이 프로젝트에서 가장 중요한 패턴이다.

**⑤ T-019.1 — 충돌 0건 Question이 `review_required`에 갇힘**
> "single_source를 자동 통과로 바꾸면서 충돌 0건 Question이 사용자 판단 트리거를 잃어 FinalAnswer 없이 `review_required`에 갇혔다"

**⑥ T-019.4 — Manager 완전 실패 시 `processing`에 갇힘**
web `applyAgendas`가 `agendas.length > 0`을 마감 조건으로 요구했다.

**⑦ T-019.5 — 새로고침 복원 경로가 새 경로를 막음**
복원 가드가 `status !== "completed"`였다. 새 경로에서는 틀린 전제였다.

**세 번째에 근본 원인을 특정했다.**
> "같은 계열 갇힘이 세 번 나왔고, 원인은 매번 **마감 판단이 '무언가 있다'는 전제에 매달려** 있던 것이다"

수정: `agendas.length > 0`을 마감 조건에서 뺐다. `every`는 빈 배열에서 true이므로 0건도 자연스럽게 마감된다. 복원 판단 기준도 상태값이 아니라 **"복원할 FinalAnswer가 없는가"**로 바꿨다.

**⑧ T-019.6 — "✓ 충돌 해결 완료" 배지의 vacuous truth**
> "`isAllResolved = unresolved.length === 0`. **빈 배열도 참**이라 '해결할 게 없었다'가 '해결을 완료했다'로 뒤집혔다"

Manager 완전 실패 시엔 바로 옆 문구가 "비교 결과를 만들지 못했습니다"라 **화면 안에서 자기모순**이었다. `hadConflicts` 조건을 추가하고 "판단할 충돌 없음" 중립 문구를 신설.

> **이 계열 5건이 전부 "빈 컬렉션"에서 나왔다.** 코드 리뷰로는 안 잡혔고, 전부 브라우저를 실제로 열어서 발견했다.

### 2.4 계측 계열 — 지표가 없으면 원인을 못 찾는다

**⑨ T-019.3.1 — 쟁점 소멸의 진짜 원인은 `quotes: []`**
`quoteRejectRate`가 0%인데 쟁점이 33.3% 폐기되는 모순이 관측됐다. 어떤 지표에도 안 잡혔다.

> "`AgendaStanceSchema`(저장 계약)는 `quotes.min(1)`인데 `CompareStanceSchema`(LLM 출력)와 LLM에 보내는 JSON Schema에는 **최소 개수 제약이 없다.** 모델이 `quotes: []` stance를 내는 것이 합법이다"

인용 순회 루프가 0회 도니 폐기율 분모에 안 잡혔다. → `empty_quotes` 사유를 신설해 지표로 드러냈다.

**스키마에 `minItems: 1`을 넣지 않기로 한 것은 의도적 결정이다.** 모델이 억지 인용을 하게 만들기 때문이다. 문제를 없애는 대신 **보이게** 만들었다.

**⑩ T-019.3.1 — 인용 폐기 원인은 날조가 아니라 조사 한 글자**
> 원문 `익명 사용자(anon)**와**…` → 모델 인용 `익명 사용자(anon)**과**…` — **조사 한 글자 차이, 내용 100% 동일**

§11의 정규화는 공백만 처리하므로 조사·어미 변형을 날조와 구분하지 못한다. **정규화를 완화하지 않았다** — 날조 탐지력과 맞바꾸는 결정이라, 데이터를 더 모으고 판단하기로 했다. 대신 `describeDiff`로 차이 위치를 저장해 나중에 판단할 근거를 남겼다.

### 2.5 타임아웃 — 같은 함정을 두 번 밟았다

**⑪ T-019.3.1 / T-019.4 — 타임아웃이 아예 작동하지 않았다**

증상은 "100초 설정인데 103초 호출이 타임아웃 0건"이라는 모순이었다.

> "`fetch`는 응답 **헤더**가 도착하면 resolve하는데 `clearTimeout`을 `finally`로 그 직후에 걸어, 생성 시간 전부가 들어가는 `response.text()` 구간이 무방비였다"

실증: **3초 타임아웃으로 호출했는데 156.5초 만에 정상 반환.**

```text
잘못    : fetch(…, { signal })  →  clearTimeout  →  await response.text()   ← 무제한
올바름  : fetch(…, { signal })  →  await response.text()  →  clearTimeout
```

**부수 효과: 이전 진단이 통째로 틀렸다.**
> "**§2.4의 이전 서술이 틀렸다** — 초과한 것은 맞지만 타임아웃된 적도 재시도된 적도 없다"

"45초 초과분이 재시도되어 지연이 배가됐다"는 분석은 근거가 없었다. 타임아웃이 애초에 안 걸렸으니까.

> "같은 함정을 두 번 밟았다 — T-019.3.1의 지연 오측정도 원인이 같았다. 그때는 프로브였고 이번엔 프로덕션 코드였다"

수정 후 정책: **단계 6 타임아웃은 재시도하지 않고 fallback으로 직행한다.** 그래서 이 값(120초)이 곧 쟁점당 지연 상한이 된다.

### 2.6 분류·표시 계열

**⑫ T-019.4 — `auto_single_source`가 사용자 결정으로 오분류**
> "사용자가 판단한 적 없는 항목이 결정 사항으로 기록되는 것"

원인 두 곳 모두 `auto_consensus`만 보고 `auto_single_source`를 빠뜨렸다. **enum 값을 하나 늘리면, 그 값을 분기하는 모든 곳을 찾아야 한다.**

**⑬ T-020.3 — 마크다운 원문 노출 / 단일 소스 헤더 오표기**
`AnswerCard`가 평문 렌더인데 프롬프트가 마크다운을 생성했다. **렌더러를 넣는 대신 프롬프트에서 마크다운을 금지**했다 — `user_composed` 콘텐츠 sanitize 부담을 피하기 위해서다.
헤더는 `generationMode`로 판단하도록 바꿨다. **"상태가 아니라 `generationMode`로 판단한다."**

**⑭ T-020.2 — `?scenario=happy-path`가 Mock이 아니었다**
> "`?scenario=happy-path`를 Mock인 줄 알고 골랐는데 **happy-path가 곧 서버 경로**여서 3사를 1회 더 썼다"

코드 결함은 아니지만 예산을 썼다. 이름이 오해를 부른다.

## 4. 반복 패턴 3가지 — 다음 사람이 알아야 할 것

### 패턴 1. "새 경로를 만들면 기존 경로의 전제가 안 맞는다"

**5번 발생했다.** 전부 브라우저를 열어서만 발견됐다. 타입 체크·빌드·린트 전부 통과한 상태로 화면만 멈춰 있었다.

체크리스트로 굳혔다(SPEC-AI-003 §9.2):
- 새 상태·새 enum 값을 만들면, **그 값을 분기하는 모든 곳**을 찾았는가
- 마감·완료 판단이 "무언가 있다"는 전제에 매달려 있지 않은가
- 빈 배열에서 `every`가 true인 것을 이용하고 있는가, 아니면 당하고 있는가
- 새로고침 복원 경로도 새 경로를 통과하는가

### 패턴 2. 계측에 쓴 시간은 반드시 회수된다

- **T-019.3.1**: 원인 하나 찾는 데 세션 하나를 통째로 썼다
- 그 뒤 `stancesDiscarded` · `stanceSurvival` · `empty_quotes` 지표를 추가
- **T-019.4**: 같은 종류의 원인을 **지표 조합만 보고 즉시** 읽어냈다
- **T-019.5**: 폐기된 인용의 차이를 영구 저장하게 만들어, 이후 재현 실행이 불필요해졌다

지표를 추가할 때 비용은 즉시 발생하고 이득은 나중에 온다. 이 프로젝트에서는 **두 태스크 만에 회수됐다.**

### 패턴 3. 진단이 틀렸으면 정정 흔적을 남긴다

이 프로젝트는 최소 3번 진단이 틀렸다.
- Manager 지연 원인 ("길게 쓴다" → 추론 토큰 88~94%)
- 재시도 배가 ("40~45%가 재시도" → 타임아웃이 아예 안 걸렸음)
- `effort: low` 효과 ("전형값 감소" → 꼬리 절단)

**전부 Spec에 "틀린 추론으로 정정" 표시와 함께 남겼다.** 지우지 않았다. 지우면 다음 사람이 같은 추론을 다시 한다.

## 5. 3자 협업 구조가 실제로 어떻게 작동했나

`02-AGENT-ARCHITECTURE.md`가 구조를 설명한다. 여기서는 **결과**를 적는다.

### 잘 작동한 것

**Spec을 먼저 쓰고 구현을 나중에 한 것.** 구현 에이전트가 판단할 여지를 줄이니 결과가 재현 가능해졌다. Spec에 없는 것을 만나면 에이전트가 **멈추고 물었다** — T-019.3 착수 시 `stances` DB 컬럼이 Spec 목록에 없는 것을 발견하고 정지한 것이 대표적이다.

**설계자와 구현자를 분리한 것.** 구현 중 발견된 사실이 설계자에게 보고로 돌아오고, 설계자가 Spec을 고쳐 다음 구현에 반영하는 순환이 생겼다. Spec 문서의 "개정 기록" 장이 그 궤적이다.

**AC를 Spec에 미리 박아둔 것.** 마지막에 subagent 5개를 병렬로 띄워 전 Spec AC를 재검증할 수 있었던 건, AC가 처음부터 검증 가능한 문장으로 쓰여 있었기 때문이다.

### 잘 안 된 것

**설계자(Cowork)가 만든 Spec 오류 8건.** 대표적인 것:
- `stances`를 "변경"이라 썼는데 실제로는 계약에 없던 것을 "신설"한 것이었다
- `stances` DB 컬럼을 마이그레이션 목록에서 **통째로 빠뜨렸다** — 계약(§13.1)과 마이그레이션(§13.2)을 따로 쓰면서 "이건 어디에 저장되나"를 묻지 않은 게 원인
- "조사는 재시도로 흡수된다"고 썼는데 같은 문서의 다른 절에서 재시도를 배제하고 있었다

**교훈: 문서를 절로 나눠 쓰면 절 사이의 정합성이 깨진다.** 계약을 바꿀 때는 항상 "이건 어디에 저장되나"를 물어야 한다.

**모델 선택에 시간이 걸렸다.** 임베딩 모델 → `qwen3.7-flash` → `qwen3.7-plus`로 오갔다. 결국 "조건을 만족하면서 가장 싼 것"이라는 기준으로 정리됐다.
