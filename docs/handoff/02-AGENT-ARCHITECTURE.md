# A부. 개발 협업 에이전트 구조

## A-1. 세 역할

```text
┌─────────────────────────────────────────────────────────┐
│  사용자 (Brett)  —  결정권자                             │
│  · 모든 설계 판단을 직접 내린다                          │
│  · Agent는 선택지와 근거를 제시할 뿐 대신 정하지 않는다   │
│  · git 명령을 직접 실행한다                              │
└──────────────┬──────────────────────────────────────────┘
               │ 결정 / 승인
      ┌────────┴────────┐
      ↓                 ↓
┌──────────────┐  ┌──────────────────────────────────────┐
│ Cowork       │  │ Claude Code                          │
│ (설계·문서)   │  │ (구현)                                │
│              │  │                                      │
│ · 설계 검토   │→ │ · 코드 작성                           │
│ · 논점 제시   │프│ · 마이그레이션                        │
│ · Spec 작성  │롬│ · 테스트·검증 실행                     │
│ · 기준 문서   │프│ · status.md 갱신                      │
│ · 구현 프롬프트│트│ · 커밋 (푸시는 사용자)                 │
│ · 결과 검토   │← │                                      │
└──────────────┘보└──────────────────────────────────────┘
                고
```

## A-2. 왜 이렇게 나눴는가

**설계와 구현을 같은 맥락에서 하면 둘 다 나빠진다.**

구현을 하다 보면 "이렇게 하면 되겠네" 하고 설계를 바꾸게 되는데, 그 변경은 문서에 남지 않는다. 반대로 설계만 하면 실제 코드와 어긋난 문서가 쌓인다.

역할을 나누면 **경계에서 검증이 강제된다.**

- Cowork가 쓴 Spec을 Claude Code가 읽고 "이 부분이 실제 코드와 다르다"고 지적한다
- Claude Code의 구현 보고를 Cowork가 Spec과 대조해 "이건 Spec 위반"이라고 판정한다
- 양쪽이 틀리면 사용자가 결정한다

이 세션에서 실제로 잡힌 것들이 A-7에 있다.

## A-3. 쓰기 권한 경계 — 가장 중요한 규칙

**누가 어떤 파일을 쓰는지가 명확히 나뉘어 있다.** 이게 흐려지면 두 에이전트가 서로의 작업을 덮어쓴다.

| 파일 | 쓰기 권한자 |
|---|---|
| `docs/specs/*.md` | **Cowork만** |
| `docs/domain-policy.md`, `docs/data-model.md` | **Cowork만** |
| `docs/decisions/ADR-*.md` | **Cowork만** |
| `docs/status.md` | **Claude Code만** (실행 기록) |
| `apps/**`, `packages/**`, `supabase/**`, `prompts/**` | **Claude Code만** |
| 코드 내 주석 | Claude Code |
| git commit / push | **사용자만** |

### A-3.1 실제로 사고가 났던 지점

T-019.1 구현 중 Claude Code가 `git add -A`를 실행해 Cowork가 작성 중이던 기준 문서 3종(`data-model.md`·`domain-policy.md`·`SPEC-SCHEMA-001`)을 함께 커밋에 담았다. 되돌리면 Cowork 작업이 사라지므로, **커밋을 정리해 자기 파일만 재커밋하고 Cowork 변경분은 워킹트리에 보존**하는 방식으로 복구했다.

이후 규칙이 추가됐다: **`git add -A` 금지, 파일을 명시할 것.**

## A-4. 작업 사이클

```text
1. 사용자가 설계안 또는 요구를 제시
      ↓
2. Cowork가 기준 문서와 대조해 비판적으로 검토
   · 충돌·공백·과잉을 찾아 논점으로 정리
   · 각 논점에 선택지와 트레이드오프 제시
      ↓
3. 사용자가 논점마다 직접 결정
   · Cowork는 추천은 하되 대신 정하지 않는다
      ↓
4. Cowork가 Spec 문서 작성
   · 0장 = 재질문하지 않을 고정 사항
   · 1장 = 사용자 결정과 근거
   · 본문 = 구현 명세
   · AC = 완료 조건
      ↓
5. Cowork가 구현 프롬프트 작성 (분할 전송)
      ↓
6. Claude Code가 수신 확인 → 구현 계획 제시 → 정지
      ↓
7. Cowork가 계획을 Spec과 대조해 판정
   · 통과 / 보완 지시 / 반려
      ↓
8. 사용자가 "진행" 승인
      ↓
9. Claude Code 구현 → 검증 실행 → 보고
      ↓
10. Cowork가 보고를 Spec과 대조해 판정
      ↓
11. Cowork가 기준 문서를 구현 결과에 맞춰 개정
      ↓
12. 사용자가 커밋·푸시
```

**중요한 것은 6번과 8번이다.** Claude Code는 계획을 세운 뒤 반드시 멈추고, 사용자 승인 없이는 파일을 건드리지 않는다.

## A-5. 프롬프트 전달 프로토콜

긴 프롬프트를 한 번에 붙여넣으면 **복사 과정에서 잘린다.** 잘린 걸 모르고 구현하면 범위를 벗어나거나 빠뜨린다.

이를 막기 위한 프로토콜이 확립됐다.

### A-5.1 구조

프롬프트를 2~3부로 나누고, 각 부의 마지막 줄에 **종료 마커**를 둔다.

```text
=== END OF PART 1/3 ===
```

### A-5.2 프롬프트 안에 강제 규칙을 심는다

프롬프트 1/3의 맨 앞에 수신 프로토콜을 넣어, 에이전트가 스스로 잘림을 검사하게 만든다.

```text
## 수신 프로토콜 (가장 먼저 읽어라)

1. 3/3을 받기 전에는 어떤 파일도 읽거나 수정하지 마라. 도구를 사용하지 마라.
2. 각 부분을 받으면 아래 두 가지만 답하고 다음을 기다려라.
   - `N/3 수신 · 종료 마커 확인됨` 또는 `종료 마커 없음 — 전송이 잘린 것으로 보임`
   - 문장이 중간에서 끊긴 곳이 있으면 그 위치를 인용해 지목하라
3. 각 부분의 마지막 줄은 `=== END OF PART N/3 ===` 이다.
4. 3/3까지 받으면 A~K 절이 모두 도착했는지 대조하라.
5. 이상이 없으면 짧은 구현 계획을 제시하고 멈춰라.
6. 사용자가 "진행"이라고 답하기 전에는 구현을 시작하지 마라.
```

### A-5.3 프롬프트 필수 요소

| 요소 | 이유 |
|---|---|
| **기준 Spec 명시** | 진실의 출처를 하나로 |
| **"프롬프트와 Spec이 다르면 Spec을 따른다"** | 잘림에 대한 안전장치 |
| **범위 (장 번호)** | 무엇을 구현할지 |
| **이번에 하지 않을 것** | 범위 침범 방지 |
| **금지 사항** | 우회·회피 차단 |
| **완료 조건(AC)** | 판정 기준 |
| **검증 명령** | 실행 가능한 확인 |
| **커밋 메시지** | 기록 일관성 |
| **보고 형식 지정** | 검토 가능성 |

### A-5.4 Spec을 복붙하지 않는다

T-019.1(계약 작업)에서는 필드명이 정확해야 해서 프롬프트에 명세를 옮겼다. 그러나 T-019.2부터는 **"Spec §5를 읽고 그대로 구현하라"**로 바꿨다.

이유는 두 가지다.

- 프롬프트가 짧아져 잘림 위험이 준다
- **진실의 출처가 둘로 갈리지 않는다.** Spec을 요약해 옮기면 요약이 원본과 어긋날 때 어느 쪽이 맞는지 알 수 없다

## A-6. 검토 원칙

### A-6.1 Cowork가 구현 보고를 검토할 때

- Spec의 각 AC를 실제 보고 내용과 대조한다
- "통과했다"는 서술이 아니라 **실행한 명령과 그 결과**를 본다
- 미확인 항목이 정직하게 보고됐는지 본다
- Spec에 없던 판단이 들어갔으면 그것이 타당한지 따로 판정한다

### A-6.2 Agent가 하지 않는 것

- 사용자 결정 사항을 대신 정하기
- 실행하지 않은 검사를 통과했다고 보고하기
- Spec 규칙을 "더 나아 보인다"는 이유로 바꾸기
- 스키마를 느슨하게 풀어 Mock을 통과시키기 (반대로 **Mock을 계약에 맞춘다**)
- 요청 범위 밖 리팩터링

### A-6.3 이견이 생기면

**구현하지 말고 보고한다.** 판단은 사용자 몫이다.

실제로 T-019.2 계획 단계에서 Claude Code가 "프롬프트와 Spec이 상충한다"며 멈추고 확인을 요청했고, 그 지적이 맞아 Spec을 개정했다(A-7.4).

## A-7. 실제로 이 구조가 잡아낸 것들

### A-7.1 계약에 없는 필드를 "변경"이라고 쓴 Spec

Cowork가 Spec에 "`AgendaSchema.stances`를 `unknown[]` → 정식 스키마로 **변경**"이라고 적었다. 실물 확인 결과 **`stances` 필드는 계약에 아예 없었다** — web의 UI 전용 파생 타입으로만 존재했다. "변경"이 아니라 "승격·신설"이었다.

→ 실물 대조 검토로 Cowork가 자기 문서를 정정.

### A-7.2 DB CHECK 제약 충돌

Spec이 "합의 Agenda도 실제 출처 참조를 저장한다"고 결정했는데, 실제 마이그레이션의 CHECK는 `auto_consensus → 'NO_VALUE'`를 강제하고 있었다. 게다가 새로 추가할 `auto_single_source`는 `else true` 분기로 빠져 **아무 검증도 받지 않는** 상태가 될 참이었다.

→ 고칠 지점 두 개를 SQL 원문과 함께 Spec에 명시.

### A-7.3 브라우저 회귀에서 발견된 갇힘 결함

`single_source`를 자동 통과로 바꾸자, **충돌이 0건인 Question이 사용자 판단 트리거를 잃어 FinalAnswer 없이 갇혔다.**

Claude Code가 시나리오 테스트 중 발견하고 수정했다. 그런데 Cowork가 검토하며 **이게 시나리오 하나의 문제가 아님**을 지적했다 — 3사가 완전히 일치해도 똑같이 발생하며, 그건 예외가 아니라 **가장 바람직한 결과**다. Mock의 happy-path는 충돌이 항상 2건이라 이 경로가 한 번도 밟히지 않았을 뿐이다.

→ Spec §12.1에 "충돌 0건 경로를 반드시 뚫어놓아야 한다"를 명시하고, 트리거 조건을 "사용자 행동"이 아니라 "Agenda 집합 갱신 시 전부 passed/rejected 확인"으로 고정.

### A-7.4 구현 분할이 드러낸 Spec 공백

T-019.2 계획 단계에서 Claude Code가 "단계 6을 건너뛰는 쟁점의 `stances`는 누가 만드는가"를 물었다. Spec에 답이 없었다.

그대로 뒀다면 stance 0개 쟁점이 검증 규칙에 걸려 **조용히 폐기됐을 것**이다.

→ Spec §7.6·§7.7 신설. 마감 지점을 단계 7 하나로 통일하고, 코드가 stance를 생성하는 방식을 명시.

### A-7.5 프롬프트 자체의 누락

Cowork가 브라우저 회귀 시나리오 목록에 `recheck-path`를 빠뜨렸다. 그런데 그 태스크의 최대 리스크가 바로 `recheckResult` 문자열→객체 전환이었다.

→ 검토 단계에서 Cowork가 자기 누락을 발견해 추가 지시.

## A-8. 이 구조의 특징 요약

| 특징 | 효과 |
|---|---|
| **역할별 쓰기 권한 분리** | 두 에이전트가 서로의 작업을 덮어쓰지 않는다 |
| **결정은 항상 사람이** | AI가 조용히 방향을 바꾸지 않는다 |
| **Spec을 단일 진실로** | 프롬프트가 잘려도 복구 가능 |
| **분할 전송 + 종료 마커** | 전달 손실을 기계적으로 검출 |
| **계획 제시 후 정지** | 잘못된 방향으로 코드를 쓰기 전에 개입 |
| **양방향 검토** | 설계가 코드를 검증하고, 코드가 설계를 검증 |
| **미확인의 정직한 보고** | "실행 못 한 검사"를 통과로 위장하지 않음 |

# B부. 제품 내부 AI 파이프라인 구조

## B-1. 두 층의 AI

```text
┌─── 1층: SourceAnswer 생성 (외부에 노출됨) ────────────┐
│                                                       │
│   Claude API      OpenAI API      Gemini API          │
│       │               │               │               │
│       └───────────────┼───────────────┘               │
│                       ↓                               │
│         구조화된 답변 3벌 (StructuredContent)          │
└───────────────────────┬───────────────────────────────┘
                        ↓
┌─── 2층: Manager AI (내부 엔진, 모델명 비노출) ─────────┐
│                                                       │
│   AgendaClassifier      ConflictComparator            │
│   (묶기 — 주제)          (판정 — 결론)                 │
│        │                      │                       │
│        └──────────┬───────────┘                       │
│                   ↓                                   │
│         Agenda 배열 (합의/충돌 판정 포함)              │
└───────────────────────────────────────────────────────┘
```

**1층 AI는 사용자에게 이름이 보인다.** "Claude가 이렇게 말했다"가 제품의 핵심 정보이기 때문이다.

**2층 AI는 이름이 보이지 않는다.** Manager는 판단하는 주체가 아니라 비교를 수행하는 도구이고, 사용자가 신경 쓸 대상이 아니다. 그래서 BYOK(사용자 키) 대상도 아니며 앱 키만 쓴다.

## B-2. 5개 포트 (ADR-005)

AI 파이프라인은 **갈아끼울 수 있는 이음새 5개**로 나뉜다.

| # | 포트 | 관심사 | 구현 Spec |
|---|---|---|---|
| 1 | Provider 호출 | 각 AI API를 어떻게 부르는가 | SPEC-AI-001 |
| 2 | 답변 프롬프트 | 3사에게 무엇을 어떻게 시키는가 | SPEC-AI-001 |
| 3 | Section 정규화 | 원문을 어떻게 구조화하는가 | SPEC-AI-001 |
| 4 | **AgendaClassifier** | **어떤 기준으로 쟁점을 나누는가** | SPEC-AI-002 |
| 5 | **ConflictComparator** | **무엇을 충돌로 볼 것인가** | SPEC-AI-002 |

각 포트는 안정된 입출력 계약과 **`version` 문자열**을 갖는다. 사용한 버전은 결과 데이터에 스탬프되어, 나중에 기준을 바꿔도 **과거 결과가 어떤 기준으로 나왔는지 재현**할 수 있다.

### B-2.1 설계 원칙

> "프레임워크가 아니라 이음새." 이음새당 인터페이스 하나, 초기 구현 하나.

플러그인 로더 같은 범용 확장 장치는 만들지 않는다. `CLAUDE.md` 13장 7번 원칙("Agent 구조·공통 모듈은 실제 반복과 재사용이 확인된 뒤 만든다")과 같은 방향이다.

## B-3. 조사가 아키텍처를 검증한 사례

Manager AI 설계를 위한 사전 조사(`docs/growth/09-ai-decision-logic.md`)에서 이런 결론이 나왔다.

> **시스템은 반드시 2단 구조여야 한다.**
>
> | 단계 | 묻는 질문 | 도구 |
> |---|---|---|
> | 1단계: 묶기 | "이 두 문장이 같은 **주제**인가?" | 임베딩 유사도 or LLM |
> | 2단계: 판정 | "이 두 문장이 같은 **결론**인가?" | NLI / LLM 추론 |

그리고 이 결론은 **이미 ADR-005에서 정해둔 `AgendaClassifier`(묶기)와 `ConflictComparator`(판정) 두 포트와 정확히 같은 구조**였다.

조사 문서의 표현을 그대로 옮기면 — **"아키텍처는 이미 옳았다."**

포트를 먼저 나눠둔 것이 조사 결과와 우연히 일치한 게 아니라, **관심사를 제대로 나누면 같은 곳에 도달한다**는 사례다.

## B-4. Manager AI의 설계 철학

한 문장으로: **"판단이 아니라 계산"**

LLM에게는 **관찰만** 시키고, 규칙 적용은 코드가 한다.

| LLM이 하는 일 | 코드가 하는 일 |
|---|---|
| 이 섹션이 어느 주제에 속하는가 | pivot 선택, 순서 셔플 |
| 두 답변의 차이가 어떤 **유형**인가 | 그 유형이 충돌인지 **판정** |
| 각 AI의 입장을 원문에서 인용 | 인용이 원문에 실제 있는지 **검증** |
| 제목이 한쪽으로 치우쳤는가 | 참여 provider 수 **계산** |

**"이건 2대 1이야"를 LLM에게 묻지 않는다.** 그건 검증할 방법이 없기 때문이다. 대신 쟁점을 먼저 확정하고 각 AI의 답을 나중에 배정하면, 참여 수가 결정론적으로 세어진다.
