## 2. 파일별 역할

### 2.1 `CLAUDE.md` — 운영 규칙

에이전트가 이 저장소에서 작업할 때 지켜야 할 규칙 전체. 13개 장.

| 장 | 내용 |
|---|---|
| 1 | 프로젝트 목적과 핵심 흐름 |
| 2 | **고정 기술 스택**과 단계별 데이터 흐름 |
| 3 | 기준 문서 목록 |
| 4 | 저장소·구조 규칙 |
| 5 | TypeScript·Zod 규칙 |
| 6 | 저장·인증·보안 규칙 |
| 7 | 프론트엔드 규칙 |
| 8 | 백엔드·AI 규칙 |
| 9 | **작업 방식** (계획 제시 → 승인 → 구현) |
| 10 | Agent와 Review 규칙 |
| 11 | **완료 보고 형식** |
| 12 | **금지 사항** |
| 13 | 핵심 원칙 7개 |

9·11·12장이 실무에서 가장 자주 인용된다. 구현 프롬프트마다 "CLAUDE.md 9장에 따라 계획을 제시하고 멈춰라", "보고는 11장 형식으로", "12장 금지 사항을 지켜라"가 들어간다.

### 2.2 `docs/product.md` — 제품 정의

서비스 개요, 핵심 용어 8개, **Value · Epic · Story 3계층**, 사용자 흐름과 로그인 정책, MVP 포함/제외.

Epic 5개 · Story 17개가 여기서 정의되고, 모든 기능은 어느 Story에 속하는지 추적된다.

### 2.3 `docs/domain-policy.md` — 도메인 규칙

**상태 머신과 비즈니스 규칙의 유일한 출처.**

| 주요 내용 |
|---|
| Question 상태 전이 |
| **Agenda 상태 머신** (draft → conflicted → passed/rejected/recheck_requested → reanswered) |
| `resolution_reason` 8종의 의미 |
| 재검토 1회 제한 규칙 |
| 완료 조건 (모든 Agenda가 passed 또는 rejected) |
| 값 부재 규칙 (`null` vs `NO_VALUE`) |
| 삭제·보관 정책 |
| 단일 SourceAnswer Fallback |

### 2.4 `docs/data-model.md` — 데이터 모델

테이블 정의, 컬럼, 제약, Enum, 인덱스, JSONB 사용 범위.

특징적인 것은 **CHECK 제약을 문서에 텍스트로 명시**한다는 점이다. 예:

```text
resolution_reason IN ('auto_consensus', 'auto_single_source',
                      'user_accepted', 'user_accepted_after_recheck')
→ selected_source_ref = 실제 출처 참조 (NOT NULL, NO_VALUE 아님)
```

이 문서와 실제 마이그레이션 SQL이 어긋나면 사고가 난다. 그래서 Spec 작성 시 **실물 SQL을 열어 대조**하는 절차가 있다.

### 2.5 `docs/decisions/ADR-*.md` — 결정 기록

되돌리기 어려운 선택을 **배경 → 결정 → 결과** 형식으로 남긴다.

현재 5개: Supabase Auth / 데이터 접근 클라이언트 이원화 / AI Provider 범위 / Astryx 디자인 시스템 / AI 파이프라인 모듈 경계.

### 2.6 `docs/specs/SPEC-*.md` — 구현 명세

### 2.7 `docs/status.md` — 실행 기록

## 3. Spec 문서의 형식

Spec은 정해진 뼈대를 따른다. SPEC-AI-002(약 1,400줄)를 예로 든다.

```text
헤더
├── 상태 (작성 중 / Ready / 완료)
├── 기준 문서 목록 (장 번호까지)
└── 작성 방식 (누가 무엇을 결정했는지)

0장. 고정 사항 — 재질문 안 함
├── 0.1 한 줄 목표
├── 0.2 기존 문서에서 오는 고정 규칙
│       (도메인 정책 / 데이터 모델 / ADR / 이전 Spec / 조사 결론)
├── 0.3 제외 범위 (무엇을 어느 Spec이 다루는지)
└── 0.4 이 단계의 한계 (명시)

1장. 결정 사항 요약
└── 논점 / 결정 / 근거 표 — 사용자가 확정한 것

2~N장. 구현 명세
└── 단계별 상세, 스키마, 규칙

후반부
├── 스키마·정책 변경 목록 (Zod / 마이그레이션 / 기준 문서 개정)
├── 관측 지표
├── 프롬프트·모델 설정
├── 보안 (위협 모델·방어)
├── Acceptance Criteria (체크박스)
├── 알려진 한계
├── 제외 범위·후속 연결
└── 개정 기록
```

### 3.1 0장 "고정 사항"의 의미

**"이 Spec에서 재논의하지 않는다"**는 선언이다.

기존 문서에서 온 규칙, 이전 Spec에서 확정된 것, 조사로 결론 난 것을 모아둔다. 이걸 명시하지 않으면 매번 같은 논의를 반복하게 된다.

예를 들어 SPEC-AI-002의 0.2절은 조사 결론 5개를 "재논의 없는 전제"로 올렸다.

- 묶기와 판정은 다른 질문이므로 2단 구조가 필수
- 순수 임베딩 클러스터링 단독, 방법 A는 탈락
- 한 섹션이 여러 쟁점에 속할 수 있게 허용
- provider 입력 순서를 셔플하고 그 순서를 기록
- 2:1 부분 합의는 자동 다수결 금지

### 3.2 1장 "결정 사항"의 의미

**사용자가 직접 내린 결정과 그 근거**를 표로 남긴다. Agent는 논점과 선택지를 제시했을 뿐이다.

SPEC-AI-002의 1장은 11건을 담고 있다. 각 행은 `논점 / 결정 / 근거` 3열이다. 근거 열이 중요하다 — 나중에 "이거 왜 이렇게 했지"를 되짚는 **유일한 기록**이 된다.

### 3.3 개정 기록

Spec은 살아 있는 문서다. 구현하며 발견된 것이 반영된다.

SPEC-AI-002의 개정 기록:

| 일자 | 내용 |
|---|---|
| 2026-07-29 | 최초 작성 — 결정 11건 확정 |
| 2026-07-29 | 실물 코드·마이그레이션 대조 검토 반영 |
| 2026-07-29 | T-019.1 구현 회귀 반영 |
| 2026-07-29 | 구현 분할 중 발견된 모호성 해소 |

**"무엇이 왜 바뀌었는지"**를 남기는 것이 목적이다.

## 4. 문서 작성 원칙

### 4.1 결정과 근거를 함께 남긴다

결정만 남기면 나중에 뒤집을 때 무엇을 잃는지 모른다.

```text
나쁨:  selected_source_ref에 실제 참조를 저장한다.

좋음:  selected_source_ref에 실제 참조를 저장한다.
       (합의 내용의 출처가 3열 재구성·투명성에 필요.
        누가 골랐는지는 resolution_reason으로 구분 가능)
```

### 4.2 미결정을 명시한다

"아직 정하지 않았다"를 문서에 남긴다. 그러면 나중에 그 자리를 찾을 수 있다.

`SPEC-SCHEMA-001`에는 이런 항목이 있었다.

> | 2-2 | 충돌 입장(stance)·`sourceRefs`의 모양 | **(b) 자유형 JSON 유지** — 정식 모양은 SPEC-AI-002(Manager)에서 확정 |

그리고 SPEC-AI-002가 실제로 그것을 확정하자, 해당 행에 취소선과 "확정 완료" 표기가 붙었다.

### 4.3 부수 효과를 기록한다

결정이 만드는 파급을 적는다.

> **부수 효과가 하나 생긴다.** `auto_consensus`가 `NO_VALUE` 쪽에서 빠지면서, **`"NO_VALUE"`는 사용자 행동에서만 발생하는 값**이 된다. Manager는 절대 만들지 않는다. 데이터만 보고 "AI가 만든 것인지 사람이 쓴 것인지"를 즉시 구분할 수 있다.

### 4.4 실패 조건을 미리 정한다

"이 지표가 이렇게 나오면 이 설계는 틀린 것"을 미리 적어두면, 나중에 순환 논리에 빠지지 않는다.

> 실측 20~30건 축적 후
>   `confidence` 표준편차 < 0.05 → 자기보고 확신도는 무의미하다고 판정
>                                → 소수 샘플 reorder로 신호 전환

### 4.5 문서 간 참조는 장·절 번호까지

"`domain-policy.md` 참조"가 아니라 "`domain-policy.md` §4.2"로 쓴다. Spec의 기준 문서 목록도 장 번호를 포함한다.

## 6. 이 체계가 만드는 효과

| 효과 | 메커니즘 |
|---|---|
| **결정이 사라지지 않는다** | 1장 결정 표 + 근거 열 + 개정 기록 |
| **같은 논의를 반복하지 않는다** | 0장 고정 사항 |
| **문서와 코드가 어긋나면 잡힌다** | Spec 작성 시 실물 대조, 구현 보고 시 Spec 대조 |
| **미결정을 잊지 않는다** | 명시적 미결정 표기 + status.md 상시 목록 |
| **범위가 번지지 않는다** | 제외 범위 표 (무엇을 어느 Spec이 다루는지) |
| **세션이 바뀌어도 이어진다** | HANDOFF 문서 |
| **완료 여부를 다투지 않는다** | Acceptance Criteria 체크박스 |
