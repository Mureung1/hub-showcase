## Day 6 (7/13) — FE·BE·Supabase 수직 슬라이스

### 새로 알게 된 점
- `service_role` 키는 권한이 강해서 React 환경변수에 넣으면 안 된다. 이번 구조는 `React → Express → Supabase`로 두고 서버의 `.env`에서만 읽는다.
- Supabase의 DB 컬럼은 `snake_case`, 화면에서 쓰는 값은 `camelCase`라서 서버 서비스에서 한 번 변환하면 프론트 코드가 단순해진다.
- “AI 결과를 수정한 뒤 저장”하려면 정리 결과 미리보기와 DB 저장을 같은 요청으로 묶으면 안 된다. `POST /api/checkins/preview`와 `POST /api/checkins`로 단계를 나누었다.
- Vite 빌드가 Windows 샌드박스에서 `spawn EPERM`으로 실패할 때 `--configLoader runner`를 사용하면 보조 프로세스 의존을 줄여 검증할 수 있다.

### 이번 시행착오
- npm 기본 캐시가 프로젝트 밖에 있어서 권한 오류가 났다. `npm install --cache .npm-cache`로 프로젝트 내부 캐시를 사용해 해결했다.
- UI부터 한 번에 만들기보다 `DB 스키마 → 서버 연결 → API 미리보기 → React 연결 → 통합 검증` 순서로 나누니 실패 지점이 명확해졌다.
- Gemini 2.5는 내부 사고 토큰도 출력 한도에 포함한다. `max_tokens`가 너무 작으면 JSON 응답이 시작 부분에서 잘릴 수 있어, 실제 `finish_reason`과 응답 길이를 확인해야 한다.
- LiteLLM의 `response_format: { type: "json_object" }`로 JSON 출력을 강제하고, 서버에서 다시 세 필드를 검증했다. 그래도 형식이 틀리면 1회 재시도한 뒤 mock으로 전환했다.

### Slack 공유 초안
Supabase를 처음 Express와 연결하면서 `service_role` 키는 절대 프론트에 두면 안 된다는 걸 배웠습니다. React가 Supabase를 직접 호출하지 않고 Express를 거치게 했고, DB의 `snake_case`를 서버에서 `camelCase`로 변환했습니다. 또 AI 결과를 사용자가 수정한 뒤 저장하려면 “미리보기 API”와 “저장 API”를 나누는 게 중요했습니다. Windows 샌드박스의 npm 캐시/빌드 권한 문제도 프로젝트 내부 캐시와 Vite config runner로 우회했습니다.

## Day 2 (7/7) — 서비스 개발 흐름 6단계

### 01. 기획 (Discovery & Plan)
- 과정: 문제 정의 → 사용자·시장 리서치 → 요구사항 정리 → 기능 우선순위 → 범위·일정 산정
- 협업: 기획·디자인·개발이 킥오프에서 목표와 성공 기준 합의
- 도구: Notion, Jira / Linear, Slack, Figjam

### 02. 설계 (Design)
- 과정: UX → 와이어프레임 → UI → 디자인 시스템 → 아키텍처·데이터모델·API 설계
- 협업: 디자이너 → 개발 핸드오프, 기술 설계 리뷰. 프론트·백엔드가 API 명세(요청/응답) 합의
- 도구: Figma, Excalidraw, ERD, OpenAPI

### 03. 개발 (Build)
- 과정: 프론트엔드(화면·상태·라우팅) / 백엔드(API·인증·로직) / 데이터베이스 / 로컬 개발환경
- 협업: 이슈 분담·브랜치 전략, 데일리 스탠드업. 합의된 API 계약 기반으로 프론트·백 병렬 개발(mock 활용)
- 도구: VS Code, Git·GitHub, Node·npm, Docker

### 04. 검증 (Test & Review)
- 과정: 단위·통합·E2E 테스트 → 코드 리뷰(PR) → QA → 버그 수정
- 협업: PR 리뷰·승인, CI가 커밋마다 자동 검사
- 도구: Vitest/Jest, Playwright, GitHub Actions, ESLint

### 05. 배포 (Ship · CI/CD)
- 과정: 빌드 → 스테이징 확인 → 릴리스 → 환경변수·시크릿 관리 → 롤백 대비
- 협업: 릴리스 승인 후 배포 파이프라인(CI/CD)이 자동 반영
- 도구: GitHub Actions, Vercel, Docker, AWS

### 06. 운영 (Operate & Iterate)
- 과정: 모니터링·로그·에러 추적 → 성능 관리 → 사용자 피드백 수집 → 회고
- 협업: 온콜 대응, 스프린트 회고로 배운 것을 다음 계획에 반영
- 도구: Sentry, GA·Amplitude, 대시보드

> 내 프로젝트 매핑: 지금은 01(기획) 단계. 이번 주 = 기획+설계, 금요일 프로토타입 데모. 2~3주차 = 개발/검증, 배포는 3주차에 미리 뚫기.

## Day 2 (7/7) — 기획 수업

### 기획 프로세스
- 순서: 문제 발견 → 문제 정의 → 사용자 시나리오 → 핵심 기능 → MVP
- 좋은 문제 정의 = 행동 단위의 구체적 순간 (예: "스터디원이 출석을 수기로 적다가 자주 빠뜨린다"). 사회 통계/배경 설명은 문제 정의가 아님
- 사용자 시나리오 = 인터랙션 단위로, 화면이 상상될 정도로 구체적으로 ("검색창을 누른다 → 카드를 클릭한다 → 상세로 들어간다")
- 핵심 시나리오 2~3개만 뽑아서 깊게. 전체 페이지 다 기획하지 말고 핵심 기능 1~2개만 스펙 좁혀가기
- 시각화 필수: 손그림/PPT/피그마로 화면 그려서 AI에 주면 쓸데없는 결과물이 안 나옴. 예쁠 필요 없음. 기준을 내가 잡아야 AI 결과물을 판단할 수 있음

### 문서 관리
- 자료 분산 금지. 레포 안에 md로 모으기 → AI가 참고할 수 있음
- 구조 예시: `docs/plan.md`(마스터플랜), `docs/specs/feature-○○.md`(기능별 명세), `docs/architecture.md`
- README = 프로젝트 대문. 위키 = 리서치 결과·기술 리포트·트러블슈팅 저장소
- 나중에 선배/회사가 저장소 볼 때: ①커밋 로그(작게 쪼갰나, AI 쓰나) ②README/문서화 순으로 봄 → 이력 관리로 중요

### 프롬프트 엔지니어링

**핵심 원리**: 프롬프트 = AI에게 주는 작업 지시서. AI는 준 정보(맥락) 안에서 가장 그럴듯한 답을 만들고, 안 준 건 알아서 가정함 → 그 가정이 내 의도와의 틈이 됨. 프롬프트는 "코드 대신 쳐줘"가 아니라 **AI가 가정할 여지를 줄이는 일**. "알아서 잘 해줘"는 결정권을 AI에 넘기는 것 → 내 서비스가 아니게 됨.

**좋은 프롬프트 5요소**
| 요소 | 무엇 | 예 |
|---|---|---|
| 맥락 | 스택·제약·목표 | "React+TS, 외부 라이브러리 없이" |
| 구체성 | 무엇·어디·어떻게 | "NewsCard 컴포넌트, src/components에" |
| 역할·예시 | 역할 부여·입출력 예 | "너는 시니어 FE야 / props 예: {title}" |
| 단계화 | 작게 쪼개기 | "먼저 UI만, 그다음 이벤트" |
| 검증 요청 | 확인 방법까지 | "끝나면 어떻게 확인하는지 알려줘" |

**나쁜 예 vs 좋은 예**
```
나쁜 예: "뉴스 카드 만들어줘"
좋은 예: "React + TypeScript로 NewsCard 컴포넌트 만들어줘.
  - props: title(string), source(string), thumbnail(string)
  - 파일 위치: src/components/NewsCard.tsx
  - CSS Modules 사용, 외부 UI 라이브러리 없이
  - 끝나면 어떤 props로 렌더 확인하면 되는지 알려줘"
```

**안티패턴 4개**
1. 추상어·형용사: "예쁘게/깔끔하게/잘" → 기준이 없음
2. 한 번에 다: "로그인부터 결제까지" → 통째로 실패
3. 맥락 생략: 스택·파일 위치 안 줌 → AI가 멋대로 구조 결정
4. 검증 없음: "됐니?"만 물음 → 진짜 되는지 확인 안 됨

**단계적 개발 — 쪼개는 3축**
- 레이어 축: UI → state·event → API → 응답 렌더링
- 중요도 축: 핵심 기능 → 옵션 기능 → 예외 처리
- 완성도 축: 최소 기능(MVP) → 개선 → 스타일링
- 한 덩어리가 크면 AI도 실패하고 나도 검증 못 함 (현업 task 단위: 30분~2시간)

**계획(Plan) 모드 — 짜기 전에 합의**
```
"바로 코드 짜지 말고, 먼저 어떻게 만들지 계획만 보여줘.
 컴포넌트 구조 / 상태 / 데이터 흐름 순으로."
→ (계획 받음) → 내가 검토·수정 → "이대로 진행"
```
방향이 틀리면 코드 나오기 전에 잡음 → 시간 절약. AI와 계획에 대한 공감대를 맞추는 목적 (Shift+Tab, 코드 수정 불가)

**리프롬프트 — 틀렸을 때 고쳐 받기**
- 공식: **현상 + 원인 추정 + 원하는 상태 + 건드리지 말 것 명시**
```
나쁜 예: "이상하다 이상해! 다시 해줘"
좋은 예: "카드가 세로로 쌓이는데 가로 3개씩이어야 해.
  flex-direction이 column인 것 같아, row로 바꿔줘.
  나머지는 그대로 둬."
```
- "다 갈아엎어줘"는 멀쩡한 부분까지 망가뜨림 → 범위를 좁혀 요청

**셀프 점검 4문항**
1. 내 프롬프트에 맥락(스택·제약)이 들어 있나?
2. 한 번에 너무 많이 시키지 않았나? (단계화)
3. "끝나면 이렇게 확인"까지 요청했나?
4. 결과가 틀렸을 때 범위를 좁혀 고쳐 요청했나?

### 실전 패턴
- **역질문 패턴**: "만들어줘" 대신 "이거 만들 건데 궁금한 것 10개 물어봐" → 답변하면서 AI가 스펙 문서화. AI는 기본적으로 사용자를 귀찮게 안 하려고 안 물어보고 지 맘대로 하므로, 물어보게 만들어야 함
- **체크리스트 패턴**: 할 일을 md 체크리스트로 만들고 "첫 번째 것만 개발해, 끝나면 체크 표시" 식으로 하나씩
- **플랜 모드 (Shift+Tab)**: 코드 수정 불가 모드. 계획 단계에서 거의 필수. AI와 계획에 대한 공감대를 맞추는 목적
- 예시(few-shot)를 주면 정답에 가깝게 나옴
- 간단한 작업은 저렴한/빠른 모델로 (계획 세우기 등)
- 목(mock) 데이터로 먼저 개발, API 전환은 어댑터 모듈로 의존성 분리
- **프롬프트 피드백 패턴**: 5요소를 AI에 주고 "이 기준으로 내 질문 자체를 점수/피드백해줘" → 내 프롬프트 실력을 개선
- **의도를 담은 역질문**: 내가 고르는 대신 의도를 주고 물어보기 — "뉴스 9개 미만이 대표 페이지에 잘 보여야 해. UX 관점에서 가장 좋은 레이아웃은?" → AI 추천 받고 내가 결정
- 체크리스트는 **의존성 순서**로 배치 ("이 작업이 끝나야 다음이 가능한 순서로 정렬해줘")

### 커밋/PR 규칙
- 커밋은 작게, 의미 있는 단위로 (환경 세팅 하나, 컴포넌트 하나). 문제 생겼을 때 원인 커밋을 찾을 수 있어야 함
- PR도 작게. PR은 하루 1개, 열어두고 push하면 자동 업데이트
- 기획은 언제든 바꿔도 됨

## Day 1 (7/6) — 환경설정 & Git

### Fork 기반 PR 워크플로우 (매일 반복)
```
①lucas로 upstream에 내 브랜치 생성 → ②Fork → ③Pull(clone) → ④작업 branch 생성
→ ⑤Agent로 개발 → ⑥commit(작게) → ⑦내 Fork로 push → ⑧원본의 내 브랜치로 PR
```
- UPSTREAM = 원본 저장소 (connect-AIAgentChallenge-26-1) / ORIGIN = 내 Fork (Yooseunghyeok) / LOCAL = 내 컴퓨터
- ①~③은 일회성. 매일 도는 건 ④~⑧
- 원본에 브랜치가 있어도 내 로컬/포크에는 없음 (완전히 분리된 저장소) → 로컬에 작업 브랜치 따로 생성
- upstream이 매일 바뀜(수십 명 PR) → 가끔 `git pull upstream main`으로 동기화 필요

### React/Vite 기초
- React = 화면을 컴포넌트(블록) 단위로 조립하는 라이브러리. 함수 하나가 화면 조각(JSX)을 return
- Vite = JSX를 브라우저가 읽는 JS로 변환 + 개발 서버 (HMR: 저장하면 새로고침 없이 반영)
- 렌더링 체인: index.html → main.jsx → App.jsx → 내 컴포넌트
- npm install = package.json 명세대로 의존성 설치 / npm run dev = 개발 서버 실행

### 시행착오
- Agent가 절대경로 처리 꼬여서 엉뚱한 중첩 폴더에 스캐폴딩 → Agent 출력을 그대로 믿지 말고 결과를 눈으로 확인할 것
- claude CLI는 레포 폴더 안에서 열어야 프로젝트를 제대로 인식
- git clone하면 현재 폴더 안에 레포 이름의 새 폴더가 생김
