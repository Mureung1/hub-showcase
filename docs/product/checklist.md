# 나만의 레시피북 MVP 티켓

이 문서는 구현 티켓, 작업 범위와 완료 판단의 기준이다. 티켓 ID를 지정해 분석, 구현 또는 상태 확인을 요청할 수 있다.

```text
FE-RECIPE-002 티켓 분석해줘
BE-AI-001 구현해줘
QA-CORE-001 상태 알려줘
```

## 티켓 규칙

- ID 형식은 `<영역>-<기능>-<3자리 번호>`를 사용하고 기존 ID를 변경하거나 재사용하지 않는다.
- 영역은 `COMMON`, `FE`, `BE`, `DB`, `QA`, `OPS`를 사용한다.
- 각 티켓은 목표, 선행 티켓, 세부 작업별 완료 기준과 티켓 검증을 포함한다.
- 상위 티켓은 모든 세부 작업과 검증이 끝났을 때만 `[x]`로 변경한다.
- 부분 구현은 증거가 있는 항목만 `[x]`로 표시하고 상위 티켓은 `[ ]`로 유지한다.
- 실제 화면, Express API, PostgreSQL과 인증·권한이 필요한 티켓은 Mock만으로 완료하지 않는다.
- 공유와 삭제·복원은 P0 핵심 흐름이 완료된 뒤 진행한다.
- P2는 선택 범위가 아니라 MVP 출시 전에 수행하는 품질·운영 단계다.

## 티켓 적절성 기준

### 역할과 책임

- React는 화면 렌더링, 폼·UI 상태와 API 연결을 담당하고 PostgreSQL이나 Supabase Data API를 직접 호출하지 않는다.
- Express는 인증, 외부 입력 검증, 권한, 비즈니스 정책과 PostgreSQL 데이터 처리를 담당한다.
- Route는 경로와 Middleware 연결, Controller는 HTTP 입출력, Service는 비즈니스 규칙, 데이터 접근 코드는 PostgreSQL 처리를 담당한다.
- 현재 규모에서 역할이 섞이지 않는 작은 Route Handler는 계층 분리만을 위해 여러 파일로 나누지 않는다.

### 기존 구조와 최소 변경

- 새 파일이나 컴포넌트보다 기존 API Client, 인증 Middleware, 오류 응답, 화면 컴포넌트와 SQL 패턴을 우선 재사용한다.
- 현재 폴더 구조를 유지하고 실제 사용 사례가 없는 추상화, 헬퍼, 설정과 라이브러리를 추가하지 않는다.
- 티켓 완료에 필요한 파일만 수정하고 관련 없는 리팩터링을 포함하지 않는다.
- 최소 변경을 이유로 입력 검증, 오류 처리, 보안, 접근성 또는 타입 안전성을 생략하지 않는다.
