# 2주차 실행 계획 — 작성 경험 수직슬라이스

> 이 문서는 이번 주(월~목)의 **실행 뷰**다. 4주 전체 우선순위·범위의 단일 출처는 [`BACKLOG.md`](./BACKLOG.md)이고, 여기서는 그중 2주차 P0를 하루 크기 작업으로 쪼개 요일에 배치한다. 대시보드(GitHub Issues/Projects)의 각 이슈가 아래 작업과 1:1로 대응한다.

## 이번 주 목표

**핵심 기능 하나를 FE→BE→DB 한 사이클로 완성한다 (수직슬라이스).**

- 완성할 기능: **역기획서 초안 저장·발행** — 에디터에서 작성 → 저장 요청 → 백엔드 처리 → Supabase 저장 → 응답 → 화면 반영, 그리고 아카이브에서 다시 조회.
- 왜 이 기능인가: 기획서 §7과 BACKLOG의 "2주차 말까지 '작성·저장'이 실제 계정·DB로 되어야 한다" 기준선과 일치한다. LLM(4주차)·코멘트(3주차)에 의존하지 않고 전체 스택을 한 번 관통하는 가장 작은 사이클이다.
- 이번 주 산출물: 위 기능 + **계획 수립 Agent**(월) + **기능 검증 Agent**(화).

## Agent 리뷰 비교

계획 수립 Agent(`plan-breakdown`)의 방법론으로 이번 주 요구사항을 **독립 분해**시킨 뒤(내 표를 안 보여준 상태), 위 계획과 비교했다. Agent가 짚은 4가지와 내 반영:

1. **"한 테이블" 해석 (반영함).** 과제는 "Supabase 한 테이블에 저장·조회"라고 명시하는데 내 초안은 `documents`+`sections` 2개 테이블이었다. Agent 제안대로 **`documents` 단일 테이블 + `sections`를 JSONB 컬럼**으로 바꿨다(위 T2). 과제 문구에 충실하고 슬라이스가 단순해진다. 대신 3주차 섹션별 코멘트에서 JSONB 인덱스로 매핑해야 하는 부채가 생기므로, 그때 정규화 여부를 다시 판단한다.
2. **로그인 미포함 → `author_id` 익명 placeholder (반영함).** 로그인은 1주차 P0인데 이번 슬라이스엔 없다. 저장 문서의 `author_id`는 익명 placeholder로 두고, 실제 계정 연결은 이월한다(아래 "이월" 참조).
3. **마크다운 에디터 라이브러리 우선순위 이견 (의도적 유지).** BACKLOG는 에디터 라이브러리 통합을 2주차 P0로 둔다. 하지만 이번 주 과제의 핵심은 "FE→BE→DB 한 사이클 완성"이라, 기존 textarea 프로토타입을 그대로 두고 **저장·발행 슬라이스를 P0로, 에디터 라이브러리는 P1(T12)로** 내렸다. 슬라이스가 완성되면 다음 순번으로 올린다. — 이 판단은 BACKLOG 우선순위를 한 항목 뒤집는 것이므로 여기 명시해 둔다.
4. **Supabase 키가 최대 크리티컬 패스 (반영함).** 화요일 BE 작업 전체가 T2(사용자 Supabase 키)에 걸려 있다. → **오늘(월) 안에 Supabase 프로젝트 생성 + 키 확보**를 최우선 액션으로 올린다.

**이월(이번 주 밖):** 로그인/회원가입(1주차 P0) → 실제 `author_id` 연결. `sections` 정규화 재검토(3주차 코멘트 때). 마크다운 에디터 라이브러리(슬라이스 후 다음 순번).
