왜 발송한 날을 빼고 계산하나

캠페인을 보낸 날은 더 이상 '평상시'가 아니다. 실제로 발송이 5건 쌓이자 비의 영향이 −22% → −19%로 흐려져 판정이 뒤집혔다. 그래서 진단은 발송일을 빼고 계산한다 — 도식 맨 아래 학습 고리가 하는 일이 이것이다.

설계 판단 세 가지도식만으로는 안 보이는, 왜 이렇게 짰는지

A — 날씨를 두 곳에서 받는 이유 한쪽이 죽어도
파이프라인은 안 멈춘다

기상청과 OpenWeatherMap을 동시에 부르고 병합한다. 한쪽이 실패하면 남은 소스로 진행하고, 둘 다 실패할 때만 멈춘다.

가중기온·습도 = 기상청 0.7 / OWM 0.3
보수강수량·확률은 max 채택 — 한 소스라도 비면 비로 본다
절약5분 캐시 — 같은 날씨를 반복해 사지 않는다
B — 검사를 두 겹으로 나눈 이유 기계가 쓴 글과 사람이 쓴 글의
기준은 같을 수 없다

같은 검사를 발송에도 걸었더니, 사장님이 직접 쓴 “ICE 아메리카노”가 영어라는 이유로 막혔다. 그래서 기준을 갈랐다.

③④ 생성물가드레일 + 한국어 전용 + 내부정보 노출 금지 → 어기면 재생성
⑦ 사람 편집물가드레일만 — 안전·법규는 지키되 표현은 존중
C — 법을 서버에 둔 이유 UI 체크는 안내일 뿐
법은 발송 API가 막는다

정보통신망법 요건을 화면이 아니라 발송 핸들러에서 강제한다. 프론트를 우회해 API를 직접 호출해도 결과는 같다.
