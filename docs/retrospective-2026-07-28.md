# 개인 회고 — 2026.07.28 (Vercel·Render 배포 준비)

오늘은 프론트엔드를 Vercel에, API 서버를 Render에 나눠 배포하기 위한 환경변수와 설정,
문서를 만들고 둘이 실제로 연결되는지를 로컬에서 검증했다. 커밋 5개와 PR 1개(#2163)를 남겼다.
다만 실제 배포는 아직 못 했다. 콘솔에서 계정으로 해야 하는 작업이 그대로 남아 있다.

## 잘한 일

오늘 가장 잘한 판단은 API 주소를 환경변수로 빼면서 **기본값을 빈 문자열로 둔 것**이다.
기본값을 Render 주소로 두면 편했겠지만 그러면 로컬에서 개발할 때도 배포 서버를 부르게 된다.
빈 문자열로 두니 `apiUrl("/api/subjects")`가 `"/api/subjects"` 그대로여서, 환경변수를
설정하지 않은 로컬은 코드를 바꾸기 전과 완전히 똑같이 동작한다. "새 기능을 어떻게 넣을까"보다
"안 넣었을 때 예전과 같은가"를 먼저 생각한 게 맞았던 것 같다.

어제 회고에 적었던 "고쳤다에서 멈추지 않고 동작한다까지 확인한다"는 습관도 이어졌다.
설정 파일만 만들어놓고 "배포하면 되겠지" 하고 끝낼 수도 있었는데, 그러지 않고 프론트를
`:4173`에, 서버를 `:3999`에 띄운 뒤 `CORS_ORIGIN`을 준 상태로 **배포 상황을 로컬에서 그대로
흉내냈다.** preflight `OPTIONS`가 204로 오고, `POST`가 201로 저장되고, 목록 조회에 그게 들어
있고, `DELETE`가 204로 지워지는 것까지 순서대로 눈으로 봤다.

잘 되는 경로만 보지 않은 것도 좋았다. `CORS_ORIGIN`을 일부러 틀린 주소로 바꿔놓고 요청해서
`Failed to fetch`로 막히는 것까지 확인했다. 성공하는 것만 보면 "가드를 넣었다"는 것만 알지
"가드가 실제로 막는다"는 건 모른다. 그런데 이때 `curl`로는 200이 그대로 오는데 브라우저에서만
막히는 걸 보고, CORS가 서버가 응답을 거부하는 게 아니라 브라우저가 막는 거라는 걸 처음으로
실감했다. 일부러 실패시켜 본 덕에 알게 된 셈이다.

작업 중에 `push`가 거절당했을 때 force를 누르지 않은 것도 다행이었다. 내가 작업하는 사이
원격 브랜치에 커밋이 18개나 올라와 있었는데, 백업 태그를 먼저 만들어두고
`git rebase origin/feature/reflection`으로 내 커밋만 위에 얹으니 충돌은 파일 하나뿐이었다.
그리고 리베이스가 끝난 뒤에 테스트와 빌드, 브라우저 확인을 **처음부터 다시 돌렸다.**
남의 리팩터링이 섞인 이상 리베이스 전에 한 검증은 더 이상 유효하지 않다고 봤는데, 실제로
테스트 개수가 27개에서 59개로 바뀌어 있었다. 다시 돌리길 잘했다.

마지막으로, 오늘 못 한 걸 그냥 안 한 채로 두지 않고 `docs/deployment.md`에 막힌 지점으로
남겼다. Supabase를 왜 연결하지 못했는지(서버가 아직 SQLite를 써서 `DATABASE_URL`을 읽는
코드 자체가 없다), 연결하려면 어느 파일을 고쳐야 하는지까지 적었다. 수업에서 "막힌 지점을
기록하면 최소 목표는 달성"이라고 한 게 이런 뜻이겠구나 싶었다. 어제 아쉬웠던 "문서를 갱신하지
않았다"도 오늘은 지켜서, `README.md`에 배포 섹션을 더하고 가이드 문서를 같이 만들었다.

## 아쉬운 일

그런데 서버 테스트는 오늘도 하나도 안 썼다. 어제 회고에 "다음엔 서버 로직도 테스트부터 짜고
시작한다"고 분명히 적어놓고 안 지켰다. 더 아쉬운 건 오늘 쓴 `CORS_ORIGIN` 파싱 코드가
쉼표로 나누고, 공백을 지우고, 끝 슬래시를 지우고, 빈 값을 거르는 게 전부라서 입력과 출력이
아주 명확한, 테스트하기 딱 좋은 순수 로직이었다는 점이다. 그걸 `curl`로 눈으로만 확인했다.
어제와 완전히 똑같은 패턴을 하루 만에 반복했다.

`feature-verifier`도 이틀 연속 안 썼다. 어제는 "쓸 생각을 아예 못 했다"였는데 오늘은
"구현 직후 돌리는 걸 순서에 고정한다"고 적어놓고도 안 썼으니 오히려 더 나쁘다.

일하는 순서에서도 헛발을 짚었다. 커밋 네 개를 타입별로 정성껏 나눠 만들고 나서 push하는
순간에야 원격이 앞서 있다는 걸 알았다. `git fetch` 한 번이면 시작할 때 알 수 있었던 일이다.
리베이스로 수습은 했지만 애초에 안 겪어도 됐다.

무엇보다 수업의 최소 기준을 아직 못 넘었다. "Vercel 주소에서 화면이 열린다", "Render 주소의
상태 확인 API가 응답한다" 둘 다 아직이다. 계정 작업이라 어쩔 수 없는 부분이 있긴 해도,
오늘 끝난 건 배포가 아니라 배포 준비다. 시작할 때 어디까지가 내 손으로 되는 일이고 어디부터가
콘솔 작업인지 먼저 갈라놨더라면 시간 배분이 달랐을 것 같다.

검증을 끝까지 밀어붙이지 못한 것도 남는다. 화면에서 폼을 채우고 버튼을 눌러 확인하려는데
브라우저가 중간에 멈춰서, `fetch`를 직접 호출하는 방식으로 바꿔 확인했다. CORS를 확인하는
목적으로는 같은 값이지만 "사용자가 실제로 버튼을 누르는 경로"는 끝까지 못 봤고, 왜 멈췄는지도
안 보고 넘어갔다.

## 다음에 다시 한다면

커밋하기 전에 `git fetch`를 하는 걸 아예 순서에 박아두려고 한다. 할지 말지 판단하지 않고
그냥 매번 한다. 오늘처럼 커밋을 다 만든 뒤에 알면 되돌릴 게 많아진다.

테스트는 목표를 작게 잡아야 할 것 같다. "서버 테스트를 쓰자"는 너무 커서 이틀 연속 실패했으니,
다음엔 `CORS_ORIGIN` 파싱처럼 함수 하나짜리 순수 로직부터 쓴다. 그 정도면 5분이면 된다.
큰 결심 대신 작은 것 하나로 시작해야 실제로 손이 갈 것 같다.

배포처럼 외부 서비스가 끼는 작업은 시작하기 전에 "내 손으로 되는 일"과 "콘솔 작업"을 먼저
갈라놓고 들어가려 한다. 그래야 오늘 어디까지 갈 수 있는지 처음부터 알 수 있다.

검증이 막혔을 때는 우회하기 전에 왜 막혔는지 한 번은 보고 넘어가려 한다. 생각해보면
어제 회고에 쓴 "경고는 끄기 전에 왜 나는지 한 번 더 본다"와 똑같은 실수다. 대상만 바뀌었다.

그리고 "다음에 할 것"은 이제 정말 이슈로 만들어야겠다. 어제 회고에 적어놓고 오늘도 안 했고,
그래서 Supabase 마이그레이션이 이번에도 문서에 "다음에"라고 적혔다. 3주 연속 같은 자리다.
다음 작업은 이슈를 등록하는 것부터 시작한다.

## 오늘 배운 것 한 줄

회고에 적은 것 중에서도 이미 한 번 해본 것만 지켜졌다. "확인하고 보고한다"는 어제 실제로
해봤기 때문에 오늘 자연스럽게 나왔지만, 테스트와 검증 에이전트는 적어두기만 했더니 이틀 연속
그대로 넘어갔다. 적는 걸로 습관이 되는 게 아니라, 한 번이라도 실제로 해봐야 다음에 손이 간다.
