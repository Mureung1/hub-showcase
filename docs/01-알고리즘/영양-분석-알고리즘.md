# 영양 분석 알고리즘

사진(또는 메뉴명) → 실제 영양 수치까지 가는 계산 로직. 화면/저장 구조는
[../03-개발스펙/architecture.md](../03-개발스펙/architecture.md)를, 코드 위치는 `CLAUDE.md`의
"Core domain flow"를 참고. 이 문서는 **로직 자체**만 다룬다.

---

## 1. 하이브리드 매칭 — AI는 "무엇·얼마나"만, 수치는 공공 DB가 우선

AI(Gemini)는 음식 식별과 섭취량(g) 추정만 담당하고, 실제 영양 수치는 식약처 공공 DB를 우선
사용한다. AI 추정치(`estimatedNutrients`)는 DB 매칭이 전부 실패했을 때만 쓰는 최종 폴백이다.

### 탐색 순서 (`src/pages/Analyze.jsx`의 `findFoodMatch`)

AI가 반환하는 두 검색어 — `dbSearchName`(표준명)과 `fallbackSearchName`(넓은 범주명) — 를
아래 순서로, 중복 없이(같은 `(검색어, DB종류)` 조합은 한 번만) 시도한다. 앞에서 매칭되면 그 결과를
쓰고 나머지는 건너뛴다.

1. **음식 DB**에서 `dbSearchName` 검색
2. `dbSearchName`을 **정규화 표준명**으로 변환해(`src/lib/foodNameMap.js`의
   `normalizeFoodSearchName` — 예: 돌솥비빔밥→비빔밥, 신라면→라면) 음식 DB 재검색
   — AI가 넘긴 검색어가 충분히 일반적이지 않을 때의 안전망
3. **가공식품 DB**에서 `dbSearchName` 검색
4. `dbSearchName`에서 **앞 2글자 수식어를 뗀** 이름으로 음식 DB 재검색
5. **음식 DB**에서 `fallbackSearchName` 검색
6. 정규화 표준명으로 **가공식품 DB** 검색
7. **가공식품 DB**에서 `fallbackSearchName` 검색
8. 전부 실패 → **AI 추정치**(`estimatedNutrients`) 사용

서버가 `FOODDB_CONNECTION_FAILED`(상류 DB 접속 불가)를 보고하면, 남은 단계를 전부 죽은 호스트에
재시도하지 않고 그 즉시 캐스케이드를 중단한다.

### 양 환산

- DB 값은 기준량(보통 100g)당 수치 → `scaleNutrients(dbNutrients, baseValue, grams)`로 실제
  소비량에 맞춰 환산한다.
- 가공식품은 DB의 `servSize`(1회 섭취참고량)를 그램 기준으로 우선 사용(더 정확), 없으면 AI의
  `estimatedGrams`.
- DB 레코드에 없는 개별 항목(예: 식이섬유)만 `fillMissingNutrients`로 AI 값을 보완한다.

### 현실성 보정 (`clampToPlausibleNutrients`, `src/lib/nutrition.js`)

DB 레코드의 **1회 제공량 자체가 비현실적인** 경우(예: 특정 음식 DB 레코드가 과대/과소 수치를
가진 경우)를 키워드 매칭으로 보정한다 — 짜장면/비빔밥/찌개 등 잘 알려진 한식 메뉴의 키워드 테이블
(`NUTRIENT_PLAUSIBILITY`)로 상·하한을 건다. DB 매칭이 없어 AI 추정치를 쓸 때도 동일한 보정을
거친다. 새 예외 케이스는 이 키워드 테이블에 추가하는 방식으로 확장한다(코드 분기를 늘리지 않는다).

### 출처 배지 (신뢰도 투명화)

| 배지 | 의미 |
|---|---|
| 식약처DB | 음식 표준DB 매칭 |
| 식약처DB(가공) | 가공식품 표준DB 매칭 |
| 공식 영양표 | 프랜차이즈로 식별된 경우(AI가 공식 수치 기준으로 응답) |
| 추정 | DB 매칭 전부 실패, AI 추정치 사용 |

## 2. 권장 영양소 계산 (`src/lib/nutrition.js`의 `calcRecommendedNutrients`)

신체정보(나이·키·몸무게·성별·활동량)가 있는 사용자에게만 적용되는, 하루 권장 섭취량 계산이다.
게스트/신체정보 미입력 사용자는 이 계산을 건너뛰고 분석 자체는 그대로 진행한다(권장량 대비 비교만
비활성).

- **BMR (Mifflin-St Jeor)**
  - 남: `10×kg + 6.25×cm − 5×age + 5`
  - 여: `10×kg + 6.25×cm − 5×age − 161`
- **TDEE** = BMR × 활동계수 (low 1.375 / moderate 1.55 / high 1.725)
- **탄단지 기본 비율**: 탄수 50% · 단백 20% · 지방 30% (kcal→g 환산: 탄4·단4·지9 kcal/g)
- **식이섬유**: 여 25g / 남 30g 기본값
- **나트륨**: 2000mg 상한 기준(초과형이라 "부족" 판정 대상이 아님)
- 모두 순수함수로 구현되어 있어 입력이 같으면 항상 같은 결과가 나온다(부작용 없음).

이 6개 지표(`calories`/`protein`/`carbs`/`fat`/`fiber`/`sodium`)가 `NUTRIENT_LABELS`로 앱 전체의
공통 스키마다. 하루 상태(달성/보통/위험) 3단계 판정, 부족 영양소 상위 N개 추출 등도 같은 파일의
분류 함수들이 담당한다.

## 3. 검증 예시 (수치가 말이 되는지 감으로 확인할 때)

- 떡볶이: 음식DB 100g 기준 144kcal → 250g 환산 → 360kcal
- 초코파이: 가공식품DB `servSize` 70g 기준 347.9kcal, DB에 없는 식이섬유만 AI 값으로 보완

개발 중에는 `import.meta.env.DEV`일 때 각 항목 처리 결과가 `[분석 진단]` 로그로 브라우저 콘솔에
찍힌다(매칭된 검색어/그램/최종 영양소) — 정확도 이슈를 조사할 때 여기서부터 본다.
