# 광고 추천 · 리더보드 점수 알고리즘

두 기능 모두 "오늘의 영양 데이터를 하나의 숫자/추천으로 압축"한다는 점에서 계열이 비슷해 한
문서에 묶었다. 기능 자체의 배경(왜 쿠팡인지, 왜 로그인 계정끼리만 비교하는지)은 `CLAUDE.md`의
"Ads" / "Leaderboard" 절 참고.

---

## 1. 영양소 기반 광고 추천 (`src/utils/adRecommendation.js`의 `recommendAdProducts`)

순수 함수. 입력은 오늘 실측 영양 데이터, 출력은 노출할 상품 배열(항상 1개 이상).

### 우선순위

1. **실측 부족 영양소 상위 1~3개**가 있으면, 그 영양소와 매칭되는 상품을 우선 노출한다.
   - 매칭 대상은 앱이 실제로 추적하는 5개 지표 — `protein`/`fiber`/`calories`/`carbs`/`fat`
     (`AD_NUTRIENTS`의 `tracked: true`). `sodium`은 상한형(초과를 막는 지표)이라 "부족" 개념이
     없어 광고 매칭에서 의도적으로 제외된다.
2. 오늘 기록이 없거나 부족 영양소를 계산할 수 없으면(신체정보 없는 게스트 등) **폴백 미량영양소
   목록을 순환**해서 보여준다(`vitaminD`/`calcium`/… 등 앱이 추적하지 않는, 광고 전용 지표).
3. **절대 빈 배열을 반환하지 않는다** — 위 두 경로가 모두 실패할 상황이 없도록 폴백 목록 자체가
   순환하며 항상 최소 1개를 채운다. 배너가 비어 보이는 상태는 설계상 존재하지 않는다.

### 지켜야 하는 제약

- `id`/`nutrient`는 추천 로직이 참조하는 키이므로, 상품 데이터(`src/data/coupangProducts.js`)를
  갱신할 때도 이 두 필드는 건드리지 않는다.
- 법정 고지 문구(`COUPANG_DISCLOSURE`)와 AD 배지는 상품이 몇 개든, 어떤 폴백 상태든 항상
  렌더링된다 — 렌더링을 생략하는 조건분기를 추가하지 않는다.
- 회귀 검증: `npm run check:ads`(`scripts/check-ad-recommendation.mjs`).

### (예정) 상품 데이터 자동 수집

지금은 상품 데이터가 손으로 입력되어 있다. 쿠팡파트너스 검색 API로 자동화하는 설계(오프라인 배치
+ 정적 JSON, 시간당 10회 API 한도 때문에 실시간 호출은 불가능하다는 조사 결과 포함)는
[../03-개발스펙/next-쿠팡API-자동추천-프롬프트.md](../03-개발스펙/next-쿠팡API-자동추천-프롬프트.md)에 정리되어 있다 — 파트너스
API 키 발급 조건(누적 판매 15만원)이 아직 충족되지 않아 **보류 중**이다.

## 2. 리더보드 점수 공식 (`src/lib/nutritionScore.js`의 `calcNutritionScore`)

로그인 계정끼리만 "오늘의 순위"를 비교한다(게스트는 기기에 묶인 임시 식별자뿐이라 비교할 고정
신원이 없음). 오늘 하루의 6개 영양소 실측치와 권장량을 입력받아 단일 점수로 압축한다.

- 이 계산식은 **JS 버전(`nutritionScore.js`)과 SQL 버전(`supabase/schema.sql`의
  `get_daily_leaderboard()`)이 반드시 동일해야 한다** — 한쪽만 고치면 클라이언트 표시 점수와
  서버 순위가 어긋난다. 공식을 바꿀 때는 항상 두 곳을 함께 수정한다.
- `get_daily_leaderboard()`는 `SECURITY DEFINER`로 실행되고 `rank`/`score`/`is_me`만 반환한다 —
  다른 사용자의 실제 섭취 데이터는 어떤 경로로도 노출되지 않는다.
- SQL 함수 자체는 `schema.sql`을 Supabase 프로젝트에 다시 실행해야 반영된다(마이그레이션 파일이
  아니라 스키마 파일에 있음 — 배포 후 잊기 쉬운 지점).
