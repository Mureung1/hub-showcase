## 1. 무엇을 증명하는가

재고 N개짜리 딜에 동시에 M개(M > N)의 예약 요청이 몰려도 **정확히 N건만 성공**하는지 확인한다.

증명 대상은 [dealRepository.decrementStock](../server/src/repositories/dealRepository.js)의 조건부 UPDATE다.

```sql
UPDATE deals SET remaining_qty = remaining_qty - $2
WHERE id = $1 AND remaining_qty >= $2
```

조건 검사와 차감이 한 문장 안에서 일어나므로, 행 락 안에서 원자적으로 처리된다.

### 판정 근거는 반드시 DB다

k6의 성공 응답 수를 세는 것만으로는 **부족하다.** 오버셀은 "서버가 201을 정상 반환했는데
실제로는 재고보다 많이 팔린" 상태이기 때문이다. 응답만 보면 정상으로 보인다.

그래서 최종 판정은 [verifyLoad.js](../server/src/db/verifyLoad.js)가 DB 상태로 내린다.
기획서 §4의 불변식을 직접 검사한다.

```
Deal.남은수량 = 총수량 - Σ(활성 Reservation.수량),  항상 >= 0
```

### CHECK 제약은 방어선이 아니다 (반드시 확인할 것)

락 미적용 경로에서도 `remaining_qty`는 **양수를 유지한다.** 읽은 값 기준으로 절대값을 쓰기 때문에
(`SET remaining_qty = 2`) 음수로 내려갈 일이 없고, `CHECK (remaining_qty >= 0)`이 발동하지 않는다.

검증 출력에서 **오버셀이 18개 났는데도 `[통과] 재고 음수 아님`이 찍히는 것**을 직접 확인하라.
이것이 이 실험의 핵심 교훈이다 — DB 제약만 믿으면 오버셀을 못 잡는다.

## 2. 구성 요소

| 파일 | 역할 |
|---|---|
| [server/src/db/seedLoad.js](../server/src/db/seedLoad.js) | 픽스처 준비 — 전용 딜 재고 리셋 + 소비자 N명 확보, `load/fixture.json` 출력 |
| [load/oversell.js](../load/oversell.js) | k6 시나리오 — 동시 M요청, 응답 집계 |
| [server/src/db/verifyLoad.js](../server/src/db/verifyLoad.js) | **최종 판정** — DB 불변식 4종 검사 |
| `UNSAFE_STOCK=1` | 비교군 스위치 — 락 미적용 경로([decrementStockUnsafe](../server/src/repositories/dealRepository.js))로 전환 |

`seedLoad`는 데모 시딩을 지우지 않고 그 위에 전용 딜 하나를 얹으며, 매 실행마다 해당 딜의
예약을 지우고 재고를 되돌린다(멱등). 회차 사이에 반복 호출하면 된다.

> `load/fixture.json`과 `load/summary.json`은 실행 산출물이라 `.gitignore` 대상이다.

| ID | 재고 | 동시 요청 | 경로 | 기대 성공 | 기대 오버셀 | 확인 포인트 |

| **TC-2** | 3 | 100 | 락 미적용 | 3 초과 | 발생 | `[통과] 재고 음수 아님`이 함께 찍히는 것 |

| **TC-4** | 5 | 50 | 락 미적용 | 5 초과 | 발생 | TC-2와 같은 양상이 재고를 바꿔도 재현되는지 |

TC-2·TC-4의 성공 건수는 **실행마다 달라진다.** 경합 타이밍에 좌우되므로 고정값을 기대하면 안 된다.
"3보다 크다"가 판정 기준이고, 정확한 수치가 아니다.

TC-1이 이 프로젝트의 핵심 주장이고, TC-2는 그 주장이 왜 필요한지 보여주는 대조군이다.

## 5. 실행 절차

터미널 **2개**가 필요하다. 모두 레포 루트(`hub/`)에서 실행한다.

### A. 안전 경로 — TC-1 / TC-3

**터미널 1** — 서버

```bash
npm run dev:server
```

**터미널 2** — 픽스처 → k6 → 검증 순서로 실행한다.

```bash
npm run seed:load -w server -- --stock=3 --users=100
```

```bash
k6 run -e VUS=100 load/oversell.js
```

```bash
npm run verify:load -w server
```

기대 출력:

```
성공_201       3
품절_409       97

[통과] 오버셀 없음 (판매 수량 <= 총 수량) — 판매 3 / 총 3
[통과] 재고 불변식 (남은 = 총 - 판매) — 남은 0 === 3 - 3 = 0
[통과] 재고 음수 아님 — 남은 0
[통과] 픽업코드 중복 없음 — 중복 0건
결과: 전 항목 통과
```

TC-3은 `--stock=5 --users=50`, `-e VUS=50`으로 바꿔 같은 순서를 반복한다.

### B. 비교군 — TC-2 / TC-4

**터미널 1**에서 서버를 끄고(`Ctrl+C`) 플래그를 켜서 다시 띄운다. PowerShell 기준:

```bash
$env:UNSAFE_STOCK=1; npm run dev:server
```

서버 첫 줄에 이 경고가 떠야 비교군으로 동작하는 것이다. 없으면 안전 경로로 돌고 있다.

```
[경고] UNSAFE_STOCK=1 — 락 미적용 재고 차감 경로로 동작합니다. 부하 테스트 전용.
```

**터미널 2**에서 A와 동일한 3개 명령을 반복한다.

> **주의**: `$env:UNSAFE_STOCK`은 그 터미널에 남는다. 안전 경로로 되돌리려면 터미널을 새로 열거나
> `$env:UNSAFE_STOCK=""` 로 지운다. bash라면 `UNSAFE_STOCK=1 npm run dev:server` 처럼 한 번만 적용된다.

| 옵션 | 위치 | 기본값 | 설명 |

## 6. 배포 환경(Vercel / Render / Supabase)에서의 차이

배포 후에는 **k6가 Render를 때리고, seed/verify 스크립트는 로컬에서 Supabase에 직접 붙는다.**

```
[로컬] k6 ──── HTTPS ────> [Render] Express ──── [Supabase] Postgres
[로컬] seedLoad / verifyLoad ──────── DATABASE_URL ────────┘
```

k6는 `-e BASE_URL`로 대상만 바꾸면 되고, 스크립트는 `server/.env`의 `DATABASE_URL`만
Supabase 것으로 바꾸면 된다. 절차 자체는 동일하다.

```bash
k6 run -e BASE_URL=https://<render-app>.onrender.com -e VUS=100 load/oversell.js
```

### 6.1 먼저 손봐야 하는 것 (현재 코드 기준)

배포 전에 확인·수정이 필요한 지점을 코드에서 확인한 결과다.

| 항목 | 현재 상태 | 배포 시 |
|---|---|---|
| 서버 포트 | `process.env.PORT \|\| 4000` ([index.js](../server/src/index.js)) | Render가 `PORT`를 주입 — **그대로 동작** |
| DB SSL | `DATABASE_SSL=true`일 때만 적용 ([pool.js](../server/src/db/pool.js)) | **해결됨.** `connectionString`을 주면 pg가 ssl 옵션을 덮어쓰므로 별도 플래그로 처리. TLS 1.3 확인 |
| CORS | `CORS_ORIGIN` 허용 목록 ([app.js](../server/src/app.js)) | **해결됨.** 미설정 시 전체 허용(로컬), 차단은 403 |
| 클라이언트 API 주소 | `VITE_API_BASE_URL` 주입 ([client.js](../client/src/api/client.js)) | **해결됨.** 미설정 시 `/api` 유지. `vercel.json` rewrite는 `/api`를 제외해야 한다(포함하면 API 응답이 HTML이 되어 흰 화면) |
| 만료 스케줄러 | 웹 프로세스에서 `setInterval` ([index.js](../server/src/index.js)) | Render 무료 티어는 유휴 시 인스턴스가 잠들어 **스케줄러가 멈춘다** |

부하 테스트만 놓고 보면 DB SSL 항목만 해결되면 되지만, 클라이언트 항목은 시연 전에 반드시 필요하다.

### 6.2 측정값이 달라지는 이유

**정확성 결과(TC-1의 "정확히 3건")는 환경이 바뀌어도 유지되어야 한다.** 오버셀 방지는 부하가 아니라
DB 락의 성질에 기대기 때문이다. 이것이 유지되지 않으면 진짜 결함이다.

반면 **응답 시간과 실패 양상은 크게 달라진다.** 로컬 수치와 비교하면 안 된다.

- **Render 무료 티어 콜드 스타트** — 유휴 후 첫 요청은 수십 초 걸린다. k6 실행 전에 헬스체크를
  한 번 호출해 인스턴스를 깨워야 한다. 안 그러면 첫 VU들이 타임아웃으로 잡힌다.
- **네트워크 왕복** — 로컬 p95는 100~200ms대였지만, 인터넷 경유는 지연이 지배적이 된다.
  동시성 경합 자체가 느슨해져 락 미적용 경로에서도 오버셀이 덜 나올 수 있다.
- **Supabase 연결 수 제한** — 무료 티어는 동시 연결이 제한된다. `pg.Pool` 기본 max는 10이라
  100 VU가 몰리면 서버 쪽에서 대기가 생긴다(오류가 아니라 지연으로 나타난다).
- **Supabase 커넥션 풀러** — Session pooler(5432)를 쓴다. 상주 Node 프로세스가 `pg.Pool`로
  커넥션을 들고 있으므로 세션 모드가 맞다. 트랜잭션(`BEGIN`~`COMMIT`, `FOR UPDATE`,
  `FOR UPDATE SKIP LOCKED`)이 풀러를 통해서도 정상 동작함을 실측으로 확인했다.
- **DB 리전은 사용자가 아니라 서버 근처에 둘 것.** DB에 접속하는 주체는 Render다.
  서울→싱가포르로 옮겨 딜 목록이 248ms→111ms가 됐다([최적화.md](./최적화.md) §7.3).

콜드 스타트 회피용 워밍업:

```bash
curl https://<render-app>.onrender.com/api/health
```

### 6.3 배포 환경에서 주의할 것

- **비교군(`UNSAFE_STOCK=1`)을 배포 서버에 켜두지 말 것.** 켠 채로 방치하면 실제 데이터에
  오버셀이 남는다. Render 환경변수로 잠깐 켰다면 측정 직후 반드시 지우고 재배포한다.
- 부하 테스트는 **전용 딜**(`[부하테스트] 선착순 상품`)만 건드리지만, `seedLoad`는 소비자
  계정을 계속 추가한다. 시연용 DB에서 돌렸다면 `load-user-%` 계정이 쌓인 것을 감안한다.
- 공용 무료 티어에 과한 부하를 주면 서비스 약관·레이트리밋에 걸릴 수 있다. VUS를 무리하게 올리지 않는다.

## 7. 트러블슈팅

| 증상 | 원인 | 조치 |
|---|---|---|
| `k6: command not found` | 설치 후 PATH가 갱신 안 됨 | 새 터미널을 연다 |
| `dealId를 찾을 수 없습니다` | 픽스처 미생성 | `npm run seed:load -w server` 먼저 실행 |
| `유저가 부족합니다` | `VUS` > 시딩된 유저 수 | `--users`를 VUS 이상으로 올려 재시딩 |
| `가게가 없습니다` | 데모 시딩 없음 | `npm run seed -w server` 실행 |
| `client password must be a string` | 레포 루트에서 스크립트 직접 실행 (`.env`는 `server/`에 있음) | `npm run ... -w server` 형태로 실행 |
| 500 `reservations_user_id_fkey` | 존재하지 않는 user id로 요청 | 픽스처를 다시 생성한다. `ON CONFLICT DO NOTHING`도 시퀀스를 소모해 id가 연속이 아니므로, k6는 `fixture.json`의 실제 id를 써야 한다 |
| `EADDRINUSE :4000` | 이전 서버가 살아있음 | `Get-NetTCPConnection -LocalPort 4000 -State Listen \| Select -Expand OwningProcess \| Stop-Process -Force` |
| 비교군인데 오버셀이 안 남 | 플래그 미적용 | 서버 첫 줄의 `[경고] UNSAFE_STOCK=1` 을 확인 |
