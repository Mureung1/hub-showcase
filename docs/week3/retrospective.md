# Week 3 회고 — 기업마당 실데이터 크롤러

**프로젝트**: 소상공인 정부지원금 큐레이터 — 업종·지역·규모를 입력하면 조건에 맞는 정부 지원금을
매칭·정렬해 보여주고, 외부 기관 사이트로 신청을 연결하는 MVP 서비스.

## 이번 주 목표

Week 2까지는 샘플 데이터로 온보딩 → 매칭 API → Supabase 조회/저장 → 화면 갱신까지 수직 슬라이스를
완성했다. 이번 주(Week 3)는 그 샘플 데이터를 **기업마당(bizinfo.go.kr) 실데이터**로 교체하는
크롤러 파이프라인을 만드는 게 목표다.

## 진행 과정

1. **조사** — 기업마당에 공식 Open API(REST, JSON/XML)가 있다는 걸 확인, 스크래핑 대신 API로 결정
2. **인증키 발급 (#28)** — 개인 신청은 승인 대기 없이 즉시 발급됨을 확인, 실제 `curl` 호출로
   응답 필드를 재확인(사전 조사 때 추정한 필드명과 실제가 달랐음)
3. **크롤러 워크스페이스 구축 (#29)** — `crawler/` npm workspace 신설, API 클라이언트 구현,
   실제 데이터 수신 확인
4. **데이터 매핑 (#30)** — API 원본 응답을 서비스가 쓰는 `Subsidy` 타입으로 변환하는 로직 작성
   (마감일 계산, 접수방법 정규화, 부족한 필드 fallback 처리), 단위 테스트로 검증

그 데이터를 Supabase에 실제로 채워 넣는 것과 주기 실행 자동화다.

## 전체 코드 기준 — 결정하기 어려웠던 부분 / 오류 / 기술스택 불확실성

Week 3 작업뿐 아니라 프로젝트 전체 코드와 git 히스토리를 훑어 정리했다.

### 결정하기 어려웠던 부분

- SQL 예약어(`match`, `where`) 때문에 DB 컬럼(`match_score`, `apply_where`)과 앱 타입 필드명
  (`match`, `where`)이 달라져서, 모든 경계에서 수동 매퍼(`server/src/db/mappers.ts`)가 필요해짐.
  공유 타입을 바꾸면 이미 만든 화면들이 줄줄이 흔들려서, "DB 컬럼명"과 "앱 타입 필드명"을 아예
  분리하는 쪽을 택함.
- `insertMatchRequest`를 레포 내부(try/catch)와 라우트(또 다른 try/catch) 두 군데서 이중으로
  방어한 것 — 테스트 가능성을 위한 합리적 방어인지, 과한 중복인지 아직 확신이 없음.
- `client.ts`의 fallback과 `insertMatchRequest`의 best-effort 저장은 겉보기엔 같은 "실패해도
  계속 진행" 패턴이지만 목적이 다름(UX 연속성 vs 부가기능 실패가 핵심 기능을 막지 않게) — 이
  구분이 처음엔 명확하지 않았고 나중에야 언어화됨.
- RLS는 켜뒀지만 정책은 하나도 안 만듦 — service_role만 쓰니 지금은 문제없지만, anon key
  경로가 생기면 뭐가 필요한지 스스로도 이해 못 한 부분으로 남겨둠.
- `getSubsidy`/`submitProfile`이 네트워크 오류·404·5xx를 전부 "mock으로 대체"로 동일하게 처리
  — "화면은 항상 뭔가 보여줘야 한다"는 원칙으로 의도적으로 단순화했지만, "진짜 없는 리소스"와
  "서버 다운"을 뭉뚱그리는 부작용도 냄(아래 오류 사례와 연결).
- 크롤러 fallback 값들(`match=50`, `dday=9999`, 자격/서류 안내문구) — 각각 "0%면 오해 소지",
  "정렬 시 뒤로 밀려야 함", "빈 배열이면 섹션이 텅 비어 보임" 같은 UI 부작용을 먼저 따져보고
  정한 값들.
- `OnboardingProfile.creditScore`/`businessYears`를 optional로 둔 것 — plan.md는 업력을
  필수라 하는데, 와이어프레임엔 UI가 없어서 "API엔 있고 화면엔 없는" 상태로 의도적으로 미룸.

### 실제로 오류가 발생했던 부분

- **`getSubsidy` 404 처리 버그** — 서버 404를 "진짜 없음"으로 취급해 mock(8건)으로 안 넘어감.
  서버 샘플이 2건뿐이던 시절이라 상세화면 8건 중 6건이 깨짐. 모든 실패를 mock fallback으로
  통일해 수정.
- **`sort=new` 순서 미보장** — Supabase는 `.order()` 없이 순서를 보장 안 함. curl로
  `['5','6','1',...]` 같은 뒤섞인 순서 확인 → `.order('id', {ascending:true})` 추가로 수정.
- **stale 주석/문서 여러 건** — `client.ts`가 "`POST /api/match` 아직 미구현"이라고 적힌 채
  실제론 이미 구현된 상태로 방치됐던 것, `CLAUDE.md`가 실제로는 없는 `pr-checks.yml` CI를
  있다고 설명하던 것 — 둘 다 검증 과정에서 발견해서 정리.
- **샘플/mock 데이터 개수 불일치** — 서버 시드 2건 vs 클라이언트 mock 8건. 위 404 버그의 실질적
  발생 원인이었고, 시드를 8건으로 맞추면서 해결.
- **bizinfo API 필드명 오추정** — 사전 웹조사로 짐작한 필드명(`title`/`author`/`description`)이
  실제 API 응답(`pblancNm`/`jrsdInsttNm`/`bsnsSumryCn`)과 전부 달랐음. 실제 curl 호출로
  재확인 후 매핑표를 다시 씀.
- **`reqstBeginEndDe`가 항상 날짜 범위는 아님** — `"예산 소진시까지"` 같은 자유 텍스트도 온다는
  걸 실행하고서야 발견, `parseDeadline()`에 별도 처리 추가.
- **`SUPABASE_URL` 오설정 함정** — Supabase 대시보드의 "REST URL"(`.../rest/v1/`)을 그대로
  넣으면 클라이언트가 깨짐. 방어적으로 `.replace()` 처리 추가.
- **`git checkout main -- CLAUDE.md` 실수** — 브랜치 전환 중 방금 만든 편집 내용을 통째로 날림.
  직전에 저장해둔 `git diff` 파일로 복구.
- **캠퍼스 레포 fork PR 자동 머지 실패** — `GITHUB_TOKEN`이 fork PR을 머지할 권한이 없어서
  실패, 수동 머지 + 이후엔 fork 대신 같은 레포에 직접 브랜치 push하는 방식으로 우회.

### 기술 스택/방식이 아직 불확실한 부분

- **README·CLAUDE.md가 크롤러를 "Node.js + Cheerio"라고 여전히 설명** — 실제로는 기업마당
  공식 API를 `fetch`로 직접 호출하고 있어 Cheerio는 아예 안 씀. 문서가 실제 구현을 못 따라감.
- **`npm run crawl` 스크립트가 README에만 존재** — 실제 스크립트명은
  `fetch:sample -w @hub/crawler`.
- **Supabase upsert 파이프라인(#31), cron 자동화(#32) 아직 미착수** — crawler가 데이터를
  가져오고 변환까지는 하지만 DB에 넣는 건 아직.
- **`districts`(전국 지역 데이터) 소스 미정** — 정적 JSON vs API, `CLAUDE.md`에 결정 안 된 채
  남아있음.
- **AI 요약(Claude API) 적용 범위 미정** — 원래 2주차 항목인데 지금(3주차)도 결정 안 됨. 계획이
  슬쩍 밀린 상태.
- **매칭 조건 필터(업종/지역) 미구현** — `subsidies-repo.ts`의 `match()` 함수가 `_profile`
  파라미터를 아예 무시함(밑줄 prefix로 unused 표시). 지금은 정렬만 하고 실제 조건 필터링은 없음.
- **매칭 점수 알고리즘 가중치 미확정** — `match` 필드가 하드코딩된 mock 값이거나 크롤러의 고정
  50점. 진짜 알고리즘은 아직 없음.
- **API 배포 타겟 미확정** — 프론트(GitHub Pages)만 배포됐고, 백엔드 호스팅(Render/Fly 등)은
  후보만 있고 안 정해짐.
- **기존 샘플 데이터를 언제 실데이터로 교체할지 미정** — 크롤러 파이프라인 검증 후로 계속
  미뤄지는 중.
- **K-스타트업/소진공/정부24 등 추가 데이터 소스** — 후순위로만 남아있고 언제 착수할지 트리거
  조건이 없음.

## 이번 주 멘토링 받고 싶은 부분

**작업 과정에서 마주했던 어려움**
- 기업마당 Open API 응답 필드가 사전 조사(웹 검색 요약)와 실제 호출 결과가 달랐다. 공공데이터
  API처럼 문서화가 부실하거나 오래된 API를 실무에서 처음 붙일 때, "일단 호출해보고 확인" 말고
  더 안전하게 접근하는 방법이 있는지 궁금하다.
- Supabase에서 `.order()`를 안 걸면 정렬 순서가 보장되지 않는다는 걸 버그가 나고서야 알았다.
  이런 "당연히 알아야 하는데 몰랐던 함정"을 미리 걸러내는 팀 차원의 장치(체크리스트, 코드리뷰
  관행, 린트 룰 등)가 실무엔 따로 있는지 궁금하다.

**해결은 했지만 '왜' 그런지 완전히 이해하지 못한 문제**
- 매칭 요청 저장(`insertMatchRequest`)을 레포 내부와 라우트 두 군데에서 이중으로 try/catch로
  감쌌다. 테스트 가능성을 위해 일부러 그렇게 했는데, 이게 실무에서도 흔한 "합리적 방어"인지
  아니면 과한 중복으로 보일지 확신이 없다.
- API가 안 주는 필드(지원금액, 자격요건, 매칭점수)에 임시값(`match=50`, 고정 문구 등)을 채워
  넣었다. 이런 "아직 없는 데이터"를 다루는 표준적인 방식이 있는지(예: nullable로 스키마를 열어
  두고 프론트에서 분기 처리 vs 지금처럼 그럴듯한 기본값으로 채우기) 궁금하다.

**실제 현업에서는 어떻게 하는지 궁금한 지점**
- 크롤링한 원본 데이터(자유 텍스트, HTML 섞인 필드 등)를 구조화된 정보로 바꿀 때, 정규식 같은
  규칙 기반 파싱과 AI 기반 추출(요약·추출) 중 실무에서는 어떤 기준으로 선택하는지 궁금하다.
- 1인 프로젝트에서도 이슈-브랜치-PR 단위를 이 정도로 세분화해서 진행했는데, 실제 팀에서는 이
  정도 단위가 표준인지, 아니면 프로젝트 규모·팀 크기에 따라 훨씬 거칠게(혹은 더 세밀하게)
  쪼개는지 궁금하다.

**개발 공부 / 진로 관련 궁금한 지점**
- Claude Code 같은 AI 에이전트로 코드를 작성하는 게 실무에서 얼마나 받아들여지고 있는지, 그리고
  이런 도구를 쓰면서도 "내가 실제로 실력이 늘고 있는지"를 스스로 어떻게 점검해야 하는지 궁금하다.
