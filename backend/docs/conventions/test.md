## 테스트 작성 규칙

테스트 코드를 작성할 때 지키는 규칙. 모든 도메인에 공통 적용한다

- 테스트는 대응하는 프로덕션 코드와 같은 패키지 구조(`src/test`)에 둔다.
- 예:는 이해를 돕기 위한 것이다.

### 1. 원칙 (FIRST)

- 빠르게(Fast)·서로 독립(Independent)·반복 가능(Repeatable)·자가 검증(Self-validating)하게 짠다.
- 각 테스트는 다른 테스트·실행 순서에 영향받지 않는다 (공유 상태는 매번 초기화).

### 2. 무엇을 테스트하나

- **비즈니스 의미(규칙·동작)를 담은 코드만** 테스트한다.
    - 예: 도메인 불변식·정규화, enum 코드 변환, 서비스 로직, 직접 쓴 쿼리
- 프레임워크가 보장하는 것·단순 위임·의미 없는 데이터 홀더는 **테스트하지 않는다**.
    - 예: getter, 필드만 있는 DTO, JPA 기본 메서드

### 3. 테스트 종류 (범위로 구분)

- **단위**: 한 클래스를 격리해 검증하고 의존은 mock한다.
- **통합**: 여러 계층이 실제로 맞물려 도는지 검증한다.
    - 실제 DB·컨텍스트를 사용한다.
- 계층이 아니라 **테스트 범위**로 나뉜다.

### 4. 계층별 전략

| 계층 | 방식 |
| --- | --- |
| 도메인·VO·enum | 순수 **단위** (불변식·변환 등 의미 있는 것만) |
| 서비스 | **DB 무관 로직**(예외 분기)=단위(Mockito)<br>**DB 의존 로직**=통합(외부만 mock) |
| 리포지토리 | 파생 쿼리·기본 메서드=테스트 X<br>직접 쓴 `@Query`만 `@DataJpaTest` |
| 컨트롤러 | 전체 통합(`@SpringBootTest` + `MockMvc`)<br>대표 케이스(`200`·`404`·`400`) |

### 5. 케이스 도출 기준

- 정상(happy)·조건 분기·경계값·실패 사유별·부수효과를 고려한다.
- **동등 분할** — 같은 성격의 입력은 하나로 대표한다 (모든 값을 다 테스트하지 않음).
- 비즈니스 의미가 있는 케이스만 남긴다.

### 6. 네이밍

- 메서드명은 `success_`(정상)/`fail_`(예외) + **짧은 키워드**로 짓는다.
    - 예: `success_within1km`, `fail_notFound`
- 상세 시나리오는 **`@DisplayName`(한글)** 에 자세히 쓴다.
- 같은 대상의 테스트는 **`@Nested`** 로 묶는다.

### 7. 구조

- 본문은 **given / when / then**으로 구분한다.
- 결과는 **대표 필드만** 검증한다 — 모든 필드를 나열하면 깨지기 쉽고 계층 간 중복이 된다.
- 각 계층은 **자기 책임만** 검증하고, 다른 계층이 검증한 로직은 재검증하지 않는다.
