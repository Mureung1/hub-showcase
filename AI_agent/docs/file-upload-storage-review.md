# 실제 파일 업로드 저장소 검토

## 현재 상태

- `/upload` 화면은 2MB 이하 파일을 브라우저에서 Data URL로 읽는다.
- `POST /api/submissions`는 파일명, MIME 타입, Data URL 문자열을 `UserMission`에 저장한다.
- 피드백/포트폴리오 화면은 저장된 Data URL을 다운로드 링크로 다시 보여준다.

## 장점

- 별도 파일 저장소 없이 MVP 흐름을 검증할 수 있다.
- 파일 링크와 파일 제출을 같은 API에서 처리할 수 있다.
- 테스트와 로컬 실행이 단순하다.

## 한계와 위험

- Base64 Data URL은 원본 파일보다 저장 크기가 커져 DB 용량을 빠르게 사용한다.
- DB row에 파일 본문이 들어가면 조회 응답이 커지고 피드백/포트폴리오 화면까지 느려질 수 있다.
- 파일 확장자, MIME 타입, 악성 파일 검사, 다운로드 권한 제어가 아직 약하다.
- Supabase DB 백업/복구 범위가 커지고, 실제 파일 관리 기능과 DB 관리 기능이 섞인다.

## 권장 방향

운영 기능으로 확장할 때는 Supabase Storage 같은 오브젝트 저장소를 사용한다.

1. 브라우저는 백엔드에서 업로드 권한을 받은 뒤 파일을 Storage에 업로드한다.
2. 백엔드는 `UserMission`에 파일 본문 대신 `storageBucket`, `storagePath`, `originalFileName`, `mimeType`, `size` 같은 메타데이터만 저장한다.
3. 다운로드/미리보기는 짧은 만료 시간을 가진 signed URL로 제공한다.
4. 파일 크기, 허용 MIME 타입, 사용자별 접근 권한을 백엔드에서 검증한다.

## 현재 결정

- 지금은 MVP 안정성을 위해 기존 2MB Data URL 저장 방식을 유지한다.
- 실제 파일 저장소 도입은 별도 작업으로 분리한다.
- 도입 시 DB 마이그레이션과 Supabase Storage 버킷 정책을 먼저 설계한다.
