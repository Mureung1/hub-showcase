# ADR - Career Mission AI

Architecture Decision Record는 프로젝트에서 반복적으로 영향을 주는 기술 선택과 그 이유를 기록하는 문서다.

## ADR-001. Express 기반 백엔드 서버 도입

### 상태

채택

### 배경

초기 화면은 React와 localStorage 중심으로 구현할 수 있지만, 회원 정보, 스펙, 분석 결과, 미션 진행 상태는 사용자별로 안전하게 저장되어야 한다. 또한 이메일 인증, JWT 인증, 외부 공공 API 연동, OpenAI API 호출처럼 브라우저에 노출하면 안 되는 값과 로직이 생겼다.

### 결정

Node.js Express 서버를 백엔드 API 서버로 사용한다.

### 이유

- React 프론트엔드와 API 서버의 책임을 분리할 수 있다.
- 인증, DB 접근, 외부 API 키, OpenAI API 키를 서버 환경 변수로 관리할 수 있다.
- MVP 범위에서 빠르게 라우트와 미들웨어를 추가할 수 있다.
- 프론트엔드는 `VITE_API_BASE_URL`만 바라보도록 단순화할 수 있다.

### 영향

- 프론트엔드 API 함수는 `/api/*` 엔드포인트를 호출한다.
- 백엔드는 CORS 허용 origin을 환경 변수로 관리한다.
- 신규 기능은 화면 구현 전에 API 계약을 먼저 정리해야 한다.

## ADR-002. PostgreSQL + Prisma 사용

### 상태

채택

### 배경

회원, 사용자 스펙, 분석 결과, 미션 진행 상태는 관계형으로 연결된다. 사용자 삭제 시 관련 데이터 정리, 사용자별 최신 분석 결과 조회, 미션 진행 상태의 중복 방지 같은 요구가 있다.

### 결정

PostgreSQL을 주 데이터베이스로 사용하고 Prisma ORM으로 스키마와 쿼리를 관리한다.

### 이유

- 사용자 중심 데이터 모델을 명확하게 표현할 수 있다.
- Prisma schema를 통해 모델 구조를 코드로 추적할 수 있다.
- `UserSpec.userId`와 `UserMission(userId, missionId)`처럼 고유 제약을 선언하기 쉽다.
- 향후 결제, 크레딧, 포트폴리오 생성 이력을 추가하기 좋다.

### 현재 모델

- `User`: 회원, 이메일 인증, 로그인 식별 정보
- `UserSpec`: 목표 직무와 스펙 입력값
- `AnalysisResult`: AI 분석 결과와 원본 응답
- `Mission`: 추천 미션 마스터 데이터
- `UserMission`: 사용자별 미션 진행 상태

## ADR-003. JWT 기반 인증 사용

### 상태

채택

### 배경

사용자별 스펙과 분석 결과를 보호해야 한다. 프론트엔드와 백엔드가 분리된 구조이므로 서버 세션보다 API 요청마다 인증 정보를 전달하는 방식이 적합하다.

### 결정

로그인 성공 시 JWT를 발급하고, 인증이 필요한 API는 `Authorization: Bearer <token>` 헤더를 요구한다.

### 이유

- 프론트엔드에서 API 요청 단위로 인증 상태를 전달하기 쉽다.
- Express 미들웨어(`requireAuth`)로 보호 라우트를 일괄 처리할 수 있다.
- API 서버가 stateless하게 동작할 수 있다.

### 영향

- `/api/auth/me`, `/api/specs/*`, `/api/analysis/*`는 JWT가 필요하다.
- 프론트엔드는 토큰을 세션 저장소에 보관하고 인증 요청에 자동 첨부한다.
- 로그아웃은 클라이언트 저장 세션을 삭제하는 방식으로 처리한다.

## ADR-004. 이메일 인증 후 로그인 허용

### 상태

채택

### 배경

가입 계정이 실제 사용 가능한 이메일인지 확인해야 한다. 무분별한 계정 생성을 줄이고, 이후 알림/결과 발송 기능과 연결할 기반이 필요하다.

### 결정

회원가입 시 이메일 인증 토큰을 발급하고, 인증 링크 확인 후 `emailVerified`가 true인 사용자만 로그인할 수 있게 한다.

### 이유

- 가입과 실제 계정 활성화를 분리할 수 있다.
- 인증 토큰 만료 시간을 둘 수 있다.
- 이메일 발송 실패 시 생성된 사용자를 삭제하여 불완전 계정을 줄인다.

### 영향

- 회원가입 요청에는 `verificationOrigin`이 필요하다.
- 이메일 인증은 `POST /api/auth/verify-email`로 처리한다.
- 개발/운영 SMTP 설정은 백엔드 환경 변수로 관리한다.

## ADR-005. 외부 검색 API는 백엔드에서 중계

### 상태

채택

### 배경

학교/전공/직업/자격증 검색은 커리어넷과 Q-Net 등 외부 공공 API에 의존한다. API 키를 프론트엔드에 노출하면 안 되고, 외부 API 장애 시 fallback 처리가 필요하다.

### 결정

프론트엔드는 백엔드 검색 API만 호출하고, 백엔드가 외부 API 호출과 fallback 데이터를 처리한다.

### 이유

- 외부 API 키를 서버 환경 변수로 보호할 수 있다.
- 외부 API 응답 형식 변경을 백엔드에서 흡수할 수 있다.
- 검색어 정규화, 별칭 매칭, fallback 목록 병합을 한곳에서 관리할 수 있다.

### 영향

- 프론트엔드는 `/api/jobs`, `/api/qualifications`, `/api/schools`, `/api/majors`를 사용한다.
- 외부 API 키가 없거나 호출이 실패하면 제한된 fallback 데이터가 반환될 수 있다.
- 자격증 목록은 서버 메모리 캐시를 사용한다.

## ADR-006. AI 분석은 서버에서 실행하고 결과를 저장

### 상태

채택

### 배경

AI 분석에는 사용자 스펙, 목표 직무, OpenAI API 키가 필요하다. AI API 키와 프롬프트를 브라우저에 노출하면 안 되며, 사용자가 이전 분석 결과를 다시 볼 수 있어야 한다.

### 결정

`POST /api/analysis` 요청 시 서버가 사용자의 저장된 스펙을 읽고 OpenAI API를 호출한 뒤, 정규화된 분석 결과를 DB에 저장한다.

### 이유

- OpenAI API 키와 프롬프트를 서버에서 보호할 수 있다.
- 분석 결과를 DB에 보관해 마이페이지/분석 화면에서 재조회할 수 있다.
- 응답 형식을 서버에서 정규화해 프론트엔드 표시 로직을 단순화할 수 있다.

### 영향

- 분석 실행 전 필수 스펙 항목이 저장되어 있어야 한다.
- 최신 분석 조회는 `GET /api/analysis/me`를 사용한다.
- 향후 크레딧 차감, 사용량 제한, 분석 캐싱은 이 서버 계층에 추가한다.

## ADR-007. API 명세 문서 유지

### 상태

채택

### 배경

프론트엔드와 백엔드가 동시에 변경되면서 요청/응답 구조가 코드에만 흩어져 있으면 연동 오류가 발생하기 쉽다.

### 결정

API 계약은 `docs/api-spec.md`에 정리한다.

### 문서 범위

- HTTP method와 path
- 인증 필요 여부
- 요청 query/body
- 성공 응답 예시
- 주요 실패 응답
- 사용하는 화면 또는 프론트엔드 API 함수

### 영향

- API 라우트를 추가하거나 응답 구조를 바꾸면 `docs/api-spec.md`도 함께 갱신한다.
- 아직 구현되지 않은 미션 진행/결과물 업로드 API는 구현 전 별도 ADR 또는 API 초안을 작성한다.

## ADR-008. 외부 검색 결과는 서버 메모리 TTL 캐시 사용

### 상태

채택

### 배경

학교/전공/직업/자격증 검색은 외부 공공 API를 호출한다. 같은 검색어가 짧은 시간에 반복되면 화면 응답 속도가 느려지고 외부 API 장애나 호출 제한의 영향을 크게 받는다.

### 결정

백엔드 검색 서비스에 서버 프로세스 메모리 기반 TTL 캐시를 둔다. 기본 TTL은 10분이며 `SEARCH_CACHE_TTL_MS` 환경 변수로 조정한다.

### 이유

- DB 마이그레이션 없이 속도와 안정성을 개선할 수 있다.
- 같은 검색어에 대한 중복 외부 API 호출을 줄일 수 있다.
- 캐시가 만료되면 최신 외부 API 결과를 다시 반영할 수 있다.
- 실패한 외부 API 호출 자체는 캐싱하지 않아 일시 장애가 장기 고정되지 않는다.

### 영향

- 서버 재시작 시 검색 캐시는 비워진다.
- 여러 서버 인스턴스를 운영하면 인스턴스별 캐시가 따로 유지된다.
- 운영 트래픽이 커지면 Redis 같은 공유 캐시로 교체할 수 있다.
