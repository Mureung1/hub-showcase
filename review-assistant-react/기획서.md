## 0. 프로젝트 개요
| 항목 | 내용 |
|---|---|
| 서비스명 | 리뷰 매니저 AI (구 "리뷰 답변 도우미") |
| 대상 사용자 | 매일 손님 리뷰를 확인하고 답변을 다는 소상공인(카페, 식당 등) |

| 현재 구현 범위 | React(프론트) + Express(백엔드) 연동 완료. 분석 로직은 규칙 기반, 저장은 `node:sqlite`. Claude API 연동은 3주차 예정 |

## 3. 핵심 기능 (우선순위 순)

### ① 리뷰 일괄 입력 & 파싱 — [핵심]
- 여러 리뷰를 줄바꿈으로 구분해 한 번에 입력
- 빈 줄 제거, 최대 15개 제한
- 입력값 검증 실패 시 명확한 에러 메시지

### ② 감정 분석 (긍정/부정/중립) — [핵심]
- 키워드 매칭 기반 규칙 엔진 (POSITIVE_WORDS / NEGATIVE_WORDS)
- "불친절"처럼 부정 접두사(불/안/못)가 붙은 경우 긍정 오탐 방지 처리
- 매칭 점수 비교로 최종 감정 판정

### ③ 핵심 키워드 추출 — [핵심]
- 맛/친절도/대기시간/가격/청결도/분위기 6개 카테고리
- 리뷰당 최대 3개 키워드, 매칭 없으면 "일반"

### ④ 답변 초안 3종 생성 — [핵심]
- 감정×키워드 조합으로 정중함/친근함/간결함 3가지 톤 생성
- 리뷰별로 즉시 확인·비교 가능

### ⑤ 답변 클립보드 복사 — [핵심]
- 버튼 클릭 시 즉시 복사, 1.5초간 "복사됨 ✓" 피드백
- 실패 시 에러 안내

### ⑥ 반복 문제 감지 & 개선 제안 — [핵심]
- 세션 누적 히스토리 기준, 동일 키워드의 부정 리뷰가 2건 이상이면 자동 노출
- 키워드별 구체적 개선 제안 문구 제공 (예: 대기시간 → "피크타임 인력 배치 조정")
- "누적 기록 초기화"로 리셋 가능

### ⑦ 에러/예외 처리 — [핵심]
- 빈 입력, 15개 초과, 클립보드 실패, 통계 조회 실패 케이스 커버

### ⑧ 리뷰마다 AI 관심도 점수 — [핵심, 신규]
- 리뷰마다 0~100점의 "관심 필요도" 점수를 함께 반환 (긍정 낮음 → 부정+복수 키워드 높음)
- 결과 카드에 배지로 노출, 어떤 리뷰부터 먼저 챙길지 판단하는 기준으로 사용
- 현재는 감정·키워드 개수 기반 규칙 점수, 3주차 Claude API 연동 시 점수 산정 방식 고도화 검토

### ⑨ 리뷰 총 분석 — [핵심, 신규]
- 세션 누적 기준 총 리뷰 수, 감정 분포(긍정/부정/중립), 평균 관심도 점수, 자주 언급된 키워드 top 5를 `/dashboard`에서 확인
- 아직 분석한 리뷰가 없으면 빈 상태 안내 + 도구 화면으로 이동하는 링크 제공

### ⑩ 월별 통계 — [핵심, 신규]
- 세션 누적 리뷰를 분석 시각(월 단위)로 묶어 월별 총 건수·평균 점수·부정 리뷰 건수 표시
- 세션이 유지되는 한(로그인 없이도 localStorage의 세션ID 기준) 누적됨

### ⑪ 회원가입 / 로그인 — [신규, 2026-07-15]
- 이메일/비밀번호로 회원가입·로그인, 토큰 기반 인증(`Authorization: Bearer`)
- 로그인 상태는 모든 화면 공통 `Header`에 표시(이메일 + 로그아웃 버튼)
- **도구 자체 이용에는 로그인이 필요 없다** — 리뷰 분석·반복 문제 감지·통계는 여전히 익명 세션으로 동작. 로그인은 신원 확인 기능에서 시작했지만, ⑫에서 리뷰 데이터와도 연결됨

### ⑫ 내 리뷰 모아보기 — [신규, 2026-07-20]

- 로그인 상태로 리뷰를 분석하면 `session_id`뿐 아니라 계정(`user_id`)에도 함께 연결됨(6-1, 6-3 참고)
- `/my-reviews` 화면에서 이 계정으로 로그인해서 분석했던 리뷰를 기기·세션 상관없이 최신순으로 모아 볼 수 있음(`GET /api/v1/reviews/mine`, 5-8 참고)
- 로그인 안 한 상태로 분석한 리뷰는 여전히 `session_id`로만 저장되고 이 목록엔 안 나옴 — 로그인 이후 분석분부터 누적됨
- Header의 로그인 사용자 영역에 "내 리뷰" 링크로 진입

## 5. API 설계 — 리뷰 분석 · 답변 초안 · 총 분석 · 월별 통계

`POST /api/v1/reviews/analyze` — 리뷰 텍스트 배열(최대 15개)을 요청으로 받아, 리뷰별 감정(긍정/부정/중립)·키워드·AI 관심도 점수·답변 초안 3종을 응답으로 반환한다.
분석된 리뷰는 세션(`X-Session-Id`) 기준으로 `node:sqlite` DB에 저장되며, 동일 세션에서 같은 키워드의 부정 리뷰가 2건 이상 누적되면 응답에 반복 문제 감지 정보를 함께 포함한다.
입력이 비어있거나 15개를 초과하면 `400` 에러를, 분석 엔진 오류 시 `500` 에러를 코드와 함께 반환한다.
누적 기록은 `DELETE /api/v1/reviews/history`로 초기화할 수 있고, 누적된 리뷰는 `GET /api/v1/stats/summary`(총 분석)와 `GET /api/v1/stats/monthly`(월별 통계)로 조회한다.

### 5-1. 엔드포인트 개요
| 항목 | 내용 |
|---|---|
| Method / Path | `POST /api/v1/reviews/analyze` |
| 설명 | 리뷰 원문 배열을 받아 리뷰별 감정·키워드·개선 제안·답변 초안 3종을 반환하고, 세션 누적 기준 반복 문제도 함께 감지한다 |
| 인증 | `X-Session-Id` 헤더 (로그인 없는 익명 세션. 반복 문제 감지용 누적 히스토리를 세션 단위로 서버가 보관) |
| Idempotent 여부 | 아니오 (호출 시마다 해당 세션의 누적 히스토리에 반영되므로 부작용 있음) |

### 5-2. Request

```json
POST /api/v1/reviews/analyze
X-Session-Id: 6f1b2e3a-...

{
  "reviews": [
    "음식 맛이 별로였고, 너무 오래 기다렸어요.",
    "직원분이 너무 불친절했어요."
  ]
}
```

| 필드 | 타입 | 필수 | 제약 |
|---|---|---|---|
| `reviews` | string[] | Y | 최소 1개, 최대 15개. 각 항목은 공백 제거 후 1자 이상 |

### 5-3. Response `200 OK`

```json
{
  "results": [
    {
      "reviewId": "r_01",
      "originalText": "음식 맛이 별로였고, 너무 오래 기다렸어요.",
      "sentiment": "negative",
      "keywords": ["맛", "대기시간"],
      "score": 80,
      "improvementSuggestion": "메뉴 맛의 일관성을 점검하고, 레시피 표준화나 조리 담당자 교육을 고려해보세요.",
      "replyDrafts": {
        "polite": "불편을 드려 진심으로 죄송합니다. 말씀해주신 맛 부분은 꼭 개선하도록 노력하겠습니다.",
        "friendly": "아이고 맛 때문에 많이 아쉬우셨겠어요 ㅠㅠ 다음엔 더 신경 쓸게요!",
        "concise": "죄송합니다. 개선하겠습니다."
      }
    }
  ],
  "recurringIssues": [
    {
      "keyword": "대기시간",
      "occurrenceCount": 3,
      "suggestion": "피크타임 인력 배치 조정을 검토해보세요."
    }
  ]
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `results[].reviewId` | string | 요청 내 순번 기반 식별자 |
| `results[].sentiment` | enum | `positive` \| `negative` \| `neutral` |
| `results[].keywords` | string[] | 최대 3개, 매칭 없으면 `["일반"]` |
| `results[].score` | number | AI 관심도 점수 0~100. 긍정 10 / 중립 40 / 부정 70(+매칭 키워드 수에 따라 최대 +20) |
| `results[].improvementSuggestion` | string \| null | 부정 리뷰가 아니면 `null` |
| `results[].replyDrafts` | object | `polite` / `friendly` / `concise` 3종 고정 키 |
| `recurringIssues` | array | 세션 누적 기준 동일 키워드의 부정 리뷰가 2건 이상일 때만 포함, 없으면 빈 배열 |

### 5-4. 에러 응답

| 상태 코드 | `code` | 상황 | 메시지 예시 |
|---|---|---|---|
| 400 | `EMPTY_INPUT` | `reviews`가 빈 배열이거나 누락 | "리뷰를 먼저 입력해주세요." |
| 400 | `NO_VALID_REVIEW` | 공백/줄바꿈만 있는 항목뿐 | "유효한 리뷰가 없어요." |
| 400 | `TOO_MANY_REVIEWS` | 15개 초과 | "한 번에 최대 15개까지 분석할 수 있어요." |
| 400 | `INVALID_JSON` | 요청 바디가 올바른 JSON이 아님(파싱 실패) | "요청 형식이 올바르지 않아요." |
| 500 | `ANALYSIS_FAILED` | 분석 엔진(추후 Claude API) 오류 | "잠시 후 다시 시도해주세요." |

에러 바디 형식은 공통 규격을 따른다.
```json
{ "error": { "code": "TOO_MANY_REVIEWS", "message": "한 번에 최대 15개까지 분석할 수 있어요." } }
```

## 6. 데이터 모델 설계

DB는 `node:sqlite`(review-assistant-server/src/db/db.js)를 쓰기로 결정했다(CLAUDE.md 참고). 아래는 그 스키마를 정리한 것이다.

> 2026-07-15: 회원 인증(`users`, `auth_tokens`) 추가로 테이블이 1개 → 3개로 늘었다. 이때는 `users`와 `reviews`가 아직 연결되어 있지 않았다.
> 2026-07-20: `reviews.user_id` 컬럼을 추가해 로그인 계정과 리뷰를 연결했다(6-1, 6-3 참고). 리뷰 저장 자체는 여전히 `session_id` 기준이고, 로그인돼 있으면 `user_id`도 함께 채워지는 방식 — `session_id`를 대체하는 게 아니라 병행한다.

### 6-1. `reviews` 테이블 (구현됨)

| 컬럼 | 타입 | 설명 | 제약조건 |
|---|---|---|---|
| `id` | INTEGER | 리뷰 고유 ID | PK, AUTOINCREMENT |
| `session_id` | TEXT | 어느 세션(익명 가게)의 리뷰인지 | NOT NULL, 인덱스(`idx_reviews_session_id`) |
| `original_text` | TEXT | 리뷰 원문 | NOT NULL |
| `sentiment` | TEXT | 감정 분류 결과 | NOT NULL, `positive` / `negative` / `neutral` 중 하나 |
| `keywords` | TEXT (JSON 배열 문자열) | 매칭된 키워드(최대 3개) | NOT NULL |
| `score` | INTEGER | AI 관심도 점수(0~100) | NOT NULL |
| `created_at` | TEXT (ISO8601) | 분석 시각 | NOT NULL, 기본값 현재 시각 |
| `user_id` | INTEGER | 분석 당시 로그인돼 있던 계정 (2026-07-20 추가) | NULL 허용(비로그인이면 null), `users(id)` 참조, 인덱스(`idx_reviews_user_id`) |

> **Supabase(Postgres)로 옮긴다면 참고**: `id`는 `bigint generated always as identity`(또는 `uuid`), `keywords`는 JSON 문자열 대신 Postgres 네이티브 `text[]` 배열 타입이 더 자연스럽고, `created_at`은 `timestamptz`로 바뀐다. 지금은 이전 계획이 없어 실제 마이그레이션은 하지 않는다.

### 6-2. `users` / `auth_tokens` 테이블 (구현됨, 2026-07-15 추가)

**`users`**

| 컬럼 | 타입 | 설명 | 제약조건 |
|---|---|---|---|
| `id` | INTEGER | 사용자 고유 ID | PK, AUTOINCREMENT |
| `email` | TEXT | 로그인 이메일 | NOT NULL, UNIQUE |
| `password_hash` | TEXT | `salt:hash` 형식 (Node `crypto.scryptSync`) | NOT NULL |
| `created_at` | TEXT (ISO8601) | 가입 시각 | NOT NULL, 기본값 현재 시각 |

**`auth_tokens`**

| 컬럼 | 타입 | 설명 | 제약조건 |
|---|---|---|---|
| `token` | TEXT | 로그인 시 발급되는 불투명 토큰(랜덤 32바이트 hex) | PK |
| `user_id` | INTEGER | 토큰 소유 사용자 | NOT NULL, `users(id)` 참조, 인덱스 |
| `created_at` | TEXT (ISO8601) | 발급 시각 | NOT NULL, 기본값 현재 시각 |

로그인마다 새 토큰이 발급되고(여러 기기 동시 로그인 허용), 로그아웃 시 해당 토큰 행만 삭제한다. 토큰 만료(TTL)는 아직 없음 — 필요해지면 `expires_at` 컬럼 추가 예정.

### 6-3. 저장하지 않는 것 / 아직 연결 안 한 것 (의도적 설계)
- **개선 제안(`improvementSuggestion`), 답변 초안 3종(`replyDrafts`)**: 키워드로부터 결정론적으로 다시 계산 가능해서 저장하지 않는다. API 응답에만 실려 나가고 끝.
- **반복 문제 목록, 총 분석 요약, 월별 통계**: 별도 캐시 테이블 없이 매 요청마다 `reviews` 테이블을 조회·집계해서 만든다(`history.service.js`, `stats.service.js`).
- **`users` ↔ `reviews` 연결 (2026-07-20 구현)**: 리뷰를 저장할 때 로그인 상태면(`Authorization: Bearer` 유효) `user_id`도 함께 채운다. `session_id` 기준 저장 방식을 대체하는 게 아니라 병행 — 비로그인 사용자는 계속 `session_id`로만, 로그인 사용자는 `session_id` + `user_id` 둘 다로 저장된다. "내 리뷰 모아보기"(`GET /api/v1/reviews/mine`, 5-8 참고)는 이 `user_id`로 조회한다.

### 6-4. 향후 확장 후보 (아직 미구현)

| 테이블 / 컬럼 | 필요해지는 시점 | 비고 |
|---|---|---|
| `sessions`(또는 `stores`) | 가게별 답변 톤 커스터마이징(4번 향후 확장) 구현 시 | `session_id`(PK), `preferred_tone`, `industry_type`, `created_at` |
| `auth_tokens.expires_at` | 토큰 만료 정책이 필요해질 때 | 지금은 로그아웃 전까지 무기한 유효 |

## 7. 인증 API (회원가입 / 로그인) — 2026-07-15 신규

로그인 여부와 무관하게 도구 자체(리뷰 분석·반복 문제 감지·통계)는 계속 익명으로 쓸 수 있다. 인증은 "누구인지 확인"하는 별도 기능으로 추가됐다.

### 7-1. 회원가입 — `POST /api/v1/auth/signup`

Request:
```json
{ "email": "user@example.com", "password": "password123" }
```

Response `201 Created`:
```json
{ "user": { "id": 1, "email": "user@example.com" }, "token": "3f2b1a..." }
```

### 7-2. 로그인 — `POST /api/v1/auth/login`

Request/Response 형식은 회원가입과 동일. 로그인할 때마다 새 토큰이 발급된다(기기별로 여러 개 동시 유효).

### 7-3. 로그아웃 — `POST /api/v1/auth/logout`
| 항목 | 내용 |
|---|---|
| 인증 | `Authorization: Bearer <token>` 헤더 |
| 설명 | 해당 토큰만 무효화(삭제). 다른 기기의 토큰에는 영향 없음 |
| 응답 | `204 No Content` |

### 7-4. 내 정보 조회 — `GET /api/v1/auth/me`
| 항목 | 내용 |
|---|---|
| 인증 | `Authorization: Bearer <token>` 헤더 (필수) |
| 설명 | 토큰으로 로그인 상태 확인. 프론트 `Header` 컴포넌트가 페이지 진입 시마다 호출해 로그인 여부를 표시 |
| 응답 `200` | `{ "user": { "id": 1, "email": "..." } }` |
| 응답 `401` | 토큰 없음/무효 — `{ "error": { "code": "UNAUTHORIZED", "message": "로그인이 필요해요." } }` |

### 7-5. 에러 응답

| 상태 코드 | `code` | 상황 |
|---|---|---|
| 400 | `INVALID_EMAIL` | 이메일 형식이 올바르지 않음 |
| 400 | `WEAK_PASSWORD` | 비밀번호 8자 미만 |
| 409 | `EMAIL_TAKEN` | 이미 가입된 이메일로 회원가입 시도 |
| 401 | `INVALID_CREDENTIALS` | 로그인 시 이메일/비밀번호 불일치 |
| 401 | `UNAUTHORIZED` | 토큰 없이 또는 무효한 토큰으로 인증 필요 API 호출 |

리뷰 API의 에러 코드(5-4)와 달리 `409`/`401`을 사용한다 — 표준 REST 관례를 따른 것으로, 이 프로젝트의 공통 에러 바디 형식(`{ "error": { "code", "message" } }`)은 동일하게 지킨다.

### 7-6. 비밀번호 저장 방식
`bcrypt` 같은 별도 패키지를 추가하지 않고, Node 내장 `crypto` 모듈의 `scryptSync`로 해싱한다(`salt:hash` 형식으로 저장). 이 프로젝트가 지금까지 지켜온 "내장 모듈로 되면 새 의존성 추가 안 함" 원칙(`node --watch`, `node:sqlite`, `node:test`)과 일관된 선택이다.

## 8. Claude API 연동 설계 (3주차, 2026-07-20)

`reviews.service.js`의 규칙 기반(단어 매칭) 감정 분석·키워드 추출·답변 초안 생성을 실제 Claude API 호출로 교체하기 위한 설계. 아직 코드는 교체하지 않았고(3주차 화요일 작업 예정), 호출 방식과 응답 스키마만 확정한다.

### 8-1. 호출 방식

- **모델**: `claude-haiku-4-5-20251001` (별칭 `claude-haiku-4-5`)
- **호출 방법**: 공식 SDK(`@anthropic-ai/sdk`) 대신 Node 내장 `fetch`로 Anthropic Messages API(`https://api.anthropic.com/v1/messages`)를 직접 호출한다. 이 프로젝트가 지금까지 지켜온 "내장 기능으로 되면 새 의존성 추가 안 함" 원칙(7-6 참고)과 일관된 선택.
- **API 키**: `ANTHROPIC_API_KEY` 환경변수, 백엔드에서만 사용(`.env.example`에 자리만 마련돼 있음, 값은 로컬 `.env`에 직접 설정 — git에 커밋 안 됨).

### 8-2. 응답 스키마 — tool-use(구조화 출력)

프롬프트로 "JSON 형식으로 답해줘"라고 요청한 뒤 텍스트를 직접 파싱하는 방식 대신, Anthropic API의 `tools` 파라미터(tool-use)로 스키마를 강제한다. 모델이 스키마에 맞는 JSON만 반환하므로 파싱 실패 가능성이 낮다.

```json
{
  "name": "submit_review_analysis",
  "description": "리뷰 하나를 분석한 결과를 제출한다",
  "input_schema": {
    "type": "object",
    "properties": {
      "sentiment": { "type": "string", "enum": ["positive", "negative", "neutral"] },
      "keywords": {
        "type": "array",
        "items": { "type": "string", "enum": ["맛", "친절도", "대기시간", "가격", "청결도", "분위기", "일반"] },
        "minItems": 1,
        "maxItems": 3
      },
      "replyDrafts": {
        "type": "object",
        "properties": {
          "polite": { "type": "string" },
          "friendly": { "type": "string" },
          "concise": { "type": "string" }
        },
        "required": ["polite", "friendly", "concise"]
      }
    },
    "required": ["sentiment", "keywords", "replyDrafts"]
  }
}
```

### 8-3. score와 improvementSuggestion은 API로 요청하지 않는다

AI에게 0~100 점수까지 맡기면 같은 입력에도 매번 값이 달라질 수 있어(비결정적) 리뷰마다 점수를 비교하는 총 분석·정렬 기능이 불안정해진다. 그래서 **score는 계속 백엔드에서 기존 `computeScore(sentiment, keywords)` 함수로 로컬 계산**한다 — API 응답으로 받은 `sentiment`/`keywords`를 그대로 이 함수에 넣는 것만 다르고, 점수 산정 공식(긍정 10 / 중립 40 / 부정 70+키워드 보너스) 자체는 바꾸지 않는다.

`improvementSuggestion`도 같은 이유로 로컬 계산으로 뺐다. `keywords`가 이미 6개 고정 카테고리(맛/친절도/대기시간/가격/청결도/분위기)라 기존 `SOLUTION_MAP`에서 바로 찾을 수 있는데, AI에게 자유 텍스트로 맡기면 매번 문구가 달라지고 API 비용도 더 든다. (8-2 초안 스키마에는 이 필드가 있었으나, 실제로 tool-use 호출을 테스트해보니 AI가 이 필드를 응답에서 아예 생략하는 경우가 있어 신뢰성 문제도 확인돼 최종적으로 제거함.) → API 응답으로 받은 `keywords[0]`을 기존 `suggestionForKeyword(keyword)` 함수에 그대로 넣어 로컬 계산한다.

### 8-4. 인터페이스 유지

`analyzeReviews(reviews)` 함수의 입출력 모양(입력: 리뷰 배열 → 출력: 리뷰별 `{ reviewId, originalText, sentiment, keywords, score, improvementSuggestion, replyDrafts }`)은 그대로 유지한다. 내부 구현만 규칙 기반 → API 호출로 바뀌고, 네트워크 호출이 생기므로 함수가 `async`로 바뀐다. 컨트롤러/라우트도 이에 맞춰 `async`/`await`로 전환된다(3주차 화요일 작업).

### 8-5. 에러 매핑

API 호출 실패(네트워크 오류, 인증 실패, 타임아웃)나 응답 파싱 실패는 기존 `ANALYSIS_FAILED`(500) 에러 코드로 매핑한다. 새 에러 코드를 추가하지 않고 기존 5-4절 체계를 그대로 재사용.
