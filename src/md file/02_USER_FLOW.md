# Portfolio Zero-to-One Builder

---

# 0. 변경 배경

본 문서는 JD 입력/이력서 업로드/프로젝트 매칭을 포함하던 기존 User Flow를 폐기하고, "GitHub 레포 입력 → AI 인터뷰 → 마크다운 초안 완성" 흐름으로 재작성한 것이다. 상세 배경은 [[01_PRD]] 0장 참고.

---

# 1. 문서 목적

본 문서는 사용자가 Portfolio Zero-to-One Builder를 이용하는 전체 과정을 정의한다.

각 단계에서

* 사용자의 행동(User Action)
* 시스템의 동작(System Action)
* AI Agent의 동작(AI Action)

을 정의하여 UI/UX 설계, API 설계, 데이터베이스 설계의 기준으로 활용한다.

---

# 2. 사용자 여정(User Journey)

```text
Landing

↓

GitHub Repository URL 입력

↓

코드 스캔 및 후보 파일 선정

↓

AI 인터뷰 시작

↓

핀포인트 질문 ⇄ 유저 답변 (반복)

↓

실시간 마크다운 프리뷰 갱신

↓

인터뷰 종료

↓

Markdown 다운로드
```

---

# 3. 상세 사용자 시나리오

## Step 1. Landing Page

### User Action

서비스에 접속한다.

### System Action

서비스 소개, 핵심 기능 소개, GitHub URL 입력창을 제공한다.

---

## Step 2. GitHub Repository 입력

### User Action

GitHub Repository URL을 입력한다.

예)

```text
https://github.com/user/project
```

**한 세션은 레포지토리 하나만 다룬다.** 유저의 GitHub 계정을 연결해 여러 레포 중 어떤 것을 분석할지 시스템이 자동으로 골라주는 기능은 MVP에 없다(이는 JD 매칭처럼 "어떤 프로젝트가 더 적합한지 판단"하는 로직이 필요해 [[01_PRD]] 9장 제외 범위와 같은 이유로 뺐다). 프로젝트가 여러 개인 유저는 레포 URL을 바꿔가며 세션을 각각 새로 시작한다.

### System Action

Repository 접근 여부 확인

↓

소스 파일 목록 수집

---

## Step 3. 코드 스캔 및 후보 파일 선정

### AI Action

다음 순서로 처리한다.

```text
확장자 필터링 (.js/.ts/.py 등 소스코드만)

↓

config/문서 파일 제외

↓

단순 가중치 스코어링
(파일 크기 + 이름 패턴, 커밋 횟수는 제외)

↓

상위 N개 후보 파일 선정
```

커밋 횟수를 제외하는 이유는 [[05_CODE_SCANNER_SCORER]] 3장 참고.

### 결과

인터뷰에 사용할 후보 파일 목록과 각 파일의 대표 코드 스니펫이 준비된다.

---

## Step 4. AI 인터뷰 시작

### System Action

좌측 채팅 패널, 우측 마크다운 프리뷰 패널로 구성된 화면을 제공한다.

### AI Action

후보 파일 중 하나를 선택해 코드를 인용하며 핀포인트 질문을 생성한다.

예)

```text
PaymentService의 결제 승인 로직에서
try-catch로 감싼 이유와 실패 시 처리 방식을 설명해 주세요.
```

---

## Step 5. 유저 답변

### User Action

채팅창에 자유 형식으로 답변한다.

### System Action

답변을 저장하고 AI에게 다음 단계 처리를 요청한다.

---

## Step 6. 답변 애매성 판단

### AI Action

답변이 다음 중 어디에 해당하는지 판단한다.

```text
이해도 충분 → Step 7로 진행

이해도 애매 → 1회 재질문

이해도 낮음(모른다고 명시) → Step 7로 진행(서술 수위 하향)
```

재질문은 최대 1회로 제한한다. 재질문 후에도 애매하면 이해도 낮음으로 간주하고 다음 단계로 넘어간다.

---

## Step 7. 톤 교정 및 마크다운 반영

### AI Action

* 유저 답변을 개발자 문체로 교정
* 이해도에 따라 서술 수위 조정
* 필요 시 면접 방어용 코멘트 삽입
* 전체 마크다운을 처음부터 다시 생성(부분 업데이트 아님)

상세 규칙은 [[06_INTERVIEW_WRITER]] 참고.

### System Action

우측 프리뷰 패널을 갱신된 전체 마크다운으로 다시 렌더링한다.

---

## Step 8. 반복

Step 4~7을 모든 후보 파일의 모든 chunk(질문)가 소진되거나 유저가 종료를 원할 때까지 반복한다. 한 파일에서 chunk가 2개면 같은 파일 안에서 질문이 한 번 더 이어진 뒤 다음 파일로 넘어간다 ([[05_CODE_SCANNER_SCORER]] 7장, [[08_DATABASE]] 8장 참고).

---

## Step 9. 인터뷰 종료 및 다운로드

### User Action

"완료" 버튼을 클릭하거나 더 이상 답변할 항목이 없다.

### System Action

최종 마크다운 파일을 다운로드로 제공한다.

---

# 4. 예외 상황(Exception Flow)

## GitHub 연결 실패

Repository 접근 실패 메시지 출력 후 재입력 요청

---

## 지원 언어가 아님

레포에 소스 파일은 있으나 지원 언어(MVP는 JS/TS)가 아닐 경우, "코드가 없다"와 다른 메시지("현재는 JS/TS 프로젝트만 지원합니다")로 안내하고 인터뷰를 시작하지 않는다 ([[05_CODE_SCANNER_SCORER]] 10장 참고).

---

## 소스 파일 부족

지원 언어인데도 분석 가능한 소스 파일이 없을 경우, 사용자에게 안내하고 인터뷰를 시작하지 않는다.

---

## 레포지토리 규모 초과

파일 개수가 임계값을 넘으면 스캔을 거부하고 "레포가 너무 커서 분석할 수 없습니다"라고 안내한다.

---

## 인터뷰 결과가 적음 (Sparse Interview)

프로젝트가 단순한 구조라 감지된 패턴이 적을 경우, 질문 개수를 억지로 늘리지 않고 그 이유를 마크다운에 안내 문구로 남긴 뒤 정상 종료한다 ([[06_INTERVIEW_WRITER]] 10.1장 참고).

---

## 커밋 히스토리 빈약

커밋 수가 적어도 스코어링에 영향이 없다 (커밋 횟수를 지표로 사용하지 않으므로 별도 예외 처리 불필요).

---

## 유저가 답변을 회피하거나 "모른다"고 명시

서술 수위를 하향 조정하고, 면접 방어용 코멘트를 삽입한 뒤 다음 질문으로 진행한다. 상세는 [[06_INTERVIEW_WRITER]] 참고.

---

## AI 생성 실패

자동 재시도, 실패 시 사용자에게 오류 안내 후 이전 턴 결과 유지

---

# 5. AI 내부 흐름

```text
GitHub Repository URL

↓

코드 스캔 / 후보 파일 선정

↓

핀포인트 질문 생성

↓

유저 답변

↓

애매성 판단 (필요 시 재질문 1회)

↓

톤 교정 + 서술 수위 조정 + 방어 코멘트

↓

전체 마크다운 재생성

↓

(반복)

↓

다운로드
```

---

# 6. UX 원칙

* 입력은 GitHub URL 하나로 최소화한다.
* 유저는 "무엇을 써야 할지"가 아니라 "질문에 어떻게 답할지"만 고민하면 된다.
* AI 결과는 항상 유저 답변에 근거하며, 답변에 없는 내용을 만들어내지 않는다.
* 이해도가 낮은 부분은 숨기지 않고 면접 방어 코멘트로 드러낸다.
* 다운로드 전 실시간 프리뷰로 항상 현재 상태를 확인할 수 있다.

---

# 7. 향후 확장 시나리오

* 이력서/JD를 선택 입력으로 추가하여 서술 강조점을 조정
* 스트리밍 채팅 UI
* 섹션 단위 부분 업데이트 프리뷰
* 인터뷰 종료 후 자기소개서/면접 질문 생성으로 이어지는 흐름
* Private GitHub 레포지토리 지원 (OAuth 로그인 도입)
* 세션 재개 (브라우저 종료 후 이어하기)
* 마크다운 프리뷰 편집 기능
