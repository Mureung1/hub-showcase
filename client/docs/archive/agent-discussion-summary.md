# Agent Discussion Summary

이 문서는 MVP UI 명세를 만들기 위한 AI 토론 기록이다. 구현 기준 문서는 아니며, 최종 반영된 기준은 `client/docs/product-prd.md`, `client/docs/user-flow.md`, `client/docs/click-unit-ui-spec.md`, `client/docs/component-implementation-notes.md`를 따른다.

## 참여 역할

- 개발자 AI 1: 프론트엔드 구현과 상태 모델 관점
- 개발자 AI 2: QA, 엣지케이스, PRD 범위 관리 관점
- 사용자 AI 1: 첫 방문 대학생 사용자 관점
- 사용자 AI 2: 재방문/기록 관리 사용자 관점

## 공통 합의

- 현재 문서는 화면 전환과 클릭 단위는 풍부하지만, 서비스 본질과 PRD 정책이 약하다.
- 서비스의 핵심 루프는 `짧은 세션 시작 -> 읽기 -> 기록 -> 내 기록에서 다시 읽기`로 고정해야 한다.
- 빠른 시작은 방 상세를 거쳐도 되지만, 방 상세가 `시작 전 확인`이라는 사실을 사용자가 즉시 이해해야 한다.
- `readyToRecord`는 내부 상태명으로 유지하되, 사용자 화면에서는 `기록 대기`로 통일해야 한다.
- 샘플 데이터는 실제 데이터와 함께 보일 수 있지만 목표 진행률과 성공지표에서는 제외해야 한다.
- 컴포넌트 설명은 단순 이름 목록이 아니라 props, state, handler, 표시 조건까지 드러나야 한다.
- localStorage MVP에서는 새로고침, 탭 충돌, 저장 실패, 파싱 실패가 핵심 QA 대상이다.

## 주요 쟁점

### 빠른 시작

- 사용자 관점: 빠른 시작이 방 상세를 거치면 이름과 행동이 충돌한다.
- 개발자 관점: 방 상세는 템플릿 결과와 시작 조건을 확인시키는 안전한 단계다.
- 합의: 방 상세를 유지하되 `시작 전 확인` 화면으로 문서화하고, CTA를 템플릿 기반 라벨로 바꾼다.

### 완료 기록

- 사용자 관점: 세션 직후 필수 입력 4개는 피로하다.
- QA 관점: 기록 데이터 품질을 위해 필수값은 유지하는 편이 낫다.
- 합의: 필수값은 유지하되 책 제목/감상을 먼저 보이고, 페이지 범위는 대략값 허용 문구로 부담을 줄인다.

### 기록 대기

- 사용자 관점: `미작성`, `나중에 작성`, `완료 기록 작성 대기`가 섞이면 다른 상태처럼 보인다.
- 개발자 관점: 내부 enum은 `readyToRecord`로 유지할 수 있다.
- 합의: 내부 상태는 `readyToRecord`, 사용자 노출 문구는 `기록 대기`로 고정한다.

### 샘플 데이터

- 사용자 관점: 샘플과 실제 데이터가 섞이면 기록 신뢰가 떨어진다.
- 개발자 관점: 시연 편의를 위해 같은 목록에 섞는 것은 가능하다.
- 합의: 목록에는 섞되 샘플 배지를 붙이고 목표 진행률/성공지표에서는 제외한다.

### 컴포넌트 분해

- 개발자 관점: `draft`, `ephemeral`, `persistent` 상태 구분이 없으면 구현이 흔들린다.
- 사용자 관점: 컴포넌트는 상태뿐 아니라 사용자가 다음에 무엇을 해야 하는지도 책임져야 한다.
- 합의: 컴포넌트 문서에 props/state/handler와 사용자 안내 책임을 함께 적는다.

## 문서 반영 결정

- `client/docs/product-prd.md`를 추가해 문제정의, 목표, 정책, QA 시나리오를 고정한다.
- `client/docs/component-implementation-notes.md`를 추가해 컴포넌트별 구현 책임을 자세히 쓴다.
- `client/docs/user-flow.md`에는 제품 본질과 PRD 링크를 보강한다.
- `client/docs/click-unit-ui-spec.md`에는 상태 모델, 빠른 시작, 기록 대기, 샘플 정책, 컴포넌트 문서 링크를 보강한다.
- `client/docs/archive/ux-friction-review.md`에는 토론에서 합의된 보완 우선순위를 반영한다.
