## 2026-07-26 · 클라이언트가 사용자 ID를 결정하던 문제

### 증상

사용자 정보가 `localStorage`에 저장되고, 모든 API 요청에 `userId`가 포함되어 있었다. 저장 값을 바꾸면 다른 사용자의 ID로 요청할 수 있었다.

### 원인

로그인 기능이 없던 초기 프로토타입의 사용자 식별 방식을 실제 API까지 그대로 사용했다. 브라우저 입력은 신뢰 경계 밖에 있는데 서버가 이를 소유권 판단에 사용했다.

### 수정

- Google 로그인 결과로 서버 세션을 만든다.
- 모든 `fetch` 요청에 `credentials: 'include'`를 적용한다.
- 책·독서 기록 API의 요청 경로와 본문에서 `userId`를 제거한다.
- 서버가 내려준 CSRF 토큰을 메모리에 보관하고 변경 요청의 `X-CSRF-Token` 헤더로 보낸다.
- 기존 `localStorage` 사용자는 자동 이전하지 않는다.

### 검증

`src/lib/api.test.js`에서 로그인 뒤 세션 쿠키 옵션과 CSRF 헤더가 적용되고, 책 생성 본문에 사용자 ID가 없는지 확인한다.

### 배울 점

화면에서 사용자 ID를 숨기는 것과 서버가 사용자를 인증하는 것은 다르다. 소유권의 기준은 수정 가능한 브라우저 저장 값이 아니라 서버가 검증한 세션이어야 한다.

## 2026-07-26 · 책장 진입 시 같은 종류의 API를 세 번 호출하던 문제

### 증상

읽는 중·완독·보관 상태마다 책장 API를 따로 호출했다. 기록 저장 후에도 같은 세 요청이 반복됐다.

### 원인

화면의 세 구역을 API 경계로 그대로 옮겼다. 하지만 세 데이터는 항상 같은 화면에서 함께 필요했다.

### 수정

`GET /api/bookshelf` 한 번으로 `reading`, `completed`, `archived`를 함께 받고 각 상태에 저장하도록 바꿨다.

### 검증

프런트 테스트와 프로덕션 빌드를 통과시켰고, 서버에서는 책장 조회가 세 쿼리 이하인지 별도로 검사한다.

### 배울 점

컴포넌트가 나뉜다고 네트워크 요청도 반드시 나뉘어야 하는 것은 아니다. 사용자 동작 한 번에 항상 같이 필요한 데이터라면 하나의 화면용 API가 더 단순할 수 있다.

## 2026-07-26 · 글귀 노출을 화면 표시 전에 기록할 수 있던 문제

### 증상

랜덤 글귀를 받은 직후 노출 API까지 연달아 호출하면, React가 배너를 실제로 그리기 전에 노출로 집계될 수 있었다.

### 원인

데이터를 가져온 시점과 사용자가 화면에서 본 시점을 같은 사건으로 취급했다.

### 수정

- 랜덤 글귀 상태가 화면에 반영된 다음 `useEffect`에서 노출을 생성한다.
- 책장 로딩이 끝나고 해당 글귀의 책이 실제 읽는 중 목록에 있을 때만 노출을 생성한다.
- 책 상세 화면에서는 배너가 보이지 않으므로 노출을 생성하지 않는다.
- 배너를 눌렀을 때만 해당 노출 ID를 활성화하고, 이후 독서 기록에 연결한다.
- 노출 기록 실패가 책 열기를 막지는 않게 했다.

### 검증

랜덤 글귀가 책장보다 먼저 도착하는 경우까지 포함해 배너 표시 조건과 노출 생성 조건을 같게 맞췄고, 프런트 전체 테스트와 빌드를 통과시켰다.

### 배울 점

분석 이벤트는 API 응답이 아니라 사용자가 실제로 경험한 순간에 최대한 가깝게 기록해야 한다. 다만 분석 실패가 핵심 행동을 막게 해서는 안 된다.

## 2026-07-26 · Google 로그인 스크립트 로딩 순서 문제

### 증상

Google Identity Services 스크립트가 React 컴포넌트보다 먼저 또는 나중에 로드될 수 있어 로그인 버튼 초기화 시점이 일정하지 않았다.

### 원인

외부 스크립트는 `async defer`로 로드되므로 컴포넌트 마운트 순서만 믿을 수 없다.

### 수정

컴포넌트 마운트 때 이미 로드됐으면 즉시 초기화하고, 아직이면 스크립트의 `load` 이벤트에서 초기화한다. 콜백은 `ref`로 유지해 불필요한 버튼 재생성을 피했다.

### 검증

`VITE_GOOGLE_CLIENT_ID`가 없을 때 설정 안내가 표시되는지 확인하고 프로덕션 빌드를 통과시켰다. 실제 Google 로그인 확인에는 등록된 OAuth 웹 클라이언트가 필요하다.

### 배울 점

외부 SDK는 React 생명주기와 별개의 생명주기를 가진다. “이미 로드됨”과 “나중에 로드됨” 두 경로를 모두 처리해야 한다.

## 2026-07-26 · 전체 쪽수를 넘는 기록 입력 문제

### 증상

도서 메타데이터에 전체 쪽수가 있어도 사용자가 그보다 큰 끝 페이지를 입력할 수 있었다.

### 원인

초기에는 `끝 페이지 >= 시작 페이지`만 검사했고 `pageCount`를 저장하지 않았다.

### 수정

`pageCount`가 있을 때 숫자 입력의 `max`를 설정하고 제출 전 범위를 검사한다. `pageCount`가 없는 책은 기존처럼 상한 없이 기록할 수 있다. 서버도 같은 검사를 수행한다.

### 검증

프런트 빌드와 서버의 페이지 범위 API 테스트를 통과시켰다.

### 배울 점

프런트 검증은 빠른 피드백을 위한 UX이고, 데이터 무결성의 최종 책임은 서버에 있다.

## 2026-07-27 · 클라이언트 환경 파일이 Git에 노출되던 문제

### 증상

Google OAuth Client ID를 `client/.env`에 설정하자 파일이 untracked 상태로 표시됐다. 그대로 전체 파일을 스테이징하면 환경별 설정이 커밋될 수 있었다.

### 원인

서버의 `.env`만 `.gitignore`에 등록했고 Vite가 읽는 클라이언트 `.env`는 제외하지 않았다.

### 수정

루트 `.gitignore`에 `client/.env`를 추가했다. 공유해야 하는 변수 이름과 기본값은 기존 `client/.env.example`에만 유지한다.

### 검증

실제 `client/.env`가 존재하는 상태에서 `git status`에 나타나지 않는지 확인한다.

### 배울 점

브라우저에 전달되는 Client ID가 비밀키가 아니더라도 로컬 환경 파일은 통째로 제외해야 한다. 공개 가능한 변수의 형식은 예제 파일로 공유하고 실제 환경값은 커밋하지 않는다.

## 2026-07-27 · React Strict Mode에서 Google 로그인을 두 번 초기화하던 문제

### 증상

로컬 온보딩을 열면 Google Identity Services가 `google.accounts.id.initialize() is called multiple times` 경고를 출력했다.

### 원인

개발 환경의 React Strict Mode는 effect의 setup과 cleanup을 한 번 더 실행한다. 로그인 effect가 실행될 때마다 Google SDK 초기화와 버튼 렌더링을 함께 반복했다.

### 수정

- 모듈에서 초기화한 Client ID를 기억해 같은 ID로 SDK를 다시 초기화하지 않는다.
- 현재 마운트된 컴포넌트의 credential handler만 모듈 콜백으로 전달한다.
- 같은 DOM 요소에는 Google 버튼을 한 번만 렌더링한다.

### 검증

`StrictMode` 아래에서 온보딩을 렌더링해 Google SDK 초기화와 버튼 렌더링이 각각 한 번만 호출되는 회귀 테스트를 추가했다.

### 배울 점

외부 SDK의 전역 초기화 횟수와 React 컴포넌트의 생명주기는 분리해야 한다. 컴포넌트는 다시 마운트될 수 있지만 SDK 초기화는 페이지 수명 동안 한 번만 수행하고, 콜백 대상만 현재 컴포넌트로 교체하는 편이 안전하다.

## 2026-07-27 · 로컬 Google 로그인 요구사항이 실행 환경에서 빠진 문제

### 증상

Google OAuth 웹 클라이언트와 포트가 일치해도 로컬 Google 로그인 버튼 요청이 origin 오류로 거부됐다. Vite 응답을 확인하니 Google의 HTTP localhost 지침에 명시된 Referrer-Policy가 없었다.

### 원인

로컬 실행 문서에는 포트가 포함된 origin만 안내했고, Vite 개발 서버에도 HTTP localhost용 referrer 정책을 설정하지 않았다.

### 수정

- 승인된 JavaScript 원본에 `http://localhost`와 `http://localhost:5173`을 모두 등록하도록 실행 문서를 고쳤다.
- Vite 개발 서버 응답에 `Referrer-Policy: no-referrer-when-downgrade`를 추가했다.
- 이 정책은 localhost 개발 서버에만 적용하고 운영 응답 정책은 배포 환경에서 별도로 정하게 했다.

### 검증

Vite 개발 서버를 다시 시작한 뒤 `curl -I http://localhost:5173`에서 Referrer-Policy 응답 헤더를 확인했다. 브라우저에서 Google 로그인 버튼 요청이 200으로 바뀌고 origin 오류가 사라지는 것까지 확인했으며, 계정 선택 이후의 실제 로그인은 사용자 상호작용으로 별도 검증한다.

### 배울 점

외부 인증 SDK는 코드와 Client ID만 맞아도 끝나지 않는다. 제공자가 요구하는 origin 조합과 브라우저 보안 헤더까지 로컬 실행 환경의 일부로 관리해야 재현 가능한 인증 QA가 된다.

## 2026-07-27 · 3D 책장을 적용해도 기존 화면과 비슷해 보인 문제

### 증상

책을 꺼내 펼치는 3D 동작은 들어갔지만 메인 화면의 인상은 이전 UI와 크게 다르지 않았다. 3D 영역은 방처럼 닫힌 프레임 안에 있었고, 글귀·이어 읽기·활동·완독·보관함은 오른쪽에 비슷한 카드로 쌓여 핵심 행동이 눈에 띄지 않았다.

### 원인

3D 렌더링 경계를 책 영역으로 제한하는 구조 변경에 집중했고, 기존 DOM 순서와 카드 중심 CSS는 그대로 유지했다. 렌더링 구조 개선만으로는 사용자가 읽는 시각적 순서까지 바뀌지 않았다.

### 수정

- 화면 제목을 전체 폭의 시작점으로 옮겼다.
- 3D 책장을 가장 큰 주 영역으로 두고 글귀와 이어 읽기만 오른쪽 복귀 맥락으로 묶었다.
- 활동 기록·완독·보관함은 아래의 별도 영역으로 분리했다.
- 3D 책장 프레임은 아래 선반만 남기고 책 크기와 간격을 키웠다.
- 카드 테두리와 그림자를 줄이고 선과 여백으로 그룹을 구분했다.

### 검증

데스크톱·태블릿·모바일 화면을 각각 캡처해 겹침과 잘림을 확인했다. 브라우저 상호작용 스냅샷과 클릭 영역 검사를 수행하고, 전체 프런트 테스트와 프로덕션 빌드를 통과시켰다.

### 배울 점

아키텍처 경계를 바꾸는 작업과 시각 디자인을 바꾸는 작업은 별개다. 화면 개선은 렌더링 방식뿐 아니라 첫 시선, 주요 행동, 정보 그룹의 순서를 스크린샷으로 비교해야 확인할 수 있다.

## 2026-07-27 · 온보딩 진입 시 세션 조회가 두 번 발생한 문제

### 증상

로그아웃 상태로 온보딩에 진입할 때 `/api/auth/session` 요청과 401 응답이 각각 두 번 발생했다. Google 로그인 버튼은 실제로 하나였지만 중복 네트워크 요청 때문에 콘솔 오류도 두 개씩 쌓였다.

### 원인

개발 환경의 React Strict Mode가 `App`의 effect를 한 번 더 실행했고, `getSession()`은 동시에 들어온 동일 요청을 매번 새 `fetch`로 보냈다.

### 수정

`getSession()`이 진행 중인 세션 요청 Promise를 공유하도록 했다. 요청이 성공하거나 실패하면 저장한 Promise를 비워 이후의 실제 재조회와 장애 복구는 막지 않는다.

### 검증

동시 호출 두 개가 `fetch` 하나를 공유하고, 실패한 뒤에는 새 요청을 보낼 수 있는 회귀 테스트를 추가했다. 실제 브라우저에서도 온보딩 진입당 세션 요청이 한 번만 발생하는지 확인했다.

### 배울 점

Strict Mode의 effect 재실행을 컴포넌트별 플래그로 막으면 다른 호출자는 같은 문제를 반복한다. 동일한 읽기 요청을 합쳐도 되는 API라면 진행 중 요청을 API 경계에서만 공유하고 완료 후 즉시 해제하는 편이 작고 안전하다.

## 2026-07-27 · 대화상자를 닫은 뒤 키보드 포커스가 사라진 문제

### 증상

책 추가와 독서 기록 대화상자는 최초 입력에 포커스가 가고 Tab도 내부에서 순환했지만, Escape로 닫으면 포커스가 열기 버튼으로 돌아가지 않고 문서 `body`에 남았다. 키보드 사용자는 다음 조작 위치를 다시 찾아야 했다.

### 원인

두 대화상자는 외부 상태로 열리는 controlled dialog였고 Base UI의 `DialogTrigger`와 직접 연결되지 않았다. 라이브러리는 포커스 트랩과 Escape 닫기는 처리했지만 닫힌 뒤 복귀할 요소는 알 수 없었다.

### 수정

각 대화상자가 닫힘에서 열림으로 바뀌는 순간의 활성 요소를 기억하고, Base UI `Dialog.Popup`의 `finalFocus`로 전달했다. 새 포커스 관리 코드나 이벤트 리스너는 만들지 않고 설치된 컴포넌트의 기본 복귀 기능을 사용했다.

### 검증

실제 브라우저에서 최초 포커스, 역방향 Tab 순환, Escape 닫기와 트리거 복귀를 확인했다. 책 추가와 독서 기록 대화상자 모두를 포함한 회귀 테스트도 추가했다.

### 배울 점

접근성 컴포넌트를 사용해도 controlled 상태와 외부 트리거를 분리하면 라이브러리가 복귀 맥락을 추론하지 못할 수 있다. 포커스 트랩뿐 아니라 닫힌 뒤 사용자가 어디서 계속하는지까지 실제 키보드로 확인해야 한다.

## 2026-07-27 · 요청 처리 중 확인 대화상자가 닫힌 문제

### 증상

기록 삭제나 완독·보관 상태 변경을 요청한 직후 Escape를 누르면, 버튼에는 처리 중 상태가 표시됐지만 대화상자는 닫혔다. 사용자는 요청이 성공했는지 실패했는지 확인할 화면을 잃었다.

### 원인

버튼과 취소 동작만 비활성화했고 Base UI가 전달하는 닫기 요청은 그대로 상위 상태에 반영했다. 따라서 Escape나 바깥 클릭은 비동기 요청 중에도 controlled dialog를 닫을 수 있었다.

### 수정

삭제 중이거나 상태 저장 중일 때는 대화상자의 `onOpenChange(false)`를 무시했다. 요청 성공 뒤 기존 완료 경로가 직접 대화상자를 닫는 동작은 유지했다.

### 검증

모바일 폭의 실제 브라우저에서 최초 포커스와 Tab 순환을 확인하고, 삭제·완독 요청 중 Escape를 눌러도 대화상자와 처리 중 안내가 유지되는지 재검증했다. 두 요청이 완료되면 정상적으로 닫히는 회귀 테스트도 추가했다.

### 배울 점

비동기 작업 중 버튼을 비활성화하는 것만으로는 중복 입력만 막을 뿐 대화상자 자체의 닫기 동작은 막지 못한다. 결과를 확인해야 하는 작업은 요청 중 모든 dismiss 경로를 같은 상태로 제어해야 한다.

## 2026-07-27 · 저장 중 입력 대화상자와 작성값이 사라진 문제

### 증상

책 추가나 독서 기록 저장 응답을 기다리는 동안 Escape를 누르면 대화상자가 닫혔다. 책 추가는 취소 버튼도 활성 상태여서 사용자가 입력값과 처리 결과를 확인할 화면을 잃을 수 있었다.

### 원인

저장 버튼만 비활성화하고 Base UI의 닫기 요청은 기존 초기화 경로로 그대로 전달했다. 저장 성공 시에도 같은 닫기 함수를 사용하고 있어 외부 dismiss와 내부 완료를 구분하지 않았다.

### 수정

저장 중 외부 `onOpenChange(false)`는 무시하고, 성공 경로는 상위 open 상태를 직접 닫은 뒤 draft를 초기화하도록 분리했다. 책 추가의 취소 버튼도 저장 중 비활성화했다.

### 검증

모바일 폭의 실제 브라우저에서 책 검색·판본 선택과 독서 기록 입력을 완료한 뒤, 두 저장 요청 중 Escape를 눌러도 대화상자와 작성값이 유지되는지 확인했다. 요청 완료 뒤 정상적으로 닫히는 회귀 테스트도 각각 추가했다.

### 배울 점

입력 대화상자는 비동기 요청 중 닫힘을 막는 것과 성공 뒤 닫고 초기화하는 동작을 별도 경로로 가져야 한다. 두 경로를 같은 핸들러에 맡기면 저장 중 차단 조건이 성공 처리까지 막거나 외부 dismiss가 draft를 지울 수 있다.

## 2026-07-27 · 저장한 글귀가 서가 복귀 전까지 갱신되지 않은 문제

### 증상

독서 기록에 글귀를 저장한 뒤 서가로 돌아오면 글귀 배너가 비어 있었고, 페이지를 새로고침한 뒤에만 방금 저장한 글귀가 나타났다.

### 원인

무작위 글귀 API는 `BookshelfPage`가 처음 마운트될 때만 호출됐다. 기록 저장 경로는 책 상세·서가·활동 데이터만 다시 불러와 새로 생긴 글귀를 상태에 반영하지 않았다.

### 수정

글귀가 포함된 기록을 저장했을 때만 기존 무작위 글귀 API를 다시 호출해 배너 상태를 갱신했다. 글귀 조회 실패가 이미 성공한 기록 저장을 실패로 보이게 하지 않도록 기존 배너 조회와 같이 오류는 독립적으로 처리했다.

### 검증

실제 로그인 세션에서 저장 직후와 새로고침 뒤 화면을 비교했다. 기록 저장 뒤 글귀를 재조회하고 서가에 표시하는 회귀 테스트를 추가했다.

### 배울 점

서버 데이터에서 파생된 화면 상태는 데이터를 생성하는 경로에서도 함께 무효화해야 한다. 다만 부가 정보 조회 실패가 핵심 저장 결과를 뒤집지 않도록 오류 경계는 분리해야 한다.

## 2026-07-27 · 모바일에서 핵심 재개 행동이 잘리고 늦게 나타난 문제

### 증상

긴 판본명을 가진 이어 읽기 카드와 글귀 배너가 데스크톱 오른쪽과 모바일 화면 밖으로 잘렸다. 모바일에서는 3D 서가가 544px 높이를 먼저 차지해 저장한 글귀와 `이어 읽기` 버튼이 첫 화면보다 한참 아래에 나타났다. 3D 책의 투명 선택 영역도 가로 36px로 모바일 터치 목표보다 작았다.

### 원인

`bookshelf-details`의 암시적 grid 열이 긴 한글 제목의 최소 콘텐츠 폭만큼 늘어났고, 640px 이하에서 `1fr`로 다시 지정해도 최소 폭이 0으로 줄지 않았다. DOM도 3D 무대 뒤에 재개 맥락이 놓여 있어 모바일에서 CSS만 쌓으면 핵심 행동이 항상 서가 다음에 나타났다. 모바일 서가 높이와 책 선택 폭은 데스크톱 구도를 축소한 값에 머물러 있었다.

### 수정

- 재개 영역의 grid 열을 `minmax(0, 1fr)`로 제한해 긴 제목을 부모 폭 안에서 줄바꿈했다.
- DOM 순서를 글귀·이어 읽기 다음 3D 서가로 바꾸고, 데스크톱에서는 명시적인 grid area로 기존 좌우 구도를 유지했다.
- 모바일 3D 무대 높이를 22rem으로 줄이고 책 선택 영역을 44px로 넓혔다.

### 검증

390px, 768px, 1440px 실제 브라우저 화면에서 가로 넘침이 없고 핵심 재개 CTA가 모바일 첫 화면에 나타나는지 확인했다. 태블릿에서 44px 미만 상호작용 요소가 없는지 검사했고, 프런트 31개 테스트와 프로덕션 빌드를 통과시켰다.

### 배울 점

CSS Grid의 `1fr`는 긴 콘텐츠의 최소 폭을 자동으로 무시하지 않는다. `minmax(0, 1fr)`가 필요한지 실제 긴 데이터로 확인해야 한다. 반응형 화면의 핵심 행동 순서는 시각적 `order`만 바꾸지 말고 키보드·스크린리더 순서와 같은 DOM에서 먼저 바로잡는 편이 안전하다.

## 2026-07-27 · 3D 책 확대 직전에 마지막 페이지가 덜 펼쳐진 문제

### 증상

책을 선택하면 내부 페이지가 앱 배경과 같은 크림색이라 책의 펼쳐진 면을 알아보기 어려웠다. 마지막 장을 넘긴 뒤 상세 화면으로 확대할 때는 페이지가 다시 살짝 접힌 것처럼 보였다.

### 원인

페이지 텍스처가 앱 배경과 같은 `#fffaf0`을 직접 사용했다. 모션은 마지막 페이지의 스프링이 끝났는지 확인하지 않고 700ms 타이머 뒤 확대를 시작했고, 실제 계측에서 확대 시작 시 회전값은 약 `-2.08rad`, 상세 화면 전환 직전에도 약 `-2.94rad`로 완전 펼침인 `-π`에 도달하지 못했다.

### 수정

내부 페이지를 흰색으로 바꿔 배경과 구분했다. 확대 단계에 들어가면 넘긴 페이지의 회전과 레이어 위치를 즉시 최종값으로 고정해, 확대 자체는 유지하면서 책만 완전히 펼친 자세를 이어가게 했다.

### 검증

회귀 테스트에서 확대 단계의 페이지 각도·레이어·즉시 고정 여부와 종이색을 확인했다. 타이머를 5배 늦춘 실제 브라우저 재현에서도 확대 프레임이 흰색 양면을 완전히 펼친 상태로 유지한 뒤 상세 화면으로 전환되는 것을 확인했다.

### 배울 점

서로 다른 스프링과 고정 타이머를 조합하면 타이머가 끝나도 시각적 자세는 끝나지 않을 수 있다. 다음 화면으로 이어지는 공유 요소는 전환 경계에서 최종 자세를 명시적으로 고정하거나, 애니메이션 완료 이벤트를 기준으로 다음 단계를 시작해야 한다.
