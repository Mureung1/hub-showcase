# 잇장 아키텍처 결정 기록

## 1. 인증과 사용자 식별

- Google Identity Services가 발급한 ID 토큰을 서버가 검증한다.
- 영구 사용자 키는 변경될 수 있는 이메일이 아니라 Google의 `sub`를 쓴다.
- 인증 상태는 직접 구현한 Servlet `HttpSession`에 저장한다. 로그인할 때 기존 세션을 폐기하고 새 세션과 CSRF 토큰을 발급한다.
- 브라우저는 사용자 ID를 API에 보내지 않는다. 서버가 세션의 사용자로 모든 책·기록·글귀의 소유권을 검사한다.
- Spring Security는 현재 규모에서 학습해야 할 동작을 가리키는 설정이 더 많다고 판단해 도입하지 않았다. OAuth 제공자 확대, 역할 기반 권한, 세션 정책 복잡도가 커지면 전환을 검토한다.
- 세션 쿠키 방식이므로 프런트와 API는 동일 사이트 배포를 기본으로 한다. 교차 사이트 배포가 필요해지면 `SameSite=None; Secure`, CORS, CSRF 정책을 함께 재검토한다.
- 기존 `localStorage` 사용자는 신뢰할 수 있는 외부 식별자가 없어 자동 병합하지 않는다.

## 2. 인증 세션과 독서 세션

- 로그인 세션은 서버 `HttpSession`, 독서 타이머의 진행 상태는 브라우저 저장소로 분리한다.
- 독서 타이머는 인증 수명과 무관하게 새로고침을 견딜 수 있고, 서버 세션에는 인증 정보와 CSRF 토큰만 둔다.
- 여러 기기에서 진행 중인 타이머를 이어야 할 요구가 확인되면 독서 세션을 서버 엔티티로 승격한다.

## 3. 글귀와 독서 기록

- `Quote`는 `ReadingRecord`와 독립된 엔티티다.
- 독서 기록을 남길 때 글귀를 함께 입력하면 하나의 트랜잭션에서 둘을 저장하지만 외래 키로 결합하지 않는다.
- 독서 기록을 지워도 글귀는 남는다. 사용자가 기억하고 싶은 문장은 당시 세션보다 수명이 길기 때문이다.
- 글귀 수정·삭제는 독립 API로 제공한다.

## 4. 글귀 재노출 측정

- `QuoteExposure`는 노출, 책 열기, 이후 독서 기록 완료만 연결한다.
- 노출 시 글귀 원문을 스냅샷으로 보관하고, 원본 글귀 삭제 시 `quote_id`만 `NULL`로 만든다.
- 범용 이벤트·퍼널 프레임워크는 만들지 않는다. A 가설인 “글귀가 다시 읽기를 유도하는가”에 필요한 최소 데이터만 수집한다.

## 5. 책장 조회와 성능

- 책장은 상태별 API 세 번 대신 `GET /api/bookshelf` 한 번으로 읽는 중·완독·보관 책을 함께 반환한다.
- 현재 구현은 책 한 번, 해당 책들의 독서 기록 한 번으로 조회한 뒤 Java에서 묶는다. N+1 조회를 없애면서 구현 복잡도를 낮춘 선택이다.
- 사용자 한 명의 독서 기록을 모두 읽는 비용이 있다. 실제 사용자별 기록량이나 책장 p95가 문제가 될 때 최신 기록·개수를 DB projection으로 집계한다.
- `pageCount`는 외부 서지 정보에 없을 수 있어 nullable로 저장하고, 값이 있을 때만 페이지 상한을 검증한다.

## 6. 상호작용과 3D 경계

- 앱 전체의 정식 상호작용과 접근성은 DOM이 담당한다.
- 3D는 책의 위치·꺼내기·펼치기 연출에만 사용하며 UI 텍스트나 입력 컨트롤을 3D 표면에 얹지 않는다.
- 전체 페이지를 3D 장면으로 만들지 않는다. 투명 canvas를 페이지에 통합하고 방 모델과 앞쪽 선반 판은 제거했다.
- 3D 모듈은 지연 로딩하고 DPR 상한을 둔다. `prefers-reduced-motion` 사용자는 펼치기 연출을 건너뛰고 상세 화면으로 바로 이동한다.
- 현재 긴 애니메이션 시간은 디버깅용이다. 연출이 확정된 뒤 실제 사용 시간으로 줄인다.

## 7. 읽기 기록 달력의 사용자·시간대·집계 경계

- `GET /api/reading-activity?from&to`는 경로의 사용자 ID를 받지 않고 세션 사용자의 기록만 조회한다. 인증 전환 전 작성된 Issue의 `/api/users/{userId}` 형태는 사용하지 않는다.
- 조회 범위는 양 끝을 포함해 최대 84일로 제한한다. 최근 12주 UI에 필요한 범위만 허용해 실수나 남용으로 전체 기록을 읽지 않게 한다.
- 현재 대상 사용자의 기준 시간대는 `Asia/Seoul`로 고정한다. 다중 시간대 요구가 확인되면 사용자별 시간대를 저장하고 기존 기록의 날짜 해석 정책과 함께 migration한다.
- 기존 `user_id, created_at` 인덱스로 범위 안의 기록만 읽고 Java에서 날짜별로 묶는다. 84일 범위의 실제 p95나 기록량이 문제가 될 때 DB 집계 projection으로 교체한다.
