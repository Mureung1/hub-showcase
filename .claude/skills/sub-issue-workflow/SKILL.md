# 서브이슈 구현 사이클

`docs/dev/task-planning-devide.md` §5~7이 정의한 방법론(작게 나누기 → 이슈 등록 →
구현 전 전략 검토)을 hub 저장소에서 실행하는 고정 절차다. 이 문서를 매번 다시
읽고 해석하는 대신, 아래 단계를 그대로 반복한다. 이번 프로젝트의 Task 0(다섯 개
서브이슈)에서 5번 실제로 검증된 사이클이다.

## 왜 이 순서가 중요한가

전략과 코드를 분리하지 않으면 사용자가 검토할 지점이 사라진다. 완료 기준을
이슈에서 직접 확인하지 않으면 "됐다고 느끼는 것"과 "실제로 끝난 것"이 어긋난다.
검증 중 발견한 문제를 그 자리에서 임의로 고치면, 사용자가 원래 다른 선택을
하고 싶었던 지점을 놓치게 된다. 아래 단계는 이 세 가지 실패를 막기 위한 것이다.

## 단계

### 1. 이슈를 직접 확인한다 (기억이나 추측 금지)
`gh issue view <번호> --repo <owner>/hub --json title,body,number`로 완료 기준
원문을 가져온다. (`gh issue view` 단독 실행은 Projects classic GraphQL 오류로
실패할 수 있다 — `--json`으로 우회한다.) 완료 기준은 이후 검증 단계에서 그대로
다시 쓸 문장이므로 정확히 옮겨 적는다. 뒤쪽 서브이슈까지 미리 훑어보면 지금
설계가 이후 단계와 어긋나지 않는지 미리 확인할 수 있다.

### 2. 전략을 먼저 제시한다 (코드 금지)
`task-planning-devide.md` §7.1 템플릿을 그대로 따른다:
1) 만들거나 고칠 파일과 각 파일의 역할
2) 데이터가 어디에 있고 어떻게 흐르는지 (state 위치, 요청과 응답)
3) 이렇게 구현하는 이유(다른 방법이 있다면 장단점도)

이 시점에는 plan mode를 쓰지 않는다 — 아직 구현 승인 전이므로 순수 텍스트로
제시한다.

**2번(데이터 흐름)과 3번(대안 비교)은 글로만 나열하지 않고 시각 요소를 쓴다:**
- 데이터 흐름은 화살표 다이어그램으로 보여준다. 각 단계 옆에 **state 위치**
  — 그 데이터가 지금 어디에 있는지(함수 지역 변수인지, 모듈 레벨 상수인지,
  디스크 파일인지, 외부 서비스가 방금 돌려준 응답인지, 어디에도 저장되지
  않고 요청 하나 끝나면 사라지는지)를 함께 적는다. 위치를 모르면 나중에
  "이 값이 재시도할 때도 남아있나?" 같은 질문에 답할 수 없다.
- 대안이 있는 설계 판단은 산문으로 장단점을 나열하지 말고 표로 비교한다.

### 3. 카테고리별 예상 질문을 추론하고 답한다 (서브이슈마다 자동)
전략을 제시한 직후, **매 서브이슈마다 자동으로** `hub-learner-persona` 서브에이전트를
`Agent` 도구로 호출한다 — 이번 전략 텍스트를 그대로 넘긴다. 이 에이전트는 사용자
본인을 모델링한 페르소나로, 인프라/네트워크·개발/데이터·비즈니스/서비스 세 카테고리로
예상 질문을 추론해 돌려준다(직접 답하지 않는다).

돌아온 질문들에 **내가 직접 답한다.** 가능하면 실제 설치된 패키지 소스나 저장소 파일을
읽어 근거를 확인한 뒤 답한다 — 추측이나 일반론으로 답하지 않는다(§7.4).

사용자가 실제로 "구체적으로 설명해", "왜 이렇게 하는데", "예시 포함해" 같은 **직접
질문**을 추가로 할 수도 있다. 이 경우도 plan mode를 건드리지 않고 대화로 바로 답한다.
사용자의 실제 질문과 페르소나가 예측한 질문은 별개다 — 페르소나 질문에 답했다고
사용자의 실제 승인·이해로 해석하지 않는다.

### 4. 명시적 승인을 기다린다
"구현해", "구현으로 넘어가" 같은 명확한 신호가 오기 전까지 코드를 쓰지 않는다.
질문에 답했다고 승인으로 해석하지 않는다.

### 5. 계획을 기록하고 승인받는다
승인 신호를 받으면 plan mode의 계획 파일에 Context(배경) · 변경 사항(실제 코드
포함) · 검증 방법 · 범위 밖을 적고 `ExitPlanMode`로 승인을 받는다. plan mode가
아니라면(이미 종료된 상태라면) 사용자의 "구현해"를 그 자체로 승인으로 보고 바로
구현한다.

### 6. 구현한다
승인된 계획대로 작성한다.

### 7. 이슈의 완료 기준으로 검증한다 — 다른 기준이 아니라 그 문장 그대로
1단계에서 옮겨 적은 완료 기준 문장을 그대로 실행/재현한다. 막연히 "동작하는 것
같다"로 넘어가지 않는다. mock이 필요하면 스크래치패드에 임시 스크립트를 만들어
쓰고, 저장소에는 남기지 않는다.

### 8. 검증 중 문제를 발견하면 — 임의로 고치지 않는다
실패나 허점이 나오면:
- 정확히 무엇이, 왜 실패했는지 먼저 설명한다 (원인을 코드 흐름으로 짚어준다)
- 이게 왜 문제인지 근거를 댄다 (CLAUDE.md·이슈 설명 등 프로젝트가 이미 명시한
  기준과 연결지을 수 있으면 연결한다)
- 고칠지 말지가 갈리는 지점이면 옵션을 나열해 비교하고(장단점 포함) 사용자에게
  선택을 맡긴다 — 승인된 계획을 벗어나는 변경이므로 되돌아가서 다시 승인받는다
- 사용자가 선택하면 계획을 수정하고 다시 검증한다

### 9. 커밋한다
- 서브이슈 하나 = 커밋 하나
- 형식: `Feat(<scope>): <서브이슈 번호> <설명>` (CLAUDE.md 커밋 컨벤션 — 프롬프트
  수정도 Feat, Docs 아님)
- 본문에 설계상 이유가 있었다면 남긴다 (나중에 "왜 이렇게 했는지" 추적 가능하게)
- 꼬리말에 `Refs #<이슈번호>`와 `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`
- **git add는 이번에 만든/고친 파일만 지정.** `git status`에 이 작업과 무관한
  변경(다른 세션의 미완성 작업 등)이 섞여 있으면 절대 같이 커밋하지 않는다.
- **Task 브랜치가 아닌 커밋(예: 이 Skill 자체의 수정)은 그 Task의 PR이 이미
  병합됐는지 먼저 확인한다.** 병합된 뒤에 브랜치에 커밋하면 그 커밋은 어디에도
  반영되지 않고 고립된다 — `agent-service`(또는 아직 분기 전이라면 그다음
  Task 브랜치를 딸 원본)에 직접 반영한다.

### 10. 다음으로 넘어간다
같은 Task(Parent 이슈)에 서브이슈가 남아있으면 1번부터 반복. Task의 마지막
서브이슈였다면:
- PR은 사용자가 GitHub UI에서 직접 올린다 — 여기서 `git push`나 `gh pr create`를
  실행하지 않는다
- 요청받으면 PR 제목·본문 텍스트만 작성해서 전달한다 (커밋 목록·설계 메모·검증
  내역 요약)
- institutional 저장소(upstream)로 보내는 PR은 `.github/pull_request_template.md`
  형식(루카스ID_실명 타이틀, 주요 작업 리스트, 내가 설명할 수 있는 부분, 아직
  이해 못 한 부분, 새로 알게 된 것)을 따로 따른다 — "내가 설명할 수 있는 부분"
  같은 개인 이해도 증빙 섹션은 초안만 제공하고, 사용자 본인이 검토·수정하도록
  안내한다 (평가자에게 보여줄 개인 학습 증빙이므로 대필하지 않는다)
- **PR이 실제로 병합되면(사용자가 GitHub UI에서 확인해줌)**, 그 Task 동안
  나온 질문·답변을 `tech-doc-architect` Skill의 용어집+ADR 템플릿으로
  `docs/dev/tech-glossary-<task 이름>.md`에 정리한다 (Task 0 → `tech-glossary.md`,
  Task 1 → `tech-glossary-judge.md`가 선례). 카테고리(인프라/네트워크·
  개발/데이터·비즈니스/서비스)별로 묶고, 서브이슈 등장 순서대로 배치한다.
  자기 정정 사례(설명이 틀려서 사용자가 바로잡은 것)도 그대로 남긴다 — 실패도
  학습 기록이다. 커밋은 사용자가 요청할 때만 한다.

## 브랜치 전략 (참고)
1 Parent Task = 1 브랜치(`redo/<task>`). 서브이슈들은 그 브랜치 안의 개별
커밋이 된다. Task 완료 시 그 브랜치에서 `agent-service`로 PR 1개.
