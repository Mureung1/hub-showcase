# Prototype Screen Sync

특정 화면 하나를 `docs/prototype/final_prototype.html`(또는 프로젝트가 지정하는 다른 번들 프로토타입)에 맞춰 프로덕션 코드로 옮기는 작업의 표준 절차다. 이 프로젝트에서 온보딩, 공통 로딩, Today 홈, ArticleIntro, Mission 작성/완료, MyGgaem 여섯 화면을 이 절차로 순서대로 처리했고 매번 같은 함정(공용 CSS 오염, 프로토타입 가짜 데이터 복사, 계산 불가능한 통계 표시)에서 갈렸다. 이 스킬은 그 함정을 매번 다시 발견하지 않도록 절차화한 것이다.

핵심 원칙 하나로 요약하면: **프로토타입은 시각 기준일 뿐 데이터 기준이 아니다.** 구조·간격·타이포·색상·상태 표현은 프로토타입을 따르고, 실제 콘텐츠·상태 전환·API 계약은 현재 코드베이스(타입, API, 기획 문서)를 따른다. 이 둘을 뒤섞으면(프로토타입의 하드코딩 문구를 그대로 넣거나, 반대로 실데이터가 없다는 이유로 화면 요소 자체를 빼먹으면) 리뷰에서 반드시 걸린다. 실데이터가 없다는 이유로 보고와 승인 없이 화면 요소를 임의로 제거하면 안된다. 구현할 수 없는 요소는 대체안과 제외안을 제시하고 사용자 승인을 받는다.

## 왜 매번 분석 → 승인 → 구현 순서를 지키는가

이 작업은 "화면을 예쁘게 고치는 것"이 아니라 "시각 자산과 기능 계약이라는 서로 다른 두 소스를 하나의 구현으로 합치는 것"이다. 어느 쪽을 우선할지(예: 공용 버튼 스타일을 이 화면만 다르게 할지, 선택 개수 제한을 프로토타입대로 정확히 3개로 강제할지)는 코드를 보기 전엔 알 수 없는 결정이 대부분이고, 그 결정에 따라 구현 방법이 완전히 달라진다. 그래서 코드를 먼저 짜지 않고 차이를 분석해 보고한 뒤 승인을 받는다 — 되돌리기 비용이 싼 단계(문서 작성)에서 판단을 확정하고, 되돌리기 비용이 비싼 단계(코드 작성)에서는 확정된 판단만 실행한다.

## 절차

### 0. 범위 확정

사용자가 지정한 화면 하나로만 작업 범위를 제한한다. 지정되지 않은 화면의 파일은 읽기는 하되(공용 컴포넌트/타입 파악을 위해) 수정하지 않는다. 여러 화면을 연달아 요청받아도 화면마다 이 절차 전체(분석→승인→구현→리뷰→완료)를 처음부터 반복한다 — 한 화면의 승인이 다른 화면에 대한 승인을 의미하지 않는다.

### 1. 필독 자료를 읽는다

- `AGENTS.md`, `docs/DEVELOPMENT.md` — 이 저장소의 작업 범위·커밋·검증 규칙의 단일 원본
- 관련 `docs/plan/` 문서 — 화면이 다루는 기능의 확정 설계, API 계약, 데이터 필드
- 관련 `docs/quality/` 문서 — 이미 확정된 QA 기준(선택 개수 제한처럼 프로토타입과 충돌할 수 있는 조건이 여기 있을 수 있다)
- 대상 화면의 `.tsx`/`.css`/`.test.tsx`
- `frontend/src/App.tsx` (화면을 마운트하는 컨테이너, 콜백 계약 확인용)
- `frontend/src/index.css` (이미 정의된 디자인 토큰과 공용 클래스 목록)
- `frontend/src/api/types.ts` (이 화면이 실제로 쓸 수 있는 API 필드)

이 순서대로 읽어야 하는 이유: 기획 문서와 QA 문서를 프로토타입보다 먼저 읽지 않으면, 프로토타입에만 있고 기획에는 없는 요소(가짜 통계, 특정 선택 개수 제한 등)를 무비판적으로 베낄 위험이 커진다.

### 2. 번들 프로토타입에서 실제 마크업을 추출한다

`final_prototype.html`은 브라우저에서 스스로 압축을 풀어 렌더링하는 번들 HTML이다. 파일을 그냥 열어 grep하면 `<script type="__bundler/manifest">` 같은 로더 코드만 보이고 실제 화면 마크업은 안 보인다. 실제 마크업은 `<script type="__bundler/template">` 태그 안에 JSON 문자열로 들어 있으므로 파이썬으로 꺼낸다.

```python
import re, json

with open('docs/prototype/final_prototype.html', encoding='utf-8') as f:
    content = f.read()

m = re.search(r'<script type="__bundler/template">(.*?)</script>', content, re.DOTALL)
template_html = json.loads(m.group(1))  # 이 문자열이 실제 HTML

with open('/tmp/claude/proto_extracted.html', 'w', encoding='utf-8') as out:
    out.write(template_html)
```

(스크래치패드 디렉터리가 지정돼 있으면 `/tmp/claude/...` 대신 그 경로를 쓴다.) 추출한 파일 안에서 `<!-- SCREEN N — 화면이름 -->` 형태의 주석으로 원하는 화면 블록을 찾는다. 같은 세션에서 다른 화면을 이어서 작업할 때는 이미 추출해 둔 파일을 재사용하고 다시 추출하지 않는다.

이 마크업 안의 `sc-if`/`sc-for`/`{{ ... }}` 같은 표현은 프로토타입 전용 템플릿 문법이다 — React 문법이 아니므로 그대로 옮기지 말고, 조건부 렌더링 로직과 반복 구조가 무엇을 의도하는지만 읽어낸다. `renderVals()`/`state` 같은 스크립트 블록에 실제 문구·조건(예: 추천 여부 판단, 카운트 로직)이 정의돼 있는 경우가 많으니 마크업만 보지 말고 같이 확인한다.

### 3. 코드를 고치기 전에 분석부터 보고한다

다음 항목을 정리해 사용자에게 보고하고, **승인 전에는 코드를 수정하지 않는다.**

1. 프로토타입 화면 구조 (헤더/본문/CTA/하단 nav 등 섹션 순서와 각 섹션 구성)
2. 현재 구현 구조
3. JSX 구조 차이 (섹션 존재 여부, 순서, 마크업 계층)
4. 순수 CSS 차이 (크기·간격·색상처럼 구조는 그대로고 값만 다른 것)
5. 실제 API/타입으로 지금 구현 가능한 요소
6. 프로토타입에만 있고 API/기획 문서에는 없는 데이터 — 이 항목은 특히 주의 깊게 찾는다. 예: 연속 기록 일수, 가짜 3줄 요약, 도메인 파싱, 관심사 배지처럼 실제로는 이 화면의 API 응답에 없는 필드. 발견하면 4번 항목에서 "만들지 않는다"고 명시하거나 대안을 제안한다.
7. 수정 대상 파일과 테스트 목록
8. 완료 기준
9. 사용자 결정이 필요한 항목 (아래 "결정이 필요한 지점" 참고)

이 보고를 생략하고 바로 구현으로 넘어가지 않는다. 사용자가 "그냥 진행해"라고 명시적으로 말한 경우에만 이 단계를 압축할 수 있다.

### 4. 결정이 필요한 지점 — 임의로 정하지 않고 옵션을 제시한다

아래 상황은 코드를 보기 전엔 답이 안 나오고, 잘못 고르면 다른 화면을 깨뜨리거나 확정된 기획을 위반한다. 발견하면 옵션과 트레이드오프를 사용자에게 제시하고 답을 받는다.

- **공용 CSS 클래스를 재사용할지, 이 화면 전용 클래스를 새로 만들지.** `index.css`의 `.screen-header`, `.screen-footer`, `.btn-primary`, `.card`, bottom nav 클래스 등은 여러 화면이 같이 쓴다. 프로토타입이 요구하는 시각 값(예: 22px 제목, flat한 하단 nav)이 지금 공용 클래스의 값과 다르면, 그 공용 클래스의 *값을 바꾸는 것*이 아니라 *이 화면 전용 클래스를 새로 만드는 것*이 기본값이다(`today-header`, `mission-footer`처럼 화면 접두어를 붙인다). 공용 클래스 값을 바꾸는 선택지는 다른 화면 전부에 영향을 주므로, 정말 그렇게 할 이유가 있지 않은 한 제안하지 않는다.
- **프로토타입의 기능 조건이 기획/QA 문서와 충돌할 때.** 예: 프로토타입은 "정확히 3개 선택"을 강제하는데 설계 문서와 QA 문서는 "1개 이상이면 시작 가능"이라고 되어 있는 경우. 이건 순수 CSS 차이가 아니라 기능 변경이므로, 어느 쪽을 따를지 사용자에게 확인 없이 정하지 않는다.
- **프로토타입에 있지만 API로 정확히 계산할 수 없는 통계/집계 요소.** 예: 연속 N일 기록, 전체 기간 합계. 현재 화면이 가진 데이터 범위(예: 선택된 월의 캘린더 데이터만)로 정확히 계산되지 않으면 절대 근사치나 프론트 계산으로 채우지 않는다 — A) 계산 가능한 다른 값으로 대체, B) 그 요소 자체를 빼는 두 옵션을 제시한다.
- **다른 화면에 이미 있는 유사 UI(하단 nav, 아이콘 등)를 공유 컴포넌트로 뽑아낼지, 이 화면에 복제할지.** 기본값은 복제다 — 공유 컴포넌트 추출은 사용 처가 실제로 2곳 이상 확정됐을 때만 검토 대상이 된다(AGENTS.md의 추상화 기준과 동일).

### 5. 구현 원칙

- 프로토타입의 하드코딩된 콘텐츠(가짜 요약 문구, 고정 날짜, 고정 리스트, 가짜 로딩 타이머)를 그대로 복사하지 않는다. 실제 상태·API 응답과 연결한다.
- 색상 등 디자인 토큰은 `index.css`에 이미 정의된 CSS custom property를 재사용한다. 같은 색을 새 이름으로 중복 추가하지 않는다.
- 이미지 asset(마스코트 등)은 이미 있는 파일만 쓴다. 새로 그리거나 이모지/CSS 도형으로 대체하지 않는다. `alt=""` + `aria-hidden="true"`로 장식 이미지임을 명시한다.
- 공통 컴포넌트(로딩 화면 등)가 이미 있으면 재사용한다. 화면마다 새로 만들지 않는다.
- 아이콘 전용 버튼에는 `aria-label`, 커스텀 선택 UI(칩, 탭 등)에는 `role`/`aria-pressed`/`aria-current` 같은 접근성 속성을 프로토타입에 없더라도 추가한다 — 프로토타입은 정적 목업이라 접근성을 고려하지 않은 경우가 많다.
- 이미 있는 아이콘 의존성(예: `lucide-react`)이 프로젝트에 있으면 새 아이콘 라이브러리를 추가하지 않고 그걸 쓴다.

### 6. 테스트

- 기존 테스트를 최대한 그대로 유지한다. 화면 구조가 바뀌어 selector가 깨지면 그 selector만 새 구조에 맞게 고친다.
- 이 화면의 문구/라벨 변경 때문에 다른 화면의 통합 테스트(`App.test.tsx` 등)가 불가피하게 깨지는 경우가 있다 — 예를 들어 탭 라벨을 바꾸면 그 탭을 클릭하는 다른 화면의 E2E 테스트가 깨진다. 이런 경우는 실제로 불가피한지 먼저 확인한 뒤, 깨지는 부분만 최소로 고치고 그 이유를 보고에 남긴다. 범위를 넓혀서 다른 화면 자체를 고치는 것과는 다르다.
- 새로 추가하는 테스트는 "구조가 그대로다"가 아니라 "기능이 유지된다/새 조건이 지켜진다"를 검증하게 짠다.

### 7. 검증과 1차 리뷰

```bash
cd frontend
npm run typecheck
npm run lint
npm test
```

이 프로젝트에는 `.claude/rules/auto-implementation-review.md`에 정의된 규칙이 이미 있어서, 프로덕션 코드를 수정한 뒤에는 `implementation-code-reviewer` 서브에이전트로 1차 리뷰를 자동 실행해야 한다. 이 스킬은 그 규칙을 대체하지 않는다 — 검증 명령까지 실행했으면 그 규칙을 그대로 따라 리뷰를 돌린다.

### 8. 완료 보고와 커밋

완료 기준(2단계에서 보고했던 목록)을 다시 확인하고, 어떤 파일을 왜 고쳤는지 요약한다. 커밋은 사용자가 명시적으로 요청할 때만 하고, 화면 하나 = 커밋 하나 단위로 나눈다. 같은 파일(`App.test.tsx` 등)이 이전 화면 작업과 이번 화면 작업에 걸쳐 함께 수정된 경우, 깔끔하게 분리되지 않으면 그 사실을 사용자에게 알리고 어느 커밋에 포함시킬지 설명한다.

## 흔한 실패 패턴 (이미 겪었던 것들)

- 프로토타입엔 있는데 API엔 없는 값(연속 기록, 도메인명, 관심사 배지 등)을 "그래도 프로토타입이랑 똑같아야 하니까" 하드코딩하거나 프론트에서 부정확하게 계산해 채워 넣음 → 항상 4단계에서 먼저 걸러낸다.
- 화면 전용 값을 공용 클래스(`index.css`)에 바로 써서 다른 화면이 같이 바뀜 → 항상 화면 접두어가 붙은 새 클래스를 만든다.
- 라벨/문구를 바꿨는데 그 문구를 클릭하는 다른 화면의 테스트가 있다는 걸 나중에 발견해서 뒤늦게 고침 → 구현 직후 반드시 전체 테스트(`npm test`, 특정 파일만이 아니라)를 돌려서 확인한다.
- 승인받지 않은 채 여러 결정(공용 클래스 재사용 여부, 기능 조건 변경)을 한꺼번에 정하고 구현부터 함 → 3~4단계를 건너뛰지 않는다.
