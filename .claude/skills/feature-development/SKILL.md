# 기능 개발 절차

`docs/features/delete-checkin-plan.md`가 이 절차를 처음 적용한 예시다. 애매하면 그 문서 구조를 그대로 따른다.

## 절차

1. **현재 코드 분석** — 새 코드부터 짜지 않는다. 이 기능이 건드릴 라우터/서비스/화면 파일을 먼저 Read해서
   기존 네이밍, 에러 처리 방식(`{ error: { message } }`, `asyncHandler`), 레이어 구조(route→service, FE는
   Supabase 직접 호출 안 함)를 파악한다. `CLAUDE.md`의 컨벤션도 같이 확인한다.
2. **화면 → 데이터 → 흐름 순서로 설계**
   - 화면: 뭐가 새로 생기고 뭐가 바뀌는지
   - 데이터: 새 컬럼/테이블이 필요한지, 기존 스키마로 되는지
   - 흐름: API 메서드/경로/요청/성공응답/실패응답 + FE→Express→DB→FE 전체 흐름
3. **구현 방법 2~3개 비교** — 하나만 받지 않는다. 표로 장단점 비교하고, 왜 이번 범위엔 이게 맞는지
   이유를 붙여 하나를 추천한다. "새 라이브러리 필요 없음", "변경 파일 최소화"를 우선순위로 둔다.
4. **완료 기준을 먼저 체크박스로 작성** — "화면에 보인다" 수준이 아니라 "새로고침해도 남아있다",
   "존재하지 않는 값이면 이렇게 응답한다"처럼 눈으로 검증 가능한 문장으로 쓴다.
5. **작업을 반나절 단위로 분할하고 이슈 초안 작성** — 각 작업은 "명확한 한 문장 + 확인 방법" 쌍으로.
   이슈 제목 = 할 일, 본문 = 배경 + 완료 기준 + 작업 목록.
6. **사용자 승인 전 코드 작성 금지** — 1~5번 결과를 `docs/features/<기능명>-plan.md`로 저장하고,
   승인받기 전에는 구현 파일을 건드리지 않는다. 계획 자체의 약점(테스트 전략 미정 등)도 숨기지 않고
   문서 마지막에 적는다.
7. **승인 후 구현 + 검증** — 작업 목록 순서대로 하나씩 구현하고, 완료 기준 체크박스를 하나씩 채워가며 확인한다.
   테스트 컨벤션(`server/tests/*.test.js`, `node:test`)을 따른다.
8. **막힌 부분/실패 기록** — 구현 중 두 번 이상 실패했거나 계획과 다르게 간 부분이 있으면
   설계 문서 하단에 짧게 남긴다. 다음 기능 설계 때 참고한다.

## 검토 기준 (3번, 6번에서 스스로 점검)

- 역할이 제자리인가 — 화면 일은 화면에, DB 접근은 서비스 레이어에만
- 기존 구조를 따르는가 — 새 패턴/새 폴더/새 라이브러리를 갑자기 끌어오지 않는가
- 변경 범위가 적절한가 — 작은 기능인데 파일을 과하게 많이 건드리지 않는가

## 출력물

- `docs/features/<기능명>-plan.md` — 1~6번 결과
- 채팅에 이슈 초안 텍스트 (실제 GitHub 이슈 생성은 사용자가 원할 때만)
