# 밀라이즈 기능 검증 스킬

구현이 끝난 기능을 점검하는 **검증자 역할**. 만드는 사람이 아니라 **의심하는 사람**의 입장에서 본다.

## 대원칙

1. **코드를 읽고 판단한 것과 실제로 실행해 확인한 것을 반드시 구분한다.** 실행 안 해봤으면
   "통과"라고 쓰지 않는다 — `확인 필요`다.
2. **문제를 찾지 못한 것과 문제가 없는 것은 다르다.** 못 본 영역은 "점검 못 함"으로 남긴다.
3. **고치지 않는다.** 검증은 보고까지다. 수정은 사용자가 지시한 뒤에 한다.
   (단, 명백한 오타 수준이면 보고에 수정안을 코드로 제시한다.)
4. **원래 요구사항 원문을 먼저 다시 읽는다.** 기억이나 구현 코드에서 요구사항을 역추론하지 않는다 —
   구현이 요구사항을 잘못 읽었을 가능성이 검증 대상이다.

---

## 점검 1. 요구사항을 모두 만족하는가

요구사항을 **문장 단위로 쪼개 표로 만든다.** "대체로 됐다"는 검증이 아니다.

```
요구사항 원문: "24.9999 → 25, 0은 0, null/undefined는 0"
  → 조건 1: 소수점 반올림
  → 조건 2: 0 → 0
  → 조건 3: null/undefined → 0
```

각 조건마다 **어느 코드가 그걸 담당하는지 파일:줄로 짚는다.** 짚지 못하면 미구현이다.

특히 볼 것:
- **말 안 한 조건이 슬쩍 들어갔는가** (스펙에 없는 동작 = 나중에 버그로 돌아옴)
- **조건들이 서로 충돌하는가**
- **"~하지 않는다"류 부정 요구사항** — 가장 자주 누락된다

---

## 점검 2. 정상 입력에서 기대한 결과가 나오는가

- 대표적인 정상 입력 2~3개로 **직접 실행해 확인**한다 (테스트 작성 또는 `node -e`)
- 반환 **타입**까지 본다 (숫자를 기대했는데 문자열 `"25"`가 오는 경우)
- 계산 결과는 **손으로 계산한 값과 비교**한다. 구현 로직을 그대로 다시 써서 비교하면 검증이 아니다

---

## 점검 3. 경계값에서 문제없는가

| 종류 | 넣어볼 값 |
|---|---|
| 0 / 빈 값 | `0`, `''`, `[]`, `{}`, `null`, `undefined` |
| 아주 큰 값 | `999999`, `Number.MAX_SAFE_INTEGER`, `Infinity` |
| 아주 작은 값 | `0.0001`, `-0`, 음수 |
| 기준선 정확히 | 아래 표 참고 |

**이 프로젝트의 실제 기준선** — 정확히 이 값일 때를 반드시 본다:

| 상수 | 값 | 어디 |
|---|---|---|
| `NUTRIENT_SATISFY_RATIO` | `0.8` | `nutrition.js` — 충족 판정 |
| `NUTRIENT_EXCEED_RATIO` | `1.5` | `nutrition.js` — 초과 판정 |
| `DAY_STATUS_THRESHOLDS` | `{good: 5, normal: 2}` | `nutrition.js` — 하루 3단계 |
| `PLAUSIBILITY_OUTLIER_LOW/HIGH` | `0.5` / `1.5` | `nutrition.js` — 보정 발동 지점 |
| `ESTIMATED_GRAMS_MIN/MAX` | `20` / `1500` | `nutrition.js` — 범용 섭취량 범위 |
| `MAX_AD_PRODUCTS` | `3` | `adRecommendation.js` |

리스트/배열은 **0개, 1개, 아주 많이(1000개)** 를 본다. `docs/03-개발스펙.md` §4와
`scripts/generate-sample-csv.mjs`(1,000행 생성기)가 이미 있다.

날짜는 **월말/월초, 연말, 윤년**을 본다 (달력 탭·`dateKey` 관련).

---

## 점검 4. 잘못된 입력에서 앱이 죽지 않는가

목표는 **"예쁘게 처리"가 아니라 "화면이 하얗게 죽지 않는 것"** 이다.

- `null`/`undefined`/타입 불일치(숫자 자리에 문자열, 객체 자리에 배열)를 넣어본다
- **0으로 나누기** — `calcAchievementPercent`처럼 권장량이 분모인 곳
- `NaN`이 계산에 섞여 화면까지 전파되는가 (`NaN`이 렌더되면 사용자에게 `NaN`이 그대로 보인다)
- 옵셔널 체이닝 없이 `a.b.c`로 접근하는 곳 — 게스트/신규 사용자는 `profile`이 `null`이다
- **실패가 조용히 지나가는가** — PRD §2가 **무음 실패를 금지**한다. 실패하면 반드시
  `ToastContext`(`useToast`)로 사용자에게 보여야 한다. `catch {}`로 삼키고 끝나면 **문제 있음**이다
- API 에러 응답(4xx/5xx), 타임아웃(`fetchWithTimeout`은 28초 후 에러), 네트워크 끊김

## 점검 5. 기존 기능을 망가뜨리지 않았는가 (회귀)

```bash
npm test              # Vitest 전체
npm run check:ads     # 광고 추천 로직
npm run check:csv     # CSV 왕복
npm run lint          # oxlint (기존 경고 5건은 원래 있던 것 — 늘었는지만 본다)
npm run build         # 빌드가 깨지지 않는지
```

**바꾼 함수를 누가 쓰는지 반드시 찾는다:**

```bash
grep -rn "바꾼함수이름" src/
```

호출부마다 **인자·반환값 계약이 그대로인지** 확인한다. 이 프로젝트에서 특히 위험한 지점:

- **`src/lib/nutrition.js`** — 거의 모든 화면이 의존한다. 여기를 바꾸면 결과/식단/달력/MY 전부 확인
- **`calcNutritionScore`(`nutritionScore.js`)** — **`supabase/schema.sql`의 SQL 버전과 공식이
  반드시 같아야 한다.** 한쪽만 바꾸면 순위와 내 점수가 어긋난다
- **`src/lib/backupFormat.js`** — 내보내기 2곳과 가져오기 1곳이 공유한다. 한쪽만 바꾸면
  "내보낸 파일을 다시 못 읽는" 과거 버그가 재발한다
- **`src/lib/dataStore.js`** — 게스트/회원 양쪽 경로가 여기서 갈린다
- **`src/lib/storage.js`의 `cjmt:` 키 접두사** — 기존 게스트 데이터 호환용이라 **이름을 바꾸면
  기존 사용자 데이터가 사라진다**
- **`src/styles/theme.js`** — 토큰을 바꾸면 전 화면에 퍼진다

## 점검 6. 밀라이즈 특유의 점검

### 6-1. 영양 수치가 현실적인가

**표시된 숫자를 상식과 대조한다.** 이 앱의 핵심 가치가 수치 신뢰도라, 계산이 "돌아가는 것"보다
"말이 되는 것"이 중요하다.

기준 감각 (`NUTRIENT_PLAUSIBILITY` 실제 값):

| 음식 | 기준량 | 열량 | 단백질 |
|---|---|---|---|
| 비빔밥 | 500g | 550~700 kcal | 12~16 g |
| 김밥 | 230g | 320~520 kcal | 7~15 g |
| 치킨 | 300g | 540~980 kcal | 40~78 g |
| 삼겹살 | 150g | 360~620 kcal | 20~34 g |
| 떡볶이 | 250g | 290~540 kcal | 5~13 g |

- 하루 권장 열량은 대체로 **1400~3000 kcal**. 계산 결과가 이 밖이면 입력 프로필을 의심
- **한 끼가 2000 kcal를 넘거나 50 kcal 미만**이면 거의 확실히 버그
- 섭취량(g)이 `PORTION_REFERENCE_G` 범위 밖인데 보정이 안 걸렸는지
- **나트륨은 상한형**이다. 많이 먹을수록 좋은 것처럼 처리한 곳이 없는지 (광고 추천에서 나트륨이
  나오면 안 되고, 점수에서는 역방향이어야 한다)
- `formatNutrient`는 **표시 직전에만** 쓴다. 중간 계산을 반올림해 누적하면 오차가 쌓인다

### 6-2. 게스트/회원 둘 다에서 동작하는가

**로그인은 절대 필수가 아니다.** 새 기능이 로그인을 전제하면 그 자체가 문제다.

| 확인 | 내용 |
|---|---|
| 화면이 `dataStore`만 쓰는가 | 화면이 직접 `supabase`/`localStorage`를 부르면 **문제 있음** (`dataStore.js`가 유일한 분기점) |
| 게스트로 전체 흐름이 되는가 | 로그아웃 상태로 사진 분석 → 저장 → 달력 → 내보내기까지 |
| 회원으로도 되는가 | 로그인 상태로 같은 흐름 |
| 프로필이 없을 때 | 신규 게스트는 `profile`이 `null`이다. 죽지 않고 `SexPromptCard`로 유도되는가 |
| 로그인 유도가 게이트인가 | 기능을 막으면 안 된다. 안내만 |
| 게스트 데이터 보존 | 로그인 시 마이그레이션은 **명시적 동의 1회**. 거절해도 로컬 데이터는 남아야 한다 |
| id 기준 | 게스트는 `dataStore.GUEST_ID`, 회원은 uid — `effectiveUserId`를 쓰는가 |

**예외는 리더보드뿐이다** (로그인 계정끼리만 순위 비교, 게스트는 자기 점수만). 이건 의도된 설계다.

### 6-3. 모바일 화면에서 깨지지 않는가

기준 폭은 **430px** (`theme.js`의 `layout.maxWidth`). 실기기 확인이 어려우면 브라우저
개발자도구 반응형 모드로 본다.

| 확인 | 내용 |
|---|---|
| 좁은 화면 | **320px**(구형 소형폰)에서 가로 스크롤이 생기거나 글자가 잘리지 않는가 |
| 긴 텍스트 | 음식 이름/식당 이름이 길 때 레이아웃이 밀리는가 (긴 한글 이름으로 테스트) |
| 숫자 자릿수 | 열량 4자리(`1100`)일 때 칸을 넘치는가 |
| 탭 바 가림 | 하단 고정 탭 바에 콘텐츠 마지막 줄이 가리는가 |
| 안전 영역 | 노치/제스처 바 — 헤더·탭 바가 `env(safe-area-inset-*)`를 쓰는가 |
| 터치 영역 | 버튼이 손가락으로 누를 만한 크기인가 (44px 권장) |
| 애니메이션 | **`transform`/`opacity`만** 쓰는가. `width`/`height`/`left` 애니메이션은 **문제 있음** (진행바는 `ProgressBarFill`의 `scaleX`) |
| 누르는 느낌 | 인터랙티브 요소에 `Pressable` 또는 `className="tds-press"`가 있는가 |
| 디자인 토큰 | 하드코딩된 `#색상`/`px` 대신 `theme.js` 토큰을 쓰는가 |
| 로딩/빈 상태 | 데이터 없을 때 화면이 텅 비지 않고 안내가 나오는가 |

### 6-4. 안드로이드 앱(APK)에서도 되는가

현재 `capacitor.config.json`이 **server-URL 모드**라 배포하면 앱에 바로 반영된다.

- 새 외부 링크는 `openExternalLink`를 쓰는가 (WebView는 `target="_blank"`를 막는다)
- 파일 저장은 `saveTextFile`을 쓰는가 (웹/네이티브 분기 유일 지점)
- 새 API 호출이 `/api`로 시작하는가 (`API_BASE`가 붙어야 앱에서 백엔드를 찾는다)
- 하드웨어 뒤로가기가 자연스러운가

### 6-5. 법적/정책 고지

- **`COUPANG_DISCLOSURE` 문구와 AD 배지는 어떤 상태에서도 생략되면 안 된다** (법정 고지)
- `recommendAdProducts`는 **절대 빈 배열을 반환하지 않아야** 한다 (배너가 비면 안 됨)
- API 키가 프론트엔드 번들에 들어가지 않았는가 — 브라우저로 나가는 건 `VITE_` 접두사가 붙은
  공개용 키뿐이다. `OPENROUTER_API_KEY` 같은 게 `src/`에 있으면 **즉시 문제 있음**

## 보고 형식

점검이 끝나면 아래 형식으로 보고한다. **요약 표를 맨 위에 둔다.**

```markdown
## 검증 결과 요약

| 구분 | 개수 |
|---|---|
| ✅ 통과 | 8 |
| ❌ 문제 있음 | 2 |
| ⚠️ 확인 필요 | 3 |

**결론: (한 줄) — 예: 핵심 요구사항 3개는 만족하나, 게스트 모드에서 화면이 죽는 문제가 있어 배포 불가.**

---

### ❌ 문제 있음

**1. 게스트 모드에서 화면이 하얗게 죽는다**
- 위치: `src/pages/Meals.jsx:42`
- 원인: `profile.sex`를 옵셔널 체이닝 없이 접근 — 신규 게스트는 `profile`이 `null`
- 재현: 로그아웃 → 프로필 미입력 상태로 `/meals` 진입
- 확인 방법: 실행함 / 코드 판독
- 제안: `profile?.sex`

### ⚠️ 확인 필요

**1. 아주 큰 값에서의 동작을 확인하지 못함**
- 이유: 실기기 없이 확인 불가 / 요구사항에 정의가 없음
- 필요한 결정: `Infinity`가 들어오면 0인가 그대로인가?

### ✅ 통과

- 요구사항 1 (소수점 반올림) — `nutrition.js:241`, 테스트 4건 실행해 확인
- ...

---

### 점검하지 못한 영역
- 실기기 확인 (안드로이드 APK) — 환경 없음
- 로그인 상태 전체 흐름 — Supabase 계정 없음
```

### 분류 기준

| 분류 | 언제 |
|---|---|
| ✅ **통과** | **실제로 확인했고** 기대대로 동작함. 코드만 읽고 "될 것 같다"는 통과가 아니다 |
| ❌ **문제 있음** | 요구사항 미충족 / 앱이 죽음 / 무음 실패 / 회귀 / 수치가 비현실적 / 법정 고지 누락 |
| ⚠️ **확인 필요** | 실행해보지 못함 / 요구사항에 정의가 없어 판단 불가 / 판단은 되나 근거가 약함 |

**심각도가 아니라 확신도로 나눈다.** "아마 될 것"은 ⚠️다.

각 항목에는 **위치(파일:줄)**, **재현 방법**, **확인 방법(실행 / 코드 판독)** 을 반드시 적는다.

## 검증 순서 체크리스트

1. [ ] 요구사항 **원문**을 다시 읽고 조건별로 쪼갠다
2. [ ] 변경된 코드를 읽는다 (`git diff`)
3. [ ] 조건마다 담당 코드를 파일:줄로 짚는다 → 점검 1

5. [ ] 경계값·잘못된 입력을 넣어본다 → 점검 3, 4
6. [ ] `npm test` / `check:ads` / `check:csv` / `lint` / `build` → 점검 5
7. [ ] `grep -rn`으로 호출부 영향 확인 → 점검 5
8. [ ] 밀라이즈 특유 항목 → 점검 6
9. [ ] 통과/문제/확인 필요로 분류해 보고. **점검 못 한 영역도 적는다**
