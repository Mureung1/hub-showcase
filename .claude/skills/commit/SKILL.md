# 최소단위 커밋 절차

변경사항 전체를 한 번에 커밋하지 않는다. 아래 절차로 논리 단위마다 커밋을 반복한다.

## 1. 변경 전수 파악

```bash
git status
git diff          # unstaged
git diff --stat
```

## 2. 논리 단위로 그룹핑

- 기준은 **의도**다: "이 커밋 하나를 되돌리면 정확히 무엇이 사라지는가?"에 한 문장으로 답할 수 있어야 한다
- 전형적 단위: 기능 1개, 버그 수정 1개, 문서 변경 1건, 설정 변경 1건, 리팩토링 1건
- 섞지 말 것: 기능+무관한 포맷팅, 기능A+기능B, 코드+무관한 문서
- 한 파일에 두 단위가 섞였으면 `git add -p <파일>` 로 헝크 단위 분리
- 그룹핑 결과(커밋 N개 계획)를 커밋 시작 전에 사용자에게 한 줄씩 보여준다

## 3. 단위별 커밋 (반복)

```bash
git add <파일1> <파일2>        # 경로 명시 — git add . / -A 금지 (훅 차단)
git diff --cached --stat       # 스테이징 내용 확인
git commit -m "type: 한국어 요약"
```

- type: `feat` / `fix` / `docs` / `style` / `refactor` / `test` / `chore`
- 요약은 50자 이내, 무엇이 왜 바뀌었는지. 본문이 필요하면 빈 줄 후 추가
- 커밋 순서는 의존 방향대로: 기반(타입/데이터) → 사용처(컴포넌트) → 문서

## 4. 커밋마다 검증

- 각 커밋 시점의 스냅샷이 독립적으로 성립해야 한다: `npx oxlint` (훅이 자동 검사), 코드 변경이면 `npm run build`
- 중간 커밋이 빌드를 깨뜨리면 안 된다 — 깨지면 그룹핑을 다시 나눈다

## 5. 마무리 보고

- 만든 커밋 목록을 `git log --oneline -<N>` 으로 보여준다
- 푸시는 사용자가 요청한 경우에만 한다

## 금지

- `git add .` / `git add -A` / `git add --all` / `git commit -a` (훅으로 차단됨)
- 사용자 요청 없는 커밋·푸시
- 여러 논리 단위를 하나의 커밋으로 뭉치기
