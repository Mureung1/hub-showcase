이 스킬은 이 세션에서 반복적으로 정한 커밋 규칙 — 메시지 형식, 개행 있는 메시지를 넣는 방법, 무엇을 커밋 대상에서 뺄지 — 을 고정해둔 것이다. "/commit" 또는 "커밋할 내용 있는지 찾아봐" 요청에 이 절차를 적용한다.

## 절대 하지 않는 것

**`git add`·`git commit`·`git push`를 직접 실행하지 않는다.** 정확한 명령과 커밋 메시지 초안만 제시하고, 사용자가 자기 터미널에서 직접 타이핑해서 실행한다. 이건 이 프로젝트 전체의 표준 규칙이고, 이 스킬도 예외를 두지 않는다.

## 1. 커밋 대상 찾기

1. `git status --short`로 전체 변경 목록을 본다.
2. 각 항목이 **이번에 한 작업과 관련 있는지** 구분한다. 관련 없는 파일(예: 예전부터 있던 미커밋 항목, 아직 커밋 보류하기로 사용자가 정한 파일)은 손대지 않는다.
3. `M`으로 표시됐지만 `git diff -- <파일>`을 찍어보면 실제 내용 변경이 없는 파일이 있을 수 있다 — Windows의 `core.autocrlf` 설정 때문에 줄바꿈 문자(LF/CRLF)만 다른 경우다("LF will be replaced by CRLF" 경고만 뜨고 `+`/`-` 라인이 없으면 이 경우다). 이런 파일은 실질적 변경이 아니므로 커밋 대상에서 자연스럽게 빠진다는 걸 사용자에게 짚어준다.

## 2. 개념 단위로 나누기

- 이번 작업이 여러 개념(예: "버그 수정" + "리팩토링")을 포함하면, 파일이 겹치지 않는 한 그냥 파일별로 나눠서 여러 번 커밋한다.
- **한 파일 안에 서로 다른 개념이 섞여 있으면** `git add -p <파일>`로 들어가서, 각 hunk("Stage this hunk [y,n,...]?")마다 관련 있는 것만 `y`, 나머지는 `n`으로 답하도록 안내한다. 어떤 hunk가 어느 커밋에 속하는지 미리 `git diff`로 확인해서 정확히 짝지어준다.
- 커밋 순서와 각 커밋에 들어갈 파일 목록을 사용자에게 먼저 표로/목록으로 보여준다.

## 3. 커밋 메시지 형식

```
타입: 제목 (한 줄)

- 본문 불릿 1
- 본문 불릿 2
```

- 타입은 `docs`/`chore`/`test`/`feat`/`fix` 중 실제로 맞는 것 하나.
- 제목은 "무엇을 했는지"를 명령형으로 간결하게.
- 본문은 "왜"를 중심으로 1~3줄 불릿.

## 4. 커밋 명령은 항상 에디터 방식으로

**절대 `-m`에 여러 줄을 넣지 않는다. `-m`을 여러 번 반복해서 붙이지도 않는다.** cmd.exe는 붙여넣은 개행을 그대로 Enter로 처리해서 여러 줄 메시지가 깨진다 — 실제로 이 문제로 커밋 메시지가 망가진 적이 있다.

대신 항상 이 순서로 안내한다:

```
git add <파일...>
git commit
```

에디터(vim)가 열리면:
1. `i` — 입력 모드 진입 (이걸 빼먹으면 타이핑이 명령으로 해석돼서 아무것도 안 써진다)
2. 위 형식대로 메시지 타이핑
3. `Esc`
4. `:wq` + Enter — 저장하고 종료

## 5. 완료 후

사용자가 실행 결과(성공/실패, 빈 메시지로 취소됐는지 등)를 캡처해서 보여주면 그걸 보고 다음 커밋으로 이어가거나 실패 원인을 짚어준다. 결과를 보지 않고 성공했다고 단정하지 않는다.
