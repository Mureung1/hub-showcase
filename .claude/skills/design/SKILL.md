# GradPlan 디자인 Skill

## 언제 이 skill을 확인해야 하는가
- 새 화면(페이지)을 만들 때
- 모달, 카드, 진행률 바 등 UI 요소를 새로 만들 때
- "이 디자인 괜찮아 보여?"라는 질문에 답할 때 (자체 검수용)

## 톤 & 방향성
- 참고 레퍼런스: 토스(Toss) 웹 — 흰 배경 + 절제된 파란색 포인트
- 무거운 남색·보라색을 메인 텍스트/배경 색으로 쓰지 않는다
- 장식보다 여백과 실제 데이터(숫자, 진행률)를 우선한다

## 컬러 토큰
```
--bg: #FFFFFF
--text-primary: #191F28   (헤딩/강조 — 남색 아님, 블랙 계열)
--text-secondary: #4E5968
--point: #3182F6          (버튼/링크 전용, 상태 표현에 쓰지 않음)
--point-light: #E8F3FF
--success: #00C880 / --success-bg: #E7FAF3   (요건 충족)
--warning: #FF9800 / --warning-bg: #FFF4E5   (부족)
--danger: #F04452 / --danger-bg: #FDEDEE     (심각한 미충족)
--card-border: #F2F4F6
--radius-md: 16px
```
전체 토큰은 `gradplan-design-system.md` 참조.

## 타이포그래피
- 폰트: Pretendard (Sora, 시스템 폰트 사용 금지)
- 헤딩: weight 700~800, `--text-primary` 색상
- 본문: weight 400, `--text-secondary` 색상

## 인터랙션 패턴 (반복적으로 쓰이는 구조)

### 패턴 1 — 다단계 입력 모달
사용자에게 여러 종류의 정보를 순차적으로 받아야 할 때 (예: 졸업요건 → 현재 이수 학점):
- 모달을 하나로 합치지 않는다. 각 정보 단계마다 별도 모달로 분리하고, 제출 시 다음 모달로 자연스럽게 전환한다
- 같은 성격의 모달은 레이아웃·버튼 스타일을 완전히 동일하게 유지한다 (사용자가 "같은 종류의 입력"이라고 인지하도록)
- 모든 모달이 끝나면, 입력값을 요약해서 보여주는 **요약 바**를 화면 상단에 남긴다
- 요약 바의 각 항목은 클릭 시 해당 모달을 다시 열어 재입력할 수 있어야 한다 — 한쪽을 수정해도 다른 쪽 데이터는 유지되어야 한다
- 실제 입력값 반영은 JS로 구현한다 (체크박스형 선택이 아닌 자유 입력값은 CSS만으로 반영 불가)

### 패턴 2 — 카드 목록 + 추가(+) 카드
사용자가 여러 개의 항목(시간표, 계획안 등)을 만들고 관리하는 화면:
- 항목 카드들과 동일한 크기의 "추가" 카드를 목록 끝에 항상 포함한다
- 추가 카드는 옅은 회색 배경 + 둥근 모서리 + 중앙에 "+" 아이콘만
- 항목이 적을 때(3개 이하)는 가로 배치, 그 이상이 되면 캐러셀로 전환 — 가운데 카드를 강조(포커스)하고 좌우는 흐리게/작게 표시, 스와이프 또는 화살표로 이동
- 추가 카드는 캐러셀 안에서도 항상 끝에 포함되어야 한다 (개수 제한 없이 계속 추가 가능해야 함)

### 패턴 3 — 진행률/상태 표시
- 상태(충족/부족/심각)는 색의 짙기가 아니라 success/warning/danger 3색으로 구분한다
- 세부 요건(다중전공/현장실습/해외학점/창업/종합설계)처럼 이진 판정(충족 여부)에 가까운 항목은 진행률 바보다 뱃지나 체크 아이콘이 더 적절할 수 있다 — 항목의 성격(연속값 vs 이진값)에 따라 표현 방식을 다르게 선택한다

## 판단 규칙 (자체 검수 체크리스트)
UI를 만든 뒤, 아래를 스스로 점검한다:
1. 헤딩 텍스트 색이 남색이 아니라 `--text-primary`(차콜)인가?
2. 상태 표현이 색의 짙기가 아니라 success/warning/danger 3색으로 구분되어 있는가?
3. 카드 구분이 그림자 남발이 아니라 얇은 보더 위주인가?
4. 파란색(`--point`)이 상태 표현이 아니라 버튼/링크에만 쓰였는가?
5. 폰트가 Pretendard로 적용되어 있는가?
6. 자유 입력값을 반영해야 하는 인터랙션에 CSS만으로 해결하려 하지 않았는가? (JS 필요 여부 먼저 판단)
7. 여러 단계의 입력을 모달 하나에 욱여넣지 않았는가?

이 중 하나라도 어긋나면, 이유를 설명하고 수정할 것.

## Don't
- 진행률 바나 뱃지에 파스텔 톤을 무분별하게 여러 개 쓰지 않는다
- 배경에 장식용 원형 그라디언트를 과도하게 넣지 않는다
- 카드마다 다른 radius 값을 임의로 쓰지 않는다 (정해진 --radius-lg/md/sm만 사용)
- 조합 가능한 상태값(체크박스 여러 개의 합산 등)을 CSS 선택자로 하드코딩하지 않는다 — 계산이 필요한 곳은 서버/JS 로직으로 분리한다
