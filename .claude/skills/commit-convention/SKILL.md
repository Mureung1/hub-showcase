# 커밋 · 브랜치 컨벤션

## 커밋 형식
`<type>: <설명>` (한글, 간결)
예) `feat: 주차장 목록 조회 API 구현`

## type
- `feat` 기능 추가
- `fix` 버그 수정
- `docs` 문서
- `refactor` 리팩터링(기능 변화 없음)
- `chore` 설정·빌드·기타
- `test` 테스트
- `style` 포맷팅(동작 무관)

## 커밋 원칙
- **작은 단위로** 자주 커밋 (한 커밋 = 한 논리적 변경)
- 커밋 메시지는 **한글**

## 브랜치
- `work`에서 브랜치 파서 작업 → 커밋 → `work` 머지. 이름 `기능명` 또는 `type/기능명`
- **작업(파일 생성·수정)을 시작하기 전에, 새 브랜치가 필요하거나 브랜치를 바꿔야 하는 상황이면 먼저 사용자에게 알리고 확인받는다.** (git 작업은 사용자가 직접 수행)

## 하지 말 것
- 여러 논리적 변경을 한 커밋에 섞기
- 의미 없는 메시지(`수정`, `ㅇㅇ` 등)
