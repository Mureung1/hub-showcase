# 시드 예시 작성·검수 절차 (SPEC 4장 집행)

시드 24개는 few-shot의 전부이자 서비스 품질의 상한이다. 코드와 독립적으로 언제든 진행 가능.

## 산출물 위치

- 초안: `docs/SEEDS.md` — 시나리오별 섹션, 상황별 3톤 세트를 JSON 블록으로 작성
- T19(프롬프트 구성) 시점에 프록시 상수로 이관한다. 이관 전까지 docs가 원본.

## 1. 상황 선정 (작성 전에 사용자와 합의)

- 시나리오당 **상황 2개** — 그 관계의 대학생 대표 상황으로 구체적으로 잡는다 (예: 팀플·조모임 → 무임승차 지적 / 일정 조율).
- 상황 2개 중 **최소 1개는 받은 메시지가 없는 "먼저 보내는" 상황** (2026-07-08 서비스 정의 확장 — 두 생성 모드 커버).
- 상황 목록(4 시나리오 × 2)을 표로 먼저 제시하고 사용자 확인 후 작성에 들어간다. 상황이 어긋나면 24개가 통째로 재작업이다.

## 2. 작성 — 세트 단위

스키마 (SPEC 4장, 필드명 주의 — `message`):

```jsonc
{
  "scenarioId": "groupwork",        // groupwork | professor | senior | friend
  "situationNote": "...",            // 이 시드가 가정한 상황
  "receivedMessage": "...",          // 먼저 보내는 상황이면 생략
  "toneLevel": 1,                    // 1 | 2 | 3 (SPEC 1장 라벨 순서)
  "message": "...",                  // 보낼 말 본문 (핵심 자산)
  "source": "team"                   // MVP 기본 team
}
```

규칙:
- **같은 상황의 3톤을 세트로** 작성 — `situationNote`·`receivedMessage`가 세트 안에서 동일해야 한다.
- 세트 안에서 **내용은 같고 태도만** 다르게. 내용이 달라지면 톤 비교가 아니다.
- 길이·형식: 팀플·선배·친구는 1~3문장 구어체, 교수님·조교님은 인사–용건–맺음 3~6문장.
- 금지: 실명·학과·식별 정보, 플레이스홀더(`[이름]`, `OO`), 허위 사유(가족상 등), 커뮤니티 사례 원문(패턴 참고 후 재작성만 — `source: "rewrite"`).
- "단호하게"·"적극적으로" 끝단도 정중함의 하한선 유지 (EDGE_CASES 6-1 — 시드가 곧 안전 가이드다).

## 3. 검수 — 세트 전수

1. **자체 스크리닝** (작성 직후): 금지 항목 스캔, 세트 내 내용 동일성, 톤 라벨-본문 정합.
2. **블라인드 정렬** (제3자 필요): 톤 라벨을 가린 세트 3개를 제3자에게 순서대로 정렬시킨다 — 이 단계는 사용자가 팀원·지인과 직접 수행해야 하므로, 검수용 자료(라벨 가린 무작위 순서 세트)를 만들어 제공한다. 정렬 불일치 세트는 재작성.
3. **전송 가능성**: 각 후보를 "지금 그 상황이라면 이대로 보낼 수 있나"로 판정. 아니오 → 재작성.

## 4. 완료 처리

- T15 = 팀플·교수님 12개 작성, T16 = 선배·친구 12개 + 24개 전수 검수 통과.
- 검수까지 끝나야 CHECKLIST 체크. 커밋은 사용자 요청 시 `/commit`.
