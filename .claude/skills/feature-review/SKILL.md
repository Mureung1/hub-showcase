# 기능 리뷰

브랜치의 이슈가 전부 끝났을 때, **`work` 에 머지하기 전에** 한다.
머지한 뒤에 발견하면 되돌리는 비용이 달라진다. 여기가 **싸게 고칠 수 있는 마지막 지점**이다.

**코드를 다시 읽는 자리가 아니다.** 코드는 이슈마다 `code-review` 에서 이미 봤다.
여기서 보는 것은 **합쳐 놓았을 때 생기는 문제**다. 커밋 하나하나가 옳아도 합치면 틀릴 수 있다.

## 먼저 돌려본다

읽어서는 안 보인다. **처음부터 끝까지 실제로 해본다.**

- 사용자가 하는 순서 그대로 — 화면에서 시작해 화면으로 끝난다
- 새로고침 · 뒤로가기 · 링크로 바로 들어오기
- 값이 없는 경우 하나 — 결과 0건 · 정보가 비어 있는 항목

여기서 막히면 나머지는 볼 필요가 없다. 고치고 다시 시작한다.

## 무엇을 보나

| 관점 | 묻는 것 |
|---|---|
| **정합성** | 같은 사실이 두 곳에 있는가. 갱신 주기가 다른 데이터를 한 화면에 같이 보여주는가 |
| **동시성** | 쓰는 중에 읽으면 어떻게 되는가. 주기 작업과 사용자 요청이 겹치면 |
| **성능** | 요청 하나에 쿼리 · 외부 호출이 몇 번인가. 데이터가 10배가 되면 |
| **장애** | 외부 API가 느리거나 죽으면 화면이 어떻게 되는가. 우리까지 같이 멈추는가 |
| **되돌리기** | 문제가 생기면 되돌릴 수 있는가. 스키마 · 적재된 데이터가 이미 바뀌었는가 |

- **숫자로 확인한다.** "괜찮아 보인다"가 아니라 쿼리 수 · 응답 시간 · 실패했을 때의 동작을 본다.
- 여기서 나온 문제는 `code-review` 의 **결함**과 같은 무게다. 애매한 채로 머지하지 않는다.

## 무엇을 건드렸나로 관점을 고른다

기능마다 다섯 개가 다 의미 있지는 않다. **건드린 것이 관점을 정한다** — 브랜치 크기가 아니다.

| 건드린 것 | 보는 관점 |
|---|---|
| 화면 · 문구 · 설정만 | 흐름 |
| 조회 경로를 추가 · 변경 | 흐름 · 성능 |
| 외부 API 호출을 추가 | 흐름 · 장애 |
| 저장 · 주기 작업 · 스키마 | 전부 |

- **흐름은 어떤 경우에도 생략하지 않는다.**
- 한 줄만 고쳤어도 그 한 줄이 주기 작업이면 전부 본다. 줄일지 애매하면 줄이지 않는다.

## 설계와 대조한다

- 플랜에서 **넣지 않기로 한 것**이 슬그머니 들어오지 않았나
- 버린 안이 중간에 되살아나지 않았나
- 설계와 다르게 갔다면 **이슈에 이유가 남아 있는가**

## 미뤄둔 것을 정리한다

이슈 리뷰에서 "나중에 보기로" 한 제안들이 여기서 만난다.

- 이번에 고칠 것 → 고친다
- 나중에 할 것 → **이슈로 등록한다.** 머릿속에 두지 않는다
- 안 할 것 → 버리고 이유를 남긴다

## 머지 조건

| 항목 | 조건 |
|---|---|
| 흐름 | 처음부터 끝까지 동작한다 |
| 다섯 관점 | 확인했고, 나온 문제는 고쳤거나 이슈로 남았다 |
| 미뤄둔 것 | 머릿속에만 남은 것이 없다 |

셋이 닫히면 `work` 에 머지한다. 머지 방식은 `commit-convention` 을 따른다.

## 하지 말 것

- 머지한 뒤에 기능 리뷰하기
- 코드만 읽고 돌려보지 않기
- 문제를 찾고도 "일단 머지" 하기
- 미뤄둔 것을 기록 없이 넘기기
