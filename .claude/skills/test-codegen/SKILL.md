# 테스트 코드 생성

이 스킬은 `server/`의 소스 파일에 테스트를 새로 작성할 때 호출한다. 컨벤션 원본은 `server/TESTING.md`(이 스킬 파일 기준 `../../../server/TESTING.md`).

## 절차

1. 대상 파일과 함께 관련 문서를 읽는다: 소스 코드 자체, 그리고 있다면 `docs/api-spec.md`(hub 루트, `server`/`my-app` 공용 — 이 스킬 파일 기준 `../../../docs/api-spec.md`) 등 도메인 규칙 문서. 기댓값은 코드 실행 결과를 베끼지 않고 이 문서/규칙을 기준으로 먼저 정한다. 해당 기능에 대한 기준 문서가 없으면 코드를 보고 임의로 추측하지 말고, 기댓값을 사용자에게 먼저 물어본 뒤 진행한다.
2. 대상을 아래 세 유형 중 하나로 구분한다. 셋 중 어디에도 안 맞으면(예: 미들웨어, DB 클라이언트 설정 파일) 임의로 판단하지 말고 사용자에게 먼저 물어본다.
   - 순수 함수(예: `postContent.js`, `brandProfileContent.js`) → DB 의존 없는 단위 테스트만
   - Repo(예: `postsRepo.js`, `brandProfileRepo.js` — Supabase를 직접 호출하지만 Express 레이어는 안 거침) → supertest 없이 함수를 직접 호출하는 실제 Supabase 통합 테스트. cleanup은 라우트 테스트와 동일하게 적용
   - 라우트(`routes/*.js`) → supertest + 실제 Supabase 통합 테스트 (mock 없음)
3. 쓰기 전에 대상 함수/엔드포인트를 이미 검증하는 `describe`/`it`이 있는지 확인한다 (대상 이름으로 된 `describe` 블록 검색). 있으면 무조건 새로 추가하지 말고 사용자에게 의도를 먼저 물어본다.
   - 소스 코드는 안 바뀌었고 재검증만 필요하다 → 코드 생성 없이 8번(테스트 실행)으로 바로 간다.
   - 소스 코드가 바뀌어서 기존 테스트의 기댓값을 갱신해야 한다 → 기존 `describe`/`it`을 수정한다.
   - 기존 케이스는 유지하고 커버리지만 넓히고 싶다 → 같은 `describe` 안에 새 `it`만 추가한다.
4. **테스트 코드를 쓰기 전에 계획부터 세운다** (3번에서 재검증만 하기로 했다면 이 단계는 건너뛰고 8번으로 간다). 대상의 조건 분기, 필수 필드, 에러 코드를 근거로 테스트 케이스를 목록으로 먼저 정리한다 — 정상 케이스, 빈 값, 경계값, 실패하는 경우로 나눠서 나열한다. 나열한 뒤 빠진 케이스가 있는지 다시 점검하고 채운다. 이 목록이 끝나기 전에는 실제 테스트 코드를 작성하지 않는다.
5. 테스트 파일 이름과 import 경로를 정한다: 소스 파일 옆에 `*.test.js`. import는 같은 폴더의 소스 파일을 상대 경로로 직접 가리킨다 (예: `import { buildNoticePost } from "./postContent.js";`). 이미 파일이 있으면 새 `describe`/`it`을 이어붙이고, 없으면 새로 만든다.
6. 라우트/Repo 테스트는 `afterEach`에서 생성한 데이터를 직접 정리한다 (`posts.test.js` 패턴 참고: id를 배열에 모아뒀다가 `supabase.from(...).delete()`). `vitest.setup.js`가 `.env`를 로드해주므로 별도 설정은 필요 없다.
7. 아래 원칙을 모두 지킨다 (TESTING.md 기준). 6번(happy path + edge case)은 4번에서 이미 목록으로 정리했으므로 그 목록대로 빠짐없이 작성했는지만 다시 확인한다.
   1. 구현이 아니라 행동을 테스트
   2. 테스트 하나 = 시나리오 하나
   3. AAA 패턴 (Arrange-Act-Assert), 주석으로 구분 — 같은 `describe` 안 모든 `it`에 예외 없이 적용 (첫 번째 `it`만 주석 달고 나머지는 생략하지 않는다)
   4. 테스트 이름만 보고 뭘 검증하는지 알 수 있게
   5. 독립성 (순서 무관, cleanup으로 보장)
   6. happy path + edge case(누락값/잘못된 값) 모두 포함
   7. (라우트) status code + 응답 형식 검증
   8. (라우트) 사이드 이펙트까지 확인 (재조회 등으로 DB 반영 여부 확인)
8. 작성 후(또는 3번에서 재검증만 필요하다고 판단했으면 바로) `server` 디렉토리에서 대상 테스트 파일만 실행한다 (`npx vitest run <테스트 파일 경로>`). 전체 스위트는 돌리지 않는다 — 실제 Supabase에 붙는 방식이라 무관한 기존 테스트까지 매번 데이터를 쓰고 지우게 하지 않기 위함.
9. 실패하면 바로 고치지 않는다 — 실패 원인(테스트 자체의 문제인지, 코드의 실제 버그인지)을 사용자에게 먼저 보여주고 해결 방향을 함께 정한다. 원인이 테스트 코드에 있으면 테스트를, 소스 코드의 실제 버그면 소스 코드를 고친다 — 이 스킬의 범위에는 구현 코드 수정도 포함된다.
   - 테스트 파일만 고쳤다면 8번으로 돌아가 그 테스트 파일만 다시 실행한다.
   - 소스 코드(구현 파일)를 고쳤다면 그 수정이 다른 곳을 깨뜨리지 않았는지 확인하기 위해 이번엔 `npm test`로 전체 스위트를 실행한다.
   - 통과할 때까지 반복한다.
10. 통과하면 결과를 요약해서 보고한다. `TESTING.md`의 "예시 파일" 표는 전체 테스트 파일 목록이 아니라 대표 패턴을 큐레이션한 것이므로, 방금 만든 파일이 표에 아직 없는 새로운 성격(예: 순수 함수 단위 테스트/라우트 통합 테스트가 아닌 제3의 패턴)을 보여줄 때만 행 추가를 제안한다. 기존 두 패턴 중 하나를 반복하는 파일이면 표는 그대로 둔다. 추가할 때는 기존 행과 같은 3열 형식을 따른다.
   - **파일**: 새로 만든 `*.test.js` 경로
   - **성격**: 테스트 종류 한 줄 요약 (예: "순수 함수 단위 테스트, DB 의존 없음")
   - **확인**: 검증하는 시나리오를 정상 케이스 + 에러 케이스 위주로 짧게 나열
