# T항목 착수 절차 (5요소 작업 프레임)

CHECKLIST의 T항목을 주먹구구로 시작하지 않는다. 아래 순서를 지킨다.

## 1. 항목·의존성 확인

- docs/CHECKLIST.md에서 해당 T항목과 **의존 열**을 읽는다.
- 의존 항목이 미완(체크 안 됨)이면 **착수하지 않고** 사용자에게 보고한다. 의존을 건너뛴 구현은 계약(타입)이 없는 상태에서 짐작으로 짜게 되어 재작업을 만든다.
- 항목 번호 없이 "다음 거 해줘"로 요청받으면: 체크 안 된 항목 중 의존이 모두 충족된 **가장 앞 번호**를 고르고, 어떤 항목인지 먼저 밝힌다.

## 2. 관련 문서 로드

항목이 참조하는 문서만 골라 읽는다 (전부 읽지 않는다):

| 항목 성격 | 필수 문서 |
|---|---|
| 타입·상수 (T2, T3) | SPEC 1~2장 |
| 화면 (T6, T7, T9) | SCREENS 해당 화면 + DESIGN 토큰 + UX 6장 요약표 |
| 상태·파이프라인 (T5, T8, T12, T13) | SCREENS 상태 정의 + SPEC 2장 + EDGE_CASES 해당 번호 |
| 시드 (T15, T16) | `/seed` 스킬로 위임 |
| 프록시·프롬프트 (T18, T19) | SPEC 2~4장 + EDGE_CASES 1-5, 1-6, 5-1, 5-2 |
| 검수·배포 (T17, T20~T23) | SPEC 5장 + MVP DoD + docs/CICD.md |

## 3. 5요소 작업 계획 수립 — 구현 전에 사용자에게 제시

코드를 쓰기 전에 아래 표를 채워서 보여준다. 한 요소라도 못 채우면 그 빈칸이 곧 질문거리다 — 짐작으로 메우지 말고 사용자에게 묻는다.

| 요소 | 채울 내용 |
|---|---|
| **맥락** | 스택·제약·목표: React+TS(Vite), 추가 라이브러리 금지(도입은 사전 승인), `any` 금지, 이 항목이 끝나면 무엇이 가능해지는가 |
| **구체성** | 무엇을·어디에·어떻게: 만들 파일/수정할 파일 경로, 컴포넌트/모듈 이름(SCREENS 컴포넌트 후보 기준), 적용할 규칙 |
| **역할·예시** | 입출력 예: props 예시, API 요청/응답 예시(SPEC 2장), 상태 전이 예시 — 실물 데이터 형태로 |
| **단계화** | 작게 쪼갠 구현 순서 (예: ① 타입 → ② UI 렌더만 → ③ 이벤트 → ④ 상태·엣지케이스). 각 단계는 독립적으로 lint·build 통과 |
| **검증** | 끝나면 어떻게 확인하는가: 테스트 항목 목록 + 수동 확인 시나리오(어떤 화면에서 무엇을 눌러 무엇이 보여야 하는지) |

## 4. 단계별 구현

- 3에서 정한 단계 순서대로 구현하고, **단계마다** `npm run lint && npm run build` (T1 이후에는 테스트 포함) 통과를 확인한다.
- 구현 중 문서(SPEC/SCREENS)와 어긋나는 지점을 발견하면 코드를 문서에 맞추는 게 기본이고, 문서가 틀렸다고 판단되면 멈추고 사용자에게 보고한다 (계약 변경은 문서 먼저 — SPEC 원칙).

## 5. 완료 처리

- 검증 계획(3의 마지막 행)을 실제로 수행한 결과를 보고한다. **테스트 없이 완료 선언 금지** (CLAUDE.md).
- docs/CHECKLIST.md의 해당 항목을 체크한다 (완료 체크의 단일 기준).
- 커밋은 사용자가 요청하면 `/commit` 절차로 한다.

## 금지

- 의존 미충족 상태 착수, MVP 범위 밖 기능, 요청 없는 리팩토링
- 5요소 계획 생략하고 바로 코드 작성
