description: Write a unit test for a single, rule-clear function (validation/calculation/transformation — not UI/design, which is faster to verify by eye) using a strict TDD sequence — spec/scenarios first, then red, then green, then refactor — with user review at the spec step before any code is written. Use when adding a test for one function/utility, or when practicing/demonstrating the red→green→refactor cycle.

이 Skill은 3주차 목요일 미션("테스트로 검증하기" + "TDD로 기능 하나 만들기")에서 정리한 절차를 그대로 굳힌 것이다. 목표는 "테스트를 나중에 붙이는 것"이 아니라, 코드보다 스펙과 테스트가 먼저 나오는 순서를 지키는 것.

## 대상 선정 기준

- **적합**: 검증(validation), 계산(calculation), 변환(transformation) — 규칙이 분명해서 입력→기대결과로 딱 떨어지는 함수.
- **부적합**: 화면(UI)/디자인 — 눈으로 확인하는 게 더 빠르므로 TDD 대상에서 제외.
- 기존 컴포넌트/페이지 안에 로직이 인라인으로 박혀 있어서 단독 테스트가 안 되는 경우("테스트하기 어려운 코드는 구조가 얽혀 있다는 신호"), 그 로직을 별도 함수로 뽑아내는 것 자체가 좋은 대상이 된다 — 단, 죽은 코드(주석 처리된 것)가 아니라 **실제로 살아있는 코드 경로**인지 먼저 확인한다.

## 절차

1. **스펙/시나리오 목록부터 정리하고, 코드는 아직 쓰지 않는다.** "입력 → 기대 결과" 표로 정상 케이스 / 빈 값·경계값 케이스 / 실패·오용 케이스를 나눠 적는다. 이 목록을 사용자에게 보여주고 빠진 케이스가 없는지 확인받는다 — 승인 전에는 테스트 파일도, 구현 파일도 만들지 않는다.
2. **Red: 테스트부터 작성한다.** 대상 함수가 아직 없으면, 테스트가 import 에러 없이 실행되고 "결과가 틀려서" 실패하는 상태(진짜 Red)를 만들기 위해 **스텁**(존재하되 항상 틀린 값만 반환하는 빈 껍데기)을 먼저 만든다. 스텁 상태로 테스트를 실행해 승인받은 케이스 중 "기대와 다른" 것들이 실제로 빨강으로 뜨는지 확인한다.
3. **Green: 통과하는 최소한의 코드로 구현한다.** 다시 테스트를 실행해 전부 초록인지 확인한다.
4. **Refactor: 정리하고, 기존 호출부를 새 함수로 교체한다.** 인라인 로직을 뽑아낸 경우, 원래 있던 자리(컴포넌트 등)가 새 함수를 import해서 쓰도록 바꾼다. 이 과정에서 "기존엔 없었지만 새 함수가 생기며 드러나는 실제 동작 차이"(예: 원래 가드 조건이 새 함수의 케이스를 다 못 덮던 것)가 있으면 반영한다.
5. **회귀 확인: 전체 테스트 스위트를 돌려서 다른 곳이 깨지지 않았는지 확인한다** (`npm test`).
6. **부가 발견 사항은 즉시 다 고치지 말고 나열해서 우선순위를 사용자에게 맡긴다.** 리팩토링 과정에서 관련된 다른 버그/누락(경쟁 상태, 디바운스 부재 등)을 발견할 수 있는데, 전부 한 번에 고치려 들지 않고 표/목록으로 정리해 "지금 할지 백로그로 남길지" 사용자가 정하게 한다.
7. **경계 걸친 검증(예: FE 로직을 BE도 신경써야 하는가)은 대안을 비교표로 제시한다.** 어느 레이어에서 처리할지 애매하면 A/B/C 안을 장단점과 함께 표로 보여주고 추천 이유를 대되, 최종 선택은 사용자가 하게 한다. 중복을 피하기로 했다면, 반대쪽 레이어에 "왜 여기 검증이 없는지 + 필요해지면 추가할 것"이라는 주석을 남겨 갭을 조용히 남기지 않는다.

## 예시 (2026-07-28 실제 진행)

`src/utils/isMeaningfulQuery.js` — 검색어에 영문/한글이 하나도 없으면(기호·숫자만) `false`를 반환하는 검증 함수:
1. 케이스 표 작성(정상/빈값/경계/실패) → 사용자 승인
2. `isMeaningfulQuery.test.js` 작성 + 스텁(`return false`)으로 Red 확인 (6개 중 3개 실패)
3. 정규식(`/[a-z가-힣]/i.test(query)`) 구현 → Green 확인 (6/6 통과)
4. `CommandListPage.jsx`의 살아있는 검색 가드(`normalizedQuery === ''`)를 `hasMeaningfulQuery`로 교체 — 리팩토링 중 "기호만 있는 검색어도 실제로는 걸러지지 않고 있었다"는 실제 갭을 발견해 같이 수정
5. 리팩토링하며 무관해 보이지만 인접한 버그(검색 응답 경쟁 상태)도 같이 발견 → 별도로 나열해 사용자가 "이것까지만 고치자"고 우선순위 결정
6. `npm test`로 전체 24개 테스트(스킵 2개 제외 22개) 통과 확인
7. BE(`server/src/routes/search.js`)에 중복 검증을 넣을지 A(FE만)/B(BE만)/C(둘 다) 비교표 제시 → 사용자가 A + 주석 절충안 선택

## Skill 업데이트 방법

새로운 종류의 "테스트하기 어려운 코드" 패턴이나, 케이스 목록에서 자주 빠지는 케이스 종류를 발견하면 이 문서의 해당 절에 추가한다.
