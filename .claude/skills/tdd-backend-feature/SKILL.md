# Backend 기능 하나를 TDD로 만들기

작은 검증/계산 로직 하나(예: 입력값 범위 체크, 초과 여부 판정)를 라우트 안에 바로 넣지 않고, 순수 함수로 분리해서 빠르게 테스트하는 절차. `backend/src/utils/overlap.ts` + `overlap.test.ts`, `backend/src/utils/validation.ts` + `validation.test.ts`가 이 패턴의 실제 예시다.

## 왜 순수 함수로 분리하는가

라우트 핸들러(`req`, `res`, DB 쿼리)를 직접 테스트하려면 서버를 띄우고 HTTP 요청을 보내야 해서 느리고 번거롭다. 판정/검증 로직만 입력을 받아 출력을 반환하는 순수 함수로 빼두면, DB나 네트워크 없이 밀리초 단위로 테스트할 수 있다. 라우트는 이 함수를 호출만 하는 얇은 껍데기로 남긴다.

## 절차

### 1. 함수 시그니처 먼저 정하기
무엇을 검증/계산할지 한 문장으로 정의하고, 입력 타입과 출력 타입을 정한다. 예: `isValidBirthYear(birthYear: number): boolean`. 파일 위치는 `backend/src/utils/<이름>.ts`.

### 2. Red — 실패하는 테스트를 먼저 쓴다
`backend/src/utils/<이름>.test.ts`를 만들고, 아직 존재하지 않는 함수를 import해서 여러 케이스를 테스트한다. 정상 케이스뿐 아니라 경계값(최소/최대 바로 안쪽·바깥쪽)과 잘못된 타입도 포함한다.

```ts
import { describe, expect, it } from "vitest";
import { <함수명> } from "./<파일명>";

describe("<함수명>", () => {
  it("<정상 케이스 설명>", () => {
    expect(<함수명>(<입력>)).toBe(<기대값>);
  });
  // 경계값, 실패 케이스도 추가
});
```

`npx vitest run backend/src/utils/<이름>.test.ts`를 실행해서 **반드시 실패하는 것을 확인**한다. 이 시점에 실패하는 이유는 파일이 없거나(import 에러) 로직이 없어서다 — 이게 정상이다. 테스트를 작성했는데 이미 통과한다면 테스트가 아무것도 검증하지 않고 있다는 신호이니 다시 살펴본다.

### 3. Green — 테스트를 통과시키는 최소 구현
테스트를 억지로 맞추는 게 아니라, 실제로 맞는 로직을 최소한의 코드로 작성한다. `npx vitest run backend/src/utils/<이름>.test.ts`로 전부 통과하는지 확인한다.

### 4. 실제 라우트에 연결
`backend/src/routes/*.ts`에서 이 함수를 import해서 기존 검증 로직 옆에 추가한다. 실패 시 400과 함께 사용자에게 보여줄 한국어 에러 메시지를 반환한다.

### 5. 회귀 확인
`npx vitest run`(전체 테스트)과 `npx tsc --noEmit`을 둘 다 실행해서 기존 테스트나 타입을 깨지 않았는지 확인한다.

### 6. 통합 확인 (선택, 하지만 권장)
`npm run dev`로 서버를 띄우고 실제 회원가입→로그인→토큰으로 문제의 API를 curl로 호출해, 잘못된 입력은 거부되고 정상 입력은 통과하는지 눈으로 확인한다. 끝나면 서버 프로세스를 종료한다.

## 하지 말아야 할 것
- 라우트 핸들러 안에 검증 로직을 바로 작성하고 테스트를 나중에 끼워 맞추지 않는다 — 순서가 뒤집히면 테스트가 구현을 보고 베끼게 되어 버그를 못 잡는다.
- 테스트 없이 "이 정도면 맞겠지" 하고 구현부터 하지 않는다.
- 하나의 테스트 파일에 관련 없는 여러 함수를 몰아넣지 않는다 — 함수 하나당 파일 하나가 기본.
