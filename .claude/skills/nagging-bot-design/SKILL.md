# Nagging Bot Design

잔소리봇 UI 작업에서 현재 제품의 디자인 언어와 기능 계약을 보존한다.
이 문서는 디자인 소개가 아니라 구현 판단과 검증을 위한 작업 규칙이다.

## 1. 기준과 우선순위

작업 전 요청 대상의 JSX, CSS, 테스트와 `src/assets`를 직접 확인한다.
문서가 충돌하면 다음 순서를 적용한다.

1. 사용자가 최근 확정한 요구
2. 현재 실제 구현 코드와 에셋
3. `CLAUDE.md`
4. `docs/checklist.md` 상단 현재 상태
5. `docs/design-concept.md`, `docs/design-research.md`, `docs/wireframe.md`
6. 이 Skill의 일반 규칙

`docs/wireframe.md`와 디자인 문서에는 과거 구조와 미구현 아이디어가 남아
있을 수 있다. 현재 코드와 대조하지 않은 기획을 복원하지 않는다.

## 2. 제품과 브랜드 원칙

잔소리봇은 사용자를 혼내는 서비스가 아니다. 회피 이유를 확인하고 지금
실행할 수 있는 가장 작은 행동 하나를 제안해 시작과 완료로 연결한다.

제품 흐름:

```text
Landing → Register → Home → Nudge → Focus → Completion → History
```

브랜드 성격:

- Calm, Premium, Warm, Clear
- 귀엽지만 유아적이지 않음
- 따뜻하지만 지나치게 감상적이지 않음
- 캐릭터는 장식이나 감독자가 아니라 사용자의 동행자
- 레벨이 올라가도 사용자를 비난하거나 위협하지 않음
- 게임 보상, 폭죽, 점수, 강한 네온 효과를 과도하게 사용하지 않음
- 정보와 핵심 행동을 캐릭터·배경보다 먼저 이해할 수 있게 함

UI 변경이 기능 흐름, API payload, 상태, 라우팅 또는 문구 계약까지 바꾸지
않는지 먼저 확인한다. 디자인 요청만으로 기능을 재설계하지 않는다.

## 3. 실제 토큰과 CSS 규칙

전역 토큰은 `src/index.css`의 실제 값을 우선 사용한다.

| 토큰         | 현재 값   | 역할             |
| ------------ | --------- | ---------------- |
| `--bg`       | `#f4f5f7` | 앱 배경          |
| `--panel-bg` | `#ffffff` | 카드·패널        |
| `--ink`      | `#1e2430` | 주 텍스트        |
| `--ink-soft` | `#656d7a` | 보조 텍스트      |
| `--line`     | `#dde1e6` | 보더·구분선      |
| `--badge-bg` | `#ececf1` | 중립 배지        |
| `--accent`   | `#4c5fd5` | 브랜드 Primary   |
| `--level-1`  | `#78cfc3` | 민트             |
| `--level-2`  | `#9285bc` | 보라             |
| `--level-3`  | `#d77f91` | 코랄·더스티 로즈 |
| `--level-4`  | `#c94a43` | 부드러운 적색    |

구현 규칙:

- 새 전역 색상·spacing token은 명시적 필요 없이 추가하지 않는다.
- Hero, TaskCard, Nudge, History의 레벨 표현은 공통 `--level-1~4`를
  재사용한다.
- Primary CTA는 기본적으로 `--accent`를 사용한다. 레벨색은 상태를
  설명하는 제한된 요소에만 사용한다.
- 컴포넌트 옆 전용 CSS 구조를 유지한다.
- CSS-in-JS, Tailwind, 새 UI 라이브러리를 임의로 도입하지 않는다.
- 기존 radius, shadow, typography, spacing을 먼저 재사용한다.
- 인라인 style은 배경 URL, 진행률처럼 동적 값에만 제한한다.
- 변경 화면의 전용 selector 아래에서 최소 수정한다.
- 스타일 변경을 이유로 DOM 구조, 이름, 공통 컴포넌트를 대규모로
  리팩터링하지 않는다.
- 현재 CSS의 오래된 주석을 디자인 계약으로 간주하지 않는다.

현재 기본 패턴:

- 앱 본문과 Navbar는 주로 `max-width: 900px` 중앙 정렬
- 기본 카드: 밝은 표면, 얇은 `--line` 보더, 부드러운 radius와 제한적 shadow
- 기본 버튼: radius `9px`, 굵은 텍스트, Primary는 `--accent`
- 시스템 UI 폰트 스택을 사용하며 새 웹폰트를 임의로 추가하지 않음
- 배경 위 텍스트는 반투명 밝은 패널 등으로 대비를 보호

## 4. Shared Journey

레벨은 캐릭터, 날씨, 배지와 강조색이 함께 보조한다. 색상만으로 레벨을
전달하지 않고 항상 `LvN` 텍스트나 상태 문구를 유지한다.

| 레벨 | 성격                               | 배경                            |
| ---- | ---------------------------------- | ------------------------------- |
| Lv0  | 맑고 평온한 기본 상태              | `journey_lv0_clear.png`         |
| Lv1  | 민트, 가벼운 개입                  | `journey_lv1_partly_cloudy.png` |
| Lv2  | 보라, 생각하고 행동을 더 작게 줄임 | `journey_lv2_cloudy.png`        |
| Lv3  | 코랄·더스티 로즈, 진지한 개입      | `journey_lv3_rain.png`          |
| Lv4  | 부드러운 적색, 가장 명확한 개입    | `journey_lv4_storm.png`         |

캐릭터 정체성을 유지한다.

- 통통한 3D 글로시 화이트 몸체
- 검은 유광 얼굴 화면과 표정
- 양옆 링 형태 스피커
- 발광 안테나
- 스카프와 짧은 팔다리
- 레벨이 달라도 같은 캐릭터로 인식되는 비율과 재질

에셋 원칙:

- 실제 경로와 파일명을 import 전에 확인한다.
- 배경: `src/assets/backgrounds/`
- 전신·얼굴·Walking·성공 캐릭터: `src/assets/characters/`
- 구름·효과·발자국·마커·그림자·말풍선: `src/assets/ui/`
- `nagbot_walk_lv3.png.png`처럼 현재 파일명이 특이해도 추측으로 고치지
  말고 실제 import와 함께 확인한다.
- PNG 캔버스와 투명 여백이 달라 실제 보이는 크기를 브라우저에서 비교한다.
- 레벨별 크기 보정이 필요하면 layout이나 `transform: scale()`보다 이미지
  `width`를 작은 범위에서 조정한다.
- 원본을 재압축, 재인코딩, 크롭, 리사이즈, 배경 제거, 색상 변경하지 않는다.
- 새 이미지나 변형이 필요하면 먼저 사용자에게 확인한다.
- 저장소에 존재한다는 이유만으로 미사용 장식 에셋을 화면에 추가하지 않는다.

시간대별 Journey 테마, Walking 프레임 애니메이션, 목적지 도착 연출은 현재
미구현이다. 현재 기능처럼 디자인하거나 설명하지 않는다.

## 5. 화면별 판단 기준

### Landing

- `ProjectIntro`의 Landing 전용 top bar와 `/register` CTA를 유지한다.
- 첫 화면에서 대상 사용자, 시작 문제, 첫 행동 제안 가치를 먼저 전달한다.
- Hero는 데스크톱 텍스트·Journey 비주얼 2열, 모바일 1열 흐름을 유지한다.
- `nagbot_landing.png`와 Journey 배경을 서비스 설명에 종속시킨다.
- 문제, 사용 흐름, 레벨별 개입, Shared Journey, 마지막 CTA의 위계를
  유지하고 기능 카드를 과도하게 늘리지 않는다.
- 흔한 보라·파랑 AI SaaS 네온 그라데이션이나 과도한 glassmorphism을
  추가하지 않는다.

### Register

- 제목, 일정, 예상되는 회피 이유의 낮은 마찰 단일 Form을 유지한다.
- 데스크톱에서는 Form 가독성을 우선하고 캐릭터 aside는 보조 역할만 한다.
- 현재 `nagbot_landing.png` 안내 캐릭터와 한 줄 안내를 반복하지 않는다.
- 768px 이하에서는 aside를 숨기고 입력을 1열로 유지한다.
- 필드 label, validation, 조건부 직접 입력, 서버 오류와 제출 상태를
  해당 맥락에서 명확히 보인다.
- 안내 문구를 늘려 Form을 길게 만들지 않는다.

### Home

- 단일 컬럼 흐름을 유지한다.

```text
Header → Stats → Journey Hero → active → waiting → done
```

- Stats는 compact한 현재 상태 요약이고 Journey Hero보다 강하지 않게 한다.
- Journey Hero는 대표 Task의 제목과 현재 행동을 중심으로 보여준다.
- Hero의 대표 Task가 목록에도 남는 현재 계약을 유지한다.
- active, waiting, done의 정보량과 강조도를 구분한다.
- active의 명시적 시작 CTA, waiting의 시작 CTA 없음, compact한 done 구조를
  임의로 바꾸지 않는다.
- TaskCard의 레벨 배지와 진행바는 같은 레벨색 체계를 사용한다.
- 진행바 길이는 현재 level 진행도를 나타내는 기존 계산을 유지하고,
  레벨별 단색 계열 fill을 사용한다.
- 캐릭터와 날씨가 Task 제목, deadline, 회피 이유, CTA를 가리지 않게 한다.

### Nudge Modal

- 현재 밝은 중성 표면의 최대 폭 `940px` 모달과 데스크톱 2열,
  620px 이하 1열 구조를 기준으로 한다.
- Level Badge, 레벨별 캐릭터, 메시지, 첫 행동, 현재 CTA를 빠르게
  이해할 수 있게 한다.
- 레벨색은 Badge, 얇은 message accent, Primary CTA 등 제한된 곳에 쓴다.
- Lv1~Lv3의 기존 checkpoint·입력·CTA와 Lv4의 `지금 시작하기`·`나중에`
  계약을 바꾸지 않는다.
- Gemini loading, 성공, rule-based fallback 모두 레이아웃이 흔들리지 않게
  한다.
- 긴 메시지와 microTask는 잘리거나 버튼을 밀어내지 않아야 한다.
- 현재 Lv4에는 진입 효과와 지속적인 약한 테두리 강조가 있으며
  `prefers-reduced-motion`에서 꺼진다. 요청 없이 이를 다른 레벨이나
  화면으로 확장하지 않는다.
- 사용자를 모욕하거나 공포감을 주는 shake, 번쩍임, 붉은 전체 배경을
  추가하지 않는다.

### Focus Mode

- 진행 상태에만 몰입형 Journey 레이아웃을 적용하고 Completion 구조와
  분리한다.
- 현재 Task, microTask, 타이머, Walking 캐릭터, 멈추기·완료 순서를 유지한다.
- Journey 배경이 화면의 중심이되 정보 패널은 최소한의 대비만 제공한다.
- 진입 당시 `journeyLevel`의 배경과 캐릭터를 세션 동안 유지한다.
- 멈추기는 일시정지가 아니라 세션 종료라는 현재 기능을 디자인으로
  오해하게 만들지 않는다.
- 캐릭터는 길 중앙의 동행자로 보이되 상단 정보와 하단 버튼을 가리지 않는다.
- 위치나 width는 이미지 내부 투명 여백과 실제 몸체 크기를 기준으로 검증한다.
- 집중을 방해하는 이동, 반복 점프, 날씨 애니메이션을 추가하지 않는다.

### Completion

- `nagbot_success.png`를 완료 순간의 중심 비주얼로 사용한다.
- `success_sparkles.png`는 캐릭터 뒤에서 낮은 opacity와 제한된 범위로만
  사용한다.
- 캐릭터, 완료 메시지, summary, 피드백, Home Primary, History 보조 링크의
  위계를 유지한다.
- 완료 데이터 조건부 표시와 이동·피드백 기능을 바꾸지 않는다.
- 폭죽, 코인, 점수, 과도한 glow 같은 게임 보상 표현을 추가하지 않는다.
- 완료 효과는 짧고 한 번 실행하는 것을 우선하고 reduced motion을 지원한다.

### History

- Summary와 최근 7일 그래프는 기록을 보조하는 compact insight다.
- 리스트·캘린더 탭과 기록이 장식보다 먼저 읽히게 한다.
- 그래프는 hover 없이 값과 요일을 확인할 수 있어야 한다.
- entry level은 색상과 함께 `LvN` 텍스트로 표시한다.
- 빈 상태, loading, error에서도 페이지 구조와 기존 이동 흐름을 유지한다.
- 데이터가 많을 때 카드 크기를 키우기보다 스캔 가능성과 줄바꿈을 우선한다.

### Navbar

- 얼굴 로고와 `잔소리봇`, 현재 메뉴, 알림 버튼의 기능을 유지한다.
- 브랜드 링크, navigation, 알림 버튼의 `focus-visible`을 유지한다.
- 모바일에서 문구를 생략하거나 아이콘 전용 메뉴로 임의 변경하지 않는다.
- Navbar 높이, wrap, Push 상태 문구를 디자인 변경만으로 바꾸지 않는다.

## 6. 문구와 개입 톤

- 사용자를 비난하거나 수치심을 주지 않는다.
- 마이크로태스크는 한 번에 하나의 실행 가능한 행동만 제안한다.
- 추상적인 격려보다 대상과 동사가 분명한 짧은 문장을 사용한다.
- Lv1·Lv2는 존댓말 중심으로 부드럽게 말한다.
- Lv3·Lv4는 더 단호하되 모욕적이거나 공격적이지 않다.
- 영어와 한국어를 불필요하게 혼용하지 않는다.
- Focus Mode, Shared Journey, History 등 현재 제품 용어를 일관되게 쓴다.

톤 참고:

- Lv1: “아직 시작하기 조금 어려운가요? 가볍게 이것부터 해볼까요?”
- Lv2: “아직 막막하다면 행동을 더 작게 줄여볼게요.”
- Lv3: “벌써 여러 번 미루고 있어. 지금 막는 이유부터 다시 확인하자.”
- Lv4: “생각 그만. 지금 바로 이것부터 시작해.”

문구를 고정 템플릿으로 복사하지 말고 강도와 태도의 기준으로만 사용한다.
기존 제품 문구 변경은 사용자가 요청한 범위에서만 수행한다.

## 7. 반응형 기준

최소 검토 viewport:

- Desktop: `1440px`
- Tablet: `768px`
- Mobile: `390px`

필요하면 `1024px`, `360px`와 높이 `700px` 이하도 추가한다.

각 상태에서 다음을 실제 렌더링 기준으로 확인한다.

- 가로·세로 overflow
- 긴 제목, 메시지, microTask, 오류 문구의 줄바꿈
- 카드·Modal 최대 너비와 내부 스크롤
- 배경의 길과 캐릭터 crop
- 이미지 비율과 실제 보이는 몸체 크기
- 버튼 겹침, 줄바꿈과 최소 터치 영역
- sticky·fixed 요소가 콘텐츠를 가리는지
- 모바일 safe area
- 키보드가 입력과 submit CTA를 가리는지
- 200% 확대와 좁은 폭에서도 핵심 행동에 접근 가능한지

media query가 존재하거나 RTL이 통과했다는 이유만으로 반응형 검증을
완료 처리하지 않는다.

## 8. 접근성

- 의미 있는 이미지에는 맥락에 맞는 `alt`를 제공한다.
- 레벨 정보가 텍스트로 함께 제공되는 캐릭터 등 장식 이미지는 `alt=""`와
  필요 시 `aria-hidden="true"`를 사용한다.
- 버튼, 링크, 입력에는 명확한 accessible name을 제공한다.
- `label`과 input, 오류와 `aria-describedby`·`aria-invalid`를 연결한다.
- 모든 기능을 키보드로 사용할 수 있게 한다.
- `:focus-visible`을 제공하고 mouse focus와 구분한다.
- 텍스트와 배경 대비를 유지한다.
- 핵심 터치 대상은 최소 `44×44px`를 확보한다.
- 색상, 날씨, 캐릭터 표정만으로 상태를 구분하지 않는다.
- Modal의 dialog name, 초기 focus, focus 이동, Escape와 backdrop 동작을
  기존 계약과 함께 확인한다.
- loading과 오류를 적절한 live region으로 전달한다.
- 동작이 있는 화면은 `prefers-reduced-motion` 대체를 제공한다.

## 9. 애니메이션

- 기능 이해나 상태 변화에 필요한 경우에만 사용한다.
- opacity와 작은 transform을 큰 위치 변화보다 우선한다.
- 일반 카드와 첫 화면에 반복 점프, 흔들림, pulse를 추가하지 않는다.
- Focus의 움직임은 느리고 제한적이어야 한다.
- Completion은 짧은 1회 효과를 우선한다.
- 기존 Lv4 테두리 강조처럼 사용자가 확정한 예외는 해당 범위에서만
  유지하고 다른 화면으로 확장하지 않는다.
- 모든 비필수 motion은 reduced-motion에서 제거하거나 정적 상태로 대체한다.

## 10. 금지 사항

- 요청하지 않은 전체 리디자인
- 최신 구현을 과거 prototype·와이어프레임으로 되돌리기
- 기능, 상태, API, DB, 라우팅을 포함하는 무단 디자인 수정
- 현재 에셋 교체, 새 이미지 생성 또는 원본 변형
- 새 디자인 시스템, UI 라이브러리, 아이콘 세트 도입
- 근거 없는 색상, 폰트, radius, shadow 변경
- 사용자가 확정하지 않은 화면, 메뉴, CTA 추가
- 모바일을 데스크톱 축소판으로만 처리
- 접근성을 후속 작업으로 미루기
- 캐릭터를 콘텐츠나 사용자 행동보다 더 강하게 배치
- 모든 화면에 glass, gradient, glow, animation 적용
- 과도한 게임화와 위협적인 Lv4 연출
- 실제 브라우저 확인 없이 이미지 crop·overflow 작업 완료 선언

## 11. UI 작업 절차

1. 요청 범위와 변경 금지 요소를 정리한다.
2. 대상 JSX, CSS, 테스트, 사용 에셋을 읽는다.
3. 관련 토큰과 현재 breakpoint·상태별 DOM을 확인한다.
4. 문서와 구현이 다르면 실제 구현과 최신 사용자 결정을 기준으로 한다.
5. 기능 계약과 시각 변경을 분리해 영향 범위를 설명한다.
6. 요청이 계획 우선이면 승인 전 코드를 수정하지 않는다.
7. 승인된 범위 안에서 기존 구조를 유지해 최소 변경한다.
8. 관련 RTL과 정적 검증을 수행한다.
9. `typecheck`, `lint`, production `build`를 요청·위험에 맞게 실행한다.
10. 1440px, 768px, 390px에서 실제 화면을 검토한다.
11. 키보드, focus, contrast, touch target, motion을 확인한다.
12. 변경 파일, 전후 차이, 실행·생략한 검증, 남은 위험을 보고한다.

사용자가 UI 검토만 요청했다면 자동으로 수정하지 않는다. 브라우저에서
문제가 보여도 승인 범위를 넘는 구조 변경은 제안으로만 남긴다.

## 12. 완료 기준

다음을 모두 충족해야 UI 작업을 완료로 보고한다.

- 요청된 화면과 상태만 변경됨
- 기능·데이터·라우팅 계약이 유지됨
- 실제 토큰과 기존 에셋을 재사용함
- Desktop, Tablet, Mobile에서 핵심 상태를 확인함
- 긴 콘텐츠, 빈 상태, loading, error 등 관련 상태를 확인함
- 키보드와 기본 접근성을 확인함
- 관련 RTL, typecheck, lint, build 결과를 보고함
- 실제 브라우저 검증이 필요한 사항을 코드 테스트로 대체하지 않음
- 실행하지 못한 검증과 이유, 수동 확인 항목을 명시함
- 관련 없는 파일과 기존 사용자 변경을 건드리지 않음

특정 테스트 개수, 임시 산출물 경로, 주차별 진행 상태를 Skill에 고정하지
않는다. 현재 상태는 `docs/checklist.md`와 실제 코드에서 다시 확인한다.

Skill 수정 자체는 현재 UI 구현을 변경하지 않는다. UI와 Skill의 불일치를
발견하면 작업 범위를 임의로 확장하지 말고 사용자에게 별도로 보고한다.
