# 가설 검증 인터뷰 분석 방법론 (원본)

이 문서는 프롬프트의 **단일 원본**이다. `README/AI_Pipeline_Design.md`(계약 문서)와 `backend/src/lib/prompts/*`(구현, Task 24)는 이 문서를 따른다. 세 곳이 어긋나면 이 문서가 정답이다.

## 0. 출처 — 백지에서 쓰지 않았다

[`naruv0134/pm-skills`](https://github.com/naruv0134/pm-skills)(9개 플러그인 · 68 스킬)에서 이 도구의 도메인(가설 검증 인터뷰 분석)에 실제로 걸리는 4개만 선별해 번역했다. 68개를 통째로 넣지 않은 이유: 세션 컨텍스트만 소모하고 실제 쓰는 건 극소수이기 때문이다.

| 선별 스킬 | 경로 | 이 도구에 가져온 것 |
|---|---|---|
| summarize-interview | `pm-product-discovery/skills/summarize-interview/SKILL.md` | "정보 공백은 `-`로 표시" 원칙을 그대로 계승(§5). 단 산출 축은 JTBD가 아니라 가설(원인→결과)로 재번역했다 |
| identify-assumptions-new | `pm-product-discovery/skills/identify-assumptions-new/SKILL.md` | "검증 안 된 전제를 위험 범주로 다루는" 감각을 근거 강도 위계(§1) 설계에 참고 |
| prioritize-assumptions | `pm-product-discovery/skills/prioritize-assumptions/SKILL.md` | `Risk = (1 - 신뢰도) × 노력` 공식의 "신뢰도" 개념을 Task 26의 `confidence`(확신도) 필드로 번역 |
| sentiment-analysis | `pm-market-research/skills/sentiment-analysis/SKILL.md` | "작은 표본 크기는 플래그" 감각 — 근거가 적을 때 성급히 단정하지 않는 태도를 반증 우선 원칙(§2)에 반영 |

**드롭인이 안 된다 — 프레임 번역이 필요하다:** `summarize-interview`는 **JTBD(Jobs To Be Done)** 축으로 정리하는 스킬이고, 이 도구는 **가설(원인→결과) 검증** 축이다. 산출물 구조가 근본적으로 다르므로 템플릿을 그대로 가져오지 않고 원칙만 추출해 우리 축으로 재번역했다. pm-skills 원본은 참조 출처로만 남기고, 이 문서가 그것을 대체한다(원본을 계속 따라가면 JTBD 축으로 다시 끌려간다).

## 1. 근거 강도 위계 (evidence_strength)

발언을 아래 세 등급 중 하나로 분류한다. 위 등급일수록 강한 근거다. `badge_label`(지지/반박/참고)과 **직교하는 축**이다 — "반박 근거인데 전언"이 가능해야 한다.

| 강도 | 정의 | 예시 |
|---|---|---|
| 직접 경험 | 화자 본인이 실제로 겪은 일을 구체적으로 진술 | "저는 지난주에 배터리가 빨리 닳아서 알림을 껐어요" |
| 의견 | 아직 겪지 않은 일에 대한 선호·예상 | "그건 좀 불편할 것 같아요" |
| 전언 | 본인 경험이 아닌 남의 말이나 일반화 | "다들 그렇게 말하던데요" |

**판정 규칙:** 지지 근거가 전부 `전언` 등급이면 `유력함`을 줄 수 없다. `유력함`이려면 `직접 경험` 등급 지지 근거가 최소 1건 있어야 한다.

## 2. 반증 우선 원칙

지지 근거를 모으기 전에 **반박 근거부터 먼저 찾는다**. 반박 근거가 1건이라도 있으면 `summary`에 그 사실을 반드시 명시한다 — 지지 근거 개수가 많다고 묻어버리지 않는다.

**판정 규칙:** 반박 근거 수가 지지 근거 수 이상이면 `유력함`을 줄 수 없다 — 최소 `수정 필요`로 내려간다.

## 3. 유도 질문 감쇠

진행자의 질문이 답을 암시한 경우(예: "이 기능 불편하지 않으셨어요?" → "네 불편했어요"), 그 답변의 근거 강도를 한 단계 낮춘다(`직접 경험` → `의견`, `의견` → `전언`).

**판정 규칙:** 질문 문장이 부정형으로 답을 암시하는 패턴("~하지 않으셨어요?", "~죠?")이고 응답자가 단순 동의로만 답했다면, 감쇠를 적용하고 그 사실을 `key_evidence`에 명시한다.

## 4. 가설 수정 방향의 3가지 형태 (direction)

`direction`은 아래 세 형태 중 **하나에 명시적으로 대응**해야 한다. "재검토가 필요합니다" 같은 막연한 문장은 금지한다.

| 형태 | 의미 | 예시 |
|---|---|---|
| 원인 축소 | 가설의 원인(조건) 범위를 좁힌다 | "거리 기반 추천" → "도보 15분 이내 거리 기반 추천" |
| 결과 재정의 | 측정 대상을 바꾼다 | "만족도가 상승할 것이다" → "재방문율이 상승할 것이다" |
| 조건 추가 | 특정 상황에서만 성립하도록 조건을 붙인다 | "만족도가 상승할 것이다" → "스마트폰 사용에 익숙한 시니어에 한해 만족도가 상승할 것이다" |

## 5. 정보 공백 처리 (pm-skills 원칙 그대로 계승)

원문이 판단 근거로 삼기에 불충분하면 추측해서 채우지 않고 `-`로 표시한다. 3주차 환각 방어 원칙과 동일 계열이다.

## 6. 판단 금지선

AI는 가설의 유지/수정/폐기를 **확정하지 않는다.** 이 스킬이 산출하는 것은 항상 초안(draft)이며, 최종 판단은 사용자가 한다. `suggested_status`·`direction` 모두 단정형이 아닌 제안 톤으로 작성한다.

## 7. 이 문서가 아직 백엔드에 적용되지 않은 상태 (중요)

**스킬 설치만으로는 `npm run eval` 점수가 1도 움직이지 않는다.** `.claude/skills/`는 Claude Code 세션(개발 도구)의 행동만 바꾸고, 실행 중인 백엔드가 Gemini에 보내는 프롬프트는 바꾸지 않는다 — 백엔드는 `.claude/`를 읽지 않는다.

- 이 문서의 규칙이 실제 판정에 반영되는 시점은 `lib/prompts/`로 이식되는 **Task 24~26**부터다.
- Task 22 baseline은 이 문서와 무관하게, **현재 프롬프트 상태 그대로** 측정한다.
- 미리 반영한 상태를 baseline으로 삼으면 "PM 방법론 도입으로 판정 정확도가 개선되었다"는 4주차 핵심 서사를 증명할 수단이 사라진다 — 금지.
