이 스킬은 AI Agent Challenge 강의 "AI와 설계하고 작업나누기"에서 배운 방식을 고정해둔 것이다: **코드를 쓰기 전에 항상 설계(무엇을 어떻게 만들지)를 먼저 확정하고, 그걸 검토한 뒤에만 구현으로 넘어간다.** 참고 문서: `docs/prompt-templates.md`(재사용 가능한 프롬프트 원문).

## 두 단계 — 기능 설계와 작업 전략은 다른 레벨이다

- **기능 전체 설계** (새 기능을 시작할 때 한 번): 화면·데이터·API를 수직 슬라이스로 정의하고, 완료 기준·크기·빠진 것·장단점·대안까지 확정한다.
- **작업 하나의 구현 전략** (기능을 나눈 이슈 하나를 실제로 짤 때마다): 파일과 역할, 데이터 흐름, 이유와 대안을 먼저 받는다.

이 둘은 순서가 다르다 — 기능 설계가 먼저 한 번 있고, 그 안에서 나뉜 작업마다 구현 전략을 반복해서 받는다. 하나를 다른 것으로 착각해 생략하지 않는다.

## 언제 이 흐름을 적용하나

- 사용자가 새 기능(화면+서버+DB에 걸친 것)을 만들자고 할 때 → 코드부터 짜지 말고 기능 설계서(완료기준/크기/빠진것/장단점/대안/수직정의/화면/테이블·컬럼/API)를 먼저 제시한다.
- 기능 설계가 끝나고 세부 작업(이슈) 하나를 실제로 구현하려 할 때 → 구현 전략(파일과 역할/데이터 흐름/이유와 대안)을 먼저 제시하고, 사용자가 이해·승인한 뒤에만 코드를 짠다.
- 오탈자 수정, 한 줄짜리 버그 픽스처럼 명백히 작은 작업에는 이 전체 절차를 강제하지 않는다 — 매번 거창하게 설계서를 요구하면 오히려 진행을 막는다. "새 기능" 또는 "여러 파일에 걸친 비트리비얼한 작업"에 한정한다.

## 기능 설계서에 포함할 것 (수평적 아닌 수직적 정의)

"[기능] UI를 만든다"가 아니라 "[기능]을 하면 실제로 [핵심 동작]이 일어나고, 새로고침해도 결과가 남는다" 형태로 기능을 정의한 뒤:

1. 완료 기준(Definition of Done)
2. 작업 크기 검토 (적당한 기간 안에 끝날지, 크면 뭘 미룰지)
3. 빠진 것 확인 (기획서·요구사항 대비)
4. 장단점과 약점 (엣지 케이스 포함)
5. 다른 방법 검토 (대안과 선택 이유)
6. 화면 변경 사항
7. 필요한 테이블/컬럼
8. 필요한 API (엔드포인트, request/response)

## 작업 하나의 구현 전략에 포함할 것

1. 만들거나 고칠 파일과 각 파일의 역할
2. 데이터가 어디에 있고 어떻게 흐르는지 (state 위치, 요청과 응답)
3. 이렇게 구현하는 이유, 다른 방법이 있다면 장단점도

기존 프로젝트 구조(라우터·컴포넌트 패턴, 이미 있는 유틸)를 그대로 따르고, 새 라이브러리를 임의로 끌어오지 않는다.

## 전략/설계를 그대로 통과시키지 않는다

사용자가 전략을 읽고 이해 안 되거나 의심스러워하면, 판단을 대신 내려주는 대신 아래로 유도한다:

- "이 방법 말고 다른 방법 2가지 + 장단점 비교표"를 만들어 보여준다.
- "왜 이렇게 하는지", "다른 방법은 없는지", "이 방식의 단점은 뭔지"를 스스로 답하고 근거를 댄다.
- 좋은 구조 판단 기준(역할이 제자리인가, 하나가 한 가지만 하나, 기존 구조를 따르나, 변경 범위가 적절한가)에 비춰 자기 검토를 먼저 해서 제시한다.

목표는 "정확한 한 번의 판단"이 아니라, 사용자가 이해하지 못한 채로 승인하는 일이 없게 하는 것이다.
