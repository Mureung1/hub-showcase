# 디자인 구현 스킬 (design-build)

이 스킬은 "디자인 산출물 → 코드 구현 → 실제 화면으로 검증 → 피드백을 스킬 자체에 누적"하는 한 사이클을 담당한다. 목표는 매번 새로 판단하지 않고, 이 파일에 쌓인 규칙대로 일관되게 작업하는 것.

## 언제 쓰는가
- 사용자가 디자인 export(zip, 이미지, 핸드오프 md, 레퍼런스 HTML 등)를 넘기며 "이대로 구현해줘"라고 할 때
- 이미 만든 UI가 의도한 디자인과 맞는지 확인해달라고 할 때
- 여러 프로젝트에 걸쳐 반복되는 작업이므로, 프로젝트 종류(React/Vue/plain HTML 등)에 상관없이 적용한다

## 절차

### 1. 디자인 소스 확보 및 정독
- 사용자가 파일 경로를 안 줬으면 Downloads 폴더 등 흔한 위치를 먼저 찾아본다 (되묻기 전에 한 번은 직접 찾아볼 것).
- zip이면 압축 해제 후 안에 있는 핸드오프 문서(README/spec)와 레퍼런스 HTML/이미지를 **전부** 읽는다. 색상값, 타이포, spacing, 인터랙션, 문구(에러 메시지, 버튼 라벨 등)까지 빠짐없이 확인 — 이 문서가 정확도의 기준이 된다.
- fidelity(충실도) 표기를 확인한다. "high-fidelity/pixel-perfect"라고 적혀 있으면 색상·수치를 임의로 반올림하거나 비슷한 값으로 대체하지 않고 그대로 옮긴다.

### 2. 대상 프로젝트에 디자인 시스템 저장
- 대상 프로젝트 루트(또는 해당 앱 폴더)에 `design/` 폴더를 만들어 원본 핸드오프 문서와 레퍼런스 파일을 그대로 보관한다. (원본을 지우지 않는다 — 나중에 다시 참조할 유일한 소스)
- 프로젝트의 스타일링 방식(CSS 변수 / Tailwind config / styled-components theme 등)에 맞는 디자인 토큰 파일을 만들어 색상(가능하면 원본 색공간 그대로, 예: OKLCH 값을 hex로 임의 변환하지 않음)·radius·spacing·shadow·폰트를 변수로 추출한다.
- 프로젝트에 `CLAUDE.md`가 없으면 만들고, 있으면 "Design system" 섹션을 추가해 `design/` 폴더와 토큰 파일을 가리키게 한다. 문구는 "새 UI 작업 전 항상 이 문서를 먼저 확인하고, 색상/spacing은 하드코딩하지 말고 토큰 변수를 쓸 것"을 명시한다. 이게 있어야 이후 세션(나 자신 포함)이 매번 같은 디자인 언어를 재사용한다.

### 3. 구현
- 기존 코드가 이미 있으면 구조(상태 관리, 컴포넌트 트리)는 최대한 유지하고, 시각적 값(색/폰트/spacing/레이아웃)과 핸드오프에 명시된 마크업 구조만 스펙에 맞춰 바꾼다.
- 레퍼런스가 사내 프로토타이핑 포맷(`<x-dc>`, `class Component extends DCLogic` 같은 것) 등 그대로 못 쓰는 포맷이면, 룩앤필/동작만 가져오고 대상 프레임워크의 관용적인 패턴(React면 useState/onChange 등)으로 재구현한다.

### 4. 반드시 실제 화면으로 검증한다 — 여기서 절대 생략하지 말 것
- 코드를 다 쓴 뒤 "다 됐다"고 말하기 전에, 반드시 dev 서버를 켜고 스크린샷을 찍어 확인한다. 이 저장소/환경에 맞는 방법(`run` 스킬 → chromium-cli 또는 Playwright 등)을 사용한다.
- 최소한 (a) 초기 상태, (b) 사용자가 실제로 상호작용하는 대표 상태(데이터 채운 결과 화면, 에러 상태 등) 두 가지는 스크린샷으로 확인한다.
- 콘솔 에러(`console --errors` 또는 동일한 수단)도 같이 확인한다.
- 스크린샷을 보고 스스로 핸드오프 스펙과 대조한 뒤 결과를 사용자에게 보고한다. "구현했습니다"가 아니라 "스크린샷으로 확인했고, 스펙과 이렇게 일치합니다/이 부분은 다릅니다"라고 말한다.

### 5. 사용자 확인 및 피드백 루프
- 검증 후 사용자에게 마음에 드는지, 의도와 다른 부분이 있는지 명시적으로 물어본다.
- 사용자가 "이 부분은 아니다/이렇게 해줬으면 좋겠다"라고 피드백을 주면:
  1. 해당 파일을 그 피드백대로 고친다.
  2. **그리고 이 SKILL.md의 "학습된 선호" 섹션에 그 피드백을 규칙으로 추가한다.** 코드만 고치고 끝내지 않는다 — 다음에 똑같은 종류의 디자인 작업을 할 때 또 틀리지 않기 위함이다.
  3. 규칙은 "무엇을/왜"가 드러나게 짧게 적는다 (예: "채도 높은 원색 배지 대신 저채도 배경 + 진한 텍스트 조합을 쓴다 — 사용자가 부드러운 톤을 선호함, 2026-07-09 리뷰 답변 도우미 작업에서 확인").

## 학습된 선호 (사용자 피드백으로 누적됨 — 여기를 계속 업데이트할 것)

- 색상 토큰은 원본 디자인이 준 색공간(OKLCH 등)을 그대로 CSS 커스텀 프로퍼티로 옮긴다. hex로 임의 변환하지 않는다.
- 감정/상태 배지 같은 태그는 solid 배경 + 흰 글자보다, **저채도 배경 + 진한 동색 텍스트** 조합(soft badge)을 기본으로 한다.
- 폰트가 핸드오프에 명시돼 있으면(this project: Pretendard Variable) CDN이든 로컬 설치든 실제로 로드되게 `index.html`/global CSS에 추가한다.
- "high-fidelity" 표기가 있는 핸드오프는 색상/라디우스/패딩 수치를 어림값으로 대체하지 않고 그대로 옮긴다.
- 구현 완료 보고 전에 반드시 스크린샷 검증을 거친다 — 검증 없이 "완료"라고 말하지 않는다.
- 기존 앱을 리스타일할 때는 상태 관리·컴포넌트 트리는 유지하고 시각적 값만 스펙에 맞춘다 (불필요한 리팩터링 금지).

## 참고: 이 스킬을 스스로 갱신하는 법
사용자가 "이 스킬 좀 고쳐줘" 또는 디자인 작업 중 명시적으로 피드백을 주면, 이 파일(`~/.claude/skills/design-build/SKILL.md`)을 직접 Edit해서 "학습된 선호" 섹션에 반영한다. 별도 확인 없이 바로 고쳐도 되는 파일이다 (사용자 개인 설정이며, 코드가 아니라 향후 참고할 규칙 문서이기 때문).
