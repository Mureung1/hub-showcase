# 주간 계획 수립 스킬 (weekly-plan)

그 주에 할 일을 md 문서에서 뽑아 **하루 크기 task**로 쪼개고, 평일 5일에 배치한 뒤,
승인을 받아 **Notion에 새 주차 페이지 + 태스크 보드**로 배선한다.

핵심 원칙: **읽고(md 전부) → 필요하면 묻고 → 쪼개고 → 사용자 승인 → 그다음에만 Notion에 쓴다.**
Notion 쓰기는 되돌리기 번거로우니 §4 승인 게이트를 반드시 통과한 뒤 실행한다.

## 0. 고정 정보

- **Notion 부모 페이지**: `Naver AI Agent Challenge` (id `395581f4-e375-80d2-8d5e-f107ad7f21d5`).
  검색이 먼저면 `notion-search "Naver AI Agent Challenge"`로 재확인.
- **기간**: 평일 5일 고정. 태스크를 `Day 1`~`Day 5`에 배치한다.
  (사용자가 실행 시 다른 일수를 명시하면 그때만 따른다.)
- **주차 번호 N**: 실행 시 사용자 입력에서 받는다("2주차" → N=2). 불명확하면 §1에서 묻는다.
- **문서·카드 카피는 한국어** (프로젝트 컨벤션).

## 1. 리서치 — md 전부 읽기 + 필요 시 질문

1. 주차 번호 N을 확인한다. 사용자 메시지에 없으면 물어본다.
2. **md 파일을 전부 읽는다**: 루트의 `*.md`(`CLAUDE.md`, `README.md` 등) + `docs/*.md`.
   - Glob `*.md`와 `docs/*.md`로 목록을 잡고 관련 문서를 읽는다.
   - 그 주 계획의 1차 원천은 보통 `docs/weekN-plan.md`(예: `docs/week2-plan.md`)다. 있으면
     우선 근거로 삼고, 거기 정의된 **우선순위(T1→T2→…)·수용기준·대상 파일·연기/제외 결정**을
     그대로 존중한다. `plan.md`(기획)·`checklist.md`·`CLAUDE.md`(스택·컨벤션)로 맥락을 보강한다.
3. **필요하면 사용자에게 묻는다.** md만으로 안 풀리는 판단은 임의로 정하지 말고 질문한다.
   전형적으로 물을 것:
   - 기간/주차가 애매할 때
   - md에 우선순위가 없거나 태스크가 하루보다 크게/작게 잡힐 때 어디서 자를지
   - 어떤 태스크를 뒤로 미루거나 선택으로 내릴지
   - 저장 방식(부모 페이지·주차 번호)이 이전과 달라질 때
   질문은 `AskUserQuestion`으로, 추천안을 첫 번째 옵션에 두고 근거를 붙인다.

## 2. 태스크 분할 — 하루 크기로

목표를 하루 안에 끝낼 크기로 쪼갠다. 카드 하나 = 하루 안에 검증 가능한 단위.

- **의존성·핵심 시나리오 우선**: 뒤 작업의 토대가 되는 것(예: 디자인 토큰·스키마)을 앞에.
  데모 임팩트 큰 핵심 흐름을 앞쪽 Day에 둔다.
- **스키마 변경(마이그레이션)은 한 Day에 모아** 리스크를 격리한다.
- 한 Day에 카드 1~4개. Day 5에는 **통합 점검 + 버퍼**(밀린 것 흡수, 시연 정리)를 둔다 —
  계획은 어긋나기 마련이라 마지막 날 여유가 완주율을 지킨다.
- 각 카드는 **무엇을·왜**가 드러나게. 가능하면 **수용기준(= 완료)**과 **대상 파일**을 설명에 적어
  나중에 "됐다"를 객관적으로 판정할 수 있게 한다(원천 md의 수용기준을 재사용).
- **영역 태그는 그 주 태스크에서 유추**한다(고정 셋 아님). 이번 예: 디자인/웹/DB/Discord/통합/문서.
  주마다 성격에 맞게 새로 뽑되, 색은 §5 매핑을 따른다.

## 3. 사용자에게 일별 표 제시

Notion에 쓰기 **전에**, 쪼갠 결과를 일별 표(마크다운)로 보여준다. 컬럼: `Day | 태스크 | 카드(요약)`.
배치 근거를 1~2줄로 덧붙인다(왜 이 순서인지). 그리고 명시적으로 승인을 요청한다.

## 4. 승인 게이트 (필수)

사용자가 명확히 "좋다/진행"이라고 답하기 전에는 Notion에 아무것도 만들지 않는다.
수정 요청이 오면 §2~§3을 고쳐 다시 제시한다. 승인 후에만 §5로 간다.

## 5. Notion 배선

승인되면 아래 순서로 만든다. (Notion 툴은 deferred이므로 먼저 `ToolSearch`로
`notion-search`·`notion-create-database`·`notion-create-pages`·`notion-create-view`·`notion-fetch`를 로드.)

### 5-1. 주차 페이지 확보
- 부모 아래 `N주차` 페이지를 찾는다(`notion-search "N주차"` 또는 부모 fetch).
- 있으면 그 페이지를 쓰고, 없으면 `notion-create-pages`로 부모(page_id) 아래 새로 만든다.

### 5-2. 태스크 DB 생성
`notion-create-database`, parent = 주차 페이지 page_id. 스키마(고정):

```sql
CREATE TABLE (
  "Name" TITLE,
  "설명" RICH_TEXT,
  "일정" SELECT('Day 1':red, 'Day 2':orange, 'Day 3':yellow, 'Day 4':green, 'Day 5':blue),
  "영역" MULTI_SELECT(<그 주 영역 태그들, 색은 아래 매핑>),
  "태스크" SELECT(<그 주 T번호 라벨들>),
  "상태" STATUS
)
```

영역 색 매핑(관례): `디자인:pink, 웹:blue, DB:green, Discord:purple, 통합:orange, 문서:gray`.
새 영역이 생기면 남은 색에서 고른다. `상태`는 STATUS 타입이라 자동으로 `시작 전/진행 중/완료` 그룹이 생긴다.

### 5-3. 카드 채우기
`notion-create-pages`, parent = 위 DB의 `data_source_id`(collection). 카드마다 속성:
`Name`, `설명`, `일정`(Day N), `영역`(멀티셀렉트는 **JSON 배열 문자열**, 예 `"[\"웹\",\"DB\"]"`),
`태스크`, `상태`(전부 `시작 전`으로 시작).
한 번의 호출에 여러 카드를 배열로 넘긴다.

### 5-4. 일별 보드 뷰
`notion-create-view`, type=board, `database_id`+`data_source_id`. configure:

```
GROUP BY "일정"
SORT BY "일정" ASC
SHOW "Name", "설명", "영역", "태스크", "상태"
```

이렇게 하면 Day 1~5가 칸반 컬럼이 되고, 카드에 영역 태그가 붙는다.

### 5-5. 완료 보고
만든 주차 페이지/DB 링크와 일별 요약 표를 사용자에게 돌려준다.

## 6. 주의

- 멀티셀렉트 값은 반드시 JSON 배열 문자열로 넣는다(그냥 문자열이면 파싱 실패).
- `create-pages`에 긴 한글을 넘길 때 `__unparsedToolInput`으로 우회하지 말고 정규 파라미터로 넘긴다
  (수동 이스케이프 중 잘려 JSON 파싱 에러가 난다).
- 매주 **새 하위 페이지 + 새 DB**를 만드는 방식이다. 기존 주차 DB를 덮어쓰지 않는다.
- 원천 md가 바뀌면 계획도 바뀐다 — 항상 그 시점 md를 다시 읽고 세운다.
