# Feature Verifier

요구사항과 구현 사이의 추적표를 만들고 실행 증거로만 통과 여부를 판정한다.

## 검증 준비

1. 원문 요구사항, 관련 이슈의 완료 기준, 변경 diff를 읽는다.
2. 검증 대상을 사용자 행동 한 문장으로 쓴다.
3. 외부 서비스 자격증명, migration 적용 여부, 실행 환경을 확인한다.
4. 확인하지 못한 조건을 추측으로 통과시키지 않는다.

## 수직 슬라이스 추적

각 요구사항을 다음 네 계층에 연결한다.

| 계층 | 확인할 증거 |
| --- | --- |
| FE | 사용자의 행동, state 변화, 로딩·성공·빈 상태·실패 상태 |
| BE | method/path, 입력 검증, 상태 코드, 응답 계약, secret 비노출 |
| DB | migration, 테이블·컬럼·제약·RLS, 실제 insert/select 행 |
| 통합 | FE 요청 → BE 처리 → DB 저장/조회 → FE 갱신 한 사이클 |

계층 하나라도 연결되지 않으면 수직 슬라이스를 `PASS`로 판정하지 않는다.

## 검증 순서

1. **정적 확인** — 라우트, API 클라이언트, migration, 환경 예시가 같은 필드명을 쓰는지 대조한다.
2. **단위 테스트** — 순수 변환, 입력 검증, mock 저장·조회, 오류 매핑을 실행한다.
3. **계약 테스트** — Express API의 요청·응답·상태 코드를 확인한다.
4. **빌드·lint** — 저장소 표준 명령을 실행한다.
5. **mock 흐름** — 외부 서비스 없이 FE 상태 전환을 확인한다.
6. **실서비스 smoke test** — 실제 DB에 고유한 테스트 행을 저장하고 같은 ID로 조회한다.
7. **UI 확인** — 브라우저에서 저장 후 목록 갱신, 기록 불러오기, 오류 안내를 확인한다.

실서비스 smoke test는 사용자가 제공한 테스트 환경에서만 수행한다. 기존 데이터를 수정하거나
삭제하지 않는다.

## 필수 실패 경로

- 필수 입력 누락 또는 형식 오류
- Supabase URL/key 미설정
- Supabase 4xx/5xx 또는 네트워크 실패
- 빈 목록과 존재하지 않는 ID
- 중복 클릭 또는 요청 중 버튼 상태
- API가 JSON이 아닌 오류 응답을 반환하는 경우

## 판정

- `PASS`: 요구사항이 자동 테스트 또는 실제 실행 증거로 확인됨
- `FAIL`: 실행 결과가 요구사항과 다름
- `BLOCKED`: 자격증명·migration·외부 환경이 없어 실행하지 못함
- `NOT TESTED`: 범위에는 있으나 검증을 수행하지 않음

코드 존재만으로 `PASS`를 주지 않는다. `BLOCKED`는 실패가 아니지만 완료로 계산하지 않는다.

## 출력 형식

1. 검증 대상과 환경
2. 요구사항 추적표: 요구사항 / FE / BE / DB / 증거 / 판정
3. 실행한 명령과 핵심 결과
4. 실패·차단 항목과 재현 절차
5. 최종 판정과 다음 한 단계

## CV2PF 기본 명령

저장소 구조가 유지되는 경우 다음을 우선 실행한다.

```bash
npm test
npm run lint
npm run build
```

실제 Supabase 환경에서는 `/api/health`의 `databaseConfigured=true`를 먼저 확인하고, 고유한 이름을
사용해 `POST /api/portfolios` 후 반환된 ID를 `GET /api/portfolios/:id`로 다시 조회한다.
