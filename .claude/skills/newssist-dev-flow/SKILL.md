# Newssist 개발 방식

1인 개발 + 바이브코딩 + **배우면서 만들기**가 이 프로젝트의 진행 방식임. 사용자는 개발 경험이 많지 않아서, 매 기능마다 "왜 이렇게 하는지"를 개념부터 설명받으면서 진행함. 코드만 빨리 짜주는 게 아니라, 짜는 이유와 개념을 같이 이해시키는 게 핵심 — DB 스키마/서버 연결 작업을 이 방식으로 진행했고, 이후 모든 기능도 같은 흐름을 따름.

## 1. 기능 착수 순서

- 기능을 나열된 순서가 아니라 **의존관계 순서**로 진행한다. 로그인처럼 다른 기능의 전제조건이 되는 것, 클러스터링처럼 데이터가 쌓여야 의미 있는 것을 구분해서 순서를 정한다.
- 매 기능 시작 전에 **DB 스키마 → API 명세 → 백엔드 → 프론트** 순으로 작게 쪼갠다. 한 번에 기능 전체를 구현하지 않고, "일단 이거 하나 되는지 확인"할 수 있는 단위로 나눈다.
- 시간/범위처럼 사용자만 답할 수 있는 결정(하루 가능 시간, 기능을 뺄지 말지 등)은 추측하지 말고 먼저 물어본다.

## 2. 설명 방식

- 새로운 개념(UNIQUE 제약, UPSERT, RLS, JWT, bcrypt, Postgres, semver, dotenv 등)이 나올 때마다 **그 개념 자체를 기초부터** 설명한다. "이미 안다고 가정"하지 않는다.
- 설명은 항상 **이 프로젝트의 실제 코드/에러 메시지/파일**을 예시로 든다 — 일반론만 얘기하지 않고 `server/index.js`의 실제 줄, 실제로 났던 에러를 갖고 설명한다.
- 왜 이렇게 설계했는지(예: read_history를 왜 UPSERT로 단순화했는지, terms를 왜 article_terms로 옮겼는지)는 **트레이드오프와 이유**를 같이 남긴다. 결정만 던지지 않는다.

## 3. 진행 단위와 검증

- 코드를 만들면 바로 실행/테스트해서 **눈에 보이는 결과(스모크 테스트)**로 확인한 다음에 다음 단계로 넘어간다. (예: schema.sql 실행 → Table Editor에서 테이블 확인 → 서버 연결 → `/api/health`로 실제 응답 확인)
- 에러가 나면 원인을 짚어주고, 고친 코드를 before/after로 보여준다.
- 큰 작업(DB 스키마 전체, 서버 스캐폴딩 전체)도 파일 단위로 나눠서 하나씩 만들고 설명한다.

## 4. Git 습관

- 브랜치는 `feature/기능명` — 작업 성격이 다르면(DB 스키마 vs API 명세서 등) 브랜치도 분리하는 걸 원칙으로 하되, 이미 진행 중인 작업에 이어붙일지는 매번 물어보고 정한다.
- 커밋은 **바뀐 이유 단위**로 쪼갠다 (CLAUDE.md 커밋 컨벤션과 동일 원칙).
- 커밋 메시지에 Claude/AI 관련 co-author 문구를 넣지 않는다.
- 커밋/push처럼 되돌리기 번거로운 작업은 실행 전에 먼저 확인받는다. 사용자가 "내가 할게"라고 하면 명령어만 알려주고 대신 실행하지 않는다.

## 5. 문서화 규칙

- API 명세서는 `docs/api-spec.md`가 단일 소스. Notion에는 일정만 관리하므로, **이 파일이 바뀔 때마다(엔드포인트 추가/변경) 먼저 사용자에게 알린다** — CLAUDE.md에도 명시돼 있음.
- 그날 배운 내용을 정리해달라는 요청이 오면, 코드 파일이 아니라 **학습 노트 아티팩트**(개념 설명 + 코드 예시 + 용어 사전 형식)로 만든다. 레포에는 안 남기고 별도 웹 페이지로 제공.
- 진행 계획/일정은 사용자가 명시적으로 파일 저장을 요청하지 않는 한 **채팅 텍스트로만** 제공한다 (Notion에 직접 옮겨서 관리하길 선호함).

## 6. 유지보수

이 문서도 실제 진행 방식이 바뀌면 그에 맞춰 고쳐 쓴다. 수정할 땐 바뀐 이유 단위로 커밋을 쪼갠다 (`newssist-design` 스킬 문서와 동일한 유지보수 원칙).
