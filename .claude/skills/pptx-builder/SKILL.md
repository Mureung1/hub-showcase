# PPT(.pptx) 만들기

## 이 스킬을 쓰는 이유
python-pptx로 슬라이드를 만드는 작업 자체는 어렵지 않지만, 실전에서 반복해서 부딪히는 문제가 두 가지 있다:

1. **파일이 저장은 되는데 PowerPoint에서 안 열리는 경우** — python-pptx는 OOXML 스키마를 검증하지 않아서, 좌표에 float가 섞이거나 XML 요소 순서가 틀려도 저장은 조용히 성공한다. 실제로 여는 순간에만 실패한다.
2. **"한 페이지만 고쳐줘"라고 했는데 전체가 바뀌는 경우** — 빌드 스크립트를 처음부터 다시 실행해서 전체 프레젠테이션을 새로 만들고 그걸로 기존 파일을 덮어쓰면, 사용자가 PowerPoint에서 직접 수정해둔 다른 페이지까지 통째로 사라진다. 실제로 이 실수로 사용자의 수동 편집 내용을 복구 불가능하게 날린 적이 있다.

이 스킬은 이 두 가지를 구조적으로 막기 위한 것이다. "처음부터 전체 덱 만들기"와 "이미 있는 파일 일부 수정하기"는 완전히 다른 절차로 다뤄야 한다 — 아래에서 분리해서 설명한다.

## 번들 리소스
- `scripts/pptx_helpers.py` — 도형·텍스트·화살표·이미지 프레임·헤더 그리드 등 재사용 헬퍼. 아래 4가지 버그가 이미 고쳐져 있다(파일 상단 docstring에 이유 설명):
  1. EMU 좌표 float 버그 (나눗셈 결과는 `Emu(int(...))`로 감쌀 것)
  2. 도형 text_frame의 vertical_anchor 기본값이 TOP이 아님
  3. 커넥터 화살표 XML의 headEnd/tailEnd 순서
  4. 한글/영문 폭이 달라서 생기는 뱃지·라벨 줄바꿈 오류
- `scripts/render_check.py` — PowerPoint COM으로 슬라이드를 PNG로 내보내는 검증 스크립트. 실제 슬라이드 비율(16:9/4:3 등)을 자동으로 읽어서 그 비율 그대로 내보낸다 — 렌더링 결과가 실제 슬라이드와 다른 비율로 찌그러지는 일이 없다.
- `references/apple-style-design.md` — "고급스럽고 조용한, 사진/스크린샷 중심" 톤이 필요할 때 참고하는 디자인 언어 문서(색·타이포·여백·컴포넌트 패턴). 발표 대상에 이미 자체 브랜드가 있으면 이 문서보다 그 브랜드 토큰이 우선한다.

작업 시작할 때 `scripts/`의 두 파일을 작업 폴더로 복사해서 쓴다 (직접 새로 구현하지 말 것 — 이미 겪은 버그를 또 만나게 된다).

## 처음부터 전체 덱 만들기

1. **디자인 토큰부터 정한다.** 발표 대상이 이미 존재하는 프로젝트/앱이면, 그 프로젝트의 디자인 시스템(색상·폰트·radius 토큰)을 그대로 가져다 쓴다 — 임의로 새 팔레트를 짓지 않는다. `pptx_helpers.py` 상단의 팔레트 상수를 프로젝트 값으로 덮어쓴다. 딱히 정해진 브랜드가 없고 고급스러운 톤이 필요하면 `references/apple-style-design.md`를 참고 톤으로 쓴다.
2. **폰트는 그 컴퓨터에 항상 있는 폰트를 우선 쓴다.** 한글은 `맑은 고딕`(`FONT_KR`), 영문은 `Segoe UI`(`FONT_EN`). Pretendard·SF Pro 같은 커스텀/시스템 전용 폰트는 pptx에 기본적으로 임베드되지 않아서, 그 폰트가 없는 컴퓨터에서 열면 다르게 보이거나 폭 계산이 틀어진다 — "어디서 열릴지 모르는" 발표 파일에는 항상 내장 폰트를 쓴다.
3. **슬라이드는 PowerPoint 표준 비율로 만든다.** 기본은 16:9(`SLIDE_W = Inches(13.333)`, `SLIDE_H = Inches(7.5)`) — 사용자가 4:3 등 다른 비율을 명시하지 않는 한 이 값을 그대로 쓴다. 비율을 바꿀 땐 `SLIDE_W`/`SLIDE_H`뿐 아니라 `HEADER_*` 좌표들도 같이 조정해야 그리드가 안 깨진다.
4. **챕터명·제목·부제목은 모든 슬라이드에서 같은 위치에 놓는다.** 슬라이드마다 y좌표를 따로 계산하지 말고 `add_slide_header(slide, title, eyebrow=..., subtitle=...)`를 거쳐서만 그린다 — 이 함수가 `HEADER_EYEBROW_Y`/`HEADER_TITLE_Y`/`HEADER_SUBTITLE_Y` 고정 좌표를 쓰기 때문에, 페이지를 넘겨도 제목이 위아래로 흔들리지 않는다.
5. **본문 하단을 비워두지 않는다, 단 장식으로 채우지 않는다 — 표지·목차 슬라이드는 예외.** 렌더링 결과에서 슬라이드 아래쪽 20~25% 이상이 완전히 빈 여백이면 밀도가 부족한 것 — 의미 있는 정보(보충 스크린샷, 근거 수치, `add_footnote()`로 각주 한 줄)로 채운다. 채울 내용이 정말 없으면(클로징 슬라이드 등) 도형이나 아이콘 같은 장식을 더하는 대신, 제목 자체를 크게 키워서 여백을 "의도된 여백"으로 만든다 — `references/apple-style-design.md`의 "본문 밀도" 절 참고. **단, 표지(첫 슬라이드)와 목차 슬라이드는 이 규칙에서 제외한다.** 소개 목적의 슬라이드는 정보를 욱여넣을수록 오히려 "난잡하다"는 인상을 준다 — 제목+부제(+최소한의 메타 정보) 정도로 단순하게 유지하고, 빈 여백은 의도된 여백으로 놔둔다.
6. **목차(발표 순서)가 필요하면 표지에 얹지 말고 별도 슬라이드로 분리한다.** 표지는 소개만 하고, "이 발표에서 다룰 내용"은 표지 바로 다음의 독립된 목차 슬라이드에 번호+제목+한 줄 설명 형식으로 나열한다. 표지에 목차까지 욱여넣으면 표지 하나가 두 가지 역할을 하려다 산만해진다.
7. **각주에는 청중에게 의미 있는 내용만 쓴다.** 저장소 이름·브랜치명·"이 자료도 코드로 생성했다" 같은 제작 과정 메타정보는 발표를 듣는 사람 입장에서 아무 의미가 없다 — 넣지 않는다. 각주는 차별점 요약, 출처, 다음 단계 예고처럼 발표 내용 자체에 관한 한 줄로 채운다.
8. **코드 스니펫을 슬라이드에 그대로 넣지 않는다.** 개발 과정을 설명하는 슬라이드라도, 발표를 듣는 사람이 코드를 읽고 이해할 거라고 가정하지 말 것. "무슨 일이 일어나는지"를 평범한 말로 풀어 쓰고, 전문 용어(fetch, 프록시, API 등)를 쓰기 전에 상대가 아는 용어인지 확인하거나 아예 쉬운 말로 바꾼다. 이 판단이 안 서면 사용자에게 청중이 누구인지 먼저 물어본다.
9. **실제 화면·데이터로 채운다.** 서비스나 앱에 대한 발표라면, 다시 그린 목업 대신 실제로 그 화면을 띄워서(Playwright 등으로) 캡처한 스크린샷을 쓴다 — 애니메이션이 있는 화면이면 애니메이션이 끝날 때까지 충분히 기다렸다가 캡처하고(중간에 캡처하면 어중간한 상태가 찍힌다), 스크롤 위치도 캡처 직전에 맨 위로 되돌려놓는다(이전 클릭들이 페이지를 스크롤시켰을 수 있다).
10. **다 만들면 반드시 렌더링해서 눈으로 확인한다.** `render_check.py`로 전체 슬라이드를 PNG로 뽑아서 Read 도구로 하나씩 열어본다. 특히 확인할 것: 텍스트가 상자 밖으로 넘치지 않는지, 절대좌표로 배치한 요소끼리 겹치지 않는지(뱃지, 화살표 라벨 등), 페이지 번호가 슬라이드 개수와 맞는지, 제목 위치가 슬라이드마다 흔들리지 않는지, 하단에 불필요한 빈 여백이 없는지(표지·목차 제외).
11. **완성본을 사용자가 쓰기 좋은 위치에 둔다.** 스크래치패드가 아니라 바탕화면이나 사용자가 지정한 프로젝트 폴더처럼 실제로 찾기 쉬운 곳에 저장한다. 프로젝트 안에서 계속 이어서 작업할 덱이라면, 빌드 스크립트와 이미지 에셋도 스크래치패드가 아니라 그 프로젝트 저장소 안(`decks/<덱 이름>/`처럼)에 둬서 세션이 끝나도 남아있게 한다.

## 이미 있는 파일 수정하기 (가장 중요 — 절대 생략하지 말 것)

사용자가 "N페이지만 고쳐줘"라고 하면, 정말로 그 페이지의 도형만 건드려야 한다. 순서:

1. **덮어쓰기 전에 무조건 백업한다.** `backup_before_overwrite(path)`를 먼저 부른다. 사용자가 PowerPoint에서 손으로 고친 파일일 수 있고, 그 편집 내용은 스크립트 어디에도 기록돼 있지 않다 — 잃으면 복구할 방법이 없다.
2. **빌드 스크립트를 처음부터 다시 실행해서 전체를 새로 만들지 않는다.** 대신 기존 파일을 열어서 그 슬라이드만 다시 그린다:
   ```python
   from pptx import Presentation
   from pptx_helpers import clear_slide, backup_before_overwrite

   path = "발표자료.pptx"
   backup_before_overwrite(path)
   prs = Presentation(path)
   slide = prs.slides[3]   # 4번째 슬라이드 (0-indexed)
   clear_slide(slide)
   # 여기서 이 슬라이드 내용만 다시 그림
   prs.save(path)
   ```
   이렇게 하면 다른 슬라이드는 파일 안에서 손도 대지 않으므로, 사용자가 PowerPoint에서 직접 수정한 내용이 그대로 남는다.
3. **한 벌짜리 빌드 스크립트(`build_deck.py` 같은)를 계속 쓰고 있었다면**, 사용자가 특정 슬라이드를 손으로 고쳤다고 알려줄 때마다 그 스크립트의 해당 부분도 텍스트만 최신 상태로 맞춰둔다 — 나중에 "전체를 처음부터 다시 만들어줘"라고 할 때를 위한 것이다. 하지만 이건 스크립트를 최신으로 유지하는 것일 뿐, **그렇게 스크립트를 고쳤다고 해서 그 스크립트를 실행해서 실제 파일을 덮어써도 된다는 뜻은 아니다.** 실행해서 덮어쓰는 건 "N페이지만 고쳐줘"가 아니라 "전체 다시 만들어줘"라고 명시적으로 말했을 때만 한다.
4. **애매하면 먼저 물어본다.** 특정 슬라이드만 고치는 게 이미 진행 중인데 사용자가 "이것도 반영해서 다시 만들어줘"처럼 범위가 넓어지는 말을 하면, 전체 재생성이 맞는지 확인하고 넘어간다 — 재생성은 되돌릴 수 없는 작업이다.
5. **수정 후에도 항상 렌더링해서 확인한다** (위 "처음부터 만들기" 5번과 동일).

## 트러블슈팅

- **PowerPoint가 파일을 열지 못한다는 에러**: python-pptx가 저장에는 성공했지만 스키마가 깨졌다는 뜻. `pptx_helpers.py`를 안 쓰고 직접 XML을 만졌다면, `zipfile`로 열어서 의심되는 슬라이드의 XML을 읽고 좌표값에 `.0`이 붙어있지 않은지(float 버그), 커스텀 XML 요소 순서가 스키마와 맞는지 확인한다.
- **PowerPoint 자체가 이 컴퓨터에 없다**: `reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\POWERPNT.EXE"`로 확인. 없으면 LibreOffice(`soffice --headless --convert-to png`)로 대체하거나, 최소한 python-pptx로 XML well-formedness라도 확인한다(스키마 검증은 안 되지만 없는 것보다는 낫다).
- **텍스트가 상자 밖으로 넘친다**: 대부분 `_text_width_in()` 같은 폭 추정이 부정확했거나, `vertical_anchor`를 안 정해서 콘텐츠 길이에 따라 위치가 흔들린 경우다. 렌더링 결과를 눈으로 봐야만 잡힌다 — 코드만 보고 괜찮을 거라고 넘어가지 말 것.
