# 작업 상세 설명 스킬

방금 한 작업을 요약(불릿 나열)이 아니라, **기능/변경 단위로 쪼개서 깊이 있게** 설명하는 스킬.

## 언제 쓰는가

- "요약만 하지 말고 자세히", "하나하나", "왜 그렇게 했어", "더 좋은 방법 없어?" 같은 요청
- 방금 답변이 커밋 목록·불릿 요약 수준이었는데 사용자가 더 파고들고 싶어할 때

일반적인 작업 완료 보고(짧은 요약)에는 쓰지 않는다 — 사용자가 명시적으로 깊이를 요구했을 때만.

## 구조

**기능/변경 단위로 섹션을 나눈다.** 파일 단위가 아니라 "사용자에게 의미 있는 변경 덩어리" 단위로 쪼갠다 (예: "GET /:id 추가"와 "입력 검증 추가"는 같은 파일을 건드려도 별개 섹션).

각 섹션마다 다음 네 가지를 반드시 채운다:

1. **뭘 했나** — 정확히 어떤 코드/파일을 어떻게 바꿨는지. 함수명·파일 경로를 구체적으로 짚는다.
2. **왜 했나** — 이 변경을 유발한 배경. 이슈/체크리스트/코드리뷰 지적사항/버그 재현 시나리오 등 **근거를 실제로 확인해서** 인용한다 (지어내지 않는다 — 근거가 없으면 "제 판단으로"라고 명시한다).
3. **어떻게 했나** — 구현 방식과 그 방식을 고른 이유. 기존 코드의 유사 패턴을 재사용했다면 어떤 패턴인지, 왜 새로 안 만들고 재사용했는지.
4. **더 나은 방법이 있었을까** — 최소 1개 이상의 대안을 실제로 제시한다. 이게 이 스킬의 핵심 차별점이다:
   - 고려했지만 안 한 이유가 있으면 그 이유를 밝힌다 (과설계, 스코프 밖, 인프라 비용 등).
   - 지금 방식의 한계·기술 부채를 숨기지 않는다. "이 부분은 임시방편이다", "이건 제 판단이라 바뀔 수 있다"처럼 확신의 정도를 솔직하게 표현한다.
   - 가능하면 "언제/어떤 조건이 되면 대안으로 바꾸는 게 좋은지"까지 제시한다 (예: "실사용 데이터가 쌓이면", "#6에서 LLM이 들어오면").

## 하지 말 것

- 네 항목을 형식적으로 다 채우려고 대안이 없는데 억지로 지어내지 않는다 — 정말 없으면 "다른 방법은 딱히 없었다"고 솔직히 말한다.
- "왜 했나"에 실제 근거(이슈 번호, 문서, 코드리뷰) 없이 그럴듯한 이유를 지어내지 않는다. 답하기 전에 `git log`, 이슈 트래커, `docs/decisions.md`·`docs/log.md`를 확인한다.
- 기능 단위를 너무 잘게 쪼개 같은 얘기를 반복하지 않는다 (예: 같은 함수의 인자 하나하나를 별도 섹션으로 쪼개지 않는다).
- 대안 제시를 "이론적으로 가능한 모든 방법 나열"로 흐르게 하지 않는다 — 실제로 저울질했거나 저울질할 가치가 있는 것만.
