# 테스트 작성 Skill

## 언제 이 skill을 확인해야 하는가
- 학점/졸업요건 판정 함수(예: `evaluateTrackRequirements`)를 새로 만들거나 로직을 수정할 때
- 계산 함수(예: `calculateSemesterPlan`, `buildGapList`)를 새로 만들거나 로직을 수정할 때
- 사용자가 "테스트 작성해줘", "테스트 케이스 정리해줘"라고 요청할 때

UI 컴포넌트 테스트(렌더링/클릭 검증)에도 적용 가능하지만, 이 skill은 특히 **학점·요건 계산처럼 조건 분기가 있는 순수 함수**를 우선 대상으로 한다.

## 1. 테스트 프레임워크: Vitest

이 프로젝트는 Jest에서 Vitest로 마이그레이션했으므로 **Vitest를 사용한다** (Jest 아님).

설치 여부부터 확인한다:
```bash
# client 또는 server 디렉토리에서
node -e "require.resolve('vitest')" 2>&1
```

설치되어 있지 않다면:
1. 설치: `npm install -D vitest`
2. `package.json`의 `scripts`에 테스트 스크립트 추가:
   ```json
   "test": "vitest run"
   ```
3. Vite 프로젝트(client)라면 `vite.config.js`에 `test: { globals: true }`가 있는지 확인 — 없으면 추가한다. 이게 있어야 `describe`/`test`/`expect`를 매 파일마다 import하지 않고 바로 쓸 수 있다.
4. Vite가 없는 프로젝트(server)라면 별도 `vitest.config.js`를 만들고 동일하게 `globals: true`를 설정한다.

이미 설치되어 있으면(현재 client/server 둘 다 설치돼 있음) 이 단계는 건너뛴다.

## 2. 파일 위치 규칙
테스트 파일은 구현 파일과 **같은 디렉토리**에 `파일명.test.js`로 둔다 (예: `gapList.js` → `gapList.test.js`). 별도 `__tests__` 폴더를 만들지 않는다.

## 3. 학점/요건 함수는 항상 아래 4가지 경계값 케이스를 포함한다

기준값(예: 9학점, 3학점 등)이 있는 함수라면 다음 네 가지를 빠짐없이 테스트한다:

| 케이스 | 설명 | 예 (기준 9학점일 때) |
|---|---|---|
| 미충족 | 기준보다 확실히 부족 | 6학점 이수 |
| 경계값 - 1 | 기준보다 딱 1만큼 부족 | 8학점 이수 |
| 정확히 충족 | 기준과 정확히 일치 | 9학점 이수 |
| 초과 이수 | 기준을 넘어섬 | 12학점 이수 |

`server/src/utils/gradRequirements.test.js`가 이 패턴의 참고 예시다 (해외대학 인정학점 9학점 요건에 대해 6/8/9/12학점 네 케이스를 전부 테스트함).

## 4. 엣지 케이스 체크리스트

함수 시그니처를 보고 아래 항목에 해당하는 게 있으면 반드시 테스트에 포함한다:

- [ ] **빈 배열/빈 입력**: `[]`을 넣었을 때 에러 없이 합리적인 기본값(0, 빈 결과 등)을 반환하는가
- [ ] **`undefined` 값**: 필수 인자를 안 넣었을 때 어떻게 동작하는가 — 조용히 무시되는지, 에러가 나는지 확인하고 **의도한 동작인지 이름 붙여서 테스트로 남긴다** (예: `gapList.test.js`의 "goalTotal/combinedTotal이 undefined면 gap이 NaN이 되어 조용히 무시된다" 케이스처럼, 버그일 수도 있는 동작도 우선 문서화한다)
- [ ] **잘못된 트랙/카테고리 문자열**: 존재하지 않는 트랙 키나 카테고리 라벨을 넘겼을 때 에러를 던지는지, 빈 결과를 주는지 확인 (예: `evaluateTrackRequirements([], 'not-a-real-track')`은 에러를 던져야 함)

## 5. 테스트 설명(`test()`의 첫 인자)은 한글로, 읽자마자 이해되게

나쁜 예: `test('case 1', () => {...})`

좋은 예: `test('창업교과목 9학점 정확히 충족하면 satisfied가 true다', () => {...})`

설명에는 **입력 조건 + 기대 결과**가 둘 다 드러나야 한다. "무엇을 넣었을 때 → 무엇이 나와야 하는지"를 테스트 코드를 안 봐도 알 수 있게 쓴다.

## 6. 작성 후 반드시 실행해서 통과 확인

테스트 파일만 작성하고 끝내지 않는다. 아래를 항상 수행한다:
```bash
npm test
```
(내부적으로 `vitest run` 실행) 전체 스위트가 통과하는지 확인하고, 기존 테스트가 깨졌다면 왜 깨졌는지 파악한 뒤 보고한다 — 의도한 동작 변경이면 그대로 두고, 의도치 않은 회귀면 고친다.

## 판단 규칙 (자체 검수 체크리스트)
테스트를 작성한 뒤 스스로 점검한다:
1. 기준값이 있는 함수라면 미충족/경계값-1/정확히충족/초과이수 4케이스가 다 있는가?
2. 빈 입력, `undefined`, 잘못된 문자열 케이스가 함수 시그니처상 의미가 있다면 포함됐는가?
3. 모든 `test()` 설명이 한글이고, 입력 조건과 기대 결과를 함께 담고 있는가?
4. `npm test`를 실제로 실행해서 통과를 확인했는가?

하나라도 어긋나면 채우고 나서 작업을 마친다.
