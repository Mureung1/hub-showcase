# TDD Workflow Skill

## 언제 쓰나
- 규칙이 분명한 함수: 검증(validation), 계산, 파싱/변환
- 조건 분기가 있는 로직 (정상/빈 값/경계값/실패 케이스가 나뉘는 것)
- 오늘처럼 "외부 스펙과 실제가 다르다"는 걸 발견했을 때 — 그 발견을 테스트 케이스로 고정해두면 같은 문제가 재발했을 때 즉시 빨강으로 드러남
- **UI/화면은 이 스킬 대상이 아님** — 눈으로 확인하는 게 더 빠름

## 4단계 (순서 절대 바꾸지 않음)

### 1. 스펙과 시나리오 (사람 확인 필수)
- 코드를 쓰기 전에, 함수가 뭘 해야 하는지 말로 먼저 정리한다
- 입력 → 기대 결과 → 이유를 표로 정리해서 제시
- **여기서 멈추고 사용자 승인을 받는다** — 케이스 빠진 거 없는지 확인 전엔 다음 단계로 안 넘어감

### 2. Red — 실패하는 테스트부터
- 시나리오 표를 그대로 테스트 코드로 옮긴다
- 대상 함수/클래스가 아직 없으면 **스텁(빈 껍데기, 항상 실패/기본값 반환)**부터 만들어서 테스트가 최소한 "실행은 되고 실패하는" 상태를 만든다
- 실행해서 빨강(실패) 확인 — 이게 정상이다, 통과하면 오히려 이상한 것

### 3. Green — 통과하는 최소한의 코드
- 테스트를 통과시키는 데 필요한 만큼만 구현한다, 더 하지 않는다
- 실행해서 초록(통과) 확인

### 4. Refactor — 동작 유지한 채 정리
- 테스트가 있으니 안심하고 구조 정리
- 리팩토링 후 반드시 테스트 재실행해서 여전히 초록인지 확인

## 언어별 도구
- **백엔드(Java)**: JUnit5, `./gradlew test`
- **프론트(JS/React)**: vitest — 아직 프로젝트에 설치 안 됐으면 먼저 설치부터:
  `npm install -D vitest @testing-library/react @testing-library/jest-dom jsdom`
  `vite.config.js`에 `test: { environment: 'jsdom', setupFiles: './src/setupTests.js' }` 추가

## 하지 말 것
- 테스트 케이스 목록을 사용자 확인 없이 바로 테스트 코드로 넘어가지 않는다
- Green 단계에서 시나리오에 없던 기능을 미리 만들어두지 않는다 (필요해지면 그때 새 테스트 추가)
- Red 단계를 건너뛰고 구현부터 하지 않는다 — 그건 그냥 원래 순서고, TDD가 아니다
- 테스트 코드 자체도 대충 넘기지 않는다 — 테스트가 틀리면 그 위의 모든 확인이 틀린다는 걸 기억할 것
