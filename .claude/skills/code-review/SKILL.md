# 코드 리뷰

코드를 다 쓰고 **검증을 통과한 뒤**, 에이전트에게 맡겨 **더 나은 코드 · 더 나은 구조**를 찾는다.
빌드가 깨진 코드를 읽는 것은 낭비다 — `workflow` 의 검증 단계를 먼저 통과한다.

**돌아가는 코드를 다시 보는 자리다.** "동작하니까 됐다" 와 "이대로 둬도 되나" 사이를 여기서 가른다.

**한 번에 읽을 수 있는 크기로 가져온다.** 크게 뭉친 변경은 리뷰가 통과 도장으로 바뀐다.
커졌으면 리뷰를 크게 하지 말고 **작업을 쪼갠다.**

## 무엇을 보나

나중에 고치는 비용이 큰 순서대로 본다.

| 관점 | 묻는 것 |
|---|---|
| **정확성** | 경계값 · 빈 값 · 실패 경로에서 어떻게 되는가. 정상 경로는 대개 맞다 |
| **책임 배치** | 이 로직이 여기 있어야 하나. 같은 규칙이 여러 곳에 흩어지지 않았나 |
| **복잡도** | 지금 쓰는 곳이 없는 추상화 · 계층 · 설정이 들어있지 않은가 |
| **데이터 접근** | 필요한 만큼만 읽는가. 트랜잭션 범위가 필요한 만큼인가 |
| **상태와 동시성** | 공유되는 객체에 가변 상태가 있는가. 순서가 바뀌어도 결과가 같은가 |
| **자원과 경계** | 외부와 통신하는 곳에 시간 제한이 있는가. 연 것을 닫는가 |
| **오류 처리** | 실패를 삼키지 않는가. 무엇이 왜 실패했는지 남는가 |
| **보안** | 외부 입력을 믿지 않는가. 비밀 · 개인정보가 로그 · 응답에 새지 않는가 |
| **가독성** | 이름이 하는 일과 맞는가. 주석이 코드와 어긋나지 않는가 |
| **테스트** | 규칙이 깨지면 실패하는가. 구현을 그대로 베낀 것은 아닌가 |

여기서 보는 **동시성은 이 코드 하나가 안전한가**이고, **데이터 접근은 이 쿼리가 필요한 만큼만 읽는가**이다.
여러 작업이 겹치거나 전체 요청을 합쳐야 보이는 문제는 `feature-review` 에서 본다.

## 두 가지를 구분해서 말한다

| 종류 | 근거 | 처리 |
|---|---|---|
| **결함** | 틀리게 동작한다 | **무조건 고친다.** 재현 조건을 함께 적는다 |
| **제안** | 더 나은 코드 · 구조가 있다 | 받아들일지 **코드를 쓴 사람이 정한다** |

- 섞어 말하면 받는 쪽이 무엇을 꼭 고쳐야 하는지 알 수 없다. **말할 때 어느 쪽인지 밝힌다.**
- 확신이 없으면 **결함이 아니라 제안으로** 말한다. 결함이라 해놓고 아니면 그다음부터 무게를 잃는다.
- 반대로 **고치기 번거롭다는 이유로 결함을 제안으로 낮추지 않는다.**

## 제안을 어떻게 내나

- **위 표의 관점에 걸리면 근거가 분명하다.** 표 밖의 것을 제안할 때는 왜 나은지를 직접 대야 한다.
- **무엇이 나아지는가**와 **무엇을 잃는가**를 같이 적는다. 잃는 게 없다고 적혀 있으면 덜 본 것이다.
- 대안이 여럿이면 하나를 고르고, 나머지를 왜 버렸는지 한 줄로 남긴다.
- **근거를 못 대면 제안이 아니라 취향이다.** 취향은 강제력이 없다.
- **제안이 다섯 개를 넘으면 리뷰가 아니라 재설계다.** 하나씩 판정하지 말고 왜 이렇게 됐는지를 먼저 본다.
- 지금 고치지 않기로 해도 **기록은 남긴다.** 같은 제안이 반복되면 그건 취향이 아니다.

## 에이전트 제안을 거르는 법

맡길 때 **무엇을 만드는 코드인지 · 이번 범위가 어디까지인지**를 함께 준다.
맥락 없이 맡기면 일반론이 돌아오고, 그걸 거르는 데 리뷰보다 시간이 더 든다.

에이전트는 **그럴듯하지만 틀린 제안**을 한다. 리뷰를 맡기는 이상 이 필터가 마지막 방어선이다.

- **실제로 돌려봤나** — 제안대로 고치면 테스트가 통과하는가
- **코드를 읽고 한 말인가** — 이름만 보고 한 말인지 확인한다
- **우리 규모에 맞나** — 데이터 양 · 트래픽 · 마감을 모르고 하는 일반론인지 본다

세 개를 통과하지 못한 제안은 **버리거나, 나중에 볼 것으로 따로 적는다.** 지금 반영하지 않는다.

**이해하지 못한 제안은 반영하지 않는다.** 설명을 요구하고, 그래도 모르겠으면 남겨 둔다.
읽지 못하는 코드가 들어오면 다음에 고칠 사람이 없다.

## 결정과 기록

- **결정은 코드를 쓴 사람이 한다.** 단, 결함은 결정 대상이 아니다.
- 반영하지 않기로 한 것은 **이유를 이슈나 PR에 남긴다.** 다음에 같은 제안을 다시 판단하지 않게.

## 리뷰가 끝나는 조건

| 항목 | 조건 |
|---|---|
| 결함 | **0개.** 하나라도 남으면 커밋하지 않는다 |
| 제안 | 남아도 된다. 대신 **고칠지 · 버릴지 · 나중에 볼지는 정한다** |

**미루는 것과 안 하는 것은 다르다.** 나중에 볼 것으로 넘긴 제안은 이슈로 남긴다. 남기지 않으면 안 한 것이다.
고친 뒤에는 **고친 부분과 그 부분이 건드리는 곳만** 다시 본다. 전체를 다시 읽지 않는다.
둘이 닫히면 `commit-convention` 으로 넘어간다.

## 하지 말 것

- 검증을 통과하지 않은 코드에 리뷰 요청하기
- 한 번에 다 못 읽을 만큼 뭉쳐서 올리기
- 결함과 제안을 구분하지 않고 말하기
- 에이전트 제안을 확인 없이 그대로 반영하기
- **이해하지 못한 코드를 반영하기**
- 리뷰에서 나온 것을 기록 없이 넘기기
