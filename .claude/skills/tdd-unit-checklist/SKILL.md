# TDD Unit Checklist — checklist 항목을 테스트로 검증하며 진행하기

> 출처: 보쇼(학교생활 알림 에이전트) 2주차 checklist 2-1 D-day 계산 함수.
> 핵심 사상: **"다 됐나?"를 사람의 주관적 판단이 아니라 초록/빨강이라는 기계적 사실로 결정한다.**
> 정답을 실행 가능한 코드(테스트)로 먼저 못 박고, 그걸 통과시키는 코드를 만든다.

⚠️ **범위 주의**: 이 스킬은 **1계단(순수함수 unit 테스트) 판**이다. Express 라우트를
supertest로 테스트하는 법, DB에 의존하는 통합 테스트는 아직 실전으로 안 겪어 미포함.
그 단계를 겪으면 "성장 기록"에 추가한다.

---

## 0. 먼저 판별한다 — 이 항목이 TDD 대상인가

**TDD를 모든 checklist 항목에 쓰지 않는다.** 착수 전에 항목의 성격부터 나눈다.

| 항목 성격 | 검증 방식 | 예 (보쇼 2-1) |
|---|---|---|
| 입력→출력이 하나로 정해짐 (계산·검증·변환) | 🔴 **TDD** | D-day 계산 (마감일+오늘 → 문구) |
| 화면 모양·색·여백·배치 | 👁 눈 검증 | 뱃지가 제자리에 뜨는지, 레이아웃 |
| 데이터 편집·설정·설치 | ✅ 그냥 하고 확인 | mock 날짜 형식 교체, vitest 설치 |

판별 질문 하나: **"입력을 넣으면 정답이 하나로 딱 떨어지는가?"**
- YES → TDD (정답이 명확하니 테스트로 박을 수 있음)
- NO (사람이 봐야 앎) → 눈 검증
- 애초에 함수가 아님 (데이터·설정) → 그냥 하고 확인

**사례**: 2-1은 세 항목이었는데 TDD는 D-day 계산 하나뿐이었다. mock 날짜 교체는 데이터
편집(함수 없음), 화면 연결은 눈 검증(뱃지가 예쁜지는 자동으로 못 봄). **한 checklist
항목 안에서도 부분마다 검증 방식이 갈린다.**

> TDD가 안 맞으면 굳이 쓰지 않는다. 화면에 억지로 테스트를 붙이면 환경 의존
> 테스트가 되어 오히려 불안정해진다(§5 사례 참고).

## 1. 절차 — red / green / refactor 3박자

"테스트 먼저, 코드 나중"은 두 박자로 들리지만 실은 세 박자다.

| 박자 | 하는 일 | 확인 |
|---|---|---|
| 🔴 red | 테스트를 쓴다. 코드가 없어 **일부러 실패** | 빨강이 떠야 정상 |
| 🟢 green | 통과하는 **최소한의** 코드 | 초록 |
| 🔧 refactor | 동작 그대로 두고 정리 | 여전히 초록 |

- **green은 최소한만**: 예쁘게·완벽하게 만들려 하지 말고 테스트가 초록 되는 딱 그만큼.
  완벽주의는 refactor에서. 순서를 지키는 게 핵심.
- **refactor는 항상 하는 게 아니다**: 정리할 게 있을 때만. 코드가 짧고 한 가지 일만
  하며 중복이 없으면 생략이 옳다 — 안 깨진 걸 건드리는 게 더 위험 (사례: D-day 함수는
  10줄이라 refactor 생략, "정리할 것 없음"도 판단이다). refactor의 값은 코드가 클수록 커짐.

## 2. red의 함정 — "진짜 빨강" vs "가짜 빨강"

테스트를 썼는데 **함수 파일이 없으면** import 오류가 나서 테스트가 **실행조차 안 된다.**
이건 "실패"가 아니라 "못 돌림"이다. 화면상 비슷해 보여 헷갈린다.

→ **스텁을 먼저 만든다.** 스텁 = 존재하지만 아직 동작 안 하는 껍데기:

```js
export function calculateDday(deadline, today) {
  return null   // 스텁 — 아직 아무것도 안 함
}
```

이러면 함수가 존재하니 테스트가 **실행되고**, null을 뱉으니 **제대로 실패(빨강)**한다.
이게 "진짜 빨강"이다.

**빨강 읽는 법**: `Expected: "D-3" / Received: null` — 이 차이가 다음에 뭘 만들지
알려주는 지도다. 스텁이 우연히 정답인 케이스(빈 값→null)는 red에서도 초록일 수 있는데,
green 후에도 그 초록이 유지되는지 확인해야 진짜 통과.

---

## 3. 스펙 = 테스트 = 완료 기준 (한 몸이다)

코드 짜기 전에 "이 입력엔 이 출력"을 표로 정하는 것 = TDD의 첫 단계.
그 표가 그대로 테스트 코드가 되고, 그게 곧 "다 됐다"의 기준이 된다.

**사례** (D-day 계산 시나리오 표 → 테스트 4개):

| 입력 (deadline, today) | 기대 출력 |
|---|---|
| 미래 마감 | "D-3" |
| 오늘 마감 | "오늘 12시 마감" |
| 마감 지남 | "마감 지남" |
| deadline 빈 값 | null |

- **우선순위가 코드 순서가 된다**: 분기 순서를 스펙에서 정해두면 그대로 구현. done을
  맨 위에서 걸러야 완료된 항목이 날짜 계산에 도달하지 않는 식.
- 스펙 표를 만드는 대화 자체가 이미 TDD를 하고 있는 것 — "코드 전에 완료 기준을 못 박는"
  그 행위.

---

## 4. 계약 우선 — 함수 시그니처를 먼저 정한다

무엇을 받고 무엇을 반환하는지(계약)를 구현 전에 확정한다. 계약이 흔들리면 테스트도
흔들린다.

- **기준값은 인자로 받는다**: `calculateDday(deadline, today)`처럼 "오늘"을 밖에서 주입.
  함수 안에서 `new Date()`를 부르면 **테스트가 "오늘"을 조종할 수 없어 내일 저절로 깨진다.**
- **테스트는 기준값 고정, 앱은 실제값**: 같은 함수에 테스트는 `new Date('2026-07-27...')`
  고정값을, 앱은 `new Date()` 진짜 오늘을 넘긴다. **한 함수, 다른 입력.** "날짜 바뀌면
  알아서 계산"이 앱에서 실제로 작동하는지는 눈으로 확인(어제 D-3 → 오늘 D-2로 저절로 바뀜).
- **한 함수는 한 가지 일만**: done 판정 같은 별개 관심사는 함수에 넣지 말고 호출부에서
  처리 (`done ? '완료 ✓' : calculateDday(...)`). 함수는 날짜 계산만.
- **시그니처를 바꾸면 기존 테스트도 같이 고친다**: 입력 형식을 문자열→Date로 바꾸면
  기존 테스트 전부 그에 맞춰 수정. 안 그러면 옛 계약으로 검사하게 됨.

## 5. 함정 모음 (성장 기록 — 실전에서 밟은 것)

- **환경 의존 테스트 금지**: 시간대 버그를 재현하려 `vi.stubEnv('TZ', 'UTC')`를 썼더니,
  Windows에서 unstub이 다음 테스트로 새어 멀쩡하던 테스트까지 오염됐다. → **환경을
  조작해 재현하지 말고 값 자체로 재현한다.** 환경 의존 테스트는 OS·시간대 따라 결과가
  흔들려 회귀 방지 도구로서 못 믿는다. "테스트가 틀리면 그 위의 모든 확인이 틀린다."

- **버그 감시보다 버그 불가능 구조**: 새벽에 날짜가 밀리는 버그의 진범은 `toISOString()`의
  UTC 변환(문자열 왕복)이었다. "밀림을 감시하는 테스트를 추가"하는 대신 **왕복 자체를
  없애(Date 객체 유지) 버그가 생길 여지를 제거**했다. 그러면 감시 테스트도 불필요해진다.
  → 증상을 지키는 것보다 원인을 없애는 게 한 수 위.

- **화면에 안 보이는 버그를 테스트가 대낮에 잡는다**: 시간대 버그는 오후엔 정상 동작해
  눈으로 안 보였다. TZ를 조작한 테스트가 그걸 재현해 존재를 증명했다. → 눈 검증만으로는
  "지금 이 환경에서 우연히 되는 것"과 "항상 되는 것"을 구별 못 한다.

- **테스트 초록 ≠ 코드 깨끗**: green 후 죽은 줄(안 쓰는 변수·중복 가드)이 남아도 결과만
  맞으면 초록이 뜬다. 함수를 화면에 붙이기 직전 파일 전문을 확인해 죽은 줄을 정리한다.

## 6. checklist에 적용하는 리듬

1. 항목 착수 → **§0으로 검증 방식 판별** (TDD / 눈 / 그냥 확인)
2. TDD 대상이면: 스펙 표 작성(§3) → red(스텁+테스트, §2) → green(최소 구현) → refactor(필요시만)
3. 화면 연결 등 눈 검증 부분은 별도로 처리 (자동 테스트 아님)
4. 항목 완료 → checklist 체크 → 커밋 (작은 단위마다)
5. 새 함정·원칙을 겪으면 이 스킬 §5에 추가

- **에이전트에게 지시할 때 "red까지만" 못 박기**: 안 그러면 빨강 보고 바로 green까지
  달려가 학습 포인트(빨강 눈으로 보기)를 건너뛴다. 단계마다 멈추고 승인받는다.
- **검증 방식이 다른 부분은 커밋도 나눈다**: TDD 결과물(함수+테스트)과 화면 연결은
  성격이 달라 별도 커밋. 히스토리에서 "무엇을 어떻게 검증했는지"가 갈려 읽힌다.
