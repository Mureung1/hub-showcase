# Feature Slice Planner

요구사항을 사용자에게 검증 가능한 세로 조각으로 나누고 실행 순서를 정한다.

## 입력 확인

1. 목표 문서, 현재 구현, 기존 이슈를 먼저 확인한다.
2. 금요일 또는 마감 시점에 시연할 핵심 사용자 시나리오를 한 문장으로 쓴다.
3. 명시되지 않은 제약은 합리적으로 가정하되 결과에 가정을 기록한다.

## 작업 분해

1. 기술 계층별 작업보다 사용자에게 보이는 end-to-end 조각을 우선한다.
2. 각 작업을 한 사람이 하루 안에 끝낼 크기(S: 반나절, M: 1~2일)로 제한한다.
3. M이 2일을 넘거나 완료 기준이 둘 이상의 독립 결과를 요구하면 다시 나눈다.
4. 조사 위험이 큰 작업은 짧은 스파이크와 구현 작업으로 분리한다.
5. 문서·테스트·예외 처리를 마지막에 몰지 말고 관련 기능의 완료 기준에 포함한다.

## 우선순위와 순서

- P0: 핵심 시나리오나 데모를 막는 작업. 한 주에 2~3개만 둔다.
- P1: 품질과 회귀 안전망에 중요하지만 P0 이후 수행할 작업.
- P2: 문서 보강이나 여유 시 개선. 밀려도 핵심 시나리오는 동작해야 한다.
- 불확실성과 의존성이 큰 작업을 앞에 두고, 각 작업의 선행 이슈를 명시한다.
- 매일 독립적으로 확인할 수 있는 결과가 남도록 요일에 배치한다.

## 완료 기준 작성

각 이슈에 다음 항목을 포함한다.

- 배경: 왜 필요한지 1~2문장
- 작업: 구현 범위를 체크리스트로 작성
- 완료 기준: 명령, 화면, 응답 또는 테스트로 관찰 가능한 조건 2~4개
- 제외 범위: 이번 이슈에서 하지 않을 것
- 메타데이터: 우선순위, 크기, 일정, 선행 이슈

"구현 완료", "정상 동작"처럼 검증할 수 없는 표현은 사용하지 않는다.

## 출력 형식

다음 순서로 결과를 낸다.

1. 주간 목표와 금요일 데모 시나리오
2. 순서·요일·우선순위·크기·의존성·완료 기준 요약표
3. GitHub 이슈별 제목과 본문
4. 범위 초과 시 가장 먼저 미룰 항목
5. 원래 계획과 비교한 누락·중복·순서 변경 제안

## 계획 점검

계획을 검토할 때 다음을 확인한다.

- P0가 3개를 넘지 않는가
- 모든 Must-Finish 목표가 적어도 한 이슈의 완료 기준에 연결되는가
- 선행 작업이 후행 작업보다 먼저 배치됐는가
- 각 작업이 하루 단위로 점검 가능한가
- 실패·키 없음·타임아웃 같은 핵심 예외가 포함됐는가
- 마지막 날에 통합 위험이 집중되지 않았는가
