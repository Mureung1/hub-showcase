# 제출 전 최종 점검 스킬

새 기능을 추가하는 게 아니라, 이미 만든 게 실제로 심사자 앞에서 문제없이 보여지는지 확인하는 절차. 코드 리뷰나 테스트만으로는 안 잡히는 "배포 URL이 실제로 뜨는지", "문서가 실제 기능과 다른 말을 하고 있지 않은지"를 훑는다.

## 절차

### 1. 라이브 URL 점검
`README.md`에 적힌 데모 링크를 그대로 실제로 쳐본다.

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://kimsunho2000.github.io/hub/
curl -s https://firstpr-backend.onrender.com/health
```

백엔드가 잠들어 있었다면 첫 응답이 느릴 수 있다(Render 무료 플랜 콜드 스타트) — 실패가 아니라 재시도로 판단한다. 가능하면 실제 GitHub ID로 `POST /api/analysis` 한 번을 배포 URL에 쳐서, 로컬이 아니라 배포 환경에서도 GitHub/DB 연결이 살아있는지까지 확인한다(`api-smoke-test`와 달리 여기선 로컬 서버를 새로 띄우지 않고 이미 떠 있는 배포 URL을 그대로 쓴다).

### 2. 문서 정합성 점검
세 문서가 같은 이야기를 하는지 맞춰본다 — 어긋나면 코드가 아니라 문서를 실제 상태에 맞게 고친다(문서가 기능을 규정하는 게 아니라 기능을 설명하는 것이므로).

- `README.md`의 "주요 기능" 설명이 실제 화면 흐름과 일치하는지 (예: 실제로는 표시 전용인 걸 "필터링 가능"처럼 과장하지 않았는지)
- `docs/checklist.md`에 미완료(`- [ ]`)로 남은 항목이 있는지, 있다면 제출 시점에 괜찮은 공백인지
- `showcase/showcase.json`의 `screenshots`·`features`·`demoUrl`이 지금 코드/README와 다른 이야기를 하고 있지 않은지

```bash
grep -n "^- \[ \]" docs/checklist.md
```

### 3. 테스트 상태 점검
```bash
npm run test:backend
npm run test:e2e
```
둘 다 통과해야 한다. 실패하는 테스트가 있는데 "일단 제출"하지 않는다 — 심사 중에 똑같은 경로를 심사자가 밟으면 그대로 재현된다.

### 4. 커밋/브랜치 상태 점검
```bash
git status --short
git log origin/N034_김선호..HEAD --oneline   # 로컬에만 있고 원격에 없는 커밋
```
- `git status`가 깨끗한지(작업 중이던 변경이 커밋 안 된 채 남아있지 않은지)
- 로컬 커밋이 `N034_김선호`(대회 운영 브랜치, `main` 아님)에 푸시됐는지
- dev→main 반영이 하루 1회 규칙대로 되고 있는지(`docs/log.md` 최근 항목의 "다음 할 일"에 미반영으로 남아있지 않은지)

## 산출물

네 항목을 각각 통과/미흡으로 짧게 보고한다. 미흡한 게 있으면 "무엇이 왜 안 됐는지"만 말하고, 고칠지 말지는 사용자에게 확인받는다 — 이 스킬 자체는 점검이지 자동 수정이 아니다.

## 하지 말 것
- 배포 URL 점검을 위해 로컬 서버를 새로 띄우기 (`api-smoke-test`의 역할이지 이 스킬의 역할이 아니다)
- 미흡한 항목을 발견했다고 바로 코드/문서를 고치기 시작하기 (점검 결과를 먼저 보고하고 확인받는다)
- 콜드 스타트로 인한 첫 요청 지연을 장애로 오판하기
