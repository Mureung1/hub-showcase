# 작업 흐름

"무엇을 만드나"가 아니라 **"어떤 순서로 만드나"** 를 정한다.

```
설계 → 이슈 등록
   └─ 이슈마다:  구현 → 검증 → 코드 리뷰 → 커밋
기능 완료 → 기능 리뷰 → 머지
```

## 0. 작업 시작 전

**브랜치를 먼저 확인한다.** `work`에서 분기하고, 분기 전에는 파일을 고치지 않는다.
브랜치 이름과 분기 규칙은 `commit-convention` 을 따른다.

## 1. 설계 — 플랜 모드

코드를 쓰기 전에 플랜 모드로 끝낸다.
먼저 `docs/product/` 에서 이번 기능에 해당하는 부분을 읽는다 — 사용자 시나리오 · PRD · 와이어프레임 · ERD · API 명세.

**무엇을 정하나** (기능에 따라 더 정할 수 있다)

- **화면** — 무엇이 보이고, 무엇이 안 보이는가
- **데이터** — 어떤 값이 어디서 오는가 (DB · 외부 API · 계산)
- **예외** — 값이 없을 때 · 외부 API가 실패할 때 · 권한이 없을 때 각각 어떻게 되는가
- **경계** — 이번 작업에 **넣지 않을 것**
- **단위** — 어떤 순서로 쪼개고, 각 조각이 혼자서도 말이 되는가

**무엇을 남기나**

- 정한 것은 **이슈로 등록한다.** 이슈 하나 = 커밋 하나 = 코드 리뷰 하나.
  **브랜치 하나 = 기능 하나** — 브랜치 안에서 이슈를 차례로 끝내고, 다 끝나면 기능 리뷰를 거쳐 머지한다.
- 고른 안뿐 아니라 **버린 안과 버린 이유**도 적는다.
- 정의 문서를 고쳐야 할 것이 나오면 코드보다 **그 문서를 먼저 고친다.**

## 2. 구현

| 영역 | 누가 쓰나 | 참조 | 테스트 |
|---|---|---|---|
| 백엔드 | 사람 | `chasewar-backend` | 코드와 **같은 작업에서** 만든다 |
| 프론트엔드 | 에이전트가 쓰고 사람이 읽는다 | `chasewar-design` | 인프라 도입 전 — 사람이 화면으로 확인 |

- 테스트를 **나중으로 미루지 않는다.** 미룬 테스트는 결국 안 쓴다.
- 에이전트에게 맡긴 코드는 **근거를 주석으로 남기게 하고 읽는다.** 읽지 않고 넘긴 코드는 다음에 고칠 사람이 없다.
- 설계와 다르게 짜야 할 이유가 생기면 → [막혔을 때](#막혔을-때)

## 3. 검증 — 통과해야 다음으로 간다

```bash
cd backend && ./gradlew build     # 테스트 포함
cd frontend && npm run build
```

- **여기를 못 넘으면 리뷰를 요청하지 않는다.**
- 테스트는 통과하는데 동작이 이상하면 테스트가 부족한 것이다. 테스트를 먼저 고친다.

## 4 ~ 6. 코드 리뷰 · 커밋 · 기능 완료

| 단계 | 언제 | 기준 |
|---|---|---|
| 코드 리뷰 | 검증을 통과한 뒤 | `code-review` |
| 커밋 | 코드 리뷰 결과를 반영한 뒤 | `commit-convention` |
| 기능 리뷰 | 이슈가 아니라 **기능 전체가** 끝났을 때 | `feature-review` |

## 흐름을 줄여도 되는 때

| 상황 | 밟는 단계 |
|---|---|
| 오타 · 문구 · 주석 · 문서만 고칠 때 | 브랜치 → 구현 → 검증 → 커밋 (설계 · 리뷰 생략) |
| 운영 장애 대응 | 먼저 고쳐 배포하고, 커밋에 이유를 남긴 뒤 **사후 리뷰** |
| 그 밖의 모든 기능 작업 | 전부 |

- **검증은 어떤 경우에도 생략하지 않는다.**
- 줄일지 애매하면 줄이지 않는다.

## 막혔을 때

| 상황 | 어떻게 하나 |
|---|---|
| 짜다 보니 설계가 틀렸다 | 코드로 우회하지 말고 **플랜으로 돌아가 고친다.** 고친 내용은 이슈에 남긴다 |
| 작업이 예상보다 커졌다 | 지금 조각을 마무리해 커밋하고 **남은 것은 새 이슈로 뗀다** |
| 리뷰 제안에 동의가 안 된다 | **결정은 코드를 쓴 사람이 한다.** 반영하지 않은 이유를 남긴다 |
| 규칙이 현실과 안 맞는다 | 한 번은 규칙대로 간다. 두 번 이상 걸리면 **규칙을 고치는 작업을 따로 만든다** |

## 하지 말 것

- 이슈 여러 개를 한 브랜치에서 진행하기
- 한 커밋에 여러 종류의 변경 섞기
- 예외를 만들고 이유를 안 남기기 — 남기지 않은 예외는 다음 사람에게 규칙으로 보인다
