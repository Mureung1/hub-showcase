이 스킬은 이 프로젝트에서 하루에도 여러 번 반복된 요청 — "이 흐름 다시 확인해보고 빠진 연결이나 어색한 구조 없는지 체크해줘", "전체 워크플로우 테스트하는데 에러 나는 부분만 찾지 말고 어색한 구조나 유지보수 개선점도 봐줘" — 를 고정해둔 것이다. 기능 하나를 막 끝냈을 때든, 여러 기능을 다 만들고 전체를 다시 훑을 때든 같은 방식으로 적용한다.

## 무엇이 다른가 — 에러 체크와 이 리뷰의 차이

일반적인 검증(lint·테스트·curl로 API 응답 확인)은 "코드가 틀렸는가"만 본다. 이 스킬은 그 위에 두 가지를 추가로 본다:

1. **연결이 빠지거나 어색한 지점** — 화면 A에서 화면 B로 넘어갈 때, 또는 한 컴포넌트의 상태가 다른 이벤트(라우트 이동·다른 데이터 갱신)와 맞물릴 때 암묵적으로 기대는 전제가 실제로 항상 성립하는지. 예: "이 컴포넌트는 항상 새로 마운트될 것"이라는 전제가 깨지는 경로가 새로 생기지 않았는지.
2. **유지보수 개선 여지** — 같은 상수·같은 패턴이 여러 파일에 중복 정의돼 있는지, 파일 하나가 여러 관심사를 떠안고 있는지. 다만 CLAUDE.md의 "요청 범위 밖 리팩토링 금지" 원칙은 그대로 적용한다 — 발견만 보고하고, 사용자가 고치라고 하기 전엔 먼저 손대지 않는다.

## 진행 순서

1. 사용자가 지정한 흐름(하나의 기능이든 여러 화면을 잇는 전체 여정이든)을 처음부터 끝까지 코드로 따라간다. 화면 이동이 있는 지점마다 "이 컴포넌트가 다시 마운트되는가, 아니면 같은 인스턴스가 props/state만 갱신되는가"를 구분해서 추적한다 — 이 둘을 구분하지 않으면 로컬 state가 리마운트 시에만 초기화된다는 사실을 놓친다.
2. 가능하면 실제로 서버·DB에 직접 요청을 보내 확인한다(curl, Prisma 직접 조회). 브라우저 도구가 없는 세션이면 이 방식으로 화면→서버→DB 연결을 검증하고, 브라우저 렌더링 자체는 못 확인했다고 명시한다(직접 본 것만 단정).
3. 화면 사이를 잇는 지점(라우트 전환, 부모-자식 간 state 소유권, 여러 화면이 같은 훅을 각자 호출하는 경우 등)을 하나씩 짚어보며, 그 지점에서 실제로 어색한 동작이 나오는 구체적인 시나리오를 하나 만들어본다 — "이럴 수도 있다"가 아니라 "이렇게 하면 이런 문제가 생긴다"까지 구체화한다.
4. 같은 상수·같은 문구 생성 로직이 몇 개 파일에 중복돼 있는지 grep으로 확인한다.

## 보고 형식

세 갈래로 나눠 보고한다 — 뭉뚱그리지 않는다.

- **① 진짜 발견한 구조적 문제**: 구체적 시나리오("A를 하고 B로 갔다가 C로 돌아오면 D가 발생한다")로 설명하고, 고칠 수 있는지와 고치는 데 드는 비용(작은 수정인지, 새 인프라가 필요한지)을 같이 밝힌다.
- **② 유지보수 개선 제안**: 급하지 않은 것들. 왜 지금 당장 문제는 아닌지도 짧게 밝힌다.
- **③ 잘 이어진 부분**: 의도한 대로 자연스럽게 맞물린 지점이 있으면 짧게라도 언급한다 — 전부 문제만 나열하면 리뷰가 아니라 트집잡기가 된다.

## 보고 후

발견한 것을 바로 고치지 않는다. 어떤 항목을 지금 고칠지, 어떤 건 알려진 한계로 남길지 사용자에게 확인받은 뒤에만 수정에 들어간다.
