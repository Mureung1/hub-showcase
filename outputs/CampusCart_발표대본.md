# CampusCart 2주차 데모 발표 대본

예상 발표 시간: 약 7분

## 1. 표지 — 25초

안녕하세요. 캠퍼스 공동구매 서비스 **CampusCart**를 만든 이시우입니다.  
CampusCart는 필요한 물건을 함께 사는 것에서 끝나지 않고, 참여자들의 위치를 바탕으로 모두에게 가까운 공동 수령지를 정하는 서비스입니다. 오늘은 문제 정의, 구현한 수직슬라이스, 실제 화면, 그리고 기능 검증 결과 순서로 보여드리겠습니다.

## 2. 문제 — 35초

공동구매는 가격은 저렴하지만 조율 비용이 큽니다. 몇 개를 살지, 배송비를 어떻게 나눌지 매번 계산해야 하고, 개설자와 참여자의 권한이 섞이면 신뢰가 흔들립니다. 특히 한 사람이 임의로 정한 수령 장소는 다른 참여자에게 불공평할 수 있습니다. 그래서 이번 주에는 단순 구매 목록보다, **참여 이후의 의사결정 흐름**을 핵심 문제로 잡았습니다.

## 3. 핵심 흐름 — 40초

사용자는 모집 상세를 확인하고 수량을 선택합니다. 그러면 예상 결제 금액이 바로 계산되고, 참여할 때 자신의 출발 위치도 함께 저장됩니다. 서버는 모든 참여자의 위치로 수령지 후보를 다시 계산합니다. 모집이 끝나면 참여자만 한 표를 행사하고, 개설자가 최종 장소를 확정해야 다음 단계로 넘어갑니다. 즉, 화면에서 시작한 선택이 서버 상태와 다음 화면에 계속 이어지는 한 바퀴를 완성했습니다.

## 4. 구조 — 40초

프론트엔드는 React와 Vite, 서버는 Express와 Zod 기반 REST API로 구성했습니다. 화면에서 참여 요청을 보내면 서버가 데이터를 저장하고 후보를 재계산한 뒤, 상세 조회 결과에 반영합니다. 현재 발표 환경은 연결 안정성을 위해 로컬 메모리 저장소를 사용합니다. Supabase 영속화와 Auth, RLS는 다음 단계로 분리했으며, 오늘 구현했다고 과장하지 않겠습니다.

## 5. 데모 1: 홈과 모집 탐색 — 40초

[화면 전환: 홈] 먼저 홈에서는 서비스의 가치와 현재 모집 현황을 확인할 수 있습니다.  
[화면 전환: 공동구매] 공동구매 페이지에서는 다른 사람이 만든 모집을 탐색하고 상세로 들어갑니다. 다른 사람의 모집이기 때문에 참여자는 수정이나 삭제를 할 수 없고, 탐색과 참여만 가능합니다. 개설자 전용 동작은 서버 권한 검사로도 막았습니다.

## 6. 데모 2: 참여와 금액 계산 — 55초

[화면 전환: 상세] 이 화면이 이번 주의 핵심 수직슬라이스입니다. 사용자가 수량을 고르면 상품 금액과 배송비 분담액을 합산해 예상 금액을 즉시 보여줍니다. 참여 버튼을 누르면 수량과 출발 위치가 `POST /join` 요청으로 저장됩니다. 같은 사용자가 다시 참여하면 서버가 409로 차단합니다. 참여 결과는 인원과 진행 상태에 바로 반영되므로, 요청부터 저장, 재조회, 화면 변경까지 실제로 연결되어 있습니다.

## 7. 데모 3: 공동 수령지 계산 — 50초

[화면 전환: 수령 장소] 처음에는 수령 장소를 네 곳으로 고정했지만, 사용자 피드백을 반영해 구조를 바꿨습니다. 각 참여자가 출발 위치를 제출하면, 서버가 후보별 이동 거리의 합을 참여자 수로 나눈 평균 이동 점수를 계산합니다. 점수가 낮은 상위 세 곳을 추천하고, 참여 위치가 바뀌면 후보도 다시 계산됩니다. 지금은 데모용 좌표를 사용하고 있으며, 다음 단계에서 실제 캠퍼스 좌표와 지도 API를 연결할 예정입니다.

## 8. 서버 제약 조건 — 45초

화면 버튼을 숨기는 것만으로는 규칙을 지킬 수 없기 때문에 핵심 제약은 서버에서 검사했습니다. 남이 만든 모집의 수정과 삭제는 403, 중복 참여는 409로 막습니다. 투표는 참여자만 한 표를 행사할 수 있고, 후보를 바꾸면 이전 표를 감소시키고 새 후보에 반영합니다. 마지막으로 수령 장소가 확정되기 전에는 결제 대기 단계로 넘어갈 수 없습니다.

## 9. 시행착오 — 45초

초기 버전은 고정된 네 장소를 보여주고 누구나 반복 투표할 수 있었으며, 다른 사람 모집에도 수정과 삭제가 노출됐습니다. 기능은 있었지만 서비스 규칙이 없었던 셈입니다. 이를 참여자 위치 기반 재계산, 사용자별 한 표, 개설자만 최종 확정하는 흐름으로 다시 설계했습니다. 화면의 역할 구분을 서버 제약으로 옮긴 것이 이번 주 가장 큰 개선입니다.

## 10. 기능 검증 Agent — 45초

구현 후에는 기능 검증 Agent를 통해 요구사항, 실행 QA, 코드 품질, 보안, 기존 맥락의 다섯 관점으로 다시 점검했습니다. 참여 위치를 바꾸면 후보가 달라지는지, 중복 참여가 409인지, 비참여자 투표가 403인지 확인했습니다. 투표 변경 시 기존 표가 빠지는 것과, 장소 확정 전 단계 전환이 차단되는 것도 실제 API로 검증했습니다. 최종 확정 뒤에는 장소가 저장되고 다음 단계로 정상 전환됩니다.

## 11. 마무리 — 35초

정리하면 Express REST CRUD, 화면에서 서버까지 이어지는 첫 수직슬라이스, 그리고 기능 검증 Agent까지는 완성했습니다. 다만 오늘 목표 중 Supabase 영속화는 아직 남아 있습니다. 다음 주에는 Supabase Auth와 RLS, DB 트랜잭션을 붙이고 실제 캠퍼스 좌표와 연동해 새로고침과 재시작 이후에도 동일한 상태가 유지되도록 만들겠습니다. 이상으로 발표를 마치겠습니다. 감사합니다.

## 라이브 데모 순서

1. `/`에서 서비스 소개와 모집 현황 확인
2. `/group-buys`에서 다른 사람의 모집 선택
3. 상세에서 수량 변경 → 예상 금액 변화 확인
4. 출발 위치와 함께 참여 → 참여 인원 변화 확인
5. `/pickup`에서 추천 후보와 평균 거리 확인
6. 모집 마감 상태에서 투표 변경 → 득표 변화 확인
7. 개설자로 최종 수령지 확정 → 다음 단계 전환 확인

## 발표 전 체크리스트

- 프론트엔드와 데모 API 서버를 모두 실행합니다.
- 홈, 공동구매, 상세, 수령 장소 페이지를 각각 새로고침해 둡니다.
- 데모용 사용자와 개설자 사용자를 구분해 둡니다.
- 참여와 투표를 반복할 경우 서버를 재시작해 초기 상태로 복원합니다.
- Supabase는 현재 미연결이며 다음 단계라는 점을 일관되게 설명합니다.
