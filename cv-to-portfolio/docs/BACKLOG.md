## 백로그란?

- **무엇:** 해야 할 일을 **우선순위 순으로 줄 세운 단일 목록**. 스프린트/주차 계획은 이 목록의 맨 위에서 꺼내 간다.
- **왜 필요:** 개발 중 "지금 이걸 해도 되나?"가 생길 때마다 기준이 되어 **흔들리지 않게** 해준다. 새 아이디어는 일단 백로그에 넣고, 지금 하던 일을 지킨다.
- **어떻게 생겼나:** 항목마다 *제목 · 우선순위 · 크기 · 완료 기준(무엇을 보여주면 끝인가)*. 완료 기준이 없으면 스코프가 무한정 늘어난다.
- **어떻게 관리:** ① 추가는 자유롭게, **정렬은 주 1회**(금요일 회고 후) ② 주차에 배정 안 된 항목은 [미배정 백로그](#미배정-백로그)에 둔다 ③ 완료는 체크 표시 + 커밋/PR 링크.

## 규약

| 표기 | 의미 |
| --- | --- |
| **P0** | 이번 주에 반드시 (데모가 이것에 걸림) |
| **P1** | 중요 — P0 다음, 밀리면 다음 주 최우선 |
| **P2** | 여유 시 — 상시 컷 대상 |
| **S / M / L** | 반나절 / 1~2일 / 3일+ |

**원칙:** 1인 주니어 기준 주당 P0는 2~3개까지만. 매주 금요일 데모에서 "새로 보여줄 것"이 나와야 한다. 결정적 렌더러는 항상 폴백으로 유지 — 어떤 주에도 "보여줄 게 없는" 상황을 만들지 않는다.

## 계획 판단 근거 (요약)

3개 관점(제품 완성도 / 기술 리스크 / 학습·데모)으로 각각 계획을 세운 뒤 합성했다.

1. **LLM 연결을 2주차로 앞당김** — 가장 불확실한 통합을 먼저 뚫어 실패를 일찍 발견(리스크 관점). 품질 우려는 같은 주의 **자동 폴백 P0**로 상쇄해 데모 하한선을 보장. 서버 seam이 이미 스캐폴드되어 있어 착수 비용도 낮음.
2. **테스트 안전망을 2주차에 부트스트랩** — 이후 견고화 작업 전체의 회귀 안전망을 초반에 깐다(제품 관점 채택).
3. **파서 견고화는 3주차 P0** — 제품의 심장이지만, 더 불확실한 통합에 첫 주를 양보. 완료 기준을 "샘플 세트 통과 + 테스트 케이스화"로 못박아 스코프 무한 확장 차단.
4. **PDF는 4주차 + day1 스파이크 게이팅** — 추출 품질을 먼저 판정하고, 저품질이면 진단 UI로 축소.
5. **배포는 이원화** — 정적 클라이언트 배포를 P0 하한선으로, 서버(AI) 배포는 P1 선택으로. 최악의 경우에도 최종 데모가 성립.
