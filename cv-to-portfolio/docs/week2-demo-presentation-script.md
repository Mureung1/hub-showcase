## 1. 표지 — CV를 바로 포트폴리오로

안녕하세요. N123 이규민입니다.

제가 만들고 있는 서비스는 CV를 바로 웹 포트폴리오로 변환해 주는 **CV2PF**입니다.

1주차에는 CV를 입력하고 디자인을 선택하면 결과 화면이 만들어지는 프로토타입을 구현했습니다.
이번 2주차에는 화면에서 끝나지 않고, 생성한 결과를 실제 서버와 데이터베이스에 저장한 뒤 다시
불러오는 첫 번째 수직 슬라이스를 완성했습니다.

오늘은 사용자의 저장 요청이 React, Express, Supabase를 거쳐 다시 화면 변화로 돌아오는 과정을
보여드리겠습니다.

**전환 멘트:** 먼저 이번 주에 해결하려고 했던 문제부터 설명하겠습니다.

## 2. 이번 주 목표 — 데이터가 돌아오는 것까지

지난주 화면은 동작했지만, 새로고침하면 생성 결과가 사라졌습니다. 화면만으로는 서버와 DB가
실제로 연결되었는지도 증명하기 어려웠습니다.

그래서 이번 주 목표를 **화면뿐만 아니라 데이터가 돌아오는 것까지**로 정했습니다.

완료 기준은 명확했습니다. 사용자가 저장 버튼을 누르면 결과가 DB의 한 행으로 저장되고, 저장된
HTML을 다시 조회했을 때 화면의 미리보기가 실제로 바뀌어야 했습니다.

즉, 단순히 API 파일을 만드는 것이 아니라 사용자 화면에서 시작해 사용자 화면으로 끝나는 한
바퀴를 완성하는 것이 목표였습니다.

**전환 멘트:** 사용자가 경험하는 흐름으로 보면 총 네 단계입니다.

## 3. 사용자 흐름 — 네 단계

첫 번째는 **결과 생성**입니다. 사용자가 CV와 디자인을 선택하면 독립적으로 실행할 수 있는
포트폴리오 HTML을 만듭니다.

두 번째는 **현재 결과 저장**입니다. React가 생성된 HTML과 제목, 디자인 정보를 Express API로
보냅니다.

세 번째는 **목록 즉시 갱신**입니다. Supabase 저장이 성공하면 응답으로 받은 데이터를 React
state에 반영해서 최근 기록 목록을 바로 바꿉니다.

네 번째는 **DB 결과 다시 보기**입니다. 사용자가 저장 기록의 불러오기 버튼을 누르면 상세 API로
HTML을 조회하고 iframe 미리보기를 그 HTML로 교체합니다.

이 네 단계가 끊기지 않고 이어지는 것을 이번 주 핵심 시나리오로 잡았습니다.

**전환 멘트:** 이제 이 흐름이 내부에서 어떻게 연결되는지 보겠습니다.

## 4. 실제 동작 구조 — React, Express, Supabase

**[화면의 구조 이미지를 왼쪽부터 오른쪽으로 가리킨다.]**

먼저 React 화면에서 사용자가 현재 결과 저장을 누릅니다. React는 생성된 HTML과 제목, 테마를
`POST /api/portfolios`로 전송합니다.

Express는 요청 본문에 필요한 값이 있는지 검증하고, 문제가 없으면 Supabase REST API를
호출합니다.

Supabase는 `portfolios` 테이블에 HTML과 메타데이터를 영구 저장합니다. 저장이 완료되면
Express가 `201` 응답과 저장된 포트폴리오 정보를 React에 돌려줍니다.

React는 이 응답으로 목록 state를 갱신합니다. 이후 불러오기를 누르면 상세 조회를 통해 저장된
HTML을 받아 iframe을 변경합니다.

여기서 중요한 보안 경계가 하나 있습니다. 브라우저가 Supabase를 직접 호출하지 않도록 했습니다.
Supabase secret key는 Express의 환경변수에서만 관리하고 브라우저 번들에는 포함하지 않았습니다.

**전환 멘트:** 이 구조가 실제 페이지에서는 다음과 같이 보입니다.

## 5. 실제 페이지 데모 — 저장하고 다시 불러오기

**[실제 페이지 화면의 포트폴리오 결과 영역을 가리킨다.]**

이 화면은 실제로 구현한 React 결과 페이지입니다. 먼저 위쪽에서 생성된 포트폴리오 HTML을
확인할 수 있습니다.

**[현재 결과 저장 버튼을 가리킨다.]**

현재 결과 저장 버튼을 누르면 React가 Express로 저장 요청을 보냅니다. 저장 중에는 버튼과 안내
문구로 상태를 보여주고, 성공하면 저장 완료 메시지와 최근 기록이 나타납니다.

**[최근 포트폴리오와 불러오기 버튼을 가리킨다.]**

저장된 항목의 불러오기를 누르면 DB에 저장된 상세 HTML을 다시 가져와 위쪽 미리보기를
교체합니다.

따라서 이 화면 한 곳에서 결과 확인, 저장, 저장 기록 조회까지 전체 흐름을 확인할 수 있습니다.

**전환 멘트:** 다음 화면은 이 동작이 실제 Supabase와 연결되었다는 실행 결과입니다.

## 6. 실제 Supabase 저장·조회 증거

저장 전 최근 포트폴리오 목록은 0개였습니다. 현재 결과 저장을 실행한 뒤 목록이 1개로
증가했습니다.

서버는 저장 성공을 의미하는 HTTP 상태 코드 `201`을 반환했습니다. 그리고 상세 조회 API로
해당 기록을 다시 요청했을 때 원본 HTML이 포함된 것을 확인했습니다.

중요한 점은 숫자만 증가한 것이 아니라, 불러오기를 눌렀을 때 조회한 HTML로 실제 iframe 내용이
바뀌었다는 것입니다.

즉, React에서 요청을 보내고 Express가 처리한 뒤 Supabase에 저장하고, 다시 조회해서 화면을
변경하는 수직 슬라이스가 실제 환경에서 동작했습니다.

**전환 멘트:** 이 화면 상태를 관리하면서 state와 props의 역할도 분리했습니다.

## 7. React 패턴 — state와 props

왼쪽의 `PortfolioLibrary`는 부모 컴포넌트입니다. 최근 포트폴리오 목록, 검색어, 디자인 필터와
같이 변경되는 값을 state로 소유합니다. 필터 결과를 계산하고 API 저장과 조회도 여기서
실행합니다.

오른쪽의 `PortfolioFilters`는 자식 컴포넌트입니다. 부모가 가진 현재 값을 props로 받아 화면에
표시합니다. 사용자가 검색어나 필터를 바꾸면 callback props를 통해 그 이벤트를 다시 부모에게
전달합니다.

정리하면 state는 변경되는 값의 주인이고, props는 부모와 자식 사이에서 값과 이벤트를 전달하는
통로입니다.

이 구조로 목록 상태의 주인을 한 곳에 두면서 필터 UI는 별도 컴포넌트로 재사용할 수 있게
했습니다.

**전환 멘트:** 마지막으로 이 기능을 어떤 기준으로 검증했는지 설명하겠습니다.

## 8. 기능 검증 — 실행 증거로 PASS 판정

기능 검증 Agent는 코드 파일이 존재하는지만 확인하지 않고, 각 계층을 실제로 실행한 증거를
확인하도록 만들었습니다.

프론트엔드는 mock 저장과 조회, 검색과 디자인 필터를 포함해 8개의 테스트를 통과했습니다.

백엔드는 정상 저장뿐 아니라 잘못된 요청과 데이터 없음, 외부 API 오류 같은 상태 코드까지 총
7개의 테스트로 확인했습니다.

DB는 하나의 `portfolios` 테이블과 migration, RLS 설정을 확인했고 실제 insert와 select도
실행했습니다.

마지막으로 브라우저에서 React에서 시작한 요청이 Express와 Supabase를 거쳐 다시 React 화면을
바꾸는 것을 확인해 최종 결과를 PASS로 판정했습니다.

**전환 멘트:** 이번 주 결과와 다음 작업을 정리하겠습니다.

## 발표 직전 체크

- HTML 슬라이드를 전체 화면으로 연다.
- 5번과 6번 슬라이드의 실제 화면 이미지가 정상 표시되는지 확인한다.
- 데모를 직접 실행한다면 프론트엔드와 Express 서버를 미리 실행한다.
- `현재 결과 저장`과 `불러오기` 버튼의 성공 상태를 미리 확인한다.
- 질문에 대비해 state와 props 차이, Express를 거치는 이유를 한 문장으로 연습한다.

## 예상 질문 한 문장 답변

**왜 Supabase를 브라우저에서 직접 호출하지 않았나요?**

Secret key 노출을 막고 입력 검증과 오류 처리를 Express 한 곳에서 관리하기 위해서입니다.

**state와 props의 차이는 무엇인가요?**

state는 변경되는 값의 주인이고, props는 부모와 자식 사이에서 값과 이벤트를 전달하는
통로입니다.

**목록 조회와 상세 조회를 나눈 이유는 무엇인가요?**

용량이 큰 HTML은 목록에서 제외하고 사용자가 불러온 한 건만 상세 조회해 응답 크기를 줄이기
위해서입니다.

**Agent는 무엇을 검증했나요?**

FE·BE·DB·통합 흐름을 나누고 자동 테스트, 실제 DB 저장·조회, 브라우저 화면 변화를 실행 증거로
확인했습니다.
