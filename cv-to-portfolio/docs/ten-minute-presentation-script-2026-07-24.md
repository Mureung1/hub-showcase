# CV2PF 10분 발표 대본

## 0:00–0:40 · 오프닝

안녕하세요. 제가 만든 CV2PF는 이력서 한 장을 지원 기업과 채용 공고에 맞는 포트폴리오
사이트로 바꿔 주는 서비스입니다.

지원할 때마다 회사가 보는 역량은 달라지지만, 매번 포트폴리오를 새로 편집하는 일은
시간이 많이 듭니다. CV2PF에서는 기업과 공고를 먼저 고르고, CV와 디자인을 선택하면
관련 경험이 잘 보이는 독립 실행형 HTML 포트폴리오를 만듭니다.

## 0:40–1:30 · 문제와 해결 가설

제가 해결하려 한 문제는 “경험이 없어서”가 아니라 “있는 경험을 지원처에 맞게 보여주기
어렵다”는 것입니다. 예를 들어 같은 프론트엔드 프로젝트라도 토스에는 문제를 주도적으로
발견하고 만든 제품 임팩트를, QANDA에는 테스트로 품질을 검증한 과정을 더 먼저 보여주는
편이 적절합니다.

그래서 생성보다 앞에 지원 기업과 JD를 선택하는 단계를 추가했습니다. 중요한 원칙도
정했습니다. AI가 이력서에 없는 경력이나 수치를 만들지 않고, 실제 경험의 순서와 표현만
바꾸도록 했습니다.

## 1:30–2:30 · 사용자 흐름

사용 흐름은 다섯 단계입니다. 첫째 기업과 채용 공고를 선택합니다. 둘째 CV를 붙여넣거나
샘플을 선택합니다. 셋째 여섯 가지 디자인 중 하나를 고릅니다. 넷째 AI가 지원 목표,
CV, 디자인 명세를 함께 분석해 HTML을 만듭니다. 마지막으로 결과를 미리 보고 내려받거나
Supabase에 저장합니다.

이 흐름은 React의 App 컴포넌트가 state로 관리합니다. 선택한 공고는 다음 단계로
props를 통해 전달되고, 생성 요청에서 `targetMarkdown`으로 변환됩니다.

## 2:30–3:30 · 아키텍처

구조를 한 바퀴 설명하겠습니다. 브라우저의 React에서 공고, CV, 디자인을 선택합니다.
React가 이 세 정보를 Express의 생성 API로 보냅니다. Express는 입력을 검증하고,
서버에만 보관한 API 키로 Anthropic에 요청합니다. 반환된 HTML은 iframe에서 바로
미리 볼 수 있습니다.

저장할 때는 다시 Express를 통해 Supabase의 portfolios 테이블에 HTML과 메타데이터를
넣습니다. 목록에서는 가벼운 정보만 조회하고, 사용자가 하나를 열 때 상세 HTML을 가져옵니다.
AI API가 실패해도 데모가 끊기지 않도록 브라우저의 로컬 렌더러가 HTML을 만드는 폴백도
두었습니다.

## 3:30–4:20 · 작업 과정

작업은 큰 기능을 한 번에 만들지 않고 작은 검증 단위로 나눴습니다. 먼저 기획서와
프로토타입으로 흐름을 확인했습니다. 다음으로 mock 데이터와 React state로 화면을
완성했습니다. 그 뒤 Express와 Supabase를 붙여 저장과 조회가 실제로 도는 수직 슬라이스를
만들었습니다.

또 즐겨찾기 토글은 실패하는 테스트를 먼저 쓰고 구현을 통과시키는 TDD로 만들었습니다.
Agent는 계획을 작업 단위로 나누고, 초기 화면 구조와 반복 검증을 돕는 역할로 사용했습니다.
세부 스타일이나 복잡한 상태 로직은 결과를 확인하면서 직접 수정했습니다.

## 4:20–7:10 · 라이브 데모

지금부터 실제 흐름을 보여드리겠습니다.

[화면: 기업·공고 선택]

현재 공식 채용 공고를 기준으로 프론트엔드 예시 다섯 개를 준비했습니다. 오늘은 QANDA
Frontend Engineer를 선택하겠습니다. 카드를 고르면 교육 임팩트, 문제 정의, 테스트 같은
인재상 키워드와 JD 핵심 업무가 보입니다. 오른쪽에는 포트폴리오에서 강조할 근거가
정리됩니다. 원문 링크와 확인일도 함께 제공해 사용자가 최신 공고를 다시 확인할 수 있습니다.

[화면: CV 입력]

다음으로 개발자 샘플 CV를 선택합니다. 마크다운 원문을 파싱해 이름, 직함, 기술, 경력,
프로젝트를 state로 관리합니다. 여기서 중요한 점은 생성기가 이 원문에 있는 사실만
사용한다는 것입니다.

[화면: 디자인 선택]

Minimal Clean 테마를 선택하겠습니다. 디자인은 색상만 바꾸는 것이 아니라 타이포,
레이아웃, 헤더 방식이 담긴 DESIGN.md 명세입니다.

[화면: 생성]

생성을 누르면 공고 분석, CV 분석, 디자인 전달, 서버 요청, HTML 검증 순서가 표시됩니다.
Express에는 지원 목표, CV, 디자인 세 가지 Markdown이 전달됩니다.

[화면: 결과]

결과 위에 QANDA Frontend Engineer 기준이라는 정보가 남고, 생성된 사이트를 iframe으로
확인할 수 있습니다. HTML 코드를 보거나 파일로 내려받을 수도 있습니다. 저장 버튼을 누르면
Supabase에 저장되고, 최근 포트폴리오 목록에서 다시 열 수 있습니다. 이 과정이 화면에서
요청하고 서버가 처리해 DB에 남긴 뒤 다시 화면에 보이는 수직 슬라이스입니다.

## 7:10–8:00 · 5개 기업 비교

예시를 모두 프론트엔드 직무로 맞춘 이유는 같은 CV에서 강조점이 어떻게 달라지는지
비교하기 위해서입니다.

토스는 주도성과 제품 임팩트, LINE Pay는 대규모 트래픽과 협업, Coupang Play는 멀티
플랫폼과 웹 성능, CLO Virtual Fashion은 시스템 설계와 글로벌 협업, QANDA는 문제 정의와
테스트를 중심으로 정리했습니다. 공고 내용을 복사해 포트폴리오에 붙이는 것이 아니라,
사용자의 실제 경험 중 어떤 근거를 먼저 보여줄지 결정하는 맥락으로 사용합니다.

## 8:00–8:40 · 검증과 한계

이 기능은 공고 데이터 다섯 개의 구조와 출처, 공고 정보의 API 전달, AI 프롬프트의 사실성
규칙, 실패 시 폴백까지 테스트했습니다. 전체 테스트와 production build로 기본 회귀도
확인합니다.

아직 한계도 있습니다. 공고는 자동 갱신이 아니라 확인일 기준 예시이며, 로컬 폴백은
지원 목표를 표시하지만 문장을 깊게 재구성하지 않습니다. 다음에는 사용자가 공고 URL을
직접 넣고, AI가 어떤 CV 근거를 왜 강조했는지 확인한 뒤 승인하는 흐름을 만들고 싶습니다.

## 8:40–10:00 · Q&A

여기까지가 CV2PF의 문제, 구현 과정, 실제 동작입니다. 질문 받겠습니다.

### 예상 질문 1. AI가 경력을 과장하면 어떻게 하나요?

프롬프트에 CV에 없는 경력, 기술, 수치, 성과를 만들지 말라는 규칙을 넣고 테스트합니다.
다음 단계에서는 생성 문장마다 사용한 CV 근거를 연결해 사용자가 승인하게 할 계획입니다.

### 예상 질문 2. 왜 공고를 자동으로 가져오지 않았나요?

이번 구현에서는 사용자 가치와 전체 데이터 흐름을 먼저 검증하기 위해 공식 공고 다섯 개를
확인일과 함께 큐레이션했습니다. 자동 수집은 공고 구조 변경, 이용 정책, 마감 상태 확인을
함께 설계해야 해서 다음 수직 슬라이스로 분리했습니다.

### 예상 질문 3. Supabase에는 무엇을 저장하나요?

포트폴리오 이름과 직함, 디자인 테마, 생성된 HTML, 생성 시각을 저장합니다. 목록에서는
메타데이터만 받고 상세 항목을 열 때 HTML을 조회해 응답 크기를 줄였습니다.

### 예상 질문 4. AI 서버가 꺼지면 서비스가 멈추나요?

생성 요청이 실패하면 로컬 결정적 렌더러로 전환합니다. 이때 결과 화면에 폴백임과
JD 문장 재구성이 제한된다는 사실을 명확히 표시합니다.

### 예상 질문 5. Agent는 어디에 활용했나요?

계획 Agent로 요구사항을 작은 작업과 우선순위로 나누고, 검증 Agent로 요구사항과 테스트
결과를 대조했습니다. 화면의 초기 구조 생성에도 활용했지만, 상태 흐름과 세부 수정은
제가 코드를 확인하고 승인하는 방식으로 진행했습니다.

### 예상 질문 6. 이 서비스의 다음 핵심 기능은 무엇인가요?

채용 공고 URL 입력, CV와 JD의 근거 매칭 표시, 생성 전 문장별 승인입니다. 단순 생성보다
“왜 이 내용을 보여주는지 설명 가능한 맞춤화”를 만드는 것이 다음 목표입니다.
