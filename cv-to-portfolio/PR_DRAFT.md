## 주요 작업 리스트

한 주 동안 **CV → 포트폴리오 생성기(CV2PF)** 의 기획부터 동작하는 프로토타입, 2주차 개발 준비까지 마쳤습니다.

**① 기획**
- 기획서 작성 — 문제 정의 · 사용자 시나리오 · **화면 구조(UI)** · 핵심 기능 → [Wiki 기획서](https://github.com/dolphin1404/NaverConnect_wm/wiki/기획서) + repo 사본
- **순수 HTML/CSS 프로토타입**(화면 4개 클릭 전환)으로 화면 흐름을 먼저 검증
- 3개 관점(제품 완성도 / 기술 리스크 / 학습·데모) AI 리뷰로 기획을 다듬어 예외 상태·접근성·직군 무관 타깃을 반영

**② 동작하는 프로토타입 (결정적 렌더러 MVP)**
- 4단계 흐름: ① CV 업로드·파싱 → ② `DESIGN.md` 테마 **6종** 선택 → ③ 생성 → ④ 미리보기 & HTML 다운로드
- 샘플 CV **4종**(개발자·디자이너·마케터·기획자) — 직군 무관 확대
- 예외·접근성: 빈 입력 비활성 · 파싱 실패 인라인 힌트 · 미지원 파일 안내 · 완료 단계 클릭 복귀 · `aria-current`/`role=status`
- **백엔드·API 키 없이 브라우저만으로 완결**

**③ 개발 환경 (2주차 준비)**
- `client/` + `server/` **npm workspaces 모노레포**로 재편
- Express API 서버 스캐폴드 — `/api/health`, `/api/generate` **seam** (routes→controllers→services 계층 분리)
- **[CLAUDE.md](cv-to-portfolio/CLAUDE.md)** — 아키텍처·구조·라이브러리 선택 근거·컨벤션·커밋/PR 규칙 정리
- `cv2pf-design` 디자인 스킬 추가

**④ 계획·산출물**
- **[4주 개발 백로그](cv-to-portfolio/docs/BACKLOG.md)** — 우선순위(P0~P2)·주차별 목표·2주차 Must-Finish → README 링크
- 1주차 발표 PPT(11장)

## 내가 설명할 수 있는 부분

핵심은 생성 엔진 **`client/src/features/generate/generatePortfolio.js`** 입니다.

저는 "디자인을 **데이터**로 다루자"는 생각으로 짰습니다. 각 테마를 색·폰트·레이아웃 같은 **디자인 토큰** 객체로 정의해 두고(`themes.js`), 이 함수는 *파싱된 CV + 선택한 토큰* 을 받아 토큰을 CSS 변수(`:root`)로 주입한 **독립 실행형 HTML 문자열 하나**를 만들어 돌려줍니다. 그래서 렌더러 코드는 하나인데 토큰만 갈아끼우면 6가지 결과가 나옵니다 — 테마를 추가할 때 렌더러를 안 건드려도 됩니다.

`layout`(single-column/timeline/two-column/sidebar)에 따라 본문 조립 방식만 분기하고, 사용자가 넣은 CV 텍스트는 전부 `esc()`로 이스케이프해서 마크업이 깨지거나 주입되지 않게 했습니다. 이렇게 **결정적 렌더러**로 만든 이유는, 같은 입력이면 항상 같은 결과라 재현·비교가 쉽고 **백엔드·API 키 없이 브라우저만으로 완결**되기 때문입니다. LLM 생성은 나중에 `server/api/generate`로 교체할 수 있게 **seam**만 열어 뒀습니다.

## 아직 이해 못 한 부분

- **서버 계층 분리** — `routes → controllers → services` 형태는 잡았지만 `/api/generate` 로직이 아직 스캐폴드라, 실제로 무엇을 controller에 얇게 두고 무엇을 service로 빼야 깔끔한지는 2주차에 채우면서 체감할 예정입니다.
- **Vite `?raw` 임포트**가 빌드 시 `.md` 내용을 번들에 어떻게 포함시키는지 정확한 원리는 아직 모릅니다(동작은 확인).
- **LLM 응답 HTML의 안전성** — 프롬프트 인젝션·깨진 마크업을 실제 코드로 어떻게 방어할지는 개념만 알고 구현은 미지입니다(백로그 3주차 P0).
- 결정적 렌더러가 **CSS를 문자열로 통째 생성**하는 방식이, 테마가 더 늘어도 유지보수에 괜찮을지 확신이 없습니다.

## 새로 알게 된 것

- **디자인을 토큰(데이터)으로** 다루면 렌더러 하나로 여러 테마를 만들 수 있다.
- **API 키는 브라우저에 노출하면 안 된다** → 그래서 서버가 필요하고, `client/server` 모노레포로 나눈 이유가 됐다.
- Vite `?raw` 로 `.md`를 문자열로 불러와 화면에 그대로 보여줄 수 있다.
- **백로그**: 새 아이디어는 일단 백로그에 넣고 *지금 하던 일*을 지킨다. 완료 기준(무엇을 보여주면 끝인가)을 못박지 않으면 스코프가 무한정 늘어난다.
- **Conventional Commits** 규칙과, 사용자 입력을 HTML로 렌더할 때 `&<>"` 이스케이프가 필수라는 점.
