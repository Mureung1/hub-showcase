# 프로젝트 개발 지침 (기획서 준수)

에이전트는 이 프로젝트(대학생 대면 소통 서비스)에서 작업할 때 아래 지침을 반드시 준수해야 합니다.

1. **기획서 참조**:
   - 코드를 생성, 수정, 리팩토링하거나 설계를 변경하기 전에 항상 워크스페이스 루트의 `plan.md` 파일을 읽고 최신 요구사항을 반영하십시오.
   - 기획서에는 다음 핵심 기능들이 정의되어 있습니다:
     - 태그 기반 게시글 등록 및 노출/검색
     - 오프라인 연결을 위한 1:1 채팅 및 실시간 메시징
     - 약속 확정 및 안전 장치(신고/차단/안전수칙)

2. **개발 준수 사항**:
   - 구현하는 모든 기능(UI 컴포넌트, API, 상태 관리 등)은 `plan.md`에 명시된 시나리오와 핵심 기능 스펙에 정확히 부합해야 합니다.
   - 기획서 내용과 다른 점이 있거나 모호한 부분이 있다면 작업을 진행하기 전 사용자에게 명확히 확인을 구하십시오.

3. **기술 스택 및 개발 규칙**:
   - **프론트엔드**: React (Vite 빌드 도구 사용)
   - **백엔드**: Express (Node.js 기반)
   - **사용 언어**: TypeScript (TS) (※ 추후 변경될 수 있으나 현재 기본 스택으로 지정)
   - **실시간 통신**: Socket.io를 사용하여 1:1 실시간 채팅 메시징 및 약속 확정 기능 구현
   - **데이터베이스**: 데이터베이스 연동이 완료되기 전까지는 백엔드 내에 임시 메모리 저장소(In-memory array) 및 임시 JSON 파일 등을 활용한 Mock API 형태로 구현
   - **라이브러리 설치 제한**: 새로운 라이브러리를 설치하기 전에는 이미 `package.json` 등에 동일하거나 호환되는 라이브러리가 존재하는지 확인하고, 이미 존재한다면 추가로 설치하지 마십시오.

4. **보안 및 파일 수정 제한**:
   - **절대 `.github` 디렉토리와 그 하위의 모든 파일들을 수정하거나 생성/삭제하지 마십시오.** 이 영역은 CI/CD 자동 빌드 및 배포, 형상 관리를 위해 사전에 구성된 핵심 영역이므로 에이전트의 변경 시도가 엄격히 금지됩니다.

5. **코딩 컨벤션 및 스타일 가이드**:
   - **코드 스타일**: 들여쓰기는 2 spaces를 사용하고, 문자열은 홑따옴표(`'`)를 사용하며 (JSX 속성은 쌍따옴표 `"`), 문장 끝에 세미콜론을 항상 명시합니다.
   - **이름 정의**: 
     - 변수/함수명은 `camelCase`를 사용합니다.
     - React 컴포넌트 및 클래스는 `PascalCase`를 사용하고 파일명 역시 `PascalCase.tsx`로 작성합니다.
     - 상수명은 `UPPER_SNAKE_CASE`를 사용합니다.
   - **TypeScript & 함수**: React 컴포넌트와 일반 핸들러는 화살표 함수(`const Component = () => {}`) 스타일을 사용합니다. `any` 타입 사용을 지양하고, 인터페이스 정의 시 기본 구조는 `interface`를, 유니온 타입 등은 `type`을 사용합니다.
   - **주석 및 문서화**: 모든 주석은 **한국어**로만 작성하며, 주요 컨트롤러, API 엔드포인트 및 복잡한 함수에는 한국어로 된 JSDoc 주석을 작성합니다.
   - **형상 관리 (Git 커밋 규칙)**: 모든 커밋 메시지는 한국어로 작성하며 Conventional Commits 형식을 준수합니다.
     - **형식**: `<유형>(<범위>): <제목>` (예: `feat(auth): 로그인 API 구현`)
     - **유형(Type)**:
       - `feat`: 새로운 기능 추가
       - `fix`: 버그 수정
       - `docs`: 문서 수정 (README 등)
       - `style`: 포맷팅, 세미콜론 누락 등 (코드 로직 변경 없음)
       - `refactor`: 코드 리팩토링
       - `test`: 테스트 코드 추가/수정
       - `chore`: 빌드, 패키지 설정, 의존성 추가 등
       - `design`: CSS, UI 스타일링 및 디자인 변경
     - **규칙**: 제목은 50자 이내로 간결히 요약하고 끝에 마침표(`.`)를 생략합니다. 이슈 번호 참조 시 끝에 `#번호` 형식으로 추가합니다. (예: `feat: 구글 로그인 기능 구현 (#42)`)

6. **추가 개발 및 운영 지침**:
   - **빌드 검증**: 작업 완료 보고 전 반드시 프론트엔드(`client/` 내 빌드 또는 `tsc --noEmit`) 및 백엔드(`server/` 내 `tsc --noEmit`) 빌드 오류가 없는지 사전 검증하십시오.
   - **API 및 에러 통일**: Express 서버 API 응답은 성공 시 `{ "success": true, "data": ... }`, 에러 발생 시 `{ "success": false, "error": { "code", "message" } }` 규격을 지킵니다.
   - **환경 변수 관리**: 포트, API Key 등 설정값은 하드코딩하지 않고 `.env`에 정의하며, 템플릿(`.env.example`)을 작성하고 유지하십시오.
   - **브랜치 규칙**: 새 작업 시 `feature/<기능명>`, `bugfix/<버그명>` 등의 명명 규칙을 적용하여 브랜치를 생성하십시오.
   - **디자인 준수**: 프론트엔드 화면 구현 시 프로젝트 루트의 `design.md` 파일을 참조하여 UI 구조를 설계하되, 색상 등 세부 스타일 정보는 규칙에 하드코딩하지 않고 `design.md`에 명시된 최신 설정만 유동적으로 반영하십시오.
