# TeamFlow 테스트 작성

TeamFlow의 기존 실행기와 테스트 패턴을 유지하면서 요구사항을 증명하는 테스트를 작성하고 실행한다.

## 작업 맥락 확인

1. 저장소 루트와 현재 Git 상태를 확인하고 기존 변경을 보존한다.
2. `CLAUDE.md`, 관련 `package.json`, 테스트 설정, 대상 코드와 인접 테스트를 읽는다.
3. 요구사항과 완료 기준을 테스트 가능한 결과로 정리한다.
4. 기대 결과가 불명확하거나 선택에 따라 기능 동작이 달라질 때만 사용자에게 질문한다.
5. 새 테스트 라이브러리를 임의로 설치하거나 실행기를 교체하지 않는다.

## 테스트 방식 결정

다음 우선순위로 방식을 선택한다.

1. 사용자가 TDD, 테스트 우선, Red 우선 진행을 명시하면 반드시 TDD를 적용한다.
2. 버그 재현, 입력 검증, 계산·정렬·필터링·변환, 권한·보안 규칙, API 계약처럼 기대 결과가 명확하면 자동으로 TDD를 선택한다. 시작 전에 `이 작업은 규칙과 기대 결과가 명확해 TDD로 진행합니다.`라고 알린다.
3. 여러 계층을 연결하는 일반 기능, 요구사항 변경 가능성이 큰 기능, 기존 UI 기능 확장은 기본적으로 구현 후 테스트를 적용한다.
4. CSS·색상·간격·레이아웃, 단순 문구, 프로토타입, 기술 탐색, 단순 설정은 자동 TDD를 선택하지 않는다.
5. 기존 테스트가 요구사항을 충분히 증명하면 새 테스트를 중복하지 말고 기존 테스트 활용으로 보고한다.

사용자가 TDD를 명시한 경우에는 자동 선택 기준보다 사용자 요청을 우선한다. 구현 후 작성한 테스트를 TDD라고 보고하지 않는다.

## 테스트 계획과 수준 선택

- 정상값, 빈 값, 경계값, 실패값 중 대상에 의미 있는 사례를 목록으로 작성한다.
- 각 사례의 입력, 기대 결과, 요구사항 근거를 연결한다.
- 순수 함수·검증·계산·변환은 단위 테스트를 우선한다.
- API 라우트, 저장소 경계, 여러 모듈 연결은 통합 테스트를 사용한다.
- React 화면과 상호작용은 컴포넌트 테스트를 사용하고 역할·레이블·표시 결과와 사용자 행동을 검사한다.
- 핵심 흐름을 가장 낮은 비용으로 충분히 증명하는 수준을 선택하고 이유를 기록한다.

다음 프로젝트 패턴을 재사용한다.

- Web: Vitest, Testing Library, `userEvent`, `jsdom`
- API: `node:test`, `node:assert/strict`
- Shared: `node:test`, `node:assert/strict`

## 테스트 작성

- 구현 세부사항보다 공개된 반환값, 상태 변화, 응답 계약, 사용자 행동을 검사한다.
- 테스트 이름과 assertion이 같은 약속을 표현하게 한다.
- 원시값에는 적절한 동등성 matcher를 사용하고 객체·배열은 구조 비교를 사용한다.
- Mock, Fake, Stub은 느리거나 불안정한 경계를 대체할 때만 사용하고 대체 대상과 확인하지 못한 범위를 기록한다.
- 비동기 작업은 실제 완료 시점을 기다린 뒤 검증한다.
- `skip`, `only`, `todo`, 실제 네트워크, 현재 시간, 실행 순서에 불필요하게 의존하지 않는다.
- 커버리지 100%를 목표로 삼지 말고 요구사항과 회귀 위험을 우선한다.

## TDD 수행

1. 요구사항을 입력과 기대 결과의 시나리오로 정리한다.
2. 시나리오를 테스트로 작성한다.
3. 관련 테스트를 실행해 요구사항이 아직 구현되지 않아 실패하는 Red를 확인한다.
4. import·설정·환경 오류가 발생하면 Red로 인정하지 말고 먼저 테스트가 실행 가능한 상태를 만든다. 대상 심볼이 없어 import가 막히면 동작하지 않는 최소 Stub을 만들고 assertion 실패를 확인한다.
5. 테스트를 통과하는 최소 구현만 작성한다.
6. 관련 테스트의 Green을 확인한다.
7. 변경 작업공간의 회귀 테스트를 실행한다.
8. 필요한 경우 동작을 유지한 채 리팩터링하고 같은 회귀 테스트를 다시 실행한다.
9. Red, Green, Refactor 후 결과의 명령과 실행 순서를 보존해 보고한다.

## 테스트 실행 범위

관련 테스트부터 실행한다.

```powershell
npm.cmd test --workspace @teamflow/web -- <test-file>
npm.cmd test --workspace @teamflow/api -- <test-file>
npm.cmd test --workspace @teamflow/shared -- <test-file>
```

그다음 변경된 작업공간 전체를 실행한다.

```powershell
npm.cmd test --workspace @teamflow/web
npm.cmd test --workspace @teamflow/api
npm.cmd test --workspace @teamflow/shared
```

Shared 변경이나 여러 앱에 걸친 변경은 저장소 루트에서 전체 회귀 테스트를 실행한다.

```powershell
npm.cmd test
```

실행할 수 없는 명령은 생략한 채 성공으로 보고하지 말고 원인, 실패 단계, 확인하지 못한 범위를 남긴다. 환경·설정·import 오류와 assertion 실패를 구분한다.

```markdown
- 테스트 대상:
- 테스트 수준과 이유:
- 추가하거나 수정한 사례:

- 실행 결과:
- Mock/Fake/Stub과 검증 한계:
- 확인하지 못한 부분:
```
