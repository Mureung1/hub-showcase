# Verify Feature

검증 결과는 항상 한국어로 작성한다. 검증과 보고만 수행하며 코드, 문서, 체크리스트, Git 상태 또는 외부 데이터를 임의로 수정하지 않는다.

## 1. 검증 범위 확인

1. 사용자의 요청에서 검증할 기능과 기대 결과를 한 문장으로 정리한다.
2. 파일을 읽기 전에 참고 문서 후보와 읽어야 하는 이유를 제시한다.
3. 사용자에게 후보를 확인하고 추가·제외할 자료가 있는지 질문한다.
4. 사용자가 승인하거나 직접 지정한 자료만 읽는다.
5. 요구사항이 모호하거나 서로 충돌하면 테스트 전에 질문한다.

바로진료에서는 다음 자료를 우선 후보로 제시한다.

- `docs/plan.md`: 사용자 문제와 핵심 시나리오
- `docs/feature-spec.md`: 상태 전이, 입력, 예외와 API 계약
- `docs/erd.md`: 저장 구조와 DB 제약
- `docs/checklist.md`: 완료 기준과 현재 상태
- 관련 GitHub Issue, PR 또는 사용자가 지정한 문서

## 2. 요구사항 추적표 작성

승인된 자료에서 관찰 가능한 완료 기준을 추출한다. 구현을 보기 전에 다음 표를 작성한다.

| 항목 | 내용 |
|---|---|
| 요구사항 | 사용자가 기대하는 동작 |
| 관련 계층 | `FE`, `BE`, `DB`, `AUTH`, `EXTERNAL` 중 해당 항목 |
| 검증 방법 | 코드 확인, 자동 테스트, API 호출, 브라우저 조작 또는 DB 조회 |
| 기대 결과 | 통과를 판단할 수 있는 구체적인 결과 |

정상 흐름만 보지 말고 입력 경계값, 권한 오류, 중복 요청, 네트워크 실패, 동시 요청과 개인정보 노출 가능성을 기능 범위에 맞게 포함한다.

## 3. 검증 순서

다음 순서로 낮은 비용의 검증부터 수행한다.

1. 관련 변경 파일과 데이터 흐름을 찾는다.
2. React 기능이면 `state → props → event → fetch → state 갱신` 흐름을 확인한다.
3. API 기능이면 `route → validation/auth → service → repository → DB → response` 흐름을 확인한다.
4. 타입 검사, 린트와 관련 단위 테스트를 실행한다.
5. API 통합 테스트와 실제 저장·조회 결과를 확인한다.
6. UI 기능이면 브라우저에서 사용자 흐름과 Network 요청·응답을 확인한다.
7. 전체 회귀 테스트와 production build는 기능 위험도에 따라 마지막에 실행한다.

테스트 통과만으로 기능 전체를 통과 처리하지 않는다. 요구사항 추적표의 각 항목에 직접 대응하는 증거가 있어야 한다.

## 4. 외부 시스템 검증

Supabase, 배포 환경, 이메일, 알림 API 등 외부 상태를 읽거나 변경하기 전에 다음 내용을 제시하고 사용자 승인을 받는다.

- 대상 환경과 서비스
- 실행할 명령 또는 요청
- 생성·수정·삭제될 데이터
- 롤백 또는 정리 방법
- 비밀값 노출 방지 방법

DB 쓰기 검증은 개발 또는 테스트 환경에서만 수행한다. 가능하면 트랜잭션 안에서 테스트 데이터를 만들고 의도적으로 롤백한다. production 데이터 변경, 실제 메시지 발송과 실제 결제는 검증 목적으로 실행하지 않는다.

## 5. 결함 판정

발견한 문제는 다음 심각도로 분류한다.

- `P0`: 핵심 흐름이 동작하지 않거나 데이터·보안에 중대한 위험이 있음
- `P1`: 주요 요구사항 위반, 잘못된 상태 전이 또는 일반 사용자가 겪는 오류
- `P2`: 제한된 예외, 복구성·사용성·테스트 부족 또는 유지보수 위험

각 결함에는 반드시 다음을 포함한다.

1. 위반한 요구사항
2. 실제 관찰 결과와 기대 결과
3. 재현 절차 또는 실패한 테스트
4. 파일과 줄 또는 API·DB 증거
5. 가능한 원인. 확정할 수 없으면 추정이라고 표시
6. 권장 수정 방향과 수정 후 재검증 방법

수정 코드를 직접 작성하거나 적용하지 않는다. 사용자가 별도 구현 작업을 요청하면 검증을 종료하고 일반 개발 작업으로 전환한다.

## 6. 결과 보고

결과는 다음 순서로 작성한다.

### 판정

`PASS`, `PARTIAL`, `FAIL` 중 하나와 한 문장 근거를 쓴다.

### 발견 사항

결함을 `P0 → P1 → P2` 순서로 제시한다. 결함이 없으면 명확히 없다고 말한다.

### 요구사항별 결과

각 요구사항을 `통과`, `실패`, `미검증`으로 표시하고 근거를 연결한다.

### 실행 증거

실행한 명령, 테스트 개수, HTTP 상태와 핵심 DB 저장·조회 결과를 요약한다. 비밀번호, 전체 전화번호, 토큰과 비밀키는 출력하지 않는다.

### 남은 위험

권한 부족, 외부 서비스 미연결, 테스트 데이터 부재 등 검증하지 못한 항목과 이유를 적는다.

### 권장 수정 순서

수정이 필요한 경우 위험과 선행 관계를 기준으로 순서를 제안한다. 직접 수정하거나 완료 표시하지 않는다.

## Do Not

- 승인 전에 후보 문서를 읽지 않는다.
- 검증 중 파일, DB, GitHub 또는 Git 상태를 임의로 수정하지 않는다.
- 외부 시스템 쓰기를 승인 없이 실행하지 않는다.
- mock 결과를 실제 API·DB 검증 결과처럼 표현하지 않는다.
- 테스트가 없다는 이유만으로 구현이 틀렸다고 단정하지 않는다.
- 재현 증거 없이 결함을 확정하지 않는다.
- 미검증 항목을 통과 처리하지 않는다.
