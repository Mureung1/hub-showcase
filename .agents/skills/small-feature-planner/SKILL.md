# Small Feature Planner

## 목적

사용자가 만들고 싶은 작은 Feature를 구현 가능한 작은 Sub Task로 나눈다.

## 실행 규칙

- 계획 작성 전 관련 컴포넌트, API 호출 흐름, 테스트 파일을 먼저 확인한다.
- 기존 프로젝트 구조와 코드를 먼저 확인한다.
- 한 번에 전체 기능을 구현하지 않는다.
- 사용자가 명시적으로 구현을 요청하기 전에는 파일을 수정하지 않는다.
- 이번 Feature 범위를 벗어나는 작업은 제외 범위에 작성한다.
- 분석, 검토, 판단 내용은 기능 범위, 제외 범위, 예상 수정 파일에 작성한다.
- Sub Task에는 실행 작업만 작성한다.
- 예상 수정 파일은 실제 프로젝트 구조를 먼저 확인한 뒤 추정하여 작성한다.
- 파일을 확신할 수 없는 경우에는 "관련 컴포넌트", "관련 API", "관련 테스트"처럼 추정임을 명시한다.
- 작업은 실제 구현 순서에 맞게 정리한다.

## Sub Task 작성 원칙

- Sub Task는 실제로 수행 가능한 행동으로 작성한다.
- Sub Task 이름은 동작과 대상을 함께 작성한다.
- "계획한다", "설계한다", "검토한다", "정리할 계획을 세운다"처럼 결과물이 불명확한 표현을 사용하지 않는다.
- 코드 변경이 필요한 작업은 어느 파일의 무엇을 변경하는지 작성한다.
- 코드 변경이 필요 없는 확인 작업은 "테스트를 실행한다", "브라우저에서 동작을 확인한다"처럼 확인 대상과 방법을 구체적으로 작성한다.
- 하나의 Sub Task에는 하나의 구현 또는 하나의 검증만 포함한다.
- 각 Sub Task는 서로 독립적으로 확인할 수 있어야 한다.
- Sub Task를 읽었을 때 바로 구현을 시작할 수 있어야 한다.
- 각 Sub Task마다 완료 조건과 확인 방법을 작성한다.
- 구현 순서는 각 단계가 이전 단계 완료 후 진행되도록 작성한다.
- 여러 Sub Task를 동시에 구현하지 않는다.
- 하나의 Sub Task가 완료되고 확인된 뒤 다음 단계로 진행한다.

## 구현 후 설명 규칙

Sub Task를 구현한 후 반드시 다음 내용을 설명한다.

- 수정한 파일
- 무엇을 수정했는지
- 왜 이렇게 구현했는지
- 코드가 어떻게 동작하는지
- 다른 구현 방법에는 무엇이 있었는지
- 사용자가 직접 확인하는 방법

다음 Sub Task는 사용자의 확인 이후에만 진행한다.

## 좋은 Sub Task 이름 예시

- WEAK_AREAS 상수 값을 변경한다.
- weakAreas 상태를 추가한다.
- toggleWeakArea 함수를 작성한다.
- 카드 className에 선택 조건을 연결한다.
- 취약 영역 다중 선택 테스트를 추가한다.
- 브라우저에서 취약 영역 선택 동작을 확인한다.

## 나쁜 Sub Task 이름 예시

- 취약 영역 데이터 정의를 정리한다.
- 선택 상태 구조를 설계한다.
- 접근성 속성을 검토한다.
- 테스트 계획을 세운다.

## 출력 형식

### 기능 범위

이번 작업에서 구현할 내용을 간단히 작성한다.

### 제외 범위

이번 작업에서 구현하지 않을 내용을 작성한다.

### 예상 수정 파일

수정하거나 새로 만들 가능성이 있는 파일과 변경 대상을 작성한다.
파일을 확신할 수 없으면 "관련 컴포넌트", "관련 API", "관련 테스트"처럼 추정임을 표시한다.

### Sub Task

각 Sub Task를 체크리스트로 작성한다.

각 항목은 다음 형식을 반드시 사용한다.

- [ ] Sub Task 이름
  - 작업 내용:
  - 완료 조건:
  - 확인 방법:

확인 방법에는 화면 확인, 테스트 실행, API 응답 확인, 빌드 확인 등을 사용할 수 있다.

### 구현 순서

Sub Task를 실제로 진행할 순서대로 정리한다.
각 단계는 이전 단계가 완료된 후 진행한다.

## 중요

계획을 먼저 보여주고 반드시 멈춘 뒤 사용자의 확인을 기다린다.
사용자가 명시적으로 구현을 요청하기 전에는 파일을 수정하지 않는다.
사용자가 구현을 요청하면 한 번에 하나의 Sub Task만 수행한다.
