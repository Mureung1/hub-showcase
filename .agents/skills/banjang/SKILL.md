# 작업반장

GitHub Issues와 Project #3을 실행 기준으로 삼아 현재 상태에서 필요한 단계부터 PR 생성 또는 병합 후 정리까지 이어간다. 사람의 제품 판단과 PR 최종 승인·병합을 제외한 명확한 반복 작업은 중간 승인을 다시 요구하지 않는다.

## 고정 범위

- 저장소: `ppre1ude/hub`
- Project: 사용자 `ppre1ude`의 Project #3 `아맞다! 프로젝트`
- 기준 브랜치: `main`
- 브랜치 규칙: `docs/coding-commit-conventions.md`의 `<type>/<이슈번호>-<영문-키워드>`
- 커밋 규칙: `<type>: <한글 명사형 요약>`
- PR 언어: 제목과 본문 모두 한국어

저장소나 원격이 위 범위와 다르면 쓰기 작업을 하지 말고 사용자에게 알린다.

## 호출과 재개

| 요청                    | 기본 동작                                           |
| ----------------------- | --------------------------------------------------- |
| `$banjang 다음 작업`    | 다음 이슈를 선택하고 명확하면 PR 생성까지 진행      |
| `$banjang #<번호> 시작` | 지정 이슈의 실행 가능성을 확인하고 PR 생성까지 진행 |
| `$banjang 리뷰 반영`    | 현재 PR의 미해결 리뷰와 실패 검사를 반영            |
| `$banjang 마무리`       | 병합을 확인하고 로컬·Issues·Project 상태 정리       |

요청이 단계 이름을 생략하면 현재 브랜치, 연결 PR과 이슈 상태로 재개 지점을 판단한다. 이미 완료된 단계를 반복하지 않는다.

## 공통 방향 설정

모든 모드에서 먼저 다음을 수행한다.

1. `git rev-parse --show-toplevel`과 `git remote get-url origin`으로 저장소를 확인한다.
2. `git status --short --branch`, 현재 브랜치와 사용자 소유 변경을 확인한다.
3. 브랜치 이름이나 사용자 요청에서 이슈 번호를 찾고 이슈 본문, 라벨, 상태와 Project 필드를 조회한다.
4. 현재 브랜치의 PR과 검사, 리뷰, 병합 여부를 조회한다.
5. `AGENTS.md`와 적용되는 하위 지침을 읽는다. 코드 작업이면 `docs/`의 모든 Markdown 문서를 읽고 범위별 문서를 적용한다.
6. GitHub 쓰기 전후에 대상 이슈와 Project 상태를 다시 조회한다.

Project 상태를 바꿀 때 `gh project view`, `gh project field-list`와 `gh project item-list`로 현재 프로젝트·필드·선택지 ID를 구한다. 필드 ID와 선택지 ID를 스킬에 하드코딩하지 않는다.

## 자동 진행과 사람 검수 경계

다음 조건이 없으면 승인된 범위의 조회, 상태 변경, 브랜치 생성, 구현, 검증, 커밋, 푸시와 PR 생성을 이어서 수행한다.

다음 경우에만 멈추고 확인을 요청한다.

- 실행 후보 사이에 제품 가치나 범위 결정을 내려야 한다.
- 이슈 완료 기준과 코드, Wiki 또는 저장소 문서가 충돌한다.
- 제품 동작, 시각 설계, 보안, 데이터 마이그레이션이나 하위 호환성 결정을 새로 내려야 한다.
- 사용자 변경과 작업 범위가 겹쳐 안전하게 분리할 수 없다.
- 필요한 권한, 비밀 정보 또는 외부 서비스가 없어 안전한 대안도 없다.
- PR 최종 승인과 병합이 필요하다.

명확한 후보 선택 근거와 논의 사항은 진행 전에 알리되, 위 조건이 아니면 답을 기다리지 않고 계속한다.

## 다음 작업 선택

1. Project #3의 항목과 각 열린 이슈의 본문·라벨을 조회한다.
2. Project 상태가 `시작 가능`, 제품 단계가 `현재 MVP` 또는 `후속 후보`이고 `ready-for-agent` 라벨이 있는 이슈만 자동 후보로 삼는다.
3. 제품 단계가 `보류` 또는 `제외`이거나 `blocked`, `needs-info`, `ready-for-human` 라벨이 하나라도 있으면 자동 후보에서 제외한다.
4. 본문의 선행 이슈가 모두 닫혔고 완료 기준과 검증 방법이 실행 가능한지 확인한다.
5. 다음 순서로 비교한다.
   - 제품 단계 `현재 MVP` → `후속 후보`
   - 우선순위 `높음` → `보통` → `낮음`
   - 주차 `2주차` → `3주차` → `4주차` → 미지정
   - 이른 완료 목표일과 시작일
   - 상위 이슈와 선행 관계가 지정한 순서
   - 더 작은 이슈 번호
6. 최상위 후보가 실행 가능하면 선택 근거와 구현 전 논의 사항을 알리고 `작업 시작`부터 계속한다.

후보가 없으면 필터별 제외 이유를 짧게 보고한다. 동순위 후보에 제품 판단이 필요하면 권장안과 대안을 제시하고 멈춘다. 사용자가 이슈 번호를 지정했다면 순위 비교 없이 해당 이슈의 상태와 선행 관계만 확인한다.

## 작업 시작

1. 작업 트리가 사용자 변경과 충돌하지 않는지 확인한다.
2. `main`으로 전환 가능한 상태에서 `git fetch origin --prune` 후 `git pull --ff-only origin main`으로 동기화한다.
3. 이슈가 열린 상태인지 다시 확인한다.
4. Project `Status`를 `진행 중`으로 바꾸고 `시작일`이 비어 있으면 오늘 날짜를 `YYYY-MM-DD` 형식으로 기록한다.
5. 작업 성격에 맞는 type과 짧은 영문 키워드로 브랜치를 만든다.
6. 이슈의 사용자 결과, 범위, 완료 기준, 검증 방법과 제외 범위를 구현 계약으로 고정한다.

이미 올바른 작업 브랜치에 있으면 새 브랜치를 만들지 않는다. 다른 미병합 작업 브랜치에 있으면 추측해서 전환하거나 변경을 옮기지 않는다.

## 구현

- 요청 범위 밖 파일과 사용자 변경을 수정하거나 stage하지 않는다.
- UI 변경 전에는 `DESIGN.md`, 프론트엔드 구조 변경에는 `docs/development-architecture.md`를 적용한다.
- 기능과 오류 수정은 실패를 재현하는 검증을 먼저 만들거나 기존 검증으로 실패를 확인한 뒤 최소 구현으로 통과시킨다.
- 내용이 바뀐 한국어 주석은 코드와 함께 갱신한다.
- 문제 해결 뒤 디버그 로그와 임시 코드를 제거한다.
- 이슈의 완료 기준이 코드와 문서 변경을 요구하면 같은 작업 범위에서 함께 갱신한다.
- 구현 중 새 제품 결정이 필요해지면 임의로 범위를 넓히지 않고 사람 검수 경계로 전환한다.

## 검증 예산

변경 위험에 비례해 다음 순서로 검증한다.

1. 구현 중에는 변경 파일과 직접 연결된 테스트·정적 검사만 실행한다.
2. PR 직전에는 이슈와 저장소가 요구하는 전체 검증을 한 번 실행한다.
3. 리뷰 수정 뒤에는 영향받은 테스트와 검사만 다시 실행한다.
4. 공통 계약, 저장 형식, 빌드·배포 설정이나 넓은 의존성이 바뀐 경우에만 전체 검증을 반복한다.
5. 문서와 스킬만 바뀌면 Prettier, 스킬 검증기와 `git diff --check`만 실행하고 제품 테스트와 빌드는 실행하지 않는다.

실행하지 않은 검증을 통과했다고 표현하지 않는다. 실패가 현재 변경과 무관하면 근거를 분리해 보고하고, 현재 변경과 관련 있으면 원인을 해결한 뒤 다시 검증한다.

## 커밋

- 의미 있는 완료 단위마다 커밋한다.
- `git diff`와 `git diff --cached`로 대상 파일을 확인한 뒤 작업 범위 파일만 명시적으로 stage한다.
- 커밋 메시지는 `docs/coding-commit-conventions.md`의 type과 `<변경 대상> + <수행한 작업>` 구조의 한글 명사형 요약을 사용한다.
- 장문형 커밋 본문을 만들지 않는다.
- 검증 결과를 확인하지 않은 상태로 커밋하지 않는다.

### 커밋 메시지 검토

1. 커밋 전에 `git diff --cached --stat`과 `git diff --cached`로 실제 변경 대상과 수행한 작업을 각각 확인한다.
2. 커밋 요약에 변경 대상과 `작성`, `추가`, `삭제`, `구현`, `연결`, `분리`, `복원`, `보완`, `교정` 같은 작업 결과가 모두 포함됐는지 확인한다.
3. `선택 모드`, `시각 체계`, `구현 정합성`처럼 주제나 추상적인 상태만 적은 요약은 커밋하지 않는다.
4. 커밋명을 짧게 만들기 위해 핵심 대상이나 작업 결과를 생략하지 않는다.
5. 커밋 직후 `git log -1 --format=%s`로 메시지를 다시 읽고 “무엇을 어떻게 바꾼 커밋인가?”에 답할 수 없으면 푸시 전에 수정한다.
6. 푸시 전 `git log --reverse --format=%s origin/main..HEAD`로 작업 브랜치의 전체 커밋명을 다시 검토한다. 기준을 충족하지 않는 커밋이 하나라도 있으면 푸시하지 않는다.

## 푸시와 Pull Request

1. 기준 브랜치와의 전체 diff, 커밋 목록과 최신 검증 결과를 확인한다.
2. 현재 브랜치를 `origin`에 upstream과 함께 푸시한다.
3. draft가 아닌 준비된 PR을 만든다. 아직 검토 준비가 되지 않았다면 PR을 만들지 말고 실제 blocker를 보고한다.
4. PR 제목과 본문을 한국어로 작성한다.
5. 본문에 다음 항목을 포함한다.
   - `Closes #<이슈번호>`
   - 변경 요약
   - 검증 명령과 결과
   - 사람이 중점 검수할 항목
6. PR 생성 후 Project `Status`를 `검토 중`으로 변경한다.
7. 즉시 확인 가능한 리뷰와 검사가 있으면 상태를 확인하되, 리뷰 생성을 기다리며 장시간 대기하지 않는다.

PR URL과 검증 근거를 보고하고 사람의 최종 승인·병합을 기다린다. `gh pr merge`를 실행하지 않는다.

## 리뷰 반영

1. 현재 브랜치와 연결된 PR을 확인한다.
2. 미해결 inline conversation, review summary, 일반 댓글과 실패 검사를 모두 조회한다.
3. 각 항목을 코드와 이슈·문서 계약에 대조해 다음으로 분류한다.
   - 명확하고 타당한 수정
   - 이미 반영됐거나 사실과 다른 제안
   - 제품·안전 결정이 필요한 제안
4. 명확한 수정은 재현 또는 영향 범위 검증을 먼저 확인하고 구현한다.
5. 관련 검증, diff 확인, 커밋과 푸시를 이어서 수행한다.
6. 권한이 있고 추가 판단이 필요 없으면 반영 근거를 답변하고 conversation을 해결한다.

사실과 다른 제안은 근거를 들어 반영하지 않는다. 제품 동작, 보안 완화나 호환성 손실이 필요한 제안은 선택지와 권장안을 제시하고 멈춘다. 리뷰 반영 뒤에도 자동 병합하지 않는다.

## 병합 후 마무리

1. PR의 `mergedAt`과 merge commit을 GitHub에서 확인한다. PR이 단순히 닫혔거나 아직 열려 있으면 정리하지 않는다.
2. 작업 트리가 안전한지 확인하고 `git fetch origin --prune`을 실행한다.
3. `main`으로 전환해 `git pull --ff-only origin main`으로 동기화한다.
4. 로컬 작업 브랜치가 병합됐고 다른 worktree에서 사용 중이지 않으며 작업 트리가 깨끗할 때만 삭제한다.
5. 원격 브랜치는 삭제하지 않는다.
6. 이슈가 열려 있으면 닫고 `ready-for-agent` 같은 실행 대기 라벨을 제거한다.
7. Project `Status`를 `완료`로 변경하고 결과를 다시 조회한다.
8. 상위 이슈의 체크리스트와 하위 진행률을 실제 완료 상태에 맞춘다.
9. 완료된 이슈가 선행 조건이던 후속 이슈를 확인한다.
   - 모든 선행 조건이 끝났고 사람 결정이 필요 없으면 `blocked`를 제거하고 `ready-for-agent`와 `시작 가능`을 설정한다.
   - `ready-for-human` 또는 `needs-info`가 있으면 자동 실행 가능 상태로 바꾸지 않는다.
10. 상위 추적 이슈의 모든 하위 작업이 끝났으면 완료 기준을 확인한 뒤 닫고 Project를 `완료`로 바꾼다.

마지막으로 병합 PR, 이슈·Project 변경, 로컬 정리, 새로 시작 가능해진 이슈와 다음 후보를 요약한다.

## 금지 동작

- 자동 병합 또는 `gh pr merge`
- 강제 푸시와 force 옵션
- 원격 브랜치 삭제
- `git reset --hard`, `git clean -fd`와 사용자 변경을 지우는 명령
- Project 필드 ID와 선택지 ID 하드코딩
- `blocked`, `needs-info`, `ready-for-human` 이슈의 추측성 구현
- 사용자 변경의 stage, 덮어쓰기, 이동 또는 삭제
- 변경 범위와 무관한 전체 코드 정리

## 결과 보고

모든 처리 메시지와 최종 응답은 한국어로 작성한다. 결과부터 말하고 다음을 짧게 포함한다.

- 선택하거나 처리한 이슈와 근거
- 브랜치, 커밋과 PR
- 실제 실행한 검증과 결과
- Issues와 Project에서 바꾼 상태
- 사람이 검수하거나 실행할 한 가지 다음 행동
