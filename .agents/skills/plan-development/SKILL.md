# Plan Development

계획 결과는 항상 한국어로 작성한다. 계획안만 제안하고 파일, GitHub Issues, GitHub Projects 또는 외부 서비스를 직접 수정하지 않는다.

## 1. 읽을 자료 확인

1. 요구사항에서 계획 범위와 산출물을 요약한다.
2. 파일 내용은 아직 읽지 말고, 참고하면 좋을 문서 후보의 경로와 읽어야 하는 이유를 제시한다.
3. 사용자에게 후보를 확인하고 추가·제외할 자료가 있는지 질문한다.
4. 승인받은 문서만 읽는다.
5. 승인 없이 저장소 전체, Wiki, 외부 링크 또는 첨부 문서를 임의로 읽지 않는다.

바로진료 저장소에서는 다음 파일을 후보로 우선 제안하되 반드시 확인받는다.

- `docs/plan.md`: 문제와 사용자 시나리오
- `docs/feature-spec.md`: 기능 규칙과 예외
- `docs/tasks.md`: 상위 백로그와 우선순위
- `docs/checklist.md`: 세부 작업과 현재 진행 상태
- 관련 GitHub Issue 또는 사용자가 지정한 문서

## 2. 요구사항 정리

승인된 자료를 읽은 뒤 다음을 짧게 정리한다.

- 목표와 사용자 가치
- 포함 범위와 제외 범위
- 확정된 기술·정책 제약
- 기존 계획과 중복되거나 충돌하는 부분
- 분해 전에 답이 꼭 필요한 질문

분해 결과가 크게 달라지는 질문만 먼저 한다. 답이 없어도 안전하게 분해할 수 있는 내용은 가정으로 숨기지 말고 `확인 필요`로 표시한다.

## 3. 작업 분해

큰 작업 아래에 하루 안에 완료하고 검증할 수 있는 작은 작업을 둔다. 각 작은 작업에 다음 정보를 모두 작성한다.

| 항목 | 규칙 |
|---|---|
| ID | 안정적인 짧은 ID 사용 |
| 유형 | `PLAN`, `DOC`, `ENV`, `DB`, `BE`, `FE`, `TEST` 중 하나 이상 |
| 우선순위 | `P0`, `P1`, `P2` |
| 예상 시간 | 낙관값이 아닌 구현·검증 포함 시간 단위 추정 |
| 선행 작업 | 먼저 끝나야 하는 Task ID, 없으면 `없음` |
| 완료 기준 | 관찰하거나 테스트할 수 있는 결과 |
| 위험 요소 | 외부 권한, 불확실한 정책, 기술 난도 또는 일정 위험 |

우선순위는 다음 기준을 사용한다.

- `P0`: 핵심 시나리오가 동작하려면 반드시 필요
- `P1`: MVP의 안전성·사용성·완성도를 높임
- `P2`: 외부 연동, 운영 자동화 또는 향후 확장

큰 작업과 작은 작업을 다음 순서로 출력한다.

1. 핵심 사용자 시나리오를 성립시키는 작업
2. 선행 데이터·인증·환경 작업
3. 예외 처리와 테스트
4. 문서화와 확장 작업

## 4. 기존 계획 비교

사용자가 직접 나눈 계획이나 기존 백로그가 있으면 다음을 별도 표로 비교한다.

- 누락된 작업
- 너무 큰 작업
- 중복 작업
- 잘못된 선행 순서
- 우선순위 차이
- 유지해야 할 사용자 결정

기존 결정을 임의로 바꾸지 말고 변경 제안과 이유를 구분해서 쓴다.

## 5. 일정 질문

작업 분해와 우선순위를 먼저 제시한 뒤 다음을 질문하고 응답을 기다린다.

1. 작업 시작일 또는 전체 기간
2. 마감일
3. 하루 작업 가능 시간

이 답을 받기 전에는 날짜나 요일에 작업을 임의 배치하지 않는다.

## 6. 일정 배치

기간 정보를 받은 뒤 다음 원칙으로 날짜별 계획을 작성한다.

1. 선행 관계와 P0를 먼저 배치한다.
2. 하루 예상 시간 합계가 작업 가능 시간을 넘지 않게 한다.
3. 구현과 검증을 같은 날 또는 바로 다음 작업으로 배치한다.
4. 외부 권한이나 사용자 입력이 필요한 작업은 앞쪽에 둔다.
5. 마지막 날에 통합 검증, 문서 갱신과 미완료 작업 재계획 시간을 둔다.
6. 완료된 과거 작업과 예정 작업을 명확히 구분한다.

일정 표에는 날짜, 목표, Task ID, 유형, 예상 시간, 완료 기준을 포함한다. 계획이 기간 안에 들어가지 않으면 작업을 숨기지 말고 초과 시간과 제외 후보를 제시한다.

## Do Not

- 승인 전에 문서 내용을 읽지 않는다.
- 해결책을 요구사항으로 바꾸거나 사용자의 확정 결정을 덮어쓰지 않는다.
- 여러 날이 필요한 큰 덩어리를 작은 작업 하나로 두지 않는다.
- 완료 기준을 `구현한다`, `확인한다`처럼 검증 불가능하게 쓰지 않는다.
- 예상 시간을 확정 일정처럼 표현하지 않는다.
- 기간 답변 전에 날짜별 일정을 만든다.
- 사용자의 승인 없이 파일이나 GitHub 상태를 변경하지 않는다.
