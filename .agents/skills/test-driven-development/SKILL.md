# Test Driven Development

결과와 진행 상황은 한국어로 설명한다. 한 번에 작은 기능 하나만 다루고 `시나리오 → Red → Green → Refactor → 검증` 순서를 바꾸지 않는다.

## 1. 대상 선정

1. 현재 코드와 테스트 환경을 확인한다.
2. 조건 분기와 입력·출력이 명확한 후보를 2~4개 제안한다.
3. 검증, 계산, 변환, 상태 규칙과 재발 방지할 버그를 우선한다.
4. 시각 디자인, 대규모 화면, 불안정한 외부 API는 첫 TDD 대상으로 피한다.
5. 사용자에게 대상과 범위를 확인받기 전에는 코드를 수정하지 않는다.

## 2. 시나리오 확정

구현을 읽고 따라 쓰기 전에 다음 표를 작성한다.

| 구분 | 입력·상황 | 기대 결과 | 이유 |
|---|---|---|---|
| 정상 | 대표 입력 | 정상 출력 | 핵심 동작 |
| 빈 값 | 비어 있거나 없음 | 명시된 기본값 또는 오류 | 누락 처리 |
| 경계값 | 최소·최대·임계점 | 경계 정책에 맞는 결과 | 조건 분기 |
| 실패 | 유효하지 않은 입력 | 거절 또는 빈 결과 | 오류 처리 |
| 회귀 | 과거 버그 상황 | 버그가 재현되지 않음 | 재발 방지 |

- 해당하지 않는 행은 제외하되 이유를 설명한다.
- 객체와 배열의 변경 여부, 순서, 중복과 권한이 중요하면 별도 시나리오로 추가한다.
- 기대 결과가 요구사항과 충돌하거나 모호하면 사용자에게 질문한다.
- 사용자가 시나리오를 승인한 뒤에만 테스트 파일을 만든다.

## 3. Red

1. 승인된 시나리오를 테스트 이름과 assertion으로 옮긴다.
2. 새 함수가 없어 import 단계에서 멈춘다면 동작하지 않는 최소 stub을 만든다.
3. 가장 좁은 테스트 명령을 실행한다.
4. 실패가 구현 미완성 때문에 발생했는지 확인한다.

Red 증거에는 테스트 파일, 전체·실패·통과 개수와 대표 기대값·실제값을 기록한다. 문법 오류, 잘못된 import, 환경 오류 또는 무관한 기존 실패를 Red로 인정하지 않는다.

## 4. Green

1. 실패한 테스트를 통과시키는 최소 코드만 작성한다.
2. 새 라이브러리, 확장 기능과 불필요한 추상화를 추가하지 않는다.
3. 테스트를 약하게 바꾸거나 삭제해서 통과시키지 않는다.
4. 요구사항이 바뀌어 테스트 수정이 필요하면 이유를 설명하고 사용자 승인을 받는다.
5. 동일한 좁은 테스트를 다시 실행해 모두 통과하는지 확인한다.

## 5. Refactor

1. Green 이후에만 중복, 이름, 책임과 파일 위치를 검토한다.
2. 기능을 실제 호출 지점에 연결하고 기존 중복 구현을 제거한다.
3. 동작과 테스트 기대값은 유지한다.
4. 관련 단위 테스트를 다시 실행한다.
5. 변경 범위에 맞춰 타입 검사, 린트, 통합 테스트와 빌드를 실행한다.

리팩터링할 내용이 없으면 억지로 변경하지 말고 없다고 기록한다.

## 6. 최종 검증

TDD 테스트 통과와 기능 검증을 구분한다. 테스트 통과 후 저장소의 `verify-feature` Skill이 있으면 독립 검증에 사용한다.

- 검증 Agent가 읽을 요구사항 문서는 사용자에게 먼저 확인받는다.
- 브라우저·API·DB 검증이 필요한 기능은 자동 테스트만으로 완료 처리하지 않는다.
- 외부 Supabase 데이터나 실제 메시지를 읽거나 변경하기 전에 별도 승인을 받는다.
- 결함이 발견되면 새 회귀 시나리오를 추가해 다음 Red-Green-Refactor 주기를 시작한다.

## 7. 완료 보고

다음을 간결하게 보고한다.

1. 구현한 기능과 사용자 관점 변화
2. Red에서 의도대로 실패한 증거
3. Green과 Refactor 후 통과한 테스트 개수
4. 실행한 타입 검사, 린트, 통합 테스트와 빌드
5. 미검증 범위와 남은 위험

## 금지 사항

- 시나리오 승인 전에 구현하지 않는다.
- 처음부터 구현과 테스트를 동시에 완성해 Red 증거를 생략하지 않는다.
- 현재 구현 결과를 정답으로 삼아 테스트 기대값을 맞추지 않는다.
- DB와 외부 API를 기본 단위 테스트 대상으로 선택하지 않는다.
- 무관한 코드를 함께 리팩터링하지 않는다.
- 테스트 통과만으로 전체 기능이 검증됐다고 단정하지 않는다.
