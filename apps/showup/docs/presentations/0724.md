## 발표 대본

### (1) 도입 — 문제 (1분)

안녕하세요. N167 채민석입니다.

ShowUp은 예약제로 운영하는 소상공인이 노쇼, 폭언, 환불 분쟁 같은 문제 고객을 반복해서 겪으면서도, 기록하고 예약 전에 확인할 수단이 없어 같은 피해를 계속 반복하는 문제를 해결하는 웹서비스입니다.

기존 예약 앱은 예약 접수에 집중하고, 문제 고객 이력 관리나 사전 경고 기능이 없습니다. ShowUp은 이 빈자리를 채웁니다.

핵심은 **자동 차단이 아니라 참고 지표**입니다. 사장님이 최종 판단을 내리되, 위험도를 한눈에 보여주어 판단을 돕습니다.

---

### (2) 핵심 기능 & 위험도 설계 (2분)

MVP 기능 2개를 확정했습니다.

**1. 고객 이벤트 기록** — 예약 상태(방문/노쇼/당일취소) 원터치 + 악성 행동 사건 기록(카테고리 4종 + 사실 메모)

**2. 위험도 조회 + 자동 경고** — 전화 뒤 4자리/이름 검색, 3등급 표시, 노쇼 3회+ 또는 abuse 1회+ 시 경고 배너 강제 표시

ShowUp의 차별점은 위험도 계산 로직입니다. 노쇼 +8, 폭언 +10, 정상 방문 −1로 회복됩니다. 0~23 안심, 24~39 주의, 40+ 위험 3등급이고, 폭언 1회 이상은 점수 무관 최소 주의를 보장합니다.

업계 관행은 2회 경고 3회 제한이지만, ShowUp은 3회 기준에 제한 대신 경고만 하여 사장님 재량을 보존하고 법적 리스크를 줄였습니다.

### (3) 기술 스택 & 아키텍처 (1.5분)

| 영역 | 선택 |
|------|------|
| 프론트엔드 | React + Vite + TypeScript + Tailwind CSS |
| 상태 | React hooks (TanStack Query/Zustand 전환은 미적용) |
| 폼 | React Hook Form + Zod |
| 백엔드 | Firebase (Auth / Firestore / Hosting) |
| AI 에이전트 | Hermes Agent + Ollama Pro 모델 4세션 |

Firebase를 선택한 이유는 인증과 가게별 데이터 격리가 핵심인데 Firestore Security Rules가 정확히 부합하고, 3주 기간에 서버+DB+Auth를 직접 구축하는 건 범위 초과이기 때문입니다.

데이터 흐름: 화면(React) → Firestore → riskRefresh.ts(calculateRiskStats 순수 함수) → 위험도 갱신 → RiskBadge/RiskAlertBanner 표시

### (6) AI 에이전트 운영 & 회고 (1.5분)

Hermes Agent 프레임워크 + Ollama Pro 모델 4세션으로 역할 분리 개발을 했습니다.

| 세션 | 모델 | 역할 |
|------|------|------|
| 리드 | GLM 5.2 | 기획·통합·일정·배포 |
| 프론트엔드 | Qwen 3.5 | UI·컴포넌트·라우팅·QA |
| 백엔드 | Kimi K2.7 Code | Firestore·로직·인덱스 |
| 보안 | GLM 5.2 | Rules·침투테스트·법무 |

핵심 전략:
- **인터페이스 우선**: BE가 schema.ts 확정 → FE는 mock으로 병행 개발
- **문서 기반 가드레일**: 각 세션이 건드릴/건드리지 말 파일 명시
- **단일 브랜치 역할 분리**: 세션별 커밋 접두어 (FE-/BE-/SEC-/LEAD-)

잘 된 점: 4세션 병렬 개발로 3주 만에 MVP 완성 + 배포, TDD로 위험도 로직 신뢰 확보, 발표 당시 보안 회귀 10개 PASS (최신 로컬 smoke test 18개 PASS)

어려웠던 점: Claude 구독 만료로 도구 이관, Spark 요금제로 Cloud Functions 불가 → 클라이언트 갱신으로 대체, 일정 2일 앞당김 (7/30 → 7/28)
