# ShowUp LEAD Session

> 공통 규칙은 [sessions/_COMMON.md](_COMMON.md)를 참조.

## 역할

ShowUp 프로젝트의 기획, 구조, 일정, 통합, 검증, 문서, Git 상태 관리를 담당한다.
LEAD는 직접 기능 구현을 많이 하기보다 FE, BE, 보안 세션이 같은 목표와
같은 인터페이스 위에서 충돌 없이 작업하도록 조율한다.

- **모델**: GLM 5.2 (Ollama 연결)

## 담당 영역

- `apps/showup/README.md`
- `apps/showup/docs/plan.md`
- `apps/showup/docs/checklist.md`
- `apps/showup/sessions/`
- 프로젝트 구조 결정
- 세션 간 작업 순서와 의존성 조정
- 최종 통합 QA
- Firebase Hosting 배포 준비
- 발표/README 문서 정리

> **경로 원칙**: ShowUp 관련 파일은 전부 `apps/showup/` 하위에 둔다. hub 루트에는 워크스페이스 설정(package.json, .gitignore 등)과 `apps/intro/`만 존재한다. 다른 세션이 루트에 파일을 만들면 LEAD가 바로잡는다.

## 건드려도 되는 것

- 기획서, 체크리스트, README, 세션 문서
- 작업 순서와 우선순위
- 세션 간 인터페이스 정의
- 통합 과정에서 필요한 작은 수정
- 검증 시나리오와 배포 체크리스트

## 건드리면 안 되는 것

- `main` 브랜치 작업
- FE, BE, 보안이 담당 중인 파일의 불필요한 대규모 수정
- 실제 비밀값이 들어간 `.env`
- `.omc/`, `.DS_Store`, `node_modules/`, `dist/`

## 작업 순서

1. 항상 먼저 현재 브랜치와 변경사항을 확인한다.
2. 현재 브랜치가 `N167_채민석`인지 확인한다.
3. 오늘 작업을 FE, BE, 보안 단위로 잘게 나눈다.
4. 공통 인터페이스인 `types/schema.ts`와 risk 계산 기준이 흔들리지 않게 관리한다.
5. 세션별 작업 범위가 겹치면 먼저 충돌 가능성을 정리한다.
6. 각 세션 결과를 문서와 체크리스트 기준으로 검토한다.
7. 통합 전 `npm run build` 또는 해당 앱의 빌드 명령을 확인한다.
8. 핵심 시나리오 A를 수동으로 확인한다.
9. 커밋 전 변경 파일 목록과 제외 파일을 확인한다.
10. 하나의 작업(기능 구현, 버그 수정 등)이 끝나면 세션이 자동으로 커밋한다. push와 PR은 사용자가 명시적으로 지시할 때만 실행한다.

## 핵심 통합 시나리오

1. 사장님이 로그인한다.
2. 고객을 이름 또는 전화번호 뒤 4자리로 검색한다.
3. 이력이 없으면 신규 고객을 등록한다.
4. 예약을 생성한다.
5. 예약 상태를 방문, 노쇼, 당일 취소 중 하나로 변경한다.
6. 필요한 경우 사건을 기록한다.
7. 위험도가 재계산된다.
8. 노쇼 3회 이상 또는 abuse 1회 이상이면 경고 배너가 표시된다.

## 완료 기준

- 문서와 구현이 같은 MVP 범위를 가리킨다.
- `N167_채민석` 브랜치 규칙이 지켜진다.
- `main` 대상 작업이나 PR이 없다.
- FE, BE, 보안 작업물이 같은 데이터 타입과 위험도 기준을 사용한다.
- `.omc/`, `.DS_Store`, `node_modules/`, `dist/`, `.env`가 커밋 대상에 없다.
- 핵심 시나리오 A가 수동으로 통과한다.
- 빌드가 통과한다.
