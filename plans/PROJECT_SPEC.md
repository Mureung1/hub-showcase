# AI Student Agent (MVP)

AI 기반 대학생활 의사결정 지원 에이전트

---

## 1. 프로젝트 개요

### 프로젝트명

AI Student Agent

### 프로젝트 소개

AI Student Agent는 대학생활에 흩어져 있는 다양한 정보를 스스로 수집하고, 이해하며, 우선순위를 판단하고, 실제 행동(Action)까지 수행하는 AI 기반 의사결정 지원 시스템이다.

기존 대학생활 플랫폼들은 공지나 일정을 단순히 모아 보여주는 역할에 머무른다.

반면 AI Student Agent는

- 정보를 자동으로 수집하고 (Observe)
- 정보를 이해하고 구조화하며 (Understand)
- 사용자 상황에 맞게 중요도를 판단하고 (Reason)
- **여러 일정이 충돌할 때 실질적인 재배치 시나리오를 제시하며 (Reason 확장)**
- 필요한 행동을 수행하며 (Act)
- 사용자 피드백을 통해 점진적으로 개인화되는 (Learn)

AI Agent를 목표로 한다.

---

## 2. 문제 정의

현재 대학생들은 다음과 같은 다양한 서비스를 동시에 이용한다.

- 학교 홈페이지
- 학과 홈페이지
- LMS(LearningX)
- 한국장학재단
- 청년정책 사이트
- 개인 일정

정보가 서로 연결되어 있지 않기 때문에

- 중요한 공지를 놓침
- 과제 제출을 잊음
- 장학금 신청 기간을 놓침
- 해야 할 일을 놓침
- 무엇부터 해야 하는지 판단하기 어려움
- **여러 마감(과제, 시험, 장학금, 공모전)이 동시에 겹칠 때, 단순히 "무엇이 더 중요한지"를 아는 것만으로는 부족하고 "한정된 시간을 어떻게 재배분해야 손실이 최소인지" 판단하기 어려움**

과 같은 문제가 반복적으로 발생한다.

현재 대부분의 서비스는 정보를 "제공"할 뿐, 사용자를 대신하여 정보를 종합적으로 분석하고 행동을 제안하거나 수행하지 않는다. 특히 일정이 충돌하는 상황에서는 단순 알림이나 우선순위 정렬만으로는 실질적인 도움이 되지 않는다.

## 3. 프로젝트 목표

AI Student Agent의 목표는

> "정보를 보여주는 플랫폼"

이 아니라

> "사용자를 대신하여 대학생활 정보를 분석하고, 충돌하는 상황에서 구체적인 행동 계획까지 제시하며, 실제 행동을 수행하는 AI Agent"

를 구축하는 것이다.

AI는 다양한 데이터 출처를 통합하여

- 어떤 정보가 중요한지
- 지금 무엇을 해야 하는지
- 어떤 일정이 우선인지
- **일정이 충돌할 때 어떻게 재배치해야 하는지**

를 판단하고, 필요한 경우 실제 행동(Action)까지 수행한다.

---

## 4. Agent Loop

AI Student Agent는 다음과 같은 Agent Loop를 수행한다.

```
Observe
  ↓
Understand
  ↓
Reason  (Priority 계산 + Conflict Resolution)
  ↓
Act
  ↓
Learn
```

### Observe

외부 시스템에서 데이터를 수집한다.

- 학교 공지
- 학과 공지
- LMS
- 장학금 정보

### Understand

LLM을 이용하여 비정형 데이터를 구조화한다.

예시

- 핵심 내용
- 마감일
- Action Item
- 카테고리

### Reason

사용자 상황과 데이터를 종합하여 Priority Score를 계산한다.

동일 시기에 여러 항목이 충돌하는 경우, **Conflict Resolution** 서브 루틴을 통해 단순 우선순위 정렬이 아닌 구체적인 재배치 시나리오를 생성한다. (자세한 내용은 8.4 참고)

### Act

사용자에게

- Today's Brief 생성
- Action Item 제안
- 마감 임박 알림
- **충돌 재배치 시나리오 제안**
- Google Calendar 일정 생성

등의 실제 행동을 수행한다.

### Learn

사용자의 행동을 분석하여 다음 추천에 반영한다. 재배치 시나리오에 대한 수락/거부 여부도 학습 데이터로 활용한다.

```
학교 공지 / 학과 공지 / LearningX / 장학금 API
        │

```

## 6. 데이터 수집

> 아래 각 항목은 실제 구현 가능성을 검토한 뒤 방식을 확정했다. 검토 근거는 17장 참고.

### 6.1 학교 공지 — 실현 가능

방식

- BeautifulSoup (정적 HTML)
- Playwright (JS 렌더링 필요한 경우)

수집 정보

- 제목
- 본문
- 작성일
- 마감일

비고: 공지사항 게시판은 대부분 로그인 없이 접근 가능한 공개 페이지이므로 크롤링에 법적/기술적 제약이 크지 않다. 단, `robots.txt` 준수, 요청 간격 제한(rate limiting)을 두어 서버 부담을 최소화한다. 개인정보(성적, 개인 시간표 등 로그인 필요한 정보)는 수집 대상에서 제외한다.

### 6.2 학과 공지 — 실현 가능

동일한 방식으로 수집한다. 단, 학과 홈페이지는 학교 공지보다 구조가 제각각이라 사이트별로 파서를 따로 작성해야 하는 유지보수 비용이 있다. MVP에서는 본인 학과 1곳만 우선 지원하고, 이후 확장한다.

### 6.3 LMS — 조건부 가능 (경로 확인 필요)

LearningX는 자체 개발 LMS가 아니라 **Canvas LMS 엔진 기반**으로 구축된 시스템이다. 이 점이 구현 방식에 중요한 영향을 준다.

**우선 시도할 방식: Canvas REST API**

- Canvas는 공식 REST API를 제공하며, 학생이 본인 계정에서 개인 액세스 토큰(Personal Access Token)을 직접 발급받아 사용하는 것이 표준적으로 지원되는 기능이다.
- 토큰만 있으면 서버 쪽에서 안정적으로 과제/공지/마감일 데이터를 JSON으로 받아올 수 있어, DOM 크롤링보다 훨씬 안정적이고 유지보수 부담이 적다.
- **확인 필요 사항**: 일부 대학은 관리자 정책으로 학생 계정의 개인 액세스 토큰 발급 기능을 막아두는 경우가 있다. 본인 학교의 LearningX에서 [계정 설정 → 승인된 통합 앱] 메뉴에 토큰 발급 옵션이 실제로 노출되는지 먼저 확인해야 한다.

**대안 방식: Chrome Extension DOM 스크래핑 (Canvas API가 막혀있을 경우)**

- 서버는 로그인하지 않고, 사용자의 브라우저에서만 DOM을 분석한다. 사용자 본인의 로그인 세션을 그대로 활용하므로 별도 인증 우회가 필요 없다.
- 단점: LMS UI가 업데이트되면 파서가 깨질 수 있어 유지보수 부담이 크다. 포트폴리오 MVP 범위에서는 감당 가능한 수준이지만, 실서비스로 확장할 경우 리스크로 남는다.

MVP 범위: LearningX만 지원하며, Week 1에 Canvas API 토큰 발급 가능 여부를 먼저 확인한 뒤 방식을 확정한다.

JSON 구조 (두 방식 모두 동일한 출력 스키마로 정규화)

```json
{
  "course": "운영체제",
  "title": "Assignment 3",
  "deadline": "2026-07-20",
  "type": "assignment"
}
```

### 6.4 장학금 — 실현 가능 (경로 수정)

한국장학재단(kosaf.go.kr) 사이트를 직접 크롤링하는 대신, **공공데이터포털의 오픈API**를 사용한다.

- 공공데이터포털에는 한국장학재단이 제공하는 `전국대학별장학금정보표준데이터`, `학자금지원정보(대학생)` 등의 오픈API가 실제로 등록되어 있으며, 회원가입 후 활용신청만 하면 사용 가능하다.
- 개발계정 기준 일 1,000건 트래픽 제한이 있으나 MVP 데모 목적으로는 충분하다.
- 직접 사이트 크롤링보다 데이터가 구조화되어 있어 Understand 단계 부담이 줄어드는 부수 효과도 있다.

### 6.5 청년정책 (온통청년) — 실현 가능하나 일정 리스크 있음

온통청년(youthcenter.go.kr)도 오픈API를 공식 제공한다. 다만 다음 제약이 있다.

- API 인증키 발급에 **담당자 심사 승인 절차**가 있어, 신청 후 승인까지 걸리는 시간을 예측하기 어렵다.
- 4주 MVP 일정에서 승인 대기가 병목이 될 수 있으므로, **Week 1에 미리 신청**해두고 승인 전까지는 목업(mock) 데이터로 개발을 진행한다.
- 승인이 일정 내에 나지 않으면 MVP 데모에서는 제외하고 "향후 확장" 항목으로 내려도 무방하다. 핵심 가치(Observe-Understand-Reason-Act-Learn 루프)를 보여주는 데는 학교 공지 + LMS + 장학금 3개 소스만으로도 충분하다.

## 7. AI Pipeline

### Step 1. 공지 요약

긴 공지를 핵심 내용 / 해야 하는 행동 / 마감일로 압축한다.

### Step 2. 정보 구조화

LLM이 비정형 텍스트를 다음 형태로 변환한다.

```json
{
  "category": "Scholarship",
  "deadline": "2026-07-20",
  "action": "Apply",
  "importance": "High"
}
```

### Step 3. Priority 계산

AI는 사용자 프로필과 공지를 비교하여 Priority Score를 계산한다.

### Step 4. Conflict Resolution (신규)

같은 기간 내 충돌하는 항목들이 감지되면, LLM이 재배치 시나리오를 생성한다. (8.4 참고)

---

## 8. Priority Engine

### 8.1 Priority Score

```
S = w1 × Interest + w2 × Deadline - w3 × Conflict + w4 × Irreversibility
```

### 8.2 Interest

사용자의 학과 / 학년 / 관심 분야와 공지 임베딩의 Cosine Similarity를 이용한다.

공지 임베딩은 생성 후 캐싱하여 불필요한 API 호출을 줄인다.

### 8.3 Deadline

```
Deadline Score = 1 / (Remaining Days + 1)
```

남은 시간이 적을수록 Priority가 증가한다.

### 8.4 Conflict Resolution (신규 확장)

기존 Conflict 항목은 동일 날짜에 존재하는 과제 / 시험 / 발표 개수를 기반으로 패널티만 부여했다. 여기서는 한 단계 더 나아가, 충돌이 감지된 항목들에 대해 **구체적인 재배치 시나리오**를 생성한다.

#### 8.4.1 Irreversibility 개념 도입

충돌 해결의 핵심 판단 기준으로 "되돌릴 수 없는 정도(Irreversibility)"를 도입한다.

| 카테고리 | Irreversibility | 근거 |
|---|---|---|
| 장학금 신청 | High | 마감 후 재신청 불가 |
| 시험 | High | 응시 기회 상실 |
| 과제 제출 | Medium | 지각 제출/감점으로 일부 복구 가능 |
| 공모전 서류 | Low~Medium | 다음 회차 존재 가능 |
| 동아리/비교과 활동 | Low | 유연하게 일정 조정 가능 |

이 값은 카테고리 기반 룰로 시작하며, 필요시 LLM이 공지 본문에서 "재신청 가능 여부", "지각 제출 허용 여부" 같은 문구를 추출해 보정한다.

#### 8.4.2 충돌 감지 → 재배치 시나리오 생성 흐름

```
1. 동일 기간(예: 3일 이내) 내 마감이 겹치는 항목 그룹화
2. 각 항목의 Deadline, Irreversibility, 예상 소요시간 정리
3. 사용자의 가용 시간(캘린더 여유 시간) 조회
4. LLM에게 구조화된 데이터 전달 → 재배치 시나리오 생성 요청
5. 결과를 JSON(+ rationale)으로 반환
6. Action Engine을 통해 사용자에게 제안
```

#### 8.4.3 LLM 입출력 예시

**입력 (구조화된 데이터)**

```json
{
  "conflict_group": [
    {"item": "운영체제 과제", "deadline": "2026-07-20", "irreversibility": "medium", "estimated_hours": 4},
    {"item": "국가장학금 신청", "deadline": "2026-07-19", "irreversibility": "high", "estimated_hours": 1},
    {"item": "SW경진대회 서류", "deadline": "2026-07-25", "irreversibility": "low", "estimated_hours": 3}
  ],
  "user_available_hours": {
    "2026-07-18": 3,
    "2026-07-19": 2,
    "2026-07-20": 4
  }
}
```

**출력 (재배치 시나리오 + rationale)**

```json
{
  "resolution": {
    "strategy": "재배치",
    "plan": [
      {
        "item": "국가장학금 신청",
        "action": "7/18 저녁 즉시 처리",
        "reason": "Irreversibility가 가장 높고 소요시간이 짧아 우선 처리 시 리스크 대비 비용이 가장 낮음"
      },
      {
        "item": "운영체제 과제",
        "action": "7/20 오전으로 조정, 7/19 저녁에 미리 착수 권장",
        "reason": "마감일 당일 4시간 확보 가능하나 여유를 위해 하루 앞당김 제안"
      },
      {
        "item": "SW경진대회 서류",
        "action": "현재 우선순위 보류, 7/22 재평가",
        "reason": "마감까지 여유 있고 Irreversibility가 낮아 다음 우선순위 계산에서 재검토"
      }
    ]
  }
}
```

이 출력은 반드시 구조화된 JSON + `reason` 필드를 포함해야 한다. Agent가 "왜 이렇게 판단했는지"를 사용자와 개발자 모두에게 투명하게 보여주는 것이 이 기능의 핵심 가치다.

#### 8.4.4 설계 시 유의점

- 완벽한 최적화 알고리즘을 목표로 하지 않는다. LLM이 1~2개의 합리적인 재배치 시나리오를 제시하는 것으로 충분하다.
- Irreversibility 값은 초기에는 단순 룰 기반으로 하드코딩하고, 향후 공지 본문 기반 추출로 고도화할 수 있음을 명시한다.
- 사용자가 시나리오를 거부하는 경우, 그 이유(예: "이미 다른 계획이 있음")를 간단히 태깅해 Learn Engine에 반영한다.

## 9. Action Engine

AI Agent는 추천에서 끝나지 않는다. 실제 행동을 수행한다.

### 9.1 Today's Brief

사용자에게 현재 가장 중요한 작업을 생성한다.

예시

```
★★★★★ 운영체제 과제 제출
★★★★☆ 국가장학금 신청
★★★★☆ SW 경진대회 신청
```

### 9.2 Notification

Priority를 주기적으로 다시 계산한다.

다음 조건을 만족하면 사용자에게 능동적으로 알림을 제공한다.

- 마감 임박
- 새로운 중요 공지
- Priority 변화
- **새로운 충돌이 감지되어 재배치 시나리오가 생성됨**

MVP

- 웹 알림 배너
- 이메일 알림

### 9.3 Conflict Resolution 제안 (신규)

충돌이 감지되면 Today's Brief 상단에 별도 카드로 재배치 시나리오를 노출한다.

예시

```
⚠ 일정 충돌 감지
운영체제 과제 · 국가장학금 신청 · SW경진대회 서류가 3일 내 겹칩니다.

AI 제안:
1. 국가장학금 신청을 오늘 저녁 먼저 처리 (재신청 불가 항목)
2. 운영체제 과제는 내일 오전으로 조정
3. SW경진대회는 다음 우선순위 계산 시 재평가

[제안 수락]  [내가 직접 조정]
```

사용자가 [제안 수락]을 누르면 9.4 Google Calendar Action으로 이어진다.

### 9.4 Google Calendar Action

공지에서 날짜 / 시간 / 이벤트를 추출한다.

AI는 Google Calendar 등록을 제안한다. 충돌 재배치 시나리오가 수락된 경우, 조정된 일정 그대로 Calendar에 반영한다.

사용자가 승인하면 Google Calendar API를 이용하여 일정을 자동 생성한다.

예시

```
공지: SW 경진대회 7월 20일 13:00
  ↓
AI: Google Calendar에 등록하시겠습니까?
  ↓
승인
  ↓
Calendar 생성
```

상대 날짜 표현이나 날짜 추출 실패 시 "확인 필요" 상태로 표시하며 사용자가 수정 후 등록한다.

## 16. 기대 효과

AI Student Agent는 단순한 대학생활 관리 플랫폼이 아니다.

분산된 대학생활 정보를 AI가 자동으로 수집하고, 이해하며, 우선순위를 판단하고, 실제 행동까지 수행하는 AI 기반 의사결정 지원 에이전트이다.

특히 여러 마감이 동시에 겹치는 상황에서, 단순히 "무엇이 중요한지"를 알려주는 데 그치지 않고 "한정된 시간을 어떻게 재배분해야 손실이 최소인지"에 대한 구체적인 판단과 근거(rationale)를 제시함으로써, 기존의 우선순위 정렬 기반 서비스와 명확히 차별화된다.

학생은 여러 시스템을 반복적으로 확인할 필요 없이 AI가 생성한 Today's Brief와 Action Item, 그리고 충돌 상황에 대한 재배치 제안을 통해 현재 가장 중요한 일을 즉시 파악할 수 있으며, 필요한 일정은 Google Calendar와 연계하여 실제 행동으로 이어질 수 있다.

이를 통해 대학생활에서 발생하는 정보 탐색 비용과 의사결정 부담을 줄이고, 중요한 공지와 과제를 놓치는 문제, 그리고 여러 마감이 겹칠 때 발생하는 의사결정 마비(decision paralysis)를 최소화하는 것을 목표로 한다.

## 17. 실현 가능성 종합 검토

MVP에 포함된 모든 데이터 소스와 기능을 실제 구현 가능 여부 기준으로 재검토했다. Claude Code로 구현을 시작하기 전 아래 표를 기준으로 우선순위와 대안 경로를 확정한다.

| 항목 | 원래 계획 | 실현 가능성 | 확정 방식 |
|---|---|---|---|
| 학교 공지 수집 | BeautifulSoup/Playwright 크롤링 | **가능** | 공개 게시판 크롤링, robots.txt 준수. 변경 없음 |
| 학과 공지 수집 | 동일 방식 | **가능** (사이트별 유지보수 비용 있음) | MVP는 본인 학과 1곳만 우선 지원 |
| LMS(LearningX) 연동 | Chrome Extension DOM 스크래핑 | **조건부 가능** | LearningX가 Canvas 엔진 기반이므로 **Canvas 개인 액세스 토큰 + REST API를 우선 시도**. 학교가 토큰 발급을 막아둔 경우에만 Chrome Extension으로 대체 |
| 장학금 정보 | 한국장학재단 직접 크롤링 | **원래 방식은 비권장, 대안은 가능** | kosaf.go.kr 직접 크롤링 대신 **공공데이터포털 오픈API**(전국대학별장학금정보표준데이터 등) 사용. 신청 즉시 이용 가능, 일 1,000건 제한 |
| 청년정책(온통청년) | 공공 API 연동 | **가능하나 승인 지연 리스크** | 오픈API 자체는 존재하나 인증키 발급에 담당자 심사 필요. Week 1 조기 신청, 승인 전엔 목업 데이터 사용. 4주 내 미승인 시 MVP에서 제외하고 향후 확장으로 이동 |
| Google Calendar 연동 | Google Calendar API | **가능** | 표준 OAuth 2.0 플로우, 공식 문서화가 잘 되어 있어 리스크 낮음 |
| LLM 요약/구조화/우선순위/충돌 재배치 | OpenAI/Gemini API | **가능** | 외부 API 의존이므로 기술적 리스크 낮음. 프롬프트 설계와 출력 스키마 검증(JSON schema validation)이 핵심 작업 |

### 핵심 판단

1. **가장 큰 리스크는 크롤링이 아니라 LMS 연동 방식과 온통청년 API 승인 시점**이다. 학교 홈페이지/학과 공지 크롤링은 기술적으로 어려운 부분이 아니다.
2. LearningX가 Canvas 기반이라는 사실을 활용하면, 원래 계획한 Chrome Extension보다 훨씬 안정적인 구현이 가능하다. **Week 1 첫째 날에 Canvas API 토큰 발급 화면이 실제로 노출되는지부터 확인**하는 것을 최우선 작업으로 둔다.
3. 온통청년은 포트폴리오의 핵심 가치(Agent Loop, Priority Engine, Conflict Resolution)를 보여주는 데 필수는 아니므로, 승인이 늦어지면 과감히 제외하고 학교 공지 + LMS + 장학금 3개 소스로 데모를 완성하는 쪽으로 스코프를 조정한다.
4. 크롤링 대상은 모두 로그인 없이 접근 가능한 공개 정보로 한정했으며, 개인정보(성적, 개인 시간표 등)는 수집하지 않는다는 원칙을 유지한다.
