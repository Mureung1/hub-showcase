## 설계 결정 사항

### 1. 다중 시험 후보 그리드 간격 (월요일, 2026-07-20)

#10(그리드 결정변수 정의) 이슈 본문에는 "30분 단위"로 적혀있었지만, **2주차 단일 시험 탐색([singleExamScheduleSearch.ts](../server/src/calc/singleExamScheduleSearch.ts))과 동일하게 15분 간격, ±1시간 범위**를 그대로 유지하기로 했다.

- 날짜 축이 늘어나면서 후보 조합 수가 커지는 건 사실이지만, 그리드 간격을 성기게(30분) 만들어 줄이기보다는 #12(로컬 탐색)가 후보 전체를 한 번에 다 평가하지 않는 방식으로 조합 폭발을 감당하기로 했다(아래 "축 단위 반환" 참고)
- 간격을 2주차와 다르게 가져가면 두 탐색기의 정밀도가 달라져서, "시험이 1개일 때 2주차 결과와 같은가"를 비교 검증하기도 번거로워짐

### 2. 최소 수면시간(및 남은 공부시간) 제약 처리 단계 (월요일, 2026-07-20)

#10 이슈 본문엔 "최소 수면시간·남은 공부 시간 확보 제약을 후보 생성 단계에서 걸러낼지 평가 단계에서 걸러낼지 결정 필요"라고 되어 있었는데, **평가 단계(#11, 목적함수)에서 패널티로 처리**하기로 결정했다.

- [2주차_계획.md](./2주차_계획.md) 3.2에 이미 적혀있던 3주차 방향("후보×후보 반복 + **패널티/가중치 점수화**", Vital-Lopez 방식)과 일치
- 후보 생성 단계에서 아예 배제하면 이분법(포함/제외)이라, 나중에 "제약 강도"를 조정하고 싶어질 때(예: 살짝 못 미쳐도 보여주되 점수만 깎기) 배제 로직 자체를 다시 설계해야 함. 패널티 방식이면 가중치 값만 조정하면 됨
- 사용자가 최소 수면시간을 아주 타이트하게 잡았을 때 후보 생성 단계에서 배제하면 유효 후보가 하나도 안 남아 #12(로컬 탐색)가 옮겨갈 이웃이 없어질 위험이 있는데, 패널티 방식은 후보 자체가 항상 존재해서 이 위험이 없음
- 따라서 [multiDayCandidates.ts](../server/src/calc/multiDayCandidates.ts)(#10)는 "카페인을 기상 전에 마시는" 것처럼 물리적으로 말이 안 되는 조합만 제외하고, 최소 수면시간 미달 여부는 판단하지 않는다 — 그 판단은 #11에서 구현

### 3. #10 후보 생성 함수의 반환 형태 — "축 단위" 반환 (월요일, 2026-07-20)

여러 밤 × 여러 카페인 섭취의 전체 조합(cartesian product)을 미리 다 만들지 않고, **밤별/카페인별로 가능한 후보 목록("축")만 따로따로 반환**하도록 설계했다.

- 예: 밤이 3개면 완전탐색 기준 `81^3`가지인데, 이걸 다 만드는 대신 `nightOptions = [night0의 81개, night1의 81개, night2의 81개]` 형태로만 반환
- #12(로컬 탐색, simulated annealing류)가 매 반복마다 축 하나를 무작위로 골라 그 축 안에서 인접한 값으로 옮겨가는 방식으로 탐색하므로, 전체 조합을 미리 만들 필요가 없음

### 4. 여러 시험 점수 합산 방식 — 최솟값(min) 채택 (월요일, 2026-07-20)

#11(목적함수) 이슈 본문의 "총합 또는 최솟값" 중 **최솟값(min)**을 쓰기로 했다.

- 총합(sum)은 한 시험에 유리하게 몰아주고 다른 시험을 희생해도 전체 점수는 높게 나올 수 있는 반면, 최솟값은 "가장 컨디션 나쁠 시험"을 최대한 끌어올리는 방향이라 시험 간 형평성이 보장됨
- [multiDayObjective.ts](../server/src/calc/multiDayObjective.ts)의 `scoreMultiDaySchedule()`이 시험별 점수(`examScores`)와 그 최솟값(`score`)을 함께 반환하도록 구현 — 최솟값 위주로 쓰되, 개별 점수도 그대로 노출해서 나중에 다른 합산 방식이 필요해지면 `examScores`만으로 재계산 가능

### 5. 다중 밤(#11) 구간의 좌표 규칙 — night[i]는 반드시 24×i를 포함해야 함 (월요일, 2026-07-20)

[candidateSleepSegments.ts](../server/src/calc/candidateSleepSegments.ts)에 추가한 `buildMultiNightSegments()`는 여러 밤을 이어붙일 때 **각 밤의 시각이 연속 타임라인 좌표(같은 날은 겹치지 않게 24시간씩 밀린 값)로 들어온다는 전제**로 동작한다:

```
night[i].bedTime  = habitualBedTime  + 24×i
night[i].wakeTime = habitualWakeTime + 24×(i+1)
```

- 처음엔 "밤마다 그냥 그날의 몇 시(원시 시각)"만 넘기면 되는 줄 알았는데, 그렇게 하면 이틀째 이후부터 수면 구간의 경과 시간이 잘못 계산되는 버그가 남(자정을 넘기는 취침→기상 구간을 매번 명시적으로 24시간 밀어줘야 하기 때문). 그래서 [multiDayCandidates.ts](../server/src/calc/multiDayCandidates.ts)(#10)를 호출할 때부터 이 규칙대로 `habitualBedTime`·`habitualWakeTime`에 24×dayIndex를 미리 반영해서 넘겨야 함
- **#12(로컬 탐색)도 이 규칙을 그대로 지켜야 함** — 후보를 조합할 때 밤 순서가 바뀌거나 좌표 규칙이 깨지면 수면압 계산 자체가 틀어짐
- 검증: 밤 1개(N=1)일 때 이 함수의 결과가 2주차 `buildCandidateSegments()`와 정확히 같은 점수를 내는지 [verifyMultiDayObjective.ts](../server/src/scripts/verifyMultiDayObjective.ts)에서 회귀 확인함(일주기리듬 C(t)가 24시간 주기라, 전체를 24시간만큼 밀어도 점수는 그대로 나온다는 성질을 이용)
