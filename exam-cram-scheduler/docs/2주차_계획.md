## 1. 이번 주 목표

**화면 없이도, 순수 함수/스크립트로 "입력 → 시험 시작 시각에 각성도가 최고가 되는 단일 시험 스케줄"까지 끝에서 끝까지 계산되는 상태를 만든다.**

카페인 없는 기본 각성도 곡선(S+C) → 카페인 얹은 곡선(P(t)) → 시험 1개 기준 역산까지가 이번 주 범위다. 다중 시험 최적화·Supabase·화면 연동은 3주차([개발_일정.md](./개발_일정.md) 2절).

### 왜 이 순서인가

"시험 시작 시각에 맞춰 최적 수면·카페인 시각을 뽑아내는 것"이 이 서비스의 핵심 가치이고, 안전 한도는 그 위에 얹는 제약 조건이다. 그래서 목요일엔 **4.1(역산)을 4.2(안전 한도)보다 먼저** 만든다 — 역산이 "진짜 되는지"부터 확인하고, 그다음에 한도로 다듬는 순서가 핵심 시나리오를 더 빨리 눈으로 볼 수 있게 해준다. 화~수(S/C/카페인 곡선)는 역산의 재료라서 그대로 앞에 둔다.

## 3. 설계 결정 사항

### 3.1 카페인 근사 함수 (월요일 확정)
정확한 Hill 방정식 계수를 논문에서 못 구해서, 공개된 표준 포화형 용량-반응 곡선(Hill/Michaelis-Menten 형태)으로 근사한다. ([계산_모델_리서치.md](./계산_모델_리서치.md) 2장 참고)

### 3.2 목요일 "목표 각성 시각 역산" 구현 방식
**패널티·가중치 없는 단순 탐색**으로 구현한다: 취침·기상·카페인 시각 후보 몇 개를 돌려서 시험 시작 시각의 P(t)를 가장 높이는 조합을 직접 고른다.

3주차의 "다중 시험 통합 최적화"(Vital-Lopez 방식: 후보×후보 반복 + 패널티/가중치 점수화)는 이 구조를 그대로 사용한다:

```
for 후보스케줄 in (수면 후보 × 카페인 후보):
    각 후보의 P(t) 곡선을 구한다
    → 이 곡선이 "시험 시작 시각에 각성도가 얼마나 높은지"로 후보를 채점한다   ← 목요일에 만드는 부분
    모든 시험에 대해 이 채점을 합산/가중합해서 최선의 후보를 고른다          ← 3주차에 얹는 부분
```

즉 목요일 작업은 버리는 임시 버전이 아니라 **최적화 루프 안에서 후보 하나를 채점하는 함수** 그 자체다. 아직 검증되지 않은 S/C/카페인 함수 위에 3주차용 무거운 탐색 로직까지 한 번에 얹으면, 버그가 생체수학 계산 문제인지 최적화 로직 문제인지 구분이 안 되기 때문에 이번 주엔 단순 탐색으로 먼저 검증한다.

### 3.3 안전 섭취 한도(4.2)는 로직만 — 화면(UI)이 아님
카페인 한도 근접 시 경고 배너 **UI는 이미 FE에 만들어져 있다** ([spec.md](./spec.md) — 스케줄 조정 화면, mock 데이터로 동작 중). 목요일 4.2는 그 배너가 참조할 **판단 로직(BE 순수 함수)** 만 만든다 — 연령/건강상태별 한도, 오늘 섭취량 차감, 초과 여부 반환. 화면에 실제로 연결하는 건 3주차다.

## 4. 참고: BE-FE 연결 시점

이번 주(2주차)는 계산 로직을 화면과 무관하게 순수 함수/스크립트로만 완성한다. 화면은 계속 mock 데이터로 동작한다.

- **3주차 화(07/21)**: `POST /api/schedule/calculate` 엔드포인트로 계산 로직 전체(S+C+카페인+역산+안전한도+최적화)를 하나의 API로 묶는다. 여기서 처음 "연결 지점"이 생긴다.
- **3주차 수(07/22)**: 정보 입력 화면 "계산하기"가 실제 API를 호출하도록 교체, 처리 중 화면도 실제 응답을 기다리도록 교체.
- **3주차 목(07/23)**: 결과 화면이 API 응답으로 실제 렌더링 + `localStorage` 저장.

계산 로직이 화면 없이 먼저 검증되어야, 이후 문제가 생겼을 때 "API 연결 문제"인지 "계산 자체 문제"인지 구분할 수 있다.
