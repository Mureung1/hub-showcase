# 서비스 기술 지도

> [기획서.md](./기획서.md) 기반으로 작성. FE/BE/DB 기술 스택과 핵심 기능 하나의 요청→응답 흐름을 정리한다.

## 7.1 내 서비스 기술 지도

FE / BE / DB에 각각 무엇을 둘지, 어떤 기술로 할지.

| 층 | 무엇을 둘까 | 어떤 기술 |
|---|---|---|
| FE | 시험 일정/수면패턴/카페인 입력 폼, 캘린더 UI, 각성도 그래프·타임라인 시각화, 슬라이더 기반 스케줄 조정 UI, 계산 결과는 브라우저 localStorage에 저장 | React |
| BE | 입력값을 받아 Two-Process Model + 카페인 상호작용 모델(UMP)로 최적 스케줄 계산하는 API, 음료별 카페인 함량·안전 섭취 기준 등 참고 데이터 제공 API | Express |
| DB | 음료별 카페인 함량표, 민감도 3단계별 반감기 값, 연령/건강상태별 안전 섭취 한도 기준 등 참고용 정적 데이터만 저장 (사용자 스케줄은 저장 안 함 — localStorage로 대체) | Supabase (Postgres) |

**결정 배경**
- 기획서 7장 "향후 고려 기능"에서 계정 동기화는 인증/DB 구축 부담으로 이번 4주 범위 밖으로 명시 → 사용자 스케줄은 DB에 저장하지 않음
- 대신 6.2/6.3장의 참고 수치(카페인 함량, 반감기, 안전 한도)를 DB에 두면 코드 재배포 없이 값 수정이 가능하고, BE/DB 계층이 실질적인 역할을 가짐
- Supabase는 예시 템플릿과 동일하고 Express와 연동이 쉬우며, 향후 계정 기능 확장 시 Auth를 그대로 활용 가능

## 7.2 핵심 기능 하나: 계산하기 (입력 → 계산 엔진)

기획서 3장 "기능 1. 정보 입력 → 검증된 계산 엔진"에 대한 요청→응답 흐름.

| 화면 동작 | 요청 (메서드+경로) | 서버 처리 | DB | 응답 | 화면 변화 |
|---|---|---|---|---|---|
| 정보 입력 화면에서 "계산하기" 클릭 | `POST /api/schedule/calculate` | ① 입력값 검증(필수 항목 누락 체크) → ② DB에서 카페인 민감도별 반감기, 연령/건강상태별 안전 섭취 한도 조회 → ③ Two-Process Model(Process S/C)로 기본 각성도 곡선 계산 → ④ UMP로 카페인 섭취 효과 결합 → ⑤ 각 시험 시각의 목표 각성 시각 역산(이동시간·여유시간 반영) → ⑥ 로컬 탐색 휴리스틱으로 다중 시험 통합 최적 스케줄 탐색 → ⑦ 오늘 이미 섭취한 카페인 잔존량 계산 후 안전 한도 초과 여부 판정 | `caffeine_reference`(음료별 함량), `sensitivity_halflife`(민감도별 반감기), `safety_limits`(연령/건강상태별 한도) 테이블 SELECT만 수행. 사용자 입력·계산 결과는 저장 안 함 | `200 OK` — `{ alertnessTimeline, recommendedSchedule, warnings }` (입력 오류 시 `400`) | 처리 중 화면(타이머로 단계 텍스트 연출) → 응답 도착 시 결과 화면으로 전환 → 각성도 그래프·추천 타임라인 렌더링, `warnings`가 있으면 경고 배너 노출 |

**결정 배경**
- "처리 중" 화면의 단계별 텍스트는 실제 서버 진행 상황이 아니라 프론트 타이머 연출로 처리 — 단일 POST 요청→응답 구조로 4주 일정에 맞게 단순화
- 요청 바디의 구체적 필드명과 DB 테이블 스키마는 추후 별도로 확정 예정
