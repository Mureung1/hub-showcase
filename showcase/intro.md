# AI와 3주간 어떻게 일했나

> 냉장고 레시피 앱(`fridge-recipe-app`)을 만들며 3주간 AI와 협업한 방식을 정리한 문서입니다.
> 무엇을 만들었는지가 아니라, **어떤 순서로 일하고 어떤 Skill·Agent를 썼는지**에 초점을 둡니다.

---

## 한 줄 요약

AI에게 코드부터 시키지 않았다. **계획 → 검증 → 구현 → 리뷰 → 문서화**를 하나의 반복 루프로 돌렸고, 그 각 단계를 전용 Skill과 Agent에 맡겨 "AI가 방향을 멋대로 정하는" 문제를 막았다.

---

## 1. 일하는 순서 (하루 단위 루프)

3주 내내 거의 같은 사이클을 반복했다. 핵심은 **코드를 쓰기 전에 항상 계획과 컨텍스트 확인을 먼저 한다**는 것.

```
① 계획 세우기      ② 컨텍스트 재확인      ③ 구현
   (무엇을 왜)   →   (진짜 그런지 코드로)  →  (최소 변경)
        ↑                                        │
        │                                        ▼
   ⑤ 문서화 ←──────  ④ 검증 & 리뷰  ←────────────┘
   (backlog 갱신)     (curl/브라우저 + 코드리뷰)
```

**① 계획 세우기.** 그날 할 일을 `docs/`의 계획 문서(`3주차 계획수립.md`)에 먼저 적는다. 목표를 정하고, 잔여 작업(`backlog.md`)에서 우선순위(P0/P1/P2)를 골라 그날 분량으로 배분한다.

**② 컨텍스트 재확인.** 계획이 실제 코드와 맞는지 확인한다. 문서와 코드가 자주 벌어지기 때문에, "여전히 재현되는 버그"인지 코드 라인까지 짚어 검증한 뒤에야 착수한다. (예: `store.js:806-818`의 크래시가 아직 살아있는지 직접 확인)

**③ 구현.** 최소 변경 원칙으로 고친다. 새 추상화·의존성을 함부로 늘리지 않고, 이미 있는 헬퍼·패턴을 먼저 찾아 재사용한다.

**④ 검증 & 리뷰.** 고친 것을 반드시 실제로 돌려본다 — `curl`로 API를 때려보거나 브라우저로 직접 클릭한다. 그 다음 `/code-review`로 사람이 아닌 도구로 회귀를 잡는다.

**⑤ 문서화.** 그날 한 일을 `backlog.md`에 날짜별로 기록하고, 새로 알게 된 함정은 `CLAUDE.md`에 컨벤션으로 남긴다. 다음 세션의 AI가 같은 실수를 반복하지 않도록.

## 2. 쓰는 Skill

작업 성격별로 전용 Skill을 나눠 썼다. 가장 많이 의존한 건 **최소 구현을 강제하는 `ponytail` 계열**과 **기획을 먼저 강제하는 계열**이다.

### 계획·기획 단계
| Skill | 언제 쓰나 | 하는 일 |
|---|---|---|
| `service-planning-with-ai` | 새 기능/서비스 방향을 잡을 때 | 문제정의 → 사용자 시나리오 → 화면흐름 → 핵심기능 → MVP 범위로 좁힘. **코드부터 짜지 못하게** 기획을 앞세움 |
| `planning-visualization` | 흐름을 그림으로 볼 때 | 유저플로우·IA·와이어프레임을 mermaid 등으로 시각화 |

### 구현 단계 — `ponytail` 계열 (과설계 방지)
| Skill | 하는 일 |
|---|---|
| `ponytail` | 모든 코딩 작업에 상시 적용. "이게 존재할 필요가 있나(YAGNI) → 이미 있나 → 표준 라이브러리로 되나 → 한 줄로 되나" 사다리를 타며 **가장 게으른(=간결한) 해법**을 강제 |
| `ponytail-review` | diff를 과설계 관점으로만 리뷰 — 지울 것 찾기 |
| `ponytail-audit` | 저장소 전체를 훑어 삭제·단순화 후보를 랭킹 |
| `ponytail-debt` | 코드에 남긴 `ponytail:` 주석(의도적 지름길)을 부채 장부로 수집 |

### 문서·산출물 단계
`docx`·`pptx`·`xlsx`·`pdf` — 문서/발표/스프레드시트 산출물을 만들 때. **원칙: 조사·검증을 먼저 끝낸 뒤에만** 서식 Skill을 불러 산출물을 만든다.

## 3. 쓰는 Agent

무거운 판단이나 격리된 작업은 전용 Agent에게 위임했다.

**`feature-slice` (직접 만든 계획 에이전트).** 요구사항을 반나절~하루 크기의 작업으로 쪼개고 우선순위를 매기는 역할만 한다. **코드는 건드리지 않는다**(`Read`/`Grep`/`Glob`만 가짐). 쪼개기 전에 반드시 관련 코드를 먼저 훑게 해서, "이미 있는 걸 새로 구현으로 착각"하는 가장 흔한 실수를 막는다.

**검증용 서브에이전트.** 고위험 작업은 별도 에이전트에 검증을 맡겨, 구현한 주체와 검증하는 주체를 분리했다.

> 핵심 설계: **Agent에 도구를 일부러 적게 준다.** `feature-slice`가 코드를 못 고치게 막은 것처럼, 권한을 좁혀야 에이전트가 역할 밖으로 벗어나지 않는다.

## 4. 3주간 실제로 이렇게 돌아갔다 (예시)

| 일차 | 계획 → 검증 → 구현 → 리뷰 → 문서화 |
|---|---|
| Day 11 | P0 버그 2건 계획 → 코드로 재현 확인 → 수정 → `/code-review`로 5건 추가 발견·처리 → backlog 기록 |
| Day 12 | FE 리렌더 원인 계획 → `useMemo` 누락 등 확인 → 5건 수정 → 브라우저 클릭 검증 → 기록 |
| Day 13 | v2 알고리즘 연결 계획 → 사용자 요청으로 OCR 실연동 먼저 → 구현 → curl 회귀 테스트 |
| Day 14 | 테스트 도입 계획 → 순수 함수 20건 단위 테스트 작성 + 백엔드 린터(oxlint) 도입 |
| Day 15 | 문서 정합화 → `CLAUDE.md`↔실제 파일명 불일치 해소 → algorithms 단일 소스 통합 |

## 5. 3주간 배운 협업 원칙

1. **코드보다 계획을 먼저.** 기획 없이 구현에 들어가면 AI가 방향을 멋대로 정한다. 기획 Skill로 이걸 구조적으로 막았다.
2. **AI를 믿되 코드로 검증.** 문서가 "고쳤다"고 해도 코드 라인으로 재확인. `curl`·브라우저·`/code-review`로 회귀를 도구가 잡게 했다.
3. **간결함을 기본값으로.** `ponytail`로 과설계를 상시 억제. 가장 짧게 동작하는 해법이 옳은 해법.
4. **에이전트 권한은 좁게.** 역할에 맞는 도구만 줘서 에이전트가 선을 넘지 않게 했다.
5. **다음 세션을 위해 기록.** 배운 함정을 `CLAUDE.md`·`backlog.md`에 남겨, AI가 매번 같은 실수를 반복하지 않게 했다.
