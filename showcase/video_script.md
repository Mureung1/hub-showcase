# 데모 영상 스크립트 — PM 가설 검증 인터뷰 분석 도구

목표 러닝타임: 4:30 ~ 4:50 (5분 미만)
형식: 화면 녹화 + 음성 내레이션 (자막 병행 권장)

---

## 0. 오프닝 (0:00 - 0:20) — 문제 정의

**화면**: 타이틀 슬라이드 또는 검은 화면에 텍스트
**내레이션**:
> "PM이 유저 인터뷰를 끝내고 나면, 가설별로 답변을 정리하고 결론을 내리는 데 많은 시간이 듭니다.
> ChatGPT나 Claude 같은 범용 AI에게 분석을 맡길 수도 있지만, 대화가 끝나는 순간 '왜 그렇게 판단했는지'의 근거도 함께 사라집니다.
> 나중에 결론에 대한 질문을 받으면, 처음부터 다시 훑어야 하죠.
> 이 문제를 풀기 위해 만든 도구를 소개합니다."

---

## 1. 서비스 소개 (0:20 - 0:45) — 핵심 가치

**화면**: 기획서의 화면 흐름도(mermaid) 또는 슬라이드
**내레이션**:
> "이 도구의 핵심 가치는 '판단 근거가 사슬로 남는다'는 것입니다.
> 가설 → 검증결과 문단 → 근거 번호 → 원문 발췌 → 수정 이력 → 최종 판단, 이 흐름이 끊기지 않고 DB에 그대로 남습니다.
> 그래서 나중에 '왜 이 결론이 나왔어?'라는 질문을 받아도, 바로 근거를 되짚어 보여줄 수 있습니다."

---

## 2. 동작 시연 (0:45 - 3:30) — 가장 비중 있게

### 2-1. 가설 입력 (0:45 - 1:15)
**화면**: 실제 앱 실행, 가설 입력 화면
**내레이션**:
> "먼저 검증하고 싶은 가설을 원인/결과 형태로 입력합니다. 여러 개를 자유 텍스트로 추가할 수 있고,
> 인터뷰 전사문을 붙여넣은 뒤 분석을 시작합니다."
**액션**: 가설 1~2개 입력 → 전사문 붙여넣기 → "AI 분석 시작" 클릭 → 진행바 노출

### 2-2. 대시보드 (1:15 - 1:45)
**화면**: 분석 완료 후 대시보드
**내레이션**:
> "분석이 끝나면 대시보드에서 가설별 검증 상태를 한눈에 볼 수 있습니다.
> 검토 전, 유력함, 근거 부족, 수정 필요 — 네 가지 상태로 정리됩니다."
**액션**: 대시보드 상태 리스트 스크롤/하이라이트

### 2-3. 가설 상세 & 근거 드로어 (1:45 - 2:30)
**화면**: 가설 상세 화면 클릭 진입
**내레이션**:
> "가설을 클릭하면 AI가 정리한 검증결과 문단과, 그 근거가 된 인터뷰 발언 태그를 확인할 수 있습니다.
> 근거를 클릭하면, 사이드 드로어에 실제 전사문 원문이 그대로 열립니다.
> AI가 요약한 게 아니라, 원문 그 자체를 보여주기 때문에 신뢰할 수 있습니다."
**액션**: 근거 태그 클릭 → 드로어 오픈 → 원문 하이라이트 확인

### 2-4. AI와 논쟁하며 리파인 (2:30 - 3:00)
**화면**: 검증결과 문단 하이라이트 → 리파인 채팅
**내레이션**:
> "결과에 동의하지 않는 부분은 하이라이트하고, AI에게 반박하거나 추가 질문을 던질 수 있습니다.
> AI는 수정 가안을 제시하고, 사용자가 미리보기 후 적용 여부를 최종 결정합니다."
**액션**: 텍스트 하이라이트 → 프롬프트 입력 → 수정 가안 미리보기 → 적용

### 2-5. 버전 히스토리 & 판단 상태 (3:00 - 3:15)
**화면**: 인라인 수정 후 버전 히스토리
**내레이션**:
> "가설 자체를 수정하면 기존 버전과 새 버전이 모두 히스토리로 남고,
> 가설별로 유지·수정·폐기 상태를 지정할 수 있습니다."

### 2-6. 결과 공유 (3:15 - 3:30)
**화면**: 공유 URL / MD / PDF 내보내기
**내레이션**:
> "완성된 결과는 URL, 마크다운, PDF로 내보내 팀과 공유할 수 있습니다."

## 3. 기술적 특징 & 문제 해결 과정 (3:30 - 4:05)

**화면**: 아키텍처 다이어그램 또는 코드 스니펫 (선택)
**내레이션**:
> "기술적으로는 React 19, TypeScript, Vite 프론트엔드와 Express, Supabase(PostgreSQL) 백엔드로 구성했고,
> Google Gemini API를 2단계 파이프라인으로 사용합니다. 1단계에서 발언별로 가설과 근거를 태깅하고,
> 2단계에서 검증결과 초안을 생성합니다.
>
> 가장 신경 쓴 부분은 AI 환각 방지입니다. AI가 만든 인용문과 근거가 실제 전사문 원문과 정확히 일치하는지
> 대조하는 검증 모듈을 만들었고, 이 검증을 통과한 결과만 DB에 저장되도록 했습니다.
> 이 로직은 Vitest로 경계 케이스까지 단위 테스트를 작성해 검증했습니다.
>
> 또, Gemini 호출이 오래 걸리는 문제를 타임아웃과 재시도 로직으로 안정화했고,
> 프론트엔드에는 사고과정을 노출하지 않는 심플한 진행바로 사용자 피드백을 제공했습니다."

## 4. Agent/AI 활용 방식 (4:05 - 4:50)

**화면**: Claude Code 사용 화면 캡처 (선택) 또는 `.claude/skills`, `.claude/agents` 폴더 트리 캡처
**내레이션**:
> "이 프로젝트는 서비스 문제 정의, 데이터 흐름, 그리고 '판단 근거가 사슬로 남는다'는 핵심 차별점을
> 제가 직접 정의했습니다.
>
> 개발은 Claude Code와 함께 진행했는데, 작업하다 보면 같은 판단을 매번 다시 설명하게 되는 지점이
> 생깁니다. 그럴 때마다 그걸 Skill이나 Agent 파일로 고정해 나갔고, 최종적으로 Skill 다섯 개와
> Agent 한 개를 실제로 사용했습니다.
>
> 화면을 만들기 시작하면서는 `pm_design_system`으로 CSS 변수와 톤앤매너를 고정해, 입력·대시보드·상세·
> 공유 화면이 각자 다른 스타일로 갈라지지 않게 했습니다. 커밋이 쌓이면서는 `branch-commit-push`로
> 브랜치와 커밋 규약을 고정했습니다.
>
> AI 분석 로직에 들어가면서 만든 게 `pm-interview-analysis`입니다. 근거 강도 위계, 반증 우선 원칙 같은
> 판정 기준의 원본 문서로, 설계 문서와 실제 프롬프트 구현이 모두 이 문서를 따르고, 셋이 어긋나면 이
> 문서를 정답으로 삼습니다. 이건 백지에서 쓴 게 아니라, 제가 따로 관리하는 PM 스킬 레포 68개 중
> 이 도메인에 실제로 걸리는 4개만 선별해서 번역해 이식한 겁니다.
>
> `analysis-quality-eval`은 분석 품질을 측정하는 절차를 고정했습니다. 핵심은 정답 라벨을 사람이 직접
> 달았다는 겁니다 — AI가 채운 라벨을 정답으로 쓰면 자기참조 평가라서 지표가 항상 100%로 나오니까요.
> 프롬프트를 바꾸기 전에 항상 이걸로 먼저 측정했습니다.
>
> `tdd-feature-loop`는 순수 로직을 만들 때 실패하는 테스트를 먼저 쓰고 실제로 실패를 눈으로 확인한
> 뒤에 구현하도록, 그리고 test 커밋과 feat 커밋을 분리하도록 고정한 스킬입니다.
>
> 마지막으로 `requirement-verifier` 에이전트는, Task의 완료 조건 원문과 코드베이스 접근 권한만 받아서
> 판정합니다. 구현했던 세션의 '다 됐습니다' 같은 결론은 아예 넘기지 않고, 받더라도 무시하고 코드만
> 직접 읽어서 PASS인지 FAIL인지 판정합니다. 구현한 쪽이 자기 코드를 자기가 채점하지 않도록 분리한 겁니다.
>
> 다만 AI가 만든 초안은 항상 사람이 최종 판단한다는 원칙은 끝까지 지켰습니다."
