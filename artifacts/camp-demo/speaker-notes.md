# AY-PLE 캠프 데모 대본

10분 내외로 운영하는 가변 속도 대본이다. 본편은 제품의 약속에서 시작해 실제 문제와 제품 경험을 먼저 보여준 뒤, 그 경험을 가능하게 하는 실행 기반을 설명한다. Product flow만 라이브로 시연하고 Runtime Inspector와 SDK 검증은 고정된 실행 증거로 설명한다.

## 발표 전 준비

저장소 루트에서 다음 명령을 실행한다.

```bash
npm run demo
```

다음 상태만 확인한다.

1. Camp deck이 <http://127.0.0.1:4174/artifacts/camp-demo/#product-promise>에서 열린다.
2. Product flow를 열어 `R`로 초기화하고 1단계 `흩어진 자료`인지 확인한다.
3. `lms-outline-notice.txt`와 `problem-solving-syllabus.pdf`를 선택하고, 제안 카드에서 AY에게 수정 요청을 보낸 뒤 수락까지 끝까지 한 번 진행한다.
4. 다시 `R`로 1단계에 초기화한 뒤 Product flow 탭을 닫고 발표 자료로 돌아온다.
5. 정적 fallback인 [근거 확인 화면](assets/guided-demo-evidence.png), [반영 완료 화면](assets/guided-demo-confirmed.png), [Runtime Inspector 완료 화면](assets/runtime-inspector-completed.jpg)을 별도 탭에 열어 둔다.

실제 Codex, 별도 인증, 외부 provider나 현재 유일한 Codex Chat runtime은 발표 경로에서 실행하지 않는다.

## 1. 제품의 약속 · `#product-promise`

### 목적

기술 구조보다 학생이 얻게 될 결과를 먼저 이해시킨다.

### 필수 멘트

“AY-PLE는 학생이 맡긴 자료를 읽고 연결해 학기 정보로 제안하는 학업 Agent 앱입니다. 무엇을 맡길지는 학생이 정하고, 원본 근거를 확인한 내용만 최종 정보가 됩니다.”

### 선택 설명

- 자료 선택, 근거 확인, 최종 결정이라는 세 가지 사용자 통제를 짚는다.
- 첫 화면은 우리가 만들고 있는 제품 경험의 최종 장면이며, 지금부터 그 장면이 필요한 이유를 역순으로 설명한다고 덧붙인다.

### 전환 문장

“먼저 학생이 지금 무엇을 반복하고 있는지 보겠습니다.”

## 2. 학생의 실제 문제 · `#student-problem`

### 목적

문제를 ‘파일 보관’이 아니라 흩어진 자료에서 정보를 다시 연결하는 반복으로 정의한다.

### 필수 멘트

“직전 학기의 실제 폴더만 봐도 PDF, 녹음, 공지와 개인 노트가 한 과목 안에 함께 있습니다. 학생은 과제 정보를 찾을 때마다 자료를 다시 열고, 찾고, 비교하고, 다른 학기 도구에 옮깁니다. 줄이고 싶은 일은 파일 저장이 아니라 이 반복입니다.”

### 선택 설명

- 파일 형식의 다양성보다 여러 자료에 걸친 맥락의 분산을 강조한다.
- 새 앱에 한 번 더 수동 입력하는 방식은 문제를 옮길 뿐이라고 설명한다.

### 전환 문장

“AY-PLE는 이 반복을 다음 네 단계의 제품 흐름으로 바꿉니다.”

## 3. AY-PLE가 바꾸는 제품 흐름 · `#product-flow`

### 목적

Agent의 자율성보다 제품이 보장하는 사용자 통제와 상태 변화를 설명한다.

### 필수 멘트

“학생이 먼저 맡길 자료의 범위를 정합니다. AY는 파일과 도구를 사용해 정보를 연결하고 원본 근거가 있는 변경안을 냅니다. 결과를 곧바로 저장하지 않고 학생이 수락·수정·거절하며, 확인한 내용만 학기 정보가 됩니다.”

### 선택 설명

- `자료 선택 → 일 맡기기·AY의 작업 → 원본 근거·변경 제안 → 사용자 결정·확인된 정보`를 한 번에 읽는다.
- AI 출력과 제품 상태 사이에 사용자 확인이 있다는 점을 강조한다.

### 전환 문장

“이 네 단계를 같은 시나리오로 직접 보여드리겠습니다.”

## 4. Product flow 라이브 데모 · `#product-demo`

### 목적

자료 범위 지정부터 확인된 학기 정보 반영까지 한 번의 제품 흐름으로 보여준다.

### 필수 멘트

데모 시작 전에 경계를 먼저 말한다.

> “이 화면은 아직 실제 파일이나 Agent가 연결된 제품이 아니라, 만들고 있는 사용자 흐름을 항상 같은 결과로 보여주는 시제품입니다.”

다음 순서로 진행한다.

1. 흩어진 자료에서 LMS 공지와 강의계획서를 선택해 AY의 작업 범위를 정한다.
2. `선택한 자료 정리하기`를 누른다.
3. 오른쪽 Chat에 사용자 말풍선 대신 `작업 요청` 카드와 AY 응답이 쌓이는 것을 짚는다.
4. `다음 →`으로 AY의 도구 기록을 확인하고, 다시 `다음 →`으로 원문 근거를 본 뒤 오른쪽 `근거를 확인했어요 · 제안 보기 →`로 제안 카드에 들어간다.
5. `수정 요청`을 누르고 카드 안에서 `과제 이름을 ‘문제해결글쓰기 개요 작성’으로 바꿔줘.`라는 prompt를 보낸다.
6. AY의 처리 상태와 응답 뒤 제안이 `수정됨 · 내 확인 필요`로 바뀌고, 마감·제출 방식과 원본 근거는 유지되는 것을 짚는다.
7. 오른쪽 AY 채팅에서 `수락하고 반영`을 누른다.
8. 사용자 결정 기록과 AY 완료 응답 뒤 `확인된 과제`가 0개에서 1개가 된 것을 짚는다.

“핵심은 문장을 생성하는 모습이 아닙니다. 학생이 범위를 정하고, AY가 자료를 읽고 연결하며, 원본 근거를 남기고, 학생이 결정하면 앱 상태가 바뀌는 흐름입니다.”

### 선택 설명

- 선택한 자료만 작업 범위가 된다는 점을 짚는다.
- 시간이 부족하면 `?step=2&present=1`로 선택이 완료된 장면에 직접 진입하고, 원문 편집·프리뷰를 건너뛴다.
- 수정 요청까지 시연하기 어렵다면 6단계에서 최초 제안을 바로 수락한다. 이 경로도 의도적으로 보존한 fallback이다.

### 전환 문장

“이 경험을 만들려면 Agent의 실행 능력과 제품이 소유할 책임을 분리해야 합니다.”

## 5. built-in Codex의 의미 · `#built-in-codex`

### 목적

Codex와 AY-PLE의 역할을 분리해 ‘built-in’이 단순한 채팅창 포함이 아님을 설명한다.

### 필수 멘트

“Codex는 실행 엔진이고, AY-PLE가 제품입니다. 학생은 Codex를 직접 조작하지 않습니다. Codex는 파일, 도구와 다단계 실행을 제공하고, AY-PLE는 어떤 자료를 맡겼는지, 지금 무엇을 하는지, 어떤 근거로 무엇을 바꾸려는지, 누가 최종 확인했는지를 소유합니다.”

### 선택 설명

- ‘AI가 앱 안에서 일한다’는 말은 실행 과정이 제품의 범위·상태·결정 규칙 안에 있다는 뜻이라고 설명한다.
- 실행 종료와 확인된 학기 정보는 서로 다른 상태라는 점을 덧붙인다.

### 전환 문장

“그래서 첫 주에는 이 실행을 제품이 다룰 수 있는 하나의 계약으로 만드는 데 집중했습니다.”

## 6. Week 1 · `#week-1`

### 목적

완료된 Runtime Harness를 기능 목록이 아니라 Week 1의 검증 질문과 정적 실행 증거로 설명한다.

### 필수 멘트

“첫 질문은 Agent 실행을 하나의 규칙으로 시작하고, 관찰하고, 취소하고, 기록할 수 있는가였습니다. Week 1 Runtime Harness에서 결정적으로 반복되는 경로와 실제 Codex 경로가 같은 규칙을 지키는지 비교했습니다. 완료뿐 아니라 취소·실패와 중간 출력도 다시 확인할 수 있게 기록했습니다. 화면은 당시 규칙으로 실행을 끝까지 관찰한 Runtime Inspector의 고정된 역사 증거입니다.”

### 선택 설명

- Inspector는 더 이상 현재 실행 표면이 아니며, 이 발표에서는 완료된 Week 1 증거를 정적 screenshot으로 보여준다고 설명한다.
- Fake adapter는 당시 같은 실행 계약을 검증한 결정적 구현이었으며 현재 runtime에는 포함되지 않는다고 덧붙인다.

### 전환 문장

“그다음 질문은 이 검증을 공식 Codex SDK 기반으로 옮기면서도 정확히 지킬 수 있는가였습니다.”

## 7. Week 2 · `#week-2`

### 목적

공식 SDK 직접 재사용, 메시지 순서 교정과 Chat Shell·Server tracer 구현을 재현 가능한 증거로 설명하고, 아직 연결하지 않은 학업 제품 경계를 명시한다.

### 필수 멘트

“공식 `openai/codex` 소스와 실행 버전을 정확한 커밋에 고정하고, 같은 Python SDK를 다시 만들 수 있는 조건과 출처를 함께 보관했습니다. 검증 중에는 시작 응답이 늦게 오면 먼저 도착한 메시지와 완료 신호를 잃는 문제가 드러났습니다. 실패를 재현하는 검증을 먼저 고정한 뒤, 먼저 온 두 신호를 도착 순서대로 보존하도록 고쳤습니다.”

“이 기반은 이제 Node↔Python bridge, 제품 Server route와 desktop Chat Shell까지 연결됐습니다. Exact local-provider와 명시적으로 승인한 격리 환경의 manual live T0도 같은 경로에서 확인했습니다. Runtime Harness·Inspector를 역사 증거로 전환한 뒤에는 이 Codex Chat이 유일한 현재 runtime입니다. 다만 지금 시연한 학업 product-flow에는 아직 연결되지 않았습니다.”

### 선택 설명

- commit, wheel, FIFO 같은 세부 구현은 질문이 있을 때 부록 A2에서 설명한다.
- 실패 재현과 교정 후 통과 카드는 문제를 숨긴 것이 아니라 실행 가능한 회귀 증거로 바꿨다는 뜻이라고 설명한다.

### 전환 문장

“결국 기술 진척의 목적은 Codex 자체가 아니라, 처음 보여드린 제품 경험을 실제 실행 기반에 연결하는 것입니다.”

## 8. 제품 중심 마무리 · `#closing`

### 목적

기술 상태표가 아니라 학생이 얻을 제품 경험과 다음 연결로 발표를 끝낸다.

### 필수 멘트

“Codex가 제품은 아닙니다. 학생이 믿고 맡기고, 근거를 보고, 결정할 수 있는 경험이 AY-PLE입니다. 다음 목표는 검증된 실행 기반과 실제 자료 선택부터 확인된 학기 정보까지의 제품 수직 흐름을 연결하는 것입니다.”

### 선택 설명

- 질문이 기술 세부로 이어질 때만 `기술 부록 보기`를 누른다.
- 질문이 없으면 이 장에서 발표를 끝낸다.

### 전환 문장

“이제 질문을 받겠습니다. 필요하면 검증 근거와 현재 경계를 부록에서 보여드리겠습니다.”

## 실패 시 fallback

| 실패 지점 | 즉시 사용할 fallback | 말할 내용 |
| --- | --- | --- |
| Product flow 새 탭이 열리지 않음 | [원본 근거 화면](assets/guided-demo-evidence.png) → [반영 완료 화면](assets/guided-demo-confirmed.png) | 자료 선택, AY 작업, 근거, 사용자 정정, 학생 결정과 확인된 정보의 흐름을 두 화면으로 설명한다. |
| Product flow 진행 중 상태가 어긋남 | `R`로 초기화하고 한 번만 재시도 | 다시 어긋나면 재시도를 반복하지 않고 정적 두 화면으로 전환한다. |
| Runtime 관련 질문에서 부록 화면이 열리지 않음 | [Runtime Inspector 완료 화면](assets/runtime-inspector-completed.jpg) | Week 1에 `started → output_delta → completed` terminal 결과를 Transcript, Events, Run Log와 History에 보존했던 정적 증거라고 설명한다. |
| 전체 로컬 server 문제 | 발표 자료와 fallback 이미지를 파일로 연다 | 제품 약속, 실제 문제, 제품 흐름, 고정된 실행 증거와 현재/다음 경계를 같은 순서로 설명한다. |

실패 시 실제 Codex, 환경 인증, 외부 provider나 현재 Codex Chat runtime을 대체 경로로 실행하지 않는다.
