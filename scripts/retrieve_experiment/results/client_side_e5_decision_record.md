# 꺼내보기 클라이언트 측 의미 검색 모델 타당성 결정 기록

- 결정일: 2026-07-23
- 결정 상태: 기각
- 검토 대상: 사용자의 브라우저에서 의미 검색용 임베딩 모델을 직접 실행하는 방식

## 한눈에 보는 결정

`꺼내보기`는 사용자가 현재 상황을 입력하면, 이전에 저장한 자료 중 지금 다시 볼
만한 항목을 찾아 주는 기능이다. 현재 제품은 제목·메모·카테고리·도메인 등의
단어 단서를 이용해 자료를 찾는다.

표현이 달라도 의미가 비슷한 자료를 찾는 의미 검색 후보로
`multilingual-e5-small`을 검토했다. E5는 답변을 생성하는 생성형 LLM이 아니라,
문장과 자료를 숫자 벡터로 변환해 의미적 유사도를 비교할 수 있게 하는 임베딩
모델이다. 이 과정에서 모델을 사용자의 브라우저에 내려받아 직접 실행하는 방식의
타당성을 측정했다.

결론은 다음과 같다.

> 사용자의 브라우저에서 로컬 E5 모델을 직접 다운로드하고 실행하는 방식은
> `꺼내보기`의 채택 후보에서 제외한다.

이 결정은 의미 검색이나 E5 모델 자체를 기각한 것이 아니다. 서버에서 E5를
실행하는 방식과 서버를 통해 관리형 임베딩 API를 사용하는 방식은 이 실험의
평가 대상이 아니었다.

## 검토한 질문

이 실험이 답하려던 질문은 하나였다.

> 사용자의 브라우저가 E5 모델과 tokenizer를 직접 내려받고 초기화해도 될 만큼
> 초기 비용과 이후 검색 시간이 현실적인가?

검토한 실행 흐름은 다음과 같다.

```text
사용자가 상황 입력
  → 브라우저가 로컬 E5로 query 벡터 생성
  → 저장 자료의 벡터와 유사도 비교
  → 관련 자료 반환
```

이 흐름은 검토를 위한 가정이었으며, 확정된 제품 아키텍처나 요구사항은 아니었다.

## 실제로 측정한 범위

제품 화면이나 운영 데이터베이스는 변경하지 않았다. 제품과 분리한 벤치마크
페이지에서 다음 항목만 측정했다.

- Desktop Chrome과 Android Chrome의 최초 모델 준비 시간
- 브라우저 캐시가 준비된 뒤의 모델 재초기화 시간
- 첫 query와 warm query의 임베딩 시간
- 고정된 모델 revision이 실제 Cache Storage에 저장됐는지
- 캐시 실행 중 모델을 원격에서 다시 요청하지 않았는지
- Worker를 중간에 종료한 뒤 새 Worker가 정상 복구되는지
- 실제 실행 backend와 출력 벡터 차원

고정 모델은 `Xenova/multilingual-e5-small` q8이며, 실제 backend는 WASM,
출력은 384차원이다. 개인 데이터, Gemini API, 외부 API key는 사용하지 않았다.

## 핵심 결과

| 항목                   | Desktop Chrome | Android Chrome |
| ---------------------- | -------------: | -------------: |
| 최초 모델 준비         |       34.109초 |       79.933초 |
| 캐시 후 모델 준비      |        2.295초 |        5.985초 |
| 캐시 후 첫 query       |       52.910ms |      216.210ms |
| 캐시 후 warm query p50 |       10.695ms |       54.375ms |
| 캐시 후 warm query p95 |       15.925ms |       78.300ms |

최초 실행에서 브라우저 origin 전체 저장소 사용량 증가분은 두 환경 모두
159,017,472 bytes였다. Cache Storage 항목에서 확인한 모델 파일은
118,308,185 bytes, tokenizer는 17,083,173 bytes였다.

두 환경 모두 고정 revision의 필수 캐시 항목을 확인했고, 캐시 실행 중 원격 모델
요청은 0건이었다. Worker 취소 뒤 새 Worker의 초기화, 첫 query, warm query
20회와 384차원 출력도 확인했다.

## 결과 해석

모델이 준비된 뒤 query 임베딩 자체는 짧게 끝났다. 문제는 사용자가 기능을 처음
사용할 때 부담해야 하는 다운로드와 초기화 비용이다.

- 사용자가 기능을 사용하기 위해 약 159MB의 브라우저 캐시를 받아야 한다.
- 최초 준비에 Desktop 약 34초, Android 약 80초가 걸렸다.
- 캐시가 있어도 매 실행에서 모델 가중치를 읽고 WASM pipeline을 초기화해야 한다.
- 이 비용은 `꺼내보기`에서 자료 몇 개를 다시 찾으려는 사용자의 기대와 맞지 않는다.

따라서 빠른 warm query만으로 클라이언트 실행 방식을 정당화할 수 없다고
판단했다.

## 결정

`꺼내보기`에서 사용자의 브라우저가 로컬 E5 모델을 직접 다운로드하고 실행하는
방식은 채택하지 않는다.

이 결정에 따라 다음 항목을 운영 설계의 전제로 사용하지 않는다.

- 브라우저 Cache Storage에 임베딩 모델을 배포하는 방식
- 브라우저 Worker가 모든 query embedding을 담당하는 방식
- 사용자가 최초 모델 다운로드와 초기화를 기다리는 UX

## 이 실험으로 판단할 수 없는 것

다음 항목은 이번 결과로 채택하거나 기각할 수 없다.

- 서버에서 E5 모델을 한 번 준비해 여러 사용자 요청을 처리하는 방식
- 애플리케이션 서버가 Gemini 등 관리형 임베딩 API를 호출하는 방식
- 실제 개인 자료에서 의미 검색이 현행 검색보다 유용한지
- 서버 지연 시간, 동시성, 운영 비용과 장애 대응
- `꺼내보기` 화면부터 검색 결과 반환까지의 전체 응답 시간

특히 이 결과를 근거로 “E5가 `꺼내보기`에 부적합하다”거나 “`꺼내보기`가
34~80초 걸린다”고 표현하면 안 된다. 측정한 것은 클라이언트 측 모델 준비
방식뿐이다.

## 다음 검토 원칙

추가 성능 실험 전에 먼저 실제 배포 구조를 선택해야 한다.

검토할 수 있는 선택지는 다음과 같다.

1. 현행 어휘 검색을 유지한다.
2. 서버에서 E5를 실행하고 자료·query embedding을 생성한다.
3. 애플리케이션 서버를 통해 관리형 임베딩 API를 사용한다.

선택할 때는 의미 검색 품질뿐 아니라 개인정보 전송 범위, 서버 운영 부담, API
비용, 응답 지연과 장애 시 대체 동작을 함께 비교해야 한다. 배포 구조가 정해진
뒤에만 그 구조에 맞는 benchmark를 진행한다.

## 증거와 원본

- `browser_benchmark_report.md`: 측정 계약과 브라우저별 전체 관측값

원본 보고서와 JSON은 재현성과 후속 검토를 위해 그대로 보존한다. 이 문서는
원본 수치를 제품 의사결정의 맥락에서 해석한 기록이다.

## 한계

- 최초 준비 시간은 각 환경의 단일 실행 기록이므로 일반적인 서비스 SLA가 아니다.
- 고정 synthetic query로 임베딩 실행 시간만 측정했다.
- 메모리 API는 일부 단계에서 시간 초과되어 모델 전체 peak 메모리를 확정하지
  못했다.
- 실제 사용자 자료와 query를 사용하지 않았다.
- 클라이언트 측 실행이 확정된 제품 요구사항인지 검증하는 실험은 아니었다.
