## 작업 기록 위치

다음 작업은 [`tasks/`](tasks/README.md)에 계획서와 검증 보고서를 반드시 남긴다.

- 모든 CHECKLIST T항목
- 여러 세션에 걸치는 작업
- 구조·계약·의존성 변경 또는 PR로 전달할 작업

T항목은 `harness/tasks/T<번호>-<짧은-이름>/`, 비-T 작업은 `harness/tasks/YYYY-MM-DD-<짧은-이름>/`을 사용한다. 각 폴더에는 `plan.md`와 `verification.md`를 두고, 같은 작업을 재개할 때 새 파일을 만들지 않고 기존 파일을 갱신한다.

단일 세션에서 끝나고 재사용할 승인·판단이 없는 작은 비-T 작업은 대화나 PR에 계획과 검증을 남겨도 된다. 저장소를 변경했다면 요약 이력은 항상 `docs/LOG.md`에 기록한다. CHECKLIST와 LOG가 각각 완료 현황과 이력의 정본이므로 별도 현황판은 만들지 않는다.

## 작업 단위와 에이전트 실행 단위

- **T항목**은 의존성·완료조건을 추적하는 백로그 단위다. T 하나를 에이전트 하나에 자동 배정하지 않는다.
- **실행 묶음**은 한 번의 승인 아래 하나의 사용자 결과를 만드는 작업 단위다. 서로 관련된 T항목을 한 묶음에서 다룰 수 있지만 각 T의 의존성과 완료 판정은 CHECKLIST에서 따로 유지한다.
- **에이전트 작업**은 실행 묶음 안에서 독립 산출물과 자체 검증을 가진 한정된 하위 작업이다. 역할은 이 작업에 적용하는 책임·권한 템플릿이지 상시 인원표가 아니다.
- 기본은 PM 단독 실행이다. 위임은 독립 산출물, 고정된 공유 계약, 읽기 전용 또는 비중첩 쓰기 경로, 인계 비용을 넘는 순효율을 모두 확인한 뒤에만 한다.
- 탐색·테스트 분석·로그 분류·완성 diff 검토처럼 읽기 중심 작업을 먼저 병렬화한다. 병렬 writer는 최대 2명이며 같은 파일, 미확정 공유 계약, 선행 출력에 의존하는 작업은 순차 실행한다.
- PM만 공유 계약, 계획·검증 상태, CHECKLIST, LOG, 최종 통합을 소유한다. 하위 에이전트 수나 역할 수를 진행률로 취급하지 않는다.

### ORCH-2 이전 방식과 현재 방식

| 판단 항목 | 이전 방식(role-first) | 현재 방식(task-first) |
| --- | --- | --- |
| 출발점 | 디자이너·프론트엔드·백엔드/AI 중 어떤 역할을 활성화할지 먼저 판단 | 하나의 사용자 결과와 실행 묶음을 먼저 정하고 독립 하위 작업이 있는지 판단 |
| T항목 해석 | 세분화된 T와 역할 분배가 쉽게 1:1로 읽힐 수 있음 | T는 의존성·완료조건 단위일 뿐 에이전트 배정 수를 정하지 않음 |
| 기본 실행 | 교차 영역이면 여러 전문 역할 활성화를 우선 검토 | PM 단독 실행이 기본이며 네 위임 게이트를 모두 통과할 때만 worker 활성화 |
| 위임 기준 | 역할 전문성과 파일 소유권 중심 | 독립 산출물·고정 계약·안전한 소유권·순효율을 모두 확인 |
| 병렬화 우선순위 | 디자인·프론트·백엔드 구현 역할 병렬화 | 탐색·테스트 분석·로그 분류·완성 diff 검토 같은 읽기 작업부터 병렬화 |
| 쓰기 작업 | 역할별 비중첩 경로라면 최대 세 전문 역할까지 가능 | writer 최대 2명, 같은 파일·공유 계약·선행 출력 의존은 반드시 순차 실행 |
| 에이전트 구조 | PM 아래 역할별 specialist | PM 아래 한정된 worker만 두는 평면 구조, worker의 재위임 금지 |
| 전달 맥락 | 역할별 정본과 작업 카드를 전달 | 격리된 task-local 맥락이 기본이며 미묘한 선행 결정이 필요할 때만 대화 맥락 확대 |
| 완료 판단 | 역할별 인계를 모아 PM이 통합·검증 | 동일하게 PM만 판정하되 실제 병렬 구간·인계 비용·충돌·재작업까지 기록 |
| 도구 확장 | 역할 구성이 정해지면 재사용 | 실제 2~3개 작업의 순효율을 확인하기 전에는 상시 custom agent·worktree 자동화 보류 |
| 상태 일관성 | 사람이 CHECKLIST·plan·verification을 함께 갱신 | 동일 책임에 `npm run harness:check`를 추가해 상태명·완료 정합성을 자동 검사 |

바뀌지 않은 원칙도 있다. PM은 계속 단일 통합자이고, 공유 계약과 CHECKLIST·LOG를 소유하며, 동일 파일 동시 수정·미승인 구조 변경·하위 에이전트의 임의 완료 판정은 허용하지 않는다. 제품의 `/api/generate`도 단일 structured-output 런타임을 유지한다.

## 상태와 책임

- 계획 상태: `제안 → 승인됨 → 진행 중 → 검증 대기 → 종료`, 필요하면 `보류`로 이동한다.
- 사용자가 범위와 구조·계약 변경을 승인하고, 에이전트가 승인 근거와 진행 상태를 기록한다. 승인받은 범위나 완료조건이 달라지면 계획을 갱신해 재승인받는다.
- `보류`에는 사유·재개 조건·다음 행동을 반드시 적는다.
- 검증 보고서의 `통과`가 완료의 유일한 근거다. 필수 완료조건과 적용되는 자동·수동 검증이 모두 통과하고 차단 위험이 없어야 한다.
- 검증 보고서가 `통과`한 뒤에만 계획을 `종료`하고, T항목이면 CHECKLIST를 체크하며, LOG에 계획서·검증 보고서 링크를 남긴다.
- `npm run harness:check`는 plan/verification 파일 쌍, 허용 상태명, CHECKLIST 완료 여부와 T 작업 상태의 정합성을 검사한다. 완료된 T는 `plan=종료`·`verification=통과`, 미완료 T는 이 조합을 가질 수 없다.

## 작업 루프

1. 시작 시 `git status --short`로 기존 변경을 기록하고 보호할 사용자 작업을 계획서에 적는다.
2. T항목이면 CHECKLIST의 의존성과 본문이 직접 가리키는 문서를 먼저 확인한다. `task-start`의 문서 라우터는 보조 기준이다. 비-T 작업은 식별자와 적용할 정본을 명시한다.
3. [`templates/task-plan.md`](templates/task-plan.md)로 변경 경계와 `AC-1` 형식의 검증 가능한 완료조건을 작성하고 사용자 승인을 받는다.
4. 승인된 단계 안에서 구현하며 단계마다 계획에 적은 관련 검증을 실행한다. 충돌이나 범위 변경은 중단·제안·승인·정본 갱신·계획 재승인 순서로 처리한다.
5. [`templates/verification-report.md`](templates/verification-report.md)에서 각 완료조건을 검증 방법·결과·근거에 연결한다.
6. 종료 시 허용된 변경 경계와 실제 diff를 비교하고, `npm run harness:check`와 작업 유형별 최종 게이트를 수행한다.
7. 통과 조건을 만족한 경우에만 완료 현황과 LOG를 갱신한다. 커밋·푸시는 사용자가 요청하면 기존 `/commit` 절차를 따른다.

## 작업 유형별 검증 게이트

| 작업 유형 | 단계 중 검증 | 최종 완료 게이트 |
| --- | --- | --- |
| 코드 | 변경과 직접 관련된 테스트 | 관련 테스트 + `npm test` + `npm run lint` + `npm run build` + `git diff --check` |
| 문서·하네스 | 링크·경로·정본 참조 확인 | 로컬 링크와 필수 항목 확인 + `git diff --check` |
| 시드·콘텐츠 | `/seed`의 자체 스크리닝 | 블라인드 정렬·전송 가능성 등 해당 T항목의 검수 기준 |
| 설정·배포 | 설정 문법과 로컬 재현 | `docs/CICD.md`의 해당 체크리스트 + 적용 가능한 테스트·빌드 |

적용되지 않는 검증은 임의로 생략하지 않고 검증 보고서에 `해당 없음`과 이유를 적는다. 템플릿을 복사한 실제 작업 문서에는 미치환 필수 항목을 남기지 않는다.

## 피드백을 하네스에 남기는 기준

일회성 실수는 해당 작업에서 수정한다. 반복될 가능성이 있는 실패만 가장 좁은 정본에 반영한다: 제품 판단은 PRD/MVP/SPEC, 작업 절차는 하네스나 스킬, 회귀는 테스트, 기계적으로 막아야 하는 규칙은 별도 승인 후 린트·훅·CI로 승격한다.
