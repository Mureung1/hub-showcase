# router

요청을 받으면 먼저 작업 유형을 분류한다. 분류 결과에 따라 읽을 문서와 산출물이 달라진다.

## 요청 유형

| 유형 | 판단 기준 | 기본 산출물 |
|---|---|---|
| 답변 | 설명, 비교, 판단을 요청함 | 근거 문서 기반 답변 |
| 질문 정리 | 요구사항이 모호하거나 결정이 필요함 | 필요한 질문과 선택지 |
| 문서 작업 | PRD, README, ADR, 하네스 수정 | 문서 변경 |
| UI 작업 | 화면, 문구, 레이아웃, 디자인 수정 | 프로토타입 또는 UI 문서 변경 |
| 기능 구현 | 실제 입력, 분류, 답글, 분석 등 동작 구현 | 코드와 테스트 |
| 검증 | 테스트, 리뷰, 문제 진단 | 검증 결과와 수정 제안 |
| 리스크 검토 | 법률, 개인정보, 플랫폼 약관, 자동화 관련 | 보수적 리스크 보고 |

## 라우팅 규칙

### PRD와 충돌할 때

- PRD를 우선한다.
- 사용자가 의도적으로 PRD 변경을 요청한 경우에만 PRD를 수정한다.
- 충돌이 큰 경우 구현하지 말고 결정이 필요한 지점을 보고한다.

### MVP와 Phase 2가 섞일 때

- MVP 작업이면 Phase 2 기능을 제외한다.
- Phase 2 기능을 요청받으면 리스크와 전제조건을 먼저 확인한다.
- 자동 수집, 자동 게시, 알림, 멀티 플랫폼은 기본적으로 Phase 2다.

### 악성 리뷰·법률 대응이 포함될 때

- `docs/GOTCHAS.md`를 반드시 확인한다.
- 법률 자문처럼 보이는 문구를 만들지 않는다.
- 자동 신고, 자동 게시, 자동 법적 판단을 만들지 않는다.

### UI 작업일 때

- `docs/UI_GUIDE.md`와 `prototype/`을 함께 본다.
- UI 문구는 존댓말과 쉬운 표현을 우선한다.
- 빨간색은 악성 의심이나 위험 경고에 집중해서 사용한다.

### 실제 코드 구현일 때

- 먼저 기술 스택이 확정됐는지 확인한다.
- 아직 스택이 없으면 구현 폴더를 임의로 만들지 않고 ADR 또는 설계 작업으로 전환한다.
