# Phase 03 — MVP vertical slice

현재 controller가 지정한 step만 수행한다. manifest의 `allowed_paths` 밖을 수정하지 않으며 실제 비밀값을 파일이나 테스트 fixture에 남기지 않는다. 외부 LLM은 adapter 뒤에 두고 모든 테스트는 결정적인 fake adapter로도 실행 가능해야 한다.

## 공통 제품 불변조건

- MVP 입력은 한 건 또는 일괄 수동 입력뿐이며 플랫폼 자동 수집은 없다.
- 분류 결과에는 유형, 복수 카테고리, 근거 한 줄과 확인 필요 여부가 있다.
- 칭찬+불만은 불만+복합, 문의+불만은 불만, 별점·본문 불일치는 본문 우선+확인 필요다.
- 매장 프로필만 문의와 이벤트의 근거로 사용하고 만료 이벤트는 제외한다.
- 악성 의심에는 ReplyDraft를 생성하지 않는다. 위험도 ①·②로 사장님이 조정한 뒤에만 생성할 수 있다.
- 게시, 신고, 보상과 법률 판단은 사장님이 직접 수행한다.
- 모든 읽기·쓰기는 인증된 사용자의 매장 소유권을 검사한다.

## `backend-daily-loop`

도메인 규칙을 UI나 LLM prompt가 아니라 Domain/Application 계층에 구현한다. 단건·일괄 입력은 원본별 성공/실패를 추적하고 중복·부분 실패를 명시한다. 구조화 LLM 출력은 스키마 검증, 안전 후처리와 재생성 한도를 거친다. 데이터 마이그레이션과 테스트용 저장소를 함께 제공한다.

## `frontend-daily-loop`

프로토타입의 디자인 의도를 재사용하되 실제 API 상태를 표시한다. 설정 → 입력 → 미리보기·등록 → 리뷰함 → 상세 수정·복사 → 완료 흐름과 악성 의심 → 대응 센터 → ①·② 재분류 복귀를 구현한다. clipboard 실패, API 오류, 저장 중 상태도 명시한다. 자동 게시처럼 보이는 버튼이나 문구는 만들지 않는다.

## `vertical-slice-integration`

격리된 DB와 fake LLM으로 S1~S3를 API 수준에서 재현한다. 매장 간 데이터 격리, 새로고침 후 상태 지속, 일괄 입력 부분 실패, 저확신 확인 필요, 악성 초안 부재, 위험도 조정 후 복귀, 완료 처리까지 검증한다. 보고서에는 실행 명령과 통과 증거를 요약하되 비밀이나 고객 원문을 남기지 않는다.

실패 시 현상, 기대값과 실제값, 재현 명령, 증거 경로를 먼저 기록하고 원인은 가설·확정·미확인으로 구분한다.
