## 2026-07-26 · 요청의 사용자 ID를 신뢰하던 소유권 문제

### 증상

책과 독서 기록 API가 경로·쿼리·본문의 `userId`를 그대로 사용했다. 다른 사용자 ID를 알면 그 사람의 데이터에 접근할 가능성이 있었다.

### 원인

사용자 생성 API만 있던 초기 단계에서 인증과 사용자 식별을 같은 것으로 취급했다.

### 수정

- Google ID 토큰의 서명, 발급자, 대상, 만료를 공식 검증기로 검사한다.
- 이메일 대신 변경되지 않는 Google `sub`를 영구 식별자로 저장한다.
- 로그인할 때 기존 세션을 폐기하고 새 `HttpSession`을 만든다.
- 모든 보호 API는 세션의 사용자 ID만 사용한다.
- 변경 요청은 32바이트 난수 CSRF 토큰을 상수 시간 비교로 검증한다.

### 검증

`AuthApiTests`에서 정상·실패 로그인, 세션 복원, 미인증 접근, CSRF 누락과 로그아웃을 검사한다.

### 배울 점

인증은 “누구라고 주장하는가”를 받는 일이 아니라 그 주장을 검증하는 일이다. 이메일은 프로필 정보이며 외부 제공자의 불변 subject가 계정 연결 키에 적합하다.

## 2026-07-26 · CORS 사전 요청이 인증에서 차단되던 문제

### 증상

브라우저가 보호 API를 호출하기 전에 보내는 `OPTIONS` 요청이 `401`로 차단될 수 있었다. 실제 API 구현과 세션이 정상이어도 브라우저에서는 책 검색이나 저장이 실패한다.

### 원인

인증 인터셉터를 `/api/**` 전체에 적용하면서 CORS preflight도 일반 API 요청처럼 세션 검사를 했다. 사전 요청에는 애플리케이션 인증 정보를 요구하면 안 된다.

### 수정

`AuthenticationInterceptor`가 `OPTIONS` 요청을 통과시키도록 했다. 실제 GET·POST·PATCH·DELETE 요청은 기존처럼 인증하고, 변경 요청은 CSRF도 검사한다.

### 검증

세션 없는 `OPTIONS /api/books/search` 요청이 허용되는 테스트를 추가했다.

### 배울 점

CORS는 컨트롤러보다 앞에서 처리되는 브라우저·HTTP 계층의 절차다. 인증 필터나 인터셉터를 전역 적용할 때 preflight를 별도로 고려해야 한다.

## 2026-07-26 · 세션 고정 가능성

### 증상

로그인 전 세션을 로그인 후에도 그대로 사용하면 공격자가 알고 있는 세션 ID에 인증 상태가 붙을 수 있다.

### 원인

단순히 기존 세션 객체에 사용자 ID를 추가하는 구현은 세션의 권한이 바뀌는 시점에 ID를 교체하지 않는다.

### 수정

로그인 요청에 기존 세션이 있으면 폐기하고 새 세션을 만든 뒤 사용자 ID와 새 CSRF 토큰을 저장한다.

### 검증

Google 로그인 뒤 반환된 새 세션으로 현재 사용자 조회와 CSRF 보호 로그아웃이 동작하는지 검사한다.

### 배울 점

로그인은 세션의 권한 수준이 바뀌는 경계다. 이때 세션 ID를 회전하거나 기존 세션을 폐기해야 세션 고정 공격을 막을 수 있다.

## 2026-07-26 · 최초 Google 로그인 동시 요청의 경쟁 조건

### 증상

같은 Google 계정의 첫 로그인 요청 두 개가 동시에 사용자를 조회하면 둘 다 “사용자 없음”을 볼 수 있었다. DB 유니크 제약이 중복 생성은 막지만 한 요청은 서버 오류로 끝난다.

### 원인

`조회 → 없으면 저장`이 하나의 원자적 DB 연산이 아니었다.

### 수정

기존 사용자를 먼저 조회하고, 없을 때 MySQL의 `INSERT IGNORE`로 생성한 뒤 영구 식별자인 `provider + subject`로 다시 조회한다. 동시 요청은 같은 유니크 키에서 하나만 생성하고 둘 다 같은 사용자를 읽는다.

### 검증

같은 Google 자격 증명으로 반복 로그인해 같은 사용자 ID가 반환되고 사용자 행이 하나만 존재하는지 검사한다.

### 배울 점

애플리케이션의 사전 조회는 동시성을 보장하지 않는다. 중복 방지는 DB 유니크 제약에 맡기고, 생성 연산도 충돌을 정상 흐름으로 처리해야 한다.

## 2026-07-26 · 책장 조회의 N+1 문제

### 증상

책 목록을 가져온 뒤 책마다 기록 개수와 최신 기록을 별도 조회했다. 책 수가 늘면 쿼리 수도 함께 증가했다.

### 원인

단일 책 응답을 만드는 메서드를 목록에도 반복 사용했다.

### 수정

- 사용자의 책을 한 번에 조회한다.
- 해당 책들의 독서 기록을 `IN` 쿼리 한 번으로 조회한다.
- Java에서 책 ID와 상태별로 묶는다.
- 책장 API 전체의 쿼리 수 상한을 세 개로 테스트한다.

### 검증

Hibernate 통계를 초기화한 뒤 `BookService.getBooks`의 prepared statement 수가 세 개 이하인지 검사한다. 현재는 두 조회가 핵심이다.

### 배울 점

N+1은 개별 쿼리가 빠른지만 봐서는 놓치기 쉽다. 목록 크기에 따라 쿼리 수가 증가하는지 확인해야 한다. 현재 방식은 사용자 한 명의 기록을 모두 읽으므로 실제 규모가 커지면 DB 집계 projection으로 바꾼다.

## 2026-07-26 · 글귀를 독서 기록에 종속시킬 때의 수명 문제

### 증상

글귀를 독서 기록의 필드나 자식으로 만들면 기록 삭제 시 다시 보고 싶은 문장까지 사라질 수 있었다.

### 원인

같은 화면에서 함께 입력된다는 이유로 두 데이터의 수명도 같다고 가정했다.

### 수정

- `Quote`를 `ReadingRecord`와 독립된 엔티티로 저장한다.
- 함께 입력하면 하나의 트랜잭션에서 원자적으로 저장하되 두 엔티티 사이 외래 키는 만들지 않는다.
- 기록 삭제는 글귀에 영향을 주지 않는다.
- 노출 기록에는 글귀 스냅샷을 저장하고 원본 글귀 삭제 시 ID만 `NULL`로 만든다.

### 검증

기록과 글귀 동시 저장, 랜덤 재노출, 노출과 후속 기록 연결, 기록 삭제 후 글귀 유지 테스트를 추가했다.

### 배울 점

데이터 모델의 관계는 입력 화면보다 데이터의 소유권과 수명으로 결정하는 편이 안전하다.

## 2026-07-26 · 외부 도서 쪽수의 불완전성과 범위 검증

### 증상

Google Books가 전체 쪽수를 주지 않는 책이 있고, 값이 있는 책도 시작·끝 페이지가 전체 쪽수를 넘을 수 있었다.

### 원인

외부 메타데이터를 항상 존재한다고 가정할 수도, 전혀 활용하지 않을 수도 없는 상태였다.

### 수정

- `pageCount`를 nullable로 저장한다.
- 값이 있을 때만 시작 페이지와 독서 기록의 끝 페이지 상한을 서버에서 검사한다.
- DB 제약으로 값이 있다면 1 이상임을 보장한다.

### 검증

320쪽 책에 321쪽을 시작 페이지로 요청하면 `INVALID_PAGE_RANGE`가 반환되는 테스트를 추가했다.

### 배울 점

외부 데이터의 “없음”은 유효한 상태로 모델링해야 한다. 동시에 값이 존재할 때 적용할 수 있는 무결성 규칙은 서버와 DB에 남겨야 한다.

## 2026-07-27 · Spring Data 파생 쿼리 비교 키워드 오류

### 증상

읽기 기록 달력의 날짜 범위 저장소 메서드를 추가한 뒤 테스트 애플리케이션 컨텍스트가 시작되지 않았다. `createdAt`의 `less`라는 하위 속성을 찾을 수 없다는 `PropertyReferenceException`이 발생했다.

### 원인

종료 시각 미만 조건을 메서드 이름에 `CreatedAtLess`로 적었다. Spring Data 파생 쿼리는 임의의 영어 표현을 해석하지 않고 정해진 `LessThan` 또는 `Before` 키워드만 인식한다.

### 수정

상한이 포함되지 않는 시각 범위를 명확히 표현하도록 저장소 메서드를 `CreatedAtBefore`로 변경했다.

### 검증

서울 날짜 경계의 기록 세 개를 이틀로 묶고 다른 사용자의 기록을 제외하는 `ReadingActivityApiTests`가 통과했다.

### 배울 점

Spring Data 메서드 이름은 문장이 아니라 제한된 쿼리 문법이다. 비교 연산은 지원 키워드를 사용하고, 저장소 빈 생성까지 포함하는 통합 테스트로 이름 해석 오류를 확인해야 한다.

## 2026-07-27 · 외부 도서 제목과 사용자 표시 이름을 분리한 판단

### 증상

책 등록 요청에는 판본 식별자와 시작 페이지만 있어 Google Books의 제목을 그대로 저장할 수밖에 없었다.

### 원인

판본 메타데이터를 가져오는 식별 정보와 책장에 표시할 사용자 제목을 하나의 값으로 취급했다.

### 수정

등록 요청에 최대 255자의 선택적 `title`을 추가하고, 값이 있으면 공백을 제거해 저장한다. 제목이 없는 기존 클라이언트 요청은 외부 메타데이터 제목을 계속 사용한다. ISBN과 provider ID로 만든 판본 키는 바꾸지 않아 사용자 제목을 고쳐도 중복 판본 판단은 유지된다.

### 검증

사용자 제목을 보낸 등록 응답에 수정한 제목이 반환되는 통합 테스트를 추가했다. 제목을 보내지 않는 기존 등록과 전체 쪽수 범위 검증도 같은 테스트에서 유지했다.

### 배울 점

외부 메타데이터의 식별 값과 사용자가 보는 표시 값은 목적이 다르다. 표시 이름을 허용하더라도 판본 식별 키를 그대로 유지하면 개인화와 데이터 무결성을 함께 지킬 수 있다.

## 2026-07-28 · Render 배포에서 JVM, 포트, 세션 쿠키가 맞지 않던 문제

### 증상

Spring Boot 서버를 Render에 그대로 연결할 네이티브 Java 런타임이 없고, 로컬 기본 포트와 쿠키 정책을 유지하면 배포 후에도 서비스 감지와 Vercel 로그인이 실패할 수 있었다.

### 원인

- Render 네이티브 런타임은 JVM을 지원하지 않는다.
- Spring Boot는 기본적으로 8080 포트를 사용하지만 Render 웹 서비스는 주입한 `PORT`에서 수신하기를 기대한다.
- Vercel과 Render는 서로 다른 site이므로 `SameSite=Lax` 세션 쿠키가 fetch 요청에 포함되지 않는다.
- 현재 Flyway 마이그레이션과 드라이버는 MySQL 전용이지만 Render의 관리형 데이터베이스는 PostgreSQL이다.

### 수정

- Gradle 빌드와 Java 21 런타임을 분리한 multi-stage Docker 이미지를 만들었다.
- `server.port=${PORT:8080}`으로 로컬 기본값을 유지하면서 Render 포트를 사용한다.
- 쿠키 SameSite를 환경 변수로 열고 배포에서는 `none`, HTTPS 전용 쿠키는 `true`로 설정한다.
- DB 마이그레이션을 섞지 않고 기존 MySQL을 외부 환경 변수로 연결한다.
- `/actuator/health`를 Render health check로 사용한다.

### 검증

Gradle 테스트를 통과했고, 로컬 Docker 이미지가 비루트 사용자로 실행되어 `PORT=10000`의 health endpoint에서 `UP`을 반환하는 것을 확인했다. 실제 Render 배포 뒤 Vercel의 Google 로그인·세션 복원을 추가 확인한다.

### 배울 점

컨테이너가 빌드되는 것과 플랫폼에서 정상 서비스되는 것은 다르다. 런타임 버전뿐 아니라 플랫폼의 포트 계약, 브라우저의 cross-site 쿠키 정책, 데이터베이스 방언까지 함께 맞아야 한다. 기존 DB가 특정 방언에 묶여 있다면 배포 작업에 DB 전환까지 섞기보다 접속 경계를 환경 변수로 유지하는 편이 변경 범위가 작다.
