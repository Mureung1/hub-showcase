# 플레이스픽 AI 전체 구현 설계

## Spring Boot 기반 네이버 검색 API 연계 실시간 모임 장소 의사결정 플랫폼

아래 설계는 **실제로 개발에 들어가기 위한 구현 기준서**로 작성한다. 목표는 단순히 “LLM API + 네이버 API 붙인 추천 서비스”가 아니라, **Spring Boot 기반 비동기 추천 파이프라인, Redis Streams 이벤트 처리, SSE 실시간 진행 상태, 공유방 투표, 캐싱, Rate Limit, 관측성, 부하 테스트까지 포함한 백엔드 중심 포트폴리오 서비스**를 만드는 것이다.

기존 기획에서 플레이스픽 AI는 “사용자의 모임 조건을 LLM API가 해석하고, 네이버 지역·블로그 검색 결과를 기반으로 장소 후보를 추천하며, Spring Boot 기반 비동기 파이프라인과 실시간 이벤트 처리로 여러 사람의 장소 합의를 돕는 AI 백엔드 서비스”로 정의했다.  따라서 구현 설계도 이 정의에 맞춰 **추천 생성, 공유, 투표, 최종 합의, 이벤트 수집**까지 하나의 흐름으로 잡는다.

# 1. 구현 설계의 기준과 의도

## 1-1. 구현 기준

| 기준       | 구현 방향                                                     |
| -------- | --------------------------------------------------------- |
| 서비스 본질   | 장소 검색이 아니라 **모임 장소 의사결정**을 돕는다.                           |
| AI 역할    | 조건 추출, 검색 쿼리 생성, 블로그 문맥 요약, 추천 이유 생성에만 사용한다.              |
| 데이터 근거   | LLM이 장소를 상상하지 않고, 네이버 검색 결과에 있는 후보만 추천한다.                 |
| 백엔드 구조   | 요청을 즉시 처리하지 않고 Job으로 등록한 뒤 Redis Streams 기반 Worker가 처리한다. |
| 실시간성     | 추천 진행 상태는 SSE로 제공하고, 투표 결과는 이벤트로 반영한다.                    |
| 비용 제어    | 네이버 API와 LLM API 호출량을 Redis Cache와 Rate Limiter로 제어한다.    |
| 대용량 처리   | 실제 네이버 API를 많이 호출하지 않고, 내부 추천 작업·투표·클릭 이벤트를 스트림으로 처리한다.   |
| 포트폴리오 가치 | API 설계, JPA 모델링, 이벤트 처리, 캐싱, 장애 대응, 관측성, 부하 테스트를 모두 보여준다. |

이 프로젝트의 핵심 차별점은 단순 장소 추천이 아니라 **모임 장소 합의**를 돕는다는 점, LLM이 장소를 만들지 않고 네이버 검색 결과 안에서만 추천한다는 점, 추천 작업을 비동기 파이프라인으로 처리한다는 점, 외부 API 호출량을 캐시와 Rate Limiter로 제어한다는 점이다. 

## 1-2. 구현 의도

구현 의도는 다음 한 문장으로 정리할 수 있다.

> **사용자가 자연어로 모임 조건을 입력하면, Spring Boot API 서버가 추천 Job을 생성하고, Redis Streams 기반 Worker가 AI 조건 추출·네이버 검색·블로그 문맥 분석·점수화·추천 이유 생성을 처리하며, 사용자는 SSE로 진행 상태를 보고, 공유방에서 친구들의 투표를 반영해 최종 장소를 합의한다.**

기존 동기 구조인 `사용자 입력 → LLM 호출 → 네이버 API 호출 → 결과 출력`은 API 연동 프로젝트처럼 보일 수 있다. 백엔드 포트폴리오로 강하게 보이려면 비동기 작업 처리, 큐 기반 워커, 캐싱, API 호출량 제한, 장애 대응, 이벤트 로그, 실시간 처리, 성능 측정이 드러나야 한다.

# 2. 전체 시스템 아키텍처

## 2-1. 최종 아키텍처

```text
[Client: Next.js / React]
  ├─ 자연어 추천 요청
  ├─ 추천 진행 상태 SSE 구독
  ├─ 추천 결과 조회
  ├─ 공유 링크 생성
  ├─ 공유방 투표
  └─ 클릭·공유·피드백 이벤트 전송

[Spring Boot API Server]
  ├─ Spring Web MVC REST API
  ├─ 요청 검증
  ├─ 사용자별 Rate Limit Interceptor
  ├─ Recommendation Job 생성
  ├─ Redis Streams 이벤트 발행
  ├─ 추천 결과 조회 API
  ├─ 공유방 생성 API
  ├─ 투표 API
  ├─ 이벤트 수집 API
  └─ SseEmitter 기반 SSE Endpoint

[Spring Worker]
  ├─ Redis Streams Consumer
  ├─ LLM 조건 추출
  ├─ 검색 쿼리 생성
  ├─ 네이버 지역 검색 호출
  ├─ 네이버 블로그 검색 호출
  ├─ 후보 중복 제거
  ├─ 블로그 문맥 분석
  ├─ 조건 기반 점수화
  ├─ 추천 이유 생성
  ├─ 추천 결과 저장
  ├─ 실패 시 Retry
  └─ 반복 실패 시 DLQ 이동

[Redis]
  ├─ Streams: recommendation-events
  ├─ Streams: user-events
  ├─ Streams: dead-letter-events
  ├─ Cache: 지역 검색 결과
  ├─ Cache: 블로그 문맥
  ├─ Cache: 추천 결과
  ├─ Rate Limit Counter
  └─ 진행 상태 저장 또는 Pub/Sub

[PostgreSQL]
  ├─ recommendation_jobs
  ├─ place_candidates
  ├─ blog_contexts
  ├─ recommendation_results
  ├─ decision_rooms
  ├─ place_votes
  ├─ event_logs
  └─ api_quota_usages

[Monitoring / Test]
  ├─ Spring Boot Actuator
  ├─ Micrometer
  ├─ Prometheus
  ├─ Grafana
  ├─ OpenTelemetry
  ├─ JUnit 5
  ├─ Testcontainers
  ├─ WireMock / MockWebServer
  └─ k6
```

이 구조는 기존 최종 아키텍처와 일치한다. Spring Boot API Server는 REST API, 요청 검증, Rate Limit, Job 생성, Redis Streams 이벤트 발행, SSE Endpoint를 담당하고, Worker는 Redis Streams Consumer로 동작하면서 LLM 조건 추출, 네이버 지역·블로그 검색, 점수화, 결과 저장, Retry/DLQ를 처리한다. Redis는 Streams, Cache, Rate Limit Counter, 진행 상태 저장을 담당하고, PostgreSQL은 추천 Job·장소 후보·추천 결과·공유방·투표·이벤트 로그·API 사용량을 저장한다.

# 4. 백엔드 패키지 설계

Spring Boot는 처음부터 마이크로서비스로 쪼개지 않고, **모듈형 모놀리식**으로 시작한다. 이유는 포트폴리오 단계에서 복잡도를 과하게 늘리기보다, 도메인 경계를 명확히 하고 테스트 가능한 구조를 만드는 것이 더 중요하기 때문이다.

```text
com.placepick
 ├── recommendation
 │    ├── api
 │    ├── application
 │    ├── domain
 │    ├── infra
 │    └── worker
 │
 ├── place
 │    ├── domain
 │    ├── application
 │    └── infra
 │
 ├── naver
 │    ├── client
 │    ├── dto
 │    └── config
 │
 ├── llm
 │    ├── client
 │    ├── prompt
 │    └── dto
 │
 ├── decisionroom
 │    ├── api
 │    ├── application
 │    ├── domain
 │    └── infra
 │
 ├── event
 │    ├── producer
 │    ├── consumer
 │    ├── domain
 │    └── infra
 │
 ├── ratelimit
 │    ├── interceptor
 │    ├── application
 │    └── infra
 │
 ├── monitoring
 │    └── metric
 │
 └── common
      ├── exception
      ├── response
      ├── config
      └── util
```

기존 Spring 패키지 설계에서도 `recommendation`, `place`, `naver`, `llm`, `decisionroom`, `event`, `ratelimit`, `monitoring`, `common`으로 분리하고, 각 패키지의 책임을 추천 요청·장소 후보·외부 API·LLM·공유방·이벤트·호출량 제한·메트릭·공통 처리로 나누는 구조를 제안했다. 

## 4-1. 패키지별 책임

| 패키지              | 책임                                                 |
| ---------------- | -------------------------------------------------- |
| `recommendation` | 추천 Job 생성, 추천 파이프라인 상태 관리, 점수화, 추천 결과 조회           |
| `place`          | 장소 후보 저장, 중복 제거, 블로그 문맥 저장, 장소 데이터 정규화             |
| `naver`          | 네이버 지역 검색·블로그 검색 API Client, 응답 DTO, 호출 예외 처리      |
| `llm`            | 조건 추출, 검색 쿼리 생성, 블로그 문맥 요약, 추천 이유 생성               |
| `decisionroom`   | 공유방 생성, 투표 제출, 최종 합의 결과 계산                         |
| `event`          | Redis Streams Producer/Consumer, 이벤트 로그 저장, DLQ 처리 |
| `ratelimit`      | 사용자별 요청 제한, 네이버/LLM API 호출량 제한                     |
| `monitoring`     | 추천 시간, 큐 pending, 캐시 hit/miss, API 호출량 메트릭         |
| `common`         | 공통 응답, 예외, 에러 코드, 시간 유틸, JSON 유틸                   |

# 5. 핵심 도메인 모델

## 5-1. 도메인 개요

```text
RecommendationJob
 ├─ ExtractedCondition
 ├─ PlaceCandidate[]
 │    └─ BlogContext
 ├─ RecommendationResult[]
 └─ DecisionRoom
      └─ PlaceVote[]
```

## 5-2. 주요 Aggregate

### RecommendationJob

추천 요청의 루트 Aggregate다.

역할:

```text
사용자 원문 입력 저장
AI가 추출한 조건 저장
추천 처리 상태 관리
추천 파이프라인의 기준 jobId 제공
추천 결과와 공유방의 상위 기준
```

상태:

```text
PENDING
PROCESSING
CONDITION_EXTRACTED
LOCAL_SEARCH_DONE
BLOG_CONTEXT_DONE
SCORING_DONE
LLM_GENERATION_DONE
COMPLETED
FAILED
```

### PlaceCandidate

네이버 지역 검색에서 가져온 장소 후보다.

역할:

```text
네이버 검색 결과 기반 장소 저장
같은 장소 중복 제거
추천 점수 계산의 대상
블로그 문맥과 연결
```

### BlogContext

후보 장소에 대한 블로그 검색 문맥이다.

역할:

```text
조용함, 웨이팅, 가성비, 단체 가능성 등 키워드 저장
긍정 키워드와 리스크 키워드 분리
추천 이유와 주의점 생성의 근거
```

### RecommendationResult

최종 후보 3개 결과다.

역할:

```text
추천 순위
점수
추천 이유
주의점
공유 문장
네이버 상세 링크
```

### DecisionRoom

친구들이 공유 링크에서 투표하는 방이다.

역할:

```text
공유 URL 생성
투표 상태 관리
최종 합의 결과 계산 기준
```

### PlaceVote

공유방 투표 기록이다.

역할:

```text
후보별 LIKE / DISLIKE 저장
익명 사용자 기준 중복 투표 방지
투표 이유 저장
후보 점수 재계산에 반영
```

# 6. 데이터베이스 설계

## 6-1. ERD 개념

```text
recommendation_jobs 1 ─ N place_candidates
recommendation_jobs 1 ─ N recommendation_results
place_candidates 1 ─ 1 blog_contexts
recommendation_jobs 1 ─ 1 decision_rooms
decision_rooms 1 ─ N place_votes
recommendation_jobs 1 ─ N event_logs
decision_rooms 1 ─ N event_logs
api_quota_usages 독립
```

## 6-2. 테이블 설계

### `recommendation_jobs`

추천 작업의 기준 테이블.

| 컬럼                     | 타입            | 설명         |
| ---------------------- | ------------- | ---------- |
| `id`                   | bigint / uuid | 추천 Job ID  |
| `session_id`           | varchar       | 익명 사용자 세션  |
| `raw_query`            | text          | 사용자 원문     |
| `structured_condition` | jsonb         | AI가 추출한 조건 |
| `status`               | varchar       | 추천 작업 상태   |
| `failure_reason`       | varchar       | 실패 이유      |
| `retry_count`          | int           | 재시도 횟수     |
| `created_at`           | timestamp     | 생성 시각      |
| `updated_at`           | timestamp     | 수정 시각      |
| `completed_at`         | timestamp     | 완료 시각      |

인덱스:

```sql
idx_recommendation_jobs_session_id
idx_recommendation_jobs_status_created_at
```

### `place_candidates`

네이버 지역 검색 결과 후보.

| 컬럼                 | 타입            | 설명            |
| ------------------ | ------------- | ------------- |
| `id`               | bigint / uuid | 후보 ID         |
| `job_id`           | FK            | 추천 Job ID     |
| `source`           | varchar       | `NAVER_LOCAL` |
| `title`            | varchar       | 장소명           |
| `category`         | varchar       | 카테고리          |
| `address`          | varchar       | 지번 주소         |
| `road_address`     | varchar       | 도로명 주소        |
| `naver_link`       | text          | 네이버 상세 링크     |
| `mapx`             | varchar       | 네이버 좌표값       |
| `mapy`             | varchar       | 네이버 좌표값       |
| `raw_payload_hash` | varchar       | 중복 제거 해시      |
| `created_at`       | timestamp     | 생성 시각         |

후보 장소와 블로그 문맥, 추천 결과, 공유방 투표, 이벤트 로그, API 호출량 관리 테이블은 기존 설계에서도 핵심 테이블로 정리되어 있다. 특히 `place_candidates`는 `source`, `title`, `category`, `address`, `road_address`, `naver_link`, `mapx`, `mapy`, `raw_payload_hash`를 가진다. 

### `blog_contexts`

장소별 블로그 문맥.

| 컬럼                   | 타입            | 설명          |
| -------------------- | ------------- | ----------- |
| `id`                 | bigint / uuid | 문맥 ID       |
| `place_candidate_id` | FK            | 후보 장소 ID    |
| `positive_keywords`  | jsonb         | 긍정 키워드      |
| `risk_keywords`      | jsonb         | 리스크 키워드     |
| `summary`            | text          | 문맥 요약       |
| `source_count`       | int           | 참고한 검색 결과 수 |
| `created_at`         | timestamp     | 생성 시각       |

### `recommendation_results`

최종 추천 결과.

| 컬럼                   | 타입            | 설명        |
| -------------------- | ------------- | --------- |
| `id`                 | bigint / uuid | 결과 ID     |

# 7. 추천 처리 파이프라인 설계

## 7-1. 전체 흐름

```text
1. 사용자가 자연어로 추천 요청
2. API Server가 RecommendationJob 생성
3. API Server가 jobId를 즉시 반환
4. Redis Streams에 recommendation.requested 이벤트 발행
5. Worker가 이벤트 소비
6. LLM API로 조건 추출
7. 검색 쿼리 생성
8. Redis Cache에서 지역 검색 결과 확인
9. 캐시가 없으면 네이버 지역 검색 호출
10. 후보 장소 중복 제거
11. 상위 후보 5개에 대해 블로그 검색 수행
12. 블로그 문맥 요약 및 키워드 추출
13. 조건 기반 점수화
14. 상위 3개 후보 선정
15. LLM API로 추천 이유·주의점·공유 문장 생성
16. RecommendationResult 저장
17. Job 상태 COMPLETED로 변경
18. SSE로 completed 이벤트 전송
19. 사용자가 공유방 생성
20. 친구들이 공유방에서 투표
21. 투표 이벤트 저장
22. 점수 재계산
23. 최종 합의 결과 제공
```

기존 설계에서도 사용자가 자연어로 요청하면 API Server가 `recommendation_job`을 생성하고 `jobId`를 즉시 반환한 뒤, Redis Streams에 이벤트를 발행하고 Worker가 조건 추출·검색·점수화·LLM 생성·결과 저장·SSE 완료 전송·공유방 투표·최종 순위 재계산을 처리하는 흐름으로 정리했다. 

## 7-2. Job 상태 전이

```text
PENDING
  ↓
PROCESSING
  ↓
CONDITION_EXTRACTED
  ↓
LOCAL_SEARCH_DONE
  ↓
BLOG_CONTEXT_DONE
  ↓
SCORING_DONE
  ↓
LLM_GENERATION_DONE
  ↓
COMPLETED
```

실패 시:

```text
PROCESSING
  ↓
FAILED
  ↓
RETRY_SCHEDULED
  ↓
PROCESSING
```

반복 실패 시:

```text
FAILED
  ↓
DLQ
```

```json
  "priority": ["분위기", "예산"]
}
```

## 10-3. 추천 문장 정책

금지 표현:

```text
무조건 만족합니다.
실제로 조용합니다.
웨이팅이 없습니다.
예약 가능합니다.
가격은 정확히 2만 원입니다.
```

허용 표현:

```text
검색 문맥상 조용한 분위기와 관련된 표현이 반복됩니다.
금요일 저녁에는 혼잡 가능성이 있어 방문 전 확인이 필요합니다.
예산 조건과 크게 충돌하지 않는 후보로 판단됩니다.
```

추천 문장은 Spring 서비스 레이어에서 `RecommendationReasonPolicy`로 검증한다. 기존 설계에서도 단정 표현을 필터링하고, “검색 문맥상”, “가능성”, “확인 필요” 표현을 강제하며, 확인 불가 정보는 `caution` 필드로 분리하는 정책을 제안했다.

# 11. 네이버 API 연동 설계

## 11-1. NaverLocalSearchClient

역할:

```text
네이버 지역 검색 호출
장소명, 카테고리, 주소, 도로명 주소, 링크, 좌표값 수집
응답 DTO를 PlaceCandidate로 변환
```

메서드:

```java
List<NaverLocalSearchItem> searchLocal(String query, int display);
```

## 11-2. NaverBlogSearchClient

역할:

```text
후보 장소명 + 지역명 기반 블로그 검색
제목, 요약, 링크, 작성일 수집
블로그 문맥 분석에 필요한 raw data 제공
```

메서드:

```java
List<NaverBlogSearchItem> searchBlogs(String query, int display);
```

## 11-3. 호출량 제한

검색 1회당 외부 API 호출량을 제한한다.

```text
지역 검색 쿼리 3개 = 3회
상위 후보 5개 블로그 검색 = 5회
총 약 8회
```

기존 비용 리스크 방지 정책에서도 검색 1회당 지역 검색 3회와 후보 5개에 대한 블로그 검색 5회, 총 약 8회로 제한하는 기준을 제안했다. 

## 11-4. 실제 구현 정책

```text
1. 외부 API 호출 전 RateLimitService 확인
2. Redis Cache 확인
3. 캐시 hit면 외부 API 호출 생략
4. cache miss면 네이버 API 호출
5. 성공 시 raw response hash 저장
6. timeout 시 제한적 retry
7. 반복 실패 시 fallback
```

# 12. 점수화 설계

## 12-1. 기본 점수

```text
최종 점수 =
지역 적합성
+ 장소 유형 적합성
+ 목적 적합성
+ 분위기 적합성
+ 예산 적합성
+ 근거 신뢰도
- 리스크 감점
```

| 항목        |    배점 |
| --------- | ----: |
| 지역 적합성    |    25 |
| 장소 유형 적합성 |    15 |
| 목적 적합성    |    20 |
| 분위기 적합성   |    25 |
| 예산 적합성    |    10 |
| 근거 신뢰도    |     5 |
| 리스크 감점    | -15까지 |

## 12-2. 투표 반영 점수

공유방 투표 후에는 최종 점수를 다시 계산한다.

```text
finalScore =
recommendationScore
+ likeCount * 4
- dislikeCount * 5
+ majorityBonus
- riskPenalty
```

예시:

```text
A식당 기존 점수: 87
좋아요 1개: +4
별로예요 0개: 0
최종 점수: 91

B식당 기존 점수: 84
좋아요 2개: +8
최종 점수: 92
```

## 12-3. 점수화 서비스

```text
RecommendationScoringService
 ├─ calculateBaseScore()
 ├─ calculateLocationScore()
 ├─ calculatePurposeScore()
 ├─ calculateMoodScore()
 ├─ calculateBudgetScore()
 ├─ calculateEvidenceScore()
 ├─ calculateRiskPenalty()
```

# 13. Redis Cache 설계

## 13-1. 캐시 대상

| 캐시 대상     | Redis Key                                  |    TTL |
| --------- | ------------------------------------------ | -----: |
| 지역 검색 결과  | `local:{location}:{placeType}:{queryHash}` | 6~24시간 |
| 블로그 검색 결과 | `blog:{placeName}:{location}`              |   1~7일 |
| 블로그 문맥 요약 | `blog-context:{placeHash}`                 |   1~7일 |
| 조건 추출 결과  | `condition:{queryHash}`                    |    1시간 |
| 추천 결과     | `recommendation:{conditionHash}`           |  1~6시간 |
| 공유방 결과    | `room-result:{roomId}`                     |   1~5분 |

## 13-2. 캐시 전략

```text
1. 동일 조건 추천 결과가 있으면 즉시 반환 가능
2. 단, 공유방 투표가 있는 추천은 투표 반영 결과를 별도 관리
3. 지역 검색 결과는 비교적 긴 TTL
4. 블로그 문맥은 중간 TTL
5. 추천 결과는 짧은 TTL
6. API 호출량 한도 임박 시 캐시 우선 반환
```

## 13-3. Cache invalidation

```text
추천 결과:
- TTL 만료 시 자동 제거
- 조건이 다르면 다른 key 사용

공유방 결과:
- 투표 발생 시 room-result:{roomId} 삭제 또는 갱신

API 사용량:
- 날짜별 key 사용
- 자정 기준 만료
```

# 16. 공유방 투표 설계

## 16-1. 공유방 생성

추천 결과가 완료된 Job에 대해서만 공유방을 만들 수 있다.

검증:

```text
1. jobId 존재 여부
2. job status == COMPLETED
3. 추천 결과 3개 존재
4. 이미 열린 room이 있으면 기존 room 반환 가능
```

## 16-2. 투표 제출

검증:

```text
1. room 존재 여부
2. room status == OPEN
3. room 만료 여부
4. placeId가 해당 room의 추천 결과에 포함되는지 확인
5. voterId + placeId 중복 투표 여부 확인
```

## 16-3. 점수 재계산

투표가 들어오면 다음 작업을 수행한다.

```text
1. place_votes 저장
2. vote.submitted 이벤트 저장
3. user-events Stream 발행
4. room-result 캐시 무효화
5. 후보별 like/dislike 집계
6. 최종 점수 재계산
7. 최종 결과 조회 시 최신 결과 반환
```

## 16-4. 중복 투표 방지

```text
idempotencyKey = roomId + voterId + placeId
```

DB unique constraint와 `event_logs.idempotency_key`를 함께 사용한다.

# 19. 장애 대응 설계

## 19-1. 장애 상황별 대응

| 장애 상황               | 대응                            |
| ------------------- | ----------------------------- |
| LLM 조건 추출 실패        | 1회 재시도 후 기본 규칙 기반 파싱 fallback |
| LLM 추천 이유 생성 실패     | 템플릿 기반 추천 문장 생성               |
| 네이버 지역 검색 timeout   | 제한적 retry 후 실패 처리             |
| 네이버 블로그 검색 실패       | 지역 검색 후보만으로 추천 진행             |
| Redis Streams 처리 실패 | retry stream 이동               |
| 반복 실패               | dead-letter-events 이동         |
| SSE 연결 끊김           | 재연결 시 현재 Job 상태 재전송           |
| 투표 중복 제출            | idempotency key로 중복 방지        |
| API quota 초과        | 캐시 결과 반환, 없으면 제한 안내           |
| DB 저장 실패            | Job FAILED 처리 후 DLQ 이벤트 생성    |

## 19-2. Retry 정책

```text
외부 API timeout:
- 최대 2회 재시도
- exponential backoff
- 이후 fallback 또는 FAILED

Worker 처리 실패:
- retry_count 증가
- retry stream 이동
- 최대 3회 이후 DLQ

이벤트 중복:
- idempotency_key 확인
- 이미 처리된 이벤트면 ACK만 수행
```

# 20. 테스트 설계

## 20-1. 테스트 계층

| 테스트        | 도구                                | 대상                                     |
| ---------- | --------------------------------- | -------------------------------------- |
| 단위 테스트     | JUnit 5                           | 점수화, 조건 후처리, 정책 검증                     |
| 통합 테스트     | Spring Boot Test + Testcontainers | PostgreSQL, Redis Streams, Redis Cache |
| 외부 API 테스트 | WireMock / MockWebServer          | 네이버 API, LLM API mock                  |
| SSE 테스트    | MockMvc / 통합 테스트                  | 진행 상태 이벤트                              |
| 이벤트 테스트    | Redis Testcontainer               | Stream 발행, 소비, ACK, DLQ                |
| 부하 테스트     | k6                                | 추천 요청, 투표 요청, Worker 처리량               |
| LLM Eval   | JSONL + JUnit                     | 조건 추출, 금지 표현 검증                        |

## 20-2. 반드시 테스트할 시나리오

```text
1. 추천 요청 생성 시 Job이 PENDING으로 저장된다.
2. Redis Streams에 recommendation.requested 이벤트가 발행된다.
3. Worker가 이벤트를 소비하고 ACK한다.
4. LLM 조건 추출 결과가 JSON Schema를 만족한다.
5. 네이버 지역 검색 결과가 PlaceCandidate로 저장된다.
6. 중복 후보가 제거된다.
7. 블로그 문맥이 BlogContext로 저장된다.
8. 점수화 결과 상위 3개만 추천된다.
9. 추천 문장에 금지 표현이 포함되면 실패한다.
10. SSE로 단계별 progress가 전달된다.
11. 공유방이 생성된다.
12. 투표가 저장되고 중복 투표가 차단된다.
13. 투표 후 최종 점수가 재계산된다.
14. 네이버 API timeout 시 retry 또는 fallback이 동작한다.
15. 반복 실패 이벤트는 DLQ로 이동한다.
```

## 20-3. k6 부하 테스트

실제 네이버 API에 부하를 주지 않고, Mock Naver API와 Mock LLM API를 둔다.

테스트 구성:

```text
k6
 → Spring Boot API Server
 → Redis Streams
 → Spring Worker
 → Mock Naver API
 → Mock LLM API
 → PostgreSQL
 → Redis Cache
```

k6 테스트와 CI 구성은 기존 개발 환경 설계에서도 `POST /api/v1/recommendations`에 대해 p95와 실패율을 측정하는 방식으로 제안했다.

```text
1. Spring Boot 프로젝트 skeleton
2. PostgreSQL / Redis Docker 환경
3. RecommendationJob Entity + API
4. Redis Streams Publisher
5. Worker Consumer skeleton
6. Mock LLM / Mock Naver API 연동
7. 추천 파이프라인
8. SSE 진행 상태
9. 추천 결과 조회
10. 공유방 / 투표
11. 캐시 / Rate Limit
12. 이벤트 로그 / 대시보드
13. Retry / DLQ
14. k6 부하 테스트
```

MVP는 자연어 조건 입력 → AI 조건 추출, 네이버 지역·블로그 검색 기반 후보 3개 추천, 공유 링크에서 친구들이 후보 투표 세 가지로 좁힌다. 백엔드 고도화 기능은 Job 생성, Redis Streams Worker, Redis Cache, API 호출량 제한, SSE, 투표 이벤트, 이벤트 로그, 대시보드, DLQ, k6 부하 테스트다.

# 24. 최종 구현 설계 요약

최종 구현은 다음 구조로 잡는다.

```text
프론트엔드:
Next.js + React + TypeScript + Tailwind CSS

백엔드:
Java 21 + Spring Boot + Spring Web MVC + JPA

비동기 처리:
Redis Streams + Spring Worker

DB:
PostgreSQL

캐시/제한:
Redis Cache + Redis Counter 기반 Rate Limit

실시간:
SseEmitter 기반 SSE

외부 API:
Naver Local Search API
Naver Blog Search API
LLM API

테스트:
JUnit 5
Testcontainers
WireMock / MockWebServer
k6

관측성:
Spring Boot Actuator
Micrometer
Prometheus
Grafana
OpenTelemetry
```

최종적으로 이 프로젝트는 다음을 구현하는 것이 목표다.

> **Spring Boot API 서버가 추천 요청을 Job으로 등록하고, Redis Streams 기반 Worker가 LLM 조건 추출·네이버 검색·블로그 문맥 분석·점수화·추천 이유 생성을 처리하며, 사용자는 SSE로 추천 진행 상태를 보고, 공유방 투표 이벤트를 통해 최종 모임 장소를 합의하는 이벤트 기반 AI 백엔드 플랫폼.**
