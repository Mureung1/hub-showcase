# 최종 기획안

# **플레이스픽 AI — 네이버 검색 API 기반 이벤트 중심 실시간 모임 장소 의사결정 플랫폼**

## 0. 최종 방향

기존 아이디어인 **AI 장소 추천 서비스**는 유지하되, 최종 주제는 더 명확하게 고도화한다.

기존 방향은 “사용자가 조건을 입력하면 AI가 장소 3개를 추천하는 서비스”였지만, 최종 기획안에서는 이를 **실시간 모임 장소 의사결정 플랫폼**으로 확장한다. 이렇게 해야 단순한 맛집 추천 서비스가 아니라, 백엔드 개발자로서 **비동기 처리, 이벤트 기반 아키텍처, 캐싱, API 호출량 제어, 실시간 상태 전송, 사용자 이벤트 처리** 역량을 보여줄 수 있다. 기존 주제를 “네이버 검색 API 기반 실시간 모임 장소 의사결정 백엔드 시스템”으로 바꾸는 것이 가장 적합하다는 검토 방향을 반영했다. 

## 서비스 한 줄 소개

**플레이스픽 AI는 사용자의 모임 조건을 AI가 해석하고, 네이버 지역·블로그 검색 결과를 기반으로 장소 후보를 추천하며, 공유 링크에서 발생하는 투표·클릭·피드백 이벤트를 실시간으로 처리하는 백엔드 중심 AI 서비스다.**

이 서비스는 네이버 공식 서비스가 아니라, **네이버 API를 활용하는 외부 서비스**로 기획한다. NAVER API HUB는 검색·쇼핑·트렌드 등 네이버 API를 하나의 콘솔에서 연동하고 운영할 수 있는 통합 허브이며, 검색 API는 블로그, 뉴스, 이미지, 지역, 지식iN 등 네이버 검색 결과를 서비스에 가져와 활용할 수 있는 API 묶음이다. 이 중 지역 검색은 네이버 지역 서비스에 등록된 업체·기관 검색 결과를 제공한다. ([NAVER CLOUD PLATFORM][1])

# 1. 기획 기준과 의도

## 1-1. 기획 기준

| 기준            | 최종 판단                                                     |
| ------------- | --------------------------------------------------------- |
| 네이버 관련성       | 네이버 지역 검색과 블로그 검색을 핵심 데이터 소스로 사용한다.                       |
| AI 기반성        | LLM API로 조건 추출, 검색 문맥 요약, 추천 이유 생성을 수행한다.                 |
| GPU 학습 없음     | 자체 모델 학습 없이 LLM API, 규칙 기반 점수화, 캐싱으로 구현한다.                |
| 백엔드 포트폴리오 적합성 | 추천 작업을 Job으로 만들고, Redis Streams 기반 비동기 파이프라인으로 처리한다.      |

| 실시간성          | 추천 진행 상태와 공유방 투표 결과를 SSE 또는 WebSocket으로 전달한다.             |
| 비용 현실성        | MVP에서는 지도·길찾기·예약·결제·자체 학습을 제외한다.                          |

## 1-2. 최종 기획 의도

이 프로젝트의 목적은 단순히 “좋은 맛집을 추천하는 것”이 아니다.

정확한 기획 의도는 다음이다.

> **여러 사람이 약속 장소를 정할 때 발생하는 검색, 비교, 공유, 의견 수렴, 최종 합의 과정을 AI와 이벤트 기반 백엔드 시스템으로 줄이는 것**

사용자는 이미 네이버에서 장소를 검색할 수 있다. 하지만 실제로 어려운 것은 검색 결과를 보고 **우리 모임 조건에 맞는지 비교하고, 단체방에서 의견을 조율하고, 최종 결정을 내리는 과정**이다. 따라서 플레이스픽 AI는 “장소 검색 서비스”가 아니라 **모임 장소 의사결정 보조 서비스**로 정의한다.

# 2. 문제 발견

## 2-1. 관찰에서 출발한 문제

모임 장소를 정할 때 사용자는 보통 다음 과정을 반복한다.

```text
1. 네이버에서 지역 + 맛집, 지역 + 조용한 카페, 지역 + 회식 장소 등을 검색한다.
2. 네이버 플레이스, 블로그, 지도, 후기 글을 여러 개 확인한다.
3. 위치, 가격, 분위기, 인원 수용 가능성, 웨이팅 가능성을 비교한다.
4. 단체 채팅방에 후보를 공유한다.
5. 친구들의 의견을 듣고 다시 검색한다.
6. 결국 가장 무난해 보이는 곳을 감으로 고른다.
```

이 과정에서 핵심 불편은 **정보 부족**이 아니라 **정보 과잉과 의사결정 피로**다. 사용자는 장소를 몰라서 힘든 것이 아니라, 후보가 너무 많고 판단 기준이 흩어져 있어서 힘들다.

## 2-2. 사용자가 직접 확인해야 하는 것

| 확인 항목 | 사용자가 느끼는 불편                    |
| ----- | ------------------------------ |
| 위치    | 역에서 가까운지 직접 확인해야 한다.           |
| 분위기   | 조용한지, 대화하기 좋은지 블로그 후기를 읽어야 한다. |
| 예산    | 가격대가 모임 조건과 맞는지 여러 글을 비교해야 한다. |
| 인원    | 4명, 5명, 단체 방문이 가능한지 확인해야 한다.   |
| 웨이팅   | 금요일 저녁이나 주말에 혼잡할지 직접 판단해야 한다.  |
| 공유    | 단체방에 보낼 후보와 이유를 다시 정리해야 한다.    |
| 합의    | 친구들의 의견을 모아 최종 장소를 다시 골라야 한다.  |

## 2-3. 발견한 핵심 니즈

사용자는 단순히 “장소를 많이 추천받고 싶다”가 아니라, 다음과 같은 니즈를 가진다.

> **“우리 모임 조건에 맞는 장소를 빠르게 3개 정도로 줄이고, 왜 괜찮은지 설명을 받고, 친구들과 쉽게 합의하고 싶다.”**

기존 정리에서도 이 서비스의 핵심은 “정보를 더 많이 보여주는 것”이 아니라, 네이버 검색 결과를 바탕으로 사용자의 상황에 맞는 결정을 돕는 것이라고 정의했다.

# 3. 문제 정의

## 문제 정의 한 문장

**모임 장소를 정해야 하는 사용자는 여러 사람의 위치, 예산, 인원, 분위기, 선호 조건을 동시에 고려해야 하는 상황에서 네이버 검색 결과와 블로그 후기를 직접 비교하고 단체방 의견까지 조율해야 해서 최종 장소를 결정하는 데 시간과 피로를 느낀다.**

## 문제 구성

| 구분      | 내용                                                                           |
| ------- | ---------------------------------------------------------------------------- |
| 누가      | 친구, 연인, 동료와 만날 장소를 정해야 하는 20~30대 사용자                                         |
| 어떤 상황에서 | 친구 모임, 데이트, 회식, 스터디, 소개팅 장소를 정할 때                                            |
| 무슨 불편을  | 네이버 검색 결과와 블로그 후기를 직접 비교하고, 단체방 의견까지 조율해야 하는 불편                              |
| 왜 문제인가  | 후보는 많지만 최종 결정을 내리기 어렵고, 장소 선택 실패에 대한 부담이 있기 때문                               |

# 5. 사용자 시나리오

지민은 금요일 저녁에 친구 4명과 강남역에서 만나기로 했다. 네이버에서 “강남역 맛집”, “강남역 조용한 음식점”, “강남역 4명 모임 장소”를 검색해 보지만 후보가 너무 많고, 블로그 후기를 하나씩 읽으며 분위기와 가격대를 비교하는 과정이 번거롭다.

지민은 플레이스픽 AI에 다음과 같이 입력한다.

```text
강남역에서 친구 4명이 갈 만한 조용한 음식점 추천해줘.
1인 2만 원대였으면 좋겠고, 너무 시끄러운 곳은 싫어.
```

서비스는 이 요청을 바로 처리하지 않고 먼저 **추천 작업 Job**을 생성한다.

```text
추천 작업 ID: rec_001
상태: PENDING
```

이후 백엔드 워커가 비동기로 작업을 처리한다.

```text
조건 분석 중
네이버 지역 검색 중
블로그 문맥 분석 중
후보 점수 계산 중
추천 문장 생성 중
완료
```

지민의 화면에는 추천 진행 상태가 실시간으로 표시된다. 추천이 완료되면 서비스는 장소 후보 3개를 보여준다.

```text
1위 A식당
2위 B식당
3위 C식당
```

각 후보에는 추천 이유와 주의점이 함께 제공된다.

```text
1위 A식당

추천 이유:
강남역 근처 후보 중 조용함, 대화하기 좋음과 관련된 블로그 문맥이 반복됩니다.
친구 4명이 대화 중심으로 만나기에 가장 무난한 후보입니다.

주의점:
금요일 저녁에는 혼잡할 수 있어 방문 전 확인이 필요합니다.
```

지민은 공유 링크를 친구들에게 보낸다. 친구들은 링크에 들어와 후보별로 좋아요, 별로예요, 의견을 남긴다.

```text
친구 1: A식당 좋음
친구 2: B식당이 더 가까움
친구 3: C식당은 웨이팅 있을 것 같음
```

서비스는 이 투표와 피드백을 이벤트로 수집한다.

```text
vote.submitted
place.clicked
share.opened
feedback.submitted
```

그리고 실시간으로 후보 점수를 다시 계산한다.

```text
A식당: 87점
B식당: 84점 → 친구 투표 반영 후 89점
C식당: 78점
```

최종적으로 서비스는 단체 합의에 가장 적합한 장소를 다시 추천한다.

```text
최종 추천: B식당
이유: 친구 2명이 선호했고, 접근성과 가격 조건이 가장 안정적입니다.
```

이 시나리오는 단순 추천이 아니라 **추천 → 공유 → 투표 → 재계산 → 최종 합의**까지 이어지므로, 서비스 가치와 백엔드 기술 가치가 동시에 드러난다.

# 6. 핵심 기능 도출

## 6-1. 사용자 기능

| 기능                  | 설명                               | 필요 이유                |
| ------------------- | -------------------------------- | -------------------- |
| 자연어 조건 입력           | 사용자가 모임 조건을 문장으로 입력              | 복잡한 필터 없이 빠르게 진입     |
| AI 조건 추출            | 지역, 인원, 장소 유형, 예산, 분위기, 회피 조건 추출 | 검색 쿼리 생성과 점수화의 기준    |

| 공유 링크 생성            | 친구들에게 후보를 공유                     | 단체 의사결정으로 연결         |
| 공유방 투표              | 친구들이 후보별 의견 제출                   | 실시간 합의 기능 구현         |
| 최종 합의 장소 재추천        | 투표와 조건을 반영해 최종 순위 조정             | 개인 추천에서 단체 결정으로 확장   |

| Redis 캐싱           | 동일 검색어, 블로그 문맥, 추천 결과 캐싱    | 성능 최적화           |
| API 호출량 제한         | 네이버 API와 LLM API 호출량 관리     | 외부 API 보호, 비용 제어 |
| SSE 추천 진행 상태       | 추천 단계별 진행 상황 실시간 전송         | 실시간 서버 푸시        |
| 공유방 투표 이벤트 처리      | 친구들의 투표를 이벤트로 수집            | 실시간 협업 기능        |
| 이벤트 로그 저장          | 클릭, 공유, 피드백, 실패 이벤트 저장      | 데이터 수집 설계        |
| 실시간 통계 대시보드        | 요청 수, 성공률, 캐시 히트율, 인기 지역 표시 | 운영·관측 역량         |
| Retry / DLQ        | 실패한 작업 재시도 및 격리             | 장애 대응            |
| Mock API 기반 부하 테스트 | 실제 네이버 API에 부하를 주지 않고 성능 검증 | 대용량 처리 검증        |

이 고도화 기능들은 기존 정리에서 제안한 핵심 백엔드 포트폴리오 요소를 반영한 것이다. 특히 추천 요청 Job 생성, Redis Streams 기반 비동기 워커, 캐싱, 호출량 제한, SSE, 이벤트 로그, 대시보드, DLQ, 부하 테스트가 최종 고도화 범위로 정리되어 있었다.

# 7. 우선순위와 MVP

## MVP 목표

**사용자가 모임 조건을 자연어로 입력하면, AI가 조건을 추출하고 네이버 지역·블로그 검색 결과를 바탕으로 후보 3개를 추천하며, 공유 링크에서 친구들이 후보에 투표할 수 있게 한다.**

## MVP 핵심 기능 3개

### MVP 1순위. 자연어 조건 입력 및 AI 조건 추출

사용자 입력을 구조화된 조건으로 바꾼다.

입력 예시:

```text
토요일 오후에 성수역에서 친구 3명이 갈 카페 추천해줘.
오래 앉아있을 수 있고 너무 시끄럽지 않았으면 좋겠어.
```

출력 예시:

```json
{
  "location": "성수역",
  "people_count": 3,
  "place_type": "카페",
  "purpose": "친구 모임",
  "preferences": ["오래 앉기 좋음", "조용함"],
  "avoid": ["시끄러운 곳"]
}
```

이 기능이 1순위인 이유는 사용자 조건을 제대로 이해하지 못하면 검색 쿼리 생성, 후보 수집, 점수화, 추천 이유 생성이 모두 부정확해지기 때문이다. 기존 MVP 정리에서도 조건 추출 AI를 1순위로 두었다. 

### MVP 2순위. 네이버 지역·블로그 검색 기반 후보 수집

조건 추출 결과를 바탕으로 네이버 지역 검색에서 장소 후보를 가져오고, 블로그 검색으로 분위기 문맥을 확인한다.

네이버 지역 검색 API는 네이버 지역 서비스에 등록된 업체 및 기관 검색 결과를 XML 또는 JSON으로 반환하는 RESTful API이며, 지역 검색은 검색 API를 사용하고 하루 호출 한도는 25,000회로 안내되어 있다. ([NAVER Developers][2])

NAVER API HUB의 검색 API는 블로그 검색과 지역 검색을 포함하며, 지역 검색은 네이버 지역 서비스의 업체·기관 검색 결과를 제공하고, 블로그 검색은 네이버 블로그 검색 결과를 제공한다. ([NAVER CLOUD PLATFORM][1])

### MVP 3순위. 후보 3개 추천 및 공유방 투표

수집한 후보를 조건별로 점수화하고 최종 3개를 추천한다. 이후 사용자는 공유 링크를 친구들에게 보내고, 친구들은 후보별로 투표한다.

결과 예시:

| 순위 | 장소  | 추천 이유                       | 주의점          |
| -: | --- | --------------------------- | ------------ |
|  1 | A식당 | 조용함, 대화 적합성, 예산 조건이 가장 잘 맞음 | 금요일 저녁 혼잡 가능 |
|  2 | B식당 | 친구 투표 반영 후 접근성과 선호도가 높음     | 가격대 확인 필요    |
|  3 | C식당 | 분위기는 좋지만 웨이팅 가능성 있음         | 방문 전 확인 필요   |

MVP는 기존 정리처럼 “자연어 조건 입력 → AI 조건 추출”, “네이버 지역·블로그 검색 기반 후보 3개 추천”, “공유 링크에서 친구들이 후보 투표” 세 가지로 좁힌다.

# 8. AI 설계

## 8-1. AI가 하는 일

| 단계        | AI 역할                                         |
| --------- | --------------------------------------------- |
| 조건 추출     | 사용자의 자연어 입력에서 지역, 인원, 예산, 목적, 분위기, 회피 조건 추출   |
| 검색 쿼리 생성  | “강남역 조용한 음식점”, “강남역 4인 모임 음식점”처럼 검색어 생성       |
| 블로그 문맥 요약 | 블로그 검색 결과 제목·요약에서 분위기, 웨이팅, 가성비, 단체 가능성 신호 추출 |
| 추천 이유 생성  | 점수화 결과를 사람이 이해하기 쉬운 문장으로 설명                   |
| 공유 문장 생성  | 단체방에 보낼 수 있는 짧은 요약 생성                         |

## 8-2. AI가 하지 않는 일

| 금지 항목          | 이유                    |
| -------------- | --------------------- |
| 존재하지 않는 장소 생성  | AI 환각 방지              |
| 확인하지 못한 가격 단정  | 검색 결과만으로 정확한 가격 확정 불가 |
| 실제 예약 가능 여부 단정 | 예약 연동을 MVP에서 제외       |
| 실제 혼잡도 단정      | 실시간 웨이팅 데이터 없음        |
| 자체 추천 모델 학습    | GPU 학습 없이 구현해야 함      |

추천은 반드시 **네이버 검색 결과에 존재하는 후보 안에서만** 수행한다. 일반 LLM 챗봇과 달리 장소를 상상해서 추천하지 않고, 네이버 검색 결과와 점수 기준에 근거하도록 설계한다.

# 9. 추천 점수 설계

## 9-1. 기본 점수표

| 평가 항목     | 판단 방식                                  | 기본 배점 |
| --------- | -------------------------------------- | ----: |
| 지역 적합성    | 사용자가 입력한 지역과 주소·장소명이 맞는가               |    25 |
| 장소 유형 적합성 | 카페, 음식점, 술집 등 조건과 일치하는가                |    15 |
| 목적 적합성    | 데이트, 친구 모임, 회식, 스터디 목적과 맞는가            |    20 |
| 분위기 적합성   | 블로그 문맥에서 조용함, 대화 가능성, 감성적 분위기 등이 확인되는가 |    25 |
| 예산 적합성    | 가격 관련 문맥이 사용자 예산과 충돌하지 않는가             |    10 |
| 근거 신뢰도    | 여러 검색 결과에서 유사 표현이 반복되는가                |     5 |
| 리스크 감점    | 웨이팅, 시끌벅적함, 협소함, 가격 부담 등               | -15까지 |

## 9-2. 사용자 강조 조건 반영

사용자가 “조용한 곳이 제일 중요해”라고 입력하면 분위기 적합성 배점을 높인다.

```text
기본:
지역 25 / 분위기 25 / 목적 20 / 예산 10 / 유형 15 / 근거 5

조용함 강조:
지역 20 / 분위기 40 / 목적 15 / 예산 10 / 유형 10 / 근거 5
```

사용자가 “역에서 가까운 곳이 제일 중요해”라고 입력하면 지역 적합성 배점을 높인다.

```text
지역 40 / 분위기 20 / 목적 15 / 예산 10 / 유형 10 / 근거 5
```

## 9-3. 추천 문장 원칙

추천 문장은 단정하지 않는다.

금지 표현:

```text
무조건 만족합니다.
실제로 조용합니다.
웨이팅이 없습니다.
예약 가능합니다.
가격은 정확히 2만 원입니다.
```

허용 표현:

```text
검색 문맥상 조용한 분위기와 관련된 표현이 반복됩니다.
금요일 저녁에는 혼잡 가능성이 있어 방문 전 확인이 필요합니다.
예산 조건과 크게 충돌하지 않는 후보로 판단됩니다.
```

# 10. 백엔드 시스템 설계

## 10-1. 최종 아키텍처

```text
[Client]
  ├─ 자연어 추천 요청
  ├─ 추천 진행 상태 SSE 구독
  ├─ 추천 결과 확인
  ├─ 공유 링크 생성
  └─ 투표·클릭·피드백 이벤트 전송

[API Server]
  ├─ 요청 검증
  ├─ 사용자별 Rate Limit
  ├─ Recommendation Job 생성
  ├─ Redis Streams 이벤트 발행
  ├─ 추천 결과 조회 API
  ├─ 공유방 생성 API
  └─ SSE Endpoint 제공

[Redis]
  ├─ Streams: recommendation-events
  ├─ Cache: 검색 결과 / 블로그 문맥 / 추천 결과
  ├─ Rate Limit Counter
  └─ 진행 상태 Pub/Sub 또는 Stream

[Worker]
  ├─ 조건 추출 LLM 호출
  ├─ 검색 쿼리 생성
  ├─ 네이버 지역 검색 호출
  ├─ 네이버 블로그 검색 호출
  ├─ 후보 중복 제거
  ├─ 조건 기반 점수화
  ├─ 추천 이유 LLM 생성
  ├─ 결과 저장
  ├─ 실패 시 Retry
  └─ 반복 실패 시 DLQ 이동

[PostgreSQL]
  ├─ recommendation_jobs
  ├─ place_candidates
  ├─ blog_contexts
  ├─ recommendation_results
  ├─ decision_rooms
  ├─ place_votes
  ├─ event_logs
  └─ api_quota_usages

[Monitoring]
  ├─ Prometheus
  ├─ Grafana
  ├─ OpenTelemetry
  └─ Structured Logging

[Load Test]
  ├─ k6
  ├─ Mock Naver API
  └─ Mock LLM API
```

이 구조는 기존 동기 처리 구조보다 백엔드 역량을 훨씬 잘 보여준다. 기존 검토에서도 단순히 “사용자 입력 → LLM 호출 → 네이버 API 호출 → 결과 출력”으로 끝나면 API 연동 프로젝트처럼 보일 수 있고, 백엔드 포트폴리오로 강하게 보이려면 비동기 작업 처리, 큐 기반 워커, 캐싱, API 호출량 제한, 장애 대응, 이벤트 로그, 실시간 처리, 성능 측정이 필요하다고 정리했다. 

## 10-2. 추천 처리 흐름

```text
1. 사용자가 자연어로 장소 추천 요청
2. API Server가 recommendation_job 생성
3. jobId를 사용자에게 즉시 반환
4. Redis Streams에 recommendation.requested 이벤트 발행
5. Worker가 이벤트를 소비해 조건 추출
6. 조건 기반 검색 쿼리 생성
7. Redis Cache에서 기존 검색 결과 확인
8. 캐시가 없으면 네이버 지역 검색 호출
9. 후보별 블로그 문맥 확인
10. 조건 기반 점수화
11. LLM으로 추천 이유와 공유 문장 생성
12. 결과를 PostgreSQL에 저장
13. 사용자에게 SSE로 완료 이벤트 전송
14. 사용자는 공유 링크 생성
15. 친구들은 공유방에서 투표
16. 투표 이벤트를 반영해 최종 순위 재계산
```

## 10-3. 추천 진행 상태

SSE 응답 예시:

```text
event: progress
data: {"step":"CONDITION_EXTRACTED","message":"조건 분석이 완료되었습니다.","progress":20}

event: progress
data: {"step":"LOCAL_SEARCH_DONE","message":"장소 후보를 찾았습니다.","progress":45}

event: progress
data: {"step":"BLOG_CONTEXT_DONE","message":"블로그 문맥 분석이 완료되었습니다.","progress":70}

event: progress
data: {"step":"SCORING_DONE","message":"후보 점수 계산이 완료되었습니다.","progress":85}

event: completed
data: {"step":"COMPLETED","message":"추천 결과가 완성되었습니다.","progress":100}
```

## 11-3. 대용량 처리 방향

대용량 처리는 네이버 API를 대량으로 호출해서 보여주지 않는다. 검색 API는 호출량 기준과 일 호출 제한이 있고 정책 변경 가능성이 있으므로, 고도화 방향은 외부 API를 많이 호출하는 것이 아니라 **사용자 요청, 클릭, 공유, 투표, 피드백, 실패 로그를 내부 이벤트 스트림으로 처리하는 것**이다. 기존 검토에서도 대용량성을 보여주려면 사용자의 클릭, 공유, 피드백, 투표, 추천 요청, API 호출 로그를 이벤트 데이터로 다뤄야 한다고 정리했다.

# 14. 캐싱과 호출량 제어

## 14-1. 캐싱 대상

| 캐시 대상     | 캐시 키 예시                          |    TTL |
| --------- | -------------------------------- | -----: |
| 지역 검색 결과  | `local:강남역:음식점`                  | 6~24시간 |
| 블로그 문맥 요약 | `blog-context:A식당:강남역`           |   1~7일 |
| 조건 추출 결과  | `condition-hash:{hash}`          |    1시간 |
| 추천 결과     | `recommendation:{conditionHash}` |  1~6시간 |
| 인기 지역 집계  | `trending:areas:10m`             |   1~5분 |

## 14-2. 호출량 관리

NAVER API HUB 검색 API는 공식 요금표 기준 0~775,000건 구간이 0원이고, 일 최대 25,000건 호출 제한이 있다. 또한 서비스 이용량은 API 호출 횟수 기준으로 집계되며, 한시적 무료 제공 정책은 추후 변경될 수 있다고 안내되어 있다. 따라서 이 기획에서는 “완전 무료”가 아니라 **무료 한도 내 MVP 운영**으로 표현하는 것이 정확하다. ([NAVER CLOUD PLATFORM][1])

검색 1회당 호출량 예시는 다음과 같이 제한한다.

| 작업                  | 호출 수 |
| ------------------- | ---: |
| 지역 검색 쿼리 3개         |   3회 |
| 상위 후보 5개에 대한 블로그 검색 |   5회 |
| 총 호출 수              | 약 8회 |

하루 100명이 1인당 3번 검색한다고 가정하면 다음과 같다.

```text
100명 × 3회 검색 × 8 API 호출 = 하루 2,400회
```

이 수치는 일 25,000건 제한 안에 들어오지만, 실제 운영에서는 Redis 기반 카운터로 일별·월별 호출량을 관리한다.

## 14-3. Rate Limiter 정책

```text
사용자별 제한:
rate:user:{sessionId}:minute
분당 5회

네이버 검색 API 일별 제한:
rate:naver-search:2026-07-09
일 최대 25,000회 기준으로 관리

LLM API 제한:
rate:llm:{date}
예산 또는 토큰 사용량 기준으로 관리
```

API 호출 전마다 Redis 카운터를 증가시키고, 한도에 가까워지면 신규 호출보다 캐시 결과를 우선 반환한다.

| Redis      | 사용    | 로컬 Docker 또는 무료/저비용 인프라 |
| PostgreSQL | 사용    | 로컬 Docker 또는 무료 플랜 가능   |
| 지도 화면      | 미사용   | MVP 제외                  |

| 자체 AI 학습   | 미사용   | GPU 불필요                 |

| 결제         | 미사용   | MVP 제외                  |

## 15-2. 지도·길찾기를 제외하는 이유

네이버 Maps는 위치 기반 서비스를 만들 수 있는 API이고, Dynamic Map, Static Map, Directions, Geocoding, Reverse Geocoding 등을 제공한다. 공식 요금표는 Maps 이용요금이 요청된 호출 수 기준으로 부과된다고 안내하며, Dynamic Map은 월 6,000,000건 이하 무료, Static Map과 Geocoding은 월 3,000,000건 이하 무료, Directions 5는 월 60,000건 이하 무료 등 무료 제공량이 있으나 대표 계정 1개 기준이다. ([NAVER CLOUD PLATFORM][3])

따라서 MVP에서는 지도 렌더링과 길찾기를 제외하고, 네이버 지역 검색 결과의 장소명·주소·네이버 링크를 활용한다. 지도 기능은 사용성 개선에는 좋지만, 이 프로젝트의 핵심 포트폴리오 가치는 **외부 API 호출 제어, 비동기 추천 파이프라인, 실시간 이벤트 처리**에 있다.

| 리스크           | 설명                         | 대응                                               |
| ------------- | -------------------------- | ------------------------------------------------ |

| 혼잡도 불확실       | 실시간 웨이팅 데이터 없음             | “혼잡 가능성” 수준으로만 표현                                |

| 지도 API 비용     | 지도/길찾기 사용 시 호출 비용 발생       | MVP 제외, 네이버 링크로 대체                               |
| 추천 작업 실패      | 외부 API 타임아웃 또는 LLM 실패      | timeout, retry, fallback, DLQ 적용                 |
| 중복 투표         | 같은 사용자가 여러 번 투표 가능         | roomId + voterId + placeId 기반 idempotency key 적용 |
| 개인정보 부담       | 로그인·실시간 위치 사용 시 부담 증가      | MVP에서는 익명 세션 기반, 정확한 위치 저장 없음                    |

네이버 개발자센터는 Search API, Search Trend API, Shopping Insight API가 NAVER API HUB로 이관되며, 2026년 7월 31일부터 개발자센터 신규 신청이 차단되고 2027년 6월 30일 이후에는 NAVER API HUB에서만 이용 가능하다고 공지했다. 따라서 이 프로젝트는 처음부터 NAVER API HUB 기준으로 설계하는 것이 안전하다. ([NAVER Developers][4])

# 20. 포트폴리오에서 강조할 점

이 프로젝트는 단순 CRUD나 단순 API 연동 프로젝트가 아니다.

포트폴리오에서는 다음 문장으로 설명한다.

> **플레이스픽 AI는 네이버 검색 API와 LLM API를 활용한 모임 장소 의사결정 서비스입니다. 추천 요청을 Job으로 등록하고 Redis Streams 기반 비동기 파이프라인에서 조건 추출, 장소 후보 수집, 블로그 문맥 분석, 점수화, 추천 문장 생성을 처리합니다. 공유 링크에서 발생하는 투표·클릭·피드백 이벤트를 실시간으로 수집하고, Redis 캐시와 Rate Limiter로 외부 API 호출량을 제어하며, Prometheus/Grafana와 k6 테스트로 성능과 안정성을 검증합니다.**

기존 검토에서도 이 방향은 서비스 기획 조건을 만족하면서 네이버 관련성, GPU 학습 없음, 백엔드 기술 깊이를 모두 확보할 수 있는 최종 선택으로 정리했다.
