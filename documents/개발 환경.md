# 1. 최종 개발 환경 목표

## 목표

**VS Code 안에서 Codex가 프로젝트 구조를 이해하고, Spring Boot 코드를 수정하고, Docker 기반 인프라를 실행하고, 테스트와 부하 테스트를 돌리고, 실패 로그를 바탕으로 다시 수정할 수 있는 agentic AI 개발 환경을 만든다.**

즉, 최종 환경은 아래처럼 동작해야 한다.

```text
사용자 또는 개발자
  ↓
Codex에게 작업 지시
  ↓
Codex가 AGENTS.md / Work Record / 아키텍처 문서 확인
  ↓
Spring Boot 코드 수정
  ↓
./gradlew test 실행
  ↓
Docker Compose로 PostgreSQL / Redis / Mock API 실행
  ↓
통합 테스트 실행
  ↓
k6 부하 테스트 실행
  ↓
Prometheus / Grafana 지표 확인
  ↓
실패 원인 분석
  ↓
수정 반복
  ↓
README / ADR / API 문서 업데이트
```

이 구조가 “AI 네이티브”한 이유는, 사람이 매번 설명하지 않아도 **프로젝트 규칙, 실행 방법, 검증 기준, 금지 사항, 완료 조건**이 저장소 안에 명시되어 있고, Codex가 그 기준에 따라 작업을 반복할 수 있기 때문이다.

# 2. 기준과 의도

## 기준 1. 재현 가능한 환경이어야 한다

Codex가 잘 동작하려면 “내 컴퓨터에서는 되는데 AI 환경에서는 안 됨”이 없어야 한다. 그래서 Java, Gradle, PostgreSQL, Redis, Prometheus, Grafana, k6, Mock API를 모두 Docker 또는 Dev Container 기준으로 묶어야 한다.

VS Code Dev Containers는 컨테이너를 완전한 개발 환경으로 사용할 수 있게 해 주고, `devcontainer.json`으로 어떤 런타임과 도구 스택을 사용할지 정의할 수 있다. ([Visual Studio Code][1])

## 기준 2. Codex가 프로젝트 규칙을 자동으로 읽어야 한다

Codex는 `AGENTS.md`를 작업 전에 읽고, 전역 지침과 프로젝트별 지침을 계층적으로 적용할 수 있다. 공식 문서에서도 Codex가 작업 전에 `AGENTS.md` 파일을 읽으며, 프로젝트별 오버라이드를 통해 일관된 기대치를 줄 수 있다고 설명한다. ([OpenAI 개발자][2])

따라서 이 프로젝트에는 반드시 루트에 `AGENTS.md`를 둬야 한다.

## 기준 3. AI가 실행할 수 있는 하네스가 있어야 한다

여기서 **하네스**는 단순 테스트 코드가 아니다.

OpenAI Cookbook에서는 하네스를 “모델 주변의 전체 계약”으로 설명한다. 여기에는 instruction, tool, routing, output requirement, validation check가 포함된다. ([OpenAI 개발자][3])

이 프로젝트에서 하네스는 다음을 의미한다.

```text
어떤 명령으로 실행하는가
어떤 테스트를 통과해야 하는가
어떤 출력 형식을 지켜야 하는가
어떤 아키텍처 규칙을 깨면 안 되는가
외부 API는 어떻게 Mock 해야 하는가
네이버 API 호출량은 어떻게 제한해야 하는가
추천 문장은 어떤 표현을 금지해야 하는가
```

## 기준 4. 루프 엔지니어링이 가능해야 한다

루프 엔지니어링은 한 번에 완벽한 답을 기대하는 방식이 아니다.

```text
구현
→ 실행
→ 검증
→ 실패 로그 수집
→ 원인 분석
→ 수정
→ 재검증
→ 문서화
```

이 반복 구조를 의도적으로 만드는 것이다.

OpenAI Cookbook의 Agent Improvement Loop도 trace, feedback, eval을 이용해 기대치를 재사용 가능하게 만들고 Codex가 다음 변경을 수행할 수 있게 하는 구조를 설명한다. ([OpenAI 개발자][3]) 또 Codex의 iterative repair loop 문서도 agent가 결과를 만들고, 검증하고, 피드백을 이용해 다음 pass에서 개선하는 closed-loop workflow를 설명한다. ([OpenAI 개발자][4])

## 기준 5. 외부 API를 실제로 때리며 테스트하면 안 된다

이 프로젝트는 네이버 API와 LLM API를 사용하지만, 대용량 처리 테스트를 실제 네이버 API에 걸면 안 된다. 기존 기획에서도 대용량 처리는 네이버 API를 무제한 호출하는 방식이 아니라, **사용자 요청, 클릭, 공유, 피드백, 추천 결과를 내부 이벤트로 처리하는 구조**로 보여줘야 한다고 정리했다. 

따라서 개발 환경에는 **Mock Naver API**와 **Mock LLM API**가 있어야 한다.

# 5. Codex 사용 방식 (선택 사항)

## Codex는 이렇게 써야 한다

이 프로젝트에서 Codex는 세 가지 모드로 나눠 쓴다.

| 상황           | Codex 사용 방식               |
| ------------ | ------------------------- |
| 설계 검토        | Chat / Plan 모드            |
| 작은 코드 수정     | Agent 모드                  |
| 테스트 실행 포함 구현 | Agent 모드 + 승인 기반 터미널 실행   |
| 대규모 리팩토링     | Plan 먼저 작성 후 단계별 Agent 실행 |
| 긴 작업         | Codex Cloud 위임 가능         |
| 위험한 명령       | 직접 승인 후 실행                |

OpenAI 문서는 Codex가 코드를 읽고, 수정하고, 실행할 수 있는 coding agent이며, VS Code 확장에서 IDE 옆에서 함께 쓰거나 Codex Cloud에 작업을 위임할 수 있다고 설명한다. ([OpenAI 개발자][5])

## 승인 정책

처음부터 Full Access로 두면 안 된다.

추천은 다음이다.

```text
기본:
approval_policy = "on-request"
sandbox_mode = "workspace-write"

위험 작업:
직접 승인 후 실행

절대 금지:
rm -rf
실제 운영 DB 접속
실제 네이버 API 대량 호출
.env 파일 출력
비밀키 커밋
```

Codex 설정은 전역 `~/.codex/config.toml`과 프로젝트별 `.codex/config.toml`에 둘 수 있고, CLI와 IDE extension이 동일한 configuration layer를 공유한다. 공식 문서도 이 설정에서 모델, 승인 정책, sandbox 설정, MCP 서버를 구성할 수 있다고 설명한다. ([OpenAI 개발자][6])

# 7. `AGENTS.md` 세팅

이 파일이 가장 중요하다. Codex가 매번 읽는 프로젝트 운영 매뉴얼이기 때문이다.

`AGENTS.md`

```md
# AGENTS.md

## Project

이 저장소는 PlacePick AI 프로젝트다.
Spring Boot 기반 네이버 검색 API 연계 실시간 모임 장소 의사결정 플랫폼을 구현한다.

핵심 목표:
- 사용자의 자연어 모임 조건을 LLM API로 구조화한다.
- 네이버 지역 검색과 블로그 검색 결과에 존재하는 장소만 추천한다.
- 추천 요청은 동기 처리하지 않고 Job으로 등록한다.
- Redis Streams 기반 Worker가 비동기로 추천 작업을 처리한다.
- 추천 진행 상태는 SSE로 제공한다.
- 공유방 투표, 클릭, 피드백 이벤트를 수집한다.
- 외부 API 호출량은 Redis Rate Limiter와 Cache로 제어한다.

## Tech Stack

- Java 17
- Spring Boot
- Spring Web MVC
- Spring Data JPA
- PostgreSQL
- Redis
- Redis Streams
- Spring Cache
- SseEmitter
- Gradle
- Docker Compose
- JUnit 5
- Testcontainers
- WireMock or MockWebServer
- k6
- Prometheus
- Grafana

## Architecture Rules

- Controller는 얇게 유지한다.
- 비즈니스 로직은 application service에 둔다.
- Entity에 외부 API DTO를 직접 노출하지 않는다.
- 외부 API 호출은 naver/client, llm/client 패키지에 둔다.
- 추천 생성은 Controller에서 직접 처리하지 않는다.
- 추천 요청은 반드시 RecommendationJob으로 저장한 뒤 Redis Streams 이벤트로 발행한다.
- Worker는 이벤트를 소비해서 조건 추출, 검색, 점수화, 결과 저장을 수행한다.
- 외부 API 호출은 DB 트랜잭션 내부에서 하지 않는다.
- 실제 네이버 API를 사용하는 테스트를 작성하지 않는다.
- 통합 테스트는 Mock Naver API와 Mock LLM API를 사용한다.
- 실제 API 키나 .env 파일 내용을 출력하거나 커밋하지 않는다.

## Package Rules

- recommendation: 추천 Job, 점수화, 결과 관리
- place: 후보 장소, 블로그 문맥, 중복 제거
- naver: 네이버 지역/블로그 검색 API client
- llm: 조건 추출, 문맥 요약, 추천 이유 생성 client
- decisionroom: 공유방, 투표, 최종 합의
- event: Redis Streams producer/consumer, event log
- ratelimit: Redis 기반 호출량 제한
- monitoring: custom metrics
- common: 공통 응답, 예외, 설정

## Done Definition

작업 완료 전 반드시 확인한다.

1. 관련 단위 테스트가 통과해야 한다.
2. 변경 범위에 따라 통합 테스트가 통과해야 한다.
3. 외부 API 호출이 필요한 테스트는 Mock API를 사용해야 한다.
4. 새 API를 추가하면 docs/api-contract.md를 업데이트한다.
5. 새 이벤트를 추가하면 docs/event-contract.md를 업데이트한다.
6. 새 프롬프트나 LLM 출력 형식을 바꾸면 docs/prompt-contract.md를 업데이트한다.
7. 실패 가능성이 있는 외부 호출은 timeout, retry, fallback 중 최소 하나를 고려한다.
8. 추천 문장은 단정 표현을 피해야 한다.

## Recommended Commands

- 전체 검증: ./gradlew check
- 단위 테스트: ./gradlew test
- 통합 테스트: ./gradlew integrationTest
- 로컬 인프라 실행: docker compose up -d
- 로컬 인프라 종료: docker compose down
- 전체 검증: ./scripts/check.sh
- 부하 테스트: ./scripts/test-load.sh

## Forbidden

- 실제 네이버 API로 부하 테스트 금지
- API key, secret, token 출력 금지
- .env 커밋 금지
- DB 트랜잭션 안에서 외부 API 호출 금지
- Controller에 복잡한 비즈니스 로직 작성 금지
- 추천 결과에 존재하지 않는 장소 생성 금지
- “무조건”, “확실히”, “예약 가능”, “웨이팅 없음” 같은 단정 표현 금지
```

Codex 공식 Best Practices에서도 `AGENTS.md`에는 repo layout, 실행 방법, build/test/lint 명령, engineering convention, PR expectation, do-not rules, 완료 조건을 담는 것이 좋다고 안내한다. ([OpenAI 개발자][7])

# 8. `PLANS.md` 세팅 (선택 사항)

복잡한 작업은 바로 구현하지 않고 계획 문서부터 만들게 해야 한다.

`PLANS.md`

```md
# PLANS.md

Codex는 다음에 해당하는 작업을 시작하기 전에 먼저 계획을 작성해야 한다.

- 새로운 도메인 추가
- DB 스키마 변경
- Redis Streams 구조 변경
- Rate Limiter 변경
- 외부 API Client 변경
- SSE / WebSocket 구조 변경
- 모니터링 지표 추가
- 테스트 구조 변경
- 대규모 리팩토링

## Plan Template

### Goal

무엇을 달성하는가?

### Current State

현재 관련 코드와 문서는 어디에 있는가?

### Proposed Change

어떤 파일을 어떻게 바꿀 것인가?

### API Impact

변경되는 API가 있는가?

### DB Impact

변경되는 테이블, 컬럼, 인덱스가 있는가?

### Event Impact

추가되거나 변경되는 이벤트가 있는가?

### Failure Handling

실패, 재시도, fallback, DLQ 처리는 어떻게 할 것인가?

### Validation

어떤 테스트와 명령으로 검증할 것인가?

### Rollback

문제가 생기면 어떻게 되돌릴 것인가?
```

Codex Best Practices도 복잡하거나 애매한 작업은 먼저 계획을 세우는 것이 좋고, Plan mode 또는 `PLANS.md` 템플릿을 사용할 수 있다고 설명한다. ([OpenAI 개발자][7])

# 16. Codex Hooks 세팅

Codex Hooks는 조심해서 써야 한다. 공식 문서에 따르면 Codex는 `hooks.json` 또는 `config.toml`의 inline hook table에서 hook을 찾고, project-local hook은 trusted project에서만 로드된다. 또한 non-managed command hook은 실행 전 review와 trust가 필요하다. ([OpenAI 개발자][12])

처음에는 강제 자동 실행보다 “알림용 hook” 또는 “가벼운 검증 hook”부터 쓰는 것이 안전하다.

`.codex/hooks.json`

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "node \"$(git rev-parse --show-toplevel)/tools/docs/codex-stop-reminder.mjs\"",
            "timeout": 10,
            "statusMessage": "Checking final-work reminder"
          }
        ]
      }
    ]
  }
}
```

Stop hook의 표준 출력은 반드시 유효한 JSON이어야 한다. 이 저장소의 hook은 테스트를 자동 실행하지 않고 변경이 있을 때 `make check`와 문서 갱신만 상기시킨다. 테스트가 오래 걸리면 Codex 루프가 느려지므로 전체 테스트 실행은 명시적인 작업 단계와 CI에 둔다.

# 21. k6 부하 테스트

k6는 개발자와 QA 엔지니어를 위한 load testing과 performance testing 도구이며, 공식 문서에서 load testing, stress test, spike test, soak test 등을 다룬다. ([Grafana Labs][14])

`k6/recommendation-load-test.js`

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 50 },
    { duration: '1m', target: 100 },
    { duration: '30s', target: 0 }
  ],
  thresholds: {
    http_req_duration: ['p(95)<300'],
    http_req_failed: ['rate<0.01']
  }
};

export default function () {
  const payload = JSON.stringify({
    query: '강남역에서 친구 4명이 갈 조용한 음식점 추천해줘. 1인 2만 원대였으면 좋겠어.',
    sessionId: `session-${__VU}`
  });

  const res = http.post('http://localhost:8080/api/v1/recommendations', payload, {
    headers: { 'Content-Type': 'application/json' }
  });

  check(res, {
    'status is 200 or 202': r => r.status === 200 || r.status === 202,
    'has jobId': r => r.body.includes('jobId')
  });

  sleep(1);
}
```

# 27. 최종 세팅 방향 요약

네가 원하는 “하네스, 루프 엔지니어링과 같이 최적의 고도화된 AI 네이티브 agentic AI 개발 환경”은 이렇게 정의하면 정확하다.

> **Codex가 코드를 생성하는 데서 끝나는 것이 아니라, AGENTS.md와 Issue/Work Record/ADR로 프로젝트 규칙과 의사 결정을 읽고, Docker Compose/Dev Container로 동일한 실행 환경을 사용하며, JUnit/Testcontainers/k6/evals/Prometheus를 통해 결과를 검증하고, 실패 로그를 바탕으로 다시 수정하는 반복형 개발 환경**

최종 추천 조합은 이것이다.

```text
IDE:
VS Code + Codex extension

Language/Backend:
Java 17 + Spring Boot

Runtime Harness:
Dev Container + Docker Compose

Infra:
PostgreSQL + Redis + Mock Naver API + Mock LLM API

Agent Instruction:
AGENTS.md + Issue/Work Record/ADR + docs/

Codex Hook:
.codex/hooks.json + 사용자 검토·신뢰

Test Harness:
JUnit 5 + Testcontainers + WireMock + Eval JSONL

Loop Harness:
scripts/check.sh + k6 + Prometheus/Grafana + CI

Development Loop:
Plan → Implement → Test → Eval → Observe → Repair → Document
```

이렇게 세팅하면 Codex를 단순 자동완성 도구가 아니라 **Spring 백엔드 프로젝트를 함께 구현하고 검증하는 agentic 개발 파트너**로 쓸 수 있다.
