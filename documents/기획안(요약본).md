# 네이버 api 활용 LLM 서비스-플레이스픽 AI 기획안 (요약본)

## 서비스 개요

**플레이스픽 AI**는 사용자가 모임 장소 조건을 자연어로 입력하면, AI가 조건을 해석하고 네이버 지역 검색·블로그 검색 결과를 바탕으로 **장소 후보 3개와 추천 이유, 단체방 공유 문장**을 제공하는 서비스다.

직접 AI 모델을 학습하지 않고, 이미 사용 가능한 **LLM API**와 **네이버 검색 API**를 활용한다. GPU 학습은 필요 없다. MVP에서는 비용과 구현 범위를 줄이기 위해 지도 화면, 길찾기, 예약, 로그인, 개인화 기능은 제외한다.

---

# 1. 문제 발견

## 어떤 불편·니즈가 있는지 캐치

사람들이 모임 장소를 정할 때 가장 불편해하는 지점은 **장소를 검색하는 것 자체가 아니라, 많은 후보 중에서 최종 장소를 고르는 과정**이다.

예를 들어 친구들과 강남역에서 만나기로 했을 때 사용자는 네이버에 다음과 같이 여러 번 검색한다.

```text
강남역 맛집
강남역 조용한 음식점
강남역 4명 모임 장소
강남역 대화하기 좋은 술집
강남역 2만원대 맛집
```

검색 결과는 많이 나오지만, 사용자는 다시 블로그 글과 장소 정보를 하나씩 확인해야 한다.

사용자가 직접 확인해야 하는 정보는 다음과 같다.

| 확인해야 하는 것 | 사용자가 느끼는 불편                 |
| --------- | --------------------------- |
| 위치        | 역에서 얼마나 가까운지 직접 봐야 함        |
| 분위기       | 조용한지, 시끄러운지 블로그 후기를 읽어야 함   |
| 예산        | 가격대가 맞는지 여러 글을 비교해야 함       |
| 인원        | 4명, 5명, 단체가 가능한지 확인해야 함     |
| 웨이팅       | 금요일 저녁이나 주말에 사람이 많은지 판단해야 함 |
| 공유        | 후보를 단체방에 설명하기 위해 다시 정리해야 함  |

즉, 사용자는 정보가 부족해서 힘든 것이 아니라 **정보가 너무 많고 흩어져 있어서 힘들다.**

## 발견한 핵심 니즈

사용자는 단순히 “장소를 많이 추천받고 싶다”가 아니라, 다음과 같은 니즈를 가지고 있다.

> “우리 상황에 맞는 장소를 빠르게 3개 정도로 줄이고, 왜 괜찮은지 설명까지 받고 싶다.”

특히 모임 장소는 혼자 결정하는 문제가 아니다. 친구, 연인, 동료, 팀원 등 여러 사람이 함께 결정해야 하므로, 사용자는 **단체방에 바로 공유할 수 있는 근거 있는 추천**을 원한다.

# 2. 문제 정의

## 누가 / 어떤 상황에서 / 무슨 불편을 겪는가

## 문제 정의 한 문장

**모임 장소를 정해야 하는 20~30대 사용자는 친구·연인·동료와 만날 장소를 고르는 상황에서 위치, 예산, 인원, 분위기, 후기 정보를 네이버 검색과 블로그에서 일일이 비교해야 해서 최종 장소를 결정하는 데 시간과 피로를 느낀다.**

## 문제를 구성하는 요소

| 구분      | 내용                           |
| ------- | ---------------------------- |
| 누가      | 모임 장소를 정해야 하는 20~30대 사용자     |
| 어떤 상황에서 | 친구 모임, 데이트, 회식, 스터디 장소를 정할 때 |
| 무슨 불편을  | 검색 결과와 블로그 후기를 직접 비교해야 하는 불편 |
| 왜 문제인가  | 후보는 많지만 최종 결정을 내리기 어렵기 때문    |
| 해결 방향   | AI가 조건을 해석하고 후보를 3개로 압축 추천   |

## 서비스가 해결할 핵심 문제

플레이스픽 AI가 해결하려는 문제는 “맛집 정보 부족”이 아니다.

정확한 문제는 다음이다.

> 사용자는 이미 네이버에서 장소 정보를 찾을 수 있지만, 그 정보를 자신의 상황에 맞게 비교하고 결정하는 데 피로를 느낀다.

따라서 이 서비스의 본질은 **장소 검색 서비스**가 아니라 **장소 의사결정 보조 서비스**다.

# 3. 사용자·시나리오

## 사용자가 서비스를 어떻게 쓰는지 흐름

## 대표 사용자

| 항목     | 내용                              |
| ------ | ------------------------------- |
| 이름     | 지민                              |
| 나이     | 27세                             |
| 상황     | 금요일 저녁에 친구 4명과 강남역에서 만나기로 함     |
| 원하는 장소 | 너무 시끄럽지 않고 대화하기 좋은 음식점          |
| 조건     | 강남역 근처, 4명, 1인 2만 원대, 조용한 분위기   |
| 불편     | 네이버 검색 결과와 블로그 글을 여러 개 비교하기 귀찮음 |
| 기대     | 후보 3개와 추천 이유를 빠르게 받고 싶음         |

---

## 사용자 시나리오

### Step 1. 사용자가 자연어로 조건을 입력한다

사용자는 복잡한 필터를 선택하지 않고, 평소 말하듯 입력한다.

```text
금요일 저녁 7시에 강남역에서 친구 4명이 만나요.
너무 시끄럽지 않고 1인 2만 원대였으면 좋겠어요.
대화하기 좋은 음식점 추천해줘.
```

---

### Step 2. AI가 사용자의 조건을 추출한다

LLM API가 사용자의 문장을 분석해 장소 추천에 필요한 조건을 구조화한다.

```json
{
  "location": "강남역",
  "date_time": "금요일 저녁 7시",
  "people_count": 4,
  "place_type": "음식점",
  "purpose": "친구 모임",
  "budget": "1인 2만 원대",
  "preferences": ["조용함", "대화하기 좋음"],
  "avoid": ["너무 시끄러운 곳"]
}
```

이 과정에서 AI는 사용자의 말을 검색 가능한 조건으로 바꾼다.

---

### Step 3. 서비스가 네이버 검색용 쿼리를 만든다

AI는 사용자의 조건을 바탕으로 여러 검색 쿼리를 만든다.

| 생성 쿼리           | 목적        |
| --------------- | --------- |
| 강남역 음식점         | 기본 후보 확보  |
| 강남역 조용한 음식점     | 분위기 조건 반영 |
| 강남역 대화하기 좋은 음식점 | 모임 목적 반영  |
| 강남역 4인 모임 음식점   | 인원 조건 반영  |
| 강남역 2만원대 맛집     | 예산 조건 반영  |

이렇게 검색어를 나누는 이유는, 사용자의 조건이 하나가 아니라 여러 개이기 때문이다.

---

### Step 4. 네이버 지역 검색으로 장소 후보를 가져온다

서비스는 네이버 지역 검색을 활용해 실제 장소 후보를 수집한다.

가져오는 정보는 다음과 같다.

| 정보     | 사용 목적                     |
| ------ | ------------------------- |
| 장소명    | 추천 후보 표시                  |
| 카테고리   | 음식점, 카페, 술집 등 분류          |
| 주소     | 지역 적합성 판단                 |
| 도로명 주소 | 사용자에게 표시                  |
| 네이버 링크 | 사용자가 상세 정보 확인             |
| 좌표값    | MVP에서는 지도 표시 없이 참고값으로만 활용 |

MVP에서는 지도 화면을 직접 보여주지 않고, 사용자가 더 자세히 보고 싶을 때 **네이버 장소 링크**로 이동하게 한다.

---

### Step 5. 네이버 블로그 검색으로 분위기 문맥을 확인한다

장소 후보마다 블로그 검색 결과를 확인해 분위기 관련 표현을 추출한다.

예를 들어 블로그 제목이나 요약에 다음 표현이 반복되는지 확인한다.

| 확인할 표현  | 의미                     |
| ------- | ---------------------- |
| 조용한 분위기 | 대화하기 좋은 장소일 가능성        |
| 소개팅 장소  | 너무 시끄럽지 않고 분위기가 좋을 가능성 |
| 웨이팅     | 대기 시간이 있을 가능성          |
| 시끌벅적    | 조용함 조건과 맞지 않을 가능성      |
| 단체석     | 여러 명이 방문하기 좋을 가능성      |
| 가성비     | 예산 조건과 맞을 가능성          |

AI는 이 문맥을 요약해 장소별 장단점을 정리한다.

---

### Step 6. 조건별 점수로 후보를 정렬한다

서비스는 AI 감각만으로 추천하지 않는다.
사용자 조건에 따라 점수를 계산한다.

예시 점수 기준은 다음과 같다.

| 평가 기준   |   배점 |
| ------- | ---: |
| 지역 적합성  |  25점 |
| 분위기 적합성 |  25점 |
| 목적 적합성  |  20점 |
| 예산 적합성  |  15점 |
| 인원 적합성  |  10점 |
| 근거 신뢰도  |   5점 |
| 총점      | 100점 |

사용자가 “조용한 곳이 제일 중요해”라고 말하면 분위기 적합성 점수를 더 높게 반영한다.

---

### Step 7. 사용자는 최종 후보 3개를 받는다

서비스는 너무 많은 후보를 보여주지 않고, 최종 3개만 추천한다.

예시 결과:

```text
1위. A식당
추천 이유:
강남역 근처 후보 중 조용함, 대화하기 좋음과 관련된 블로그 문맥이 반복됩니다.
친구 4명이 대화 중심으로 만나기에 가장 무난한 후보입니다.

주의점:
금요일 저녁에는 혼잡할 수 있어 방문 전 확인이 필요합니다.
```

---

### Step 8. 단체방 공유 문장을 생성한다

사용자는 추천 결과를 직접 다시 정리하지 않아도 된다.
서비스가 단체방에 보낼 문장을 생성한다.

```text
강남역 후보 3개 뽑아봤어.
1순위는 A식당인데 조용하고 대화하기 좋아 보여서 제일 무난해.
2순위는 B식당이고 가성비가 좋아.
3순위는 C식당인데 분위기는 좋은데 웨이팅이 있을 수 있대.
나는 A식당이 제일 괜찮아 보여!
```

# 4. 핵심 기능 도출

## 시나리오를 굴리는 데 꼭 필요한 기능

## 핵심 기능 1. 자연어 조건 입력

사용자가 장소 조건을 문장으로 입력하는 기능이다.

예시:

```text
성수역에서 친구 3명이 갈 만한 조용한 카페 추천해줘.
오래 앉아있을 수 있으면 좋겠어.
```

이 기능이 필요한 이유는 사용자가 복잡한 필터를 하나씩 선택하지 않고도 바로 서비스를 사용할 수 있게 하기 위해서다.

---

## 핵심 기능 2. 조건 추출 AI

LLM API가 사용자의 문장에서 추천에 필요한 조건을 뽑는다.

추출해야 하는 항목은 다음으로 제한한다.

| 항목     | 예시                  |
| ------ | ------------------- |
| 지역     | 강남역, 성수역, 홍대입구      |
| 인원     | 2명, 4명, 6명          |
| 장소 유형  | 카페, 음식점, 술집         |
| 목적     | 친구 모임, 데이트, 회식, 스터디 |
| 예산     | 1인 1만 원대, 2만 원대     |
| 선호 분위기 | 조용함, 감성적, 활기참       |
| 제외 조건  | 웨이팅 심함, 너무 시끄러움     |

이 기능이 없으면 사용자의 문장을 네이버 검색에 적합한 조건으로 바꿀 수 없다.

---

## 핵심 기능 3. 네이버 지역 검색 기반 후보 수집

추출된 조건을 바탕으로 네이버 지역 검색을 호출해 실제 장소 후보를 가져온다.

이 기능은 서비스의 네이버 관련성을 만드는 핵심 기능이다.
AI가 장소를 상상해서 추천하는 것이 아니라, 네이버 검색 결과에 있는 장소만 후보로 사용한다.

---

## 핵심 기능 4. 네이버 블로그 검색 기반 분위기 요약

장소 후보별로 블로그 검색 결과를 확인해 분위기와 주의점을 요약한다.

이 기능이 중요한 이유는, 사용자가 장소를 고를 때 가장 어려워하는 부분이 단순 위치가 아니라 **분위기 판단**이기 때문이다.

예를 들어 “조용한지”, “대화하기 좋은지”, “웨이팅이 있는지”, “단체가 가능한지” 같은 정보는 장소명만 보고 알기 어렵다.

---

## 핵심 기능 5. 조건 기반 점수화

후보 장소를 사용자 조건에 맞게 점수화한다.

점수화 기준은 다음과 같다.

```text
최종 점수 =
지역 적합성
+ 분위기 적합성
+ 목적 적합성
+ 예산 적합성
+ 인원 적합성
- 리스크 요소
```

이 기능이 필요한 이유는 AI 추천이 막연해지지 않도록 하기 위해서다.
사용자는 “왜 이 장소가 1위인지” 납득할 수 있어야 한다.

---

## 핵심 기능 6. 후보 3개 추천 및 이유 생성

점수가 높은 장소 3개를 골라 추천 이유와 주의점을 생성한다.

결과는 다음 형식으로 제공한다.

| 항목     | 내용                      |
| ------ | ----------------------- |
| 순위     | 1위, 2위, 3위              |
| 장소명    | 추천 장소 이름                |
| 추천 이유  | 사용자 조건과 맞는 점            |
| 주의점    | 웨이팅, 혼잡, 가격대 등 확인 필요 사항 |
| 네이버 링크 | 상세 확인용 링크               |

---

## 핵심 기능 7. 공유용 문장 생성

추천 결과를 단체방에 바로 보낼 수 있도록 짧은 요약 문장을 생성한다.

이 기능은 장소 결정이 개인 행동이 아니라 **단체 합의 과정**이라는 점에서 중요하다.

---

# 5. 우선순위·MVP

## 핵심 2~3개로 좁히기

MVP의 목표는 모든 기능을 구현하는 것이 아니다.

MVP의 목표는 다음 하나다.

> 사용자가 모임 조건을 한 문장으로 입력하면, 네이버 검색 결과 기반으로 장소 후보 3개와 추천 이유를 받을 수 있게 한다.

따라서 MVP에서는 핵심 기능을 3개로 좁힌다.

---

## MVP 1순위. 조건 추출 AI

### 기능 설명

사용자의 자연어 입력을 구조화된 조건으로 변환한다.

입력 예시:

```text
토요일 오후에 성수역에서 친구 3명이 갈 카페 추천해줘.
오래 앉아있을 수 있고 너무 시끄럽지 않았으면 좋겠어.
```

출력 예시:

```json
{
  "location": "성수역",
  "people_count": 3,
  "place_type": "카페",
  "purpose": "친구 모임",
  "preferences": ["오래 앉기 좋음", "조용함"],
  "avoid": ["시끄러운 곳"]
}
```

### 1순위인 이유

사용자 조건을 제대로 이해하지 못하면 검색 쿼리 생성, 후보 수집, 점수화, 추천 이유 생성이 모두 부정확해진다.
따라서 가장 먼저 구현해야 하는 기능이다.

---

## MVP 2순위. 네이버 지역·블로그 검색 기반 후보 수집

### 기능 설명

조건 추출 결과를 바탕으로 네이버 지역 검색에서 장소 후보를 가져오고, 네이버 블로그 검색으로 분위기 문맥을 확인한다.

예시:

| 사용자 조건   | 검색에 반영되는 내용 |
| -------- | ----------- |
| 성수역      | 지역 검색 기준    |
| 카페       | 장소 유형 필터    |
| 조용함      | 블로그 문맥 확인   |
| 오래 앉기 좋음 | 블로그 문맥 확인   |
| 친구 3명    | 인원 적합성 판단   |

### 2순위인 이유

이 기능이 있어야 플레이스픽 AI가 단순 챗봇이 아니라 **네이버 검색 결과 기반 서비스**가 된다.
AI가 임의로 장소를 만들어내지 않고 실제 검색 결과에 있는 후보만 추천하게 만드는 핵심 장치다.

---

## MVP 3순위. 후보 3개 추천 및 공유 문장 생성

### 기능 설명

수집한 후보를 조건별로 점수화하고, 최종 3개를 추천한다.
각 장소마다 추천 이유와 주의점을 함께 제공한다.

결과 예시:

| 순위 | 장소  | 추천 이유                     | 주의점          |
| -: | --- | ------------------------- | ------------ |
|  1 | A카페 | 조용함, 오래 앉기 좋음 조건과 가장 잘 맞음 | 주말 오후 혼잡 가능  |
|  2 | B카페 | 분위기가 좋고 역에서 가까움           | 가격대가 높을 수 있음 |
|  3 | C카페 | 가성비가 좋고 접근성이 좋음           | 조용함 조건은 약함   |

공유 문장 예시:

```text
성수역 카페 후보 3개 골라봤어.
1순위는 A카페인데 조용하고 오래 앉기 좋아 보여.
2순위는 B카페고 분위기가 좋지만 가격대가 조금 있을 수 있어.
3순위는 C카페인데 가성비가 좋아.
나는 A카페가 제일 무난해 보여!
```

### 3순위인 이유

사용자가 원하는 최종 결과는 단순한 장소 목록이 아니라 **결정 가능한 추천**이다.
후보 3개와 추천 이유, 공유 문장까지 제공해야 실제 모임 장소 결정 과정에서 사용할 수 있다.

# MVP에서 제외할 기능

| 제외 기능        | 제외 이유                      |
| ------------ | -------------------------- |
| 지도 화면 표시     | 무료 MVP에서는 비용과 구현 부담이 생김    |
| 길찾기·이동 시간 계산 | Maps API 사용이 필요하므로 초기 제외   |
| 예약 연동        | 외부 제휴와 추가 개발 필요            |
| 로그인          | 초기 검증에는 불필요                |
| 개인화 추천       | 사용자 데이터가 충분히 쌓인 뒤 가능       |
| 네이버 리뷰 크롤링   | 권한·약관 이슈가 생길 수 있음          |
| 자체 AI 모델 학습  | GPU 학습이 필요하므로 기획 조건과 맞지 않음 |

# 최종 정리

**플레이스픽 AI는 모임 장소를 정해야 하는 사용자가 네이버 검색 결과와 블로그 후기를 직접 비교하는 불편을 줄이기 위해, LLM API로 조건을 해석하고 네이버 지역·블로그 검색 결과를 기반으로 장소 후보 3개와 추천 이유를 제공하는 AI 장소 의사결정 서비스다.**

MVP에서는 다음 3가지만 구현한다.

```text
1. 사용자의 자연어 조건을 AI가 추출한다.
2. 네이버 지역 검색과 블로그 검색으로 장소 후보와 분위기 문맥을 수집한다.
3. 조건에 맞는 후보 3개와 추천 이유, 공유 문장을 제공한다.
```
