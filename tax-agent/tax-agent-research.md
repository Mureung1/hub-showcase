# tax-agent 방향 재검토 리서치 (2026-07-08)

## 이 문서의 배경

`7-7/PLAN.md`에서 "매출/매입 불일치 탐지"(1순위)를 이미 상세 설계까지 마쳤지만, 다시 검토해보니 이 방향이 아쉽게 느껴짐:

1. **너무 수동적/읽기 전용** — 완전자동화이긴 해도 "조회 후 알림"에 그쳐 에이전트라기보다 리포팅 툴에 가까움
2. **차별성 부족** — 캐시노트/자비스/삼쩜삼 등 기존 서비스와 비슷해 보임
3. **국세청 단속 리스크** — 최근 뉴스에서 국세청이 스크래핑 플랫폼을 단속 중이라는 걸 확인

대안으로 "세금계산서 발행 agent"를 재고 중이나 인증수단 자동화 가능성이 불확실해서, 아래 세 가지를 리서치했다: (1) 인증수단별 자동화 가능성, (2) 국세청 규제 동향, (3) 기존 서비스 지형과 빈틈. 마지막에 이를 근거로 한 새 방향 후보를 정리했다.

## 1. 인증수단별 agent 자동화 가능성

### 1-1. 비교표

| 인증수단 | 최초 등록/연결 | 이후 재로그인 | Playwright 자동화 난이도 | 확정도 |
|---|---|---|---|---|
| **공동인증서**(구 공인인증서) | 은행/인증기관에서 발급, 파일(PC/USB)로 보관·내보내기 가능 | 인증서 파일 경로 + 비밀번호만 있으면 로그인 — 모바일 탭/앱푸시 불필요 | 낮음 — 파일 경로+비밀번호를 폼에 입력하는 수준 | **비교적 확정적** — `7-7/PLAN.md`가 이미 이 결론으로 설계됨 |
| **금융인증서** | 은행 앱에서 본인인증 후 금융결제원 클라우드에 등록(최초 1회, 사람 필요) | PC/모바일에서 "자동연결" 설정 시 이후엔 **간편비밀번호만으로 로그인** 가능(문서상 확인) | **미확정** — 인증서 실체가 로컬 파일이 아니라 금융결제원 클라우드 세션이라, Playwright가 이 "자동연결" 상태를 프로그래밍 방식으로 재현/유지할 수 있는지는 실제 스파이크 없이는 모름. 브라우저 쿠키/디바이스 지문 기반일 가능성이 있어 매번 새 환경에서는 재인증이 필요할 수 있음 | **미확정 — 실사용 스파이크 필요** |
| **간편인증**(카카오/PASS 등 민간인증서) | 앱 설치 + 최초 등록 | **매 로그인마다 모바일 앱 푸시 승인 필요**(국세청 공식 매뉴얼 "간편인증(민간인증서) 사용자 매뉴얼" 기준) | 높음 — 사람의 모바일 탭 없이는 원천적으로 불가능 | 확정적 — 완전자동화 불가 |

### 1-2. 시사점

- "금융인증서를 쓰면 더 쉬워질 것"이라는 가설은 **아직 검증 안 됨**. 오히려 공동인증서보다 자동화 난이도가 같거나 높을 가능성이 있음(로컬 파일이 아니라 클라우드 세션이라 Playwright 컨텍스트 이식이 더 까다로울 수 있음). 이걸 확인하려면 실제 금융인증서로 홈택스/손택스 자동연결을 설정해보고, 다른 브라우저 프로필/서버 환경에서 재로그인이 되는지 스파이크가 필요함 — 이는 `7-7/PLAN.md`의 "3일차 스파이크"와 같은 성격의 검증되지 않은 리스크임.
- 반대로 **공동인증서는 이미 기존 계획에서 "완전자동화 가능"으로 검증(리서치 기준)됐고, 실제 스파이크만 남은 상태** — 인증수단 자체는 이미 답이 나와 있었을 가능성이 큼. 즉 "본인인증을 agent가 컨트롤할 수 있는가"라는 불안은 공동인증서 기준으로는 이미 상당 부분 해소돼 있었음.
- **(2026-07-08 추가) 공동인증서는 현재 사용자가 활용 불가**하다고 확인됨 — 이후 스파이크는 금융인증서 중심으로 진행.

### 1-3. 실측 확인 (2026-07-08, Playwright로 홈택스 로그인 화면 탐색 — 자격증명 미입력)

`7-8/hometax-fincert-spike/`에 자격증명 없이 화면 구조만 확인하는 Playwright 스크립트(`explore-login.mjs`)를 작성해 실행했다. 로그인·비밀번호 없이도 다음이 실측으로 확인됨:

1. **"공동인증서"와 "금융인증서"가 로그인 화면에서 하나의 버튼("공동·금융인증서")으로 통합돼 있음.** 클릭하면 "인증서 선택창"(드림시큐리티 위젯)이 뜨고, 그 안에 위치 탭이 `브라우저 / 금융인증서 / 하드디스크·이동식디스크 / 휴대전화 / 스마트인증`으로 나뉨 — 즉 금융인증서는 별도 탭으로 독립돼 있어, 코드 상으로도 공동인증서와는 다른 흐름을 타는 것으로 보임.
2. **"금융인증서" 탭을 누르면 완전히 별도의 "금융인증서비스" 모달이 새로 뜨고, 여기서 "개인" vs "사업자(개인사업자/법인사업자)"를 먼저 선택해야 함.** → **금융인증서는 사업자용 인증서 발급이 실제로 지원됨**이 확인됨. 기존에 리서치했던 "전자(세금)계산서 발급은 사업자등록번호로 발급된 인증서만 가능"이라는 안내 문구와 맞물려, **사업자용 금융인증서를 쓰면 세금계산서 발행에도 쓸 수 있을 가능성이 있음**(단, 실제 발급까지 확인한 건 아님 — 개인용/사업자용 금융인증서를 각각 은행에서 신규 발급받아야 함).
3. **"공동인증서를 클라우드에 저장하기"(화면 우측 안내) 흐름은 명시적으로 "이름 + 휴대폰번호 입력 → SMS 확인코드 전송 → 코드로 로그인"을 요구함.** 이는 최초 1회 연결 단계에서 사람이 필요하다는 기존 가정과 일치. 다만 이 안내는 "공동인증서 클라우드 저장"에 대한 것이고, **"금융인증서" 자체의 로그인 흐름(개인/사업자 선택 이후 화면)은 이번 탐색에서 확인 전 — 실제 인증정보 입력 직전에 멈췄음**(자격증명 없이 진행할 수 없어서 의도적으로 중단).
4. 화면은 매우 동적(WebSquare 프레임워크 + iframe 다수, 로딩 스피너)이라 **정적 셀렉터보다 `getByRole`/`getByText` + 좌표 클릭 혼합 전략이 필요**했음 — 셀렉터가 페이지 로드마다 자동생성 ID(`mf_wfHeader_group1503` 등)를 쓰는 부분도 있어, 실제 자동화 스크립트는 role/text 기반 selector를 우선하고 id는 보조로만 써야 안정적일 것.

**다음 단계(사람이 필요)**: 사용자가 은행 앱에서 금융인증서(가능하면 **사업자용**)를 발급받고, 손택스/홈택스에서 "자동연결"을 최소 1회 실제로 설정한 뒤 — `login-test.mjs`(아직 미작성, 이 스파이크의 2단계)로 "간편비밀번호만으로 새 브라우저 세션에서 재로그인이 되는지"를 실측할 차례.

### 1-4. 실측 확인 (2026-07-08, `login-test.mjs` 2단계 스파이크 — 사용자가 직접 로그인)

`hometax-fincert-spike/login-test.mjs` 작성 후 사용자가 직접 금융인증서로 로그인(자동연결 체크)하고, 그 `storageState`(쿠키/로컬스토리지)를 저장한 뒤 **완전히 새 브라우저 컨텍스트**에서 재사용해봄:

- **결과: 재인증 없이 로그인 상태가 그대로 유지됨.** 즉 최초 1회 사람이 수동으로 금융인증서 등록·자동연결을 설정해두면, 이후에는 Playwright가 `storageState`만 가지고 재인증 없이 세션을 재현할 수 있다는 것을 실측으로 확인.
- **단, 아직 "확정"으로 보기엔 이름:**
  - **다른 환경(서버)에서도 되는가 미검증** — 이번 테스트는 같은 PC/같은 브라우저에서 storageState를 재사용한 것. 실제 배포 환경(다른 머신)에서 이 세션이 그대로 통하는지는 아직 확인 안 됨 — 기기 지문/IP 바인딩이 있다면 서버에서는 막힐 수 있음.
  - **만료 시간 미검증** — 지금 당장은 되지만, 몇 시간/며칠 후에도 재인증 없이 되는지는 아직 모름.
- **만료 시간 관련 공개 정보 검색 결과**: 명확한 "자동연결 세션 유지 기간"을 공식 문서에서 찾지 못함. 확인된 건 서로 다른 두 가지뿐이라 혼동 주의:
  - 금융인증서 자체의 **발급 유효기간은 3년**(은행에서 발급하는 인증서 갱신 주기) — 이건 브라우저 세션 만료와는 다른 개념.
  - 홈택스는 보안상 "일정 시간 미조작 시 자동 로그아웃"하는 일반적인 idle timeout 정책이 있다는 것만 확인되고, 구체적인 분 단위 시간은 검색으로 확인 안 됨.
  - 즉 **"자동연결 등록 자체가 며칠/몇 주까지 유효한지"는 문서화된 답을 못 찾음 — 실측(며칠 뒤 재시도)으로만 확인 가능**.

**결론: 아직 "완전자동화 확정"으로 기록하지 않음.** 같은 환경 즉시 재사용은 되는 것으로 확인됐으나, 다른 환경(서버)에서의 동작 여부와 만료 시간은 미검증 상태로 남겨두고, 추후 스파이크로 이어서 확인해야 함.

### 1-5. 실측 확인 (2026-07-08, `invoice-account-check.mjs` — 발급 메뉴 접근 3단계 스파이크 Step 1)

세금계산서 발행 agent 자동화(로그인 포함) 스파이크를 시작하며, 저장된 `storageState`(개인 계정, 1-4에서 검증)로 홈택스 전체메뉴 → "전자(세금)계산서 발급" → "전자(세금)계산서 건별발급"을 실제로 클릭해봄.

- **결과: "개인은 이용할 수 없다"는 제한 메시지 확인.** 리서치(1-2)에서 예상했던 "전자(세금)계산서 발급은 사업자등록번호로 발급된 인증서만 가능"이 실측으로 확정됨.
- 메뉴 항목 자체(전체메뉴 사이트맵)는 계정 종류와 무관하게 항상 노출되지만, 실제 클릭 시점에 계정 종류를 검사해 개인 계정을 막는 구조.
- **다음 단계(사람이 필요)**: 사업자용 금융인증서로 `login-test.mjs`를 다시 실행해 `storageState`를 사업자 계정으로 덮어써야 함 — 그래야 발급 화면 구조 탐색(Step 2)으로 진행 가능.

### 1-6. 실측 확인 (2026-07-09, `personal-tax-explore.mjs` — 개인 계정으로 자동화 가능한 세금 업무 지도 그리기)

사업자용 금융인증서를 아버지에게 받지 못해 당분간 확보 불가 상태가 됨(전자세금계산서 발급 경로는 계속 막혀 있음). 대신 **개인 금융인증서만으로 무엇을 자동화할 수 있는지**를 넓게 훑는 새 스파이크(`hometax-fincert-spike/personal-tax-explore.mjs`)를 실행했다. `login-test.mjs`(1-4)로 저장해둔 개인 계정 `storageState.json`(2026-07-08 생성)을 재사용 — 새 로그인 없이 다음날에도 세션이 살아있는지부터 확인 대상이었다.

**확인된 것**:
1. **개인 계정 storageState가 하루 뒤에도 재인증 없이 로그인 상태로 재사용됨** — 1-4에서 "만료 시간 미검증"으로 남겨뒀던 질문에 대해, 최소 "당일 재사용"을 넘어 "다음날 재사용"까지는 된다는 것을 실측으로 추가 확인. (며칠~몇 주 단위 만료는 여전히 미검증.)
2. **"전체메뉴" 사이트맵 자체는 로그인 상태와 무관하게 접근 가능**해 보임 — 개인 계정에서 좌측 대분류 탭 9개(계산서·영수증·카드 / 증명･등록･신청･사업장현황 / 세금신고 / 납부·고지·환급 / 지급명세·자료·공익법인 / 장려금·연말정산·기부금 / 상담·불복·제보 / 세무대리·납세관리 / 기타)와 그 하위 링크 70개(현재 열린 첫 탭 기준)를 스크린샷+텍스트로 확보(`reports/personal/all-menu-dump.json`, gitignore 처리됨).
3. **WebSquare 특유의 "가려진 요소" 함정을 실측으로 발견**: 텍스트만으로 요소를 찾으면(`getByText`), 화면에 떠 있는 전체메뉴 모달 "뒤"에 깔린 동일 텍스트(예: 헤더의 즐겨찾기 아이콘 "소득금액증명")가 매칭되어, 클릭 시 그 위 레이어(엉뚱한 `w2popup_window`)에 가로막히는 `TimeoutError`가 발생함. `document.elementFromPoint`로 "그 좌표에서 실제로 맨 위에 있는 요소인지"까지 검증하도록 스크립트를 보강함 — 이 저장소의 기존 교훈("id보다 role/text 우선")에 "보이는 텍스트라도 진짜 클릭 가능한 최상위 요소인지 별도 확인 필요"가 추가됨.
4. **후보 3개 중 "환급금" 링크는 실제로 찾아서 클릭까지 성공**(대분류 탭 "납부·고지·환급" 진입 후). 다만 클릭 직후 "로그인 정보가 없습니다" 알림과 함께 로그인 페이지로 튕겨나감 — **이 시점엔 세션이 이미 끊겨 있었음**. "국세증명 발급"(카테고리는 열렸으나 하위 항목 중 추측한 라벨과 일치하는 게 없었음)과 "현금영수증 조회"(카테고리 탭 자체를 못 찾음 — 아마 같은 세션 단절의 연쇄 효과)는 이번 라운드에서 확인 실패.
5. **세션이 끊긴 원인은 미확정이지만, 유력한 가설이 있음**: 이번 실행 당시 **이전(라벨 수정 전) 실행에서 열어뒀던 브라우저 창이 동일한 `storageState`(=동일 쿠키)로 계속 떠 있는 상태**였다. 서로 다른 두 브라우저 프로세스가 동일 세션 쿠키로 동시에 홈택스에 요청을 보내면, 서버가 한쪽을 로그아웃시키는 종류의 충돌이 있었을 가능성이 있음(확정 아님 — 단순 idle timeout과 우연히 겹쳤을 가능성도 배제 못 함). **실측 규칙으로 반영**: 이 스파이크 계열 스크립트는 항상 이전 브라우저 프로세스를 완전히 종료한 뒤 단일 인스턴스로만 실행할 것.

## 2. 국세청 규제/리스크 동향 (2025~2026)

- **스크래핑 단속 배경**: 삼쩜삼, 토스 등 세무플랫폼이 사용자를 대신해 홈택스에 대량 접속·스크래핑하면서 홈택스 시스템 지연을 유발 → 국세청이 서버 증설/IP 차단 같은 임시조치에서 벗어나 구조적 대응에 착수.
- **오픈API 전환 계획**: 국세청이 "엔티스고도화" 사업(약 5억 원 규모)을 통해 스크래핑을 대체하는 오픈API 체계를 구축 중. 세무플랫폼이 조회 대상 납세자를 사전 등록하고 인증정보 기반으로만 접근하도록 제한하는 방향.
- **이용수수료**: "수익자 부담 원칙"에 따라 국세 데이터 이용수수료를 플랫폼에 부과하는 방안 추진 중.
- **실제 충돌 사례**: 2025년 종합소득세 신고 기간에 삼쩜삼 등 민간 플랫폼이 홈택스 접속 제한을 겪은 사례 보도됨. 국세청과 토스 간 신경전도 있었음(2025-12 뉴스).
- **개인 계정 직접 조회는?** — 기사들은 "세무플랫폼"(대량·다수 사용자 대행) 단속에 초점이 맞춰져 있고, "일반사용자와 세무플랫폼 사용자를 분리"하는 방향이 언급됨. 즉 **본인이 본인 사업자 계정으로 자기 데이터만 조회하는 개인 프로젝트 시나리오는, 대량 스크래핑 플랫폼과는 성격이 다를 가능성이 있음** — 하지만 이건 뉴스에 명시적으로 확인된 사실이 아니라 추론이다. `7-7/PLAN.md`가 이미 이 구분("무단 스크래핑 판례와는 성격이 다름")을 전제로 설계됐는데, 최신 뉴스는 이 전제를 뒤집진 않지만 **국세청이 전반적으로 "스크래핑"이라는 접근 방식 자체에 예민해진 시기**라는 맥락은 추가됐다. 개인정보보호법 시행령 개정안에서도 "대리인의 스크래핑은 원칙적으로 API 연계를 권장하고, 사전협의된 신뢰 기관에 한해 제한적으로만 허용"하는 방향이 나오고 있어, 중장기적으로 스크래핑 기반 설계는 점점 입지가 좁아지는 추세.
- **결론**: 개인 프로젝트/데모 수준에서 당장 법적 문제가 될 가능성은 낮지만, "국세청이 스크래핑을 근본적으로 대체하려는 시점"이라는 걸 감안하면 **스크래핑/RPA를 기술의 핵심 차별점으로 삼기보다는, 공식 채널(오픈API, ASP) 위에서 판단력을 차별화하는 방향이 더 지속가능**해 보임.

## 3. 공식 API vs RPA/스크래핑 채널

| 채널 | 커버 범위 | 성격 |
|---|---|---|
| **국세청 공식 오픈API**(data.go.kr) | 사업자등록정보 진위확인/상태조회(휴폐업, 과세유형)만. 1회 100건, 1일 100만 건 제한 | 완전 합법, 무료, 그러나 매출/매입/세금계산서/현금영수증 데이터는 **다루지 않음** |
| **ASP사 API**(팝빌, 홈택스빌 등) | 전자세금계산서 발행·조회, 홈택스수집(매입/매출/현금영수증 등) — 국세청과 정식 계약된 사업자가 건당 과금으로 제공 | 합법이지만 유료(건당 수수료) — `7-7/PLAN.md`가 이미 "건당 수수료는 사실상 외주 아니냐"며 배제한 경로 |
| **직접 RPA(Playwright + 인증서)** | 홈택스 UI에 나오는 모든 것 | 무료, 자유도 높음, 그러나 위 규제 동향상 리스크가 커지는 방향. UI 변경에도 취약 |

시사점: "무료 + 자유도"를 원하면 RPA뿐이고, "합법성/안정성"을 원하면 ASP 유료 API뿐이다. 공식 무료 오픈API는 세무 데이터 자체를 다루지 않으므로 현재로선 선택지가 아님. 이 트레이드오프 자체가 방향 결정에서 중요한 축이 될 수 있다.

|---|---|---|---|
| 삼쩜삼(자비스앤빌런즈) | 개인 종소세 환급, 1인 사업자 세무 지원 | 개인/1인 사업자 | 국세청 스크래핑 단속의 당사자 |
| 자비스(Jarvis) | 세금계산서 자동 수취, 카드 연동, 경비 자동 분류 | 회계 담당자 없는 초기 스타트업 | 자동수취(읽기) 위주 |
| 캐시노트 | 매출 조회, 카드/배달 정산 통합 | 소상공인(약 160만 곳, 국내 표준급) | 매출 가시성에 강점, 세무 판단·불일치 탐지는 상대적으로 약함 |
| 위하고(WEHAGO) | 클라우드 회계, 다인원 협업 | 5~30인 성장기 스타트업 | 정식 회계 프로그램에 가까움 |
| 팝빌/홈택스빌 | 세금계산서 발행 API, 홈택스수집 API | B2B (ERP 연동사) | 인프라 사업자, 최종 사용자용 UX는 없음 |

**상대적으로 안 채워진 빈틈**:
- **사전(prospective) 의사결정 지원**: 위 서비스들은 대부분 "이미 일어난 거래"를 정리·신고하는 사후(retrospective) 처리. "이 지출을 지금 하면 공제가 되는지", "이번 분기 예상 부가세가 얼마인지" 같은 **의사결정 시점의 시뮬레이션/대화형 조언**은 약함.
- **초소규모 프리랜서/크리에이터**: 캐시노트·위하고는 사업장/직원 단위 소상공인·중소기업에 최적화. 매출이 불규칙하고 세무 지식이 거의 없는 1인 프리랜서·크리에이터를 대화형으로 온보딩하는 경험은 약함(삼쩜삼이 근접하지만 "환급"에 특화).
- **세무사 보조(B2B2C)**: 위 서비스는 전부 "사업자 본인"이 최종 사용자. 세무사 사무실이 다수 고객사의 이상 징후를 한 번에 브리핑받는 도구는 상대적으로 덜 포화된 영역.
- **능동적 후속조치**: 불일치를 "탐지"하는 서비스는 있어도(국세청 AI 자체 포함), 탐지된 항목에 대해 수정신고서 초안을 자동 작성하거나 세무사에게 구조화된 리포트를 자동 발송하는 등 "탐지 다음 단계"까지 자동화하는 서비스는 눈에 띄지 않음.

## 5. 새 방향 후보 (브레인스토밍 시드 — 결론 아님)

아래는 위 갭 분석에서 도출한 후보들이다. 각각 장단점을 간단히 붙였고, 다음 대화에서 사용자와 좁혀나갈 출발점으로만 쓴다.

1. **"탐지 + 능동적 후속조치" 확장판** — 기존 불일치 탐지 인프라(`matcher.ts` 등)를 재사용하되, 발견된 항목에 대해 (a) 수정신고서/경정청구 초안 자동 생성, (b) 세무사에게 자동 발송되는 구조화 리포트, (c) 사용자에게 "이 항목 지금 조치할까요?" 같은 대화형 액션 제안을 추가. 기존 설계를 크게 갈아엎지 않고 "수동적" 단점만 보완 가능. 단, 여전히 캐시노트류와 톤이 겹칠 수 있음.
2. **합법 채널(ASP API) 기반 + 판단 레이어 차별화** — 스크래핑/RPA 대신 팝빌 등 ASP API로 데이터를 받고(리스크 최소화), 차별점은 "판단·설명·제안"에 둠(LLM이 불일치 원인을 설명하고 조치를 제안). 규제 리스크는 낮아지지만 ASP 건당 비용이 발생하고, 데모/개인 프로젝트에서 비용 문제를 어떻게 다룰지 별도 고민 필요.
3. **프리랜서/크리에이터 대상 사전 절세 시뮬레이션 대화형 에이전트** — "이 지출 공제될까?", "올해 예상 세금 얼마?"를 대화로 물어보면 즉시 시뮬레이션. 기존 서비스가 약한 "사전 의사결정" 영역을 정면으로 노림. 다만 세법 판단의 정확성 책임 문제(잘못된 조언의 리스크)가 큼 — 면책/불확실성 표시 설계가 중요해짐.
4. **세무사 사무실 보조 B2B2C** — 사용자를 소상공인 본인이 아니라 세무사로 바꿔서, 여러 고객사의 이상 징후를 요약 브리핑. 경쟁이 상대적으로 적은 영역이지만, 부트캠프 개인 프로젝트로는 "세무사"라는 타겟에 대한 도메인 지식/인터뷰가 부족할 수 있음.
5. **세금계산서 발행 agent (원래 2순위 부활, 단독 1순위로 격상)** — 공동인증서 자동화는 이미 검증됐다는 걸 재확인했으니, "발행"이라는 명확한 쓰기 액션이 있는 이 시나리오를 다시 1순위로 올리는 안. 확인게이트(발행 직전 사람 승인)는 유지. "능동적으로 뭔가 실행하는 에이전트"라는 데모 임팩트가 가장 강함. 단, 되돌릴 수 없는 법적 문서 생성이라는 리스크는 여전함.
