# 1단계 계획 — 장부 기록 자동화 (분개 AI) ★주력

> 작성일: 2026-07-15 · 상위 문서: `../PLAN.md` · 근거: `../notes/보고서-준비물-워크플로우.md`
> **이 프로젝트의 핵심.** 세무사무소에서 사람이 실제로 시간을 쓰는 유일한 반복 노동이 여기 있다.

---

## 1. 이 단계가 핵심인 이유

| 단계 | 지금 사람이 하나? | 왜 |
|---|---|---|
| 0단계 수집 | **아니오** | 수임동의를 걸면 홈택스 자료가 세무프로그램으로 자동 유입. 이미 기계가 함 |
| **1단계 분개 판정** | **예 — 노동 집중** | 통장 한 줄이 매출인지 보증금인지 차입금인지 판정. 1년 수백~수천 줄 |
| 4단계 세무조정 | 아니오 | 세무사랑Pro가 장부를 받아 자동 생성 |

자료를 **가져오는** 일에는 사람이 없다. 가져온 자료를 **판정하는** 일에 사람이 있다. AI가 대체할 수 있는 지점은 정확히 여기다.

```
2025-03-14   입금   3,300,000   (주)ABC
             ↑ 이게 매출인가? 임대보증금인가? 차입금인가? 대표 가지급금 회수인가?
```

---

## 2. 입력 / 출력 / 정답지

**입력**
| 자료 | 출처 | 인증서 필요? |
|---|---|---|
| 법인 통장 거래내역 1년치 (전 계좌) | 은행 사이트 엑셀 다운로드 | ❌ 불필요 ← 이 단계를 지금 시작할 수 있는 이유 |
| 전자세금계산서 매출·매입 내역 | 홈택스 or 세무사무소 요청 | ⚠️ 법인 인증서 or 수임 세무사 경유 |
| 법인카드 사용내역 | 카드사 or 홈택스 | ⚠️ 카드사 직접이면 불필요 |
| 급여대장 | 내부 | ❌ |

**출력**: 전표 — `일자 / 차변계정 / 대변계정 / 금액 / 적요 / 거래처코드 / 증빙유형 / 신뢰도 / 판정근거`

> 증빙유형 태그를 여기서 붙여두는 것이 중요하다. 4단계의 기업업무추진비 적격증빙 판정이 이 태그를 요구하는데, 실제 카드내역에는 이 태그가 없어서 나중에 붙이려면 못 붙인다.

**정답지**: 종이책의 재무상태표·손익계산서 + **계정별 명세서**

```
통장내역 1년치 → AI 자동 분개 → 계정별 잔액 집계
                                    ↓ 대조
                    종이책 재무제표 (세무사가 사람 손으로 분개한 결과)
```

계정별 명세서(보통예금·미지급금·단기차입금·임대보증금)에는 **거래처별 잔액**까지 있어서, 총액보다 훨씬 촘촘한 채점이 가능하다.

**정답지의 한계 — 정직하게 기록**
1. 종이책에는 전표가 없다. 계정별 **총액**만 있고 건별 라벨은 없다 → 이건 **채점표(oracle)이지 학습 데이터셋이 아니다.**
2. 상계 오류를 못 잡는다: A거래를 B계정으로, B거래를 A계정으로 서로 바꿔 틀리면 합계는 맞는다. 확률은 낮지만 0이 아니다.
3. **부분적 역산은 가능하다**: 임대료수입 잔액이 3,600만원인데 통장에 매달 300만원씩 12번 들어왔다면 그 12건의 라벨을 역산할 수 있다. 임대업처럼 거래가 단순하면 상당수 계정이 이런 식으로 풀린다.

---

## 3. 설계 방향

**규칙 엔진 + LLM 하이브리드 + 사람 확인 큐.** "AI가 전부 한다"가 아니라 **"확실한 건 자동, 애매한 건 사람에게"** — 실무에서 실제로 쓰이는 유일한 형태다. 세무는 틀리면 가산세가 나와서 무인 자동화는 아무도 안 쓴다.

```
통장내역 → ① 규칙 매칭 (반복거래)      → 확정 (신뢰도 高)
              ↓ 미매칭
           ② 세금계산서/카드 대사        → 확정 (증빙이 답을 말해줌)
              ↓ 미매칭
           ③ LLM 판정 (Claude API)      → 신뢰도 점수 + 판정근거
              ↓ 신뢰도 낮음
           ④ 사람 확인 큐               → 사람이 고치면 ①의 규칙으로 승격 (학습 루프)
```

- **①이 대부분을 먹는다**: 임대업이면 매달 같은 임차인에게 같은 금액이 들어오고, 관리비·이자·급여·4대보험도 반복이다. 거래 패턴이 단순한 업종이라 유리하다.
- **②가 핵심 대사**: `(주)ABC 3,300,000 입금`은 통장만 보면 판정 불가다. 같은 날짜·금액의 세금계산서가 있으면 매출로 확정된다. **세금계산서 자료 없이는 매출/매입 판정에 구조적 한계가 있다** (아래 R1).
- **③은 처음 보는 거래만**: 전체의 소수여야 정상이다. LLM 호출량이 적어야 비용·속도가 실무 수준이 된다.

## 4. Step

| # | 담당 | 작업 | 산출물 |
|---|---|---|---|
| 1-0 | **[사용자]** | **법인 통장 거래내역 1년치 엑셀 확보** (전 계좌, 작년 사업연도 전체) | 이 단계 전체의 관문 |
| 1-0b | [사용자] | 세금계산서 내역 확보 시도 — 세무사무소에 요청하는 것이 현실적 (인증서 불요) | 없으면 R1 적용 |
| 1-1 | [클로드] | 통장 파서: 은행별 엑셀 포맷 → 정규화 스키마. 거래처명 정규화(공백·법인격 표기 흔들림 흡수) | `src/ingest/` |
| 1-2 | [클로드] | 규칙 엔진: 반복거래 패턴 매칭 (거래처+금액+주기) | `src/rules/` |
| 1-3 | [클로드] | 증빙 대사기: 세금계산서·카드내역과 날짜·금액·거래처 매칭 | `src/reconcile/` |
| 1-4 | [클로드] | LLM 판정기: 미매칭 거래 → 계정과목 후보 + 신뢰도 + 판정근거 (Claude API) | `src/classify/` |
| 1-5 | [클로드] | **채점기**: 분개 결과 계정별 집계 vs 종이책 재무제표·명세서 → 계정별 차이 리포트 | `src/score/` ★ |
| 1-6 | **[공동]** | 오답 분석 루프: 차이 나는 계정 → 원인 거래 추적 → 규칙 보강 → 재실행. 수렴할 때까지 | |
| 1-7 | [클로드] | 사람 확인 큐: 저신뢰 거래 목록 + 한 번 고치면 규칙 승격 | |

**Step 1-5(채점기)가 이 단계의 심장이다.** 이게 없으면 분개 AI는 "그럴듯해 보이는 것"에 그치고, 있으면 "실제 세무사 결과와 X% 일치"라고 말할 수 있다.

---

## 5. 완료 기준

- **1차**: 계정별 잔액이 종이책 재무제표와 대조되어, 차이가 전부 설명됨(추적 완료)
- **2차**: 금액 기준 자동 판정률 목표 — 규칙+대사로 **90%+ 자동 확정**, 나머지는 확인 큐
- **최종 주장 가능한 문장**: "작년 1년치 통장 N건을 자동 분개해 실제 재무제표를 재현했고, X%는 사람 개입 없이 확정됐다"

## 6. 리스크

| # | 리스크 | 대응 |
|---|---|---|
| R1 | **세금계산서 자료가 없으면 매출/매입 판정이 구조적으로 불가** — 통장의 입금 한 줄만으로는 매출인지 보증금인지 알 수 없다 | ① 세무사무소에 매출·매입 내역 요청 ② 안 되면 임대업 특성상 임대료는 반복 패턴으로 역산 가능하므로 그 범위로 한정하고 한계를 명시 |
| R2 | 상계 오류를 채점기가 못 잡음 | 계정별 명세서의 거래처별 잔액까지 대사해 해상도를 높임. 남는 한계는 문서화 |
| R3 | LLM 판정의 비결정성·환각 | LLM은 미매칭 소수 건에만 사용. 반드시 판정근거 출력. 신뢰도 낮으면 사람 큐. 자동 확정 금지 |
| R4 | 통장 거래내역에 거래처 실명 포함 (개인정보) | `data/private/` 로컬 전용 + git 제외. 거래처는 코드로 마스킹 후 처리 |
| R5 | 은행별 엑셀 포맷 제각각 | 파서를 은행별 어댑터로 분리. 보유 계좌의 은행만 우선 지원 |
| R6 | 1년치 통장을 못 구함 | 이 단계 자체가 성립 불가 → 4단계(재료가 종이책에 이미 있음)로 우선순위 이동 |

## 7. 다음 단계와의 연결

- 출력(전표) → **2단계**(결산수정분개·시산표)의 입력
- 여기서 붙인 **증빙유형 태그** → 4단계 기업업무추진비 적격증빙 판정의 필수 입력
- 확립된 **거래처별 계정 매핑 규칙** → 내년 실사용 시 그대로 재사용 (자산이 누적됨)
