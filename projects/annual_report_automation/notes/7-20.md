### 필수 (없으면 실사용 시 사고로 이어짐)

**1. 세액 계산 정확성 — 정답지 재현 검증** *(이미 있음: `cli/reproduce.py`, 5/5 재현)*
이유: 세무조정 엔진의 존재 이유가 "정확한 세액"이다. 로직 버그가 곧 잘못된 납부세액 = 사용자의 금전적 손해·가산세 리스크로 직결된다.
적용: `domain/rates.py`(세율·상각률·한도)가 바뀔 때마다(세법 개정) 재현 검증을 다시 돌려 회귀를 잡아야 한다 — 지금은 수동이니, 최소한 "언제 마지막으로 몇 년도 세율로 검증했는지"를 문서에 박아두길 권한다.

**2. 입력 무결성 게이트가 계산 이전에 항상 강제** *(이미 있음: `validate.py` + `api/main.py`의 `계산_실행`이 `out["v"]["ok"]` 아니면 422로 차단)*
이유: 대차 불일치·자산대장 오류가 있는 데이터로 세액을 뽑으면 숫자 자체가 의미 없다. 지금 구조는 "검증 실패 시 계산 자체를 막는다"라서 올바른 방향.
적용: 프론트엔드가 붙을 때도 이 게이트를 절대 우회하지 않도록(FE에서 "검증 통과했다고 가정하고 스냅샷만 보여주기" 같은 지름길 금지).

**3. Decimal 기반 금액 처리** *(이미 있음: `money.py`, 엔진 전체가 float 안 씀)*
이유: 세액 계산에서 float 반올림 오차는 원 단위 오류로 바로 이어진다. 이미 잘 지켜지고 있으니 새 모듈 추가 시에도 이 규칙을 깨지 않는 게 핵심.

**4. "세무사 업무 대체 아님" 법적 고지**
이유: 세무사법상 유료 세무대리는 세무사 고유 업무다. 이 서비스가 "계산을 대신 신고까지 해주는 도구"처럼 보이면 법적 리스크가 있다. 지금은 "계산 보조 도구"에 가깝지만, 결과 화면·Excel 출력 어디에도 "참고용이며 최종 신고 전 세무사 검토를 권장한다"는 고지가 없다.
적용: FE 결과 화면과 Excel 출력(`export/excel.py`) 양쪽에 고지 문구 삽입.

**5. API 인증/인가 & CORS 제한 — FE 연결 전 필수**
이유: `taxengine/api/main.py`에 지금 인증이 전혀 없고 CORS가 `allow_origins=["*"]`다. 코드 주석에도 "FE origin 정해지면 좁힐 것"이라고 스스로 적어뒀다. 회사 재무정보(매출·자산·손익)가 오가는 API인데, 이 상태로 인터넷에 노출되면 누구나 타사 회사 데이터를 조회/생성할 수 있다.
적용: FE 연결 시점에 최소 (a) CORS를 실제 FE origin으로 제한 (b) 최소한의 인증(세션 쿠키든 API 키든) 도입 — CHECKLIST.md에도 "FE 연결 시점에 다시 볼 것"이라 명시돼 있으니 그 시점을 놓치지 않는 게 핵심.

### 권장 (당장 없어도 돌아가지만, 방치하면 신뢰도·유지보수성이 무너짐)

이유: 지금 API가 `HTTPException(422, str(e))`처럼 내부 예외 문자열을 그대로 클라이언트에 반환하는 곳이 있다. 스택트레이스·DB 경로 등이 새어나가지 않는지 FE 연결 전에 점검.

**5. Rate limiting / 남용 방지**
이유: 인증 도입과 함께, 계산 엔드포인트가 무제한 호출 가능하면 리소스 남용이나 무차별 데이터 탐색에 취약.

## 4. 추가 FEATURE 제안 3가지 (로그인 등 기본 기능 제외)

### 1. 절세 시나리오 비교 UI
**뭘 하는가**: 이미 백엔드에 있는 `engine/scenario.py`/`cli/scenario.py`(감가상각 방법·내용연수 조합별 세액 비교)를 프론트엔드 화면으로 노출. "지금 방식대로 하면 세금 얼마, 정률법으로 바꾸면 얼마" 식으로 시각적 비교표를 보여준다.
**왜 좋은가**: 계산 로직은 이미 완성돼 있고 CLI로만 쓸 수 있는 상태(`cli/scenario.py`)라 — FE 연결만 하면 되는, 투입 대비 효과가 가장 큰 기능. 소상공인 입장에서 "세금이 얼마인지"보다 "어떻게 하면 덜 낼 수 있는지"가 훨씬 와닿는 질문이라 제품 차별화 포인트도 된다. (단, 이미 CLI/테스트에 "모든 조합은 과세이연형(총 세부담은 불변)"이라는 경고가 붙어 있으니 FE에도 그 경고를 그대로 노출해야 함.)

### 2. 계산 결과 쉬운 말 설명 ("왜 이 금액인가요?")
**뭘 하는가**: `export/excel.py`가 이미 각 항목에 근거 조문·산식 각주를 달고 있는데, 이걸 소상공인이 읽어도 이해되는 자연어 설명으로 바꿔 결과 화면에 노출("기업업무추진비 한도가 000원인 이유는 귀사 매출이 OOO구간이라서입니다" 같은 식).
**왜 좋은가**: CHECKLIST/메모리 기록대로 타깃이 "세무 지식·엑셀 능숙도 낮은 소상공인"인데, 지금 있는 근거자료(조문 각주)는 세무 지식이 있어야 읽히는 형태다. 이미 있는 데이터를 재가공하는 것뿐이라 새 계산 로직이 필요 없고, "그냥 숫자만 뱉는 계산기"에서 "이해시켜주는 서비스"로 포지셔닝을 바꾸는 효과가 크다.

### 3. 다년도 추이 대시보드 (전년 대비 이상치 하이라이트)
**뭘 하는가**: 이미 쌓이고 있는 `계산스냅샷` 이력(`db/snapshot.py`)을 활용해, 회계연도가 누적될수록 "작년 대비 이 계정과목이 유난히 늘었다/줄었다", "실효세율이 전년보다 몇 %p 변했다" 같은 걸 자동으로 표시.
**왜 좋은가**: 스냅샷 테이블이 이미 사업연도마다 계산 결과를 저장하도록 설계돼 있어서 별도 데이터 수집 없이 시계열 비교가 바로 가능하다. 다만 이건 hometax 트랙에서 "단순 불일치 탐지는 기존 서비스 대비 차별성이 약하다"고 판단해 방향을 튼 전례가 있으니 — 여기서는 "탐지"에서 그치지 않고 2번 기능과 엮어서 "왜 늘었는지 설명까지" 붙여야 같은 함정을 피할 수 있다.

**우선순위 추천**: 1번(시나리오 UI)이 가장 즉시 착수 가능(백엔드 완성, FE 연결만 필요)하고, 2번은 1번과 같은 화면에 자연스럽게 붙일 수 있어 세트로 진행하는 게 효율적입니다. 3번은 스냅샷 데이터가 최소 2개 사업연도 이상 쌓인 뒤에야 의미가 생기므로 우선순위상 후순위로 두는 걸 권합니다.

  기본적으로 제공합니다.                                                                       
                                                                                               
  주요 특징은 다음과 같습니다:                                                                 
                                                                                               
  1. 서버 사이드 렌더링 (SSR - Server-Side Rendering): 사용자가 페이지를 요청할 때마다 서버에서
  HTML을 미리 렌더링하여 클라이언트에 보내주기 때문에 초기 로딩 속도가 빠르고 검색 엔진        
  최적화(SEO)에 매우 유리합니다.                                                               
  2. 정적 사이트 생성 (SSG - Static Site Generation): 빌드 시점에 HTML을 미리 생성해 두어, 요청
  시에는 이미 만들어진 HTML을 빠르게 제공합니다. 블로그나 문서 페이지처럼 내용이 자주 바뀌지   
  않는 곳에 적합합니다.                                                                        
  3. 직관적인 라우팅 (Routing): 파일 시스템 기반의 라우팅을 제공합니다. (예: pages 또는 app    
  폴더 안에 파일을 만들면 자동으로 해당 이름의 라우트로 연결됩니다.)                           
  4. API 라우트: 백엔드 서버를 따로 구축하지 않고도 Next.js 프로젝트 내에서 간단한 API 서버    
  기능을 만들 수 있습니다.                                                                     
  5. 자동 최적화: 이미지 크기 조절, 폰트 로딩, 스크립트 로딩 등을 자동으로 최적화하여 웹사이트 
  성능을 높여줍니다.

  좋게 만들기 위한 강력한 도구"**라고 이해하시면 됩니다.

  ### 3. 앱 개발만의 독특한 개념과 어려운 지식 (웹과 무엇이 다른가?)

  봅니다. 반면, 앱은 코드를 완전히 하나의 압축된 실행 파일 프로그램으로 포장(컴파일 및

  ④ 로컬 데이터베이스 (Local DB)

  ### 1. 밸런스 붕괴 (UX 저하 vs 인플레이션 방지)

  그동안 키운 나의 스탯이 확정되어 **'하나의 완성된 내 아바타 카드(명예의 전당)'**로 박제되는

  이렇게 하면 성취감을 온전히 보존하면서도 밸런스 인플레이션을 막을 수 있습니다.

  ### 1. 스탯 반감(밸런스) 포기가 가져올 '인플레이션' 문제                                     
                                                                                               
  스탯이 1200 이상일 때 반감되는 것이 유저 경험(UX)을 해칠 것 같아 배제하셨다고 했습니다.      
  하지만 이대로 가면 **'숫자의 가치 상실'**이라는 더 큰 문제에 직면합니다.                     
                                                                                               
  • 발생 이유: 스탯에 상한선이 없으면 유저의 스탯은 한 달 뒤 1만, 1년 뒤 10만이 됩니다.        
  초반에는 할 일 하나를 끝내고 [지능 +10]을 얻는 것이 기쁘지만, 내 전체 스탯이 10만일 때 오르는
  [지능 +10]은 아무런 감흥을 주지 못합니다.                                                    
  • 문제점: 성취감을 시각적으로 보여준다는 기획의 핵심 목표가 무너집니다. RPG 게임이 만렙을    
  설정하거나 시즌제를 도입하는 이유는, 유저가 자신의 성장을 '유의미한 비율'로 체감하게 만들기  
  위해서입니다. 무한한 스탯 확장은 결국 도파민 분비를 멈추게 만듭니다.                         
                                                                                               
  ### 2. '친구 서포트 카드' 시스템의 치명적 한계                                               
                                                                                               
  친구의 현실 스탯을 내 서포트 카드로 쓴다는 발상은 참신하지만, 실제 서비스 운영 시 가장 큰    
  병목(Bottleneck)이 될 것입니다.                                                              
                                                                                               
  • ① 콜드 스타트(Cold Start)와 진입 장벽:                                                     
      • 발생 이유: 생산성 앱은 지극히 개인적인 툴입니다. 내 주변 친구 4명이 이 앱을 동시에,    
      그것도 꾸준히 써야만 내 슬롯 4개를 채울 수 있습니다.                                     
      • 문제점: 초기 유저는 앱을 깔자마자 "친구 4명을 초대하지 않으면 손해를 본다"는 압박을    
      받습니다. 친구를 구하지 못한 유저는 박탈감을 느끼고 앱을 이탈할 확률이 매우 높습니다.    
  • ② 프리라이더(무임승차)와 의존성 문제:                                                      
      • 발생 이유: 내 스탯 상승이 '친구의 노력'에 달려있기 때문입니다.                         
      • 문제점: 만약 내 서포트 카드가 된 친구가 갑자기 며칠간 앱을 안 쓰면 어떻게 되나요? 내   
      버프 효과도 떨어지나요? 내 현실의 노력을 기록하는 앱인데, 타인의 게으름 때문에 내 효율이 
      떨어지거나, 반대로 남의 노력에 기대어 내 스탯이 뻥튀기된다면 "내 성장을 시각화한다"는    
      앱의 본질이 심각하게 훼손됩니다.                                                         
  • ③ 프라이버시 문제:

  ### 3. BM (가챠 시스템)의 자기모순

  • 발생 이유: 유저가 이 앱을 쓰는 이유는 "나의 실제 노력"을 기록하고 보상받기 위함입니다.     
  • 문제점: 돈을 내고 좋은 서포트 카드를 뽑아서 내 [지능 스탯] 상승률을 2배로 뻥튀기할 수      
  있다면, 그 스탯은 '내가 진짜로 열심히 공부한 결과'인가요, 아니면 '돈으로 산 가짜 스탯'인가요?
  경쟁 기반의 게임(PVP)에서는 스탯 뻥튀기가 돈을 쓸 이유가 되지만, 자기만족형 투두 리스트에서  
  돈으로 스탯을 사는 순간 기록의 신뢰성과 성취감이 산산조각 납니다. 유저들은 "결국 현질        
  앱이네"라며 조롱할 것입니다.                                                                 
                                                                                               
  ### 4. BERT(AI) 자동 카테고리화의 기술적/UX적 맹점                                           
                                                                                               
  AI를 붙이면 다 해결될 것 같지만, 실무 프로세스에서는 거대한 짐이 됩니다.                     
                                                                                               
  • ① 서버 비용 및 네트워크 지연(Latency):                                                     
      • 발생 이유: BERT 같은 자연어 처리 모델은 무겁습니다. 유저가 할 일을 입력할 때마다 서버로
      데이터를 보내고 AI가 판단하여 내려줘야 합니다.                                           
      • 문제점: 투두 앱의 생명은 '오프라인 상태에서의 빠른 기록'입니다. 지하철에서 데이터가    
      끊겼을 때 할 일을 등록하지 못하거나 2~3초의 딜레이가 발생한다면, 유저들은 답답해서 다    
      떠납니다.                                                                                
  • ② 엣지 케이스(Edge Case) 분류 오류:                                                        
      • 발생 이유: 유저의 입력은 정형화되어 있지 않습니다.                                     
      • 문제점: 유저가 "파이썬(애완 뱀) 밥 주기"라고 입력했는데 AI가 '파이썬'이라는 단어만 보고
      [지능/코딩] 스탯으로 분류해 버리면 어떨까요? 잘못된 스탯이 오르면 유저는 불쾌해하며      
      일일이 수정(Fix)해야 하고, 이는 AI가 없는 것만 못한 '불편한 앱'으로 전락하게 만듭니다.

## 핵심 세금계산 엔진 상세 코드 리뷰 (사용자 검증용)

사용자께서 직접 세금 계산 로직의 정확성을 검증하실 수 있도록, 핵심 엔진(	ax.py, mt.py)의 계산 로직을 코드 단위로 상세히 풀어서 설명합니다.

### 1. 	axengine/engine/tax.py (법인세 과세표준 및 세액 계산 코어 엔진)
법인세법 제13조(과세표준), 제55조(세율)에 근거하여 별지 제3호 서식의 계산 구조를 그대로 옮겨놓은 메인 계산 모듈입니다.

- **누진세액(과세표준, 세율표) 함수**
  - **역할**: 누진세율 구조(예: 2억 이하 9%, 200억 이하 19% 등)에 따라 세금을 계산합니다.
  - **검증 로직**: 
    1. 입력받은 과세표준을 순회하면서 세율표의 각 구간(상한액) 단위로 쪼갭니다.
    2. 구간액 = min(과세표준, 현재 구간 상한) - 이전 구간 상한 공식을 통해 해당 구간에 해당하는 금액만 발라냅니다.
    3. 추출된 구간액에 해당 구간의 세율(율)을 곱하고, 1원 미만을 버림(절사) 처리하여 해당 구간의 세액을 구합니다.
    4. 모든 구간에 대해 이 과정을 반복 합산하여 전체 산출세액을 도출합니다.

- **계산(입력) 함수 (전체 법인세 계산 흐름)**
  - **각사업연도소득 계산**: 
    - 각사업연도소득 = 당기순이익 + 가산조정(익금산입 등) - 차감조정(손금산입 등) + 기부금한도초과
    - 결산서상의 당기순이익에서 세무조정 사항을 가감하여 세법상의 실질 소득을 확정합니다.
  - **이월결손금 공제한도 적용 (법인세법 §13①)**: 
    - 중소기업인 경우 각사업연도소득의 100%, 일반기업인 경우 80%를 한도로 이월결손금을 공제받을 수 있도록 상한(min(이월결손금, 소득 * 공제율))을 둡니다.
  - **과세표준 산출**: 
    - 과세표준 = 각사업연도소득 - 이월결손금공제 - 비과세소득 - 소득공제 
    - 계산된 값이 0보다 작을 수 없도록 max(0, ...) 하한선 로직이 적용되어 있습니다.
  - **법인세 산출세액 도출**: 
    - 도출된 과세표준과 사업연도개시일에 해당하는 법인세율표를 앞선 누진세액() 함수에 넘겨 기본 세금(산출세액)을 구합니다.
  - **최저한세(AMT) 검증 및 적용**: 
    - 조특법에 따라 아무리 감면을 많이 받아도 내야 하는 최소한의 세금이 있는지 확인합니다 (mt.계산 모듈 호출). 
    - 최저한세에 걸릴 경우, 그 미달분만큼 원래 받으려던 공제감면세액을 깎아버립니다(적용후 공제감면세액 산출).
  - **최종 차감납부세액 계산**: 
    - 차감납부세액 = 산출세액 - (적용후 공제감면세액) + 가산세 - 기납부세액(미리 낸 세금)
  - **지방소득세 산출**: 
    - 법인세 과세표준과 동일한 금액을 기준으로 별도의 지방소득세 누진세율표를 적용해 지방소득세를 독립적으로 계산합니다.

### 2. 	axengine/engine/amt.py (최저한세 계산 엔진)
조세특례제한법 제132조에 따라 과도한 조세 감면을 방지하기 위한 안전장치 로직입니다.

- **계산(과세표준, 산출세액, 공제감면세액, 중소기업) 함수**
  - **최저한세 산출**: 
    - 중소기업 여부 및 과세표준의 크기에 따라 법정 최저한세율(율)을 가져옵니다. (예: 중소기업은 기본 7%)
    - 최저한세 = 절사(과세표준 * 율) 공식을 통해 기업이 부담해야 할 최소 세액을 확정합니다.
  - **감면후세액 비교**: 
    - 감면후세액 = 산출세액 - 공제감면세액 (현재 예정된 세금)을 계산합니다.
  - **공제감면 배제액 산출 (핵심 로직)**: 
    - 만약 감면후세액이 최저한세보다 작다면(즉, 세금을 너무 적게 내게 생겼다면), 그 차액(최저한세 - 감면후세액)만큼 원래 받으려던 공제감면세액을 무효화(배제)시킵니다.
    - 단, 무효화 할 수 있는 금액은 애초에 신청했던 공제감면세액을 초과할 수 없으므로 min(공제감면세액, 최저한세 - 감면후세액) 처리가 되어 있습니다.
  - **결과 적용**: 
    - 최종적으로 깎인 공제감면세액을 메인 세금 계산 엔진(	ax.py)으로 다시 돌려주어 정상적인 세금이 부과되도록 돕습니다.

# 프로젝트 3층 구조 정리 — FE / BE / DB (코드 기준, 2026-07-21)

아래 내용은 전부 현재 코드에 실제로 있는 것을 자연어로 옮긴 것이다. 각 항목에 파일 경로를 병기했고, 세법 근거 조문은 코드 주석·docstring에 적힌 것을 그대로 인용했다. 코드 스스로 "미검증/단순화"라고 표시한 부분은 §5에 따로 모았다.

## 0. 전체 흐름 한 줄 요약

```
[FE] taxwiz-fe 입력 마법사 (React)
   → JSON POST (한글 키 그대로)
[BE] taxengine/api/main.py (FastAPI)
   → db/migrate.py 검증+저장 → db/reader.py 로드 → pipeline.py 계산 → db/snapshot.py 스냅샷 저장
[DB] SQLite (taxengine/db/taxwiz.db)
   → 계산 결과 요약 JSON 응답 → FE ReviewPanel에 표시
```

핵심 설계 원칙 하나가 전 층을 관통한다: **CSV·DB·API·FE가 전부 같은 한글 키 계약을 쓴다**(예: `사업연도개시일`, `취득가`, `전기이월부인액`). 그래서 엔진(`pipeline.실행_데이터()`)은 입력이 CSV에서 왔는지 DB에서 왔는지 모른다 — `pipeline.py:23-28` docstring이 이를 명시한다.

## 1. FE — taxwiz-fe (React + TypeScript + Vite)

**FE는 세금 계산을 하나도 하지 않는다.** 입력 수집과 결과 표시만 담당하고, 계산은 전부 BE로 넘긴다.

- **진입점**: `src/App.tsx`가 `TaxInputWizard` 하나만 렌더링한다. (README에 적혀 있던 부가세 계산기 `src/scenarios/vatScenario.ts`는 현재 소스 트리에 존재하지 않는다 — 법인세 조정 입력 마법사로 정리된 상태.)
- **입력 엔진** (`src/taxinput/engine.ts`): "질문 하나 = cell 하나" 구조. `cellsForTopic()`이 매 렌더마다 현재 입력 상태로부터 다음에 물어볼 질문(cell) 목록을 다시 계산하는 파생값 방식이라, 값 하나가 바뀌면(예: "자산 몇 건?") 이후 질문(자산별 반복 입력)이 자동으로 생성된다. 질문 카탈로그는 `catalog.ts`(재무상태표/손익계산서 계정 그룹, 자산 구분, 상각방법, 조정 유형, 용어집)에 있다.
- **API 클라이언트** (`src/taxinput/api.ts`):
  - `buildFiscalYearPayload()` — 화면 입력 상태(`TaxInputState`)를 BE 스키마(`taxengine/api/schemas.py`)와 1:1 한글 키 JSON으로 변환. 이때 FE 표시용 라벨("익금산입(가산)")을 엔진 값("익금산입")으로 되돌리는 매핑, 지배주주 지분율 합산 등도 여기서 한다.
  - `submitAndCalculate()` — **호출 3연타가 FE→BE 흐름의 전부다**: ① `POST /companies` (회사 생성) → ② `POST /companies/{id}/fiscal-years` (입력 전체 제출) → ③ `POST /fiscal-years/{id}/calculate` (계산 실행). 주석에 명시된 대로 "기존 사업연도 수정" 엔드포인트가 없어서 **재계산할 때마다 새 회사·새 사업연도를 만든다**.
- **결과 표시** (`src/taxinput/components/ReviewPanel.tsx`): 계산 성공 시 과세표준·산출세액·차감납부세액·총납부세액을 표시. BE가 422(입력 무결성 검증 실패)를 돌려주면 `ApiError.checks`로 실패한 검증 항목(이름·상세)을 목록으로 보여준다 — 즉 **서버의 검증 실패 사유가 그대로 화면까지 전달되는 경로가 이미 있다**.

## 2. BE — taxengine (Python, FastAPI)

### 2-1. API 계층 (`taxengine/api/main.py`)

docstring 스스로 밝히듯 "라우트가 하는 일은 대부분 기존 모듈 호출 한 줄" — 비즈니스 로직은 API 파일에 없다. 엔드포인트:

| 엔드포인트 | 하는 일 |
|---|---|
| `POST /companies` | `migrate.회사_생성()` |
| `POST /companies/{id}/fiscal-years` | `migrate.데이터_이관()` — **저장 전에 `validate.검증()`을 강제**, 실패 시 롤백 + 422 |
| `POST /fiscal-years/{id}/calculate` | `reader.로드()` → `pipeline.실행_데이터()` → **검증 실패 시 422로 차단, 스냅샷 저장 안 함** → `snapshot.저장()` → 요약 반환 |
| `GET /fiscal-years/{id}/snapshots` | 계산 이력 조회 |

전기 사업연도 연결은 API가 자동으로 한다: `최근_사업연도_찾기()`로 같은 회사의 직전 연도를 찾아 `전기사업연도id`로 연결하고, `자산_명_매핑()`으로 전기 자산과 '명' 문자열 매칭해 `전기자산id`를 잇는다.

⚠️ 현재 인증 없음, CORS `allow_origins=["*"]` — 코드 주석에 "FE origin 정해지면 좁힐 것"이라고 명시된 미완 상태.

### 2-2. 계산 파이프라인 (`taxengine/pipeline.py` `실행_데이터()`) — 실행 순서 그대로

**1단계. 입력 무결성 검증** (`validate.py`) — 재무회계 원리 기반 3가지 검사:
- 재무상태표 대차평형: **자산 − 자산차감 = 부채 + 자본** (복식부기 항등식)
- 손익계산서: **당기순이익 = 수익 − 비용** (여기서 계산된 당기순이익이 이후 세무조정의 출발점이 된다)
- 자산대장 정합성: 기초누계 ≤ 취득가, 취득일·취득가 누락 여부

**2단계. 감가상각 시부인** (`engine/depreciation.py` — 근거: 법인세법 §23, 시행령 §26, 시행규칙 §15)
- 개념 구분(docstring이 강조): **상각범위액** = 세법이 허용하는 그 해 최대 손금(코드가 계산), **회사계상액** = 회사가 장부에 실제 적은 감가상각비(입력값). 시부인 = 둘의 비교.
- 상각범위액: 정액법 = 취득가액 × 정액률, 정률법 = 미상각잔액(취득가 − 기초누계) × 정률률. 상각률은 `domain/rates.py`의 별표4 상각률표(시행규칙 §15 별표4, 정액률 = 1/n, 정률률 = 1 − 0.05^(1/n)). 세법 공식은 잔존가치를 빼지 않는다는 것도 코드에 명시.
- 신규 취득 자산은 월할 계산 — 취득한 달을 1개월로 산입 (시행령 §26⑨, `사용월수()`).
- 판정: 회사계상액 > 상각범위액이면 초과분 **손금불산입(유보)**, 미달이면 **전기이월부인액 한도 내에서 손금추인(△유보)**, 한도 넘는 시인부족액은 소멸. 자산별 계산으로 통산 금지.
- 법정 강제(`상각선택()`): 건축물은 정액법만 허용(시행령 §26), 업무용승용차는 2016.1.1 이후 취득분 5년 정액법 강제(§27의2). 사용자가 다른 값을 골라도 무시하고 법정값을 쓴다 — 절세 시나리오 엔진이 불법 조합을 만드는 것 자체가 불가능해지는 구조.

**3단계. 기업업무추진비(구 접대비) 한도 시부인** (`engine/entertainment.py` — 근거: 법인세법 §25, 별지 제23호 갑·을). `company` 입력에 수입금액이 있을 때만 실행(없으면 하위호환으로 사람이 adjustments에 직접 적은 금액을 쓴다).
- ① 적격증빙 검증(을): 건당 3만원 초과 지출 중 적격증빙 없는 분 → **한도와 무관하게 전액 손금불산입**. 단, 건별 증빙 태그가 입력에 없어 이 금액 자체는 사람이 입력한다(코드 주석 R2에 명시된 한계).
- ② 한도 검증(갑): 한도 = 기본한도 × 사업연도월수/12 + 수입금액 구간별 적용률 누적. 기본한도 일반 1,200만 / 중소기업 3,600만. 수입금액 적용률: 100억 이하 0.3% / 100억~500억 0.2% / 초과 0.03%.
- 소규모 부동산임대법인이면 한도 50% 축소(§25⑤). 판정 기준(`domain/company.py`): 부동산임대업 주업 + 상시근로자 5인 미만 + 지배주주 지분 50% 초과.

**4단계. 업무용승용차 관련비용 판정** (`engine/car.py` — 근거: 법인세법 §27의2, 별지 제29호). 차량대장이 있을 때만 실행. 판정 순서:
- ① 업무전용자동차보험 미가입 → 관련비용(감가상각비+기타비용) **전액 손금불산입**
- ② 운행기록부 작성 시 관련비용 × 업무사용비율만 인정. 미작성 시 업무사용비율 = min(1, 1,500만원 ÷ 관련비용합계) — 사실상 1,500만원 한도
- ③ 인정된 감가상각비는 별도로 **800만원 한도** — 초과분 손금불산입(유보로 이월)
- ④ 소규모임대법인은 한도 절반(800만→400만, 1,500만→500만)

**5단계. 조정 합산**: 가산조정 = 수동 입력한 (익금산입+손금불산입) + 감가부인 + 추진비 손금불산입 + 승용차 손금불산입. 차감조정 = 수동 (손금산입+익금불산입) + 감가추인.

**6단계. 별지3 세액 계산** (`engine/tax.py` — 근거: 법인세법 §13(과세표준), §55(세율), §13①(이월결손금)):
```
당기순이익 (1단계 검증에서 확정)
+ 가산조정 − 차감조정 + 기부금한도초과
= 각 사업연도 소득금액
− 이월결손금 공제  ← 한도: 소득의 중소 100% / 일반 80% (rates.py 이월결손금공제율, §13)
− 비과세소득 − 소득공제
= 과세표준
× 누진세율  ← §55. 사업연도 개시일 ≥ 2026-01-01이면 전 구간 1%p 인상 분기
              (2억 이하 9→10%, 2억~200억 19→20%, 200억~3,000억 21→22%, 초과 24→25%)
= 산출세액
− 공제감면세액 (최저한세 적용 후)  ← 아래 최저한세
+ 가산세 − 기납부세액
= 차감 납부할 세액
```
- **최저한세** (`engine/amt.py` — 조특법 §132): 공제·감면 후 세액이 [감면 전 과세표준 × 최저한세율]에 못 미치면 그 차액만큼 공제·감면을 배제. 율은 중소 7%, 일반 100억 이하 10% / 100억~1,000억 12% / 초과 17% (`rates.py 최저한세율()`).
- **지방소득세**: 같은 과세표준에 독립 누진세율(0.9%/1.9%/2.1%/2.4%) 적용 — 지방세법 §103조의20, 위택스 별도 신고라는 주석 포함. 총납부세액 = 차감납부세액 + 지방소득세.
- 결과에 별지3 형태의 `단계` 배열(부호·라벨·금액)과 구간별 세율 내역이 같이 담긴다 — FE/Excel에서 "왜 이 금액인지" 보여줄 재료.

### 2-3. 금액 처리 규율 (`money.py`)

엔진 전체가 float를 쓰지 않고 **Decimal(십진 임의정밀도)**만 쓴다 — 부동소수 오차 원천 차단. 원 단위 미만은 기본 **절사(ROUND_DOWN)** — "세법 상각·세액 계산의 기본 규칙"이라고 주석에 명시. 불리언이 금액으로 새는 것도 타입 에러로 막는다.

### 2-4. 파이프라인 밖의 보조 엔진 3개

- **법인세비용 수렴 루프** (`engine/convergence.py`): "법인세비용을 계상해야 당기순이익이 확정되고, 당기순이익이 있어야 세액이 나오고, 세액이 나와야 법인세비용을 계상"하는 순환 참조를 반복 계산으로 해소. 법인세비용은 손금불산입(기타사외유출) 항목이라 당기순이익 감소분과 가산조정 증가분이 정확히 상쇄 → 각사업연도소득 불변 → 실무상 2회면 수렴. 종이책 재현(pipeline)과 달리 **새 사업연도를 처음부터 계산**할 때 쓰는 별도 경로.
- **절세 시나리오** (`engine/scenario.py`): 자산별 (상각방법 × 내용연수 ±25% 범위 — 시행규칙 §15 별표5·별표6) 적법 조합 전부의 세액을 계산해 오름차순 정렬. 반환값에 `과세이연_경고` 상수가 항상 포함된다: "생애 전체 상각액 합계는 고정이므로 유리한 조합은 전부 과세이연일 뿐, 총 부담이 줄어드는 게 아니다."
- **연도 간 자동이월** (`carryover.py` — 근거: 자본금과적립금조정명세서(을)의 유보 누적 관리): 이월 3종 — ① 당기 기초누계 = 전기 기초누계 + 전기 회사계상액, ② 당기 전기이월부인액 = 전기 이월부인 + 전기 부인 − 전기 추인(유보 누적), ③ 이월결손금 = 전기 미공제 잔액 + 당기 발생결손. `연속성검증()`이 "전기가 함의하는 당기 기초값 == 당기 입력값"을 대조해 연도 밀림·오타를 잡는다. **단, 현재 CLI 경로에서만 호출되고 API 경로에는 배선돼 있지 않다.**

### 3-2. 저장 규칙 (스키마 주석에 명시된 설계 결정)

- **금액은 전부 INTEGER(원 단위)** — SQLite는 DECIMAL을 선언해도 내부적으로 REAL(부동소수)로 저장할 수 있어 NUMERIC/REAL/DECIMAL 타입을 아예 쓰지 않는다. `money.py`의 Decimal 규율과 짝.
- **비율은 basis point 정수**(1% = 100bp, 예: 100.00% → 10000) — 지배주주지분율·업무사용비율. 같은 부동소수 회피 이유.
- **세율·상각률 등 법령 상수는 테이블화하지 않는다** — `rates.py` 코드에 둔다. "코드 리뷰가 필요한 값이라 사용자 데이터와 성격이 다르다"는 방침.
- **연도 간 체인을 FK로 고정**: `사업연도.전기사업연도id`, `자산.전기자산id`. 기초누계·전기이월부인액은 전기에서 자동 계산해 채우는 값이 아니라 **당해 연도의 리터럴 입력값**으로 저장한다 — 종이 신고서에 실제 적힌 숫자와 1:1 대응해야 감사 추적이 성립하기 때문. 전기 행과의 일치 여부는 검증(carryover 로직)으로만 확인.

### 3-3. 감사 추적 (append-only)

- **계산스냅샷**: 입력을 수정할 때마다 재계산해 **새 행을 추가**하고 UPDATE로 덮어쓰지 않는다 — "이 세액이 그 시점 입력값으로 계산됐다는 사실 자체가 세무 감사 추적의 핵심"(주석). 별지3 핵심 산출값 컬럼 + 엔진버전 + `원본결과_json`(pipeline 반환값 전체를 JSON으로 통째 보존). 시부인·한도 등 세부 내역은 입력에서 언제든 재계산 가능한 순수 파생값이라 정규화 테이블을 따로 두지 않는다(중복 소스 = 불일치 리스크).
- **입력수정이력**: 어느 테이블/행/필드가 언제 무엇에서 무엇으로 바뀌었는지 범용 로그 하나로.

### 3-4. 이관·로드 (`migrate.py` / `reader.py`)

- `migrate.py`: CSV(또는 API 요청 바디)를 DB로 옮기기 **전에 `validate.검증()`을 반드시 통과**시킨다 — DB CHECK 제약은 행 하나짜리 오타만 잡고, 대차평형처럼 여러 행을 합산해야 아는 오류는 못 잡기 때문. 실패 시 `검증실패` 예외 → 호출자가 롤백. ORM 없이 sqlite3 표준 라이브러리 + 파라미터 바인딩.
- `reader.py`: `사업연도id` 하나를 받아 **CSV 로더(`loader.로드()`)와 정확히 같은 모양의 한글 키 딕셔너리**로 복원한다(bp→퍼센트, 0/1→bool 되돌림). 이 대칭 덕에 엔진 코드는 하나도 안 바꾸고 CSV 경로와 DB 경로가 같은 계산을 한다.

## 4. 요청 한 건의 전체 시퀀스 (FE 제출 버튼 기준)

1. 사용자가 마법사에서 입력 완료 → ReviewPanel에서 제출
2. `api.ts buildFiscalYearPayload()` — 화면 상태를 한글 키 JSON으로 변환
3. `POST /companies` → 회사 행 INSERT
4. `POST /companies/{id}/fiscal-years` → `validate.검증()` (대차평형·당기순이익·자산 정합성) → 통과 시 사업연도·재무제표·자산·차량·조정 행 INSERT (+전기 연도가 있으면 FK 자동 연결), 실패 시 롤백+422
5. `POST /fiscal-years/{id}/calculate` → `reader.로드()`로 DB에서 입력 복원 → `pipeline.실행_데이터()` (§2-2의 6단계) → 검증 재확인(실패 시 422, 저장 안 함) → `snapshot.저장()` (append-only) → 커밋
6. 응답: {스냅샷id, 각사업연도소득, 과세표준, 산출세액, 차감납부세액, 총납부세액} → ReviewPanel 표시. 422면 실패한 검증 항목 목록 표시.

## 5. 코드가 스스로 표시해 둔 한계·미검증 (판단 시 참고)

내가 지어낸 게 아니라 코드 주석/docstring에 이미 적혀 있는 것들:

1. **최저한세 일반법인 100억 초과 구간(12%/17%) 웹 검증 미완** (`rates.py`) — "대형 법인에 적용하기 전 국가법령정보센터에서 재확인할 것". 중소 7%만 검증 완료(2026-07-20).
2. **지방소득세 2026년분 인상 연동 여부 미확인** (`rates.py`) — "신고 시점에 지방세법 §103조의20 확인 필요".
3. **최저한세 배제 순서 단순화** (`amt.py`) — 실제 배제 순서(시행령 §126: 손금산입/익금불산입 → 세액공제 → 감면 → 소득공제)를 구현하지 않고 `공제감면세액` 합산액 하나를 단일 배제 대상으로 취급. 항목별 이월관리가 들어오기 전까지의 의도적 단순화.
4. **업무용승용차 미반영 4가지** (`car.py`) — 월할 계산(12개월 아닌 사업연도), 전기이월 감가상각한도초과액의 당기 추인, 리스·렌트 감가상각비상당액 환산, 연두색 번호판 미부착 전액부인(2024.1.1~). (참고: 같은 파일의 "파이프라인 미통합" 주석은 stale — 실제로는 `pipeline.py:54`에 이미 연결됨.)
5. **추진비 적격증빙 없는 금액은 수동 입력** (`entertainment.py` R2) — 건별 증빙유형 태그가 입력에 없어 자동 판정 불가. 자동화된 건 한도 계산뿐.
6. **연속성검증(연도 간 이월 대조)이 API 경로에 미배선** — CLI에서만 동작. API로 2년차를 만들면 이월값 오류를 못 잡는다.
7. **API 인증 없음 + CORS 전체 허용** (`api/main.py`) — FE 연결 시점에 좁히기로 한 TODO 상태.
8. **FE 재계산 = 매번 새 회사·사업연도 생성** (`api.ts`) — 수정 엔드포인트 부재의 임시 우회. 같은 회사 데이터가 DB에 중복 누적된다.
