## 1. 한 장 요약

**만들 것**: 작년 연간결산 보고서를 코드로 재현해 실물과 대조 검증하고, 그 엔진으로 **세무사 전달용 완성 초안**을 만든다. 그 위에 상용 프로그램이 안 해주는 **절세 시나리오 비교**를 얹는다.

**핵심 통찰**: 종이 보고서 안에 세무조정의 **입력(재무제표·자산명세)과 출력(세액)이 둘 다** 있다 → 장부 없이도 4단계 엔진을 지금 만들고 채점할 수 있다. 그리고 그 종이는 나중에 분개 AI의 **채점표**가 된다.

**지금 막힌 것**: 법인 통장 1년치 (주력 트랙의 관문) · 법인 인증서 (내년 실사용 때)

**지금 할 것**: 종이책 구조화 입력 → 4단계 세액 엔진 → 절세 시나리오 (통장·인증서 불필요)

## 2. 확정 사항

### 2-1. 목표·범위

| 항목 | 결정 | 근거 |
|---|---|---|
| 1차 목표 | 실제 작년 보고서를 코드로 재현하고 **실물과 대조 검증** | 정답지가 있는 유일한 지점 |
| 최종 수준 | 데모용이 아닌 실사용 — **세무사 전달용 완성 초안** | 성실신고확인·외부조정은 세무사 서명이 법적 필수 |
| 입력 방식 | 종이 보고서를 보며 **수기 입력** (클로드가 CSV 템플릿 제공) | PDF 없음, 홈택스 재발급은 법인 인증서 필요 |
| 코드 | `ledger-automation` 재사용 없이 **신규 제작** | 사용자 지정 |
| 민감정보 | **`data/private/` 로컬 전용 + git 제외**, 식별자는 입력 단계부터 마스킹 | 주민번호·거래처·계좌 포함 |
| 절세 기능 | **원안대로 전면 구현** — 단 법적 제약을 코드로 강제해 불법 조합은 생성 불가. "추천"이 아닌 **적법 조합 비교표 + 근거 조문** | 세무대리 업역 리스크 회피 |
| 기술 스택 | Node.js(ESM) + `node --test` · 입력 CSV · 출력 Excel+HTML | 빌드 스텝 없이 확실히 도는 것 우선 |
| LLM 프레임워크 | LangGraph는 **1단계 분개 판정에만** | 수집은 결정론적 작업이라 LLM이 오히려 나쁨 (§3-4) |

### 2-2. 방법론 원칙

**정답지 원칙 (이 프로젝트의 헌법)**
세무는 틀리면 가산세가 나온다. **"대충 맞는 AI"는 실무에서 아무도 안 쓴다.** 어느 단계를 만들든 "얼마나 맞나"를 말할 수 있어야 한다.

**따라서 mock 데이터로 정확성을 주장하지 않는다.** 입력과 기댓값을 둘 다 내가 쓰면 순환논증이라 반증이 불가능하다. Mock이 정당한 자리는 두 곳뿐:
- **단위 테스트 fixture** — 세법이 정한 외부 정답(상각률표 예제 등). 이건 mock이 아니라 교과서 정답
- **흐름 데모** — 정확성이 아니라 파이프라인을 보여주는 용도 (`demo/`)

## 3. 논의로 **폐기된 것** — 다시 꺼내지 않기 위해

### 3-1. 원천자료 수집 자동화 ❌

**초기 근거(틀림)**: "수임동의로 이미 자동화됐으니 할 필요 없다"
**진짜 근거(팩트체크)**:
- 합법적 경로가 **없다**. 오픈뱅킹 API는 핀테크 업종 기업만, 마이데이터는 자본금 5억+금융위 허가, 펌뱅킹은 은행과 개별 계약
- 국세청이 **적극 단속 중** (2025.5 예고 없는 IP 차단, 스크래핑 원천차단 사업 착수, 트래픽 과금 검토)
- 금융당국은 **마이데이터 스크래핑을 2022.1.5부터 전면 금지**(신용정보법 §33조의2) — 정책 방향이 명확
- **얻는 게 월 몇 분**이다

⚠️ **추적 대상**: 국세청이 공식 오픈 API 게이트웨이를 설계 중(사업비 5.16억, 미완성). 완성되면 이 판단의 전제가 바뀐다.

### 3-2. 헤드리스 Chromium 은행 자동화 ❌

- **기술**: 간편인증·OTP는 **원천적으로 자동화 불가**(휴대폰 실시간 승인). 키보드보안(nProtect/델피노), KB의 **멀티로그인탐지 로그아웃**(홈택스 스파이크의 동시세션 문제와 같은 패턴), FDS(로직 비공개)
- **법**: 표준약관에 크롤링 금지 **명문 조항은 없었고**, 전자금융거래법 §6③의 "양도"도 대법원(2011도16167)이 확정적 이전으로 해석 → 본인 자동화는 해당 없어 보임. **그러나** 정보통신망법 §48①의 포괄 법리 + 마이데이터 규제 방향 → **회색지대**
- **결론**: 리스크 ≫ 이득

### 3-3. LangChain/LangGraph로 수집 에이전트 ❌

프레임워크를 바꿔도 **층위가 다른 문제**라 안 풀린다. 막히는 건 "만들 수 있느냐"가 아니라 "해도 되느냐"다.
게다가 수집은 로그인→클릭→다운로드의 **완전히 결정론적** 작업이라 LLM 에이전트를 쓰면 비결정적·느림·비쌈·디버깅 난해로 **오히려 나빠진다.** Playwright 스크립트가 낫다.

### 3-4. 크롬 확장으로 다운로드 자동화 — ⏸️ 보류 (금지 아님)

**헤드리스보다 훨씬 나은 자리다**: 본인 브라우저·본인 세션·본인이 보는 앞. FDS에 덜 걸리고 "대량 스크래핑"과 성격이 다르다. `projects/hometax/guide-extension/`이 이미 있어 비용도 낮다.

**그러나 우선순위 낮음**: 로그인이 사람이면 이미 브라우저 앞에 앉아 있는 상태 → 아끼는 건 **월 5분**. 옆에 **몇 시간짜리 문제**(76줄 분개)가 있다.

### 3-5. 5단계 신고·납부 자동화 ❌

접수증·납부서는 **신고 행위의 부산물**이라 만드는 대상이 아니다. 신고 자체는 세무사 서명이 법적 필수.

## 4. 지도 — 세무사무소가 하는 일 5단계

```
0단계  원천자료 수집    통장내역, 세금계산서, 카드내역, 증빙
1단계  장부 기록        거래 한 줄 한 줄을 분개(계정과목 판정)   ← ★주력
2단계  결산             감가상각 등 수정분개 → 시산표 확정
3단계  결산보고서       재무상태표·손익계산서 출력
4단계  세무조정         조정명세서 → 세액 계산                  ← 병렬
5단계  신고·납부        홈택스 제출 → 접수증·납부서 (부산물)
```

**보유 자료**: 종이 연간결산 보고서 1권 = **3·4·5단계의 결과물**. 0~2단계의 재료(전표·통장)는 없음.

### 단계별 전략 평가 (팩트체크 반영본)

| 단계 | 지금 사람이 하나? | AI가 이길 수 있나 | 정답지 | 지금 가능? |
|---|---|---|---|---|
| 0단계 수집 | ⚠️ **온라인 셀프서비스** — API 아님, 사람이 로그인·클릭 | **하면 안 됨** (§3-1) | — | ❌ |
| **1단계 분개** | ✅ **노동 집중** — 수임동의가 **통장·급여·현금·고정자산을 커버 안 함** | ✅ **승부처** — 업계 AI도 "초안+검토" 구조로 같은 방향 | 통장 + 종이책 재무제표 | 통장 필요 |
| 2단계 결산 | 부분 | 중간 | 종이책 시산표 | 자산대장 입력 후 |
| 3단계 보고서 | ❌ 자동 출력 | 낮음 (기계적 변환) | 종이책 전체 | ✅ 즉시 |
| 4단계 세무조정 | ⚠️ **부분** — 2025년에야 AI 등장, 그전엔 반나절~3시간. **판단 항목은 사람** | **중간~높음** — ① 판단 항목이 빈 곳 ② **일반 법인용 제품이 시장에 없음** ③ 절세 비교는 상용도 안 함 | 종이책 (완전) | ✅ 즉시 |
| 5단계 신고 | 세무사 서명 | **법적으로 불가** | — | ❌ |

**핵심**: 자료를 *가져오는* 일은 "자동화됐다"가 아니라 **"사람이 클릭하는 온라인 셀프서비스"**다. 안 하는 이유는 *이미 됐기 때문이 아니라* **합법 경로가 없고 이득이 작기 때문**이다. AI가 대체할 지점은 **1단계(판정)**이고, **4단계도 생각보다 비어 있다.**

**틀린 것으로 판명된 내 단언들** (상세: [`notes/팩트체크-자동화-현황.md`](notes/팩트체크-자동화-현황.md)):

| 단언 | 판정 | 실제 |
|---|---|---|
| "0단계 수집엔 이미 사람이 없다" | **절반 틀림** | 온라인 발급 ≠ 자동 수집. **공개 API가 확인된 항목이 하나도 없음** |
| "AI 스크래핑은 열등한 재구현" | **틀림** | **기존 기능 자체가 스크래핑.** WEHAGO가 자기 공지에 "대량 수집(스크래핑) 지연"이라 씀. 국세청 공식 API는 "사업자등록 진위확인" 하나뿐 |
| "세무조정은 이미 자동화됐다" | **과장** | 더존이 **2025.2에야** "반나절 걸리던 세무조정을 3분 만에"로 AI 출시. WEHAGO T는 2025.3. 이미 됐다면 지금 팔 이유가 없음 |

**결과**: 1단계 주력은 **유지(오히려 강화)**, 4단계는 **재평가(과소평가했음)** → **2트랙 병렬이 옳았다.**

**메타 교훈**: 검증 없이 세 명제를 단언하고 그 위에 계획을 세웠다. 팩트체크를 지시받지 않았다면 틀린 전제로 갔을 것이다. → **앞으로 "이미 ~되어 있다"류의 전제는 근거를 달거나 검증한다.**

## 6. 실행 순서

```
[공통 선행] 3단계 역할 A — 종이책 구조화 입력       ← 모든 길이 여기서 시작
     │      (1단계 채점표 + 2단계 채점표 + 4단계 재료 + 내년 이월 DB)
     │
     ├─→ [트랙 A · 즉시 가능] 4단계 세무조정 엔진 → 세액 재현 → 절세 시나리오
     │        재료가 종이책에 이미 있음. 통장·인증서 불필요
     │
     └─→ [트랙 B · 주력, 통장 확보 후] 1단계 분개 AI → 2단계 결산 → 3단계 역할 B
              통장 1년치가 관문. 확보되면 즉시 주력 전환
```

**두 트랙은 병렬이고, 버리는 작업이 없다**: 종이책 입력은 두 트랙 모두의 재료이자 채점표이고, 트랙 A의 세액 엔진은 나중에 트랙 B의 **최종 채점기**가 된다 — "분개가 맞았는가"의 궁극적 증명은 "세액이 맞게 나왔는가"다.

⚠️ **2·3·4단계는 일직선이 아니라 수렴 루프**: 법인세비용을 계상해야 당기순이익이 확정되고 → 세액이 나오고 → 그게 법인세비용이 된다. 반복 계산으로 수렴시킨다 ([`plans/PLAN-2-결산.md`](plans/PLAN-2-결산.md) §4). **아키텍처 설계 시 처음부터 반영.** (데모에서 2회차 수렴 확인 — 법인세비용이 손금불산입이라 소득이 불변이기 때문)
