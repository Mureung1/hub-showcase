# 연간결산 보고서 자동화 — 파이프라인 데모

> 작성일: 2026-07-16 · 상위 계획: [`../PLAN.md`](../PLAN.md)
> **데모 전용.** 세무사무소가 1년간 하는 일(0~5단계)이 어떻게 흘러가는지 보여주는 용도입니다.

## 실행

```bash
cd projects/annual_report_automation/demo
npm install
npm start          # → http://localhost:3100
npm test           # 엔진 검증 24개 (node --test)
```

빌드 스텝 없음 — Express + vanilla JS. 오늘 바로 돌아가는 것이 목적이라 프레임워크·트랜스파일을 넣지 않았습니다.

## ⚠️ mock 데이터에 대하여

**전부 가상의 데이터입니다.** (주)데모임대는 실재하지 않고, 숫자도 실제 법인과 무관합니다.

이 데모는 **흐름을 보여주는 용도**이지 계산의 정확성을 주장하지 않습니다. 정확성을 주장하려면
정답지(실제 세무사가 만든 보고서)와 대조해야 하는데, mock에는 정답지가 없습니다 —
입력과 기댓값을 둘 다 우리가 쓰면 순환논증이라 반증이 불가능합니다. (`../PLAN.md` §3)

### 다만 mock의 범위를 최소화했습니다

```
mock으로 주는 것  →  0단계 원천자료만 (통장내역 76건 · 자산대장 3건 · 기초잔액)
엔진이 계산하는 것 →  전표 · 시산표 · 재무제표 · 세무조정 · 세액 · 시나리오
```

시산표·재무제표·세액을 하드코딩하지 않고 **실제로 계산**합니다. 그래서:
- 데모의 숫자가 저절로 맞아떨어집니다 (자산 = 부채 + 자본이 우연이 아니라 필연)
- 실제로 만들 아키텍처와 **같은 구조**입니다 — 나중에 mock만 실데이터로 갈아끼우면 됩니다

## 화면은 2개뿐입니다

초기 버전은 엔진 구조를 그대로 나열한 8개 탭이었는데, **정보량만 많고 흐름이 안 보였습니다.**
`docs/design.md` §4의 여백 철학("한 화면에 핵심 메시지 1개 + 보조 비주얼 1개")에 맞춰 다시 만들었습니다.

### ① 워크플로우 — 지도

세무사무소가 1년간 하는 일 6단계를 한 화면에. **누가 하는가**만 보여줍니다.

```
0단계 수집    1단계 장부기록   2단계 결산   3단계 보고서   4단계 세무조정   5단계 신고
  기계          ★ 사람          기계         기계           기계           사람
              ↑ AI가 대체할 수 있는 곳                                   ↑ 법적으로 불가
```

핵심 질문 하나로 수렴합니다 — **"6단계 중 4개를 기계가 이미 하는데, 세무사무소는 왜 아직 사람을 비싸게 쓸까?"**
답: 자료를 *가져오는* 일에는 사람이 없고, 가져온 자료를 *판정하는* 일에 사람이 있습니다.

### ② 시나리오 체험 — 스토리

통장 76건에서 세액까지 9스텝으로 따라갑니다. **결정 지점은 2개**뿐이고 나머지는 기계가 합니다.

| 스텝 | 담당 | 내용 |
|---|---|---|
| 0 | — | 통장 76건 도착 — 우리가 가진 전부 |
| 1 | 기계 | 75건 자동 분개, 1건 막힘 (자동화율 바) |
| **2** | **★ 사람** | **확인 큐 — 통장 한 줄을 직접 판정** |
| 3 | 기계 | 결산 (감가상각 3건 · 선급비용 1건) |
| 4 | 기계 | 재무제표 — 자산 = 부채 + 자본 |
| 5 | 기계 | 세무조정 5건 (소득처분 태그) |
| 6 | 기계 | 별지3 세액 확정 (사다리) |
| **7** | **★ 사람** | **절세 시나리오 — 상각방법 선택** |
| 8 | — | 세무사 전달용 초안 완성 |

두 결정 지점 모두 **실제로 파이프라인을 다시 굴립니다.** 화면용 가짜 반응이 아닙니다.

## 데모의 클라이맥스 — 스텝 2

`임차인C 10,000,000 입금` 한 줄을 크게 띄우고 직접 고르게 합니다. 고르면 세액 차이가 밝혀집니다.

| 판정 | 과세표준 | 총 납부액 |
|---|---|---|
| 임대보증금 (부채) — 정답 | 88,036,163 | **8,575,579** |
| 임대료수입 (수익) — 오분개 | 98,036,163 | **9,565,579** |

**차이 990,000원.** 통장 한 줄의 계정과목 판정이 세금을 직접 가릅니다 — 그리고 세무는 틀리면
가산세가 나오기 때문에 "대충 맞는 AI"는 실무에서 아무도 안 씁니다.

스텝 3에서 이어지는 반전: **오분개해도 시산표 대차평형은 통과합니다.**
대차평형은 전기(轉記) 오류만 잡지 계정 착오를 못 잡습니다 → 그래서 정답지가 필요합니다.

## 스텝 7 — 절세 시나리오

법적 제약을 코드로 강제합니다(`depreciation.js`의 `상각선택()`). 건물에 정률법을 억지로 주입해도
법정 방법이 강제되어 세액이 바뀌지 않습니다 — 테스트로 검증했습니다.

| 자산 | 선택 가능? | 사유 |
|---|---|---|
| 건물 | ❌ 정액 40년 강제 | 세법상 건축물은 정액법만 (시행령 §26) |
| 승용차 | ❌ 정액 5년 강제 | 업무용승용차 특칙 (법인세법 §27의2) |
| 비품 | ✅ 정액/정률 × 4~6년 | 당기 신규 취득 → **6개 적법 조합** |

최대 차이 358,380원. **단, 절대 절감이 아니라 과세이연입니다** — 화면에 경고로 못박았습니다.
1,000만원은 어느 방법을 택하든 5년에 걸쳐 전액 손금이 됩니다. 유리한 건 "늦게 내는 것"이지
"덜 내는 것"이 아닙니다. 그래서 출력은 **"추천"이 아니라 "적법 조합 비교표 + 근거 조문"**입니다.

### API

| 엔드포인트 | 용도 |
|---|---|
| `GET /api/pipeline?q1=&방법=&연수=` | 1~5단계 전체. `q1`=확인 큐 답변, `방법`·`연수`=비품 상각 선택 |
| `GET /api/scenarios` | 적법 조합 6개 + 경고 + 배제된 변수 |
| `GET /api/impact` | 분개 판정 하나의 세액 영향 |
| `GET /api/source` | 0단계 원천자료 (통장·자산대장·규칙) |

두 결정 지점이 파라미터로 파이프라인에 들어가므로, 화면의 선택이 **실제 재계산**을 일으킵니다.

## 테스트가 검증하는 것 / 안 하는 것

**검증한다**
- 세법이 정한 **외부 정답**이 있는 계산 — 1억 5년 정률 = 45,100,000 (별표4 상각률 0.451). mock이 아님
- 내부 정합성 — 대차평형, 자산=부채+자본, 수렴, 별지3 각 단계의 산술
- 법적 제약 강제 — 건물에 정률법 주입 시 무시되는지, 내용연수가 ±25% 범위인지

**검증하지 않는다 (못 한다)**
- mock 회사의 세액이 "맞다"는 것 → 정답지가 없음. 실제 프로젝트에서 **종이 보고서가 채점표**가 됩니다

## 실제 프로젝트와의 관계

이 데모는 흐름의 지도이고, 실제 작업은 `../plans/`의 4개 계획서를 따릅니다.
가장 큰 차이는 **정답지의 유무**입니다:

```
데모:  mock 통장 → 엔진 → 세액        (채점 불가 — 정답이 없음)
실제:  진짜 통장 → 엔진 → 재무제표  ←→  종이 보고서 (채점표)
                          → 세액     ←→  종이 별지3   (채점표)
```
