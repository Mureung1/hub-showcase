## 전체 흐름 요약 (2026-07-21)

이 프로젝트(`annual_report_automation`)를 한 문장으로 요약하면 — **소상공인이 재무제표 숫자를 입력하면, 세법이 정한 규칙대로 세무조정을 계산해 별지3 세액과 근거 조문을 뽑아주는 시스템**입니다. Step 1~17을 거치며 다섯 단계가 순서대로 만들어졌습니다.

```
[웹 위저드 입력] → [API 요청] → [무결성 검증] → [DB 저장] → [계산 엔진] → [스냅샷 저장] → [결과 응답/Excel]
```

**1) 입력 — CSV 손입력에서 웹 위저드로 (Step 1, 5, 16)**
처음엔 종이책 숫자를 CSV 7종(`data/templates/` — 회사·재무상태표·손익계산서·자산·차량·조정·정답지)에 손으로 옮겨 적는 방식이었어요. 실데이터는 `data/private/`에만 두고 git이 절대 추적 못 하게 막았습니다(Step 1). 입력 즉시 `validate.검증()`이 재무상태표 대차평형 같은 정합성을 검사합니다(Step 5). 이후 타깃이 소상공인으로 정해지면서(memo: [[project_annual_report_target_users]]) `taxwiz-fe`(React) 위저드가 이 CSV 입력을 대체했습니다 — 질문 하나씩 답하면 같은 7종 데이터가 만들어져요(Step 16).

**2) 저장 — CSV 폴더 하나=회사 하나에서 멀티테넌시 DB로 (Step 11~14)**
CSV 폴더 하나가 회사 하나라는 가정은 여러 소상공인이 웹으로 쓰는 순간 깨집니다. 그래서 SQLite 스키마를 설계하고(`schema.sql`, Step 11), CSV→DB 이관 스크립트가 연도별 이월 체인을 자동으로 이어 붙이게 만들었어요(`migrate.py`, Step 12). 이관 직전에도 `validate.검증()` 게이트를 걸어, 대차가 안 맞는 데이터는 애초에 DB에 못 들어가게 막고 실패 시 전체 롤백됩니다(Step 14).

**3) 계산 엔진 — 세법 조문을 코드로 (Step 2~4, 7~10)**
`taxengine/` 안에 법이 정한 숫자(`rates.py`)부터 감가상각 시부인(`depreciation.py`), 누진세액 계산(`tax.py`), 최저한세(`amt.py`)·기업업무추진비(`entertainment.py`)·업무용승용차(`car.py`) 한도, 법인세비용 자기순환 수렴(`convergence.py`), 절세 시나리오 비교(`scenario.py`)까지 순서대로 쌓았습니다. `pipeline.py`의 `실행()`/`실행_데이터()`가 이 모든 계산을 한 곳에서 호출하며, CSV 경로든 DB 경로든 같은 계산 로직을 재사용해요(Step 13). 금액은 처음부터 끝까지 `Decimal`로 다뤄 부동소수 오차를 차단합니다(Step 7).

**4) 검증 — 정답지와 원 단위까지 대조 (Step 6, 8, 13)**
`reproduce.py`가 종이책의 실제 계산값(정답지)과 엔진 결과를 원 단위까지 대조합니다(Step 6). `carryover.py`는 작년 값이 올해 기초값으로 정확히 이어졌는지 연도 간 연속성을 검증하고(Step 8), CSV로 직접 계산한 결과와 DB를 거쳐 계산한 결과가 정말 같은지도 별도로 교차검증합니다(Step 13).

**5) 출력·서비스 — API와 Excel (Step 10, 15, 17)**
`export/excel.py`가 계산 결과를 각 숫자 옆에 근거 법조문 각주까지 붙여 Excel로 뽑아주고(Step 10), FastAPI 서버(`api/main.py`)가 이 계산 기능을 HTTP로 노출합니다 — 엔드포인트는 대부분 기존 함수 호출 몇 줄뿐이고, 무결성 검증도 그대로 상속받아요(Step 15). `taxwiz-fe`가 이 API를 실제로 호출하도록 연결되어, 회사 생성 → 사업연도 생성(입력 제출) → 계산 실행 순서로 요청을 보내고 결과(각사업연도소득·과세표준·산출세액·차감납부세액)를 화면에 표시합니다(Step 17).

**지금 경계선**: 로그인/인증 없음(누구나 API 호출 가능), 업무용승용차는 계산 로직만 있고 실제 차량 원시데이터 스키마는 없어서 시나리오 연결은 보류, 기존 사업연도 "수정" 기능 없음(재계산할 때마다 새로 생성). 다음에 이 파일을 다시 훑는다면 이 세 가지가 여전히 열려 있는지부터 확인하면 됩니다.

## Step 1 — 실데이터를 git에서 차단하는 안전장치 (2026-07-16 14:20)

**무엇을 했는지 (한 줄)**
프로젝트 뼈대(`package.json`, 폴더들)를 세우고, 개인정보가 든 실제 데이터가 실수로 git에 올라가지 않도록 `data/.gitignore`와 마스킹 규칙 문서(`data/README.md`)를 만들었어요.

**핵심 코드** — `data/.gitignore`

```gitignore
# private/ 내용은 전부 무시하되, 폴더 자체는 .gitkeep으로 유지한다.
private/*
# ↑ private 폴더 "안의 모든 것"을 git이 무시하게 함 (실데이터는 여기에만 둠)
!private/.gitkeep
# ↑ 딱 이 빈 파일 하나만 예외로 추적 → 폴더 구조는 남기되 내용물은 안 올림
```

여기서 트리키한 점: `private/`(슬래시로 끝)라고 쓰면 git이 폴더째 무시해서 `.gitkeep` 예외조차 안 먹혀요. 그래서 `private/*`(안의 것들)로 써야 "폴더는 유지, 내용만 차단"이 됩니다. 실제로 `git check-ignore`로 실데이터는 막히고 `.gitkeep`은 통과하는 걸 확인했어요.

마스킹 규칙(`data/README.md`)의 핵심은 — 주민번호는 **아예 입력하지 않고**, 이름은 `대표A`, 거래처는 `거래처01` 같은 코드로 바꿔 넣습니다. 금액·날짜만 진짜 값으로요.

**새로 나온 용어**
- `.gitignore`: git이 "이 파일들은 추적하지 마"라고 알려주는 목록 파일
- 마스킹(masking): 이름·주민번호 같은 걸 알아볼 수 없는 코드로 바꿔 넣는 것

**확인 질문**
`private/`가 아니라 `private/*`라고 써야 했던 이유를 한 문장으로 설명해보시겠어요?

**무엇을 했는지 (한 줄)**

```javascript
export function 상각선택(자산, 선택 = {}) {
  if (자산.업무용승용차) {
    return { 방법: '정액', 내용연수: 5, 고정: true, 사유: '업무용승용차 5년 정액 강제(§27의2)' };
    // ↑ 업무용 승용차는 무조건 5년·정액법. 사용자가 뭘 넣든 이 값으로 덮어씀

  if (고정방법) {
    return { 방법: 고정방법, ... 고정: true, 사유: `${자산.구분}은 ${고정방법}법만 허용(시행령 §26)` };

  }
  return { 방법: 선택.방법 ?? 자산.방법, ... 고정: false };

}
```

**핵심 코드 2** — 시부인 판정 (`시부인` 함수 내부)

```javascript
  const 차이 = 계상 - 범위.금액;
  // ↑ 회사가 장부에 적은 금액(계상) − 세법이 허용하는 한도(범위)
  if (차이 > 0) {
    부인액 = 차이;                    // 한도보다 많이 적었으면 초과분을 세금 계산에서 빼줌(손금불산입)

    추인액 = Math.min(-차이, 전기부인); // 적게 적었으면, 작년에 부인당했던 금액을 부족분만큼 되살림
  }
```

**새로 나온 용어**
- 감가상각: 비싼 자산(건물·차)을 산 값을 한 번에 비용 처리하지 않고 여러 해에 걸쳐 나눠 비용으로 인정하는 것

- 정액법/정률법: 매년 같은 금액씩 깎기 / 초기에 많이 깎고 점점 줄이기

## Step 4 — 세금 계산 본체, 별지3 (2026-07-16 14:39)

**무엇을 했는지 (한 줄)**
`src/engine/tax.js`에 실제 세금을 뽑는 계산을 넣었어요. 당기순이익에서 시작해 세무조정을 더하고 빼서 과세표준을 구하고, 거기에 누진세율을 적용합니다.

**핵심 코드** — 구간별 누진세액 (`누진세액`)

```javascript
export function 누진세액(과세표준, 세율표) {
  let 이전상한 = 0, 세액 = 0;
  for (const 구간 of 세율표) {
    const 구간액 = Math.max(0, Math.min(과세표준, 구간.상한) - 이전상한);
    // ↑ 이 구간에 "실제로 걸리는 금액"만 잘라냄. 예: 과세표준 3억이면 2억은 첫 구간, 1억은 다음 구간
    if (구간액 > 0) {
      const 부분 = Math.floor(구간액 * 구간.율);
      세액 += 부분;
      // ↑ 각 구간의 세금을 따로 계산해서 누적. 전체에 최고세율을 곱하는 게 아님
    }
    이전상한 = 구간.상한;
    if (과세표준 <= 구간.상한) break;
  }
  return { 세액, 내역 };
}
```

핵심은 "누진"이에요. 3억을 벌었다고 3억 전체에 높은 세율을 매기는 게 아니라, 2억까지는 낮은 세율, 넘는 1억만 높은 세율 — 이렇게 층층이 쌓아 계산합니다.

**새로 나온 용어**
- 당기순이익: 회계상 "올해 번 돈" (수익 − 비용)
- 누진세율: 금액이 클수록 높은 세율이 적용되는 구조 (단, 구간별로 나눠서)
- `Math.floor`: 소수점을 버리고 정수로 내림 (세금은 원 단위라 소수를 버림)

## Step 5 — 입력을 읽고 오타를 잡는 검증기 (2026-07-16 14:44)

**무엇을 했는지 (한 줄)**
종이책을 사람이 손으로 CSV에 입력하면 반드시 오타가 나요. `src/io/csv.js`(파일 읽기)와 `src/validate/integrity.js`(정합성 검사)로 그 오타를 기계가 잡게 했어요.

**핵심 코드** — 재무상태표 대차평형 검사 (`검증` 함수 내부)

```javascript
    const 자산 = sum(재무상태표.filter((r) => r.구분 === '자산'), '금액');
    const 자산차감 = sum(재무상태표.filter((r) => r.구분 === '자산차감'), '금액');
    const 부채 = sum(재무상태표.filter((r) => r.구분 === '부채'), '금액');
    const 자본 = sum(재무상태표.filter((r) => r.구분 === '자본'), '금액');
    const 좌 = 자산 - 자산차감, 우 = 부채 + 자본;
    // ↑ 회계의 철칙: (자산 − 감가상각누계액) 은 반드시 (부채 + 자본) 과 같아야 함
    add('재무상태표 대차평형 (자산−차감 = 부채+자본)', 좌 === 우, ...);
    // ↑ 이 둘이 안 맞으면 = 입력 어딘가에 오타가 있다는 확실한 신호
```

## Step 7 — 백엔드를 JavaScript → Python으로 전면 이관 (2026-07-16 16:30)

**무엇을 했는지 (한 줄)**
Step 1~6에서 JS로 만든 엔진 전체를 Python으로 다시 만들었어요(`taxengine/` 패키지). 계산 결과·테스트 27개·재현 성공은 그대로인데, **금액을 부동소수 대신 `Decimal`로 다뤄서 더 정확해졌고**, 김진영 님이 코드를 읽을 수 있게 됐습니다. 옛 JS(`src/`, `test/`)는 제거했어요.

**왜 바꿨나 — 정확성의 급소**
JS의 숫자(`number`)는 `0.1 + 0.2`가 `0.30000000000000004`가 되는 부동소수 오차가 있어요. 세금은 조정이 여러 해 누적돼서, 작은 오차가 몇 년 뒤 신고서와 원 단위로 어긋날 수 있습니다. Python `Decimal`은 이걸 언어 차원에서 막아줍니다.

**핵심 코드 1** — 금액을 Decimal로 강제 (`taxengine/money.py`, 새 파일)

```python
def 원(v) -> Decimal:
    """숫자·문자열을 원 단위 Decimal로 변환. 천단위 쉼표와 빈 값 허용."""
    if v is None or v == "":
        return Decimal(0)
    if isinstance(v, Decimal):
        return v
    return Decimal(str(v).replace(",", ""))
    # ↑ 핵심: str(v)로 문자열을 거쳐 Decimal을 만듦. float를 거치지 않아 오차가 안 낌

def 절사(d: Decimal) -> Decimal:
    """원 단위 미만 버림 (JS Math.floor에 대응)."""
    return d.quantize(Decimal(1), rounding=ROUND_DOWN)
    # ↑ 반올림 방식을 코드에 명시. 세법은 필드마다 절사/반올림 규칙이 달라서 이렇게 박아둠
```

**핵심 코드 2** — 같은 로직, 언어만 바뀐 예 (`engine/depreciation.py`)

```python
    정률 = 선택["방법"] == "정률"
    취득가 = 원(자산["취득가"])
    기준액 = 취득가 - 원(자산.get("기초누계", 0)) if 정률 else 취득가
    # ↑ JS의 삼항연산자(A ? B : C)가 Python에선 "B if A else C" 순서로 바뀜
    연액 = 절사(기준액 * 율)
    금액 = 절사(연액 * 월수 / 12)
    # ↑ JS의 Math.floor(...) 자리에 절사(...)가 들어감. 계산 결과는 동일
```

JS와 Python은 문법이 다르지만(삼항연산자 순서, `??` → `.get()`, `Math.floor` → `절사`), **로직과 계산 결과는 똑같습니다.** 그래서 테스트 기댓값(1억·5년 정률 = 45,100,000 등)도 그대로 통과하고, 재현도 여전히 정답지와 5/5 일치합니다.

**핵심 코드 3** — 테스트 도구도 바뀜 (`tests/test_depreciation.py`)

```python
class 상각범위액_교과서예제(unittest.TestCase):
    def test_기계장치_1억_5년_정률법_1년차(self):
        자산 = {"취득일": "2020-01-01", "취득가": 100_000_000, "기초누계": 0}
        self.assertEqual(상각범위액(자산, {"방법": "정률", "내용연수": 5}, FY2025)["금액"], D(45_100_000))
        # ↑ JS의 node --test → Python의 unittest. assertEqual로 "엔진값 == 세법 정답" 확인
```

JS의 `node --test`처럼 Python도 표준 라이브러리 `unittest`를 써서 **추가 설치 없이** 테스트가 돌아갑니다.

**새로 나온 용어**
- Decimal: 파이썬의 "정확한 십진 계산" 타입. 돈 계산에 부동소수(float) 대신 씀
- 부동소수(float): 소수를 2진수로 근사 저장하는 방식. 빠르지만 `0.1+0.2` 같은 미세 오차가 생김
- `quantize`: Decimal을 원하는 자릿수로 반올림/절사하는 메서드
- unittest: 파이썬 표준 테스트 도구 (JS의 node --test에 대응)

## Step 8 — 연도 간 자동이월 (2026-07-16 17:20)

**무엇을 했는지 (한 줄)**
2024 책자를 넣고 2025 책자를 이어 넣을 때, **작년 값이 올해 기초값으로 정확히 흘러갔는지** 자동으로 검사하는 기능을 만들었어요(`carryover.py`). 한 해만 맞추는 건 우연일 수 있지만, 두 해가 연결되면 우연이 아니거든요.

**핵심 코드 1** — 작년 자산 → 올해 기초값 (`carryover.py`)

```python
def 자산이월(전기자산: dict, 전기회사: dict) -> dict:
    a = 자산행(전기자산)
    s = 시부인(a, 전기회사)
    return {
        "명": a["명"],
        # 당기 기초누계 = 전기 기초누계 + 전기에 실제 계상한 상각비
        "기초누계": 원(a.get("기초누계", 0)) + s["회사계상액"],
        # ↑ 작년까지 깎은 총액 + 작년에 깎은 금액 = 올해 시작 시점의 누적 상각액
        "전기이월부인액": 원(a.get("전기이월부인액", 0)) + s["부인액"] - s["추인액"],
        # ↑ '유보'(회계·세무 차이)가 해마다 쌓이고 풀리는 걸 누적. 세무조사가 제일 먼저 보는 값
    }
```

**핵심 코드 2** — 작년이 함의하는 값과 올해 입력값을 대조 (`연속성검증`)

```python
    기대 = {v["명"]: v for v in (자산이월(a, 전기회사) for a in 전기결과["자산대장"])}
    # ↑ 작년 데이터로 "올해 기초값은 이래야 한다"를 계산
    당기 = {a["명"]: a for a in 당기_자산대장}
    for 명, exp in 기대.items():
        cur = 당기.get(명)
        누계_ok = 원(cur.get("기초누계", 0)) == exp["기초누계"]
        add(f"[{명}] 기초누계 이월", 누계_ok, ...)
        # ↑ 계산한 기대값 == 사람이 올해 입력한 값 인지 비교. 다르면 = 두 해 사이 입력 오류 신호
```

이게 강력한 이유 — 재현 CLI에 `--prev 작년폴더`를 붙이면 **[0] 연도 간 이월 연속성** 단계가 맨 앞에 붙어요. 실제로 2024→2025 예시를 돌려보니 기초누계·유보·이월결손금 3개가 다 맞았고(✓), 기초누계를 일부러 틀리게 넣으면 "이월이 어긋난다"며 멈춥니다. **두 해 사이의 실수(연도 밀림, 오타, 이월 누락)를 잡는 장치**예요.

작업하면서 공통 로직(폴더 로드·자산 정규화)을 `loader.py`로, 순수 계산부를 `pipeline.py`로 분리했어요 — 재현 CLI와 이월 검증이 같은 계산을 공유하게요. 테스트는 27개 → **35개**로 늘었습니다.

**새로 나온 용어**
- 자동이월(carryover): 작년 신고서의 기말 값이 올해 신고서의 기초 값이 되는 것을 자동 반영
- 유보: 회계와 세무의 차이가 회사 안에 남아 다음 해로 넘어가는 것 (해마다 쌓이고 풀림)
- 이월결손금: 작년에 손해(결손)가 났으면 올해 소득에서 빼주는 것

**확인 질문**

## Step 9 — 실데이터 없이 되는 4개 확장: 최저한세·추진비한도·승용차한도·수렴루프 (2026-07-20)

**무엇을 했는지 (한 줄)**
실데이터(종이책 수기 입력) 완료를 기다리는 동안, 데이터 없이도 만들 수 있는 4개 모듈을 추가했어요 — 최저한세 배제(`amt.py`), 기업업무추진비 한도(`entertainment.py`), 업무용승용차 한도(`car.py`), 법인세비용 수렴 루프(`convergence.py`). 앞의 둘은 실제로 `pipeline.py`에 연결해서 예시 데이터 재현(5/5)도 계속 통과하게 만들었고, 승용차는 계산 로직만 만들고 연결은 보류했어요(이유는 아래).

**핵심 코드 1** — 최저한세는 "신청한 공제감면 이상으로는 못 깎는다" (`engine/amt.py`)

```python
배제액 = Decimal(0)
if 감면후세액 < 최저한세:
    # 배제할 수 있는 건 어차피 "신청한 공제·감면세액"까지다 — 신청액이 0이면
    # 배제할 대상 자체가 없어 최저한세는 아무 영향을 주지 않는다.
    배제액 = min(공제감면세액, 최저한세 - 감면후세액)
```

처음엔 이 `min(...)`을 안 쓰고 "감면후세액이 최저한세보다 작으면 무조건 적용"이라고만 짰다가 테스트가 잡아냈어요 — 공제감면세액이 아예 0인데도 "최저한세가 적용됐다"고 나오는 버그였습니다. 최저한세는 **깎아주는 걸 도로 뺏는 장치**지, 없는 세금을 더 물리는 장치가 아니라는 게 핵심이에요.

**핵심 코드 2** — 기업업무추진비는 두 손금불산입을 더한다 (`engine/entertainment.py`)

```python
적격지출 = max(Decimal(0), 회사계상액 - 적격증빙없는금액)
한도초과 = max(Decimal(0), 적격지출 - 한도결과["한도"])
손금불산입합계 = 적격증빙없는금액 + 한도초과
# ↑ 증빙 없는 지출은 한도와 무관하게 무조건 부인, 나머지(적격지출)만 한도와 비교
```

**연결하면서 생긴 버그 하나** — `tests/test_reproduce.py`가 `pipeline.py`를 안 쓰고 세무조정 로직을 통째로 복붙해서 갖고 있었어요. 그래서 `pipeline.py`에 추진비 로직을 넣었더니, 복붙본은 그걸 모르니까 정답지와 500,000원이 어긋나며 테스트가 깨졌습니다. 고친 방법은 복붙본을 지우고 `pipeline.실행()`을 그대로 호출하게 바꾼 것 — 로직이 한 군데에만 있으면 이런 드리프트가 애초에 안 생겨요.

**핵심 코드 3** — 법인세비용 수렴은 사실 "값과 무관하게 답이 같다" (`engine/convergence.py`)

```python
당기순이익 = 세전당기순이익 - 법인세비용
가산조정 = 가산조정_세전 + 법인세비용
# ↑ 법인세비용이 얼마든, 당기순이익에서 빠진 만큼 가산조정에 그대로 다시 더해져서
#   각사업연도소득(= 당기순이익 + 가산조정 - ...)은 법인세비용 값과 무관하게 항상 같다
```

그래서 이 루프는 항상 "0원으로 1차 계산 → 나온 세액으로 2차 계산 → 2차 결과가 1차와 똑같이 나와서 수렴" 이렇게 딱 2회에 끝나요. 테스트(`test_각사업연도소득은_법인세비용_값과_무관하게_불변`)로 이 성질 자체를 검증했습니다.

**업무용승용차는 왜 연결을 안 했나**
계산 로직(`car.py`)과 테스트는 완성했지만, `pipeline.py`에 연결하려면 "차량별 감가상각비·유류비·보험료 같은 원시 데이터"가 필요한데 지금 CSV 어디에도 그 스키마가 없어요. 억지로 숫자를 지어내 연결하면 그건 이 프로젝트가 금지하는 "가짜 데이터로 정확성을 주장하는 것"이 되니까, 계산기만 만들어두고 실제 차량 데이터가 들어오면 연결하기로 했습니다.

**새로 나온 용어**

- 배제: 최저한세에 걸려서 원래 받을 수 있었던 공제·감면을 도로 못 받게 되는 것
- 기업업무추진비: 접대비의 새 법률 명칭 (2024.1.1부터)
- 적격증빙: 세법이 인정하는 지출 증빙(카드영수증·세금계산서 등) — 없으면 금액이 맞아도 손금불산입
- 순환 참조: A를 구하려면 B가 필요하고 B를 구하려면 A가 필요한 상태 — 반복 계산(iteration)으로 푼다

## Step 11 — DB 스키마 설계 (서브 에이전트, 2026-07-20)

**무엇을 했는지 (한 줄)**
지금까지 만든 엔진은 CSV 폴더 하나 = 회사 하나를 가정하는데, 소상공인 여러 명이 웹으로 쓰게 되면 이 가정이 깨져요. 그래서 서브 에이전트에게 "CSV 구조를 DB로 옮기면 어떤 스키마가 되는가"를 설계시켰습니다(`notes/DB-스키마-설계.md`, `taxengine/db/schema.sql`). 코드는 안 건드리고 설계 문서·DDL만 추가했어요.

**핵심 결정 1** — 이월값은 "매번 재계산"이 아니라 "그대로 저장 + FK로 검증"

```sql
-- 전기 자산이 함의하는 당기 기초누계 vs 당기에 실제 입력된 기초누계
SELECT 당기.id, 당기.명,
       (전기.기초누계 + 전기.회사계상액) AS 기대_기초누계,
       당기.기초누계 AS 입력_기초누계
FROM 자산 AS 당기
JOIN 자산 AS 전기 ON 당기.전기자산id = 전기.id
```

`carryover.py`가 이미 "두 해 값을 각각 입력받아 불일치를 찾는" 설계(우연이 아니라 진짜 연결됐는지 검증)라서, DB가 자동으로 재계산해버리면 그 검증 기능 자체가 사라져요. 그래서 `전기자산id` 같은 자기참조 FK로 "값은 그대로 저장하되 어디서 이어지는지"만 명시하는 쪽을 택했습니다.

**핵심 결정 2** — 비율도 금액처럼 정수로

```sql
지배주주지분율_bp  INTEGER  -- 1% = 100bp, 100.00% → 10000
```

`money.py`가 금액을 Decimal/정수로 다루는 이유(부동소수 오차 차단)를 지분율·업무사용비율 같은 비율 필드에도 그대로 적용했어요.

**새로 나온 용어**
- 멀티테넌시: 하나의 시스템을 여러 회사·여러 사용자가 각자 데이터를 분리해서 같이 쓰는 구조
- basis point(bp): 1%를 100등분한 단위 — 퍼센트를 소수 없이 정수로 표현하는 관행
- append-only: 기존 행을 고치지 않고 새 행만 계속 추가하는 저장 방식 (이력이 자동으로 남음)

## Step 12 — CSV → SQLite 이관 스크립트 (2026-07-20)

**무엇을 했는지 (한 줄)**
Step 11에서 만든 스키마(DDL)만 있고 실제로 CSV를 그 안에 채워 넣는 코드는 없었어요. `taxengine/db/migrate.py`(이관 로직)와 `taxengine/cli/migrate.py`(CLI)로 그 마지막 조각을 채웠습니다. `taxengine.loader.로드()`가 이미 CSV를 파싱해 딕셔너리로 주니까, 이 스크립트는 그 딕셔너리를 SQL INSERT로 옮기기만 해요.

```
python -m taxengine.cli.migrate --company "회사명" data/example-2y/2024 data/example-2y/2025
```

**핵심 동작 — 연도를 여러 개 한 번에 넘기면 이월이 자동으로 이어진다**

폴더를 오래된 연도 → 최신 연도 순서로 넘기면, 스크립트가 직전 폴더에서 만든 자산 id들을 "명(자산 이름)" 기준으로 기억해뒀다가 다음 폴더의 자산을 넣을 때 `전기자산id`로 이어 붙여요. 사업연도끼리도 `전기사업연도id`로 똑같이 연결됩니다. 나중에 회사를 나눠서(예: 2024년 먼저, 2025년은 몇 주 뒤에) 이관하고 싶으면 `--company-id`로 기존 회사를 지정하면 되는데, 이때는 DB에 이미 있는 가장 최근 사업연도를 스크립트가 스스로 찾아서 이어 붙입니다.

**의도적으로 안 만든 것**
설계 문서(Step 11) §9의 마지막 단계 — "이관 직후 `pipeline.py`를 한 번 돌려 `계산스냅샷` 첫 행 만들기" — 는 이번에 빼뒀어요. "CSV를 DB로 옮기는 것"과 "옮긴 데이터로 세액을 처음 계산하는 것"은 서로 다른 책임이라고 보고 경계를 나눴습니다.

**테스트**: `tests/test_migrate.py` 14개 — 단일연도 이관, 2개년 이월 체인, 회사를 나눠서 이관해도 이어지는지, `--dry-run`이 정말 아무것도 안 남기는지, DB 파일이 없을 때 스키마로 새로 만드는지를 확인.

**새로 나온 용어**
- dry-run: 실제로 실행하지 않고 "이렇게 될 것"만 미리 보여주는 모드
- 이관(migration): 데이터를 한 저장 형식(CSV)에서 다른 저장 형식(DB)으로 옮기는 작업

## Step 13 — DB 리더 + 계산스냅샷 저장 (2026-07-20 후속)

**무엇을 했는지 (한 줄)**
Step 12에서 일부러 빼뒀던 조각 — "DB에 넣은 데이터로 실제 세액 계산 돌리기" — 을 채웠습니다. `taxengine/db/reader.py`(DB→엔진 입력 변환, `migrate.py`의 반대 방향)와 `taxengine/db/snapshot.py`(계산 결과를 `계산스냅샷` 테이블에 저장)를 새로 만들고, `pipeline.py`를 살짝 나눠서 CSV든 DB든 같은 계산 함수를 쓰게 했습니다.

```python
# taxengine/pipeline.py
def 실행(d) -> dict:
    """폴더 d의 종이책 CSV로 세무조정을 계산해 결과 묶음을 돌려준다."""
    return 실행_데이터(로드(d))            # CSV 경로: 기존 로더로 읽고 계산

def 실행_데이터(data: dict) -> dict:
    """이미 로드된 데이터(로드()와 같은 모양의 딕셔너리)로 세무조정을 계산한다."""
    회사, 손익계산서, 재무상태표 = data["회사"], data["손익계산서"], data["재무상태표"]
    # ... (계산 본체는 그대로, "어디서 읽었는지"만 몰라도 되게 분리)
```

이렇게 나눠두면 DB 경로는 `실행_데이터(reader.로드(conn, 사업연도id))`처럼 **CSV를 읽는 코드를 한 줄도 안 건드리고** 그대로 계산기를 재사용할 수 있어요.

**까다로웠던 부분 — DB는 정수만 쓰는데 엔진은 bool/퍼센트를 기대한다**

Step 11에서 `업무용승용차`·`중소기업` 같은 참/거짓 값은 DB에 0/1로, `지배주주지분율` 같은 비율은 basis point(1%=100bp) 정수로 저장하기로 했었죠. 그런데 감가상각 엔진(`depreciation.py`)의 `상각선택()`은 `자산.get("업무용승용차")`가 실제 파이썬 `True`/`False`이길 기대해요. 그래서 `reader.py`는 DB에서 읽은 `1`/`0`을 파이썬 `bool()`로, `bp` 값을 `Decimal(bp) / 100`으로 다시 풀어서 돌려줍니다 — DB 전용 인코딩이 엔진까지 새어 들어가지 않게 여기서 막는 거예요.

```python
# taxengine/db/reader.py
"업무용승용차": bool(업무용승용차),                                    # 0/1 → True/False
"지배주주지분율": (Decimal(지분율_bp) / 100) if 지분율_bp is not None else None,  # bp → %
```

**계산스냅샷 — append-only 감사 이력**

```python
# taxengine/db/snapshot.py
def 저장(conn, 사업연도id, out, *, 엔진버전=None, 입력해시=None) -> int:
    ...
    cur = conn.execute("INSERT INTO 계산스냅샷 (...) VALUES (...)", (...))
    return cur.lastrowid   # UPDATE가 아니라 매번 새 행 — Step 11 §6.1의 "덮어쓰지 않는다" 원칙
```

핵심값(차감납부세액 등)은 조회하기 쉽게 컬럼으로 뽑아두고, `pipeline.py` 계산 결과 전체는 `원본결과_json`에 통째로 남겨요. 그런데 계산 결과 안의 금액은 파이썬 `Decimal` 타입이라 `json.dumps()`가 기본으로는 못 다뤄서, `default=str`처럼 "모르는 타입은 문자열로 바꿔라"는 규칙을 하나 얹어줬습니다.

**검증 — CSV로 직접 계산한 값과 DB를 거쳐 계산한 값이 정말 똑같은지**

`tests/test_db_reader_snapshot.py`가 같은 예시 데이터를 ① CSV에서 바로 계산한 결과와 ② CSV→DB 이관 후 DB에서 읽어 계산한 결과를 나란히 비교해요. 차감납부세액·과세표준·감가상각 부인액까지 전부 일치해야 통과합니다 — "엔진이 입력 출처를 몰라도 된다"는 설계 주장을 실제로 증명하는 테스트예요.

**의도적으로 안 만든 것**: HTTP API 서버. 지금은 여전히 CLI(`python -m taxengine.cli.snapshot --db ... --fiscal-year-id N`)로만 이 계산을 돌릴 수 있어요. FE(`taxwiz-fe/`)가 이 기능을 쓰려면 이 함수들을 감싸는 API가 필요한데, 그건 FE가 어느 정도 만들어진 뒤 진행하기로 했습니다.

**새로 나온 용어**
- 어댑터(adapter): 서로 다른 모양의 데이터를 한쪽이 이해하는 모양으로 바꿔주는 중간 변환기 (여기서는 `reader.py`가 DB 행 → 엔진이 기대하는 딕셔너리로 바꿔줌)
- append-only: 기존 행을 고치지 않고 새 행만 추가하는 저장 방식 (Step 11에서도 나온 개념 — 여기서 실제로 구현됨)
- 역직렬화(deserialize): 문자열(JSON)로 저장해둔 데이터를 다시 원래 구조(딕셔너리 등)로 되돌리는 것

**확인 질문**
`실행()`과 `실행_데이터()`를 굳이 나눈 이유를, "CSV"와 "DB"라는 단어를 써서 한 문장으로 설명해보시겠어요?

## Step 14 — 이관 시 무결성 검증 게이트 (2026-07-20 후속)

**무엇을 했는지 (한 줄)**
`migrate.py`가 CSV를 DB에 그냥 밀어넣기만 하고, 재무상태표 대차가 안 맞거나 자산 기초누계가 취득가를 넘는 것 같은 오류는 전혀 안 걸러내고 있었어요. `cli/reproduce.py`(CSV 직접 계산)는 항상 `validate.검증()`을 거치는데 DB 이관 경로만 그 관문이 빠져 있었던 거죠. `taxengine/db/migrate.py`의 `폴더_이관()`에 같은 검증을 추가했습니다.

```python
# taxengine/db/migrate.py
class 검증실패(ValueError):
    """이관하려는 CSV가 taxengine.validate.검증()을 통과하지 못했을 때 발생."""


def 폴더_이관(conn, 회사id, folder, 전기사업연도id, 전기자산_매핑):
    data = 로드(folder)
    v = 검증(재무상태표=data["재무상태표"], 손익계산서=data["손익계산서"], 자산대장=data["자산대장"])
    if not v["ok"]:
        실패내역 = "; ".join(f"{c['name']} — {c['detail']}" for c in v["checks"] if not c["ok"])
        raise 검증실패(f"{folder}: 입력 무결성 검증 실패 — {실패내역}")
    # 검증을 통과한 뒤에야 사업연도_삽입() 등으로 실제 INSERT를 시작한다
    ...
```

**왜 DB의 CHECK 제약만으로는 부족한가**

`schema.sql`의 CHECK 제약(`구분 IN ('자산','부채',...)` 같은 것)은 **행 하나**만 보고 판단할 수 있는 오류만 잡아요. 그런데 "대차평형"(자산 합계 == 부채+자본 합계)이나 "자산 기초누계가 취득가를 넘으면 안 됨" 같은 검사는 **여러 행을 합산·비교**해야 알 수 있어서 DB 제약으로는 표현이 안 됩니다. 그래서 CSV 계산 경로에 이미 있던 `validate.검증()`(SQL이 아니라 파이썬 함수)을 그대로 재사용했어요.

**실패하면 전부 롤백된다**

`이관()`은 폴더 하나라도 `검증실패`를 던지면 그 호출 전체를 롤백해요(2개년을 한 번에 이관하다 두 번째 연도가 깨져 있으면, 이미 잘 들어간 첫 번째 연도도 같이 취소됩니다). "부분적으로 맞는 데이터"가 DB에 남는 것보다, 전부 다시 고쳐서 재시도하는 쪽이 안전하다고 판단했어요.

**테스트**: `tests/test_migrate.py`의 `검증실패_이관_거부` 3개 — 대차 안 맞음, 자산 기초누계 초과, 2개년 중 하나만 깨져도 전체 롤백되는지 확인. CLI로도 스모크 테스트: 깨진 재무상태표를 이관하면 종료 코드 1과 함께 어떤 검증이 왜 실패했는지 그대로 출력됨.

**새로 나온 용어**
- 게이트(gate): 다음 단계로 못 넘어가게 막는 관문 — 여기서는 "검증 통과 못 하면 INSERT 자체를 안 함"
- 롤백(rollback): 트랜잭션 안에서 한 작업들을 전부 취소해 원래 상태로 되돌리는 것

## Step 15 — HTTP API 서버 (2026-07-20, "연결 지점만" 만들기)

**무엇을 했는지 (한 줄)**
지금까지 `taxengine`은 전부 CLI(`python -m taxengine.cli.*`)로만 쓸 수 있었어요. 프론트엔드가 웹 요청(fetch)으로 이 기능을 쓰려면 HTTP로 응답하는 서버가 있어야 하는데, 그게 하나도 없었습니다. FastAPI로 `taxengine/api/main.py`를 만들어 그 자리를 채웠어요. 지금은 "엔드포인트만 있고 프론트엔드가 실제로 호출하진 않는" 상태예요(연결은 나중에 하기로 함).

**핵심 원칙 — 이 파일에는 새 로직을 안 만든다**

```python
# taxengine/api/main.py
@app.post("/fiscal-years/{fiscal_year_id}/calculate")
def 계산_실행(fiscal_year_id: int, conn: sqlite3.Connection = Depends(get_conn)):
    data = db_로드(conn, fiscal_year_id)      # Step 13에서 만든 DB 리더
    out = 실행_데이터(data)                    # Step 13에서 만든 계산 함수
    스냅샷id = 스냅샷_저장(conn, fiscal_year_id, out)  # Step 13에서 만든 스냅샷 저장
    conn.commit()
    return {"스냅샷id": 스냅샷id, "차감납부세액": int(out["r"]["차감납부세액"]), ...}
```

엔드포인트 안에는 대부분 기존 함수 호출 한두 줄뿐이에요. API는 그냥 "HTTP 요청을 파이썬 함수 호출로 바꿔주는 얇은 막" 역할만 합니다 — 이렇게 해야 CLI로 검증된 로직(테스트 120개)을 API에서 다시 검증할 필요가 없어져요.

**핵심 결정 — JSON 계약은 CSV의 콤마 문자열을 그대로 따라가지 않는다**

CSV는 "12,500,000"처럼 쉼표 섞인 문자열을 허용하지만(사람이 손으로 타이핑하기 편하라고), JSON API는 처음부터 숫자 타입(`12500000`)으로 받게 만들었어요(`taxengine/api/schemas.py`의 pydantic 모델). 웹 폼이 보낼 데이터는 애초에 진짜 숫자이지 콤마 문자열이 아니니까요 — CSV 전용 관행을 API까지 억지로 끌고 오지 않았습니다.

**요청 바디는 로더가 쓰는 것과 똑같은 한글 키를 쓴다**

```python
# taxengine/api/schemas.py
class 사업연도생성요청(BaseModel):
    회사: 회사프로필입력
    손익계산서: list[재무제표행입력]
    재무상태표: list[재무제표행입력] | None = None
    자산대장: list[자산행입력] = []
    ...
```

이렇게 하면 `요청.model_dump()`가 곧바로 `taxengine.loader.로드()`가 CSV에서 만들던 것과 똑같은 모양의 딕셔너리가 돼서, `데이터_이관()`(Step 14에서 검증 게이트를 넣은 그 함수)에 그대로 넘길 수 있어요. Step 14의 무결성 검증(대차평형 등)도 API 경로에서 자동으로 같이 걸립니다 — 실패하면 422 응답과 함께 어떤 검사가 왜 실패했는지 돌려줍니다.

**의도적으로 남겨둔 것**
- CORS가 전부 허용(`*`)이고 로그인/인증이 없어요 — FE가 어디서 붙을지, 회사별 접근 제어가 필요한지가 아직 안 정해져서 지금 만들면 추측성 설계가 됩니다.
- `taxwiz-fe/`가 이 API를 호출하는 코드는 없어요 — 이번엔 "연결 지점"까지만 만들기로 했습니다.

**테스트**: `tests/test_api.py` 6개 — `TestClient`(FastAPI가 실제 서버를 안 띄우고 요청/응답을 시뮬레이션하는 도구)로 "회사 생성 → 사업연도 생성 → 계산 → 스냅샷 이력 조회" 전체 흐름을 확인. `data/example/fy2025`를 JSON으로 옮겨 적어 넣었는데, 계산 결과가 종이책 정답지(차감납부세액 8,575,599)와 정확히 일치. 진짜 uvicorn 서버를 띄워서 `/health`·`/docs`·POST 요청도 별도로 확인함.

**새로 나온 용어**
- HTTP API: 웹 요청(주소 + 방식)으로 프로그램 기능을 부르는 방식. `POST /companies`처럼 "주소 + 동사"로 표현
- 엔드포인트(endpoint): API에서 하나의 요청을 받는 개별 주소(예: `/companies`)
- pydantic 모델: 파이썬에서 "이 데이터는 이런 필드·타입을 가져야 한다"를 선언해두면, 요청이 들어올 때 자동으로 검사·변환해주는 라이브러리
- CORS: 웹 브라우저가 "다른 주소(origin)의 서버로 요청을 보내도 되는지"를 검사하는 보안 규칙
- TestClient: 진짜 네트워크를 안 열고, 코드 안에서 API 요청/응답을 흉내 내서 빠르게 테스트하는 도구

`taxengine/api/main.py`의 엔드포인트 함수들이 왜 대부분 몇 줄 안 되는지, Step 13·14에서 만든 것과 연결 지어 설명해보시겠어요?

## Step 16 — taxwiz-fe: taxengine 입력 위저드 (2026-07-20)

**무엇을 했는지 (한 줄)**
`taxwiz-fe/`(React)에 taxengine이 읽는 7종 CSV(회사·재무상태표·손익계산서·자산·차량·조정)를 웹 화면으로 입력받는 "질문 하나씩 답하는" 위저드를 새로 만들었어요(`src/taxinput/`). 입력 중인 질문은 화면 상단에 고정돼 있고, 답할 때마다 그 카드가 바로 아래 이력 목록 맨 위로 내려가 쌓입니다. 기존에 있던 부가세 퀴즈 화면(`pages/`, `scenarios/`, `components/progressive-form/`)은 이 세션에서 방향이 확정되며 완전히 안 쓰는 코드가 돼서 지웠고, 재사용 가능한 조각(`Button`, `NumberInput`, `SelectCard`, `Tooltip`)만 남겼어요.

**핵심 코드 1** — "질문 목록"은 매번 현재 데이터로 새로 계산한다 (`taxinput/engine.ts`)

```typescript
export function cellsForTopic(topicKey: string, io: EngineIO): Cell[] {
  if (topicKey === "company") return COMPANY_FIELDS.map((f) => wrapBoundField(f, io));
  if (topicKey.startsWith("bs:")) {
    const g = BS_GROUPS.find((x) => x.key === topicKey.slice(3))!;
    return genGroupCells(topicKey, g, "bsExtra", "bs", io);
    // ↑ "재무상태표에 추가할 과목이 더 있나요?"에 "네"라고 답하면 이 함수가
    //   다음 렌더에서 이름/금액 질문 두 개를 자동으로 더 만들어냄
  }
  ...
}
```

고정된 질문 목록을 만들어두는 게 아니라, **지금까지 입력한 값을 보고 다음 질문 목록을 매번 다시 계산**해요. 그래서 "과목을 몇 개 더 추가할지"처럼 사용자가 답하기 전엔 모르는 질문 개수도 자연스럽게 처리됩니다.

**핵심 코드 2** — 다음 질문으로 넘어가는 시점을 렌더 이후로 미룬 이유 (`taxinput/useEngine.ts`)

```typescript
// commit() 안에서 cell.set(value)를 부르면 리액트는 그 변경을 "나중에" 반영해요.
// 그래서 commit() 함수 안에서 바로 "질문이 몇 개 남았지?"를 확인하면 방금 한
// 답이 아직 반영 안 된 옛날 값을 보게 됩니다. 그 대신 데이터가 실제로 바뀐
// "다음" 렌더에서 실행되는 useEffect가 이 판단을 하게 미뤘어요.
useEffect(() => {
  if (cursor.frontier < cells.length) return;       // 아직 이 주제(topic) 안에 질문이 남음
  const idx = TOPIC_ORDER.indexOf(cursor.topicKey);
  setCursor((prev) => ({ topicKey: TOPIC_ORDER[idx + 1], frontier: 0, ... }));
}, [cursor.frontier, cursor.topicKey, cursor.editingId, cells.length]);
```

리액트 데모를 만들며 실제로 겪은 함정이에요 — 처음엔 `commit()` 안에서 바로 판단하게 짰다가, "추가 과목이 있나요?"에 "네"라고 답하면 새로 생겨야 할 "과목명이 뭔가요?" 질문을 건너뛰고 곧장 다음 주제로 넘어가버리는 버그가 났어요. 원인은 **아직 반영되지 않은 옛날 데이터**를 보고 "질문이 다 끝났다"고 잘못 판단한 것. `useEffect`로 판단 시점을 늦춰서 해결했습니다.

**핵심 코드 3** — 카드가 "내려가는" 애니메이션은 직접 계산하지 않는다 (`taxinput/components/AnsweredRow.tsx`)

```tsx
<motion.button layout layoutId={cell.id} ...>
```

같은 `layoutId`를 답변 전 카드(`ActiveCell`)와 답변 후 카드(`AnsweredRow`)에 똑같이 붙여주면, 프레이머모션(framer-motion) 라이브러리가 "이 둘은 같은 것의 두 모습"이라 판단하고 위치·크기 변화를 알아서 부드럽게 이어줘요. 원래 목업(순수 HTML/JS 버전)에서는 이 효과를 직접 좌표를 계산해서 흉내 냈었는데(FLIP 기법), 리액트에서는 라이브러리가 대신 해주니 코드가 훨씬 짧아졌습니다.

**QA 과정에서 실제로 잡은 버그**: 브라우저로 직접 눌러보다가, 숫자 입력창에서 Enter를 눌러도 다음 질문으로 안 넘어가는 걸 발견했어요. 원인은 금액 입력 컴포넌트(`NumberInput`)가 자기 내부의 키보드 입력을 바깥으로 안 알려주고 있었던 것 — 감싸는 태그에 `onKeyDown`을 달아서 이벤트가 위로 "버블링"되는 걸 잡는 방식으로 고쳤어요.

**새로 나온 용어**
- 위저드(wizard): 여러 단계를 하나씩 밟아가며 입력을 완성하는 화면 흐름
- 클로저(closure): 함수가 자신이 만들어질 때의 주변 변수를 "기억"해서 나중에도 쓸 수 있는 것 (`get`/`set` 함수가 어떤 계정과목인지 기억하는 방식)
- 이벤트 버블링(bubbling): 자식 요소에서 일어난 이벤트(클릭, 키보드 입력 등)가 부모 요소까지 타고 올라가며 전달되는 것
- layoutId(프레이머모션): 서로 다른 두 컴포넌트에 같은 값을 붙이면 "같은 것의 전후 모습"으로 인식해 위치·크기 변화를 자동으로 애니메이션해주는 속성

**확인 질문**
`commit()` 함수 안에서 바로 "다음 주제로 넘어갈지" 판단하면 안 됐던 이유를, "리액트는 상태 변경을 나중에 반영한다"는 말을 써서 한 문장으로 설명해보시겠어요?

```typescript
}
```

`taxengine/api/schemas.py`가 CSV·DB와 필드명을 1:1로 맞춘다고 문서에 적어놓은 원칙을, FE도 그대로 따라갔어요 — 새 이름 체계를 만들지 않고 백엔드가 이미 정한 한글 키를 그대로 씁니다.

**핵심 코드 2** — 서버 응답의 두 가지 오류 모양을 하나로 통일 (`taxinput/api.ts`)

```typescript
const detail = body?.detail;
if (detail && typeof detail === "object" && Array.isArray(detail.checks)) {
  throw new ApiError(detail.message || "요청이 거부됐어요", detail.checks);
  // ↑ POST .../calculate가 실패하면 {message, checks: [...]} 형태로 옴
}
throw new ApiError(typeof detail === "string" ? detail : `요청이 실패했어요 (HTTP ${res.status})`);
// ↑ POST .../fiscal-years가 실패하면 detail이 그냥 문자열 하나로 옴 (FastAPI의 기본 에러 모양)
```

같은 서버인데 실패하는 위치에 따라 에러 응답 모양이 달라요(하나는 구조화된 객체, 하나는 그냥 문자열). curl로 직접 두 실패 경로를 재현해보고서야 이 차이를 알았고, 두 모양 다 처리하도록 분기했습니다.

**QA 방법 — 브라우저 대신 curl로 API 계약을 먼저 검증**

위저드는 질문이 90개가 넘어서 브라우저로 처음부터 끝까지 눌러보며 테스트하기엔 비효율적이었어요. 대신 실제 API 서버를 띄우고(`python -m taxengine.api.main`) FE가 보낼 것과 똑같은 모양의 JSON을 curl로 직접 쏴봤습니다.

```bash
curl -X POST http://127.0.0.1:8000/companies/1/fiscal-years -d @fy_req.json
curl -X POST http://127.0.0.1:8000/fiscal-years/1/calculate
# → {"차감납부세액":6300000, ...}  (매출 1억 − 급여 3천만 = 소득 7천만, 중소기업 9%)
```

계산 결과가 손으로 검산한 값과 정확히 맞아떨어지는 걸 확인한 뒤, 이 테스트가 만든 로컬 DB 파일(`taxengine/db/taxwiz.db`)은 지우고 `.gitignore`에 추가했어요 — 실행할 때마다 새로 생기는 산출물이라 커밋 대상이 아니거든요.

**의도적으로 안 만든 것**: "기존 사업연도 수정" 기능. API에 그 엔드포인트가 없어서, 재계산할 때마다 회사·사업연도를 새로 만들어요(DB에 이력이 계속 쌓임) — 지금 단계에선 그게 "옛날 데이터가 남아서 계산이 꼬이는" 상황보다 안전하다고 판단했습니다.

**새로 나온 용어**
- fetch: 브라우저가 서버에 HTTP 요청을 보내는 표준 자바스크립트 함수
- 페이로드(payload): 요청에 실어 보내는 실제 데이터 본문
- 스모크 테스트(smoke test): 전체를 꼼꼼히 검사하기 전에 "일단 기본적으로 돌아가긴 하는지"만 빠르게 확인하는 테스트

## 용어집

- `.gitignore`: git이 "이 파일들은 추적하지 마"라고 알려주는 목록 파일
- 마스킹(masking): 이름·주민번호 같은 걸 알아볼 수 없는 코드로 바꿔 넣는 것
- 과세표준: 세금을 매기는 기준 금액 (여기에 세율을 곱하면 세금이 나옴)
- 삼항연산자(`A ? B : C`): "A가 참이면 B, 아니면 C"를 한 줄로 쓰는 문법
- 감가상각: 비싼 자산을 산 값을 여러 해에 걸쳐 나눠 비용으로 인정하는 것
- 시부인: 회사가 적은 감가상각비와 세법 한도를 비교해 조정하는 것
- 손금불산입: "비용으로 안 쳐줌" → 세금 매길 소득이 늘어남
- 정액법/정률법: 매년 같은 금액씩 깎기 / 초기에 많이 깎고 점점 줄이기
- 당기순이익: 회계상 올해 번 돈 (수익 − 비용)
- 누진세율: 금액이 클수록 높은 세율이 적용되는 구조 (구간별로 나눠서)
- `Math.floor`: 소수점을 버리고 정수로 내림
- CSV: 쉼표로 칸을 나눈 표 파일 (엑셀로 열 수 있음)
- 대차평형: 재무상태표의 자산 합과 부채+자본 합이 같아야 한다는 원칙
- `.filter(...)`: 배열에서 조건에 맞는 것만 골라내는 문법
- CLI: 명령어로 실행하는 프로그램
- 정답지: 종이책에 적힌 세무사의 실제 계산값. 엔진 채점 기준
- 부인/추인: 세금 계산에서 비용을 빼거나(부인) 되살리는(추인) 것
- Decimal: 파이썬의 "정확한 십진 계산" 타입. 돈 계산에 float 대신 씀
- 부동소수(float): 소수를 2진수로 근사 저장. 빠르지만 `0.1+0.2` 같은 미세 오차 발생
- quantize: Decimal을 원하는 자릿수로 반올림/절사하는 메서드
- unittest: 파이썬 표준 테스트 도구 (JS의 node --test에 대응)
- 자동이월(carryover): 작년 신고서 기말 값이 올해 기초 값이 되는 것을 자동 반영
- 유보: 회계·세무 차이가 회사 안에 남아 다음 해로 넘어가는 것 (해마다 쌓이고 풀림)
- 이월결손금: 작년에 손해(결손)가 났으면 올해 소득에서 빼주는 것
- 위저드(wizard): 여러 단계를 하나씩 밟아가며 입력을 완성하는 화면 흐름
- 클로저(closure): 함수가 만들어질 때의 주변 변수를 기억해서 나중에도 쓸 수 있는 것
- 이벤트 버블링(bubbling): 자식 요소의 이벤트가 부모 요소까지 타고 올라가며 전달되는 것
- fetch: 브라우저가 서버에 HTTP 요청을 보내는 표준 자바스크립트 함수
- 페이로드(payload): 요청에 실어 보내는 실제 데이터 본문
- 스모크 테스트(smoke test): 전체를 꼼꼼히 검사하기 전에 기본 동작만 빠르게 확인하는 테스트
