## 0. 한 줄 결론

| 차원 | 결정 | 지금? |
|---|---|---|
| **금액 타입** | **원 단위 정수(BigInt/INTEGER)** + 나눗셈은 decimal.js 경유 후 명시적 절사 | ★ **지금 당장** |
| **BE 언어** | 현 **JavaScript 유지** (BigInt 보완). 단 Python이 정확성 관점 이론적 최적 — §2 | 유지 + 보완 |

핵심 통찰: 세 조사가 **한 곳으로 수렴**했다 — "정확성의 급소는 언어가 아니라 **금액을 부동소수로 다루는 것**"이다. 이것만 잡으면 나머지(언어·DB·FE)는 과잉투자를 피하는 문제로 내려간다.

## 1. 금액 정밀도 — 진짜 급소 (BE·DB 조사 공통 결론) ★

### 문제

JavaScript `number`(IEEE 754 double)는 10진 소수를 정확히 표현 못 한다.
- `0.1 + 0.2 === 0.30000000000000004`
- 단가 8.5 × 세율 0.2 = `1.7000000000000002` → 반올림하면 1.71이 나와야 할 곳에 1.70
- `$2.78`을 float로 저장하면 `2.7799999713897625`

세무조정은 조정 항목이 **누적·이월되며 여러 해에 걸쳐 재계산**되므로, 작은 오차도 몇 년 뒤 국세청 신고 서식과 원 단위로 어긋난다. **이 프로젝트에서 절대 허용 불가.**

> 현재 코드는 `Math.floor`로 원단위 내림해 우연히 피하고 있지만, 이건 규율이 아니라 운이다.

### 해결 (업계 표준)

**"돈은 최소단위 정수로 저장하라"** (ISO 4217, Modern Treasury, 다수 출처 일치).
- 원화(KRW)는 소수 단위(전)가 실무상 없어서 **원 단위 정수 자체가 최소단위** — 미국의 "센트 곱하기"보다 오히려 간단.
- **한계**: 정수 저장만으론 부족하다. 세율 곱셈(22% 등)에서 다시 소수가 생긴다. → "임의정밀도로 계산 → 마지막에만 명시적 절사/반올림 → 정수로 확정"이라는 설계가 필요.

### 한국 세무 절사 규칙 (BE 조사)

필드마다 규칙이 다르다: 원단위 절사 / 10원 미만 절사 / 사사오입(반올림). 장부 프로그램은 보통 반올림.
→ 엔진은 **필드별 반올림 모드를 코드에 명시**할 수 있어야 한다. (`quantize(..., ROUND_HALF_UP)` 같은 API)

## 2. BE 언어 — 유지 vs 전환

### 조사 결론: 정확성만 보면 Python이 이론적 1위

BE 에이전트의 순위: **1위 Python(`Decimal` 내장) · 2위 Kotlin/Java(`BigDecimal`) · 3위 C#(`decimal`)**. JS/TS는 "언어가 공짜로 안 주는 정확성을 서드파티로 메꾸는 상태"라 근본적 열위.

근거 보강:
- 프랑스 정부 세금엔진 **OpenFisca = Python**. 단 집단통계용이라 `float32`를 써서 **원단위 정확성엔 오히려 반례** — 우리는 따라가면 안 됨.
- 국내 더존 스마트A = **C#/.NET**(`decimal` 네이티브). 국내 세무 SW가 수십 년 이 스택을 쓴 방증.
- Excel 출력: Python `openpyxl`은 수식 계산 지원, Node `exceljs`는 **수식 저장만 하고 계산 못 함** → 값 정확성엔 openpyxl 우위.

### 그런데 나의 판단: **지금은 JS 유지 + BigInt 보완**

전환하지 않는 이유 (조사 결과를 뒤집는 게 아니라, "정확성"과 "1인이 지금 굴릴 수 있는가"를 함께 봄):

1. **급소는 언어가 아니라 금액 타입이다.** BigInt로 원단위 정수를 강제하면 JS에서도 부동소수 오차는 **원천 차단**된다. Python으로 가는 이득의 대부분을 언어 전환 없이 얻는다.
2. **엔진이 이미 있고, 테스트 27개가 교과서 정답과 원단위 일치**한다. 검증된 자산을 버리는 비용이 실재한다(사용자가 "재사용 무시하라" 했지만, 그건 조사 가중치용 지시지 멀쩡한 코드를 버리라는 뜻은 아니라고 판단).
3. **LLM 파이프라인 궁합은 무승부.** Claude Agent SDK는 Python·TS 공식 동등. 1단계 분개 AI를 붙일 때 JS라고 불리하지 않다.

**단, JS 유지의 대가를 정직히 기록한다** (BE 조사가 경고한 것):
- BigInt는 정수 전용이라 세율 곱셈마다 스케일링을 **직접 관리**해야 함 → 실수 여지
- 이 규율(금액은 BigInt만, 나눗셈은 decimal.js 경유)을 **린트·타입 래퍼로 강제**하지 않으면 언젠가 `number`가 섞여 든다
- 즉 "언어가 공짜로 줄 안전장치를 컨벤션으로 재구현하는 지속 비용"을 진다

→ **재검토 트리거**: 만약 (a) 금액 규율이 자꾸 깨지거나 (b) 1단계 분개 AI를 Python 생태계(LangGraph 등)로 크게 키우게 되면, 그때 Python 전환을 다시 저울질한다. 지금은 아니다.

### 지금 할 보완책 (우선순위 순)

1. **금액을 원 단위 `BigInt`로 전환.** `type Won = bigint` 같은 래퍼로 `number`와 안 섞이게.
2. **나눗셈·세율 곱셈은 decimal.js 경유** → 필드별 명시적 절사/반올림 → 다시 BigInt 확정.
3. 이 경계를 지키는 **린트 규칙** 또는 최소한 테스트로 강제.

## 3. DB — SQLite (DB 조사)

### "행 수"가 아니라 "정확성"이 DB를 요구한다

1법인·연1회·거래 수백~수천 건은 행 수로는 CSV로 버틸 크기다. **그런데 세 가지가 이미 DB를 요구**한다:
1. **참조 무결성** — 전표 ↔ 계정과목 FK. CSV는 강제 못 함.
2. **연도 간 원자적 이월** — 유보 잔액·이월결손금은 전기 데이터가 당기 입력. "당기 저장 + 차기 이월 갱신"이 all-or-nothing이어야 하는데 파일은 반쪽 상태가 남을 수 있음.
3. **감사 추적** — "이 숫자가 어느 전표에서 나왔나"를 조인으로 추적. CSV는 사실상 불가.

이 셋은 과잉이 아니라 **"정확성"과 정확히 겹친다.** 반면 PostgreSQL은 1인 로컬엔 과함(서버·계정·백업 별도).

### ★ SQLite의 함정 — DECIMAL을 믿지 마라

SQLite는 동적 타입이라 `DECIMAL(10,2)`로 선언해도 내부적으로 INTEGER나 **REAL(부동소수)로 저장**한다.
→ **금액은 반드시 `INTEGER`(원 단위)로 저장.** 컬럼명 `NUMERIC`만 믿으면 오차가 스며든다.
→ `better-sqlite3`의 `defaultSafeIntegers(true)`(BigInt 모드)로 2^53 초과 정수 안전 처리.

### 이월 데이터 모델 (표준 패턴)

`tax_carryover(법인id, 항목, 사업연도, 기초잔액, 당기증감, 기말잔액, 산출근거_FK)`.
**기말잔액 → 다음 연도 기초잔액으로 복사하는 명시적 "이월 실행" 단계**를 둔다. 매번 처음부터 재계산하면 과거 신고서와 어긋날 위험.

감사 추적: 계산 결과에 **원본 입력(전표/거래 ID) FK**를 남기고, UPDATE 대신 append + "최종본" 플래그(불변 로그).

### 개인정보 (DB 조사)

- **주민번호는 규모 무관 항상 암호화 의무** (개인정보 안전성 확보조치 기준, 위반 시 3천만원 이하 과태료).
- 실무 권고: **원본 주민번호를 아예 저장하지 말고 마스킹 값만** → 암호화 의무 자체를 회피. (이 프로젝트의 마스킹 규칙과 일치)
- 원본이 꼭 필요하면 그 컬럼만 SQLCipher 또는 AES-256-GCM + 키는 `.env`(git 제외).

### 지금 vs 나중

- **지금**: CSV → SQLite 스키마 설계(계정과목·전표·이월 최소 3테이블), 금액 컬럼 전부 INTEGER, 이월 명시 컬럼화. **CSV는 은행 원본 import 포맷으로만 남김.**
- **나중**: ORM(Drizzle) 도입 / SQLCipher 파일 암호화(마스킹만으로 부족해질 때) / PostgreSQL·DuckDB(다법인·대량 정산 때)
- ⚠️ **미확인**: `better-sqlite3`의 Windows 네이티브 빌드 — `npm install` 시 프리빌트 바이너리 가용 여부 직접 확인 필요.

## 4. FE — 만들지 마라 (FE 조사)

### 전면 커스텀 UI는 과잉엔지니어링

"많은 숫자를 표에 입력"은 **스프레드시트가 이미 가장 잘하는 일.** 1인·로컬·감사추적 불필요라 커스텀 앱이 스프레드시트를 이길 지점(다중 사용자·연동)이 없다.

**단 하나 예외 — 판정 큐** ("이 통장 거래가 매출? 보증금?"). 분기 로직이 있는 상호작용이라 스프레드시트가 약하다. 여기만 최소 커스텀 가치가 있다.

### 단계적 트리거

| 시점 | 무엇을 | 신호 |
|---|---|---|
| **지금** | UI 안 만듦. CLI + 엑셀 템플릿(드롭다운 검증·SUMIF 대차체크). 판정 큐는 터미널 y/n | — |
| 1단계 | **읽기 전용 HTML 결과 뷰어** (프레임워크 없이 반나절, 인쇄 CSS) | CLI 텍스트를 눈으로 검증하기 불편해질 때 |
| 2단계 | **SvelteKit**으로 승인/반려 판정 UI | 판정할 거래가 수십~수백 건 될 때 |
| 3단계 | Tauri 데스크톱 패키징 | 남에게 실행파일로 넘겨야 할 때 (아마 불필요) |

### 만든다면 (확정 안 함)

- 프레임워크: 화면 소수면 순수 HTML+JS 유지. 늘면 **SvelteKit**(React보다 1인 생산성 우위).
- 데이터 그리드 필요 시 **AG Grid Community**(무료·상업제한 없음). Handsontable은 비상업 라이선스라 법인 실사용과 충돌 위험.
- 로컬 실행: 지금은 localhost + 브라우저. 데스크톱은 Tauri + sidecar(Node 엔진 바이너리 임베드) — Electron보다 번들·메모리·보안 우위.
- 출력: **SheetJS**(xlsx) + 브라우저 `@media print`. 별도 PDF 라이브러리 불필요. (단 명세서 서식이 복잡하면 PDF 양식에 값 오버레이가 나을 수 있음 — 실제 서식 봐야 판단)

## 5. 종합 실행 순서

```
[지금 · 정확성 급소]   금액을 BigInt(원단위)로 전환 + 나눗셈 decimal.js 경유
        ↓
[곧 · 무결성]          CSV → SQLite (금액 INTEGER, 이월 테이블, 감사 FK)
        ↓
[유지]                 BE는 JS 유지. Python 전환은 트리거(§2) 걸릴 때 재검토
        ↓
[안 함]                FE 커스텀 UI. CLI+엑셀로 충분. 판정 큐만 나중에
```

**가장 값싸고 효과 큰 한 수**: BigInt 금액 전환. 언어·DB·FE를 안 바꾸고도 이 프로젝트의 진짜 리스크(원단위 오차)를 잡는다.

## 6. 확실히 못 정한 것

- 국세청/홈택스의 **필드별 절사·반올림 규칙 공식 문서** 없음 → 종이 보고서에서 역산해야 함 (재현 검증할 때 자연히 드러남)
- `better-sqlite3` Windows 빌드 가용성 (설치해봐야 앎)
- Python 전환의 실제 손익분기 — 1단계 분개 AI 규모가 정해져야 판단 가능
- 명세서 인쇄 서식 복잡도 — 실제 종이책 봐야 `@media print` vs PDF 오버레이 결정
